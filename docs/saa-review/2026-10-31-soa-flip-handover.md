## 작업 루틴

1. 검수자가 터미널에서 실행 — **레포 루트에서** `node flutter_app/tool/review.mjs flip soa <taskId>`
   (사용자 터미널 cwd는 `flutter_app`이 아니라 레포 루트다. `review.mjs`가 `APP_DIR`을 `import.meta.url`로 잡고 `flutter test`도 `cwd: APP_DIR`로 돌려 **cwd와 무관**하다.)
2. AI가 검증 — `git branch --show-current` 확인 → **"verified 외 변경 줄"** 계수(정상이면 `content_index.dart` questionCount 1줄 + `soa_questions_test.dart` 허용 목록 1줄뿐)
3. **전체 스위트를 따로 돌린다** — `flip`은 `CERTS[soa].tests` 두 파일만 돌린다. 기준선 **2,583** · `flutter analyze` 0건
4. Task별 독립 커밋 → 적당한 지점에 `develop` PR
5. 릴리스는 배포 전 대조군(라이브 md5 vs git blob) → `main` PR → Pages `headSha` 추적 → 라이브 검증

**flip은 사람 전용이다.** AI는 `verified: true`를 쓰지 않고 `flip`을 실행하지 않는다(로컬 실험으로도).

## 2026-10-31에 실측한 함정

- ⚠️ **릴리스·머지 직후 다음 작업 브랜치를 바로 끊어 둔다.** HEAD가 `develop`에 남아 있어 검수자의 flip이 `develop`에서 실행된 사고가 있었다. 커밋 전 발견해 `git checkout -b`로 **stash 없이** 복구했다(새 브랜치는 같은 커밋에서 끊기므로 미커밋 변경이 따라온다). `develop` 직접 커밋은 금지다.
- ⚠️ **사람의 flip과 AI 편집이 동시에 일어난다.** `git add -A <파일들>`로 **경로를 명시**해야 커밋이 깨끗이 갈린다(`git show --stat`으로 확인). 쓰는 도중 측정했을 수 있으니 **정착 후 전체 스위트를 다시** 돌린다.
- ⚠️ **두 브랜치에 흩어진 flip의 cherry-pick은 반드시 충돌한다**(같은 `questionCount`·허용 목록 줄). 해소는 **양쪽의 합집합**이고 `<cert>_questions_test`가 "목록에 있는 Task는 verified ≥1, 없는 Task는 전 문항 드래프트"로 교차 검증한다. **문항 파일 무변경은 원본 커밋과 md5 대조**로 증명한다. 패치가 달라져 `git cherry`가 `+`로 나오므로 **브랜치 삭제 판정은 `git cherry`가 아니라 내용 대조**로 한다.
- ⚠️ **flip 재실행은 멱등**이다(`git status` 빈 출력). 같은 명령이 두 번 돌아도 커밋할 것이 생기지 않는다.
- ⚠️ **`gh pr merge`는 호출마다 달라진다** — 같은 세션에서 #300·#306은 통과, #304는 `[Production Deploy]` 차단(단독 호출도 동일). 과거 기록을 근거로 넘기지 말고 **매번 시도**하고, 실제 거부를 받으면 그때 검수자에게 명령을 넘긴다.
- ⚠️ **브랜치 삭제가 섞인 복합 명령은 `[Git Destructive]`로 막힌다** — `checkout`·`merge`·`branch -D`·`push --delete`를 한 줄에 묶지 말고 **삭제는 단건으로 따로** 호출한다(단건은 통과).
- ⚠️ **라이브 화면은 브라우저 캐시에 속는다.** 배포 전부터 열려 있던 탭이 옛 `main.dart.js`로 배포 전 수치를 보여 줬다(서버 번들 md5는 이미 바뀐 뒤였다). **탭을 닫고 캐시 버스팅 쿼리(`?cb=<날짜>`)로 새로 연다.** 화면 수치가 측정치와 어긋나면 먼저 캐시를 의심한다.
- ⚠️ `grep -c`가 0을 반환하면 exit 1이라 `&&` 체인이 끊긴다 — 0건 확인용 grep은 `;`로 잇는다.
- ⚠️ 자격증 상세의 약점 모의고사 `(0/3)`은 콘텐츠 게이트가 아니라 **3회 응시 규칙** 잠금이다. 게이트 개방 후의 정상 상태이지 결함이 아니다.

## locked 선언 — 이제 하나도 없다

다섯 자격증이 전부 열려 **locked 선언이 0건**이다. "지금 잠긴 cert"를 표본으로 쓰는 테스트를 **다시 만들면 안 된다**. 잠금 동작은 다음 셋으로만 검증한다 — 전부 실제 flip 상태와 무관해 앞으로 어떤 flip에도 묶이지 않는다:

1. 합성 빈 엔트리 — `SOA-C03·DEA-C01: 정책만으로는 열리지 않는다`
2. ANS-C01 — `정책 없는 cert는 fail closed`(가이드는 있고 정책은 없는 cert를 쓴다)
3. `debugContentIndexOverride` 주입(#286)

규율과 "새 자격증을 열 사람에게" 절차는 `flutter_app/test/content_index_test.dart` 주석에 적혀 있다.

### 새 자격증을 열 때

- **착수 전에 "깨질 단정" 전수 점검을 먼저 한다.** SOA는 미리 `content_index_test`의 locked 선언 1건으로 확정했고 실제로도 그대로였다. 몇 분 비용으로 flip 중단을 막는다. (`<cert>_v11_topics_test`류의 `"verified": true` 0건 단정이 남아 있으면 그것도 flip을 막는다 — SOA는 #285가 이미 제거해 뒀다.)
- **게이트 개방 flip은 커밋이 둘로 갈린다.** locked(`isFalse`)는 flip **전**에 지워야 하고(안 지우면 문항 파일을 다 쓴 뒤 레드, `--force`는 쓰기 **전** 구조 검사만 건너뛴다), 개방 단정(`isTrue`)은 flip **후**에만 통과한다. 순서는 ① 제거 → ② flip → ③ 개방 단정 포함 커밋이고, **가드 순증 0**이라 기준선이 2,583 → 2,582 → 2,583으로 복귀한다. 개방 단정 단독 실행이 "게이트가 실제로 열렸다"는 측정 그 자체다.
- 자격증별로 분리해 두면 한 자격증을 여는 PR이 다른 자격증 줄을 건드리지 않는다.
