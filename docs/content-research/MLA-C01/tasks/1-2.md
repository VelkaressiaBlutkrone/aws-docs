### 2.2 데이터 정리·변환 — 이상값·결측·중복·결합 (K1, SK1)

왜 정리하는가: 모델은 특성 값의 분포·범위에 민감하고 이상값은 정확도를 떨어뜨리며 학습 시간을 늘린다. 결측값은 ML 데이터셋에서 흔하다 〔S2〕.

| 작업 | SageMaker Data Wrangler (변환 그룹·옵션) | AWS Glue DataBrew (레시피 단계) | AWS Glue (Studio·PySpark) | 근거 |
|---|---|---|---|---|
| 이상값 탐지·처리 | **Handle outliers**(이상치 처리하기): 숫자 4종 Robust standard deviation / Standard deviation / Quantile / Min-Max numeric outliers(표준편차 수·분위수·임계값 지정) + 범주용 **Replace rare**(드문 범주를 지정 문자열로). 처리 방식(Fix method) Clip·Remove·Invalidate | 이상값 계열 5단계 FLAG_OUTLIERS, REMOVE_OUTLIERS, REPLACE_OUTLIERS, RESCALE_OUTLIERS_WITH_Z_SCORE, RESCALE_OUTLIERS_WITH_SKEW. 탐지 전략 Z_SCORE·MODIFIED_Z_SCORE·IQR, threshold 기본 3, 제거 방식 DELETE_ROWS 또는 CLEAR | 이번에 읽은 Glue Studio 변환 목록·PySpark 변환 목록에 이상값 전용 변환은 없음 → Filter·SQL·Derived column 등으로 구현 | 〔S2〕〔S100〕〔S20〕〔S31〕〔S32〕 |
| 결측값 대체 | **Handle missing values**(누락된 값 처리): Fill missing(지정한 값), Impute missing(숫자 평균·중앙값, 범주 최빈값, 새 열에 기록), Add indicator for missing(불리언 표시 열), Drop missing(행 삭제) | Missing 계열: FILL_WITH_AVERAGE·_CUSTOM·_EMPTY·_LAST_VALID·_MEDIAN(결측을 모든 값의 중앙값으로)·_MODE·_MOST_FREQUENT·_NULL·_SUM, REMOVE_MISSING, REPLACE_WITH_* 계열 | **FillMissingValues**(ML 모델이 대체값을 예측해 새 필드에 기록), DI 변환 FillWithMode, Drop Null Fields, Remove null rows | 〔S2〕〔S27〕〔S23〕〔S32〕〔S31〕〔S96〕 |
| 중복 제거 | Concatenate 의 'Remove duplicates after concatenation', 사용자 지정 변환 스니펫(`dropDuplicates`). 이전 Canvas 노코드 변환에는 Manage rows → Drop duplicate rows | DELETE_DUPLICATE_ROWS(이전 행과 완전 일치), REMOVE_DUPLICATES(선택 열 기준), FLAG_DUPLICATE_ROWS, FLAG_DUPLICATES_IN_COLUMN | **Drop Duplicates**(행 전체 또는 키), DI 변환 RemoveDuplicates·FlagDuplicateRows·FlagDuplicatesInColumn, **FindMatches**(공통 키 없는 유사 중복, ML) | 〔S2〕〔S5〕〔S21〕〔S22〕〔S27〕〔S32〕〔S31〕〔S34〕 |
| 결합(조인·합치기) | Join 7종(Left Outer, Left Anti, Left semi, Right Outer, Inner, Full Outer, Cartesian Cross), Concatenate(행 이어 붙이기) | JOIN 7종(INNER_JOIN, LEFT_JOIN, RIGHT_JOIN, OUTER_JOIN, LEFT_EXCLUDING_JOIN, RIGHT_EXCLUDING_JOIN, OUTER_EXCLUDING_JOIN), UNION(여러 데이터셋의 행을 하나로) | Join(inner·outer·left·right·left semi·left anti), Union(같은 스키마의 행 결합), mergeDynamicFrame(기본키 기준 병합, 스테이징이 덮어씀), Lookup(카탈로그 테이블에서 열 추가) | 〔S2〕〔S24〕〔S25〕〔S32〕〔S33〕 |

자주 틀리는 지점:
- Process numeric·Handle missing 은 한 번에 한 열에만 적용된다 〔S3〕.
- Impute missing 은 계산값(평균·중앙값·최빈값)으로 새 열을 채우고, 임의 문자열·상수로 채우려면 Fill missing 을 쓴다 〔S2〕.
- Glue Drop Null Fields 는 모든 값이 null 인 열을 제거한다. 빈 문자열·문자열 "null"·-1·0 같은 자리표시자는 자동으로 null 로 인식하지 못한다 〔S96〕.
- 정확 일치 중복은 DELETE_DUPLICATE_ROWS·REMOVE_DUPLICATES·Drop Duplicates 로, 철자·표기가 다른 유사 중복은 FindMatches 로 푼다 〔S21〕〔S22〕〔S32〕〔S34〕. REMOVE_DUPLICATES 는 행 전체가 아니라 선택한 열의 중복 값 기준이다 〔S22〕.
- 이상값 탐지 통계는 단계를 정의할 때 Data Wrangler 가 보유한 데이터로 계산되고, 잡 실행에도 같은 통계가 쓰인다 〔S2〕.

> 🧠 원리: Spark DataFrame 은 스키마가 먼저 필요하고 스키마 추론에 데이터를 한 번 더 훑어야 하며, 같은 필드의 타입이 레코드마다 다르면 string 으로 보고하기 쉽다. Glue DynamicFrame 은 레코드가 자기 기술적(self-describing)이라 초기 스키마 없이 읽고, 불일치는 choice 타입으로 표현했다가 `resolveChoice` 로 해소한다 〔S33〕. 지저분한 데이터 ETL 에 DynamicFrame 을 쓰는 이유가 문서 설명이다.

### 2.3 특성 추출·변환 — 스케일링·표준화·정규화·비닝·로그 변환·특성 분할 (K2)

특성 공학은 특성 생성(one-hot, 비닝, 분할, 계산된 특성), 변환·대체(비선형 변환·비닝, 결측 대체), 추출(PCA·ICA·LDA 같은 차원 축소), 선택으로 구성된다 〔S89〕.

| 기법 | 정의(문서 근거) | Data Wrangler | DataBrew | 근거 |
|---|---|---|---|---|
| 스케일링 일반 | 특성 값의 범위를 맞춰 한 특성이 모델을 지배하지 않게 함 | Process numeric(숫자 처리) 스케일러 4종, Spark 라이브러리 기반 | SCALE 의 strategy 4종 | 〔S2〕〔S13〕〔S90〕 |
| 정규화(Min-Max) | 값을 지정한 범위로 변환 | Min Max Scaler | MIN_MAX(0~1), SCALE_BETWEEN(지정한 두 값 사이) | 〔S2〕〔S13〕 |
| 표준화(Z-score) | 평균 0·표준편차 1 로 변환 | Standard Scaler(평균을 빼고 단위 분산으로) | Z_SCORE(문서가 이상값 처리에 가장 적합하다고 명시), MEAN_NORMALIZATION | 〔S2〕〔S13〕 |
| 이상값에 강건한 스케일 | 이상값에 덜 흔들리는 통계 사용 | Robust Scaler | Z_SCORE, RESCALE_OUTLIERS_WITH_Z_SCORE(이상값 처리에 권장) | 〔S2〕〔S13〕〔S101〕 |
| 최대 절대값 스케일 | 각 값을 최대 절대값으로 나눔 | Max Absolute Scaler | 같은 이름의 단계 없음 | 〔S2〕〔S13〕 |
| 비닝(binning) | 숫자 변수를 구간(범주)으로 변환하는 비선형 변환 | 변환 그룹 목록에 binning 없음 → Custom formula·사용자 지정 변환 | BUCKETIZATION(콘솔명 Binning, splits 또는 percentage) | 〔S89〕〔S14〕〔S2〕 |
| 로그 변환 | 분포의 모양·왜도를 바꾸는 변환 | Custom formula(Spark SQL)·사용자 지정 변환. 이전 Canvas 노코드 함수 Log(밑 10)·Ln | SKEWNESS 의 LOG(밑은 value 파라미터), ROOT, SQUARE | 〔S15〕〔S2〕〔S5〕 |
| 특성 분할 | 한 열을 여러 특성으로 쪼갬 | Featurize date/time(Output=Columns 면 연·월·일 열 생성), Search and edit 의 Split string by delimiter, Manage vectors 의 Flatten | SPLIT_COLUMN_BETWEEN_DELIMITER·_BETWEEN_POSITIONS·_FROM_END·_FROM_START·_MULTIPLE_DELIMITER·_SINGLE_DELIMITER·_WITH_INTERVALS | 〔S2〕〔S26〕〔S89〕 |
| 차원 축소 | 여러 특성을 소수의 주성분으로 | Reduce dimensionality(PCA): 성분 수 직접 지정 또는 분산 임계 비율 중 하나만 지정 | — | 〔S2〕〔S89〕 |

- **정규화 vs 표준화 용어**: DataBrew SCALE 은 "scales or normalizes" 라 서술하고 〔S13〕, Linear Learner 문서는 "Normalization, or feature scaling" 이라 부르지만 구현은 평균을 0, 표준편차를 1 로 옮기는 방식이다 〔S90〕. 'normalization' 이 min-max 인지 z-score 인지는 서비스 정의를 따라 판단한다.
- **스케일·분포에 민감한 알고리즘 — 공식 근거가 있는 것만**: (1) Linear Learner 는 정규화 옵션(`normalize_data`, `normalize_label`)이 있고 목적은 한 특성의 가중치가 모델을 지배하지 않게 하는 것이며, 회귀는 특성·레이블 모두 기본 켜짐, 이진 분류는 특성만 켜짐 〔S90〕. (2) Data Wrangler 문서: 모델은 특성 값의 분포·범위에 민감하고 이상값은 정확도 저하·학습 시간 증가를 부른다 〔S2〕. (3) Featurize date/time: 선형 모델·딥 네트워크에는 cyclic, 트리 기반 알고리즘에는 ordinal 임베딩 모드를 권장 〔S2〕. 그 밖의 알고리즘(k-NN, k-means 등)은 이번에 읽은 공식 문서에 스케일 민감성 서술이 없어 쓰지 않는다 → §9.
- **Featurize date/time 입력 처리**: 입력은 날짜 문자열 또는 Unix 타임스탬프다. 형식을 지정하고 추론을 끄면 가장 빠르고, 형식 추론을 켜면 첫 형식을 열 전체의 형식으로 가정해 다른 형식은 NaN 이 되며, 형식 지정도 추론도 안 하면 가장 견고하지만 훨씬 느리다 〔S2〕.
- **시계열 특성(Transform time series)**: Group by, Resample, Handle missing, Validate timestamp, Standardize length, Extract features, Lagged features, Datetime range, Rolling window 9종 〔S2〕.

> 🧠 원리: Data Wrangler 의 스케일러 4종은 Spark 라이브러리의 같은 이름 스케일러(StandardScaler·RobustScaler·MinMaxScaler·MaxAbsScaler)로 정의되며 문서가 각 항목에 Spark 문서 링크를 단다. 그중 Robust Scaler 는 "이상값에 강건한 통계"를 쓴다고 서술된다 〔S2〕. DataBrew 는 Z_SCORE 를 "이상값 처리에 가장 적합"으로 서술한다 〔S13〕.

### 2.4 인코딩 — 원-핫·서수(레이블)·유사성·이진·토큰화 (K3)

범주형 데이터는 순서가 없는 nominal 과 내재 순서가 있는 ordinal 로 나뉘며, 인코딩은 범주를 숫자 표현으로 만드는 과정이다 〔S2〕.

| 선택지 | 언제 | 핵심 제약·옵션 | 함께 헷갈리는 것 | 근거 |
|---|---|---|---|---|
| Data Wrangler **One-hot encode**(원-핫 인코딩) | 순서 없는(nominal) 범주를 0/1 벡터·열로 | Output style Vector(희소 벡터 한 열) 또는 Columns(범주별 열), Drop last category, Invalid handling strategy(Skip·Keep·Error), Is input ordinal encoded | Ordinal encode, DataBrew ONE_HOT_ENCODING | 〔S2〕 |
| Data Wrangler **Ordinal encode**(서수 인코딩) | 순서가 있는(ordinal) 범주를 0부터 범주 수 사이의 정수로 | Invalid handling strategy: Skip·Keep(마지막 범주로 유지)·Error·Replace with NaN(알고리즘이 결측을 처리할 때 권장) | 레이블 인코딩(일반 개념), DataBrew CATEGORICAL_MAPPING | 〔S2〕 |
| Data Wrangler **Similarity encode**(유사성 인코딩) | 범주 변수가 매우 많거나 잡음(오탈자)이 많은 데이터 | 3-gram 토큰 → min-hash 임베딩, 비슷한 문자열은 비슷한 값의 벡터, 저차원·범주 수에 확장·잡음에 강함, Target dimension 기본 30. 문서는 one-hot 보다 범용적이라고 서술 | One-hot(범주 수만큼 차원), Replace rare | 〔S2〕 |
| DataBrew **ONE_HOT_ENCODING** | 범주를 n개 숫자 열로(n=고유값 수) | 대상 열 고유값 최대 10개 | Data Wrangler One-hot encode | 〔S16〕 |
| DataBrew **CATEGORICAL_MAPPING** | 범주를 숫자·다른 값으로 매핑(순서형 포함) | categoryMap, keepOthers, other, deleteOtherRows, mapType | One-hot | 〔S17〕 |
| **Binary encoding**(이진 인코딩) | 가이드 예시 항목 | ⚠️ 이번에 조사한 AWS 도구 문서(Data Wrangler 인코딩 3종, DataBrew 데이터 과학 단계 7종)에 동명 변환·정의가 없음 → §9 | One-hot | 〔S2〕〔S13〕 |
| **Label encoding**(레이블 인코딩) | 가이드 예시 항목 | AWS 문서에 같은 이름의 변환은 없고 가장 가까운 것이 Ordinal encode·CATEGORICAL_MAPPING(공식 대응표 없음) → §9 | Ordinal encode | 〔S2〕〔S17〕 |

텍스트 토큰화·벡터화:

| 도구 | 변환 | 핵심 옵션 | 근거 |
|---|---|---|---|
| Data Wrangler | Featurize text → **Vectorize**(벡터화) | Tokenizer: Standard(공백 기준 분리 + 소문자) 또는 Custom(최소 토큰 길이, regex 로 gap 분리 여부, regex 패턴, 소문자 변환). Vectorizer: Count(최소 term·문서 빈도, 최대 문서 빈도, 최대 어휘 크기, Binary outputs) 또는 Hashing(계산이 더 빠름, 특성 수 지정). Apply IDF 로 TF-IDF. Output format: Vector 또는 Flattened(Count 벡터라이저에서만) | 〔S2〕 |
| Data Wrangler | Featurize text → **Character statistics** | 단어 수·문자 수·대문자·소문자·숫자·특수문자 비율을 새 열로 | 〔S2〕 |
| DataBrew | **TOKENIZATION**(토큰화) | delimiter, expandContractions(축약 확장), stemmingMode(PORTER 또는 LANCASTER), stopWordRemovalMode, customStopWords | 〔S18〕 |

- 새 범주 주의: Data Wrangler 인코더는 단계를 정의한 시점의 범주에 대해서만 인코딩을 만든다. 이후 .flow 파일로 갱신된 데이터를 처리하거나 샘플링으로 일부 범주가 빠지면 새 범주는 누락값으로 취급되어 Invalid handling strategy 가 적용된다 〔S2〕.
- DataBrew 의 이진화(BINARIZATION)는 숫자 열을 임계값과 비교해 0 또는 1 로 만드는 별도 단계다(범주 인코딩이 아님) 〔S19〕.

- DataBrew: 프로젝트(데이터 연결·샘플 미리보기) → 레시피(변환 단계 저장·게시) → 레시피 잡 → S3 〔S10〕〔S11〕.
- Glue: 작업(job)을 시각적·스크립트로 작성 → 실행. 스트리밍은 별도 스트리밍 ETL 작업 〔S30〕〔S35〕.
- EMR: 클러스터(또는 Serverless 애플리케이션)에 Spark 작업 제출 〔S37〕〔S38〕.
- Processing: CreateProcessingJob(API·CLI·SDK)으로 스크립트·컨테이너 실행 〔S40〕.

고르는 순서: 코드 여부 → 실행 기반(서버리스·클러스터·관리형 컨테이너) → 입출력·연동(Feature Store·Pipelines·Data Catalog·S3) → 규모(5 GB 초과 Data Wrangler 권장, 레시피 100변환 한도).

DataBrew 레시피 단계(recipe step) 범주(콘솔 변환 분류): Basic column(Filter, Column), Data cleaning(Format, Clean, Extract), Data quality(Missing, Invalid, Duplicates, Outliers), PII(마스킹·대체·암호화·행 섞기), Column structure(Split, Merge, Create), Column formatting(소수 자릿수·천 단위 구분·숫자 축약), Data structure(Nest-Unnest, Pivot, Group, Join, Union), Data science(Text, Scale, Mapping, Encode), Functions(Mathematical, Aggregate, Text, Date and time, Window, Web, Other) 〔S12〕. 레시피 단계는 API 에서 recipe action 이라 부르고, 레시피는 게시(publish)한 버전을 레시피 잡에서 실행한다 〔S11〕.

| Firehose 레코드 포맷 변환 | JSON 을 Parquet·ORC 로 변환해 S3 에 저장 | 역직렬화기(Apache Hive JSON SerDe 또는 OpenX JSON SerDe)·Glue 데이터 카탈로그 스키마·직렬화기(ORC·Parquet SerDe) 3요소 필요. 변환을 켜면 S3 만 목적지로 쓸 수 있다(콘솔 도움말). JSON 이 아닌 입력(CSV 등)은 Lambda 로 먼저 JSON 변환 | Lambda 변환(내용 변환) | 〔S45〕〔S102〕 |
| Lambda 이벤트 소스 매핑 | Kinesis·MSK 등 스트림을 Lambda 가 직접 소비 | BatchSize 기본 100(SQS 는 10), 배칭 윈도 0–300초(스트림 기본 0), ParallelizationFactor 기본 1(Kinesis·DynamoDB Streams 전용), 동기 호출 6 MB | Firehose 의 Lambda 변환 | 〔S47〕 |
| Glue 스트리밍 ETL | 서버리스 Spark Structured Streaming 으로 Kinesis Data Streams·Kafka·MSK 를 소비해 S3·JDBC 에 적재 | 기본 100초 윈도, 체크포인트로 위치 추적(작업 북마크 미지원), 타임아웃 7일 미만, 시간당 과금, 스키마 감지 시 스트리밍 조인 불가 | EMR 의 Spark 스트리밍, Flink | 〔S35〕〔S36〕 |
| EMR 의 Spark 구조적 스트리밍 | 기존 Spark 코드·클러스터 제어 | Kinesis Data Streams 커넥터가 EMR 7.1.0 이상 릴리스 이미지에 내장, GetRecords(공유 처리량)·SubscribeToShard(향상된 팬아웃) 지원 | Glue 스트리밍 | 〔S39〕 |
| Managed Service for Apache Flink | 장기 실행 스트리밍 ETL·연속 애플리케이션, 상태 세밀 제어·사용자 지정 타이머(DataStream API) | Java·Scala·Python·SQL. 프로비저닝·AZ 장애 조치·병렬 계산·자동 확장·체크포인트/스냅샷 백업을 서비스가 처리. 임시 탐색·대화형 쿼리는 Studio 노트북 | Kinesis Data Analytics(구명칭) | 〔S46〕〔S49〕 |

- 선택 기준 요약: 전송 경로에서 레코드 단위 가벼운 변환 → Firehose + Lambda. 형식 변환만 → Firehose 레코드 포맷 변환. 스트림을 코드로 직접 소비 → Lambda 이벤트 소스 매핑. Spark SQL·DataFrame 윈도 집계 → Glue 스트리밍(서버리스) 또는 EMR(클러스터 제어). 상태 유지·사용자 지정 타이머·늦은 이벤트 처리 → Flink 〔S46〕.
- Firehose 는 변환된 데이터를 Lambda 에서 돌려받아 목적지 버퍼 크기 또는 간격에 먼저 도달할 때 목적지로 보낸다 〔S41〕.
- 특성 저장소로 스트리밍 특성을 넣을 때는 동기 호출 `PutRecord` 를 쓴다 〔S50〕〔S66〕 → 2.8.
- 구명칭: Kinesis Data Firehose → Amazon Data Firehose 〔S48〕, Kinesis Data Analytics → Managed Service for Apache Flink 〔S49〕.

> 🧠 원리: Firehose 의 Lambda 변환은 레코드를 하나씩 호출하지 않고 버퍼링한 배치를 Lambda 동기 호출 방식으로 호출한다. 문서는 요청으로 보내는 버퍼 크기가 6 MB 이하여야 하고 함수 응답도 6 MB 를 넘지 않아야 한다고 명시하며, Lambda 호출이 5분을 넘기면 타임아웃 오류가 난다고 설명한다 〔S41〕. Glue 스트리밍은 Spark Structured Streaming 위에 만들어져 작업 북마크 대신 체크포인트로 읽은 위치를 추적하므로 멈췄다 재시작해도 이어서 처리하고, 다시 처리하려면 체크포인트 폴더를 지운다 〔S35〕〔S36〕.

### 2.8 SageMaker Feature Store — 특성 생성·관리 관점 (SK2)

Feature Store 는 특성의 생성·저장·공유·관리를 단순화한다. 특성과 메타데이터는 **특성 그룹(feature group)** 에 저장되고, 특성 그룹은 변경 가능해 만든 뒤 스키마를 발전시킬 수 있다. 특성 처리 코드를 일관되게 적용·수집하면 학습 중 성능과 서빙 중 성능의 차이(training-serving skew)가 줄어든다 〔S50〕. 한국어 공식 표기는 특성 저장소·특성 그룹·온라인/오프라인 저장소다 〔S95〕. SageMaker AI 기능 묶음 신규 고객 중단 공지의 대상이 아니다 〔S85〕. 특성 그룹 이름·설명·태그에는 PII·기밀 정보를 넣지 않는다 〔S50〕.

**필수 요건**

| 요소 | 요건 | 근거 |
|---|---|---|
| 특성 그룹 | 이름은 AWS 리전·계정 안에서 고유. 온라인 설정과 오프라인 설정 중 최소 하나 필요 | 〔S50〕〔S55〕 |
| 특성 정의 | 이름 + 타입(Integral, Fractional, String). 그룹당 최대 2,500개. 이름에 is_deleted·write_time·api_invocation_time 사용 불가 | 〔S55〕 |
| 레코드 식별자 | 모든 특성 그룹에 필수(`RecordIdentifierFeatureName`), 특성 정의 중 하나. 식별자 값별 최신 레코드만 온라인에 저장 | 〔S51〕〔S55〕 |
| 이벤트 시간 | 모든 레코드에 필수(`EventTimeFeatureName`). Fractional 은 초 단위 Unix 타임스탬프, String 은 ISO-8601. Iceberg 오프라인 형식이면 String 이어야 함 | 〔S51〕〔S55〕〔S53〕 |
| 레코드 | 레코드 식별자 값과 이벤트 시간의 조합이 레코드를 고유하게 식별 | 〔S51〕 |

**온라인 vs 오프라인** (상세 비교는 §4 짝 4): 온라인 스토어는 식별자별 최신 레코드만 두고 낮은 밀리초 읽기와 높은 쓰기 처리량을 겨냥해 실시간 예측에 쓰며 `GetRecord` 로 최신 레코드를 조회한다. 오프라인 스토어는 모든 레코드를 이력 데이터베이스로 보관해 탐색·학습·배치 추론에 쓰고 sub-second 지연이 필요 없을 때 쓴다. 둘을 함께 켜면 학습·서빙 데이터 불일치를 막도록 동기화된다 〔S50〕〔S51〕〔S52〕〔S53〕. 스트리밍 소스(Kinesis·MSK)에서 뽑은 특성을 온라인 스토어에 바로 넣을 수 있고, 서로 다른 두 특성 그룹을 클라이언트 애플리케이션에서 각각 조회해 실시간 추론용 조인을 할 수 있다 〔S50〕.

**온라인 스토어 유형**

| 선택지 | 언제 | 핵심 제약 | 함께 헷갈리는 것 | 근거 |
|---|---|---|---|---|
| Standard (기본) | 일반 온라인 서빙 | 관리형 저지연 저장소, 오프라인과 병행 가능 | Standard_V2 | 〔S52〕 |
| Standard_V2 | 일부 특성만 자주 갱신 | UpdateRecord 로 개별 특성 부분 갱신, 이벤트 시간으로 순서 어긋난 쓰기 거부. Standard 에서 마이그레이션은 단방향. 가이드 범위 여부는 §9 | PutRecord(전체 덮어쓰기) | 〔S52〕〔S57〕 |
| InMemory | 초저지연 대규모 실시간 조회 | ElastiCache(Redis OSS) 기반, list·set·vector 컬렉션 타입, 기본 최대 50 GiB, 온라인 전용(오프라인 복제 없음), 고객 관리형 KMS 키 미지원, 생성에 약 10~15분, 자동 확장 중 쓰로틀링·지연 증가 가능, PrivateLink 로 네트워크 지연 감소 | Standard | 〔S52〕〔S55〕 |

**오프라인 스토어**: 고객 계정의 S3 에 이벤트 시간 기반 접두사로 저장되는 append-only 저장소이며 파일 형식은 Parquet 뿐이다 〔S50〕〔S54〕. 테이블 형식은 Glue(기본)와 Apache Iceberg(문서가 권장으로 표기; 작은 파일 압축으로 쿼리 가속)이고, Glue 형식은 이벤트 시간 기준 시간 단위 파티션, Iceberg 는 일 단위 파티션이며 구성할 수 없다 〔S53〕〔S54〕〔S56〕. 특성 그룹 생성 시 AWS Glue 데이터 카탈로그가 기본으로 자동 구성되어 Athena 로 쿼리한다 〔S62〕. 레코드에는 `api_invocation_time`, `write_time`, `is_deleted` 필드가 덧붙는다 〔S54〕.

**TTL**: `ExpiresAt = EventTime + TtlDuration`. 특성 그룹 수준(기본값) 또는 레코드 수준(`PutRecord`, 우선)으로 지정하고 Unit 은 Seconds·Minutes·Hours·Days·Weeks, Value 는 양의 정수다. 미지정이면 null 이라 덮어쓰기 전까지 유지된다. 만료 레코드는 온라인 스토어에서 하드 삭제되고 삭제 레코드는 오프라인에 추가된다. 온라인 스토어 없이 TTL 을 쓰면 400 오류다. 삭제는 백그라운드로 처리되어 문서 표현상 며칠 걸린다. `GetRecord`·`BatchGetRecord` 에서 `ExpirationTimeResponse` 를 Enabled 로 하면 `ExpiresAt` 를 볼 수 있다 〔S61〕. 명시적 삭제는 `DeleteRecord`: SoftDelete(기본, 특성 값을 null 로 두고 조회 불가)와 HardDelete 모두 오프라인에 삭제 마커를 추가한다 〔S60〕.

**수집·조회 API**

| API·경로 | 역할 | 핵심 동작·제약 | 근거 |
|---|---|---|---|
| `PutRecord` | 수집(쓰기) | 동기 호출. Record 는 전체 덮어쓰기(부분 갱신은 UpdateRecord). `TargetStores` 로 OnlineStore·OfflineStore 선택(기본은 그룹의 모든 스토어). 더 이른 EventTime 레코드는 이력이라 오프라인에만 기록. `TtlDuration` 으로 레코드 TTL | 〔S57〕 |
| `GetRecord` | 온라인 조회 | 최신 레코드만, 없으면 빈 결과. `FeatureNames` 로 일부 특성만 | 〔S58〕 |
| `BatchGetRecord` | 온라인 배치 조회 | 여러 특성 그룹·레코드 식별자를 한 번에, Identifiers 최대 100개 | 〔S59〕 |
| SDK `ingest` | 데이터프레임 배치 수집 | PutRecord 위에서 동작, 클라이언트 병렬도 조절 | 〔S68〕〔S69〕 |
| Spark 커넥터 | Spark DataFrame 배치 수집(EMR·Glue 작업·Processing 작업·노트북) | 기본은 온라인(PutRecord) + 오프라인, `target_stores` 로 오프라인 직접 또는 온라인만 | 〔S67〕 |
| Data Wrangler 내보내기·Feature Processor | 시각적 특성 설계 → 특성 그룹 / 변환 함수 선언 후 Spark 실행·수집 | 노트북(Processing 잡)·대상 노드 / `@feature_processor` | 〔S66〕〔S8〕〔S70〕 |

**시점 정확(point-in-time) 조인·시간 여행**: 오프라인 스토어는 append-only 이고 이벤트 시간이 있어 과거 시점의 특성 값을 재현할 수 있다. SDK `create_dataset()` 은 여러 특성 그룹·pandas DataFrame 을 조인하며 `with_feature_group`(기본 inner join), `with_event_time_range`, `as_of`, 시점 정확 조인, `include_duplicated_records`·`include_deleted_records` 같은 보조 메서드를 제공하고 기본값은 삭제·중복 레코드 제외다 〔S62〕. 제품 페이지는 오프라인 API 의 point-in-time 쿼리가 과거 시점의 특성 상태를 조회해 미래 데이터 유입(feature leakage)을 막는다고 설명한다 〔S63〕. Athena 샘플 쿼리와 Glue 크롤러 스케줄로 카탈로그를 최신으로 유지할 수 있다 〔S62〕.

**교차 계정 공유**: AWS RAM 으로 공유한다. 발견 가능성(discoverability)은 특성 그룹 카탈로그를 공유해 계정 단위로 전부 보이게 하고 〔S65〕, 접근 권한은 특성 그룹 리소스 단위로 read-only·read-write·admin 을 부여한다. 접근 권한만 주면 검색은 안 되고 발견 가능성은 따로 부여해야 하며, 온라인·오프라인 특성 그룹의 공유 방법이 다르다 〔S64〕. 오프라인 데이터의 세밀한 접근 제어는 AWS Lake Formation 과 함께 구현할 수 있다 〔S63〕.

> 🧠 원리: 온라인 스토어는 같은 식별자에서 가장 늦은 이벤트 시간의 레코드만 남기고, 오프라인 스토어는 모든 레코드를 쌓는다. 그래서 더 이른 이벤트 시간의 `PutRecord` 는 이력으로 오프라인에만 기록된다 〔S57〕〔S51〕. 같은 식별자·이벤트 시간의 중복 레코드도 오프라인에 있을 수 있어 `create_dataset` 은 기본으로 중복·삭제 레코드를 제외한다 〔S62〕. 이 이력 위에서 이벤트 시간을 기준으로 시점 정확 조인을 한다 〔S63〕.

| 내장 작업 유형 | 이미지(경계 상자, 이미지 분류 단일·다중 레이블, 의미 분할, 레이블 검증·조정), 텍스트(개체명 인식, 텍스트 분류 단일·다중 레이블), 비디오·비디오 프레임(분류, 프레임 객체 감지, 프레임 객체 추적), 3D 점군(객체 감지, 객체 추적, 의미 분할). 비디오 프레임·3D 점군 유형에는 조정(adjustment) 유형이 있음. 자체 UI·도구로 사용자 지정 레이블링 워크플로도 가능 | 〔S76〕〔S71〕 |
| 작업 인력 3종 | Mechanical Turk(전 세계 50만 명 이상 독립 계약자), 비공개(자체 직원·계약자, Amazon Cognito 또는 자체 OIDC IdP 로 관리), 공급업체(AWS Marketplace 의 레이블링 전문 업체) | 〔S71〕〔S79〕 |
| 주석 통합 | 여러 작업자의 주석을 하나의 레이블로 합침. 콘솔 기본 작업자 수는 텍스트 분류 3, 이미지 분류 3, 경계 상자 5, 의미 분할 3, 개체명 인식 3(API 는 `NumberOfHumanWorkersPerDataObject`). 다중 클래스는 기댓값 최대화(EM) 변형과 베이지안 추론, 경계 상자는 Jaccard 지수(IoU)가 비슷한 상자끼리 평균, 의미 분할은 픽셀 투표 + 평활화, NER 은 Jaccard 유사도로 군집화 | 〔S75〕 |
| 자동 데이터 레이블링 | 능동 학습으로 사람이 레이블링할 데이터를 ML 이 골라 비용·시간 절감. 자세한 조건은 아래 | 〔S74〕 |
| 레이블 검증·조정 | 검증(label verification)은 기존 레이블의 정확성을 표시·평가하되 수정은 못 하고, 조정(label adjustment)은 이전 주석을 수정. 지원 유형: 경계 상자, 의미 분할, 3D 점군 3종, 비디오 프레임 객체 감지·추적 | 〔S77〕 |
| 체이닝·복제 | 체이닝은 이전 잡의 출력 매니페스트를 새 잡의 입력으로 써서 중단 잡 이어가기·자동 레이블링 전환·데이터 추가에 사용, 복제(cloning)는 이전 잡의 설정을 복사 | 〔S78〕 |
| 스트리밍 레이블링 잡 | 새 데이터 객체를 지속적으로 보내는 상시 잡. 수동 중지 또는 유휴가 길면 종료, SageMaker API 로만 지원, 자동 데이터 레이블링 불가 | 〔S72〕〔S74〕 |

**자동 데이터 레이블링 조건** (〔S74〕): 지원 작업 유형은 이미지 분류(단일 레이블)·의미 분할·객체 감지(경계 상자)·텍스트 분류(단일 레이블) 4종이며 사용자 지정 작업 유형과 스트리밍 잡은 불가. 최소 1,250개 객체, 최소 5,000개를 강하게 권장. 시작 시 무작위 표본을 사람에게 보내고 그중 10% 초과가 실패하면 잡이 실패한다. 이미지·텍스트 분류는 사람 레이블 대비 95% 이상 정확도를 목표로 신뢰도 임계값을 정하고(경계 상자·의미 분할은 평균 IoU 기준), SageMaker 학습·추론 비용이 든다. 사용 전에 모델을 미세 조정하거나 대표 표본으로 정확도를 평가하라고 권고한다.

**Mechanical Turk 인력 주의** (〔S80〕): 전 세계 인력으로 연중무휴 가용하며 문서 표현상 보통 가장 빠르게 처리된다. 빌링은 Ground Truth·A2I 청구에 포함되어 별도 MTurk 계정이 필요 없다. 기밀·개인·보호 건강 정보를 이 인력과 공유하지 않아야 하고, 입력 데이터에 PII 가 없음을 지정하지 않으면 Ground Truth 잡과 A2I 작업이 실패한다.

**Amazon A2I**: AI 서비스(Rekognition·Textract 등)나 사용자 지정 ML 모델의 저신뢰 예측 또는 무작위 표본 예측을 사람이 검토하도록 휴먼 검토 워크플로를 구축·관리한다. 콘텐츠 중재·문서 텍스트 추출용 내장 워크플로가 있고 자체 워크플로도 만들 수 있다. 사용 예는 Textract·Rekognition·Comprehend·Transcribe·Translate·표 형식 데이터·SageMaker 엔드포인트의 실시간 추론 검토다 〔S81〕. 작업 인력 옵션은 Ground Truth 와 같다 〔S79〕.

### 2.10 변환 파이프라인 안의 데이터 검증 (SK3 → Task 1.3 에서 상세)

Task 1.3 몫이므로 한 줄과 링크만 둔다.
- Data Wrangler: **Data Quality and Insights Report** 가 누락값·이상값 수, 타깃 누수·불균형 같은 문제를 알려 준다. 전체 데이터에 대해 만들면 SageMaker Processing 잡이 쓰인다 〔S9〕.
- DataBrew: 데이터 품질 규칙 세트(ruleset)를 프로파일 잡에 추가해 검증하고 검증 보고서를 얻는다 〔S28〕.
- Glue: PySpark 변환 목록에 `EvaluateDataQuality` 가 있다(상세는 1.3) 〔S31〕.
- Ground Truth: 레이블 검증·조정 잡으로 레이블 품질을 점검한다 〔S77〕.

### 패턴 2. 스트리밍 데이터 변환 경로 — Firehose+Lambda 제약, 포맷 변환, Spark 구조적 스트리밍, Flink (K5)

PutRecord 한 번으로 두 스토어에 쓰이며 TargetStores 로 대상을 고를 수 있다 〔S50〕〔S57〕. 시점 정확 데이터셋은 오프라인 스토어에서 SDK `create_dataset`(point-in-time 조인)이나 Athena 로 만든다 〔S62〕. TTL 은 온라인 스토어 전제(하드 삭제, 삭제 레코드는 오프라인에 추가) 〔S61〕. InMemory 는 초저지연이지만 온라인 전용이다 〔S52〕. 교차 계정은 AWS RAM 으로 하되 발견 가능성(카탈로그)과 접근 권한(그룹 단위)을 따로 부여한다 〔S64〕〔S65〕.
- 오답 유인(섞이는 선택지): "Athena 로 실시간 추론 조회"(오프라인은 sub-second 지연이 필요 없는 용도), "InMemory + 오프라인 동시 사용"(불가), "더 이른 EventTime 레코드도 온라인 스토어를 덮어쓴다"(이력으로 오프라인에만 기록), "TTL 이 오프라인 이력까지 지운다"(아님), "접근 권한만 주면 특성 그룹이 검색된다"(발견 가능성은 별도), "Standard_V2 에서 Standard 로 되돌리기"(단방향) 〔S51〕〔S52〕〔S57〕〔S61〕〔S64〕.

### 패턴 4. 레이블링·사람 검토 — Ground Truth vs A2I, 작업 인력, 자동 레이블링, 현재 상태 ⚠️ (K6, SK3)
- 시나리오 단서: "학습용 이미지·텍스트·비디오·3D 점군에 레이블이 필요", "민감 데이터라 퍼블릭 인력은 불가", "사람이 레이블링할 데이터를 ML 이 골라 비용 절감", "추론 결과 중 신뢰도 낮은 건을 사람이 검토", "여러 작업자의 결과를 하나의 레이블로", "기존 레이블의 정확성 확인(검증)과 수정(조정)" 〔S71〕〔S74〕〔S75〕〔S77〕〔S81〕.
- 정답 방향: 학습 데이터 레이블링 = Ground Truth(내장 작업 유형 4계열, 인력 3종, 주석 통합, 자동 데이터 레이블링). 추론 결과의 사람 검토 = A2I(저신뢰 예측·무작위 표본). 민감 데이터 = 비공개 인력(또는 공급업체)이며 MTurk 에는 기밀·개인·보호 건강 정보를 공유하지 않는다. 자동 레이블링은 내장 4개 작업 유형만, 최소 1,250개(권장 5,000개), 스트리밍 잡 불가이며 학습·추론 비용이 든다. 검증(label verification)은 정확성만 표시하고 수정은 못 하며 수정은 조정(label adjustment) 잡이다 〔S74〕〔S77〕〔S80〕.
- ⚠️ 상태: Skill 문장에 Ground Truth·Mechanical Turk 가 남아 있어 시험 범위이지만 현재 상태가 다르다. Ground Truth·A2I 는 신규 고객 불가(기존 고객은 정상 사용), Ground Truth Plus 는 2026-06-30 지원 종료, Mechanical Turk 는 폐쇄(SageMaker 문서 2026-09-30, What's New 지원 종료 2026-09-29) 〔S71〕〔S81〕〔S82〕〔S79〕〔S83〕〔S84〕〔S85〕. 학습문서는 기능 설명을 가이드 기준으로 쓰되 이 상태를 병기한다.
- 오답 유인(섞이는 선택지): A2I 를 학습 데이터 레이블링에 사용, MTurk 에 기밀 데이터 투입, 스트리밍 레이블링 잡에 자동 레이블링 적용, label verification 잡으로 레이블 수정, "Ground Truth Plus 로 해결"(지원 종료), Well-Architected ML Lens 가 아직 Ground Truth Plus 를 권장하는 점(공지와 상충 → §9) 〔S91〕.

### 짝 6. One-hot vs Ordinal(레이블) vs Similarity (vs Binary) 인코딩
- 구분 기준:

| 선택지 | 맞는 데이터 | 결과·옵션 | 함정 |
|---|---|---|---|
| One-hot encode | 순서 없는(nominal) 범주 | 범주마다 0/1 열 또는 희소 벡터(Output style: Vector·Columns). 옵션: Drop last category, Invalid handling strategy(Skip·Keep·Error), Is input ordinal encoded 〔S2〕 | DataBrew ONE_HOT_ENCODING 은 대상 열 고유값 최대 10개 〔S16〕. 인코더는 단계 정의 시점의 범주만 알아 새 범주는 누락 취급 〔S2〕 |
| Ordinal encode | 순서 있는(ordinal) 범주(예: High school, Bachelors, Masters) | 0부터 범주 수 사이의 정수. Invalid handling: Skip·Keep(마지막 범주로 유지)·Error·Replace with NaN 〔S2〕 | NaN 대체는 알고리즘이 결측을 처리할 때 권장 〔S2〕 |
| Similarity encode | 범주 변수가 매우 많거나 잡음(오탈자)이 많은 데이터 | 3-gram 토큰 + min-hash 임베딩, 저차원(Target dimension 기본 30), 범주 수 증가에 확장·잡음에 강함 〔S2〕 | 문서가 one-hot 보다 범용적이라고 서술 〔S2〕 |
| DataBrew CATEGORICAL_MAPPING | 범주를 숫자·다른 값으로 매핑 | categoryMap, keepOthers, other, mapType 〔S17〕 | 'label encoding' 과의 공식 대응표는 없음(§9) |
| Binary encoding | 가이드 예시 항목 | 이번에 조사한 AWS 도구 문서(Data Wrangler 인코딩 3종, DataBrew 데이터 과학 단계 7종)에 동명 변환 없음 〔S2〕〔S13〕 | 일반 ML 개념으로만 서술(§9) |

### 짝 7. Standard vs Min Max vs Robust vs Max Absolute 스케일러 (정규화 vs 표준화 용어)
- 구분 기준:

| 스케일러 | 문서 정의 | DataBrew 에서 가까운 단계(공식 대응표는 없음) |
|---|---|---|
| Standard Scaler | 평균을 빼고 단위 분산으로 스케일링(표준화) 〔S2〕 | SCALE 의 Z_SCORE(평균 0·표준편차 1, 이상값 처리에 가장 적합하다고 명시) 〔S13〕 |
| Min Max Scaler | 각 특성을 지정한 범위로 〔S2〕 | SCALE 의 MIN_MAX(0~1)·SCALE_BETWEEN(두 값 사이) 〔S13〕 |
| Robust Scaler | 이상값에 강건한 통계 사용 〔S2〕 | RESCALE_OUTLIERS_WITH_Z_SCORE(Z-score 정규화를 적용하며 이상값 처리에 권장) 〔S101〕 |
| Max Absolute Scaler | 각 값을 최대 절대값으로 나눔 〔S2〕 | 같은 이름의 단계 없음(SCALE 의 strategy 는 4종) 〔S13〕 |

  - 용어 함정: DataBrew SCALE 은 "scales or normalizes" 로 서술하고 〔S13〕, Linear Learner 문서는 "Normalization, or feature scaling" 이라 부르지만 구현은 평균 0·단위 표준편차로 옮기는 방식이다 〔S90〕. 그러므로 'normalization' 이 min-max 인지 z-score 인지는 서비스 정의를 따라 판단한다.
- 근거: 〔S2〕〔S13〕〔S20〕〔S90〕

### 후보 1 (난이도: foundational)
- 대응 Skill: SK1 / K4 (K1)
- 문제: 한 소매업체의 비즈니스 분석가들이 Amazon S3 의 CSV 데이터를 ML 학습 전에 정리·정규화해야 한다. 분석가는 코드를 작성하지 않으며, 미리 만들어진 변환 수백 개 중에서 클릭으로 골라 쓰고, 그 단계를 레시피로 저장해 새 데이터에 다시 적용한 뒤 결과를 S3 에 쓰고 싶어 한다. 서버나 클러스터는 관리하고 싶지 않다. 가장 적합한 서비스는?
- 보기:
  - A) AWS Glue DataBrew
  - B) Amazon EMR 클러스터에서 실행하는 Apache Spark 애플리케이션
  - C) AWS Glue ETL 작업(PySpark 스크립트)
  - D) SageMaker Processing 작업(사용자 지정 컨테이너의 전처리 스크립트)
- 정답: A
- 근거: 〔S10〕 https://docs.aws.amazon.com/databrew/latest/dg/what-is.html (코드 없이 정리·정규화하는 시각적 도구, 250개 이상 사전 구축 변환, 서버리스, 레시피, 출력은 S3) 〔S29〕 https://docs.aws.amazon.com/prescriptive-guidance/latest/serverless-etl-aws-glue/databrew.html
- 오답 근거: B) EMR 은 Hadoop·Spark 같은 프레임워크를 실행하는 관리형 클러스터 플랫폼으로 코드 작성이 전제된다 〔S37〕 / C) Glue ETL 과 DataBrew 의 차이는 DataBrew 쪽에 코드 작성이 필요 없다는 점이다 〔S29〕 / D) Processing 은 스크립트·노트북·컨테이너 기반이라 노코드·레시피 요구와 맞지 않는다 〔S40〕

### 후보 2 (난이도: associate)
- 대응 Skill: K3 (K2)
- 문제: ML 엔지니어가 SageMaker Data Wrangler 로 고객이 직접 입력한 '도시' 열을 인코딩한다. 이 열은 고유 값이 매우 많고 'San Fransisco' 와 'San Francisco' 같은 오탈자가 섞여 있다. 철자가 비슷한 문자열은 비슷한 벡터가 되도록, 낮은 차원으로 인코딩하려 한다. 어떤 변환을 써야 하는가?
- 보기:
  - A) Encode categorical 의 One-hot encode
  - B) Encode categorical 의 Ordinal encode
  - C) Encode categorical 의 Similarity encode
  - D) Handle outliers 의 Replace rare
- 정답: C
- 근거: 〔S2〕 https://docs.aws.amazon.com/sagemaker/latest/dg/data-wrangler-transform.html (Similarity encode: 범주 변수가 매우 많거나 잡음이 많을 때 사용, 3-gram 토큰 + min-hash 로 유사한 문자열을 유사한 값의 벡터로 인코딩, 저차원, one-hot 보다 범용적)
- 오답 근거: A) One-hot 은 범주마다 열(또는 벡터 위치)이 생겨 오탈자도 별개 범주가 되고, 문서는 Similarity 가 더 범용적이라고 서술한다 〔S2〕 / B) Ordinal 은 범주를 0부터 범주 수 사이의 정수로 바꾸는 순서형 범주용이라 철자 유사도를 보존하지 않는다 〔S2〕 / D) Replace rare 는 드문 범주를 지정 문자열(예: Others)로 바꾸는 이상값 처리 변환이지 벡터 인코딩이 아니다 〔S2〕

### 후보 3 (난이도: associate)
- 대응 Skill: K5
- 문제: Amazon Data Firehose 로 들어오는 CSV 로그를 Amazon S3 에 Parquet 형식으로 저장해야 한다. AWS Glue 데이터 카탈로그에는 스키마 테이블이 이미 있고, 추가 서버는 관리하고 싶지 않다. 가장 적합한 구성은?
- 보기:
  - A) Firehose 레코드 포맷 변환을 켜고 입력 형식으로 CSV 를 선택한다
  - B) Firehose 의 Lambda 변환으로 CSV 를 JSON 으로 바꾸고, 이어서 레코드 포맷 변환(JSON → Parquet, Glue 스키마 참조)을 켠다
  - C) Lambda 변환 함수가 Parquet 파일을 직접 만들어 base64 로 인코딩해 반환하게 하고 포맷 변환은 끈다
  - D) Glue 스트리밍 ETL 작업을 만들고 작업 북마크로 처리 위치를 관리한다
- 정답: B
- 근거: 〔S45〕 https://docs.aws.amazon.com/firehose/latest/dev/record-format-conversion.html (JSON → Parquet·ORC 변환, JSON 이 아닌 입력은 Lambda 로 먼저 JSON 변환) 〔S41〕 https://docs.aws.amazon.com/firehose/latest/dev/data-transformation.html
- 오답 근거: A) 포맷 변환은 JSON 입력을 Parquet·ORC 로 바꾸는 기능이며 CSV 같은 형식은 Lambda 로 먼저 JSON 으로 바꿔야 한다 〔S45〕 / C) 문서가 안내하는 경로는 Lambda 로 JSON 변환 후 Firehose 포맷 변환 기능을 쓰는 방식이다. Lambda 결과는 recordId·result·data(base64) 형식이며 요청·응답 6 MB 제약이 있다 〔S44〕〔S41〕 / D) Glue 스트리밍 ETL 은 작업 북마크를 지원하지 않고 체크포인트로 읽은 위치를 추적한다 〔S35〕

## 8. MLA-C02 개정 영향

> 출처: 공식 비교 페이지 — 영문 https://docs.aws.amazon.com/aws-certification/latest/machine-learning-engineer-associate-02/mla-02-comparison.html · 한국어 https://docs.aws.amazon.com/ko_kr/aws-certification/latest/machine-learning-engineer-associate-02/mla-02-comparison.html (조회일 2026-10-17). 아래 항목은 **공식 원문을 그대로** 옮겼다(영문 / 한국어). 이 절의 내용은 MLA-C01 노트 본문의 사실 근거가 아니라 **C02 대비용 참고**이다.

- **C02 대응 Task**: 1.2 Perform data transformation, feature engineering, and pre-processing. / 1.2 데이터 변환, 특성 추출 및 사전 처리를 수행합니다.
- **C02에서 추가된 콘텐츠 (5개)** — 이 C01 노트에는 없는 내용이다(C02용 조사가 별도로 필요):
  - 1.2.5 Configure and use embedding models to transform text and image data into numerical representations.
    - 한국어: 1.2.5 임베딩 모델을 구성하고 사용하여 텍스트 및 이미지 데이터를 수치 표현으로 변환합니다.
  - 1.2.6 Apply advanced text pre-processing techniques (for example, tokenization, domain-specific augmentation).
    - 한국어: 1.2.6 고급 텍스트 사전 처리 기법을 적용합니다(예: 토큰화, 도메인별 증강).
  - 1.2.7 Prepare documents for Retrieval Augmented Generation (RAG) applications (for example, chunking strategies, metadata extraction).
    - 한국어: 1.2.7 검색 증강 생성(RAG) 애플리케이션에 사용할 문서를 준비합니다(예: 청킹 전략, 메타데이터 추출).
  - 1.2.8 Mask, redact, and anonymize data.
    - 한국어: 1.2.8 데이터를 마스킹, 편집 및 익명화합니다.
  - 1.2.9 Prepare data for FM fine-tuning, continuous pre-training, and model distillation.
    - 한국어: 1.2.9 FM 미세 조정, 지속적인 사전 훈련 및 모델 증류를 위한 데이터를 준비합니다.
- **C02에서 삭제된 콘텐츠**: 이 Task에는 없음
- 참고: 비교 페이지는 '추가'된 항목만 번호(예: 1.1.7)로 나열하며, 번호가 건너뛰는 항목(예: 1.1.1~1.1.6)이 C01의 어느 항목에 대응하는지는 **설명하지 않는다**.

## 9. 확인 필요 항목

- [G-1.2-1] DataBrew 의 2026-10-17 현재 신규 고객 가능 여부는? — 2025-10·2026-03·2026-06·2026-09 What's New 4건의 서비스 목록을 직접 읽음(DataBrew 항목 없음, Glue 는 Ray 작업 기능만 〔S97〕) + DataBrew 문서 이력 검색(가용성 변경 항목 미발견). 목록 부재는 긍정 확인이 아니다 — 학습문서에는 "공지 목록에 없음"으로만 쓰고 '정상 제공'으로 단정하지 말 것. 필요하면 컨트롤러가 AWS 수명 안내(S88)와 함께 재확인.
- [G-1.2-2] DataBrew 사전 구축 변환 수는 250인가 350인가? — 공식 DataBrew 가이드는 "over 250"(S10), 일부 AWS Big Data 블로그 본문은 "over 350"으로 서술 — 공식 문서 수치 250 만 쓰고 블로그 350 은 쓰지 않는다.
- [G-1.2-3] Data Wrangler "over 300 built-in transformations"(S5)와 DataBrew "over 250"(S10)을 비교해도 되는가? — 두 문서 모두 집계 기준을 제시하지 않는다. 수치 비교형 문항 금지, 각각 서술형 사실로만 쓴다.
- [G-1.2-4] Data Wrangler 에 이름이 binning·bucketize 인 내장 변환이나 로그 전용 변환이 있는가? — 변환 문서 목차(S2·S3)에서 확인하지 못했고 Custom formula(Spark SQL)·사용자 지정 변환·Canvas 구 노코드 함수 Log/Ln(S5)만 확인. DataBrew BUCKETIZATION·SKEWNESS 가 문서상 명확한 대응 — 학습문서는 "Data Wrangler 변환 목록에 binning 그룹 없음"으로 표현.
- [G-1.2-5] 'binary encoding'·'label encoding' 의 AWS 공식 정의나 동명 변환이 있는가? — Data Wrangler Encode categorical(S2), DataBrew 데이터 과학 단계 7종(S13), 문서 검색 결과 모두 없음. Ordinal encode(S2)와 CATEGORICAL_MAPPING(S17)이 가장 가깝지만 공식 대응표는 없다 — 일반 ML 개념으로 서술하되 AWS 변환 이름과 1:1 로 단정하지 말고, 정의 출처가 필요하면 별도 확보.
- [G-1.2-6] Ground Truth·A2I·Mechanical Turk 의 공식 대체 서비스는 무엇인가? — SageMaker AI features 공지(S85)의 "similar capabilities" 링크는 기능 목록 페이지(https://docs.aws.amazon.com/sagemaker/latest/dg/whatis-features.html, 링크 대상은 WebFetch 로만 확인)로 연결되며 구체 서비스명을 지정하지 않는다. MTurk 문서(S79)는 "대체 작업 인력 옵션으로 전환"만 안내 — 대체 서비스명은 단정하지 말고 이 두 사실만 서술.
- [G-1.2-7] Mechanical Turk 종료일 — SageMaker 문서는 9월 30일(S79), What's New 는 9월 29일 지원 종료(S84)로 하루 차이 — 학습문서에 둘 다 표기.
- [G-1.2-8] Well-Architected ML Lens 가 Ground Truth Plus 를 여전히 권장(S91)하는데 What's New 는 2026-06-30 지원 종료(S83) — 문서끼리 상충. 공지를 우선하고 Ground Truth Plus 관련 문항은 ⚠️ 와 함께 출제.
- [G-1.2-9] Feature Store SDK 메서드 이름을 무엇으로 쓸까? — 개발자 가이드 안에서 `feature_group.ingest`(S68)와 `ingest_dataframe`(https://docs.aws.amazon.com/sagemaker/latest/dg/feature-store-introduction-notebook.html)가 함께 보이고 "SDK for Python (Boto3)" 문구가 SageMaker Python SDK 와 Boto3 에 섞여 쓰인다. 시점 정확 조인 메서드도 가이드는 `point_time_accurate_join`(S62), AWS ML 블로그는 `point_in_time_accurate_join`(https://aws.amazon.com/blogs/machine-learning/build-machine-learning-ready-datasets-from-the-amazon-sagemaker-offline-feature-store-using-the-amazon-sagemaker-python-sdk/) — 문항에서 메서드명 단정 금지, 개념(ingest, point-in-time 조인) 중심.
- [G-1.2-10] Standard_V2·UpdateRecord 가 시험 가이드(Version 1.0) 범위인가? — 최신 문서(S52·S57)에 있으나 가이드 Skill 문장에는 언급이 없다 — 학습문서에는 '참고'로만 두고 문항화는 보류.
- [G-1.2-11] k-NN·k-means 등 개별 알고리즘의 스케일 민감성은? — SageMaker 알고리즘 문서 검색(https://docs.aws.amazon.com/sagemaker/latest/dg/k-nearest-neighbors.html, https://docs.aws.amazon.com/sagemaker/latest/dg/k-means.html 포함)에서 스케일 민감성 서술을 찾지 못했다. 근거가 있는 것은 Linear Learner 정규화(S90), Data Wrangler Handle outliers 문장(S2), Featurize date/time 임베딩 모드 권장(S2)뿐 — 그 밖의 알고리즘 문항은 만들지 말 것.
- [G-1.2-12] Firehose 버퍼 힌트 두 종류 — Lambda 변환 버퍼(0.2–3 MB·0–900초, S41)와 목적지 버퍼 간격 힌트(60–900초, S42)는 문서에서 따로 서술되지만 수치가 비슷해 혼동을 부른다. 6 MB 는 Lambda 동기 호출 페이로드 한도로 버퍼 상한(3 MB)과 별개 — 문항에서 어느 한도인지 명시.
- [G-1.2-13] Feature Store 온라인 스토어의 구체 지연 수치(ms)는? — S50·S52 는 low millisecond·very low latency 같은 정성 표현만 쓰고 수치가 없다 — 수치형 문항 금지.
- [G-1.2-14] Data Wrangler 문서 두 계열(Studio Classic 계열 S1·S2, Canvas 계열 S3·S4)의 차이는? — 변환 그룹 목차를 비교한 결과 이름이 같다. Canvas 문서에만 Chat for data prep 과 Canvas 처리 흐름(S6)이 추가된다. 현행 제공 위치는 Canvas 이므로 학습문서는 Canvas 기준으로 쓰고 Studio Classic 명칭을 병기.
- [G-1.2-15] A2I 유지 모드 날짜의 출처 — A2I 개요(S81)는 "no longer open to new customers" 만 서술하고 '2026-07 유지 모드'는 Textract API 문서(S82), 2026-07-30 신규 고객 불가는 What's New 2026-06 목록(S83)에서 확인 — 학습문서에는 두 근거를 병기.
- [G-1.2-16] ko_kr 번역 품질 — S92~S95 는 기계 번역(영문 우선 고지)이다. 예: Ground Truth 개요(S93)는 "MTurk, 공급업체, 비공개 인력" 중 선택 문장을 "선택한 공급업체인 Amazon Mechanical Turk 의 워커"로 옮겨 의미가 흐려진다. 한국어 용어는 S92~S95 표기(이상치 처리하기, 누락된 값 처리, 카테고리 인코딩·서수·원-핫·유사성 인코딩, 특성 저장소, 프라이빗 작업 인력)를 참고하되 서술은 영문 기준.
- [G-1.2-17] 가이드 K6 한국어 문장("만들기하는")이 어색하다 — 컨트롤러가 공식 ko_kr 가이드와 글자 단위로 일치함을 확인한 원문이다 — `MLA-C01.json` 은 수정하지 말고 학습문서에서 자연스러운 한국어로 풀어 쓴다.
