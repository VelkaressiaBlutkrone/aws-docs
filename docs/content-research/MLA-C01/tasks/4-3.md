### 2.1 SageMaker 실행 역할(execution role)과 `iam:PassRole` — 사람의 역할 vs 서비스의 역할 (K1, SK2)

**정의.** SageMaker AI는 사용자를 대신해 다른 AWS 서비스를 호출하며, 그 권한을 **IAM 실행 역할(execution role)** 로 부여한다〔S1〕. 모든 실행 역할의 신뢰 정책은 동일하다 — `Principal.Service = sagemaker.amazonaws.com`, `Action = sts:AssumeRole`〔S1〕. 즉 "누가 assume하는가"가 SageMaker AI 서비스 주체다.

**`iam:PassRole` — 누가, 어떻게.**
- 실행 역할을 요청에 실어 보내는 API(`CreateTrainingJob`, `CreateProcessingJob`, `CreateHyperParameterTuningJob`, `CreateModel`, `CreateNotebookInstance`, `CreateDomain`, `CreateUserProfile` 등)를 부르는 주체는 그 역할을 서비스에 건넬 권한(`iam:PassRole`)이 있어야 한다〔S1〕〔S5〕.
- 정책은 `Resource`를 허용할 역할 ARN으로 좁히고, `Condition`에 `iam:PassedToService = sagemaker.amazonaws.com`을 둔다〔S1〕〔S3〕〔S5〕.
- 대표 오류: `User: arn:aws:iam::...:user/... is not authorized to perform: iam:PassRole` → 호출자의 정책에 PassRole을 추가한다〔S4〕.
- ⚠️ 함정 1: 역할에 태그를 붙이고 `ResourceTag` 조건으로 PassRole을 통제하는 방식은 결과가 일정하지 않다고 문서가 경고한다〔S5〕.
- ⚠️ 함정 2: PassRole은 같은 AWS 계정의 서비스에만 쓴다. 다른 계정의 서비스에 역할을 건네려면 대상 계정에 그 역할을 assume할 수 있는 역할을 먼저 만들어야 한다〔S5〕.

> 🧠 원리: PassRole을 별도 권한으로 분리한 이유는 "사용자가 자기에게 없는 권한을 가진 역할을 서비스에 건네 우회하는 것"을 막기 위해서다. 문서 예: S3 권한이 없는 사용자가 S3 권한이 있는 역할을 서비스에 건넬 수 있다면 서비스가 그 사용자를 대신해 S3 작업을 수행하게 된다〔S5〕.

**사용자(연합) 역할 vs 실행 역할** 〔S6〕

| 구분 | 사용자 연합 역할(user federation role) | SageMaker 실행 역할 |
|---|---|---|
| assume하는 주체 | 사용자가 직접 assume〔S6〕 | SageMaker AI 서비스가 assume〔S6〕 |
| 용도 | AWS Management Console 등 AWS 리소스 접근〔S6〕 | 사용자 또는 자동화 도구를 대신해 서비스가 기능 수행(예: Studio가 사용자 프로필의 실행 역할로 AWS 리소스에 접근)〔S6〕 |
| 지정 위치 | 문서에 별도 서술 없음 | 사용자 프로필, 사용자 프로필에 없으면 도메인 수준〔S6〕 |

- 커스텀 웹 앱이 presigned URL로 Studio에 접근하면 두 역할이 섞인 하이브리드가 되므로, 사용자가 할 수 있는 일과 Studio가 대신 할 수 있는 일 양쪽 모두에 최소 권한을 적용해야 한다〔S6〕.

**실행 역할을 어디에 연결하나.** 실행 역할은 도메인(기본 실행 역할)·공간(space 기본 실행 역할)·사용자 프로필·노트북 인스턴스에 연결하거나 작업 API 호출에 ARN으로 전달한다〔S1〕. 역할을 바꾸면 그 역할을 쓰는 모든 ID의 권한이 바뀐다: 사용자 실행 역할을 바꾸면 그 사용자가 만든 private space가, space 기본 실행 역할을 바꾸면 도메인의 shared space가 바뀐 역할을 가정한다〔S1〕.

**API별로 실행 역할에 추가해야 하는 권한(문서 명시)** 〔S1〕

| 상황 | 실행 역할에 필요한 것 |
|---|---|
| 프라이빗 VPC를 지정한 작업(훈련·튜닝·처리·AutoML) | `ec2:CreateNetworkInterface`, `ec2:CreateNetworkInterfacePermission`, `ec2:DeleteNetworkInterface`, `ec2:DeleteNetworkInterfacePermission`, `ec2:DescribeNetworkInterfaces`, `ec2:DescribeVpcs`, `ec2:DescribeDhcpOptions`, `ec2:DescribeSubnets`, `ec2:DescribeSecurityGroups`. 처리 작업은 이 ec2 권한에 조건·리소스 필터를 걸면 생성 시 검증이 실패한다〔S1〕 |
| 입력이 SSE-KMS로 암호화됨 | `kms:Decrypt`〔S1〕 |
| 출력 설정에 KMS 키 지정 | `kms:Encrypt`〔S1〕 |
| 리소스 구성(ML 스토리지 볼륨)에 KMS 키 지정 | `kms:CreateGrant`〔S1〕 |
| `CreateDomain`에 고객 관리형 키(`KmsKeyId`) 지정 | `kms:CreateGrant`, `kms:DescribeKey` — `CreateApp` 호출 시 적용된다〔S1〕 |
| 노트북 인스턴스에서 SageMaker API 호출 | 문서 예시는 `sagemaker:*` 등과 함께 `iam:PassRole`(조건 `iam:PassedToService`)을 포함〔S1〕 |

**Pipelines.** 파이프라인은 파이프라인 실행 역할을 받으며, 생성자 쪽 역할에 그 역할을 지정한 `iam:PassRole`이 필요하다. 기본적으로 각 단계는 파이프라인 실행 역할을 쓰지만 단계별로 다른 역할을 줄 수 있고, 이는 한 단계의 코드가 직접 관계가 없는 다른 단계의 리소스에 영향을 주지 못하게 하려는 설계다〔S57〕.

**혼동된 대리인(confused deputy) 방지.** 실행 역할 신뢰 정책에 `aws:SourceArn` 조건을 추가한다. SageMaker Studio 예: `ArnLike aws:SourceArn = arn:aws:sagemaker:us-west-2:123456789012:*` (계정 번호가 ARN에 있으므로 `aws:SourceAccount`는 따로 필요 없음)〔S58〕.

### 2.2 관리형 정책과 최소 권한 접근법 — 정책 선택, 범위 좁히기, 사용량 기반 축소 (K1, SK1, SK2)

**관리형 정책에서 시작해 최소 권한으로 이동한다.** 문서의 정책 모범 사례: AWS 관리형 정책으로 시작하고, 사용 사례에 특화된 고객 관리형 정책으로 권한을 더 줄이며, 조건으로 추가 제한하고, IAM Access Analyzer로 정책을 검증하고, MFA를 요구한다〔S3〕. 관리형 정책 페이지의 권고는 "use the most restricted policy"다〔S2〕.

| 정책 | 무엇을 주나 | 시험에서 중요한 한계 |
|---|---|---|
| `AmazonSageMakerFullAccess` | SageMaker AI(및 geospatial) 리소스·작업 전체 + 관련 서비스 일부〔S2〕 | S3는 이름에 `SageMaker`/`Sagemaker`/`sagemaker`/`aws-glue`가 들어간 버킷·객체에 대해서만 일부 작업 허용(그 밖에 `s3:CreateBucket`, `s3:ListBucket` 등은 모든 S3 리소스에 허용)〔S1〕. 모든 IAM 역할을 SageMaker에 전달할 수 있고, Glue·Step Functions·RoboMaker에는 이름에 "AmazonSageMaker"가 든 역할만 전달 가능〔S2〕. **도메인 생성 권한은 포함하지 않음**〔S2〕 |
| `AmazonSageMakerReadOnly` | SageMaker AI 리소스 읽기 전용〔S2〕 | 감사자·모니터링용 |
| 그 밖의 용도별 관리형 정책 | Canvas·Feature Store·Pipelines·Model Governance·Model Registry 등 용도별 정책이 따로 있음〔S2〕〔S8〕 | 필요한 기능 단위로 고른다 |
| `AdministratorAccess`, `DataScientist` | 문서가 "권장하지 않음"으로 분류〔S2〕 | |

**S3 권한의 범위를 요청 필드에 맞춰 좁힌다**(실행 역할 최소 권한 예시) 〔S1〕

| 권한 | 좁히는 대상(요청 필드) |
|---|---|
| `s3:ListBucket` | `InputDataConfig.DataSource.S3DataSource.S3Uri`의 버킷 |
| `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject` | `S3Uri`, `OutputDataConfig.S3OutputPath`; `CreateModel`이면 `PrimaryContainer.ModelDataUrl` 등 |
| ECR 권한(`ecr:BatchCheckLayerAvailability`, `ecr:GetDownloadUrlForLayer`, `ecr:BatchGetImage`) | `AlgorithmSpecification.TrainingImage`(`CreateModel`이면 `PrimaryContainer.Image`) 리포지토리 ARN |
| CloudWatch Logs | 튜닝 작업 예시는 로그 그룹 `/aws/sagemaker/TrainingJobs*`로 한정 |
| `cloudwatch:PutMetricData`, `ecr:GetAuthorizationToken` | 문서 예시는 `Resource: "*"`로 둔다(문서는 CloudWatch 동작이 `"*"` 리소스에 적용된다고 명시) |

**주체별 역할 설계(SK2).**

| 주체 | 부여 | 막을 것 | 근거 |
|---|---|---|---|
| 데이터 과학자·ML 엔지니어(사람) | SageMaker 작업 권한 + **특정 실행 역할에 한정한 `iam:PassRole`** | 임의 역할 전달, 관리자 정책 | 〔S2〕〔S5〕 |
| SageMaker 실행 역할(서비스) | 작업이 쓰는 S3 프리픽스·ECR 리포지토리·KMS 키·로그 그룹만 | 광범위한 `Resource: "*"` | 〔S1〕 |
| 추론을 호출하는 애플리케이션 | `sagemaker:InvokeEndpoint`를 **특정 엔드포인트 ARN**으로 한정 | `Resource` 와일드카드 | 〔S89〕 |
| 읽기 전용 감사자 | `AmazonSageMakerReadOnly` | 변경 권한 | 〔S2〕 |
| 조직 전체 가드레일 | SCP·Deny 문장으로 KMS·VPC·격리 강제(2.4) | 보안 설정 누락 | 〔S12〕 |

**IAM 그룹(K1).** IAM 사용자 그룹은 IAM 사용자의 모음이며 그룹에 ID 기반 정책을 붙여 여러 사용자의 권한을 한 번에 관리한다. 그룹은 인증 주체가 아니라 권한 단위이므로 **리소스 기반 정책의 `Principal`로 쓸 수 없다**(예: S3 버킷 정책에 그룹을 주체로 지정 불가)〔S45〕.

**정책 평가 규칙.** 기본은 암묵적 거부이고 명시적 거부가 명시적 허용을 이긴다〔S46〕. 명시적 거부는 정책에 `Deny`가 있을 때, 암묵적 거부는 적용되는 `Deny`도 `Allow`도 없을 때 발생한다〔S91〕. 실행 역할에 permissions boundary가 있으면 SageMaker는 IAM 정책과 경계가 **둘 다** 허용한 동작만 실행한다〔S59〕. 조직 수준에서는 SCP가 구성원 계정 사용자·역할의 유효 권한을 제한한다〔S12〕.

**사용량 기반으로 줄이기.**
- IAM Access Analyzer는 정책 검증(100개 넘는 정책 점검과 실행 가능한 권고)〔S3〕과 CloudTrail 활동 기반 **정책 생성**을 제공한다. 정책 생성은 최대 90일의 과거 CloudTrail 이벤트를 분석하며, 서비스 역할과 이벤트를 기록하는 CloudTrail 추적(trail)이 먼저 있어야 한다〔S43〕.
- 적용 흐름(Role Manager 대체 가이드): 넓은 정책(예: `AmazonSageMakerFullAccess`)으로 대표 기간(30–90일 권장) 워크로드를 돌린 뒤 Access Analyzer로 실제 사용 작업만 담은 정책을 생성해 교체한다〔S8〕.
- 사용 이력을 수동으로 보는 방법: CloudTrail Event history를 사용자 이름으로 필터링하거나 IAM 콘솔의 Access Advisor(마지막 접근 정보)를 본다〔S88〕.

**태그 기반 접근 제어(ABAC).** `sagemaker:ResourceTag/<키>` 조건으로 팀별 리소스를 분리할 수 있지만, 목록·`Search` 계열 API 등 일부 호출에는 태그 기반 정책이 적용되지 않는다〔S3〕. 사용자 정의 태그는 갱신 시 덮어쓸 수 있으므로 태그 부여 권한을 좁게 주어야 하고, AWS가 생성하는 태그(`sagemaker:domain-arn`, `sagemaker:user-profile-arn`, `sagemaker:space-arn`)는 사용자가 바꿀 수 없다〔S3〕.

### 2.3 SageMaker Role Manager ⚠️ — 페르소나 기반 역할 생성기(신규 고객 중단)와 대체 경로 (K1)

> ⚠️ 상태(L3): "Amazon SageMaker Role Manager is no longer open to new customers" — 기존 고객은 계속 사용하고, 보안·가용성 개선은 이어가되 새 기능은 계획이 없다〔S8〕. SageMaker AI 기능 묶음 공지에는 Role Manager가 2026-07-30부터 신규 고객에게 열려 있지 않은 기능으로 포함되어 있고, 같은 공지는 다른 SageMaker AI 기능의 가용성에는 영향이 없다고 명시한다〔S55〕. MLA-C01 가이드(Version 1.0)는 K1의 예로 Role Manager를 들고 있으므로 시험 대비로는 개념을 알아야 하나, 오늘 기준 신규 계정에서는 쓸 수 없다.

**무엇인가.** ML 관리자가 데이터 과학자·MLOps 엔지니어 같은 페르소나별 최소 권한을 SageMaker AI 콘솔에서 IAM 역할로 만들고 관리하게 해 주는 기능이다〔S7〕. 일반 ML 활동용으로 **사전 구성된 페르소나 3개**와 사전 정의된 권한(ML activity)을 제공한다〔S7〕.

| 페르소나 | 용도 | 사전 선택 ML 활동(일부) |
|---|---|---|
| Data scientist | 일반 ML 개발·실험 권한〔S9〕 | Run Studio Classic Applications, Manage ML Jobs, Manage Models, Manage AWS Glue Tables 등〔S9〕 |
| MLOps | 운영 활동 권한〔S9〕 | Manage Models, Manage Pipelines, Search and visualize experiments, Amazon S3 Full Access 등〔S9〕 |
| SageMaker AI compute | SageMaker 컴퓨팅 리소스(훈련·추론)가 쓰는 서비스 실행 역할〔S9〕 | Access Required AWS Services〔S9〕 |

- 1단계에서 입력한 VPC 서브넷·보안 그룹·KMS 키 같은 조건은 선택한 모든 ML 활동에 자동 전달되고, `InstanceTypes`·`IntercontainerTrafficEncryption` 같은 조건을 활동별로 더 붙일 수도 있다〔S6〕.
- 결과물은 일반 IAM 역할이다. 이름에 기본으로 `sagemaker-` 접두어가 붙고 IAM 콘솔에서 수정·삭제할 수 있다〔S6〕〔S8〕. 콘솔 로그인용 사람 역할은 만들 수 없고, 서비스 역할을 만든 뒤 IAM 콘솔에서 편집해 사람용 접근 역할을 추가해야 한다〔S6〕.
- 접근 위치(과거): SageMaker AI 콘솔 Admin configurations > Role manager > Create a role, 또는 도메인·노트북·훈련 작업·추론 모델 생성 중 "Create role using the role creation wizard"〔S8〕.

**대체 경로(공식 가이드가 안내하는 것)** 〔S8〕

| 필요 | 대체 수단 |
|---|---|
| 실행 역할 생성 | IAM 콘솔·CLI·SDK에서 `sagemaker.amazonaws.com` 신뢰 정책 역할 생성(콘솔: SageMaker AI – Execution 사용 사례, `AmazonSageMakerFullAccess` 자동 부착) |
| 페르소나별 권한 | AWS 관리형 정책 직접 부착: 일반 개발 `AmazonSageMakerFullAccess`, 읽기 `AmazonSageMakerReadOnly`, Canvas `AmazonSageMakerCanvasFullAccess`+`AmazonSageMakerCanvasAIServicesAccess`, 파이프라인 `AmazonSageMakerPipelinesIntegrations`, Feature Store `AmazonSageMakerFeatureStoreAccess`, 모델 거버넌스 `AmazonSageMakerModelGovernanceUseAccess`, 모델 레지스트리 `AmazonSageMakerModelRegistryFullAccess` |
| 사용량 기반 최소 권한 | IAM Access Analyzer 정책 생성(정적 활동 템플릿 대신 실제 CloudTrail 접근 패턴 기반) |
| 인력 ID·중앙 접근 관리 | AWS IAM Identity Center 권한 세트, 외부 IdP 연합, Studio와의 trusted identity propagation |
| 반복 가능한 거버넌스 | CloudFormation·CDK로 역할 정의. `@aws-cdk/aws-sagemaker-alpha`의 `Persona`·`Activity` 구성요소는 표준 `aws-cdk-lib/aws-iam`으로 교체 |

- 기존 Role Manager가 만든 역할은 Role Manager 런타임 의존성이 없는 표준 IAM 역할이라 정리·마이그레이션이 필요 없다〔S8〕.

> 🧠 원리: Role Manager는 사전 정의된 **정적 활동 템플릿**이고, Access Analyzer는 실제 사용 기록에 맞춘 **사용량 기반 권고**다. 문서는 후자가 정적 템플릿을 대체한다고 설명한다〔S8〕.

**이름이 같은 다른 기능(혼동 주의).** AWS Security Blog는 IAM 콘솔 Account settings에서 켜는 **IAM role manager**를 소개한다. 활성화하면 지원 서비스 콘솔에서 리소스를 만들 때 AWS가 필요한 IAM 역할을 만들어 붙여 주고, 만든 역할은 일반 IAM 역할이다〔S10〕. SageMaker AI 콘솔의 SageMaker Role Manager(페르소나 기반)와는 켜는 위치·동작이 다르다. MLA-C01 가이드 K1이 말하는 대상은 IAM role manager가 아니라 SageMaker Role Manager다.

### 2.4 SageMaker 조건 키로 보안 설정 강제 — Deny·SCP 가드레일 (K1, K2, K3, SK2)

SageMaker는 `sagemaker:` 접두 조건 키로 "리소스를 만들 때 요청에 담긴 보안 설정"을 IAM 정책에서 검사하게 해 준다〔S3〕. 키의 실존·타입·의미의 정본은 Service Authorization Reference다〔S11〕.

| 강제하려는 것 | 조건 키(타입) | 정책에서의 쓰임(문서 예) |
|---|---|---|
| ML 볼륨 KMS 암호화 | `sagemaker:VolumeKmsKeyArn`(ARN). **구 이름 `sagemaker:VolumeKmsKey`는 deprecated**〔S11〕 | 노트북 인스턴스·Studio 도메인(EFS)·훈련/처리/변환/튜닝 작업에서 키가 없으면(`Null: "true"`) Deny〔S12〕. 특정 키만 허용은 `ArnEquals`(훈련·튜닝 작업 등)〔S3〕 |
| 출력 KMS 암호화 | `sagemaker:OutputKmsKeyArn`(ARN). 구 `sagemaker:OutputKmsKey`는 deprecated〔S11〕 | 키 지정 여부 검사〔S11〕 |
| VPC 안에서만 실행 | `sagemaker:VpcSubnets`, `sagemaker:VpcSecurityGroupIds`(ArrayOfString)〔S11〕 | 훈련·튜닝·처리·모델·노트북 생성에서 둘 다 없으면(`Null: "true"`) Deny〔S12〕. 허용 서브넷·SG만: `ForAllValues:StringEquals` + `Null: "false"`〔S3〕 |
| 컨테이너 네트워크 차단 | `sagemaker:NetworkIsolation`(Bool)〔S11〕 | `false`이면 Deny(훈련·튜닝)〔S12〕. 허용형 예: `Bool true`일 때만 Allow〔S3〕 |
| 노드 간 트래픽 암호화 | `sagemaker:InterContainerTrafficEncryption`(Bool)〔S11〕 | `false`이면 Deny(훈련·튜닝). 훈련 속도가 느려질 수 있다고 문서가 주의〔S12〕 |
| 노트북 직접 인터넷 | `sagemaker:DirectInternetAccess`(String)〔S11〕 | `Enabled`이면 Deny〔S12〕. 허용형: `Disabled` + VPC 지정일 때만 Allow〔S3〕 |
| 노트북 root 권한 | `sagemaker:RootAccess`(String)〔S11〕 | `Enabled`이면 Deny(`CreateNotebookInstance`·`UpdateNotebookInstance`)〔S12〕 |
| Studio 도메인 인터넷 | `sagemaker:AppNetworkAccessType`(String)〔S11〕 | `PublicInternetOnly`이면 `CreateDomain` Deny〔S12〕 |
| 인스턴스 유형 제한 | `sagemaker:InstanceTypes`(ArrayOfString)〔S11〕 | 허용 유형 목록 밖이면 Deny(비용 통제)〔S12〕 |
| 모델 승인 상태 | `sagemaker:ModelApprovalStatus`〔S11〕 | Model Registry 승인 단계 통제용 키 |
| 훈련 입력 파일 시스템 | `sagemaker:FileSystemId`·`FileSystemDirectoryPath`·`FileSystemAccessMode`·`FileSystemType`〔S3〕 | EFS/FSx 경로·읽기 전용 모드로 한정〔S3〕 |
| 태그 | `aws:RequestTag/<키>`, `sagemaker:ResourceTag/<키>`〔S11〕 | 필수 태그 강제(Deny), 팀별 접근 분리〔S12〕〔S3〕 |

**Deny 가드레일 예(백서)** — 훈련·튜닝 작업에서 네트워크 격리가 꺼져 있으면 거부〔S12〕:

```json
{
  "Effect": "Deny",
  "Action": ["sagemaker:CreateHyperParameterTuningJob", "sagemaker:CreateTrainingJob"],
  "Resource": "*",
  "Condition": { "Bool": { "sagemaker:NetworkIsolation": "false" } }
}
```

**두 가지 정책 패턴.**
1. **Allow + 조건** — 조건을 만족할 때만 허용. 문서 예: `CreateNotebookInstance`를 `DirectInternetAccess=Disabled`·`RootAccess=Disabled`이고 서브넷·보안 그룹이 지정된 경우에만 허용〔S3〕.
2. **Deny + 조건(가드레일)** — 조건을 만족하지 않는 요청을 거부. 백서의 가드레일 예제는 모두 Deny 문장이며, 조직 단위 적용은 AWS Organizations의 SCP가 맡는다〔S12〕.

> 🧠 원리: 정책 평가에서 명시적 거부는 어떤 허용보다 우선한다〔S46〕. 그래서 "다른 정책이 허용해도 막아야 하는" 필수 통제(암호화·VPC·격리)는 Deny 형태로 쓴다.

**호출 출처 제한(네트워크 조건).**
- API 호출을 VPC 안으로 제한: `aws:SourceVpc`(특정 VPC) 또는 인터페이스 엔드포인트 경유만 허용하려면 `aws:SourceVpce`를 쓴다〔S3〕.
- IP 제한: `IpAddress` + `aws:SourceIp`로 API·런타임 호출 또는 `CreatePresignedNotebookInstanceUrl`을 특정 대역에서만 허용한다〔S3〕. 노트북 인스턴스 접근을 IP로 거르는 이 방식은 VPC 인터페이스 엔드포인트로 접속할 때와 호환되지 않는다고 문서가 명시한다〔S3〕. Studio·노트북 presigned URL 실행도 `aws:SourceIp`로 제한할 수 있다〔S12〕.
- ⚠️ VPC 한정 IAM 정책을 적용하면 사용자는 콘솔로 해당 API를 쓸 수 없다〔S3〕.

**키 이름 함정.** 문서 안에서도 불일치가 있다 — 예제 페이지의 "Enforce encryption of input data" 본문은 `sagemaker:VolumeKmsKey`라고 쓰지만 JSON은 `sagemaker:VolumeKmsKeyArn`을 쓴다〔S3〕. 백서의 가드레일 예제도 `sagemaker:VolumeKmsKey`를 쓴다〔S12〕. 현재 정본(SAR)은 `...Arn` 키가 대체 키라고 명시한다〔S11〕. 시험 보기는 구 이름일 수 있으니 둘을 함께 외운다(섹션 9 참고).

### 2.5 ML 아티팩트 보호 — S3·KMS·ECR·Model Registry·데이터 레이크 (SK1, K1)

| 아티팩트 | 어디에 | 접근 제어 수단 | 교차 계정·추가 주의 |
|---|---|---|---|
| 훈련 데이터·모델 아티팩트·출력 | S3 | 실행 역할의 요청 필드 단위 최소 권한(2.2)〔S1〕; 버킷 정책의 `aws:SourceVpce`/`aws:SourceVpc` 조건〔S84〕 | 기본 암호화는 SSE-S3지만 교차 계정은 고객 관리형 키 필요〔S14〕. S3 버전 관리+MFA delete로 삭제·변조 대비〔S88〕 |
| 컨테이너 이미지 | ECR | 리포지토리 정책(리소스 기반)〔S77〕, 불변 태그〔S76〕, 이미지 스캔〔S75〕 | 다른 계정 주체를 정책에 넣는 것은 신뢰의 절반이며, 그 주체에 ID 기반 정책으로도 권한을 줘야 한다〔S77〕 |
| 모델 버전 | Model Registry(모델 패키지 그룹) | 모델 패키지 그룹 리소스 정책(`put_model_package_group_policy`)〔S56〕〔S62〕, `sagemaker:ModelApprovalStatus` 조건 키〔S11〕 | 교차 계정 배포는 모델 그룹·ECR 리포지토리·S3 버킷 3종 정책 + 학습 출력 KMS 키 필요〔S56〕 |
| 데이터 레이크 테이블·위치 | Glue Data Catalog / S3 | Lake Formation 권한 + IAM 정책으로 세분화된 접근〔S87〕 | Data Catalog 리소스를 외부 계정과 공유 가능〔S87〕 |
| 접속 정보·토큰 | Secrets Manager | 코드에 넣지 않고 Secrets Manager에서 런타임에 조회, 실행 역할에 조회 권한 부여(2.11)〔S79〕〔S88〕 | |

- **S3 버킷 정책 + VPC 엔드포인트.** 특정 VPC 엔드포인트가 아니면 모든 작업을 거부하는 `Deny` + `StringNotEquals aws:SourceVpce` 패턴이 S3 문서의 예제다. 이 정책은 콘솔 요청이 그 엔드포인트에서 오지 않으므로 콘솔 접근도 막아 버릴 수 있다〔S84〕. 엔드포인트 쪽에서도 정책을 걸 수 있으나 기본 엔드포인트 정책은 VPC 내 모든 사용자·서비스에 S3 전체 접근을 허용한다〔S20〕.
- **KMS.** AWS KMS는 키 정책·IAM 정책·그랜트와 SCP·VPC 엔드포인트 정책 같은 부가 정책을 함께 평가해 키 사용 허용 여부를 결정한다〔S47〕.
- **교차 계정 모델 배포 레시피(문서).** 모델 그룹에 `sagemaker:DescribeModelPackageGroup`, 모델 버전 리소스에 `DescribeModelPackage`·`ListModelPackages`·`UpdateModelPackage`·`CreateModel`을 상대 계정에 허용하는 리소스 정책, ECR 리포지토리 정책, S3 버킷 정책, KMS 그랜트를 모두 만든다〔S56〕. 하나라도 빠지면 `CreateModel`이 "no resource-based policy allows the sagemaker:CreateModel action"으로 실패한다〔S62〕.
- **AWS 관리형 키는 공유할 수 없다.** S3용 AWS 관리형 키의 키 정책은 편집할 수 없어 교차 계정 권한을 줄 수 없다 → 출력 버킷이 다른 계정이면 고객 관리형 키를 요청에 명시하고 실행 역할에 암호화 권한을 준다〔S15〕.

> 🧠 원리: 교차 계정 접근은 "리소스 쪽 허용"과 "주체 쪽 허용"이 모두 있어야 성립한다. ECR 문서도 같은 구조를 설명한다〔S77〕. 따라서 모델·이미지·아티팩트·키는 각각 리소스 정책이 필요하다.

### 2.6 암호화 — 저장 중·전송 중 (K2)

**저장 중(at rest).**

| 대상 | 기본 동작 | 사용자가 KMS 키를 주면 | 제약 |
|---|---|---|---|
| 노트북·모델 구축 데이터·모델 아티팩트·훈련/배치 변환/처리 출력 | AWS 관리형 S3 키로 SSE-S3 자동 암호화〔S14〕 | 작업 요청에 KMS 키 지정(출력은 S3에 KMS로 암호화 업로드)〔S15〕 | 교차 계정은 고객 관리형 키 필수〔S14〕. S3 Express One Zone·디렉터리 버킷은 SSE-S3만, SSE-KMS 불가〔S14〕〔S15〕 |
| ML 스토리지 볼륨(노트북·처리·훈련·튜닝·변환·엔드포인트) | 키를 안 주면 일시적(transient) 키로 암호화 후 즉시 폐기〔S15〕. 노트북 인스턴스는 OS·ML 볼륨 모두 시스템 관리 KMS 키〔S15〕 | KMS 키 전달(볼륨 지정 시 실행 역할에 `kms:CreateGrant`)〔S15〕〔S1〕 | 로컬 스토리지가 있는 Nitro 인스턴스는 하드웨어 모듈로 암호화되며 이 유형에는 KMS 키를 쓸 수 없다〔S15〕 |
| 작업 출력(S3) | 키 미지정 시 역할 계정의 기본 S3용 KMS 키〔S15〕 | | |

> 🧠 원리: 처리·배치 변환·훈련 컨테이너와 저장소는 임시적(ephemeral)이다. 작업이 끝나면 출력이 S3에 업로드되고 인스턴스가 해체되므로 지속되는 민감 데이터는 KMS로 암호화한 S3나 ML 스토리지 볼륨에 둔다〔S15〕.

**전송 중(in transit).**
- 서비스 간 인터네트워크 전송은 TLS 1.2를 지원한다(TLS 1.3 권장)〔S16〕. 데이터 보호 모범 사례에도 TLS 1.2 요구·1.3 권장이 있다〔S18〕.
- ⚠️ 서비스 플랫폼 내부(intranetwork)의 일부 전송은 **기본적으로 암호화되지 않는다** — 서비스 제어 평면↔훈련 인스턴스 통신(고객 데이터 아님), 분산 처리 작업 노드 간, **분산 훈련 작업 노드 간**〔S16〕. 훈련·처리 클러스터 노드 간 통신은 암호화를 선택할 수 있으며 의료 분야에서는 암호화가 모범 사례다〔S16〕〔S17〕.
- 설정: 훈련·튜닝 작업 요청에 `EnableInterContainerTrafficEncryption=True`를 주고, API 사용 시 VPC 보안 그룹에 **UDP 500**과 **ESP 50**(자기 보안 그룹 ID를 소스로) 인바운드·아웃바운드 규칙을 먼저 추가한다〔S17〕. 단일 인스턴스 작업에는 영향이 없고, 다중 인스턴스에서는 통신량에 따라 훈련 시간·비용이 늘 수 있다〔S17〕〔S16〕.
- FIPS 검증 엔드포인트가 SageMaker API와 호스팅 모델 요청 라우터(런타임)에 제공된다〔S16〕.

> 🧠 원리: 분산 ML 프레임워크·알고리즘이 노드 간에 보내는 정보는 일반적으로 훈련 데이터셋이 아니라 가중치 같은 모델 관련 정보다. 그래도 규제 요구가 있으면 노드 간 트래픽 암호화를 켠다〔S17〕.

**데이터 보호 권고(요약).** MFA, SSL/TLS, CloudTrail 로깅, AWS 암호화 솔루션 사용, S3의 민감 데이터 발견에 Macie 사용을 권고한다〔S18〕.

### 2.7 ML 리소스 네트워크 격리 수단 비교 — VPC 모드 / 네트워크 격리 / Studio `VpcOnly` / 노트북 인터넷 차단 (K2, K3, SK5)

**출발점.** SageMaker AI 훈련 컨테이너와 배포된 추론 컨테이너는 **기본적으로 인터넷이 열려 있다**. 악의적 사용자나 실수로 설치한 공개 라이브러리 코드가 데이터를 원격 호스트로 보낼 수 있는 경로가 되므로 용도에 맞는 격리 수단을 고른다〔S19〕.

| 수단 | 설정(파라미터) | 효과 | 핵심 제약·함정 |
|---|---|---|---|
| 기본(미설정) | — | 컨테이너가 퍼블릭 인터넷의 외부 서비스·리소스에 접근 가능. VPC 구성이 없으면 사용자 VPC 안의 리소스에는 접근하지 못한다〔S19〕〔S22〕 | 데이터 반출 경로가 열려 있음 |
| **VPC 모드** | 훈련·튜닝: `VpcConfig`, 모델: `CreateModel`의 `VpcConfig`, 처리: `NetworkConfig.VpcConfig`, 노트북: `SubnetId`+`SecurityGroupIds`〔S19〕〔S21〕〔S26〕〔S93〕 | SageMaker가 서브넷·보안 그룹 정보로 ENI를 만들어 컨테이너에 붙여 VPC 리소스에 접근시킨다. 트래픽·인터넷 접근은 사용자가 보안 그룹·라우팅으로 통제〔S19〕〔S20〕 | 추가 네트워크 구성 비용과 잘못 구성할 위험이 있다〔S19〕. `Subnets` 최대 16개, `SecurityGroupIds` 최대 5개〔S24〕. default tenancy VPC만〔S20〕 |
| **네트워크 격리** | `EnableNetworkIsolation=True`(`CreateTrainingJob`·`CreateHyperParameterTuningJob`·`CreateModel`)〔S19〕 | 훈련·추론 컨테이너는 S3를 포함한 어떤 서비스로도 아웃바운드 호출을 못 하고 AWS 자격 증명도 받지 못한다. S3 다운로드·업로드는 SageMaker가 실행 역할로 컨테이너와 별도로 처리한다〔S19〕 | 다중 인스턴스 훈련은 컨테이너 피어 간 통신만 허용〔S19〕. AWS Marketplace 리소스로 훈련·모델 실행 시 **필수**〔S19〕. Chainer·SageMaker AI 강화 학습 관리형 컨테이너는 S3 접근이 필요해 미지원〔S19〕 |
| 네트워크 격리 **+** VPC | 둘 다 지정 | 데이터·아티팩트 업·다운로드는 사용자 VPC 서브넷을 경유하지만 컨테이너 자체는 계속 격리되어 VPC·인터넷 리소스에 접근하지 못한다〔S19〕 | `VpcConfig`를 지정하면 네트워크 격리는 알고리즘 컨테이너용 ENI를 만들지 않고 S3용 ENI만 남긴다〔S63〕 |
| Studio 도메인 `VpcOnly` | `CreateDomain`의 `AppNetworkAccessType=VpcOnly`(기본값 `PublicInternetOnly`)〔S25〕 | EFS 외 모든 트래픽이 지정한 VPC·서브넷을 경유하고 인터넷은 기본 비활성〔S25〕 | **사설 서브넷만** 가능〔S23〕. 인터페이스 엔드포인트 또는 NAT가 없으면 Studio 노트북·훈련·호스팅을 못 한다〔S25〕 |
| 노트북 인스턴스 | `DirectInternetAccess=Disabled` — `SubnetId` 지정 필수〔S26〕 | VPC 안의 리소스만 접근. SageMaker 훈련·엔드포인트 서비스에 닿으려면 NAT 게이트웨이(또는 VPC 엔드포인트)가 필요〔S26〕〔S60〕 | `DirectInternetAccess`·`KmsKeyId` 변경은 리소스 교체(Replacement)〔S26〕. 생성 후 네트워크 설정은 변경할 수 없다〔S60〕 |

> 🧠 원리(네트워크 격리가 성립하는 이유): 격리를 켜도 입력 데이터 다운로드와 CloudWatch 로그·메트릭 전송은 노드에서 도는 SageMaker 내부 프로세스가 컨테이너와 별개로 수행한다. 컨테이너는 입력 채널로 제공된 데이터만 읽고, 어떤 경우에도 AWS 자격 증명을 받지 않는다〔S63〕.

**구분 포인트.** 컨테이너가 외부 네트워크 접근을 아예 받지 않게 하는 수단은 **네트워크 격리**다〔S19〕. VPC 모드는 트래픽을 사용자가 통제하는 VPC 경로로 돌리는 수단이며, VPC 밖 리소스가 필요하면 인터페이스 엔드포인트나 NAT 게이트웨이(+ 보안 그룹 아웃바운드 허용)를 직접 구성해야 한다〔S19〕〔S20〕.

**리소스별 설정 위치**

| 리소스 | VPC 지정 | 인터넷·격리·암호화 설정 |
|---|---|---|
| 노트북 인스턴스 | `SubnetId`, `SecurityGroupIds`〔S26〕 | `DirectInternetAccess`, `RootAccess`〔S26〕〔S27〕 |
| Studio 도메인 | `VpcId`, `SubnetIds`(+ 보안 그룹)〔S25〕 | `AppNetworkAccessType`〔S25〕 |
| 훈련·튜닝 작업 | `VpcConfig`〔S20〕 | `EnableNetworkIsolation`〔S19〕, `EnableInterContainerTrafficEncryption`〔S17〕 |
| 처리 작업 | `NetworkConfig.VpcConfig`〔S93〕 | — |
| 모델·엔드포인트 | `CreateModel`의 `VpcConfig`〔S21〕 | `EnableNetworkIsolation`〔S19〕 |

**노트북 인스턴스의 root 권한(함께 묻는 항목).** 기본값은 사용자에게 root 접근이 있다. `RootAccess=Disabled`로 끄면 되지만 수명 주기 구성 스크립트는 root로 실행되어 노트북 실행 역할의 전체 권한을 상속하므로, 수명 주기 구성 변경 권한을 신뢰된 관리자에게만 주고 CloudWatch Logs(`/aws/sagemaker/NotebookInstances`)로 감시해야 한다〔S27〕.

### 2.8 VPC·서브넷·보안 그룹 요건과 VPC 엔드포인트 (K3, SK5)

**1) 서브넷 크기·가용 영역.**
- 훈련 인스턴스당 사설 IP는 EFA를 쓰지 않으면 최소 2개, EFA를 쓰면 최소 5개〔S20〕.
- 호스팅: 인스턴스가 하나여도 **서로 다른 가용 영역에 서브넷 2개 이상**을 만들어야 한다〔S21〕.
- Studio: 사용자당 IP 2–4개 권장, 여러 가용 영역에 퍼진 서브넷이 IP 가용성에 유리〔S23〕.
- 훈련·Studio 모두 default tenancy VPC의 서브넷만 구성할 수 있다〔S20〕〔S23〕.
- 훈련 컨테이너 이미지용 서브넷은 따로 지정하지 않는다 — SageMaker가 ECR에서 이미지를 자동으로 가져온다〔S20〕. 처리 작업도 같다〔S93〕.

**2) 보안 그룹 규칙(문서가 명시한 것)**

| 시나리오 | 필요한 규칙 | 근거 |

| Studio `VpcOnly` | 도메인↔EFS 사이 NFS(TCP 2049), 보안 그룹 내 TCP(최소 8192–65535, Jupyter Server↔Kernel Gateway 연결). 앱을 성공적으로 띄우려면 2049를 인·아웃바운드 모두 허용해야 함 | 〔S23〕〔S25〕 |

| `VpcOnly`에서 노트북 실행 | 보안 그룹이 아웃바운드 연결을 허용 | 〔S23〕〔S25〕 |

**4) 엔드포인트 정책·PrivateLink의 보안 포인트.**
- VPC 엔드포인트 정책으로 주체·액션·리소스를 제한할 수 있다. 문서 예: `sagemaker:InvokeEndpoint`를 특정 엔드포인트(`myEndpoint`)에만 허용하면 `CreateEndpoint`·`CreateTrainingJob` 같은 다른 API와 다른 엔드포인트 호출은 이 VPC 엔드포인트를 통해서는 거부된다. 하지만 VPC **밖**에서의 다른 API 호출은 이 정책으로 막히지 않으므로 별도 IAM 정책으로 제한해야 한다〔S22〕. FIPS 런타임 엔드포인트의 `InvokeEndpoint`는 VPC 엔드포인트 정책을 지원하지 않는다〔S22〕.
- presigned URL: `CreatePresignedNotebookInstanceUrl`이 돌려준 `AuthorizedUrl`의 트래픽은 퍼블릭 인터넷을 지나므로 VPC 엔드포인트만으로 접근할 수 없고, 기본적으로 사용자가 URL을 외부에 공유할 수 있어 IAM 권한으로 네트워크 내부에서만 쓰게 제한해야 한다〔S22〕.
- 온프레미스에서 VPC 엔드포인트로 호출하려면 VPC 내 인스턴스를 거치거나 Site-to-Site VPN·Direct Connect로 VPC에 연결한다〔S22〕.
- S3 엔드포인트 정책으로 Amazon Linux 패키지 저장소(`packages.*.amazonaws.com`, `repo.*.amazonaws.com`, `amazonlinux.*.amazonaws.com`)에 대한 `s3:GetObject`를 Deny하면 훈련·모델 컨테이너에서의 패키지 설치를 막을 수 있다〔S20〕〔S21〕.
- 사용자 지정 IAM 정책으로 VPC 모델을 쓰려면 ENI 관련 ec2 권한을 정책에 직접 추가해야 한다(`AmazonSageMakerFullAccess`에는 포함)〔S21〕.

### 2.9 격리된 ML 시스템 참조 설계 — 계층 방어 체크리스트 (SK5, K3)

문서 근거가 있는 요소를 층별로 묶었다. 한 층이 뚫려도 다음 층이 막도록 겹쳐 쓰는 것이 핵심이다.

| 층 | 구성 | 근거 |
|---|---|---|

### 2.11 CI/CD 파이프라인 보안 모범 사례 (K4)

| 영역 | 모범 사례 | 근거 |
|---|---|---|
| **비밀 관리** | CodePipeline: 파이프라인·액션 구성이나 파이프라인 변수 기본값에 토큰·비밀번호를 직접 입력하지 않는다(로그에 표시되므로). Secrets Manager에 저장하고 참조한다〔S65〕. CodeBuild: 민감 값을 `PLAINTEXT` 환경 변수에 두지 않는다(콘솔·CLI에 평문 노출). 환경 변수 유형 `PARAMETER_STORE` 또는 `SECRETS_MANAGER`를 쓴다〔S70〕 | 〔S65〕〔S70〕 |
| 로그 마스킹의 한계 | CodeBuild 로그는 Parameter Store·Secrets Manager 문자열을 숨기지만 **저장된 값과 정확히 일치할 때만** 가려진다. Base64 인코딩 등 변환한 값은 다른 문자열이라 마스킹되지 않는다 | 〔S71〕 |
| Secrets Manager vs Parameter Store | Secrets Manager는 자동 교체(rotation)를 설정할 수 있다. Parameter Store는 저장된 비밀의 자동 교체 서비스를 제공하지 않으며, 비밀을 Secrets Manager에 두고 Parameter Store 파라미터로 참조하는 방식을 안내한다 | 〔S81〕〔S80〕 |
| SageMaker와 Secrets Manager | 노트북 인스턴스에 연결하는 Git 비공개 저장소 자격 증명을 Secrets Manager로 관리할 수 있다. 코드에 자격 증명을 넣지 말고 SageMaker 실행 역할에 Secrets Manager 접근 권한을 줘서 노트북에서 조회하는 구조를 권고 | 〔S79〕〔S88〕 |
| **서비스 역할 최소 권한** | CodeBuild는 빌드 유형별로 목적이 분리된 최소 권한 IAM 역할을 쓴다(테스트 빌드 역할과 릴리스 빌드 역할을 분리). CloudTrail 활동에서 최소 권한 정책을 만들어 주는 IAM Access Analyzer 정책 생성을 활용한다 | 〔S74〕 |
| 신뢰 정책 | CodeBuild 서비스 역할 신뢰 정책(`codebuild.amazonaws.com`)에 `aws:SourceAccount`·`aws:SourceArn` 조건 키로 혼동된 대리인 문제를 방지하도록 권장 | 〔S73〕 |
| 액션별 역할 | CodePipeline의 각 액션에 별도 IAM 역할을 두는 것이 최소 권한 모범 사례(교차 계정 파이프라인 사례) | 〔S95〕 |
| SageMaker Pipelines | 파이프라인 실행 역할을 전달하는 쪽에 `iam:PassRole` 필요. 기본은 각 단계가 파이프라인 실행 역할을 쓰지만 단계마다 다른 역할을 줄 수 있어 단계 간 영향 범위를 분리 | 〔S57〕 |
| **아티팩트 암호화** | CodePipeline S3 아티팩트는 서버 측 암호화를 구성한다. 파이프라인 생성 마법사가 만드는 기본 키는 AWS 관리형 키이고 변경·삭제 불가, 고객 관리형 키는 교체·변경 가능. CodePipeline은 **대칭** KMS 키만 지원. 버킷 정책으로 SSE-KMS가 아닌 업로드와 `aws:SecureTransport=false` 요청을 거부할 수 있다 | 〔S65〕〔S66〕 |
| **교차 계정 배포** | 파이프라인 계정(A)에서 고객 관리형 KMS 키를 만들어 서비스 역할과 B 계정에 사용 권한을 주고, 아티팩트 버킷 정책으로 B 접근을 허용하며, B의 교차 계정 역할을 A의 서비스 역할이 `sts:AssumeRole`로 assume하게 한다. 파이프라인에는 기본 키 대신 고객 관리형 키를 쓰도록 편집한다. 파이프라인 계정이 아닌 두 계정 사이에서는 아티팩트를 전달할 수 없다 | 〔S67〕 |
| **수동 승인** | 승인 액션 앞에서 파이프라인이 멈추고 IAM 권한이 있는 주체가 승인·거부한다. 거부되거나 7일 안에 응답이 없으면 액션 실패와 같다. Source 스테이지에는 추가할 수 없다. SNS 알림을 쓰려면 서비스 역할에 SNS 권한을, 승인 상태를 갱신할 IAM 주체에는 승인 권한을 먼저 부여해야 한다 | 〔S68〕〔S69〕 |
| 수동 승인 + 자동 검사 | 자동 보안 스캔을 통과한 뒤 민감 환경으로 가기 전에 사람 검토 게이트를 둔다 | 〔S74〕 |
| **컨테이너 이미지** | ECR 스캔: **Basic**(AWS 네이티브 기술+CVE DB, OS 취약점, 수동·푸시 시 스캔)과 **Enhanced**(Amazon Inspector 연동, 자동·지속 스캔, OS+언어 패키지). 불변 태그(Immutable)로 같은 태그 덮어쓰기를 막고 덮어쓰기 시도 시 `ImageTagAlreadyExistsException`. 리포지토리 정책은 리소스 기반 정책 | 〔S75〕〔S76〕〔S77〕 |
| 빌드 네트워크 | CodeBuild를 VPC에서 돌릴 때 사설 서브넷만, 보안 그룹은 빌드로의 인바운드 불허, 빌드가 공용 엔드포인트에 닿으려면 NAT 게이트웨이(인터넷 게이트웨이로 대체 불가) 필요, 다중 AZ | 〔S72〕 |
| 소스·웹훅 | 신뢰할 수 없는 기여자의 PR을 자동 빌드하지 않는다(저장소 자격 증명·환경 변수 접근). push 이벤트 빌드, 브랜치 필터, 신뢰 기여자 필터, 최소 범위의 토큰을 Secrets Manager에 저장 | 〔S74〕 |
| 구성 변경 감사 | CloudTrail로 빌드 활동, AWS Config로 CodeBuild 프로젝트 구성(웹훅 필터 포함) 변경 이력·알림 | 〔S74〕 |
| 의존성 | 외부 라이브러리는 CodeArtifact 같은 사설 저장소에 가져와 두고 환경을 격리 | 〔S88〕 |
| 코드 검토 ⚠️ | Amazon CodeGuru Reviewer(L13)는 2025-11-07부터 새 저장소 연결(association)을 만들 수 없다. 코드 보안 분석 대안으로 Amazon Q Developer(SAST·비밀 노출 탐지·의존성 취약점)와 Amazon Inspector Code Security를 안내 | 〔S82〕〔S83〕 |

> 🧠 원리: CI/CD 파이프라인은 "코드를 실행하는 곳"이어서 자격 증명·환경 변수·서비스 역할이 곧 공격 표면이다. 문서가 반복해서 권하는 축은 (1) 비밀을 구성·환경 변수에 평문으로 두지 않는다, (2) 역할을 단계·용도별로 쪼개 최소 권한으로 둔다, (3) 아티팩트를 KMS로 암호화한다, (4) 민감 단계 앞에 사람 승인 게이트를 둔다, (5) 신뢰할 수 없는 입력(외부 PR)을 자동 실행하지 않는다〔S65〕〔S74〕.

## 3. 시험에서 묻는 방식

> 공식 Skill 문장("최소 권한 액세스 구성", "IAM 정책·역할 구성", "모니터링·감사·로깅", "보안 문제 해결·디버깅", "VPC·서브넷·보안 그룹으로 격리")이 "무엇을 고르게 하는지"에서 도출한 출제 패턴이다. 시험 덤프는 보지 않았다.

### 패턴 1. 누가 무엇을 어디까지 — 최소 권한 설계 (SK1, SK2, K1)
- 시나리오 단서: "데이터 과학자가 훈련 작업은 만들 수 있지만 다른 팀의 S3 데이터는 보면 안 된다", "`iam:PassRole` 권한 오류", "모든 훈련 작업에 KMS 암호화와 VPC 사용을 강제", "추론 애플리케이션은 특정 엔드포인트만 호출", "권한을 실제 사용량에 맞춰 줄이고 싶다".
- 정답 방향: 사람 쪽에는 SageMaker 작업 권한 + **특정 실행 역할에만** `iam:PassRole`(조건 `iam:PassedToService=sagemaker.amazonaws.com`), 실행 역할은 요청 필드 단위로 S3 프리픽스·ECR 리포지토리·KMS 키에 한정, 애플리케이션은 `sagemaker:InvokeEndpoint`를 특정 엔드포인트 ARN으로 한정, 조직 차원의 강제는 **Deny + 조건 키/SCP**, 사용량 기반 축소는 **IAM Access Analyzer 정책 생성**.
- 오답 유인(섞이는 선택지): `AdministratorAccess`·`AmazonS3FullAccess` 부여, 실행 역할 신뢰 정책의 주체를 사용자 ARN으로 변경, IAM 그룹을 버킷 정책의 `Principal`로 지정, 태그로 PassRole 통제, Role Manager ⚠️(신규 고객 불가) 신규 도입, 허용(Allow) 조건만으로 필수 통제를 강제.
- 근거: 〔S1〕〔S5〕〔S12〕〔S43〕〔S45〕〔S89〕

### 패턴 2. 격리·암호화 요구 → 설정 선택 (SK5, K2, K3)
- 시나리오 단서: "훈련 컨테이너가 데이터를 외부로 보낼 수 없어야 한다", "인터넷 없이 S3의 데이터로 훈련", "VPC 안의 RDS에 접근하는 훈련", "분산 훈련 노드 간 트래픽까지 암호화", "Studio를 인터넷 없이 운영", "온프레미스에서 SageMaker API 호출".
- 정답 방향: 컨테이너 외부 통신 완전 차단 → **네트워크 격리**(`EnableNetworkIsolation`); VPC 리소스 접근·트래픽 통제 → **VPC 모드**(`VpcConfig`, 사설 서브넷 + S3 게이트웨이 엔드포인트, 필요 시 NAT/인터페이스 엔드포인트); Studio 전체 → **`VpcOnly`** + 인터페이스 엔드포인트(`sagemaker.api`·`sagemaker.runtime` 등) 또는 NAT + 보안 그룹(NFS 2049 등); 노드 간 암호화 → **컨테이너 간 트래픽 암호화**(+ UDP 500·ESP 50 규칙); 온프레미스 접근 → 인터페이스 엔드포인트(게이트웨이 엔드포인트는 온프레미스 불가).
- 오답 유인(섞이는 선택지): NAT만 두고 격리했다고 판단, 보안 그룹만으로 컨테이너 egress 차단, 퍼블릭 서브넷에서 `VpcOnly`, 인터넷 게이트웨이로 S3 접근, "분산 훈련 노드 간 통신은 기본으로 암호화된다"(기본은 비암호화 구간), AWS 관리형 S3 키로 교차 계정 접근.
- 근거: 〔S19〕〔S20〕〔S23〕〔S17〕〔S16〕〔S85〕

### 패턴 3. 감사·모니터링 질문 → 서비스 매칭 (SK3)
- 시나리오 단서: "누가 엔드포인트를 만들고 지웠나", "엔드포인트를 누가 호출했는지 추적", "구성 변경 이력과 규정 준수 자동 평가", "S3 학습 데이터에 개인정보가 있는지", "컨테이너 로그와 경보", "훈련 클러스터 네트워크 흐름".
- 정답 방향: 제어 영역 호출자 → **CloudTrail 관리 이벤트**; 엔드포인트 호출자 → **CloudTrail 데이터 이벤트**(`AWS::SageMaker::Endpoint`, 별도 활성화); 구성 이력·규칙 평가 → **AWS Config**; 로그·경보 → **CloudWatch**; S3 민감 데이터 → **Macie**; 네트워크 흐름 → **VPC Flow Logs**.
- 오답 유인(섞이는 선택지): CloudWatch로 API 호출자 식별, Config로 API 호출 기록 추적, "기본 trail이 `InvokeEndpoint`까지 기록한다"(데이터 이벤트는 기본 미기록), CloudTrail Lake ⚠️를 새 계정의 해법으로 선택, GuardDuty·Inspector·Security Hub·Audit Manager·Artifact처럼 가이드 범위 외 서비스.
- 근거: 〔S28〕〔S38〕〔S39〕〔S29〕〔S40〕〔S3〕

### 패턴 4. 오류 증상 → 원인 → 조치 (SK4)
- 시나리오 단서: "`not authorized to perform: iam:PassRole`", "`AmazonSageMakerFullAccess`가 있는데도 S3 `AccessDenied`", KMS로 암호화된 버킷, "Studio(`VpcOnly`)가 `Connection timed out`", "`no resource-based policy allows the sagemaker:CreateModel action`", "노트북 인터넷 차단 후 훈련 호출 실패".
- 정답 방향: **권한 문구**면 ID 기반 정책 → 리소스 정책(S3·ECR·KMS·모델 패키지 그룹) → 권한 경계·SCP 순서로 좁히고(KMS는 `kms:Encrypt`·`kms:Decrypt`·`kms:CreateGrant`), **타임아웃**이면 엔드포인트·NAT·라우트 테이블·보안 그룹을 점검, 호출 사실은 CloudTrail로 확인.
- 오답 유인(섞이는 선택지): 곧바로 관리자 권한 부여, 보안 그룹 전체 개방, 퍼블릭 서브넷으로 이동, 네트워크 격리를 끄는 것으로 해결 시도, 사용자 정책에만 S3 권한 추가(PassRole·KMS·버킷 정책 무시).
- 근거: 〔S4〕〔S59〕〔S62〕〔S23〕〔S60〕〔S91〕

- 참고: 비교 페이지는 '추가'된 항목만 번호(예: 1.1.7)로 나열하며, 번호가 건너뛰는 항목(예: 1.1.1~1.1.6)이 C01의 어느 항목에 대응하는지는 **설명하지 않는다**.

- [G-4.3-1] 조건 키 이름 — `sagemaker:VolumeKmsKey`(구)와 `sagemaker:VolumeKmsKeyArn`(현재) 중 시험 보기가 쓰는 이름은? — 확인한 곳: Service Authorization Reference는 구 키를 deprecated로 표시하고 `...Arn`을 대체 키로 명시〔S11〕. 예제 페이지는 본문에 `VolumeKmsKey`, JSON에는 `VolumeKmsKeyArn`을 쓰고〔S3〕, 백서는 `VolumeKmsKey`를 쓴다〔S12〕 — 제안: 학습문서·문항에서 두 이름을 병기하고, 키 이름 자체를 정답 근거로 삼지 않는다.
- [G-4.3-2] CloudTrail `InvokeEndpoint` 기록 — 현재 SageMaker 문서는 `AWS::SageMaker::Endpoint` 데이터 이벤트로 선택 기록할 수 있다고 명시한다〔S28〕. 과거 문서나 시험 대비 자료가 "InvokeEndpoint는 기록되지 않는다"고 서술했는지, 데이터 이벤트 지원 시작 시점이 언제인지는 확인하지 못했다 — 확인한 곳: 현재판 CloudTrail 문서, What's New 검색(해당 공지 미발견) — 제안: 문항은 "데이터 이벤트를 별도로 켜야 기록된다"를 정답 조건으로 명시하고, 구판 서술을 따르는 시험 지문 가능성은 컨트롤러가 MLA-C02 비교와 함께 판단한다.
- [G-4.3-3] Role Manager 신규 고객 중단 날짜 — 개별 공지 페이지(`role-manager-availability-change.html`)에는 날짜가 없고〔S8〕, 날짜(2026-07-30)는 SageMaker AI 기능 묶음 공지에서 확인했다〔S55〕 — 제안: 학습문서는 두 페이지를 함께 인용한다(컨트롤러 공지 L3와 일치).
- [G-4.3-4] 새 "IAM role manager"(AWS Security Blog) — 게시일과 IAM User Guide 문서 위치를 확인하지 못했다. MLA-C01 가이드 범위가 아니다〔S10〕 — 제안: SageMaker Role Manager와의 혼동 주의 한 줄로만 다룬다.
- [G-4.3-5] VPC 모드 SageMaker 작업의 ECR 인터페이스 엔드포인트 요구 여부 — SageMaker 훈련·처리 문서는 SageMaker가 컨테이너 이미지를 ECR에서 자동으로 가져온다고만 서술한다〔S20〕〔S93〕. 백서는 데이터 과학자 환경에 ECR 엔드포인트를 권장하고〔S13〕, Studio `VpcOnly` 필수 엔드포인트 목록에는 ECR이 없으며〔S23〕, ECR 문서는 ECR을 직접 쓰는 클라이언트의 엔드포인트 구성을 안내한다〔S78〕 — 제안: "ECR 엔드포인트 필수"를 정답이나 오답의 근거로 쓰지 않는다.
- [G-4.3-6] VPC 모드 훈련 실패의 정확한 오류 문구(예: S3 데이터 다운로드 실패 메시지) — 확인한 SageMaker 공식 문서에서 찾지 못했다. 본문은 원인(S3 엔드포인트·NAT·라우트 테이블·보안 그룹)만 서술한다〔S20〕 — 제안: 오류 문구를 정답 단서로 쓰지 않는다.
- [G-4.3-7] re:Post 문서의 표기 오류 — S3 AccessDenied 문서가 `CreateTrainingJob`에 필요한 권한을 "s3:ListObject"로 적었으나〔S59〕, SageMaker 문서의 정책 예시는 `s3:ListBucket`이다〔S1〕 — 제안: 학습문서는 S1의 `s3:ListBucket`을 쓴다.
- [G-4.3-8] Studio `VpcOnly` 포트 규칙의 적용 범위 — 해당 문서는 Jupyter Server·Kernel Gateway(Studio Classic 구조) 용어로 TCP 8192–65535를 설명하며〔S23〕, 새 Studio(JupyterLab·Code Editor 공간)에도 같은 범위가 적용되는지 구분하지 않는다. NFS 2049는 `CreateDomain` API 문서가 Studio 앱 실행에 필수라고 명시한다〔S25〕 — 제안: 포트 범위를 문항 근거로 쓸 때 "문서 기준"임을 밝힌다.
- [G-4.3-9] 규정 준수 프로그램 목록 — SageMaker AI의 Compliance validation 문서는 개별 프로그램(HIPAA·PCI DSS·SOC 등)을 나열하지 않는다〔S48〕. HIPAA 적격 여부만 HIPAA 목록에서 확인했고(갱신일 2026-10-15)〔S49〕, 그 밖의 프로그램은 게시일을 확인하지 못한 오래된 블로그에만 있어 본문에 쓰지 않았다 — 제안: 규정 준수 문항은 "범위 확인은 AWS Services in Scope by Compliance Program, 보고서는 AWS Artifact, HIPAA는 적격 서비스 목록"까지만 출제한다.
- [G-4.3-10] CodeBuild 보안 모범 사례 단일 페이지 — 해당 URL(`.../codebuild/latest/userguide/security-best-practices.html`)이 CodeBuild 개요 페이지로 리다이렉트되어 전용 페이지를 확인하지 못했다 — 제안: 데이터 보호〔S71〕·VPC〔S72〕·서비스 역할〔S73〕·환경 변수 API〔S70〕 문서와 AWS Security Blog〔S74〕를 개별 근거로 쓴다.
- [G-4.3-11] Config 관리형 규칙의 나머지 — 규칙 목록에는 `sagemaker-` 접두 규칙이 더 있다(이름만 확인: 데이터 품질·모델 편향·모니터링 스케줄의 격리 규칙, Feature Group 암호화 규칙 등)〔S90〕. 세부 동작과 트리거는 2.12 표의 8개 규칙만 확인했다 — 제안: Config 문항은 그 8개 범위에서 출제한다.
- [G-4.3-12] 범위 외 서비스 목록의 출처 — MLA-C01 가이드 부록(영문 PDF Version 1.0)의 범위 외 목록(AWS Artifact·AWS Audit Manager·Amazon GuardDuty·Amazon Inspector·AWS Security Hub·AWS WAF·AWS Resource Access Manager 등)은 로컬 PDF 추출본에서 확인했고 공개 URL을 출처로 달지 않았다 — 제안: 컨트롤러가 가이드 PDF URL로 출처를 보완한다. Model Registry 공유에 쓰이는 AWS RAM은 범위 외라 본문에서 다루지 않았다.
- [G-4.3-13] 한국어 표기 — ko_kr 문서는 기계 번역 페이지이며 영어판이 우선한다는 고지가 붙어 있다. 확인한 표기: 실행 역할, 역할 전달, SageMaker 역할 관리자(Role Manager), 네트워크 격리, 컨테이너 간 트래픽 암호화, 프라이빗 서브넷, `VPC only`(VPC 전용 모드), 관리 이벤트·데이터 이벤트, 이벤트 기록(Event history), 추적(trail). 확인한 ko_kr 페이지: sagemaker-roles, role-manager, mkt-algo-model-internet-free, train-encrypt, studio-notebooks-and-internet-access, logging-using-cloudtrail — 제안: 학습문서는 영어 용어를 병기한다.
- [G-4.3-14] 교차 계정 모델 배포 예제 정책의 범위 — 문서의 예제 코드는 ECR에 `ecr:*`, S3에 `s3:*`처럼 넓은 권한을 상대 계정에 준다〔S56〕. 이를 더 좁힐 수 있는지는 문서에 없다 — 제안: 문항에서 "예제 그대로가 최소 권한"이라고 단정하지 않는다.
- [G-4.3-15] 레포 `MLA-C01.json` 수정 제안 — 없음.
