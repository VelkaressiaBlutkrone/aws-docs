### 2.1 데이터 형식 한눈에 보기 — 행 기반·열 기반·RecordIO (K1, SK2)

형식을 고르는 기준은 "누가, 어떻게 읽는가"다. (a) 분석 엔진(Athena·Spark)이 많은 열 중 일부만 반복해서 읽는지, (b) 수집·스트리밍 파이프라인이 레코드를 계속 쓰는지, (c) SageMaker 알고리즘이 정해진 `ContentType` 만 받는지에 따라 정답이 달라진다.

| 형식 | 저장 방식 | 강점 · 쓰는 때 | 약점 · 제약 | 근거 |
|---|---|---|---|---|
| CSV | 행 기반. AWS Glue 문서 표현은 "minimal, row-based" | 단순·범용. SageMaker 내장 알고리즘 다수가 `text/csv` 로 받음 | 열 단위 선택·통계 기반 건너뛰기 불가. 압축된 텍스트는 일반적으로 병렬 처리 불가. 값에 따옴표가 있으면 Athena에서 Open CSV SerDe 필요 | 〔S12〕〔S1〕〔S8〕〔S16〕 |
| JSON / JSON Lines | 행 기반 텍스트(중첩 가능) | 이벤트·로그 같은 반정형 데이터. Firehose 형식 변환의 입력. JSON Lines(`application/jsonlines`)는 BlazingText·DeepAR 입력, Object2Vec 도 JSON Lines | CSV와 같은 텍스트 제약. Firehose 변환은 JSON 문서를 배열로 묶은 입력을 허용하지 않음 | 〔S18〕〔S1〕〔S2〕 |
| Avro | 행 기반. Glue 문서 표현은 "performance-oriented, row-based" | 쓰기가 잦은 수집·스트리밍. 백서: 읽기보다 쓰기가 잦을 때 유리 | 백서: Parquet·ORC가 Avro보다 압축이 좋음 | 〔S10〕〔S14〕 |
| Parquet | 열 기반. Glue 문서 표현은 "performance-oriented, column-based" | 읽기 중심 분석. Spark SQL에서 공식 권장. Athena는 필요한 열·블록만 읽음. SageMaker XGBoost·DeepAR 가 입력으로 받음 | 파일이 너무 작으면 열 기반 오버헤드가 이점을 넘음. Athena가 Parquet의 복합 타입(array·map·struct) 열을 읽으면 행 전체를 읽는 알려진 한계 → ORC가 대안 | 〔S11〕〔S7〕〔S9〕〔S15〕〔S3〕〔S2〕 |
| ORC | 열 기반. Glue 문서 표현은 "performance-oriented, column-based" | Athena 문서: 파일이 더 작은 편이고 ORC 인덱스가 쿼리를 빠르게 할 수 있으며 복합 타입을 폭넓게 지원 | 복잡한 쿼리 범위는 Parquet이 더 넓다고 서술됨 | 〔S13〕〔S7〕 |
| RecordIO-protobuf | SageMaker가 정의한 이진 레코드. 관측값을 4바이트 float 집합으로 바꿔 protobuf `values` 필드에 담음 | 내장 알고리즘 다수의 표준 입력. Pipe 모드와 함께 쓰임 | 직접 만들려면 변환 필요(Python이면 제공되는 변환 사용을 강하게 권장) | 〔S1〕〔S2〕〔S5〕 |

- **RecordIO 이름 혼동**: `application/x-recordio` 는 Object Detection(MXNet) 의 content type이고, `application/x-recordio-protobuf` 는 Factorization Machines·K-Means·k-NN·LDA·Linear Learner·NTM·PCA·RCF·Sequence-to-Sequence 가 쓰는 SageMaker protobuf 형식이다. 이미지 분류·객체 탐지(MXNet) 알고리즘은 recordIO 또는 이미지 파일을 받는다. 〔S1〕〔S2〕
- **기본 블록 크기**: Parquet row group 기본 128 MB, ORC stripe 기본 64 MB. 기본값보다 줄이는 것은 권장되지 않고, 열이 많으면 키우는 편이 성능에 유리하다. 〔S8〕 Athena 문서는 Parquet 블록 128 MB·ORC 스트라이프 64 MB 가 기본이며 ORC 스트라이프가 8 MB 미만이면 Athena가 스트라이프 전체를 읽는다고 적고 있다. 〔S9〕

> 🧠 원리: 열 기반이 분석에 유리한 이유는 공식 문서에 이렇게 정리돼 있다. 쿼리에 필요한 열만 읽고, 같은 열의 값이 모여 있어 압축 효율이 높으며, 파일 메타데이터(예: 최솟값·최댓값)로 필요 없는 데이터를 건너뛴다. 〔S8〕 Athena는 압축 해제 전 스캔 바이트 수로 요금을 매기므로 압축과 열 기반이 속도와 비용을 함께 줄인다. 〔S8〕 압축 텍스트(CSV·JSON)는 대부분의 압축 형식이 파일을 처음부터 읽어야 해서 병렬 처리가 제한되는 반면, Parquet·ORC는 내부 블록 단위로 여러 reader가 나눠 읽을 수 있다. 〔S8〕〔S7〕

### 2.2 데이터 접근 패턴별 형식 선택 가이드 (SK2, K1)

| 데이터 접근 패턴 | 권장 | 이유 (공식 문서 근거) | 근거 |
|---|---|---|---|
| 수 TB 로그를 Athena·Spark SQL로 쿼리, 일부 열만 반복 조회 | Parquet(또는 ORC) + 압축 + 파티션 | 필요한 열·블록만 읽어 스캔 바이트 감소 | 〔S7〕〔S8〕〔S15〕 |
| Athena에서 array·map·struct 같은 복합 타입 열을 자주 조회 | ORC 고려 | Parquet는 복합 타입 열 조회 시 행 전체를 읽는 알려진 한계. ORC는 복합 타입 지원이 넓음 | 〔S9〕〔S7〕 |
| 쓰기가 잦은 수집·스트리밍 단계 | Avro(이후 분석용으로 Parquet·ORC 변환) | 행 기반은 쓰기가 잦을 때 유리, Parquet·ORC는 읽기 위주 | 〔S14〕 |
| JSON 스트림을 S3에 쌓아 바로 쿼리 | Firehose 형식 변환(JSON → Parquet·ORC) | 변환은 Glue Data Catalog 스키마를 참조 | 〔S18〕 |
| 소량 교환용·사람이 읽는 데이터 | CSV·JSON(+압축) | 단순하지만 열 선택 불가, 압축 시 병렬성 제약 | 〔S8〕〔S12〕 |
| SageMaker 내장 알고리즘 대용량 학습 | RecordIO-protobuf(+Pipe) 또는 알고리즘이 받는 CSV | 알고리즘마다 받는 content type 이 정해져 있음 | 〔S1〕〔S2〕 |
| XGBoost 학습 입력을 열 기반 파일로 | Parquet(`application/x-parquet`) | XGBoost 지원 형식 | 〔S3〕 |
| 작은 파일 수백만 개(이미지 등)를 File 모드로 학습 | 큰 파일 컨테이너로 직렬화(TFRecord·WebDataset·RecordIO) | File 모드는 파일마다 내려받는 오버헤드가 큼 | 〔S6〕 |

- **형식 변환 도구**: Athena `CREATE TABLE AS SELECT`(CTAS) 한 번으로 Parquet·ORC 변환, 또는 AWS Glue ETL·크롤러. Glue로 CSV→ORC, JSON→Parquet·ORC 도 같은 방식으로 가능하다. 〔S7〕〔S83〕
- **압축**: Athena는 gzip(호환 범위 넓음)과 zstd(성능·압축률 균형) 등을 지원한다. 〔S8〕 CSV·TSV·JSON 은 파일 확장자로 압축 형식을 판단하고, 확장자가 없으면 비압축 평문으로 본다. ZIP 은 지원하지 않고 `tar.gz` 도 지원하지 않는다. 〔S17〕
- **작은 파일 문제**: 작은 파일이 많으면 쿼리 계획·요청 오버헤드가 커지고, 극단적이면 S3 요청 한도에 걸려 `SlowDown` 오류가 난다. 해결은 쓰기 전에 파일을 크게 쓰거나 Glue ETL로 합치는 것이다. 〔S8〕 (증상별 조치는 2.10)
- **파티션**: 파티션 키로 필터하면 일치 파티션만 읽는다. 키가 너무 많으면 작은 파일이 양산되고 너무 적으면 스캔량이 늘어난다. 자주 쓰는 쿼리에 맞춰 설계하고 드문 쿼리는 최적화 대상에서 뺀다. 〔S8〕

### 2.3 SageMaker 학습 입력 형식과 content type (K1)

학습 전 전처리 결과는 S3에 게시되고, 학습 단계에서는 "학습 데이터 직렬화(사용자) → 역직렬화(알고리즘)" 변환이 일어난다. 학습을 시작할 때 데이터를 한꺼번에 올려 두어야 하며, 같은 위치에 데이터를 더 추가하면 새 모델을 만들기 위해 새 학습 호출이 필요하다. 〔S1〕

**(1) content type → 알고리즘** (공식 표는 "commonly supported" 일부 목록) 〔S1〕

| ContentType | 알고리즘 |
|---|---|
| `text/csv` | IP Insights, K-Means, k-NN, LDA, Linear Learner, NTM, PCA, RCF, XGBoost |
| `application/x-recordio-protobuf` | Factorization Machines, K-Means, k-NN, LDA, Linear Learner, NTM, PCA, RCF, Sequence-to-Sequence |
| `application/x-recordio` | Object Detection |
| `application/jsonlines` | BlazingText, DeepAR |
| `text/libsvm` | XGBoost |
| `application/x-image`, `image/jpeg`, `image/png` | Object Detection, Semantic Segmentation |

**(2) 알고리즘별 입력 모드·파일 형식** (표 "Parameters for Built-in Algorithms") 〔S2〕

| 입력 모드 | 알고리즘 : 파일 형식 |
|---|---|
| File 만 | AutoGluon-Tabular·CatBoost·IP Insights·LightGBM·TabTransformer·Text Classification-TensorFlow : CSV / DeepAR : JSON Lines 또는 Parquet / Object2Vec : JSON Lines / Seq2Seq : recordIO-protobuf / Image Classification-TensorFlow·Object Detection-TensorFlow : 이미지 파일 |
| File 또는 Pipe | Factorization Machines : recordIO-protobuf / K-Means·k-NN·LDA·Linear Learner·NTM·PCA·Random Cut Forest : recordIO-protobuf 또는 CSV / XGBoost : CSV·LibSVM·Parquet / BlazingText : 텍스트 파일 / Image Classification-MXNet·Object Detection-MXNet : recordIO 또는 이미지 / Semantic Segmentation : 이미지 |

**(3) 자주 걸리는 형식 규칙**

- **CSV**: 헤더 레코드가 없어야 하고 타깃(레이블) 변수는 첫 번째 열이어야 한다. 레이블이 없는 비지도 알고리즘은 content type 에 레이블 열 수를 적는다(예: `content_type=text/csv;label_size=0`). 〔S1〕 XGBoost도 CSV 입력에 헤더 레코드가 없어야 하며, 열 기반 입력에서는 첫 열을 레이블로 가정한다. 〔S3〕
- **XGBoost**: `text/libsvm`(기본), `text/csv`, `application/x-parquet`, `application/x-recordio-protobuf` 를 지원하고, 공식 문서는 성능을 위해 File 모드 사용을 권장한다. 〔S3〕
- **Linear Learner**: 학습은 recordIO-wrapped protobuf 와 CSV 를 지원하고 둘 다 File·Pipe 모드로 쓸 수 있다. `application/x-recordio-protobuf` 입력은 Float32 텐서만 지원한다. 〔S4〕
- **RecordIO-protobuf**: 관측값을 4바이트 float 집합의 이진 표현으로 바꿔 protobuf `values` 필드에 담는다. 만든 protobuf 는 S3에 두고 `create_training_job` 의 `InputDataConfig` 로 넘긴다. 〔S1〕
- **Pipe 모드와 형식**: Pipe 모드용 TensorFlow 확장은 텍스트·TFRecord·RecordIO 형식을 스트리밍한다. 〔S5〕

**(4) 가이드의 "유효성이 검증된 형식 및 검증되지 않은 형식"**

공식 문서에서 이 용어를 정의해 설명하는 페이지는 찾지 못했다(섹션 9 [G-1.1-1]). 아래는 이 문구와 겹칠 수 있는 공식 메커니즘이며, 같은 개념이라고 단정하지 않는다.

- AWS Glue Schema Registry 는 Kinesis 스트림으로 생산되는 데이터가 등록된 스키마로 지속적으로 검증되도록 한다. 〔S32〕
- Firehose 형식 변환은 Glue Data Catalog 의 스키마를 참조하고, 스키마가 입력 구조와 맞지 않으면 변환된 데이터에 스키마에 없는 속성이 빠진다. 〔S18〕
- SageMaker 알고리즘은 형식 규칙(예: CSV 헤더 없음·레이블 첫 열)을 요구한다. 〔S1〕

> 🧠 원리: SageMaker 학습의 입력 형식은 "알고리즘 컨테이너가 역직렬화할 수 있는 형식"으로 정해진다. 그래서 분석용으로 좋은 Parquet 이어도 그 알고리즘이 받는 content type 이 아니면(예: Linear Learner 는 recordIO-protobuf 또는 CSV) 입력이 되지 않는다. 〔S2〕〔S4〕

### 2.4 SageMaker 학습의 데이터 소스와 입력 모드 (K2)

SageMaker 학습 잡이 데이터를 읽는 위치는 **Amazon S3, Amazon EFS, Amazon FSx for Lustre** 세 가지다. 학습 잡을 만들 때 저장 위치와 입력 모드를 함께 지정하며, 데이터셋은 학습 잡과 같은 AWS 리전에 있어야 한다. 〔S5〕

| 방식 | 정의 | 지원 소스 | 고르는 기준 | 제약 | 근거 |
|---|---|---|---|---|---|
| File (기본값) | 학습 시작 전에 S3 데이터를 컨테이너의 로컬 디렉터리로 모두 내려받고, 다 받은 뒤 학습 시작 | S3 prefix·manifest·augmented manifest | 데이터가 비교적 작을 때(예: 50–100 GB 미만). SageMaker 로컬 모드와 호환 | 학습 인스턴스 스토리지에 전체 데이터가 들어가야 함. 다운로드 시간은 데이터 크기·파일 평균 크기·파일 수에 좌우 | 〔S5〕〔S6〕 |
| FastFile | S3 객체를 POSIX 호환 파일 시스템 인터페이스로 노출하고, 읽는 시점에 스트리밍. 시작 전 전체 다운로드 없음 | S3 prefix 만 (manifest·augmented manifest 불가) | 더 큰 데이터셋·큰 파일(50 MB 초과)에서 먼저 시도. 파일 컨테이너 150 MB 초과에 이상적. FSx 와 달리 파일 시스템·VPC 가 필요 없음 | 순차 읽기에 최적(임의 읽기는 가능하나 처리량 저하). CloudTrail 기록 증가로 비용이 늘 수 있음. S3 prefix 의 파일이 적을수록 시작이 빠름 | 〔S5〕〔S6〕 |
| Pipe | S3 데이터를 높은 동시성으로 프리페치해 이름 있는 FIFO 파이프로 스트리밍. 디스크에는 최종 모델 아티팩트 분량만 필요 | S3 (알고리즘이 Pipe 를 지원할 때: 2.3 표) | 시작 시간 단축·EBS 크기 절감이 필요한 대용량 | 각 파이프는 한 프로세스만 읽을 수 있음. 더 새롭고 쓰기 쉬운 FastFile 로 대부분 대체되는 추세 | 〔S5〕〔S2〕 |
| FSx for Lustre | 학습 시작 시 파일 시스템을 마운트. 마운트는 저장된 데이터 크기와 무관하게 빠름 | FSx for Lustre (보통 S3 버킷과 연결, 읽을 때 지연 로딩) | 데이터가 File 모드에는 너무 크거나, 직렬화하기 어려운 작은 파일이 많거나, 임의 읽기 패턴일 때 | VPC 연결 필수. 파일 시스템이 단일 AZ 이므로 그 AZ 의 서브넷 지정 필요. 지연 로딩 콜드 스타트와 파일 시스템 초기화 오버헤드 | 〔S5〕〔S6〕〔S72〕 |
| EFS | 학습 시작 시 EFS 를 마운트 | EFS | 학습 데이터가 이미 EFS 에 있을 때 | 학습 전에 데이터가 EFS 에 있어야 함. VPC 연결 필수 | 〔S5〕〔S6〕 |
| S3 Express One Zone | 단일 AZ 고성능 스토리지 클래스(디렉터리 버킷)를 입력 위치로 사용 | S3 Express One Zone directory bucket (File·FastFile·Pipe 모두) | 지연 민감한 학습 | 출력은 SSE-S3 만 가능(SSE-KMS 미지원) | 〔S5〕〔S61〕 |

- **분산 학습 분할**: File 모드에서 여러 인스턴스로 학습할 때 `ShardedByS3Key` 로 데이터셋을 인스턴스 간에 나눈다. 〔S5〕
- **선택 흐름(SageMaker 공식 가이드)**: ① 데이터가 이미 EFS 에 있으면 EFS → ② S3 에 있고 비교적 작으면(50–100 GB 미만) File → ③ 작지만 작은 파일이 많으면 큰 컨테이너(TFRecord·WebDataset·RecordIO 등, 예: 파일당 150 MB)로 직렬화 → ④ 더 크고 큰 파일(50 MB 초과)이면 먼저 FastFile → ⑤ File 모드에 너무 크거나 작은 파일을 못 묶거나 임의 읽기면 FSx for Lustre. 〔S6〕

> **FSx for NetApp ONTAP 은 SageMaker 학습의 직접 데이터 소스인가?** SageMaker 학습의 지원 소스 목록은 S3·EFS·FSx for Lustre 이며 FSx for NetApp ONTAP 은 들어 있지 않다. 〔S5〕 다만 FSx for ONTAP 볼륨에 **S3 access point** 를 붙이면 `GetObject`·`PutObject` 같은 S3 객체 연산으로 파일 데이터를 읽고 쓸 수 있고, 데이터는 ONTAP 파일 시스템에 그대로 남아 NFS·SMB 접근도 유지된다. 〔S75〕 AWS 뉴스 블로그는 이 기능으로 파일 데이터를 SageMaker 모델 학습 등 S3 연동 서비스에 쓸 수 있다고 소개한다. 〔S76〕 즉 "S3 호환 경로"로 쓰는 것이지 학습 채널로 직접 마운트하는 것으로 문서에 적혀 있지는 않다(섹션 9 [G-1.1-2]).

> 🧠 원리: File 모드는 "전부 내려받은 뒤 학습"(그동안 학습 시작 불가), FastFile·Pipe 는 "읽는 만큼 스트리밍", FSx·EFS 는 "파일 시스템을 마운트"하는 구조다. 〔S5〕 그래서 시작 지연·디스크 용량 문제는 스트리밍(FastFile·Pipe)이나 마운트(FSx·EFS)로 풀고, 작은 파일 수가 문제면 직렬화하거나 FSx 로 간다. 〔S6〕

**(3) Kinesis Data Streams 핵심**

- 데이터 레코드는 시퀀스 번호·파티션 키·데이터 blob 으로 이루어지고, 파티션 키는 MD5 해시로 128비트 정수에 매핑되어 샤드의 해시 키 범위로 배정된다. 〔S28〕 레코드를 쓸 때는 항상 파티션 키를 지정해야 한다. 〔S27〕
- 샤드 하나의 용량은 읽기 최대 초당 5 트랜잭션·총 2 MB/s, 쓰기 초당 1,000 레코드·총 1 MB/s 이고 스트림 용량은 샤드 용량의 합이다. 〔S28〕 `PutRecords` 한 요청은 최대 500 레코드. 〔S26〕
- **용량 모드**

| 모드 | 용량 관리 | 과금 | 고르는 때 | 주의 | 근거 |
|---|---|---|---|---|---|
| Provisioned | 샤드 수를 직접 지정(`UpdateShardCount` 로 조정) | 샤드 시간당 | 예측 가능한 트래픽, 샤드 분할 같은 세밀한 제어 | 피크에 맞추지 못하면 예외 발생 → 수동 확장 | 〔S27〕〔S28〕 |
| On-demand Standard | 자동 확장. 직전 30일 피크의 2배까지 수용 | 읽고 쓴 GB 당 | 변동이 크고 예측하기 어려운 트래픽 | 직전 피크의 2배를 넘으면 약 15분간 쓰기 예외 가능. 파티션 키가 불균형하면 해결 못 함 | 〔S27〕 |
| On-demand Advantage | 계정 수준 설정. warm throughput 으로 용량 사전 확보 가능 | 스트림당 고정 요금 없음, 최소 25 MiB/s 수집·25 MiB/s 읽기 약정 | 일정한 대량 처리량·많은 EFO 소비자·수백 개 스트림 | 활성화 후 최소 24시간 유지 | 〔S27〕 |

- **보존 기간**: 기본 24시간, 최대 8760시간(365일). 늘리면 24시간 초과분에 추가 요금이 붙고, 줄이면 새 보존 기간보다 오래된 레코드에 거의 즉시 접근할 수 없게 된다. 〔S29〕〔S28〕
- 새 on-demand 스트림은 기본적으로 쓰기 4 MB/s·읽기 8 MB/s 로 시작한다. 모드 전환은 스트림당 24시간에 두 번까지. 〔S26〕

**(4) Amazon Data Firehose 핵심**

- 대상: S3, Redshift, OpenSearch Service·Serverless, Splunk, Apache Iceberg Tables, HTTP 엔드포인트(서드파티 포함). 소스는 직접 PUT 또는 기존 Kinesis 데이터 스트림(MSK 도 한도 문서에 소스로 등장). 레코드는 최대 1,000 KB. 〔S19〕〔S23〕
- **버퍼**: 버퍼 크기(MB)와 버퍼 간격(초) 중 먼저 만족하는 조건에서 전달한다. S3 는 크기 1–128 MB(기본 5)·간격 0–900초(기본 300). 〔S20〕 전달이 뒤처지면 버퍼 크기를 자동으로 키워 따라잡는다. 〔S20〕 Parquet 변환·동적 파티셔닝을 켜면 S3 버퍼 크기는 64–128 MB(기본 128). 〔S24〕
- **Lambda 변환**: 버퍼 크기 힌트 0.2–3 MB(기본 1 MB), 간격 0–900초(기본 60초). Lambda 를 동기 호출하며 요청·응답 페이로드 한도는 6 MB, 호출 시간은 최대 5분이다. 〔S21〕
- **형식 변환**: 입력은 JSON 만 받아 Parquet·ORC 로 변환한다(CSV 같은 형식은 Lambda 로 먼저 JSON 으로 바꿈). 역직렬화기(Hive JSON SerDe·OpenX JSON SerDe)·Glue Data Catalog 스키마·직렬화기(Parquet·ORC SerDe) 3요소가 필요하다. 〔S18〕
- 변환(Lambda)·형식 변환을 쓰는 경우 원본을 다른 S3 버킷에 백업할 수 있다(소스가 Direct PUT 또는 KDS 일 때). 〔S19〕〔S20〕
- Direct PUT 소스에는 스트림당 합산 쿼터(예: us-east-1·us-west-2·eu-west-1 은 500,000 records/s·2,000 requests/s·5 MiB/s, 그 밖의 리전은 100,000 records/s·1,000 requests/s·1 MiB/s)가 있고, 한도를 넘으면 자동으로 한도를 올리되 시간이 걸리므로 실패한 레코드를 계속 재시도해야 한다. 소스가 KDS 이면 이 쿼터가 적용되지 않고 Firehose 가 한도 없이 확장된다. 〔S23〕

**(5) Managed Service for Apache Flink 와 MSK 핵심**

- Flink: 장시간 실행되는 스트리밍 ETL·연속 애플리케이션이면 IDE 로 만드는 Flink 애플리케이션, 임시 탐색·대화형 쿼리면 Studio 노트북을 권장한다. 〔S36〕 SQL 전용이던 KDA for SQL 애플리케이션은 종료되었다(2.11). 〔S38〕
- MSK: 기존 애플리케이션·도구·플러그인을 코드 변경 없이 지원한다. 〔S39〕 MSK Serverless 는 용량을 자동으로 프로비저닝·확장하고 처리량 기반 요금이며 Kafka ACL 은 미지원이다. 〔S40〕
- KDS vs MSK: 스트리밍이 처음이면 KDS, 이미 Kafka 로 돌아가는 애플리케이션이면 MSK. 〔S33〕 백서 표는 관리 오버헤드를 KDS "Low", MSK "Low(Serverless)~Medium(Provisioned)" 로, 보존을 KDS 최대 365일·MSK 설정 가능(계층형 저장소로 S3 활용)으로 비교한다. 〔S35〕 백서는 오픈소스 기술이 전략상 중요하고 Kafka 에 익숙하며 70 ms 미만의 실시간 지연을 원하면 Kinesis 보다 MSK 를 권장한다고 적는다. 〔S34〕

> 🧠 원리: KDS 는 파티션 키를 해시해 샤드에 배정하므로 "키 분포"가 곧 처리량 분포다. 그래서 특정 키가 몰리면 샤드 하나만 한계에 닿는다. 〔S28〕 Firehose 는 버퍼가 차거나 시간이 되면 한 번에 내보내므로 "준실시간 + 큰 파일" 에 맞고, 파일을 키울수록 S3 요청 수와 작은 파일 문제가 줄어든다. 〔S20〕〔S8〕

### 2.6 스토리지 옵션 비교와 초기 구성 결정 — 비용·성능·데이터 구조 (K4, SK6)

스토리지는 **데이터 구조**(객체·공유 파일·블록·관계형·키-값) × **접근 패턴**(빈도·순차/임의·공유 여부) × **비용 구조**(사용량 과금·프로비저닝 과금·최소 보관 기간)로 고른다.

**(1) Amazon S3 스토리지 클래스** 〔S61〕

| 클래스 | 설계 용도 | 핵심 특징·제약 |
|---|---|---|
| S3 Standard | 자주 접근하는 데이터, 밀리초 접근. 클래스를 지정하지 않으면 기본 | 최소 보관 기간·최소 객체 크기 없음 |

**(4) 초기 스토리지 구성 결정 체크리스트 (SK6)**

1. **데이터 구조**: 객체 → S3, 공유 파일 → EFS(범용)·FSx(고성능·특화), 블록 → EBS, 관계형 → RDS, 키-값 → DynamoDB. 〔S61〕〔S70〕〔S72〕〔S65〕〔S81〕〔S80〕
2. **접근 빈도**: 자주 → Standard, 불확실 → Intelligent-Tiering, 드묾 → IA, 아카이브 → Glacier 계열(복원 필요). 〔S61〕
3. **학습 읽기 패턴**: 순차·큰 파일 → S3 + FastFile, 작은 파일 대량·임의 읽기 → FSx for Lustre, 이미 EFS 에 있는 데이터 → EFS. 〔S6〕
4. **성능**: 지속 IOPS → io2/io1, 대용량 순차 처리량 → st1, 병렬 고처리량 공유 파일 → FSx for Lustre. 〔S65〕〔S72〕
5. **비용 모델**: 임시 처리 → FSx for Lustre scratch, 장기·가용성 중요 → persistent. 〔S73〕 예측이 어려운 처리량 → EFS Elastic, 알고 있는 처리량 → Provisioned, 크기에 비례한 처리량 → Bursting. 〔S71〕 변동 큰 스트림 → KDS on-demand, 예측 가능 → provisioned. 〔S27〕
6. **위치**: 학습 데이터는 학습 잡과 같은 리전. EFS·FSx 는 VPC 필요, FSx for Lustre 는 단일 AZ. 〔S5〕

**(1) S3 Transfer Acceleration 상세** 〔S55〕

- **정의**: 클라이언트와 S3 범용 버킷 사이의 장거리 파일 전송을 빠르고 쉽고 안전하게 하는 **버킷 수준** 기능. CloudFront 의 전 세계 엣지 로케이션에 도착한 데이터를 최적화된 네트워크 경로로 S3 에 전달한다.
- **적합한 상황**: 전 세계 고객이 중앙 범용 버킷에 업로드 / 대륙 간 GB–TB 를 정기 전송 / 인터넷 대역폭을 업로드에 다 못 쓸 때. 멀리 떨어질수록 개선 폭이 크고, 큰 객체·많은 콘텐츠·빠른 인터넷 연결에 이상적이다. 〔S56〕
- **요구사항·제약**: 가상 호스트 스타일 요청만 지원 / 버킷 이름은 DNS 호환이어야 하고 마침표(".")가 없어야 함 / 버킷에서 기능을 켜야 하며 켠 뒤 속도가 오르기까지 최대 20분 / `bucket-name.s3-accelerate.amazonaws.com` 엔드포인트 사용(기존 엔드포인트도 계속 사용 가능) / 지원 리전 한정 / 추가 데이터 전송 요금 가능. 가속으로 이득을 볼 수 있는 전송에만 과금하며, Speed Comparison 도구로 효과를 먼저 확인할 수 있다. 〔S55〕〔S56〕

**(2) 멀티파트·객체 크기** — 파트 번호는 1–10,000이고 파트 크기 5 MiB–5 GiB(마지막 파트는 최소 없음). 완료 또는 중단 전에는 업로드된 파트의 저장 요금이 계속 붙으므로 `AbortIncompleteMultipartUpload` 수명주기 규칙을 권장한다. 〔S59〕〔S58〕 최대 객체 크기는 최신 문서 기준 "객체당 최대 50 TB(실제 한도 53.7 TB = 48.8 TiB)"이며, 오래된 자료의 5 TB 와 다르다(섹션 9 [G-1.1-5]). 〔S60〕〔S59〕

**(3) EBS Provisioned IOPS** — io1 은 4 GiB–16 TiB 볼륨에 100–64,000 IOPS 를 프로비저닝하고(비율 최대 50:1, 예: 100 GiB → 5,000 IOPS), 64,000 IOPS 는 Nitro 기반 인스턴스에서만 달성된다. 〔S66〕 io2 Block Express 는 최대 256,000 IOPS(IOPS:GiB 1,000:1)·4,000 MiB/s·평균 지연 500 µs 미만(16 KiB I/O)이며 2025-04-30 이후 모든 io2 가 Block Express 다. 〔S66〕 프로비저닝한 IOPS 성능을 99.9% 의 시간 동안 제공한다. 〔S66〕

> 🧠 원리: Transfer Acceleration 은 "지리적 거리 때문에 느린 구간"을 엣지 경유로 줄이는 것이고, 멀티파트·병렬 요청은 "한 연결의 처리량 한계"를 여러 연결로 푸는 것이다. 〔S55〕〔S56〕 둘은 목적이 달라 함께 쓸 수 있다.

### 2.9 여러 소스의 데이터 병합 (SK4)

| 상황 | 도구 | 이유·제약 | 근거 |
|---|---|---|---|
| 서버리스로 대규모 ETL, 여러 소스 조인, 카탈로그 필요 | **AWS Glue** (크롤러 → Data Catalog → Spark ETL 잡 + Join 변환) | 크롤러가 스키마를 추론해 Data Catalog 에 테이블을 만든다. Join 변환은 두 데이터셋을 키로 결합하고, 입력은 정확히 2개 | 〔S85〕〔S84〕 |
| SQL 로 S3 데이터(와 외부 소스)를 결합하고 결과를 새 테이블로 저장 | **Athena** (CTAS · Federated Query) | CTAS 로 쿼리 결과를 Parquet·ORC 등으로 저장. 연합 쿼리는 읽기 전용 | 〔S83〕〔S82〕 |
| Spark 클러스터를 직접 다루는 대규모 처리, 기존 Hadoop/Spark 자산 | **Amazon EMR** (Spark) | Hadoop·Spark 같은 빅데이터 프레임워크를 관리형 클러스터에서 실행 | 〔S92〕 |
| 비교적 작은 데이터(약 10 GB 이하)를 스크립트(pandas 등)로 병합 | Glue **Python shell** · AWS SDK for pandas | Python shell 은 소·중규모 기본 ETL(약 10 GB 이하)용. 1 DPU(16 GB) 또는 0.0625 DPU(1 GB). AWS SDK for pandas 는 pandas 를 Athena·Glue·Redshift·S3 등과 연결하는 AWS 오픈소스 라이브러리 | 〔S91〕〔S93〕 |
| 노코드/시각적 전처리 흐름에서 여러 소스 결합 | **Data Wrangler** 데이터 흐름 | 흐름에서 서로 다른 소스의 데이터셋을 결합 | 〔S45〕 |
| 스트림과 정적 데이터 결합 | Managed Service for Apache Flink · Glue 스트리밍 ETL | Glue 스트리밍 오토스케일링은 `ForEachBatch` 밖에서 만든 정적 DataFrame 과의 조인을 지원하지 않음 | 〔S34〕〔S88〕 |

- **Glue 크롤러 흐름**: 지정한 사용자 정의 분류기가 먼저 형식·스키마를 추론하고, 맞는 것이 없으면 내장 분류기(예: JSON)가 시도한다 → 데이터 스토어에 연결 → 추론된 스키마 생성 → Data Catalog 에 메타데이터(테이블)를 기록한다. 〔S85〕 크롤러는 파일 기반·테이블 기반 스토어를 모두 크롤할 수 있다. 〔S86〕
- **Glue Join**: 두 데이터셋의 키 이름을 지정해 결합하며 조인 유형(내부·왼쪽·오른쪽 등)을 고른다. 양쪽에 같은 이름의 키가 있으면 충돌 메시지가 나오는데, **Resolve it** 로 `ApplyMapping` 노드를 자동 추가(한쪽 키에 접두 부여)하거나 앞단에서 키를 제거·이름 변경한다. 〔S84〕
- **DynamoDB 는 JOIN 연산자가 없다.** 다른 소스와 결합하려면 S3 로 내보낸 뒤 Athena·Glue·EMR 등으로 처리한다. 〔S80〕〔S79〕
- **JDBC 소스(RDS 등)를 Glue 로 읽을 때** JDBC 읽기는 기본적으로 병렬화되지 않아 실행기 하나가 테이블 전체를 순차로 읽는다. 〔S89〕 (메모리 문제는 2.10)

> 🧠 원리: 병합의 전제는 "공통 스키마(카탈로그)와 맞는 키"다. Glue Data Catalog 테이블을 Athena 쿼리·Glue ETL·Firehose 형식 변환이 함께 참조하므로, 한 번 정의한 스키마를 여러 도구가 공유한다. 〔S85〕〔S18〕〔S8〕

### 짝 6. S3 Transfer Acceleration vs 멀티파트 업로드 vs prefix 분산 vs DataSync

### 후보 1 (난이도: associate)
- 대응 Skill: K1 / SK2
- 문제: 한 팀이 S3 에 쌓인 수 TB 의 gzip 압축 CSV 로그를 Athena 로 쿼리해 ML 특성을 만든다. 쿼리는 100여 개 열 중 3~4개만 반복해서 조회하고, 비용은 스캔한 바이트에 비례한다. 쿼리 성능과 비용을 가장 크게 개선하는 저장 방식 변경은?
- 보기:
  - A) gzip 파일 여러 개를 더 큰 gzip 파일 하나로 합친다.
  - B) 데이터를 Parquet 같은 열 기반 형식으로 변환하고 압축과 파티션을 적용한다.
  - C) 데이터를 Avro 형식으로 변환한다.
  - D) 데이터를 JSON Lines 로 바꾸고 ZIP 으로 압축한다.
- 정답: B
- 근거: 〔S7〕 https://docs.aws.amazon.com/athena/latest/ug/columnar-storage.html 〔S8〕 https://docs.aws.amazon.com/athena/latest/ug/performance-tuning-data-optimization-techniques.html
- 오답 근거: A) 압축된 텍스트 파일은 일반적으로 병렬 처리가 어렵고 열 선택도 불가능해 여전히 전체를 스캔한다 〔S8〕 / C) Avro 는 행 기반으로 쓰기가 잦은 수집에 적합하고, 읽기 중심 분석에는 Parquet·ORC 가 적합하다 〔S14〕 / D) Athena 는 ZIP 형식을 지원하지 않고 JSON Lines 도 행 기반 텍스트다 〔S17〕

## 9. 확인 필요 항목

- [G-1.1-1] 가이드 K1 의 "유효성이 검증된 형식 및 검증되지 않은 형식"(영문 "validated and non-validated formats")을 공식 문서가 어떻게 정의하는가? — AWS 문서 검색(검증 형식·스키마 검증 관련 질의), SageMaker 공통 데이터 형식 페이지, Firehose 형식 변환, Glue Schema Registry(KDS) 문서를 읽었으나 이 용어를 정의한 페이지는 찾지 못함. 겹칠 수 있는 메커니즘(2.3 (4))만 정리했고 같은 개념이라고 단정하지 않음 — 학습문서에서는 "공식 정의 없음"을 밝히고 2.3 (4)의 세 메커니즘을 예시로만 제시. 문항에는 이 용어를 직접 묻는 선택지를 만들지 말 것.
- [G-1.1-2] FSx for NetApp ONTAP 이 SageMaker 학습·Studio 의 직접 데이터 소스인가? — SageMaker "Setting up training jobs to access datasets"(S3·EFS·FSx for Lustre 만 명시), FSx for ONTAP S3 access point 문서(S3 API 로 접근, 데이터는 ONTAP 에 유지)와 AWS 뉴스 블로그(SageMaker 학습에 사용 가능하다고 소개)를 확인. SageMaker 문서에서 ONTAP 을 학습 채널로 직접 마운트한다는 서술은 찾지 못함 — 학습문서에는 "S3 access point 경유(S3 호환 경로)"로 쓰고, 문항은 "직접 마운트"를 정답으로 두지 말 것.
- [G-1.1-3] Kinesis Data Streams 레코드 크기와 쓰기 한도 수치가 문서마다 다른가? — Quotas 페이지는 "base64 인코딩 전 데이터 페이로드 최대 10 MiB", `PutRecord` 행은 샤드당 "최대 10 MiB/s", `PutRecords` 행은 "1 MB/s" 로 적고, Terminology 페이지는 "데이터 blob 최대 1 MB" 와 "샤드 쓰기 1 MB/s" 로 적음. 어느 쪽이 최신인지 문서에 표시가 없는 서술 불일치 — 문항에는 샤드당 1 MB/s·1,000 records/s(여러 페이지 일치)만 쓰고, 레코드 최대 크기는 출제 근거로 쓰지 말 것.
- [G-1.1-4] Firehose 버퍼 간격의 하한은 0초인가 60초인가? — 버퍼 힌트 표(S3 대상 0–900초, 기본 300)와 FAQ(0–900초)는 0초부터, Quota 페이지("buffer interval hints range from 60 seconds to 900 seconds")와 백업 설정 본문(60–900초)은 60초부터로 적음. 제로 버퍼링은 "애플리케이션 대상용이며 S3 백업 대상에는 불가"라는 문장도 있어 S3 주 대상에서의 적용 범위가 모호함 — 학습문서에는 "S3 기본 5 MB·300초, 간격 0–900초(문서에 따라 60초부터)"로 병기.
- [G-1.1-5] S3 최대 객체 크기는 5 TB 인가 50 TB 인가? — 현재 S3 문서(객체 개요·멀티파트 한도)는 "객체당 최대 50 TB(실제 한도 53.7 TB=48.8 TiB)"이고 AWS Storage 블로그 등 이전 자료는 5 TB 로 적음 — 2025년 이전에 만들어진 시험 대비 자료는 5 TB 를 쓸 수 있으므로, 문항은 이 수치를 정답 근거로 삼지 말고 학습문서에 "최신 문서 기준 50 TB" 주석을 달 것.
- [G-1.1-6] SageMaker 알고리즘 입력 채널 이름은 모두 `train` 인가? — "Common Data Formats for Training" 은 "모든 알고리즘에서 ChannelName 이 train 이어야 한다"고 적지만 "Parameters for Built-in Algorithms" 표는 AutoGluon-Tabular·CatBoost·LightGBM·TabTransformer 등의 채널을 `training` 으로 적음 — 알고리즘별 표를 우선하고 문항에서 채널 이름을 정답 근거로 쓰지 말 것.
- [G-1.1-7] EFS 성능 모드 권장이 자료마다 다른가? — 현재 EFS 성능 문서는 Max I/O 를 이전 세대 유형으로 두고 모든 파일 시스템에 General Purpose 를 권장함(Elastic 처리량 파일 시스템은 Max I/O 미지원). 2022년 AWS 머신러닝 블로그(https://aws.amazon.com/blogs/machine-learning/choose-the-best-data-source-for-your-amazon-sagemaker-training-job/)는 I/O worker 가 많은 학습에 Max I/O 를 선택지로 설명 — 현재 문서를 따르고 Max I/O 를 정답으로 하는 문항은 피할 것.
- [G-1.1-8] Kinesis Data Streams 의 "data delivery"(S3·Iceberg 스트리밍 테이블로 직접 전달, on-demand 모드 필요)가 시험 범위인가? — KDS Terminology 페이지와 Quotas 페이지(2026-10-17 조회)에서 확인했고 MLA-C01 가이드 Version 1.0 에는 없는 최신 기능 — 학습문서에는 각주로만 두고, 문항에서는 "KDS 단독으로 S3 적재" 를 정답으로 삼지 말 것.
- [G-1.1-9] Feature Store SDK 수집 함수 이름이 `ingest` 인가 `ingest_dataframe` 인가? — 예제 노트북(fraud detection)은 `feature_group.ingest(data_frame=..., max_workers=3, wait=True)`, 소개 노트북(introduction)은 `from sagemaker.mlops.feature_store import ingest_dataframe` 를 사용(SageMaker Python SDK 버전별 표기 차이) — 시험 용어는 `ingest`/`PutRecord` 이므로 학습문서에 두 표기를 병기.
- [G-1.1-10] Amazon MSK 가 시험 범위인가? — 가이드 K3 는 "Apache Kafka" 를 예로 들지만 부록의 범위 내 서비스 목록(Analytics 등)에는 Amazon MSK 가 없고 Kinesis·Amazon Data Firehose·Amazon Managed Service for Apache Flink 만 있음(영문 PDF Version 1.0 부록 확인) — 목록이 "non-exhaustive" 이므로 MSK 는 'Kafka 관리형 서비스'로 간략히 다루고 심화 문항은 피할 것.
- [G-1.1-11] Canvas 안의 Data Wrangler 가 가져올 수 있는 소스의 단일 정리 페이지가 있는가? — Studio Classic 문서(`data-wrangler-import`)는 S3·Athena·Redshift·Snowflake·Databricks(+EMR·Salesforce Data Cloud·SaaS)를 나열하고, Canvas 문서는 "Connect to data sources"(S3·Athena·RDS·Redshift 프로비저닝·DocumentDB·JDBC·Snowflake·Salesforce Data Cloud·SaaS 40개 이상)를 참조하라고 함. Canvas 데이터 흐름이 이 목록 전부를 그대로 지원한다고 한 문장으로 확정한 페이지는 찾지 못함 — 학습문서에는 두 목록을 구분해 적고 문항은 S3·Athena·Redshift·Snowflake 같은 공통 소스에 한정할 것.
- [G-1.1-12] FastFile 모드를 SageMaker 내장 알고리즘이 지원하는가? — "Parameters for Built-in Algorithms" 표의 입력 모드 열은 File·Pipe 만 적고 FastFile 지원 여부는 표에 없음. FastFile 일반 설명은 S3 prefix 입력에 모드 지정으로 전환 가능하다고만 함 — 문항에서 "내장 알고리즘 + FastFile" 조합을 정답으로 삼지 말 것.
- [G-1.1-13] EBS gp3/gp2 의 최대 IOPS·처리량 수치는 어디서 인용하는가? — EBS volume types 표의 해당 셀이 각주 번호와 붙어 있어 15단어 이하 원문 인용으로 안전하게 분리하지 못함(io1·io2 수치는 Provisioned IOPS 페이지에서 인용) — 학습문서에서 gp3 수치가 필요하면 표 원문을 직접 확인.
- [G-1.1-14] Firehose 개명 시점(2024-02-09)은 어느 문서로 확인하는가? — 컨트롤러 공지(N4)의 날짜를 따름. 인용한 AWS CLI 문서 문장("previously known as")에는 날짜가 없음 — 날짜를 쓰려면 AWS 공지 페이지를 추가로 확인.
- [G-1.1-15] 후보 문항이 SK1·SK4·SK6 을 덮지 않는다 — 후보 5개 한도 내에서 K1·K2·K3·SK2·SK3·SK5 를 선택함 — 학습문서 작성 시 2.6(SK6)·2.7(SK1)·2.9(SK4)와 섹션 5 사실 행(S3 Transfer Acceleration, EBS Provisioned IOPS, Glue/Athena/EMR)으로 추가 문항을 만들 것.
- 레포 `MLA-C01.json` 수정 제안: 없음 (Task 1.1 의 지식·기술 문구는 공식 ko_kr 가이드와 일치).
