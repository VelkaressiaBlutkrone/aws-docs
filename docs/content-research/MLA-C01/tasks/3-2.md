### 2.1 SageMaker 엔드포인트 오토 스케일링의 구조 — Application Auto Scaling 연동 (K5, K2)

SageMaker AI(구 Amazon SageMaker, 2024-12-03 개명 〔S41〕)의 오토 스케일링은 "모델에 프로비저닝된 인스턴스 수를 워크로드 변화에 맞춰 늘리고 줄이는" 기능이다. 워크로드가 늘면 인스턴스를 더 켜고, 줄면 불필요한 인스턴스를 제거해 쓰지 않는 프로비저닝 비용을 막는다〔S1〕. 실제 조정은 SageMaker가 아니라 **Application Auto Scaling(AAS)** 이 수행하며, SageMaker AI·CloudWatch·AAS 세 서비스의 API가 함께 동작한다〔S13〕. AAS는 EC2 Auto Scaling이 다루지 못하는 개별 AWS 서비스(ECS 서비스, DynamoDB, Lambda 프로비저닝된 동시성, SageMaker 변형·추론 컴포넌트·서버리스 프로비저닝된 동시성 등)의 자동 조정을 맡는 서비스다〔S21〕.

**확장 대상(scalable target) 3종** — AAS는 정책이나 예약 작업을 만들기 전에 scalable target 등록을 요구하며, 대상은 리소스 ID·확장 차원(scalable dimension)·네임스페이스의 조합으로 식별된다〔S17〕.

| 확장 대상 | `ScalableDimension` | `ResourceId` 형식 | 무엇을 늘리고 줄이나 |
|---|---|---|---|
| 엔드포인트 변형(production variant) | `sagemaker:variant:DesiredInstanceCount` | `endpoint/<엔드포인트명>/variant/<변형명>` | 인스턴스 수 〔S17〕〔S23〕 |
| 서버리스 엔드포인트의 프로비저닝된 동시성 | `sagemaker:variant:DesiredProvisionedConcurrency` | 위와 동일 | 프로비저닝된 동시성 값 〔S8〕〔S17〕 |
| 추론 컴포넌트(inference component) | `sagemaker:inference-component:DesiredCopyCount` | `inference-component/<이름>` | 모델 복사본(copy) 수 〔S17〕 |

- **구성 순서**(CLI/API): ① scalable target 등록(`MinCapacity`·`MaxCapacity`) → ② 정책 정의 → ③ 정책 적용〔S13〕. 콘솔로 구성하면 SageMaker AI가 scalable target을 자동 등록한다〔S17〕.
- **권한**: `SagemakerFullAccessPolicy` 에 필요한 권한이 모두 들어 있다. 자체 정책을 쓰면 `application-autoscaling:*`, `cloudwatch:PutMetricAlarm`·`DescribeAlarms`·`DeleteAlarms`, 서비스 연결 역할 생성(`iam:CreateServiceLinkedRole`) 권한 등을 직접 넣어야 한다〔S13〕. 서비스 연결 역할 이름은 `AWSServiceRoleForApplicationAutoScaling_SageMakerEndpoint` 이며 scalable target을 처음 등록할 때 자동 생성된다〔S17〕.
- **엔드포인트 업데이트와의 상호작용**: 오토 스케일링 대상 변형의 *인스턴스 유형*을 바꾸는 `UpdateEndpoint` 는 실패한다. 먼저 정책을 삭제하고 `DeregisterScalableTarget` 으로 등록을 해제한 뒤 업데이트하고, 다시 등록·정책 연결을 한다. 예외로 *모델만* 바꾸는 업데이트는 오토 스케일링이 허용한다〔S12〕.
- **IaC 표현**: CloudFormation에서는 `AWS::ApplicationAutoScaling::ScalableTarget` + `AWS::ApplicationAutoScaling::ScalingPolicy` 로 선언한다〔S46〕.
- **한국어판 용어**: 오토 스케일링 정책, 대상 추적 조정 정책, 단계 조정, 예약 기반 크기 조정, 휴지 기간(= cooldown), 최소·최대 크기 조정 제한. 공식 ko_kr 문서는 기계 번역이며 원문과 충돌하면 영문이 우선한다고 명시한다〔S85〕.

> 🧠 원리: 대상 추적 정책이면 AAS가 CloudWatch 경보를 직접 만들고 관리하며 지표·목표값으로 조정량을 계산한다〔S18〕. 단계 정책은 사용자가 CloudWatch 경보를 만들어 정책에 연결해야 한다〔S19〕.

### 2.2 스케일링 정책 유형 비교 — 대상 추적 vs 단계 vs 예약 (K2, K5)

SageMaker 문서는 워크로드 변화에 자동 대응하는 정책으로 **대상 추적(target tracking)과 단계(step) 두 가지**를 소개하고, 시간 기반 조정은 **예약 작업(scheduled action)** 으로 별도 설명한다〔S2〕.

| 정책 유형 | 언제 | 핵심 제약·메커니즘 | 함께 헷갈리는 것 |
|---|---|---|---|
| 대상 추적(Target tracking) | 지표를 목표값 근처로 유지하고 싶을 때. SageMaker는 "대부분의 경우" 이 유형을 권장〔S2〕 | 지표(metric)와 목표값(target value)만 지정하면 AAS가 경보·조정량 계산을 맡음〔S2〕〔S18〕. 증가 시 용량을 공격적으로, 감소 시 보수적으로 조정〔S18〕. 쿨다운 기본 300초〔S2〕 | 단계 정책(경보를 직접 만들어야 함) |
| 단계(Step) | 위반 크기에 따라 증감량을 다르게 주는 고급 구성〔S2〕〔S19〕. **활성 인스턴스 0대에서 scale-out** 하려면 필수〔S2〕 | 경보를 사용자가 정의해 정책에 연결〔S19〕. 쿨다운 기본값 300〔S19〕 | 대상 추적은 0대 상태를 깨우는 용도가 아님 → 2.4 |
| 예약(Scheduled) | 예측 가능한 시간대 패턴(수요가 시간에 따라 반복) | 정해진 시각에 최소·최대 용량을 바꿈. 현재 용량이 새 최소보다 작으면 최소로 scale-out〔S20〕. SageMaker에서는 CLI/API로만 관리〔S2〕 | 정책과 병행 가능: 예약은 선제적(proactive), 정책은 반응적(reactive)〔S25〕 |
| 예측(Predictive) | AAS 기능 목록에는 있음〔S21〕 | CloudFormation 레퍼런스는 "ECS 서비스에서 지원"이라고 명시〔S24〕. SageMaker 문서의 정책 소개에는 없음〔S2〕 | "예측 스케일링"을 SageMaker 정답으로 고르는 함정 |

- **여러 정책 동시 적용**: 한 대상에 대상 추적 정책을 여러 개 둘 수 있다(지표가 서로 달라야 함). scale-out은 *하나라도* 준비되면 수행하고 scale-in은 *모두* 준비돼야 수행한다. 동시에 지시하면 가장 큰 용량을 주는 정책을 따른다〔S18〕. 단계 정책과 섞으면 충돌로 의도치 않은 동작이 날 수 있어 주의가 필요하다〔S18〕.
- **예약 + 정책**: 예약 작업이 실행된 뒤에도 정책은 계속 동적 판단을 한다〔S2〕. 예약은 조정의 *경계(min/max)* 를 바꾸고, 그 안에서 정책이 움직인다〔S18〕〔S25〕.
- **가이드 문구와의 대응**(본 노트의 해석): K5의 "수요 기준" = 대상 추적·단계, "시간 기준" = 예약 스케일링.

> 🧠 원리: 예약 작업은 "현재 용량 vs 지정한 최소·최대"를 비교해 최소보다 작으면 올리고 최대보다 크면 내린다〔S20〕. 그래서 "아침에 최소 용량을 올려 두는" 방식으로 사전 준비를 구현한다.

### 2.3 스케일링 지표 선택 — 모델 지연 vs CPU vs 인스턴스당 호출 수 (SK6, K2)

**사전 정의(predefined) 지표 vs 사용자 지정(custom) 지표**: 사전 정의 지표는 열거형으로 정의되어 코드나 SageMaker 콘솔에서 이름으로 지정할 수 있다. 사전 정의·사용자 지정 지표 모두 AWS CLI나 AAS API로 대상 추적 정책에 적용할 수 있다〔S2〕.

| `PredefinedMetricType` | 대상 | 의미 | 비고 |
|---|---|---|---|
| `SageMakerVariantInvocationsPerInstance` | 변형(실시간) | 변형의 인스턴스 하나가 **분당** 호출된 평균 횟수〔S10〕. CloudWatch `InvocationsPerInstance` 는 호출 수를 `InstanceCount` 로 정규화한 값〔S14〕〔S22〕 | SageMaker가 "강력 권장"〔S10〕. 표준 지표라 1분 주기〔S3〕. **비동기 엔드포인트에서는 발행되지 않음**〔S7〕 |
| `SageMakerInferenceComponentInvocationsPerCopy` | 추론 컴포넌트 | 복사본당 호출 수〔S22〕 | |
| `SageMakerVariantConcurrentRequestsPerModelHighResolution` | 변형 | 모델 컨테이너가 받는 동시 요청 수(컨테이너 안 대기 포함)〔S3〕 | 10초마다 발행 → scale-out이 빨라지고 scale-in 속도는 표준 지표와 같음〔S3〕 |
| `SageMakerInferenceComponentConcurrentRequestsPerCopyHighResolution` | 추론 컴포넌트 | 복사본이 받는 동시 요청 수〔S3〕〔S22〕 | 위와 동일 |
| `SageMakerVariantProvisionedConcurrencyUtilization` | 서버리스 PC | 프로비저닝된 동시성 사용률〔S8〕〔S22〕 | 예: TargetValue 0.5〔S8〕 |

**사용자 지정 지표**: "용량에 비례해 변하는 어떤 프로덕션 변형 지표든" 쓸 수 있다〔S3〕. 다만 모든 SageMaker 지표가 되는 것은 아니며, 지표는 *유틸리제이션 지표*여야 하고 인스턴스가 얼마나 바쁜지를 나타내야 하며 인스턴스가 늘면 값이 줄어야 한다〔S10〕. AAS도 같은 요건(유효한 utilization 지표, 용량에 비례)을 적는다〔S18〕. **프로덕션에 쓰기 전에 사용자 지정 지표로 오토 스케일링을 반드시 테스트**해야 한다〔S3〕.

- 예시: `CPUUtilization`(네임스페이스 `/aws/sagemaker/Endpoints`, 평균 50%)〔S3〕. GPU 기반 멀티 모델 엔드포인트에는 `GPUUtilization` 예시가 있다〔S10〕. 온라인 설명 가능성(SageMaker Clarify 기능〔S89〕)을 켠 엔드포인트는 `ExplanationsPerInstance` 를 "강력 권장"한다〔S3〕 — ⚠️ SageMaker Clarify는 신규 고객에게 닫혀 있다(아래 F 표 참조)〔S88〕.
- ⚠️ `CPUUtilization` 은 코어별 사용률의 *합*이라 4 vCPU면 범위가 0%~400%다〔S14〕. 목표값을 정할 때 이 척도를 고려해야 한다.

| 후보 | 공식 문서상 위치 | 선택 기준 |

| 모델 지연 시간(`ModelLatency`) | 사전 정의 지표 목록에는 없음〔S22〕. Inference Recommender의 오토 스케일링 추천 결과가 `ModelLatency`·`InvocationsPerInstance` 를 함께 다룸〔S11〕. ML Lens는 지표 예시로 "request latency"를 듦〔S34〕 | 부하 테스트에서 *피크 RPS를 판정하는 기준*(지연이 늘기 시작하는 지점)〔S4〕과 알람·모니터링. 정책의 직접 스케일링 지표로 쓰라는 공식 권고 문구는 확인하지 못함 → 섹션 9 |
| 동시 요청 수(고해상도) | 사전 정의 지표〔S3〕 | 트래픽 급증에 더 빨리 반응해야 할 때(10초 주기)〔S3〕 |
| 백로그 크기 | 비동기 엔드포인트용 사용자 지정 지표 `ApproximateBacklogSizePerInstance`〔S6〕〔S7〕 | 큐 기반 비동기 추론 |
| 프로비저닝된 동시성 사용률 | 서버리스 PC용 사전 정의 지표〔S8〕 | 서버리스 PC를 부하에 맞춰 조정 |

**부하 테스트로 목표값 정하기**(공식 절차)〔S4〕: ① 인스턴스 1대로 엔드포인트를 만들고 병렬 요청을 늘려 가며 RPS와 모델 지연을 관찰한다. 모델 지연이 늘거나 성공률이 떨어지는 지점이 인스턴스당 *피크 RPS(MAX_RPS)* 다. ② `SageMakerVariantInvocationsPerInstance = (MAX_RPS * SAFETY_FACTOR) * 60` 로 목표값을 계산한다(분당으로 측정했다면 ×60 생략). ③ SAFETY_FACTOR는 **0.5부터 시작**해 증가·감소 트래픽에서 모두 검증한다. (예시 계산: MAX_RPS 100, SAFETY_FACTOR 0.5 → 목표값 3000.) ML Lens도 같은 취지로 부하 테스트와 Inference Recommender 사용을 권한다〔S34〕.

**Inference Recommender의 오토 스케일링 추천**: 완료된 추천 작업에서 `GetScalingConfigurationRecommendation` 으로 정책 추천을 받는다. 입력은 `TargetCpuUtilizationPerCore`(기본 50%)와 예상 트래픽 `ScalingPolicyObjective`(분당 최소·최대 호출), 출력은 권장 `MinCapacity`·`MaxCapacity`·쿨다운·지표별 `TargetValue` 이며 `PutScalingPolicy` 로 적용한다〔S11〕.

> 🧠 원리: 대상 추적은 "지표가 목표값을 넘으면 용량을 더하고 밑돌면 뺀다"는 구조라서 지표가 용량에 반비례해 움직여야 올바르게 수렴한다. 문서가 "인스턴스가 늘면 지표가 줄어야 한다"고 요구하는 이유가 이것이다〔S10〕〔S18〕.

### 2.4 용량 한도·쿨다운·0대로 줄이기 (K5)

| 항목 | 값·동작 | 근거 |
|---|---|---|
| 최소 용량 | 일반 변형은 **1 이상**이어야 하고 최대값 이하여야 함 | 〔S2〕 |
| 최대 용량 | 최소값 이상. SageMaker는 이 값에 한도를 강제하지 않음 | 〔S2〕 |
| 트래픽이 0이 되면 | 지정한 최소 인스턴스 수까지 scale-in(0대가 아님), 값이 0인 지표를 발행 | 〔S2〕 |
| 수동 조정 | 최소값을 올리면 수동 scale-out, 최대값을 내리면 수동 scale-in | 〔S2〕 |
| 쿨다운 기본값 | scale-in·scale-out 각각 **300초**(정책에서 설정). AAS 표에서 SageMaker 변형·추론 컴포넌트·서버리스 PC가 300, Lambda PC 등은 0/null | 〔S2〕〔S18〕 |
| 쿨다운 조정 지침 | 인스턴스가 너무 빨리 늘고 줄면 값을 늘리고, 충분히 빨리 늘지 않으면 줄임 | 〔S2〕 |
| 서버리스 PC 최소 | `--min-capacity` 1 이상 | 〔S8〕 |
| 비동기 엔드포인트 | `MinCapacity` 0으로 scale-in to zero 가능 | 〔S6〕 |
| 추론 컴포넌트 기반 | 0대 가능: 컴포넌트 `MinCapacity` 0 + 변형 `ManagedInstanceScaling.MinInstanceCount` 0 | 〔S5〕〔S16〕 |

- **쿨다운의 의미**: scale-out 쿨다운은 "지속적으로, 그러나 과하지 않게" 늘리려는 장치이고, scale-in 쿨다운은 가용성을 지키려 보수적으로 줄이려는 장치다. scale-in 쿨다운 중에 다른 경보가 scale-out을 요구하면 즉시 scale-out 하며 scale-in 쿨다운은 중단된다. 쿨다운은 정책 관련 조정에만 적용되고 예약 작업은 쿨다운을 기다리지 않고 시작할 수 있다〔S18〕.
- **0대에서 다시 깨우기(추론 컴포넌트)**: 0대로 줄어든 엔드포인트는 인스턴스가 다시 프로비저닝될 때까지 요청에 응답하지 못한다. 이를 자동화하려면 **단계 스케일링 정책 + CloudWatch 경보**를 만든다. 경보 지표는 엔드포인트가 요청을 받았는데 활성 인스턴스가 없을 때 SageMaker가 내보내는 `NoCapacityInvocationFailures` 다. 프로비저닝에는 수 분이 걸리고 그동안의 호출은 오류가 난다〔S5〕.
- **0대에서 다시 깨우기(비동기)**: 요청은 큐에 쌓여 대기하며, 추가 단계 정책 없이는 백로그가 대상 추적 목표를 넘을 때에야 scale-up이 시작된다. 큐에 요청이 하나라도 있으면 바로 깨우려면 `HasBacklogWithoutCapacity` 경보에 연결한 단계 정책을 추가한다〔S6〕. 이 지표는 큐에 요청이 있는데 인스턴스가 0대일 때 1이다〔S7〕.
- **최소 용량 선택(가용성)**: 프로덕션 엔드포인트는 인스턴스를 여러 대 두라는 것이 공식 권고이며, VPC를 쓰면 서로 다른 AZ의 서브넷을 최소 2개 구성한다. 추론 컴포넌트로 99.95% 가용성을 목표로 하면 복사본을 2개보다 많이, 관리형 오토 스케일링의 최소 인스턴스를 2로 설정하라고 한다〔S28〕.
- **경보 지연 감각**(블로그 예시, 추론 컴포넌트 수준 대상 추적): 정책을 만들면 대상당 CloudWatch 경보 2개가 생기고, 하나는 3분(1분 데이터 포인트 3개) 위반 시 scale-out, 다른 하나는 15분(1분 데이터 포인트 15개) 위반 시 scale-in을 트리거한다〔S80〕. 즉 scale-in이 의도적으로 느리다.

### 2.5 추론 옵션별 용량 모델과 스케일링 방식 (K1, K2, K5, SK1)

SageMaker AI는 추론 옵션을 실시간·서버리스·비동기·배치 변환 네 가지로 나눈다〔S26〕. **용량을 누가 정하느냐**(프로비저닝 vs 온디맨드)가 스케일링 방식을 가른다.

| 옵션 | 용량 모델 | 스케일링 방식 | 0대까지? | 핵심 제약 |
|---|---|---|---|---|
| 실시간(인스턴스 기반) | **프로비저닝** — 항상 가용, "인스턴스를 사용하는 만큼" 과금〔S27〕 | AAS 대상 추적·단계·예약, 변형 `DesiredInstanceCount`〔S2〕〔S17〕 | 불가(최소 1)〔S2〕 | 페이로드 25MB·처리 60초(스트리밍 응답 8분)〔S26〕 |
| 실시간 + 추론 컴포넌트 | 인스턴스는 프로비저닝, 모델은 복사본 단위 | 컴포넌트 `DesiredCopyCount` 스케일 + 변형 `ManagedInstanceScaling`〔S5〕〔S16〕〔S17〕 | 가능(복사본 0 + 최소 인스턴스 0)〔S5〕 | 한 엔드포인트에 여러 모델을 올림〔S59〕 |
| 서버리스 | **온디맨드** — SageMaker가 컴퓨트를 자동 시작·확장, 인스턴스 선택·스케일링 정책 관리 불필요〔S9〕 | 정책 없음. 동시성 한도(`MaxConcurrency` 1~200)로 상한〔S9〕〔S15〕 | 유휴 시 0〔S9〕 | 메모리 1024~6144MB, 이미지 10GB, VPC·네트워크 격리·MME·데이터 캡처·다중 변형 불가〔S9〕, 페이로드 4MB·60초〔S26〕 |
| 서버리스 + 프로비저닝된 동시성(PC) | 온디맨드 + 지정한 수만큼 미리 웜 | PC를 AAS로 대상 추적·예약〔S8〕 | PC 최소 1〔S8〕 | PC ≤ `MaxConcurrency`〔S9〕 |
| 비동기 | 큐 + 인스턴스(고정 수로 처리율 조절 가능)〔S27〕 | 백로그 지표 대상 추적〔S6〕 | 가능〔S6〕 | 페이로드 1GB·처리 1시간〔S26〕. `InvocationsPerInstance` 미발행〔S7〕 |
| 배치 변환 | 작업 시간 동안만 인스턴스 과금, 상시 엔드포인트 없음〔S27〕 | 해당 없음 | — | 오프라인 대용량 처리〔S26〕 |

- **서버리스 동시성 개념**: 서버리스 엔드포인트는 "동시에 처리할 수 있는 호출 수" 할당량을 가진다. 리전·계정 전체 서버리스 엔드포인트가 공유하는 총 동시성은 일부 리전(US East 오하이오·버지니아 북부, US West 오레곤, 싱가포르·시드니·도쿄, 프랑크푸르트·아일랜드)에서 1000, 나머지 리전은 500이며, 엔드포인트별 최대 동시성은 200, 리전당 서버리스 엔드포인트는 50개다. 상한을 넘는 호출은 스로틀링된다〔S9〕. 서버리스 추론은 AWS Lambda와 통합되어 고가용성·내결함성·자동 확장을 제공한다〔S9〕.
- **서버리스 변환 방향**: 실시간 → 서버리스 변환은 `ValidationError`, 서버리스 → 실시간은 가능하나 되돌릴 수 없다〔S9〕.
- **멀티 모델 엔드포인트(MME)**: 오토 스케일링에는 `InvocationsPerInstance` 를 권장하고, 목표값은 지연 요구에 따라 달라지므로 부하 테스트로 정한다〔S10〕.
- ⚠️ 서버리스 "제외 기능" 목록(영문 Feature exclusions, ko_kr 기계 번역은 "독점 기능")에 Model Monitor가 있다〔S9〕〔S86〕. Model Monitor 자체는 신규 고객에게 닫혀 있다〔S83〕.
- 한국어판 용어: 서버리스 추론, 프로비저닝된 동시성, 콜드 스타트〔S86〕.

### 2.6 온디맨드 리소스 vs 프로비저닝된 리소스 (K1, SK1)

이 노트의 정의: **온디맨드**는 필요할 때 용량을 받아 쓴 만큼 내는 방식, **프로비저닝**은 용량(또는 사용 약정)을 미리 정해 두는 방식이다. 서비스마다 같은 구분이 이름만 바꿔 나타난다.

| 영역 | 온디맨드 | 프로비저닝 | 고르는 기준 |
|---|---|---|---|
| SageMaker 추론 | 서버리스 추론: 컴퓨트를 자동 시작·확장하고 유휴 시 0, 쓴 만큼 과금〔S9〕 | 실시간 엔드포인트: 인스턴스를 상시 확보, 인스턴스 사용에 과금〔S27〕 | 간헐적·예측 불가·콜드 스타트 허용 → 서버리스. 일관된 지연이 필요한 지속 트래픽 → 실시간〔S27〕 |
| 서버리스 안에서 | 순수 온디맨드(콜드 스타트 가능)〔S9〕 | **프로비저닝된 동시성(PC)**: 지정한 수만큼 컴퓨트를 미리 초기화해 밀리초 내 응답. PC 사용량(메모리·기간·동시성)에 별도 과금〔S9〕 | 예측 가능한 버스트 + 지연 예측성〔S9〕 |
| Lambda(참고) | 요청마다 필요하면 실행 환경 초기화(콜드 스타트) | provisioned concurrency: 환경을 미리 초기화해 콜드 스타트 지연을 줄임, 추가 요금〔S32〕 | 서버리스 추론이 Lambda와 통합돼 같은 개념을 따름〔S9〕 |
| EC2 구매 옵션 | On-Demand: 약정·선결제 없이 종량〔S30〕. Spot: 여분 용량, 2분 전 통지로 중단 가능〔S31〕 | Savings Plans·Reserved Instances: 사용량/구성 약정으로 할인〔S30〕 | 중단 허용·유연 → Spot, 지속·예측 가능 → 약정〔S31〕 |
| SageMaker 약정 | 온디맨드 요금 | **SageMaker AI Savings Plans**: 시간당($/hour) 일정 사용량을 1년 또는 3년 약정, 최대 64% 절감. 노트북·Processing·Data Wrangler·훈련·실시간 추론·배치 변환의 ML 인스턴스 사용에 인스턴스 패밀리·크기·리전과 무관하게 자동 적용〔S27〕 | 여러 SageMaker 서비스에 걸쳐 *일정한* 사용량이 있을 때〔S27〕 |
| 용량 예약 | — | **SageMaker 훈련 계획(training plans)**: 훈련 작업·HyperPod·추론 엔드포인트·Studio 앱용 컴퓨트 용량을 예약. 추론 엔드포인트는 예약 기간에만 동작〔S39〕〔S40〕 | 고수요 GPU 확보가 목적일 때(할인이 목적이 아님) |
| Bedrock(참고) | PT 구매 전 기본 호출 | Provisioned Throughput: 모델 단위(MU)를 고정 비용으로 구매, 시간당 과금, 약정 없음·1개월·6개월, 맞춤 모델은 PT 필수〔S33〕 | 예측 가능한 처리량·맞춤 모델 |

- **가격 할인 ≠ 용량 확보**: EC2 의사결정 가이드는 구매 옵션(On-Demand·Savings Plans·Reserved Instances·Spot)은 청구 계산 방식이고 용량 예약(Capacity Reservations)은 용량을 잡아 두는 방식이어서 서로 독립적이며 겹쳐 쓴다고 설명한다〔S30〕. Spot은 Savings Plans 대상이 아니다〔S31〕.
- Savings Plans 적용 대상으로 나열된 항목에는 실시간 추론·배치 변환이 있고 서버리스·비동기 추론은 명시돼 있지 않다〔S27〕 → 섹션 9.

> 🧠 원리: 서버리스 추론은 컴퓨트를 요청에 맞춰 자동 시작·확장하므로 유휴 비용이 없고, 대신 첫 요청에 콜드 스타트가 생긴다. 프로비저닝된 동시성은 그 콜드 스타트를 "웜 상태 유지 비용"으로 사 오는 장치다〔S9〕.

### 2.7 비용 효율·확장성·유지관리성 모범 사례 (SK1)

### 2.8 IaC 선택과 SageMaker 리소스 — CloudFormation vs CDK (K3, SK2)

| 비교 축 | AWS CloudFormation | AWS CDK |
|---|---|---|
| 작성 방식 | JSON/YAML 텍스트, **선언형** — 원하는 상태를 선언〔S50〕〔S55〕 | TypeScript·JavaScript·Python·Java·C#·Go 같은 범용 언어, **명령형** 로직(조건·반복) 사용 가능〔S48〕〔S50〕 |
| 결과/배포 | 템플릿을 CloudFormation이 프로비저닝 | 코드를 *합성(synthesize)* 해 CloudFormation 템플릿을 만들고 CloudFormation으로 배포 — 광범위한 리소스 지원·견고한 배포 프로세스 같은 CFN의 이점 유지〔S48〕〔S50〕 |
| 추상화 | 리소스 1:1 | L1(리소스 1:1, 이름 `Cfn*`) / L2(의도 기반 API, 안전한 기본값) / L3(패턴)〔S49〕 |
| 신규 리소스 | CloudFormation에 리소스가 있어야 CDK L1이 생성됨 | L1에 새 리소스·속성이 반영되기까지 최대 1주 걸릴 수 있음〔S49〕 |
| 선택 기준 | 단순하고 선언적인 인프라 | 복잡한 인프라는 CDK 고려〔S54〕. 개발 역량이 있는 조직에는 CloudFormation 대신 CDK 권장〔S55〕 |
| 절충(trade-off) | 원하는 *상태*를 선언하는 방식 — 그 상태에 이르는 로직·순서를 코드로 정의하는 것은 CDK 쪽 기능〔S50〕 | 추상화 계층(L1/L2/L3)과 언어·툴체인을 알아야 하고, 실험적(alpha) 모듈은 API가 바뀔 수 있음〔S53〕 |

**SageMaker 리소스의 IaC 표현**
- ⚠️ **이름 변경**: 2024-12-03 *Amazon SageMaker → Amazon SageMaker AI* 로 개명됐지만 API 네임스페이스·CLI·`AmazonSageMaker*` 관리형 정책·**CloudFormation 리소스 `AWS::SageMaker::*` 접두어**·서비스 연결 역할·콘솔/문서 URL의 `sagemaker` 는 그대로다〔S41〕. 템플릿의 리소스 타입 이름은 바뀌지 않았다.
- CloudFormation 리소스 타입: `AWS::SageMaker::Model`, `EndpointConfig`, `Endpoint`, `InferenceComponent`, `Pipeline`, `Project`, `ModelPackageGroup`, `FeatureGroup` 등〔S42〕.
- 의존 체인 `Model → EndpointConfig → Endpoint`: 같은 템플릿에서 `Fn::GetAtt`(예: `Model.ModelName`, `EndpointConfig.EndpointConfigName`)로 연결한다〔S43〕〔S44〕〔S45〕. 갱신 동작: `Endpoint` 의 `EndpointConfigName` 변경은 *무중단(No interruption)*, `EndpointConfig` 의 `ProductionVariants` 변경은 *교체(Replacement)*, `Model` 의 `VpcConfig`·`EnableNetworkIsolation` 변경도 *교체*다〔S43〕〔S44〕〔S45〕. EndpointConfig는 변형을 최대 10개까지 둘 수 있다〔S45〕.
- 오토 스케일링은 `AWS::ApplicationAutoScaling::ScalableTarget`·`ScalingPolicy` 로 별도 선언한다(예: `PredefinedMetricType: SageMakerVariantInvocationsPerInstance`)〔S46〕. ⚠️ SageMaker 서버리스 문서는 "프로비저닝된 동시성의 오토 스케일링은 CloudFormation에서 현재 지원되지 않는다"고 쓰지만, CloudFormation `ScalableTarget` 레퍼런스는 `sagemaker:variant:DesiredProvisionedConcurrency` 를 허용 값으로 나열한다〔S9〕〔S23〕 → 문서 간 상충, 섹션 9.
- **CDK**: `aws_cdk.aws_sagemaker` 는 L1(`CfnModel`·`CfnEndpointConfig`·`CfnEndpoint` 등)만 있으며 "공식 손으로 작성한 L2가 아직 없다"고 안내한다〔S52〕. 대신 별도 패키지 `@aws-cdk/aws-sagemaker-alpha` 가 `Model`·`EndpointConfig`·`Endpoint`·`ContainerImage`·`ModelData` L2를 제공하지만 **실험적**이어서 하위 호환 없이 API가 바뀔 수 있다〔S53〕. alpha 모듈은 `networkIsolation`, 서버리스 변형(`maxConcurrency` 1~200, `memorySizeInMB` 1024~6144, `provisionedConcurrency`), 컨테이너 시작 헬스체크 타임아웃, `autoScaleInstanceCount`·`scaleOnInvocations`(초당 요청 상한 기반)를 노출하며, 서버리스와 인스턴스 변형을 한 EndpointConfig에 섞을 수 없다〔S53〕.
- **SageMaker Projects**: 조직이 ML 개발 환경과 MLOps용 CI/CD를 표준화하는 기능이다. 템플릿은 **S3 버킷에 둔 사용자 지정 템플릿**, AWS Service Catalog 템플릿, SageMaker AI 제공 템플릿으로 프로비저닝하며 문서는 Service Catalog보다 S3 보관을 권장한다〔S56〕. SageMaker 제공 템플릿은 Service Catalog 제품으로 노출되고 ECR에 푸시되는 이미지를 CI/CD로 빌드하는 템플릿도 있다〔S57〕. ⚠️ 2024-09-09부터 *AWS CodeCommit 저장소를 쓰는 프로젝트 템플릿은 지원되지 않는다*〔S56〕 — CodeCommit *서비스* 자체는 2025-11-25 신규 고객에게 다시 열렸으니 혼동하지 말 것〔S82〕.
- **배포 방법 선택**(SageMaker 공식 안내): 노코드는 Studio JumpStart, 코드 기반 세밀 제어는 SageMaker Python SDK `ModelBuilder`, 대규모·반복 운영은 Boto3·CloudFormation 같은 IaC와 CI/CD 도구〔S58〕.

### 2.9 스택 간 통신 (SK2)

| 방식 | 범위 | 핵심 규칙 |
|---|---|---|
| `Outputs` + `Export` → 다른 스택에서 `Fn::ImportValue` | 같은 계정·같은 리전 | Export 이름은 계정·리전 내 고유. 임포트 중인 출력은 삭제·변경 불가(강한 참조)〔S47〕 |
| `Fn::GetStackOutput` | 계정·리전을 넘어 가능 | Export 불필요한 약한 참조 — 대상이 삭제돼도 소비 스택에 알리지 않으며 참조 무결성을 강제하지 않음〔S47〕 |
| 중첩 스택(`AWS::CloudFormation::Stack`) | 하나의 부모 아래 그룹 내부 | 그룹 *내부* 정보 공유용. 그룹 밖의 스택과 공유하려면 Export〔S47〕 |
| CDK 자동 참조 | 같은 환경의 다른 스택 리소스를 props로 전달 | CDK가 생산 스택에 export, 소비 스택에 `Fn::ImportValue` 를 자동 합성(기본 = strong). 참조 강도: Strong(export/ImportValue, 기본) / Weak(`Fn::GetStackOutput`, 결합 없음) / Both(전환 단계)〔S51〕 |

- 전형적 사용: 네트워크 스택이 VPC·보안 그룹·서브넷을 `Export`, 애플리케이션 스택이 `Fn::ImportValue` 로 가져옴. 네트워크 스택을 먼저 만들어야 하며 스택 이름을 export 이름 접두어로 써 출처를 구분한다〔S90〕. SageMaker에서는 네트워크 스택의 서브넷·보안 그룹 ID를 모델 스택의 `VpcConfig` 가 쓰는 구조에 해당한다(적용은 본 노트의 해석).
- `Export` 이름은 리소스에 의존하는 `Ref`/`GetAtt` 를 쓸 수 없고 `Fn::ImportValue` 인수도 마찬가지다〔S47〕.
- CDK에서 강한 참조끼리 얽히면 의존성 교착(deadly embrace)이 생길 수 있어 CDK가 참조 강도를 제어하게 한다〔S51〕.
- 같은 스택 안에서는 `Ref`·`Fn::GetAtt` 로 충분하다(예: `Model.ModelName` → `EndpointConfig`)〔S43〕〔S45〕.

> 🧠 원리: `Export`/`ImportValue` 는 CloudFormation이 "누가 무엇을 쓰는지"를 추적하므로 소비자가 남아 있으면 생산 스택의 출력을 지우거나 바꿀 수 없다. `GetStackOutput` 은 값을 읽기만 하므로 자유롭지만 참조 무결성은 없다〔S47〕.

### 2.10 컨테이너화 개념과 AWS 컨테이너 서비스 (K4)

- **개념**: 컨테이너는 애플리케이션의 코드·구성·의존성을 하나의 객체로 패키징하는 표준 방식이고, 컨테이너 이미지는 컨테이너를 만드는 읽기 전용(불변) 템플릿이다〔S65〕. SageMaker AI는 스크립트 실행·알고리즘 훈련·모델 배포 때 항상 Docker 컨테이너를 사용한다〔S60〕.

| 서비스 | 역할 | 핵심 | 헷갈리는 것 |
|---|---|---|---|
| Amazon ECR | 컨테이너 이미지 **레지스트리**(AWS 관리형, 프라이빗 리포지토리는 IAM 리소스 기반 권한, Docker·OCI 이미지 푸시/풀)〔S66〕 | 수명 주기 정책, 이미지 스캔(scan on push), 교차 리전·교차 계정 복제, pull through cache〔S66〕 | 이미지를 *저장*할 뿐 실행하지 않음 |
| Amazon ECS | AWS 관리형 **컨테이너 오케스트레이션** — 컨테이너화 애플리케이션을 배포·관리·확장〔S69〕 | 용량 옵션: ECS Managed Instances / EC2 인스턴스(직접 관리) / Fargate(서버리스) / ECS Anywhere(온프레미스). 서비스 오토 스케일링이 태스크 수를 자동 조정〔S69〕 | Kubernetes가 아닌 AWS 고유 오케스트레이터 |
| Amazon EKS | 완전 관리형 **Kubernetes** 서비스. 표준 EKS는 컨트롤 플레인을 AWS가 관리, EKS Auto Mode는 노드(데이터 플레인)까지 관리〔S70〕 | Kubernetes 적합 인증, EC2·EBS·ECR 등과 연동〔S70〕 | ECS와 달리 Kubernetes API/도구 사용 |
| AWS Fargate | ECS의 **서버리스 컴퓨트 엔진** — 서버 관리·용량 계획 불필요, 종량 과금〔S69〕 | 호스트 관리 없이 컨테이너만 지정 | ECS의 EC2 용량 옵션(서버를 직접 관리)과 대비 |
| SageMaker AI | 컨테이너를 *관리형*으로 실행하는 ML 플랫폼(훈련·호스팅). 이미지는 ECR 등에서 가져옴〔S59〕〔S60〕 | 엔드포인트·AAS 오토 스케일링·모델 레지스트리와 통합 | ECS/EKS에 직접 올리는 서빙과 달리 ML 전용 운영 기능 제공 |

- Lambda도 컨테이너 이미지(최대 10GB)로 작은 모델을 추론할 수 있고, GPU가 필요하면 ECS·Kubernetes 같은 컨테이너 서비스나 SageMaker 엔드포인트를 고려하라고 안내한다〔S38〕. 배포 대상 선택 자체(SageMaker 엔드포인트 vs Kubernetes vs ECS/EKS vs Lambda)는 Task 3.1 범위다.

### 2.11 컨테이너 구축·유지 — BYOC와 ECR (SK3)

**컨테이너 선택 사다리**〔S60〕: ① 내장 알고리즘 이미지 → ② 사전 빌드 프레임워크 이미지(TensorFlow·PyTorch 등) → ③ 사전 빌드 이미지를 *확장*(커스텀 패키지가 필요하면, `requirements.txt` 를 지원하는 프레임워크는 그 파일로 해결) → ④ 기존 이미지를 SageMaker에 맞게 *어댑트*(Training 또는 Inference Toolkit 활성화) → ⑤ 사전 빌드 이미지가 없는 커스텀 프레임워크면 직접 빌드(BYOC).

**툴킷**: SageMaker Training Toolkit(훈련용)과 SageMaker AI Inference Toolkit(배포용)이 컨테이너를 SageMaker에 맞추는 기능을 구현하며 코드·리소스 위치와 시작 시 실행할 엔트리포인트를 정의한다〔S60〕〔S64〕. 훈련·추론 이미지를 하나로 쓸 수도 있고 둘로 나눌 수도 있다. 둘로 나누면 저장 요구와 비용이 늘 수 있고, 작은 컨테이너가 더 빨리 시작해 호스팅이 트래픽 증가에 더 빠르게 확장한다〔S64〕.

**훈련 컨테이너 계약**

| 항목 | 규칙 | 근거 |
|---|---|---|
| 실행 | 기본 `docker run image train`. 이미지 안에서 `train` 스크립트를 찾음 | 〔S63〕 |

- 모델 아티팩트가 있는 S3 버킷은 만들려는 모델과 **같은 리전**이어야 한다〔S59〕. 서버리스 추론에서 BYOC는 이미지 10GB 이하, 컨테이너당 워커 1개·모델 1벌 권장, 프라이빗 Docker 레지스트리 불가다〔S9〕.
- **ECR에 올려 SageMaker에서 쓰는 절차**〔S71〕: ① 리포지토리 생성(없으면) ② `aws ecr get-login-password` 로 Docker 로그인 ③ `docker build` → `docker tag`(레지스트리 URI) → `docker push` ④ 푸시 후에는 SageMaker 환경 어디서나 ECR 이미지 URI로 호출. 모델·엔드포인트 배포 전에 ECR 이미지 URI·모델 아티팩트의 S3 경로·실행 역할을 준비한다〔S59〕.
- **ECR 이미지 유지**:
  - 스캔: *기본(Basic)* 은 CVE 데이터베이스로 OS 취약점만, 수동 또는 푸시 시 스캔. *강화(Enhanced)* 는 Amazon Inspector 연동으로 OS+프로그래밍 언어 패키지, 푸시 시·지속 스캔, 새 취약점은 EventBridge 이벤트로 통지〔S67〕. 리포지토리를 scan on push로 설정할 수 있다〔S66〕.
  - 수명 주기 정책: 하나 이상의 규칙(rule)이 리포지토리에서 만료시킬 이미지를 결정하며, 적용 전에 미리보기(preview)로 만료 대상을 확인한다. 규칙 우선순위 숫자가 낮을수록 우선. 조건을 충족한 이미지는 24시간 이내 만료〔S68〕. 미사용 이미지를 정리하는 규칙을 정의하고 적용 전에 테스트할 수 있다〔S66〕.
  - 이미지 빌드 CI/CD: 컨테이너 파일 변경이 파이프라인을 일으켜 이미지를 빌드·ECR에 푸시하는 SageMaker Projects 템플릿〔S57〕.

### 2.12 VPC 안의 SageMaker 엔드포인트 (SK4)

| 요구 | 구성 | 핵심 제약 |
|---|---|---|
| 엔드포인트 컨테이너를 내 VPC에 두고 VPC 리소스에 접근 | `CreateModel` 의 `VpcConfig`(`Subnets`, `SecurityGroupIds`) — SageMaker가 ENI를 만들어 모델 컨테이너에 연결〔S72〕 | **서로 다른 AZ의 서브넷 2개 이상**(호스팅 인스턴스가 1대여도)〔S72〕〔S28〕. API 한도: 서브넷 1~16개, 보안 그룹 1~5개〔S73〕. 사용자 정의 IAM 정책에는 `ec2:CreateNetworkInterface` 등 ENI 권한 필요(`SageMakerFullAccess` 에는 포함)〔S72〕 |
| VPC 안 컨테이너가 S3의 모델·데이터에 접근 | **S3 VPC 엔드포인트(게이트웨이)** + 라우팅 테이블. 엔드포인트 정책으로 접근 제한 가능〔S72〕 | 인터넷이 막힌 VPC에서 이 엔드포인트가 없으면 S3 버킷에 연결할 수 없음〔S72〕 |
| 컨테이너가 다른 AWS 서비스·외부에 접근 | 인터페이스 엔드포인트를 지원하는 서비스는 인터페이스 VPC 엔드포인트, 미지원 서비스·외부 리소스는 **NAT 게이트웨이** + 보안 그룹 아웃바운드 허용〔S72〕 | |
| 클라이언트가 인터넷 없이 SageMaker API·Runtime 호출 | **인터페이스 VPC 엔드포인트(AWS PrivateLink)** — SageMaker API용, SageMaker Runtime용〔S74〕 | 프라이빗 DNS를 켜면 기본 호스트명이 VPC 엔드포인트로 해석됨. Runtime 엔드포인트는 클라이언트의 AZ에서 활성화돼야 DNS 해석이 정상. VPC 엔드포인트 정책으로 호출 가능한 엔드포인트를 제한〔S74〕 |
| 컨테이너가 어떤 네트워크 호출도 못 하게 | `EnableNetworkIsolation=true`(`CreateModel`) → 인바운드·아웃바운드 호출 불가(S3 포함), AWS 자격 증명 미제공〔S75〕 | S3 다운로드·업로드는 SageMaker가 실행 역할로 컨테이너와 별도로 처리〔S75〕. VPC와 함께 쓰면 이 전송이 VPC 서브넷을 경유〔S75〕. AWS Marketplace 리소스 사용 모델·훈련에 필수〔S75〕 |
| 서버리스 엔드포인트에 VPC | **불가** — VPC 구성·네트워크 격리가 제외 기능〔S9〕 | |

- VPC를 구성하지 않으면 훈련·추론 컨테이너는 기본적으로 인터넷에 접근하고, VPC 내부 리소스에는 접근하지 못한다〔S74〕.
- 클라이언트가 VPC 밖(온프레미스)이면 Site-to-Site VPN 또는 Direct Connect로 VPC에 연결한 뒤 PrivateLink를 쓴다〔S74〕.
- Studio에서 모델과 엔드포인트를 함께 배포하려면 IAM 역할·VPC(서브넷·보안 그룹)·네트워크 격리 설정이 같아야 한다〔S59〕.
- IaC 표현: `AWS::SageMaker::Model` 의 `VpcConfig`·`EnableNetworkIsolation`〔S43〕, CDK alpha의 `networkIsolation`〔S53〕.
- ⚠️ 네트워크 격리를 켜면 Chainer·SageMaker 강화 학습 관리형 컨테이너는 S3 접근이 필요해 지원되지 않는다〔S75〕. 한국어판은 "인터넷이 연결되지 않은 모드에서 훈련 및 추론 컨테이너 실행"·"네트워크 격리"로 표기한다〔S87〕.

> 🧠 원리: 네트워크 격리는 *컨테이너*의 네트워크를 끊을 뿐 SageMaker 서비스의 데이터 이동까지 끊지 않는다 — 모델 다운로드·결과 업로드는 컨테이너 밖에서 실행 역할로 수행된다〔S75〕. `VpcConfig` 는 반대로 컨테이너에 VPC 안의 네트워크 인터페이스를 줘서 VPC 리소스와 통신하게 하는 설정이다〔S72〕.

### 2.13 SageMaker SDK로 모델 배포·호스팅 (SK5)

- **배포 흐름(API 수준)**: ① 모델 생성(`CreateModel`: 컨테이너 이미지 + `ModelDataUrl` + 실행 역할) → ② 엔드포인트 구성(`CreateEndpointConfig`: 프로덕션 변형에 모델·인스턴스 유형·초기 인스턴스 수를 할당) → ③ 엔드포인트(`CreateEndpoint`: 구성을 받아 리소스를 프로비저닝하고 모델 배포)〔S59〕. 추론 컴포넌트 방식은 ③ 이후 `CreateInferenceComponent` 로 모델을 올리고 CPU·메모리 같은 자원을 할당한다〔S59〕. 엔드포인트는 모델과 엔드포인트 구성으로 이루어지며 SageMaker Python SDK의 `.deploy()` 는 엔드포인트 구성을 대신 만들어 준다〔S76〕.
- **배포 수단**: SageMaker Studio(대화형), SageMaker Python SDK, Boto3, AWS CLI〔S59〕.
- **SDK 클래스 대응**(⚠️ 메이저 버전에 따라 이름이 다름):

| 단계 | SDK v2(레거시) | SDK v3(현재 문서 기준) | 근거 |
|---|---|---|---|
| 훈련 | `Estimator` 및 프레임워크 서브클래스(`PyTorch`, `SKLearn` …) `.fit()` | `ModelTrainer` 단일 클래스 `.train()` | 〔S77〕〔S78〕〔S84〕 |
| 모델·배포 | `Model`(+ 프레임워크 모델 클래스) / `Estimator.deploy()` → `Predictor` | `ModelBuilder` → `.deploy()` → `Endpoint` | 〔S59〕〔S77〕〔S78〕 |
| 호출 | `Predictor.predict()` | `endpoint.invoke(body=..., content_type=...)` | 〔S59〕〔S77〕 |

- **현재 공식 권장 버전**: 개발자 가이드의 실시간 추론 배포 문서는 "SageMaker Python SDK v3" 로 `ModelBuilder` 를 소개하고〔S59〕, SDK 1.x 사용자에게는 3.x로 업그레이드하라고 안내한다〔S79〕. 공식 GitHub README는 v3에서 통합 `ModelTrainer`·`ModelBuilder` 가 도입되었고 "Estimator, Model, Predictor 및 모든 하위 클래스는 V3에서 지원되지 않는다"고 하며, v2를 쓰려면 `pip install sagemaker==2.*` 를 안내한다〔S78〕. SDK v3 문서도 같은 대체 관계를 적는다〔S84〕. 시험 가이드(v1.0)가 v2 용어(Estimator·Model·Predictor)로 출제될 가능성이 있으므로 둘 다 알아 둔다(섹션 9 G-3.2-8).
- `ModelBuilder` 는 모델 아티팩트나 추론 코드를 받아 의존성 수집·직렬화/역직렬화 추론·패키징을 자동으로 처리해 준다〔S59〕. 추론 컴포넌트 기반 엔드포인트는 엔드포인트 유형을 `EndpointType.INFERENCE_COMPONENT_BASED` 로 지정한다〔S59〕.

### 짝 8. `VpcConfig` vs `EnableNetworkIsolation` vs 인터페이스 VPC 엔드포인트 vs S3 게이트웨이 엔드포인트·NAT

  - D) 가장 큰 인스턴스 유형으로 바꾸고 오토 스케일링을 끈다.

- [G-3.2-1] 가이드 SK1의 예시 구절 "dynamically adding Spot Instances, by using Amazon EC2 instances, by using Lambda behind the endpoints"(영문 PDF) / "엔드포인트 뒤에서 Lambda 사용으로 스팟 인스턴스 동적 추가"(한국어판)가 가리키는 단일 공식 아키텍처·패턴은 무엇인가? — 확인한 곳: SageMaker 개발자 가이드(inference-cost-optimization, deployment-best-practices, model-managed-spot-training), EC2 Spot 사용 설명서, ML Lens MLREL05-BP01, Generative AI Lens GENSUS01-BP01, EKS 모범 사례(CPU 추론·Spot), AWS ML 블로그(API Gateway→Lambda→엔드포인트, Lambda 컨테이너 추론). 세 구절을 하나의 구성으로 묶어 설명하는 문서는 찾지 못했다. 영문 PDF는 세 항목을 쉼표로 나열하고 한국어판은 한 문장으로 합쳐 쓴다 — 제안: 학습문서는 2.7 B 표처럼 구절을 분리해 *개별 패턴*으로 설명하고 "공식 문서가 이 구성을 하나의 아키텍처로 설명한다"고 쓰지 않는다. `MLA-C01.json` 은 공식 ko_kr 가이드와 일치하므로 수정하지 말고 영문 구절 병기만 권장.
- [G-3.2-2] 서버리스 프로비저닝된 동시성의 Application Auto Scaling을 CloudFormation으로 선언할 수 있는가? — 확인한 곳: 서버리스 추론 문서(serverless-endpoints.html: "현재 CloudFormation에서 지원되지 않음")와 CloudFormation `AWS::ApplicationAutoScaling::ScalableTarget` 레퍼런스(허용 `ScalableDimension` 에 `sagemaker:variant:DesiredProvisionedConcurrency` 포함) — 두 문서가 상충(F39·F40). 실제 배포로 검증하지 않았다 — 제안: 학습문서에는 두 서술을 병기하고 CloudFormation 지원 여부를 문항 정답 근거로 쓰지 않는다.
- [G-3.2-3] "최소값은 1 이상"(오토 스케일링 정책 개요)과 "0까지 scale-in"(비동기·추론 컴포넌트)은 어떻게 양립하는가? — 확인한 곳: endpoint-auto-scaling-policy(최소 1 이상, 예외 미기재) vs async-inference-autoscale(`MinCapacity` 0)·endpoint-auto-scaling-zero-instances(`MinInstanceCount` 0, 추론 컴포넌트)·Application Auto Scaling SageMaker 통합 페이지(추론 컴포넌트 최소 0 예시) — 제안: "일반 실시간 변형 1 이상, 추론 컴포넌트 기반·비동기는 0 허용, 서버리스 프로비저닝된 동시성은 1 이상"으로 정리해 서술.
- [G-3.2-4] 가이드 SK6의 "model latency" 예시를 대상 추적 정책의 스케일링 지표로 쓰라는 공식 권고가 있는가? — 확인한 곳: Application Auto Scaling 사전 정의 지표 목록(SageMaker 항목에 `ModelLatency` 없음), Inference Recommender 오토 스케일링 추천(`InvocationsPerInstance`·`ModelLatency` 기준), ML Lens("request latency" 예시), CDK alpha의 `metric_model_latency()` 알람 예시. 정책 지표로 쓰라는 명시 문장은 찾지 못했다 — 제안: 문항은 `InvocationsPerInstance`(SageMaker 권장)·CPU 사용률·백로그를 정답 방향으로 두고, 지연 시간은 모니터링·알람·부하 테스트 판정 지표로 설명.
- [G-3.2-5] SageMaker 엔드포인트에 Application Auto Scaling 예측(predictive) 스케일링을 쓸 수 있는가? — 확인한 곳: Application Auto Scaling "What is" 페이지(예측 스케일링을 기능으로 소개), CloudFormation `PredictiveScalingPolicyConfiguration`("ECS 서비스에서 지원"), SageMaker 정책 개요(대상 추적·단계·예약만 소개). SageMaker 미지원을 명시한 문장은 없다(부재 근거) — 제안: "공식 문서가 ECS만 명시하고 SageMaker 소개 목록에는 없다"로 서술하고 "SageMaker는 지원하지 않는다"고 단정하지 않는다.
- [G-3.2-6] SageMaker 호스팅 엔드포인트 인스턴스에 Spot을 쓸 수 있는가? — 확인한 곳: SageMaker 문서에서 Spot은 관리형 스팟 훈련(자동 모델 튜닝 포함)만 확인. 엔드포인트 구성 문서(CloudFormation `EndpointConfig`·`ProductionVariant`)에서 Spot 옵션을 찾지 못했고 가능·불가를 명시한 문장도 없다 — 제안: 단정하지 말고 문항은 "훈련 = 관리형 스팟 훈련"으로 한정.
- [G-3.2-7] SageMaker AI Savings Plans가 서버리스·비동기 추론 사용에도 적용되는가? — 확인한 곳: inference-cost-optimization 문서의 적용 대상 열거(노트북·Processing·Data Wrangler·훈련·실시간 추론·배치 변환)에 서버리스·비동기가 없다. aws.amazon.com 요금 페이지 원문은 이 노트에서 대조하지 않았다 — 제안: 서버리스·비동기와 Savings Plans의 관계를 정답 근거로 쓰지 말 것.
- [G-3.2-8] MLA-C01 시험(가이드 v1.0)이 전제하는 SageMaker Python SDK 버전과 현재 공식 문서(v3)의 차이는? — 확인한 곳: 개발자 가이드 실시간 추론 배포 문서(v3 `ModelBuilder`·`Endpoint`), SDK 1.x→3.x 업그레이드 안내(xgboost-version-0.90), GitHub README("Estimator, Model, Predictor and all their subclasses will not be supported in V3", `pip install sagemaker==2.*`), SDK v3 문서. v2의 지원 종료 일정은 문서에서 찾지 못했고 가이드 v1.0은 SDK 버전을 명시하지 않는다 — 제안: 학습문서에 v2 용어와 v3 대응을 병기(2.13 표), 문항은 API 흐름(`CreateModel → CreateEndpointConfig → CreateEndpoint`)·서비스 선택 중심.
- [G-3.2-9] "SageMaker Projects = Service Catalog 기반"이 여전히 정답 프레임인가? — 확인한 곳: What is a SageMaker AI Project?(S3 사용자 지정 템플릿·Service Catalog·SageMaker 제공 템플릿 병행, S3 권장, CodeCommit 템플릿은 2024-09-09부터 미지원), MLOps Project Templates(SageMaker 제공 템플릿 = Service Catalog 제품). 가이드 범위 내 서비스 목록에는 AWS Service Catalog가 있다 — 제안: "템플릿은 S3 또는 Service Catalog, 제공 템플릿은 Service Catalog 제품"으로 둘 다 서술.
- [G-3.2-10] 서버리스 엔드포인트의 콜드 스타트 지연을 보는 지표는 `OverheadLatency` 인가 `ModelSetupTime` 인가? — 확인한 곳: 서버리스 추론 문서(`OverheadLatency` 가 새 컴퓨트 시작 시간을 추적한다고 서술) vs SageMaker CloudWatch 지표 문서(`ModelSetupTime` = 서버리스의 새 컴퓨트 시작 시간, `OverheadLatency` = SageMaker 오버헤드). 두 문서가 다르다. 본 Task 직접 범위가 아니라 Task 4.2 영역 — 제안: 4.2 노트·학습문서에서는 CloudWatch 지표 문서를 기준으로 서술.
- [G-3.2-11] 한국어판 용어를 그대로 시험 대비 용어로 써도 되는가? — 확인한 곳: ko_kr 오토 스케일링 정책 개요·서버리스 추론·네트워크 격리 페이지는 "기계 번역으로 제공… 영어 버전이 우선"이라 표기하며, "Feature exclusions"를 "독점 기능"으로, cooldown을 "휴지 기간"으로 옮긴다 — 제안: 학습문서는 영문 용어를 병기하고 "독점 기능"은 "제외 기능(Feature exclusions)"으로 풀어 쓴다.
- [G-3.2-12] 가이드 범위 내 서비스 목록의 "AWS Auto Scaling"은 SageMaker 엔드포인트용 Application Auto Scaling을 가리키는가? — 확인한 곳: 영문 시험 가이드 PDF 서비스 목록("AWS Auto Scaling", Management and Governance), Application Auto Scaling 문서(대상 추적 제한 사항에 "AWS Auto Scaling scaling plan"을 별도 대상으로 언급). 목록의 정확한 지칭과 현재 서비스 상태를 알려 주는 공지는 찾지 못했다 — 제안: 학습문서는 SageMaker 엔드포인트에는 Application Auto Scaling, EC2에는 EC2 Auto Scaling으로 구분해 서술하고, 목록상 "AWS Auto Scaling"의 지칭은 컨트롤러가 추가 확인.
- [G-3.2-13] 변형 대상 추적 정책의 경보 평가 기간(scale-out 3분, scale-in 15분)이 공식 문서에 명시되는가? — 확인한 곳: AWS ML 블로그의 추론 컴포넌트 수준 예시에서만 확인(2.4 마지막 항목). 개발자 가이드·Application Auto Scaling 문서에서는 수치를 찾지 못했다 — 제안: 해당 수치는 블로그 예시로만 언급하고 문항 정답 근거로 쓰지 말 것.
