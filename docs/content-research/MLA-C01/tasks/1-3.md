### 2.2 Clarify 용어: facet · label · positive label · group variable

핵심 구분: **facet**은 편향을 재는 대상 속성(열), **label**은 모델이 예측할 목표(관측 레이블), **positive label values**는 특정 인구통계 그룹에 유리한 레이블 값이다 〔S11〕.

| 용어 | 공식 정의 | 설정 위치 |
|---|---|---|
| Facet / Facet value | 편향을 측정하는 대상 속성이 담긴 열(특성) / 편향이 유리·불리하게 작용할 수 있는 그 속성의 값 〔S11〕 | 분석 구성 `facet[].name_or_index`·`value_or_threshold`, SDK `BiasConfig(facet_name, facet_values_or_threshold)` 〔S13〕〔S12〕 |
| Label / Positive label values | 모델 학습 목표인 관측 레이블 / 특정 그룹에 유리한 결과를 뜻하는 레이블 값 〔S11〕 | `label_values_or_threshold`(숫자 레이블이면 임계값을 하한으로 양성 선택), SDK `label_values_or_threshold=[1]` 〔S13〕〔S12〕 |
| Group variable | CDD 계산에서 하위집단을 만드는 범주형 열. 이 지표(Simpson's paradox 관련)에만 필요 〔S11〕 | `group_variable` 〔S13〕 |
| facet a / facet d | 문서 표기: a = 편향이 유리하게 작용하는 쪽, d = 불리한 쪽. `n_a`·`n_d`는 각 facet의 관측 레이블 수 〔S2〕 | 지표 공식의 기호 |
| Bias metric / Bias report | 편향 수준을 숫자로 돌려주는 함수 / 데이터셋(또는 데이터셋+모델)에 대한 지표 모음 〔S11〕 | Data Wrangler Bias Report 화면 |

- facet은 모델이 학습에 쓰지 않는 민감 속성이어도 지정할 수 있다("even if your model is trained without using sensitive attributes"). facet을 별도 데이터셋(`facet_dataset_uri`, CSV 전용)으로 줄 수도 있다 〔S13〕.
- 범주형 facet에서 `value_or_threshold`를 생략하면 고유값마다 하나의 그룹으로 지표를 계산한다 〔S13〕.
- Data Wrangler UI: 예측 대상(Label)이 **값(Value)인지 임계값(Threshold)인지**와 양성 결과를 정하고, 검사할 열(Facet)과 그 값/임계값을 정한 뒤 지표를 고른다. 범주형이면 Value, 숫자형이면 Threshold를 선택한다 〔S16〕〔S15〕.

### 2.3 사전 훈련(pre-training) 편향 지표 8종

> 🧠 원리: 사전 훈련 지표 중 첫 번째(CI)는 결과 레이블을 보지 않는 **facet 불균형**을 재고, 나머지는 facet a·d의 **결과 레이블 분포**를 서로 다른 방식으로 비교한다 〔S2〕. 모델 출력을 쓰지 않으므로 학습 전에 계산할 수 있다 〔S11〕.

| 지표 (config 키) | 무엇을 재나 | 정의 요약 | 값 범위 (개별 지표 페이지) | 해석 | 비고 |
|---|---|---|---|---|---|
| Class Imbalance, CI (`CI`) | facet 간 구성원 수 불균형 | (n_a − n_d) / (n_a + n_d) | −1 ~ +1 | +: a가 더 많음 / 0 근처: 균형 / −: d가 더 많음 / ±1 근처: 매우 불균형 | 레이블과 무관. 큰 불균형이면 재균형 고려 〔S3〕 |
| Difference in Proportions of Labels, DPL (`DPL`) | 관측 긍정 레이블 비율 차이 | q_a − q_d (q = n(1)/n) | (−1, 1) (이진·다범주 레이블), 연속 레이블은 임계값으로 이진화 | +: a의 긍정 비율이 높음 / 0: demographic parity / −: d가 높음 | 모델은 훈련 데이터의 결정을 모방하므로 높은 DPL은 예측에도 반영될 수 있음 〔S4〕 |
| Kullback-Leibler Divergence, KL (`KL`) | 두 facet 레이블 분포의 발산(상대 엔트로피) | Σ P_a(y)·log[P_a(y) / P_d(y)] | 0 ~ +∞ | 0 근처: 유사 / 클수록 큰 발산 | 비대칭이며 삼각부등식을 만족하지 않아 진짜 거리가 아님, 자연로그(nats) 〔S5〕. 한 facet에 특정 레이블 샘플이 없으면 무한대 가능 〔S21〕 |
| Jensen-Shannon Divergence, JS (`JS`) | KL 기반의 **대칭** 발산 | ½[KL(P_a ‖ P) + KL(P_d ‖ P)], P = ½(P_a + P_d) | 0 이상 ln(2) 미만 | 0 근처: 유사 | KL의 무한대 문제를 피함 〔S6〕〔S21〕 |
| Lp-norm, LP (`LP`) | 분포 간 p-노름 거리 | (Σ ‖P_a − P_d‖^p)^(1/p), 2-노름 = 유클리드 | 0 이상 √2 미만 | 0 근처: 유사 | 음이 아닌 값이라 **역방향 편향(reverse bias)을 탐지하지 못함** 〔S7〕 |
| Total Variation Distance, TVD (`TVD`) | L1-노름의 절반 | ½ · L1(P_a, P_d) | 0 이상 1 미만 | 0 근처: 유사 | 분포 간 가능한 최대 차이, "facet a의 몇 개 결과를 바꿔야 d와 같아지는가"로 해석 〔S8〕 |
| Kolmogorov-Smirnov, KS (`KS`) | 분포 간 **최대** 발산 | max(abs(P_a(y) − P_d(y))) | 0 ~ 1 | 0 근처: 모든 결과 범주에 고르게 분포 / 1 근처: 한 결과의 레이블이 한 facet에 몰림 | 가장 불균형한 레이블을 찾아 줌. 예) 40/40/20% vs 20/10/70% → 0.5 〔S9〕 |
| Conditional Demographic Disparity, CDD (`CDDL`) | 거절 비중 − 수락 비중(DD)을 하위집단으로 조건화한 값 | DD_d = n_d(0)/n(0) − n_d(1)/n(1), CDD = (1/n) Σ n_i · DD_i (하위집단 크기 가중 평균) | −1 ~ +1 | +: facet d의 거절 비중이 수락 비중보다 큼(격차) / −: 격차 없음 / 0 근처: 평균적으로 격차 없음 | `group_variable` 필요. **Simpson's paradox** 배제용, 조건화하지 않으면 CDD = 0 ⇔ DPL = 0 〔S10〕 |

- ⚠️ **문서 간 불일치**: 요약표(cheat sheet)는 KL·JS·LP·TVD 범위를 모두 "0 ~ +∞"로, DPL 범위를 [−1, +1]로 적었지만 〔S2〕, 개별 지표 페이지는 JS < ln 2 〔S6〕, LP < √2 〔S7〕, TVD < 1 〔S8〕, DPL (−1, 1) 〔S4〕로 적는다. KS 페이지의 범위 문장은 "LP values"로 오기되어 있다 〔S9〕. 학습 문서에는 개별 지표 페이지 값을 쓰고 불일치를 각주로 남기는 편이 안전하다 → [G-1.3-2].
- 암기 틀: **CI**(수·표현) · **DPL**(양성 비율) · **CDD**(하위집단으로 조건화) · **분포형 5종**(KL·JS·LP·TVD·KS).

### 2.4 지표 선택 틀, 사전 vs 사후, 데이터 유형(숫자·텍스트·이미지) 주의

1. **3분류 틀(AWS 블로그)**: ① 레이블과 무관한 facet 표현 = CI 단독, ② 긍정 레이블만 = DPL(고급: CDDL, Simpson's paradox 통제), ③ 레이블별 분포 = KL(고급: JS·LP·TVD·KS). 이진 레이블이면 분포형 지표는 DPL과 같은 통찰을 주므로 DPL로 충분하다 〔S21〕.
2. **질문 → 지표**: "그룹 표현이 현실을 반영하나?" → CI, "레이블이 한 그룹에 긍정을 더 많이 주나?" → DPL 〔S21〕. Pre-training bias는 "충분히 대표되지 않은 그룹" 또는 "편향된 레이블" 문제를 측정한다 〔S11〕.
3. **사전 vs 사후**: 사전(CI·DPL 등)은 원시 데이터의 편향, 사후(DPPL·DI 등)는 모델 예측의 편향이다 〔S11〕〔S21〕. DPL과 DPPL을 비교하면 훈련 후 긍정 비율 편향이 커졌는지 볼 수 있다 — DPPL > DPL이면 증가, DPPL < DPL이면 모델이 증폭하지 않은 것이지만 다른 지표(Counterfactual Fliptest, Accuracy Difference)의 무편향까지 보장하지는 않는다 〔S91〕. DI는 DPPL의 비율형이며 무편향 값이 1이다 〔S21〕.
4. **숫자·텍스트·이미지 (가이드 K1 문구)**: 지표 정의는 "facet별 샘플 수·레이블 분포"다 〔S3〕〔S4〕. 공식 Clarify 문서에서 사전 훈련 편향 분석 예시는 CSV·JSON Lines·JSON 같은 표 형식 데이터이고 〔S13〕, NLP·컴퓨터 비전 구성 예시는 SHAP 설명가능성용이다 〔S12〕〔S13〕. 텍스트·이미지 데이터에서 facet과 레이블을 얻는 방법은 문서에 서술이 없다 → [G-1.3-1]. 학습 문서에는 "지표는 facet 열과 레이블 열을 기준으로 계산한다"까지만 쓰고, 텍스트·이미지는 불균형 해소(2.5~2.7)와 증강 관점에서 다루는 편이 안전하다.
5. **이름이 비슷한 다른 기능 구분**: Data Wrangler의 Data Quality and Insights Report(결측·이상치·불균형·target leakage 점검)는 Bias Report와 다른 분석이다 〔S15〕. SageMaker Debugger의 내장 규칙 `ClassImbalance`는 **훈련 중** 클래스별 표본 수 불균형과 클래스별 오예측을 점검하는 별개 기능이다 〔S93〕. ⚠️ Debugger도 2026-06-30 공지의 유지보수 목록에 포함돼 있다 〔S77〕 (개별 페이지 문구는 미확인 → [G-1.3-6]).

### 2.5 클래스 불균형(CI) 해소 전략 한눈에 (K2)

> 🧠 원리: facet 불균형이 크면 모델이 큰 facet에 맞춰 적합하고 작은 facet의 훈련 오차가 커지며, 작은 데이터셋에서는 과적합 위험도 커진다 〔S3〕. 대응은 (a) 데이터 분포를 바꾸거나(리샘플링·증강·합성) (b) 학습 손실에서 소수 클래스를 더 크게 반영(가중치)하는 두 갈래다. Clarify는 불균형을 **측정**하고 "학습 전에 샘플을 재균형하라"고 안내할 뿐이며 〔S3〕, 실제 조정은 Data Wrangler(Canvas)의 Balance data 같은 별도 단계가 한다 〔S23〕.

| 전략 | 동작 | AWS 공식 문서에 이름이 붙은 구현 | 제약·주의 |
|---|---|---|---|
| Random oversampling | 소수 범주 샘플을 무작위 복제 (예: 사기가 10%면 같은 비율이 되도록 8번 복제) | Data Wrangler / Canvas **Balance data** 〔S23〕〔S92〕 | 복제이므로 새 값은 만들지 않는다. 이진 분류 개선용이며 열 벡터(column vectors)가 있는 데이터셋은 균형 조정 불가 〔S23〕. 텍스트 분류 사례: 데이터 포인트를 반복해도 소수 클래스의 중요도를 키워 성능이 오름 〔S35〕 |
| Random undersampling | 과대 대표 범주에서 샘플을 무작위로 제거해 원하는 비율을 맞춤 | Balance data 〔S23〕 | 데이터 양이 줄어듦 |
| SMOTE (Synthetic Minority Oversampling Technique) | 소수 범주 샘플 사이를 **보간**해 합성 소수 샘플 생성. 숫자 특징은 가중 평균, 비수치 특징은 두 원본 중 하나에서 확률적으로 복사. 이웃(거리)은 숫자 특징만으로 계산 〔S23〕 | Balance data의 SMOTE. 블로그: 각 샘플은 k-최근접 이웃과만 보간하며 흔한 k는 5 〔S25〕 | 비현실적 합성 샘플(예: 초식 동물인 개) 가능 〔S25〕. 과도한 오버샘플링은 특징 공간 겹침을 키워 일부 지표(Kappa·F1)가 떨어질 수 있음(사기 탐지 사례) 〔S36〕 |
| 클래스 가중치 (알고리즘 수준) | 손실에서 소수 클래스에 큰 가중을 줌 | XGBoost `scale_pos_weight` (기본 1, 전형값 sum(음성)/sum(양성)) 〔S27〕. Linear Learner `positive_example_weight_mult` (이진; `balanced`·`auto`·양의 실수, 기본 1.0, 음성 가중은 1 고정)와 `balance_multiclass_weights` (다중클래스, 기본 false) 〔S26〕 | 데이터는 그대로 두고 학습만 조정. SMOTE로 이미 균형을 맞춘 뒤에는 `scale_pos_weight`를 제거한 사례 〔S36〕 |
| 가중·층화 샘플링 | 학습 중 소수 그룹에서 더 자주 추출 | Responsible AI Lens: weighted sampling, oversampling, stratified sampling 〔S32〕 | 개념 수준 권고 |
| 증강 (augmentation) | 기존 데이터를 변형해 새 표본 생성 | 2.6~2.7 | 컴퓨터 비전에서 불균형 해소 용도로 언급 〔S29〕 |
| 합성 데이터 생성 | 생성 모델(GAN·VAE·확산 모델 등)로 새 데이터 생성 | 2.7 | 편향 승계·품질 검증 필요 〔S29〕〔S31〕 |

- ML Lens의 한 문장 요약: "리샘플링, 가중, 또는 과소 대표 그룹을 위한 합성 데이터 생성" 세 축으로 데이터 불균형을 다룬다 〔S33〕.
- **Balance data 설정** (블로그 예시): 균형을 맞출 **target column**을 고르고, 원하는 소수:다수 비율(desired ratio; 예: 0.66 → 원래 1:4였던 비율을 2:3으로)을 정한 뒤 연산자(Random oversample·Random undersample·SMOTE)를 고른다. SMOTE에는 이웃 수(number of neighbors)와 정규화 여부 옵션이 있다. 현재 이 연산자들은 **이진 분류** 문제만 지원하며, 세 방식 모두 숫자·비수치 특징이 섞인 데이터를 지원한다 〔S25〕.
- CI는 facet별 구성원 수를, Balance data는 선택한 target column의 클래스 비율을 다룬다 〔S3〕〔S25〕. 두 기능이 자동 연동된다는 문서 설명은 없다.

### 2.7 증강·합성 데이터: 정의, 용도, 주의 (K2, SK3)

- **정의**: 기존 데이터로부터 새 데이터를 인위적으로 생성하는 과정(주로 ML 학습용). 이점은 성능 향상·데이터 의존도 감소·과적합 완화·프라이버시 향상·제한된 데이터 대응이다 〔S29〕.
- **기법 분류** 〔S29〕: 컴퓨터 비전(위치·색 증강, random erasing), 오디오(노이즈·속도·피치), 텍스트(2.6), 신경 스타일 전이, 적대적 학습. 생성형 AI는 GAN·VAE·확산 모델로 합성 데이터를 만든다. AWS 예: Amazon Bedrock(생성형 데이터 증강), Rekognition Custom Labels(자동 증강).
- ⚠️ **편향 승계**: 합성 증강은 원본과 같은 편향을 가진 새 데이터를 만든다 → 증강 **전에** 원본의 편향을 먼저 해소하라 〔S29〕. 증강에는 편향 왜곡을 줄이기 위한 감독이 필요하다 〔S29〕.
- **레이블 일관성**: 증강 표본에도 원본과 같은 레이블 규칙을 유지하고, 합성 이미지는 사람이 검토(human-in-the-loop)해 품질을 높인다 〔S29〕.
- **합성 데이터 품질 검증 항목** (Responsible AI Lens RAIDP02-BP04): 사람 기준으로 현실성 확인, 특정 그룹에 편향된 예시를 만들거나 편향을 증폭하는지 점검, 분포·상관 등 통계 속성 보존, 엣지 케이스 포함 여부, 한계·실패 모드 문서화 〔S31〕.
- ⚠️ **합성 ≠ 익명화**: AWS Clean Rooms ML의 합성 데이터는 협업자 간 개인을 비식별화해 모델을 학습시키는 기능이지만, PII를 포함한 개별 값을 제거·편집·난독화하지 않는다(원본에서 레코드 전체가 아니라 값을 샘플링). 비슷한 행이 있으면 원본과 똑같아 보이는 행이 생길 수 있다 〔S30〕. 같은 문서는 클래스 분포가 크게 불균형한 열을 피하라고 권고하며(극단적 불균형은 합성 데이터의 프라이버시를 낮춤), 시계열(순차 상관 유지 필요)·텍스트·비정형 데이터는 합성을 지원하지 않는다 〔S30〕. → 불균형 해소용 합성(SMOTE·생성 모델)과 프라이버시용 합성(Clean Rooms ML)은 목적이 다르다.

### 2.8 편향 소스(선택·측정 등)의 정의·탐지·완화 (SK2)

| 편향 소스 | AWS 정의 | 문서가 제시하는 탐지·대응 |
|---|---|---|
| 선택 편향 (selection bias) | 수집한 전체 데이터셋이 모집단을 직접 대표하지 못함. 무작위 샘플링을 쓰지 않거나 다양한 데이터 포인트를 빠뜨릴 때 발생 〔S34〕 | 학습 데이터가 실제 분포를 반영하는지(그룹 표현) 점검 → CI 〔S21〕〔S3〕. 불균형은 리샘플링·가중·합성으로 대응 〔S33〕 |
| 측정 편향 (measurement bias) | 데이터 수집 과정의 오류. 모범적 수집 관행 없이 모은 데이터는 부정확하거나 비대표적 (예: 한 플랫폼 사용자만으로 실험) 〔S34〕 | 학습 전 통계 분석으로 불일치·대표성 부족을 확인 〔S34〕 |
| 레이블 편향 (label bias) | 주석자가 무의식적으로 편향을 주입. 주관적 데이터일수록 두드러짐 〔S34〕 | 레이블 분포 비교: DPL 등 〔S4〕〔S11〕. 높은 DPL은 역사적 편견을 반영한 신호일 수 있음 〔S4〕 |
| 배제 편향 (exclusion bias) | 중요한 정보를 학습 데이터에서 누락 (예: 일부 지역 억양만으로 학습한 음성 인식) 〔S34〕 | 대표성 점검 〔S34〕 |
| 회상 편향 (recall bias) | 학습 중 특정 클래스에 쏠린 표현·주의 때문에 한 클래스만 잘 식별하고 나머지는 성능이 낮음 〔S34〕 | 클래스 불균형 대응(2.5) |
| 알고리즘 편향 (algorithm bias) | 모델 구조의 설정 오류 〔S34〕 | 데이터 준비가 아니라 모델 측 이슈 → 사후 훈련 지표 〔S21〕 |
| 오래된 데이터 | 몇 년 전 과거 데이터로 학습하면 현재와 어긋난 응답 〔S34〕 | 지속 모니터링 〔S34〕 |

- **ML Lens 분류**: "선택 편향, 측정 편향, 집계(aggregation) 편향, 평가(evaluation) 편향"이 ML 수명주기 여러 단계에서 들어올 수 있다고 정리하고, 학습 전에 SageMaker AI Clarify로 민감 속성 분포를 보고 불균형·상관을 찾으라고 권한다 〔S33〕.
- **완화 3단계**: 전처리(학습 데이터 수정), 훈련 중(공정성 제약 반영), 후처리(모델 출력 조정). 본 Task의 범위는 **전처리(데이터 준비)** 다 〔S33〕. 사후 모니터링과 피드백 루프도 권고되지만 Task 4.x 영역이다 〔S33〕.
- **일반 예방**: 학습 전 통계 분석으로 불일치·대표성 부족을 확인하고, 다양한 주석팀으로 레이블 편향을 줄인다 〔S34〕. 단일 지표만 쓰는 것은 안티패턴이다 〔S33〕.

### 2.9 데이터세트 분할·셔플·층화 샘플링 (SK3)

> 🧠 원리: 분할·셔플·층화는 훈련/검증/테스트가 같은 분포를 대표하고, 순서나 그룹 구조가 학습을 한쪽으로 치우치게 하지 않도록 하는 장치다. 훈련 채널의 `ShuffleConfig` 문서는 셔플이 "bias and possible overfitting"을 줄이는 데 도움이 된다고 설명한다 〔S37〕. 층화 분할은 분할들 사이에 입력 열의 값 비율이 같게 유지되도록 한다 〔S23〕.

| 기법 | 동작 | 도구 | 언제·주의 |
|---|---|---|---|
| Randomized split | 원본에서 서로 겹치지 않는 무작위 표본으로 분할 | Data Wrangler Split data 〔S23〕 | 큰 데이터에서는 ordered split보다 느릴 수 있음 |
| Ordered split | 관측의 순서대로 분할(예: 앞 80% 훈련, 뒤 20% 테스트) | 〔S23〕 | 기존 순서를 유지해야 할 때 |
| Stratified split | 입력 열의 각 값이 각 분할에 비례해 들어가게 분할 (예: 값 1·2·3의 약 80%씩이 훈련 세트로) | 〔S23〕 | 입력 열의 고유값이 **100개 이하**여야 함 |
| Split by key | 같은 키(예: customer_id)가 둘 이상의 분할에 나타나지 않게 분할 | 〔S23〕 | 동일 고객의 데이터가 훈련·테스트에 섞이는 것을 방지 |
| 공통 옵션 | splits 비율의 합은 1, error threshold(0~1, 0이면 정확·값이 크면 성능↑ 정확도↓), random seed(재현 가능한 분할) | 〔S23〕 | |
| Sampling 변환 | Limit(첫 행부터), Randomized, Stratified. 층화 표본은 원본 분포를 대표하게 함 | Data Wrangler 〔S23〕 | 사용 사례별로 다른 표본·변환 적용 가능 |
| Canvas 샘플링 | FirstK / Random / Stratified. FirstK는 단순하지만 무작위 정렬이 아니면 편향이 생길 수 있음 | Canvas 데이터 플로우 〔S24〕 | 탐색용 표본 |
| Quick model (Data Quality and Insights Report) | 데이터를 80% 훈련 / 20% 검증 폴드로 나눔, 분류는 층화 분할(각 분할의 레이블 비율 동일) | Data Wrangler 분석 〔S15〕 | 별도의 Quick Model 시각화는 70% / 30%로 나눔 〔S15〕 |
| 훈련 채널 셔플 | `ShuffleConfig(Seed)`: S3Prefix 매치 결과·manifest의 객체 순서·augmented manifest의 JSON 줄을 셔플. Pipe 모드면 매 에폭 시작 시 셔플. `ShardedByS3Key`와 결합하면 노드 간에도 셔플 | `CreateTrainingJob` 채널 설정 〔S37〕 | 큰 데이터에서 에폭마다 순서를 바꿔 편향·과적합 완화 |
| 중복 행 제거 | 중복 행은 훈련/검증을 독립 분할로 나누는 프로세스(quick model·예측력 추정·하이퍼파라미터 튜닝)를 방해 → Drop duplicates | Data Wrangler 〔S15〕 | 데이터 수집 오류가 만든 중복에 주의 |

- Pipe 모드는 관리형 샤딩과 셔플을 지원한다 〔S83〕.
- target leakage(타깃과 지나치게 상관된, 실제 예측 시점엔 없는 열)는 Data Wrangler Target Leakage 분석으로 확인한다 — AUC-ROC가 1이면 누수를 의심한다 〔S15〕.

### 2.10 S3 서버 측 암호화 옵션과 전송 중 암호화 (K3)

> 🧠 원리: 서버 측 암호화는 S3가 객체를 디스크에 쓸 때 암호화하고 읽을 때 복호화한다. 요청을 인증하고 권한이 있으면 암호화 객체와 비암호화 객체의 접근 방식에 차이가 없다 〔S38〕. 옵션은 "키를 누가 관리하나(S3 / KMS / 고객 제공)"와 "암호화 계층 수"로 갈린다 〔S38〕.

| 옵션 | 키 관리 | 핵심 사실 | 권한·감사 |
|---|---|---|---|
| SSE-S3 | S3 관리 키. 객체마다 고유 키를 쓰고 그 키를 정기 교체되는 루트 키로 다시 암호화, AES-256 | **모든 버킷의 기본값**. 2023-01-05부터 모든 신규 객체 업로드가 추가 비용·성능 영향 없이 자동 암호화 〔S38〕. 기존에 암호화되지 않은 버킷의 **기존 객체는 자동 암호화되지 않음**, SSE-S3 또는 SSE-KMS 기본 설정이 이미 있는 버킷은 변경 없음 〔S41〕 | 별도 키 권한 없음 |
| SSE-KMS | AWS KMS 키 (AWS managed `aws/s3` 또는 customer managed) | 키 정책·교체·비활성·CloudTrail 감사를 직접 통제. 키는 버킷과 **같은 Region**의 **대칭** 키만. S3 Bucket Keys로 KMS 요청 비용을 최대 99% 절감. AWS managed key로 암호화한 객체는 교차 계정 공유 불가 → customer managed key 필요 〔S40〕. 기본 암호화를 SSE-KMS로 바꿔도 기존 객체의 암호화 유형은 그대로이며 S3 Batch Operations의 Copy로 재암호화한다 〔S38〕 | 업로드 `kms:GenerateDataKey`, 다운로드 `kms:Decrypt` (멀티파트 업로드는 둘 다) 〔S40〕 |
| DSSE-KMS | AWS KMS 키 | SSE-KMS와 비슷하나 독립된 **AES-256 두 계층**(KMS 데이터 키 → 별도 S3 관리 키)을 서버 측에서 모두 적용. 다층 암호화를 요구하는 컴플라이언스에 대응하면서 S3 데이터를 분석하는 다양한 서비스를 쓸 수 있음 〔S38〕 | KMS 키 정책 |
| SSE-C | 고객이 **요청마다** 키를 제공 | 키를 매 요청에 보내야 해서 다른 사용자·역할·AWS 서비스와 접근을 공유하기 비실용적 〔S39〕. ⚠️ **2026-04부터 신규 범용 버킷과 SSE-C 객체가 없는 기존 버킷에서 기본 차단**. 차단 중 SSE-C를 지정한 PutObject·CopyObject·PostObject·멀티파트·복제 요청은 HTTP 403 AccessDenied. 필요하면 `PutBucketEncryption`으로 `BlockedEncryptionTypes`를 `NONE`으로 설정 〔S39〕 | 키 관리는 전부 고객 몫 |

- 네 옵션은 **상호 배타적**이며 같은 객체에 서로 다른 유형을 동시에 적용할 수 없다 〔S38〕. 요청에서 다른 유형을 지정하려면 SSE-KMS·DSSE-KMS·SSE-C를 쓰고, 버킷 기본 설정으로 바꿀 수 있는 것은 SSE-KMS·DSSE-KMS다 〔S38〕.
- 요청이 `aws:kms`만 지정하고 키 ID를 주지 않으면 S3는 AWS managed key를 쓰는 것으로 본다 〔S40〕. 키 별칭(alias)은 요청자 계정에서 해석되므로 교차 계정에서는 완전한 키 ARN을 권장한다 〔S40〕.
- **전송 중(in transit)**: S3에서 HTTPS(TLS) 연결만 허용하려면 버킷 정책에서 `aws:SecureTransport` 조건 키가 false(= HTTP로 보낸 요청)인 요청을 Deny한다 〔S42〕. SageMaker API·콘솔 요청은 TLS 1.2를 요구하고 1.3을 권장한다 〔S55〕. SageMaker 서비스 플랫폼 내부의 일부 intranetwork 트래픽(분산 학습·처리 작업의 노드 간 통신)은 기본적으로 암호화되지 않으며 선택적으로 암호화한다(2.11) 〔S54〕.
- ML Lens: 암호화는 **필드 수준 암호화·데이터 난독화**와 함께 설계하고, AWS Glue가 PII를 자동 탐지하며 KMS·CloudHSM이 암호화 전략을 지원한다고 정리한다 〔S60〕.

### 2.11 SageMaker에서 KMS 키를 지정하는 위치와 권한 (K3)

> 🧠 원리: SageMaker는 S3 데이터를 ML 스토리지 볼륨으로 가져와 처리하므로 "작업 중 볼륨", "S3로 나가는 출력", "서비스 전용 저장소(Feature Store·Studio의 EFS)", "노드 간 트래픽"을 따로 암호화한다. KMS 키를 주지 않으면 볼륨은 일회용(transient) 키로 암호화되고 그 키는 즉시 폐기된다 〔S44〕.

| 대상 | 파라미터 (API) | 암호화 범위 | 메모 |
|---|---|---|---|
| 노트북·처리·학습·튜닝·배치 변환·엔드포인트의 ML 스토리지 볼륨 | AWS KMS 키를 SageMaker에 전달 〔S44〕 | 볼륨 | 미지정 시 transient 키. 노트북 인스턴스는 키가 없으면 시스템 관리 KMS 키로 OS·ML 데이터 볼륨을 암호화 〔S44〕 |
| 학습 작업 볼륨 | `CreateTrainingJob` → `ResourceConfig.VolumeKmsKeyId` 〔S45〕 | 학습 ML 인스턴스의 스토리지 볼륨 | Nitro 기반 로컬 스토리지 인스턴스는 하드웨어 모듈로 암호화되어 `VolumeKmsKeyId`를 요청할 수 없음 〔S45〕 |
| 학습 출력 | `OutputDataConfig.KmsKeyId` 〔S46〕 | S3의 모델 아티팩트 (S3 서버 측 암호화) | 키 ID·ARN·별칭 모두 가능, 실행 역할에 `kms:Encrypt` 필요. 키 정책이 `CreateTrainingJob`·`CreateTransformJob`·`CreateHyperParameterTuningJob`에 지정한 역할에 권한을 줘야 함. 미지정 시 역할 계정의 S3 기본 KMS 키 〔S46〕 |
| 처리 작업 볼륨 | `ProcessingResources.ClusterConfig.VolumeKmsKeyId` 〔S47〕 | 처리 ML 인스턴스의 스토리지 볼륨 | Nitro 로컬 스토리지 인스턴스는 지정 불가 〔S47〕 |
| 처리 작업 출력 | `ProcessingOutputConfig.KmsKeyId` 〔S48〕 | 처리 출력 (모든 출력에 적용) | 키 ID·ARN·별칭 〔S48〕 |
| 엔드포인트 | `CreateEndpointConfig.KmsKeyId` 〔S49〕 | 엔드포인트를 호스팅하는 ML 인스턴스의 스토리지 볼륨 | 키 정책이 `CreateEndpoint`·`UpdateEndpoint`에 지정한 역할에 권한을 줘야 함. Nitro 로컬 스토리지는 이 파라미터로 암호화되지 않음 〔S49〕 |
| Feature Store | 온라인: `OnlineStoreSecurityConfig.KmsKeyId` 〔S52〕. 오프라인: 피처 그룹 생성 시 오프라인 S3 위치용 KMS 키 〔S51〕 | 온라인 스토어의 S3 객체 / 오프라인 스토어 S3 위치 | `CreateFeatureGroup` 호출자는 `kms:Encrypt`·`Decrypt`·`DescribeKey`·`CreateGrant`·`RetireGrant`·`ReEncryptFrom`·`ReEncryptTo`·`GenerateDataKey`·`ListAliases`·`ListGrants`·`RevokeGrant`, 데이터 평면(`PutRecord`·`GetRecord`·`DeleteRecord`)은 `kms:Decrypt` 〔S52〕. 오프라인 스토어는 `roleArn`에 `kms:GenerateDataKey` 〔S51〕 |
| Studio (도메인) | `CreateDomain.KmsKeyId` 〔S50〕 | 도메인에 붙는 EFS 볼륨 | 기본은 AWS managed key, 더 많은 제어가 필요하면 customer managed key 〔S50〕 |
| 컨테이너 간 트래픽 (분산 학습) | `EnableInterContainerTrafficEncryption=True` (`CreateTrainingJob`·`CreateHyperParameterTuningJob`) 〔S53〕 | 인스턴스 간 통신 (기본은 비암호화 〔S54〕) | 사전 조건: 보안 그룹에 자기 자신(Self Security Group ID)을 소스로 하는 인·아웃바운드 규칙 UDP 500, ESP 50(포트 N/A) 〔S53〕 |

- **컨테이너 간 암호화의 영향**: 훈련 시간이 늘 수 있고(특히 분산 딥러닝), 영향받는 알고리즘은 비용도 늘지만 XGBoost·DeepAR·linear learner 같은 내장 알고리즘은 통상 영향이 작다. 단일 인스턴스 작업에는 영향이 없다. 분산 ML 프레임워크·알고리즘은 통상 훈련 데이터가 아니라 가중치처럼 모델 관련 정보를 주고받는다. 의료 분야는 노드 간 통신 암호화가 모범 사례다 〔S53〕.
- **강제 수단 (IAM 조건 키)**: `sagemaker:VolumeKmsKey`가 null이 아닐 때만 작업 생성을 허용하면 볼륨 암호화를 강제하고, `sagemaker:InterContainerTrafficEncryption`이 true일 때만 허용하면 컨테이너 간 암호화를 강제한다 〔S57〕.
- **키 정책·권한 요건 정리**:
  1. 키 정책이 KMS 접근 제어의 기본 수단이다. 키 정책이 허용하지 않으면 IAM 정책만으로는 허용할 수 없고(기본 키 정책은 IAM 정책을 활성화하는 문장을 포함), 키 정책은 Region 단위로 적용된다 〔S56〕.
  2. SSE-KMS로 암호화된 S3 입력을 읽으려면 실행 역할에 `kms:Decrypt`, 출력 쓰기에는 `kms:GenerateDataKey`(및 `kms:Encrypt`)가 필요하다 〔S40〕〔S46〕.
  3. 작업의 ML 스토리지 볼륨에 KMS 키를 쓰면 IAM 정책에 `kms:CreateGrant`도 허용해야 한다 〔S58〕.
  4. 출력 버킷이 다른 계정이면 AWS managed key(`aws/s3`)의 키 정책은 편집할 수 없어 교차 계정 권한을 줄 수 없으므로, **자체 customer managed key**를 작업 요청에 지정하고 실행 역할이 그 키로 암호화할 수 있게 한다 〔S44〕.
  5. SageMaker 출력을 S3 Express One Zone(디렉터리 버킷)에 저장하면 SSE-S3로 암호화되며 SSE-KMS는 지원되지 않는다 〔S44〕.
- ⚠️ 기본 암호화 설명이 문서마다 다르다(한 페이지는 "AWS managed key for Amazon S3 (SSE-S3)"로, 다른 페이지·API 레퍼런스는 "역할 계정의 S3 기본 KMS 키"로 서술) → [G-1.3-5] 〔S43〕〔S44〕〔S46〕.

### 2.12 민감 데이터 탐지·분류·익명화·마스킹 서비스 (K4)

> 🧠 원리: ML Lens는 민감 데이터를 학습에 쓰기 전에 **식별 → 분류 → 처리**(데이터 제거·마스킹·토큰화·PCA 등) 순서로 다루라고 한다 〔S59〕. 서비스마다 입력(S3 객체 / 텍스트 / 표 형식 컬럼)과 결과(탐지·보고만 / 편집 / 해시·암호화)가 다르다.

| 서비스 | 입력·대상 | 하는 일 | 핵심 제약·메모 |
|---|---|---|---|
| Amazon Macie | **S3 객체** | 머신러닝과 패턴 매칭(managed data identifiers)으로 민감 데이터를 탐지하고, 정규식 기반 custom data identifier를 직접 정의할 수 있다. 탐지하면 sensitive data finding을 만든다 〔S61〕〔S62〕 | 방식 2가지: **자동 민감 데이터 검색**(버킷 인벤토리를 지속 평가하고 샘플링으로 대표 객체를 골라 분석)과 **민감 데이터 검색 작업**(대상 버킷·샘플링 깊이·조건을 지정, 1회 또는 반복) 〔S62〕. 문서가 서술하는 기능은 탐지·보고이고 마스킹·편집은 서술되지 않는다 |
| Amazon Comprehend (PII) | **영어·스페인어 텍스트 문서** | PII 엔터티의 위치 파악(실시간 분석 또는 비동기 배치) 또는 **편집(redaction)** 〔S63〕 | 편집은 **비동기 배치 작업만** 가능 〔S63〕. `StartPiiEntitiesDetectionJob`, `Mode=ONLY_REDACTION`, `RedactionConfig`: `PiiEntityTypes`(전부는 `["ALL"]`), `MaskMode` = `REPLACE_WITH_PII_ENTITY_TYPE`(예: "[NAME]") 또는 `MASK`(+ `MaskCharacter` 한 글자) 〔S64〕. 입력·출력 버킷은 호출하는 API와 같은 Region 〔S64〕 |
| Amazon Comprehend Medical (PHI) | **임상 텍스트** (영어만) | `DetectPHI`로 PHI 엔터티만 탐지 (모든 엔터티는 `DetectEntitiesV2`) 〔S65〕〔S66〕 | 엔터티마다 신뢰 점수를 주며, 규정 준수 용도에는 추가 사람 검토를 권고한다. HIPAA의 18개 식별자와 1:1 대응하지는 않는다 〔S65〕 |
| AWS Glue — Detect Sensitive Data (Glue Studio 시각적 ETL 변환 / `detect()` API) | ETL 중인 표 형식 데이터 (셀·컬럼 단위) | PII 탐지 + 처리: Redact detected text, Partially redact, **Apply cryptographic hash (SHA-256)**, 탐지 결과를 새 열로 추가(Enrich) 〔S67〕 | 스캔 방식 2가지: **Detect PII in each cell**(모든 행, 포괄적)과 **Detect fields containing PII**(행 샘플링 + 탐지 임계값, 비용 절감) 〔S67〕. 민감도 High(기본)/Low 〔S67〕 |
| AWS Glue DataBrew | 표 형식 데이터 (시각적 준비) | 프로파일 작업에서 PII 엔터티 탐지 + 레시피 단계로 마스킹·해시·암호화 〔S68〕〔S70〕 | 아래 목록 |

- **Glue 상세**: 엔터티는 all available patterns / categories(Universal·HIPAA·Networking·국가별 — Korea·Japan 등 포함) / specific patterns 중에서 고르고, 정규식 + context words로 사용자 정의 엔터티를 만들 수 있다. DataFrame의 `actionUsed` 값은 `DETECT`·`REDACT`·`PARTIAL_REDACT`·`SHA256_HASH`다. 열 포함·제외, 엔터티별 다른 동작 같은 fine-grained override가 가능하되, 한 열에 편집 동작 두 개(redaction·hashing)는 함께 쓸 수 없다 〔S67〕.
- **DataBrew PII 탐지 (프로파일 작업)**: `EntityDetectorConfiguration`을 정의하지 않으면 엔터티 탐지가 비활성이다. 탐지 가능한 유형은 USA_SSN, EMAIL, USA_ITIN, USA_PASSPORT_NUMBER, PHONE_NUMBER, USA_DRIVING_LICENSE, BANK_ACCOUNT, CREDIT_CARD, IP_ADDRESS, MAC_ADDRESS, USA_DEA_NUMBER, USA_HCPCS_CODE, USA_NATIONAL_PROVIDER_IDENTIFIER, USA_NATIONAL_DRUG_CODE, USA_HEALTH_INSURANCE_CLAIM_NUMBER, USA_MEDICARE_BENEFICIARY_IDENTIFIER, USA_CPT_CODE, PERSON_NAME, DATE이며, 그룹 `USA_ALL`은 PERSON_NAME과 DATE를 제외한 나머지를 포함한다 〔S70〕.
- **DataBrew 마스킹·익명화 기법 (8가지)** 〔S68〕: ① Substitution(진짜처럼 보이는 다른 값으로 대체) ② Shuffling(같은 열의 값을 다른 행끼리 섞음) ③ Deterministic encryption(같은 값 → 항상 같은 암호문) ④ Probabilistic encryption(적용할 때마다 다른 암호문) ⑤ Decryption(키로 복호화) ⑥ Nulling out / deletion(null로 바꾸거나 열 삭제) ⑦ Masking out(문자 뒤섞기 또는 일부 가리기) ⑧ Hashing(해시 함수 적용). 사용자가 되돌릴 수 없게 난독화하거나, 가역적으로 만들 수 있다 〔S68〕.
- **DataBrew PII 레시피 단계**: `CRYPTOGRAPHIC_HASH`, `DECRYPT`, `DETERMINISTIC_DECRYPT`, `DETERMINISTIC_ENCRYPT`, `ENCRYPT`, `MASK_CUSTOM`, `MASK_DATE`, `MASK_DELIMITER`, `MASK_RANGE`, `REPLACE_WITH_RANDOM_BETWEEN`, `REPLACE_WITH_RANDOM_DATE_BETWEEN`, `SHUFFLE_ROWS`. PII 전용은 아니지만 열을 지우는 `DELETE` 같은 기본 단계도 PII 처리에 쓸 수 있다 〔S69〕.
- **DataBrew 암호화 단계의 권한**: AWS Encryption SDK를 사용하며 `ENCRYPT`로 암호화한 데이터는 같은 SDK로 DataBrew 밖에서 복호화할 수 있다. `DETERMINISTIC_ENCRYPT`는 AES-GCM-SIV(256비트 키)이고 DataBrew의 `DETERMINISTIC_DECRYPT`로만 복호화한다. 암호화에는 지정한 KMS 키에 `kms:GenerateDataKey`가 필요하고, 결정적 암호화는 Secrets Manager 시크릿에 `secretsmanager:GetSecretValue`도 필요하다 〔S94〕.
- **혼동 정리 — 마스킹 vs 해시 vs 암호화**: 마스킹은 문자를 가리거나 대체(Glue의 partial redact·DataBrew의 masking out), 해시는 해시 함수 적용(Glue SHA-256·DataBrew hashing), 암호화는 키로 가역 변환(DataBrew deterministic/probabilistic). 결정적 암호화는 같은 값에 항상 같은 암호문이 나오고, 확률적 암호화는 적용할 때마다 다른 암호문이 나온다 〔S68〕.

### 2.13 접근 통제(Lake Formation)와 PII·PHI·데이터 레지던시 (K4, K5)

**Lake Formation — 분류 기반 접근 제어**

- **LF-TBAC(태그 기반 접근 제어)**: 속성으로 권한을 정의하는 권한 부여 전략이다. 속성을 LF-Tags라 부르며 Data Catalog 리소스에 붙이고, 주체에게 태그 값에 대한 권한을 주면 리소스 태그 값과 일치할 때 작업이 허용된다. 빠르게 커지는 환경, 정책 관리가 번거로운 환경에 유용하며 Data Catalog 객체가 많을 때 권장되는 방법이다. **IAM 태그와 LF-Tags는 다르며 서로 바꿔 쓸 수 없다**(LF-Tags는 Lake Formation 권한, IAM 태그는 IAM 정책용) 〔S71〕. LF-Tags는 계층적이어서 데이터베이스에 붙이면 그 안의 모든 테이블이, 테이블에 붙이면 모든 컬럼이 상속하고 필요하면 재정의할 수 있다 〔S95〕.
- **데이터 필터**: 데이터 필터를 만들어 열 수준·행 수준·셀 수준 보안을 구현하고, 테이블에 `SELECT` 권한을 부여할 때 필터를 고른다. 필터는 특정 테이블에 속하며 필터 이름, 열 사양(포함/제외할 열), 행 필터 표현식(PartiQL `WHERE` 절의 일부 문법)으로 구성된다 〔S72〕. 쿼리 결과에 포함될 열·행·셀을 제한하는 기능이며, 값을 변환하는 기능은 서술되지 않는다.

| 데이터 필터 구성 | 보안 수준 |
|---|---|
| 모든 열(wildcard) + 행 필터 표현식 | 행 수준 (row filtering) 〔S72〕 |
| 특정 열 포함/제외 + 모든 행(all-rows wildcard) | 열 수준 (column filtering) 〔S72〕 |
| 특정 열 포함/제외 + 행 필터 표현식 | 셀 수준 (cell filtering) 〔S72〕 |

**규정 준수 용어와 ML 데이터 준비에서의 함의 (K5)**

| 용어 | 공식 설명 | 데이터 준비에서의 함의 |
|---|---|---|
| PII | 개인을 식별할 수 있는 개인 데이터(주소·은행 계좌번호·전화번호 등) 〔S68〕. 텍스트에서는 개인 데이터에 대한 텍스트 참조 〔S63〕 | 분석가·데이터 과학자가 개별 개인의 PII에 접근하지 않도록 준비 단계에서 난독화한다 〔S68〕. 익명화로 충분한데 원본 PII를 그대로 쓰는 것은 안티패턴이다 〔S59〕 |
| PHI | 건강 정보. HIPAA의 18개 식별자에 기반한 PHI는 특별한 주의가 필요하다 〔S65〕 | Comprehend Medical `DetectPHI`로 탐지하되 신뢰 임계값을 정하고 사람 검토를 병행한다 〔S65〕. 의료 분야는 분산 학습 노드 간 통신 암호화가 모범 사례다 〔S53〕 |
| 데이터 레지던시 | 데이터가 저장·처리되는 지리적 위치 요구. AWS는 고객이 콘텐츠를 저장할 Region을 선택하며 고객 동의 없이 그 Region 밖으로 이동·복제하지 않는다고 설명한다(서비스 제공 또는 법·정부 명령에 따른 예외) 〔S73〕. 모든 서비스가 모든 Region에 있지는 않다 〔S73〕 | 허용 Region 밖의 작업을 막는 것이 핵심이다(아래). ML 맥락: 훈련 데이터는 훈련 작업과 같은 Region 〔S83〕, SSE-KMS 키는 버킷과 같은 Region 〔S40〕, Comprehend 입력·출력 버킷은 API와 같은 Region 〔S64〕 |

- **리전 제한 구현**: `aws:RequestedRegion` 조건 키로 지정한 Region 밖의 작업을 Deny하는 ID 기반 정책(또는 SCP). CloudFront·IAM·Route 53·Support처럼 us-east-1 단일 엔드포인트를 쓰는 글로벌 서비스는 `NotAction`으로 제외해야 요청이 막히지 않는다 〔S74〕. AWS Control Tower의 **Region deny control**은 같은 형식의 SCP로 거버넌스 대상이 아닌 Region의 작업을 차단하며, IAM·Organizations 같은 글로벌 서비스는 data residency 통제에서 제외된다 〔S75〕.
- "데이터 레지던시"의 한 문장 정의는 이번 조사에서 AWS 공식 문서로 확인하지 못했다 → [G-1.3-7].
- ⚠️ Comprehend PII 문서는 PII 접근 제어·편집에 **S3 Object Lambda Access Points**를 쓸 수 있다고 설명하지만 〔S63〕, S3 Object Lambda는 2025-11-07부터 신규 고객에게 열리지 않는 유지보수 상태다 〔S76〕 (개별 페이지는 다른 페이지로 리디렉션되어 문구는 미확인 → [G-1.3-8]).

### 2.14 데이터 품질 검증: AWS Glue Data Quality vs AWS Glue DataBrew (SK1)

> 🧠 원리: 두 도구 모두 "규칙 집합(ruleset)을 데이터에 적용해 통과·실패를 판정"한다. Glue Data Quality는 오픈소스 Deequ 기반 서버리스 서비스로 규칙을 DQDL(Data Quality Definition Language)로 쓰고 Data Catalog와 ETL 작업 두 진입점에서 실행한다 〔S78〕. DataBrew는 코딩 없이 데이터를 정제·정규화하는 시각적 준비 도구이며, 프로파일 작업(profile job)에 ruleset을 연결해 검증한다 〔S81〕〔S82〕.

| 항목 | AWS Glue Data Quality | AWS Glue DataBrew (data quality rules + profile job) |
|---|---|---|
| 성격 | 서버리스, 오픈소스 DeeQu 기반 〔S78〕 | 코딩 없는 시각적 데이터 준비 도구, 250개 이상의 기성 변환 〔S81〕 |
| 규칙 작성 | DQDL. 25개 이상의 기본 규칙에서 시작하고 "Create Data Quality Rules → Recommend rules"로 규칙을 추천받을 수 있다 〔S78〕〔S79〕 | 콘솔에서 ruleset 정의: 열 하나 또는 여러 열에 같은 규칙 적용, 여러 단순 검사를 모두(AND) 또는 하나라도(OR) 만족하도록 결합 〔S82〕 |
| 규칙 유형(예) | `ColumnValues`, `Completeness`, `IsComplete`, `IsUnique`, `IsPrimaryKey`, `Uniqueness`, `RowCount`, `Mean`, `StandardDeviation`, `ReferentialIntegrity`, `DatasetMatch`, `DataFreshness`, `CustomSql`, `DetectAnomalies` 등 30여 종 〔S79〕 | 집계값(max·min·중복 값 수) 또는 행별 비집계 값을 기대값과 비교하며, 행별 규칙은 통과 비율 임계(예: 95% 이상)를 지정. 예) 열 값이 0~100 사이, 결측 비율이 5% 이하 〔S82〕 |
| 점수·판정 | **데이터 품질 점수** = ruleset을 평가했을 때 통과(true)한 규칙의 비율 〔S78〕 | 규칙의 기준이 하나라도 충족되지 않으면 ruleset 전체가 검증 실패. 결과는 SUCCEEDED / FAILED / ERROR 이벤트로 전달 〔S82〕 |
| 실행 위치 | ① AWS Glue **Data Catalog**(카탈로그에 등록한 테이블·Athena 뷰; 콘솔·API) ② AWS Glue **ETL 작업**(Glue Studio·노트북·스크립트; Glue가 지원하는 모든 소스) 〔S78〕 | **프로파일 작업**에 ruleset을 연결해 실행 → 데이터 프로파일 + 검증 보고서를 S3에 출력. 전체 또는 일부 행 샘플 선택 〔S82〕 |
| ML 기반 기능 | 이상 탐지(anomaly detection), 동적 규칙(dynamic rules, ETL 전용) 〔S78〕〔S79〕〔S80〕 | 문서에 ML 기반 이상 탐지는 서술되지 않음 (기대값과 비교) |
| 규칙 추천 | Data Catalog에서 지원, ETL에서는 미지원. 기본 BASIC, 2026-09-18부터 Amazon Bedrock 기반 ADVANCED 모드 〔S78〕 | — |
| 불량 레코드 식별 | ETL 작업에서만 가능 (Data Catalog는 불가) 〔S78〕 | 규칙별 결과 확인 (행 격리 기능은 서술 없음) |
| 제약 | 중첩·리스트형 데이터는 평가 불가. ruleset당 규칙 2,000개·65KB. 통계는 계정당 100,000개, 최대 2년 보존 〔S78〕 | 배열·구조체 같은 복합 타입 열에는 규칙을 정의할 수 없음 〔S82〕 |

- **Glue Data Quality 구성요소**: rule(불리언을 반환하는 DQDL 표현식), analyzer(통계만 수집해 이상 탐지에 활용), ruleset(Data Catalog 테이블과 연결된 리소스, 저장 시 ARN 부여), observation(규칙·분석기 통계를 시간에 따라 분석해 만든 미확인 인사이트) 〔S78〕.
- **DQDL 문법**: 대소문자 구분, `Rules = [ ... ]` 목록, 규칙 구조 `<RuleType> <Parameter> <Parameter> <Expression>`. 복합 규칙은 `and`·`or`(각 규칙을 괄호로 감쌈)로 결합하며 기본은 열 전체를 먼저 평가한 뒤 결합하고, 행 단위로 평가하려면 `compositeRuleEvaluation.method`를 `ROW`로 설정한다. `where` 절로 규칙 적용 전에 데이터를 필터링한다 〔S79〕.
- **동적 규칙**: `last()` 연산자로 과거 결과와 비교한다(예: `RowCount > avg(last(5))`). `DynamicRules`는 **ETL에서만** 지원된다 〔S79〕.
- **이상 탐지**: 이상을 탐지하려면 최소 3개의 데이터 포인트가 필요하다. ML이 과거 추세를 학습해 값을 예측하고, 실제 값이 예측 상·하한을 벗어나면 Anomaly Observation을 만든다. 이상이 생겨도 데이터 품질 점수에는 영향이 없다. 모드는 Linear(기본; 추세·계절성)와 Fixed가 있다. 이상 탐지는 ETL과 Data Catalog 모두에서 지원되며 Catalog 테이블은 평가 실행에 `ObservationScope: ALL`을 줘서 켠다 〔S80〕.
- **DataBrew 프로파일 작업**: 통계로 중복 행 수(`DUPLICATE_ROWS_COUNT`)와 숫자 열 간 Pearson 상관(기본: 처음 10개 숫자 열)을 구성할 수 있고, 선택적으로 PII 엔터티 탐지도 켠다 〔S70〕. 한 데이터셋에 여러 ruleset을 적용할 수 있다(예: 최소 기준 ruleset과 더 엄격한 ruleset) 〔S82〕.
- **선택 기준** (문서에 기재된 기능 차이에서 도출한 정리이며, 두 도구를 직접 비교한 공식 문장은 없다):
  1. 규칙을 코드(DQDL)로 관리하고 ETL·Data Catalog 파이프라인에 품질 게이트를 넣는다 → Glue Data Quality 〔S78〕.
  2. ML 기반 이상 탐지나 과거 통계 기반 동적 임계값이 필요하다 → Glue Data Quality (동적 규칙은 ETL) 〔S79〕〔S80〕.
  3. 불량 레코드를 행 단위로 식별·격리한다 → Glue Data Quality의 ETL 작업 〔S78〕.
  4. 코딩 없이 시각적으로 프로파일링·정제하고 같은 도구에서 규칙 검증까지 한다 → DataBrew 〔S81〕〔S82〕.
  5. SageMaker 안에서 모델링 전에 점검한다면 Data Wrangler의 Data Quality and Insights Report(결측·이상치·불균형·target leakage)도 선택지다 〔S15〕.

### 2.15 모델 훈련 리소스로 데이터 로드: S3 입력 모드 vs EFS vs FSx for Lustre (SK4)

> 🧠 원리: 훈련 작업은 데이터를 (a) 시작 전에 로컬 볼륨으로 내려받거나(File), (b) S3에서 필요할 때 스트리밍하거나(FastFile·Pipe), (c) 파일 시스템을 컨테이너에 마운트(EFS·FSx for Lustre)해서 읽는다 〔S83〕. 데이터셋은 훈련 작업과 같은 AWS Region에 있어야 한다 〔S83〕.

| 소스·모드 | 동작 | 유리한 상황 | 제약·주의 |
|---|---|---|---|
| S3 **File** 모드 (기본값) | 훈련 시작 전에 전체 데이터셋을 로컬 볼륨(EBS 또는 NVMe)으로 내려받고, 다 받은 뒤 훈련을 시작 〔S83〕 | 작은 데이터셋(예: 50~100GB 미만) 〔S89〕. 로컬 모드 호환, `ShardedByS3Key`로 인스턴스별 분할 〔S83〕 | 훈련 인스턴스 스토리지에 전체 데이터가 들어가야 함. 다운로드 속도는 데이터 크기·평균 파일 크기·파일 수에 좌우되고, Spot 중단 후 재개하면 다시 다운로드한다 〔S83〕〔S89〕. 파일이 작고 많으면(50MB 미만) 오버헤드가 커져 TFRecord·WebDataset·RecordIO 같은 큰 컨테이너 파일로 직렬화를 권장 〔S89〕 |
| S3 **FastFile** 모드 | S3 객체를 POSIX 호환 파일 시스템처럼 노출하고, 스크립트가 읽을 때 필요한 만큼 스트리밍 〔S83〕 | 큰 파일(50MB 초과, 컨테이너 파일은 150MB 초과) 중심의 큰 데이터셋. FSx for Lustre보다 간단(파일 시스템·VPC 불필요) 〔S89〕 | S3 prefix만 지원(manifest·augmented manifest 불가). 무작위 접근은 되지만 순차 읽기에서 가장 좋음. CloudTrail 비용이 늘 수 있음(S3 data events, KMS 복호화 이벤트) 〔S83〕 |
| S3 **Pipe** 모드 | S3에서 높은 동시성으로 미리 가져와 이름 있는 FIFO 파이프로 스트리밍. 파이프 하나는 한 프로세스만 읽음 〔S83〕 | 디스크는 최종 모델 아티팩트 분량만 있으면 됨 〔S83〕 | 더 새롭고 쓰기 쉬운 FastFile로 대체되는 추세. 관리형 샤딩·셔플은 지원 〔S83〕 |
| **FSx for Lustre** | 파일 시스템을 마운트한 뒤 스크립트 시작. 마운트는 데이터셋 크기와 무관하게 빠름 〔S83〕 | File 모드에는 너무 크거나, 작은 파일이 많은데 직렬화가 어렵거나, 무작위 읽기 패턴일 때 〔S89〕 | 훈련 작업이 **VPC에 연결**돼야 함. 파일 시스템이 단일 AZ이므로 같은 AZ ID에 매핑되는 서브넷을 지정 〔S83〕. S3와 연결하면 파일을 읽을 때 지연 로딩(lazy load)되어 첫 에폭이 콜드 스타트이며, 미리 로드해 완화 〔S89〕 |
| **Amazon EFS** | 지정한 EFS 파일 시스템을 마운트한 뒤 스크립트 시작 〔S83〕 | 훈련 데이터가 이미 EFS에 있을 때(ML 외 용도로 쓰이는 경우) 〔S89〕 | 데이터가 훈련 전에 이미 EFS에 있어야 하고 VPC에 연결돼야 함 〔S83〕. 성능 모드 General Purpose / Max I/O, 처리량 bursting / provisioned 중 선택 〔S89〕 |

- **입력 채널 구성 (`FileSystemDataSource`)**: `CreateTrainingJob`의 `InputDataConfig[].DataSource.FileSystemDataSource`에 `FileSystemId`(fs-…), `FileSystemType`(`EFS` 또는 `FSxLustre`), `DirectoryPath`, `FileSystemAccessMode`(`ro` 또는 `rw`)를 지정하며 네 필드 모두 필수다 〔S85〕. FSx의 `DirectoryPath`는 `MountName`으로 시작해야 한다(예: `/1234abcd/ns1/`) 〔S84〕. Python SDK에서는 `FileSystemInput`(file_system_id, file_system_type, directory_path, file_system_access_mode)과 `ModelTrainer`의 `Networking(subnets, security_group_ids)`를 함께 쓴다 〔S84〕.
- **네트워크·보안 요건**:
  - 훈련 작업을 VPC에서 실행한다: `VpcConfig`의 `Subnets`·`SecurityGroupIds` 〔S86〕. 서브넷에는 인스턴스당 최소 비공개 IP 2개(EFA 사용 시 5개)가 있어야 한다 〔S86〕.
  - FSx for Lustre: 서브넷은 파일 시스템과 같은 AZ, S3와 연결한 경우 VPC에 S3 엔드포인트 추가 〔S84〕. 보안 그룹 규칙은 TCP 988과 TCP 1018–1023(Lustre 서버·클라이언트 보안 그룹 사이) 〔S87〕. EFA 지원 인스턴스(P4d·P3dn 등)는 보안 그룹 인·아웃바운드 규칙을 적절히 열어야 SageMaker가 FSx에 접근한다 〔S84〕. 훈련 작업의 IAM 역할에 FSx 접근·읽기 권한이 필요하다 〔S84〕.
  - EFS: 마운트 대상의 보안 그룹은 NFS **TCP 2049** 인바운드를 허용하고, 클라이언트 쪽은 2049 아웃바운드를 허용한다 〔S88〕. SageMaker 훈련 작업의 보안 그룹도 NFS 2049를 허용하는지 확인해야 한다 〔S90〕.
  - 인터넷이 없는 VPC에서 S3 데이터를 읽으려면 S3 VPC 엔드포인트(Gateway 유형)를 만들어야 한다 〔S86〕.
- **분산 학습의 S3 분배**: `S3DataDistributionType` = `FullyReplicated`(각 인스턴스에 전체 복제) 또는 `ShardedByS3Key`(인스턴스당 약 1/n 객체). S3 객체 수보다 많은 인스턴스를 쓰면 일부 노드는 데이터를 받지 못한 채 비용만 낸다 〔S96〕.
- **빠른 판단표** (블로그 기준): 작은 데이터 → File, 큰 파일·큰 데이터 → FastFile, 작은 파일이 많고 직렬화가 어렵거나 무작위 읽기 → FSx for Lustre, 이미 EFS에 있음 → EFS 〔S89〕. FSx for Lustre는 프로비저닝 크기(최소 1.2TB)로 과금되고 S3·EFS는 사용량 기준이다. S3를 장기 저장소로 쓰면 FSx는 Scratch 2를 권장한다 〔S89〕.

## 3. 시험에서 묻는 방식

> 출제 방식은 공식 가이드 Skill 문장과 공식 문서에서 도출한 것이다(덤프·유출 자료 미사용). 가이드의 예시 서비스(SageMaker Clarify, DataBrew, AWS Glue Data Quality, Amazon EFS, Amazon FSx)가 "무엇을 고르게 하는가"를 기준으로 4개 패턴으로 묶었다.

### 패턴 1. "학습 전에 편향을 측정하고 불균형을 완화하라" (K1·K2·SK2·SK3)
- 시나리오 단서: "모델을 학습하기 전에/데이터 준비 단계에서", 민감 속성(성별·연령) facet, "코드 없이", 소수 클래스가 5~10%, 정형·이미지·텍스트 중 데이터 유형 지정, 분할 시 클래스 비율 유지.
- 정답 방향:
  - **측정**(모델 불필요): facet 구성원 수 불균형 → CI, 긍정 레이블 비율 차이 → DPL, 하위집단으로 조건화(Simpson's paradox) → CDD, 레이블 분포 거리 → KL·JS·LP·TVD·KS. 실행은 Clarify 처리 작업(⚠️ 신규 고객 불가) 또는 Data Wrangler(Canvas)의 Bias Report. 모델 예측이 필요한 DPPL·DI는 사후 훈련 지표.
  - **완화**: 정형 → Balance data(Random oversampling / Random undersampling / SMOTE) 또는 알고리즘 클래스 가중치(`scale_pos_weight`, `positive_example_weight_mult`); 이미지 → 증강(회전·자르기·밝기·색), 텍스트 → 오버샘플링·증강; 합성 데이터는 편향 승계·품질 검증을 전제; 분할은 **층화(stratified)** 로 클래스 비율 유지, 훈련 채널은 `ShuffleConfig`로 셔플.
- 오답 유인(섞이는 선택지): Model Monitor·사후 훈련 지표(예측이 있어야 계산), SHAP 설명가능성, Data Quality and Insights Report(결측·이상치·누수), "Clarify가 데이터를 직접 균형 조정", Clean Rooms ML 합성 데이터(프라이버시용), 무작위 분할(클래스 비율 보장 없음), Canvas FirstK 샘플링(무작위 정렬이 아니면 편향), SageMaker Debugger `ClassImbalance`(훈련 중 점검).
- 근거: 〔S3〕〔S4〕〔S10〕〔S11〕〔S21〕〔S23〕〔S25〕〔S26〕〔S27〕〔S29〕〔S30〕〔S37〕

### 패턴 2. "민감 데이터를 어디서·어떻게 찾고, 가리고, 암호화하나" (K3·K4·K5)
- 시나리오 단서: S3 버킷 전체에서 PII 위치 파악 / 영어 텍스트에서 이름·전화번호를 치환 / 임상 노트의 PHI / ETL 중 SHA-256 해시 / 시각적 정제 중 결정적 암호화 / 열·행 단위 접근 제한 / 특정 Region 밖 사용 금지 / 키 사용 감사·고객 관리형 키 / 분산 학습 노드 간 통신.
- 정답 방향:
  - 탐지·분류: S3 객체 → **Macie**, 텍스트 PII → **Comprehend**(편집은 비동기 배치 `ONLY_REDACTION`), 임상 텍스트 PHI → **Comprehend Medical** `DetectPHI`.
  - 마스킹·익명화: ETL → **Glue Detect Sensitive Data**(redact·partial redact·SHA-256 hash), 시각적 준비 → **DataBrew**(대체·셔플·결정적/확률적 암호화·마스킹·해시).
  - 접근 통제: **Lake Formation** LF-Tags(속성 기반)·데이터 필터(열/행/셀).
  - 레지던시: Region 선택 + `aws:RequestedRegion` 기반 Deny(SCP·Control Tower Region deny).
  - 암호화: S3는 모든 신규 객체가 기본 SSE-S3, 감사·교차 계정은 SSE-KMS(customer managed key), 이중 계층은 DSSE-KMS; SageMaker는 `VolumeKmsKeyId`(볼륨)·`OutputDataConfig.KmsKeyId`(출력), 노드 간 통신은 `EnableInterContainerTrafficEncryption`.
- 오답 유인(섞이는 선택지): Macie로 텍스트 편집, Comprehend로 S3 버킷 인벤토리 스캔, 실시간 `DetectPiiEntities`로 편집, Lake Formation으로 값 변환(마스킹), Clean Rooms ML 합성 데이터로 PII 제거, SSE-S3로 키 사용 감사, AWS managed key로 교차 계정 공유, `VolumeKmsKeyId`로 노드 간 통신 암호화, 신규 버킷에서 SSE-C(2026-04부터 기본 차단), LF-Tags와 IAM 태그 혼동.
- 근거: 〔S38〕〔S39〕〔S40〕〔S44〕〔S45〕〔S46〕〔S53〕〔S54〕〔S61〕〔S62〕〔S63〕〔S64〕〔S65〕〔S67〕〔S68〕〔S71〕〔S72〕〔S74〕〔S75〕

### 패턴 3. "데이터 품질 규칙을 어디서 어떻게 검증하나" (SK1)
- 시나리오 단서: DQDL, 품질 점수, Data Catalog 테이블·ETL 파이프라인, ML 기반 이상 탐지·동적 임계값, 코딩 없이 시각적 프로파일링·정제, 프로파일 작업에 ruleset 연결, 불량 레코드 격리.
- 정답 방향: DQDL·점수·이상 탐지·Catalog/ETL 게이트 → **AWS Glue Data Quality**(동적 규칙은 ETL 전용, 불량 레코드 식별도 ETL). 시각적 프로파일 + ruleset 검증 + 정제 레시피 → **DataBrew**. SageMaker 안에서 모델링 전 점검 → Data Wrangler Data Quality and Insights Report.
- 오답 유인(섞이는 선택지): Clarify(편향 지표이지 품질 규칙 엔진이 아님), Macie(민감 데이터 탐지), Model Monitor(배포 후 모니터링, Task 4.x), DataBrew에서 ML 이상 탐지(문서 서술 없음), Data Catalog에서 동적 규칙·분석기·레이블 사용(ETL 전용), 룰셋 크기·개수 한도 무시.
- 근거: 〔S15〕〔S78〕〔S79〕〔S80〕〔S81〕〔S82〕

### 패턴 4. "훈련 데이터를 어떤 경로로 로드하나" (SK4)
- 시나리오 단서: 데이터 크기(수십 GB vs 수 TB)·파일 크기와 개수, 훈련 시작 지연, 무작위 읽기 패턴, 이미 EFS에 있는 데이터, VPC·보안 그룹·서브넷, Spot 재개, 분산 학습.
- 정답 방향: 작은 데이터 → File(기본값), 큰 파일 중심 대용량 → FastFile(VPC 불필요), 작은 파일이 많고 직렬화가 어렵거나 무작위 읽기 → FSx for Lustre(VPC 필수, 단일 AZ 서브넷, S3 연동 시 지연 로딩), 데이터가 이미 EFS → EFS(VPC 필수, NFS 2049). 입력 채널은 `FileSystemDataSource`(FileSystemId·FileSystemType·DirectoryPath·FileSystemAccessMode).
- 오답 유인(섞이는 선택지): Pipe를 최신 권장으로 착각(FastFile로 대체되는 추세), FastFile에 manifest 사용(불가), FSx/EFS를 VPC 없이 연결, FSx를 다른 AZ 서브넷으로 연결, EFS 데이터가 훈련 시 자동 복사된다는 가정, FSx 마운트 시간이 데이터 크기에 비례한다는 가정(비례하지 않음), 분산 학습에서 인스턴스 수를 S3 객체 수보다 크게 설정.
- 근거: 〔S83〕〔S84〕〔S85〕〔S86〕〔S87〕〔S88〕〔S89〕〔S90〕〔S96〕

## 4. 흔한 함정·혼동 짝

### 짝 1. 사전 훈련(pre-training) vs 사후 훈련(post-training) 편향 지표
- 구분 기준:

| 구분 | 사전 훈련 | 사후 훈련 |
|---|---|---|
| 입력 | 원시 데이터의 facet·관측 레이블 | 데이터 + 모델의 예측 레이블 |
| 모델 필요 | 불필요 (model-agnostic) 〔S11〕 | 필요 (예측 라벨 또는 모델 → shadow 엔드포인트) 〔S13〕 |
| 예 | CI, DPL, KL, JS, LP, TVD, KS, CDD 〔S13〕 | DPPL, DI, DCA, DCR, SD, RD, DAR, DRR, AD, TE, CDDPL, FT, GE 〔S13〕 |
| SDK 메서드 | `run_pre_training_bias` | `run_post_training_bias` (둘 다는 `run_bias`) 〔S12〕 |
| 질문 | 학습 데이터에 충분한 표현이 있나 / 레이블이 편향됐나 〔S11〕 | 모델이 그룹별로 다르게 예측·오류를 내나 〔S21〕 |

  DPL(사전)과 DPPL(사후)을 비교하면 훈련이 긍정 비율 편향을 키웠는지 가늠한다 〔S91〕.
- 근거: 〔S11〕〔S12〕〔S13〕〔S21〕〔S91〕

### 짝 2. CI vs DPL vs CDD
- 구분 기준: CI는 **레이블과 무관**하게 facet별 샘플 **수**의 불균형(표현)을, DPL은 facet별 **긍정 레이블 비율**의 차이를, CDD는 DD(거절 비중 − 수락 비중)를 **하위집단(`group_variable`)으로 조건화**해 Simpson's paradox를 배제한다. 조건화하지 않으면 CDD = 0 ⇔ DPL = 0이다. 부호 방향도 다르다: CI·DPL은 양수가 "facet a 쪽이 더 많음/긍정 비율이 높음"인 반면, CDD(DD)는 양수가 **facet d의 불리함**(거절 비중이 수락 비중보다 큼)을 뜻해 방향이 반대로 느껴지기 쉽다 〔S3〕〔S4〕〔S10〕.
- 근거: 〔S3〕〔S4〕〔S10〕〔S21〕

### 짝 3. KL vs JS vs LP vs TVD vs KS (분포형 지표)
- 구분 기준:

| 지표 | 핵심 성질 | 범위 |
|---|---|---|
| KL | 비대칭·진짜 거리 아님·nats. facet에 특정 레이블이 없으면 무한대 가능 〔S5〕〔S21〕 | 0 ~ +∞ |
| JS | KL 기반이지만 **대칭**, 무한대 회피 〔S6〕〔S21〕 | 0 이상 ln(2) 미만 |
| LP | p-노름 거리, **음이 아님 → 역방향 편향 탐지 불가** 〔S7〕 | 0 이상 √2 미만 |
| TVD | L1의 **절반**, 최대 차이 〔S8〕 | 0 이상 1 미만 |
| KS | **최대** 발산, 가장 불균형한 레이블 〔S9〕 | 0 ~ 1 |

  이진 레이블이면 분포형 지표는 DPL과 같은 통찰이므로 DPL로 충분하다 〔S21〕.
- 근거: 〔S5〕〔S6〕〔S7〕〔S8〕〔S9〕〔S21〕

### 짝 4. 오버샘플링 vs 언더샘플링 vs SMOTE vs 클래스 가중치
- 구분 기준:

| 방법 | 데이터 변화 | 핵심 |
|---|---|---|
| Random oversampling | 소수 샘플 **복제**로 증가 | 새 값 없음 〔S23〕 |
| Random undersampling | 다수 샘플 **제거**로 감소 | 데이터 손실 〔S23〕 |
| SMOTE | 소수 샘플 **보간**으로 합성 샘플 증가 | 숫자는 가중 평균, 비수치는 복사, 거리는 숫자 특징만 〔S23〕 |

### 짝 5. 증강(augmentation) vs 합성 데이터 vs 복제(oversampling) — 그리고 "합성 ≠ 익명화"
- 구분 기준: 복제는 같은 표본을 반복, 증강은 기존 표본을 **변형**(이미지 자르기·회전·색 조정, 텍스트 동의어 치환), 합성 데이터 생성은 모델(GAN·VAE·확산 모델)이 **새 표본**을 만든다 〔S29〕. 증강·합성은 원본의 편향을 그대로 승계하므로 증강 전에 원본 편향을 해소하고 품질을 검증한다 〔S29〕〔S31〕. Clean Rooms ML의 프라이버시용 합성 데이터는 PII 값을 제거·편집하지 않으며 목적이 불균형 해소가 아니다 〔S30〕.

## 6. 자가 점검 문항 후보

> 후보 5개 한도 안에서 K1·K2·K3·K4/K5·SK1을 우선 덮었다. SK3(분할·셔플·증강)과 SK4(EFS·FSx)는 섹션 3 패턴 1·4, 섹션 4 짝 10에서 컨트롤러가 직접 파생할 수 있다. 모든 후보는 재료이며 verified 표시가 없다(검수는 사람 몫).

### 후보 1 (난이도: associate)
- 대응 Skill: K1 / SK2
- 문제: 은행이 대출 승인 모델을 학습하기 전에 학습 데이터를 점검한다. 연령 facet 중 40세 미만 신청자의 샘플이 전체의 8%뿐인지, 즉 결과 레이블과 무관하게 그룹 표현이 부족한지 확인하려 한다. 아직 모델이 없어 예측 라벨은 없다. 이 목적에 가장 적합한 편향 지표는?
- 보기:
  - A) Class Imbalance (CI)
  - B) Difference in Positive Proportions in Predicted Labels (DPPL)
  - C) Disparate Impact (DI)
  - D) Conditional Demographic Disparity (CDD)
- 정답: A
- 근거: 〔S3〕 https://docs.aws.amazon.com/sagemaker/latest/dg/clarify-bias-metric-class-imbalance.html , 〔S21〕 https://aws.amazon.com/blogs/machine-learning/learn-how-amazon-sagemaker-clarify-helps-detect-bias/

## 9. 확인 필요 항목

- [G-1.3-1] 가이드 K1은 "숫자, 텍스트 및 이미지 데이터에 대한 사전 훈련 편향 지표"를 말하는데, 텍스트·이미지 데이터에서 facet과 레이블을 어떻게 정의하고 사전 훈련 지표를 어떻게 적용하는지 설명한 공식 문서를 찾지 못했다. Clarify 문서에서 사전 훈련 편향 분석 예시는 표 형식(CSV·JSON Lines·JSON·Parquet)이고, NLP·컴퓨터 비전 구성은 SHAP 설명가능성용으로만 제시된다 — 확인한 곳: S11, S12, S13 — 제안: 학습 문서에는 "지표 정의는 facet 열과 레이블 열 기준"까지만 쓰고 텍스트·이미지 적용 방법은 쓰지 않는다.
- [G-1.3-2] Clarify 요약표(S2)와 개별 지표 페이지의 값 범위 표기가 다르다. 요약표는 KL·JS·LP·TVD를 모두 "0 ~ +∞", DPL을 [−1, +1]로 적었고, 개별 페이지는 JS [0, ln 2), LP [0, √2), TVD [0, 1), DPL (−1, 1)로 적는다. KS 페이지의 범위 문장은 "LP values"로 오기되어 있다 — 확인한 곳: S2, S4, S6~S9 — 제안: 학습 문서는 개별 지표 페이지 값을 쓰고 불일치를 각주로 남기며, 문항에서는 범위 숫자를 정답 근거로 삼지 않는다.
- [G-1.3-3] 시험 가이드 Version 1.0은 Clarify를 명시하지만 Clarify는 신규 고객에게 닫힌 Maintenance 상태다. 이 상태가 실제 출제(예: Clarify 대신 다른 도구를 묻는지)에 어떻게 반영되는지는 공식 문서로 확인할 수 없다 — 확인한 곳: S1, S19, S77 및 가이드 PDF 텍스트 — 제안: 학습 문서와 문항 해설에 ⚠️ 상태를 병기하고, 컨트롤러가 섹션 8(MLA-C02 비교)에서 MLA-C02의 대응 Task 1.3 "Validate data quality and manage bias"와 함께 서술한다.
- [G-1.3-4] Data Wrangler(Canvas) Bias Report의 지표 목록과 "기본 선택 지표"에 대해 공식 문서는 "지표를 선택한다"까지만 서술하고, 기본 지표가 CI·DPL·JS라는 설명은 AWS 블로그(S22)에만 있다. Balance data의 target column·desired ratio·이웃 수 옵션도 블로그(S25)에만 있고 공식 문서(S23)에는 연산자 설명만 있다 — 확인한 곳: S14, S15, S16, S22, S23, S25 — 제안: 해당 UI 세부는 [블로그] 근거로 표기한다.
