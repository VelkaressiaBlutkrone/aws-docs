### 2.1 ML 인프라 핵심 성능 지표(활용률·처리량·가용성·확장성·내결함성)와 ML Lens 원칙

K1은 ML 인프라의 주요 성능 지표 예시로 **활용률(utilization)·처리량(throughput)·가용성(availability)·확장성(scalability)·내결함성(fault tolerance)** 을 든다. 공식 문서에서 이 5개를 한 문장으로 정의한 곳은 찾지 못했다(→ 섹션 9 [G-4.2-1]). 대신 Well-Architected Machine Learning Lens가 (1) 추론 엔드포인트의 핵심 KPI로 "지연·처리량·자원 활용률"을 명시하고 〔S4〕, (2) 설계 원칙 "Enable resiliency"에서 ML 모델의 내결함성과 복구 가능성을 검증하라고 하며 〔S3〕, (3) 필러를 정의한다 — 성능 효율성은 "컴퓨팅 자원의 효율적 사용" 〔S5〕, 신뢰성은 "워크로드가 의도한 기능을 올바르고 일관되게 수행하는 능력" 〔S6〕. 아래 표는 이 문장들을 SageMaker AI 지표에 이어 붙인 **학습용 정리**이며 표 자체가 AWS 문장은 아니다.

| 개념 | 묻는 질문 | SageMaker AI에서 보는 곳 | 근거 |
|---|---|---|---|
| 활용률 | 인스턴스가 얼마나 일하는가 → 과소·과다 프로비저닝 판단 | `CPUUtilization`·`MemoryUtilization`·`DiskUtilization`·`GPUUtilization` (`/aws/sagemaker/Endpoints`) | 〔S1〕〔S4〕, 경보 예시: CPU 지속 80% 초과·20% 미만 〔S50〕 |
| 처리량 | 단위 시간에 몇 건을 처리하는가 | `Invocations`(Sum), `InvocationsPerInstance` | 〔S1〕〔S4〕 |
| 가용성 | 요청에 계속 응답하는가 | 운영 엔드포인트의 다중 인스턴스·다중 AZ 배치, `Invocation5XXErrors`·`InvocationModelErrors` | 〔S8〕〔S1〕 |
| 확장성 | 부하 변화에 맞춰 용량이 늘고 줄어드는가 | 엔드포인트 오토 스케일링과 이를 뒷받침하는 모니터링 | 〔S7〕〔S12〕 |
| 내결함성 | 장애가 나도 서비스와 복구가 유지되는가 | 다중 AZ 분산, 헬스 체크(/ping) 실패 시 인스턴스 자동 교체, 서버리스의 Lambda 연동 내결함성 | 〔S3〕〔S8〕〔S77〕〔S14〕 |

> 🧠 원리: 활용률·처리량은 "자원을 효율적으로 쓰는가"(성능 효율성·비용) 질문이고, 가용성·확장성·내결함성은 "필요할 때 계속 동작하는가"(신뢰성) 질문이다. 이 분류는 필러 정의 두 개 〔S5〕〔S6〕를 근거로 한 것이다.

문서 근거가 있는 가용성 수치와 권고: 운영 엔드포인트마다 인스턴스를 여러 개 배포하고, VPC를 쓰면 서로 다른 AZ의 서브넷을 2개 이상 지정하며, 추론 컴포넌트로 99.95% 가용성을 목표로 하면 복사본을 2개 초과로 두고 관리형 오토 스케일링의 최소 인스턴스를 2로 설정한다 〔S8〕. SageMaker AI는 AZ 장애나 인스턴스 장애 시 인스턴스를 AZ 전반에 다시 분산하려 시도한다 〔S8〕.

ML Lens MLOPS05-BP01(배포 환경 지표 수립)의 실행 단계를 시험 관점으로 줄이면 다음과 같다 〔S4〕: CloudWatch로 성능 지표 수집(엔드포인트는 CPU·Memory·Disk 활용률, `ModelLatency`, `InvocationsPerInstance`) → 사고 시 대시보드·로그·트레이스로 원인 분석 → KPI 정의 → 경보 기반 SNS 알림 → 이상 탐지로 KPI 예상 범위를 만들어 이탈 시 배포 중단·롤백 → EventBridge로 자동 워크플로 → X-Ray로 분산 추적. 같은 문서가 Model Monitor를 데이터 드리프트 감시 수단으로 언급하지만 ⚠️ Model Monitor는 현재 신규 고객에게 닫혀 있다 〔S31〕(→ 2.15).

### 2.2 SageMaker AI의 CloudWatch 지표·네임스페이스·게시 주기·로그

⚠️ 명칭: 2024-12-03에 Amazon SageMaker가 **Amazon SageMaker AI** 로 이름이 바뀌었다. `sagemaker` API 네임스페이스·CLI·`AmazonSageMaker*` 관리형 정책·`AWS::SageMaker::*`·콘솔/문서 URL은 그대로다 〔S72〕. 새 "Amazon SageMaker"는 통합 데이터·분석·AI 플랫폼의 이름이라 구 SageMaker와 혼동하기 쉽다 〔S72〕.

| 네임스페이스 | 대상 | 대표 지표 | 근거 |
|---|---|---|---|
| `AWS/SageMaker` | 엔드포인트 호출(InvokeEndpoint) | `Invocations`·`InvocationsPerInstance`·`Invocation4XXErrors`·`Invocation5XXErrors`·`InvocationModelErrors`·`ModelLatency`·`OverheadLatency`·`ModelSetupTime`(서버리스), 멀티 모델: `ModelLoadingWaitTime`·`ModelDownloadingTime`·`ModelLoadingTime`·`ModelCacheHit` | 〔S1〕 |
| `/aws/sagemaker/Endpoints` | 엔드포인트 인스턴스 | `CPUUtilization`·`MemoryUtilization`·`DiskUtilization`·`GPUUtilization`·`GPUMemoryUtilization`, 멀티 모델 `LoadedModelCount` | 〔S1〕 |
| `/aws/sagemaker/InferenceComponents` | 추론 컴포넌트 | `*UtilizationNormalized` 계열 | 〔S1〕 |
| `/aws/sagemaker/TrainingJobs`·`ProcessingJobs`·`TransformJobs` | 훈련·처리·배치 변환 잡 | CPU·Memory·GPU·GPUMemory·Disk 활용률 (`DiskUtilization`은 배치 변환 미지원) | 〔S1〕 |
| `/aws/sagemaker/InferenceRecommendationsJobs` | Inference Recommender 잡 | `ClientInvocations`·`ClientInvocationErrors`·`ClientLatency`(밀리초)·`NumberOfUsers` | 〔S1〕 |
| `AWS/Sagemaker/ModelBuildingPipeline` | 파이프라인 실행·단계 | `ExecutionStarted`/`Failed`/`Succeeded`/`Stopped`/`Duration`, `Step*` | 〔S1〕 |

- **게시 주기·보존**: 기본 1분 〔S1〕. `MetricsConfig`의 `MetricPublishFrequencyInSeconds`로 10·30·60·120·180·240·300초 중에서 바꿀 수 있고, 호출 지표(`AWS/SageMaker`)는 이때 `EnableEnhancedMetrics=True`가 필요하며 인스턴스 지표는 필요 없다 〔S1〕. `EnableEnhancedMetrics=True`이면 `InstanceId`(GPU는 `AcceleratorId`) 차원이 추가돼 인스턴스별로 드릴다운한다 〔S1〕. 지표는 15개월 보관되지만 CloudWatch 콘솔 검색은 최근 2주 안에 갱신된 지표만 보여 준다 〔S1〕.
- **값 읽기**: `CPUUtilization`은 코어별 0~100을 합산하므로 4코어면 0~400%, `GPUUtilization`도 GPU 수만큼 곱해지며, `MemoryUtilization`은 0~100%다 〔S1〕. 다중 인스턴스 잡은 인스턴스마다 지표를 보고하지만 CloudWatch 기본 보기는 전체 인스턴스 평균이다 〔S1〕.
- **로그**: 컨테이너·노트북 수명 주기 구성이 `stdout`/`stderr`로 내는 출력은 CloudWatch Logs로 간다. 로그 그룹은 엔드포인트 `/aws/sagemaker/Endpoints/[EndpointName]`(스트림 `[production-variant-name]/[instance-id]`), 훈련 `/aws/sagemaker/TrainingJobs`, 처리 `/aws/sagemaker/ProcessingJobs`, 변환 `/aws/sagemaker/TransformJobs`, Inference Recommender `/aws/sagemaker/InferenceRecommendationsJobs` 등이며 기본 보존은 무기한이고 로그 그룹에서 보존 기간을 바꾼다 〔S2〕〔S9〕. 로그 스트림이 없거나 비어 있으면 실행 역할에 `logs:CreateLogGroup`·`logs:CreateLogStream`·`logs:PutLogEvents`·`cloudwatch:PutMetricData` 등을 허용하는 정책이 있는지 확인한다 〔S76〕.
- ⚠️ 더 촘촘한 훈련 프로파일링: 지표 문서는 100ms 단위 프로파일링에 SageMaker Debugger를 권하지만 〔S1〕 ⚠️ Debugger는 신규 고객에게 닫혀 있고 〔S9〕, ⚠️ SageMaker Profiler는 2027-06-30에 지원이 종료된다 〔S10〕. Profiler 문서는 시스템 자원(CPU·GPU·메모리·디스크) 모니터링을 CloudWatch로 대체하라고 안내한다 〔S10〕.

> 🧠 원리: 호출 지표(`AWS/SageMaker`)는 "요청"을 세고, 인스턴스 지표(`/aws/sagemaker/Endpoints`)는 "자원"을 잰다. 호출이 느린 이유가 모델인지 자원 포화인지 가르려면 두 네임스페이스를 같은 시간축에 겹쳐 봐야 하고, 지표가 안 보이면 네임스페이스·차원(`EndpointName`, `VariantName`)부터 확인한다 〔S1〕.

### 2.3 지연 분해와 오류 지표 읽는 법

엔드포인트에서 클라이언트가 체감하는 전체 시간은 **네트워크 지연 + 오버헤드 지연 + 모델 지연** 으로 나뉜다 〔S1〕〔S11〕.

| 구성 | CloudWatch 지표 | 무엇을 재는가 | 줄이는 법(문서 권고) |
|---|---|---|---|
| 모델 지연 | `ModelLatency`(µs) | 모델 컨테이너와의 통신 시간 + 컨테이너 안에서 추론을 끝내는 시간 〔S1〕 | 모델을 엔드포인트 밖에서 벤치마크, SageMaker Neo 컴파일, Inferentia 컴파일, 모델이 지원하면 GPU, 과부하면 오토 스케일링 〔S11〕 |
| 오버헤드 지연 | `OverheadLatency`(µs) | SageMaker AI가 요청을 받아 응답을 돌려주기까지의 시간에서 `ModelLatency`를 뺀 값. 요청·응답 페이로드 크기, 요청 빈도, 인증/인가에 따라 변함 〔S1〕 | 페이로드 줄이기, 첫 호출 콜드 스타트는 테스트 요청으로 사전 워밍 〔S11〕. 서버리스는 콜드 스타트 시간이 여기에 포함됨 〔S15〕 |
| 네트워크 지연 | 해당 SageMaker 지표 없음(문서는 단일 모델 엔드포인트에서 모델·오버헤드 지연 지표만 제공된다고 안내) | 클라이언트↔엔드포인트 왕복, AWS 인프라 밖에서 발생 〔S11〕 | 클라이언트를 엔드포인트 리전 가까이에 두기, CDN·엣지 활용, 클라이언트 네트워크 최적화 〔S11〕 |

- 엔드 투 엔드 지연은 `ModelLatency`+`OverheadLatency`의 단순 합이 아니다 — 인터넷 구간이 더해진다 〔S75〕. 로드 테스트 때는 엔드포인트 지표에 집중하라는 권고가 있다 〔S75〕.
- 꼬리 지연은 평균이 아니라 백분위수로 본다 — `ModelLatency`의 유효 통계에 Percentiles가 포함되고 〔S1〕, 블로그는 p99·p90을 그래프로 보라고 권한다 〔S75〕.
- 오류 지표: `Invocation4XXErrors`/`Invocation5XXErrors`는 모델이 4xx/5xx를 반환한 호출(응답마다 1 또는 0, Average·Sum), `InvocationModelErrors`는 2XX가 아닌 모든 모델 호출이라 소켓 오류·비정상 HTTP 응답·요청 타임아웃까지 포함한다 〔S1〕.
- ⚠️ 단위 함정: CloudWatch `ModelLatency`는 마이크로초이고 〔S1〕, Inference Recommender 결과 표의 `ModelLatency`는 밀리초이며 〔S84〕, `ClientLatency`도 밀리초다 〔S1〕.

> 🧠 원리: 문서가 첫 단계로 권하는 것은 "CloudWatch 지표로 지연이 모델·오버헤드·네트워크 중 어디에서 나는지부터 가르는 것"이다 〔S11〕. 어디서 나는지에 따라 조치(모델/확장, 페이로드/워밍, 클라이언트 위치)가 갈리므로 진단표(2.13)도 이 순서를 따른다.

### 2.4 관찰성 도구: AWS X-Ray, CloudWatch Lambda Insights, CloudWatch Logs Insights

| 도구 | 보는 것 | 언제 쓰나 | 핵심 사실·주의 |
|---|---|---|---|
| AWS X-Ray | 애플리케이션이 처리하는 **요청 단위** 데이터 — 요청이 거치는 구성요소와 다운스트림 호출(세그먼트·서브세그먼트), 트레이스 맵으로 병목·지연 급증 식별 〔S21〕〔S79〕 | API Gateway→Lambda→(SageMaker 엔드포인트)처럼 여러 구성요소를 거치는 요청에서 **어느 구간이 느린지** 찾을 때 | ML Lens는 "ML 애플리케이션 구성요소 간 요청 추적"에 X-Ray를 권한다 〔S4〕. X-Ray 통합 서비스 목록은 '예시'이며 Lambda·API Gateway·ELB·EventBridge·SNS·SQS 등이고 SageMaker는 기재돼 있지 않다 〔S22〕(→ 섹션 9 [G-4.2-3]). `InvokeEndpoint`의 `CustomAttributes`로 trace ID를 실어 보내는 예시는 있으나 모델 코드가 응답에 되돌려야 한다 〔S80〕. ⚠️ X-Ray SDK/Daemon은 2026-02-25부터 유지보수 모드이며 OpenTelemetry 이전이 권장된다 〔S22〕(서비스 자체는 계속) |
| CloudWatch Lambda Insights | Lambda 함수의 시스템 수준 지표(CPU 시간·메모리·디스크·네트워크)와 콜드 스타트·워커 종료 같은 진단 정보 〔S23〕 | 추론 전·후처리 Lambda의 콜드 스타트·메모리 문제를 가릴 때 | CloudWatch Lambda 확장(Lambda 레이어)을 설치하면 호출마다 성능 로그 이벤트가 나가고 임베디드 메트릭 형식으로 지표가 추출된다 〔S23〕. 사용한 만큼 지표·로그와 확장 실행 시간에 과금 〔S23〕 |
| CloudWatch Logs Insights | 로그 그룹을 대화형으로 질의·분석 〔S24〕 | SageMaker `/aws/sagemaker/Endpoints/...` 로그에서 오류 패턴·느린 요청을 찾을 때, 사고 원인 후보 확인과 수정 검증 〔S24〕 | 쿼리 언어 3종(Logs Insights QL·OpenSearch PPL·OpenSearch SQL), 계정당 동시 쿼리 100개(대시보드 포함), 60분 타임아웃, 결과 7일, 스캔한 데이터량 기준 과금 〔S24〕. 여러 명령은 파이프 문자로 연결하고 `fields`·`filter`·`stats`·`sort`·`limit` 등을 쓴다 〔S81〕 |

예시 쿼리(작성자 구성, 명령 목록은 〔S81〕 기준) — 엔드포인트 로그에서 최근 오류 20건:

```
fields @timestamp, @message
| filter @message like /ERROR/
| sort @timestamp desc
| limit 20
```

> 🧠 원리: 세 도구는 보는 단위가 다르다. X-Ray는 "요청 하나가 서비스 사이를 이동한 경로", Lambda Insights는 "Lambda 실행 환경의 자원·콜드 스타트", Logs Insights는 "로그 텍스트의 집계·검색"이다. CloudWatch 지표(2.2)가 "무엇이 느려졌나"를 알려 주면 이 도구들이 "어디서·왜"를 좁힌다 〔S21〕〔S23〕〔S24〕.

### 2.6 AWS CloudTrail: 관리 이벤트 vs 데이터 이벤트, 추적 만들기, CloudTrail Lake

CloudTrail은 SageMaker AI에 대한 **모든 API 호출을 이벤트로 캡처**한다(콘솔 호출·코드 호출 모두) 〔S32〕. 용어(ko_kr 문서): 이벤트 기록(Event history), 추적(trail), 관리 이벤트(management events), 데이터 이벤트(data events), 이벤트 데이터 스토어(event data store).

| 구분 | 관리 이벤트 | 데이터 이벤트 |
|---|---|---|
| 의미 | 리소스 관리 작업(제어 평면) 〔S32〕 | 리소스 안·위에서 일어나는 작업(데이터 평면), 고빈도 〔S32〕 |
| 기본값 | 기본적으로 기록 〔S32〕 | 기본적으로 기록하지 않음, 추가 요금 〔S32〕 |
| 이벤트 기록(Event history, 90일) | 기록됨 〔S32〕 | 기록되지 않음 〔S32〕 → 추적(trail)에서 별도 선택 |
| SageMaker AI 예 | 모든 제어 평면 작업(예: `CreateEndpoint`·`CreateModel`) 〔S32〕 | `AWS::SageMaker::Endpoint` → `InvokeEndpoint`·`InvokeEndpointAsync`·`InvokeEndpointWithResponseStream`, `AWS::SageMaker::Job` → `CompleteRollout`·`Sample`·`SampleWithResponseStream` 〔S32〕 |
| 요청 파라미터 | 기록됨(예시 이벤트에 `requestParameters`) 〔S32〕 | `InvokeEndpoint`·`InvokeEndpointAsync`·`Sample`·`SampleWithResponseStream`은 요청 파라미터를 기록하지 않음 〔S32〕 |

- `InvokeEndpoint` **기록 여부**: 현재 문서 기준으로 **데이터 이벤트로 기록할 수 있다**(옵트인). 기본값은 미기록이고 이벤트 기록(Event history)에도 안 남는다 〔S32〕. 고급 이벤트 선택기(`eventCategory`=`Data`, `resources.type`, `resources.ARN`)로 필요한 엔드포인트만 골라 기록하고, 기존 추적에 `aws cloudtrail put-event-selectors`로 붙인다 〔S32〕. (→ 섹션 9 [G-4.2-4])
- 자동 모델 튜닝이 만드는 훈련 잡처럼 고객 API 호출이 아닌 서비스 이벤트는 `eventType`이 `AwsApiCall`이 아니라 `AwsServiceEvent`다 〔S32〕.
- **이벤트 기록(Event history)**: 계정을 만들면 자동으로 켜져 있고, 리전별 최근 90일의 관리 이벤트를 조회·검색·다운로드할 수 있는 변경 불가 기록이다 〔S32〕. 90일을 넘겨 보관하려면 추적을 만든다 〔S32〕〔S33〕.

**추적 만들기(SK2)** — 콘솔 절차 요약 〔S33〕〔S82〕:

1. CloudTrail 콘솔 → Trails → **Create trail**, 추적 이름 입력.
2. (조직 추적이면) 관리 계정 또는 위임된 관리자 계정에서만 만들 수 있다 〔S33〕〔S82〕.
3. **저장 위치**: 새 S3 버킷 생성(CloudTrail이 필요한 버킷 정책을 만들어 적용, 서버 측 암호화 기본 활성) 또는 기존 버킷(CloudTrail 쓰기 권한이 있는 버킷 정책 필요) 〔S82〕.
4. 로그 파일 SSE-KMS 암호화(콘솔 기본값 Enabled, 끄면 SSE-S3), **Additional settings**의 로그 파일 검증(다이제스트 파일)·SNS 알림, 선택 사항인 **CloudWatch Logs 전송**(새/기존 로그 그룹+IAM 역할; 로그 그룹은 현재 계정에 있어야 함) 〔S82〕.
5. **Choose log events**에서 관리 이벤트(Read/Write 선택)와 데이터 이벤트를 고른다. 데이터 이벤트는 추가 요금이 붙고, 고급 이벤트 선택기에서 리소스 유형(SageMaker 엔드포인트는 `AWS::SageMaker::Endpoint`)과 로그 선택기 템플릿(전체·읽기 전용·쓰기 전용 등)을 정하거나 Custom 조건을 만든다 〔S82〕〔S32〕.

- 콘솔로 만든 추적은 **모두 다중 리전 추적**이고, 단일 리전 추적은 AWS CLI로만 만든다. 다중 리전 추적을 권장한다 〔S33〕. 추적은 로그 파일을 S3로 전송하며, 진행 중인 관리 이벤트 사본 1부는 CloudTrail 요금 없이(S3 저장 요금은 별도) 전송된다 〔S32〕.
- 추적의 이점: 90일을 넘는 이벤트 기록, 지정 이벤트의 자동 모니터링·경보(CloudWatch Logs 전송), Athena로 로그 쿼리 〔S33〕. 추적 설정이 잘못되면(예: S3 버킷 접근 불가) CloudTrail이 30일 동안 재전송을 시도하며 그 요금이 부과된다 〔S33〕.

⚠️ **CloudTrail Lake(N: L14)** — 이벤트를 SQL로 질의하는 이벤트 데이터 스토어 기능 〔S32〕. 2026-05-31부터 **신규 고객에게 닫혔고** 기존 고객은 계속 사용한다. 추적·Insights·집계 이벤트는 영향 없으며 CloudWatch로의 이전이 권장된다 〔S34〕〔S35〕. 시험 가이드의 SK2는 'CloudTrail 추적 만들기'이므로 Lake는 개념 구분 정도로만 다룬다.

> 🧠 원리: CloudTrail은 "누가·언제·어떤 API를 어떤 파라미터로 호출했는가"를 남기는 **감사(audit) 기록**이다. 모델 성능 지표를 보여 주는 도구(CloudWatch)와 목적이 다르다. 데이터 이벤트는 양이 많아 기본 제외이고(이벤트 기록에도 안 남음) 필요한 리소스만 골라 추적으로 켠다 〔S32〕.

### 2.7 EventBridge로 인프라 모니터링, 그리고 CloudTrail로 재훈련 기록·모니터링·호출

**(a) SageMaker AI → EventBridge 상태 변경 이벤트(SK4)**

SageMaker AI는 상태 변경 이벤트를 **거의 실시간(near real time)** 으로 EventBridge에 보낸다. 한 상태 변경에 이벤트가 여러 번 올 수 있으며 오류가 아니다 〔S37〕. 문서 목록은 18개 유형이다(직접 센 값) 〔S37〕.

| detail-type(`source`=`aws.sagemaker`) | 활용 예 |
|---|---|
| SageMaker Training Job State Change | 훈련 완료·실패(`FailureReason`) 알림, 후속 단계 자동 시작 〔S37〕 |
| SageMaker Processing Job / Transform Job / HyperParameter Tuning Job State Change | 전처리·배치 변환·튜닝 잡 상태 감시 〔S37〕 |
| SageMaker Endpoint State Change | 엔드포인트 InService/Failed 등 상태 알림 〔S37〕 |
| SageMaker Endpoint Deployment State Change | 블루/그린·카나리 배포 중 `Baking`·`Updating`("Scaling out desired instance count to X") 등 세부 상태 〔S37〕 |
| SageMaker Model Package State Change | 모델 승인 상태 변경 등 모델 레지스트리 이벤트 〔S37〕 |
| SageMaker Model Building Pipeline Execution / Step Status Change | 파이프라인 실행·단계 상태(`currentPipelineExecutionStatus` 등) 〔S37〕 |
| Feature Group · Image · Image Version · Model Card · Model · Job · HyperPod(Cluster Event·Node Health·State Change) | 그 밖의 리소스 상태 〔S37〕 |

호출 가능한 동작 예: Lambda 호출, EC2 Run Command, Kinesis Data Streams로 중계, Step Functions 상태 머신 활성화, SNS 알림 등 〔S37〕.

**(b) CloudWatch 경보 → EventBridge**: CloudWatch는 `CloudWatch Alarm State Change`·`CloudWatch Alarm Configuration Change`·`CloudWatch Alarm Contributor State Change`를 EventBridge로 보낸다(`source`=`aws.cloudwatch`) 〔S39〕. 지표 임계 이탈(예: 엔드포인트 CPU 포화)을 EventBridge 규칙으로 받아 Lambda·SSM Automation·SNS 등으로 연결하는 데 쓴다. ML Lens는 EventBridge로 "훈련 잡 상태 변경, 엔드포인트 상태 변경, 임계값 초과 시 컴퓨팅 용량 증설" 같은 이벤트에 자동으로 응답하는 워크플로를 정의하라고 안내한다 〔S4〕.

**(c) K3 — CloudTrail로 재훈련 활동 기록·모니터링·호출**

| 단계 | 방법 | 근거 |
|---|---|---|
| 기록 | `CreateTrainingJob`·`StartPipelineExecution` 등 SageMaker 제어 평면 호출은 관리 이벤트로 기본 기록, 90일 초과 보관·분석은 추적(trail)+S3 | 〔S32〕〔S33〕 |
| 모니터링 | 추적을 CloudWatch Logs로 보내 경보를 걸거나, EventBridge 규칙으로 특정 API 이벤트를 감시 | 〔S33〕〔S36〕 |
| 호출(트리거) | "새 훈련 데이터 감지에는 AWS CloudTrail과 CloudWatch Events(EventBridge)를 결합해 Step Functions 워크플로를 자동 시작" | 〔S40〕 |
| 대상 | SageMaker Pipelines는 EventBridge 대상이며 `StartPipelineExecution`을 호출한다. 이벤트 예: S3에 새 파일 업로드, 드리프트로 인한 엔드포인트 상태 변경, SNS 토픽 | 〔S38〕 |

- 새 데이터 파일 업로드 감지 경로(문서 근거 조합): S3 객체 쓰기는 **데이터 이벤트** 〔S32〕 → 해당 버킷의 데이터 이벤트를 기록하는 추적이 있어야 하고 〔S36〕 → EventBridge 규칙이 `AWS API Call via CloudTrail` 이벤트(공개 AWS 서비스 API 호출 요청)를 매칭 〔S36〕 → 대상으로 SageMaker Pipeline 또는 Step Functions 〔S38〕〔S40〕. 대안으로 S3 버킷의 EventBridge 알림을 켜서 `ObjectCreated` 이벤트를 직접 받는 구성도 쓰인다 〔S31〕(Model Monitor 대체 솔루션이 이 방식을 사용).
- EventBridge가 CloudTrail 이벤트를 받으려면 **로깅 중인 추적이 있어야** 한다 〔S36〕. 규칙의 기본 상태 `ENABLED`는 쓰기(변경) 관리 이벤트와 데이터 이벤트를 매칭하고(데이터 이벤트는 추적이 해당 유형을 캡처하도록 설정돼 있어야 함), **읽기 전용 관리 이벤트** 는 규칙 상태가 `ENABLED_WITH_ALL_CLOUDTRAIL_MANAGEMENT_EVENTS`일 때만 매칭된다 〔S36〕.
- ML Lens MLPERF06-BP05는 재훈련 트리거를 일정·성능 임계 이탈·데이터 드리프트·새 훈련 데이터 도착으로 정의하고, 성능 지표 기반 CloudWatch 알림이 재훈련 워크플로를 알리거나 자동 실행하도록 구성하라고 한다 〔S40〕. ⚠️ 같은 문서의 드리프트 감시 수단 Model Monitor는 신규 고객에게 닫혀 있으며 CloudWatch 사용자 지정 지표+이상 탐지 경보가 가벼운 대안으로 안내된다 〔S31〕.

> 🧠 원리: CloudTrail은 감사 기록, EventBridge는 이벤트 라우터다. 둘을 잇는 이벤트가 `AWS API Call via CloudTrail`이고 〔S36〕, "S3에 파일이 올라왔다"는 사실은 S3 데이터 이벤트로 CloudTrail에 남아야 이 경로로 흐른다 〔S32〕〔S36〕. 반대로 SageMaker가 직접 보내는 상태 변경 이벤트(2.7a)는 추적 없이도 EventBridge로 온다 — SageMaker AI가 EventBridge에 직접 이벤트를 전달한다고 서술돼 있다 〔S37〕.

### 2.8 인스턴스 패밀리와 적정 규모 조정: Inference Recommender vs Compute Optimizer

**인스턴스 범주(K4)**

| 범주 | 문서 정의 | 계열 예 | ML에서의 의미 |
|---|---|---|---|
| 범용(General purpose) | 컴퓨팅·메모리·네트워킹 자원의 균형 〔S41〕 | M, T 〔S42〕 | 균형 잡힌 요구의 모델·노트북 |
| 컴퓨팅 최적화(Compute optimized) | 고성능 프로세서가 유리한 컴퓨팅 집약 애플리케이션용이며 용도 예에 **머신 러닝 추론**이 있음 〔S41〕 | C 〔S42〕 | CPU 기반 추론·배치 처리 |
| 메모리 최적화(Memory optimized) | 대용량 데이터셋을 메모리에서 처리하는 워크로드 〔S41〕 | R, X, U, z1d 〔S42〕 | 메모리 병목(큰 모델·큰 데이터프레임). 메모리 부족이면 더 큰 메모리 인스턴스로 〔S87〕 |
| 가속 컴퓨팅(Accelerated computing) | 하드웨어 가속기·보조 프로세서로 부동소수점 연산·그래픽 처리 등을 효율화 〔S41〕 | G, P, DL, Inf, Trn 등 〔S42〕 | GPU 추론·훈련 |
| 추론 최적화(AWS Inferentia: Inf1·Inf2) | 딥러닝 추론용으로 고성능·저지연 제공 〔S43〕 | Inf1/Inf2 (가속 컴퓨팅 목록에 포함 〔S42〕) | 모델을 Inferentia용으로 컴파일하면 추론당 비용을 낮추며 처리량을 높일 수 있음(모델이 지원할 때) 〔S11〕 |

- SageMaker 추론에는 Inferentia·Graviton 칩을 포함해 70종이 넘는 인스턴스 유형·크기가 있다 〔S51〕. SageMaker 훈련 인스턴스 유형은 `ml.` 접두를 뗀 EC2 인스턴스 유형에 대응한다 〔S20〕.
- 선택 순서(ML Lens): 알고리즘이 컴퓨트·메모리·I/O 중 어디에 묶이는지 먼저 분석하고 〔S83〕, 새 모델은 작은 인스턴스로 시작해 데이터로 확인될 때만 키운다 〔S83〕. 딥러닝은 GPU 이득 여부를, 전통 ML은 CPU로 충분한지를 따진다 〔S49〕.

**도구 비교(SK5)**

| 항목 | SageMaker AI Inference Recommender | AWS Compute Optimizer |
|---|---|---|
| 방식 | 로드 테스트·모델 튜닝을 자동화해 인스턴스 유형·구성을 추천 〔S44〕 | 리소스 구성과 CloudWatch 사용 지표를 분석해 rightsizing·유휴 권장(옵트인 필요, 기본 최근 14일 분석) 〔S46〕 |

| 출력 | 인스턴스 유형·개수·컨테이너 파라미터·모델 최적화와 비용·처리량·지연 지표 〔S44〕〔S49〕 | EC2 등: 사이징 권장 / **SageMaker 엔드포인트: 유휴(idle) 권장** 〔S47〕〔S48〕 |
| SageMaker 엔드포인트 적용 | 실시간·서버리스 엔드포인트를 대상으로 한다 〔S44〕 | 문서 기준 SageMaker 지원은 '유휴 권장'(14일간 호출 0건) 〔S47〕〔S48〕 ⚠️ 가이드 SK5 예시와 범위 차이 → 섹션 9 [G-4.2-2] |
| 비용 | 잡이 실행되는 동안 사용한 인스턴스에 대해서만 과금 〔S44〕 | (이 노트에서 요금 미조사) |

- **Compute Optimizer FAQ 서술**: 권장 대상 나열 문장에 'SageMaker Endpoint'가 들어 있으나 권장 유형(사이징/유휴)은 구분하지 않는다 〔S89〕. 사용자 가이드가 SageMaker에 대해 명시하는 것은 유휴 권장이다 〔S47〕〔S48〕.
- **추천 잡 2종**: Default 잡은 모델 패키지 ARN만으로 추천 인스턴스에서 일련의 부하 테스트를 실행하며 45분 안에 끝나고, Advanced 잡은 사용자가 인스턴스·트래픽 패턴·지연/처리량 요건을 정하는 맞춤 부하 테스트로 평균 2시간 걸린다. 결과에는 초기 인스턴스 수가 있어 오토 스케일링 정책 구성에 쓴다 〔S45〕. 서버리스 엔드포인트용 부하 테스트도 가능하다 〔S45〕.
- **기존 엔드포인트 벤치마크 제약**: 잡당 엔드포인트 1개·변형 1개, 오토스케일링을 쓰는 엔드포인트 불가, 실시간 전용(멀티 모델 불가). 라이브 트래픽을 받는 운영 엔드포인트에는 돌리지 않는다 〔S78〕.
- **결과 지표**: `ModelLatency`(밀리초)·`MaximumInvocations`·`CostPerHour`·`CostPerInference`·`CpuUtilization`·`MemoryUtilization` — 지연에 민감하면 지연, 처리량이 목적이면 `CostPerInference`에 초점을 둔다 〔S84〕.
- **적정 규모 신호(수치는 출처별로 구분)**: ML Lens 예시 — CPU 활용률이 지속적으로 80%를 넘으면 과소 프로비저닝, 20% 미만이면 과다 프로비저닝 신호로 경보를 둔다 〔S50〕. 블로그 — 30% 미만이면 인스턴스 축소 가능, 60~70% 안팎 활용률을 권장 〔S75〕(블로그 테스트 기반이며 공식 문서 기준이 아님). 새 모델·사용 패턴 변화 때 Inference Recommender를 다시 돌린다 〔S49〕.

> 🧠 원리: Inference Recommender는 **배포 전(또는 비운영 엔드포인트)에 모의 부하로** 후보 구성을 비교하고, Compute Optimizer는 **이미 쌓인 사용 지표로** 자원을 평가한다 〔S44〕〔S46〕. 입력(모델+샘플 vs 지표 이력)이 다르므로 "배포 전 후보 비교"는 전자의 일이다.

### 2.10 태깅 전략과 비용 할당 태그(활성화가 핵심)

1. **태그와 비용 할당 태그**: 태그는 키·값 쌍 레이블이고, 비용 할당 태그는 이를 이용해 AWS 비용을 세부 수준으로 추적한다. 유형은 **AWS 생성 태그**(AWS가 정의·적용, `aws:` 접두, 예 `createdBy`)와 **사용자 정의 태그**(사용자가 정의·적용, `user:` 접두) 2가지다 〔S57〕.
2. **활성화 필수**: 두 유형 모두 **각각 활성화**해야 Cost Explorer와 비용 할당 보고서에 나타난다 〔S57〕〔S58〕. 활성화는 Billing and Cost Management 콘솔의 Cost allocation tags에서 태그 **키** 단위로 하며, 키를 활성화·비활성화하면 같은 키의 모든 값에 적용되고, `UpdateCostAllocationTagsStatus` API로 일괄 활성화할 수 있다 〔S58〕. 조직에서는 관리 계정(또는 단독 계정)만 이 관리자 화면에 접근한다 〔S57〕.
3. **지연**: 태그를 적용하면 활성화 대상에 뜨기까지 최대 24시간, 활성화되기까지 다시 최대 24시간 〔S58〕. 모든 태그가 콘솔에 나타나기까지 최대 24시간 〔S57〕. SageMaker Studio 가이드는 활성화 후 Cost Explorer 필터에 뜨기까지 24~48시간으로 안내한다 〔S59〕.
4. **SageMaker 자동 태그**: Studio에서 만든 훈련 잡·처리 잡·커널 앱 등에 `sagemaker:domain-arn`이 자동으로 붙고, 더 세밀하게 `sagemaker:user-profile-arn` 또는 `sagemaker:space-arn`이 붙는다 〔S59〕. 2022-11-30 이후 Studio UI에서 만든 리소스부터 기본 적용된다 〔S61〕. 이 자동 태그도 **비용 분석에 쓰려면 먼저 활성화**해야 한다 〔S59〕.
5. **태그 전파(SK7 인프라 준비)**:
   - 도메인 `TagPropagation` 속성(CreateDomain/UpdateDomain)을 켜면 도메인·사용자 프로필·스페이스에 지정한 사용자 지정 태그가 Studio·JupyterLab·Code Editor·Canvas에서 만들어지는 SageMaker 리소스로 전파된다(도메인 수준 설정만 가능) 〔S60〕.
   - SageMaker 리소스는 태그 50개 한도가 있고, 도메인+프로필 태그 합계가 한도를 넘으면 리소스 생성이 실패하며 자동 ARN 태그도 한도에 포함된다 〔S60〕.
   - 하이퍼파라미터 튜닝 잡의 태그는 `AddTags` 호출 **이후** 시작되는 훈련 잡에만 전파되므로 처음부터 모두 적용하려면 `CreateHyperParameterTuningJob`의 `Tags`로 지정한다. 도메인·사용자 프로필 태그도 이후 시작하는 앱에만 적용된다 〔S62〕.
6. **전략과 거버넌스(ML Lens)**: 프로젝트·환경·ML 단계(훈련·추론·실험)·소유자·비용 센터 같은 일관된 스키마를 정하고, CloudFormation·CDK·Terraform으로 태깅을 자동화하며, AWS Config 규칙이나 Organizations 태그 정책으로 강제한다. 재훈련·호스팅 같은 ML 활동 범주로 비용을 묶는다 〔S63〕〔S64〕.

> 🧠 원리: 리소스 태그는 "리소스에 붙은 라벨"일 뿐이고, 결제 시스템이 그 라벨로 비용을 나눠 보여 주려면 **비용 할당 태그로 활성화**하는 별도 단계가 필요하다 〔S57〕. 그래서 "태그를 달았는데 Cost Explorer에서 안 보인다"의 1순위 점검 항목은 활성화 여부와 반영 지연(최대 24~48시간)이다 〔S58〕〔S59〕.

- **Savings Plans 유형 4종**: Compute(EC2·Fargate·Lambda), Database, EC2 Instance, SageMaker AI 〔S69〕. SageMaker 사용량에는 SageMaker AI Savings Plans가 맞고 Compute Savings Plans는 EC2·Fargate·Lambda 쪽이다 〔S69〕.
- **적용 대상**: SageMaker Studio Classic 노트북·On-Demand 노트북·Processing·Data Wrangler·Training·Real-Time Inference·Batch Transform의 ML 인스턴스 사용량 〔S51〕(목록은 'including'이라 서버리스·비동기 적용 여부는 단정하지 않음 → 섹션 9 [G-4.2-13]).
- **순서**: Savings Plans를 사기 전에 먼저 인스턴스를 right-size한다 〔S88〕. 약정 후보는 오래 실행될 구성요소를 골라 분석한다 〔S67〕. Cost Explorer에서 권장 약정 수준을 보고 구매한다 〔S85〕.
- **가격 약정 vs 용량 예약**: Savings Plans는 가격 할인이고 용량을 예약해 주지 않는다 〔S86〕. 특정 GPU 인스턴스 용량이 필요한 시점이 정해져 있다면 훈련 플랜처럼 용량을 예약하는 수단이 별도다 〔S70〕.

### 2.12 용량 문제 해결: 서비스 할당량, 프로비저닝된 동시성, 오토 스케일링

| 증상 | 원인(문서) | 조치 |
|---|---|---|
| `ResourceLimitExceeded` — "account-level service limit 'ml.m5.xlarge for endpoint usage' is 0 Instances …" | 계정·리전·사용 유형별 SageMaker 쿼터 초과 〔S13〕 | Service Quotas 콘솔 → AWS services → Amazon SageMaker → 해당 쿼터 선택 → **Request increase at account-level** 〔S13〕. 증설은 즉시 반영되지 않으므로 미리 요청 〔S20〕 |
| 오토 스케일링 중 "Failed to set desired instance count … service limit" | 스케일 아웃이 인스턴스 유형 쿼터에 도달 〔S12〕 | 해당 쿼터 증설 요청 〔S12〕 |
| 훈련 잡이 대기하다 `InsufficientCapacityError` | 온디맨드 용량 부재(best-effort) 〔S20〕 | `MaxPendingTimeInSeconds` 조정, 후보 인스턴스 유형 목록(instance preference list), 여러 AZ 서브넷, 훈련 플랜 〔S20〕 |
| 오토 스케일링이 아예 동작 안 함 | 선택한 AZ에 인스턴스 유형 없음, 해당 유형 용량 부족, 정책 오설정 〔S12〕 | AZ별 가용성 확인, 다른 인스턴스 유형, 임계값 조정, `describe-scaling-activities --include-not-scaled-activities` 〔S12〕 |
| 서버리스 엔드포인트 지연·스로틀 | 엔드포인트의 최대 동시성을 넘는 호출은 스로틀 〔S14〕 | `MaxConcurrency`(엔드포인트당 최대 200, 리전 합산 1000 또는 500) 조정, Provisioned Concurrency 〔S14〕 |
| 서버리스 유휴 후 첫 요청 지연 | 콜드 스타트(모델 크기·다운로드·컨테이너 시작 시간에 좌우) 〔S14〕 | Provisioned Concurrency(≤ `MaxConcurrency`) — 할당한 만큼은 밀리초 내 응답 준비 〔S14〕 |
| Lambda 콜드 스타트 | 사전 초기화된 실행 환경이 없음 〔S16〕 | 프로비저닝된 동시성(추가 요금) 〔S16〕 |

- **서비스 쿼터 모니터링**: SageMaker AI는 사용량 지표를 Service Quotas와 통합하는 서비스이며, 사용량이 쿼터에 근접하면 알리는 CloudWatch 경보를 만들 수 있고 `SERVICE_QUOTA(m1)` 수학 함수로 사용률(%)을 계산한다 〔S19〕.
- **SageMaker 서버리스**: 기본은 요청이 없으면 0으로 축소한다 〔S14〕. Provisioned Concurrency는 Application Auto Scaling으로 목표 지표 또는 일정 기반 관리가 가능하다 〔S14〕. 메모리는 1024~6144MB(1GB 단위), 엔드포인트당 최대 동시성 200, 리전당 서버리스 엔드포인트 50개 〔S14〕. 서버리스를 실시간으로 바꾸면 되돌릴 수 없다 〔S14〕.
- **오토 스케일링 설정 요소(모니터링·문제 해결 관점)**: 타깃 트래킹은 Application Auto Scaling이 CloudWatch 경보를 직접 만들고 관리한다 〔S18〕. `ScaleOutCooldown`·`ScaleInCooldown`으로 쿨다운을 정하며 쿨다운은 용량의 급격한 변동을 막는 장치다 〔S17〕〔S18〕. 최소·최대 인스턴스 수, 목표 지표, 쿨다운을 함께 설계한다 〔S50〕. 실시간 엔드포인트는 `InvocationsPerInstance`, 비동기는 `ApproximateBacklogSizePerInstance`를 스케일링 지표로 쓴다 〔S12〕.
- **스케일링이 느리거나 안 줄어드는 이유**: 경보가 여러 데이터 포인트를 모은 뒤에야 동작 → Datapoints to alarm 감소; CPU 활용률 기반 정책은 트래픽이 줄어도 스케일 다운하지 않을 수 있음; 워밍업 중인 인스턴스는 집계 지표에 포함되지 않음 〔S12〕. 블로그 설명은 스케일 아웃 경보 3분(1분 데이터 포인트 3개)·스케일 인 15분과, 쿨다운이 엔드포인트 업데이트 시간보다 짧으면 효과가 없다는 점을 든다 〔S74〕(공식 SageMaker 문서에서 수치 확인 못함 → 섹션 9 [G-4.2-9]).
- **용량 예약**: 확정된 시점에 특정 GPU 용량이 필요하면 훈련 플랜(2.11)을, 가격만 낮추려면 Savings Plans를 쓴다 〔S70〕〔S86〕.

## 3. 시험에서 묻는 방식

### 패턴 1. 지연·오류 증상에서 "어떤 지표·도구로 어디를 보고 무엇을 고치나"
- 시나리오 단서: 실시간 엔드포인트의 지연이 오른다 / `ModelLatency`는 그대로인데 `OverheadLatency`만 늘었거나 첫 호출만 느리다 / 서버리스 엔드포인트가 유휴 뒤 첫 요청에서 느리다 / 5xx가 늘었다 / API Gateway→Lambda→엔드포인트처럼 여러 구성요소를 거치는 요청에서 어느 구간이 느린지 모른다.
- 정답 방향: 먼저 CloudWatch 지표로 모델 지연·오버헤드 지연·네트워크 지연을 가른다. 모델 지연이면 모델 최적화(Neo/Inferentia)·오토 스케일링·인스턴스 상향, 오버헤드·콜드 스타트면 페이로드 축소·사전 워밍(서버리스는 Provisioned Concurrency), 5xx면 엔드포인트 로그(Logs Insights)와 인스턴스 자원 지표, 여러 서비스에 걸친 구간 지연은 X-Ray, Lambda 구간은 Lambda Insights.
- 오답 유인(섞이는 선택지): CloudTrail(API 호출 감사 도구라 성능 원인 분석에 맞지 않음), SageMaker Model Monitor(데이터·모델 품질 드리프트 감시용이며 신규 고객 중단), Inference Recommender(배포 전 벤치마크), 원인 분해 없이 인스턴스만 키우기(오버헤드·네트워크 원인에는 효과 없음).

### 패턴 2. 감사 vs 알림·자동화 vs 지표 — CloudTrail·EventBridge·CloudWatch 구분과 재훈련 호출
- 시나리오 단서: 누가 엔드포인트를 만들거나 삭제했는지 감사 / 엔드포인트 호출 이력을 남겨야 함 / S3에 새 훈련 데이터가 올라오면 재훈련 파이프라인을 자동 시작 / 훈련 잡이 실패하면 알림 / CloudWatch 경보 상태 변화에 자동 대응 / 90일을 넘는 API 기록 보관.
- 정답 방향: 감사 = CloudTrail(SageMaker 제어 평면은 관리 이벤트로 기본 기록, `InvokeEndpoint`는 데이터 이벤트로 옵트인, 90일 초과 보관은 추적(trail)+S3). 알림·자동화 = EventBridge(SageMaker 상태 변경 이벤트, CloudWatch 경보 상태 변경 이벤트, 로깅 중인 추적을 거친 `AWS API Call via CloudTrail`). 재훈련 호출 = CloudTrail 이벤트→EventBridge 규칙→SageMaker Pipelines/Step Functions. 임계 이탈 감시 = CloudWatch 경보.
- 오답 유인(섞이는 선택지): 이벤트 기록(Event history)에서 데이터 이벤트 찾기(기록되지 않음), 추적 없이 CloudTrail 이벤트를 EventBridge로 받기(추적 필요), CloudTrail Lake(신규 고객 중단), X-Ray(요청 경로 추적용), Model Monitor(드리프트 감시용이며 S3 업로드 감지 도구가 아님).

## 4. 흔한 함정·혼동 짝

### 짝 1. CloudTrail vs CloudWatch vs EventBridge vs X-Ray
- 구분 기준: "무엇에 답하나"로 가른다.

| 서비스 | 답하는 질문 | SageMaker 예 |
|---|---|---|
| CloudTrail | 누가·언제·어떤 API를 호출했나(감사 기록) | `CreateEndpoint` 등 관리 이벤트, `InvokeEndpoint`는 데이터 이벤트(옵트인) 〔S32〕 |
| CloudWatch(지표·로그·경보) | 지금 얼마나 느리고 바쁜가, 임계 초과를 알려라 | `ModelLatency`, `CPUUtilization`, 경보·대시보드 〔S1〕〔S25〕 |
| EventBridge | 어떤 상태 변화·API 호출이 일어나면 무엇을 자동 실행하나 | Training Job State Change → Lambda/Pipelines 〔S37〕〔S38〕 |
| X-Ray | 요청 하나가 구성요소 사이를 지나며 어디서 시간을 썼나 | API Gateway→Lambda→엔드포인트 호출 체인 〔S21〕〔S4〕 |

- CloudTrail과 EventBridge는 "API 호출 이벤트로 동작을 트리거"할 때 결합한다(로깅 중인 추적 필요) 〔S36〕.
- 근거: 〔S1〕〔S4〕〔S21〕〔S25〕〔S32〕〔S36〕〔S37〕〔S38〕

### 짝 2. 관리 이벤트 vs 데이터 이벤트 (그리고 이벤트 기록 vs 추적)
- 구분 기준: 컨트롤 플레인(리소스 관리) = 관리 이벤트, 기본 기록. 데이터 플레인(리소스 안·위의 작업, 고빈도) = 데이터 이벤트, 기본 미기록·추가 요금·**이벤트 기록(Event history, 90일)에 남지 않음** → 추적(trail)에서 별도 선택해야 한다 〔S32〕.
- SageMaker: `InvokeEndpoint`·`InvokeEndpointAsync`·`InvokeEndpointWithResponseStream`은 `AWS::SageMaker::Endpoint` 데이터 이벤트이며 요청 파라미터는 기록하지 않는다. `CreateTrainingJob`·`CreateEndpoint` 등은 관리 이벤트다 〔S32〕.
- 이벤트 기록은 최근 90일의 관리 이벤트만 보여 주는 읽기용 기록이고, 90일을 넘기거나 데이터 이벤트를 남기려면 추적을 만들어 S3(·CloudWatch Logs)로 보낸다 〔S32〕〔S33〕.
- 근거: 〔S32〕〔S33〕

### 짝 3. ModelLatency vs OverheadLatency (vs 네트워크 지연)
- 구분 기준: `ModelLatency` = 컨테이너와의 통신 + 컨테이너 안 추론. `OverheadLatency` = SageMaker AI 쪽 처리(수신~응답 반환에서 `ModelLatency`를 뺀 값) — 페이로드·요청 빈도·인증/인가에 따라 변함. 네트워크 지연 = 클라이언트↔엔드포인트 왕복(AWS 인프라 밖). 서버리스에서는 콜드 스타트가 `OverheadLatency`에 포함되고 `ModelSetupTime`이 새 컴퓨트 기동 시간을 따로 잰다 〔S1〕〔S11〕〔S15〕.
- 단위 함정: CloudWatch `ModelLatency`·`OverheadLatency`는 마이크로초, Inference Recommender 결과·`ClientLatency`는 밀리초 〔S1〕〔S84〕.
- 근거: 〔S1〕〔S11〕〔S15〕〔S84〕

### 짝 4. SageMaker AI Inference Recommender vs AWS Compute Optimizer (vs Trusted Advisor)
- 구분 기준: Inference Recommender는 **모델+샘플 페이로드로 모의 부하 테스트**를 돌려 후보 인스턴스를 비교한다(배포 전·비운영 엔드포인트, 잡 실행 중에만 과금). Compute Optimizer는 **이미 쌓인 CloudWatch 사용 지표(기본 최근 14일)** 로 평가하며, 문서가 SageMaker 엔드포인트에 대해 명시하는 것은 유휴(14일 호출 0건) 권장이다. Trusted Advisor는 계정 전반 점검이며 SageMaker 관련 비용 점검은 Savings Plans 구매 권장이다(Cost Optimization Hub 옵트인 필요) 〔S44〕〔S45〕〔S46〕〔S47〕〔S48〕〔S55〕.
- 함정: 운영 중(라이브 트래픽) 엔드포인트에 Inference Recommender를 돌리지 않는다(기존 엔드포인트 벤치마크는 오토스케일링 사용 엔드포인트 불가) 〔S78〕. 가이드 SK5의 Compute Optimizer 예시는 문서 범위와 차이가 있다 → 섹션 9 [G-4.2-2].
- 근거: 〔S44〕〔S45〕〔S46〕〔S47〕〔S48〕〔S55〕〔S78〕

### 짝 5. 가격 약정(Savings Plans) vs 용량 예약(훈련 플랜) vs 스팟 vs 온디맨드
- 구분 기준:

| 수단 | 얻는 것 | 얻지 못하는 것 |
|---|---|---|
| SageMaker AI Savings Plans | 시간당 사용량 약정(1·3년)으로 최대 64% 할인, 인스턴스 패밀리·크기·리전·구성요소 변경에도 자동 적용 〔S69〕〔S51〕 | 용량 보장(가격 할인일 뿐) 〔S86〕, 구매 후 약정 조건 변경 〔S69〕 |
| 훈련 플랜(flexible training plans) | 인스턴스 유형·수량·AZ·기간을 정해 컴퓨팅 용량을 예약(훈련 잡·HyperPod·추론 엔드포인트·Studio 앱) 〔S70〕 | 대상 리소스 간 교환 〔S70〕 |
| 관리형 스팟 훈련 | 훈련 잡을 온디맨드 대비 최대 90% 절감 〔S68〕 | 중단 없는 보장, 온디맨드 폴백(스팟 용량이 없으면 대기 후 중지) 〔S68〕 |
| 온디맨드 | 약정 없이 초 단위 과금 〔S20〕 | 용량 보장(best-effort, 부족하면 대기 후 `InsufficientCapacityError`) 〔S20〕 |

- Compute Savings Plans·EC2 Instance Savings Plans는 EC2(·Fargate·Lambda) 쪽이고 SageMaker 사용량에는 SageMaker AI Savings Plans를 쓴다 〔S69〕.
- 근거: 〔S20〕〔S51〕〔S68〕〔S69〕〔S70〕〔S86〕

### 짝 6. 비용 할당 태그 — AWS 생성 vs 사용자 정의, 그리고 "태그 달기" vs "활성화"
- 구분 기준: AWS 생성 태그는 AWS(또는 Marketplace ISV)가 정의·적용(`aws:` 접두), 사용자 정의 태그는 사용자가 정의·적용(`user:` 접두). **두 유형 모두 따로 활성화해야** Cost Explorer·비용 할당 보고서에 나타난다. 태그를 리소스에 붙이는 것(리소스 태깅)과 결제 쪽에서 활성화하는 것은 별개 단계다 〔S57〕〔S58〕.
- SageMaker 자동 태그(`sagemaker:domain-arn` 등)도 비용 분석에 쓰려면 활성화해야 하고, 활성화 후에도 Cost Explorer 필터에 뜨기까지 최대 24~48시간 걸린다 〔S59〕〔S61〕.
- 근거: 〔S57〕〔S58〕〔S59〕〔S61〕

### 짝 7. Cost Explorer vs Budgets vs Trusted Advisor vs CUR
- 구분 기준: Cost Explorer = 발생 비용 분석·시각화·예측(13개월 조회·18개월 예측, 현재 문서). Budgets = 임계값(실제·예측)을 정해 알림·작업(6가지 예산 유형, 하루 최대 3회 갱신). Trusted Advisor = 환경 점검 후 권고(전체 점검은 유료 플랜). CUR/Data Exports = 가장 상세한 원천 데이터를 S3로(Athena·Redshift·Quick 연동) 〔S52〕〔S56〕〔S54〕〔S65〕.
- 함정: Cost Explorer는 알림을 보내는 도구가 아니고, Budgets는 비용을 분석하는 도구가 아니다. 태그로 쪼개 보려면 태그 활성화가 선행돼야 한다 〔S57〕.
- 근거: 〔S52〕〔S54〕〔S56〕〔S57〕〔S65〕

### 짝 8. 정적 임계값 경보 vs 이상 탐지 경보 vs 복합 경보
- 구분 기준: 정적 = 고정 숫자와 비교(예: CPU 80% 초과). 이상 탐지 = 정적 임계값 없이 ML이 학습한 예상 값 밴드와 비교(계절성·추세 반영). 복합 = 다른 경보의 상태를 규칙으로 조합해 소음을 줄임(EC2/Auto Scaling 작업 불가) 〔S25〕〔S26〕.
- 근거: 〔S25〕〔S26〕〔S50〕

### 짝 9. SageMaker 서버리스 Provisioned Concurrency vs MaxConcurrency vs Lambda의 프로비저닝된 동시성·예약된 동시성
- 구분 기준: SageMaker 서버리스의 `MaxConcurrency`는 엔드포인트가 동시에 처리할 호출의 상한(초과분은 스로틀, 엔드포인트당 최대 200)이고, `ProvisionedConcurrency`는 그 안에서 미리 데워 두는 몫(≤ `MaxConcurrency`)이다 〔S14〕. Lambda의 프로비저닝된 동시성은 사전 초기화된 실행 환경 수이고 예약된 동시성은 환경을 미리 초기화하지 않는다 〔S16〕.
- 근거: 〔S14〕〔S16〕

### 짝 10. CloudWatch 대시보드 vs Amazon Quick Sight
- 구분 기준: CloudWatch 대시보드는 운영 지표·경보를 여러 리전에 걸쳐 한 화면에 보여 주는 상태판이고, Amazon Quick(구 QuickSight)의 BI 기능 Quick Sight는 데이터 소스(예: Athena로 쿼리하는 CUR)에 연결해 대시보드를 만들고 임베드하는 분석 도구다 〔S27〕〔S28〕〔S66〕. 명칭은 'Amazon QuickSight→Amazon Quick'으로 바뀌었다 〔S28〕.
- 근거: 〔S27〕〔S28〕〔S66〕

## 9. 확인 필요 항목

- [G-4.2-1] K1의 5개 지표(활용률·처리량·가용성·확장성·내결함성)를 한 문장으로 정의한 공식 문서가 있는가 — ML Lens(MLOPS05-BP01·설계 원칙·성능 효율성/신뢰성 필러 정의)와 SageMaker CloudWatch 지표 문서를 확인했으나 5개를 함께 정의한 문장은 없었다. ML Lens가 직접 언급하는 것은 지연·처리량·자원 활용률(MLOPS05-BP01)과 내결함성·복구 가능성(설계 원칙)뿐이다 — 제안: 학습문서는 2.1의 표를 '학습용 정리'로 밝히고, 문항은 개념 정의 암기가 아니라 '어떤 지표·설정이 어떤 개념을 보여 주는가'를 묻는 형태로 만든다.
- [G-4.2-2] AWS Compute Optimizer가 SageMaker 엔드포인트에 적정 규모(rightsizing) 권장을 제공하는가 — Compute Optimizer 사용자 가이드(what-is, supported-resources, view-idle-recommendations, requirements)가 SageMaker에 대해 명시하는 것은 '엔드포인트 유휴 권장'(14일 호출 0건)뿐이고 rightsizing 권장 서술은 찾지 못했다. 반면 FAQ의 권장 대상 나열에는 'SageMaker Endpoint'가 들어 있고 권장 유형은 구분되지 않는다. 가이드 SK5는 'Inference Recommender 및 Compute Optimizer 사용'을 예로 든다 — 제안: 'Compute Optimizer로 SageMaker 엔드포인트를 사이징한다'를 문항의 정답·오답 근거로 단정하지 말고, 사이징의 정답은 Inference Recommender, Compute Optimizer는 유휴·EC2 등으로 한정한다. 레포 `MLA-C01.json`은 가이드 원문이므로 수정 제안 없음.
- [G-4.2-3] SageMaker 엔드포인트가 X-Ray 세그먼트를 자체적으로 내보내는가 — X-Ray 개발자 가이드(what-is, integrating with services, concepts)의 통합 서비스 목록은 '예시'이며 SageMaker는 기재돼 있지 않고, ML Lens는 'ML 애플리케이션 구성요소 간 요청 추적'에 X-Ray를 권한다. 엔드포인트 내부 트레이싱 지원 여부는 확인하지 못했다 — 제안: 'X-Ray = 앞단 애플리케이션 체인(API Gateway·Lambda 등)의 구간별 지연 추적'으로 서술하고 '엔드포인트가 자동으로 세그먼트를 보낸다'는 단정은 피한다.
- [G-4.2-4] `InvokeEndpoint`의 CloudTrail 기록 서술이 자료마다 다른가 — SageMaker 개발자 가이드의 영문판과 ko_kr 기계 번역판 모두 현재는 '데이터 이벤트로 기록 가능, 기본 미기록'으로 서술한다. 과거 서술은 확인하지 못했다(현재 문서만 확인) — 제안: 문항은 '기본값은 미기록, 데이터 이벤트(`AWS::SageMaker::Endpoint`)로 옵트인'으로 써서 어느 서술과도 모순되지 않게 한다.
- [G-4.2-5] Trusted Advisor 전체 점검의 지원 플랜 요건 — 현재 문서는 Business Support+·Enterprise Support·Unified Operations 플랜이고 Developer Support·Business Support·Enterprise On-Ramp는 2027-01-01 종료 공지다. 시험 가이드(v1.0) 시점의 플랜 명칭과 다를 수 있으나 과거 서술은 확인하지 못했다 — 제안: 문항은 '유료 지원 플랜에서 전체 점검, Basic은 Service Limits 중심'으로 쓰고 플랜 명칭은 쓰지 않는다.
- [G-4.2-6] SageMaker 인스턴스에 예약 인스턴스(RI)가 적용되는가 — Savings Plans 문서(plan-types, sp-ris), How AWS Pricing Works, SageMaker 비용 최적화 문서를 확인했으나 RI는 EC2·RDS 등으로만 서술되고, SageMaker에 RI를 적용한다는 문장도 적용되지 않는다는 문장도 찾지 못했다. 가이드 SK10은 RI를 예로 든다 — 제안: 학습문서는 'SageMaker AI의 약정 할인 수단 = SageMaker AI Savings Plans(용량 예약은 훈련 플랜)'로 쓰고 'SageMaker는 RI 불가'는 단정하지 않는다. RI를 오답 선택지로 쓸 때의 근거는 '문서가 SageMaker 비용 절감 수단으로 지목하는 것은 SageMaker Savings Plans'로 한정한다.
- [G-4.2-7] 서버리스 콜드 스타트를 재는 지표가 `OverheadLatency`인가 `ModelSetupTime`인가 — 서버리스 문서는 콜드 스타트 시간이 `OverheadLatency`에 포함된다고 서술하고, 지표 참조 문서는 `ModelSetupTime`을 '서버리스 엔드포인트의 새 컴퓨트 기동 시간'으로 별도 정의한다(서로 다른 지표를 가리키는 것처럼 읽히는 중복 서술) — 제안: 두 지표를 함께 서술('콜드 스타트 시간은 OverheadLatency에 포함, ModelSetupTime은 컴퓨트 기동 시간')하고 단일 지표만 정답으로 두지 않는다.
- [G-4.2-8] 오토 스케일링 반응 시간 수치 — 스케일 아웃 경보 3분(1분 데이터 포인트 3개)·스케일 인 15분은 AWS Machine Learning 블로그에만 있고 공식 SageMaker 개발자 가이드에서 같은 수치를 찾지 못했다. 기본 쿨다운 값도 공식 문서로 확인하지 못했다 — 제안: 수치는 단정하지 말고 '경보 평가 기간+지표 게시·반응 지연+쿨다운이 스케일 반응 시간을 이룬다' 수준으로 서술한다.
- [G-4.2-9] 시점 의존 수치 — Cost Explorer 13개월 조회·18개월 예측, Budgets 하루 최대 3회 갱신 등은 2026-10-17 문서 기준이다. CUR 문서는 한 페이지 안에서 '하루 한 번 갱신'·'하루 최소 한 번'·'하루 최대 세 번'이 섞여 있다 — 제안: 갱신 횟수·예측 개월 수 같은 수치를 문항의 정답 근거로 쓰지 않는다.
- [G-4.2-10] 비용 할당 태그의 소급 적용(backfill) — `cost-alloc-tags` 문서 하위 주제에 'Backfill cost allocation tags'가 있으나 본문은 읽지 않았다 — 제안: '활성화한 시점부터만 추적된다'고 단정하지 말고, 필요하면 해당 페이지를 추가 확인한다.
- [G-4.2-11] SageMaker AI Savings Plans의 서버리스·비동기 추론 적용 여부 — 문서의 적용 목록(Studio Classic 노트북·On-Demand 노트북·Processing·Data Wrangler·Training·Real-Time Inference·Batch Transform)에 서버리스·비동기 추론은 없으나 'including'으로 서술돼 비배타 여부를 단정할 수 없다 — 제안: 서버리스·비동기 추론에 대한 적용 여부를 묻는 문항은 만들지 않는다.
- [G-4.2-12] Quick Sight가 CloudWatch 지표를 직접 데이터 소스로 읽는지 — 확인한 예는 CUR→Athena→Quick 데이터셋, Model Monitor 대체 구성의 Athena Iceberg→QuickSight 대시보드 등 S3/Athena 경유뿐이다 — 제안: 'Quick Sight = Athena/S3 등 데이터셋 기반 BI'로 서술하고 'CloudWatch 지표를 Quick Sight에 직접 연결'은 단정하지 않는다.
- [G-4.2-13] 'Amazon Quick'이 현재 정식 명칭인가 — Quick 사용자 가이드(what-is)와 Q Business 이전 문서가 'Amazon Quick', QuickSight의 BI 기능을 'Amazon Quick Sight'로 부르고, AWS BI 블로그 제목은 'Quick Suite'를 쓴다(시기별 표기 공존, 컨트롤러 N6와 일치) — 제안: 학습문서는 'Amazon Quick(구 Amazon QuickSight, 중간 표기 Quick Suite)'로 병기하고 한국어판 'Amazon Quick Sight'는 Quick 안의 BI 기능명으로 설명한다. 가이드 원문 JSON은 수정 제안 없음.
- [G-4.2-14] 훈련 플랜(flexible training plans)의 세부 — 훈련 플랜이 존재하고 훈련 잡·HyperPod·추론 엔드포인트·Studio 앱에 쓰인다는 것만 확인했다. 지원 인스턴스·리전·요금은 문서의 별도 표에 있으며 조사하지 않았다. 가이드는 훈련 플랜을 직접 언급하지 않는다 — 제안: 학습문서는 '용량을 예약하는 수단이 있다' 수준으로만 다룬다.
- [G-4.2-15] 채팅 앱으로 예산·경보 알림 받기(AWS Chatbot → Amazon Q Developer in chat applications) — Budgets 문서의 하위 주제에 'Receiving budget alerts in chat applications'가 있다는 것만 확인했고, AWS Chatbot의 현재 명칭·상태는 확인하지 못했다(컨트롤러의 미확인 수명 항목) — 제안: 다루려면 별도 확인 후 사용한다.
