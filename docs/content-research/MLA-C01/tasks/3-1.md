### 2.3 비동기 추론 상세 (K5·K3)

흐름: ① `CreateEndpointConfig`에 `AsyncInferenceConfig`(`OutputConfig` 필수, `ClientConfig` 선택)를 넣어 엔드포인트 구성 〔S8〕〔S97〕 ② 요청 페이로드를 S3에 두고 `InvokeEndpointAsync`에 `InputLocation`으로 지정(인라인 `Body`는 128,000 bytes 이하이며 `InputLocation`과 상호 배타) 〔S8〕〔S11〕 ③ SageMaker가 큐잉하고, 처리 완료 여부와 무관하게 `InferenceId`와 출력 위치를 HTTP 202로 반환 〔S11〕 ④ 결과는 S3 `S3OutputPath`(실패 응답은 `S3FailurePath`)에 저장되고 SNS 성공/오류 토픽으로 알림 가능 〔S8〕〔S12〕〔S98〕. `AsyncInferenceConfig`가 있으면 그 엔드포인트는 비동기 호출만 받는다 〔S8〕.

| 항목 | 값·동작 |
|---|---|
| 페이로드·처리 시간 | 최대 1 GB, 요청 최대 60분 〔S10〕 |
| 요청 처리 한도 `InvocationTimeoutSeconds` | 기본 900초, 1–3600초 〔S11〕 |
| 큐 대기 한도 `RequestTTLSeconds` | 기본 21,600초(6시간), 60–21,600초 〔S11〕 |
| 인스턴스당 동시 호출 `MaxConcurrentInvocationsPerInstance` | 1–1000, 미지정 시 SageMaker가 선택 〔S13〕 |
| SNS 알림 | `SuccessTopic`·`ErrorTopic`, 추론 응답을 알림에 싣는 것은 128 KB 이하일 때만 〔S12〕 |
| 오토스케일링 | `ApproximateBacklogSizePerInstance` 기반 목표 추적 권장, `MinCapacity=0`으로 0까지 〔S9〕 |
| 0에서 되살리기 | 정책이 없으면 큐 길이가 목표를 넘어야 스케일 업 → 추가 정책 `HasBacklogWithoutCapacity`(스텝 스케일링 + CloudWatch 경보) 〔S9〕 |
| 정책 수 | 여러 스케일링 정책은 충돌 가능, 비권장 〔S10〕 |
| 컨테이너 | 실시간·배치와 같은 컨테이너 재사용 가능, 타임아웃·페이로드 한도 확인 〔S10〕. invoke가 오래 걸리는 동안 `/ping`이 타임아웃 나면 Unhealthy로 판정될 수 있음 〔S10〕 |
| 가드레일·섀도 | 배포 가드레일(블루/그린·롤링)은 비동기에도 적용 〔S30〕, 섀도 테스트는 불가 〔S36〕 |

> 🧠 원리: `InvokeEndpointAsync` 응답에는 추론 결과가 없고 결과 위치만 있다 〔S11〕 → 클라이언트는 처리 완료까지 연결을 붙잡지 않는다. 그래서 동기 호출 한도(60초)를 넘는 긴 처리와 큰 페이로드를 다룰 수 있고, 요청이 없으면 인스턴스를 0까지 줄여 비용을 아낄 수 있다 〔S1〕〔S9〕.

### 2.4 배치 변환 상세 (K3·K5)

용도: 대규모 데이터셋 추론, 영속 엔드포인트가 필요 없는 추론, 입력 레코드와 추론을 연계해 해석, 데이터 전처리 〔S14〕. 잡이 시작되면 SageMaker가 인스턴스를 띄워 워크로드를 분산하고, S3 객체를 키 기준으로 인스턴스에 매핑한다. 입력 파일이 하나뿐이면 인스턴스를 여러 대 띄워도 한 대만 일한다 〔S14〕. 출력은 입력 파일명에 `.out`이 붙은 파일이며 입력 순서를 유지한다 〔S14〕.

| 파라미터 | 의미 | 값·기본값 |
|---|---|---|
| `SplitType` | `None`/`Line`/`RecordIO`/`TFRecord`. `Line`이면 줄 단위 미니배치, `None`이면 파일 전체를 한 요청으로 〔S14〕〔S15〕 | `BatchStrategy`는 `Line`·`RecordIO`·`TFRecord`일 때만 의미가 있음 〔S15〕 |
| `BatchStrategy` | `MultiRecord`: `MaxPayloadInMB` 한도까지 가능한 많은 레코드. `SingleRecord`: 요청당 1건 〔S15〕 | |
| `MaxPayloadInMB` | 미니배치 페이로드 상한 | 기본 6 MB, 최대 100 MB, `0`이면 HTTP chunked(알고리즘이 지원할 때만, 내장 알고리즘 미지원) 〔S15〕 |
| `MaxConcurrentTransforms` | 인스턴스당 동시 요청 수 | `0`/미설정이면 execution-parameters 사용, 미활성이면 1. `MaxConcurrentTransforms × MaxPayloadInMB ≤ 100 MB`. 권장값은 컴퓨트 워커 수 〔S14〕〔S15〕 |
| `AssembleWith` | `Line`이면 출력 레코드를 줄 구분자로 연결(출력 파일 수는 입력 파일 수와 같음) 〔S14〕 | |
| `TransformResources.InstanceCount` | 변환 인스턴스 수 | 기본 1, 최대 100. 분산 변환은 2 이상 〔S16〕 |
| `ModelClientConfig` | `InvocationsTimeoutInSeconds`(기본 600, 1–3600), `InvocationsMaxRetries`(기본 3, 0–3) 〔S17〕 | |
| `DataProcessing` | `InputFilter`·`OutputFilter`·`JoinSource`로 추론 입력 제외, 해석용 입력 포함 〔S15〕 | |

제약: CSV 입력의 줄바꿈 포함 필드 미지원 〔S14〕. 기본 지원 형식은 CSV·JSON, 최대 타임아웃 3600초, 레코드(미니배치) 페이로드 100 MB(FAQ) 〔S3〕. 내장 알고리즘은 콘솔이 최적값을 자동 설정하고, 사용자 지정 알고리즘은 execution-parameters 엔드포인트로 값을 제공한다 〔S14〕. 추론 파이프라인 모델도 배치 변환에 사용할 수 있다 〔S25〕. 변형 비교는 변형마다 별도 변환 잡을 만든다 〔S14〕. Savings Plans가 적용된다 〔S4〕.

> 🧠 원리: MME는 요청이 오면 해당 모델을 S3에서 인스턴스 스토리지로 받아 컨테이너 메모리에 로드하고, 메모리가 부족하면 쓰지 않는 모델을 메모리에서 내린다(스토리지 볼륨에는 남고 볼륨이 차면 삭제) 〔S20〕. 그래서 첫 호출에 콜드 스타트가 있고, 인스턴스 메모리는 모델 캐시 공간, vCPU 수는 동시 호출 한도로 사이징한다 〔S22〕. MCE는 컨테이너를 모두 띄워 두므로 콜드 스타트가 없지만 15개로 제한된다 〔S3〕〔S23〕.

**선택 기준**: 같은 프레임워크 + 모델 수 많음 + 간헐 호출 → MME. 다른 프레임워크 + 소수 + 항상 로드 → MCE direct. 순차 처리 체인 → 직렬 파이프라인. 대형 모델별로 GPU·메모리 몫과 스케일링을 따로 → 추론 컴포넌트 〔S26〕〔S27〕. Triton 컨테이너는 단일 모델·앙상블·MME 모드를 모두 지원한다 〔S59〕.

⚠️ 컨테이너 헬스체크 실패 시 인스턴스를 자동 교체하는 동작은 추론 컴포넌트를 쓰는 엔드포인트에는 적용되지 않는다고 문서가 명시한다 〔S57〕.

### 2.7 배포 모범 사례 1 — 모델 버전 관리·승인·롤백 (K1)

- **Model Registry**: Model Group이 같은 문제의 모델 버전들을 묶고, 학습할 때마다 새 버전으로 등록한다. 승인 상태(`PendingManualApproval` → `Approved`/`Rejected`)로 스테이징하고 메타데이터·리니지·CI/CD 자동화를 연결한다 〔S37〕〔S38〕.
- **승인이 배포를 트리거**: `Approved`로 바꾸면 CI/CD 배포가 시작될 수 있고, 파이프라인의 조건 단계가 성능 평가 후 상태를 자동 변경할 수 있다 〔S38〕.
- **롤백 패턴**: SageMaker 프로젝트 템플릿에서 `Approved` → `Rejected` 전환은 "가장 최근 Approved 버전"을 다시 배포하는 CI/CD를 시작한다 〔S38〕.
- **엔드포인트 갱신은 기본이 블루/그린**: 새 플릿(그린)을 띄우고 트래픽을 옮긴 뒤 구 플릿(블루)을 종료한다 〔S31〕. 자동 롤백·트래픽 시프팅은 §2.8.
- **IaC·CI/CD**: 대규모 운영은 CloudFormation/Boto3 + CI/CD 도구로 리소스를 프로비저닝·관리한다 〔S2〕.
- **다른 배포 대상의 버전·롤백**: Lambda는 버전 + 가중 별칭으로 카나리, 필요하면 빠르게 되돌린다 〔S79〕. ECS는 롤링 업데이트의 배포 서킷 브레이커가 실패 배포를 마지막 COMPLETED 배포로 자동 롤백한다 〔S81〕.
- **테스트 환경**: 프로덕션 엔드포인트에 올리기 전에 SageMaker 노트북 인스턴스에서 로컬 모드(`instance_type='local'`)로 배포해 검증한다 〔S93〕. 서버리스·비동기(0 스케일)는 개발·테스트의 유휴 비용을 줄인다 〔S4〕.

### 2.8 배포 모범 사례 2 — 배포 가드레일·섀도 테스트·A/B (K1)

가드레일은 프로덕션 모델 갱신을 위한 완전 관리형 배포 옵션 세트로, 오케스트레이션·모니터링·롤백 메커니즘을 직접 만들 필요가 없다 〔S30〕. **실시간·비동기 엔드포인트에만 적용**된다 〔S30〕.

| 방식 | 트래픽 이동 | 주요 파라미터·제약 | 장점 | 단점·주의 | 추천 상황 |
|---|---|---|---|---|---|
| 블루/그린 all-at-once (올앳원스) | 한 번에 100% 이동 후 베이킹 기간, 이상 없으면 블루 종료 〔S30〕 | | 업데이트 시간·비용 최소 〔S31〕 | 회귀 시 100% 트래픽 영향 〔S31〕 | 시간·비용 최소화 |
| 블루/그린 canary (캐너리) | 2단계: 소량 canary → 나머지 〔S31〕 | `CanarySize` ≤ 그린 플릿 용량의 50%, `WaitIntervalInSeconds`(canary 베이킹), `TerminationWaitInSeconds`, `MaximumExecutionTimeoutInSeconds` 〔S32〕 | 영향 범위를 canary로 한정 〔S31〕 | 배포 내내 두 플릿 병행 〔S31〕 | 영향 범위와 이중 운영 시간의 균형 |
| 블루/그린 linear (리니어) | n개 균등 단계 〔S30〕 | `LinearStepSize` 10–50%, 단계마다 베이킹 〔S33〕 | 회귀 위험 최소 〔S31〕 | 기간·비용이 단계 수에 비례 〔S31〕 | 위험 최소화 |
| 롤링 (롤링 배포) | 배치 크기만큼 새 인스턴스 → 트래픽 이동 → 구 인스턴스 정리 반복 〔S34〕 | `MaximumBatchSize` 5–50%(인스턴스 수 또는 %), `RollbackMaximumBatchSize`, `WaitIntervalInSeconds`, `MaximumExecutionTimeoutInSeconds` ≤ 28,800초 〔S34〕 | 블루/그린보다 필요 용량이 적음 〔S34〕 | 서버리스·다중 변형 엔드포인트 불가 〔S35〕 | 대형 모델·대형 엔드포인트, 수요 높은 가속 인스턴스 〔S34〕 |

공통: 모니터링용 **CloudWatch 경보를 먼저 만들고** `DeploymentConfig.AutoRollbackConfiguration.Alarms`에 이름으로 지정한다. 베이킹 기간에 경보가 하나라도 울리면 트래픽이 블루(구) 플릿으로 롤백된다 〔S31〕〔S34〕. `UpdateEndpoint`/`CreateEndpoint`로 배포를 만들며, `RetainDeploymentConfig=True`로 생성 시 설정을 재사용한다 〔S32〕. 신규 엔드포인트 구성은 기존과 변형 이름이 같아야 한다 〔S35〕. Marketplace 컨테이너나 Inf1 인스턴스를 쓰면 가드레일 대신 "all-at-once + 최종 베이킹 없음" 블루/그린으로 폴백한다 〔S35〕. 다단계·베이킹이 있는 블루/그린은 업데이트 동안 두 플릿 요금을 모두 낸다 〔S31〕. 롤링이 실패하고 자동 롤백도 실패하면 `UpdateRollbackFailed` 상태가 되며, 다시 `UpdateEndpoint`로 복구한다 〔S34〕.

**섀도 테스트(한 줄 + 위임)**: 같은 엔드포인트에 섀도 변형을 띄워 요청 사본을 보내 운영 지표를 비교하고 프로덕션 변형의 응답만 반환한다 〔S36〕. 서버리스·비동기·Marketplace·멀티 컨테이너·MME·Inf1 엔드포인트는 사용 불가 〔S36〕 → 상세는 Task 2.3/4.1 노트로 위임.

**A/B (프로덕션 변형)**: 변형별 가중치로 트래픽을 나누거나 `TargetVariant`로 특정 변형을 직접 호출한다 〔S39〕.

> 🧠 원리: 블루/그린은 새 플릿을 전부 띄운 뒤 트래픽을 옮기며 베이킹 기간 동안 경보를 감시하고 이상이 있으면 블루로 되돌린다 〔S31〕. 롤링은 단계마다 구 플릿을 정리하므로 한꺼번에 필요한 추가 인스턴스가 배치 크기 수준이다 〔S34〕.

### 2.9 컴퓨팅 자원 선택 — 패밀리·CPU vs GPU·가속기·네트워킹 (K4·SK2)

EC2 범주 〔S43〕: 범용(컴퓨트·메모리·네트워킹 균형) / 컴퓨팅 최적화(고성능 프로세서가 이점인 컴퓨트 집약, 예시에 ML 추론 포함) / 메모리 최적화(대용량 데이터를 메모리에서 처리) / 스토리지 최적화 / 가속 컴퓨팅(하드웨어 가속기·보조 프로세서) / HPC. 가속 컴퓨팅 패밀리에는 DL, G, Inf, P, Trn 등이 있다 〔S44〕.

**요구사항 → 인스턴스 선택 표**

| 요구사항 | 선택 | 근거 |
|---|---|---|
| 트리 기반 고전 ML 훈련(LightGBM 등) | CPU. LightGBM은 메모리 바운드라 범용(M5)이 컴퓨트 최적화(C5)보다 낫다. XGBoost는 CPU·GPU 훈련·추론을 지원하며 권장 인스턴스는 훈련·추론 요구와 버전에 따라 다름 | 〔S51〕〔S50〕 |
| 대규모 딥러닝 훈련 | GPU P-계열(P3은 HPC·딥러닝 훈련용 설계) 또는 Trainium(Neuron SDK로 훈련). 인스턴스 간 통신이 중요한 확장형 훈련은 EFA 지원 고대역 인스턴스 | 〔S52〕〔S45〕〔S53〕〔S44〕 |
| 딥러닝·생성형 AI 추론의 지연·비용 | GPU G-계열(g4dn은 ML 추론 적합) 또는 Inferentia(DL·생성형 AI 추론의 최저 비용을 표방, Neuron SDK로 배포하며 Neo 컴파일 대상에 포함) | 〔S52〕〔S45〕〔S64〕 |
| 소형 모델·낮은 QPS·분류·임베딩 | CPU(Graviton 포함). EKS 가이드의 표: CPU는 p95 100–500ms 허용·동시 100 req/s 미만, GPU/Trainium은 p95 50ms 미만 요구·100 req/s 초과 | 〔S82〕 |
| CPU 추론의 가격 대비 성능 | Graviton(ARM). 컨테이너 이미지가 ARM 호환이거나 멀티 아키텍처여야 함 | 〔S49〕 |
| 모델이 인스턴스 메모리보다 큼 | 메모리가 더 큰 인스턴스를 선택(모델 크기가 선택 요인) | 〔S47〕 |
| 소형 모델이 매우 많음 | 인스턴스 공유(MME/MCE/IC) | 〔S4〕 |
| GPU 용량 확보가 어려움 | GPU는 용량 예약이 필요한 경우가 많음 → 롤링 배포로 추가 용량 최소화 | 〔S82〕〔S34〕 |

**네트워킹 대역폭**: Elastic Fabric Adapter(EFA)는 AI·ML·HPC 가속을 위해 EC2 인스턴스에 붙이는 네트워크 장치다 〔S53〕. 크기마다 대역폭이 크게 다르다(예: inf2.48xlarge 100 Gbps, p5.48xlarge 3200 Gbps) 〔S44〕. 작은 크기는 기준 대역폭에 크레딧 기반 버스트가 붙는다(예: g5.xlarge 기준 2.5 Gbps, 최대 10 Gbps) 〔S44〕.

**SageMaker AI 호스팅 인스턴스**: `ml.` 접두 인스턴스 70종 이상, Inferentia·Graviton 포함 〔S4〕. 배치 변환 인스턴스 유효값에는 GPU(P3·G4dn·G5·G6), Inf2, Trn1이 들어 있다 〔S16〕.

**프로덕션 vs 테스트(K4)**: 테스트는 로컬 모드로 배포 전에 검증하고 〔S93〕 서버리스·비동기(0 스케일)로 유휴 비용을 억제하며 〔S4〕, 프로덕션은 Inference Recommender 결과 + 오토스케일링 + Savings Plans로 맞춘다 〔S4〕〔S41〕. Inference Recommender 작업은 프로덕션 엔드포인트가 아닌 비프로덕션 엔드포인트에서 돌린다 〔S42〕.

⚠️ **Elastic Inference(EI)**: 2023-04-15부터 신규 고객은 SageMaker·ECS·EC2에서 EI 액셀러레이터 인스턴스를 시작할 수 없고 〔S54〕, ECS 콘솔 문서는 "더 이상 제공되지 않는다"고 적는다 〔S55〕. 선택지로 고르지 않는다(최종 종료일은 §9 G-3.1-6).

⚠️ **Trainium 표기**: AWS 제품 페이지는 현재 훈련과 추론 모두를 표방한다 〔S46〕. 반면 AWS 블로그는 "주로 훈련용"이라 설명하고 〔S91〕, Neuron SDK 문장은 "Inferentia에 배포, Trainium에서 훈련"으로 역할을 나눈다 〔S45〕. DLAMI의 Trainium 페이지는 추론 워크로드용이라고 적어 상충한다 〔S48〕(§9 G-3.1-5). 문항에서 Inf와 Trn을 짝으로 쓸 때는 훈련·추론 단서를 문장에 명시해 모호함을 없앤다(제안).

**Compute Optimizer**: EC2·Auto Scaling 그룹·Lambda·EBS·ECS(Fargate) 등 컴퓨트 리소스의 구성·사용률을 분석해 크기 조정을 권고하는 범위 내 서비스다 〔S90〕〔S89〕. SageMaker 엔드포인트용 추천은 Inference Recommender가 맡는다(§2.10).

### 2.10 SageMaker Inference Recommender와 성능·비용·지연 절충 (SK1·SK2·K4)

Inference Recommender는 SageMaker AI ML 인스턴스 전반에서 부하 테스트와 모델 튜닝을 자동화해 실시간 또는 서버리스 엔드포인트에 가장 적합한 인스턴스 유형·구성을 고르게 돕는다. 고려 요소는 인스턴스 수, 컨테이너 파라미터, 모델 최적화, 최대 동시성, 메모리 크기다 〔S40〕. 작업 중 쓴 인스턴스에 대해서만 요금을 낸다 〔S40〕.

| 구분 | Default (Inference recommendations) | Advanced (Endpoint recommendations) |
|---|---|---|
| 입력 | 모델 패키지 ARN만 〔S41〕 | 원하는 인스턴스 또는 서버리스 + 커스텀 트래픽 패턴 + 지연·처리량 요구 〔S41〕 |
| 소요 | 45분 이내 〔S41〕 | 평균 2시간(작업 시간·구성 수에 따라) 〔S41〕 |
| 용도 | 예비 추천 | 맞춤 부하 테스트 기반 엔드포인트 추천 |

공통: 출력은 인스턴스 구성 목록 + 환경 변수 + 비용·처리량·지연 지표이며 오토스케일링 정책에 쓸 초기 인스턴스 수도 제공한다. 둘 중 하나만 써도 된다 〔S41〕. 모델 세부 페이지에서 비용·처리량·지연 기준 상위 5개 "prospective instances"를 즉시 볼 수 있다(예비 결과이므로 추가 작업 권장) 〔S41〕. 서버리스 엔드포인트도 부하 테스트 대상이다 〔S41〕. 이 문서의 하위 주제에는 Neo로 컴파일한 추천과 오토스케일링 정책 추천도 있다 〔S41〕.

기존 엔드포인트 벤치마킹의 제약: 작업당 엔드포인트 1개, 변형 1개, 오토스케일링 사용 불가, 실시간 전용, 실시간 멀티 모델 엔드포인트 미지원, 라이브 트래픽을 받는 프로덕션 엔드포인트에서 실행 금지 권고 〔S42〕.

### 2.12 엣지 최적화 — SageMaker Neo·IoT Greengrass·Edge Manager (K7)

- **Neo**: 모델을 한 번 학습하고 클라우드와 엣지 어디서나 실행하도록 컴파일(컴파일러 + 런타임)한다 〔S64〕. Gluon·Keras·MXNet·PyTorch·TensorFlow·TensorFlow-Lite·ONNX 모델을 Android·Linux·Windows 기기의 Ambarella·ARM·Intel·Nvidia·NXP·Qualcomm·Texas Instruments·Xilinx 프로세서용으로 최적화하며, FP32 또는 INT8·FP16 양자화 파라미터를 다룬다 〔S64〕. 대상은 클라우드 인스턴스(Inferentia 포함)와 엣지 디바이스 두 가지다 〔S64〕.
- **클라우드 대상**: `ml_c4`/`ml_c5`/`ml_m4`/`ml_m5`/`ml_p2`/`ml_p3`/`ml_g4dn`, Inf1(`ml_inf1`), Inf2·Trn1(문서가 지정한 리전) 〔S65〕.
- **엣지 대상**: Raspberry Pi 3, Texas Instruments Sitara, Jetson TX1 등. 컴파일된 모델을 S3에서 디바이스로 내려받아 DLR(Deep Learning Runtime)로 실행하거나 AWS IoT Greengrass로 배포한다 〔S66〕〔S67〕.
- **IoT Greengrass와의 관계**: Neo로 컴파일한 모델을 SageMaker 엔드포인트 또는 Greengrass 디바이스에 배포할 수 있다 〔S64〕. Greengrass는 엣지 배포·모니터링 도구이며(Edge Manager 대안으로도 안내됨 〔S69〕) **시험 가이드의 범위 외 서비스 목록에 있다** 〔S88〕 → Neo 중심으로 학습하고 Greengrass는 짝 개념으로만 다룬다.
- ⚠️ **SageMaker Edge Manager**: 2024-04-26에 중단(콘솔 접근·엣지 패키징 작업·디바이스 플릿 관리 불가, 서비스 내 참조 삭제) 〔S68〕〔S69〕. 대안은 크로스 플랫폼 엣지 런타임 ONNX, 엣지 배포·모니터링의 AWS IoT Greengrass V2, 또는 MQTT + IoT Jobs 기반 OTA다 〔S69〕.
- ⚠️ **AWS IoT Greengrass v1**: 2025-10-13 What's New에서 Sunset 대상으로 공지됐고 2026-10-07에 지원이 종료됐다. v2로 이전한다 〔S70〕〔S71〕.

> 🧠 원리: Neo의 컴파일러는 프레임워크별 연산을 프레임워크 중립 중간 표현으로 바꾸고 최적화한 뒤 대상용 바이너리를 생성하며, 대상 플랫폼마다 컴파일된 모델을 실행하는 런타임이 따로 있다 〔S64〕.

### 2.13 배포 오케스트레이터 선택 — SageMaker Pipelines vs Step Functions vs MWAA (SK3·K2)

SageMaker AI Workflows 개요는 SageMaker가 직접 제공하는 기술(Pipelines, Kubernetes 오케스트레이션, Notebook Jobs)과 SageMaker와 통합되는 외부 서비스(Airflow, Step Functions, AWS Batch)를 나눈다 〔S73〕.

| 서비스 | 공식 정의 | ML 워크플로 사례·통합 | 인프라·운영 | 선택 단서 |

### 패턴 1. 트래픽·지연·페이로드 단서로 추론 옵션 고르기
- 시나리오 단서: "간헐적/예측 불가 트래픽, 유휴 시간, 콜드 스타트 허용" / "수백 MB~GB 입력, 수십 분 처리, 결과는 나중에·알림" / "야간에 전체 데이터셋, 영속 엔드포인트 불필요" / "밀리초 응답, 상시 트래픽, 토큰 스트리밍" / "GPU 필요 또는 VPC 격리·데이터 캡처·Model Monitor 필요 + 간헐 트래픽".

## 4. 흔한 함정·혼동 짝

### 짝 1. 실시간 vs 서버리스 vs 비동기 vs 배치 변환
- 구분 기준:

| 구분 | 실시간 | 서버리스 | 비동기 | 배치 변환 |
|---|---|---|---|---|
| 호출 단위 | 요청(동기) | 요청(동기) | 요청(큐, S3 경유) | 데이터셋(잡) |
| 한도 | 25 MB·60초 | 4 MB·60초 | 1 GB·1시간 | 미니배치 100 MB, 호출 타임아웃 3600초 |
| 0 스케일 | 일반 엔드포인트 불가 | 가능 | 가능 | 엔드포인트 자체가 없음 |
| GPU | 가능 | 불가 | 가능 | 가능 |
| 요금 | 인스턴스 시간 | ms + 데이터량 | 인스턴스 시간 | 잡 기간 인스턴스 |

  특히 혼동: 서버리스 ↔ 비동기(둘 다 0 스케일), 비동기 ↔ 배치(둘 다 대용량·긴 처리, 결과 S3 저장).
- 근거: 〔S1〕〔S3〕〔S5〕〔S9〕〔S14〕〔S16〕

### 짝 2. 서버리스 추론 vs AWS Lambda
- 구분 기준: 서버리스 추론은 SageMaker 엔드포인트(Model Registry 연계, 메모리 1–6 GB, 4 MB·60초, 동시성 ≤200, GPU 불가)이고, Lambda는 범용 함수(메모리 ≤10,240 MB, 이미지 10 GB, 타임아웃 15분, 동기 6 MB)다. 서버리스 추론은 AWS Lambda와 통합되어 고가용성을 제공하지만 같은 서비스가 아니다.
- 근거: 〔S5〕〔S78〕

### 짝 3. MME vs 멀티 컨테이너 vs 직렬 추론 파이프라인 vs 추론 컴포넌트
- 구분 기준: 프레임워크가 같으면 MME(동적 로딩·콜드 스타트), 다르면 MCE(최대 15개·상주), 순서가 있으면 파이프라인(Serial), 모델별 자원·복사본 제어가 필요하면 IC. MCE의 `Mode`는 `Direct`(독립 호출)와 `Serial`(기본, 파이프라인)로 갈린다.
- 근거: 〔S20〕〔S23〕〔S25〕〔S27〕

### 짝 4. 블루/그린(all-at-once·canary·linear) vs 롤링 vs 섀도 테스트 vs A/B
- 구분 기준: 사용자 응답에 영향이 있는가(섀도: 없음 / canary·linear·롤링·A/B: 있음), 필요 용량(롤링 < 블루/그린), 자동 롤백 여부(가드레일: CloudWatch 경보 기반 자동 롤백 제공). 가드레일은 실시간·비동기에만 적용, 섀도 테스트는 서버리스·비동기·MME·멀티 컨테이너 불가.
- 근거: 〔S30〕〔S31〕〔S34〕〔S36〕〔S39〕

### 짝 5. Inferentia vs Trainium vs GPU vs Graviton vs (구) Elastic Inference
- 구분 기준: Inferentia(Inf1/Inf2)는 DL·생성형 AI 추론 최저 비용을 표방하며 Neuron 컴파일 필요, Trainium(Trn1/Trn2)은 훈련 중심으로 설명되어 왔으나 현재 제품 페이지는 훈련·추론 모두 표방(§9), GPU는 G(추론)·P(훈련) 계열, Graviton은 ARM CPU(가격 대비 성능, ARM 이미지), Elastic Inference는 신규 고객 불가.
- 근거: 〔S45〕〔S46〕〔S52〕〔S49〕〔S54〕

### 짝 6. SageMaker Neo vs Inference Recommender vs Compute Optimizer
- 구분 기준: Neo는 대상 하드웨어용 모델 컴파일·최적화, Inference Recommender는 부하 테스트로 SageMaker 엔드포인트의 인스턴스·구성을 추천(Neo 컴파일 결과 비교 포함), Compute Optimizer는 EC2·ASG·Lambda·EBS·ECS(Fargate) 사용률 기반 크기 조정 권고.
- 근거: 〔S64〕〔S40〕〔S90〕

### 짝 7. SageMaker Pipelines vs Step Functions vs MWAA
- 구분 기준: SageMaker 중심 ML 파이프라인과 모델 레지스트리 연계는 Pipelines, 여러 AWS 서비스를 엮는 워크플로는 Step Functions(SageMaker `.sync` 지원·콜백 토큰 미지원), 기존 Airflow 자산·오픈 소스 이식성은 MWAA, Kubernetes 중심은 Operators/Kubeflow.
- 근거: 〔S73〕〔S74〕〔S75〕〔S77〕

### 짝 8. Neo vs Edge Manager(중단) vs IoT Greengrass(v1 종료·v2 현행)
- 구분 기준: Neo는 컴파일, Edge Manager는 엣지 패키징·플릿 관리였고 2024-04-26 중단, Greengrass는 엣지 배포·모니터링(v2)이며 시험 범위 외. Edge Manager 대안으로 ONNX와 Greengrass V2가 안내된다.
- 근거: 〔S64〕〔S69〕〔S70〕〔S88〕

### 짝 9. SageMaker 엔드포인트 vs EKS/ECS vs Lambda
- 구분 기준: 관리형 ML 호스팅 기능(가드레일·MME·Recommender)이 필요하면 SageMaker, Kubernetes 표준화는 EKS(또는 SageMaker Operators), 컨테이너 + GPU 인스턴스 + 서킷 브레이커는 ECS, 경량·이벤트성은 Lambda(10 GB·15분·6 MB 확인).
- 근거: 〔S30〕〔S82〕〔S80〕〔S78〕

## 6. 자가 점검 문항 후보

### 후보 1 (난이도: associate)
- 대응 Skill: K5 / SK6 / SK1
- 문제: 영상 분석 모델이 요청마다 최대 약 800 MB의 입력을 받고 처리에 약 40분이 걸린다. 요청은 하루 중 가끔 몰리며 결과는 몇 분 뒤에 받아도 되지만, 요청이 없는 시간에는 인스턴스 비용이 들지 않아야 한다. 어떤 SageMaker AI 배포 옵션이 가장 적합한가?
- 보기:
  - A) 실시간 엔드포인트에 오토 스케일링을 적용한다
  - B) 서버리스 추론 엔드포인트(메모리 6144 MB)를 사용한다
  - C) 비동기 추론 엔드포인트를 만들고 오토 스케일링 최소 용량을 0으로 설정한다
  - D) 요청이 올 때마다 배치 변환 작업을 수동으로 시작한다
- 정답: C
- 근거: 〔S1〕 https://docs.aws.amazon.com/sagemaker/latest/dg/deploy-model-options.html , 〔S9〕 https://docs.aws.amazon.com/sagemaker/latest/dg/async-inference-autoscale.html
- 오답 근거: A) 실시간은 페이로드 25 MB·처리 60초 한도이고 일반 엔드포인트는 0 인스턴스로 줄일 수 없다 〔S1〕〔S28〕 / B) 서버리스는 요청·응답 4 MB, 60초 한도다 〔S6〕 / D) 배치 변환은 사전에 모인 데이터셋을 잡 단위로 처리하는 오프라인 방식이며 미니배치 페이로드 상한이 100 MB다 〔S14〕〔S15〕

## 9. 확인 필요 항목

- [G-3.1-1] 실시간 엔드포인트 페이로드 한도가 25 MB인가 6 MB인가? — 25 MB: 공식 비교 페이지(deploy-model-options.html)와 호스팅 FAQ(hosting-faqs.html)〔S1〕〔S3〕. 6 MB: InvokeEndpoint API 레퍼런스의 `Body` 길이 6,291,456 〔S18〕, aws.amazon.com FAQ 〔S92〕. 어느 쪽이 최신인지 문서에 날짜가 없다. — 제안: 학습문서는 "25 MB(개발자 가이드 기준, API 레퍼런스는 6 MiB로 표기)"로 병기하고 문항에서는 이 수치에 의존하지 않는다.
- [G-3.1-2] 비동기 추론의 처리 시간 한도는 1시간인가 15분인가? — 1시간: 비교 페이지·호스팅 FAQ·`InvocationTimeoutSeconds` 최대 3600초 〔S1〕〔S3〕〔S11〕. 15분: aws.amazon.com FAQ 〔S92〕(요청 기본값 900초와 일치). — 제안: "기본 15분, 최대 60분"으로 서술.
- [G-3.1-3] 비동기 요청 페이로드를 반드시 S3에 둬야 하는가? — 개발자 가이드는 S3 배치를 요구 〔S8〕, API 레퍼런스는 128,000 bytes 이하 인라인 `Body`를 허용(`InputLocation`과 상호 배타) 〔S11〕. — 제안: 두 표기를 병기하고 문항은 "대용량은 S3"로 한정.
- [G-3.1-4] 스케일 투 제로 서술이 문서마다 다르다 — 비동기 문서는 "Unlike other hosted models…"로 비동기만 0 스케일이라고 쓰지만 〔S9〕, 추론 컴포넌트를 호스팅하는 실시간 엔드포인트도 0 인스턴스까지 줄일 수 있다고 한다 〔S28〕. 서버리스도 0까지 줄어든다 〔S5〕. — 제안: 시험용 기본 답은 "서버리스·비동기", 추론 컴포넌트는 예외로 병기.
- [G-3.1-5] Trainium의 역할 표기가 상충한다 — 제품 페이지는 "AI training and inference" 〔S46〕, 블로그는 "mainly for … training" 〔S91〕, DLAMI Trainium 페이지는 inference 워크로드용으로 서술 〔S48〕, Neuron SDK 문장은 Trainium에서 훈련 〔S45〕. — 제안: 학습문서는 "Inf = 추론 특화, Trn = 훈련 중심(현재 제품 페이지는 추론도 표방)"으로 쓰고, 문항에서 Trn과 Inf를 오답 짝으로 쓸 때는 훈련 vs 추론 구분 단서를 명시.
- [G-3.1-6] Elastic Inference의 최종 종료일은? — SDK 문서는 2023-04-15 이후 신규 온보딩 중단 〔S54〕, ECS 콘솔 문서는 "no longer available" 〔S55〕만 확인했다. 참고로 `https://docs.aws.amazon.com/sagemaker/latest/dg/ei.html`은 `whatis.html`로, `https://docs.aws.amazon.com/elastic-inference/latest/developerguide/what-is-ei.html`은 `deploy-model.html`로 2026-10-17 현재 리다이렉트된다(MCP 열람 결과). — 제안: "신규 고객 불가(사실상 종료)"로 표기하고 날짜를 단정하지 않는다.
- [G-3.1-7] BYOC `/ping` 호출 방식 — 요구사항 목록은 `/invocations`와 `/ping`에 POST를 수용한다고 쓰고, 헬스체크 절은 주기적 GET 요청이라고 쓴다 〔S57〕. — 제안: "추론은 POST /invocations, 헬스체크는 GET /ping(200 응답)"으로 서술하되 원문 불일치를 메모.
- [G-3.1-8] Hugging Face TGI와 LMI 컨테이너의 공식 SageMaker 개발자 가이드 전용 페이지 — TGI는 AWS 블로그 〔S63〕만 확인, LMI는 SageMaker 가이드의 목차 페이지 〔S61〕와 DJL Serving 페이지 〔S60〕만 확인했고 상세 문서는 외부(docs.djl.ai)다. — 제안: 학습문서에서 TGI·LMI는 "대형 모델 추론용 사전 빌드 컨테이너 예시" 수준으로만 다룬다.
- [G-3.1-9] Lambda가 GPU를 지원하지 않는다는 공식 문서 문장을 찾지 못했다 — AWS ML 블로그가 GPU가 필요하면 ECS·Kubernetes·SageMaker 엔드포인트를 고려하라고 안내 〔S85〕할 뿐이다. Lambda Managed Instances 등 신규 기능의 가속기 지원 여부도 미확인. — 제안: 문항에서 "Lambda는 GPU 불가"를 정답 근거로 쓰지 말고 한도(10 GB·15분·6 MB)로 판단하게 한다.
- [G-3.1-10] 비동기 추론의 "제외 기능(Exclusions)" 목록 — 비동기 개발자 가이드가 링크한 Exclusions 페이지가 현재 `whatis.html`로 리다이렉트되어 열람할 수 없었다 〔S8〕. 비동기와 MME·추론 파이프라인 등의 호환 여부는 미확인. — 제안: 해당 호환성 문항은 만들지 않는다.
- [G-3.1-11] 요금 수치 — SageMaker 요금 페이지는 동적이라 단가를 수집하지 않았다(과금 구조만 〔S4〕〔S5〕). — 제안: 문항은 단가 대신 구조(인스턴스 시간 / ms + 데이터 / 잡 기간)로 출제.
- [G-3.1-12] Compute Optimizer가 SageMaker 엔드포인트 인스턴스를 분석하는지 — CLI 레퍼런스 설명은 EC2·ASG·Lambda·EBS·ECS(Fargate)만 나열 〔S90〕. SageMaker 지원 여부를 단정하는 문서는 찾지 못했다. — 제안: 오답 선택지로 쓸 때 "SageMaker 엔드포인트 추천은 Inference Recommender"만 근거로 삼는다.
- [G-3.1-13] 한국어 공식 표기가 기계 번역이라 페이지마다 다르다 — "일괄 변환"〔S94〕 / "배치 변환"(일부 페이지·가이드 Skill의 "배치 추론"), "섀도우 테스트"(ko_kr shadow-tests.html), "다중 모델/다중 컨테이너 엔드포인트"(multi-model-endpoints.html, multi-container-endpoints.html), "추론 구성 요소"(realtime-endpoints-deploy-models.html, 헤딩에는 "추론 구성 요쇼" 오타), "캐너리/카나리"(deployment-guardrails.html), "프로비저닝된 동시성"(serverless-endpoints.html), "SageMaker Edge Manager 수명 종료"(edge-eol.html). — 제안: 학습문서에서 영문 용어를 병기하고 한국어 표기는 가이드 Skill 문장("배치 추론", "서버리스 엔드포인트")을 우선한다.
- [G-3.1-14] IoT Greengrass는 가이드 범위 외인데 Neo 문서·Edge Manager 대안 안내가 Greengrass를 전제로 한다 〔S88〕〔S64〕〔S69〕. — 제안: 문항은 Neo(컴파일·DLR)까지만 묻고 Greengrass 운영 세부는 출제하지 않는다.
- [G-3.1-15] Trn1 네트워크 대역폭 수치 — DLAMI 페이지는 Trn1을 "100 Gbps"로 적고 〔S48〕 EC2 사양표는 trn1.32xlarge를 8 × 100 Gigabit으로 적어 〔S44〕 상충한다. 이 노트는 Trn1 대역폭 수치를 사실 행에 쓰지 않았다. — 제안: 대역폭 문항은 EC2 사양표(`ac.html`) 기준 수치만 사용.
- [G-3.1-16] MLA-C01.json 수정 제안 — 없음(K1–K7·SK1–SK6 원문은 공식 가이드와 일치).
