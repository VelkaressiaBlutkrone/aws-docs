### 2.2 드리프트의 정의와 탐지 기법 (K1)

공식 문서는 용어를 여러 층으로 나눠 쓴다. ML Lens는 **데이터 드리프트**와 **개념 드리프트** 2종을 쓰고, Model Monitor는 감시 대상 기준으로 **데이터 품질·모델 품질·편향·특성 기여도** 4종의 드리프트를 감시한다. AWS 블로그는 데이터 드리프트를 공변량 이동·레이블 이동·개념 이동 3종으로 더 쪼갠다.

| 용어 | 공식 정의(요지) | 무엇이 변하나 | 출처 |
|---|---|---|---|
| 데이터 드리프트 | 학습에 쓴 데이터와 비교한 데이터 분포의 유의미한 변화. 입력 분포의 변화이며 모델 성능 저하로 이어질 수 있음 | 입력(특성) 분포 | 〔S52〕〔S56〕〔S55〕 |
| 개념 드리프트 | 타깃 변수의 성질이 바뀜. 입력과 타깃 변수 사이 관계의 변화 | 입력과 타깃의 관계 | 〔S52〕〔S56〕 |
| 공변량 이동(covariate shift) [블로그] | 입력 분포가 시간에 따라 변하지만 입력이 주어졌을 때 출력의 조건부 분포는 그대로 | 입력 분포 | 〔S60〕 |
| 레이블 이동(label shift) [블로그] | 클래스 변수(타깃 레이블) 분포의 변화. 블로그 예: 학습 세트의 스팸 대 비스팸 비율이 50%였는데 실제로는 이메일의 10%만 비스팸 | 레이블 분포 | 〔S60〕 |
| 개념 이동(concept shift) [블로그] | 분포가 아니라 입력과 타깃 변수 사이 관계가 시간에 따라 변함 | 입력-출력 관계 | 〔S60〕 |
| 데이터 품질 드리프트(Model Monitor) | 프로덕션 데이터의 통계적 성질이 학습한 기준선 데이터에서 멀어지면 모델이 예측 정확도를 잃기 시작함 | 입력 통계·스키마 | 〔S19〕 |
| 모델 품질 드리프트(Model Monitor) | 모델의 예측을 실제 정답(ground truth) 라벨과 비교해 측정하는 모델 성능 지표의 변화 | 정확도 등 성능 지표 | 〔S20〕〔S1〕 |
| 편향 드리프트 | 학습 데이터와 배포 중 라이브 데이터가 달라질 때 편향이 도입·악화됨. 일시적(휴일 시즌)일 수도 영구적일 수도 있음 | 공정성 지표 | 〔S26〕 |
| 특성 기여도 드리프트 | 라이브 데이터 분포의 드리프트가 특성 속성(attribution) 값의 드리프트를 낳을 수 있음 | SHAP 기여도 순위 | 〔S29〕 |
| 예측(레이블) 드리프트 | Model Monitor 문서·ML Lens에는 별도 정의가 없다. 가장 가까운 공식 계열 문장은 블로그의 레이블 이동 | - | 〔S60〕, 섹션 9 |

> 🧠 원리: Model Monitor는 학습 데이터로 만든 기준선의 통계·제약과 프로덕션 데이터를 비교하는 방식이라 입력 분포 변화(데이터 드리프트)를 직접 잡는다〔S1〕〔S19〕. 반대로 개념 드리프트는 입력 분포가 그대로여도 일어날 수 있고, 입력에 대한 통계 검정만으로는 잡기 어려워 하류 비즈니스 지표·사용자 피드백을 함께 본다는 것이 공식 가이던스다〔S59〕. 그래서 예측을 정답 라벨과 직접 비교하는 모델 품질 모니터링이 성능 저하를 측정하는 수단이 된다〔S20〕.

**탐지 기법 정리**

| 대상 | 기법 | 공식 근거 | 상세 |
|---|---|---|---|
| 입력 분포 | 기준선 통계·제약 대비 위반 검사 + 분포 거리. 두 분포의 누적분포함수(CDF) 최대 절대 차이(L∞, `linf_simple`)가 `comparison_threshold`(기본 0.1)를 넘으면 위반. 표본이 부족하면 `linf_robust`(Two-sample Kolmogorov-Smirnov 기반). 범주형 특성은 `categorical_comparison_threshold`와 `categorical_drift_method`(기본 `LInfinity`=K-S, 대안 `ChiSquared`)로 따로 설정 | 〔S12〕〔S13〕 | 2.6 |
| 입력 분포 | KL 발산, Jensen-Shannon 발산, PSI를 Model Monitor가 지원한다고 ML Lens가 기술. Model Monitor 제약 스키마에는 이 척도가 없음(상충 가능). 대체 경로의 Evidently는 PSI·KS를 계산 | 〔S55〕〔S2〕 | 섹션 9 |
| 모델 성능 | 정답 라벨과 예측을 병합해 지표(회귀 `mae`·`mse`·`rmse`·`r2`, 분류 `accuracy`·`precision`·`recall`·`f1`·`auc` 등) 비교 | 〔S20〕〔S24〕 | 2.8 |
| 모델 성능·개념 드리프트 | 사람 검토 라벨과 모델 추론을 비교(휴먼 인 더 루프) ⚠️ A2I는 신규 고객 불가 | 〔S54〕 | 2.14 |
| 개념 드리프트 | 하류 비즈니스 지표·사용자 피드백 모니터링 | 〔S59〕 | - |
| 공정성 | 편향 지표(예: DPPL)의 허용 범위 + Normal Bootstrap 신뢰구간 | 〔S26〕 | 2.9 |
| 설명가능성 | 전역 SHAP 값의 특성 순위를 NDCG로 비교, 0.90 미만이면 경보 | 〔S29〕〔S30〕 | 2.9 |

참고: AWS 가이던스는 KS 같은 흔한 드리프트 척도가 LLM 임베딩처럼 다차원 데이터에서는 덜 효과적이라고 지적한다(생성형 AI 맥락)〔S59〕.

### 2.3 Model Monitor 개요와 동작 흐름 (SK1, K2)

Model Monitor는 프로덕션 ML 모델의 품질을 모니터링하고, 규칙으로 드리프트를 감지해 편차가 생기면 알려 준다. 편차를 조기에 알면 모델 재훈련, 업스트림 시스템 감사, 품질 문제 수정 같은 조치를 사람이 일일이 지켜보지 않고도 취할 수 있다〔S1〕.

**설정 방식 3가지**〔S1〕: ① 실시간 엔드포인트의 지속 모니터링, ② 정기적으로 실행되는 배치 변환 작업의 지속 모니터링, ③ 비동기 배치 변환 작업의 일정 모니터링.

**흐름**(문서는 실시간 캡처·배치 캡처를 따로 나열하며, 여기서는 하나로 묶었다)〔S1〕:
1. 데이터 캡처 활성화 — 실시간 엔드포인트는 요청과 예측을, 배치 변환은 입력과 출력을 캡처한다.
2. 학습에 쓴 데이터셋으로 **기준선**을 만든다. 기준선이 지표를 계산하고 지표의 제약을 제안한다. 실시간·배치 예측이 제약을 벗어나면 위반으로 보고된다.
3. **모니터링 스케줄**을 만든다(수집할 데이터, 수집 빈도, 분석 방법, 생성할 보고서).
4. 최신 데이터를 기준선과 비교한 보고서를 점검한다. 위반, 지표, CloudWatch 알림을 본다.

**실행의 정체.** 스케줄이 처리 작업(processing job)을 시작해 해당 기간의 수집 데이터를 기준선 통계·제약과 비교하고 위반 보고서를 만든다. 특성별 CloudWatch 지표도 발행한다〔S16〕. 스케줄을 만들 때 처리 작업의 인스턴스 수와 유형을 고객이 지정한다〔S18〕. 실행 결과 상태는 `Completed`, `CompletedWithViolations`, `Failed`이다〔S14〕.

**제약과 범위(시험 함정 후보)**

| 항목 | 실시간 엔드포인트 | 배치 변환 작업 |
|---|---|---|
| 설정 위치 | `CreateEndpointConfig`의 `DataCaptureConfig`(Python SDK는 `DataCaptureConfig` 클래스를 `deploy()`에 전달) | `CreateTransformJob`의 `DataCaptureConfig`(SDK는 `BatchDataCaptureConfig`를 `batch_data_capture_config`에 전달) |

| 출처 | 〔S7〕〔S9〕〔S43〕〔S23〕 | 〔S8〕 |

- 캡처에 Model Monitor가 꼭 필요한 것은 아니다. 요청·응답 페이로드 캡처는 학습·디버깅·모니터링에 쓰는 독립 기능이다〔S7〕〔S6〕.

### 2.6 기준선, statistics.json, constraints.json, 위반 (K2, SK1)

**기준선 작업.** SageMaker Python SDK의 `DefaultModelMonitor.suggest_baseline(..)`로 기준선 처리 작업을 시작한다. 사전 구축 컨테이너가 기준선 통계를 만들고 제약을 제안해 `output_s3_uri`에 쓴다〔S10〕.
- 학습에 쓴 데이터셋을 기준선 데이터셋으로 쓰는 것이 일반적이며, 학습 데이터 스키마와 추론 데이터 스키마(특성 수와 순서)가 정확히 일치해야 한다〔S10〕.
- 컬럼 이름은 Spark와 호환되게 소문자와 `_`만 쓴다〔S10〕〔S18〕.
- 예측/출력 컬럼은 학습 데이터셋의 첫 컬럼으로 가정한다〔S10〕.
- 생성된 제약은 검토·수정할 수 있다. 제약을 더 공격적으로 하거나 완화해 위반의 수와 성격을 조절한다〔S18〕.

**산출 파일**

| 파일 | 만들어지는 때 | 내용 | 출처 |
|---|---|---|---|
| `statistics.json` | 기준선 + 데이터 품질 모니터링 실행(현재 데이터셋도 계산). 데이터 품질 모니터링에서만 생성 | 데이터셋 수준 `item_count`, 특성별 `inferred_type`. 숫자형은 `num_present`·`num_missing`·`mean`·`sum`·`std_dev`·`min`·`max`·KLL 스케치 분포(기본 10개 버킷, 변경 불가), 문자열형은 `distinct_count`·범주 분포 | 〔S11〕〔S14〕 |
| `constraints.json` | 기준선 작업 | 특성별 `inferred_type`, `completeness`, `num_constraints.is_non_negative`, `string_constraints.domains`, 그리고 `monitoring_config` | 〔S12〕〔S10〕 |

| `constraint_check_type` | 플래그되는 조건 |

**CloudWatch 지표(데이터 품질).** `emit_metrics`가 `Enabled`면 데이터셋의 모든 특성·열에 대해 발행한다. 숫자형은 `feature_data_{feature_name}` 이름으로 `Max`·`Min`·`Sum`·`SampleCount`·`Average` 통계를, 숫자·문자열 공통으로 완전성 `feature_non_null_{feature_name}`(`Sum`)과 기준선 드리프트 `feature_baseline_drift_{feature_name}`(`Sum`)를 낸다〔S15〕. 실시간은 `/aws/sagemaker/Endpoints/data-metric` 네임스페이스(차원 `EndpointName`, `ScheduleName`), 배치 변환은 `/aws/sagemaker/ModelMonitoring/data-metric`(차원 `MonitoringSchedule`)이다〔S15〕.

> 🧠 원리: 기준선 단계의 컨테이너가 통계를 계산하고 제약을 "제안"하며, 같은 컨테이너가 모니터링 단계에서 기준선 대비 제약 검증과 지표 발행을 한다〔S10〕. `baseline_drift_check`는 분포 거리가 `comparison_threshold`를 넘을 때 위반이고, 그 거리는 두 누적분포함수의 최대 절대 차이로 정의돼 있다〔S12〕〔S13〕.

### 2.7 모니터링 스케줄(cron)과 실행 (SK1)

`CreateMonitoringSchedule` API로 스케줄을 만든다. 반복 실행하거나 즉시 한 번 실행할 수 있다〔S16〕. `ScheduleExpression`의 지원 표현식은 다음과 같다〔S17〕.

| 목적 | 표현식 | 비고 |
|---|---|---|
| 매시간 | `cron(0 * ? * * *)` | 문서가 나열한 반복 표현식 중 가장 짧은 주기(1시간) |
| 매일 특정 시각(UTC) | `cron(0 [00-23] ? * * *)` | 예: 정오 `cron(0 12 ? * * *)`, 자정 `cron(0 0 ? * * *)`. 일 단위는 파라미터를 생략하면 SageMaker AI가 하루 중 시각을 정함(권장) |
| N시간마다 | `cron(0 [00-23]/[01-24] ? * * *)` | 예: 17시부터 12시간마다 `cron(0 17/12 ? * * *)`, 자정부터 2시간마다 `cron(0 0/2 ? * * *)` |
| 1회 즉시 | `NOW` | `DataAnalysisStartTime`·`DataAnalysisEndTime` 필수 |

- **최소 간격**: 문서에 "minimum interval" 문구는 없고, 위 지원 표현식에서 반복 주기의 최소 단위가 1시간이다(섹션 9 G-4.1-4).
- **실행 지연**: 요청 시각과 실제 실행 사이에 0~20분의 지연이 있을 수 있다〔S17〕. 시간당 스케줄의 첫 실행은 UTC 정시 경계를 넘은 뒤 시작한다〔S14〕.
- **분석 창**: `DataAnalysisStartTime`·`DataAnalysisEndTime`은 ISO 8601 기간 형식의 오프셋(예: 종료를 시작 1시간 전으로 `-PT1H`)이며, 두 시각의 간격은 24시간을 넘을 수 없다〔S17〕.
- **입력 대상**: 스케줄 하나에는 엔드포인트 입력 또는 배치 변환 입력 중 하나만 지정한다(모델 품질 문서)〔S22〕. 배치는 `BatchTransformInput`에 캡처 위치(`data_captured_destination_s3_uri`)를 넘긴다〔S16〕.
- **모델 품질의 런타임**: 한 실행의 최대 런타임이 정답 병합 작업과 모니터링 작업으로 나뉘므로, 시간당 스케줄이면 `StoppingCondition`의 `MaxRuntimeInSeconds`를 1800 이하로 둔다. 한 실행은 다음 실행 시작 전에 끝나야 한다〔S22〕.
- **리소스·삭제**: 스케줄 삭제는 스케줄을 중지하고 실행 이력은 지우지 않는다〔S2〕. 엔드포인트를 지우려면 먼저 스케줄을 삭제해야 한다〔S18〕. 인스턴스 리소스는 스케줄이 삭제될 때까지 예약된다는 FAQ 문장이 있다(섹션 9 G-4.1-6)〔S18〕.
- **온디맨드**: SageMaker Processing 작업을 직접 실행하면 온디맨드 모니터링이 된다〔S18〕.

### 2.8 모델 품질: 정답(ground truth) 병합과 오프셋 (K2, SK1)

모델 품질 모니터링은 모델의 예측을 모델이 맞히려는 실제 정답 라벨과 비교한다. 데이터 품질과 같은 단계에 **정답 라벨을 S3에서 가져와 캡처한 예측과 병합하는 단계**가 더해진다〔S20〕.

**절차**〔S20〕〔S21〕〔S22〕〔S23〕
1. 데이터 캡처 활성화.
2. 기준선: 예측과 정답 라벨이 함께 있는 데이터셋(보통 학습 데이터셋)으로 `ModelQualityMonitor.suggest_baseline`을 실행. 인자에 `problem_type`(예: `BinaryClassification`), `inference_attribute`, `probability_attribute`, `ground_truth_attribute`를 준다. 결과 제약은 "임계값"이며 지표가 임계를 넘으면 위반으로 보고된다. 제약은 검토·수정을 권장한다.
3. 스케줄: `ModelQualityMonitor.create_monitoring_schedule`.
4. 정답 라벨 수집·업로드: 엔드포인트나 배치 변환 작업이 캡처한 데이터에 주기적으로 라벨을 붙여 S3에 올린다.
5. 병합·비교: 캡처 예측과 정답을 병합한 뒤 지표 계산.

**정답 레코드(JSON Lines)**〔S23〕

```
{"groundTruthData": {"data": "1", "encoding": "CSV"},
 "eventMetadata": {"eventId": "aaaa-bbbb-cccc"},
 "eventVersion": "0"}
```

| 항목 | 규칙 | 출처 |
|---|---|---|
| 매칭 키 | 레코드마다 고유 식별자가 필요. `inferenceId`(호출자가 `InvokeEndpoint`에 제공)가 캡처 데이터에 있으면 그것으로 병합하고, 없으면 자동 생성되는 `eventId`로 매칭. 정답 쪽 `inferenceId`가 캡처 쪽과 일치하게 만드는 책임은 사용자에게 있음 | 〔S23〕〔S18〕 |
| 형식·경로 | JSON Lines(`.jsonl`). 캡처 데이터와 같은 경로 형식 `s3://bucket/prefix/yyyy/mm/dd/hh`. 경로의 날짜는 라벨을 수집한 날짜이며 추론이 생성된 날짜와 같을 필요 없음 | 〔S23〕 |
| 작업 정의 | boto3는 `create_model_quality_job_definition`의 `GroundTruthS3Input.S3Uri`, SageMaker Python SDK는 `ModelQualityMonitor.create_monitoring_schedule`의 `ground_truth_input` | 〔S23〕 |

**오프셋(라벨 지연 대응).** 정답은 늦게 올 수 있으므로 스케줄에 오프셋을 지정한다〔S22〕. `StartTimeOffset`·`EndTimeOffset`은 작업의 시작·종료 시각에서 뺄 시간이며 ISO 8601 형식(`-PT#H`, `-P#D`)이다.
- 라벨이 1일 뒤부터 오고 1주 뒤에 완료되면 `StartTimeOffset=-P8D`, `EndTimeOffset=-P1D`. 이 스케줄이 2020-01-09T13:00에 돌면 2020-01-01T13:00부터 2020-01-08T13:00까지의 데이터를 분석한다〔S22〕.
- FAQ 예시: 정답이 예측 3일 뒤에 도착하면 `start_time_offset="-P3D"`, `end_time_offset="-P1D"`. 정답이 6시간 뒤에 도착하고 시간당 스케줄이면 `-PT6H`와 `-PT1H`〔S18〕. ⚠️ 이 두 FAQ 예시를 위 스케줄 페이지의 계산 규칙으로 풀면 분석 창에 아직 정답이 도착하지 않은 예측이 들어가 두 문서의 예시가 서로 맞지 않는다(섹션 9 G-4.1-16). 오프셋 문항의 근거는 스케줄 페이지의 계산 예시를 쓴다.

**지표(문제 유형별)**〔S24〕: 회귀 `mae`·`mse`·`rmse`·`r2`. 이진 분류 혼동 행렬, `recall`·`precision`·`accuracy`·`f0_5`·`f1`·`f2`·`auc`, TPR/TNR/FPR/FNR, ROC·정밀도-재현율 곡선, 그리고 각 지표의 `*_best_constant_classifier` 값. 다중 분류 혼동 행렬, `accuracy`, `weighted_recall`·`weighted_precision`·`weighted_f0_5`·`weighted_f1`·`weighted_f2`와 `*_best_constant_classifier`. 지표의 표준편차는 표본이 200개 이상일 때만 제공되며, 데이터의 80%를 무작위로 5회 뽑아 계산한다〔S24〕.

**CloudWatch.** 스케줄 생성 때 `enable_cloudwatch_metrics=True`이면 모델 품질 작업이 모든 지표를 CloudWatch로 보낸다. 네임스페이스는 실시간 `aws/sagemaker/Endpoints/model-metrics`, 배치 `aws/sagemaker/ModelMonitoring/model-metrics`. 지표가 지정 임계를 못 맞출 때 알람을 만들 수 있다〔S24〕.

> 🧠 원리: 정답이 늦게 도착하면 최신 구간에는 라벨이 없다. 문서는 모델 품질 같은 작업이 정답이 확보된 데이터만 쓰도록 `start_time_offset`·`end_time_offset`으로 작업이 쓰는 데이터의 시간 창을 고르라고 설명한다〔S18〕〔S22〕.

### 2.9 Clarify 연계: 데이터 분포 변화 감지 (SK3, K1)

⚠️ Clarify와 Model Monitor는 모두 신규 고객에게 닫혀 있다(2.1). 아래는 가이드(Version 1.0) 기준 내용이다.

**분포 변화를 어떤 도구가 보는가**

| 변화의 신호 | 공식 도구 | 판정 방식 | 출처 |
|---|---|---|---|
| 입력 특성의 통계·스키마가 학습 때와 다름 | Model Monitor 데이터 품질(Clarify 불필요) | 기준선 대비 분포 거리·데이터 타입·완전성 등 위반 검사 | 〔S19〕〔S13〕 |
| 라이브 데이터 변화로 공정성 지표가 나빠짐 | Clarify 편향 드리프트(Model Monitor에 통합) | 편향 지표 허용 범위 + 신뢰구간 | 〔S26〕 |
| 라이브 데이터 변화로 특성 중요도 순위가 바뀜 | Clarify 특성 기여도 드리프트(Model Monitor에 통합) | 전역 SHAP 순위의 NDCG | 〔S29〕 |
| 예측이 정답과 어긋남 | Model Monitor 모델 품질 | 정답 라벨 대비 성능 지표 | 〔S20〕 |

**편향 드리프트**〔S26〕
- 학습 때는 편향이 없어도 배포 후 라이브 데이터가 학습 데이터와 달라지면 편향이 도입되거나 악화될 수 있다. 예: 주택 가격 예측 모델의 출력이, 학습에 쓴 모기지 금리가 현재 실제 금리와 다르면 편향될 수 있다.
- 방식: 허용 범위 `A=(amin,amax)`를 정한다(예: DPPL 지표를 (-0.1, 0.1)로). 벗어나면 "bias detected" 경보. 검사 주기를 예컨대 2일로 두면 최근 2일 창의 데이터로 DPPL을 계산한다.
- 표본이 적으면 우연히 극단값이 나올 수 있으므로 Normal Bootstrap Interval로 신뢰구간 `C`를 구성한다. `C`가 `A`와 겹치면 "라이브 분포의 편향 지표가 허용 범위 안일 가능성이 있다"로 해석하고, 서로소(disjoint)면 허용 범위 밖이라 확신해 경보를 낸다.
- 위반 판정: 분석 결과 파일(`analysis.json`)의 편향 지표가 기준선 제약 값보다 나쁘면 위반. 0에 가까울수록 분포가 균형이라는 뜻이며, 기준선 DPPL 제약이 0.2일 때 분석 결과가 0.1이면 0에 더 가까우므로 위반이 아니고, -0.3이면 0에서 더 멀어 위반이다〔S27〕. 위반 파일 필드는 `facet`·`facet_value`·`metric_name`·`constraint_check_type`(현재 `bias_drift_check`만)·`description`〔S27〕.
- CloudWatch: 학습 전·후 편향 지표를 `aws/sagemaker/Endpoints/bias-metrics`(배치 `aws/sagemaker/ModelMonitoring/bias-metrics`)로 게시. 지표 이름은 `bias_metric` 뒤에 지표 약어를 붙임(예: 클래스 불균형 `bias_metric_CI`). 속성 `Endpoint`·`MonitoringSchedule`·`BiasStage`(`Pre-training`/`Post-Training`)·`Label`·`LabelValue`·`Facet`·`FacetValue`. 끄려면 작업 정의 `Environment`의 `publish_cloudwatch_metrics`를 `Disabled`로〔S28〕.

**특성 기여도 드리프트**〔S29〕
- 라이브 데이터 분포의 드리프트는 편향뿐 아니라 특성 속성(attribution) 값의 드리프트도 낳을 수 있다. 예(대학 입시 가상 시나리오): 훈련 데이터 속성 SAT 0.70 / GPA 0.50 / 학급 석차 0.05가 라이브에서 0.10 / 0.20 / 0.70이 되어 순위가 완전히 뒤바뀜.
- 비교 지표: 특성 순위가 어떻게 바뀌었는지 비교하되, 순위 변화에 민감할 뿐 아니라 원시 속성 점수에도 민감해야 한다(같은 폭으로 순위가 떨어져도 훈련 때 속성 점수가 높던 특성에 더 민감). 이 성질 때문에 **NDCG(Normalized Discounted Cumulative Gain)** 점수를 쓴다. `NDCG = DCG / iDCG`이며 값은 [0, 1] 범위, 1이면 라이브의 특성 순위가 훈련 때와 같다. 위 예시의 NDCG는 0.69. **0.90 미만이면 경보**.
- 위반 판정: 레이블별 전역 SHAP 값의 nDCG 점수가 0.9 미만이면 위반을 기록한다. 합산한 전역 SHAP 값을 평가하므로 위반 항목에 "feature" 필드가 없다. 필드는 `label`·`metric_name`(현재 `shap`만)·`constraint_check_type`(현재 `feature_attribution_drift_check`만)·`description`〔S30〕.
- CloudWatch: `aws/sagemaker/Endpoints/explainability-metrics`(배치 `aws/sagemaker/ModelMonitoring/explainability-metrics`). 지표 2종 — 특성별 전역 SHAP 값(`feature_` 뒤에 특성 이름, 예: `feature_X`)과 지표의 `ExpectedValue`. 속성 `Endpoint`·`MonitoringSchedule`·`ExplainabilityMethod`(`KernelShap`)·`Label`·`ValueType`(`GlobalShapValues`/`ExpectedValue`)〔S31〕.
- "순위 상관 지표" 질문에 대한 답: 기여도 드리프트 공식 문서 3개 페이지(개요·위반·CloudWatch)에서 쓰는 지표는 NDCG뿐이며, Spearman·Kendall 같은 순위 상관계수 용어는 이 페이지들의 원문에 나오지 않는다(2026-10-17 원문 대조)〔S29〕〔S30〕〔S31〕.

> 🧠 원리: 편향 드리프트는 단일 계산값이 아니라 신뢰구간을 허용 범위와 비교한다. 문서는 작은 표본으로 계산한 값이 우연히 극단값을 보일 수 있기 때문이라고 설명한다〔S26〕. 기여도 드리프트가 순위만 비교하지 않고 NDCG를 쓰는 이유로 문서가 든 것은 두 가지 요구다. 순위 변화에 민감해야 하고, 같은 폭으로 순위가 떨어져도 훈련 때 속성 점수가 컸던 특성의 변화에 더 민감해야 한다〔S29〕.

⚠️ Clarify 중단 안내는 편향 지표를 pandas·scikit-learn으로, 기여도를 SHAP 라이브러리로 직접 계산하라고 안내한다〔S3〕.

### 2.10 CloudWatch 지표·경보·로그 (SK2)

CloudWatch는 원시 데이터를 수집해 근실시간 지표로 처리하고, 이 통계는 15개월 보관된다. CloudWatch 콘솔 검색은 최근 2주 안에 갱신된 지표만 보여 준다〔S32〕. 임계값을 감시하는 경보를 설정해 알림을 보내거나 조치를 취할 수 있다〔S32〕.

**네임스페이스와 대표 지표**〔S32〕

| 대상 | 네임스페이스 | 대표 지표·차원 |
|---|---|---|
| 엔드포인트 호출 | `AWS/SageMaker` | `Invocations`, `Invocation4XXErrors`, `Invocation5XXErrors`, `InvocationModelErrors`, `ModelLatency`, `OverheadLatency`, `InvocationsPerInstance`. 차원 `EndpointName`, `VariantName` |
| 엔드포인트 인스턴스 | `/aws/sagemaker/Endpoints` | `CPUUtilization`, `MemoryUtilization`, `DiskUtilization`, `GPUUtilization` 등 |
| 처리·훈련·변환 작업 | `/aws/sagemaker/ProcessingJobs`, `/aws/sagemaker/TrainingJobs`, `/aws/sagemaker/TransformJobs` | CPU·메모리·디스크·GPU 사용률(`DiskUtilization`은 배치 변환 미지원). 차원 `Host` |
| Pipelines 실행·스텝 | `AWS/Sagemaker/ModelBuildingPipeline` | 실행 `ExecutionStarted`·`ExecutionFailed`·`ExecutionSucceeded`·`ExecutionStopped`·`ExecutionDuration`, 스텝 `StepStarted`·`StepFailed`·`StepSucceeded`·`StepStopped`·`StepDuration`. 차원 `PipelineName`, `StepName` |
| Model Monitor | 2.4 표 | 데이터 품질·모델 품질·편향·기여도 지표 |

**엔드포인트 오류·지연 지표 해석**〔S32〕

| 지표 | 정의 | 유효 통계 |
|---|---|---|
| `Invocation4XXErrors` | 모델이 4xx HTTP 응답을 반환한 `InvokeEndpoint` 요청 수. 4xx면 1, 아니면 0을 보냄 | Average, Sum |
| `Invocation5XXErrors` | 모델이 5xx 응답을 반환한 요청 수 | Average, Sum |
| `InvocationModelErrors` | 2XX가 아닌 모든 모델 호출. 4XX/5XX 상태 코드, 저수준 소켓 오류, 잘못된 HTTP 응답, 요청 타임아웃 포함 | Average, Sum |
| `Invocations` | `InvokeEndpoint` 요청 수. 총 요청 수는 Sum | Sum |
| `ModelLatency` | 모델이 응답하는 데 걸린 시간(단위 마이크로초). 컨테이너와의 로컬 통신과 컨테이너 안의 추론 시간을 포함 | Average, Sum, Min, Max, Sample Count, Percentiles |
| `OverheadLatency` | SageMaker AI 오버헤드로 더해진 시간. 요청 수신부터 응답 반환까지에서 `ModelLatency`를 뺀 값 | Average, Sum, Min, Max, Sample Count |

전체 지연은 네트워크 지연, 오버헤드 지연, 모델 지연 세 요소로 이뤄진다〔S32〕. 호출 제약: 모델 컨테이너는 60초 안에 응답해야 하며 모델 처리 시간도 최대 60초다〔S43〕. `ModelError`는 모델(컨테이너)이 4xx 또는 5xx를 반환한 경우이며 HTTP 424다〔S43〕.

**지표 주기.** 기본 1분 주기이며 `MetricsConfig`의 `MetricPublishFrequencyInSeconds`로 10, 30, 60, 120, 180, 240, 300초를 설정한다. 호출 지표에서 이 설정을 쓰려면 `EnableEnhancedMetrics`가 `True`여야 한다. 1초 고해상도 지표는 3시간만 보존된다〔S32〕.

**정상 범위를 학습하는 경보.** CloudWatch 이상 탐지는 통계·머신러닝으로 지표를 분석해 정상 기준선을 정하고 이상을 드러낸다. 이 경보는 정적 임계값이 없고 기대 값 대역과 비교한다. 최대 2주의 지표 데이터로 학습하며 요금이 부과된다〔S35〕. SageMaker 공식 안내는 Model Monitor를 대체하는 경량 옵션으로 CloudWatch 커스텀 지표 + 이상 탐지 경보를 든다〔S2〕.

**로그.** 알고리즘·모델 컨테이너나 노트북 인스턴스 수명 주기 구성이 `stdout`/`stderr`로 보내는 내용은 CloudWatch Logs로 간다. 로그 그룹은 `/aws/sagemaker/Endpoints/[EndpointName]`(스트림 `[production-variant-name]/[instance-id]`), `/aws/sagemaker/TrainingJobs`, `/aws/sagemaker/ProcessingJobs`, `/aws/sagemaker/TransformJobs` 등. 기본값은 로그를 무기한 저장하며 그룹별 보존 기간을 바꿀 수 있다〔S33〕.

### 2.11 EventBridge·Pipelines·오케스트레이터 이벤트 (SK2)

Amazon EventBridge는 SageMaker AI의 상태 변경 이벤트를 감시해 훈련 작업 상태 변경, 엔드포인트 상태 변경 같은 이벤트에 자동으로 대응하게 한다. 이벤트는 근실시간으로 전달된다. 상태 변경마다 이벤트가 여러 번 올 수 있으며 이는 정상 동작이고 오류를 뜻하지 않는다〔S34〕. 자동화 대상 예: Lambda 호출, EC2 Run Command, Kinesis Data Streams, Step Functions 상태 머신, SNS 토픽〔S34〕.

| 이벤트 | `detail-type` | 핵심 필드·값 | 출처 |
|---|---|---|---|
| 훈련 작업 | `SageMaker Training Job State Change` | `TrainingJobStatus`가 `Failed`면 `FailureReason` 포함 | 〔S34〕 |
| 처리 작업 | `SageMaker Processing Job State Change` | `ProcessingJobStatus`, 실패 시 `FailureReason` | 〔S34〕 |
| 배치 변환 작업 | `SageMaker Transform Job State Change` | `TransformJobStatus`, 실패 시 `FailureReason` | 〔S34〕 |
| 엔드포인트 | `SageMaker Endpoint State Change` | `EndpointStatus`(예: `IN_SERVICE`) | 〔S34〕 |
| 엔드포인트 배포 | `SageMaker Endpoint Deployment State Change` | `VariantStatus`: `Creating`·`Deleting`·`Updating`·`ActivatingTraffic`·`Baking`. `Baking`은 자동 롤백 구성의 CloudWatch 경보를 지켜보는 대기 기간 | 〔S34〕 |
| 파이프라인 실행 | `SageMaker Model Building Pipeline Execution Status Change` | `currentPipelineExecutionStatus`·`previousPipelineExecutionStatus`: `Executing`·`Succeeded`·`Failed`·`Stopping`·`Stopped` | 〔S34〕 |
| 파이프라인 스텝 | `SageMaker Model Building Pipeline Execution Step Status Change` | `currentStepStatus`: `Starting`·`Executing`·`Succeeded`·`Failed`·`Stopping`·`Stopped`. `Failed`면 `failureReason`. 캐시 적중 시 `cacheHitResult` | 〔S34〕 |
| 그 밖 | 하이퍼파라미터 튜닝 작업, 피처 그룹, 모델 패키지, 모델 카드, 이미지 등 | - | 〔S34〕 |

**다른 워크플로 서비스의 상태 이벤트**

| 서비스 | 이벤트 | 값 | 출처 |
|---|---|---|---|
| AWS Step Functions | `Step Functions Execution Status Change`(source `aws.states`) | `status`: `RUNNING`·`SUCCEEDED`·`FAILED`·`TIMED_OUT`·`ABORTED`·`PENDING_REDRIVE` | 〔S36〕 |
| AWS Glue | `Glue Job State Change`(SUCCEEDED·FAILED·TIMEOUT·STOPPED에서 생성), `Glue Job Run Status`(작업 지연 알림 임계 초과 시 RUNNING·STARTING·STOPPING), `Glue Crawler State Change` | ETL 실패 시 SNS 토픽 알림, 성공 시 Lambda 호출 같은 활용이 문서 예시 | 〔S37〕 |

**파이프라인 모니터링의 세 축**: ① EventBridge 상태 변경 이벤트, ② CloudWatch 파이프라인 지표(2.10), ③ 파이프라인 안의 품질 게이트 `QualityCheck`·`ClarifyCheck` 스텝(2.3)〔S34〕〔S32〕〔S38〕.

**자동 롤백·재훈련 연결.** 배포 가드레일의 baking period 동안 지정한 CloudWatch 경보가 울리면 SageMaker AI가 이전 엔드포인트로 완전 롤백한다. 경보가 없으면 자동 롤백이 동작하지 않는다〔S47〕. 모니터링에서 드리프트가 확인되면 CloudWatch 경보로 재훈련 워크플로를 알리거나 자동 실행하고, Pipelines·Model Registry·블루/그린·카나리 배포를 이어 붙이는 구성을 ML Lens가 제시한다〔S57〕.

### 2.12 A/B 테스트: 프로덕션 변형 (SK4)

프로덕션 환경에서 모델·인스턴스·컨테이너를 비교해 가장 성능이 좋은 후보를 고르는 용도로 **프로덕션 변형(production variant)** 을 쓴다. 멀티 변형 엔드포인트는 변형별 트래픽 분배를 지정해 호출을 분산하거나, 요청마다 특정 변형을 직접 호출할 수 있다〔S40〕.

| 방식 | 설정 | 동작 | 출처 |
|---|---|---|---|
| 트래픽 분배 | 엔드포인트 구성에서 변형마다 가중치 `InitialVariantWeight`(Float, 최소 0, **미지정 시 기본 1.0**) | 변형의 트래픽 = 그 변형의 가중치 ÷ 모든 변형 가중치의 합. 모델 A 가중치 2, B 가중치 1이면 3분의 2와 3분의 1. 가중치 1·1이면 50%씩 | 〔S41〕〔S44〕〔S40〕 |
| 직접 호출 | `InvokeEndpoint`의 `TargetVariant` | 지정 변형이 처리. 트래픽 분배가 있어도 대상 지정 라우팅이 분배(가중치 기반 기본 동작)를 **재정의(override)** | 〔S40〕〔S43〕 |
| 운영 중 조정 | `UpdateEndpointWeightsAndCapacities` | 변형 가중치(여러 변형) 또는 변형 1개의 용량을 변경. **엔드포인트를 업데이트하지 않고** 트래픽 분포를 바꿈. 호출을 받으면 엔드포인트 상태가 `Updating`, 끝나면 `InService`. 변형별 인자는 `VariantName`과 `DesiredWeight`·`DesiredInstanceCount` | 〔S42〕〔S40〕 |

- **변형 수 한도**: 엔드포인트 구성의 `ProductionVariants`는 1~10개〔S44〕.
- **변형마다 다를 수 있는 것**: 모델, 인스턴스 유형·개수. 서로 다른 인스턴스 유형으로 모델을 시험할 수 있다〔S40〕.
- **어느 변형이 처리했는지**: 응답 헤더 `x-Amzn-Invoked-Production-Variant`(`InvokedProductionVariant`)〔S43〕. 캡처 데이터 경로에도 변형 이름이 들어간다〔S7〕.
- **변형별 모니터링**: SageMaker AI가 변형마다 `Latency`·`Invocations` 같은 지표를 CloudWatch에 낸다〔S40〕. 호출 지표의 `EndpointName, VariantName` 차원이 특정 엔드포인트의 변형으로 필터한다〔S32〕. 모델 성능(정확도·정밀도·재현율·F1·ROC/AUC)은 변형별로 계산해 비교한다〔S40〕.
- **절차(문서 예시 4단계)**: ① 모델 생성·배포(가중치 1·1) → ② 호출(분배 호출 + `TargetVariant` 호출) → ③ 변형별 성능 평가 → ④ 우수 변형 쪽으로 트래픽 증가(예: 가중치 25·75, 최종 0·1이면 모든 요청이 Variant2로)〔S40〕.
- **위치**: 새 모델과 기존 모델의 프로덕션 트래픽 A/B 테스트는 새 모델 검증의 효과적인 마지막 단계다〔S40〕. ML Lens도 모델 업데이트 시 프로덕션 변형으로 현재·신규 버전 A/B를 하라고 한다(MLPERF06-BP04)〔S56〕.

> 🧠 원리: 가중치는 절댓값이 아니라 합 대비 비율로 해석되므로 4:1이나 0.8:0.2가 같은 분배다〔S41〕. 그래서 트래픽 비율을 바꾸려면 엔드포인트 구성을 새로 만들지 않고 `UpdateEndpointWeightsAndCapacities`로 가중치만 바꾸면 된다〔S40〕.

### 2.13 A/B vs 섀도 vs 블루/그린 (SK4)

섀도 테스트의 비교 관점은 Task 2.3 몫이며, 여기서는 프로덕션 모니터링 관점의 차이만 적는다.

| 방식 | 호출자가 받는 응답 | 트래픽 | 목적 | 제약·비용 | 출처 |
|---|---|---|---|---|---|
| A/B(프로덕션 변형 가중치) | 가중치에 따라 각 변형의 응답이 실제 호출자에게 감 | 가중치 비율로 분배 | 실제 사용자 트래픽에서 모델 성능 비교 후 승자를 정함 | 변형 1~10개 | 〔S40〕〔S44〕 |
| `TargetVariant` 직접 호출 | 지정한 변형의 응답 | 요청 단위 지정 | 특정 변형 시험·검증 | 분배를 재정의 | 〔S43〕〔S40〕 |
| 섀도 테스트 | 프로덕션 변형의 응답만 호출자에게 반환. 섀도 변형 응답은 폐기하거나 비교용으로 기록 | 요청 복사본을 같은 엔드포인트의 섀도 변형으로 실시간 전달 | 사용자 영향 없이 지연·오류율 같은 운영 지표를 검증 | 서버리스, 비동기, Marketplace 컨테이너, 다중 컨테이너, 멀티모델 엔드포인트, Inf1 인스턴스 엔드포인트는 사용 불가. `CreateEndpointConfig`에서 `ShadowProductionVariants`를 쓰면 `ProductionVariants`와 각각 1개씩만. 추가 요금 없음(섀도 모델을 호스팅하는 인스턴스·스토리지 요금은 발생) | 〔S45〕〔S44〕〔S48〕 |
| 블루/그린·롤링 배포(배포 가드레일) | 전환 후 새 플릿이 응답 | all at once / canary / linear 트래픽 전환 | 안전한 모델 업데이트와 자동 롤백 | CloudWatch 경보가 자동 롤백의 전제 조건 | 〔S46〕〔S47〕 |

## 3. 시험에서 묻는 방식

> 아래 패턴은 공식 가이드 Skill 문장(SK1~SK4, K1~K3)이 "무엇을 고르게 하는지"에서 도출했고, 정답 방향의 근거는 공식 문서다. 기출·덤프를 참고하지 않았다.

### 패턴 1. 증상으로 모니터 유형(드리프트 종류)을 고른다 (SK1, SK3, K1)
- 시나리오 단서:
  - "프로덕션 입력 특성의 분포·스키마·결측이 학습 때와 달라졌다" → 데이터 품질 모니터링
  - "예측을 실제 결과(라벨)와 비교해 정확도·RMSE 하락을 본다", "정답이 며칠 뒤 확정된다" → 모델 품질 모니터링
  - "특정 집단에 대한 예측의 공정성 지표(예: DPPL)가 라이브 데이터에서 허용 범위를 벗어났다" → 편향 드리프트(Clarify 연계)
  - "모델이 중요하게 쓰는 특성의 순위가 학습 때와 뒤바뀌었다", "SHAP" → 특성 기여도 드리프트(NDCG)
  - "입력 분포는 그대로인데 입력과 정답의 관계가 바뀌어 정확도가 떨어진다" → 개념 드리프트이므로 정답 라벨을 쓰는 모델 품질 모니터링
- 정답 방향: 데이터 품질은 학습 데이터 기준선과 입력 통계를 비교하고 라벨이 필요 없다. 모델 품질은 정답 라벨과 예측을 병합해 성능 지표를 비교한다. 편향·기여도 드리프트는 Clarify가 Model Monitor와 함께 제공하는 모니터링이다. 데이터 드리프트=입력 분포 변화, 개념 드리프트=입력과 타깃 변수 관계 변화로 구분한다.
- 오답 유인(섞이는 선택지):
  - 같은 4종 안의 다른 유형(데이터 품질 vs 모델 품질, 편향 vs 기여도)
  - 데이터 품질 모니터링으로 편향·기여도 순위 변화까지 잡으려는 선택지(데이터 품질은 통계·스키마 제약 위반만 본다)
  - A/B 테스트·섀도 테스트(배포 비교 기법이며 드리프트 감시 도구가 아님)
  - CloudWatch 경보만 두는 선택지(운영 지표이며 통계적 드리프트 감시가 아님)
- 근거: 〔S1〕〔S19〕〔S20〕〔S26〕〔S29〕〔S52〕〔S56〕

### 패턴 2. Model Monitor의 구성 요소·제약·순서를 묻는다 (SK1, K2)
- 시나리오 단서:
  - "엔드포인트에 데이터 캡처만 켰는데 위반 보고서가 없다" → 캡처는 입력·출력 수집이며, 기준선과 모니터링 스케줄이 있어야 비교·보고가 이뤄진다
  - "정답 라벨이 하루 뒤부터 도착해 일주일 뒤 완료된다", "라벨 없는 최신 데이터가 평가에 섞인다" → `StartTimeOffset`·`EndTimeOffset`(스케줄 페이지 예시: -P8D, -P1D), 라벨은 JSON Lines를 `yyyy/mm/dd/hh` 경로에, `inferenceId`/`eventId`로 매칭
  - "멀티모델 엔드포인트를 모니터링", "이미지·텍스트 입력 모델" → 멀티모델 미지원, 사전 구축 컨테이너는 표 형식만이므로 자체 컨테이너(BYOC)
  - "배치 변환 작업 모니터링" → 배치 데이터 캡처(`DataCaptureConfig`, `GenerateInferenceId`)와 `BatchTransformInput`. 한 스케줄에는 엔드포인트 입력과 배치 입력 중 하나만
  - "캡처가 중간에 멈춘다" → 디스크 사용률 75% 미만 유지
  - "엔드포인트를 지울 수 없다" → 모니터링 스케줄을 먼저 삭제
  - "스케줄 최소 주기" → 문서의 지원 표현식 중 최단은 매시간
- 정답 방향: 위 대응. 흐름은 캡처 → 기준선(학습 데이터) → 스케줄 → 보고서·CloudWatch 확인이고, 모델 품질은 정답 병합 단계가 추가된다.
- 오답 유인(섞이는 선택지): `NOW` 표현식(1회 즉시 실행, 반복 아님), 샘플링 비율 100(라벨 지연과 무관), 데이터 품질 모니터로 교체(라벨은 불필요하지만 정확도 측정 불가), 분 단위 cron(지원 표현식에 없음), 데이터 캡처만으로 위반 보고(기준선·스케줄 필요).
- 근거: 〔S1〕〔S7〕〔S8〕〔S10〕〔S16〕〔S17〕〔S18〕〔S22〕〔S23〕

### 패턴 3. 파이프라인·엔드포인트 오류를 어떤 관측 수단으로 감지·통지하는가 (SK2)
- 시나리오 단서:
  - "파이프라인·훈련·처리 작업이 실패하면 즉시 알림" → EventBridge의 상태 변경 이벤트 규칙(`Failed`) → SNS·Lambda 등 대상
  - "엔드포인트 5xx·오류율·지연이 임계를 넘으면 경보" → CloudWatch 지표(`Invocation5XXErrors`, `InvocationModelErrors`, `ModelLatency`) + 경보
  - "컨테이너 내부 오류 원인 조사" → CloudWatch Logs(`/aws/sagemaker/Endpoints/[EndpointName]`)
  - "정적 임계값 없이 정상 범위를 자동 학습" → CloudWatch 이상 탐지
  - "파이프라인 중간에 데이터·모델 품질 게이트" → `QualityCheck`·`ClarifyCheck` 스텝
  - "ETL·오케스트레이션 실패" → Glue Job State Change, Step Functions Execution Status Change
  - "배포 후 문제 시 자동 롤백" → 배포 가드레일 + CloudWatch 경보
- 정답 방향: 상태 변경(성공·실패)은 EventBridge 이벤트, 수치 임계는 CloudWatch 경보, 원인 분석은 로그를 쓴다.
- 오답 유인(섞이는 선택지): Model Monitor(통계적 드리프트 감시이며 작업 실패·5xx 알림 수단이 아님), Clarify 모니터링, Data Capture(요청·응답을 S3에 남기는 기능이며 알림 기능이 아님).
- 근거: 〔S32〕〔S33〕〔S34〕〔S35〕〔S36〕〔S37〕〔S38〕〔S47〕〔S6〕

### 패턴 4. 프로덕션에서 신·구 모델을 비교하는 방식을 고른다 (SK4)
- 시나리오 단서:
  - "실제 사용자 트래픽의 일부(예: 20%)만 새 모델이 응답, 성능 비교 후 확대" → 프로덕션 변형 가중치(`InitialVariantWeight`) + `UpdateEndpointWeightsAndCapacities`
  - "특정 요청만 새 모델로 보내 시험" → `InvokeEndpoint`의 `TargetVariant`
  - "사용자 영향 없이 지연·오류율을 검증" → 섀도 테스트(응답은 프로덕션 변형만 반환)
  - "문제가 생기면 자동으로 되돌린다" → 블루/그린 배포 가드레일 + CloudWatch 경보
  - "서버리스·멀티모델·비동기 엔드포인트" → 섀도 테스트 사용 불가
- 정답 방향: 분배·성능 비교는 변형 가중치, 특정 변형 지정은 `TargetVariant`(분배를 재정의), 무영향 검증은 섀도, 안전한 배포는 가드레일이다. 가중치 변경은 엔드포인트 업데이트 없이 `UpdateEndpointWeightsAndCapacities`로 한다.
- 오답 유인(섞이는 선택지): 섀도로 A/B 수행(응답이 호출자에게 안 감), 가중치를 바꿀 때마다 엔드포인트 새로 생성, 블루/그린 all at once(전량 이동), Model Monitor로 트래픽 분할(감시 도구), 데이터 캡처 샘플링 비율을 트래픽 분배로 착각.
- 근거: 〔S40〕〔S41〕〔S42〕〔S43〕〔S45〕〔S46〕〔S47〕〔S9〕

## 4. 흔한 함정·혼동 짝

### 짝 1. 데이터 품질 vs 모델 품질 모니터링
- 구분 기준: 정답(ground truth) 라벨이 필요한가, 무엇을 기준선과 비교하는가.

| 구분 | 데이터 품질 | 모델 품질 |
|---|---|---|
| 비교 대상 | 캡처한 입력의 특성 통계·스키마 vs 기준선 | 모델 예측 vs 실제 정답 라벨로 계산한 성능 지표 |
| 정답 라벨 | 불필요 | 필요(S3에 올려 캡처 예측과 병합하는 단계가 추가됨) |
| 기준선 입력 | 학습 데이터셋(`DefaultModelMonitor.suggest_baseline`) | 예측과 라벨이 함께 있는 데이터셋(`ModelQualityMonitor.suggest_baseline`의 `problem_type`·`inference_attribute`·`ground_truth_attribute`) |
| 산출·지표 | `statistics.json`, `constraints.json`, 위반 6종, 특성별 `feature_*` 지표 | 문제 유형별 성능 지표(회귀 `mae`·`rmse` 등, 분류 `accuracy`·`f1`·`auc` 등)와 임계 제약 |
| CloudWatch 네임스페이스(실시간) | `/aws/sagemaker/Endpoints/data-metric` | `aws/sagemaker/Endpoints/model-metrics` |
| 잡는 문제 | 입력 분포 변화(데이터 드리프트), 스키마·결측 변화 | 성능 저하(개념 드리프트 포함) |

- 근거: 〔S19〕〔S20〕〔S21〕〔S22〕〔S24〕〔S13〕〔S15〕〔S14〕

### 짝 2. 데이터 드리프트 vs 개념 드리프트 (vs 레이블 이동)
- 구분 기준: 변하는 것이 입력 분포인가, 입력과 타깃 사이의 관계인가.

| 구분 | 데이터 드리프트 | 개념 드리프트 |
|---|---|---|
| 변하는 것 | 입력(특성) 분포 | 입력과 타깃 변수 사이의 관계(타깃 변수의 성질) |
| 감지 | 입력 통계·분포 거리로 직접 감지 | 입력 분포가 그대로일 수 있어 정답 대비 성능, 하류 비즈니스 지표, 사용자 피드백으로 감지 |
| Model Monitor 대응 | 데이터 품질 | 모델 품질(정답 필요) |
| 블로그 세분화 | 공변량 이동(입력 분포 변화), 레이블 이동(클래스 변수 분포 변화) | 개념 이동(입출력 관계 변화) |

- 레이블 이동은 ML Lens의 2종 구분에 별도 대응 용어가 없다(섹션 9 G-4.1-2).
- 근거: 〔S52〕〔S56〕〔S59〕〔S60〕

### 짝 3. 편향 드리프트 vs 특성 기여도 드리프트
- 구분 기준: 공정성 지표를 보는가, SHAP 특성 순위를 보는가.

| 구분 | 편향 드리프트 | 특성 기여도 드리프트 |
|---|---|---|
| 보는 것 | 편향 지표(학습 전·후)가 기준선 제약보다 나빠졌는가 | 전역 SHAP 값의 특성 순위가 기준선과 달라졌는가 |
| 판정 | 허용 범위 A와 Normal Bootstrap 신뢰구간 C 비교(서로소면 경보). 위반은 지표가 기준선 제약보다 나쁠 때 | NDCG 0.90 미만이면 경보, 위반 판정은 nDCG 0.9 미만 |
| 위반 유형 | `bias_drift_check` | `feature_attribution_drift_check` |
| CloudWatch | `bias_metric_<약어>`, 네임스페이스 `aws/sagemaker/Endpoints/bias-metrics` | `feature_<특성>`(전역 SHAP)·`ExpectedValue`, 네임스페이스 `aws/sagemaker/Endpoints/explainability-metrics` |
| 요구 | Clarify 분석 구성, 정답 데이터 | SHAP 기준선 |
| ko_kr 표기 | 바이어스 드리프트 | 특성 어트리뷰션 드리프트 |

- 근거: 〔S26〕〔S27〕〔S28〕〔S29〕〔S30〕〔S31〕〔S18〕〔S61〕

### 짝 4. 실시간 엔드포인트 vs 배치 변환 모니터링
- 구분 기준: 캡처를 어디에 설정하고 어떤 객체로 스케줄에 넘기는가.

| 구분 | 실시간 엔드포인트 | 배치 변환 |
|---|---|---|
| 캡처 설정 | `CreateEndpointConfig`의 `DataCaptureConfig`(샘플링 비율, Input·Output) | `CreateTransformJob`의 `DataCaptureConfig`(`DestinationS3Uri`, `GenerateInferenceId`) |
| 캡처 저장 | `{endpoint-name}/{variant-name}/yyyy/mm/dd/hh/filename.jsonl` | `/input`·`/output` 아래 JSONL 매니페스트 + `yyyy/mm/dd/hh` 접두 |

### 짝 5. Model Monitor vs CloudWatch 경보 vs EventBridge 이벤트
- 구분 기준: 감시 대상이 통계적 드리프트인가, 운영 지표인가, 상태 변경인가.

| 구분 | Model Monitor | CloudWatch 지표·경보 | EventBridge 이벤트 |
|---|---|---|---|
| 감시 대상 | 기준선 대비 모델 품질(입력 통계, 성능, 편향, 기여도) | 엔드포인트·작업·파이프라인 운영 지표의 임계 또는 정상 범위 | 리소스 상태 변경(성공·실패·진행) |
| 트리거 | 모니터링 스케줄이 처리 작업을 주기 실행 | 지표가 임계(또는 이상 탐지 대역)를 이탈 | 상태 변경 이벤트가 규칙과 일치 |
| 대표 예 | `baseline_drift_check` 위반, `CompletedWithViolations` | `Invocation5XXErrors`, `ModelLatency`, `ExecutionFailed` | `SageMaker Training Job State Change`, 파이프라인 실행 `Failed` |
| 연결 | 특성별 지표를 CloudWatch로 발행해 경보로 이어짐 | 알림·조치 | Lambda, SNS, Step Functions 등 호출 |

| 구분 | 변형 가중치 A/B | `TargetVariant` | 섀도 테스트 | 블루/그린(가드레일) |

### 짝 8. 엔드포인트 오류·지연 지표: 4XX vs 5XX vs ModelErrors, ModelLatency vs OverheadLatency
- 구분 기준: 오류 지표는 포함 범위, 지연 지표는 측정 구간이 다르다.

| 지표 | 세는 것·측정 구간 | 포함 범위·비고 |
|---|---|---|
| `Invocation4XXErrors` | 모델이 4xx를 반환한 `InvokeEndpoint` 요청 | 4xx만 |
| `Invocation5XXErrors` | 모델이 5xx를 반환한 요청 | 5xx만 |
| `InvocationModelErrors` | 2XX가 아닌 모든 모델 호출 | 4XX/5XX, 저수준 소켓 오류, 잘못된 HTTP 응답, 요청 타임아웃 포함 |
| `ModelLatency` | 모델이 응답하는 데 걸린 시간(컨테이너와의 로컬 통신 + 컨테이너 내 추론) | 단위 마이크로초 |
| `OverheadLatency` | 요청 수신부터 응답 반환까지에서 `ModelLatency`를 뺀 SageMaker AI 오버헤드 | 요청·응답 크기, 요청 빈도, 인증·권한 부여에 따라 달라짐 |

- 전체 지연은 네트워크 지연, 오버헤드 지연, 모델 지연으로 이뤄진다. 모델 컨테이너는 60초 안에 응답해야 하고, 컨테이너가 4xx·5xx를 반환하면 `ModelError`(HTTP 424)다.
- 근거: 〔S32〕〔S43〕

- 보기:
  - A) 스케줄에 `StartTimeOffset`을 `-P8D`, `EndTimeOffset`을 `-P1D`로 지정하고, 라벨을 JSON Lines로 `yyyy/mm/dd/hh` 경로에 올려 `inferenceId`(또는 `eventId`)가 캡처 데이터와 일치하게 한다.
  - B) 스케줄 표현식을 `NOW`로 바꿔 라벨이 올라올 때마다 즉시 실행한다.
  - C) 라벨이 필요 없는 데이터 품질 모니터링으로 교체한다.
  - D) 데이터 캡처 샘플링 비율을 100으로 올린다.
- 정답: A
- 근거: 〔S22〕〔S23〕 https://docs.aws.amazon.com/sagemaker/latest/dg/model-monitor-model-quality-schedule.html (스케줄 페이지의 -P8D/-P1D 계산 예시. FAQ의 오프셋 예시는 섹션 9 G-4.1-16 참조)
- 오답 근거: B) `NOW`는 1회 즉시 실행이며 `DataAnalysisStartTime`·`DataAnalysisEndTime`이 필수다〔S17〕. 반복 실행 방식이 아니다. C) 데이터 품질 모니터링은 정답 라벨을 쓰지 않으므로 정확도 같은 모델 품질 지표를 측정하지 못한다〔S22〕. D) 샘플링 비율은 캡처할 요청의 비율일 뿐 라벨이 확보되는 시점과 무관하다〔S9〕.

### 후보 3 (난이도: foundational)
- 대응 Skill: SK3
- 문제: 대출 심사 모델을 배포했다. 라이브 데이터에서 모델이 중요하게 쓰는 특성의 중요도 순위가 학습 때와 크게 뒤바뀌는 것을 자동으로 감지해 경보를 받고 싶다. 가장 적합한 구성은?
- 보기:
  - A) 모델 품질 모니터링을 구성하고 `mae` 임계를 설정한다.
  - B) Model Monitor 특성 기여도 드리프트 모니터링을 구성한다. SHAP 기준선과 비교해 NDCG가 0.90 미만이면 경보가 난다.
  - C) 편향 드리프트 모니터링을 구성하고 DPPL 허용 범위를 (-0.1, 0.1)로 둔다.
  - D) 데이터 품질 모니터링의 `categorical_values_check`로 라이브 데이터의 새 범주 값을 감시한다.
- 정답: B
- 근거: 〔S29〕〔S30〕 https://docs.aws.amazon.com/sagemaker/latest/dg/clarify-model-monitor-feature-attribution-drift.html
- 오답 근거: A) `mae`는 정답 라벨 대비 오차를 보는 회귀 모델 품질 지표이며〔S24〕 특성 중요도 순위와 무관하다. C) 편향 드리프트는 공정성 지표를 허용 범위와 비교한다〔S26〕. D) `categorical_values_check`는 기준선보다 미지의 값이 늘었는지 보는 데이터 품질 위반 유형이다〔S13〕.

### 후보 4 (난이도: associate)
- 대응 Skill: SK2
- 문제: 야간 SageMaker Pipelines 재훈련 파이프라인 실행이 실패하면 즉시 운영팀에 알려야 한다. 별도로 프로덕션 엔드포인트의 5xx 응답이 임계를 넘을 때도 경보가 필요하다. 올바른 구성은?
- 보기:
  - A) Model Monitor 데이터 품질 스케줄을 매시간 실행하고 `constraint_violations.json`을 확인한다.
  - B) 파이프라인 실행 상태 변경 이벤트(상태 `Failed`)에 대한 EventBridge 규칙으로 SNS 토픽에 알리고, `Invocation5XXErrors` 지표에 CloudWatch 경보를 만든다.
  - C) Clarify 편향 드리프트 모니터링을 켜고 `bias_drift_check` 위반을 확인한다.
  - D) 엔드포인트 데이터 캡처 샘플링을 100%로 올리고 S3에 쌓인 캡처 파일을 정기적으로 읽는다.
- 정답: B
- 근거: 〔S34〕〔S32〕 https://docs.aws.amazon.com/sagemaker/latest/dg/automating-sagemaker-with-eventbridge.html
- 오답 근거: A) 데이터 품질 모니터링은 입력 통계·스키마의 기준선 위반을 본다〔S19〕. 작업 실패나 5xx를 알리는 수단이 아니다. C) 편향 드리프트는 공정성 지표 변화를 본다〔S26〕. D) 데이터 캡처는 입력·출력을 S3에 기록하는 기능이다〔S6〕. 오류를 감지해 알리는 기능이 아니다.

### 후보 5 (난이도: associate)
- 대응 Skill: SK4
- 문제: 현재 모델(Variant A)과 새 모델(Variant B)을 같은 엔드포인트에서 운영하며 실제 사용자 요청의 20%만 새 모델이 응답하게 하려 한다. 변형별 지표를 비교해 좋으면 엔드포인트를 다시 만들지 않고 트래픽을 늘리고 싶다. 올바른 구성은?
- 보기:
  - A) 두 `ProductionVariant`에 `InitialVariantWeight` 4와 1을 지정해 배포하고, 변형별 CloudWatch 지표를 비교한 뒤 `UpdateEndpointWeightsAndCapacities`로 가중치를 바꾼다.
  - B) 새 모델을 `ShadowProductionVariants`에 배포한다.
  - C) 블루/그린 all at once 트래픽 전환으로 새 모델 플릿에 전체 트래픽을 옮긴다.
  - D) 엔드포인트를 두 개 만들고 각 엔드포인트의 데이터 캡처 샘플링 비율을 80과 20으로 설정한다.
- 정답: A
- 근거: 〔S41〕〔S40〕〔S42〕 https://docs.aws.amazon.com/sagemaker/latest/dg/model-ab-testing.html
- 오답 근거: B) 섀도 변형은 요청 복사본만 받고 응답은 호출자에게 돌려주지 않는다〔S45〕. 사용자의 20%가 새 모델 응답을 받는 요구를 충족하지 못한다. C) all at once는 전체 트래픽을 한 번에 green 플릿으로 옮기는 방식이라 20% 분할이 아니다〔S46〕. D) 샘플링 비율은 데이터 캡처 비율이며 트래픽 분배가 아니다〔S9〕.

## 9. 확인 필요 항목

> 확인 필요 항목: 본문에 단정해서 쓸 수 없었던 불확실·상충·미확인 사항이다. 형식은 `[G-4.1-n] 질문 — 확인한 곳 — 제안`.

- [G-4.1-1] "특성 기여도 드리프트"의 한국어 공식 표기는 무엇인가 — ko_kr Model Monitor 개요·기여도 드리프트 페이지(둘 다 기계 번역 고지가 붙음)에서 확인: 목차 표기는 "프로덕션 환경의 모델에 대한 특성 어트리뷰션 드리프트", 본문 서술은 "특징 속성 드리프트", 편향은 "바이어스 드리프트"이다〔S61〕〔S62〕. 위임 지시문의 "특성 기여도 드리프트"는 이 페이지들에 나오지 않는다 — 제안: 학습문서는 영문(Feature attribution drift)을 병기하고 ko_kr 표기가 기계 번역임을 감안해 용어를 한 가지로 통일.
- [G-4.1-2] 예측(레이블) 드리프트(prediction drift)의 공식 정의가 있는가 — Model Monitor 개요·데이터 품질·모델 품질 페이지, ML Lens 모니터링 단계와 MLPERF06-BP03·BP04 원문을 확인했으나 별도 정의가 없다. ML Lens는 데이터 드리프트·개념 드리프트 2종, AWS 블로그는 공변량 이동·레이블 이동·개념 이동 3종이다〔S52〕〔S56〕〔S60〕. 검색 결과에서 Accenture 이름이 붙은 백서(AWS 백서 경로에 게시)가 "Prediction drift and Feedback drift"를 이름만 나열하는 것을 봤지만 정의가 없어 인용하지 않았다 — 제안: 예측 드리프트 정의를 정답 근거로 쓰지 말고, 레이블 이동은 [블로그] 근거의 보조로만 사용.
- [G-4.1-3] Model Monitor가 지원하는 드리프트 척도는 무엇인가(출처 상충) — ML Lens MLPERF06-BP03은 Model Monitor가 KL 발산·Jensen-Shannon 발산·PSI 같은 통계 척도를 지원한다고 쓴다〔S55〕. 그러나 constraints.json 스키마 문서는 L∞(`linf_simple`·`linf_robust`)와 범주형 `LInfinity`·`ChiSquared`만 나열하고, Model Monitor 개요·데이터 품질·제약 스키마 페이지 원문에는 KL·Jensen-Shannon·PSI·Wasserstein 용어가 없다(2026-10-17 원문 대조)〔S12〕〔S19〕. PSI·KS는 대체 경로(Evidently) 문서에 나온다〔S2〕 — 제안: Model Monitor 내장 척도의 종류·개수를 정답 근거로 쓰는 문항 금지.
- [G-4.1-4] 모니터링 스케줄의 "최소 간격" 공식 수치가 있는가 — ScheduleConfig API는 지원 표현식(매시간, 매일, N시간 간격 `cron(0 [00-23]/[01-24] ? * * *)`, `NOW`)만 나열하고 "minimum interval"이라는 문구는 없다〔S17〕. 1시간 미만 반복이 지원된다는 문장도, 금지된다는 문장도 없다 — 제안: "문서의 지원 표현식 중 반복 최단 단위는 1시간"으로만 서술하고 "최소 간격은 1시간"이라 단정하는 문항 회피.
- [G-4.1-5] 데이터 캡처 샘플링 기본값은 얼마인가 — 기본 20%는 Python SDK `DataCaptureConfig`(`sampling_percentage`) 설명에만 나오고〔S7〕, API의 `InitialSamplingPercentage`는 정수 0~100의 필수 파라미터로 기본값 표기가 없다〔S9〕 — 제안: 20% 기본값은 "Python SDK 기준"으로 한정해 서술.
- [G-4.1-6] Model Monitor 비용 문장의 적용 범위 — (a) FAQ의 "인스턴스 리소스가 스케줄 삭제 전까지 예약된다"는 문장은 배치 변환 모니터링을 설명한 단락에 있어, 실시간 엔드포인트 스케줄에도 같은 방식으로 적용되는지 문서가 구분하지 않는다〔S18〕. (b) 요금 페이지의 "내장 규칙은 최대 30시간 무료"는 Real-Time Inference 항목 아래 문장이며, 같은 페이지 프리 티어 표(첫 2개월)와의 관계와 현행 적용 범위를 확인하지 못했다〔S48〕 — 제안: 요금 수치를 단정하는 문항은 피하고 "스케줄이 처리 작업 인스턴스를 반복 기동해 비용이 생기며 스케줄 삭제로 멈춘다" 수준으로만 사용.
- [G-4.1-7] 서버리스·비동기 추론 엔드포인트에서 데이터 캡처와 Model Monitor가 지원되는가 — Model Monitor 개요·데이터 캡처·FAQ, `DataCaptureConfig` API에서 해당 문장을 찾지 못했다. 섀도 테스트 문서만 서버리스·비동기 추론을 사용 불가로 명시한다〔S45〕 — 제안: 지원 여부를 정답 근거로 쓰지 말 것.

- [G-4.1-16] 오프셋 예시의 문서 간 불일치 — 스케줄 페이지의 계산 예시는 실행 시각 2020-01-09T13:00, `StartTimeOffset=-P8D`, `EndTimeOffset=-P1D`일 때 2020-01-01T13:00부터 2020-01-08T13:00까지를 분석한다고 밝혀, 분석 창이 [실행 시각 − 시작 오프셋, 실행 시각 − 종료 오프셋]임을 보여 준다〔S22〕. 이 규칙을 FAQ 예시에 적용하면(정답이 예측 3일 뒤 도착, `-P3D`/`-P1D` → 창 [T−3일, T−1일]; 정답이 6시간 뒤 도착, `-PT6H`/`-PT1H` → 창 [T−6시간, T−1시간]) 창 안의 예측 대부분은 정답이 도착하기 전 데이터가 된다〔S18〕 — 제안: 오프셋 문항은 스케줄 페이지의 계산 예시를 근거로 쓰고 FAQ 예시의 수치는 정답 근거로 쓰지 말 것.
