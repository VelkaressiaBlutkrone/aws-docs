### 2.1 CI/CD 원칙과 ML 워크플로 적용 (K4)

**공식 정의**

- **지속적 통합(CI)**: 팀이 버전 관리 시스템을 쓰며 같은 위치(예: main 브랜치)에 작업을 자주 통합하고, 각 변경을 빌드·검증해 통합 오류를 최대한 빨리 찾는 개발 관행. 초점은 코드의 자동 빌드·테스트다 〔S6〕.
- **지속적 전달(CD)**: 릴리스 프로세스를 자동화하는 방법론. 모든 변경이 자동으로 빌드·테스트·배포되며, 프로덕션 최종 푸시 직전에 사람·자동 테스트·비즈니스 규칙이 시점을 결정한다. 성공한 변경을 즉시 릴리스할 수 있을 뿐, 모든 변경을 바로 릴리스해야 하는 것은 아니다 〔S6〕.
- AWS 규범 가이드는 CI/CD를 소프트웨어 릴리스 수명 주기 자동화로 설명하고, CI/CD 파이프라인이 sandbox·development·testing·staging·production 환경을 모두 포괄한다고 적는다. 브랜치 전략이 복잡할수록 파이프라인도 복잡해지고 CI/CD의 중요성도 커진다 〔S29〕.

**ML 워크플로에서 달라지는 점**

- ML용 CI/CD는 코드 변경만이 아니라 데이터·모델 파라미터·훈련 구성을 함께 추적해야 한다 〔S64〕.
- Well-Architected ML Lens(MLOPS04-BP01)가 제시하는 구성 요소: IaC/CaC(CloudFormation 또는 CDK)로 환경 일관성 확보 → 코드·구성·인프라 정의·모델 아티팩트의 버전 관리 → 오케스트레이션 도구 선택(SageMaker AI Pipelines / Step Functions / MWAA) → CodePipeline으로 빌드·테스트·배포 자동화(스테이징 → 프로덕션, 승인 게이트, Model Registry 연동) → Model Monitor 기반 모니터링 → 품질 임계 미달 시 자동 롤백(CodeDeploy의 canary/blue-green 등) 〔S64〕.
- MLOps 체크리스트: 지속적 통합 단계는 커밋 시 자동 테스트를 돌리고 데이터·특성·모델 검사까지 포함한다 〔S67〕. 지속적 배포 단계는 모델 승격 방식(canary/shadow/blue-green/A-B) 중 하나 이상과 롤백 수단 하나 이상을 요구한다 〔S68〕.

**ML CI/CD의 세 루프 (정리)**

| 루프 | 시작시키는 것 | 주 도구 | 산출물·게이트 |
|---|---|---|---|
| 코드 루프(CI) | 커밋·풀 리퀘스트·병합 같은 리포지토리 이벤트 | CodePipeline(source) → CodeBuild(build/test) | 테스트 리포트, 빌드 아티팩트 〔S6〕〔S15〕 |
| 모델 루프(ML 파이프라인) | 코드 변경·신규 데이터·일정·드리프트 경보 | SageMaker Pipelines(전처리 → 훈련 → 평가 → Condition → 등록) | Model Registry의 모델 버전과 승인 상태 〔S40〕〔S52〕 |
| 배포 루프(CD) | 모델 버전 승인 | CodePipeline + CloudFormation / SageMaker 배포 가드레일 / CodeDeploy(Lambda·ECS·EC2) | 스테이징 → 수동 승인 → 프로덕션, 경보 기반 롤백 〔S50〕〔S55〕 |

> 🧠 원리: SageMaker Projects 템플릿이 이 세 루프를 하나로 묶는다. CodePipeline(또는 Jenkins)이 코드가 체크인될 때마다 SageMaker 파이프라인을 실행하고, 파이프라인이 만든 모델 버전을 승인하면 그 버전을 엔드포인트에 배포할 수 있다 〔S49〕.

### 2.3 AWS CodePipeline: 구조·유형(V1/V2)·트리거·실행 모드·할당량 (K1, SK1)

**구조** 〔S2〕

- **파이프라인**은 소프트웨어 변경이 릴리스를 거치는 방식을 기술하는 워크플로 구성이며 여러 **스테이지**로 이뤄진다. 스테이지는 환경을 격리하고 그 환경에 동시에 들어오는 변경 수를 제한하는 논리 단위이고, 스테이지 안의 **액션**은 직렬 또는 병렬(`runOrder`)로 실행된다.
- **전환(transition)** 은 실행이 다음 스테이지로 넘어가는 지점이다. 스테이지의 inbound transition을 비활성화하면 실행이 그 스테이지에 진입하지 못한다. 비활성 전환에 여러 실행이 도착하면 전환을 다시 켰을 때 가장 최근 실행만 다음으로 진행한다.
- 액션끼리는 파이프라인 아티팩트 버킷(아티팩트 저장소)을 통해 산출물을 넘긴다.
- 실행이 실패하면 파이프라인 전체를 통과하지 못하고 멈춘다. 실패한 실행은 재시도할 수 있고(추월되었거나 재시도 불가인 경우 제외), 실패한 스테이지는 이전 성공 실행으로 롤백할 수 있다.
- 액션 유형은 `source`, `build`, `test`, `deploy`, `approval`, `invoke` 6종이다.

> 🧠 원리: 스테이지는 한 번에 하나의 실행만 처리하도록 잠긴다. 그래서 같은 스테이지 앞에서 기다리는 실행의 운명이 실행 모드(SUPERSEDED / QUEUED / PARALLEL)로 갈린다 〔S2〕.

| `RollbackStage` 〔S4〕 | 스테이지 롤백(수동·자동) | — |

- 소스 액션 하나에는 트리거를 하나만 지정할 수 있다 〔S4〕.
- V2 트리거 필터: 코드 푸시는 Git 태그·브랜치·파일 경로로, 풀 리퀘스트는 이벤트(opened·updated·closed)·브랜치·파일 경로로 거를 수 있다 〔S2〕.
- 소스별 변경 감지 리소스 〔S5〕: CodeCommit·ECR은 EventBridge 규칙(CodeCommit은 콘솔 기본값이자 권장), S3는 EventBridge 규칙 + CloudTrail 리소스 또는 이벤트가 켜진 버킷, 서드파티 Git(Bitbucket Cloud·GitHub·GitHub Enterprise Server·GitLab)은 연결 리소스(GitHub Enterprise Server·GitLab self-managed는 호스트 리소스 추가).
- 일정으로 시작: EventBridge 규칙을 Schedule 유형으로 만들고 타깃을 CodePipeline으로 지정해 파이프라인 ARN을 입력한다 〔S77〕. EventBridge 문서는 예약 규칙을 레거시로 분류하고 Scheduler 사용을 권장한다 〔S71〕.
- 폴링 파이프라인은 리전당 300개로 고정이고 30일 넘게 비활성이면 폴링이 꺼진다 〔S1〕〔S2〕.

**스테이지 조건(V2)** 〔S2〕: 조건은 규칙 묶음이며 '게이트'라고도 부른다. 진입(Entry) 조건, 실패 시(On Failure) 조건, 성공 시(On Success) 조건 3종이 있고 결과로 스테이지 실패 또는 스테이지 롤백을 걸 수 있다. 예: On Success 조건의 `CloudWatchAlarm` 규칙이 배포 환경의 경보를 발견하면 성공한 스테이지를 롤백한다.

**핵심 할당량(요약)** 〔S1〕: 리전당 파이프라인 수, 폴링 파이프라인 상한, 파이프라인당 스테이지·스테이지당 액션 범위, 액션 유형별 타임아웃(CodeBuild 빌드 36시간·테스트 8시간·사용자 지정 24시간·CloudFormation 배포 3일·CodeDeploy 배포 5일·수동 승인 기본 7일[설정 5분~60일])은 섹션 5의 사실 행에 인용과 함께 정리했다. 이 쿼터는 리전별이고 증액할 수 있으나 폴링 파이프라인 상한은 고정이다. Lambda 호출·Step Functions 호출·S3 배포 같은 다른 액션 유형에도 각자의 타임아웃이 정해져 있다.

### 2.4 AWS CodeBuild: buildspec·컴퓨트·캐시·테스트 리포트·할당량 (K1, SK1, SK5)

**buildspec** 〔S12〕

- YAML 형식의 빌드 명령·설정 모음. 소스에 포함하면 기본 이름은 소스 루트의 `buildspec.yml`이고, 이름·위치를 바꾸거나(S3 버킷 포함) 프로젝트에 직접 정의할 수 있다. 한 프로젝트에는 buildspec을 하나만 지정한다.
- 버전은 `0.2`를 권장한다. `0.1`은 명령마다 별도의 셸 인스턴스에서 실행되어 앞선 명령의 상태(디렉터리 이동·환경 변수)가 이어지지 않는다 〔S12〕〔S16〕.
- 최상위 구조: `version`, `run-as`, `env`(`variables` / `parameter-store` / `secrets-manager` / `exported-variables` / `git-credential-helper`), `proxy`, `phases`, `reports`, `artifacts`, `cache`.
- 단계(`phases`): `install` → `pre_build` → `build` → `post_build`. 각 단계에 `commands`, `finally`, `on-failure`를 둘 수 있다.

| 단계 | 문서가 드는 용도 |
|---|---|
| `install` 〔S12〕 | 빌드 환경에 패키지 설치(예: Mocha·RSpec 같은 테스트 프레임워크). `runtime-versions`로 런타임 버전 지정 |
| `pre_build` 〔S12〕 | Amazon ECR 로그인, npm 의존성 설치 |
| `build` 〔S12〕 | 테스트·빌드 실행(예: Mocha, RSpec, sbt) |
| `post_build` 〔S12〕 | JAR/WAR 패키징, Docker 이미지를 ECR로 푸시, SNS 알림 |

- `on-failure` 값: `ABORT`(빌드 중단) / `CONTINUE`(다음 단계로) / `RETRY` / `RETRY-count` / `RETRY-regex` / `RETRY-count-regex`(재시도 횟수·오류 메시지 정규식 지정). Lambda 컴퓨트·예약 용량에서는 지원되지 않는다 〔S12〕.
- `finally` 블록은 `commands`가 실패해도 실행되며, 그 단계는 `commands`와 `finally`가 모두 성공해야 성공이다 〔S12〕.
- 환경 변수 우선순위: start build 호출 값 > 빌드 프로젝트 정의 > buildspec 선언. 민감값은 평문 `variables`가 아니라 `parameter-store` 또는 `secrets-manager`로 가져온다(평문은 콘솔·CLI에 노출될 수 있음) 〔S12〕.
- `exported-variables`는 CodePipeline과 함께 현재 빌드의 변수를 후속 스테이지로 내보낸다 〔S12〕.

**컴퓨트** 〔S13〕: EC2와 AWS Lambda 2가지 모드. EC2는 유연성, Lambda는 빠른 시작과 자동 확장에 최적화. EC2 모드는 온디맨드(`BUILD_GENERAL1_SMALL`·`BUILD_GENERAL1_LARGE` 같은 사전 정의 유형) 또는 예약 용량 플릿(vCPU·메모리·디스크를 직접 지정)으로 실행한다.

**캐시** 〔S14〕〔S12〕〔S80〕

| 캐시 | 저장 위치·공유 범위 | 비고 |
|---|---|---|
| Amazon S3 | S3 버킷, 여러 빌드 호스트가 공유 〔S80〕 | buildspec `cache`의 `key`는 정확 일치로 찾고, `fallback-keys`는 접두 검색 〔S12〕 |
| 로컬(Local) | 해당 빌드 호스트에서만 사용 〔S80〕 | 모드 3종: source cache·Docker layer cache·custom cache. Docker layer cache는 Linux 전용이며 privileged 모드가 필요 〔S14〕 |

- `cache.action`은 `restore`(복원만) / `save`(저장만)이며 생략하면 둘 다 수행한다 〔S12〕.

**테스트 리포트** 〔S15〕〔S12〕

- 단위·구성·기능 테스트를 빌드 중에 실행하고 결과를 리포트로 남긴다. 지원 형식은 Cucumber JSON, JUnit XML, NUnit XML, NUnit3 XML, TestNG XML, Visual Studio TRX이며 buildspec `reports`에서 `file-format`을 생략하면 `JUNITXML`이다.
- buildspec에 리포트 그룹 이름만 쓰면 CodeBuild가 그룹을 만들어 준다(`<프로젝트명>-<그룹명>` 형식). 기존 그룹을 쓰려면 ARN을 쓴다. 한 프로젝트에 리포트 그룹은 최대 5개다 〔S12〕.
- 리포트는 생성 30일 후 만료되어 볼 수 없다. 더 오래 보관하려면 원시 파일을 S3로 내보내며, 내보낸 파일은 만료되지 않는다. S3 업로드에는 프로젝트의 CodeBuild 서비스 역할 권한이 쓰인다 〔S15〕.

**핵심 할당량(요약)** 〔S11〕: 빌드 타임아웃 5~2160분(36시간), 프로젝트당 리포트 그룹 수, 리포트 보존 30일은 섹션 5에 인용과 함께 있다. 동시 실행 빌드 쿼터는 컴퓨트 유형별로 다르며 기본값은 내부 지표로 정해진다. Linux GPU Small·Large 환경의 동시 빌드 기본 쿼터는 0이라 사용 전에 증액을 요청해야 한다 〔S11〕.

### 2.5 AWS CodeDeploy: 컴퓨트 플랫폼·AppSpec·배포 구성·롤백·할당량 (K1, K5, SK1)

**컴퓨트 플랫폼 3종과 배포 유형** 〔S20〕〔S21〕〔S27〕

| 플랫폼 | 배포 대상 | 배포 유형 | AppSpec | 트래픽 이동 구성 |
|---|---|---|---|---|
| EC2/On-Premises 〔S20〕〔S21〕〔S27〕 | 인스턴스에 애플리케이션 리비전 | in-place 또는 blue/green(blue/green은 EC2 인스턴스만) | 항상 YAML | 최소 정상 호스트 기반 구성(AllAtOnce / HalfAtATime / OneAtATime 또는 사용자 지정). canary·linear·all-at-once 트래픽 이동은 해당 없음 |
| AWS Lambda 〔S20〕〔S21〕〔S27〕 | Lambda 함수의 새 버전 | blue/green(트래픽 이동) | YAML 또는 JSON | canary / linear / all-at-once |
| Amazon ECS 〔S20〕〔S21〕〔S27〕 | 새 task set(교체 task set) | blue/green(트래픽 이동) | YAML 또는 JSON | canary / linear / all-at-once |

- in-place는 기존 인스턴스에서 이전 버전을 멈추고 새 버전을 설치하는 방식이라 가용성이 영향받을 수 있다. blue/green은 새 환경(green)에 설치하고 검증한 뒤 트래픽을 옮긴다 〔S26〕.
- Lambda·ECS 배포에서는 CodeDeploy agent를 쓰지 않는다 〔S21〕.

**AppSpec와 훅** 〔S21〕〔S22〕

- AppSpec 파일은 배포를 라이프사이클 이벤트 훅의 연속으로 관리한다. EC2/On-Premises에서는 소스 파일을 인스턴스 위치로 매핑하고(`files`), 권한을 지정하고, 단계별 스크립트를 실행한다. Lambda에서는 배포할 함수 버전과 검증 함수를, ECS에서는 서비스·컨테이너 이름과 포트, 검증 함수를 지정한다.
- EC2/On-Premises 훅: `ApplicationStop` → `DownloadBundle` → `BeforeInstall` → `Install` → `AfterInstall` → `ApplicationStart` → `ValidateService`(마지막 이벤트, 배포 성공 여부 검증), 그리고 로드 밸런서용 `BeforeBlockTraffic` / `BlockTraffic` / `AfterBlockTraffic` / `BeforeAllowTraffic` / `AllowTraffic` / `AfterAllowTraffic`. `DownloadBundle`·`Install`·`BlockTraffic`·`AllowTraffic`은 CodeDeploy agent 전용이라 스크립트를 걸 수 없다. 첫 배포에는 AppSpec이 아직 없으므로 `ApplicationStop` 훅이 실행되지 않는다 〔S22〕.
- Lambda 훅: `BeforeAllowTraffic`, `AfterAllowTraffic` 2종. ECS 훅: `BeforeInstall`, `AfterInstall`, `AfterAllowTestTraffic`, `BeforeAllowTraffic`, `AfterAllowTraffic` 5종 〔S22〕.
- Lambda·ECS 검증 함수는 `putLifecycleEventHookExecutionStatus`로 `Succeeded` / `Failed`를 CodeDeploy에 알려야 하며, 1시간 안에 알리지 않으면 배포가 실패한다. ECS의 `BeforeInstall` 시점에는 롤백이 불가능하다 〔S22〕.

**배포 구성** 〔S19〕

| 플랫폼 | 사전 정의 구성 | 동작 요약 |
|---|---|---|
| EC2/On-Premises 〔S19〕 | `CodeDeployDefault.AllAtOnce` / `HalfAtATime` / `OneAtATime` | 구성을 지정하지 않으면 `OneAtATime`. AllAtOnce는 한 인스턴스라도 성공하면 전체 성공, HalfAtATime은 절반 이상 성공해야 성공 |
| Amazon ECS 〔S19〕 | `ECSCanary10Percent5Minutes`, `ECSCanary10Percent15Minutes`, `ECSLinear10PercentEvery1Minutes`, `ECSLinear10PercentEvery3Minutes`, `ECSAllAtOnce` | Network Load Balancer를 쓰면 `ECSAllAtOnce`만 지원 |
| AWS Lambda 〔S19〕 | `LambdaCanary10Percent5Minutes` / `10Minutes` / `15Minutes` / `30Minutes`, `LambdaLinear10PercentEvery1Minute` / `2Minutes` / `3Minutes` / `10Minutes`, `LambdaAllAtOnce` | canary는 첫 증분에 10%를 보내고 나머지 90%는 지정 시간 뒤에 이동, linear는 10%씩 지정 간격마다 이동 |

- 영역(AZ)별 정상 호스트 수를 지정하는 zonal 구성은 사전 정의가 없어 직접 만들어야 한다. Lambda·ECS는 사용자 지정 canary·linear 구성을 만들 수 있다(CloudFormation blue/green 방식은 불가) 〔S19〕.

**롤백** 〔S23〕〔S24〕

- 배포 그룹(또는 개별 배포)에서 배포 실패 또는 모니터링 임계 충족 시 자동 롤백을 설정할 수 있고, 이때 마지막 정상(last known good) 리비전이 배포된다. 개별 배포에서 그룹의 롤백 설정을 덮어쓸 수 있다.
- 롤백은 이전에 배포한 리비전을 새 배포로 재배포하는 방식이며 새 배포 ID가 부여된다. 실패한 배포를 수동으로 이전 리비전 재배포해 되돌릴 수도 있다. 자동 롤백 발생은 SNS 알림으로 받을 수 있다.

> 🧠 원리: CodeDeploy의 "롤백"은 별도 기능이 아니라 이전 리비전을 대상으로 한 재배포다. 그래서 롤백도 훅과 배포 구성의 영향을 받고 자체 배포 ID를 가진다 〔S24〕.

**핵심 할당량(요약)** 〔S18〕: Lambda 배포 최대 50시간은 섹션 5에 인용과 함께 있다. 배포 그룹당 동시 배포 수, 배포 그룹당 연결 경보 수, EC2/On-Premises 인플레이스 배포 최대 시간, 라이프사이클 이벤트 제한 시간 같은 쿼터도 같은 페이지에 있으며 일부는 증액할 수 있다.

### 2.6 문제 해결(트러블슈팅) 체크리스트 (SK1)

| 서비스 | 증상 | 원인 → 조치 | 근거 |
|---|---|---|---|
| CodeBuild | 로그에 `Cannot connect to the Docker daemon at unix:/var/run/docker.sock` | privileged 모드를 쓰지 않음 → 프로젝트 환경에서 Privileged 플래그를 켜고, 필요하면 buildspec `install` 단계에서 Docker 데몬을 시작 | 〔S16〕 |
| CodeBuild | 앞선 명령에서 설정한 환경 변수·디렉터리가 다음 명령에서 사라짐 | buildspec `0.1`은 명령마다 별도 셸 → `0.2` 사용 | 〔S16〕〔S12〕 |
| CodeBuild | 경고 `Skipping install of runtimes. Runtime version selection is not supported by this build image` | `runtime-versions`를 지정했는데 지원되는 표준 이미지(Ubuntu Standard 또는 Amazon Linux 2 standard)가 아닌 이미지를 사용 → 지원 이미지를 쓰거나 `runtime-versions`를 뺀다 | 〔S12〕 |
| CodePipeline | 소스 액션이 "Could not access the CodeCommit repository ... pipeline IAM role has sufficient permissions" | 파이프라인 서비스 역할에 리포지토리 접근 권한 부여 | 〔S10〕 |
| CodePipeline | S3·ECR·CodeCommit 소스인데 자동 시작이 멈춤 | 콘솔에서 브랜치명·객체 키 등을 끝부분만 바꾸면 변경 감지 이벤트 규칙이 갱신되지 않을 수 있음 → 이름의 앞부분을 바꾸거나 CLI·CloudFormation으로 규칙을 관리 | 〔S10〕 |
| CodePipeline | 폴링 파이프라인이 더는 시작되지 않음 | 30일 넘게 비활성이면 폴링이 꺼짐 → 이벤트 기반 변경 감지로 이전 | 〔S2〕 |
| CodePipeline | 실행 모드를 QUEUED·PARALLEL로 바꾼 뒤 실행 한도에 도달해 실행이 실패 | 모드별 동시 실행 한도를 확인하고 그 안으로 조절 | 〔S10〕〔S1〕 |
| CodeDeploy | 로그에 `Missing credentials - please check if this instance was started with an IAM instance profile` | 인스턴스에 IAM 인스턴스 프로파일이 없거나 권한 부족 | 〔S25〕 |
| CodeDeploy | "The deployment failed because a specified file already exists at this location" | 배포 시 덮어쓰기(overwrite) 또는 유지(retain) 옵션을 선택 | 〔S25〕 |
| CodeDeploy | Lambda·ECS 배포가 훅 단계에서 시간 초과 | 검증 함수가 1시간 안에 `putLifecycleEventHookExecutionStatus`로 결과를 알리지 않음 | 〔S22〕 |
| CodeDeploy | "Validation of PKCS7 signed message failed" | SHA-1만 지원하는 오래된 agent → agent 업데이트 | 〔S25〕 |
| SageMaker Pipelines | 일시적 오류로 단계 실패 | 단계에 재시도 정책(`Step.SERVICE_FAULT`·`Step.THROTTLING`·`SageMaker.JOB_INTERNAL_ERROR`·`SageMaker.CAPACITY_ERROR`·`SageMaker.RESOURCE_LIMIT`) 설정 | 〔S45〕 |

- CodeDeploy 배포 실패 원인은 로그 파일에서 찾을 수 있고, 인스턴스별로 보는 대신 CloudWatch Logs로 모으길 권장한다. EC2/On-Premises 문제 해결을 자동화하는 Systems Manager 런북이 `AWSSupport-TroubleshootCodeDeploy`다 〔S25〕.

### 2.7 버전 관리(Git)와 코드 리포지토리–파이프라인 연동 (K3, K6)

**Git 기본** 〔S81〕〔S36〕〔S37〕

- 버전 관리는 소스 코드를 저장하고 변경을 추적하는 시스템이며, 변경이 버전으로 저장되어 비교하거나 이전 버전으로 되돌릴 수 있다. Git은 소스 코드 변경 관리용 오픈 소스 버전 관리 도구다 〔S81〕.
- 커밋은 브랜치에서 한 모든 변경을 저장하는 기능이고, 푸시는 로컬 저장소의 커밋을 호스팅 저장소로 복사하는 것이며, 풀 리퀘스트는 변경을 병합하기 전에 다른 기여자가 검토하도록 요청하는 절차다 〔S36〕〔S81〕.
- 병합 전략 〔S37〕: **fast-forward**는 대상 브랜치 포인터를 소스 브랜치의 최신 커밋으로 옮기며 병합 커밋을 만들지 않고 이력을 보존한다(가능하면 Git 기본 동작). **squash**는 소스 브랜치 변경을 커밋 하나로 합쳐 적용하고 개별 이력은 남기지 않는다. **three-way**는 병합 커밋을 만들면서 소스 브랜치의 개별 커밋을 이력에 유지한다.
- ML 자산(코드·구성·인프라 정의·모델 아티팩트)도 버전 관리 대상이며, ML Lens는 CodeCommit 또는 서드파티 리포지토리와 실험을 허용하면서 안정적 운영 환경을 유지하는 브랜치 전략을 함께 권한다 〔S64〕.

**리포지토리 → 파이프라인 연동 방식** 〔S5〕〔S7〕〔S8〕〔S79〕

| 소스 | 변경 감지 | 후속 액션에 넘기는 형태 | 비고 |
|---|---|---|---|
| AWS CodeCommit 〔S5〕 | EventBridge 규칙(콘솔로 만들면 자동 생성, 권장) | 기본: 커밋의 얕은 복사 ZIP / Full clone: Git URL 참조(하위 CodeBuild 액션만 사용 가능) | ⚠️ 신규 고객 2024-07-25 중단 → 2025-11-25 재개 〔S38〕 |
| GitHub·GitHub Enterprise Server·GitLab.com·GitLab self-managed·Bitbucket Cloud 〔S5〕 | 연결(connections)이 변경 감지를 관리. GitHub App에 설치된 웹훅이 push 이벤트를 구독 | ZIP 또는 Full clone(CodeBuild 전용) | 연결 하나가 해당 제공자의 모든 리포지토리를 지원. GitHub(OAuth app) 액션은 비권장 |
| Amazon S3 〔S5〕 | EventBridge 규칙 + CloudTrail 또는 이벤트가 켜진 버킷 | 객체 버전 | 버전 관리가 켜진 버킷을 소스로 구성 |
| Amazon ECR 〔S5〕 | EventBridge 규칙 | 이미지 | 컨테이너 이미지 변경을 EventBridge로 감지 |

- ⚠️ 명칭: 연결 기능은 2024-03-29에 AWS CodeStar Connections에서 AWS CodeConnections로 개명되었다 〔S9〕. SageMaker 프로젝트 문서는 아직 "AWS CodeStar connection"이라 적고, 이 연결에 키 `sagemaker`·값 `true` 태그를 달라고 요구한다 〔S50〕.
- 리포지토리 이벤트로 파이프라인을 시작하는 세 가지 방식(정리): ① 이벤트 기반(CodeCommit·S3·ECR의 EventBridge 규칙) ② 연결의 웹훅(서드파티 Git) ③ V2 파이프라인의 트리거 정의(push·PR, 태그·브랜치·파일 경로 필터) 〔S2〕〔S4〕〔S5〕.

### 2.8 브랜치 전략과 파이프라인 호출: Gitflow vs GitHub Flow (SK2)

AWS 규범 가이드는 세 가지 일반 전략을 복잡도 순(단순 → 복잡)으로 Trunk, GitHub Flow, Gitflow라고 설명한다 〔S28〕.

| 항목 | Trunk | GitHub Flow | Gitflow |
|---|---|---|---|
| 핵심 | 모든 개발자가 단일 브랜치(trunk 또는 main)에서 작업, 하루 여러 번 소규모 커밋 〔S34〕 | 단명 feature 브랜치를 완료되면 main에 병합 〔S32〕 | feature 브랜치 → 승인 후 통합 브랜치(`develop`)에 병합 → 기능이 모이면 `release` 브랜치를 만들어 상위 환경에 배포 〔S28〕〔S30〕 |
| 브랜치 | trunk(main) | main + 단명 feature | 영구 `main`·`develop` + `feature`·`release`·`hotfix` 지원 브랜치 〔S35〕 |
| 배포 시점 | 항상 릴리스 가능 상태를 유지하며 자주 통합 〔S34〕 | main에 병합되는 즉시 배포 〔S32〕 | 예정된 릴리스 주기에 맞춰 release 브랜치로 〔S30〕 |
| 적합 | 자동 테스트와 CI에 의존하는 팀 〔S34〕 | 작고 성숙한 팀, 지속적 전달 지향 〔S33〕 | 크고 분산된 팀, 엄격한 릴리스·규정 준수 요구, 여러 프로덕션 버전 동시 유지 〔S31〕 |
| 부적합 | — | 엄격한 규정 준수·릴리스 절차가 있는 팀, 병합 충돌이 잦음 〔S33〕 | 지속적 전달을 지향하는 조직, release 브랜치가 오래 살아 기술 부채 누적 〔S31〕 |
| 파이프라인 호출(정리) | main push 시 빌드·테스트·배포 파이프라인 | main push는 배포 파이프라인, PR 이벤트(opened/updated)는 사전 검증 파이프라인 | 브랜치별 파이프라인: develop·feature는 통합 환경, release·main·hotfix는 상위 환경 〔S35〕 |

- Gitflow는 세 전략 중 가장 복잡해 CI/CD 파이프라인에 규정 준수용 단계가 더 필요하고 여러 프로덕션 릴리스를 동시에 지원해야 한다 〔S29〕.
- CodePipeline V2 + 연결 소스 + `QUEUED` 모드로 `main`·`develop`·`hotfix`·`release` 브랜치 푸시를 순서대로 처리하는 릴리스 파이프라인, 별도의 feature 개발 파이프라인을 만드는 예가 AWS DevOps 블로그에 있다 〔S35〕.

> 🧠 원리: 브랜치 전략이 복잡할수록 사람이 절차를 우회할 여지가 늘기 때문에 CI/CD가 가드레일 역할을 하며 그 중요성도 커진다 〔S29〕.

### 2.9 SageMaker Pipelines: DAG·단계·파라미터·캐싱·재시도 (SK3, SK4)

**정의와 장점** 〔S39〕

- ML 개발을 자동화하는 목적 특화 워크플로 오케스트레이션 서비스다. 오케스트레이션 인프라(서버리스)를 SageMaker AI가 자동으로 프로비저닝·확장·종료하고, 시각 편집기·SDK·API·JSON으로 만들고 관리한다. 다른 SageMaker AI 기능·AWS 서비스와 통합되며, 비용은 Studio 환경과 파이프라인이 오케스트레이션하는 하위 작업(훈련·처리·추론·S3 저장 등)에 대해서만 낸다. 내장 버전 관리와 ML Lineage Tracking으로 변경·실행 이력과 데이터 계보를 추적한다.

**DAG** 〔S40〕〔S42〕

- 파이프라인은 방향성 비순환 그래프(DAG)로 연결된 단계 묶음이고, DAG 구조는 한 단계의 출력 속성을 다른 단계의 입력으로 넘기는 **데이터 의존성**으로 결정된다(`<step_name>.properties.<property>` 형식).
- 데이터 의존성이 없는 단계는 실행 즉시 시작되어 병렬로 돈다. 동시 단계 수는 `ParallelismConfiguration`으로 제한한다.
- 데이터 연결 없이 시작 순서만 강제하려면 `DependsOn`(custom dependency)을 쓴다. 순환 의존성은 검증 예외를 일으킨다.

**단계 유형 (현재 문서 기준 18종)** 〔S41〕〔S40〕

| 단계 | 하는 일 | 알아둘 점 |
|---|---|---|
| Execute code 〔S41〕 | 사용자 코드(Python 함수·스크립트·노트북)를 단계로 실행 | Studio 드래그앤드롭용. 내부적으로 SageMaker 훈련 작업으로 실행 |
| Processing 〔S41〕 | 데이터 처리용 processing 작업 | 예제 DAG의 전처리(`AbaloneProcess`)·평가(`AbaloneEval`) 단계 |
| Training 〔S41〕 | 훈련 작업 | 예제 DAG의 `AbaloneTrain` |
| Tuning 〔S41〕 | 하이퍼파라미터 튜닝(HPO) 작업 | 여러 훈련 작업을 실행하고 각 작업이 모델 버전을 만든다 |
| AutoML 〔S41〕 | AutoML 작업으로 모델 자동 훈련 | 현재는 앙상블링(ensembling) 훈련 모드만 지원 |
| Model 〔S41〕 | 모델 생성(Create model) 또는 등록(Register model) | Create model은 예: 배치 변환 준비, Register model은 Model Registry의 버전 있는 모델 패키지 그룹에 등록 |
| Deploy model (endpoint) 〔S41〕 | 새 엔드포인트를 만들거나 기존 엔드포인트에 배포 | 실시간 추론. IAM에 `sagemaker:CreateModel`·`CreateEndpointConfig`·`CreateEndpoint`·`UpdateEndpoint` 등이 필요 |
| Transform 〔S41〕 | 배치 변환 작업으로 데이터셋 예측 생성 |  |
| Condition 〔S41〕 | 단계 속성을 평가해 다음 동작을 분기(조건 목록 + true 분기 + false 분기) | 중첩 불가, 양 분기에 같은 단계 사용 불가 |
| Callback 〔S41〕 | 외부 프로세스·서비스를 워크플로에 편입: SQS 큐에 토큰 메시지를 보내고 응답을 기다린다 | 완료 시 `SendPipelineExecutionStepSuccess` / `SendPipelineExecutionStepFailure`에 토큰 전달 |
| Lambda 〔S41〕 | Lambda 함수 실행 | 기존 함수는 파이프라인과 같은 리전이어야 함 |
| ClarifyCheck 〔S41〕 | 편향 분석·설명 가능성에 대한 baseline drift 검사 | ⚠️ Clarify 컨테이너 사용(Clarify 신규 고객 중단) |
| QualityCheck 〔S41〕 | 데이터 품질·모델 품질 baseline 제안과 drift 검사 | ⚠️ Model Monitor 컨테이너 사용(Model Monitor 신규 고객 중단) |
| EMR 〔S41〕 | 실행 중인 EMR 클러스터에서 EMR 단계 처리, 또는 파이프라인이 클러스터를 만들고 관리 |  |
| Notebook Job 〔S41〕 | SageMaker Notebook Job을 비대화형으로 단계 실행 | 드래그앤드롭 UI에서는 Execute code 단계를 쓴다 |
| Fail 〔S41〕 | 조건·상태가 충족되지 않을 때 실행을 중단하고 사용자 지정 오류 메시지 제공 | 동시에 실행 중인 단계가 있으면 그 단계가 끝나야 파이프라인이 종료됨 |

- 위 표의 "Model"은 Create model·Register model을 합친 항목이라 문서 목록의 18종과 대응한다(Execute code, Processing, Training, Tuning, AutoML, Model, Create model, Register model, Deploy model, Transform, Condition, Callback, Lambda, ClarifyCheck, QualityCheck, EMR, Notebook Job, Fail). 문서 본문에는 위 목록에 없는 "Fine-tuning step" 절도 있다(섹션 9 G-3.3-6).
- 이 Task의 키워드(훈련·추론 작업 구성)에 대응하는 단계는 Training·Tuning(훈련), Create model·Deploy model (endpoint)·Transform(추론)이다.

**파라미터** 〔S43〕: `ParameterString` / `ParameterInteger` / `ParameterFloat` / `ParameterBoolean` 4종. 기본값을 두고 실행 시작 시 값을 덮어쓸 수 있다(`pipeline.start(parameters=...)`). 단계 정의에 쓰는 모든 파라미터는 파이프라인 정의에 선언해야 한다.

**캐싱** 〔S44〕

| 항목 | 내용 |
|---|---|
| 기본값 〔S44〕 | 꺼짐(opt-in) |
| 켤 때 필수 〔S44〕 | 타임아웃 — 이전 실행이 재사용 후보로 남는 최대 나이 |
| 재사용 기준 〔S44〕 | 단계 유형별 기본 cache key 속성이 같은 이전 실행(단계 서명) |
| 재사용 조건 〔S44〕 | 성공한 실행만. 타임아웃 안에 여러 개면 가장 최근 성공 실행. 진행 중인 실행이 걸리면 둘 다 계속 실행되고 성공 시 캐시 갱신 |
| 범위 〔S44〕 | 개별 파이프라인 안(다른 파이프라인의 단계는 재사용 불가) |
| 지원 단계 〔S44〕 | Processing, Training, Tuning, AutoML, Transform, ClarifyCheck, QualityCheck, EMR |

**재시도 정책** 〔S45〕

| 항목 | 내용 |
|---|---|
| 지원 단계 〔S45〕 | Processing, Training, Tuning, AutoML, Create model, Register model, Transform, Notebook job |
| 예외 유형 〔S45〕 | `Step.SERVICE_FAULT`, `Step.THROTTLING`(둘은 Pipelines가 기본으로 자동 재시도하며 정책으로 덮어쓸 수 있음), `SageMaker.JOB_INTERNAL_ERROR`, `SageMaker.CAPACITY_ERROR`, `SageMaker.RESOURCE_LIMIT` |
| 설정 필드 〔S45〕 | `ExceptionType`, `IntervalSeconds`(첫 재시도 전 대기), `BackoffRate`(재시도마다 간격에 곱하는 배수), `MaxAttempts`(기본 5, 최대 20), `ExpireAfterMin` |
| 제약 〔S45〕 | `MaxAttempts`와 `ExpireAfterMin`은 둘 중 하나만 지정(둘 다 주면 검증 오류). 튜닝·AutoML 단계는 내부 재시도 때문에 `SageMaker.JOB_INTERNAL_ERROR`를 재시도하지 않음 |

**실행 방법과 트리거** 〔S43〕〔S46〕〔S53〕

- 수동·SDK 시작(`pipeline.start(parameters=...)`), EventBridge 규칙의 타깃(`StartPipelineExecution`), SageMaker Python SDK의 파이프라인 일정(`PipelineSchedule`, EventBridge Scheduler 서비스 주체 `scheduler.amazonaws.com` 사용)으로 시작한다 〔S46〕.
- SageMaker 파이프라인은 EventBridge 타깃으로 지원되며 S3 신규 파일 업로드·드리프트로 인한 엔드포인트 상태 변화·SNS 토픽 같은 이벤트로 시작할 수 있다. 규칙은 이벤트 패턴 또는 일정(Schedule)이고, 사용자 지정·파트너 이벤트 버스에서는 Schedule이 지원되지 않으며, 파라미터는 정적 값 또는 JSON path 동적 값이다 〔S46〕.
- SageMaker는 파이프라인 실행·단계 상태 변화도 EventBridge 이벤트로 보내며, 상태 변화마다 이벤트가 여러 번 올 수 있다 〔S53〕.

**ClarifyCheck·QualityCheck의 baseline 수명 주기** ⚠️ 〔S47〕

- 두 단계는 항상 새 baseline을 계산한다. 모델 패키지에는 데이터 편향·모델 편향·설명 가능성(ClarifyCheck)과 모델 품질·데이터 품질(QualityCheck)까지 5종의 baseline을 등록할 수 있다.
- `skip_check=False`일 때 이전 baseline 대비 위반이 감지되면 단계가 실패하고 파이프라인이 진행되지 않아 드리프트한 모델이 등록되지 않는다.

| 사용 사례 | `skip_check` / `register_new_baseline` | 드리프트 검사 | 이후 `DriftCheckBaselines` |
|---|---|---|---|
| 정기 재훈련, 이전 baseline 유지 〔S47〕 | False / False | 기존 baseline 대비 검사 | 최신 승인 모델 또는 공급한 baseline |
| 정기 재훈련, baseline 갱신 〔S47〕 | False / True | 기존 baseline 대비 검사 | 새로 계산한 baseline |
| Model Monitor 위반 때문에 재훈련, 이전 baseline 유지·해당 검사 건너뜀 〔S47〕 | True / False | 검사 없음 | 최신 승인 모델 또는 공급한 baseline |
| 최초 실행, 또는 위반 재훈련에서 검사 건너뛰고 baseline 갱신 〔S47〕 | True / True | 검사 없음 | 새로 계산한 baseline |

**Pipelines는 Projects 없이도 쓴다**: 파이프라인은 훈련 작업·처리 작업처럼 독립 엔티티라 노트북에서 SDK로 만들고 실행할 수 있다 〔S49〕.

**Model Registry와 승인 → 배포 자동화** 〔S51〕〔S52〕〔S53〕〔S73〕

- Model Registry는 모델을 카탈로그화(모델 그룹 안의 모델 버전), 메타데이터 연결, 승인 상태 관리, **CI/CD로 모델 배포 자동화**를 지원한다 〔S51〕.
- 승인 상태는 `PendingManualApproval` / `Approved` / `Rejected`이며, SageMaker 제공 프로젝트 템플릿을 쓰면 상태 전이가 동작을 일으킨다 〔S52〕.

| 전이 | 동작 |
|---|---|
| `PendingManualApproval` → `Approved` 〔S52〕 | 승인된 모델 버전의 CI/CD 배포 시작 |
| `PendingManualApproval` → `Rejected` 〔S52〕 | 동작 없음 |
| `Rejected` → `Approved` 〔S52〕 | 승인된 모델 버전의 CI/CD 배포 시작 |
| `Approved` → `Rejected` 〔S52〕 | 가장 최근 `Approved` 버전을 배포하는 CI/CD 시작 |

- 승인은 SDK(Boto3)·Studio 콘솔로 하거나 파이프라인의 Condition 단계로 자동 평가할 수 있다 〔S52〕.
- 모델 패키지 상태 변화는 EventBridge의 `SageMaker Model Package State Change` 이벤트로 전달되어 Lambda·배포 파이프라인을 시작시킬 수 있다 〔S53〕. 블로그 예제에서도 등록된 모델의 배포 파이프라인은 그 상태에 따라 시작된다 〔S73〕.

> 🧠 원리: 승인 상태 전이가 곧 CI/CD 트리거다. `Approved`로 바뀌는 순간 배포가 시작되고, `Approved` → `Rejected`는 가장 최근 `Approved` 버전으로 다시 배포하게 만든다 〔S52〕.

**승인 → 배포 자동화의 표준 흐름(정리)**: ① 모델 구축 파이프라인이 모델을 `PendingManualApproval`로 등록 → ② Condition 단계 또는 사람이 승인 → ③ 상태 변화 이벤트(또는 템플릿의 트리거)가 배포 파이프라인 시작 → ④ CloudFormation으로 스테이징 엔드포인트 배포 → ⑤ 수동 승인 → ⑥ 프로덕션 배포 〔S50〕〔S52〕〔S53〕.

### 2.12 배포 전략과 롤백: SageMaker 가드레일 ↔ CodeDeploy 구성 (K5)

**전략 정의(공식)** 〔S26〕: in-place(기존 컴퓨트 자원에서 이전 버전을 멈추고 새 버전 설치), blue/green(동일한 두 환경 사이 트래픽 전환), canary(점진 노출 후 전체 교체), linear(동일 증분·동일 간격), all-at-once(전체 한 번에). in-place는 all-at-once(서비스 중단 가정) 또는 롤링 업데이트로 수행한다.

**플랫폼별 지원 매트릭스** 〔S27〕

| 전략 | Amazon ECS | AWS Lambda | EC2/온프레미스 |
|---|---|---|---|
| In-place 〔S27〕 | 지원 | 지원 | 지원 |
| Blue/green 〔S27〕 | 지원 | 지원 | 지원(EC2 인스턴스만) |
| Canary 〔S27〕 | 지원 | 지원 | 미지원 |
| Linear 〔S27〕 | 지원 | 지원 | 미지원 |
| All-at-once 〔S27〕 | 지원 | 지원 | 미지원 |

**SageMaker 배포 가드레일** 〔S54〕〔S55〕〔S56〕

- 비동기·실시간 추론 엔드포인트에만 적용되며 두 가지다: blue/green(트래픽 이동 모드 3종 — all at once / canary / linear)과 rolling.
- 엔드포인트를 업데이트하면 SageMaker AI는 자동으로 blue/green으로 새 플릿(green)을 프로비저닝하고 트래픽을 옮기며, green이 정해진 평가 기간(베이킹 기간) 동안 정상이면 이전 플릿(blue)을 종료한다 〔S55〕.
- 베이킹 기간 중 사전 지정한 CloudWatch 경보가 하나라도 울리면 모든 트래픽이 blue 플릿으로 롤백된다. 다단계·베이킹이 있는 blue/green은 업데이트 기간 동안 두 플릿 모두 과금된다 〔S55〕.

| 모드 | 정의 | 장점 | 단점 | 추천 |
|---|---|---|---|---|
| All at once | 한 단계로 전체 트래픽 이동 | 갱신 시간 최소 | 회귀 업데이트가 트래픽 100%에 영향 | 시간·비용 최소화 〔S55〕 |
| Canary | 두 단계: 작은 일부(canary) → 나머지 | 회귀 업데이트의 영향 범위를 카나리 플릿으로 한정 | 배포 내내 두 플릿 병행 | 영향 범위와 병행 시간 사이 균형 〔S55〕 |
| Linear | 고정 비율을 사전에 정한 횟수의 균등 간격 단계로 이동 | 여러 단계로 위험 최소화 | 갱신 시간·비용이 단계 수에 비례 | 여러 단계로 분산해 위험 최소화 〔S55〕 |
| Rolling | 지정한 배치 크기로 용량을 점진 프로비저닝·이동하고 단계마다 이전 인스턴스 정리 | blue/green보다 필요 용량이 적음 | — | 대형 모델·인스턴스가 많은 엔드포인트 〔S56〕 |

**API 구성 (이름과 범위)** 〔S60〕〔S58〕〔S59〕〔S61〕〔S62〕〔S57〕

- `DeploymentConfig` = `BlueGreenUpdatePolicy` 또는 `RollingUpdatePolicy`(하나만) + `AutoRollbackConfiguration`. 업데이트 정책을 지정하지 않으면 all at once 트래픽 이동의 blue/green이 기본이다 〔S60〕〔S58〕.
- `BlueGreenUpdatePolicy`: `TrafficRoutingConfiguration`(필수), `TerminationWaitInSeconds`(기본 0, 이전 플릿 종료 전 추가 대기), `MaximumExecutionTimeoutInSeconds`(600~28800초, 총 대기 시간보다 커야 함) 〔S58〕.
- `TrafficRoutingConfiguration`: `Type` = `ALL_AT_ONCE` / `CANARY` / `LINEAR`, `WaitIntervalInSeconds`(단계 사이 대기), `CanarySize`(변형 전체 인스턴스 수의 50% 이하), `LinearStepSize`(10~50%) 〔S59〕.
- `RollingUpdatePolicy`: `MaximumBatchSize`(5~50%), `WaitIntervalInSeconds`(베이킹 기간), `MaximumExecutionTimeoutInSeconds`, `RollbackMaximumBatchSize`(미지정 시 이전 플릿 전체 용량을 한 번에 복구) 〔S62〕.
- `AutoRollbackConfiguration.Alarms`: 엔드포인트 지표를 감시하는 CloudWatch 경보 1~10개. 배포 중 하나라도 울리면 롤백한다 〔S61〕.
- 제약: 새 엔드포인트 구성은 기존과 같은 variant 이름이어야 하고, Marketplace 컨테이너·Inf1 인스턴스를 쓰는 엔드포인트는 가드레일을 쓸 수 없다(all at once, 최종 베이킹 없는 blue/green으로 대체). rolling은 서버리스·다중 변형 엔드포인트에서도 쓸 수 없다 〔S57〕.

|---|---|---|
| All-at-once | `CodeDeployDefault.LambdaAllAtOnce` / `ECSAllAtOnce` 〔S19〕 | `ALL_AT_ONCE`(기본) 〔S58〕〔S59〕 |
| Canary | `LambdaCanary10Percent5Minutes` 등: 첫 증분 10% 이동 후 나머지는 지정 시간 뒤 〔S19〕 | `CANARY`: 2단계, `CanarySize`, `WaitIntervalInSeconds` 〔S59〕 |
| Linear | `LambdaLinear10PercentEvery1Minute` 등: 10%씩 지정 간격 〔S19〕 | `LINEAR`: n단계, `LinearStepSize` 〔S59〕 |
| Rolling / in-place | EC2/온프레 in-place + `HalfAtATime` / `OneAtATime` 〔S19〕〔S26〕 | `RollingUpdatePolicy`: 배치 5~50% 〔S62〕 |
| Blue/green | EC2(인스턴스)·Lambda·ECS 〔S27〕 | 엔드포인트 업데이트의 기본 방식 〔S55〕 |
| 롤백 트리거 | 배포 그룹에 연결한 경보·실패한 훅·자동 롤백 설정 → 마지막 정상 리비전 재배포 〔S23〕 | `AutoRollbackConfiguration` 경보 + 베이킹 기간 〔S61〕〔S55〕 |
| 적용 대상 | EC2/온프레·Lambda·ECS 〔S20〕 | 비동기·실시간 엔드포인트 〔S54〕 |

- CodeDeploy 사전 정의 canary·linear는 값이 고정된 이름(예: 10%, 5분)이고, SageMaker는 용량(인스턴스 수·비율)과 대기 시간을 API 파라미터로 직접 지정한다(정리). CodeDeploy는 SageMaker 엔드포인트를 컴퓨트 플랫폼으로 지원하지 않는다 〔S20〕.
- MLOps 체크리스트는 모델 승격 방식으로 canary·shadow·blue/green·A/B 중 하나 이상과 롤백 수단 하나 이상을 요구한다. shadow는 새 모델이 기존 모델과 함께 트래픽을 받되 기존 모델만 추론 결과를 출력한다 〔S68〕.

> 🧠 원리: 베이킹 기간에는 이전 플릿(blue)이 아직 살아 있어서 경보가 울리면 즉시 트래픽을 되돌릴 수 있다. 그래서 canary·linear처럼 베이킹이 길어질수록 두 플릿이 병행하는 시간만큼 비용이 늘어난다 〔S55〕.

- buildspec의 `finally` 블록은 `commands`가 실패해도 실행되므로(정리 목적) 품질 게이트로 쓰기에 맞지 않는다(정리) 〔S12〕.

### 2.14 모델 재훈련 메커니즘 (SK6)

| 트리거 | 구성 | 근거·주의 |
|---|---|---|
| 일정 기반 | EventBridge Scheduler(권장) 또는 EventBridge 규칙(Schedule, 레거시) → 타깃으로 SageMaker 파이프라인(`StartPipelineExecution`) | 예약 규칙은 레거시이며 Scheduler 사용이 권장된다 〔S71〕. 성능·데이터 패턴과 무관한 고정 일정 재훈련은 ML Lens의 안티패턴이다 〔S65〕 |
| 신규 데이터 도착 | S3 EventBridge 알림 → `Object Created` 규칙 → SageMaker 파이프라인 / Glue 워크플로 / Lambda·Step Functions | 〔S69〕〔S46〕〔S70〕〔S65〕 |
| 드리프트·품질 위반 | Model Monitor 일정 실행 → CloudWatch 지표 → 임계 초과 CloudWatch 경보 → EventBridge 규칙 → 모델 구축 파이프라인 시작 | 블로그 패턴 〔S73〕, ML Lens 〔S78〕〔S65〕. ⚠️ Model Monitor 신규 고객 중단 〔S74〕 |
| 모델 레지스트리 이벤트 | `SageMaker Model Package State Change` → 배포 파이프라인 | 재훈련이 아니라 릴리스 자동화 〔S53〕〔S52〕 |
| 코드 변경 | CodePipeline source(커밋·PR) → CodeBuild가 SageMaker 파이프라인 실행 | 〔S50〕〔S49〕 |
| 수동·파라미터 | `pipeline.start(parameters=...)` 또는 EventBridge 타깃의 정적·동적 파라미터 | 〔S43〕〔S46〕 |

- ML Lens의 재훈련 프레임워크 〔S65〕: ① 성능 지표 정의 ② Model Monitor로 모니터링(데이터 품질·모델 품질·편향 드리프트·특성 기여도 드리프트) ③ 재훈련 조건 정의(일정 주기, 임계 이하 성능 저하, 데이터 드리프트, 신규 훈련 데이터) ④ SageMaker Pipelines로 재훈련 파이프라인(전처리·특성·훈련·평가·배포, 배포 전 홀드아웃 검증 포함) ⑤ Model Registry 버전 관리 ⑥ 신규 데이터 자동 처리(S3 이벤트 → Lambda/Step Functions) ⑦ 오케스트레이션 ⑧ blue/green·canary 같은 배포 안전장치와 성능 저하 시 자동 롤백 ⑨ 정답 데이터를 모으는 피드백 루프 ⑩ 재훈련 프로세스 문서화.
- "필요할 때만 재훈련"(MLSUS06-BP02) 〔S78〕: KPI에서 임계값을 정하고, Model Monitor로 운영 모델을 평가하며, 임계 초과 시 울리는 CloudWatch 경보로 자동화된 파이프라인(SageMaker Pipelines·Step Functions·서드파티)을 시작하고, 재훈련 모델은 canary 같은 방식으로 배포한다.
- Pipelines 쪽 설계 〔S47〕: Model Monitor가 위반을 감지해 재훈련하는 경우 해당 검사 유형을 이전 baseline과 비교하지 않고(`skip_check=True`) 새 baseline을 모델 레지스트리에 갱신(`register_new_baseline=True`)할 수 있다.

> 🧠 원리: Model Monitor가 일정에 따라 실행되며 CloudWatch에 지표를 게시하고, 임계 초과 경보가 EventBridge 규칙을 거쳐 모델 구축 파이프라인을 시작한다. 같은 파이프라인은 일정 규칙으로도 시작할 수 있다 〔S73〕.

### 패턴 1. ML 워크플로 자동화에 어떤 서비스(조합)를 쓰는가

- 시나리오 단서: "전처리 → 훈련 → 평가 → 모델 등록을 자동화", "모델 구축 자동화", "운영 오버헤드 최소", "단계별 감사 추적·계보", "코드를 커밋하면 빌드·테스트·배포", "이미 Apache Airflow를 쓴다", "SageMaker 밖의 여러 AWS 서비스를 엮는다".
- 정답 방향: ML 단계의 DAG는 SageMaker Pipelines, 코드 변경에 따른 빌드·테스트·배포 릴리스는 CodePipeline(+CodeBuild, CodeDeploy 또는 CloudFormation), 두 층을 묶은 표준 구성은 SageMaker Projects 템플릿이다. 더 복잡한 오케스트레이션이나 SageMaker 밖 서비스 통합은 Step Functions, 기존 Airflow 자산은 MWAA를 고른다.
- 오답 유인(섞이는 선택지): CodePipeline만으로 훈련·평가·등록 같은 ML 단계를 오케스트레이션(CodePipeline 통합 목록에는 ML 단계 전용 액션이 없다), "ML 감사 추적"을 이유로 Step Functions 선택, 새로 시작하는 단순한 요구에 MWAA 도입.

### 패턴 2. 무엇이 파이프라인을 시작시키는가 (트리거 설계)

### 패턴 3. 점진 배포와 자동 롤백을 어떻게 구성하는가

- 시나리오 단서: "일부 트래픽(용량)에만 먼저 적용", "경보가 울리면 자동으로 이전 버전으로", "다운타임 없이", "대형 모델·인스턴스가 많아 용량이 모자람", "Lambda / ECS / EC2 / SageMaker 엔드포인트 중 어디에 배포하는가".

## 4. 흔한 함정·혼동 짝

### 짝 1. SageMaker Pipelines vs AWS CodePipeline

- 구분 기준: "ML 작업의 DAG"인가 "코드 릴리스 흐름"인가. 둘은 경쟁 관계가 아니라 SageMaker Projects 템플릿에서 함께 쓰인다 — CodePipeline이 코드 체크인마다 SageMaker 파이프라인을 실행한다.

| 구분 | SageMaker Pipelines | AWS CodePipeline |
|---|---|---|
| 다루는 대상 | ML 워크플로 단계(Processing·Training·Tuning·Transform·Condition·RegisterModel 등 18종) 〔S39〕〔S41〕 | 소프트웨어 릴리스 단계. 액션 유형 6종(source·build·test·deploy·approval·invoke) 〔S2〕 |
| 단계 연결 | 단계 출력 속성을 입력으로 넘기는 데이터 의존성이 DAG를 결정 〔S40〕 | 스테이지는 순서대로, 스테이지 안 액션은 `runOrder`로 직렬·병렬 〔S2〕 |
| 시작 | EventBridge 규칙·SDK·수동·일정 〔S46〕 | 소스 변경(이벤트·웹훅)·일정·수동 〔S4〕 |
| 산출물 | Model Registry의 모델 버전, 파라미터화된 실행 〔S40〕〔S43〕 | 빌드 아티팩트, 환경 배포 〔S2〕 |
| 연결 방법 | Projects 모델 구축 템플릿: CodePipeline의 build 단계가 SageMaker 파이프라인을 만들고 실행한 뒤 완료까지 대기 〔S50〕 | ML 단계 전용 액션 제공자는 통합 목록에 없음 〔S79〕 |

- 근거: 〔S39〕〔S2〕〔S49〕〔S50〕

### 짝 2. SageMaker Pipelines vs AWS Step Functions vs Amazon MWAA

- 구분 기준: ML 전용·감사 추적 중심이면 Pipelines, 더 복잡한 오케스트레이션이나 SageMaker 밖 서비스 통합이면 Step Functions, 기존 Apache Airflow 자산과 통합해야 하면 MWAA(Well-Architected ML Lens의 선택 기준).

| 구분 | SageMaker Pipelines | Step Functions | MWAA |
|---|---|---|---|
| 선택 기준 | ML 워크플로를 SDK로 만들고 Studio에서 관리, 모든 단계 자동 로깅 〔S64〕 | 더 복잡한 오케스트레이션 요건, SageMaker 밖 AWS 서비스 통합 〔S64〕 | 기존 Airflow 배포와 통합 〔S64〕 |
| 성격 | ML 개발 자동화용 목적 특화 서비스, 서버리스 오케스트레이션 〔S39〕 | SageMaker 인프라를 오케스트레이션하는 Python 다단계 ML 워크플로 〔S48〕 | 워크플로를 AWS 리소스에서 추상화하는 오픈 소스 선택지 〔S72〕 |
| 시작 | EventBridge 타깃 〔S46〕 | EventBridge 이벤트로 Step Functions 상태 머신 활성화 가능 〔S53〕 | 이 노트에서는 조사하지 않음 |

- 근거: 〔S64〕〔S48〕〔S72〕

### 짝 3. Canary vs Linear vs All-at-once (그리고 Rolling)

- 구분 기준: 트래픽(또는 용량)을 몇 단계로, 어떤 간격으로 옮기는가. 영향 범위를 줄일수록 두 환경이 병행하는 시간과 비용이 늘어난다.

| 방식 | 이동 방식 | 위험 | 시간·비용 | SageMaker 설정 | CodeDeploy 사전 정의 예 |
|---|---|---|---|---|---|
| All-at-once 〔S55〕〔S19〕 | 한 번에 전체 | 회귀 업데이트가 100% 트래픽에 영향 | 가장 빠르고 저렴 | `ALL_AT_ONCE`(기본) | `CodeDeployDefault.LambdaAllAtOnce` |
| Canary 〔S55〕〔S19〕 | 2단계: 작은 일부 → 나머지 | 영향 범위를 카나리로 한정 | 두 플릿이 전 기간 병행 | `CANARY` + `CanarySize`(50% 이하) | `LambdaCanary10Percent5Minutes` |
| Linear 〔S55〕〔S19〕 | n개의 균등 단계 | 가장 점진적 | 단계 수에 비례해 증가 | `LINEAR` + `LinearStepSize`(10~50%) | `LambdaLinear10PercentEvery1Minute` |
| Rolling 〔S55〕〔S19〕 | 배치 단위로 교체하며 이전 인스턴스 정리 | 배치 크기로 조절 | 필요 용량이 적음 | `RollingUpdatePolicy`(배치 5~50%) | EC2 in-place `HalfAtATime` / `OneAtATime` |

- 근거: 〔S55〕〔S56〕〔S59〕〔S62〕〔S19〕〔S26〕

### 짝 4. SageMaker 배포 가드레일 vs CodeDeploy 배포 구성

- 구분 기준: 배포 대상이 무엇인가(SageMaker 엔드포인트 vs EC2·Lambda·ECS)와 롤백이 어떻게 일어나는가(이전 플릿으로 트래픽 복귀 vs 이전 리비전 재배포).

| 구분 | SageMaker 배포 가드레일 | CodeDeploy 배포 구성 |
|---|---|---|
| 적용 대상 | 비동기·실시간 추론 엔드포인트 〔S54〕 | EC2/온프레미스·Lambda·ECS(SageMaker 엔드포인트는 해당 없음) 〔S20〕 |
| 구성 지정 | `UpdateEndpoint`/`CreateEndpoint`의 `DeploymentConfig` 〔S54〕〔S60〕 | 사전 정의 구성 이름 또는 사용자 지정 구성(Lambda·ECS는 사용자 지정 canary·linear 가능) 〔S19〕 |
| 롤백 트리거 | `AutoRollbackConfiguration`의 CloudWatch 경보 + 베이킹 기간 〔S61〕〔S55〕 | 배포 그룹의 자동 롤백 설정: 배포 실패 또는 모니터링 임계 충족 〔S23〕 |
| 롤백 방식 | 트래픽을 이전 플릿(blue)으로 복귀 〔S55〕 | 마지막 정상 리비전을 새 배포로 재배포 〔S23〕〔S24〕 |
| 비용 특성 | 다단계·베이킹이면 업데이트 기간 동안 두 플릿 과금 〔S55〕 | — |

- 근거: 〔S54〕〔S20〕〔S19〕〔S23〕〔S61〕

### 짝 5. Gitflow vs GitHub Flow (vs Trunk)

- 구분 기준: 팀 규모, 릴리스 주기(예정된 릴리스 vs 지속 배포), 규정 준수 요구. 복잡도는 Trunk < GitHub Flow < Gitflow.

| 구분 | Gitflow | GitHub Flow | Trunk |
|---|---|---|---|
| 브랜치 | 영구 `main`·`develop` + `feature`·`release`·`hotfix` 〔S35〕 | 단명 `feature` 브랜치 + `main` 〔S32〕 | 단일 trunk(main) 〔S34〕 |
| 배포 | develop에 기능이 모이면 release 브랜치로 상위 환경 배포 〔S30〕 | main에 병합되는 즉시 배포 〔S32〕 | 항상 릴리스 가능 상태를 유지하며 자주 통합 〔S34〕 |
| 적합 | 크고 분산된 팀, 엄격한 릴리스·규정 준수, 여러 프로덕션 버전 동시 유지 〔S31〕 | 작고 성숙한 팀, 지속적 전달 〔S33〕 | 자동 테스트·CI에 의존 〔S34〕 |
| 부적합 | 지속적 전달 지향 조직, 장수 release 브랜치의 기술 부채 〔S31〕 | 엄격한 규정 준수·릴리스 절차가 있는 팀, 잦은 병합 충돌 〔S33〕 | — |
| 파이프라인(정리) | 브랜치별 파이프라인, CodePipeline V2 브랜치 필터 + QUEUED 〔S35〕 | main push → 배포, PR 이벤트 → 사전 검증 〔S2〕 | main push → 배포 |

- 근거: 〔S28〕〔S29〕〔S30〕〔S31〕〔S32〕〔S33〕〔S34〕〔S35〕

### 짝 6. 일정 기반 vs 이벤트 기반 vs 드리프트 기반 재훈련 (그리고 EventBridge Scheduler vs 예약 규칙)

- 구분 기준: 재훈련을 "언제 필요한지"를 시간이 정하는가(일정), 데이터가 정하는가(새 데이터 도착), 성능이 정하는가(드리프트·임계 위반). ML Lens는 성능·데이터 패턴과 무관한 고정 일정 재훈련을 안티패턴으로 본다.

| 방식 | 구성 | 언제 | 주의 |
|---|---|---|---|
| 일정 | EventBridge Scheduler(권장) 또는 예약 규칙(레거시) → 파이프라인 | 비즈니스 요건상 정해진 주기 | 고정 일정만 쓰면 안티패턴 〔S65〕〔S71〕 |
| 이벤트(데이터) | S3 EventBridge 알림 → `Object Created` 규칙 → 파이프라인·Glue 워크플로·Lambda/Step Functions | 새 훈련 데이터가 도착 | 〔S69〕〔S46〕〔S70〕〔S65〕 |
| 드리프트·성능 | Model Monitor → CloudWatch 지표·경보 → EventBridge 규칙 → 파이프라인 | 임계 초과·위반 | ⚠️ Model Monitor 신규 고객 중단 〔S73〕〔S74〕 |

- 근거: 〔S65〕〔S71〕〔S46〕〔S73〕〔S69〕

### 짝 7. CodePipeline V1 vs V2 (그리고 실행 모드 SUPERSEDED / QUEUED / PARALLEL)

- 구분 기준: 트리거 필터(Git 태그·PR·브랜치·파일 경로), 파이프라인 수준 변수, PARALLEL·QUEUED 실행 모드, 스테이지 롤백·조건·자동 재시도, Commands 액션이 필요하면 V2.

| 구분 | V1 | V2 |
|---|---|---|
| 용도 〔S3〕 | 표준 배포 | 런타임 변수로 구성하는 배포, Git 태그로 시작하는 배포 〔S3〕 |
| 실행 모드 〔S3〕 | SUPERSEDED만 | SUPERSEDED(기본)·QUEUED·PARALLEL 〔S3〕〔S2〕 |
| SUPERSEDED 〔S3〕 | 더 최근 실행이 대기 중 실행을 추월 | 동일 〔S2〕 |
| QUEUED 〔S3〕 | 미지원 | 실행이 대기하며 순서대로 처리 〔S35〕 |
| PARALLEL 〔S3〕 | 미지원 | 실행이 서로 독립 〔S35〕 |

- 근거: 〔S3〕〔S2〕〔S35〕〔S4〕

### 짝 8. 모델 품질 게이트(Condition 단계) vs Model Registry 승인 vs CodePipeline 수동 승인·스테이지 조건

- 구분 기준: 누가(자동 규칙/사람) 어느 지점(평가 직후/레지스트리/스테이징→프로덕션)에서 흐름을 막거나 여는가.

| 게이트 | 판정 주체 | 위치 | 효과 |
|---|---|---|---|
| Pipelines `Condition` 단계 | 파이프라인이 평가 지표로 자동 판정 | 평가 단계 직후 | 거짓 분기(예: `Fail`)로 실행 중단 〔S41〕〔S40〕 |
| Model Registry 승인 상태 | 사람 또는 Condition 단계가 상태 갱신 | 레지스트리 | `Approved` 전이가 CI/CD 배포를 시작 〔S52〕 |
| CodePipeline 수동 승인 액션 | 사람 | 스테이징과 프로덕션 사이 | 승인 대기(기본 타임아웃 있음) 〔S1〕〔S50〕 |
| CodePipeline 스테이지 조건(V2) | 규칙(예: `CloudWatchAlarm`) | 스테이지 진입·성공·실패 | 스테이지 실패 또는 롤백 〔S2〕〔S3〕 |

- 근거: 〔S41〕〔S52〕〔S2〕〔S50〕

### 짝 9. CodeBuild S3 캐시 vs 로컬 캐시 (그리고 EC2 vs Lambda 컴퓨트)

- 구분 기준: 캐시가 여러 빌드 호스트에 공유되는가(S3), 한 빌드 호스트에만 있는가(로컬). 컴퓨트는 유연성(EC2) vs 빠른 시작과 자동 확장(Lambda).

| 구분 | Amazon S3 캐시 | 로컬 캐시 |
|---|---|---|
| 공유 범위 | S3 버킷, 여러 빌드 호스트가 사용 〔S80〕 | 해당 빌드 호스트만 〔S80〕 |
| 알맞은 경우 | 빌드보다 내려받기가 더 싼 산출물, 큰 산출물은 전송 시간이 부담 〔S80〕 | 큰 산출물(즉시 사용 가능) 〔S80〕 |
| 모드 | buildspec `cache`(`key`·`fallback-keys`·`action`) 〔S12〕 | source cache·Docker layer cache(Linux 전용, privileged 필요)·custom cache 〔S14〕 |

| 컴퓨트 | 특징 |
|---|---|
| EC2 | 유연성에 최적화. 온디맨드(`BUILD_GENERAL1_*`) 또는 예약 용량 플릿 〔S13〕 |
| AWS Lambda | 시작 지연이 낮아 빠르고 자동 확장(대기열 없음). `on-failure` 속성은 미지원 〔S13〕〔S12〕 |

- 근거: 〔S80〕〔S14〕〔S12〕〔S13〕

## 9. 확인 필요 항목

- [G-3.3-1] SageMaker Projects의 CodeCommit 템플릿 종료 시점이 두 공식 문서에서 다르다 — 프로젝트 개요 문서(S49)는 "2024-09-09부터 CodeCommit 저장소를 쓰는 템플릿은 지원하지 않는다", 템플릿 문서(S50)는 "2024-10-28에 CodeCommit 템플릿이 제거되었다"고 적는다 — 학습문서·문항에는 정확한 일자를 정답 근거로 쓰지 말고 "2024년 가을부터 신규 프로젝트는 서드파티 Git 템플릿을 쓴다"로 서술한다.
- [G-3.3-2] CodeCommit이 2025-11-25부터 신규 고객을 다시 받기 시작했는데(S38) SageMaker Projects의 CodeCommit 템플릿이 복원되었는가 — S49·S50에서 복원 언급을 찾지 못했다 — 복원 여부를 단정하지 말고, CodeCommit 재개(S38)와 템플릿 제거(S49·S50)를 별개 사실로 병기한다.
- [G-3.3-3] Well-Architected ML Lens(S64·S65)가 권하는 "AWS Step Functions Data Science SDK"의 현재 지원 상태 — ML Lens 원문은 계속 언급한다. 해당 SDK의 GitHub 저장소 첫 화면에서는 보관(archive)·지원 중단 표시를 찾지 못했으나(웹 요약 도구 확인이라 신뢰도 낮음) 공식 수명 공지는 찾지 못했다 — Step Functions 서비스 자체만 다루고 이 SDK를 정답 근거로 쓰지 않는다.
- [G-3.3-4] SageMaker Pipelines · Step Functions · MWAA · CodePipeline을 직접 비교하는 공식 표가 있는가 — 없었다. S48(SageMaker AI Workflows 개요), S64(ML Lens MLOPS04-BP01), S72(MWAA FAQ)만 확인했다 — 2.11 비교표는 "(정리)"임을 학습문서에 밝히고, 문항 정답 근거는 ML Lens의 선택 문장(Pipelines: SDK·감사 추적 / Step Functions: 더 복잡하거나 SageMaker 밖 통합 / MWAA: 기존 Airflow 통합)으로 한정한다.
- [G-3.3-5] CodePipeline에 SageMaker 파이프라인을 직접 실행하는 전용 액션 제공자가 있는가 — S79의 통합 목록(Source·Build·Test·Deploy·Approval·Invoke의 제공자 제목 전체)에서 SageMaker 전용 항목을 찾지 못했다. 부재 자체는 공식 문장으로 인용할 수 없다 — "전용 액션이 없다"를 단정 사실로 쓰지 말고, SageMaker Projects 템플릿이 CodeBuild 단계(S50)로 파이프라인을 만들고 실행·대기한다는 문서 내용만 쓴다.
- [G-3.3-6] SageMaker Pipelines 단계 문서(S41)의 단계 목록(18종)에는 없는데 본문 목차에는 "Fine-tuning step" 절이 있다 — 해당 절의 내용은 조사하지 않았다 — 학습문서는 목록의 18종을 기준으로 삼고 Fine-tuning 단계를 문항 소재로 쓰지 않는다.
- [G-3.3-7] CodeBuild 동시 빌드 기본 쿼터 — S11의 표는 대부분 1(Linux GPU는 0)로 보이는데 같은 페이지 주석은 "기본값은 내부 지표로 정해지며 일부 플랫폼·컴퓨트 유형은 기본이 20"이라고 적어 서로 맞지 않는다 — 구체 동시 빌드 수를 문항·학습문서에 쓰지 말고 "컴퓨트 유형별로 다르며 증액 요청 가능"만 서술한다(GPU Small 0은 표에서 직접 인용했다).
- [G-3.3-8] 쿼터 수치(S1·S11·S18)는 리전별이고 항목마다 증액 가능 여부가 다르며 바뀔 수 있다 — 수치를 암기시키는 문항은 피하고 "증액 가능 / 고정(예: 폴링 파이프라인 상한)" 구분과 서비스 간 대소 관계 중심으로 출제한다.
- [G-3.3-9] 일정 기반 시작을 안내하는 문서가 서로 다르다 — CodePipeline 일정 문서(S77)는 EventBridge 규칙(Schedule), SageMaker Python SDK 일정(S46)은 EventBridge Scheduler 서비스 주체(`scheduler.amazonaws.com`)를 쓰고, EventBridge 문서(S71)는 예약 규칙을 레거시로 분류하며 Scheduler를 권장한다 — 문항 정답은 "EventBridge(Scheduler 또는 규칙)"로 열어 두고 한쪽을 오답으로 단정하지 않는다.
- [G-3.3-10] 명칭 불일치 — SageMaker 프로젝트 문서(S50)는 아직 "AWS CodeStar connection"이라 쓰는데 서비스는 2024-03-29에 AWS CodeConnections로 개명되었다(S9) — 학습문서는 "AWS CodeConnections(구 CodeStar Connections)"로 병기한다.
- [G-3.3-11] Model Monitor·Clarify의 신규 고객 중단(S74·S75)이 Pipelines의 `QualityCheck`·`ClarifyCheck` 단계(각각 Model Monitor·Clarify 컨테이너 사용, S41)에 미치는 영향 — 확인한 범위(두 단계 절의 앞부분과 baseline 수명 주기 문서 S47)에는 중단 공지 문구가 없고 단계 자체의 향후 지원 변화도 확인하지 못했다 — 시험 범위 기능이므로 다루되 ⚠️를 병기하고 "신규 고객에게 닫힌 기능에 의존한다"까지만 쓴다.
- [G-3.3-12] Model Monitor 위반 → CloudWatch 경보 → EventBridge 규칙 → 파이프라인 시작이라는 전체 체인을 한 공식 문서가 서술하는가 — 찾지 못했다. 체인은 블로그(S73)와 공식 문서의 조각(S65: CloudWatch 경보로 재훈련 워크플로 실행, S46: 드리프트로 인한 엔드포인트 상태 변화가 EventBridge 이벤트 예)의 조합이다 — 학습문서에 체인을 쓸 때 블로그 출처임을 밝히고, 문항에서는 "경보 → EventBridge → 파이프라인" 구조를 정답 방향으로만 쓴다.
- [G-3.3-13] 블로그 근거 3건(S35 CodePipeline 브랜치 기반 개발, S73 드리프트 재훈련, S80 CodeBuild 캐시 전략)은 공식 문서가 아니다 — 정답을 확정하는 유일한 근거로 쓰지 않고 공식 문서(S2·S3·S4 / S65·S78 / S14)와 병용한다.
- [G-3.3-14] Amazon MWAA의 트리거·스케줄링 방식(센서 등)은 조사하지 않았다 — 가이드 Skill이 MWAA를 직접 요구하지 않고 이 Task의 질문이 선택 기준 비교로 한정되어 S64·S72의 선택 기준 문장만 사용했다 — 필요하면 MWAA 사용자 가이드를 추가로 확인한다.
- [G-3.3-15] EC2/온프레미스의 all-at-once 표기가 두 공식 문서에서 달라 보인다 — DevOps 백서 매트릭스(S27)는 Canary·Linear·All-at-once를 EC2/온프레미스에서 지원하지 않는다고 표시하는데, CodeDeploy 배포 구성 문서(S19)는 EC2/온프레미스 사전 정의 구성으로 `CodeDeployDefault.AllAtOnce`를 나열한다 — 이 노트는 매트릭스의 all-at-once를 Lambda·ECS의 트래픽 이동 구성(canary·linear·all-at-once)으로, EC2/온프레미스의 `AllAtOnce`·`HalfAtATime`·`OneAtATime`을 최소 정상 호스트 기반의 배포 속도 구성으로 읽었으나 이 구분을 명시한 공식 문장은 찾지 못했다 — 문항에서는 "EC2/온프레미스에는 canary·linear 트래픽 이동이 없다"까지만 정답 근거로 쓴다.
