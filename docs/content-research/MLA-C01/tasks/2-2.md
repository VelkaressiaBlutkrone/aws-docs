### 2.1 훈련 프로세스의 요소 — 에포크·반복(스텝)·배치 크기·학습률 (K1)

SageMaker 공식 문서는 분산 훈련 개념 절에서 훈련 용어를 정의한다〔S1〕. 공식 ko_kr 문서(기계 번역이며 영문 우선)는 epoch를 '에포크', iteration을 '반복', global batch size를 '글로벌 배치 크기', per-replica batch size를 '복제본별 배치 크기', micro-batch를 '마이크로 배치'로 옮긴다〔S85〕.

| 용어 | 공식 문서의 정의(요지) | 관계·주의 | 근거 |
|---|---|---|---|
| 에포크(epoch) | 전체 데이터셋을 한 번 통과하는 훈련 주기 (F1) | 한 에포크 안에 여러 반복이 들어가는 것이 일반적. 에포크 수는 모델·사용 사례마다 다름 | 〔S1〕 |
| 반복(iteration) | 글로벌 배치 크기의 미니 배치로 수행하는 순방향·역방향 패스 1회 (F2) | 반복 수 = (샘플 수 ÷ 글로벌 배치 크기) × 에포크 수. 예: 샘플 5,000개·배치 500이면 에포크당 10회 (F3) | 〔S1〕 |
| 스텝(step) | 영문 가이드의 steps. SageMaker 문서의 정의 용어는 iteration이고, Bedrock 이미지 모델은 `stepCount`(각 배치에 모델이 노출되는 횟수)를 별도 하이퍼파라미터로 둠 (F14) | 문서가 steps=iteration이라고 명시한 문장은 확인하지 못함 (G-2.2-9) | 〔S1〕〔S73〕 |
| 글로벌 배치 크기(= 미니 배치) | 매 반복에서 클러스터의 GPU로 보내는 레코드 수이자 그래디언트를 계산하는 레코드 수 | 데이터 병렬이면 복제본 수 × 복제본별 배치 크기 (F4) | 〔S1〕 |
| 복제본별 배치 크기 | 데이터 병렬에서 각 모델 복제본이 받는 레코드 수 | 각 복제본이 순방향·역방향으로 가중치 갱신을 계산한 뒤 복제본 간에 평균(동기화)하고 다음 배치로 진행 | 〔S1〕 |
| 마이크로 배치 | 미니 배치(하이브리드면 복제본별 배치)의 부분집합 | SMP가 파이프라인에 하나씩 투입하고 실행 순서는 라이브러리 런타임이 정의 | 〔S1〕 |
| 학습률 | 계산된 오차에 대해 가중치를 얼마나 바꿀지에 영향을 주는 변수 (F5) | 수렴 능력·수렴 속도·최적성에 중요 | 〔S1〕 |
| 하이퍼파라미터 | 훈련 과정 자체를 지배하는 구성 변수 (F138) | 모델 파라미터는 훈련 중 학습되는 값 | 〔S46〕 |

> 🧠 원리: 미니 배치 SGD는 미니 배치의 각 레코드로 오차와 그래디언트를 구한 뒤 평균 그래디언트로 각 계수의 갱신 방향을 정한다. 레코드 사이의 통신이 최종 평균뿐이라 미니 배치 처리는 병렬화·분산에 적합하다. 다만 그 평균을 모든 워커와 주고받는 allreduce 단계가 클러스터가 커질수록 늘어나는 오버헤드가 된다 (F27). 〔S1〕

**같은 개념, 다른 파라미터 이름** — 시험 지문은 서비스마다 다른 이름을 쓴다.

| 대상 | 에포크 | 배치 크기 | 학습률 | 근거 |
|---|---|---|---|---|
| Linear Learner | `epochs` — 훈련 데이터에 대한 최대 패스 수 | `mini_batch_size` — 데이터 이터레이터의 미니 배치당 관측치 수 | `learning_rate` — 옵티마이저의 파라미터 갱신 보폭 | 〔S27〕 |
| Image Classification | `epochs` | `mini_batch_size` — 멀티 GPU면 GPU마다 mini_batch_size÷GPU 수 (F13) | `learning_rate`(초기 학습률), `lr_scheduler_step`으로 지정한 에포크에서 감소 | 〔S29〕 |
| XGBoost | `num_round` — 훈련 라운드 수(필수 값. 에포크 대신 부스팅 라운드) | — | `eta` — 업데이트의 보폭 축소(과적합 방지) | 〔S25〕 |
| JumpStart 파운데이션 모델 미세 조정 | `epoch` | `per_device_train_batch_size` | `learning_rate` | 〔S67〕 |
| Amazon Bedrock 사용자 지정 | `epochCount` | `batchSize`(모델별로 범위가 다르고 일부는 고정) | `learningRate`, `learningRateWarmupSteps`(Claude 3는 `learningRateMultiplier`) | 〔S73〕 |

**배치 크기·학습률·에포크가 수렴·메모리·속도에 미치는 영향** (문서에 있는 내용만)

| 요소 | 수렴 | 메모리 | 속도·비용 | 근거 |
|---|---|---|---|---|
| 배치 크기 | 분산에서 노드를 늘리면 배치 크기도 비례해서 늘리고, 수렴 속도를 위해 학습률도 올림(선형 스케일링 규칙 — 미니 배치가 k배면 학습률도 k배) (F9, F10). 배치 정규화가 있는 모델은 GPU당 배치가 지나치게 작아지면 단일 노드에서 본 수렴이 깨질 수 있음 (F12) | 메모리에 맞을 때까지 배치를 줄이고, 1에서도 부족하면 모델 병렬로 전환 (F11). 모델이 크면 GPU 메모리 한계로 GPU당 배치가 작아져 효율이 떨어짐 (F34) | 데이터 병렬은 미니 배치 크기를 키우고 각 미니 배치를 더 빨리 처리하는 전략〔S1〕. 미니 배치 SGD는 설계상 훈련 시간이 데이터셋 크기에 이론상 선형〔S1〕 | 〔S2〕〔S3〕〔S7〕 |
| 학습률 | 0.01은 훨씬 작은 조정이라 수렴이 오래 걸릴 수 있고, 0.1은 훨씬 커서 오버슈트할 수 있음 (F6, F7). 학습률을 올려 수렴을 앞당기는 것은 덜 바람직함 (F8). 급격한 증가를 막으려고 학습률을 점진적으로 올리는 워밍업을 사용 | — | Bedrock은 워밍업 스텝 수를 별도 하이퍼파라미터로 노출하며 훈련 샘플이 적으면 큰 워밍업 값을 피하라고 권고 | 〔S70〕〔S73〕〔S3〕 |
| 에포크 | Bedrock: 큰 데이터셋은 더 적은 에포크, 작은 데이터셋은 더 많은 에포크로 수렴 (F182). 과소적합이면 에포크(패스)를 늘림 (F92) | — | Bedrock 훈련 비용은 처리 토큰 수(훈련 말뭉치 × 에포크)에 비례 (F179, F180) | 〔S73〕〔S51〕〔S72〕 |

### 2.2 훈련 시간 단축 ① — 조기 중지 (K2)

'조기 중지(early stopping)'는 문서마다 층위가 다른 서로 다른 장치를 가리켜 시험 보기에서 이름이 같아 헷갈린다. 층위부터 구분한다. (공식 ko_kr 문서는 같은 페이지 안에서 '조기 중지'와 '초기 중지'를 섞어 쓴다〔S87〕. 가이드의 표기는 '조기 중지'다.)

| 층위 | 설정 | 동작 | 제약·주의 | 근거 |
|---|---|---|---|---|
| ① 알고리즘 내부(단일 훈련 작업) | XGBoost `early_stopping_rounds`; Linear Learner `early_stopping_patience`·`early_stopping_tolerance`; Image Classification `early_stopping`(기본 False)·`early_stopping_min_epochs`·`early_stopping_patience`·`early_stopping_tolerance`; Bedrock Claude 3 등 `earlyStoppingThreshold`·`earlyStoppingPatience` (F21–F23) | 검증 지표가 patience 동안 개선되지 않으면 해당 훈련 작업을 종료. XGBoost는 호스팅 시 최적 모델을 사용 | 알고리즘·모델마다 파라미터 이름이 다름. Linear Learner는 검증 데이터가 없으면 훈련 데이터의 `loss`로 평가 | 〔S25〕〔S27〕〔S29〕〔S73〕 |
| ② AMT 튜닝 작업 수준 | `TrainingJobEarlyStoppingType`=`AUTO`(SDK `early_stopping_type='Auto'`, 콘솔 Early stopping=Auto). API 기본값은 OFF (F20) | 각 에포크 후 목표 지표를 이전 훈련 작업들의 같은 에포크까지 이동 평균의 중앙값과 비교해 더 나쁘면 해당 훈련 작업을 중단 (F15) | 에포크마다 목표 지표를 내는 알고리즘만 가능 (F16). 지원 내장 알고리즘 목록은 2018-12-13 기준 (F17). Linear Learner는 `objective_loss`를 목표 지표로 쓸 때만. PyTorch·Spark는 훈련 코드에서 에포크마다 지표를 로그로 기록해야 함. 다중 알고리즘 튜닝에서는 사용 불가 (F127) | 〔S35〕〔S41〕〔S42〕 |
| ③ Hyperband 내부 | `Strategy`=`Hyperband` | 중간·최종 결과로 자원을 재할당하고 부진한 구성을 자동 중지 (F104) | `TrainingJobEarlyStoppingType`은 OFF여야 함 (F19). 반복형 알고리즘에만 (F105) | 〔S33〕 |
| ④ Debugger 규칙(참고) | Debugger 내장 규칙 기반 중지 | — | ⚠️ SageMaker Debugger는 신규 고객 중단 (F60). 규칙 상세는 Task 2.3 소관이라 여기서는 상태만 | 〔S20〕 |

> 🧠 원리: AMT 조기 중지는 '다른 훈련 작업들과의 상대 비교'다. 같은 에포크까지의 이전 작업 지표(이동 평균)의 중앙값보다 현재 작업이 나쁘면 끊는다 (F15). 알고리즘 내부 조기 중지는 '자기 자신의 검증 지표 추이'(patience)로 끊는다. Hyperband는 여기에 더해 살아남는 구성에 에포크를 재할당한다. 〔S35〕〔S33〕

효과는 컴퓨트 시간 절감과 과적합 회피다 (F18). AWS 개념 페이지도 조기 중지를 모델이 노이즈를 학습하기 전에 훈련을 멈추는 것으로 설명하되, 시점을 잘못 잡으면 여전히 부정확하다고 경고한다〔S51〕.

### 2.3 훈련 시간 단축 ② — 분산 훈련: 데이터 병렬(SMDDP) vs 모델 병렬(SMP) (K2)

SageMaker AI의 분산 훈련 라이브러리는 데이터 병렬용과 모델 병렬용 두 가지다. 공식 ko_kr 표기는 '데이터 병렬화'·'모델 병렬화'다〔S85〕. PyTorch DDP, `torchrun`, MPI(`mpirun`), 파라미터 서버 같은 다른 분산 프레임워크도 쓸 수 있다〔S1〕.

| 구분 | 데이터 병렬 — SMDDP(SageMaker AI distributed data parallelism library) | 모델 병렬 — SMP v2(SageMaker model parallelism library v2) |
|---|---|---|
| 정의 | 훈련 데이터를 클러스터의 여러 GPU로 나누고, 각 GPU가 모델 복제본을 가진 채 서로 다른 배치를 처리한 뒤 가중치 갱신을 공유·동기화하고 다음 배치로 진행〔S1〕 | 모델 자체를 클러스터의 여러 GPU로 분할. 각 GPU가 모델의 일부를 담고 데이터가 그 사이를 흐름〔S1〕 |
| 언제 | 큰 데이터셋을 쓰고 모델이 단일 GPU에 들어갈 때 (F24, F37) | 모델이 단일 디바이스에 안 맞을 때, 또는 모델 크기 때문에 큰 배치를 못 쓰고 작고 비효율적인 배치를 강요받을 때 (F25, F26, F37) |
| 핵심 제약 | 모델과 레코드 한 개는 디바이스 하나에 들어가야 함〔S1〕. allreduce 오버헤드가 클러스터 확장에 따라 증가 (F27). 지원 인스턴스는 ml.p3dn.24xlarge·ml.p4d.24xlarge·ml.p4de.24xlarge (F29). TensorFlow 지원 중단 (F30) | v1 문서는 보관(Archived)되고 현행은 v2 (F31). v2는 PyTorch FSDP API와 정렬. 모델 분할 방식과 실행 일정에 따라 GPU 활용도·훈련 시간이 크게 달라짐〔S1〕〔S6〕 |
| 구성 요소 | `AllReduce`(그래디언트 동기화)와 `AllGather`를 AWS 네트워크·인스턴스 토폴로지에 맞게 최적화 (F28)〔S5〕 | 하이브리드 샤딩 데이터 병렬, 전문가 병렬(MoE), 텐서 병렬, 활성화 체크포인트·오프로딩 등〔S6〕〔S7〕. 혼합 정밀도(FP16/BF16, P5의 FP8)도 기본 지원〔S9〕 |
| 메모리 산정 | — | 혼합 정밀도(FP16/BF16)와 Adam이면 파라미터당 약 20바이트 → 100억 파라미터는 최소 200GB (F32). 메모리 풋프린트는 파라미터 수에 비례 (F33) |
| 헷갈리는 짝 | 샤딩 데이터 병렬(sharded data parallelism)은 모델 상태(파라미터·그래디언트·옵티마이저 상태)를 데이터 병렬 그룹 안에서 쪼개는 메모리 절감 기법이며 SMP v2가 제공〔S7〕 | 하이브리드 = 모델 병렬 + 데이터 병렬 조합〔S2〕 |

**문서가 권하는 선택 순서** 〔S2〕〔S17〕
1. 큰 데이터셋이면 데이터 병렬부터 시작 (F24).
2. 훈련 중 메모리가 부족하면 먼저 모델 하이퍼파라미터 변경, 배치 크기 축소(1로 줄여도 부족하면 모델 병렬), 그래디언트 압축(FP16·INT8)과 혼합 정밀도, 입력 크기 축소(NLP 시퀀스 길이·이미지 해상도)를 시도하고, 그래도 안 되면 모델 병렬 또는 하이브리드로 전환 (F25).
3. 모델이 단일 디바이스에 안 맞으면 처음부터 모델 병렬 (F26).
4. ML Lens도 같은 기준: 모델이 단일 GPU에 들어가면 데이터 병렬로 처리 속도를 높이고, 안 들어가면 모델 병렬 (F37).

**함정**
- 인스턴스를 늘려도 항상 빨라지지 않는다. 클러스터 크기가 커지면 노드 간 통신이 오버헤드가 되어 오히려 느려질 수 있고〔S1〕, 단순한 모델은 큰 인스턴스에서 추가 컴퓨트를 못 쓰거나 GPU 통신 오버헤드로 더 느려질 수 있다 (F38).
- SMDDP는 다중 노드에서 효과가 크다 (F35). 훈련 중 CPU 라이브러리로 전처리하면 AllReduce도 CPU를 쓰므로 CPU 병목이 생길 수 있어, 전처리를 훈련 전에 끝내거나 GPU 기반으로 옮기라고 권한다〔S3〕. 다중 노드에서는 FSx for Lustre를 권장 (F36).
- 반복적 대규모 파운데이션 모델 훈련용으로는 SageMaker HyperPod의 영속 클러스터가 ML Lens에서 언급된다〔S17〕 (범위 밖, 한 줄).
- 내장 알고리즘은 자체적으로 여러 인스턴스·GPU 병렬화를 제공한다〔S22〕. XGBoost는 CPU 분산 훈련에서 입력을 인스턴스 수 이상의 파일로 나누고 `ShardedByS3Key`를 쓰며, GPU 분산 훈련은 Dask(`use_dask_gpu_training`)를 쓰고 CSV·Parquet만 지원하며 Pipe 모드에서는 실패한다〔S24〕.

> 🧠 원리: 데이터 병렬은 '모델은 같고 데이터만 나눠' 각 워커가 계산한 그래디언트를 평균(allreduce)해 같은 가중치를 유지한다. 그래서 모델 + 레코드 1개가 한 디바이스에 들어가야 하고, 워커가 늘수록 평균 단계의 통신 비용이 커진다 (F27). 모델 병렬은 '데이터는 같고 모델을 나눠' 메모리 한계를 넘지만, 순진하게 층을 나누면 한 시점에 한 GPU만 계산해 활용도가 떨어지므로 파이프라인 실행 일정으로 보완한다. 〔S1〕〔S2〕

| (증류) | 증류(distillation) | 작은 모델이 큰 모델의 성능을 모방하도록 훈련 (F68) | 비용·지연 감소 | Bedrock 모델 증류: 교사 → 학생 (F175) | 〔S56〕〔S72〕 |
| 특성 선택 업데이트 | 특성 선택(feature selection) | 가장 중요한 특성만 남기고 무관한 특성을 제거. AWS 개념 페이지는 이를 pruning이라고도 부름 (F75) | 모델 복잡도·과적합 감소 | PCA: 데이터셋의 특성 수(차원)를 줄이는 내장 알고리즘 (F74) | 〔S51〕〔S23〕 |
| (참고) 컴파일 | SageMaker Neo | Task 3.1 소관. Neo는 FP32 또는 INT8/FP16으로 양자화된 파라미터의 모델을 최적화 (F76) | | | 〔S58〕 |

⚠️ **용어 충돌**: 한국어 가이드의 '정리'는 영문 pruning이며 모델 압축 맥락(가중치·파라미터 제거)이다. 그런데 AWS 'What is Overfitting?' 페이지는 '특성 선택 — 또는 pruning'이라 부른다 (F75, G-2.2-12). 보기에서 pruning이 나오면 '무엇을 제거하는가(가중치·파라미터 vs 특성)'로 구분한다.

> 🧠 원리: 양자화는 FP32·FP16/BF16 같은 고정밀 표현을 FP8·4비트 같은 저정밀 표현으로 바꿔 (1) 메모리 풋프린트, (2) 추론 단계마다 옮겨야 하는 데이터량(메모리 대역폭), (3) 연산 지연을 함께 줄인다. 대가는 품질 저하 가능성이다. 〔S57〕

### 2.6 정규화와 과적합·과소적합·치명적 망각 (K5, SK6)

정규화(regularization)의 목적은 모델이 훈련 예제를 일반화하지 않고 암기(과적합)하지 않도록 극단적인 가중치에 패널티를 주는 것이다〔S48〕. AWS 개념 페이지는 정규화를 '과적합을 줄이려는 훈련·최적화 기법의 모음'으로 소개하고 L1(Lasso: 가중치 절댓값에 패널티)·L2(Ridge: 가중치 제곱에 패널티)·드롭아웃을 나열한다〔S51〕. ⚠️ L1/L2 효과를 가장 또렷하게 설명한 공식 문장은 레거시 Amazon Machine Learning 문서(서비스 신규 사용자 중단)에 있다 (F64, G-2.2-14).

| 기법 | 효과(공식 문서 표현) | SageMaker·Bedrock 파라미터 | 헷갈리는 것 | 근거 |
|---|---|---|---|---|
| L1 | 작은 가중치를 0으로 밀어 사용 특성 수를 줄임 → 희소(sparse) 모델·노이즈 감소 (F77) | Linear Learner `l1`(쓰지 않으려면 0) (F79); XGBoost `alpha`(키울수록 모델이 보수적) (F81) | L2와 달리 가중치를 0으로 만들어 특성 선택 효과가 남 | 〔S48〕〔S27〕〔S25〕 |
| L2 | 전체 가중치를 작게 만들고 특성 간 상관이 높을 때 가중치를 안정화 (F78) | Linear Learner `wd`(weight decay = L2 정규화 파라미터) (F80); XGBoost `lambda` (F82) | 가중치 감쇠(weight decay)와 L2: Linear Learner 문서는 동일시하고 Nova 글도 'weight decay applies L2'라 설명 (F84). 단 Image Classification `weight_decay`는 sgd·nag에만 적용 (F83) | 〔S48〕〔S27〕〔S25〕〔S29〕〔S52〕 |
| 드롭아웃 | 신경망 전용. 훈련 중 무작위 뉴런을 비활성화해 특정 뉴런에 의존하지 않게 함 (F85) | JumpStart LoRA `lora_dropout`〔S67〕; XGBoost 트리용 `rate_drop` (F86) | 신경망 기법이라 선형 모델(Linear Learner)에는 해당 없음 | 〔S51〕〔S67〕〔S25〕 |
| 조기 중지 | 모델이 노이즈를 학습하기 전에 훈련을 멈춤 | 2.2의 알고리즘 내부·AMT·Hyperband | 시점을 잘못 잡으면 여전히 부정확 | 〔S51〕〔S35〕 |
| 특성 선택(= pruning) | 중요한 특성만 남기고 무관한 특성 제거 → 모델 유연성 감소 (F75) | PCA(차원 축소) (F74) | 모델 압축의 가중치 pruning과 다른 용법 | 〔S51〕〔S23〕 |
| 데이터 증강 | 샘플을 조금씩 변형(이동·뒤집기·회전)해 과도하게 특정한 특성을 배우지 않게 함 | Image Classification `augmentation_type`(`crop`·`crop_color`·`crop_color_transform`) | | 〔S51〕〔S29〕 |
| 앙상블 | 약한 학습자들을 결합해 더 정확한 결과 | 2.13 | | 〔S51〕 |
| 데이터 양 확보 | 성능이 나쁠 때 하이퍼파라미터 조정 전에 데이터 양 부족부터 배제 | | | 〔S51〕 |

**과적합·과소적합 처방 표**

| 진단 | 지표 패턴 | 처방 | 근거 |
|---|---|---|---|
| 과적합(overfitting, 높은 분산) | 훈련 데이터 성능은 좋은데 평가·테스트 성능은 나쁨. 테스트 오류율이 높고 훈련·테스트 정확도 격차가 큼 | 모델 유연성을 줄인다: 정규화 증가 (F90), 특성 선택(특성 조합·n-gram·수치 구간 수 감소), 조기 중지, 드롭아웃, 데이터 증강, 앙상블, 데이터 양 확대. XGBoost는 `max_depth`↓ (F87), `eta`↓, `subsample`<1 (F88), `gamma`↑ (F89), `min_child_weight`↑, `alpha`·`lambda`↑ | 〔S49〕〔S51〕〔S25〕 |
| 과소적합(underfitting, 높은 편향) | 훈련 데이터에서도 성능이 나쁨. 모델이 너무 단순하거나 특성이 부족하거나 충분히 오래 훈련되지 않음 | 모델 유연성을 늘린다: 도메인 특성·특성 곱 추가와 특성 처리 변경, 정규화 감소 (F91), 기존 데이터에 대한 패스(에포크) 증가 (F92) | 〔S49〕〔S51〕 |
| 데이터 부족으로 둘 다 나쁨 | 훈련·평가 정확도가 모두 낮음 | 훈련 예제 수와 패스 수를 늘림 | 〔S49〕 |
| 검증 방법 | 과적합 탐지는 별도 데이터로 테스트하거나 K-겹 교차 검증. AMT는 훈련 지표 대신 검증 지표로 튜닝 (F130) | | 〔S51〕〔S28〕 |

> 🧠 원리: 복잡한 모델은 데이터의 진짜 패턴뿐 아니라 우연한 아티팩트까지 학습해 훈련 데이터에서는 잘 맞지만 새 데이터에는 일반화하지 못한다 → 정규화는 극단적 가중치에 패널티를 줘 모델 유연성을 낮춘다. L1은 작은 가중치를 0으로 밀어 특성 수를 줄이고(희소), L2는 모든 가중치를 고르게 줄인다. 〔S48〕

**치명적 망각(catastrophic forgetting)** — 과적합·과소적합과 별개의 위험으로, 사전 훈련 모델을 미세 조정할 때 문제 된다.
- 정의: 좁은 도메인 데이터로 훈련하면 사전 훈련에서 얻은 일반 능력을 덮어써 도메인 밖 작업 성능(지시 따르기·추론·폭넓은 지식)이 떨어지는 현상 (F96). ⚠️ 이 정의 문장은 [블로그]에서만 확인했고 [공식] 문서에는 PEFT 설명 속 '치명적인 언어 능력 손실' 언급뿐이다 (G-2.2-13). 정기 재훈련일수록 심해질 수 있다는 서술도 [블로그]다〔S55〕.

| 완화 방법 | 설명 | 근거 |
|---|---|---|
| 파라미터 효율 미세 조정(PEFT) | LoRA·어댑터·프리픽스 튜닝처럼 일부 파라미터만 갱신해 과적합 또는 언어 능력의 치명적 손실을 방지 (F97). 단점은 전체 갱신 대비 성능이 낮을 수 있음. JumpStart는 `lora_r`·`lora_alpha`·`lora_dropout`을 제공 (F171) | 〔S53〕〔S67〕 |
| 데이터 믹싱 | SFT 중 사용자 데이터에 Amazon Nova 자체 데이터를 섞어 일반 능력을 보존하며 도메인에 특화 (F98) — Nova Forge 기능 | 〔S54〕 |
| 이전 데이터 재사용 | 재훈련 때 과거 데이터를 일부 저장해 재사용하면 망각을 부분적으로 완화 (F99) — [블로그] | 〔S55〕 |
| 체크포인트 선택 | 기존 정렬(alignment)을 얼마나 보존할지 체크포인트로 선택 — Nova Forge [블로그] | 〔S52〕 |

### 2.7 모델 성능 개선 방법과 하이퍼파라미터의 영향 (K4, K7)

공식 문서에는 '모델 성능을 개선하는 방법'을 한 곳에서 정의한 페이지가 없어 여러 문서를 조합했다 (G-2.2-24).

| 개선 방법 | 문서가 말하는 내용 | SageMaker·AWS 연결 | 근거 |
|---|---|---|---|
| 데이터 확대 | 반복 개선의 첫 단계는 훈련 예제 수 증가 (F93). 성능이 나쁠 때 하이퍼파라미터 조정 전에 데이터 양 부족부터 배제 | 증분 훈련: 기존 모델 아티팩트 + 확장된 데이터셋으로 새 모델 훈련 (F95) | 〔S50〕〔S51〕〔S31〕 |
| 특성 처리 | 변수 추가와 더 나은 특성 처리 | Autopilot이 데이터 분석·전처리·특성 선택을 자동화〔S45〕 | 〔S50〕〔S45〕 |
| 하이퍼파라미터 튜닝 | 훈련 파라미터의 대안 값을 시도 | AMT (2.8·2.9) | 〔S50〕〔S32〕 |
| 정규화·특성 선택 | 과적합 시 모델 유연성 감소 | 2.6 | 〔S51〕〔S49〕 |
| 전이 학습·미세 조정 | 사전 훈련 모델을 새 데이터셋으로 이어서 훈련 — 더 작은 데이터셋과 더 짧은 훈련 시간 (F164, F165) | JumpStart·Bedrock (2.12) | 〔S70〕 |
| 앙상블 | 약한 학습자를 결합해 더 정확한 결과 | 부스팅·스태킹 (2.13) | 〔S51〕 |
| 클래스 불균형 처리 | XGBoost `scale_pos_weight` (F94), Linear Learner `positive_example_weight_mult`(양성 가중치)·`balance_multiclass_weights` | 내장 알고리즘 파라미터 | 〔S25〕〔S27〕 |
| 자동화 | AutoML이 전처리·특성 공학·알고리즘 선택·HPO를 자동 처리 (F137) | Autopilot·Canvas (2.9) | 〔S47〕 |

**하이퍼파라미터가 성능에 미치는 영향** — K7의 '트리 수·신경망 계층 수' 예시. ML Lens는 신경망은 학습률·배치 크기·네트워크 아키텍처 파라미터, 트리 모델은 트리 깊이·트리 수·리프당 최소 샘플을 핵심 하이퍼파라미터로 든다 (F138)〔S46〕.

| 알고리즘 | 하이퍼파라미터 | 문서가 말하는 효과 | 근거 |
|---|---|---|---|
| XGBoost | `num_round` | 훈련 라운드 수(필수). AMT 문서가 성능 영향이 가장 큰 5개 중 하나로 꼽음 (F132). `early_stopping_rounds`로 검증 점수가 개선되지 않으면 훈련을 멈춤 (F21) | 〔S25〕〔S26〕 |
| XGBoost | `max_depth` | 키울수록 모델이 복잡해지고 과적합 가능성이 커짐 (F87) | 〔S25〕 |
| XGBoost | `eta` | 업데이트 보폭을 줄여 과적합을 막음(작을수록 보수적) | 〔S25〕 |
| XGBoost | `gamma`·`min_child_weight` | 클수록 알고리즘이 보수적 (F89) | 〔S25〕 |
| XGBoost | `subsample`·`colsample_*` | 행·열을 샘플링해 트리를 키움 → 과적합 방지 (F88) | 〔S25〕 |
| XGBoost | `alpha`·`lambda` | L1·L2 정규화 항, 키울수록 보수적 (F81, F82) | 〔S25〕 |
| Image Classification | `num_layers` | 네트워크의 층 수. 큰 이미지·작은 이미지별로 ResNet 논문 기반 권장 집합에서 선택하며, 전이 학습이면 베이스 네트워크의 아키텍처를 정의하므로 그 집합에서만 선택 가능 | 〔S29〕 |
| Image Classification | `use_pretrained_model` | 켜면 대응하는 층 수의 사전 훈련 모델을 로드하고 최상단 FC 층만 무작위 가중치로 재초기화(전이 학습), 끄면 처음부터 훈련 | 〔S29〕 |
| Image Classification | `augmentation_type`·`weight_decay`·`precision_dtype` | 데이터 증강 / 가중치 감쇠(sgd·nag만) (F83) / 가중치 정밀도(float16이면 메모리 감소) (F72) | 〔S29〕 |
| Linear Learner | `l1`·`wd`·`learning_rate`·`mini_batch_size`·`use_bias`·`positive_example_weight_mult` | AMT 권장 튜닝 대상. AMT를 쓰면 내부 병렬 모델 튜닝이 꺼지고 `num_models`=1 (F131) | 〔S27〕〔S28〕 |

⚠️ 트리 수가 정확히 어떤 방향으로 성능을 바꾸는지(예: 많을수록 과적합)는 이번에 확인한 SageMaker 문서에 직접 서술이 없다. 문서가 보여주는 것은 `num_round`가 영향이 큰 하이퍼파라미터라는 점(F132)과 검증 점수 정체 시 `early_stopping_rounds`로 멈출 수 있다는 점(F21)이다 (G-2.2-17).

### 2.8 하이퍼파라미터 튜닝(AMT) ① — 전략·범위·스케일·병렬성·지표 (K6, SK4)

**AMT란** 사용자가 지정한 알고리즘·하이퍼파라미터 범위로 훈련 작업을 많이 돌려 선택한 지표 기준 최적 모델을 찾는 기능이다. 하이퍼파라미터 튜닝(HPO)이라고도 부르며 내장 알고리즘·사용자 지정 알고리즘·프레임워크 컨테이너에 모두 쓸 수 있고 관리형 스팟 훈련도 쓸 수 있다 (F100)〔S32〕. 공식 ko_kr 표기는 '그리드 검색·임의 검색·베이지안 최적화·하이퍼밴드'다〔S86〕(가이드는 random search를 '무작위 검색'으로 표기).

| 전략 | 동작 | 병렬성 | 장점·제약 | 선택 기준 | 근거 |
|---|---|---|---|---|---|
| Grid | 범주형 값 조합을 모두 시도. `MaxNumberOfTrainingJobs`는 생략 가능하고 지정하면 고유 조합 수와 같아야 함 (F101) | 조합 수만큼 | 범주형만 지원. 같은 하이퍼파라미터면 최적값이 동일 | 재현·투명성, 탐색 공간을 고르게 훑기 (F108) | 〔S33〕〔S38〕 |
| Random | 매 작업마다 범위에서 무작위 조합. 이전 결과와 무관 (F102) | 가장 많은 병렬 (F107) | 최대 동시 작업을 써도 튜닝 성능이 변하지 않음 | 대규모 병렬, 짧은 훈련 작업 | 〔S33〕〔S38〕 |
| Bayesian | 회귀로 다음 후보를 선택, 탐색/활용 절충 (F103) | 순차적 성격이라 대규모 확장에 약함 (F106) | 이전 결과를 활용해 점진적 개선 | 짧은 훈련 작업에서 효율 | 〔S33〕〔S38〕 |
| Hyperband | 다중 충실도. 중간·최종 결과로 에포크 재할당, 부진한 구성 자동 중지 (F104) | 많은 병렬 작업으로 확장 | 반복형 알고리즘(에포크마다 지표)만 (F105). `TrainingJobEarlyStoppingType`은 OFF (F19) | 큰 작업에서 계산 시간 절감 (F109) | 〔S33〕〔S38〕 |

**병렬 작업 수와 Bayesian 효율**: 이전 시도 결과로 후속 시도를 개선할 수 있으므로 '의미 있는 추가 결과를 주면서 리전·계정 컴퓨트 한도 안에 드는 가장 큰 병렬 수'를 고르라는 것이 문서 지침이다(`MaxParallelTrainingJobs`)〔S38〕. Bayesian은 순차적 성격 때문에 병렬로 키우는 데 한계가 있고(F106) Random은 병렬에 가장 유리하다(F107).

**범위와 스케일**
- 하이퍼파라미터는 값이 변하지 않는 정적(static)과 범위를 탐색하는 동적(tunable)으로 나뉜다. 동적 범위는 `ParameterRanges`의 범주형(Categorical)·정수형(Integer)·연속형(Continuous) 세 하위 필드로 정의하고 동시 탐색은 최대 30개, 정적 포함 총 100개, 범주형은 30개 값까지다 (F110–F112)〔S34〕〔S38〕.
- 정수·연속 범위의 `ScalingType`:

| 스케일 | 언제 | 제약 | 근거 |
|---|---|---|---|
| `Auto` | SageMaker가 최적 스케일을 선택 | 판단이 어렵거나 스케일을 모를 때. 기본 가정은 선형 | 〔S34〕〔S38〕 |
| `Linear` | 최저~최고 값 범위가 상대적으로 작을 때(한 자릿수 이내) | — | 〔S34〕 |
| `Logarithmic` | 범위가 여러 자릿수에 걸칠 때. 예: 학습률 0.0001~1.0 — 선형 탐색이면 예산의 대부분이 큰 값 구간에 쓰임 (F115) | 값이 0보다 큰 범위만 (F113) | 〔S34〕 |
| `ReverseLogarithmic` | 1에 매우 가까운 작은 변화에 민감한 범위 | 연속형만, 0 이상 1 미만 범위 안에서만 (F114) | 〔S34〕 |

> 🧠 원리: 선형 스케일로 0.0001~1.0을 균일하게 뽑으면 구간 길이 비율 때문에 대부분의 시도가 0.1~1.0에 몰려 작은 값 영역을 거의 못 본다. 로그 스케일은 자릿수마다 균등하게 뽑아 전체 범위를 고르게 탐색한다 (F115). 〔S34〕

**목표 지표(objective metric) 지정**
- 내장 알고리즘은 지표가 이미 정의되어 있고 자동으로 튜닝에 전달된다〔S39〕. 알고리즘이 내보내는 지표 중 하나를 목표로 고르고 `Maximize`/`Minimize`를 정한다. 예: XGBoost는 `validation:auc`(Maximize)·`validation:rmse`(Minimize) 등〔S26〕, Linear Learner는 `validation:objective_loss`(Minimize) 등〔S28〕.
- 사용자 지정 알고리즘은 `MetricDefinitions`(이름 + 정규식)로 stdout·stderr 로그에서 지표를 파싱하며, 적어도 하나의 지표를 로그에 써야 한다〔S39〕.
- 과적합을 피하려면 훈련 지표보다 검증 지표로 튜닝 (F130). 분산 훈련에서는 마지막으로 실행 중인 작업이 보고한 지표가 쓰임 (F128). AMT는 목표 지표를 전달하려고 `_tuning_objective_metric` 하이퍼파라미터를 자동 추가하며 이것이 총 한도에 포함됨 (F111).
- 완료 기준(`TuningJobCompletionCriteria`)과 `ResourceLimits`(최대 훈련 작업 수·튜닝 작업 최대 실행 시간·동시 훈련 작업 수)로 중지 시점을 정함. 기준을 여러 개 지정하면 하나라도 충족 시 중지 (F126)〔S40〕〔S34〕.
- 같은 `RandomSeed`를 주면 하이퍼파라미터 구성을 재현할 수 있음(Random·Hyperband는 높은 재현성, Bayesian은 재현성 향상)〔S38〕.
- 여러 알고리즘을 한 튜닝 작업에서 비교하는 기능이 있으나 웜 스타트·조기 중지는 단일 알고리즘 튜닝에서만 가능 (F127)〔S42〕.

### 2.9 하이퍼파라미터 튜닝(AMT) ② — 웜 스타트·할당량·모범 사례·Autotune·자동화 기능 (SK4, SK5)

**웜 스타트(warm start)** — 이전 튜닝 작업(들)을 출발점으로 새 튜닝 작업을 시작한다. 이전 작업의 결과로 탐색할 조합을 정하며 Bayesian 또는 Random 검색을 쓴다〔S36〕.

| 유형 | 새 튜닝 작업이 쓰는 것 | 바꿀 수 있는 것 | 근거 |
|---|---|---|---|
| `IDENTICAL_DATA_AND_ALGORITHM` | 부모와 같은 입력 데이터·훈련 이미지 | 탐색 범위, 최대 훈련 작업 수, 튜닝 가능↔정적 전환(총수 동일). 알고리즘 변경 없는 로깅 개선 등만 허용. `OverallBestTrainingJob` 필드 제공 | 〔S36〕 |
| `TRANSFER_LEARNING` | 입력 데이터·범위·최대 동시/전체 작업 수·이미지 버전이 부모와 달라도 됨 | 데이터셋·알고리즘 변경이 목표 지표 값에 크게 영향을 주면 웜 스타트의 유용성이 떨어질 수 있음 | 〔S36〕 |

제약: 부모 최대 5개(모두 종료 상태) (F122), 목표 지표 동일 (F123), 정적+튜닝 가능 하이퍼파라미터 총수 동일·타입 변경 불가·전환 횟수 상한 (F122, F203), 비재귀 (F124), 시작이 더 오래 걸림〔S36〕. 사용 이유: 훈련 작업 수를 점진적으로 늘림, 새 데이터로 튜닝, 범위·정적/튜닝 가능 구성 변경, 중단된 튜닝 작업 이어가기〔S36〕. ML Lens도 비용 절감을 위해 웜 스타트와 체크포인트를 권한다〔S46〕.

**할당량(기본값)** — 한도 표〔S37〕. 훈련 인스턴스 쿼터는 별도로 적용된다(모든 튜닝 작업의 동시 훈련 인스턴스가 합산).

|---|---|---|---|
| 동시(병렬) 튜닝 작업 수 | 100 | 불가(N/A) | F116 |
| 동시에 탐색 가능한 하이퍼파라미터 수 | 30 | 불가 | F110 |

⚠️ 상충: 웜 스타트 문서는 훈련 작업 상한을 500으로 쓰고 (F125, G-2.2-2), 지표 수는 20과 40이 공존한다 (G-2.2-3). 상향이 필요하면 AWS Support Center에서 Service limit increase → 한도 유형 'SageMaker AI Automatic Model Tuning [Hyperparameter Optimization]'을 선택한다〔S37〕.

**모범 사례 요약**〔S38〕〔S46〕: (1) 큰 작업은 Hyperband, 작은 작업은 Random·Bayesian (F109). (2) 튜닝 하이퍼파라미터 수는 적게 (F110). (3) 범위는 알려진 부분집합으로 좁게 — 가능한 모든 값을 덮는 범위는 계산 시간이 크고 일반화가 나빠질 수 있음. (4) 올바른 스케일 선택(`Auto` 가능). (5) 병렬 수는 의미 있는 추가 결과를 주는 최대치. (6) 분산 훈련 시 목표 지표는 마지막 실행 작업의 것 (F128). (7) 시드로 재현. (8) 조기 중지·웜 스타트·병렬 실행·결과 분석·구성 문서화 (ML Lens).

**Autotune**: 하이퍼파라미터 범위·`ResourceLimits`·`TrainingJobEarlyStoppingType`(기본 활성)·`RetryStrategy`·`Strategy`·`ConvergenceDetected`의 최적 값을 자동으로 추측한다. `ParameterRanges`의 `AutoParameters`에 하이퍼파라미터 이름과 예시 값(`ValueHint`)을 주고 `Autotune: {Mode: Enabled}`로 켜면 AMT가 적합 여부를 판단해 범위를 정하고, `DescribeHyperParameterTrainingJob`으로 결과 범위를 볼 수 있다 (F129)〔S34〕.

### 2.10 내장 알고리즘·프레임워크·스크립트 모드 (SK1, SK2)

SageMaker AI는 구현 옵션을 노력 수준이 높아지는 순서로 제시한다. 사전 훈련 모델(JumpStart)이 가장 적은 노력이고, 그다음 내장 알고리즘, 사전 제작 프레임워크 이미지(스크립트 모드), 사용자 지정 Docker 이미지 순이다〔S22〕. 문서는 '세 가지 옵션'이라 쓰지만 목록은 네 개다 (F148, G-2.2-11).

| 구현 | 코드 필요 | 사전 코딩된 알고리즘 | 서드파티 패키지 | 사용자 코드 | 노력 |
|---|---|---|---|---|---|
| 내장 알고리즘 | 아니오 | 예 | 불가 | 불가 | 낮음 |
| Scikit-learn · Spark ML · XGBoost(오픈소스) | 예 | 예 | PyPI만 | 예 | 중간 |
| TensorFlow · PyTorch · MXNet · Chainer | 예 | 아니오(직접 구현) | PyPI만 | 예 | 중간~높음 |
| 사용자 지정 이미지 | 예 | 아니오 | 모든 출처 | 예 | 높음 |

(표는 〔S22〕의 구현 가이드 표를 옮긴 것. MXNet·Chainer는 SageMaker Python SDK v3에서 미지원 ⚠️ — F62, F63)

**내장 알고리즘으로 모델 개발 (SK1)**
- 코드 없이 데이터·하이퍼파라미터·컴퓨트만 제공하면 실험을 시작할 수 있고, 해당되는 알고리즘은 여러 컴퓨트 인스턴스 병렬화와 GPU 지원이 기본이다 (F145). 이미 사전 훈련된 모델이 있어도 같은 알고리즘의 내장 버전에 알려진 하이퍼파라미터를 넣는 편이 스크립트 모드로 이식하는 것보다 쉬울 수 있다고 문서가 설명한다〔S22〕.
- 모든 내장 알고리즘 공통 정보(Docker 레지스트리 경로·데이터 형식·권장 EC2 인스턴스·CloudWatch 로그)는 'Parameters for Built-in Algorithms'에 모여 있다〔S23〕.
- 내장 알고리즘 범주 〔S23〕: 표 형식 지도 학습(AutoGluon-Tabular·CatBoost·Factorization Machines·k-NN·LightGBM·Linear Learner·TabTransformer·XGBoost), 시계열(DeepAR), 임베딩(Object2Vec), 비지도(PCA·K-Means·Random Cut Forest·IP Insights), 텍스트(BlazingText·Seq2Seq·LDA·NTM·Text Classification-TensorFlow), 이미지(Image Classification·Object Detection·Semantic Segmentation). 사전 훈련 모델·솔루션 템플릿은 JumpStart가 제공.
- XGBoost는 내장 알고리즘으로도, 로컬 환경의 훈련 스크립트를 돌리는 프레임워크(오픈소스) 모드로도 쓴다 (F149). 이미지 URI 태그에는 `:latest`·`:1`을 쓰지 말고 지원 버전을 명시한다 (F150). 훈련 인스턴스 권장은 2.4.
- 알고리즘별 하이퍼파라미터·AMT 튜닝 범위는 2.7·2.8.

**스크립트 모드로 프레임워크 훈련 (SK2)**
- 정의: 내장 알고리즘으로 안 될 때 지원 프레임워크 이미지에서 사용자 스크립트(`.py`)를 실행하는 방식 (F146). `requirements.txt`로 PyPI 패키지를 설치할 수 있고 코드 디렉터리를 함께 올릴 수 있지만, PyPI에 없거나 프레임워크 이미지에 없는 패키지는 쓸 수 없다 (F147).
- 지원 프레임워크 목록(문서): Apache MXNet ⚠️, Apache Spark, Chainer ⚠️, Hugging Face, PyTorch, Scikit-learn, SparkML Serving, TensorFlow, Triton Inference Server〔S61〕 (⚠️ = SDK v3 미지원, F62, F63).
- SDK 세대: v2는 프레임워크별 Estimator에 `entry_point`+`source_dir`, v3는 `ModelTrainer` 하나에 `SourceCode`(source_dir + command/entry_script)·`Compute`·`InputData`·`StoppingCondition` 같은 설정 객체 (F157, F158)〔S64〕. 공식 문서 본문은 'ModelTrainer'로 바뀌는 중이다 (G-2.2-8).

| 스크립트가 쓰는 규약 | 경로·의미 | 근거 |
|---|---|---|
| `SM_MODEL_DIR` | `/opt/ml/model` — 최종 모델 아티팩트 저장. 종료 시 `model.tar.gz`로 압축·S3 업로드 (F151) | 〔S14〕 |
| `SM_CHANNEL_<CHANNEL_NAME>` | `/opt/ml/input/data/<channel_name>` — 채널별 훈련 데이터 읽기. 채널은 작업당 최대 20개 (F152, F46) | 〔S14〕 |
| `SM_OUTPUT_DIR`(문서 표 표기) | `/opt/ml/output/data` — 손실·정확도·가중치·그래디언트 등 부수 출력. 모델 아티팩트와 다름. 블로그·예제는 `SM_OUTPUT_DATA_DIR` (F153, G-2.2-7) | 〔S14〕〔S65〕 |
| `/opt/ml/checkpoints` | 체크포인트 ↔ S3 동기화 (F54) | 〔S12〕〔S14〕 |
| `SAGEMAKER_SUBMIT_DIRECTORY` | `/opt/ml/code` — 훈련 스크립트·라이브러리·의존성이 복사되는 위치 | 〔S14〕 |
| `SM_HPS` / `SM_HP_<NAME>` | 하이퍼파라미터의 JSON 딕셔너리 / 이름이 `<NAME>`인 개별 값 (F154, F155) | 〔S66〕 |
| `SM_CHANNELS`·`SM_NUM_GPUS`·`SM_CURRENT_HOST` | 입력 채널 목록 / 컨테이너의 GPU 수 / 현재 컨테이너 이름 | 〔S66〕 |

- 하이퍼파라미터 전달: Estimator에 넘긴 하이퍼파라미터가 입력 스크립트의 인자(argparse)로 전달된다 (F156). SageMaker 전용 인자(모델 경로·출력 경로·채널 경로)의 기본값은 환경 변수에서 읽는다〔S65〕.
- File 모드는 SageMaker local mode와 호환되어 노트북에서 컨테이너를 빠르게 띄워 스크립트를 테스트할 수 있다 (F41)〔S13〕.

> 🧠 원리: SageMaker는 훈련 컨테이너를 시작할 때 채널 데이터를 `/opt/ml/input/data/<채널>`에 두고(File 모드), 하이퍼파라미터를 스크립트에 넘기며, 스크립트가 `/opt/ml/model`에 쓴 파일을 `model.tar.gz`로 압축해 S3에 올린다. 스크립트는 SageMaker 전용 API 없이 경로·환경 변수 규약만 따르면 된다. 〔S14〕〔S66〕

프레임워크별 `model.tar.gz` 구조(문서 예시)〔S59〕
- TensorFlow: `[model_version_number]/variables`·`[model_version_number]/saved_model.pb` + `code/inference.py`·`code/requirements.txt`
- PyTorch: `model.pth` + `code/inference.py` + `code/requirements.txt`(버전 조건 있음)
- MXNet: `model-symbol.json`·`model-shapes.json`·`model-0000.params` + `code/inference.py` + `code/requirements.txt`(버전 조건 있음)

기타
- SDK v3에서는 `ModelBuilder`가 추론 핸들러와 모델 아티팩트(`s3_model_data_url`)를 패키징·배포하고 컨테이너 이미지·모델 서버(예: DJL Serving)를 지정할 수 있다〔S64〕.

> 🧠 원리: SageMaker 호스팅은 모든 것이 컨테이너 기반이며 프레임워크 컨테이너는 `/opt/ml/model/`에 풀린 모델 아티팩트와 `code/` 아래 추론 스크립트를 찾는다. 그래서 외부 모델은 '구조가 맞는 tar.gz'만 만들면 사전 빌드 컨테이너가 그대로 서빙하고, 구조·런타임을 맞출 수 없을 때만 컨테이너를 확장하거나 BYOC로 간다. 〔S59〕

### 2.12 사전 훈련 모델 파인튜닝 — SageMaker JumpStart와 Amazon Bedrock (SK3)

**파인튜닝이란**: 사전 훈련 모델을 새 데이터셋으로 처음부터가 아니라 이어서 훈련하는 것으로 전이 학습(transfer learning)이라고도 하며, 더 작은 데이터셋과 더 짧은 훈련 시간으로 정확한 모델을 만들 수 있다 (F164, F165)〔S70〕. 모델 가중치를 바꾸는 사용자 지정 방법이다 (F166)〔S67〕. 공식 ko_kr은 fine-tuning을 '미세 조정'으로 쓰고, Bedrock 개요의 증류(distillation) 항목 제목은 '추출'로 번역돼 있다〔S88〕 (G-2.2-19).

**SageMaker JumpStart**

| 유형 | 훈련 데이터 | 특징 | 근거 |
|---|---|---|---|
| 도메인 적응 미세 조정 | CSV·JSON·TXT, 한 폴더 안의 단일 파일. CSV/JSON은 `Text` 열(없으면 첫 열)을 사용 (F167, F168) | 업계 전문 용어 같은 도메인 언어에 적응. 검증 폴더는 선택이며 없으면 훈련 데이터의 일부를 검증용으로 분할(비율은 하이퍼파라미터로 조정) | 〔S68〕 |
| 명령 기반(instruction) 미세 조정 | JSON Lines(.jsonl)의 프롬프트-응답 쌍. 선택적 `template.json`이 입출력 형식을 기술하며 없으면 기본 템플릿(prompt/completion) 사용 (F169) | 일부 모델만 호환. `instruction_tuned` 하이퍼파라미터로 전환 | 〔S69〕〔S67〕 |
| 공통 하이퍼파라미터 | `epoch`·`learning_rate`·`per_device_train_batch_size`·`lora_r`·`lora_alpha`·`lora_dropout`·`int8_quantization`·`enable_fsdp` 등 (F171) | 모델마다 지원 범위가 다름 | 〔S67〕 |

- 실행: Studio의 모델 상세 카드에서 Train을 선택하거나 SageMaker Python SDK를 쓴다. 문서 제목은 JumpStartEstimator에서 'ModelTrainer class'로 바뀌었고, SDK v3 예시는 `ModelTrainer.from_jumpstart_config(JumpStartConfig(model_id=...))` → `train(input_data_config=[InputData(channel_name="train", ...)])` → `ModelBuilder`로 배포다〔S71〕.
- 인스턴스: Studio에서는 선택한 모델과 호환되는 인스턴스만 고를 수 있다 (F170). 일부 모델(예: Llama 2)은 EULA 수락이 필요하다〔S70〕. 문서에 열거된 지원 모델 목록(Llama 2·Mistral·Falcon·Flan-T5·Gemma·Code Llama 등)은 변동되므로 암기 대상이 아니다 (G-2.2-16)〔S67〕.

**Amazon Bedrock 모델 맞춤화**

| 방법 | 데이터 | 목적 | 근거 |
|---|---|---|---|
| 지도 미세 조정(SFT) | 레이블된 데이터(입력→출력 예제), JSONL (F173, F178) | 특정 작업 성능 개선, 모델 파라미터 조정 | 〔S72〕〔S74〕 |
| 강화 미세 조정(RFT) | 훈련 프롬프트(또는 Bedrock 호출 로그) + AWS Lambda 보상 함수 (F174) | 피드백 기반 학습으로 정렬 개선 | 〔S72〕 |
| 증류 | 사용 사례별 프롬프트(선택적으로 레이블된 프롬프트-응답 쌍). 교사 모델 응답을 생성해 학생 모델을 미세 조정 (F175) | 큰 모델의 지식을 작고 빠르고 저렴한 모델로 이전 | 〔S72〕 |
| 연속 사전 훈련(CPT) | 레이블 없는 대용량 도메인 데이터 (F176) | 새 도메인 지식 학습 | 〔S77〕〔S78〕 ⚠️ 개요 페이지 미열거 (G-2.2-5) |

- 데이터 형식: `.jsonl`(한 줄 = 한 레코드). 비대화형은 `prompt`+`completion`, 대화형은 Converse API 형식(`bedrock-conversation-2024`의 system·messages), 이미지 생성·임베딩 모델은 `image-ref`+`caption`. 형식은 맞춤화 방법·모델·입출력 모달리티에 따라 다르고, 훈련 데이터셋은 최소한 필수이며 검증 데이터셋 지원 여부는 모델마다 다르다 (F178)〔S74〕.
- 하이퍼파라미터(모델별): `epochCount`·`batchSize`·`learningRate`·`learningRateWarmupSteps`, Claude 3는 `learningRateMultiplier`와 `earlyStoppingThreshold`·`earlyStoppingPatience`, 이미지 모델은 `stepCount` (F14, F23, F181)〔S73〕. 에포크는 전체 데이터를 한 번 처리하므로 늘리면 비용이 늘고 (F180), 큰 데이터셋은 더 적은 에포크로 수렴한다 (F182). 비용은 처리 토큰 수(훈련 말뭉치 토큰 × 에포크)와 월별 모델 스토리지로 구성 (F179).
- 추론: 사용자 지정 모델은 Provisioned Throughput 구매(콘솔 도움말: 복사본 포함 추론에 필요) 또는 사용자 지정 모델 배포를 통한 온디맨드 추론(사용한 만큼만 과금)이다 (F183, F184). 온디맨드는 2025-07-16 이후 맞춤화한 모델, 지원 기반 모델(Nova Lite·Nova 2 Lite·Nova Micro·Nova Pro·Llama 3.3 70B Instruct), US East (N. Virginia)·US West (Oregon) 조건이 있다 (F185, F186, G-2.2-6)〔S75〕〔S76〕〔S77〕.
- 맞춤화 대상 모델 범주(훈련 데이터 준비 문서): 텍스트→텍스트(Titan Text·Cohere Command·Meta Llama 3.1/3.2/3.3·Claude 3 Haiku 등), 텍스트-이미지(Titan Image Generator), 이미지-임베딩(Titan Multimodal Embeddings). Nova는 별도 문서〔S74〕.
- 메모: Bedrock 맞춤화 API의 `customizationType`에는 `FINE_TUNING`·`CONTINUED_PRE_TRAINING`·`DISTILLATION`·`REINFORCEMENT_FINE_TUNING`·`IMPORTED`가 있다 (F177)〔S78〕.

**JumpStart vs Bedrock 선택** — 문서가 두 서비스를 직접 비교한 문장은 확인하지 못했으므로 서비스 성격으로 단서를 정리한다. ① 훈련 작업의 인스턴스·하이퍼파라미터·VPC·암호화 키를 직접 구성하고 SageMaker로 배포 → JumpStart·SageMaker 훈련 (F170, F171)〔S70〕. ② 훈련 인프라를 직접 관리하지 않고 데이터셋과 하이퍼파라미터만 제공 → Bedrock 맞춤화이며, 사용자 지정 모델은 Provisioned Throughput 또는 조건부 온디맨드로 호출 (F183–F186).

### 2.13 앙상블·스태킹·부스팅·배깅 (SK7)

| 기법 | 정의(공식 문서) | SageMaker 사례 | 근거 |
|---|---|---|---|
| 앙상블(ensembling) | 여러 개별 알고리즘의 예측을 결합. 결과가 자주 부정확한 약한 학습자들을 결합해 더 정확한 결과를 얻음. 주요 방법은 배깅과 부스팅이며 과적합을 막는 전략 중 하나로 소개됨 | — | 〔S51〕 |
| 부스팅(boosting) | 서로 다른 모델을 차례로 훈련해 최종 결과를 얻음 (F139) | XGBoost: 더 단순한 모델들의 추정치를 결합하는 그래디언트 부스팅 트리 (F141). LightGBM(GOSS·EFB 기법)·CatBoost(ordered boosting·범주형 처리)도 그래디언트 부스팅 트리 구현 | 〔S51〕〔S24〕〔S23〕 |
| 배깅(bagging) | 모델들을 병렬로 훈련 (F140) | SageMaker 문서의 직접 사례는 확인하지 못함 (G-2.2-18) | 〔S51〕 |
| 스태킹(stacking) | 여러 모델을 다층으로 쌓아 결합 | AutoGluon-Tabular: 여러 모델을 앙상블하고 다층으로 스태킹 (F142). Autopilot Ensembling 모드: AutoGluon으로 여러 베이스 모델을 훈련해 스태킹 앙상블로 결합, 10 trial (F143, F144) | 〔S30〕〔S44〕 |

- 구분: Autopilot의 Ensembling은 'AutoGluon 기반 스태킹으로 모델을 결합', HPO는 '하이퍼파라미터를 튜닝해 최적 모델 하나를 찾음'이다. Auto 모드는 데이터셋이 100MB보다 크면 HPO, 아니면 Ensembling을 고른다〔S44〕. AMT는 한 알고리즘의 최적 구성을 찾는 기능이고 앙상블은 여러 모델의 예측을 결합하는 기법이다.
- 특성 선택(SK6·K4 연계): 모델 유연성을 줄이는 과적합 처방이며 PCA는 특성 수를 줄이는 내장 알고리즘이다 (2.5·2.6, F74, F75).

> 🧠 원리: 부스팅은 모델을 차례로 훈련해 최종 결과를 만들고(XGBoost는 더 단순한 모델들의 estimate(예측 값)를 결합) 배깅은 모델을 병렬로 훈련한다. '순차 vs 병렬'이 두 방법을 가르는 문서상의 기준이다. 〔S51〕〔S24〕

### 2.14 모델 버전 관리 — SageMaker Model Registry (SK9)

공식 ko_kr 표기는 모델 레지스트리·모델 그룹·모델 버전·컬렉션·승인 상태·모델 계보다〔S89〕.

**구조**
- **Model (Package) Group**: 특정 문제를 푸는 모델들을 추적하는 묶음. 훈련한 모델을 등록할 때마다 새 모델 버전으로 추가된다〔S79〕.
- **모델 버전(모델 패키지)**: 1부터 시작해 새 패키지가 추가될 때마다 증가하고 (F191), 반드시 Model Group에 속한다 (F192). AWS Marketplace 모델 패키지는 버전 관리 엔터티가 아니며 Model Group과 연결되지 않는다 (F193)〔S80〕.
- **Collection**: Model Group을 카테고리로 묶는 선택 계층 (F190)〔S79〕.
- 기능 목록: 프로덕션용 모델 카탈로그, 모델 버전 관리, 훈련 지표 같은 메타데이터 연결 (F188), Model Cards 정보 조회, 계보를 통한 추적성·재현성 (F187), 스테이징 구성 정의, 승인 상태 관리 (F189), 프로덕션 배포, CI/CD 자동화, 모델 공유〔S79〕.

**교차 계정**: 다른 계정이 만든 Model Group에 등록하려면 교차 계정 IAM 리소스 정책(ECR·S3·KMS 정책, `put_model_package_group_policy`)이 필요하고 (F199) 훈련 시 출력 데이터 구성 암호화에 KMS 키를 써야 한다 (F200)〔S82〕. AWS RAM으로 모델 패키지 그룹을 공유할 수 있으며 발견가능성(Discoverability)과 접근가능성(Accessibility) 두 권한 범주가 있다 (F201)〔S83〕.

**'반복성·감사'와의 연결**: ① 계보를 통한 추적성·재현성 (F187), ② 훈련 지표·구성 같은 메타데이터 기록 (F188), ③ 번호가 있는 버전과 Model Group (F191, F192), ④ 승인·스테이징 이벤트 이력 (F202), ⑤ 교차 계정 권한 분리 (F199–F201). 참고로 AMT의 `RandomSeed`는 하이퍼파라미터 구성 재현을 돕는다 (2.8)〔S38〕.

## 3. 시험에서 묻는 방식

### 패턴 1. 훈련이 느리거나 비싸다 — 병목 원인에 맞는 단축 수단 고르기 (K2)
- 시나리오 단서: ① 배치 크기를 1로 줄여도 GPU 메모리 부족(OOM)이 나거나 수백억 파라미터라 모델이 단일 GPU에 안 들어감. ② 모델은 GPU 하나에 들어가지만 데이터가 커서 며칠 걸려 인스턴스를 늘려 시간을 줄이고 싶음. ③ 중단돼도 괜찮은 훈련 작업의 비용 절감, 스팟 인스턴스 사용. ④ 훈련 시작 전 S3 다운로드가 오래 걸리거나 데이터셋이 인스턴스 디스크보다 큼. ⑤ 반복 실험 때마다 인스턴스 기동을 기다림. ⑥ 검증 지표가 더 개선되지 않는데 에포크가 남음. ⑦ GPU 활용도가 낮은데 큰 인스턴스를 씀.
- 정답 방향: 병목이 '메모리'면 모델 병렬(SMP v2·하이브리드) ①, '처리량'이면 데이터 병렬(SMDDP, 다중 노드·지원 인스턴스) ②, '비용 + 중단 허용'이면 관리형 스팟 훈련 + 체크포인트(`MaxWaitTimeInSeconds`) ③, '시작 지연'이면 FastFile(또는 Pipe)·관리형 웜 풀(`KeepAlivePeriodInSeconds`) ④⑤, '개선 정체'면 조기 중지(알고리즘 내부 `early_stopping_*` / AMT `TrainingJobEarlyStoppingType` / Hyperband) ⑥, '단순 모델에 과대한 인스턴스'면 적정 크기로 조정 ⑦ (F11, F24–F27, F38, F42, F48–F55).
- 오답 유인(섞이는 선택지): OOM인데 SMDDP로 인스턴스만 증설(데이터 병렬은 모델과 레코드 1개가 한 디바이스에 들어가야 함). OOM인데 FastFile·스팟(메모리와 무관). 비용 절감인데 인스턴스 대형화. 체크포인트 없이 스팟으로 장시간 훈련(체크포인트 없는 내장 알고리즘은 대기 상한 3600초). 스팟 절감 '최대 90%'를 고정 90%로 읽는 함정. ⚠️ Training Compiler(신규 릴리스 없음)·SageMaker Profiler(2027-06-30 지원 종료)·Debugger(신규 고객 중단)를 해법으로 고르는 보기.
- 근거: 〔S1〕〔S2〕〔S4〕〔S10〕〔S12〕〔S13〕〔S15〕〔S16〕〔S35〕〔S18〕〔S19〕〔S20〕

### 패턴 2. 과적합·과소적합·치명적 망각 — 증상에서 처방과 정규화 기법 고르기 (K5, SK6, K4)
- 시나리오 단서: 훈련 정확도는 높은데 검증·테스트 정확도가 크게 낮음(과적합). 훈련 데이터에서도 성능이 낮음(과소적합). 선형 모델에서 불필요한 특성의 가중치를 0으로 만들고 싶음. 가중치를 전반적으로 줄이고 상관된 특성의 가중치를 안정화하고 싶음. 신경망이 특정 뉴런에 의존함. 미세 조정 뒤 도메인 밖 일반 질문의 성능이 떨어짐. XGBoost 트리가 너무 깊어 과적합.
- 정답 방향: 과적합 → 모델 유연성 감소(정규화 증가: L1·L2·드롭아웃, 특성 선택, 조기 중지, 데이터 증강·확대, 앙상블; XGBoost는 `max_depth`·`eta`↓, `subsample`<1, `gamma`·`min_child_weight`·`alpha`·`lambda`↑). L1은 희소(특성 제거), L2(= weight decay)는 가중치 전반 축소. 과소적합 → 유연성 증가(특성 추가·더 큰 모델), 정규화 감소, 에포크 증가. 치명적 망각 → PEFT(LoRA 등)·데이터 믹싱·과거 데이터 재사용 (F77–F99).
- 오답 유인(섞이는 선택지): L2를 희소화 수단으로 고르기. 드롭아웃을 선형 모델(Linear Learner)에 적용. 과소적합에 정규화 증가, 과적합에 에포크 증가. 치명적 망각을 L1/L2로 해결. '가지치기(가중치 제거)'와 '특성 선택(AWS 페이지의 pruning)' 혼동. Image Classification `weight_decay`가 모든 옵티마이저에 적용된다는 가정(실제는 sgd·nag만).
- 근거: 〔S48〕〔S49〕〔S51〕〔S25〕〔S27〕〔S29〕〔S53〕〔S54〕

### 패턴 3. AMT 구성 선택 — 전략·범위 스케일·병렬성·웜 스타트·할당량 (K6, K7, SK4, SK5)
- 시나리오 단서: 에포크마다 지표를 내는 신경망이고 훈련 작업이 김. 서로 독립인 수많은 작업을 동시에 실행. 이전 결과를 활용해 조합을 점점 개선. 결과 재현이 중요하고 범주형 값만 있음. 학습률 범위가 여러 자릿수에 걸침. 이전 튜닝 결과를 이어서 새 데이터로 튜닝. 범위·자원 설정을 자동으로 맡기고 싶음. 병렬 작업 수 한도 상향 요청. 파이프라인 안에서 튜닝.
- 정답 방향: Hyperband(반복형 알고리즘, 조기 중지 내장이라 `TrainingJobEarlyStoppingType`=OFF), Random(최대 병렬), Bayesian(순차적이라 대규모 병렬에 약함), Grid(범주형만·재현). 학습률 같은 다자릿수 범위는 `Logarithmic`(0 초과), 1 근처에 민감한 연속 범위는 `ReverseLogarithmic`, 판단이 어려우면 `Auto`. 웜 스타트는 부모 최대 5개·같은 목표 지표이고, 같은 데이터면 `IDENTICAL_DATA_AND_ALGORITHM`·데이터가 바뀌면 `TRANSFER_LEARNING`. 범위·한도를 자동 추측하려면 Autotune(`AutoParameters`·`ValueHint`). 파이프라인은 `TuningStep` (F100–F137, F203).
- 오답 유인(섞이는 선택지): Hyperband를 에포크별 지표가 없는 알고리즘에 쓰거나 `TrainingJobEarlyStoppingType`=Auto와 병용. 대규모 병렬에 Bayesian. Grid에 연속형 범위. `ReverseLogarithmic`을 정수 범위에 적용. 웜 스타트에서 목표 지표 변경·부모 6개·조상 정보가 자동 상속된다는 가정. 훈련 지표로 튜닝(검증 지표 권장). 한도 숫자 혼동(튜닝 작업당 병렬 훈련 작업은 기본 10에서 100까지 상향, 튜닝 작업당 훈련 작업은 750이며 Random만 10000까지 상향, 웜 스타트 문서의 500은 상충 표기 — G-2.2-2).
- 근거: 〔S33〕〔S34〕〔S35〕〔S36〕〔S37〕〔S38〕〔S39〕〔S43〕〔S44〕

### 패턴 4. 외부·사전 훈련 모델을 가져오고 맞춤화하고 버전 관리하기 (K8, SK1, SK2, SK3, SK9)
- 시나리오 단서: 온프레미스에서 훈련한 PyTorch·TensorFlow 모델을 SageMaker 엔드포인트에 배포. PyPI 밖 패키지나 사용자 지정 서빙 스택이 필요. 내장 알고리즘에 없는 알고리즘을 프레임워크 코드로 훈련. 레이블 없는 도메인 코퍼스로 전문 용어에 적응. 프롬프트-응답 쌍으로 특정 작업 성능 개선. 보상 함수로 정렬. 큰 모델의 능력을 작고 싼 모델로 이전. 새 버전마다 수동 검토 후 배포하고 승인 이력을 감사. 다른 계정과 모델 공유.
- 정답 방향: 외부 훈련 모델 → `model.tar.gz`(프레임워크별 디렉터리 구조, `code/inference.py`)로 패키징해 사전 빌드 컨테이너로 호스팅(BYOM). 사전 빌드 이미지로 안 되면 이미지를 확장하거나 BYOC(ECR, `/ping`·`/invocations`). 스크립트 모드는 `entry_point`(SDK v2)·`SourceCode`(SDK v3)로 지원 프레임워크에서 훈련. 도메인 적응(CSV·JSON·TXT)·연속 사전 훈련은 레이블 없는 데이터, 명령 기반·지도 미세 조정은 레이블된 프롬프트-응답 쌍(JSONL), RFT는 보상 함수, 증류는 교사→학생. Model Registry는 Model Group에 `PendingManualApproval`로 등록한 뒤 `Approved`로 바꿔 CI/CD를 시작하고 승인·스테이지 이력으로 감사하며, 교차 계정은 리소스 정책 + KMS (F145–F202).
- 오답 유인(섞이는 선택지): 사전 빌드 컨테이너로 충분한데 BYOC를 고름. 모델 파일을 압축 없이 S3에 두고 지정. Bedrock 사용자 지정 모델을 바로 온디맨드로 호출(Provisioned Throughput 또는 조건부 온디맨드 배포가 필요). 연속 사전 훈련에 레이블 쌍을 사용. 증류를 정확도 개선 수단으로 해석. 처음부터 `Approved`로 등록하면서 수동 검토를 기대. ⚠️ MXNet·Chainer를 SDK v3 신규 설계에 선택. Estimator(SDK v2)와 ModelTrainer(SDK v3) 표기 혼동.
- 근거: 〔S22〕〔S59〕〔S60〕〔S64〕〔S67〕〔S68〕〔S69〕〔S72〕〔S75〕〔S76〕〔S77〕〔S79〕〔S81〕〔S82〕〔S83〕〔S84〕

## 4. 흔한 함정·혼동 짝

### 짝 1. 데이터 병렬(SMDDP) vs 모델 병렬(SMP)
- 구분 기준: 병목이 '처리량'이면 데이터 병렬, '메모리'면 모델 병렬.

| 구분 | 데이터 병렬 (SMDDP) | 모델 병렬 (SMP v2) |
|---|---|---|
| 나누는 대상 | 훈련 데이터(배치) | 모델(층·파라미터·상태) |
| GPU마다 모델 | 전체 복제본 | 일부만 |
| 병목 신호 | 모델은 맞는데 데이터가 커서 오래 걸림 | OOM, 모델이 단일 디바이스에 안 맞음 |
| 통신 | 그래디언트 동기화(AllReduce)가 클러스터 확장에 따라 오버헤드 증가 | 분할·파이프라인 실행 일정에 따라 활용도가 좌우됨 |
| 현행 상태·제약 | 지원 인스턴스 ml.p3dn.24xlarge·ml.p4d.24xlarge·ml.p4de.24xlarge, TensorFlow 지원 중단 | v2가 현행(PyTorch FSDP 정렬), v1은 보관 |
| 함께 헷갈리는 것 | 샤딩 데이터 병렬·하이브리드(모델 상태를 데이터 병렬 그룹 안에서 분할) | 텐서 병렬·전문가 병렬·활성화 체크포인트 |

- 근거: 〔S1〕〔S2〕〔S4〕〔S5〕〔S6〕〔S7〕〔S8〕 (F24–F37)

### 짝 2. Grid vs Random vs Bayesian vs Hyperband (AMT 전략)
- 구분 기준: 이전 결과를 쓰는가, 병렬로 얼마나 늘릴 수 있는가, 입력 제약(범주형 전용·반복형 전용)이 있는가.

| 전략 | 이전 결과 활용 | 병렬성 | 입력·제약 | 이럴 때 |
|---|---|---|---|---|
| Grid | 없음(모든 조합을 순회) | 조합 수가 곧 작업 수 | 범주형만. `MaxNumberOfTrainingJobs`는 조합 수와 같아야 함 | 재현·투명성, 탐색 공간을 고르게 훑기 |
| Random | 없음(작업 간 독립) | 가장 많은 병렬 작업 | 제약 적음 | 대규모 병렬, 서로 독립인 실험 |
| Bayesian | 있음(회귀로 다음 후보 선택, 탐색/활용 절충) | 순차적 성격이라 대규모 확장에 약함 | 제약 적음 | 짧은 훈련 작업에서 점진적 개선 |
| Hyperband | 중간·최종 결과로 에포크 재할당, 부진한 구성 중지 | 많은 병렬로 확장 | 반복형 알고리즘(에포크마다 지표)만, `TrainingJobEarlyStoppingType`=OFF | 길고 큰 훈련 작업, 신경망 |

- 근거: 〔S33〕〔S38〕〔S41〕 (F101–F109, F19)

### 짝 3. L1 vs L2(= weight decay) vs 드롭아웃
- 구분 기준: 무엇에 패널티를 주는가(가중치 절댓값 / 가중치 제곱 / 뉴런 자체), 결과가 희소한가, 적용 대상이 선형 모델인가 신경망인가.

| 기법 | 효과 | 파라미터 예 | 함정 |
|---|---|---|---|
| L1 | 작은 가중치를 0으로 → 희소 모델·특성 수 감소 | Linear Learner `l1`, XGBoost `alpha` | 0으로 만드는 것은 L1뿐, 키울수록 모델이 보수적 |
| L2 | 전체 가중치 축소, 상관된 특성에서 가중치 안정화 | Linear Learner `wd`, XGBoost `lambda`, Image Classification `weight_decay` | weight decay와 같은 개념으로 설명되지만 Image Classification은 sgd·nag에만 적용 |
| 드롭아웃 | 훈련 중 무작위 뉴런 비활성화 | JumpStart `lora_dropout`, XGBoost `rate_drop`(트리 드롭) | 신경망용. 선형 모델에는 해당 없음 |

- 근거: 〔S48〕〔S27〕〔S25〕〔S29〕〔S51〕〔S52〕〔S67〕 (F77–F86)

### 짝 4. 조기 중지의 층위 — 알고리즘 내부 vs AMT `Auto` vs Hyperband 내부
- 구분 기준: '누가 무엇과 비교해 끊는가'.

| 층위 | 판단 주체 | 비교 기준 | 설정 |
|---|---|---|---|
| 알고리즘 내부 | 훈련 작업 자신 | 자기 검증 지표가 patience 동안 개선되지 않음 | XGBoost `early_stopping_rounds`, Linear Learner·Image Classification `early_stopping_*`, Bedrock `earlyStopping*` |
| AMT `Auto` | 튜닝 작업 | 같은 에포크까지 이전 훈련 작업들의 이동 평균의 중앙값보다 나쁨 | `TrainingJobEarlyStoppingType`=`AUTO` (API 기본값 OFF), 에포크별 지표 필요 |
| Hyperband | 튜닝 전략 | 중간·최종 결과로 유망한 구성에 에포크 재할당, 부진한 구성 중지 | `Strategy`=`Hyperband`, `TrainingJobEarlyStoppingType`은 OFF |

- 근거: 〔S25〕〔S27〕〔S29〕〔S35〕〔S33〕〔S41〕〔S73〕 (F15–F23)

### 짝 5. File vs FastFile vs Pipe (및 FSx for Lustre·EFS)
- 구분 기준: 훈련이 시작되는 시점, 인스턴스 저장소 요구, 지원하는 입력 형태.

| 모드 | 훈련 시작 | 인스턴스 저장소 | 입력 형태 | 비고 |
|---|---|---|---|---|
| File(기본) | 전체 다운로드 후 | 데이터셋 전체를 담을 공간 | S3 prefix·manifest·augmented manifest | local mode 호환, `ShardedByS3Key` |
| FastFile | 파일 식별 직후 즉시 | 전체를 담을 필요 없음 | S3 prefix만 | POSIX 인터페이스, 순차 읽기에 최적, CloudTrail 비용 증가 가능 |
| Pipe | 스트리밍으로 즉시 | 최종 모델 아티팩트 분량 | FIFO 파이프(프로세스당 하나) | FastFile로 대체되는 추세, TensorFlow 확장·관리형 샤딩·셔플 |
| FSx for Lustre·EFS | 마운트(데이터셋 크기와 무관) | — | 파일 시스템 | VPC 연결 필요, FSx는 단일 AZ |

- 근거: 〔S13〕〔S14〕〔S3〕 (F40–F47)

### 짝 6. 웜 스타트(AMT) vs 관리형 웜 풀 vs 체크포인트 vs 증분 훈련
- 구분 기준: 무엇을 재사용하는가 — 탐색 정보 / 인스턴스 / 훈련 중 상태 / 완성된 모델 아티팩트. 이름의 'warm' 때문에 가장 많이 섞인다.

| 이름 | 재사용하는 것 | 단위 | 설정 | 비고 |
|---|---|---|---|---|
| 웜 스타트 | 이전 튜닝 작업들의 결과(탐색 정보) | AMT 튜닝 작업 | `WarmStartConfig`(부모 최대 5개) | `IDENTICAL_DATA_AND_ALGORITHM`·`TRANSFER_LEARNING`, 같은 목표 지표 |
| 관리형 웜 풀 | 훈련 인프라(인스턴스) | 훈련 작업 | `KeepAlivePeriodInSeconds` | 반복 실험의 기동 지연 감소 |
| 체크포인트 | 훈련 중 모델 상태 | 훈련 작업 | `/opt/ml/checkpoints` ↔ S3 | 스팟 재시작·중단 후 재개 |
| 증분 훈련 | 기존 모델 아티팩트 + 확장 데이터셋 | 훈련 작업 | 이전 `model.tar.gz`로 시작 | 일부 내장 알고리즘만 지원 |

- 근거: 〔S36〕〔S15〕〔S12〕〔S31〕 (F55, F122–F125, F95)

### 짝 7. 미세 조정 vs 연속 사전 훈련 vs 증류 (Bedrock) · 도메인 적응 vs 명령 기반 (JumpStart)
- 구분 기준: 입력 데이터가 레이블 있는 입출력 쌍인가, 레이블 없는 도메인 코퍼스인가, 큰 모델의 응답인가.

| 방법 | 서비스 | 데이터 | 목적 | 비고 |
|---|---|---|---|---|
| 지도 미세 조정(Fine-tuning) | Bedrock | 레이블된 입출력(JSONL, `prompt`·`completion` 또는 Converse 형식) | 특정 작업 성능 개선 | 모델 파라미터 조정 |
| 연속 사전 훈련(CPT) | Bedrock | 레이블 없는 대용량 도메인 데이터 | 새 도메인 지식 | ⚠️ 사용자 가이드 개요에는 미열거, 콘솔 도움말·API에는 존재 (G-2.2-5) |
| 강화 미세 조정(RFT) | Bedrock | 프롬프트 + 보상 함수(AWS Lambda) | 응답 품질 정렬 | 레이블 쌍 불필요 |
| 증류(Distillation) | Bedrock | 사용 사례별 프롬프트(+선택적 레이블) | 작고 빠른 학생 모델에 능력 이전 | 교사가 응답을 생성해 학생을 미세 조정 |
| 도메인 적응 미세 조정 | JumpStart | CSV·JSON·TXT, 한 폴더의 단일 파일 | 업계 용어 등 도메인 언어 적응 | 가중치 수정 |
| 명령 기반 미세 조정 | JumpStart | JSON Lines 프롬프트-응답 쌍, 선택적 `template.json` | 특정 작업 성능 | `instruction_tuned`로 전환 |

- 근거: 〔S72〕〔S73〕〔S74〕〔S77〕〔S78〕〔S68〕〔S69〕〔S67〕 (F166–F182)

### 짝 8. 스크립트 모드 vs BYOM(모델만 가져오기) vs 컨테이너 확장 vs BYOC
- 구분 기준: 무엇을 가져오는가(코드 / 이미 훈련된 모델 / 의존성 / 이미지 전체)와 훈련이 어디서 일어나는가.

| 방식 | 가져오는 것 | 훈련 위치 | 컨테이너 | 제약 |
|---|---|---|---|---|
| 스크립트 모드 | 훈련 코드(.py) | SageMaker | AWS 프레임워크 이미지 | PyPI 패키지만, 지원 프레임워크 한정 |
| BYOM | 외부에서 훈련한 모델 아티팩트 | 외부 | 사전 빌드 프레임워크 이미지로 호스팅 | `model.tar.gz` + 프레임워크별 구조 |
| 컨테이너 확장 | 추가 의존성 | SageMaker | SageMaker 베이스 이미지 + 의존성 | 베이스 이미지 정책 따름 |
| BYOC | 이미지 전체 | SageMaker 또는 외부 | 사용자 이미지(ECR) | 훈련·추론 툴킷, 호스팅은 포트 8080의 `/ping`·`/invocations` |

### 짝 9. Estimator(SDK v2) vs ModelTrainer(SDK v3)
- 구분 기준: 같은 '스크립트 모드'를 가리키는 클래스 체계의 세대 차이. 공식 문서 본문은 'ModelTrainer'로 바뀌는 중이지만 가이드(Version 1.0)의 표현은 SageMaker AI 스크립트 모드이다 (G-2.2-8).

| 구분 | v2 Estimator 패턴 | v3 ModelTrainer 패턴 |
|---|---|---|
| 훈련 클래스 | `SKLearn`·`PyTorch`·`XGBoost` 등 프레임워크별 | `ModelTrainer` 하나 |
| 코드 주입 | `entry_point` + `source_dir` | `SourceCode`(`source_dir` + `command` 또는 `entry_script`) |
| 컨테이너 | AWS 관리형 프레임워크 이미지 | 직접 만든 이미지·AWS DLC·서드파티 이미지 |
| 배포 | Model + Predictor | `ModelBuilder` |
| 비고 | MXNet·Chainer는 v3에서 미지원 ⚠️ | 입력 채널은 `InputData`, 컴퓨트는 `Compute`, 웜 풀은 `keep_alive_period_in_seconds` |

- 근거: 〔S64〕〔S62〕〔S63〕 (F62, F63, F157, F158)

### 짝 10. 양자화 vs 가지치기 vs 증류 (+ 특성 선택·Neo)
- 구분 기준: 무엇을 바꾸는가 — 수치 정밀도 / 파라미터 개수 / 모델 자체(작은 학생) / 입력 특성 / 컴파일.

| 기법 | 바꾸는 것 | 결과 | 주의 |
|---|---|---|---|
| 양자화(데이터 유형 변경) | 가중치·활성화의 수치 정밀도 | 크기·메모리·지연 감소 | 품질 저하 가능, 보정으로 완화 |
| 가지치기(정리) | 중복·불필요한 파라미터 | 더 작은 모델 | AWS 개념 페이지는 '특성 선택'을 pruning이라고도 부름 |
| 증류 | 작은 학생 모델을 큰 교사 모델에 맞춰 훈련 | 비용·지연 감소 | Bedrock 모델 증류 |
| 특성 선택·PCA | 입력 특성 수 | 복잡도·과적합 감소 | PCA는 내장 알고리즘 |
| 컴파일(Neo) | 대상 하드웨어용 컴파일 | 성능 최적화 | Task 3.1 소관 |

- 근거: 〔S56〕〔S57〕〔S51〕〔S23〕〔S58〕〔S72〕 (F66–F76, F175)

### 짝 11. Model Group vs 모델 버전 vs Collection, 그리고 승인 상태 vs 스테이지 상태
- 구분 기준: 계층(묶음 단위)과 상태 체계(CI/CD 트리거용 승인 상태 / 거버넌스용 스테이지)를 구분.

| 개념 | 의미 | 비고 |
|---|---|---|
| Model (Package) Group | 같은 문제를 푸는 모델들의 묶음 | 등록할 때마다 새 모델 버전이 추가됨 |
| 모델 버전(모델 패키지) | 1부터 증가하는 번호, 반드시 Model Group에 속함 | AWS Marketplace 모델 패키지는 버전 관리 엔터티가 아님 |

| 승인 상태 | `PendingManualApproval`·`Approved`·`Rejected` | `Approved`로 바꾸면 CI/CD 배포가 시작될 수 있음 |

### 후보 1 (난이도: associate)
- 대응 Skill: K2
- 문제: ML 엔지니어가 PyTorch로 수백억 파라미터 규모의 트랜스포머 모델을 SageMaker에서 훈련한다. 배치 크기를 1로 줄여도 단일 GPU 메모리 부족(OOM) 오류가 계속된다. 훈련을 계속 진행하면서 이 문제를 해결하는 방법은?
- 보기:
  - A) ml.p4d.24xlarge 인스턴스 수를 늘리고 SageMaker 분산 데이터 병렬 라이브러리(SMDDP)로 각 GPU에 모델 복제본을 두고 데이터를 나눈다
  - B) SageMaker 모델 병렬 라이브러리(SMP v2)로 모델을 여러 GPU에 분할(샤딩 데이터 병렬·텐서 병렬 등)해 훈련한다
  - C) 훈련 입력 모드를 File에서 FastFile로 바꿔 S3 데이터를 스트리밍한다
  - D) 관리형 스팟 훈련을 켜고 체크포인트를 Amazon S3에 저장한다
- 정답: B
- 근거: 〔S2〕 https://docs.aws.amazon.com/sagemaker/latest/dg/distributed-training-strategies.html — 모델이 단일 디바이스에 안 맞으면 모델 병렬로 시작하고, 배치를 1로 줄여도 OOM이면 모델 병렬을 시도. 〔S1〕 https://docs.aws.amazon.com/sagemaker/latest/dg/distributed-training.html — 데이터 병렬은 모델과 레코드 1개가 한 디바이스에 들어가야 함
- 오답 근거: A) 데이터 병렬은 각 GPU가 모델 복제본을 가져야 하므로 모델이 GPU에 안 들어가는 OOM을 해결하지 못함 〔S1〕 / C) 입력 모드는 데이터 로딩 시작 지연에 관한 옵션이며 GPU 메모리와 무관 〔S13〕 / D) 스팟은 비용 절감과 중단 복구 수단이지 메모리 문제의 해법이 아님 〔S10〕

### 후보 2 (난이도: foundational)
- 대응 Skill: K5 / SK6
- 문제: 데이터 과학자가 SageMaker Linear Learner로 수천 개의 특성을 가진 이진 분류 모델을 훈련했더니 훈련 정확도는 높은데 검증 정확도가 크게 낮다. 중요하지 않은 특성의 가중치를 0으로 만들어 모델을 단순화하고 과적합을 줄이려 한다. 가장 적절한 조치는?
- 보기:
  - A) `wd`(L2 정규화 파라미터) 값을 키운다
  - B) `l1`(L1 정규화 파라미터)을 0보다 크게 설정한다
  - C) `mini_batch_size`를 키운다
  - D) `epochs`를 늘려 더 오래 훈련한다
- 정답: B
- 근거: 〔S48〕 https://docs.aws.amazon.com/machine-learning/latest/dg/training-parameters.html — L1 정규화는 작은 가중치를 0으로 밀어 희소 모델을 만듦(레거시 서비스 문서). 〔S27〕 https://docs.aws.amazon.com/sagemaker/latest/dg/ll_hyperparameters.html — `l1`은 L1 정규화 파라미터, `wd`는 L2 정규화 파라미터
- 오답 근거: A) L2는 전체 가중치를 작게 만들고 안정화할 뿐 0으로 만드는 기법이 아님 〔S48〕 / C) 배치 크기는 정규화 기법이 아님 〔S27〕 / D) 에포크 증가는 과소적합의 처방이며 복잡한 모델에서는 분산(과적합)이 오히려 커질 수 있음 〔S51〕

## 9. 확인 필요 항목

- [G-2.2-1] 관리형 스팟 훈련의 `MaxWaitTimeInSeconds`와 `MaxRuntimeInSeconds` 관계가 '커야 한다(larger)'인가 '같거나 커야 한다(equal to or greater)'인가 — 관리형 스팟 훈련 가이드(S10)는 "must be larger than", StoppingCondition API 레퍼런스(S11)는 "equal to or greater than" (F49, F50) — 경계값(두 값이 같을 때)에 의존하는 문항은 만들지 말고 '대기 시간 ≥ 실행 시간 상한' 수준으로만 출제.
- [G-2.2-2] AMT 튜닝 작업당 훈련 작업 최대 수가 750인가 500인가 — 한도 표(S37)는 Bayesian·Random·Hyperband·Grid 모두 기본 750(Random만 10000까지 상향), 웜 스타트 문서(S36)는 "500 maximum training jobs" (F118, F125) — 전용 한도 표를 우선하되 숫자 자체를 정답으로 요구하는 문항은 피하고, 필요하면 두 문서의 불일치를 해설에 명시.
- [G-2.2-3] AMT 튜닝 작업당 지표 수가 20인가 40인가 — 한도 표(S37)는 "정의 가능한 지표 20", 지표 정의 문서(S39)는 "최대 40개 모니터링" (F120, F121) — 확정 불가. 문항화하지 말 것.
- [G-2.2-4] 가이드 SK5 '자동화된 하이퍼파라미터 최적화 기능 통합'이 가리키는 공식 기능이 무엇인가 — 가이드 영문 원문 "Integrating automated hyperparameter optimization capabilities"는 기능명을 특정하지 않음. 후보는 AMT의 Autotune(S34), SageMaker Pipelines 튜닝 스텝(S43), Autopilot의 HPO 모드(S44), Canvas AutoML(S47). 공식 문서에서 이 문구를 직접 설명한 페이지는 찾지 못함 — 컨트롤러는 네 후보를 모두 SK5 재료로 쓰되 하나를 정답으로 단정하지 말 것.
- [G-2.2-5] Amazon Bedrock 사용자 지정 방법에 '연속 사전 훈련(Continued pre-training)'이 현재도 있는가 — 사용자 가이드 개요(S72)는 지도 미세 조정·강화 미세 조정·증류 3종만 열거하지만 콘솔 도움말 패널(S77)과 Boto3 API(S78)는 연속 사전 훈련을 포함 (F172, F176, F177) — 가이드(Version 1.0)는 2024년 기준이라 '미세 조정·연속 사전 훈련·증류'가 정답 후보였을 가능성이 있으므로 문항에서는 연속 사전 훈련을 쓰되 해설에 개요 페이지의 열거 차이를 적을 것.
- [G-2.2-6] Bedrock 사용자 지정 모델 추론에 Provisioned Throughput가 필수인가 — 콘솔 도움말(S77)은 "you need to purchase Provisioned Throughput", 사용자 가이드(S75)는 Provisioned Throughput 또는 온디맨드 배포 두 옵션이며 온디맨드는 2025-07-16 이후 사용자 지정한 모델·지원 모델(Nova·Llama 3.3 70B)·두 리전으로 제한 (F183–F186) — 일반 경로는 Provisioned Throughput, 온디맨드는 조건부 옵션으로 서술.
- [G-2.2-7] 스크립트가 부수 출력을 쓰는 환경 변수가 `SM_OUTPUT_DIR`인가 `SM_OUTPUT_DATA_DIR`인가 — 공식 표(S14)는 `/opt/ml/output/data`를 `SM_OUTPUT_DIR`로 표기하고, AWS 블로그 예제(S65)는 `SM_OUTPUT_DATA_DIR`를 사용하며 훈련 툴킷 문서(S66)는 두 변수 모두 별도 항목이 없음 (F153) — 경로(`/opt/ml/output/data`)와 모델 경로(`/opt/ml/model`, `SM_MODEL_DIR`)의 구분만 출제하고 변수명 철자는 묻지 말 것.
- [G-2.2-8] 시험에서 스크립트 모드를 Estimator(SDK v2) 표기로 묻는가 ModelTrainer(SDK v3) 표기로 묻는가 — 공식 문서 본문은 'Estimator'를 'ModelTrainer'로 바꾸는 중이고(S63·S62·S71), 블로그(S64)가 v2→v3 대응표를 제공. 가이드 Version 1.0(2024)은 SageMaker AI 스크립트 모드로만 서술 (F157, F158) — 보기에 두 표기를 병기하고 `entry_point`(v2)·`SourceCode`(v3) 대응을 해설에 포함.
- [G-2.2-9] 영문 가이드의 steps(단계)가 SageMaker 문서에서 iteration(반복)과 같은 개념으로 정의된 문장이 있는가 — 분산 훈련 문서(S1)는 iteration만 정의하고 steps는 정의하지 않으며, Bedrock `stepCount`(S73)는 '각 배치에 노출되는 횟수'로 따로 정의 (F2, F14) — 학습문서에서는 '훈련 루프에서 가중치를 갱신하는 1회 = iteration/step'으로 설명하되 문서가 명시한 등식이 아님을 밝힐 것.
- [G-2.2-10] AMT 조기 중지를 지원하는 내장 알고리즘 목록이 최신인가 — 문서 스스로 2018-12-13 기준이라 밝히고 알고리즘이 에포크별 지표를 내면 지원한다고 설명 (F17, F16) — 목록 암기 문항은 피하고 '에포크별 목표 지표 발행' 조건을 묻는 문항으로.
- [G-2.2-11] 구현 옵션이 '세 가지'인가 네 가지인가 — 알고리즘 구현 선택 문서(S22)는 "three implementation options"라 쓰지만 목록은 사전 훈련 모델·내장 알고리즘·사전 제작 프레임워크 이미지·사용자 지정 Docker 이미지 네 개 (F148) — '노력 수준이 낮은 순: 사전 훈련 모델 < 내장 < 프레임워크 스크립트 모드 < 사용자 지정 이미지' 순서만 사용하고 개수는 묻지 말 것.
- [G-2.2-12] 가이드 SK8의 '정리(pruning)'가 모델 압축(가중치·파라미터 제거)인가 특성 선택인가 — 한국어 가이드는 '정리', 영문은 pruning. GenAI Lens(S56)는 파라미터 제거로, AWS 'What is Overfitting?'(S51)은 '특성 선택 — 또는 pruning'으로 설명 (F67, F75) — 보기에서 pruning이 나오면 제거 대상(파라미터 vs 특성)을 지문에서 확인해야 한다고 해설.
- [G-2.2-13] 치명적 망각(catastrophic forgetting)의 정의와 완화법을 설명한 [공식] 문서가 있는가 — 정의 문장은 [블로그](S52·S55)에서만 확인. [공식]은 PEFT가 '치명적인 언어 능력 손실'을 막는다는 문장(S53)과 Nova 데이터 믹싱 문서(S54)뿐 (F96–F99) — 문항 해설에 [블로그] 출처 표기를 유지하고, 완화법은 PEFT·데이터 믹싱·과거 데이터 재사용을 '문서에 언급된 방법'으로 한정.
- [G-2.2-14] L1/L2·과적합 처방·모델 크기 설명의 근거가 서비스 신규 사용자 중단된 레거시 Amazon Machine Learning 문서(S48·S49·S50)에 있다 — 현행 SageMaker 문서는 Linear Learner `l1`·`wd`, XGBoost `alpha`·`lambda` 파라미터 설명만 있고 효과 서술은 짧음 (F64, F77–F80) — 개념 설명 근거로만 쓰고 서비스 기능 문항(Amazon ML)은 만들지 말 것.
- [G-2.2-15] SMDDP 지원 인스턴스에 P5가 포함되는가 — SMDDP 지원 인스턴스 표(S4)는 ml.p3dn.24xlarge·ml.p4d.24xlarge·ml.p4de.24xlarge만 나열하고 SMP v2 문서는 P4·P5를 언급 (F29, F32) — SMDDP 인스턴스 목록을 정답 근거로 삼는 문항은 최신 문서 재확인 후 출제.
- [G-2.2-16] JumpStart로 미세 조정 가능한 모델 목록과 모델별 훈련 인스턴스 — 미세 조정 문서(S67)의 목록은 Llama 2·Mistral 7B 등 비교적 구형 위주이고 Studio는 모델별 호환 인스턴스만 선택하게 함(S70). 'Available foundation models' 표의 Fine-tunable 열이 최신 정본일 수 있으나 이번에 전체 대조는 하지 않음 (F167–F171) — 모델 이름 암기 문항은 피하고 '도메인 적응(CSV·JSON·TXT) vs 명령 기반(JSON Lines+`template.json`)' 구분을 출제.
- [G-2.2-17] 트리 모델의 트리 수·깊이가 모델 아티팩트 '크기'에 미치는 영향을 직접 서술한 공식 문서가 있는가 — XGBoost 문서(S25)는 `max_depth`·`num_round`를 복잡도·훈련 라운드 수로만 설명하고 크기는 말하지 않음 (F87) — K3 문항에서는 '파라미터 수·정밀도·체크포인트 포함'처럼 문서가 직접 말하는 요인만 쓰고 트리 수와 크기의 관계는 해설에서 일반 상식으로 분리해 표기.
- [G-2.2-18] 배깅의 SageMaker 사례(예: Random Forest)가 공식 문서에 있는가 — 배깅·부스팅 정의는 AWS 개념 페이지(S51), 부스팅 사례는 XGBoost·LightGBM·CatBoost(S23·S24), 스태킹 사례는 AutoGluon·Autopilot(S30·S44). scikit-learn Random Forest 예제는 블로그(S64)에 있으나 '배깅'이라는 설명은 SageMaker 문서에서 확인하지 못함 (F139–F144) — 문항에서 Random Forest=배깅이라는 일반 ML 지식을 SageMaker 문서 근거처럼 서술하지 말 것.
- [G-2.2-19] 공식 ko_kr 문서의 용어 — ko_kr 문서는 기계 번역이며 영문이 우선(S85–S89). 한 페이지 안에서 '조기 중지'와 '초기 중지'가 섞이고(S87), Bedrock 증류의 제목이 '추출'로 번역되며(S88), random search가 '임의 검색'(가이드는 '무작위 검색')이고(S86), 승인 상태 전이 목록의 마지막 줄이 'Rejected > Approved'로 중복 표기됨(영문은 Approved→Rejected)(S89) — 학습문서에서는 가이드 표기를 기본으로 하고 영문 용어를 병기.
- [G-2.2-20] SageMaker Pipelines 모델 등록 스텝의 현재 명칭 — Model Registry 문서(S82)는 `RegisterModel` 스텝을 안내하지만 블로그 예제는 `ModelStep`+`model.register()`를 사용 — 문서 표기인 `RegisterModel`을 따르되 SDK 버전에 따라 `ModelStep`일 수 있음을 보기·해설에 주의.
- [G-2.2-21] AMT `Strategy` 기본값 — 튜닝 설정 API 레퍼런스(S41)는 `Strategy`를 필수(Required: Yes)로 표기하고 값은 Bayesian·Random·Hyperband·Grid — 이전 문서·SDK의 'Bayesian 기본값' 서술은 이번에 현행 문서로 확인하지 못함 — 기본 전략을 묻는 문항은 피할 것.
- [G-2.2-22] (해소 보고) LIFECYCLE-NOTICES의 L5 중 Debugger 개별 페이지 문구 — "Amazon SageMaker Debugger is no longer open to new customers"(S20)로 확인함 (F60) — 공지 파일의 '미확인' 항목 갱신 제안. 한편 Ground Truth·A2I는 이 Task 범위가 아니라 확인하지 않음.
- [G-2.2-23] SK8 '특성 선택 업데이트'를 구체 SageMaker 기능(예: Data Wrangler의 특성 중요도·Autopilot의 특성 선택)으로 설명한 문서 — 이번에는 일반 개념(S51)과 PCA(S23)·Autopilot 개요(S45)만 확인하고 기능별 근거는 수집하지 않음 — 컨트롤러가 Task 1.2 노트와 대조해 필요 시 보강.
