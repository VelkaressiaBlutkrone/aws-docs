### 2.1 분류 지표: 혼동 행렬에서 출발하는 지표들

혼동 행렬(confusion matrix)은 예측과 실제 레이블을 견주어 네 칸을 센다. Autopilot 문서의 정의는 TP = 예측 1·실제 1, TN = 예측 0·실제 0, FP = 예측 1·실제 0, FN = 예측 0·실제 1 이다. 보고서의 혼동 행렬에는 실제 레이블 기준으로 맞은 예측과 틀린 예측의 개수·비율이 들어간다 〔S2〕.

> 🧠 원리: 정확도·정밀도·재현율·F1 은 모두 같은 네 칸(TP/FP/FN/TN)을 서로 다른 분모로 나눈 값이다 〔S1〕〔S2〕. Clarify 의 사후 편향 지표도 "그룹별 이진 분류 혼동 행렬의 숫자를 조합한 것"이다 〔S25〕.

| 지표 | 공식 문서의 정의 | 범위·방향 | 언제 우선하나 | 함정·한계 | 근거 |
|---|---|---|---|---|---|
| Accuracy(정확도) | 올바르게 분류한 항목 수 ÷ 전체 분류 항목 수 | 0~1, 클수록 좋음 | 클래스가 균형일 때의 기본 지표 | 양성·음성 수 차이가 크면 왜곡 → `BalancedAccuracy` (문서 예: 스팸이 1%) | 〔S1〕 |
| Precision(정밀도) | TP ÷ (TP+FP). 양성이라고 예측한 것 중 실제 양성 비율 | 0~1 | 거짓 양성(FP)의 비용이 클 때 (문서 예: 안전하지 않은 항공기를 안전으로 판정) | FN 은 보지 않음 | 〔S1〕 |
| Recall(재현율 — 가이드 표기는 '리콜', 민감도, TPR) | TP ÷ (TP+FN). 실제 양성 중 찾아낸 비율 | 0~1 | 양성을 빠짐없이 찾아야 할 때 (문서 예: 암 검사) | 전부 양성으로 예측하면 재현율이 만점 → 단독 사용 금지 | 〔S1〕 |
| F1 | 정밀도와 재현율의 조화평균 = 2·(P·R)/(P+R) | 0~1 | 둘 다 중요할 때. Autopilot 이진 분류의 기본 목적 지표 | 이진용. 다중 분류는 `F1macro`(클래스별 F1 의 평균) | 〔S1〕〔S3〕 |
| BalancedAccuracy | 0.5·((TP/P)+(TN/N)) | 0~1 | 양성·음성 수가 크게 다른 불균형 데이터 | — | 〔S1〕 |
| LogLoss(교차 엔트로피) | 예측 클래스가 아니라 확률 출력의 품질을 평가 | 0~∞, 0 이 완벽 | 높은 확률로 틀리는 예측을 크게 벌주고 싶을 때 | 확률 출력이 있어야 함 | 〔S1〕 |
| FPR(위양성률) | FP ÷ (FP+TN). ROC 곡선의 가로축 | 0~1, 작을수록 좋음 | ROC 곡선을 읽을 때 | — | 〔S2〕 |

혼동 행렬을 읽는 법(Autopilot 모델 품질 보고서): 세로축이 실제 레이블, 가로축이 예측 레이블이고, 색 막대는 샘플이 많은 칸을 더 짙은 톤으로 칠한다. 왼쪽 위에서 오른쪽 아래로 가는 대각선이 맞은 예측이고 반대 대각선이 틀린 예측이다. 다중 분류 보고서의 혼동 행렬은 레이블 최대 15개까지 담고, 어떤 레이블 행이 `Nan` 이면 검증 데이터에 그 레이블이 없다는 뜻이다 〔S2〕.

### 2.2 곡선 지표: 임계값, ROC·AUC, 정밀도-재현율 곡선(PR-AUC)

- **임계값(threshold, cut-off)**: 확률·점수를 클래스로 바꾸는 기준값이다. Autopilot 문서는 확률을 분류로 바꾸려고 임계값과 비교한다고 설명하고, 임계값을 올리면 FP 는 줄고 FN 은 는다고 적는다 〔S1〕. 구서비스 Amazon ML 의 기본 컷오프는 0.5 였고 〔S7〕, Clarify 사후 편향 분석에서 수치 예측을 이진 레이블로 바꿀 때 쓰는 `probability_threshold` 도 기본값이 0.5 다(점수가 임계값보다 크면 1, 이하이면 0) 〔S39〕.
- **ROC 곡선**: 임계값을 바꿔 가며 TPR(= 재현율)을 FPR 에 대해 그린 곡선이다. **AUC** 는 그 곡선 아래 면적으로, 모든 분류 임계값에 걸친 성능을 하나의 값으로 요약한다. 0~1 이며 1 이 완벽, 0.5 는 무작위 분류기와 같다 〔S1〕〔S2〕. 0 에 가까우면 모델이 올바른 패턴은 배웠지만 예측이 거꾸로 나온다는 뜻이고 데이터 문제의 신호일 수 있다 〔S2〕.
- **AUC 는 임계값에 독립적**이라서 임계값을 고르지 않고도 모델의 예측 정확도를 가늠할 수 있다 〔S7〕(⚠️ 구서비스 문서).
- **PR 곡선과 AUPRC**: 정밀도와 재현율의 트레이드오프를 그린 곡선이다. AUPRC 는 TN 의 수를 고려하지 않기 때문에 데이터에 TN 이 매우 많은 경우(문서 예: 희귀 돌연변이를 가진 유전자 모델링)에 모델 성능을 평가하기 좋다 〔S2〕.
- **이득(gain)·향상(lift) 곡선**: 이진 분류 보고서에 들어가는 곡선으로, 데이터의 일부만 골랐을 때 양성을 얼마나 찾는지(gain)와 무작위 선택 대비 몇 배 찾는지(lift)를 보여 준다 〔S2〕.

| 곡선 지표 | 가로·세로 | 읽는 법 | 우선 쓰는 상황 | 근거 |
|---|---|---|---|---|
| ROC-AUC | FPR · TPR(재현율) | 1 에 가까울수록 좋고 0.5 는 무작위 | 임계값과 무관하게 모델 간 분리 능력 비교 | 〔S1〕〔S2〕 |
| PR 곡선 · AUPRC | 재현율 · 정밀도 | 오른쪽 위로 휠수록 좋음 | 양성이 드물고 TN 이 압도적인 데이터 | 〔S2〕 |
| 혼동 행렬 | 실제 · 예측 | 대각선에 몰릴수록 좋음 | 특정 임계값에서 FP/FN 이 어디서 나는지 확인 | 〔S2〕 |

> 🧠 원리: FPR = FP/(FP+TN) 이라 분모에 TN 이 들어가고, 정밀도 = TP/(TP+FP) 는 TN 이 들어가지 않는다 〔S2〕. AUPRC 가 TN 을 고려하지 않는다는 문서의 설명은 이 정의와 일치한다.

### 2.3 회귀 지표와 잔차 진단

| 지표 | 공식 문서의 정의 | 범위·방향 | 특징·함정 | 근거 |
|---|---|---|---|---|
| MSE | 예측값과 실제값 차이를 제곱해 평균 낸 값 | 항상 양수, 작을수록 좋음 | Autopilot 회귀의 기본 목적 지표 | 〔S1〕〔S3〕 |
| RMSE | 예측과 실제 차이의 제곱을 평균한 뒤 제곱근을 취한 값 | 0~∞, 작을수록 좋음 | 큰 오차·이상치의 존재를 드러내는 지표. **스케일에 의존**하므로 크기가 다른 데이터셋끼리 비교하면 안 됨 | 〔S1〕 |
| MAE | 절대 오차의 합 ÷ 관측 수. 예측선에서 실제값까지의 평균 거리 | 0~∞, 작을수록 좋음 | 오차 크기를 그대로 평균 | 〔S1〕 |
| R2(결정계수) | 모델이 종속변수의 분산을 얼마나 설명하는지 | 문서 표기 −1~1, 클수록 좋음 | 0 근처는 설명력이 거의 없음. 음수는 상수 함수(수평선)보다 못하다는 뜻 | 〔S1〕 |
| MASE(시계열) | 예측의 MAE 를 단순 기준 예측 방법의 MAE 로 나눈 값 | 작을수록 좋음 | 1 보다 작으면 기준보다 좋고 1 보다 크면 기준보다 나쁨 | 〔S6〕 |
| wQL·Average wQL(시계열) | P10·P50·P90 분위수 예측의 가중 절대 차이 | 작을수록 좋음 | Average wQL 이 시계열 Autopilot 의 기본 지표 | 〔S3〕〔S6〕 |

**잔차(residual) 진단**
- 잔차는 실제값과 예측값의 차이다. 구서비스 Amazon ML 문서는 양의 잔차(실제값이 예측값보다 큼)를 모델이 목표를 실제보다 낮게 예측한 과소 예측(underestimating)으로, 음의 잔차를 실제보다 높게 예측한 과대 예측으로 해석한다 〔S8〕(⚠️ 구서비스 문서).
- 잔차 히스토그램이 0 을 중심으로 한 종 모양이면 모델이 특정 구간을 체계적으로 과대·과소 예측하지 않는다는 뜻이다. 0 을 중심으로 하지 않으면 예측 오차에 구조가 남아 있으므로 변수를 더 넣는 것이 도움이 될 수 있다 〔S8〕〔S2〕.
- Autopilot 보고서는 표준화 잔차(잔차 ÷ 표준편차)를 그리고, 절댓값이 3 보다 큰 점을 일반적으로 이상치로 본다. 표준화 잔차가 다른 값보다 훨씬 크거나 작으면 그 관측을 모델이 잘 맞히지 못한다는 뜻이다 〔S2〕.
- "실제 대 예측" 도표에서는 최적 직선에서 멀수록 모델 오차가 크다 〔S2〕.

> 🧠 원리: RMSE 는 오차를 제곱한 뒤 평균하므로 큰 오차가 더 크게 반영되고, 그래서 문서가 "큰 오차와 이상치의 존재를 알려 주는 지표"라고 설명한다 〔S1〕. MAE 는 절대 오차의 단순 평균이다 〔S1〕.

### 2.4 지표 선택 기준과 '히트 맵' 시각화

**선택 기준 — 문제 유형, 오류 비용의 비대칭, 클래스 불균형, 임계값**

| 상황 | 우선 볼 지표 | 이유(공식 문서 표현) | 피해야 할 선택 | 근거 |
|---|---|---|---|---|
| 거짓 양성(FP)의 비용이 큼 | Precision | FP 비용이 클 때 중요한 지표 (문서 예: 안전하지 않은 항공기를 안전으로 판정) | Recall 만 단독 사용 | 〔S1〕 |
| 양성을 놓치는 비용이 큼 (FN 비용 큼) | Recall | 암 검사처럼 실제 양성을 모두 찾아야 함. 문서 예: 자율주행 차량의 임박한 충돌 탐지에는 재현율에 더 가중 | Precision 만 단독 사용, Accuracy | 〔S1〕〔S2〕 |
| 정밀도·재현율 둘 다 중요 | F1 (또는 임계값 조정) | 조화평균. ML Lens 는 오류 유형별 상대 비용에 맞춰 분류 임계값을 조정하라고 안내 | Accuracy | 〔S1〕〔S14〕 |
| 클래스 불균형 (양성이 드묾) | BalancedAccuracy, AUPRC, F1 | 양성·음성 수가 크게 다른 불균형 데이터에서 BalancedAccuracy 가 더 나은 정확도 척도. AUPRC 는 TN 수를 무시 | Accuracy | 〔S1〕〔S2〕 |
| 불균형을 학습 단계에서 보정 | 샘플 가중치(Autopilot, 앙상블 모드), `scale_pos_weight`(XGBoost) | 문서: `scale_pos_weight` 는 불균형 클래스에 유용하며 고려할 전형적 값으로 음성 사례 수 ÷ 양성 사례 수를 제시 | — | 〔S1〕〔S5〕 |
| 임계값에 독립적으로 모델 비교 | AUC | 모든 분류 임계값에 걸친 성능 요약 | 특정 임계값의 Accuracy | 〔S1〕〔S7〕 |
| 확률 출력의 품질 | LogLoss | 높은 확률로 틀린 예측을 크게 벌줌 | Accuracy | 〔S1〕 |
| 회귀 | RMSE(큰 오차·이상치에 민감), MAE(평균 절대 오차), R2(설명력) | 정의는 2.3 참고 | 스케일이 다른 데이터셋 간 RMSE 비교 | 〔S1〕 |
| 다중 클래스 | F1macro, PrecisionMacro, RecallMacro, Accuracy | 클래스별 값을 평균 | 단일 클래스 지표만 사용 | 〔S1〕〔S3〕 |

- ML Lens 는 지표를 비즈니스 KPI 와 맞추라고 한다(예: 기술 지표인 정밀도·재현율·지연 시간과 전환율·비용 절감 같은 비즈니스 지표). 또한 정확도만 보고 설명 가능성·공정성·추론 속도 같은 다른 요소를 무시하는 것을 안티패턴으로 든다 〔S14〕.
- 성능 지표만으로 충분하지 않은 경우 모델 편향(Clarify)도 평가 기준에 넣는다(2.9~2.12). ML Lens 는 편향·공정성 영향 분석에 Clarify 를 쓰라고 안내한다 〔S14〕.

> 🧠 원리: "무엇이 더 비싼 오류인가"가 지표를 정한다. FP 가 비싸면 분모에 FP 가 들어가는 정밀도를, FN 이 비싸면 분모에 FN 이 들어가는 재현율을 본다 〔S1〕. 임계값을 올리면 FP 가 줄고 FN 이 늘어나므로 〔S1〕 임계값은 두 오류 비용의 상대 크기에 맞춰 조정한다 〔S14〕.

### 2.5 성능 기준선(baseline)을 만드는 방법

공식 문서에서 "baseline" 은 서로 다른 세 가지 뜻으로 쓰인다. K2 의 "성능 기준선"은 ①에 해당하며 가이드는 구체 서비스를 명시하지 않는다. ②·③은 이름이 같아 혼동하기 쉬운 짝이다(섹션 4 짝 8).

| 구분 | 목적 | 만드는 방법(공식 문서 표현) | 상태 | 근거 |
|---|---|---|---|---|
| ① 성능 기준선(비교용 단순 모델) | 개선 여부를 재는 기준점. 허용 가능한 최소 성능 파악 | 단순한 아키텍처·명백한 특성·단순한 알고리즘으로 기준 모델을 만들고(SageMaker 내장 알고리즘으로 빠르게 가능), 이후 실험을 이 기준점과 비교한다. 교차 검증으로 기준선이 견고한지 확인할 수 있다. 기준 없이 복잡한 알고리즘부터 고르는 것은 안티패턴 | 현행 | 〔S13〕〔S14〕 |
| ①′ 지표 자체의 기준값 | "상수 답만 내는 모델보다 나은가" 확인 | 이진 분류 기준 AUC = 0.5(무작위 예측). 회귀 기준 RMSE = 항상 목표의 평균을 예측하는 가상 모델의 RMSE. 다중 분류 기준 macro-F1 = 항상 최빈 클래스를 예측하는 가상 모델의 값. 시계열 MASE 는 단순 기준 예측의 MAE 로 정규화(1 미만이면 기준보다 좋음) | 기준값 정의는 ⚠️ 구서비스 Amazon ML 문서(AUC·RMSE·macro-F1). MASE 는 현행 Autopilot 시계열 | 〔S7〕〔S8〕〔S9〕〔S6〕 |
| ② 운영 기준선(Model Monitor baseline) | 배포 후 데이터 드리프트·모델 품질 저하 탐지의 표준 | 학습 데이터셋으로 baseline job(`DefaultModelMonitor.suggest_baseline`)을 돌려 기준 통계를 만들고 제약(constraints)을 제안한다. 모델 품질은 예측값과 정답(ground truth) 레이블이 든 데이터셋으로 `ModelQualityMonitor.suggest_baseline` 을 실행해 지표를 계산하고 제약을 제안한다 | ⚠️ Model Monitor 는 신규 고객 중단(대체 경로: 오픈소스 모니터링 솔루션 + QuickSight + CloudWatch) | 〔S17〕〔S18〕〔S19〕 |
| ③ 설명 기준선(SHAP baseline) | 특성이 "없는" 상태를 대신할 기준 인스턴스 | 생략하면 입력 데이터셋을 K-means·K-prototypes 로 클러스터링해 자동 계산한다. 평균·중앙값·최빈값으로 만든 평균적 인스턴스를 직접 줄 수도 있다 | ⚠️ Clarify 는 신규 고객 중단 | 〔S38〕〔S39〕 |

- Amazon ML 문서는 기준값 비교의 의미를 이렇게 적는다: 회귀·다중 분류 모델을 "항상 같은 답을 내는 모델"과 비교해 자기 모델이 더 나은지 확인한다 〔S8〕〔S9〕.
- **평가는 학습에 쓰지 않은 데이터로** 해야 한다. 학습에 쓴 데이터로 정확도를 재면 일반화가 아니라 암기를 보상한다 〔S11〕. 분할 예: Amazon ML 콘솔 기본은 앞 70% 학습·나머지 30% 평가, 모델 선택까지 하려면 60/20/20(학습/평가/검증) 〔S11〕. Autopilot 앙상블 모드는 검증 데이터를 주지 않으면 80% 학습·20% 검증으로 자동 분할한다 〔S1〕.
- ML Lens(BP02)의 성능 개선 절차는 ① 기준 모델 → ② 실험 추적(관리형 MLflow) → ③ 알고리즘 비교 → ④ 특성 공학 → ⑤ 데이터 양·품질 → ⑥ 앙상블 → ⑦ 하이퍼파라미터 튜닝 → ⑧ 개선 여부를 체계적으로 평가 순서다 〔S13〕.
- **현재 운영 중인 모델이 곧 기준선**이 되는 경우: 섀도 테스트는 새 구성의 성능을 현재 배포된 인프라와 견주어 평가하고 〔S59〕, A/B 테스트는 새 모델과 기존 모델을 운영 트래픽으로 비교해 새 모델이 더 나으면 기존 모델을 교체한다 〔S63〕(2.14).

> 🧠 원리: 기준선은 "아무것도 학습하지 않은 규칙"(평균·최빈 클래스·무작위)이 내는 점수다. 모델이 그 점수보다 나아야 가치가 있다는 것이 Amazon ML 문서의 논리다 — AUC 0.5 는 "무작위로 0/1 을 예측하는 가상 모델"의 값이고, 이진 모델은 이보다 잘해야 쓸모가 있다 〔S7〕.

### 2.6 과적합·과소적합을 식별하는 방법

핵심 진단은 **훈련 데이터의 오차와 평가(검증·테스트) 데이터의 오차를 함께 보는 것**이다. 구서비스 Amazon ML 문서는 "훈련 데이터와 평가 데이터의 예측 오차를 보면 과소적합인지 과적합인지 알 수 있다"고 적는다 〔S10〕(⚠️ 구서비스 문서). AWS 의 현행 설명 페이지도 같은 기준이다 〔S12〕.

| | 과소적합(underfitting) | 과적합(overfitting) |
|---|---|---|
| 징후 | 훈련 데이터에서도 성능이 나쁨. 훈련·테스트 모두 부정확 → **높은 편향(high bias)** | 훈련 데이터에서는 좋고 평가·테스트에서는 나쁨. 훈련-테스트 정확도 사이의 큰 격차 → **높은 분산(high variance)** | 
| 원인(문서) | 모델이 데이터 관계에 비해 너무 단순, 특성 부족, 충분한 시간 동안 충분한 데이터로 학습하지 못함 | 훈련 데이터가 적거나 잡음이 많음, 모델이 패턴 대신 데이터를 암기, 모델 복잡도가 높아 잡음까지 학습 |
| 대응(문서) | 모델 유연성을 높임: 도메인 특성 추가·특성 처리 방식 변경, 정규화를 줄임. 에포크(데이터 통과 횟수)를 늘림 | 모델 유연성을 낮춤: 특성 선택(특성 조합 축소), 정규화를 늘림. 훈련 데이터 증가, 조기 종료(early stopping), 앙상블, 데이터 증강 |
| 근거 | 〔S10〕〔S12〕 | 〔S10〕〔S12〕 |

- 특성이 부족해서가 아니라 **학습 데이터 양이 부족해서** 훈련·테스트 성능이 모두 나쁠 수도 있다. 이때는 훈련 예제를 늘리거나 기존 데이터에 대한 학습 패스 수를 늘린다 〔S10〕〔S12〕.
- 문서가 가장 좋은 과적합 탐지법으로 꼽는 것은 더 많은 데이터로 모델을 시험하는 것이다. 훈련 데이터의 일부를 테스트 데이터로 떼어 높은 테스트 오차와 훈련-테스트 정확도 격차를 확인한다. **K-겹 교차 검증**은 훈련 세트를 K 개 폴드로 나눠 폴드마다 검증 데이터로 번갈아 쓰며 점수를 평균한다 〔S12〕. 모델 설정까지 평가 데이터로 고르면 모델 선택 자체가 과적합될 수 있으므로 검증용 데이터를 따로 둔다(60/20/20 예) 〔S11〕.
- Autopilot 은 HPO 모드에서 훈련 인스턴스 50,000개 이하의 작은 데이터셋에 k-겹 교차 검증을 자동 적용하고(k = 5), 앙상블 모드는 크기와 상관없이 교차 검증을 한다. 교차 검증은 과적합·선택 편향을 줄이지만 훈련 시간을 평균 20% 늘릴 수 있다 〔S1〕.
- 클래스 불균형도 과적합 위험과 연결된다. Clarify CI 문서는 작은 facet 의 데이터가 적으면 모델이 더 큰 facet 에 맞춰 학습하고 작은 데이터셋에 과적합될 위험도 크다고 설명한다 〔S26〕.

**SageMaker 에서 쓰는 도구**
- Debugger 내장 규칙 `overfit` 은 검증 손실과 훈련 손실을 비교해 과적합을 탐지한다. `overtraining` 은 훈련·검증 손실이 모두 줄다가 더 이상 개선되지 않는 시점 이후에도 계속 학습하면 검증 손실이 다시 증가하며 과적합이 시작되는 상황을 다룬다 〔S44〕(⚠️ Debugger 신규 고객 중단, 2.8).
- 문서의 대응 안내: 과적합을 막는 표준 방법은 모델 정규화이고, 과훈련(overtraining)은 조기 종료로 피할 수 있다 〔S44〕.
- 자동 모델 튜닝(AMT) 조기 종료 옵션은 개선이 없는 훈련 작업을 일찍 멈춰 계산 시간을 줄이고 과적합도 피하게 한다 〔S68〕. XGBoost 의 `early_stopping_rounds` 는 검증 점수가 개선되는 동안만 학습한다 〔S5〕.

> 🧠 원리: 모델이 훈련 데이터를 암기하면 훈련 오차는 계속 줄지만 보지 못한 데이터의 오차는 오른다. 그래서 두 오차의 격차(또는 검증 손실의 반등)가 과적합 신호이고 〔S12〕〔S44〕, 두 오차가 모두 높으면 모델이 관계를 포착하지 못한 과소적합이다 〔S10〕.

### 2.7 수렴 문제의 종류와 징후

수렴(convergence) 문제는 Debugger 문서가 "비수렴(non-converging) 문제"라고 부르는 훈련 문제 묶음이다. Debugger 개요 문서는 훈련 작업에 과적합, 포화된 활성화 함수, 기울기 소실 같은 문제가 생기면 모델 성능이 나빠진다고 설명하며, Debugger 를 "비수렴(non-converging) 문제를 탐지하는" 도구로 소개한다 〔S43〕.

| 문제 | 징후 | 원인·연관 | 확인 방법 (Debugger 내장 규칙) | 근거 |
|---|---|---|---|---|
| 기울기 소실(vanishing gradient) | 기울기 절댓값의 평균이 지정 임계값 밑으로 떨어지거나 0 이 됨 → 가중치가 거의 갱신되지 않음 | 너무 작은 가중치 초기화, 포화된 tanh·sigmoid | `vanishing_gradient`, `saturated_activation`(포화 한계는 기울기 소실 임계값을 기준으로 정해짐) | 〔S44〕 |
| 텐서·기울기 폭주(exploding) | 훈련 중 텐서에 무한대 또는 NaN(비유한 값) 발생 | 너무 큰 가중치 초기화 | `exploding_tensor`, 업데이트 대 가중치 비율이 너무 크면 가중치가 최적값에서 멀어지므로 `weight_update_ratio` | 〔S44〕 |
| 손실이 줄지 않음 | 손실이 적절한 비율로 감소하지 않음 | 규칙 설명에는 원인 목록이 없음(원인은 이 표의 다른 행과 학습률에서 찾음) | `loss_not_decreasing` | 〔S44〕 |
| 아주 느린 수렴 | 업데이트가 너무 작아 수렴이 매우 느림 | 가중치 대비 업데이트 비율이 작음 | `weight_update_ratio`(작은 비율 쪽 조건) | 〔S44〕 |
| 학습 정체 | 일정 시간 동안 새 텐서 출력이 없음 | 작업이 멈춤·진행 없음 | `stalled_training_rule`(발동 시 훈련 중지 가능) | 〔S44〕 |
| 불량 가중치 초기화 | 활성화 입력 분산이 층마다 크게 다름, 기울기 분포가 좁음, 초기 단계에서 손실이 수렴하지 않음 | 좋은 초기화는 가중치·기울기의 대칭을 깨고 층 간 활성화 분산을 비슷하게 유지. 너무 작으면 기울기 소실, 너무 크면 폭주 | `poor_weight_initialization`(처음 몇 단계만 검사) | 〔S44〕 |
| 죽은 ReLU | 한 층에서 비활성 ReLU 비율이 `threshold_layer` 값을 넘음. 블로그 설명: ReLU 출력이 0 이라 기울기가 0 이 되고 가중치가 더는 갱신되지 않아 모델이 학습하지 못함 | ReLU 활성도가 임계 아래로 떨어짐 | `dead_relu` | 〔S44〕〔S15〕 |
| 입력·데이터 문제 | 이미지 입력 평균이 0 에서 임계값 이상 벗어남. 패딩·미지 토큰 비율이 높음. 클래스 간 표본 수 불균형이 임계 초과 | 컴퓨터 비전 모델은 평균 0·분산 1 입력을 요구하는 경우가 많음 | `check_input_images`, `nlp_sequence_ratio`, `class_imbalance`, `all_zero`, `unchanged_tensor`, `tensor_variance` | 〔S44〕 |
| 학습률 | 너무 높으면 최적해를 지나쳐 불안정해지고, 너무 낮으면 안정적이지만 학습이 느림 | 하이퍼파라미터 | 손실 곡선, `loss_not_decreasing`; 분산 훈련에서는 노드(전역 배치)를 늘리면 학습률도 올리고, 점진적 학습률 워밍업으로 초반 수렴을 안정화 | 〔S74〕〔S73〕 |
| 검증 손실 반등 | 훈련 손실은 줄지만 검증 손실이 다시 늘어남 | 과적합·과훈련 | `overfit`, `overtraining` (2.6) | 〔S44〕 |

- Debugger 규칙은 적용 범위가 다르다. `dead_relu`, `exploding_tensor`, `poor_weight_initialization`, `saturated_activation`, `vanishing_gradient`, `weight_update_ratio` 는 딥러닝 프레임워크(TensorFlow·MXNet·PyTorch) 전용이고 XGBoost 에는 쓸 수 없다 〔S44〕.
- 컴퓨터 비전·NLP 입력 점검은 딥러닝 응용용 규칙(`check_input_images`, `nlp_sequence_ratio`)이다 〔S44〕.

> 🧠 원리: `weight_update_ratio` 문서에 따르면 훈련 조건은 업데이트가 기울기에 걸맞을 때 가장 좋다. 지나치게 큰 업데이트는 가중치를 최적값에서 멀어지게 하고 아주 작은 업데이트는 수렴을 매우 느리게 한다 〔S44〕. 학습률 문서도 같은 구조다. 큰 학습률은 큰 보폭으로 파라미터를 갱신해 빠른 수렴을 줄 수 있지만 최적해를 지나쳐 불안정해질 수 있고, 작은 학습률은 안정적이지만 학습이 느리다 〔S74〕.

### 2.8 SageMaker Model Debugger 로 수렴 디버깅 ⚠️

> ⚠️ **서비스 상태**: "Amazon SageMaker Debugger is no longer open to new customers" — 기존 고객은 계속 쓸 수 있고 새 기능은 없다 〔S48〕. 같은 묶음 공지(Clarify·Model Monitor·Profiler 등)의 신규 고객 중단일은 2026-07-30 이다 〔S21〕. 별개로 **SageMaker Profiler 는 2027-06-30 에 지원 종료**(이후 콘솔·리소스 접근 불가)다 〔S49〕. 가이드(Version 1.0)가 SK6 에서 Debugger 를 명시하므로 개념과 규칙 이름은 그대로 익히되, 공지가 안내하는 대체 경로(아래 표)를 함께 알아 둔다.

**무엇을 하나**: 훈련 작업의 출력 텐서를 실시간으로 디버깅해 수렴하지 않는 문제를 찾는다 〔S43〕. *텐서*는 훈련 반복마다의 순전파·역전파에서 갱신된 파라미터의 데이터 모음이고, Debugger 는 이 출력 텐서를 모아 훈련 상태를 분석한다 〔S45〕. 지원 프레임워크는 Apache MXNet, PyTorch, TensorFlow, XGBoost 다 〔S43〕.

**수집(텐서·컬렉션)**
- `CollectionConfig` 와 `DebuggerHookConfig` API 가 텐서를 *컬렉션*으로 묶어 S3 에 저장한다. 별도 지정이 없으면 기본 경로는 `<훈련 작업 이름>/debug-output/` 이다 〔S45〕.
- 내장 컬렉션 예: `weights`, `gradients`, `losses`, `biases` 〔S46〕. 정규식 `include_regex` 로 사용자 컬렉션을 만드는 예는 내장 규칙 문서의 코드 샘플에 나온다 〔S44〕.
- 훈련 스크립트 수정은 필요할 때만 한다(`sagemaker-debugger` SDK) 〔S43〕.

**디버깅 절차(SK6)**
1. 필요하면 훈련 스크립트를 `sagemaker-debugger` SDK 로 수정하고, 훈련 작업에 Debugger(hook 설정 + 규칙)를 구성한다 〔S43〕.
2. 훈련을 시작하고 내장 규칙이 문제를 감시하는 상태를 실시간으로 본다 〔S43〕.
3. 규칙이 발동하면 알림을 받거나 조치를 자동화한다: 내장 액션 `StopTraining`(훈련 작업 중지), `Email`, `SMS`(Amazon SNS `SMDebugRules` 토픽 필요), 또는 CloudWatch Events + Lambda 로 사용자 액션 〔S47〕〔S43〕.
4. 수집한 텐서를 TensorBoard 로 시각화해 원인을 파고든다 〔S43〕.
5. 문제를 고치고 목표 정확도에 이를 때까지 1~4 를 반복한다 〔S43〕.

**내장 규칙 묶음(규칙 이름은 `rule_configs.<이름>()` 으로 호출)**

| 적용 범위 | 규칙 |
|---|---|
| XGBoost 훈련 보고서 | `create_xgboost_report` |
| 딥러닝(TensorFlow·MXNet·PyTorch) | `dead_relu`, `exploding_tensor`, `poor_weight_initialization`, `saturated_activation`, `vanishing_gradient`, `weight_update_ratio` |
| 딥러닝 + XGBoost 공통 | `all_zero`, `class_imbalance`, `loss_not_decreasing`, `overfit`, `overtraining`, `similar_across_runs`, `stalled_training_rule`, `tensor_variance`, `unchanged_tensor` |
| 딥러닝 응용 | `check_input_images`, `nlp_sequence_ratio` |
| XGBoost 전용 | `confusion`, `feature_importance_overweight`, `tree_depth` |

근거 〔S44〕. 한 훈련 작업에 붙일 수 있는 내장 규칙은 최대 20개이고 내장 규칙 사용에 추가 비용은 없다 〔S44〕. `CreateXgboostReport` 규칙은 XGBoost 훈련에서 출력 텐서(하이퍼파라미터, 손실·정확도 지표, 특성 중요도, 예측, 레이블 등)를 모아 보고서를 자동 생성한다 〔S44〕.

**⚠️ 대체 경로 — Debugger·Profiler 공지가 안내하는 역량별 대체**

| Debugger 역량 | 대체 | 제공하는 것 | 근거 |
|---|---|---|---|
| 훈련 지표 로깅 | MLflow / TensorBoard | 훈련 실행 간 지표를 기록·시각화·비교 | 〔S48〕 |
| 모델·파라미터 추적 | MLflow | 하이퍼파라미터·모델 버전·아티팩트를 완전한 재현성으로 추적 | 〔S48〕 |
| 기울기·활성화·가중치 분석 | TensorBoard | 훈련 단계별 모델 내부를 보는 히스토그램·분포 플러그인 | 〔S48〕 |
| 시스템 리소스 프로파일링(CPU·GPU·메모리·디스크) | Amazon CloudWatch | 실시간 사용률 지표와 대시보드 | 〔S48〕 |
| 자동 훈련 진단 | CloudWatch Alarms + MLflow | 손실 수렴·기울기 노름·자원 사용률 같은 기록 지표를 임계값으로 감시하고, MLflow 실행 비교로 실험 간 회귀 식별 | 〔S48〕 |
| (Profiler) GPU/CPU 커널 추적·동기화·로더 분석 | PyTorch Profiler / TensorFlow Profiler + TensorBoard, CloudWatch | 프레임워크 기본 프로파일러와 TensorBoard 로 커널 수준 가시성 | 〔S49〕 |

- 과거 Debugger 텐서 데이터는 S3 에 남고 `smdebug` 클라이언트 라이브러리로 읽을 수 있다 〔S48〕.

> 🧠 원리: Debugger 는 훈련 중 저장한 텐서(가중치·기울기·손실 등)에 *규칙*을 돌려 문제를 판정한다. 규칙은 텐서의 통계(예: 기울기 절댓값 평균, 검증/훈련 손실 비율)를 임계값과 비교하고 〔S44〕, 규칙 상태에 따라 훈련 중지·알림 같은 액션이 실행된다 〔S47〕.

### 2.9 SageMaker Clarify 개요와 훈련 데이터(사전) 편향 지표 ⚠️

> ⚠️ **서비스 상태**: "Amazon SageMaker Clarify is no longer open to new customers" — 기존 고객은 계속 사용하고 새 기능은 없다 〔S20〕. 묶음 공지의 신규 고객 중단일은 2026-07-30 〔S21〕. 가이드의 K4·SK5 가 Clarify 를 명시하므로 지표 이름과 의미는 그대로 익히고, 대체 경로는 2.12 에 정리한다.

**Clarify 가 훈련 데이터와 모델에 대해 제공하는 분석 범주(K4)** 〔S22〕
1. **사전(pre-training) 편향 지표** — 데이터 속 편향을 이해해 더 공정한 데이터셋으로 훈련하게 한다.
2. **사후(post-training) 편향 지표** — 알고리즘·하이퍼파라미터 선택이 만든 편향, 앞 단계에서 드러나지 않은 편향을 본다. 데이터·레이블에 더해 **모델 예측**을 사용한다.
3. **Shapley 값(SHAP)** — 특성이 모델 예측에 미치는 영향. **훈련된 모델이 필요**하다.
4. **부분 의존성 도표(PDP)** — 한 특성 값을 바꿨을 때 예측 대상 변수가 얼마나 달라지는지. **훈련된 모델이 필요**하다.
- 이 분석은 SageMaker Clarify 전용 컨테이너 이미지로 도는 *처리 작업(processing job)* 으로 실행하고, 분석 설정은 JSON(`analysis_config`)으로 준다 〔S22〕〔S39〕. 운영 중인 모델의 편향 드리프트·특성 기여도 드리프트 모니터링도 가능하다(Task 4.1 영역) 〔S22〕.

**Clarify 용어(문서의 정의)** 〔S23〕

| 용어 | 뜻 |
|---|---|
| facet | 편향을 측정하는 대상 속성(열). 유리한 쪽을 *facet a*, 불리한 쪽을 *facet d* 로 표기 |
| facet value | 편향이 유리하게·불리하게 작용할 수 있는 속성 값 |
| label / predicted label | 관측 레이블(정답) / 모델이 예측한 레이블 |
| positive label values | 표본이 *긍정 결과*를 가졌음을 나타내는 레이블 값 |
| group variable | 조건부 인구통계 격차(CDD)에서 하위 그룹을 나누는 범주형 열(심슨 역설 대응). 이 지표에만 필요 |
| bias metric / bias report | 편향 수준을 나타내는 수치 함수 / 데이터셋(또는 데이터셋+모델)에 대한 지표 모음 |

**사전 편향 지표 8종** — 모든 사전 지표는 모델 출력에 의존하지 않으므로 어떤 모델에도 유효(model-agnostic)하다 〔S24〕. 첫 지표 CI 는 결과가 아니라 facet 별 표본 수 불균형만 보고, 나머지는 facet a·d 의 결과 레이블 분포를 여러 방식으로 비교한다 〔S24〕.

| 약어 | 이름 | 무엇을 재나 | 범위 | 해석 | 근거 |
|---|---|---|---|---|---|
| CI | Class Imbalance | facet 값 간 구성원 수 불균형. CI = (na − nd) / (na + nd) | 정규화 −1~+1 | 양수: facet a 표본이 많음. 0 근처: 균형. 음수: facet d 표본이 많음. ±1 근처면 편향 예측 위험이 큼 → 학습 전 재표집 고려 | 〔S24〕〔S26〕 |
| DPL | Difference in Proportions of Labels | facet 별 양성 레이블 비율 차. DPL = qa − qd | 이진·다중 facet 레이블 −1~+1, 연속 레이블 (−∞,+∞) | 양수: a 의 양성 비율이 높음. 0 근처: 인구통계 평등(demographic parity). 음수: d 가 높음 | 〔S24〕〔S27〕 |
| KL | Kullback-Leibler Divergence | facet 간 결과 분포의 엔트로피적 발산 | 0~+∞ | 0 근처: 레이블 분포 유사. 클수록 발산 큼 | 〔S24〕 |
| JS | Jensen-Shannon Divergence | facet 간 결과 분포의 엔트로피적 발산 (KL 과 같은 질문) | 0~+∞ | 위와 동일 | 〔S24〕 |
| LP | Lp-norm | facet 별 결과 분포 사이의 p-norm 차 | 0~+∞ | 위와 동일 | 〔S24〕 |
| TVD | Total Variation Distance | L1-norm 차이의 절반 | 0~+∞ | 위와 동일 | 〔S24〕 |
| KS | Kolmogorov-Smirnov | facet 간 결과 분포의 최대 발산 | 0~+1 | 0 근처: 모든 결과 범주에서 레이블이 facet 간 고르게 분포. 1 근처: 한 범주의 레이블이 전부 한 facet 에 몰려 매우 불균형 | 〔S24〕 |
| CDD | Conditional Demographic Disparity | facet 전체와 하위 그룹별 결과 격차(심슨 역설 배제용) | −1~+1 | 양수: facet d 가 수락보다 거절이 많은 결과. 0 근처: 평균적으로 격차 없음. 음수: facet a 가 수락보다 거절이 많음 | 〔S24〕 |

- 분석 설정의 `methods` 에 쓰는 약어는 `CI`, `DPL`, `KL`, `JS`, `LP`, `TVD`, `KS`, `CDDL` 이다. CDD 의 설정 약어는 CDDL 이다 〔S39〕. `methods` 를 `all` 로 두면 사전 지표를 모두 계산한다 〔S39〕.
- 이 8종과 2.10 의 사후 13종을 합치면 21개이며, 블로그도 Clarify 가 21개 지표를 제공한다고 적는다 〔S42〕.
- 편향 분석 설정의 핵심 항목: `label`(정답 열), `label_values_or_threshold`(긍정 결과를 뜻하는 레이블 값·임계값, 편향 분석에 필수), `facet`(`name_or_index`, `value_or_threshold`), `group_variable`(CDD·CDDPL 용), 그리고 사후 지표·SHAP·PDP 에 필요한 `predictor` 〔S39〕.

**사전 지표를 쓰는 순서(SK1)**: ① 데이터 단계에서 CI·DPL 로 표본 불균형과 레이블 편향을 본다 → ② 훈련 후 같은 facet 에 사후 지표를 계산한다 → ③ DPL 과 DPPL 을 비교하면 훈련이 양성 비율 편향을 키웠는지 알 수 있다(DPPL > DPL 이면 훈련 후 편향 증가) 〔S28〕. 어떤 지표가 사용 사례에 맞는지는 사람이 판단해야 하며 이해관계자와 협의해 정한다 〔S25〕.

> 🧠 원리: 사전 지표는 모델 출력에 의존하지 않고 원본 데이터의 레이블·facet 분포만 비교한다. 그래서 모델 훈련에 자원을 쓰기 전에 계산할 수 있다 〔S24〕. 반대로 사후 지표는 예측 레이블이 필요하므로 모델(또는 예측 결과)이 있어야 한다 〔S22〕.

### 2.10 Clarify 사후(post-training) 편향 지표 13종 ⚠️

사후 지표는 데이터·레이블에 **모델의 예측 레이블**을 더해 계산한다. 대부분은 인구통계 그룹(facet)별 이진 분류 혼동 행렬의 숫자를 조합한 값이고, 이 개념들은 동시에 모두 만족시킬 수 없어 사용 사례에 맞는 지표를 사람이 골라야 한다 〔S25〕. 문서 요약표에 실린 지표는 13개다(본문은 "eleven" 이라고 쓰지만 목록은 13개 — 섹션 9 [G-2.3-1]) 〔S25〕. 예측 레이블을 이진화하는 `probability_threshold` 기본값은 0.5 다 〔S39〕.

| 약어 | 이름 | 무엇을 비교하나 | 범위 | 해석(부호) | 근거 |
|---|---|---|---|---|---|
| DPPL | Difference in Positive Proportions in Predicted Labels | facet a 와 d 의 **예측 양성 비율 차** (q′a − q′d) | 이진·다중 −1~+1, 연속 (−∞,+∞) | 양수: a 의 예측 양성 비율이 높음. 0 근처: 비슷. 음수: d 가 높음 | 〔S25〕〔S28〕 |
| DI | Disparate Impact | 예측 양성 비율의 **비** (q′d / q′a). 예: a 60%·d 50% → 0.5/0.6 = 0.8 | 0~∞ | 1 미만: a 의 예측 양성 비율이 높음. 1: 인구통계 평등(demographic parity). 1 초과: d 가 높음 | 〔S25〕〔S29〕 |
| CDDPL | Conditional Demographic Disparity in Predicted Labels | facet 전체와 하위 그룹별 예측 레이블의 거절·수락 격차(하위 그룹 크기로 가중 평균) | −1~+1 | 양수: d 가 예측 수락보다 거절 비율이 큼. 0 근처: 평균적으로 격차 없음. 음수: a 가 거절 비율이 큼. 심슨 역설을 배제하려고 하위 그룹으로 조건화 | 〔S25〕〔S35〕 |
| FT | Counterfactual Fliptest | facet d 의 각 구성원과 가장 비슷한 facet a 구성원(k-최근접 이웃)의 예측이 다른지 | 이진·다중 −1~+1 (연속 레이블은 임계값으로 이진화) | 양수: d 에 불리한 반사실 결정이 유리한 결정보다 많음 | 〔S25〕〔S34〕 |
| AD | Accuracy Difference | facet 간 **예측 정확도 차** (ACCa − ACCd) | −1~+1 | 양수: a 의 정확도가 높아 d 가 FP·FN 을 더 겪음(d 에 대한 잠재 편향). 한계: Type I 과 Type II 오류를 구분하지 못함 | 〔S25〕〔S30〕 |
| RD | Recall Difference | facet 간 **재현율(TPR) 차** (TPRa − TPRd) | 이진·다중 −1~+1 (연속 레이블 불가) | 양수: 모델이 a 의 진짜 양성을 더 많이 찾음 → d 에 불리 | 〔S25〕〔S31〕 |
| SD | Specificity difference | facet 간 **특이도(TNR) 차** | 이진·다중 −1~+1 | 문서 요약표 기준 양수: 모델이 d 에서 FP 를 덜 만든다고 보고 d 에 불리하다고 표기 | 〔S25〕 |
| DAR | Difference in Acceptance Rates | facet 간 **정밀도 차** — 예측 양성 중 TP 비율 TP/(TP+FP) 의 차 | −1~+1 | 양수: d 에서 FP 가 상대적으로 더 많아 d 에 불리 | 〔S25〕 |
| DRR | Difference in Rejection Rates | facet 간 음성 예측의 정밀도 차 — TN/(TN+FN) 비율의 차 | −1~+1 | 양수: a 에서 FN 이 상대적으로 더 많아 생기는 편향 | 〔S25〕 |
| DCAcc | Difference in Conditional Acceptance | 관측 양성 대비 예측 양성(수락) 비율의 facet 간 차 | (−∞,+∞) | ⚠️ 부호 해석이 요약표와 개별 페이지에서 상충 — 섹션 9 [G-2.3-2] | 〔S25〕 |
| DCR | Difference in Conditional Rejection | 관측 음성 대비 예측 음성(거절) 비율의 facet 간 차 | (−∞,+∞) | ⚠️ 위와 같은 상충 — 섹션 9 [G-2.3-2] | 〔S25〕 |
| TE | Treatment Equality | facet 간 **FP 와 FN 비율**의 차. 개별 페이지 식은 FNd/FPd − FNa/FPa. FPa 또는 FPd 가 0 이면 무한대 | 이진·다중 (−∞,+∞) (연속 레이블 정의 없음) | ⚠️ 요약표와 개별 페이지의 정의·부호 설명이 다름 — 섹션 9 [G-2.3-2] | 〔S25〕〔S32〕 |
| GE | Generalized entropy | 예측이 개별 입력에 준 **혜택(b = y′ − y + 1)의 불평등**. 지수 가중치 alpha = 2. facet 의 유리·불리와 무관 | 이진·다중 (0, 0.5) | 0: 불평등 없음(모두 정답이거나 모두 FP). 0.5: 최대 불평등. 모두 FN 이면 정의되지 않음 | 〔S25〕〔S33〕 |

**시험 단서 → 지표 (요약표의 예시 질문을 한 줄로)** 〔S25〕
- "그룹 간 **예측 양성 비율**이 다른가?" → DPPL(차이), DI(비율), 하위 그룹까지 보려면 CDDPL.
- "모델이 그룹마다 **같은 정확도**로 맞히는가?" → AD. "**재현율**이 그룹마다 다른가?" → RD. "**특이도**가 다른가?" → SD. "대출 *수락* 예측의 **정밀도**가 같은가?" → DAR. "대출 *거절* 예측의 정밀도가 같은가?" → DRR. "FP 대 FN 의 상대 비율이 그룹마다 같은가?" → TE.
- "관측된 수락(거절)이 예측 수락(거절)과 그룹마다 다르게 어긋나는가?" → DCAcc(수락) / DCR(거절).
- "모든 특성이 비슷한 다른 그룹 사람과 **예측이 다른가**?" → FT. "두 후보 모델 중 어느 쪽 결과 분포가 더 **불평등**한가?" → GE.

**사전 지표와의 짝**: 사전 DPL(관측 레이블의 양성 비율 차) ↔ 사후 DPPL(예측 레이블의 양성 비율 차), 사전 CDD ↔ 사후 CDDPL(관측 대신 예측 레이블로 계산한 같은 지표) 〔S28〕〔S35〕. CDDPL 문서는 이 지표가 사전 CDD 와 같되 관측 레이블 대신 예측 레이블로 계산한다는 점만 다르다고 설명한다 〔S35〕.

> 🧠 원리: 사후 지표의 상당수는 facet 별 혼동 행렬(TP·FP·TN·FN)에서 나온다. RD 는 TPR(재현율)의 차, SD 는 TNR(특이도)의 차, DAR·DRR 은 정밀도 계열의 차, AD 는 정확도의 차이므로, 2.1 의 분류 지표 정의를 그대로 facet a·d 에 적용한 것이다 〔S25〕〔S30〕〔S31〕.

### 2.11 Clarify 로 모델 출력 해석(SK5): SHAP, PDP, 기준선, 결과 읽기 ⚠️

Clarify 의 설명 가능성은 **모델에 무관한(model-agnostic) 특성 기여도** 방식이다. 훈련 후 "왜 이 예측이 나왔나"를 이해하고, 추론 중 인스턴스별 설명을 줄 수 있다. 구현은 SHAP 의 확장 가능한 구현이고, PDP 는 특성이 예측 결과에 주는 한계 효과를 보여 준다. 컴퓨터 비전(CV)·자연어(NLP)도 같은 SHAP 알고리즘으로 설명한다 〔S36〕. 기여도 분석은 디버깅에도 쓰인다. 모델이 잡음이거나 무관한 특성으로 추론하는지 확인할 수 있기 때문이다 〔S22〕.

| 방법 | 답하는 질문 | 산출물 | 요구사항·특징 | 근거 |
|---|---|---|---|---|
| **SHAP(Shapley 값)** | 각 특성이 이 예측(로컬) 또는 모델 전체(글로벌)에 얼마나 기여했나 | 로컬 SHAP 값(인스턴스별), 글로벌 SHAP 값(집계), `expected_value`, 상위 최대 10개 글로벌 SHAP 막대 차트 | 훈련된 모델 필요. Kernel SHAP. 기준선(baseline) 필요 | 〔S22〕〔S37〕〔S39〕〔S40〕 |
| **PDP(부분 의존성 도표)** | 한 특성 값을 바꾸면 예측이 평균적으로 어떻게 변하나 (다른 특성은 주변화) | 특성별 `feature_values`(버킷 중앙값)·`data_distribution`·`model_predictions`, PDP 차트(x = 특성값, y = 예측) | 훈련된 모델 필요. `grid_resolution` 으로 버킷 수 지정 | 〔S22〕〔S36〕〔S40〕 |
| **CV 설명** | 이미지의 어느 부분(슈퍼픽셀)이 예측에 영향을 줬나 | 슈퍼픽셀별 SHAP 값의 **히트 맵** 이미지 | `image_config`(`model_type`: `IMAGE_CLASSIFICATION`·`OBJECT_DETECTION`) | 〔S39〕〔S40〕 |
| **NLP 설명** | 어떤 토큰·문장이 예측에 기여했나 | 단위별 로컬 SHAP, 상위 토큰의 글로벌 SHAP(`global_top_shap_text`) | `text_config`(`granularity`: `token`·`sentence`·`paragraph`) | 〔S39〕〔S40〕 |
| **시계열 설명** | 예측에 시간 단계·입력 변수가 얼마나 기여했나 | 비대칭 Shapley 값(`timewise` 또는 `fine_grained`) | `asymmetric_shapley_value`(`direction`: `chronological`·`anti_chronological`·`bidirectional`) | 〔S39〕〔S40〕 |

**Shapley 값의 원리** — 예측을 "게임", 모델에 들어간 특성을 "플레이어"로 본다. 특성 d 개면 가능한 특성 조합이 2^d 개라 모델을 모두 훈련하는 것은 비현실적이므로 Clarify 는 근사를 담은 SHAP 의 효율적 Kernel SHAP 구현을 쓴다. 특성별 Shapley 값의 합은 모델 예측과 특성이 없는 더미 모델 예측의 차이에 해당한다 〔S37〕.

**기준선(baseline) — 설명이 "대비"라서 중요하다** 〔S38〕
- 설명은 기준선과의 편차를 설명하므로 같은 예측도 기준선에 따라 설명이 달라진다. 기준선은 정보가 적은 가상 인스턴스(수치 특성은 평균·중앙값, 범주 특성은 최빈값)일 수도, 특정 집단을 대표하는 정보적 인스턴스일 수도 있다.
- 기준선(`baseline`)을 주지 않으면 입력 데이터를 K-means·K-prototypes 로 클러스터링해 자동 계산한다 〔S38〕. 이때 데이터셋을 1~12 사이의 적정 클러스터 수로 나누며(`num_clusters` 로 클러스터 수를 직접 줄 수 있다), 기준선 인스턴스 수는 합성 데이터셋 크기와 SHAP 작업 시간에 직접 영향을 준다 〔S39〕. 자동 생성된 기준선은 `explanations_shap/baseline.csv` 에 저장된다 〔S40〕.

**SHAP 설정(`shap`)과 재현성** 〔S39〕
- `num_samples`: Kernel SHAP 샘플 수. 합성 데이터셋 크기와 작업 시간에 직접 영향(정밀도 대 시간 절충).
- `seed`: SHAP explainer 의 의사 난수 생성기 초기값. 지정하면 같은 작업에서 일관된 SHAP 값이 나오고, 지정하지 않으면 같은 작업을 다시 돌릴 때 SHAP 값이 조금 달라질 수 있다.
- `agg_method`: 로컬 → 글로벌 집계 방식. 기본값 `mean_abs`(절댓값 평균), 그 밖에 `mean_sq`(제곱 평균), `median`.
- `use_logit`(기본 `false`), `save_local_shap_values`(기본 `false`), `features_to_explain`.

**PDP 설정(`pdp`)** 〔S39〕: `features`(SHAP 을 요청하지 않으면 필수), `top_k_features`(`features` 없이 SHAP 을 요청하면 SHAP 기여도 상위 특성을 골라 PDP 를 그림, 기본 10), `grid_resolution`(수치 특성 범위를 나눌 버킷 수).

**결과 파일 읽기** 〔S40〕
- `analysis.json`: 편향 지표와 특성 중요도(JSON). `report.ipynb` 등 보고서(설정의 `report` 로 Notebook·HTML·PDF 세 벌 생성) 〔S39〕. `explanations_shap/out.csv`: 로컬 SHAP 값(`save_local_shap_values` 를 켠 경우).
- SHAP 결과는 `explanations → kernel_shap → <레이블> → global_shap_values`(특성별 글로벌 값)와 `expected_value`(기준선 데이터셋의 평균 예측)에 있다. 글로벌 값은 로컬 값을 `agg_method` 로 집계한 것이다.
- 로컬 SHAP 은 개별 인스턴스에서의 특성 중요도, 글로벌 SHAP 은 데이터셋 전체에서의 집계다. 이미지 히트 맵에서는 큰 양수가 예측과 강한 양의 상관, 큰 음수가 강한 음의 상관, 절댓값이 클수록 관계가 강하다.

**실시간(온라인) 설명** — 실시간 추론 엔드포인트에 Clarify explainer 를 붙이면 `InvokeEndpoint` 응답에 예측과 설명(특성 기여도)이 함께 온다. 엔드포인트 구성(`CreateEndpointConfig`)에 Clarify explainer 설정을 넣고, explainer 가 모델 컨테이너에 예측을 요청한 뒤 기여도를 계산해 반환한다 〔S41〕.

**운영 주의** 〔S39〕
- 예측이 필요한 분석(`shap`·`pdp`·`post_training_bias`)에서 모델 이름(`model_name`)을 주면 Clarify 가 임시 엔드포인트(**shadow endpoint**)를 만들고 계산이 끝나면 삭제한다. 이 이름은 SageMaker 섀도 테스트의 *shadow variant* 와 무관하다(섹션 4 짝 3).
- 기존 엔드포인트(`endpoint_name`)를 지정하면 부트스트랩 시간은 줄지만 엔드포인트 부하가 커지고, `shap`·`pdp` 가 보낸 합성 데이터가 엔드포인트 지표·캡처 데이터를 오염시킬 수 있어 프로덕션 엔드포인트 사용은 권장되지 않는다.
- ML Lens 는 이해관계자 신뢰와 규제 준수를 위해 Clarify 로 특성 중요도 설명을 만들고, 모델 복잡도와 설명 가능성 사이의 절충을 고려하라고 안내한다 〔S14〕.

> 🧠 원리: Shapley 값은 "특성이 있을 때와 없을 때(기준선 값으로 대체)의 예측 차이"를 특성 조합 전반에 걸쳐 평균한 값이다. Clarify 는 기준선과 입력 인스턴스 사이에 여러 합성 인스턴스를 만들어(특성의 부재 = 기준선 값, 존재 = 입력값) 이를 계산하므로 기준선과 `num_samples` 가 결과와 실행 시간을 좌우한다 〔S37〕〔S38〕〔S39〕.

### 2.14 섀도 변형 vs 프로덕션 변형: 성능 비교 (SK4)

엔드포인트 하나 뒤에 여러 모델·버전을 **변형(variant)** 으로 둘 수 있다. 변형은 ML 인스턴스와 SageMaker 모델에 지정된 서빙 구성요소로 이뤄지고, 같은 엔드포인트 뒤의 모든 변형은 같은 추론 코드를 공유하며, 변형마다 인스턴스 유형이나 모델이 달라도 되고 서로 독립적으로 오토스케일 된다. 변형 유형은 **production variant** 와 **shadow variant** 두 가지다 〔S58〕.

| 항목 | 섀도 변형(섀도 테스트) | 프로덕션 변형 가중치(A/B 테스트) | 근거 |
|---|---|---|---|
| 요청 처리 | 프로덕션 변형이 들어오는 요청의 100% 를 받아 응답한다. 섀도 변형은 복제된 일부 요청을 받지만 **응답을 반환하지 않는다** | 프로덕션 변형이 여러 개면 요청은 가중치에 따라 **한 변형에만** 라우팅되고 그 변형이 호출자에게 응답한다 | 〔S60〕〔S58〕 |
| 사용자 영향 | 없음. 호출 앱에는 프로덕션 변형 응답만 반환되고, 섀도 응답은 폐기하거나 오프라인 비교용으로 기록한다 | 새 변형으로 간 요청의 응답이 실제 사용자에게 간다 | 〔S59〕〔S58〕 |
| 쓰는 이유 | 모델·컨테이너·인스턴스 변경을 사용자 영향 없이 검증. 오프라인 검증을 마친 새 모델을 승격하기 전에 지연 시간·오류율 같은 운영 성능을 보려 할 때 | 새 모델과 기존 모델을 실제 트래픽으로 비교해 더 나은 쪽으로 교체(새 모델 검증의 마지막 단계로 효과적) | 〔S59〕〔S63〕 |
| 설정(콘솔) | SageMaker AI 콘솔 **Inference → Shadow tests → Create shadow test**. 기존 엔드포인트에서 실행하거나 새 엔드포인트를 만들어 실행 | 엔드포인트 구성에서 변형별 가중치 지정 | 〔S60〕〔S63〕 |
| 설정(API) | `CreateEndpointConfig` 의 `ShadowProductionVariants` 에 섀도 변형 지정. 또는 추론 실험 `CreateInferenceExperiment`: `Type` = `ShadowMode`, `ShadowModeConfig`(`SourceModelVariantName` = 모든 요청을 받는 프로덕션 변형, `ShadowModelVariants` 1개 = `ShadowModelVariantName` + `SamplingPercentage`), `Schedule`, 선택적 `DataStorageConfig`(요청·응답 데이터 캡처용 S3) | `ProductionVariants` 항목의 `InitialVariantWeight`(미지정 기본 1.0, 트래픽 비율 = 해당 가중치 ÷ 모든 변형 가중치의 합). `InvokeEndpoint` 의 `TargetVariant`(지정하면 무작위 가중치 분배보다 우선). `UpdateEndpointWeightsAndCapacities`(엔드포인트 갱신 없이 가중치 변경) | 〔S64〕〔S65〕〔S76〕〔S66〕〔S67〕〔S63〕 |
| 개수 제한 | 엔드포인트당 shadow variant 최대 1개이고, 섀도 변형이 있으면 production variant 도 최대 1개. 추론 실험의 `ModelVariants` 는 1~2개 | production variant 를 여러 개 둘 수 있음 | 〔S60〕〔S65〕〔S58〕 |
| 기간 | 시작 시각·기간을 정한다. 기본 7일, 최소 1시간·최대 30일. API 에서 `Schedule` 을 안 주면 즉시 시작해 7일 뒤 종료. 끝나면 엔드포인트가 시험 이전 상태로 복귀 | 기간 개념 없음. 가중치를 직접 조정 | 〔S60〕〔S65〕 |
| 섀도 비율 조정 | `SamplingPercentage`(최대 100). 예약 중·진행 중에도 트래픽 샘플링 비율 변경 가능 | 가중치 변경 | 〔S66〕〔S60〕 |
| 비교에 쓰는 지표 | 콘솔 대시보드가 프로덕션·섀도 변형의 호출·인스턴스 지표를 나란히 보여 줌: `Invocations`, `InvocationsPerInstance`, `ModelLatency`, `Invocation4XXErrors`, `Invocation5XXErrors`, `InvocationModelErrors`, `CPUUtilization`, `MemoryUtilization`, `DiskUtilization`. 오류가 적을수록 안정적인 모델, 지연이 낮을수록 빠른 모델 또는 인프라. **정확도 같은 모델 품질**은 Data Capture 로 요청·응답을 기록해 오프라인으로 비교 | 변형별 `Latency`, `Invocations` 등이 CloudWatch 로 나감. 예제는 변형마다 정확도·정밀도·재현율·F1·ROC/AUC 를 계산해 비교하고 더 나은 변형으로 트래픽을 옮김 | 〔S61〕〔S60〕〔S59〕〔S63〕 |
| 승격 | 대시보드의 **Deploy shadow variant**(진행 중이면 먼저 테스트를 완료). 인스턴스 설정 3옵션: 프로덕션 설정 유지 / 섀도 설정 유지 / 사용자 지정. 섀도·사용자 지정 설정을 쓰려면 100% 트래픽 샘플링으로 시험하라고 권장. 승격하면 기존 프로덕션 변형은 엔드포인트에서 빠지고 섀도 변형이 대체 | `UpdateEndpointWeightsAndCapacities` 로 가중치를 옮김(예: 50:50 → 25:75 → 0:100 후 이전 변형 삭제) | 〔S62〕〔S63〕 |
| 호환되지 않는 엔드포인트 | 서버리스 추론, 비동기 추론, Marketplace 컨테이너, 다중 컨테이너 엔드포인트, 다중 모델 엔드포인트, Inf1(Inferentia 기반) 인스턴스는 섀도 테스트 불가(설정 시 검증 오류) | 문서에 같은 제한 목록 없음 | 〔S59〕 |

- **성능 비교 관점의 정리**: 섀도 테스트의 기본 산출물은 *운영 성능*(지연 시간·오류율·자원 사용률)이다. 예측의 *정확도*를 비교하려면 Data Capture 로 섀도 응답을 로깅해 오프라인에서 정답과 대조한다 〔S59〕〔S60〕. 반대로 A/B 는 실제 응답이 사용자에게 가므로 변형별 정확도·정밀도·재현율·F1·AUC 평가까지 한 뒤 가중치를 옮긴다 〔S63〕.
- 엔드포인트 구성으로 직접 만드는 섀도 변형(`ShadowProductionVariants`)은 문서가 *장기 실행(long running)* 섀도 변형으로 소개한다. 반면 콘솔·`CreateInferenceExperiment` 기반 섀도 테스트에는 최소 1시간·최대 30일의 기간이 있다 〔S64〕〔S60〕.
- Model Monitor·Debugger 와 달리 섀도 테스트·A/B 는 이번 공지(2026-07-30 중단)의 대상이 아니다 〔S21〕.

> 🧠 원리: 섀도는 "요청을 복제하되 응답은 버리는" 구조라 사용자는 프로덕션 변형 응답만 받고, 새 변형의 지연·오류를 실제 트래픽에서 안전하게 측정한다 〔S59〕. A/B 는 "요청을 가중치로 나눠 한 변형에만 보내는" 구조라 각 변형의 응답이 사용자에게 가므로 두 모델을 실제 결과로 비교할 수 있는 대신 새 변형의 응답이 사용자에게 전달된다 〔S58〕.

### 2.15 모델 성능·훈련 시간·비용의 절충 평가 (SK2)

ML Lens(MLPERF04-BP05)는 트레이드오프 분석을 "경쟁하는 요구(정확도·복잡도·편향·공정성·운영 제약)를 균형 맞추는 모델 구성을 찾는 일"로 정의하고, 한 번 하고 끝나는 활동이 아니라 ML 수명주기 내내 다시 평가하라고 한다. 안티패턴은 정확도만 보는 것, 편향을 무시하는 것, 단순 모델로 충분한데 복잡한 모델을 배포하는 것이다 〔S14〕. 구체 수단별 영향은 다음과 같다(각 수단의 상세 설정은 Task 2.2 영역이므로 여기서는 절충만 다룬다).

| 수단 | 훈련 시간 | 비용 | 성능·주의 | 근거 |
|---|---|---|---|---|
| **AMT 조기 종료**(`TrainingJobEarlyStoppingType` = `AUTO`) | 개선이 없는 훈련 작업을 일찍 멈춰 계산 시간 감소 | 같은 이유로 감소 | 과적합 방지. 각 epoch 후 목적 지표를 이전 작업들의 러닝 평균 중앙값과 비교해 더 나쁘면 중지. 알고리즘이 epoch 마다 목적 지표를 내야 함(XGBoost, Linear Learner 는 `objective_loss` 일 때만 등) | 〔S68〕 |
| **튜닝 전략 선택** | 큰 작업은 Hyperband 가 계산 시간을 줄임(저성능 작업 조기 중지·자원 재할당). Bayesian 은 순차적이라 크게 확장되지 않음. random search 는 병렬 작업을 가장 많이 돌림 | — | 작은 훈련 작업은 random 또는 Bayesian. 결과 재현·투명성이 중요하면 grid search | 〔S57〕 |
| **탐색 공간 축소** | 한 번에 최대 30개 하이퍼파라미터를 지정할 수 있지만 수를 줄이면 계산 시간이 줄어 최적 구성에 더 빨리 수렴. 범위가 너무 넓으면 계산 시간이 길어짐 | 계산 시간에 비례 | 범위가 너무 넓으면 일반화가 약한 모델이 나올 수 있음. 로그 스케일 하이퍼파라미터는 `ScalingType` 을 맞추면(또는 `Auto`) 탐색이 효율적 | 〔S57〕 |
| **병렬 훈련 작업 수**(`MaxParallelTrainingJobs`) | 튜닝 작업이 병렬로 띄울 수 있는 훈련 작업 수의 상한 | 리전·계정 컴퓨팅 한도 안에서 선택 | 이전 시도 결과로 다음 시도를 개선하므로 "의미 있는 증분 결과를 주는 최대 병렬 수"를 고르라고 안내 | 〔S57〕 |
| **관리형 스팟 훈련** | 스팟 중단으로 시작·완료가 늦어질 수 있음 | 온디맨드 대비 최대 90% 절감 | 체크포인트를 쓰면 마지막 체크포인트에서 재개. `MaxWaitTimeInSeconds` 는 `MaxRuntimeInSeconds` 보다 커야 함. 온디맨드로 전환되지 않음. 체크포인트가 없는 내장 알고리즘은 `MaxWaitTimeInSeconds` 3600초(60분) 제한 | 〔S69〕 |

| **Autopilot 훈련 모드** | 앙상블 모드 10 trial, HPO 모드 기본 최대 100 trial | trial 수에 비례 | 100 MB 미만 데이터셋은 최적의 실행 시간·성능을 위해 앙상블 모드 권장. Auto 모드는 100 MB 초과면 HPO 선택 | 〔S70〕 |
| **분산 훈련** | 훈련 시간 단축(문서 목적) | 문서는 통신 오버헤드만 언급 | 클러스터가 커질수록 노드 간 통신 오버헤드가 늘어 전체 계산 성능이 떨어진다. 노드·전역 배치를 늘리면 학습률도 올리고 점진적 워밍업을 쓴다 | 〔S71〕〔S73〕 |
| **인스턴스 크기·유형** | 단순 모델은 큰 인스턴스에서 더 빨라지지 않고 GPU 통신 오버헤드로 더 느려질 수도 있음 | 불필요하게 큰 인스턴스는 낭비 | 작은 인스턴스로 시작해 성능 데이터가 있을 때만 키우고, CPU·GPU 를 둘 다 실험해 비용-구성을 비교 | 〔S72〕 |
| **모델 복잡도** | — | — | 단순 모델이 더 설명하기 쉽고 배포하기 쉽지만 정확도를 일부 포기할 수 있음. 단순 선형 모델부터 딥러닝까지 복잡도별로 시험해 성능을 비교하고, 복잡도·설명 가능성·편향·공정성을 함께 평가(Clarify) | 〔S14〕 |
| **임계값·편향-분산** | — | — | 정밀도 대 재현율은 오류 유형별 상대 비용으로 임계값을 조정. 과소적합(높은 편향)·과적합(높은 분산)은 체계적 실험으로 균형 | 〔S14〕 |

**상황별 선택**
- 훈련·튜닝이 오래 걸리는 큰 작업 → Hyperband + 조기 종료, 하이퍼파라미터 수·범위 축소 〔S57〕〔S68〕.
- 중단돼도 되는 훈련을 싸게 → 관리형 스팟 + 체크포인트 〔S69〕.
- 작은 데이터에서 견고한 일반화 → 교차 검증(시간 약 20% 증가 감수) 〔S1〕.
- 작은 표 형식 데이터(100 MB 미만)의 Autopilot → 앙상블 모드 〔S70〕.
- 큰 딥러닝 모델의 시간 단축 → 분산 훈련(통신 오버헤드·학습률 조정 고려) 〔S71〕〔S73〕.
- ⚠️ 자원 활용률(GPU·CPU)로 인스턴스를 줄이는 근거는 원래 Debugger 의 시스템 모니터링이 제공했으나 Debugger 는 신규 고객 중단이며 대체는 CloudWatch 다 〔S72〕〔S48〕.

> 🧠 원리: AMT 문서에 따르면 튜닝 작업의 계산 복잡도는 하이퍼파라미터 수와 탐색할 값의 범위에 좌우된다 〔S57〕. 분산 훈련 문서에 따르면 클러스터가 커질수록 노드 간 통신 오버헤드가 늘어 전체 계산 성능이 떨어진다 〔S71〕. 스팟 훈련은 스팟 가격이 온디맨드 대비 할인이라 청구 시간이 훈련 시간보다 짧아지지만 중단으로 완료가 늦어질 수 있다 〔S69〕. 한 수단이 시간이나 비용 한 축을 줄이면 성능·안정성 쪽에서 대가를 치를 수 있으므로 기준 모델 대비 개선과 함께 평가한다 〔S14〕.

## 3. 시험에서 묻는 방식

### 패턴 1. 오류 비용·클래스 불균형을 보고 평가 지표를 고른다 (K1·SK1)
- 시나리오 단서: 사기 거래·희귀 질환·장비 고장처럼 **양성이 전체의 극소수**이고 놓치면 손실이 큼 / 오탐(거짓 경보)의 비용이 큼(안전 승인 시스템 등) / "정확도가 99% 인데 쓸모없다" / 임계값을 바꿔도 모델을 공정하게 비교하고 싶음 / 회귀에서 큰 오차·이상치가 치명적 / 단위가 다른 데이터셋끼리 오차 비교
- 정답 방향: FN 비용이 크면 **Recall**(필요하면 임계값을 낮춤), FP 비용이 크면 **Precision**, 둘 다 중요하면 **F1**(조화평균) 또는 비용에 맞춘 임계값 조정. 불균형이면 **BalancedAccuracy·AUPRC(PR 곡선)·F1**(TN 수를 무시하는 AUPRC 가 TN 이 압도적인 데이터에 유리). 임계값과 무관한 모델 비교는 **AUC**, 확률 출력의 품질은 **LogLoss**. 회귀는 **RMSE**(큰 오차·이상치에 민감, 스케일 의존)·**MAE**·**R2**. 다중 분류는 **F1macro·PrecisionMacro·RecallMacro**
- 오답 유인(섞이는 선택지): Accuracy(불균형에서 왜곡) / "Recall 을 높이면 Precision 도 같이 오른다"(임계값에 따른 트레이드오프) / ROC-AUC 와 PR-AUC 혼동 / 분류 지표(F1·AUC)를 회귀에 적용 / RMSE·MAE·R2 혼동 / **훈련 데이터**에서 잰 지표를 일반화 성능으로 해석
- 근거: 〔S1〕〔S2〕〔S3〕〔S14〕

### 패턴 2. Clarify 의 사전·사후 편향 지표와 설명 도구(SHAP·PDP)를 구분한다 (K4·SK1·SK5) ⚠️
- 시나리오 단서: **훈련 전** 데이터셋에서 연령·성별 같은 그룹 간 표본 수·레이블 비율 불균형을 확인하고 싶고 모델이 아직 없음 / 훈련된 모델이 그룹별로 승인 비율을 다르게 예측함 / 그룹별 재현율·정밀도·정확도 격차 / "어떤 특성이 이 예측에 가장 기여했나" / "한 특성 값을 바꾸면 예측이 어떻게 변하나" / 이미지 모델이 어느 영역을 봤는지 / 새 계정이라 Clarify 를 쓸 수 없음
- 정답 방향: 훈련 전 데이터는 **사전 지표**(CI·DPL·KL·JS·LP·TVD·KS·CDD, 모델 비의존), 훈련 후 예측 격차는 **사후 지표**(DPPL·DI·AD·RD·SD·DAR·DRR·TE·DCAcc·DCR·CDDPL·FT·GE, 모델 예측 필요). 특성 기여도는 **SHAP**(로컬·글로벌), 특성 값 변화에 따른 예측 변화는 **PDP**, 이미지는 슈퍼픽셀 SHAP **히트 맵**. ⚠️ 신규 고객에게 닫힌 Clarify 의 대체는 표준 지표 산식을 pandas·scikit-learn 으로 계산하고 SHAP 라이브러리를 직접 쓰며 결과를 SageMaker AI MLflow 에 기록
- 오답 유인(섞이는 선택지): Model Monitor(운영 중 드리프트 감시) / Debugger `class_imbalance`(학습 중 클래스 간 표본 불균형, facet 편향이 아님) / Ground Truth·A2I(레이블링·사람 검토 서비스로 이 Task 범위 밖) / Amazon Bedrock Evaluations(FM 평가 전용, 예측형 편향·설명 대체 아님) / 사후 지표를 모델 없이 계산할 수 있다는 보기
- 근거: 〔S22〕〔S24〕〔S25〕〔S36〕〔S20〕

### 패턴 3. 훈련 곡선과 Debugger 규칙으로 과적합·과소적합·수렴 문제를 진단하고 조치한다 (K3·K5·SK6) ⚠️
- 시나리오 단서: 훈련 정확도는 높은데 검증 정확도가 크게 낮음 / 훈련·검증이 모두 낮음 / 손실이 줄지 않거나 NaN·무한대 / 기울기가 거의 0 / 검증 손실이 다시 올라감 / 새 텐서 출력 없이 학습이 멈춤 / ReLU 출력이 대부분 0 / 입력 이미지 정규화 이상
- 정답 방향: 과적합(높은 분산) → 정규화↑, 훈련 데이터↑, 조기 종료, 특성 선택·모델 단순화, 교차 검증으로 확인. 과소적합(높은 편향) → 모델 유연성·특성↑, 정규화↓, 에포크↑. - 오답 유인(섞이는 선택지): Clarify(편향·설명 도구, 수렴 진단 아님) / Model Monitor(배포 후 데이터·모델 품질 드리프트) / Profiler(GPU·CPU 병목, ⚠️ 2027-06-30 지원 종료) / 과적합인데 모델 크기를 더 키우는 조치 / 훈련 데이터 정확도만 보고 판단
- 근거: 〔S10〕〔S12〕〔S43〕〔S44〕〔S48〕

### 짝 1. 사전(pre-training) 편향 지표 vs 사후(post-training) 편향 지표 ⚠️

| | 사전 편향 지표 | 사후 편향 지표 |
|---|---|---|
| 입력 | 관측 레이블·facet(모델 출력에 의존하지 않음) | 데이터·레이블 + 예측 레이블(모델 또는 예측 결과 데이터셋) |

| 짝지어 보는 지표 | DPL, CDD | DPPL(DPL 의 예측 레이블 버전), CDDPL(CDD 의 예측 레이블 버전) |

### 짝 2. 섀도 변형(shadow variant) vs 프로덕션 변형 가중치(A/B)
- 구분 기준: **응답이 사용자에게 가는가**, 요청을 복제하는가 나누는가.

| | 섀도 변형 | 프로덕션 변형 A/B |
|---|---|---|
| 요청 | 프로덕션 변형이 100% 응답. 섀도는 복제본 일부만 받고 응답 안 함 | 가중치대로 요청이 한 변형에만 라우팅 |
| 사용자 영향 | 없음 | 새 변형으로 간 요청의 응답이 사용자에게 감 |
| 설정 키워드 | `ShadowProductionVariants`, `ShadowModeConfig`, `SamplingPercentage`, 콘솔 Inference → Shadow tests | `InitialVariantWeight`, `TargetVariant`, `UpdateEndpointWeightsAndCapacities` |
| 비교 | 지연·오류·자원 대시보드(품질은 Data Capture 로 오프라인) | 변형별 CloudWatch 지표와 정확도·F1·AUC 등 직접 평가 |
| 제약 | 서버리스·비동기·다중 모델·다중 컨테이너·Marketplace·Inf1 불가, 변형 최대 1개 | 문서에 같은 제한 없음 |

### 짝 3. Clarify 의 shadow endpoint vs 섀도 테스트의 shadow variant
- 구분 기준: 이름만 비슷하다. Clarify 의 shadow endpoint 는 **분석 작업용 임시 엔드포인트**이고, shadow variant 는 **운영 엔드포인트 뒤에서 요청 사본을 받는 변형**이다.
- Clarify: 분석 설정에 `model_name` 을 주면 처리 작업이 모델 이름으로 임시 엔드포인트(shadow endpoint)를 만들어 예측을 얻고 계산이 끝나면 삭제한다. 이미 있는 엔드포인트를 쓰려면 `endpoint_name` 을 주고, 이 값이 `model_name` 보다 우선한다 〔S39〕.
- 섀도 테스트: 운영 엔드포인트의 production variant 에 요청을 보내고 그 복제본을 shadow variant 가 받는다 〔S59〕〔S60〕.

### 짝 4. 정밀도 vs 재현율 / ROC-AUC vs PR-AUC / Accuracy vs BalancedAccuracy
- 구분 기준:

| 쌍 | 구분 |
|---|---|
| Precision vs Recall | 분모가 TP+FP 인가 TP+FN 인가. FP 비용이 크면 Precision, FN 비용이 크면 Recall. 임계값을 올리면 FP 가 줄고 FN 이 늘며, 정밀도와 재현율은 서로 트레이드오프 관계 |
| ROC-AUC vs PR-AUC(AUPRC) | ROC 는 FPR(분모에 TN 포함)과 TPR, PR 곡선은 Precision 과 Recall 이며 TN 을 고려하지 않아 TN 이 압도적인 불균형 데이터에 유리. 둘 다 임계값 전반을 요약하고 AUC 0.5 는 무작위 수준 |
| Accuracy vs BalancedAccuracy | Accuracy 는 전체 정답률, BalancedAccuracy 는 양성·음성 각각의 정답률을 평균(0.5·((TP/P)+(TN/N)))해 불균형에서 더 적절 |
| 성능 지표 vs 편향 지표 | RD·DAR·AD 는 Recall·Precision·Accuracy 를 facet a·d 사이의 **차이**로 바꾼 값 — 모델 전체 성능이 아니라 그룹 간 격차를 본다 |

- 근거: 〔S1〕〔S2〕〔S25〕

### 짝 5. 과적합(overfitting) vs 과소적합(underfitting)

|---|---|---|
| 훈련 성능 | 나쁨 | 좋음 |
| 평가·테스트 성능 | 나쁨 | 훈련보다 훨씬 나쁨(큰 격차) |
| 편향·분산 | 높은 편향 | 높은 분산 |
| 조치 | 특성·모델 유연성↑, 정규화↓, 에포크↑ | 정규화↑, 특성 선택, 데이터↑, 조기 종료, 앙상블, 증강 |

- 근거: 〔S10〕〔S12〕

### 짝 7. SHAP vs PDP (로컬·글로벌 기여도 vs 한계 효과)
- 구분 기준: 질문이 "각 특성이 **이 예측에 얼마나 기여**했나"(SHAP)인지 "한 특성을 **바꾸면 예측이 평균적으로 어떻게 변하나**"(PDP)인지.

| | SHAP | PDP |
|---|---|---|
| 산출 | 로컬(인스턴스별)·글로벌(`agg_method` 로 집계) 기여도, `expected_value` | 특성별 `feature_values`·`data_distribution`·`model_predictions` 곡선 |
| 필요 | 기준선(baseline), Kernel SHAP, 훈련된 모델 | 훈련된 모델. `features` 또는 SHAP 요청(`top_k_features`) |
| 설정 | `shap`: `baseline`·`num_samples`·`seed`·`agg_method` | `pdp`: `features`·`top_k_features`·`grid_resolution` |

- 근거: 〔S36〕〔S37〕〔S39〕〔S40〕

### 짝 8. 세 가지 baseline: 성능 기준선 vs Model Monitor 기준선 vs SHAP 기준선 ⚠️
- 구분 기준: **무엇과 비교하려는 기준인가**.

| | 성능 기준선 | Model Monitor 기준선 | SHAP 기준선 |

### 짝 10. RMSE vs MAE vs R2 (회귀 지표)
- 구분 기준: **오차의 크기·단위를 보는가(RMSE·MAE) 설명력을 보는가(R2)**, 큰 오차에 민감한가.
- RMSE: 큰 오차·이상치에 민감, 스케일 의존이라 크기가 다른 데이터셋 비교 금지. MAE: 절대 오차의 평균. R2: 분산 설명 비율, 음수면 상수 함수보다 못함 〔S1〕.
- 근거: 〔S1〕

## 6. 자가 점검 문항 후보

### 후보 1 (난이도: associate)
- 대응 Skill: K1 / SK1
- 문제: 신용카드 사기 탐지 이진 분류 모델을 평가한다. 사기 거래는 전체의 0.3% 이고, 사기를 놓치는 비용이 오탐 비용보다 훨씬 크다. 데이터가 매우 불균형할 때 모델을 가장 적절하게 평가하는 방법은?
- 보기:
  - A) 전체 정확도(Accuracy)가 가장 높은 모델을 고른다.
  - B) 재현율(Recall)과 정밀도-재현율 곡선 아래 면적(AUPRC)을 보고, 분류 임계값을 오류 비용에 맞춰 조정한다.
  - C) RMSE 가 가장 낮은 모델을 고른다.
  - D) 훈련 데이터에서 계산한 F1 점수가 가장 높은 모델을 고른다.
- 정답: B
- 근거: 〔S1〕〔S2〕〔S14〕 https://docs.aws.amazon.com/sagemaker/latest/dg/autopilot-model-insights.html — 재현율은 양성을 모두 찾아야 할 때(암 검사) 중요하고, AUPRC 는 TN 수를 고려하지 않아 TN 이 압도적인 데이터에 유용하며, ML Lens 는 오류 유형별 상대 비용에 맞춰 분류 임계값을 조정하라고 안내한다.
- 오답 근거: A) 양성·음성 수 차이가 큰 불균형 데이터에서는 정확도가 왜곡되어 BalancedAccuracy 같은 지표가 필요하다 〔S1〕 / C) RMSE 는 회귀 지표다 〔S1〕 / D) 평가는 학습에 쓰지 않은 데이터로 해야 하며 훈련 데이터 지표는 일반화 성능이 아니다 〔S11〕

### 후보 2 (난이도: foundational)
- 대응 Skill: K4 / SK1
- 문제: 대출 승인 모델을 훈련하기 전에, 연령대(facet)별 훈련 데이터의 표본 수 불균형과 양성 레이블 비율 차이를 점검하려 한다. 아직 훈련된 모델은 없다. 기존 SageMaker Clarify 고객이라고 가정할 때 가장 적절한 분석은?
- 보기:
  - A) 사후 편향 지표인 DPPL 과 DI 를 계산한다.
  - B) 사전 편향 지표인 CI(Class Imbalance)와 DPL(Difference in Proportions of Labels)을 계산한다.
  - C) SHAP 글로벌 값으로 특성 중요도를 계산한다.

## 9. 확인 필요 항목

- [G-2.3-1] Clarify 사후 편향 지표는 11개인가 13개인가? — https://docs.aws.amazon.com/sagemaker/latest/dg/clarify-measure-post-training-bias.html 본문은 "eleven"이라 쓰지만 같은 페이지의 요약표·주제 목록은 13개(DPPL, DI, CDDPL, FT, AD, RD, DCAcc, DAR, SD, DCR, DRR, TE, GE)다. 사전 8개 + 사후 13개 = 21개는 블로그의 "21 different metrics"와 일치한다 — 제안: 학습문서는 사후 13개(총 21개)로 쓰고 "문서 본문 표기와 불일치"를 주석으로 남기며, 문항에서 개수를 정답 근거로 삼지 않는다.
- [G-2.3-2] DCAcc·DCR·TE 의 부호 해석과 정의가 페이지마다 같은가? — 요약표(clarify-measure-post-training-bias.html)와 개별 페이지(clarify-post-training-bias-metric-dcacc.html, -dcr.html, -te.html)를 대조했다. 예: DCAcc 양수를 요약표는 "possible bias against the qualified applicants from the disfavored facet d" 로, 개별 페이지는 facet a 에 대한 편향으로 설명한다. TE 는 요약표가 FP 대 FN 비율의 차로, 개별 페이지가 FNd/FPd − FNa/FPa 로 쓰고 "이전 버전은 FPa/FNa − FPd/FNd" 라는 주석을 단다 — 제안: 이 세 지표는 이름·비교 대상(관측 대 예측, FP 대 FN 비율)·범위만 쓰고 부호 해석을 정답 근거로 쓰지 않는다.
- [G-2.3-3] 가이드 K1 의 '히트 맵(heat maps)'은 어떤 평가 기법을 가리키는가? — 가이드 원문(섹션 1)은 설명 없이 나열한다. 공식 문서 확인 결과 Autopilot 지표·성능 보고서 페이지에는 "heat map"이라는 단어가 없고(혼동 행렬을 색 막대로 설명), 이 단어는 Clarify 컴퓨터 비전 설명(슈퍼픽셀 SHAP)과 Debugger Insights 시스템 사용률 문서에 나온다. AWS 블로그 예제 코드는 혼동 행렬을 seaborn `heatmap` 으로 그린다 — 제안: 학습문서에 두 의미(혼동 행렬의 색 농도, SHAP 히트 맵)를 병기하고 출제 의도는 미확정으로 표기한다. 컨트롤러가 섹션 8 에서 MLA-C02 가이드에 같은 단어가 있는지 비교한다.
- [G-2.3-4] K2 '성능 기준선'의 현행 공식 정의가 있는가? — 현행 문서에서 "기준 모델" 개념은 ML Lens(MLPERF04-BP02·BP05)에 있고, 지표 기준값(AUC 0.5, 평균을 예측하는 모델의 RMSE, 최빈 클래스 예측의 macro-F1)은 이번 조사 범위에서는 구서비스 Amazon Machine Learning 문서에서만 찾았다(문서 상단에 갱신·신규 사용자 중단 공지). Model Monitor baseline 은 ⚠️ 신규 고객 중단이다 — 제안: 학습문서에서 기준선의 세 의미(성능·운영·SHAP)를 구분하고 Amazon ML 출처는 "구서비스 문서"로 표기한다. 시험이 어느 의미를 묻는지는 가이드에 명시가 없다.
- [G-2.3-5] SK3 '재현 가능한 실험'의 정답 서비스는 Experiments 인가 MLflow 인가? — experiments.html 은 Experiments Python SDK 추적이 Studio Classic 에서만 가능하고 MLflow 통합을 권장한다고 쓰며, lineage-tracking.html 은 Studio Classic 이 신규 온보딩 불가라고 쓴다. 가이드 문구는 서비스 이름 없이 "AWS 서비스를 사용하여 재현 가능한 실험 수행"이다 — 제안: Experiments(Classic)·MLflow·Model Registry·ML Lineage Tracking·시드를 모두 다루고, 문항은 "추적·비교·버전·계보" 개념으로 출제하며 서비스 하나만 정답으로 못 박지 않는다.
- [G-2.3-6] Autopilot 성능 보고서의 정밀도·재현율 가중 지침이 정확한가? — autopilot-model-insights.html 의 "If your problem has a low penalty for false negative values, but a high penalty for missing a true negative results, give more weight to precision over recall." 는 "missing a true negative"의 의미가 모호하다. 같은 문서군의 지표 페이지는 "Precision is an important metric when the cost of a false positive is high" 로 일관되게 설명한다 — 제안: 학습문서에는 FP 비용 기준 설명만 쓰고 앞 문장은 인용하지 않는다.
- [G-2.3-7] Debugger `save_interval` 기본값은? — debugger-built-in-rules.html·debugger-save-tensors.html·debugger-configure-hook.html 에서는 예제가 값을 500 으로 지정할 뿐 기본값을 명시한 문장을 찾지 못했다(AWS 블로그 "Training, debugging and running time series forecasting models with the GluonTS toolkit on Amazon SageMaker"는 기본 500 단계라고 쓰지만 공식 개발자 가이드에서는 미확인) — 제안: 학습문서에서 기본값을 단정하지 않는다.
- [G-2.3-8] SageMaker AI MLflow 의 요금·"추가 비용 없음" 서술은 확인되는가? — debugger-availability-change.html 은 서버리스 MLflow 기능이 추가 비용 없이 제공된다고 쓰지만, mlflow.html·mlflow-app-setup.html 에서는 요금 문장을 찾지 못해 본문에 쓰지 않았다 — 제안: 요금 문항은 만들지 않고, 필요하면 동적 페이지인 SageMaker AI 요금 페이지를 별도로 확인한다.
- [G-2.3-9] Clarify 온라인 설명 문서에 신규 고객 중단 배너가 없는 이유는? — clarify-online-explainability.html 본문(2026-10-17 조회)에는 다른 Clarify 페이지에 붙은 "no longer open to new customers" 배너가 없다 — 제안: 기능 상태는 페이지별 배너가 아니라 Clarify availability change(clarify-availability-change.html)를 기준으로 ⚠️ 처리한다.
- [G-2.3-10] Profiler 지원 종료가 Debugger 의 시스템 모니터링·프로파일링(ProfilerConfig, ProfilerReport 규칙, Insights 대시보드)에도 적용되는가? — profiler-availability-change.html 은 `ProfilerConfig` 제거 절차를 안내하고 Debugger Insights 문서에도 Profiler 지원 종료 배너가 붙어 있으나, Debugger 프로파일링 기능의 종료일을 명시한 문장은 찾지 못했다 — 제안: 학습문서는 "SageMaker Profiler 2027-06-30 지원 종료"만 쓰고 Debugger 프로파일링의 종료일은 단정하지 않는다.
- [G-2.3-11] R2 의 범위는 −1~1 인가? — autopilot-metrics-validation.html 은 "Values range from one (1) to negative one (-1)"이라고 쓴다. 이 노트는 문서 표기를 그대로 옮겼고 범위가 엄밀한지는 확인하지 않았다 — 제안: 학습문서에서는 "문서 표기"를 붙이고 문항에서 R2 하한값을 정답 근거로 쓰지 않는다.
- 레포 `MLA-C01.json` 수정 제안: 없음.
