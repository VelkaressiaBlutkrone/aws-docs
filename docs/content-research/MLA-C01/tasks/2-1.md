### 2.1 모델링 접근 방식의 선택 사다리 (노력·통제권)

같은 문제를 푸는 방법은 여러 층으로 나뉘며, 층이 올라갈수록 필요한 코드·ML 전문성·운영 부담이 커지는 대신 알고리즘과 인프라를 바꿀 수 있는 통제권도 커진다. SageMaker 문서는 구현 선택지를 사전학습 모델(JumpStart) → 내장 알고리즘 → 프레임워크 스크립트 모드 → 커스텀 Docker 이미지 순으로 노력이 커진다고 정리한다.(F3)〔S2〕 AWS 의사결정 가이드는 이 사다리의 가장 아래(쉬운 쪽)에 "사전 구축된 기능을 ML 전문성 없이 앱에 넣는" 관리형 AI 서비스를 두고, 사전 구축 기능을 넘어서는 맞춤 모델이 필요할 때 SageMaker 같은 ML 서비스를 쓰라고 안내한다.〔S46〕 이때 전문 AI 서비스는 사전학습 모델이라 알고리즘을 바꿀 여지가 제한적이다.(F116)

| 단계 | 대표 선택지 | 코드·전문성 | 통제권 | 언제 쓰나 | 근거 |
|---|---|---|---|---|---|
| ① 관리형 AI 서비스 | Translate·Transcribe·Polly·Rekognition·Textract·Comprehend·Lex·Personalize 등 | 코드·설정 거의 없음, ML 전문성 불필요 | 낮음(입력 데이터·일부 파라미터). 일부는 사용자 정의 모델 학습 기능 제공(Comprehend Custom, Rekognition Custom Labels) | 번역·음성 인식 같은 사전 구축 기능이 요구와 일치할 때 | 〔S46〕〔S80〕〔S60〕 |
| ② 파운데이션 모델 | Amazon Bedrock, SageMaker JumpStart 의 FM | API 호출 중심(프롬프트 엔지니어링 → 미세조정 → RAG 순으로 맞춤) | 중간 | 생성형 AI·요약·질의응답, 사전학습 모델 미세조정 | 〔S45〕〔S43〕 |
| ③ SageMaker 내장 알고리즘 | XGBoost·Linear Learner·K-Means 등 24종(2.4) | 코딩 불필요 — 입력은 데이터·하이퍼파라미터·컴퓨트 | 중간(알고리즘 고정) | 자체 데이터로 학습, 대규모 확장·GPU 필요 | 〔S2〕 |
| ④ 프레임워크 스크립트 모드 | Scikit-learn·Spark ML·XGBoost(오픈소스)·TensorFlow·PyTorch·MXNet·Chainer | 코드 필요(노력 Medium ~ Medium-high). Scikit-learn·Spark ML·XGBoost 는 사전 코딩 알고리즘 있음, TensorFlow·PyTorch·MXNet·Chainer 는 알고리즘을 직접 구현 | 높음, 단 PyPI 패키지까지 | 내장 알고리즘에 없는 알고리즘을 직접 코딩 | 〔S2〕 |
| ⑤ 커스텀 Docker 이미지 | ECR 등 온라인 저장소의 이미지 | 노력 High | 최고(어느 소스의 패키지든) | 지원 프레임워크 밖의 패키지·언어(예: Stan·Julia) | 〔S2〕 |

- 내장 알고리즘의 장점: 코딩 없이 실험을 시작할 수 있고, 해당되는 알고리즘은 다중 인스턴스 병렬화와 GPU 지원이 기본 제공된다.(F4)〔S2〕
- 스크립트 모드의 한계: 지원 프레임워크 이미지에는 PyPI 에 있는 패키지만 추가할 수 있다. PyPI 밖 소프트웨어가 필요하면 커스텀 이미지다.(F5)〔S2〕
- 한국어 병기: 기본 제공 알고리즘(built-in algorithms), 사전 훈련된 모델(pre-trained models), 솔루션 템플릿(solution templates)〔S3〕. ko_kr 문서는 기계 번역본이라 영어판이 우선한다.

> 🧠 원리: 알고리즘과 문제 유형의 대응은 일대일이 아니라 다대다이므로(F6)〔S2〕 한 문제를 여러 층의 선택지가 풀 수 있다. 어느 층을 고를지는 알고리즘 적합성만으로 정해지지 않고 데이터량·필요한 맞춤 정도·운영 부담·해석 가능성·비용(2.2~2.11)으로 좁혀진다.

AWS 가 제시하는 진행 경로: 생성형 AI 에서는 Bedrock 에서 시작해 맞춤화 요구가 커지면 SageMaker AI 로 진행하는 것이 일반적인 경로다.(F120)〔S45〕 비용 관점의 사전 점검은 ML Lens 의 "커스텀 모델 vs 사전학습 모델 트레이드오프 분석"이다 — 사용 가능한 사전학습 대안을 보지 않고 모든 사례에 커스텀 모델을 만드는 것이 안티패턴이다.(F81)〔S49〕

### 2.2 ML 솔루션 적합성 판단 — 데이터와 문제 복잡도 (SK1)

서비스·알고리즘을 고르기 전에 ML이 이 문제에 맞는지부터 판단한다.(F115)〔S46〕 Well-Architected ML Lens 의 "ML 문제 프레이밍" 단계는 ML 이 적합한지 평가하라고 하며, 규칙으로 충분한 문제(F74)와 데이터가 부족한 문제(F75)를 부적합 사례로 든다.〔S47〕 MLCOST02-BP01 은 이를 비용 관점에서 구체화한다 — ML 은 데이터 준비·전용 하드웨어·유지보수 투자가 필요하므로 단순 규칙이 더 싸게 개발·유지될 수 있다.(F77)〔S48〕

| 평가 축 | 확인 질문 | 판단 | 근거 |
|---|---|---|---|
| 규칙으로 해결되는가 | 목표값을 단순 규칙·계산·정해진 단계로 정할 수 있는가 | 가능하면 ML 불필요. 규칙 기반 baseline 과 비교하지 않는 것은 안티패턴(F78) | 〔S47〕〔S48〕 |
| 데이터 가용성·품질 | 이미 가진 데이터·더 모아야 할 데이터가 있고 품질·양이 ML 에 충분한가 | 부족하면 ML 부적합 또는 수집·레이블링 계획이 선행 | 〔S48〕〔S47〕 |
| 문제 복잡도 | 규칙이 못 잡는 복잡한 패턴이나 변화하는 조건에 적응해야 하는가 | 사기 탐지처럼 패턴이 계속 변하면 ML 유리, 단순 재고 관리는 규칙 기반이 적합할 수 있음 | 〔S48〕 |
| 비용·자원 | 데이터 준비·저장·학습·레이블링·재학습·호스팅·유지보수 비용이 가치로 정당화되는가 | 데이터 과학자 시간이 가장 부족한 자원일 수 있어 인력 배분도 비용에 포함 | 〔S48〕 |
| 해석·설명 요구 | 규제·감사로 예측 이유를 설명해야 하는가 | 해석하기 쉬운 단순 모델로 시작(F76) (2.6) | 〔S47〕〔S51〕 |

MLCOST02-BP01 의 구현 단계(요약): 문제·성공 기준 정의 → 가진 데이터와 수집할 데이터, 양·품질 충분성 평가 → 비용 항목 산정 → baseline(규칙 기반, 기본 ML 은 AWS Marketplace·JumpStart 사전 구축 솔루션) 설정 → SageMaker/Autopilot 으로 프로토타입 후 정확도·추론 시간·총비용 비교 → Clarify 로 설명 가능성 확인 → 데이터 기반 결정. Canvas 의 무코드 환경으로 빠르게 타당성을 검증하는 방법도 제시한다.〔S48〕

### 2.3 ML 문제 유형과 학습 패러다임 (K1)

SageMaker 문서는 ML 을 지도·비지도·강화 세 패러다임으로 나누고(F7)〔S2〕, 어떤 패러다임·문제 유형인지는 "가진(또는 모을 수 있는) 데이터로 어떤 추론을 하고 싶은가"로 정해진다고 설명한다.〔S2〕

| 패러다임(한국어) | 데이터 조건 | 문제 유형 | SageMaker 내장 알고리즘 예 |
|---|---|---|---|
| 지도 학습(supervised) | 입력(특징) + 목표값(레이블) | 분류: 목표값이 범주형(이진/다중)(F8), 회귀: 목표값이 연속형(F9) | XGBoost·Linear Learner·k-NN·Factorization Machines·LightGBM·CatBoost·AutoGluon·TabTransformer(표), DeepAR(시계열), 이미지·텍스트 지도 알고리즘 |
| 비지도 학습(unsupervised) | 레이블·목표값 없음(F10) | 차원 축소·군집 분석·이상 탐지·밀도 추정 | PCA·K-Means·Random Cut Forest·IP Insights·LDA·NTM |
| 강화 학습(reinforcement) | 환경과 시행착오로 상호작용하며 장기 보상을 최대화 | 탐험(불확실 보상)과 활용(알려진 보상)의 균형 | SageMaker AI RL 툴킷 — 컨테이너는 2024-04 지원 종료 ⚠️(F58) |

근거: 분류·회귀·비지도 정의와 유형은 〔S2〕, 강화 학습 설명은 〔S2〕, RL 컨테이너 종료는 〔S32〕.

- 신경망처럼 여러 학습 패러다임·여러 문제 유형에 쓰이는 알고리즘이 있으므로 "알고리즘 이름 → 패러다임"이 항상 일대일은 아니다.〔S2〕
- 비지도 문제 유형의 설명: 차원 축소는 고차원 희소 공간을 중요한 성질을 보존한 저차원 공간으로 변환(차원의 저주 완화, 시각화), 군집 분석은 특징·거리 함수·군집 수를 정해 유사한 것끼리 묶음, 이상 탐지는 나머지와 크게 다른 드문 항목(예: 은행 사기, 의료 오류)을 식별, density estimation 은 관측 데이터로 기저의 확률 밀도 함수를 구성(가장 단순한 형태가 재조정한 히스토그램).〔S2〕

AWS 개념 페이지가 정리한 일반 지도 학습 알고리즘의 기능(분류·회귀):〔S54〕

| 알고리즘 | 공식 설명 |
|---|---|
| 로지스틱 회귀 | 입력 데이터가 특정 분류(이진 또는 다중)에 속할 가능성을 판단(F94) |
| 결정 트리 | if-then-else 구조(F91) — 분류뿐 아니라 회귀에도 적용 |
| 랜덤 포레스트 | 여러 결정 트리로 단일 트리 기반 모델보다 정확한 결과(F92) |
| 서포트 벡터 머신 | 일반 로지스틱 회귀 분포를 따르지 않는 분류 데이터를 더 정확히 적합 — 데이터셋을 더 높은 차원으로 변환한 뒤 처리(F93) |
| 선형 회귀 | 직선으로 데이터를 적합, 가장 단순하고 기본적인 ML 알고리즘 중 하나(F95) |
| 다항 회귀 | 데이터를 다항 곡선에 적합 |
| 신경망 | 다중 출력 회귀 같은 복잡한 관계 모델링에 많이 쓰임(은닉층 노드가 복잡한 관계에 적합) |

모델 선택의 함정도 같은 페이지가 짚는다 — 과적합은 학습 데이터의 패턴을 너무 정확히 따라 새 데이터에서 일관성 없는 결과를 내는 것이고, 과소적합은 데이터에 비해 너무 단순한 모델을 쓴 것이다(예: 현실 데이터 대부분은 선형 회귀에 맞지 않음(F96)). 기본 모델은 적은 시간·투자로 만들고 돌릴 수 있지만 복잡한 모델은 단계마다 더 많은 설정과 비용이 든다.(F97)〔S54〕

### 2.4 SageMaker 내장 알고리즘 카탈로그 (K4) — 현재 공식 문서에 존재하는 24종

"Parameters for Built-in Algorithms" 표(행 24개)가 현재 문서의 내장 알고리즘 전체 목록이다.〔S9〕 개요 페이지는 이를 학습 패러다임(지도·비지도)과 도메인(텍스트·이미지)으로 묶어 안내하고〔S1〕, 계열별 페이지가 입력 채널·형식·인스턴스·병렬화 표를 따로 둔다.〔S4〕〔S5〕〔S6〕〔S7〕〔S8〕 아래 표는 이 표들과 알고리즘별 페이지를 합친 것이다. "분산" 열은 공식 표의 Parallelizable(다중 인스턴스 분산 학습 가능 여부)이다.

한국어 병기는 ko_kr 문서 기준(기계 번역본, 어색한 표기는 섹션 9): 선형 학습자(Linear Learner), k-means, 이미지 분류 - MXNet, 객체 감지 - MXNet, 의미 체계 분할(Semantic Segmentation), 주제 모델링(topic modeling), 클러스터링(군집), 시계열 예측, 임베딩, 차원 축소, 이상 탐지, 음성을 텍스트로 변환.〔S3〕

> ⚠️ 상태 요약: ① 이름이 바뀌거나 목록에서 폐기 표시된 내장 알고리즘은 찾지 못했다 — 24종 모두 현재 알고리즘 목록에 있다. ② 다만 버전·컨테이너·프레임워크 수준의 경고가 있다: XGBoost 0.90 버전은 deprecated(F14), DeepAR 컨테이너는 기반 MXNet 이 end-of-maintenance 라 2024-08 이후 보안 패치가 중단됨(F56), Apache MXNet 은 SageMaker Python SDK v3 에서 미지원(F59)(Image Classification·Object Detection 은 이름 그대로 MXNet 기반, Semantic Segmentation 은 MXNet Gluon·GluonCV 기반), 강화 학습(RL) 컨테이너는 지원 종료(F58). 이 경고들이 해당 알고리즘을 내장 목록에서 제외했다는 뜻인지 설명하는 문구는 찾지 못했다(섹션 9).

### 2.6 해석 가능성과 모델·알고리즘 선택 (K3)

**용어.** 해석 가능성(interpretability)은 사람이 결정의 원인을 이해할 수 있는 정도다.(F84)〔S52〕 AWS "Explainable AI" 설명은 기법을 두 부류로 나눈다 — ① 블랙박스 모델의 결정을 내린 뒤에 설명하는 사후(post hoc) 방법(Explainable ML)(F108), ② 모델 자체가 어느 정도 해석 가능한 방식으로 동작함을 활용하는 방법(Interpretable ML).(F109)〔S56〕 ML Lens 는 "explainability"(모델이 결정에 이르는 과정을 이해·해석하게 해 주는 것(F88)), 백서·Prescriptive Guidance 는 "interpretability"라는 표현을 쓰며, 이 Task 의 한국어 Skill 은 "해석 가능성"이다. 규제 산업(의료·금융)은 해석 가능성 자체를 요구하기도 한다.(F110)〔S53〕

**성능과의 트레이드오프.** 복잡한 모델(딥 뉴럴 네트워크 등)은 정확도가 높을 수 있으나 해석이 어렵고(F82), 결정 트리·선형 회귀 같은 단순 모델은 더 직관적인 설명을 주는 대신 성능을 일부 포기할 수 있다.(F83)〔S51〕 어느 쪽을 고를지는 비즈니스 맥락이 정한다 — ML Lens 예시: 신용 승인 시스템은 거절 이유 설명이 필요하고, 제조 품질관리는 설명보다 정확도를 우선할 수 있다.〔S51〕

| 접근 | 대표 모델 | 해석 방식 | 성능 | 근거 |
|---|---|---|---|---|
| 내재적(intrinsic) 해석 | 선형 회귀(예측 = 입력의 가중합), 결정 트리(if-then 규칙)(F85). SageMaker 내장 알고리즘에서는 Linear Learner 가 선형 모델 계열 | 선형 모델은 계수 자체가 명확한 설명(F104), 단일 트리는 분기 변수·리프 값이 곧 설명(F105) | 비선형 상호작용을 못 잡아 성능이 낮은 경우가 많음 | 〔S52〕〔S55〕 |
| 사후(post hoc) 해석 | 신경망, 트리 앙상블(XGBoost·LightGBM·CatBoost), 딥 표 형식(TabTransformer), 이미지·시퀀스 신경망 | 단순 모델은 물론 신경망 같은 복잡 모델에도 적용(F86)하는 모델 비의존(model-agnostic) 기법 — LIME·SHAP·PDP 등. 트리 앙상블은 Tree SHAP 이 권장(F106), 신경망은 integrated gradients, 그 밖의 모델은 Kernel SHAP(F107) | 비선형 상호작용을 잡아 성능 높음. 대신 설명은 사후·근사이며 Kernel SHAP 은 비용이 큼 | 〔S52〕〔S55〕 |

> 표의 "대표 모델"에서 내장 알고리즘을 두 부류에 배정한 것은 알고리즘 페이지의 설명(선형 함수 학습·GBDT 앙상블·신경망 구조)을 백서·Prescriptive Guidance 의 분류에 연결한 해석이다. 알고리즘 페이지 중 해석 가능성을 직접 언급하는 곳은 TabTransformer 뿐이다.(F27)〔S17〕 내장 24종 목록에는 단일 결정 트리 전용 알고리즘이 없다.〔S9〕

**AWS 권고 순서.** 해석 가능하고 성능이 충분한 단순 모델로 시작하고, 성능 개선이 필요해지면 복잡도를 높이면서 사후 분석으로 결과를 해석한다.(F87)〔S52〕 ML 문제 프레이밍 단계도 "해석하기 쉽고 디버깅이 수월한 모델로 시작"을 단계로 둔다.(F76)〔S47〕 MLPERF06-BP02 는 안티패턴으로 ① 모델을 불투명한 채로 두는 것, ② 배포 뒤로 설명 요구를 미루는 것, ③ 규제·비즈니스가 설명을 요구하는데 성능 지표를 우선하는 것, ④ 단순 모델로 충분한데 복잡 모델을 쓰는 것을 든다. 구현 단계에서는 설명 요구가 높으면 결정 트리·규칙 기반·선형 모델 같은 내재적 해석 모델을 고려하고(F89), 성능이 우선이면 복잡한 모델에 사후 설명 기법을 붙이는 것이 적절할 수 있다고 한다.(F90)〔S51〕

| 도구 | 하는 일 | 상태 | 근거 |

> 🧠 원리: 입력과 출력의 관계가 단순한 모델은 사람이 규칙을 그대로 읽을 수 있어 해석 가능성이 높지만 비선형 상호작용을 포착하지 못해 성능이 낮아지고, 복잡한 모델은 비선형 상호작용을 포착하는 대신 내부를 직접 읽을 수 없어 사후 분석이 필요해진다. 백서는 이를 "무엇을 예측했는가(성능)"와 "왜 그렇게 예측했는가(해석 가능성)"의 트레이드오프로 표현한다.〔S52〕

선택 체크리스트: ① 설명 의무(규제·감사·고객 이의 제기)가 있는가 → 내재적 모델로 시작 ② 성능이 부족하면 복잡도를 올리되 SHAP 같은 사후 설명 계획을 함께 세움 ③ 설명 요구가 낮고 정확도가 핵심이면 복잡 모델 허용 ④ 설명 도구 선택 시 Clarify 가 신규 고객에게 닫혀 있음(⚠️)을 인지.〔S51〕〔S52〕〔S58〕

### 2.9 SageMaker JumpStart 와 Amazon Bedrock — 모델·솔루션 템플릿 선택 (SK3, K2)

**파운데이션 모델(FM)** 은 다양한 하위 작업에 적응할 수 있는 대형 사전학습 모델로, 더 특화된 모델 개발의 출발점이다.(F72)〔S42〕 FM 을 맞춤화하는 권장 순서는 ① 프롬프트 엔지니어링(가중치 변경 없음) ② 부족하면 도메인 데이터로 미세조정(가중치 변경) ③ 지식 라이브러리를 쓰되 재학습이 필요 없는 RAG 이다.(F73)〔S43〕

**SageMaker JumpStart** 는 다양한 문제 유형의 사전학습 오픈소스 모델을 제공하고 배포 전 점진 학습·튜닝을 허용하며(F66), 일반적 사용 사례용 인프라를 구성해 주는 솔루션 템플릿과 예제 노트북도 제공한다.(F67)〔S40〕 개요 페이지는 JumpStart 의 사전학습 모델·솔루션 템플릿이 다루는 15가지 문제 유형을 이미지 분류·표 형식 분류/회귀·텍스트 분류·객체 탐지·텍스트 임베딩·질의응답·문장 쌍 분류·이미지 임베딩·개체명 인식·인스턴스 세분화·텍스트 생성·텍스트 요약·시맨틱 분할·기계 번역으로 나열한다.(F54)〔S1〕
- 가능한 작업: Studio 의 Models 랜딩 페이지에서 사전학습 모델을 배포·미세조정·평가(Deploy·Fine-tune·Customize·Evaluate)할 수 있으나 모든 모델이 커스터마이즈·미세조정·평가를 지원하지는 않는다.(F70)〔S40〕
- 솔루션 템플릿 사용 사례: 수요 예측·신용 등급 예측·사기 탐지·컴퓨터 비전·문서에서 데이터 추출·예지보전·이탈 예측·개인화 추천·강화 학습·헬스케어/생명과학·금융 가격·인과 추론.〔S41〕
- ⚠️ 솔루션 템플릿(JumpStart Solutions)은 Studio Classic 에서만 사용 가능(F68)하고 Studio Classic 은 신규 온보딩이 불가능하다(F69) — 두 문장을 합치면 신규 계정은 솔루션 템플릿을 쓸 수 없다는 뜻으로 읽히지만 문서가 그렇게 직접 쓴 문장은 찾지 못했다(섹션 9).〔S41〕〔S40〕
- ⚠️ 2026-03-13 일부 모델이 카탈로그에서 delist 됨(기존 엔드포인트는 계속 동작).(F71)〔S40〕
- 모델 라이선스: 공개·독점 FM 은 제공자별 라이선스가 다르며 사용자가 검토·준수할 책임이 있고, 일부 FM 은 EULA 수락이 필요하다.〔S44〕

**Amazon Bedrock** 은 선도 AI 기업의 고성능 FM 에 대한 완전관리형 접근을 제공하며(F123), 100개 이상의 FM 을 지원한다.(F124)〔S63〕 Bedrock Marketplace 로 공개·독점 FM 100개 이상을 시험·통합할 수 있다.〔S45〕 맞춤화 방법은 지도 미세조정(레이블 데이터)·강화 미세조정(보상 함수)·증류(큰 teacher 모델의 지식을 작고 빠르고 저렴한 student 모델로 이전)〔S66〕이며 콘솔 도움말은 레이블 없는 대규모 데이터로 도메인 지식을 학습시키는 continued pre-training 도 나열한다.〔S67〕 다른 환경(예: SageMaker AI)에서 맞춤화한 모델은 Custom Model Import 로 가져올 수 있다.〔S45〕

### 2.10 AutoML — SageMaker Autopilot 과 Canvas (알고리즘 선택의 자동화, SK2·SK3)

가이드 항목에 직접 이름이 없어도 "알고리즘을 직접 비교·선택하지 않고 맡기는" 선택지로 시험 선택지에 섞일 수 있다. 공식 문서 기준 두 기능 모두 현재 존재한다(2026-10-17).〔S36〕

- **SageMaker Autopilot**: 모델 구축·배포를 자동화하는 AutoML 기능 묶음. 데이터 분석·전처리, 모델 선택(여러 알고리즘을 탐색하고 교차 검증 리샘플링으로 지표를 만들어 비교)(F61), 하이퍼파라미터 최적화, 학습·평가, 배포를 자동화한다.〔S35〕 지원 문제 유형: 표 형식 회귀·이진/다중 분류(CSV/Parquet), 텍스트 분류, 이미지 분류, 시계열 예측, LLM 미세조정(텍스트 생성) — 표 형식 외에는 AutoML API V2 로만 사용한다.〔S35〕 AUTO 모드에서는 데이터셋 100 MB 미만이면 ENSEMBLING, 더 크면 HYPERPARAMETER_TUNING 을 선택한다.(F63)〔S39〕 특징 중요도 설명 리포트를 자동 생성한다(2.6).(F62)
- ⚠️ **Autopilot UI → Canvas**: 2023-11-30 이후 Autopilot UI 는 Canvas 로 이전(F60), Studio Classic 사용자는 기존 UI를 계속 쓰고 코드 사용자는 AutoML API 를 계속 쓴다.〔S35〕〔S36〕
- **SageMaker Canvas**: 분석가·시민 데이터 과학자를 위한 무코드 환경 — 데이터 준비, 특성 엔지니어링, 알고리즘 선택, 학습·튜닝, 추론.〔S36〕〔S37〕 지원 사용자 정의 모델: 숫자 예측(회귀), 2 범주/3+ 범주 예측(이진/다중 분류), 시계열 예측, 단일 레이블 이미지 예측, 다중 범주 텍스트 예측.〔S37〕 데이터셋으로 최대 250개 모델을 만들어 가장 좋은 것을 고른다.(F64)〔S38〕 Ready-to-use 모델은 Rekognition·Textract·Comprehend 기반이다.(F65)〔S37〕 Forecast 사용자의 안내 이전 대상이기도 하다.(F179)〔S99〕
- AutoGluon-Tabular(내장 알고리즘: 앙상블·스태킹으로 높은 정확도)와 Autopilot(여러 알고리즘 탐색·튜닝·배포를 자동화하는 워크플로)은 다르다 — 전자는 하나의 알고리즘(프레임워크), 후자는 선택 과정 자체의 자동화다.(F25)〔S16〕〔S35〕

## 3. 시험에서 묻는 방식

> 이 섹션은 가이드 Skill 문장이 "무엇을 고르게 하는가"에서 도출한 출제 방식이다(문제 덤프를 보지 않음). SK2·SK3·SK5 는 "여러 선택지 중 제약에 맞는 하나를 고르는" 유형이고, K3·SK1 은 "요구 조건이 선택을 바꾸는" 유형이다.

### 패턴 1. 요구를 가장 적은 노력으로 충족하는 접근 고르기 (AI 서비스 vs FM vs 내장 알고리즘 vs 커스텀)
- 시나리오 단서: "ML 전문 인력이 없다", "운영 오버헤드 최소", "빠르게 출시"; 번역·음성 인식·이미지 분석·문서 추출·감성 분석 같은 일반 기능; "자체 데이터로 맞춤하되 레이블 데이터가 적다"; 요약·질의응답·콘텐츠 생성; "대규모 자체 데이터와 알고리즘 통제"; "알고리즘을 직접 코딩"·"특수 패키지".
- 정답 방향: 사전 구축 AI 서비스(요구가 맞으면) → 서비스의 사용자 정의 기능(Comprehend Custom·Rekognition Custom Labels)이나 JumpStart 미세조정(맞춤 + 소량 데이터) → 생성형은 Bedrock → 대규모·통제는 내장 알고리즘 → 내장에 없으면 스크립트 모드 → 지원 프레임워크 밖 패키지는 커스텀 이미지. 사다리를 올라가야 하는 이유가 시나리오에 명시된다(2.1).
- 오답 유인(섞이는 선택지): 문제에 비해 과한 SageMaker 커스텀 학습·Docker 이미지; 이름이 비슷하고 용도가 다른 서비스(Textract / Rekognition / Comprehend, Kendra / Q Business / Bedrock Knowledge Bases, Lex / Q); Bedrock 과 SageMaker AI 의 혼동; 최신 상태가 중요한 문항에서 신규 고객 중단·종료 서비스(Forecast·Fraud Detector·Lookout 계열·Kendra·A2I, 2.8).
- 근거: 〔S2〕〔S46〕〔S45〕〔S49〕

### 패턴 2. 데이터 형태·문제 유형으로 내장 알고리즘 고르기
- 시나리오 단서: 정답 레이블의 유무(지도/비지도), 목표값이 범주형/연속형, 데이터 형태(표·고차원 희소·텍스트 코퍼스·이미지·시계열), 요구 출력(점수·군집·토픽·경계 상자·픽셀·임베딩), 인프라 제약(GPU 전용·CPU 전용·단일 인스턴스), 입력 형식(recordIO-protobuf 와 CSV).
- 정답 방향: 2.5 의 매핑 — 희소 고차원·클릭 예측 → Factorization Machines, 이상 점수 → Random Cut Forest, IP 이례성 → IP Insights, 미지정 토픽 → LDA/NTM, 단어 임베딩·빠른 텍스트 분류 → BlazingText, 번역·요약 → Sequence-to-Sequence, 관련 시계열 다수 예측 → DeepAR, 차원 축소 → PCA, 군집 → K-Means, 쌍 임베딩 → Object2Vec, 이미지 레이블/상자/픽셀 → 분류/탐지/분할.
- 오답 유인: 이름·역할이 비슷한 쌍(LDA/NTM, K-Means/PCA, RCF/IP Insights, 이미지 3종, Linear Learner/Factorization Machines, BlazingText/Seq2Seq/Object2Vec — 섹션 4); 지도/비지도 혼동(Object2Vec 은 지도, BlazingText 는 모드에 따라 양쪽); 모든 표 형식 알고리즘이 분산·GPU 를 지원한다는 가정(CatBoost CPU 전용, AutoGluon·TabTransformer 단일 인스턴스, RCF 는 GPU 이점 없음, Seq2Seq 는 GPU 전용).
- 근거: 〔S1〕〔S9〕〔S4〕〔S5〕〔S6〕〔S7〕

### 패턴 3. 해석 가능성(설명 요구)이 모델 선택을 좌우하는 문항
- 시나리오 단서: 규제·감사·고객 이의 제기, "거절 사유를 설명해야", 의료·금융·신용 심사, "이해관계자 신뢰"; 반대로 "정확도가 최우선", 제조 품질관리; "블랙박스", "SHAP", "특징 기여도".
- 정답 방향: 설명 요구가 높으면 해석 가능한 단순 모델(선형·결정 트리·규칙)로 시작, 성능이 부족하면 복잡 모델 + 사후 설명(SHAP, SageMaker Clarify — 단 신규 고객에게는 닫힘 ⚠️). 설명 요구가 낮고 성능이 핵심이면 복잡 모델 허용. 해석 가능성과 성능은 트레이드오프이며 배포 후가 아니라 모델 선택 단계에서 결정한다(2.6).
- 오답 유인: 가장 정확한 딥러닝을 무조건 선택; 설명 검토를 배포 후로 미룸; 비지도 군집으로 사유를 대체; "복잡한 모델은 설명이 불가능하다"는 단정(사후 기법으로 가능); Clarify 를 편향 탐지 전용으로만 오해; Bedrock Evaluations 가 표 형식 모델 설명을 대체한다는 오해.
- 근거: 〔S51〕〔S52〕〔S55〕〔S57〕〔S58〕

### 패턴 4. 비용 기준으로 서비스·모델·구매 옵션 고르기
- 시나리오 단서: "트래픽이 변동적/예측 불가", "PoC", "비실시간 대량", "안정적 대량 + 처리량 보장", "월 수천 장 이상 이미지", "비용을 최소화", "GPU 가 필요한가", "사용자 정의 모델 추론".
- 정답 방향: 변동·PoC → 온디맨드·종량제 관리형; 비실시간 → 배치(최대 50% 절감); 안정적 대량·처리량 보장 → Provisioned Throughput·Savings Plans; 이미지 대량 → SageMaker 엔드포인트가 더 저렴할 수 있음; 알고리즘은 단순한 것부터, CPU 권장·전용 알고리즘에 GPU 를 붙이지 않음(2.11).
- 오답 유인: 항상 Provisioned Throughput; "사용자 정의 모델은 온디맨드 불가"(구 규칙 vs 최신 문서, 섹션 9); GPU 는 항상 비싸다(XGBoost 1.2-2 이상은 GPU 가 더 빨리 끝나 비용 효율적); 관리형 서비스가 언제나 가장 싸다/비싸다는 일반화.
- 근거: 〔S68〕〔S45〕〔S59〕〔S50〕〔S10〕〔S64〕

## 4. 흔한 함정·혼동 짝

### 짝 1. LDA vs NTM (둘 다 비지도 토픽 모델링)
- 구분 기준: 같은 문제(문서 집합의 미지정 토픽 도출)를 풀지만 하드웨어와 지표 성향이 다르다. 토픽은 사전에 지정되지 않고 사람이 문서를 분류하는 방식과 일치한다는 보장이 없다는 점은 둘 다 같다.〔S22〕〔S23〕

| 항목 | LDA | NTM |
|---|---|---|
| 방식 | 확률적 모델 — 문서는 토픽의 혼합, 토픽은 단어 확률 분포 | 신경망 접근 |
| 인스턴스 | 단일 인스턴스 CPU 만(F34) | CPU·GPU, 여러 GPU 인스턴스 병렬화(F35) |
| 지표 경향 | collapsed Gibbs sampling 으로 학습한 LDA 는 perplexity 우수(F37) | topic coherence 에 유망(F36) |
| 입력 | recordIO-protobuf, CSV(dense: 레코드 수 × 어휘 크기) | recordIO-protobuf, CSV + 선택 보조 채널 vocab.txt(WETC 점수) |

- 근거: 〔S22〕〔S23〕〔S1〕

### 짝 2. Linear Learner vs XGBoost vs Factorization Machines (표 형식 지도 학습 3종)
- 구분 기준: 모델 구조(선형 / 트리 앙상블 / 선형 + 쌍별 상호작용), 데이터 성격(일반 표 / 고차원 희소), 입력 형식, 해석 방식.

| 항목 | Linear Learner | XGBoost | Factorization Machines |
|---|---|---|---|
| 모델 | 선형 함수 / 선형 임계 함수(F15) | GBDT 앙상블(약한 모델 결합) — 회귀·분류·랭킹(F11) | 선형 모델 확장, 쌍별(2차) 상호작용만(F18) |
| 잘 맞는 데이터 | 일반 표 형식, 빠른 기준선 | 일반 표 형식, 다양한 데이터 유형·분포에 강건 | 고차원 희소(클릭 예측·아이템 추천)(F17) |
| 입력 | recordIO-protobuf·CSV | CSV·LibSVM·Parquet | recordIO-protobuf(Float32)만(F19) |
| 해석 | 계수를 그대로 읽는 내재적 해석 계열(F104) | 트리 앙상블 → Tree SHAP 등 사후 해석(F106) | 선형 + 2차 항(문서에 해석 언급 없음) |
| 인스턴스 | CPU·GPU | CPU, GPU(1.2-2 이상)(F13) | CPU(희소)·GPU(밀집만)(F20) |

- 근거: 〔S11〕〔S10〕〔S13〕〔S9〕〔S55〕

### 후보 1 (난이도: associate)
- 대응 Skill: K4 / SK2
- 문제: 광고 플랫폼이 사용자·광고 카테고리·페이지 카테고리 같은 범주형 특징을 원-핫 인코딩한 고차원 희소 데이터로 클릭 여부를 예측한다. 특히 "특정 광고 카테고리가 특정 페이지 카테고리에 놓일 때 클릭률이 높다" 같은 특징 간 상호작용을 효율적으로 포착해야 한다. 가장 적합한 SageMaker 내장 알고리즘은?
- 보기:
  - A) Linear Learner
  - B) Factorization Machines
  - C) K-Means
  - D) Random Cut Forest
- 정답: B
- 근거: 〔S13〕 https://docs.aws.amazon.com/sagemaker/latest/dg/fact-machines.html — "선형 모델의 확장으로 고차원 희소 데이터 안의 특징 간 상호작용을 경제적으로 포착하며 클릭 예측·아이템 추천에 적합"(F17)
- 오답 근거: A) Linear Learner 는 선형 함수(임계 함수)를 학습하는 일반 선형 모델로 특징 간 상호작용을 명시적으로 모델링하지 않는다 / C) K-Means 는 레이블 없이 군집을 찾는 비지도 알고리즘이라 클릭 여부 예측에 맞지 않는다 / D) Random Cut Forest 는 이상 점수를 매기는 비지도 이상 탐지 알고리즘이다

- 문제: 은행이 대출 승인 모델을 만든다. 규제 당국은 거절된 모든 신청에 대해 거절 사유를 설명하도록 요구한다. 모델 선택에 대한 AWS 권고와 가장 부합하는 접근은?

  - B) 해석 가능한 단순 모델(선형 모델·결정 트리)로 시작하고, 성능 개선이 필요하면 복잡도를 높이면서 SHAP 같은 사후 설명 기법으로 결과를 해석한다
  - C) 앙상블 모델을 먼저 배포한 뒤 배포 후에 해석 가능성을 평가한다

## 9. 확인 필요 항목

- [G-2.1-1] LightGBM 의 분산 학습·인스턴스 표기가 문서마다 다르다 — Tabular 개요 표는 "CPU (single instance only) / Parallelizable No", Parameters 표는 "CPU / Yes", LightGBM 알고리즘 페이지는 "single-instance and multi-instance CPU training" 이라고 쓴다.〔S4〕〔S9〕〔S14〕 — 제안: 알고리즘 개별 페이지를 정본으로 보되 문항에서 LightGBM 의 분산 가능 여부를 정답 근거로 쓰지 않는다.
- [G-2.1-2] BlazingText 인스턴스 표기 불일치 — Text 개요 표는 "GPU (single instance only) or CPU", Parameters 표는 "CPU or GPU (single instance only)", 알고리즘 페이지는 cbow·skipgram·supervised 는 단일 CPU/GPU, batch_skipgram 은 단일·다중 CPU 라고 모드별로 쓴다.〔S5〕〔S9〕〔S25〕 — 제안: 모드별 설명을 정본으로 하고 "병렬화 불가"를 단정하지 않는다.
- [G-2.1-3] DeepAR 컨테이너 보안 패치 종료 시점 상충 — 같은 지원 정책 페이지가 본문에서는 "2024-08 이후 보안 패치·업데이트 중단"이라 하고 내장 알고리즘 표에서는 forecasting-deepar 의 end of patch 를 2025-08-26 으로 적는다. 또한 표의 나머지 내장 알고리즘 이미지 대부분은 end of patch 2024-05-15 로 적히는데, 같은 페이지는 내장 알고리즘 이미지가 in-place 업데이트이며 latest 태그를 권장한다고 쓴다.〔S32〕 — 확인한 곳: 지원 정책 페이지 전문 — 제안: 학습문서에서 "DeepAR 폐기" 같은 단정을 하지 말고 "컨테이너 보안 패치 중단 공지(MXNet end-of-maintenance)"까지만 서술. 표의 날짜가 알고리즘 사용 불가를 뜻하는지는 컨트롤러가 AWS 문의/콘솔로 확인.
