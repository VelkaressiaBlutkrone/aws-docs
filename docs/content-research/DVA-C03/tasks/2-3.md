## 핵심 개념

### 모델 접근은 이제 "기본 허용"이다 (Skill 2.3.1)

⚠️ **가장 흔할 구식 오해.** 예전 자료는 "콘솔에서 모델 액세스를 요청해야 한다"고 적지만, 공식 문서는 이렇게 적는다.

> "Access to many Amazon Bedrock foundation models is enabled by default with the correct AWS Marketplace permissions."

- 기본 접근은 **모델이 지원되는 모든 상용 리전**에 적용된다.
- 서드파티 모델을 **처음 호출하면 Amazon Bedrock이 배경에서 구독 절차를 자동 시작**한다. 설정 기간(최대 **15분**) 동안 호출이 일시적으로 성공할 수 있고, 전제 조건이 빠져 있으면 구독이 실패해 이후 호출이 `AccessDeniedException`을 돌려준다. 권한을 부여한 뒤 구독 완료까지 **최대 2분**이 더 걸릴 수 있다.
- **전제 조건 3가지**: ① IAM 역할의 `aws-marketplace:Subscribe`·`Unsubscribe`·`ViewSubscriptions` ② **Anthropic 모델은 최초 사용(FTU) 양식** 제출 ③ 유효한 결제 수단.
- FTU 양식은 콘솔 또는 **`PutUseCaseForModelAccess`** API로 낸다. 제출이 즉시 끝나지 않고 계약이 **보류 상태**에 머물 수 있으며, 그동안 호출은 계속 `AccessDeniedException`이다. 상태는 **`GetFoundationModelAvailability`**의 `agreementAvailability`로 확인한다. 관리 계정에서 낸 제출은 같은 AWS Organization의 다른 계정에 **상속**된다.
- **EULA를 먼저 검토해야 하는 조직**은 ① SCP·IAM으로 모델 접근을 선차단 → ② EULA 검토 → ③ 동의할 때만 정책으로 개방한다. 서드파티 모델은 **첫 호출 자체가 EULA 동의**로 간주된다.
- 세분화 통제는 IAM 리소스 ARN으로 한다 — `arn:aws:bedrock:<region>::foundation-model/<model-id>`에 `bedrock:InvokeModel`·`InvokeModelWithResponseStream`을 Allow/Deny.

> ⭐ **2.3.2와 이어지는 함정**: 구독을 여는 첫 호출도 보통의 `bedrock:InvokeModel`처럼 인가된다. 그래서 **`IpAddress` 조건으로 `aws:SourceIp`를 걸어 두면** 그 조건을 만족하는 곳에서 호출해야 하는데, **VPC 엔드포인트를 통한 요청에는 `aws:SourceIp`가 아예 없다.** 그런 조건은 충족될 수 없다.

### 데이터 프라이버시 — 두 축을 따로 본다 (Skill 2.3.2)

Skill 문구가 예시로 **두 가지**를 든다. 섞으면 안 된다.

**① 사설 연결 — VPC 인터페이스 엔드포인트(PrivateLink)**

> "You can access Amazon Bedrock as if it were in your VPC, without the use of an internet gateway, NAT device, VPN connection, or Direct Connect connection."

- 인터페이스 엔드포인트를 만들면 활성화한 **서브넷마다 엔드포인트 네트워크 인터페이스**가 생긴다. VPC 인스턴스에 **퍼블릭 IP가 필요 없다.**
- 런타임 호출용 서비스 이름은 `com.amazonaws.<region>.bedrock-runtime`이다(제어 평면용은 별도).
- 엔드포인트 **정책**으로 특정 모델 ARN·특정 보안 주체만 허용하는 최소 권한을 걸 수 있다.

**② 학습 미사용 — 서비스 약속이지 설정이 아니다**

> "Amazon Bedrock does not use your inputs or outputs to train models or to improve the service, and does not share them with model providers."

- 그래서 **Bedrock은 AI 서비스 옵트아웃 정책의 대상 서비스가 아니다** — 끌 설정이 없기 때문이다. "옵트아웃 정책을 적용해야 학습에 안 쓰인다"는 **거짓**이다.
- ⚠️ 다만 **일부 모델은 남용 탐지(abuse detection) 목적으로 입출력을 최대 30일 보관**한다. 남용 탐지는 서비스 개선과 별개이고 옵트아웃 정책의 적용 대상이 아니다.

### 입출력 필터링 — Guardrails (Skill 2.3.3)

Amazon Bedrock Guardrails가 제공하는 **보호 장치(safeguard)** 목록이다.

| 보호 장치 | 하는 일 |
|---|---|
| **콘텐츠 필터** | 유해 텍스트·이미지 탐지·필터링. 사전 정의 범주 **Hate · Insults · Sexual · Violence · Misconduct · Prompt Attack**. 범주별로 **강도 조절** |
| **프롬프트 공격** | 콘텐츠 필터 **안의 한 범주**다(별도 보호 장치가 아니다). **탈옥(jailbreak) · 프롬프트 인젝션 · 프롬프트 유출(prompt leakage)** 탐지 |
| **거부 주제** | 애플리케이션 맥락에서 원치 않는 주제를 정의해 차단(예: 금융 앱의 불법 투자 조언) |
| **단어 필터** | 사용자 지정 단어·구문 **정확 일치** 차단. 욕설은 기성 옵션 제공 |
| **민감 정보 필터** | PII(표준 형식) 또는 **사용자 지정 정규식** 탐지. **차단 또는 마스킹** 선택. 확률적 ML 기반이고 **맥락 의존적**이다 |
| **맥락 근거 확인** | 근거 없는(환각) 응답 탐지 |
| **자동 추론 확인** | 구조화된 수학적 지식 표현과 대조해 사실 부정확성 탐지 |

**적용 방식 두 가지**

1. **인라인** — 추론 API 호출에 guardrail ID·버전을 지정한다.
2. **독립 실행 — `ApplyGuardrail` API.** **파운데이션 모델을 호출하지 않고** 임의의 텍스트를 평가한다. 입력과 출력을 따로 평가할 수 있고, RAG라면 **검색 전에** 사용자 입력을 먼저 검사할 수 있다. 모델과 **분리돼 있어** Bedrock 밖 모델(자체 호스팅·서드파티)의 트래픽에도 쓸 수 있다.

⚠️ 표준(Standard) 티어에서는 콘텐츠 필터·거부 주제 탐지가 **코드 요소 안**(주석·변수/함수 이름·문자열 리터럴)까지 확장된다. 추론(reasoning) 콘텐츠 블록은 평가 대상에서 제외된다.

### 에이전트 상호작용 보안 (Skill 2.3.4)

Skill이 든 예시 **세 가지**에 각각 대응되는 기능이 있다.

**① 도구 사용 권한 부여 · ③ 사람 승인 흐름 — Bedrock Agents**

- **사용자 확인(user confirmation)**: 작업 그룹을 구성할 때 특정 작업에 켤 수 있다. 켜면 에이전트가 **확인 질문을 던지고** 사용자가 승인/거부한다. 공식 문서가 이 기능의 목적을 **프롬프트 인젝션 방어**로 직접 적는다 — 응답에 섞여 들어온 지시를 에이전트가 그대로 따르는 것을 사람이 끊는다.
- **제어 반환(return of control)**: 작업 그룹의 `actionGroupExecutor`에 `customControl = RETURN_CONTROL`을 지정하면, Lambda로 넘기는 대신 **`InvokeAgent` 응답의 `invocationInputs`**로 호출 정보를 돌려준다(고유 `invocationId` 동반). 애플리케이션이 직접 실행한 뒤 같은 `invocationId`·`actionGroup`으로 `sessionState`에 결과를 실어 다시 보낸다.
  ⚠️ `sessionState`에 `returnControlInvocationResults`를 넣으면 **`inputText`는 무시된다.**

**② 세션 격리 — AgentCore**

- **AgentCore Identity**는 인바운드 인증(IAM 또는 외부 IdP의 JWT로 호출자를 검증)과 아웃바운드 인증(에이전트가 외부 서비스에 쓸 자격 증명 관리)을 나눠 다룬다.
- 다중 홉(Gateway → Runtime → Gateway → Target)에서 세션 동일성은 **Workload Identity Chain(WIC)**으로 보존된다. Gateway가 `sessionId`와 `callerPrincipal`을 담은 **Workload Access Token(WAT)**을 발급하고 Runtime이 교환하며 체인을 늘린다.
- 호출자는 **최초 요청에만** `x-amzn-bedrock-agentcore-policy-session-id`를 넘기면 되고, 에이전트 코드가 내부 WAT 헤더를 읽거나 전달할 필요가 없다. **세션 ID가 WAT 안에 실려 중간 경유지가 위조·변조할 수 없다.**

### 모니터링 로그의 민감 콘텐츠 (Skill 2.3.5)

**모델 호출 로깅(model invocation logging)**

- **기본적으로 꺼져 있다.** 켜면 호출 로그·모델 입력·모델 출력이 수집된다.
- 대상은 **S3 · CloudWatch Logs**(둘 다 가능)이고 **KMS 키로 암호화**할 수 있다.
- ⚠️ **Guardrails를 걸어 둬도 이 로그에는 가드레일 이전의 사용자 입력이 담긴다** — 즉 프롬프트·완성 로그에는 민감 정보가 있다고 가정해야 한다.

**CloudWatch Logs 데이터 보호 정책**

- 로그 그룹에 **데이터 보호 정책**을 걸면 선택한 데이터 식별자와 일치하는 민감 데이터가 **모든 송출 지점**(Logs Insights · 지표 필터 · 구독 필터)에서 마스킹된다.
- 마스킹 해제는 **`logs:Unmask`** 권한을 가진 사용자만 가능하다(`GetLogEvents`·`FilterLogEvents`의 `unmask` 파라미터, Insights의 `unmask` 쿼리 명령).
- **계정 수준**(`PutAccountPolicy`)과 **로그 그룹 수준**(`PutDataProtectionPolicy`) 정책이 있고, 둘 다 걸리면 **누적**된다(어느 쪽에 적힌 식별자든 마스킹). 로그 그룹당 그룹 수준 정책은 **하나**뿐이고 정책 길이 상한은 **30,720자**다.
- **관리형 데이터 식별자**(금융·PHI·PII 사전 구성)와 **사용자 지정 식별자**를 쓸 수 있다. 일부 관리형 식별자는 근처에 특정 키워드가 함께 있어야 탐지된다.
- ⚠️ **탐지·마스킹은 수집(ingest) 시점에 일어난다 — 정책을 걸기 전에 들어온 로그 이벤트는 마스킹되지 않는다.**
- 탐지 시 `AWS/Logs` 네임스페이스에 **`LogEventsWithFindings`** 지표가 로그 그룹별로 발행된다. 감사 결과는 CloudWatch Logs · S3 · **Data Firehose**로 보낼 수 있다.

## 시험에서 묻는 방식

- "입력과 출력이 모델 학습에 쓰이지 않게 하려면?" → **설정이 아니라 서비스 약속**이다. 옵트아웃 정책을 고르는 보기는 오답. 단 남용 탐지 30일 보관은 별개.
- "인터넷을 거치지 않고 Bedrock을 호출하려면?" → 인터페이스 VPC 엔드포인트(PrivateLink).
- "프롬프트 인젝션을 막으려면?" → Guardrails **콘텐츠 필터의 Prompt Attack 범주**. 에이전트라면 **사용자 확인**이 함께 나온다.
- "Bedrock 밖 모델에도 같은 안전 장치를 쓰려면?" → **`ApplyGuardrail`** API.
- "로그에 PII가 남는다" → 모델 호출 로깅은 가드레일 **이전** 입력을 담는다 → CloudWatch Logs **데이터 보호 정책** + `logs:Unmask` 분리 + KMS 암호화.
- "민감 작업 전에 사람이 승인하게 하려면?" → 작업 그룹의 **사용자 확인**(승인/거부) 또는 **제어 반환**(앱이 직접 실행).

## 흔한 함정·혼동 짝

| 혼동 | 가르는 기준 |
|---|---|
| 모델 액세스 "요청" vs **기본 허용** | 지금은 **기본 허용 + 첫 호출 시 자동 구독**이다. 막히면 Marketplace 권한·Anthropic FTU·결제 수단을 본다 |
| **프롬프트 공격**이 별도 보호 장치? | 아니다 — **콘텐츠 필터 안의 한 범주**다 |
| 단어 필터 vs 거부 주제 | 단어 필터는 **정확 일치**, 거부 주제는 **주제 단위** |
| 민감 정보 필터 vs CloudWatch 데이터 보호 | 전자는 **모델 입출력**, 후자는 **로그 이벤트**. 둘 다 필요할 수 있다 |
| 인라인 guardrail vs `ApplyGuardrail` | 모델을 **호출하면서** vs **호출하지 않고** |
| 사용자 확인 vs 제어 반환 | 전자는 **사람에게 묻는다**, 후자는 **앱에 실행을 넘긴다** |
| 계정 수준 vs 로그 그룹 수준 데이터 보호 정책 | **누적**된다. 로그 그룹 수준은 그룹당 **1개** |
| 마스킹 시점 | **수집 시점**이다 — 소급 적용되지 않는다 |

## 사실·숫자

- 자동 구독 설정 기간 **최대 15분** · 권한 부여 후 구독 완료 **최대 2분**
- 남용 탐지 입출력 보관 **최대 30일**(일부 모델)
- 데이터 보호 정책 길이 상한 **30,720자** · 로그 그룹당 **1개**
- 콘텐츠 필터 사전 정의 범주 **6종**(Hate · Insults · Sexual · Violence · Misconduct · Prompt Attack)
- 지표 **`LogEventsWithFindings`** (`AWS/Logs`)

## 확인 필요

- **`InvokeGuardrailChecks` API** — Bedrock FAQ가 "에이전틱 애플리케이션용 리소스 없는 독립 검사"로 언급하지만 **사용자 가이드에서 확인하지 못했다.** 정본으로 확인되기 전에는 `ApplyGuardrail`만 쓴다.
- **Guardrails Classic/Standard 티어의 가격·가용성 차이** — 기능 차이는 확인했으나 티어 선택 기준은 확인하지 못했다.
- **AgentCore Identity 정본 페이지** — 위 11번은 콘솔 도움말 패널 경로다. 개발자 가이드 쪽 대응 페이지를 다시 찾는다.
- **"세션 격리"의 공식 용어 대응** — Skill 문구의 *session isolation*이 AgentCore의 세션 기반 정책·WIC를 가리키는지, Runtime의 세션 분리를 가리키는지 단정하지 못했다.
- **AgentCore 로깅의 민감 콘텐츠 보호** — 2.3.5를 Bedrock 모델 호출 로깅 기준으로 정리했다. AgentCore 쪽 로그에 같은 통제가 있는지는 확인하지 못했다.
- 블로그 출처 1건(15번)은 전략 서술에만 썼고 **사실·숫자에는 쓰지 않았다.**
