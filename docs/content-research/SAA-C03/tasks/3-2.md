### 2-1. 컴퓨트 서비스 선택 매트릭스 (Knowledge 1·5·6, Skill 3)

### 2-2. EC2 인스턴스 유형·기능 선택 (Skill 3)
| 범주 | 용도(공식 서술) | 대표 시리즈 |
|---|---|---|
| 범용 | 컴퓨트·메모리·네트워킹 균형 — 웹 서버·코드 저장소·중소 DB | M, T |
| 컴퓨트 최적화 | 고성능 프로세서가 이득인 컴퓨트 집약 — 배치·미디어 트랜스코딩·게임 서버 | C |
| 메모리 최적화 | 대용량 데이터를 메모리에서 처리 — 인메모리 DB·분석·엔터프라이즈 앱 | R, X, U, Z |
| 스토리지 최적화 | 수백만 저지연 랜덤 I/O, 대용량 로컬 데이터 순차 읽기/쓰기 — 고처리량 DB·스트리밍 | I, D, Im, Is |
| 가속 컴퓨팅 | 하드웨어 가속기 — 부동소수점·그래픽·패턴 매칭·ML | P, G, Trn, Inf, F, VT |
| HPC 최적화 | HPC 대규모 최고 가격 대비 성능 — 시뮬레이션·딥러닝·렌더링 | Hpc (Hpc6a/6id/7a/7g/8a) |
(F-01·F-02)
- **명명 규칙**: 시리즈(`c`)+세대(`7`)+옵션(`gn`)+`.`+크기. 옵션: `a`=AMD, `g`=Graviton, **`i`=Intel**, `b`=블록 스토리지 최적화, `d`=인스턴스 스토어, `e`=추가 스토리지/메모리, `n`=네트워크·EBS 최적화, `flex`, `z`=고주파수; `Im`=vCPU:메모리 1:4 스토리지, `Is`=1:6 (F-02). 메모리 최적화 예: r7i.large=2 vCPU/16 GiB(1:8) `[블로그]` (F-03).
- **T(버스트)**: 기준선 이하 평균이면 추가 요금 없음, T8i·T4g·T3a·T3는 **기본 unlimited**(24시간 평균이 기준선 초과 시 vCPU-시간당 정액 추가), Spot은 standard 권장, Dedicated Host의 T3는 unlimited 불가 → 지속 고부하는 M 계열 (F-04).
- **Graviton(Arm)**: 동급 x86 대비 가격 대비 성능 **최대 40%**, 에너지 최대 60% 절감(AWS 서술) — 범용·컴퓨트·메모리·스토리지 최적화 계열에 존재, 모든 vCPU가 물리 코어 (F-05). Lambda는 arm64로 최대 19% 성능·20% 비용 개선 `[블로그]` (F-18).
- **배치 그룹**:

| 전략 | 목적 | 한도·규칙 |
|---|---|---|
| **Cluster** | 저지연·고처리량(HPC·MPI) | **단일 AZ**(피어링 VPC 가능), 같은 그룹 내 단일 흐름 **10 Gbps**(그룹 밖 5 Gbps), 동일 유형·한 번에 시작 권장, 버스트(T) 등 일부 유형 불가, 인터넷·DX 트래픽 5 Gbps |
| **Partition** | 대규모 분산/복제(HDFS·HBase·Cassandra) | 리전 내 다중 AZ, **AZ당 최대 7 파티션**, 파티션 간 랙 분리, 파티션 가시성, Dedicated Instances는 2 파티션 |
| **Spread** | 소수 핵심 인스턴스 최대 격리 | 인스턴스별 별도 하드웨어(랙), **AZ당 7개**, 유형 혼합·점진 시작 가능 |
| **Precision time** | 고정밀 시간 동기 하드웨어 | 클러스터 PG의 parent로 연결 가능 |
(F-06)
- **네트워크**: 향상된 네트워킹(SR-IOV, 추가 요금 없음) — Nitro는 **ENA**(최대 100 Gbps); **EFA**=ENA+OS-bypass(SRD), MPI/NCCL, **같은 서브넷·AZ·VPC 안에서만**(AZ/VPC 못 넘고 라우팅 불가, Outposts 미지원); Hpc7a EFA 300 Gbps (F-07).
- **HPC 조합**: 클러스터 배치 그룹 + EFA(+ EFA 지원 Hpc/P/Trn 계열) + **FSx for Lustre**(Task 3.1) — 용량 보장은 클러스터 PG에 On-Demand Capacity Reservation 권장(Capacity Blocks는 배치 그룹 미지원) (F-06).

### 2-3. 스케일링 설계 — 지표·조건 (Knowledge 4, Skill 2)
| 정책 | 동작 | 언제 |
|---|---|---|
| **대상 추적** | 지표를 목표값에 근접 유지(알람 자동 생성) | **대부분의 경우 충분·권장**. 지표는 용량이 늘면 값이 줄어드는 성격이어야 비례 조절 |
| **단계 조정** | CloudWatch 알람 구간별 증감, 활동 진행 중에도 추가 알람에 반응 | 임계 구간별 정밀 반응 |
| **단순 조정** | 알람 1개→고정 증감, 쿨다운 완료까지 대기 | 레거시(단계 조정 권장) |
| **예약** | 시간표대로 용량 설정 | 예측 가능한 일정 |
| **예측** | ML로 48시간 예측, 사전 스케일 아웃 | 반복 패턴·초기화가 오래 걸리는 앱 (스케일 인은 동적 정책 필요) |
(F-08·F-10; 쿨다운·정책 충돌 규칙은 `2-2.md` F-13)
- **사전 정의 대상 추적 지표**: `ASGAverageCPUUtilization`, `ASGAverageNetworkIn/Out`, `ALBRequestCountPerTarget`(`ResourceLabel` 필요). 그 외(큐 깊이·사용자 정의)는 **사용자 지정 지표** (F-08).
- **SQS 큐 기반 워커 스케일링**: 큐 길이만 목표로 삼으면 인스턴스 수를 고려하지 못해 과다 증설 → **backlog per instance = `ApproximateNumberOfMessages` ÷ InService 인스턴스 수**, 목표 = 허용 지연 ÷ 메시지당 평균 처리 시간. 예: 인스턴스 10·메시지 1,500·처리 0.1초·허용 10초 → 목표 100, 현재 150 → 5대 증설 (F-09).
- **웜 풀**: ASG 옆에 사전 초기화 인스턴스를 두어 스케일 아웃 지연 단축(상태 Stopped/Running/Hibernated), 풀 인스턴스는 ASG 지표에 기여하지 않음, 기본 크기=최대−희망 용량, 수명 주기 훅 대기 기본 **1시간** (F-11).
- **스케일링 플랜(AWS Auto Scaling) vs 서비스별 정책**: 스케일링 플랜은 Aurora 복제본·EC2 ASG·ECS 태스크·DynamoDB 용량·Spot Fleet을 한곳에서 구성하는 서비스이나, **예측 스케일링만 쓰면 ASG에 직접 정책을 두라고 권장**하며 마이그레이션 가이드 제공. EC2 **시작 구성(launch configuration)** 은 2024-10-01부터 신규 계정 미지원 → **시작 템플릿** (F-12).
- **Application Auto Scaling(ECS 등)**: ECS 서비스 지표 `ECSServiceAverageCPUUtilization`·`…MemoryUtilization`(20초 고해상도 변형 있음)·`ALBRequestCountPerTarget`; 사용자 지정 지표(큐 메시지 수 등) 가능; **지표가 목표 초과일 때만 스케일 아웃**(미만에서 아웃 불가)·데이터 부족 시 스케일 안 함·**아웃은 빠르게, 인은 점진적**·배포 중 스케일 인 중단 (F-13).
- **Lambda 확장**: 동시 실행 기본 1,000(증액 가능), 함수당 10초마다 1,000 환경, Provisioned vs Reserved 동시성 (`2-1.md` F-13·F-15). **SQS 이벤트 소스 매핑**: 5 배치·5 동시 호출로 시작→분당 최대 300 증가→최대 1,250, FIFO는 활성 메시지 그룹 수까지, **최대 동시성(ScalingConfig)** 또는 **프로비저닝 모드**(폴러 2–200~2–2,000) 중 택일 (F-19).

### 2-4. 분리(decoupling)·메시징 (Knowledge 3, Skill 1)
- **원칙**: 생산자와 소비자 사이에 **큐/토픽**을 두면 각 구성요소를 독립적으로 스케일·장애 격리. SQS는 **버퍼링 로드 밸런서** 역할 — 소비자 증설에 시간이 걸려도 메시지 유실 없음 (F-20).
- **게시/구독 + 큐(팬아웃)**: SNS 토픽 1개 → 여러 SQS 큐로 복제·푸시 → 병렬 비동기 처리, 각 구독 서비스는 자기 큐로 독립 스케일 (F-20).
- 서비스 비교(SQS 표준/FIFO·SNS·EventBridge 버스 vs Pipes·Step Functions·한도·DLQ·Lambda 연동)는 **`2-1.md` §2 및 F-01~F-12** 참조. 패턴 선택: 1:1 작업 큐=SQS, 1:N 알림/팬아웃=SNS(+SQS), 이벤트 라우팅·SaaS 연동=EventBridge, 오케스트레이션=Step Functions.

### 2-5. 서버리스 패턴 (Knowledge 5)
- **Lambda + 이벤트 소스(SQS/Kinesis/API Gateway/S3…)**, 실패 처리=`ReportBatchItemFailures`·DLQ·Destinations (`2-1.md` F-07·F-14), **콜드 스타트 완화**=Provisioned Concurrency·SnapStart(Java) (`2-1.md` F-15).
- **Lambda 사이징 (Skill 4)**: 메모리 128–10,240 MB에 비례해 CPU 할당, **1,769 MB=1 vCPU**; 메모리는 성능 제어의 주 수단이며 메모리 증가가 실행 시간을 줄여 **비용이 비슷하거나 줄 수 있음**(예: 1,000회, 128 MB 11.722초 $0.024628 vs 1,024 MB 1.465초 $0.024638 `[블로그]`); **Lambda Power Tuning**으로 최적점 탐색; Compute Optimizer 메모리 권장 옵트인 (F-18).
- **Fargate 사이징**: 태스크 vCPU·메모리 조합·임시 스토리지 최대 200 GiB (`2-1.md` F-21), Compute Optimizer가 **태스크 수준 CPU·메모리** 권장(24시간 이상 지표 필요) (F-25).
- **Fargate Spot**: 중단 허용 태스크 할인 요금, **2분 경고**(EventBridge 이벤트+SIGTERM), `stopTimeout` ≤120초 (F-15).

### 2-6. 컨테이너 오케스트레이션 (Knowledge 6)
| 질문 | ECS | EKS | Fargate |
|---|---|---|---|
| 정체 | AWS 네이티브 오케스트레이터 | 관리형 Kubernetes | 서버리스 **컴퓨트 엔진**(ECS/EKS 위) |
| 선택 신호 | AWS 서비스와 긴밀 통합·낮은 러닝커브 | K8s가 주 플랫폼 인터페이스, 플랫폼 팀 보유 | 서버·클러스터 관리 최소화 |
(F-16)

### 2-8. 배치/빅데이터 컴퓨트 (Knowledge 1)
- **AWS Batch**: 작업(컨테이너)·작업 정의·작업 큐·컴퓨트 환경. 큐에 제출하면 Batch가 실행 위치를 정하고 필요 시 용량 추가/제거; 컴퓨트 환경은 **EC2/SPOT 또는 FARGATE/FARGATE_SPOT**(혼합 불가, 같은 큐의 환경은 같은 아키텍처); **우선순위 큐**(높은 값 우선)·의존성·공정 공유 정책·GPU 스케줄링; 작업 제한 시간 최소 60초 (F-21).
- **Amazon EMR**: **Serverless**(클러스터 관리 없이 자동 확장, 가장 빠른 시작) / **on EC2**(클러스터 제어·장기 실행·커스텀 AMI·Spot) / **on EKS**(Spark 작업을 기존 K8s 클러스터에 제출). 코어 노드는 HDFS 보유, **태스크 노드는 Spot 권장**(중단돼도 데이터 손실 없음); on EC2는 클러스터 단위, on EKS는 작업 단위(vCPU·메모리)로 스케일 (F-22).

## 3. 시험에서 묻는 방식 (패턴)
1. **큐 기반 워커 확장**: "SQS 메시지가 쌓이면 EC2 워커를 늘리고 비면 줄여라" → **ASG + backlog-per-instance 사용자 지정 지표 대상 추적**. 오답: 큐 길이 단순 목표, CPU 지표만, 수동 조정.
2. **지연이 큰 부팅**: "스케일 아웃 시 초기화에 10분 걸려 응답 지연" → **웜 풀**(+예측 스케일링으로 사전 확장).
3. **반복 패턴**: "매일 오전 9시 트래픽 급증이 예측" → **예약 또는 예측 스케일링**; 지표 기반 보완은 대상 추적.
4. **서버리스 vs 컨테이너 vs Batch**: "15분 초과 배치, 완료 후 종료, Spot으로 비용 절감" → **AWS Batch**(Fargate/EC2 Spot 환경). "이벤트당 짧은 처리" → Lambda. "서버 관리 없이 컨테이너" → **Fargate**.
5. **HPC/ML 분산 학습**: "노드 간 초저지연·MPI" → **클러스터 배치 그룹 + EFA(+FSx for Lustre)**, 단일 AZ·같은 서브넷 제약 주의.
6. **Lambda 성능**: "함수가 CPU 병목" → **메모리 증가**(CPU 비례), Power Tuning으로 비용-성능 최적점; "콜드 스타트 지연 제거" → Provisioned Concurrency.
7. **엣지 로직**: "CDN 엣지에서 URL 재작성·헤더 조작을 초저지연" → **CloudFront Functions**; "엣지에서 외부 호출·복잡 로직" → **Lambda@Edge**; "5G 단말 초저지연" → **Wavelength**; "대도시 근접 + 데이터 레지던시" → **Local Zones**; "온프레미스에서 AWS 인프라" → **Outposts**.
8. **컨테이너 선택**: "Kubernetes 표준 필요" → **EKS**; "AWS 네이티브, 운영 최소" → **ECS on Fargate**; "중단 허용 컨테이너 배치" → **Fargate Spot**.
9. **분리 설계**: "하나의 이벤트를 여러 소비자가 독립적으로 처리하고 장애 격리" → **SNS 토픽 + 소비자별 SQS 큐(팬아웃)**.

## 4. 흔한 함정·혼동 짝
- **Fargate는 오케스트레이터가 아니다**(ECS/EKS의 컴퓨트 엔진). Fargate는 Local Zones·Wavelength·Outposts 미지원.
- **App Runner는 신규 고객 불가(2026-04-30~)**: 옛 자료의 "간단한 웹 앱 컨테이너 → App Runner" 식 답은 현재 신규 설계로는 쓸 수 없음. 도메인 3 가이드 본문에는 App Runner가 없음(대체 서비스 권고 문장은 미확보 → `99-gaps.md`).
- **대상 추적은 "지표가 목표 초과"일 때만 아웃**, 큐 길이 같은 비례하지 않는 지표는 backlog per instance로 보정.
- **예측 스케일링은 스케일 아웃만**(인은 동적 정책), 최소 24시간 데이터, 처음엔 forecast-only.
- **단순 조정은 레거시**: 쿨다운·진행 중 활동 대기 때문에 단계 조정이 권장.
- **시작 구성 ≠ 시작 템플릿**: 시작 구성은 2024-10-01부터 신규 계정 미지원.
- **클러스터 배치 그룹은 단일 AZ → AZ 장애 SPOF**(Task 2.2). 분산 장애 격리는 Partition/Spread.
- **Spread = AZ당 7개**, **Partition = AZ당 7개 파티션**(인스턴스 수는 계정 한도).
- **T 인스턴스 unlimited 기본**: 지속 고부하면 추가 과금 → M 계열.
- **EFA는 같은 서브넷 내 OS-bypass**, 라우팅 불가·AZ/VPC 못 넘음.
- **CloudFront Functions vs Lambda@Edge**: 단순·초고속 변환 vs 연산·외부 연동. 캐시 가능 콘텐츠는 Lambda@Edge가 캐시 미스에서만 실행.
- **Lambda 메모리 ↔ CPU**: 별도 CPU 설정 없음(비례). 하지만 메모리를 올려도 CPU 한계를 넘으면 이득이 줄어듦(Power Tuning으로 변곡점 확인).
- **Batch 컴퓨트 환경은 EC2와 Fargate를 한 큐에 섞을 수 없음.**
- **EKS Auto Mode 노드는 최대 21일**(워크로드가 노드 순환을 견뎌야 함).
- **Lambda 실행 시간**: 함수 타임아웃은 최대 900초(15분)이며, 비동기·이벤트 소스 매핑 호출 타임아웃을 90분까지 허용하는 것은 Lambda Managed Instances뿐(`2-1.md` F-13·F-16).

## 6. 자가 점검 문항 후보 (재료)
1. **큐 기반 워커 스케일링**: SQS에서 메시지를 소비하는 EC2 워커 ASG. 큐가 비면 줄이고 쌓이면 늘리되 과다 증설을 피하라. → **backlog per instance 사용자 지정 지표 + 대상 추적**(목표=허용 지연÷메시지 처리 시간). 오답: 큐 길이 자체를 목표로 대상 추적. 근거 F-08·F-09.
2. **계산**: 인스턴스 10대, 큐 가시 메시지 1,500, 처리 0.1초/건, 허용 지연 10초일 때 목표 backlog와 증설 수? → 목표 10÷0.1=100, 현재 150 → **5대 증설**. 근거 F-09.
3. **웜 풀**: 앱 초기화가 길어 스케일 아웃 중 지연이 발생. → **웜 풀**(및 예측 스케일링). 근거 F-10·F-11.
4. **서버리스 선택**: 이벤트당 수 초 처리·15분 이내·최소 운영. → **Lambda**; 15분 초과·완료 후 종료·Spot → **AWS Batch**. 근거 F-21·`2-1.md` F-13.
5. **HPC 클러스터**: MPI 시뮬레이션 100노드, 노드 간 지연 최소. → **클러스터 배치 그룹(단일 AZ) + EFA 지원 인스턴스**, 공유 파일은 FSx for Lustre. 오답: 분산 배치 그룹(7개 한도·지연 이점 없음), 다중 AZ. 근거 F-06·F-07.
6. **엣지 로직**: CDN에서 모든 요청의 URL을 재작성하고 헤더를 추가하며 1 ms 미만 지연. → **CloudFront Functions**; 엣지에서 DynamoDB 조회가 필요하면 **Lambda@Edge**. 근거 F-23.
7. **컨테이너**: Kubernetes 매니페스트를 유지하되 노드 패치/관리 부담을 줄이고 싶다. → **EKS Auto Mode**(또는 Fargate); 오답: 자체 관리형 노드. 근거 F-17.
8. **Lambda 사이징**: CPU 집약 함수가 느리고 메모리는 충분하다. → **메모리 증가**(CPU 비례)와 Power Tuning으로 비용 최적점 확인, arm64 검토. 근거 F-18.
