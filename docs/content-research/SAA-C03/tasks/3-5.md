## 2. 핵심 개념

### 2-1. 수집 패턴·빈도와 구성 선택 (Knowledge 2, Skill 6)
| 패턴 | 지연·단위 | 특징 | 대표 서비스 |
|---|---|---|---|
| **배치** | 분~일, 묶음(경계 있는 데이터) | 여러 소스·형식을 결합, 전체 데이터에 다중 패스 분석, 필요할 때만 컴퓨트(서버리스 확장: Glue·EMR Serverless·Batch+Fargate) | DataSync·Glue ETL·EMR |
| **마이크로 배치** | 수 초~수 분 | 연속 스트림을 작은 청크로 나눔, 스트리밍보다 저렴한 **준실시간** | Firehose(버퍼)·Spark Streaming |
| **스트리밍** | 초~ms, 레코드/소량 묶음 | 클라이언트 장애 시 이벤트 유실 위험↓, 보고 시간 단축, 다중 독립 소비자 | Kinesis Data Streams·MSK·Flink |
(F-07. 하이브리드=실시간 계층+배치 계층, 예: 스트림에서 실시간 인사이트 → S3에 적재 후 배치 변환. 개별 이벤트마다 전송하면 비효율이라 스트리밍도 어느 정도 배칭을 사용.)
- **동종(homogeneous) vs 이기종(heterogeneous) 수집**: 동종=형식·엔진 그대로 이동(속도·암호화·무결성·자동화가 목표, ETL의 "추출·적재" 단계), 이기종=수집 중 변환(타입·형식 변환부터 ML 속성 도출까지). DB 마이그레이션 동종/이기종은 `3-3.md` §2-2 (F-07).
- **수집 구성 결정 요소**: ① 빈도·지연 허용(배치/마이크로/스트리밍) ② 데이터 크기·속도(전송 시간, §2-3) ③ 소비자 수·재처리 여부(Data Streams vs Firehose) ④ 목적지·형식(S3·Redshift·OpenSearch…, Parquet 변환) ⑤ 보안(전송·저장 암호화, 프라이빗 연결).

### 2-2. 스트리밍 아키텍처 (Knowledge 7, Skill 2)
| 서비스 | 역할 | 핵심 |
|---|---|---|
| **Kinesis Data Streams** | 실시간 수집·보존·다중 소비 | 샤드=기본 처리량 단위; 보존 24시간~(확장 7일, 장기 365일); EFO; 용량 모드 (F-01·F-02) |
| **Amazon Data Firehose** | 관리형 **적재**(준실시간) | S3·Redshift·OpenSearch·Splunk·Iceberg·HTTP; 버퍼; Lambda 변환; **JSON→Parquet/ORC 변환(S3만)**; 동적 파티셔닝 (F-04) |
| **Managed Service for Apache Flink** | 스트림 **분석·집계**(서브초 지연) | Kinesis Data Streams·MSK 입력, Java·Python·SQL·Scala (F-05) |
| **Amazon MSK** | **Apache Kafka** 호환 관리형 | 기존 Kafka 도구·API 유지, MSK Serverless~Provisioned (F-06) |
| **Kinesis Video Streams** | 영상 스트림 | 카메라·디바이스 영상 수집 (`saa-t3-9`) |
- **Data Streams 처리량 설계**: 샤드당 쓰기 **1 MB/s 또는 1,000 레코드/s**, 읽기 **2 MB/s(비-EFO 소비자들이 공유)**, EFO 소비자마다 샤드당 2 MB/s(예: 2샤드×2 MB/s×소비자 5=20 MB/s), 1 GB/s 스트림≈1,024샤드 (F-01).
- **용량 모드**: **온디맨드**(용량 계획 불필요·자동 샤드 관리·기본 쓰기 4 MB/s, 이전 30일 피크의 2배까지 수용, 15분 내 2배 초과 시 스로틀 가능→재시도) vs **프로비저닝**(샤드 수 지정, `UpdateShardCount`/Auto Scaling); 모드 전환은 24시간에 2회 (F-02).
- **선택 규칙**: 재처리·다중 독립 소비자·커스텀 처리=Data Streams; 코드 없이 목적지 적재·형식 변환=Firehose; 실시간 집계/윈도우 분석=Flink; Kafka 호환 필수=MSK; 예측 불가 트래픽=Data Streams 온디맨드 (F-01·F-02·F-04~F-06).
- **스트리밍 보안**: IAM 정책, HTTPS 엔드포인트, **KMS 서버 측 암호화**(사용자 지정 키는 생산자·소비자에 KMS 권한 필요 — 없으면 PutRecord/GetRecords 실패), 클라이언트 측 암호화, **VPC 인터페이스 엔드포인트(PrivateLink)** 로 IGW·NAT·VPN 없이 접근 + 엔드포인트 정책/IAM 조건으로 특정 스트림·엔드포인트만 허용 (F-03).

### 2-3. 데이터 전송 솔루션과 크기·속도 (Knowledge 3·6, Skill 3)
| 서비스 | 용도 | 핵심 | 비고 |
|---|---|---|---|
| **AWS DataSync** | 온프레미스↔AWS(및 AWS 서비스 간) **온라인** 대량·반복 전송 | 에이전트(VM) 배포, NFS·SMB·자체 관리 오브젝트 스토리지 ↔ S3·EFS·FSx, 증분·스케줄·필터·대역폭 제한·무결성 검증·전송 중 암호화, 인터넷/DX/VPN | 에이전트 1개당 동시 태스크 1개 (F-08) |
| **Storage Gateway** | 로컬 캐시가 필요한 **하이브리드 스토리지** 인터페이스 | S3 File·Volume·Tape | `3-1.md` F-20 |
| **Transfer Family** | 기존 SFTP/FTPS/FTP/AS2 워크플로를 S3·EFS로 | 프로토콜별 시간당+데이터 요금 | `2-1.md` F-27 |
| **Direct Connect / VPN** | 안정적 사설 회선·암호화 터널 | 속도·복원력 | `3-4.md` F-18·F-19 |
| **S3 Transfer Acceleration·멀티파트** | 원거리 업로드 가속 | 엣지 경유, 병렬 파트 | `3-1.md` F-03·F-04 |
| **DMS** | DB 이전·CDC | 동종/이기종 | `3-3.md` F-20 |
| **Snow 패밀리** | (구) 오프라인 대용량 | **Snowball Edge는 신규 고객 불가** — 대안: DataSync(온라인)·**Data Transfer Terminal**(물리 시설 업로드)·파트너 | F-09 |
- **전송 시간 산술**(이상적 100% 효율 가정, 실제는 오버헤드 가산): `시간 = 데이터량(bit) ÷ 가용 대역폭(bit/s)`. 예: 10 TB ÷ 100 Mbps ≈ 9.3일(공식 예시는 "약 10일"), 100 TB ÷ 1 Gbps ≈ 9.3일, 1 PB ÷ 10 Gbps ≈ 9.3일 (F-08의 공식 예시와 일치하는 계산). 대역폭의 일부만 쓰도록 DataSync 대역폭 제한을 설정하고 시간 창을 계획 (F-08).
- **Data Transfer Terminal**: 시간대를 예약해 가까운 시설에서 **보유 스토리지 장치**를 가져가 고대역폭으로 업로드(시설당 100 Gbps 광 연결 2개, 장치 통제권은 고객이 유지) (F-09).

### 2-4. 데이터 레이크 구축·보호 (Skill 1, Knowledge 5)
- **구축 요소**: S3(저장) + **Glue Data Catalog**(메타데이터 허브: Athena·Redshift Spectrum·EMR·RDS 등이 공유) + **Lake Formation**(권한) + 수집(Firehose·DataSync·Glue) + 분석(Athena·EMR·Redshift) (F-11·F-13).
- **Lake Formation**: 데이터 레이크를 안전하게 구성하는 **중앙 관리 지점**, Data Catalog에 메타데이터·접근 설정 저장; **S3 위치를 등록**(IAM 역할 지정: 서비스 연결 역할 또는 사용자 지정 — 교차 계정·암호화된 위치·EMR 접근 시 사용자 지정), 통합 엔진(Athena·Glue·Redshift Spectrum·EMR)은 **신뢰된 호출자**로서 임시 자격 증명을 받아 S3 접근; 데이터베이스·테이블·**열·행·셀 수준** 권한(엔진별 지원 범위 상이), **LF-tags**(태그 기반 접근 제어), CloudTrail 감사 (F-13).
- **암호화·감사**: S3 서버 측 암호화+KMS 키 정책에 등록 역할·Glue 잡/크롤러 역할 포함, 버킷 정책으로 KMS 암호화 업로드 강제, Glue 보안 구성, 전송 중 TLS, CloudTrail·S3 액세스 로깅 (F-13의 `[블로그]`, F-16). S3 암호화 세부는 `1-3.md`, 비공개 접근(게이트웨이 엔드포인트)은 `3-4.md` F-13.
- **수집 접점 보안(Knowledge 5)**: Kinesis=IAM+KMS+VPC 엔드포인트(F-03), S3=버킷 정책·액세스 포인트·게이트웨이 엔드포인트, DataSync=전송 중 암호화(F-08), Transfer Family·Storage Gateway 엔드포인트 유형은 `2-1.md` F-27·`3-1.md` F-20.

### 2-5. 데이터 변환·형식 변환 (Knowledge 4, Skill 7)
| 방법 | 언제 | 핵심 |
|---|---|---|
| **AWS Glue ETL**(Spark) | 서버리스 배치 변환, 스키마 자동 발견 | 크롤러가 S3 스키마 추론→Data Catalog; **잡 북마크**로 증분 처리(DynamicFrame+`transformation_ctx`+`job.init/commit`, Spark DataFrame API는 미지원); 최적화 Parquet 라이터(스키마 진화); DPU-시간 과금 (F-11) |
| **Athena CTAS** | S3에서 SQL만으로 CSV→Parquet/ORC 변환·파티셔닝 | `CREATE TABLE AS SELECT`에 저장 형식 지정 (F-12) |
| **Firehose 변환** | 스트림 도중 JSON→Parquet/ORC | S3 목적지만, Glue Data Catalog 스키마, 버퍼 ≥64 MiB(기본 128 MiB) (F-04) |
| **Lambda 변환(Firehose)** | 레코드 단위 가공(로그 파싱 등) | 블루프린트, 원본 백업 (F-04) |
| **EMR(Spark)** | 커스텀 코드·대규모·장기 실행 | `3-2.md` F-22 |
- **왜 Parquet**: 열 단위 압축(컬럼 타입별 코덱)·**조건부 푸시다운**(통계로 블록 건너뜀)·분할 가능(병렬 읽기) → 스캔량↓=비용↓·성능↑. 압축·파티셔닝·열 형식 변환으로 쿼리당 비용 **30~90%** 절감, 파일은 너무 작지 않게(일반적으로 128 MB 초과) (F-12).

### 2-7. 시각화 전략 (Skill 4)
- **Amazon Quick(Quick Sight)**: 서버리스·임베드 가능·ML 기반 BI, 사용자 확장(수십만), **SPICE**(인메모리 엔진, 데이터는 삭제 전까지 유지·자동 복제)로 빠른 대시보드, ML 인사이트(예측·이상 탐지), 연결: Athena·Redshift·RDS·S3·SaaS·온프레미스 DB·VPC 프라이빗 서브넷 (F-14).
- **전략**: 대시보드 응답성이 핵심이면 SPICE로 가져오기, 항상 최신이 필요하면 직접 쿼리(Athena/Redshift), 외부 사용자에게 제품 내 노출이면 임베딩; 열/행 수준 보안·VPC 접근·암호화는 Enterprise 기능으로 서술됨(과거 백서) (F-14).

## 3. 시험에서 묻는 방식 (패턴)
1. **다중 소비자 클릭스트림**: "초당 수천 이벤트, 두 개 애플리케이션이 각자 처리, 재처리 필요" → **Kinesis Data Streams**(필요하면 EFO). 함정: Firehose(단일 목적지·재처리 불가).
2. **코드 없는 S3 적재+형식 변환**: "IoT 로그를 JSON→Parquet로 S3에 자동 저장" → **Firehose**(형식 변환은 S3 목적지에서만).
3. **즉석 로그 분석**: "S3의 수 TB 로그를 인프라 없이 SQL" → **Athena**; 비용 절감은 **Parquet+파티션+압축**.
4. **열 수준 접근 제어**: "분석가별 PII 열 숨김" → **Lake Formation**(데이터 필터/LF-tags), IAM만으로는 어려움.
5. **온프레미스 NFS→S3 정기 동기화**: "증분·검증·대역폭 제한" → **DataSync**(에이전트). 캐시된 파일 인터페이스가 필요하면 **S3 File Gateway**.
6. **대량 이관 계획**: "200 TB를 1 Gbps로, 보유 장치 반출 가능" → 전송 시간 계산(≈18.5일) 후 **DataSync(+DX)** 또는 **Data Transfer Terminal**; 옛 답 "Snowball"은 신규 고객 불가.
7. **서버리스 ETL vs 클러스터**: "Spark ETL, 서버 관리 없음, 스키마 자동 발견" → **Glue**; "특정 라이브러리·Spark 버전 고정·장기 실행" → **EMR**.
8. **트래픽 예측 불가 스트림**: "용량 계획 없이" → **Data Streams 온디맨드**; "Kafka API 유지" → **MSK**.
9. **BI**: "서버리스 대시보드·임베디드 분석" → **Amazon Quick(Quick Sight)** + SPICE.
10. **프라이빗 수집**: "VPC에서 Kinesis에 인터넷 없이" → **인터페이스 VPC 엔드포인트**+엔드포인트 정책.

## 4. 흔한 함정·혼동 짝
- **Data Streams vs Firehose**: 재처리·커스텀 소비자·보존(최대 365일) vs 관리형 준실시간 적재(버퍼 지연). Firehose의 **형식 변환은 S3 전용**, 변환 사용 시 OpenSearch·Redshift·Splunk 목적지 불가.
- **소비자가 늘면 읽기 대역폭을 나눠 쓴다**: 비-EFO 소비자는 샤드당 2 MB/s를 **공유**, EFO는 소비자별 2 MB/s.
- **온디맨드 ≠ 무한 즉시**: 이전 피크의 2배, 15분 내 초과 시 스로틀(재시도 필요). 모드 전환 24시간 2회.
- **Kinesis Data Analytics → Managed Service for Apache Flink**(개명), **Kinesis Data Firehose → Amazon Data Firehose**.
- **Lake Formation은 IAM 대체가 아님**: 등록 위치·IAM 역할·LF 권한이 함께 필요하고, 엔진별 열/행/셀 지원 범위가 다름(예: Athena Spark 미지원, Hive on EMR 행 수준 미지원, Glue ETL은 5.0+).
- **Glue 잡 북마크**: DynamicFrame·`transformation_ctx` 필수, 동시 실행 시 최대 동시성 1, Spark DataFrame으로 읽으면 무효.
- **Athena 비용**=스캔 바이트(최소 10 MB/쿼리). 작은 파일 다수는 오히려 오버헤드 → 128 MB 이상으로 합침. S3/Athena 요청 5,500/s 한계.
- **DataSync 에이전트는 1 태스크씩**: 병렬 전송은 에이전트 추가.
- **Snow 패밀리**: Snowball Edge는 2025-11 이후 신규 고객 불가(유지보수), 어떤 Snow 디바이스도 신규 주문 불가. (현행 3.5 Task 본문 예시에는 Snow가 없으나 현행 In-Scope 서비스 목록에는 "AWS Snow Family"가 아직 포함 — 이전 버전에서 제거됐는지는 확인하지 못함 → `99-gaps.md`)
- **Quick(Quick Sight) SPICE**: 인메모리 가져오기(삭제 전까지 유지) vs 직접 쿼리의 신선도 차이.
- **Storage Gateway/DataSync 구분**: 하이브리드 캐시 인터페이스(지속 접근) vs 전송 작업(일회성·스케줄 이전).
- **Redshift Spectrum/통합 데이터 레이크 쿼리 엔진**: RG·Serverless에서는 Spectrum 별도 요금 없이 통합 엔진 사용(문서 서술).

## 6. 자가 점검 문항 후보 (재료)
1. **다중 독립 소비자**: 클릭스트림을 실시간 집계 앱과 아카이브 앱이 각자 처리, 장애 시 재처리 필요. → **Kinesis Data Streams**(비-EFO 소비자는 샤드당 2 MB/s 공유, 지연·처리량이 중요하면 **EFO**). 오답: Firehose. 근거 F-01·F-04.
2. **샤드 계산**: 레코드 평균 2 KB, 초당 3,000건을 쓰는 스트림의 최소 샤드 수? → 대역폭 3,000×2 KB≈6 MB/s ÷ 1 MB/s = 6샤드, 건수 3,000 ÷ 1,000 = 3샤드 → 둘 중 큰 값 **6샤드**. 근거 F-01.
3. **형식 변환 적재**: JSON 로그를 Parquet로 변환해 S3에 near real-time 저장, 코드 최소화. → **Firehose 형식 변환**(스키마는 Glue 테이블, 버퍼 ≥64 MiB). 오답: OpenSearch 목적지 병행(변환 시 S3만). 근거 F-04.
4. **CSV→Parquet 일괄 변환**: S3 CSV 5 TB를 Athena 비용 절감을 위해 변환. → **Athena CTAS(Parquet)** 또는 **Glue ETL**(서버리스 Spark), 파티셔닝·압축 병행. 근거 F-11·F-12.
5. **열 수준 접근**: 분석가 그룹별로 PII 열만 숨김, Athena·Redshift Spectrum에 일관 적용. → **Lake Formation**(데이터 필터/LF-tags, S3 위치 등록). 단 Athena Spark는 미지원. 근거 F-13.
6. **전송 시간**: 온프레미스 NFS 80 TB를 1 Gbps 회선으로 S3에 보내는 최소 시간? → 80 TB = 6.4×10^14 bit ÷ 10^9 bit/s = 6.4×10^5 s ≈ **7.4일**(이상적 가정, 실제 더 길어짐). 대역폭을 일부만 쓰려면 **DataSync 대역폭 제한**. 근거 F-08.
7. **옛 Snowball 문제**: 인터넷 대역폭이 부족한 사이트에서 수백 TB를 이전. → **DataSync(+Direct Connect)** 또는 **Data Transfer Terminal**. Snowball Edge는 신규 불가. 근거 F-09.
8. **서버리스 ETL vs EMR**: 일 1회 짧은 Spark ETL, 서버 관리 없이 → **Glue**(또는 EMR Serverless); 하루 종일 도는 잦은 잡·데이터 유지 필요 → EMR on EC2. 근거 F-11.
9. **프라이빗 수집**: 인터넷 경로 없는 VPC의 앱이 Kinesis로 전송. → **인터페이스 VPC 엔드포인트**(+엔드포인트 정책으로 특정 스트림만). 근거 F-03.
