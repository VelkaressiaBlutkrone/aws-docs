### 2-2. S3 성능 설계 (Skill 1·2, Knowledge 2)
- **확장성**: 총 데이터 양·객체 수 **무제한**, 개별 객체 0바이트~**50 TB**(단일 PUT은 5 GB까지, 큰 객체는 멀티파트) (F-01·F-24).
- **요청 성능은 버킷이 아니라 프리픽스 단위**: 파티션된 프리픽스당 **3,500 PUT/COPY/POST/DELETE** 또는 **5,500 GET/HEAD** 초당, 프리픽스 수 제한 없음 → 여러 프리픽스에 **병렬**(예: 10개 → 읽기 55,000 rps). 급증 시 S3가 자동 파티셔닝하며 일시적 **503 SlowDown** → 지수 백오프 재시도 (F-02).
- **성능 기법 4종** (F-02~F-04):

| 기법 | 무엇을 해결 | 비고 |
|---|---|---|
| 프리픽스 병렬화 | 요청 처리율 한계 | 키 이름을 무작위화할 필요 없음(고유 키 네이밍은 모범 사례 아님) |
| 멀티파트 업로드 | 대용량 업로드 속도·재시도 | 파트 독립·순서 무관·병렬; **100 MB 초과 시 고려**, 5 GB 초과 단일 객체는 필수; 완료 못 한 파트는 저장 비용 → `AbortIncompleteMultipartUpload` |
| Transfer Acceleration | 원거리 업로드/다운로드 | CloudFront 엣지 경유, 대륙 간·큰 객체에 효과, **가속된 전송에만 과금**, 별도 엔드포인트(`<bucket>.s3-accelerate.amazonaws.com`) |
| 바이트 범위 요청 | 대용량 부분 읽기·병렬 다운로드 | 병렬 GET (File Gateway도 캐시 미스 시 사용) |
- **강한 일관성**: 모든 GET/PUT/LIST에서 read-after-write 강한 일관성, 추가 비용·성능 영향 없음 (F-05).
- **S3 Express One Zone**: 단일 AZ·디렉터리 버킷, **일관된 한 자릿수 ms**, Standard 대비 접근 최대 10배·요청 비용 최대 80% 저렴, 컴퓨트와 **같은 AZ에 공존** 가능, 가용성 99.95%(SLA 99.9%); 디렉터리 버킷 기본 읽기 200,000·쓰기 100,000 rps(증액 시 최대 읽기 200만·쓰기 20만) → ML 학습·분석·대화형 워크플로. **단일 AZ라 유실 불가 원본 저장소로는 부적합** (F-06).

### 2-3. EBS 볼륨 선택 (Skill 1·2, Knowledge 2)
| 구분 | gp3 | gp2 | io2 Block Express | io1 | st1 | sc1 |
|---|---|---|---|---|---|---|
| 계열 | 범용 SSD | 범용 SSD(구) | 프로비저닝 IOPS SSD | 프로비저닝 IOPS SSD | 처리량 HDD | 콜드 HDD |
| 크기 | 1 GiB–**64 TiB** | 1 GiB–16 TiB | 4 GiB–**64 TiB** | 4 GiB–16 TiB | 125 GiB–16 TiB | 125 GiB–16 TiB |
| 최대 IOPS | **80,000** | 16,000 | **256,000** | 64,000 | 500 | 250 |
| 최대 처리량 | 2,000 MiB/s | 250 MiB/s | 4,000 MiB/s | 1,000 MiB/s | 500 MiB/s | 250 MiB/s |
| 내구성 | 99.8–99.9% | 99.8–99.9% | **99.999%** | 99.8–99.9% | 99.8–99.9% | 99.8–99.9% |
| Multi-Attach | ✗ | ✗ | ✓ | ✓ | ✗ | ✗ |
| 부팅 볼륨 | ✓ | ✓ | (표에 명시 없음) | (표에 명시 없음) | ✗ | ✗ |
| 용도 | 범용 기본, 가상 데스크톱, 중소형 단일 인스턴스 DB, 부팅 | 레거시 범용 | 지속 IOPS·**평균 500 µs 미만** 서브밀리초, **80,000 IOPS·2,000 MiB/s 초과** | 지속 IOPS·**16,000 IOPS 초과**, I/O 집약 DB | 빅데이터·데이터 웨어하우스·로그 처리 | 드문 접근·최저 비용 |
(F-07·F-08. I/O 크기 기준: gp3 25.6 KiB, gp2/io1/io2 16 KiB로 최대 IOPS 달성)
- **IOPS와 처리량의 지배 지표**: SSD 계열은 IOPS(작은 I/O, 트랜잭션), HDD 계열은 처리량(큰 순차 스트리밍) (F-08).
- **gp3 vs gp2**: gp3는 **기본 3,000 IOPS·125 MiB/s(용량 무관, 버스트 없음)** + IOPS·처리량 **독립 프로비저닝**(IOPS는 GiB당 500비율로 최대 80,000, 처리량은 IOPS당 0.25 MiB/s로 최대 2,000 MiB/s), GiB당 gp2보다 **20% 저렴**. gp2는 **GiB당 3 IOPS**(최소 100, 1 TB 미만은 3,000 버스트)라 IOPS를 늘리려면 용량을 늘려야 함 (F-09).
- **제약**: 인스턴스가 **EBS 최적화**여야 프로비저닝 IOPS를 모두 사용; **Nitro 인스턴스만 io2 256,000 IOPS**(그 외는 최대 32,000 달성); io1 1,000 MiB/s는 64,000 IOPS 프로비저닝+Nitro 필요 (F-07·F-11).
- **Multi-Attach**: **io1/io2만**, **같은 AZ의 최대 16개 Nitro 인스턴스**, 비부팅 데이터 볼륨. 표준 파일 시스템(XFS·EXT4·NTFS)은 동시 접근용이 아니어서 **클러스터 인식 파일 시스템**이나 **NVMe 예약(펜싱)** 이 필요 (F-10).
- **Elastic Volumes(확장 가능성)**: 크기·유형·IOPS를 운영 중 변경(최신 세대 인스턴스는 분리·중지 불필요), 변경 뒤 **파일 시스템을 직접 확장**, **크기 축소 불가**(작은 볼륨 새로 만들어 rsync/robocopy), 같은 볼륨은 **롤링 24시간에 최대 4회** 수정 (F-11).
- **인스턴스 스토어**: 호스트에 **물리적으로 부착**된 임시 블록 스토리지 — 시작 시에만 연결, 인스턴스 수명 동안만 존재. **재부팅은 유지**, **중지·최대 절전·종료·인스턴스 유형 변경·은퇴·드라이브 장애는 소실**. 장기 데이터는 EBS/S3/EFS로 복사 (F-12). → 캐시·버퍼·스크래치처럼 **재생성 가능한** 초고성능 데이터용.

### 2-4. EFS (Skill 1·2, Knowledge 2)
- **NFS v4.0/4.1**(4.1 권장) 기반, 수천 EC2 동시 마운트, **Linux 전용(Windows EC2 마운트 미지원)**, 페타바이트까지 **자동 증감**(용량 사전 지정 없음) (F-15·F-24).
- **구성 3축**: 파일 시스템 유형(**Regional**=다중 AZ / **One Zone**) × 성능 모드 × 처리량 모드 (F-13).
- **성능 모드**: **General Purpose**(기본·최저 지연, One Zone은 항상 GP) vs **Max I/O**(*이전 세대*, 지연 높음, One Zone·Elastic 처리량 미지원) — **모든 파일 시스템에 GP 권장** (F-14).
- **처리량 모드 선택**:

| 모드 | 언제 | 요금 |
|---|---|---|
| **Elastic**(권장) | 스파이크·예측 어려움, 평균/피크 비율 **5% 이하** | 쓰고 읽은 만큼 |
| **Provisioned** | 요구 처리량을 알고 있음, 평균/피크 **5% 이상** | 프로비저닝 처리량 |
| **Bursting** | 처리량이 저장 용량에 비례하면 충분 (80% 초과·크레딧 소진 시 Elastic/Provisioned로 전환) | 스토리지 요금에 포함 |
- **성능 수치(General Purpose, Regional)** (F-13): Elastic 읽기 IOPS 900,000–2,500,000·쓰기 500,000, 처리량 읽기 20–60 GiBps / 쓰기 1–5 GiBps; Provisioned 55,000/25,000 IOPS, 3–10 / 1–3.33 GiBps; Bursting 35,000/7,000 IOPS, 3–5 / 1–3 GiBps; 지연은 읽기 ~1 ms·쓰기 ~2.7 ms(One Zone 쓰기 ~1.6 ms). **IOPS는 별도 과금 없음**(처리량에 포함).
- **스토리지 클래스**: Standard(SSD, 지연 1 ms/2.7 ms) vs IA·Archive(첫 바이트 **수십 ms**) (F-15). *(비용 관점은 Task 4.1)*

### 2-6. 하이브리드 스토리지 (Knowledge 1)

|---|---|---|

| 물리 **테이프 백업** 대체 | **Tape Gateway** | 가상 테이프 라이브러리, 테이프를 S3/Glacier에 보관, 주요 백업 앱 지원 (F-20) |
| 온프레미스에 **로컬 데이터 처리·데이터 레지던시** | **AWS Outposts + S3 on Outposts / EBS on Outposts** | S3 API 그대로(S3 Outposts 클래스), DataSync로 리전과 전송 (F-22) |
| Windows 파일 서버 캐시 | ~~FSx File Gateway~~ | **2024-10-28부터 신규 고객 불가**(기존 고객은 계속 사용) — 새 설계 선택지로 고르지 말 것 (F-20) |
- 게이트웨이는 **VM(VMware ESXi·Hyper-V·KVM·Nutanix AHV)·하드웨어 어플라이언스·EC2**로 배포. **Direct Connect**와 함께 쓰면 전용 회선(공용 VIF로 Storage Gateway 엔드포인트 접근) (F-20). 대량 일회성 이전·반복 동기화는 DataSync·Snow(Task 3.5).

## 3. 시험에서 묻는 방식 (패턴)
1. **공유 스토리지 선택**: "여러 AZ의 Linux EC2 수백 대가 동시에 읽고 쓰는 공유 파일 시스템, 용량 예측 불가" → **EFS**(Regional, Elastic 처리량). 오답: EBS Multi-Attach(같은 AZ·클러스터 FS 필요), S3(파일 시스템 아님).
2. **Windows 환경**: "Windows 서버 SMB 공유 + AD 인증" → **FSx for Windows File Server**. 함정: EFS는 Windows 미지원.
3. **HPC/ML**: "S3 데이터를 서브밀리초·초고처리량 파일 시스템으로 처리" → **FSx for Lustre**(S3 링크). 영구 데이터면 persistent, 임시면 scratch.
4. **블록 성능**: "DB가 200,000 IOPS·서브밀리초 필요" → **io2 Block Express**(Nitro, 최대 256,000). "80,000 이하 일반 DB·가성비" → **gp3**(IOPS 독립 프로비저닝). "큰 순차 스캔·로그 처리 저비용" → **st1**.
5. **S3 성능**: "전 세계 클라이언트가 한 리전 버킷에 대용량 업로드" → **Transfer Acceleration**(+멀티파트); "초당 요청 한계" → **프리픽스 병렬화**; "한 자릿수 ms·AZ 공존" → **S3 Express One Zone**.
6. **하이브리드**: "온프레미스 NFS/SMB 앱을 코드 변경 없이 S3 지원 + 로컬 캐시" → **S3 File Gateway**; "iSCSI + EBS 스냅샷 복구" → **Volume Gateway**; "물리 테이프 교체" → **Tape Gateway**.
7. **휘발성 vs 영속**: "가장 빠른 임시 스크래치, 인스턴스 중지 시 소실 허용" → **인스턴스 스토어**; "중지 후에도 보존" → **EBS**.

## 4. 흔한 함정·혼동 짝
- **EBS Multi-Attach ≠ 파일 공유**: 같은 AZ·io1/io2·클러스터 FS 필요. 일반 공유는 EFS/FSx.
- **EFS vs FSx for Windows**: NFS(Linux 전용) vs SMB(Windows, AD 필수에 가까운 통합).
- **FSx for Lustre vs OpenZFS vs ONTAP**: HPC/S3 통합 vs ZFS 데이터 서비스·NFS vs 멀티프로토콜(iSCSI 포함).
- **gp3 ≠ "gp2의 더 비싼 버전"**: 오히려 20% 저렴하고 IOPS/처리량 독립 — 용량을 늘려 IOPS를 얻는 건 gp2 방식.
- **인스턴스 스토어**: 재부팅은 유지, 중지·종료·장애는 소실. 인스턴스 유형 변경도 소실.
- **EFS 성능 모드 Max I/O**: 과거 "대규모 병렬 워크로드용" 선택지였으나 현재는 이전 세대·지연 높음; Elastic 처리량과 병용 불가.
- **S3 성능 한도는 프리픽스 단위**이지 버킷 단위가 아니다. 객체 키 무작위화는 더 이상 모범 사례가 아니다.
- **Transfer Acceleration은 1 GB 미만에서 이득 작음** `[블로그]`; 가속 안 되는 구간은 과금 없음.
- **S3 Express One Zone / EFS One Zone / EBS는 단일 AZ** — 성능은 좋아도 AZ 장애 내성 없음(Task 2.2).
- **Storage Gateway 유형 혼동**: File(파일↔객체) / Volume(블록·iSCSI) / Tape(VTL). FSx File Gateway는 신규 불가.

## 6. 자가 점검 문항 후보 (재료)
1. **공유 파일 + 다중 AZ**: Linux EC2 수백 대(여러 AZ)가 같은 파일 세트를 읽고 쓰며 용량이 예측 불가. → **EFS(Regional)**, 스파이크성이면 **Elastic 처리량**. 오답: EBS Multi-Attach(같은 AZ·클러스터 FS), S3(파일 시스템 아님). 근거 F-10·F-14·F-15·F-24.
2. **Windows 공유**: AD 인증을 쓰는 SMB 파일 공유를 AWS로. → **FSx for Windows File Server**. 오답: EFS(Windows 미지원). 근거 F-15·F-16.
3. **HPC/ML**: S3 데이터셋을 서브밀리초 지연·고처리량 파일 시스템으로 처리, 결과는 S3로. → **FSx for Lustre**(DRA 링크; 임시면 scratch). 근거 F-17.
4. **EBS 선택 계산**: 미션 크리티컬 DB가 200,000 IOPS 지속·서브밀리초. → **io2 Block Express**(Nitro, 최대 256,000). 오답: gp3(80,000)·io1(64,000). 근거 F-07.
5. **gp3 최적화**: gp2 1 TB 볼륨의 IOPS가 3,000에 막혀 성능은 올리고 비용은 줄이고 싶다. → **gp3로 전환**하고 필요한 IOPS·처리량만 독립 프로비저닝(GiB당 20% 저렴). 근거 F-09.
6. **전 세계 업로드**: 해외 지사들이 한 리전 S3 버킷에 수 GB 파일을 올리며 속도가 불안정. → **S3 Transfer Acceleration + 멀티파트**. 근거 F-03·F-04.
7. **하이브리드**: 온프레미스 앱이 NFS로 쓰는 파일을 S3에 객체로 두고 최근 데이터는 로컬 저지연. → **S3 File Gateway**. 근거 F-20.
8. **인스턴스 스토어**: 인스턴스를 중지했다가 다시 시작해도 임시 캐시 데이터가 남아 있어야 한다. → 인스턴스 스토어는 **소실**(재부팅만 유지) → **EBS**. 근거 F-12.
