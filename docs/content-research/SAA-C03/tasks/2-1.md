## 2. 핵심 개념

### 2-1. 아키텍처 스타일과 결합도 (Skill 1·3, Knowledge: 마이크로서비스·이벤트 기반·멀티 티어)
| 스타일 | 핵심 | 결합을 낮추는 서비스 |
|---|---|---|
| 멀티 티어 | 웹/앱/데이터 계층 분리, 계층별 독립 확장 | ELB(계층 사이), SQS(비동기 완충), 캐시(ElastiCache·CloudFront) |
| 마이크로서비스 | 작은 서비스, **스테이트리스** 설계(상태는 DynamoDB·ElastiCache·S3로 외부화) | API Gateway, ECS/EKS/Fargate, Lambda |
| 이벤트 기반 | 생산자는 소비자를 모름(이벤트/메시지로 연결) | SNS, SQS, EventBridge, Step Functions, Lambda 이벤트 소스 |
- **스테이트리스 vs 스테이트풀**: 세션/상태를 인스턴스 로컬에 두면 수평 확장·교체가 어렵다 → 세션 외부화 또는 ALB 스티키 세션(임시 방편) (F-24).
- **수평(스케일 아웃) vs 수직(스케일 업)**: 수평은 인스턴스 수 증가(로드 밸런서+Auto Scaling 필요, 스테이트리스 전제), 수직은 인스턴스 크기 증가(재시작·상한 존재). 세부 정책은 `3-2.md`.

### 2-2. 메시징·이벤트·오케스트레이션 선택 (Skill 3)
| 서비스 | 모델 | 쓰는 때 | 핵심 사실 |
|---|---|---|---|
| **SQS Standard** | 큐(Pull) | 부하 완충, 처리량 우선 | 사실상 무제한 처리량, **최소 1회**, 순서 최선 노력 (F-01) |
| **SQS FIFO** | 큐(Pull) | 순서·중복 제거 필수 | 기본 300 TPS/API(배치 시 3,000 msg/s), **고처리량 모드 최대 70,000 msg/s** (F-02) |
| **SNS** | Pub/Sub(Push) | 1:N 동시 전달 | SQS·Lambda·HTTP(S)·이메일·SMS·모바일 푸시·Firehose (F-08·09) |
| **SNS+SQS 팬아웃** | 토픽→여러 큐 | 독립 소비·재시도·DLQ | 소비자별 큐·DLQ로 격리 |
| **EventBridge 이벤트 버스** | 규칙 기반 라우팅 | 속성 기반 필터, SaaS/AWS 이벤트, 다대다 | 이벤트 항목 256 KB, 규칙당 대상 5개 (F-10·11) |
| **EventBridge Pipes** | 점대점 | 소스→(필터·보강)→대상 | SQS·Kinesis·DynamoDB Streams·MSK·MQ 등 소스 (F-11) |
| **EventBridge Scheduler** | 스케줄 | 크론/일회성 작업 | 270+ 서비스·6,000+ API 대상 `[블로그]` |
| **Step Functions** | 상태 머신 | 다단계 분기·재시도·승인 대기 | Standard: 정확히 1회·최대 1년 / Express: 최소 1회·최대 5분 (F-12) |
- **SQS 핵심 설정**: 가시성 제한 시간 기본 30초(0~12시간), 보존 60초~14일(기본 4일), 지연 0~900초, 롱 폴링 0~20초 (F-04). **DLQ**는 `maxReceiveCount`를 넘긴 메시지를 이동 (F-06). Lambda+SQS는 `ReportBatchItemFailures`로 **실패 항목만** 재노출 (F-07).
- **SQS vs SNS vs EventBridge 판단**: 큐=한 소비자 그룹이 가져감(완충), SNS=구독자 전원에게 전달, EventBridge=이벤트 내용 기반 선택 라우팅(+Pipes 점대점).
- **Amazon MQ**(in-scope): 기존 JMS/AMQP/MQTT 브로커 마이그레이션(앱 코드 변경 최소) — 이번 조사에서 공식 문장 미확보(`99-gaps.md`).

### 2-3. 컴퓨트 선택: Lambda · Fargate · ECS/EKS(EC2) · EC2 (Skill 4·5)
| 항목 | Lambda | Fargate(ECS/EKS) | ECS/EKS on EC2 |
|---|---|---|---|
| 실행 단위 | 이벤트 함수 | 서버리스 컨테이너 태스크/파드 | 컨테이너(노드 직접 관리) |
| 최대 시간 | **15분**(Managed Instances 비동기 90분) | 제한 없음 | 제한 없음 |
| 크기 | 메모리 128~10,240 MB(1,769 MB=1 vCPU), `/tmp` 512~10,240 MB | 태스크 0.25~16 vCPU(32 vCPU 옵션), 메모리 최대 120 GB(32 vCPU는 244 GB), 임시 스토리지 기본 20·최대 200 GiB | 인스턴스 유형에 따름(GPU 등) |
| 과금 | 요청+실행시간(GB-초) | vCPU·메모리·스토리지 사용 시간(초 단위) | EC2 비용 |
| 콜드 스타트 | 있음(프로비저닝 동시성·SnapStart로 완화) | 이미지 풀 시간 | — |
- **Lambda 주요 한도**: 동시 실행 기본 1,000(증액 가능), 함수당 확장 속도 10초마다 1,000 실행 환경, 페이로드 동기 6 MB/비동기 1 MB, 컨테이너 이미지 10 GB, zip 50 MB(API 업로드)/250 MB(압축 해제), 레이어 5개 (F-13).
- **Lambda 비동기 호출**: 기본 **2회 재시도**, 이벤트 큐 보관 최대 6시간, DLQ·Destinations(성공/실패, S3는 실패 대상만) (F-14).
- **예약(Reserved) vs 프로비저닝(Provisioned) 동시성**: 예약=최대 한도/보장 슬롯(사전 초기화 없음), 프로비저닝=사전 초기화로 콜드 스타트 제거(추가 요금). SnapStart(Java 등)는 프로비저닝 동시성과 병용 불가 (F-15).
- **ECS vs EKS**: ECS=AWS 네이티브(제어 평면 추가 요금 없음), EKS=Kubernetes 표준(클러스터당 시간당 **$0.10** 표준 지원 / **$0.60** 연장 지원, 버전당 14개월+12개월) (F-22).
- **컨테이너로 마이그레이션**: App2Container(기존 Java/.NET 앱을 코드 변경 없이 컨테이너화·ECS/EKS 산출물 생성) — 현재 제공 상태는 `99-gaps.md` (F-28).

## 3. 시험에서 묻는 방식 (패턴)
1. **디커플링**: "주문 이벤트를 재고·결제·배송이 각자 처리, 한 시스템 장애가 다른 곳에 번지지 않게" → SNS 토픽 + SQS 큐별 구독 + DLQ.
2. **순서·정확히 한 번**: "금융 거래 순서 보장, 중복 금지" → SQS FIFO(+MessageGroupId, 처리량 필요 시 배치/고처리량).
3. **서버리스 vs 컨테이너**: "15분 초과 배치, 서버 관리 불가" → Fargate(또는 Batch). "이벤트 단발 처리, 운영 최소" → Lambda. "Kubernetes 표준 유지" → EKS.
4. **API 설계**: "캐싱·사용량 계획·WAF" → REST API / "저비용 단순 Lambda 프록시" → HTTP API / "채팅" → WebSocket API.
5. **워크플로**: "승인 대기 포함 수주 단위 프로세스, 감사 이력" → Step Functions Standard. "초당 수만 건 단기 IoT 변환" → Express.
6. **확장/스테이트**: "서버 교체해도 세션 유지" → 세션 외부화(ElastiCache/DynamoDB) — ALB 스티키는 임시 방편.
7. **읽기 부하**: "읽기 쿼리로 기본 DB가 느림, 쓰기는 정상" → 읽기 전용 복제본(+필요 시 캐시).
8. **레거시 이전**: "코드 변경 없이 기존 Java 앱 컨테이너화" → App2Container(→ECS/EKS) 또는 리호스팅/Amazon MQ 등 상황별.

## 4. 흔한 함정·혼동 짝
- **SQS=한 번에 한 소비자, SNS=구독자 전원**. 여러 시스템 동시 전달이 필요하면 SNS(또는 SNS+SQS).
- **SNS 직접 구독 vs SNS→SQS**: 재시도·버퍼·DLQ가 필요하면 SQS를 끼운다.
- **FIFO 남용**: 순서가 필요 없으면 Standard(처리량·비용).
- **Visibility timeout 너무 짧음 → 중복 처리**(삭제가 아니라 재노출). DLQ 없이 운영 금지.
- **Reserved vs Provisioned concurrency**: 콜드 스타트 제거는 Provisioned.
- **Step Functions Standard vs Express**: 보장(정확히 1회/최소 1회)·시간(1년/5분)·과금(전환/실행·시간) 3축.
- **API Gateway 29초**: 장시간 작업은 비동기(SQS/Step Functions) 패턴으로. 타임아웃 증액은 Regional·프라이빗 REST API 한정.
- **REST vs HTTP API**: 캐싱·API 키·WAF·요청 검증은 REST 전용.
- **ALB vs NLB**: 경로/호스트 라우팅·Lambda 대상은 ALB, 정적 IP·L4는 NLB. NLB 교차 영역 기본 꺼짐.
- **Fargate는 ECS/EKS의 실행 유형**(독립 오케스트레이터 아님).
- **읽기 전용 복제본≠고가용성**: 복제는 비동기, 장애 조치는 Multi-AZ(`2-2.md`).
- **EKS 요금**: 제어 평면 요금 존재($0.10/h), 지원 종료 버전은 $0.60/h로 상승.

## 6. 자가 점검 문항 후보 (재료)
1. **팬아웃**: 주문 1건을 재고·결제·분석 3개 시스템이 각각 독립 속도로 처리, 하나의 실패가 다른 시스템에 영향 없음. → **SNS 토픽 + 시스템별 SQS 큐(+DLQ)**. 오답: SQS 단일 큐 공유(한 소비자만 가져감), SNS→Lambda 직접(버퍼·DLQ 약함). 근거 F-01·F-06·F-08.
2. **FIFO**: 은행 이체 이벤트를 계정별 순서대로·중복 없이 처리, 초당 수천 건. → **SQS FIFO + MessageGroupId + 배치(필요 시 고처리량 모드)**. 오답: Standard(순서 최선 노력). 근거 F-02.
3. **컴퓨트**: 하루 1회 40분 걸리는 컨테이너 배치, 서버 관리 최소화. → **Fargate**(또는 AWS Batch). 오답: Lambda(900초 한도). 근거 F-13.
4. **API**: 모바일 백엔드에서 클라이언트별 사용량 한도·응답 캐싱·WAF가 필요. → **API Gateway REST API**(+사용 계획, 캐시, WAF). 오답: HTTP API(캐싱·API 키 없음). 근거 F-19.
5. **워크플로**: 환불 승인에 사람 승인 대기(최대 몇 주)와 단계별 감사 이력. → **Step Functions Standard**. 오답: Express(5분). 근거 F-12.
6. **콜드 스타트**: 지연 민감 API의 Lambda 첫 호출 지연 제거. → **프로비저닝 동시성**. 오답: 예약 동시성. 근거 F-15.
7. **부분 배치 실패**: SQS 트리거 Lambda가 10건 배치 중 1건만 실패해도 전체 재처리되어 중복. → **ReportBatchItemFailures 활성화** + DLQ. 근거 F-07.
8. **스테이트**: 장바구니 상태를 서버에 두는 웹 계층을 오토 스케일링으로 바꾸려 한다. → **세션 외부화(ElastiCache/DynamoDB)**, 임시로는 ALB 스티키 세션. 근거 F-24.
