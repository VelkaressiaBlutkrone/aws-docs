### 2-2. 엔진 선택과 마이그레이션 (Knowledge 6, Skill 3)
- **MySQL vs PostgreSQL(Skill 3 예시)**: 공식 한 줄 비교 문장은 확보하지 못함 → `99-gaps.md`. 확인된 차이는 **Aurora 테이블 크기 한도**(MySQL 호환 64 TiB / PostgreSQL 호환 32 TiB)와 **Backtrack은 Aurora MySQL 전용**(F-03·F-05의 `[블로그]`) 정도.
- **동종(homogeneous) vs 이기종(heterogeneous) 마이그레이션 (Knowledge 6)**: DMS는 같은 엔진 간(예: Oracle→Oracle)과 다른 엔진 간(예: Oracle→MySQL) 모두 지원. **이기종은 AWS SCT(또는 DMS Schema Conversion)로 스키마·코드 객체를 변환**하고 DMS로 데이터 이전·**CDC(지속 복제)**, 동종은 엔진 **네이티브 도구**로 스키마를 옮길 수 있음. 원본·대상 중 하나는 AWS 서비스여야 함 (F-20).
- **상용 엔진 필요(Oracle·SQL Server·Db2) → RDS**, 클라우드 네이티브 성능·확장(공유 스토리지·15 리더) → **Aurora** (F-03·F-05·F-09). RDS Custom for Oracle은 **2027-03-31 지원 종료** (F-19).

### 2-3. RDS vs Aurora (Skill 2·4)
| 항목 | RDS | Aurora |
|---|---|---|
| 호환 엔진 | MySQL·MariaDB·PostgreSQL·Oracle·SQL Server·Db2 | MySQL·PostgreSQL |
| 스토리지 | EBS(gp2/gp3/io1/io2), **기본 볼륨 최대 64 TiB**, Oracle·SQL Server는 추가 볼륨 3개(총 256 TiB), 스토리지 오토스케일링 (F-09) | **공유 클러스터 볼륨**: 3 AZ, 자동 확장(10 GiB 단위), **최대 128 TiB 또는 256 TiB(엔진 버전별)**, 삭제 시 축소 (F-03) |
| 읽기 확장 | 읽기 전용 복제본 **최대 15**(MySQL·MariaDB·PostgreSQL) / 5(Oracle·SQL Server) / 3(Db2), 비동기 (F-08) | Aurora 복제본 **최대 15**, 같은 스토리지 공유로 지연 보통 100 ms 미만, 리더 엔드포인트 (F-05) |
| 고가용성 | Multi-AZ(60~120초 / 클러스터 35초 미만) (`2-2.md` F-03·F-04) | 3 AZ 6사본, 장애 조치 보통 30초 미만 (`2-2.md` F-06) |
| 글로벌 | 교차 리전 읽기 복제본 | **Aurora Global Database**: 보조 리전 **최대 10**, 보조 클러스터 읽기 인스턴스 16 (F-06) |
| 서버리스 | 없음 | **Aurora serverless**(구 Serverless v2): ACU 0.5~256, 0 ACU 자동 일시정지 (F-07) |
| I/O 과금 | EBS 성능(IOPS·처리량) 프로비저닝 | **Standard**(I/O 건당) vs **I/O-Optimized**(I/O 과금 없음, I/O 비중 ≥25%일 때) (F-04) |
- **쓰기는 단일 라이터가 한계**(RDS·Aurora 모두) — 읽기는 복제본/리더로 확장, 쓰기 확장은 인스턴스 스케일 업·샤딩·DynamoDB 등 (F-05의 `[블로그]`).

### 2-4. 용량 계획 (Knowledge 4)
| 대상 | 용량 단위·결정 요소 | 핵심 |
|---|---|---|
| **RDS 스토리지** | 스토리지 유형·크기·IOPS | gp2=GiB당 3 IOPS(버스트 3,000), gp3=기본 3,000 IOPS·125 MiB/s(<400 GiB)+독립 프로비저닝, **Provisioned IOPS(io1/io2) 1,000–256,000** (F-09) |
| **RDS 오토스케일링** | 최대 스토리지 임계값 | 여유 ≤10% + 5분 이상 + 최적화 완료·24시간 내 변경 4회 미만일 때 증설(증분=max(10 GiB, 10%, 7시간 예측 증가)), 추가 볼륨에는 미지원 (F-09) |
| **Aurora** | 인스턴스 클래스(메모리 최적화 db.r 등) + 스토리지 자동 | 스토리지 크기와 무관하게 IOPS 한도 없음 — 더 높은 IOPS가 필요하면 **인스턴스를 스케일 업** (F-03) |
| **Aurora serverless** | ACU(≈2 GiB 메모리+CPU+네트워킹) 범위 최소~최대 | Performance Insights는 최소 2 ACU 필요 (F-07) |
| **DynamoDB** | RCU/WCU(프로비저닝) 또는 온디맨드 | 아래 2-5 (F-16) |
| **모니터링** | RDS Performance Insights | DB 부하=평균 활성 세션(AAS), waits·SQL·hosts·users·databases로 분해, Max vCPU 선으로 CPU 대기 판단 (F-21) |
- **인스턴스 클래스**: 컴퓨트·메모리 용량을 정하는 선택지(예: db.m·db.r 계열)이며 복제본은 기본적으로 원본 클래스를 상속(다르게 지정 가능) (F-08).

### 2-5. DynamoDB 설계·확장 (Knowledge 3·4, Skill 2·4)
- **용량 모드**: **프로비저닝**(RCU/WCU 지정, 예측 가능 트래픽에 저렴, Auto Scaling 병용 가능) vs **온디맨드**(요청당 과금, 예측 불가). RCU=**강한 일관성 읽기 1회/초(≤4 KB)** 또는 최종 일관성 2회/초, WCU=쓰기 1회/초(≤1 KB). 예: 항목 20 KB의 일관 읽기 1회=5 읽기 단위 (F-16·F-22).
- **온디맨드 확장 특성**: 신규 테이블은 초당 쓰기 4,000·읽기 12,000까지 즉시 지속, **이전 피크의 2배까지 즉시 수용**, 30분 안에 2배를 넘으면 스로틀 가능 → 사전 워밍 또는 30분 이상 간격으로 증가 (F-16).
- **파티션 한계와 핫 파티션**: 파티션당 읽기 3,000·쓰기 1,000 단위/초가 설계 한도 → **카디널리티 높은 파티션 키**로 균등 분산, 쓰기 편중은 **쓰기 샤딩**(키 접미사), 적응형 용량·버스트(미사용 용량 최대 5분, 최선 노력)는 임시 완화일 뿐 (F-16·F-22).
- **인덱스**: GSI(다른 파티션 키·정렬 키, 자체 처리량, 언제든 추가·삭제, **강한 일관성 읽기 불가**) vs LSI(같은 파티션 키+다른 정렬 키, 테이블과 처리량 공유, **테이블 생성 시에만** 생성, 키 값당 10 GB 한도); 테이블당 GSI 20·LSI 5(기본) (F-17).
- **읽기 일관성**: 기본=최종 일관성, 강한 일관성은 **처리량 2배** 소비 (F-17). 항목 최대 **400 KB** (F-22).
- **Streams(24시간 로그)·TTL(수일 내 삭제, 쓰기 처리량 미소비)** (F-18). **글로벌 테이블** active-active·MREC/MRSC는 `2-2.md` F-08.

### 2-7. 연결과 프록시 (Knowledge 5)
- **RDS Proxy**: 연결 **풀링·다중화(multiplexing)** 로 DB 최대 연결 한도를 넘어 확장, 버스트 연결 관리, **정상 장애 조치**(연결 유지·복구 단축 — `2-2.md` F-05), 서버리스(Lambda)는 **함수의 IAM 실행 역할로 프록시·DB 인증**해 코드에서 자격증명 처리 불필요, 용량 자동 확장, 처리 불가 연결은 거부해 DB 성능 보호 (F-10).
- **핀닝(pinning)**: 세션 상태가 바뀌어 연결을 다른 클라이언트가 재사용할 수 없으면 1:1로 고정돼 다중화 효율이 떨어짐. 사용자별 풀이 쪼개지는 다중 테넌트(사용자·스키마별 계정)에서 특히 비효율 (F-10).

| 캐시+내구성 있는 주 DB를 하나로 | **MemoryDB** | F-15 |
- **전략** (F-13): **지연 로딩(lazy loading, cache-aside)**=미스 시 DB 조회 후 적재(오래된 데이터 가능, 빈 노드에도 문제 없음) / **쓰기 시 갱신(write-through)**=항상 최신(빈 노드에서 누락 가능, 불필요 데이터 적재) / **TTL** 병용으로 둘의 장점 결합.
- **DAX 세부**: 강한 일관성 읽기는 캐시하지 않고 테이블로 직행, 기본 TTL 5분·LRU 축출, 쓰기는 write-through로 항목 캐시 갱신, 전송·저장 암호화 지원 (F-14).
- 엣지/CDN 캐시(CloudFront)·API Gateway 캐시는 `3-4.md`.

### 2-9. 글로벌 인프라 관점 (Knowledge 1)
- AZ 장애 대비=**Multi-AZ**, 리전 장애·글로벌 지연 대비=**Aurora Global Database / DynamoDB 글로벌 테이블 / RDS 교차 리전 복제본** (`2-2.md` F-01·F-03·F-04·F-06~F-08). Aurora Global Database는 메모리 최적화 인스턴스 클래스를 요구 (F-06).

## 3. 시험에서 묻는 방식 (패턴)
1. **읽기 폭증**: "보고서 쿼리가 운영 DB를 느리게 함 / 읽기 트래픽 급증" → **읽기 전용 복제본(Aurora는 리더 엔드포인트+Auto Scaling)**. 함정: Multi-AZ 스탠바이로 읽기(불가), 비동기라 즉시 일관성이 필요하면 부적합.
2. **반복 조회 가속**: "같은 쿼리 결과를 계속 DB에서 읽음" → **ElastiCache(지연 로딩+TTL)**; DynamoDB면 **DAX**(마이크로초, 코드 변경 최소).
3. **Lambda→RDS 연결 고갈**: "동시 실행이 늘면 `Too many connections`" → **RDS Proxy**(IAM 인증).
4. **이기종 마이그레이션**: "Oracle→Aurora PostgreSQL, 최소 다운타임" → **SCT(스키마 변환) + DMS(전체 적재+CDC)**. 동종이면 DMS/네이티브 도구.
5. **예측 불가·간헐적 부하**: 관계형=**Aurora serverless**(ACU, 자동 일시정지), 키-값=**DynamoDB 온디맨드**.
6. **글로벌**: "전 세계 읽기 저지연+DR" → **Aurora Global Database**; "다중 리전 쓰기·active-active" → **DynamoDB 글로벌 테이블**.
7. **고IOPS OLTP**: "지속 고 IOPS·예측 가능한 지연" → **Provisioned IOPS(io2)**; Aurora라면 **I/O-Optimized**(I/O 비용 비중 큼).
8. **세션/실시간 순위**: 세션 스토어·리더보드 → **ElastiCache for Valkey/Redis OSS**(Memcached는 복제·영속성 없음). "캐시가 아니라 주 DB로 영속 보장" → **MemoryDB**.
9. **DynamoDB 설계**: "특정 파티션 키에 트래픽 편중으로 스로틀" → **카디널리티 높은 키·쓰기 샤딩**(용량만 늘려도 파티션 한도 3,000/1,000 단위).

## 4. 흔한 함정·혼동 짝
- **Multi-AZ(동기·읽기 불가) vs 읽기 복제본(비동기·읽기 확장)** — 서로 대체 불가(`2-2.md` 함정 참조).
- **Aurora 복제본은 공유 스토리지**라 지연이 작지만, **RDS 읽기 복제본은 로그 재생**이라 쓰기 부하가 크면 수 분까지도 지연.
- **Aurora 읽기 복제본 15개 vs Global Database 보조 클러스터 16개** — 15=한 클러스터의 Aurora 복제본, 16=보조 클러스터당 읽기 인스턴스 총합(리전 최대 10개).
- **DAX는 DynamoDB 전용**이며 **강한 일관성 읽기는 캐시 우회**; ElastiCache는 범용(RDS 등).
- **Memcached ≠ Redis/Valkey**: 복제·장애 조치·영속성·고급 자료구조는 Valkey/Redis OSS만. ElastiCache는 이제 **Valkey 포함 3엔진**.
- **ElastiCache(휘발 캐시) vs MemoryDB(영속 인메모리 DB)** — 데이터 손실 허용 여부로 구분.
- **GSI는 강한 일관성 읽기 불가, LSI는 테이블 생성 시에만** (사후 인덱스 필요하면 GSI).
- **온디맨드는 무한 즉시 확장이 아님**: 이전 피크의 2배까지 즉시, 그 이상은 30분 규칙.
- **TTL 삭제는 "수일 내"**(과거 자료의 48시간 표기는 현행 아님), 정확한 만료 보장 수단이 아님.
- **RDS Proxy 핀닝**: 세션 상태를 쓰면 다중화 이득이 줄어듦.
- **Aurora 스토리지 최대 128 TiB vs 256 TiB**: 엔진·버전에 따라 다름(PostgreSQL 17.5+/16.9+/15.13+, MySQL 3.10+만 256 TiB).
- **Timestream for LiveAnalytics는 신규 불가**·**RDS Custom for Oracle은 지원 종료 예정(2027-03-31)** — 옛 자료의 "시계열=Timestream" 단답 주의.

## 6. 자가 점검 문항 후보 (재료)
1. **Aurora 읽기 자동 확장**: Aurora MySQL 리더의 평균 CPU가 높을 때 자동으로 리더를 늘리고 싶다. → **Aurora Auto Scaling**(대상 추적, 리더 평균 CPU 지표 또는 평균 연결 수)과 **리더 엔드포인트**. 오답: Multi-AZ 스탠바이 추가(읽기 불가), RDS 읽기 복제본 수동 생성. 근거 F-05.
2. **연결 고갈**: Lambda 동시 실행이 늘어 RDS MySQL `max_connections` 초과. → **RDS Proxy**(풀링·다중화, Lambda IAM 실행 역할로 인증). 근거 F-10.
3. **DynamoDB 읽기 가속**: 읽기 집중 DynamoDB 테이블의 응답을 마이크로초로, 코드 변경 최소. → **DAX**(최종 일관성 읽기). 강한 일관성이 필요한 읽기는 DAX를 우회. 근거 F-14.
4. **RCU 계산**: 항목 6 KB, 강한 일관성 읽기 초당 100회, 최종 일관성이라면? → 6 KB는 4 KB 단위로 올림해 2 RCU/회 → 강한 일관성 **200 RCU**, 최종 일관성 **100 RCU**. 근거 F-16·F-22(20 KB=5 단위 예시와 동일 원리).
5. **이기종 마이그레이션**: 온프레미스 Oracle을 Aurora PostgreSQL로, 가동 중단 최소. → **AWS SCT(DMS Schema Conversion)로 스키마 변환 + DMS로 전체 적재 및 CDC**. 근거 F-20.
6. **서버리스 관계형**: 개발·테스트용 MySQL 호환 DB, 유휴 비용 최소·예측 불가한 부하. → **Aurora serverless**(ACU, 최소 0 ACU 자동 일시정지; 구 Serverless v2). 근거 F-07.
7. **온디맨드 한계**: 평소 읽기 5만/초이던 DynamoDB 온디맨드 테이블에 갑자기 30분 안에 25만/초 → 이전 피크의 2배(10만)를 넘으면 스로틀 가능, **사전 워밍 또는 30분 이상 간격 증가**. 근거 F-16.
8. **세션 스토어**: 웹 세션 공유, 장애 시 자동 전환 필요. → **ElastiCache for Valkey/Redis OSS Multi-AZ 복제 그룹**; 오답: Memcached(복제·장애 조치 없음). 근거 F-11·F-12.
9. **캐시 전략**: DB 데이터가 바뀌어도 오래된 값이 남는 문제와 빈 캐시 노드 대비를 모두 줄이려면? → **지연 로딩 + 쓰기 시 갱신 + TTL 병용**. 근거 F-13.
