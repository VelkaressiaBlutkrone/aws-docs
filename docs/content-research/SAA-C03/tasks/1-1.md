## 2. 핵심 개념

### 2-1. 자격증명 주체와 모범 사례 (Skill 1·2)
| 주체 | 자격증명 | 한 줄 | 비고 |
|---|---|---|---|
| 루트 사용자 | 이메일+암호(+MFA) | 계정 소유자. 일상 작업 금지 | 액세스 키 만들지 않기, MFA 필수 |
| IAM 사용자 | 장기 자격증명(암호·액세스 키) | 꼭 필요한 예외에만 | 사용자당 액세스 키 2개 |
| IAM 그룹 | 없음(권한 묶음) | 사용자 집합에 정책 부착 | 그룹 중첩 불가, 사용자는 최대 10개 그룹 소속 |
| IAM 역할 | **임시** 자격증명(STS) | 수임(assume)한 주체가 쓰는 신분 | EC2 인스턴스 프로필·Lambda 실행 역할 |
| 페더레이션 사용자 | 외부 IdP/디렉터리 → 임시 자격증명 | 직원은 IAM Identity Center 권장 | SAML 2.0·OIDC |

- 공식 모범 사례 골자(요약): ① 사람은 IdP 페더레이션으로 **임시 자격증명** ② 워크로드는 **IAM 역할** ③ **MFA 필수**(가능하면 passkey·보안 키 같은 피싱 방지 MFA) ④ 장기 액세스 키는 꼭 필요할 때만, 사용 이력 보고 정리 ⑤ 루트 자격증명 보호 ⑥ **최소 권한** ⑦ 미사용 자격증명 정기 제거 ⑧ 조건(Condition) 사용 ⑨ Access Analyzer로 공개·교차 계정 접근 검증 ⑩ 다계정 가드레일(SCP/RCP) ⑪ 권한 경계로 위임 → (F-30~33)
- 온프레미스·타 클라우드 워크로드도 임시 자격증명을 쓸 수 있다: **IAM Roles Anywhere**(X.509 인증서), `AssumeRoleWithSAML`, `AssumeRoleWithWebIdentity` (F-31).

### 2-2. 정책 유형과 평가 (Skill 2·5)
| 정책 유형 | 부착 대상 | 권한 부여? | 역할 |
|---|---|---|---|
| 아이덴티티 기반 | 사용자·그룹·역할 | O | 일반 권한 |
| 리소스 기반 | 리소스(S3·SQS·SNS·KMS·Lambda 등) | O | 교차 계정, 리소스 쪽 접근 통제 |
| 역할 신뢰 정책 | 역할(= IAM이 지원하는 유일한 리소스 정책) | 수임 허용 | "누가 수임 가능한가" |
| 권한 경계(Permissions boundary) | 사용자·역할 | X(상한) | 위임 시 최대 권한 제한 |
| SCP | Organizations 루트·OU·계정 | X(상한) | 멤버 계정 IAM 주체 가드레일 |
| RCP(리소스 제어 정책) | Organizations 루트·OU·계정 | X(상한) | 조직 내 **리소스** 접근 가드레일 |
| 세션 정책 | 임시 세션 | X(상한) | AssumeRole 시 추가 제한 |

- **평가 요약**: 명시적 Deny가 모든 Allow를 이긴다. 같은 계정에서 아이덴티티 정책+리소스 정책은 **합집합**, 아이덴티티 정책+권한 경계는 **교집합**, 조직 소속이면 SCP·RCP까지 **모두 허용해야** 통과 (F-34).
- **교차 계정**: 리소스 정책에 다른 계정을 Principal로 두는 것은 "절반"뿐 — 상대 계정의 **아이덴티티 정책도 허용**해야 한다. 같은 계정이면 리소스 정책 허용만으로 충분 (F-35). 단 **KMS 키·IAM 역할**은 같은 계정에서도 리소스 정책(키 정책/신뢰 정책)이 주체를 명시적으로 허용해야 한다 (F-36 `[블로그]`).

### 2-3. 역할 기반 접근 제어와 교차 계정 (Skill 3)
| 패턴 | 동작 | 주체의 기존 권한 | 언제 |
|---|---|---|---|
| **역할 수임(AssumeRole / 콘솔 역할 전환)** | 대상 계정 역할의 신뢰 정책이 소스 주체를 허용 + 소스 쪽 `sts:AssumeRole` 허용 | 세션 동안 **원래 권한을 내려놓고** 역할 권한만 가짐 | 감사·세션 단위 격리, 제3자 접근(ExternalId) |
| **리소스 기반 정책 교차 계정** | 리소스 정책이 상대 계정 주체 허용(+상대 계정 ID 정책) | **원래 권한 유지** — 양쪽 리소스 동시 사용(복사 작업) | 두 계정 리소스를 오가며 작업할 때 (F-37) |

- STS 임시 자격증명 API 분류: `AssumeRole`(계정 간·계정 내 역할), `AssumeRoleWithSAML`(SAML IdP), `AssumeRoleWithWebIdentity`(OIDC/웹 ID), `GetSessionToken`(IAM 사용자 MFA 세션), `GetFederationToken`(프록시 앱, IAM 사용자 장기 자격증명으로 호출). 모바일/웹 앱 사용자는 Cognito 또는 `AssumeRoleWithWebIdentity` 권장 (F-10).
- **제3자(SaaS) 접근**: 역할 + 신뢰 정책의 `sts:ExternalId` 조건으로 **혼동된 대리인(confused deputy)** 방지. External ID는 비밀이 아니다 (F-38 `[블로그]`).

### 2-4. 다중 계정 전략 (Skill 4)
- **AWS Organizations**: 루트 → OU(중첩 5단계) → 계정. 정책 유형: SCP·RCP·선언적 정책·백업·태그·챗 애플리케이션·AI 옵트아웃·Security Hub 정책(F-16~20).
- **SCP**: 멤버 계정의 IAM 주체(루트 사용자 포함)의 **최대 권한**을 제한. 권한을 주지 않음. 관리 계정·서비스 연결 역할·조직 밖 계정에는 영향 없음 (F-11~15).
- **Control Tower**: 모범 사례 landing zone을 자동 구성(Organizations·IAM Identity Center 등 오케스트레이션). **Security OU**에 **Log Archive**·**Audit** 공유 계정이 생김(F-23). **통제(controls)**는 *동작(behavior)* 3종 × *지침(guidance)* 3종으로 직교 분류(F-21·22):

| 동작 | 구현 | 상태 값 |
|---|---|---|
| 예방(Preventive) | SCP·RCP·선언적 정책 | 적용됨/미활성 |
| 탐지(Detective) | AWS Config 규칙 | 정상/위반/미활성 |
| 사전예방(Proactive) | CloudFormation 훅 | PASS/FAIL/SKIP |

  지침: 필수(Mandatory, 항상 적용·변경 불가) / 강력 권장 / 선택(Elective).
- **루트 사용자 관리(다계정)**: 관리 계정 루트는 MFA 등록이 **필수**(35일 유예). 멤버 계정은 **중앙 루트 접근 관리**로 루트 자격증명 자체를 제거할 수 있고, 새 멤버 계정은 기본적으로 루트 자격증명이 없다 (F-31).

### 2-5. 디렉터리 서비스 연동 시점 (Skill 6)
| 선택지 | 쓰는 때 | 핵심 특징 |
|---|---|---|
| **IAM Identity Center(조직 인스턴스)** | 직원이 여러 AWS 계정·앱에 SSO | 권한 세트로 계정별 역할 배포. ID 소스는 **조직당 1개**: Identity Center 디렉터리 / 외부 IdP(SAML 2.0, SCIM) / AD(AWS Managed Microsoft AD·AD Connector·신뢰) |
| **IAM SAML/OIDC 공급자** | 단일 계정, 소규모 연동, 앱 워크로드 | `AssumeRoleWithSAML`·`AssumeRoleWithWebIdentity` |
| **AWS Managed Microsoft AD** | 실제 Windows AD가 AWS에 필요(Group Policy·신뢰·스키마 확장), 사용자 많음 | 표준 3만/엔터프라이즈 50만 개체 |
| **AD Connector** | 온프레미스 AD를 **그대로** 쓰고 AWS가 프록시만 | 디렉터리 데이터를 클라우드에 캐시·복제하지 않음 |
| **Simple AD** | (레거시) 소규모·Samba 호환 | **신규 고객 불가**, Identity Center ID 소스로 **미지원** |
| **Amazon Cognito** | 앱 **최종 사용자(고객)** | (Task 1.2에서 상세) |

## 3. 시험에서 묻는 방식 (패턴)
1. **조직 가드레일**: "수십 개 계정에서 루트 포함 모든 주체가 승인 리전 밖/특정 서비스를 못 쓰게" → OU/루트에 **SCP(Deny + 조건)**. 함정: 관리 계정은 SCP 비적용, 글로벌 서비스 예외 필요.
2. **계정 간 접근**: "개발 계정 앱이 운영 계정 DynamoDB/S3를 읽어야 함, 장기 키 금지" → 대상 계정 **역할(신뢰 정책) + 소스 `sts:AssumeRole`**, 또는 리소스 정책+ID 정책. "두 계정을 동시에 오가며 복사"면 리소스 정책 방식.
3. **직원 SSO**: "온프레미스 AD 직원 수백 명이 여러 계정 콘솔/CLI 접근" → **IAM Identity Center + AD(AD Connector/Managed AD) 또는 외부 IdP**. IAM 사용자 일괄 생성은 오답.
4. **위임**: "개발자가 역할을 만들되 관리자 권한은 못 갖게" → **권한 경계**.
5. **워크로드 자격증명**: "EC2/Lambda/온프레미스 서버가 AWS API 호출" → 인스턴스 프로필/실행 역할, 온프레미스는 **IAM Roles Anywhere**. 코드·환경 변수의 액세스 키는 오답.
6. **루트 보호**: "계정 생성 직후/조직 편입 후 첫 조치" → 루트 MFA·액세스 키 삭제·이메일 보호, 다계정이면 중앙 루트 접근 관리.

## 4. 흔한 함정·혼동 짝
- **SCP vs 권한 경계 vs 세션 정책 vs RCP**: 넷 다 권한을 *부여하지 않는* 상한. 대상이 다름 — SCP(조직 내 *주체*), RCP(조직 내 *리소스*), 권한 경계(개별 사용자·역할), 세션 정책(세션).
- **SCP 적용 범위**: 멤버 계정 루트 O / 관리 계정(루트 포함) X / 서비스 연결 역할 X / 조직 밖 계정 사용자 X.
- **Control Tower 분류 혼동**: preventive·detective·proactive(동작) ≠ mandatory·strongly recommended·elective(지침).
- **신뢰 정책 vs 권한 정책**: 둘 다 있어야 역할이 동작. 신뢰 정책 = 리소스 정책의 일종.
- **역할 수임 vs 리소스 정책**: 역할 수임은 원 권한을 내려놓음, 리소스 정책은 유지.
- **Identity Center vs Cognito vs IAM SAML**: 직원·다계정(Identity Center) / 앱 최종 사용자(Cognito) / 단일 계정·소규모(IAM IdP).
- **AD Connector vs Managed Microsoft AD vs Simple AD**: 프록시(데이터 복제 없음) / 실제 AD(신뢰·GPO) / Samba 기반 레거시(신규 불가). AD는 SAML IdP가 아니다 — Identity Center는 AD를 **Directory Service 경유**로 연결.
- **Identity Center 인스턴스**: 조직 인스턴스(계정 접근·권한 세트 가능) vs 계정 인스턴스(앱 전용, 계정 접근 불가).
- **역할 체이닝 세션 1시간 상한**: `DurationSeconds`를 1시간 넘게 지정하면 체이닝에서는 실패.
- **리전 제한 SCP**: `aws:RequestedRegion` Deny만 쓰면 IAM·Organizations·Route 53·CloudFront 같은 **글로벌 서비스 호출도 막힌다** → `NotAction`으로 예외 (F-40).

## 6. 자가 점검 문항 후보 (재료 — 최종 문항은 취합 세션 저작·사람 검수)
1. **조직 가드레일**: 40개 계정 조직에서 멤버 계정의 루트 사용자 포함 모든 주체가 `eu-west-1`·`us-east-1` 밖에서 리소스를 만들지 못하게 하되 IAM·Organizations 같은 글로벌 서비스는 계속 쓰게 한다. → **루트/OU에 SCP: `NotAction`(글로벌 서비스 목록) + `Deny` + `aws:RequestedRegion` `StringNotEquals`**. (오답 후보: 관리 계정에 SCP 부착 → 비적용; 권한 경계 → 개별 주체 단위; IAM 정책 → 계정 관리자가 해제 가능.) 근거: F-11·F-12·F-40.
2. **교차 계정**: 개발 계정의 배치 작업이 운영 계정 S3 버킷을 읽되 장기 액세스 키는 금지. → **운영 계정에 역할(신뢰 정책=개발 계정 주체) + 개발 계정 주체에 `sts:AssumeRole` 허용**(또는 버킷 정책+개발 계정 ID 정책). 두 계정을 동시에 오가며 복사해야 하면 **리소스 정책** 방식이 원 권한을 유지. 근거: F-35·F-37.
3. **직원 SSO**: 온프레미스 AD 사용자 3,000명이 20개 계정에 SSO, AD는 그대로 유지, 사용자 동기 복제 최소화. → **IAM Identity Center(조직 인스턴스) + AD Connector**(또는 외부 IdP SAML+SCIM, 데이터 복제를 감수하면 Managed AD 신뢰). 오답 후보: Simple AD(신규 불가·Identity Center 미지원), IAM 사용자 일괄 생성. 근거: F-24~29.
4. **권한 위임**: 개발 팀장이 팀원용 IAM 역할을 직접 만들게 하되 어떤 역할도 `iam:*`·결제 권한을 가질 수 없게. → **권한 경계(Permissions boundary)를 생성 조건으로 강제**. 근거: F-34(경계=교집합)·best-practices 마지막 절.
5. **제3자 접근**: 모니터링 SaaS 업체가 고객 계정에 접근할 때 혼동된 대리인 문제 방지. → 역할 신뢰 정책에 **`sts:ExternalId` 조건**(업체가 고객별 고유 값 생성). External ID는 비밀 아님. 근거: F-38.
6. (보너스) **루트 사용자**: 새 멤버 계정을 대량 생성한다. 루트 자격증명 관리 부담을 줄이려면? → **중앙 루트 접근 관리로 멤버 계정 루트 자격증명 제거**(필요 시 권한 있는 세션으로 복구 작업). 근거: F-31.
