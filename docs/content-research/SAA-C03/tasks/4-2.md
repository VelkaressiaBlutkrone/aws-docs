### 2-2. Spot과 Auto Scaling 혼합 (Knowledge 4·9, Skill 2)
- **Spot 적합/부적합**: 상태 비저장·내결함·유연(빅데이터·컨테이너·CI/CD·웹 서버·HPC·렌더링) 적합, 상태 저장·비유연·노드 밀결합 부적합. 중단 시 On-Demand로 장애 조치하는 설계는 오히려 다른 Spot 중단을 유발할 수 있어 비권장 (F-08).
- **가용성을 높이는 법**: 인스턴스 유형·AZ 다양화(풀 수=AZ×유형), 속성 기반 인스턴스 유형 선택, Spot 배치 점수, **price-capacity-optimized** 할당 전략 (F-08).
- **ASG 혼합 인스턴스 정책**: 기본은 On-Demand, On-Demand 비율(0~100%)·기본(base) 용량 지정으로 나머지를 Spot으로, 소수 반올림은 On-Demand 쪽 (F-09). 예: base 10 + 나머지 50/50 → 그룹 크기 20일 때 On-Demand 15(기본 10+5)·Spot 5, 크기 40일 때 On-Demand 25(10+15)·Spot 15 (F-09 공식 표).
- **중단 동작**: 중단 시 동작으로 **최대 절전**을 지정할 수 있다(Spot에는 `Stop` API로 최대 절전 불가) (F-08). 종료·중지 선택지는 기존 학습문서 서술이며 이번 조회에서 직접 문장은 확보하지 못함(`99-gaps.md`).

### 2-3. 스케일링 전략과 최대 절전·스케줄링 (Knowledge 9, Skill 2)
| 전략 | 비용 효과 | 근거 |
|---|---|---|
| **수평(Scale out/in)** | 수요 따라 인스턴스 수 조정 — 유휴 감소, 장애 격리. 정책: 대상 추적·단계·예약·예측(`3-2.md` F-08·F-10), 웜 풀(F-11) | `3-2.md`, `2-1.md` |
| **수직(Scale up/down)** | 인스턴스 크기 변경 — 재시작 수반, 크기 적정화(Compute Optimizer)와 결합 | F-13 |
| **예약·스케줄 중지** | 비업무 시간 인스턴스 중지(Instance Scheduler) → 개발/테스트 약 **75%** 절감(주 40시간 vs 168시간) | F-11 |
| **최대 절전(Hibernate)** | RAM을 EBS 루트 볼륨에 저장하고 중지 → 재시작 시 상태 복원. **hibernated(stopped) 동안 인스턴스 사용료 없음**, EBS(RAM 내용 포함)만 과금 | F-10 |
- **Stop vs Hibernate vs Terminate**: Stop=RAM 소실·EBS 유지·사용료 없음 / Hibernate=RAM 유지(EBS에 저장)·EBS 과금 / Terminate=루트 삭제(`DeleteOnTermination` 규칙은 `4-1.md` F-17). 최대 절전은 *시작 시* 활성화해야 하며 사전 워밍(pre-warm)에 적합 (F-10).
- **웜 풀**: 사전 초기화 인스턴스를 Stopped·Running·Hibernated 상태로 대기시켜 확장 지연을 줄이는 기능(`3-2.md` F-11). 풀 상태별 과금 방식은 이번 조회에서 직접 문장을 확보하지 못함(`99-gaps.md`) — Stopped/Hibernated는 F-01·F-10의 규칙(사용료 없음·EBS 과금)에 비춰 추정하지 말고 확인 필요.

### 2-4. 인스턴스 패밀리·크기 선택 (Knowledge 7, Skill 5·6)
- **범주**: 범용·컴퓨트·메모리·스토리지·가속 컴퓨팅, 이름=시리즈+세대+옵션(a=AMD·g=Graviton·i=Intel) (`3-2.md` F-01·F-02). 버스트(T)는 평균 사용률이 기준선 이하일 때 저렴하고 unlimited 모드에서 초과분은 vCPU-시간당 추가 요금 (`3-2.md` F-04).
- **프로세서로 줄이기**: AMD(a)는 Intel 대비 컴퓨트 비용 약 **10%** 저렴(예: c6a.xlarge $0.153 vs c6i.xlarge $0.17), Graviton(g)은 Intel 대비 약 **20%** 저렴하면서 성능 20%+ — AWS 서술은 "최대 **40%** 가격 대비 성능"; **Windows Server는 Graviton(ARM) 불가** (F-12). Fargate도 Graviton이면 약 20% 낮은 비용·최대 40% 가격 대비 성능 (F-14).
- **Graviton 이전 시 주의**: ARM64 호환성(바이너리·라이브러리·서드파티 에이전트)·비프로덕션 선검증·부하 테스트; 호환 어려운 레거시·라이선스 CPU 종속은 연기 (F-12).
- **크기 적정화**: Compute Optimizer가 과거 사용 지표(기본 룩백 14일)로 EC2·ASG 크기 권고, Graviton 이전 우선순위 권고 포함 (F-13, `4-1.md` F-35). 기능이 부족한 작은 크기는 성능 문제를 부르므로 지표(CPU·메모리·네트워크) 근거로 판단.
- **라이선스 비용**: license-included Windows/SQL Server는 **Optimize CPUs**로 vCPU·하이퍼스레딩을 줄이면 vCPU 기반 라이선스 요금 절감 (F-24).

### 2-5. 컴퓨팅 서비스 선택 — Lambda vs Fargate vs EC2 (Knowledge 8, Skill 3)
| 항목 | Lambda | Fargate(ECS/EKS) | EC2 |
|---|---|---|---|
| 과금 | 요청 수 + 기간(GB-초, **1 ms 단위**) | 프로비저닝된 vCPU·메모리·(추가)스토리지, **초 단위·최소 1분** | 인스턴스 시간(초 단위, 최소 60초) |
| 유휴 시 | 0원(프로비저닝 동시성 제외) | 태스크 종료 시 0원 | 켜져 있으면 과금 |
| 절감 수단 | Compute SP(기간·PC 최대 약 17%), Graviton, 계층 요금, 메모리 튜닝 | Fargate Spot 최대 70%, Compute SP, Graviton | RI/SP, Spot, Graviton, 스케줄 중지 |
| 유리한 패턴 | 간헐적·이벤트·가변 | 장기 실행 서비스·마이크로서비스·배치(서버 관리 없이) | 24/7 고사용률·특수 하드웨어·세밀한 제어 |
- **break-even 판단**(FinOps 가이드): 개발/테스트는 스케줄·스케일 투 제로로 컨테이너·함수 모두 저렴, **24/7 고처리량 프로덕션은 컨테이너(약정 적용)가 Lambda보다 유리할 수 있음**(호출당 과금) (F-16). Lambda는 무료 티어(월 100만 요청·400,000 GB-초)·예시 단가 $0.20/100만 요청·$0.00001667/GB-초 (F-15).
- **단순 규칙**: 요건(지연·실행 시간 15분·상태)을 충족한 뒤 *사용 패턴*으로 선택 — 가변·간헐=Lambda, 지속 서버리스 컨테이너=Fargate, 지속·고사용률·세밀 제어=EC2+약정. 서비스별 한도는 `2-1.md` F-13·F-21, `3-2.md` F-16~F-18 참조.

### 2-6. 로드 밸런싱 전략과 비용 (Skill 1)
| LB | 계층 | 과금 단위 | 비용 관점 선택 |
|---|---|---|---|
| **ALB** | L7(HTTP/HTTPS/gRPC) | 시간당 + **LCU**(신규 연결 25/s · 활성 연결 3,000/분 · 1 GB/시간 · 규칙 평가 1,000/s 중 **가장 큰 하나**) | 호스트·경로·헤더 기반 라우팅으로 **여러 앱을 한 ALB에 통합**해 LB 수 절감 |
| **NLB** | L4(TCP/UDP/TLS) | 시간당 + **NLCU**(TCP: 신규 800/s · 활성 100,000 · 1 GB/시간 중 최대) | 대규모 연결·정적 IP·소스 IP 보존, 대역폭 지향 앱은 ALB 대비 LB 비용 약 25% 절감 사례 |
| **GWLB** | L3 | 시간당 + GLCU | 가상 어플라이언스(방화벽·IDS/IPS) 투명 삽입 |
- 정적 IP+HTTP 라우팅이 모두 필요하면 NLB 앞단·ALB 대상 조합이 가능하나 **LB 두 개의 추가 비용·관리** (F-18). 교차 영역 로드 밸런싱의 AZ 간 전송 요금은 `2-1.md` F-25. NLB·GWLB는 **LCU 예약**(예약분은 사용과 무관하게 과금)이 있음 (F-17).
- 유형 정의·프로토콜은 `3-4.md` F-15~F-17, `2-1.md` F-23.

### 2-7. 필요 가용성 vs 비용 — 프로덕션과 비프로덕션 (Skill 4)
- **프로덕션**: 가용성 요건(SLA)에 맞춰 다중 AZ·Auto Scaling·기본 용량은 약정(RI/SP)으로, 변동분은 On-Demand/Spot — 용량 보장이 필요한 AZ에는 Zonal RI 또는 ODCR+SP (F-05·F-07).
- **비프로덕션**: 24/7·고가용성이 필수가 아니므로 **스케줄 중지(약 75% 절감)**, **Spot 허용**, 작은 크기, 규제 제약이 없으면 **더 저렴한 리전** 배치 (F-11·F-08·F-22).
- 유의: "비프로덕션은 단일 AZ로 충분"과 같은 구성 판단은 AWS 공식 문장으로 확보하지 못해 **설계 판단**으로만 취급(`99-gaps.md`).

### 2-8. 글로벌 인프라·분산·하이브리드 컴퓨팅 비용 (Knowledge 3·5·6)
- **리전 선택**: 서비스 요금은 리전마다 다름(토지·전력·세금 등) → 규정·지연 제약이 없다면 저렴한 리전(예: dev/test를 us-east-1에), 이전비보다 절감이 크면 이전, 계산은 Pricing Calculator (F-22, `3-4.md` F-22).
- **엣지 처리**: CloudFront Functions($0.10/100만 호출)는 Lambda@Edge($0.60/100만 요청+기간 요금, 무료 티어 없음)보다 훨씬 저렴 → 경량 변환은 CloudFront Functions 우선, Lambda@Edge는 트리거를 가장 구체적인 behavior로 제한하고 메모리 최적화 (F-21, `3-2.md` F-23). Local Zones·Wavelength는 지연·레지던시 목적(`3-2.md` F-24).
- **Outposts**: 구성(EC2+EBS gp2+S3) 선택 후 **3년 약정**(All/Partial/No Upfront), 가격에 배송·설치·유지보수·패치 포함, 종료 시 갱신 또는 반납 → "온프레미스 로컬 처리·데이터 레지던시이면서 AWS 운영 모델" 요구에 맞고 *단순 비용 절감용은 아님* (F-19).

## 3. 시험에서 묻는 방식 (패턴)
1. **안정 사용 + 변경 가능성**: "3년간 EC2·Fargate·Lambda를 쓰며 패밀리·리전이 바뀔 수 있음" → **Compute Savings Plans**. 함정: EC2 Instance SP·Standard RI(고정).
2. **패밀리·리전 확정 + 최저가**: → **EC2 Instance Savings Plans**(또는 Standard RI). 특정 AZ 용량 보장 필요하면 **Zonal RI** 또는 **ODCR + SP**.
3. **중단 가능 배치**: → **Spot**(+다양화·price-capacity-optimized, ASG 혼합 정책). 함정: 상태 저장 DB를 Spot에 두기, Savings Plans로 Spot 할인 기대.
4. **개발/테스트 비용 최소**: → **업무 시간 외 중지(Instance Scheduler)**, 약 75%. 함정: RI를 비상시 가동 환경에 구매.
5. **상태 유지 빠른 재개**: "메모리 상태를 보존하며 중지, 재시작 빠르게" → **EC2 최대 절전**(시작 시 활성화, EBS+RAM 저장 비용 발생).
6. **간헐적 워크로드**: → **Lambda**(요청 없으면 0원). 24/7 고트래픽이면 EC2/컨테이너+SP가 더 저렴할 수 있음.
7. **컨테이너 비용**: "서버 관리 없이 컨테이너, 중단 허용 작업" → **Fargate Spot**; 상시 서비스 → Fargate+Compute SP/Graviton.
8. **LB 비용**: "ALB 여러 개를 줄이고 싶다" → **호스트/경로 라우팅으로 한 ALB에 통합**; "대규모 TCP, 정적 IP" → NLB; "방화벽 어플라이언스 삽입" → GWLB.
9. **크기 적정화**: "과대 프로비저닝 의심" → **Compute Optimizer**(권고만, 자동 변경 안 함), 비용 가시화는 Cost Explorer.
10. **동일 성능 더 저렴**: "x86 Linux 컨테이너를 더 싸게" → **Graviton**(호환성 검증); Windows는 불가.
11. **온프레미스 로컬 처리 + AWS 운영 모델**: → **Outposts**(3년 약정). 엣지 경량 변환 → CloudFront Functions.
12. **리전 선택**: "규제 제약 없는 개발 환경 비용" → 더 저렴한 리전.

## 4. 흔한 함정·혼동 짝
- **Savings Plans는 용량을 예약하지 않는다**: 용량 보장은 Zonal RI 또는 ODCR. SP·Regional RI는 ODCR과 결합해 할인.
- **Standard RI 72% vs Convertible 66%**(현행 표기) — 옛 자료의 "54%"는 구버전 서술. Convertible은 교환 가능, **Standard만 Marketplace 판매 가능**(12% 수수료, 잔여 ≥1개월).
- **SP 유형이 4종**(Compute·EC2 Instance·Database·SageMaker AI): 문서마다 2~3종으로 서술. **Database SP는 1년 약정**·최대 35%(→ `4-3.md`).
- **RI/SP는 취소 불가**, 시간당 약정은 이월 불가 → 약정은 최소 사용량 기준.
- **No Upfront RI도 약정**(월 지불 의무, 결제 이력 필요), 미사용 RI도 과금.
- **Spot 폴백**: 중단 시 On-Demand로 자동 폴백하는 설계는 비권장(다른 Spot 중단 유발), 상태 저장·밀결합 워크로드는 Spot 부적합.
- **최대 절전 비용**: 사용료는 없지만 **EBS(RAM 포함) 과금**, `stopping` 중에는 과금, Spot은 Stop API로 최대 절전 불가.
- **Stop ≠ 비용 0**: 중지 인스턴스도 EBS·Elastic IP(미연결 시) 비용(`4-1.md` F-16).
- **LCU는 최대 차원 하나만 과금**: 신규 연결·활성 연결·처리 바이트·규칙 평가 중 최대. 처음 10개 규칙은 무료.
- **Lambda 요청 요금은 Savings Plans 할인 대상이 아님**(기간·프로비저닝 동시성만).
- **Lambda 프로비저닝 동시성은 무료 티어 제외**, 켜 둔 시간만큼 과금. 고사용률 상시 부하는 컨테이너/EC2가 유리할 수 있음.
- **Fargate Savings Plans 절감률 표기가 페이지마다 다름**(약 50%·52%·최대 66%는 Compute SP 일반) → 수치 암기 금지, 구조로 이해.
- **Graviton ≠ 모든 워크로드**: Windows Server 불가, x86 전용 바이너리·라이선스 CPU 종속은 이전 보류.
- **Outposts는 비용 절감 서비스가 아님**: 로컬 처리·지연·레지던시 요건용, 3년 약정.
- **Lambda@Edge vs CloudFront Functions**: 가능하면 CloudFront Functions(단가 1/6 수준, 제약 있음).

## 6. 자가 점검 문항 후보 (재료)
1. **안정 + 유연성**: 3년간 EC2·Fargate를 쓰고 리전·패밀리가 바뀔 수 있다. → **Compute Savings Plans**(최대 66%, EC2·Fargate·Lambda 자동 적용). 오답: Standard RI·EC2 Instance SP. 근거 F-02·F-03.
2. **용량 보장+할인**: 특정 AZ의 인스턴스를 연중 확실히 확보하고 할인도 받아야 한다. → **Zonal RI** 또는 **ODCR+SP/Regional RI**. 오답: SP 단독(용량 예약 없음). 근거 F-05·F-07.
3. **Spot 설계**: 이미지 렌더링 배치를 가장 싸게, 중단되면 재시도. → **Spot**(유형·AZ 다양화, price-capacity-optimized, 체크포인트). 오답: Standard RI. 근거 F-08.
4. **ASG 혼합**: 웹 계층이 상시 4대 필요, 피크에 20대까지. → ASG 혼합 정책에서 **On-Demand 기본 용량 4**(+RI/SP 약정), 초과분 **Spot**. 근거 F-09.
5. **개발 환경 절감**: 개발·테스트 EC2/RDS를 근무 시간 외 사용하지 않음. → **Instance Scheduler**(약 75% 절감, 40h vs 168h). 오답: RI 구매. 근거 F-11.
6. **상태 유지 중지**: 인메모리 캐시가 채워진 EC2를 며칠 중지했다가 즉시 복원. → **EC2 최대 절전**(시작 시 활성화, RAM→EBS 저장, EBS 비용만 발생). 오답: Stop(RAM 소실). 근거 F-10.
7. **약정 크기**: 시간당 사용량이 $3~$8로 변동한다. → 약정은 **최소 안정치(≈$3)** 기준, 초과분은 On-Demand/Spot(시간당 약정은 이월 불가). 근거 F-04.
8. **LB 통합**: 마이크로서비스 6개가 각자 ALB를 둔다. → 호스트·경로 기반 라우팅으로 **ALB 통합**(LB 수·시간당 요금 절감, LCU는 최대 차원 하나). 근거 F-17·F-18.
9. **Lambda vs EC2**: 하루 종일 일정한 고트래픽 API. → 약정 적용 컨테이너/EC2가 더 저렴할 수 있음; 간헐적이면 Lambda. 근거 F-16.
10. **Fargate 절감**: 중단 허용 배치 태스크. → **Fargate Spot**(최대 70%), 상시는 Compute SP+Graviton. 근거 F-14.
11. **크기 적정화**: 평균 CPU 8%인 m5.2xlarge 20대. → **Compute Optimizer** 권고(작은 크기 또는 Graviton), 권고는 *수동 적용*. 근거 F-13.

13. **온프레미스 로컬 처리**: 지연·레지던시로 공장 내 AWS 인프라 필요. → **Outposts**(3년 약정). 근거 F-19.
14. **리전**: 규제 제약 없는 개발 환경 비용 절감. → 요금이 낮은 리전으로 이전. 근거 F-22.
