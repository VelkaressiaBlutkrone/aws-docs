### 2-3. Intelligent-Tiering — 무엇이 자동이고 무엇이 선택인가 (Knowledge 9·10, Skill 8)
| 단계 | 조건 | 비고 |
|---|---|---|
| Frequent Access | 업로드/전환 직후 | Standard 수준 단가 |
| Infrequent Access | **연속 30일** 미접근 | 최대 40% 절감 |
| Archive Instant Access | **연속 90일** 미접근 | 최대 68% 절감, ms 접근 |
| (선택) Archive Access | 최소 90일(설정 가능) | 최대 71%, 분~시간 → **RestoreObject 필요** |
| (선택) Deep Archive Access | 최소 180일(설정 가능) | 최대 95%, RestoreObject 필요 |
- **검색 요금 없음**, 계층 간 이동에 별도 계층화·수명 주기 요금 없음, 접근하면 Frequent Access로 복귀 (F-06).
- **128 KB 미만 객체는 모니터링·자동 계층화 대상이 아님** → 항상 Frequent 단가이며 모니터링 요금도 없음 (F-07). 즉 "소형 객체가 많으면 I-T가 무조건 손해"가 아니라 "소형 객체는 절감 효과가 없다"가 정확한 서술. 수명 주기 규칙도 128 KB 미만을 I-T로 옮기지 않음.
- **I-T vs 수명 주기**: 접근 패턴을 **알 때**(로그: 30일 후 거의 안 봄) → 수명 주기 전환이 모니터링 요금 없이 더 싸다. 패턴이 **불확실·불규칙**하면 I-T. 둘은 혼용 가능(수명 주기로 Standard→I-T 이동, F-07).

### 2-4. S3 수명 주기 관리 (Knowledge 7, Skill 5·9)
- **액션**: Transition(클래스 이동), Expiration(만료/삭제), `AbortIncompleteMultipartUpload`(미완료 멀티파트 파트 삭제), 버전 관리 버킷의 `NoncurrentVersionTransition/Expiration`(+ `NewerNoncurrentVersions`로 최근 N개 이전 버전 유지) (F-09).
- **제약**: 클래스 "폭포" 하향만 가능(예: Standard-IA→Standard 불가), 30일 미만 보관 객체는 Standard-IA/One Zone-IA로 못 옮김, **2024-09 이후 생성 설정은 128 KB 미만 객체를 기본 미전환**(`ObjectSizeGreaterThan/LessThan` 필터로 허용), Standard-IA 객체는 30일 후 Glacier로, 규칙은 하루 1회 실행 (F-08).
- **전환 비용**: 객체 하나 전환 = 요청 1건 과금, 전환 후에는 새 클래스 단가. 최소 보관 전에 삭제·덮어쓰기·전환 → 잔여 기간 일할 과금 (F-01·F-02·F-05). 수천만 소형 객체를 Glacier로 보내면 전환 요청비·40 KB 메타데이터가 절감액을 초과 → **집계(tar) 후 전환** (F-05).
- **전형 패턴(로그)**: Standard 30일 → Standard-IA(총 30일 이상 보관 충족) → 90일 시점 Glacier FR/Deep Archive → 법정 보존 만료 시 Expire. 버전 관리 버킷은 이전 버전 만료 규칙 필수 (F-09).
- **분석 도구**: Storage Class Analysis(Standard→IA 최적 시점), Storage Lens(조직 전체 지표) (F-10·F-11).

### 2-5. 업로드 전략 — 배치 vs 개별 (Skill 1)
- 요청은 **건당 과금**(S3 PUT·LIST는 1,000건 단위 가격 — 예: DataSync 요금 예시가 PUT $0.005/1,000건을 사용, F-27)이고, 소형 객체는 클래스별 최소 과금 크기(IA 128 KB)·Glacier 객체당 40 KB 메타데이터·전환 요청이 겹쳐 단가 효율이 나쁘다 → **작은 파일을 묶어(아카이브/tar·Firehose 버퍼·배치 업로드) 큰 객체로** 올리면 요청 수·전환 수·메타데이터가 줄어든다 (F-05).
- 반대로 **큰 객체는 멀티파트**(병렬·재시도 이점, `3-1.md` F-03·F-04)로 올리되 **중단된 업로드는 수명 주기로 정리**(F-09). 묶음의 단점: 객체 일부만 읽어도 전체를 받아야 하고 개별 수명 주기·삭제 불가 → 읽기 패턴이 개별 접근형이면 "묶기"는 부적절.
- 임계: 128 KB~1 MB 구간 객체가 수백만 개(>1 TB 규모)면 집계 이득이 크고, 소규모(≈16 GB, 7.5만 개)면 이득이 무시할 수준이라는 AWS 사례 (F-05).

### 2-6. 데이터 전송 비용·가장 저렴한 이전 방법 (Knowledge 8, Skill 3·7)
- **S3 전송 요금 규칙**: 인터넷→S3(인바운드)는 무료, 같은 리전의 S3↔S3·S3→같은 리전 AWS 서비스·S3→CloudFront는 무료, 인터넷 아웃바운드는 월 100 GB(전 서비스·리전 합산)까지 무료 후 과금 (F-13).
- **가속 옵션은 추가 과금**: S3 Transfer Acceleration은 가속 엔드포인트 전송량에 대해 별도 GB당 요금(인·아웃·타 리전) (F-14) → 속도가 요구되지 않으면 일반 엔드포인트가 더 싸다.
- **이전 수단 비교(비용 관점)**: DataSync=전송 GB당 고정 요금, 약정·최소 없음 (F-27) / Transfer Family=프로토콜 시간당+전송량(`2-1.md` F-27) / Storage Gateway=캐시형 하이브리드 접근(`3-1.md` F-20), Tape Gateway=가상 테이프(F-26) / **Snow 패밀리는 신규 불가**(`3-5.md` F-09)이므로 "Snowball이 가장 싸다"류 옛 정답은 제외 / 전용선·VPN(`3-4.md` F-18·F-19) / 시간 계산·대역폭 제한은 `3-5.md` §2-3.
- **VPC 내부 S3 접근**: 게이트웨이 엔드포인트는 무료이고 NAT 게이트웨이를 거치지 않아 NAT 처리 요금이 없다(`3-4.md` F-13, 상세는 `4-4.md`).

### 2-7. EBS 비용 (Knowledge 6, Skill 2·8)
- **볼륨 유형**: gp3는 gp2 대비 GiB당 **최대 20% 저렴**하면서 3,000 IOPS·125 MiB/s를 크기와 무관하게 기본 제공, 더 높은 성능은 별도 추가 과금 (F-15). HDD(st1/sc1)는 처리량 지향·sc1이 최저가이나 부팅 불가 (`3-1.md` F-08). io1→io2는 같은 가격에 내구성 향상 (F-15).
- **전환·크기 조정**: Elastic Volumes로 유형·IOPS·처리량 변경 시 인스턴스 중단 없음(gp2→gp3 포함), **크기 축소 불가**·24시간 롤링 4회 제한(`3-1.md` F-11) → 과대 프로비저닝은 새 볼륨으로 이전해야 줄일 수 있다. Compute Optimizer·Trusted Advisor가 과잉 프로비저닝 EBS를 권고 (F-35).
- **낭비 패턴**: 인스턴스를 중지해도, 볼륨을 분리해도 **프로비저닝 용량 요금은 계속** — 삭제해야 멈춤 (F-16). 종료 시 자동 삭제는 `DeleteOnTermination`이 결정: 부팅(루트) 볼륨은 기본 삭제, **추가 데이터 볼륨은 기본 보존**(콘솔로 시작 시 첨부해도 보존) → 종료만으로는 데이터 볼륨 과금이 끝나지 않는다 (F-17).
- **스냅샷**: 증분(최초 1회만 전체), 저장된 데이터 양(GB-월)으로 과금, 빈 블록 미과금. 스냅샷 삭제는 그 스냅샷에만 고유한 데이터를 지우고 **참조되는 데이터는 이후 스냅샷으로 비용이 이전** → 중간 스냅샷 삭제가 항상 비용을 줄이지는 않음 (F-18). Recycle Bin 보관분도 표준 요금 (F-18).
- **수명 주기 자동화**: Data Lifecycle Manager(DLM)가 스냅샷·EBS 기반 AMI의 생성·보존·삭제를 자동화(보존 만료 삭제로 비용 절감), 사용자 지정 정책은 교차 리전 복사·**아카이브**·FSR 지원; AWS Backup으로도 중앙 관리 가능 (F-19).
- **Snapshots Archive**: 90일 이상 보관할 드물게 쓰는 스냅샷은 **최대 75% 저렴**(아카이브 시 전체 스냅샷으로 변환·최소 90일·복원 최대 72시간·복원 요금), 월/분기/연 스냅샷에 적합하고 **일 단위 증분 스냅샷을 아카이브하면 오히려 비쌀 수 있음** (F-20).

### 2-8. EFS·FSx 비용 계층 (Knowledge 4·10, Skill 8·10)
| 서비스 | 비용 절감 수단 | 주의 |
|---|---|---|
| **EFS** | 클래스: Standard → **IA**(드문 접근, 분기 몇 회) → **Archive**(연 몇 회 이하). 수명 주기 기본값: 30일 미접근 → IA, 90일 미접근 → Archive, 기본은 접근해도 **되돌리지 않음**(첫 접근 시 Standard 복귀 옵션·**Intelligent-Tiering**). **One Zone** 클래스는 Standard 대비 47% 저렴(단일 AZ) | IA는 읽기·쓰기마다 **데이터 접근 요금**(Archive의 접근 요금 세부는 가격 페이지 미확인), IA·Archive 모두 128 KiB 미만은 128 KiB로 과금, Archive는 최소 보관 90일·Elastic 처리량+범용 모드 필요 (F-21~F-23) |
| **FSx for Windows** | **HDD** 선택(20 TB 다중 AZ 월 비용 예: SSD $4,699 vs HDD $543, 리전·시점 의존), **데이터 중복 제거**, 필요 시 여러 소형 파일 시스템으로 SSD/HDD 혼합 | 용량은 **증가만 가능**(감소 불가) (F-24·F-29) |
| **FSx for ONTAP** | SSD 티어 + **용량 풀 티어링**(볼륨별 정책, 사용한 만큼만 과금), 압축·중복 제거 | SSD는 프로비저닝 과금 (F-24) |
| **FSx for Lustre** | **Scratch**(복제 없음·임시 처리 비용 절감) vs Persistent, 스토리지 클래스 SSD / **Intelligent-Tiering(저장량 과금)** / HDD | Scratch는 서버 장애 시 데이터 유실 (F-24) |

## 3. 시험에서 묻는 방식 (패턴)
1. **패턴 불명 + 검색 요금 회피**: "접근 빈도를 예측할 수 없는 데이터, 운영 부담 최소·비용 최적" → **S3 Intelligent-Tiering**. 함정: Standard-IA(검색 요금), 수명 주기(패턴 필요).
2. **수명 주기 설계**: "30일 자주, 이후 드물게, 1년 후 삭제" → Standard→(30일)Standard-IA→(90일)Glacier→Expire. 함정: 30일 이전에 IA로 이동, 소형 객체 대량 Glacier 이동.
3. **재생성 가능 데이터 + 가장 저렴한 ms 접근**: → **One Zone-IA**(단일 AZ 손실 허용). 원본이면 Standard-IA.
4. **즉시 접근 가능한 아카이브**: "분기 1회, ms" → **Glacier Instant Retrieval**. "연 1~2회, 몇 시간 OK" → Glacier Flexible. "규정 7년, 거의 안 읽음" → **Deep Archive**.
5. **요청자 부담**: "데이터셋을 공유하되 다운로드 비용은 사용자가 부담" → **Requester Pays**(익명 불가·요청자 인증 필요).
6. **EBS 절감**: "gp2 다수, 성능 유지하며 비용 절감" → **gp3 전환**(Elastic Volumes, 무중단). "오래된 스냅샷 비용" → **DLM 보존 정책** 또는 **Snapshots Archive**(분기·연 단위). "분리된 볼륨" → 삭제.
7. **EFS 비용**: "Linux 공유 파일, 접근이 줄어드는 파일 많음" → **EFS 수명 주기(IA→Archive)/Intelligent-Tiering**, 다중 AZ 불필요하면 **One Zone**.
8. **Windows 파일, 비용 최소**: "홈 디렉터리·부서 공유" → **FSx for Windows HDD** + 중복 제거.
9. **비용 책임 분리**: "팀/프로젝트별 비용 보고" → **비용 할당 태그 활성화** + Cost Explorer; "여러 계정 할인 합산" → **통합 결제**.
10. **예산 초과 방지**: "월 한도 초과 시 알림·자동 차단" → **AWS Budgets + 예산 작업**.
11. **이전**: "온프레미스 파일 서버 → S3/EFS 정기 동기화, 최소 운영" → **DataSync**. "테이프 백업 SW 유지" → **Tape Gateway**. 옛 정답 "Snowball"은 신규 불가.
12. **오토 스케일링**: "스토리지가 가득 차기 전에 자동 확장" → 탄력 서비스(S3·EFS) 선택, EBS·FSx면 알람+자동 증설.

## 4. 흔한 함정·혼동 짝
- **Glacier = 항상 최저 비용?** 최소 보관(90/180일)·검색 요금·복원 시간·객체당 40 KB 메타데이터가 있어 소형·자주 읽는 데이터는 오히려 비쌈.
- **EC2 Stop/Terminate와 EBS 과금**: Stop·분리 모두 EBS 요금 지속. Terminate도 **루트만 기본 삭제**, 추가 데이터 볼륨은 기본 보존 → 손수 삭제하거나 `DeleteOnTermination` 설정.
- **스냅샷 삭제 = 비용 감소?** 참조 데이터는 보존되고 비용이 다음 스냅샷으로 이전.
- **Snapshots Archive는 증분이 아님**: 전체 스냅샷이라 크기가 커질 수 있고, 일 단위 증분에는 비효율.
- **I-T 오해**: 128 KB 미만 객체는 모니터링 요금이 없는 대신 절감도 없음. Archive/Deep Archive Access는 **선택 활성화**이며 복원(RestoreObject) 필요, 기본 3계층만 ms 접근.
- **Standard-IA에서 Glacier로**: IA에서 30일 이상 있어야 이동(re:Post 서술). 30일 미만 객체는 IA로 이동 불가.
- **수명 주기 vs 소형 객체**: 128 KB 미만은 기본 미전환(2024-09 이후 설정), 필터로 허용 가능하나 전환비가 절감을 초과하기 쉬움.
- **버전 관리 + 수명 주기**: 이전 버전이 계속 쌓여 과금 → `NoncurrentVersionExpiration`.
- **미완료 멀티파트**: 파트 저장 요금 지속 → `AbortIncompleteMultipartUpload`.
- **Requester Pays ≠ 저장 요금 이전**: 소유자는 저장 요금을 계속 부담, 요청·다운로드만 요청자 부담. 익명 접근 불가.
- **Transfer Acceleration 비용**: 가속 엔드포인트 전송분에 추가 GB 요금(필요 없으면 켜지 않음).
- **FSx for Windows 용량 감소 불가**: 증설만 가능 → 과대 프로비저닝 주의.
- **Storage Class Analysis ≠ Storage Lens**: 전자는 접근 패턴 분석(Standard→IA 시점)용 S3 분석 기능, 후자는 조직 전체 사용·활동 지표 대시보드(권고는 고급 티어).
- **AWS Backup 콜드 전환 조건**: 최소 90일 보관이 강제되고 대상 리소스가 제한됨(모든 리소스가 콜드 가능한 것은 아님).
- **Trusted Advisor 전체 점검은 유료 지원 플랜 필요**(Basic은 일부 보안·서비스 한도 점검). 2027-01-01 플랜 개편 전후 명칭 주의.

## 6. 자가 점검 문항 후보 (재료)
1. **로그 수명 주기**: 처음 30일 자주 조회, 이후 90일까지 가끔, 1년 후 삭제. → 30일 Standard-IA, 90일 Glacier FR(또는 DA), 365일 Expiration(IA 30일·Glacier 90일 최소 보관 충족). 오답: 20일에 IA 이동(30일 미만 불가). 근거 F-01·F-05·F-08.
2. **패턴 불명**: 수 TB, 접근 불규칙, 검색 요금 회피, 운영 최소. → **Intelligent-Tiering**(검색 요금 없음, 객체당 모니터링 요금). 오답: Standard-IA·Glacier FR. 근거 F-06.
3. **재생성 가능 썸네일**: 원본은 다른 곳에 있고 썸네일만 ms 접근·가장 저렴. → **One Zone-IA**. 오답: Standard-IA(원본 전용). 근거 F-01.
4. **분기 1회 규정 감사**: 즉시(ms) 접근 필요한 아카이브. → **Glacier Instant Retrieval**. 오답: Flexible Retrieval(복원 대기). 근거 F-02·F-04.
5. **gp2→gp3**: gp2 100 GiB 볼륨(기본 300 IOPS)을 비용 절감하며 성능 향상. → **gp3**(기본 3,000 IOPS·125 MiB/s, GiB당 최대 20% 저렴, Elastic Volumes 무중단). 근거 F-15.
6. **EBS 낭비**: 인스턴스를 종료했는데 EBS 요금이 계속 나온다. → 추가 데이터 볼륨은 `DeleteOnTermination` 기본 보존이라 남음(루트만 삭제) → 볼륨 삭제·속성 설정. 오답: 인스턴스 중지만으로 요금 중단. 근거 F-16·F-17.
7. **스냅샷 비용**: 월말 스냅샷 수십 개를 3년 보관, 거의 복원 안 함. → **EBS Snapshots Archive**(최대 75%, 최소 90일, 복원 최대 72시간)+DLM 보존. 오답: 일 단위 증분을 아카이브(오히려 비쌀 수 있음). 근거 F-19·F-20.
8. **EFS**: 개발 환경 Linux 공유 파일, 단일 AZ 허용, 오래된 파일 많음. → **EFS One Zone + 수명 주기(IA/Archive)**(Archive는 Elastic+범용 모드). 근거 F-21~F-23.
9. **Windows 홈 디렉터리**: SSD 대비 비용 절감. → **FSx for Windows HDD** + 중복 제거. 근거 F-24.
10. **요청자 부담**: 대용량 공개 데이터셋 제공, 사용자가 전송 비용 부담. → **Requester Pays**(익명 불가). 근거 F-12.
11. **비용 책임 분리**: 팀별 비용 보고. → 태그 부여+**결제 콘솔 활성화**(최대 24시간+24시간), Cost Explorer·CUR에서 태그로 그룹화. 근거 F-30.
12. **예산 통제**: 월 한도의 80% 도달 시 알림, 초과 시 신규 리소스 생성 차단. → **Budgets**(실제/예측 알림)+**예산 작업**(IAM 정책/SCP 적용). Cost Explorer는 차단 불가. 근거 F-32·F-33.
13. **소형 객체 폭증**: 수백만 개 4 KB 로그 파일을 Glacier로 아카이브하려 한다. → **tar 등으로 집계 후 업로드/전환**(전환 요청·40 KB 메타데이터·IA 128 KB 최소 과금 회피). 근거 F-05.
14. **FSx 확장**: Windows 파일 시스템이 80% 찼다. → 용량 **증가만 가능**, CloudWatch 알람+Lambda 자동화(템플릿), 축소 불가. 근거 F-29.
