## 2. 핵심 개념

### 2-1. 용어와 지표 (Skill 3, Knowledge: 스토리지 옵션·특성)
- **가용성 = 일정 기간 중 워크로드가 사용 가능한 시간의 비율**. 연간 허용 중단: 99.9% ≈ 8시간 45분 / 99.95% ≈ 4시간 22분 / 99.99% ≈ 52분 / 99.999% ≈ 5분 (F-02).
- **HA(고가용성)** = 장애를 자동 감지·복구해 중단을 최소화(짧은 중단 허용). **내결함성(FT)** = 구성요소가 실패해도 **무중단** 지속(능동 이중화, 비용 큼). **DR** = 리전급 재해 복구(RTO/RPO로 정량화). 시험 문구: "highly available"=Multi-AZ+자동 복구, "fault tolerant"=더 강한 무중단.
- 측정 지표: 가용성 %, MTBF·MTTR, RTO(복구 시간 목표)·RPO(복구 시점 목표), 요청 성공률·오류율(F-02).
- 서비스별 SLA/설계 목표(F-26·F-08·F-09): RDS Multi-AZ(인스턴스·클러스터) **99.95%**, 단일 DB 인스턴스 99.5%; Aurora Multi-AZ **99.99%**, 단일 AZ 99.9%; DynamoDB 단일 리전 99.99% / 글로벌 테이블 **99.999%**; S3 Standard 가용성 99.99%·내구성 11 9s; EFS Regional 99.99%.

### 2-2. 글로벌 인프라와 SPOF 제거 매핑 (Skill 2·4, Knowledge: 글로벌 인프라)
- **리전** = 격리된 **최소 3개 AZ**(독립 전원·냉각·물리 보안, 중복 저지연 네트워크). 2026-10-17 기준 **39개 리전·124개 AZ**, 추가 계획(사우디·칠레), Local Zone 46·Wavelength Zone 33, CloudFront POP 750+ (F-01). AZ는 수 km 이상 떨어져 있으나 서로 100 km 이내 (F-01).
- **서비스가 이미 다중 AZ인 것**(설정 불필요): S3(Standard 계열 ≥3 AZ), DynamoDB(리전 서비스), EFS Regional(≥3 AZ), Aurora 스토리지(6 사본/3 AZ), ELB 노드, Lambda/Fargate(다중 AZ 배치 시).
- **직접 이중화해야 하는 것**: EC2(ASG 다중 AZ), RDS(Multi-AZ 활성화), NAT 게이트웨이(AZ별 또는 Regional NAT, `1-2.md` F-09·10), EBS(AZ 내 복제만 → 스냅샷/다중 AZ 앱 계층), ElastiCache(Multi-AZ+복제본 — 공식 문장 미확보 `99-gaps.md`).
- **스토리지 특성(내구성·가용성)**:

| 스토리지 | 내구성/가용성 | AZ 내성 |
|---|---|---|
| S3 Standard / Standard-IA / Glacier 계열 | 11 9s / 가용성 99.99%(Standard)·99.9%(IA·Intelligent) | ≥3 AZ, AZ 손실에도 유지 |
| S3 One Zone-IA | 11 9s(AZ 내) / 99.5% | **AZ 손실에 취약**, S3 Express One Zone 99.95% 단일 AZ |
| EBS | AZ 내 다중 서버 복제, 일반 AFR 0.1~0.2%, **io2 Block Express 99.999%(AFR 0.001%)**, Multi-Attach(최대 16 Nitro 인스턴스·같은 AZ) | **단일 AZ** (스냅샷으로 보호) |
| EFS Regional / One Zone | 11 9s / 99.99% / One Zone 99.9% | Regional=≥3 AZ, One Zone=단일 AZ |
(F-09~F-11)

### 2-3. 데이터베이스 가용성 (Skill 2·5, Knowledge: 프록시)
| 옵션 | 구성 | 장애 조치 | 비고 |
|---|---|---|---|
| **RDS Multi-AZ DB 인스턴스** | 다른 AZ에 동기 스탠바이 1개 (읽기 **불가**) | 보통 **60~120초** | DNS 엔드포인트 전환, SLA 99.95% (F-03·26) |
| **RDS Multi-AZ DB 클러스터** | 3개 AZ에 primary+**읽기 가능한 스탠바이 2개** | 보통 **35초 미만** | 커밋 지연 최대 2배 개선, 읽기 용량 추가 (F-04) |
| **Aurora** | 스토리지 6사본/3 AZ, 리더 최대 15 | 보통 **30초 미만**(리더 승격) | 2사본 손실에도 쓰기·3사본 손실에도 읽기 가능, Multi-AZ 클러스터 SLA 99.99% (F-06) |
| **Aurora Global Database** | 보조 리전 **최대 10**(2026-10-17 사용자 가이드; 구 블로그는 5), 스토리지 수준 복제 | 승격 보통 **1분 미만**, 복제 지연 보통 **1초 미만** | PostgreSQL은 `rds.global_db_rpo`로 RPO 관리 (F-07) |
| **DynamoDB 글로벌 테이블** | 다중 리전 active-active | 리전 장애 시 다른 리전 사용 | MREC(기본, 1~2초·last-writer-wins) vs **MRSC**(2025-06~, 동기·강한 일관 읽기) (F-08) |
- **RDS Proxy**: 연결 풀링·다중화로 장애 조치 때 연결 유지, 복구 **최소 3초**까지 단축(블로그), Multi-AZ 클러스터 마이너 업그레이드 중단 약 1초 (F-05). 앱은 프록시 엔드포인트만 쓰면 되어 **코드 변경 최소**.
- **읽기 전용 복제본은 가용성 기능이 아니다**(비동기·수동 승격; Aurora 리더는 자동 승격 대상).

### 2-4. 컴퓨트 계층 자가 복구 (Skill 1·2·7)
- **ASG + ELB**: 다중 AZ 분산, 인스턴스 헬스 체크 실패 시 자동 교체. 헬스 체크 유형 기본 EC2 상태, **ELB 유형을 켜야** 애플리케이션 수준 장애 감지. **헬스 체크 유예 기간**: 콘솔 기본 **300초**, CLI/SDK 기본 **0초** (F-12). 수명 주기 훅을 쓰면 유예 0 가능.
- **조정 정책**: 대부분 **대상 추적**으로 충분, 단계 조정은 알람 구간별, 예약·예측 정책 병행 가능. 정책 여러 개면 **용량이 큰 쪽** 우선. 기본 쿨다운 300초 (F-13).
- **EC2 자동 복구(개별 인스턴스, 앱 수정 불가 시)**: `StatusCheckFailed_System` CloudWatch 경보에 **recover** 작업 → 새 하드웨어로 이동하며 **인스턴스 ID·IP·EIP·EBS 연결 유지**, 단 **RAM·인스턴스 스토어 데이터는 소실**, 시스템 상태 검사 실패에만 해당 (F-14). 대안: ASG min=max=1.
- **변경 불가능한(immutable) 인프라**: 운영 중 업데이트·패치·구성 변경을 제자리에서 하지 않고 **새 리소스를 병렬 배포 후 트래픽 전환**(블루/그린), 롤백 쉬움, 구성 드리프트 감소 (F-21). AMI/Image Builder·CloudFormation으로 자동화(Skill 1: 인프라 무결성 자동화).

### 2-5. 트래픽 전환: Route 53 · ARC (Knowledge: 장애 조치·Route 53)
| 정책 | 용도 |
|---|---|
| Simple / Weighted / Latency / Geolocation / Geoproximity / IP-based | 일반 라우팅 |
| **Failover** | **Active-Passive** (기본 리소스 비정상 시 보조로) |
| **Multivalue answer** | 건강한 레코드 최대 **8개** 무작위 응답 (ELB 대체 아님) (F-16) |
- **Active-Active**는 failover 이외 정책 + 헬스 체크 조합, **Active-Passive**는 failover 정책 (F-16).
- **헬스 체크**: 간격 기본 **30초**(고속 **10초**), 실패 임계값 기본 **3**(1~10), 건강 판정은 헬스 체커의 **18% 초과**가 정상일 때, HTTP(S)는 4초 내 TCP 연결 + 2초 내 2xx/3xx, **HTTPS는 인증서를 검증하지 않음** (F-15).
- **장애 조치 시간 = TTL + (간격 × 임계값)** (예: 60 + 10×5 = 110초) (F-15).
- **ARC(Application Recovery Controller)**: **zonal shift**(AZ 장애 시 트래픽 이탈, 임시·최대 3일, 사전 용량 확보 필요), **zonal autoshift**(AWS가 자동 시작), **routing control**·**Region switch**(다중 리전 전환). 추가 요금: zonal shift 무료, routing control·Region switch 유료 (F-17).
- Global Accelerator는 DNS 캐시 영향이 없는 대안(`3-4.md`).

### 2-6. DR 전략 (Skill 6, Knowledge: DR 전략·Service Quotas)
| 전략 | RPO | RTO | 상시 가동 | 대표 수단 |
|---|---|---|---|---|
| Backup & Restore | 시간 | **24시간 이하** | 백업만 | AWS Backup 교차 리전, S3 CRR, 스냅샷 복사 |
| Pilot Light | 분 | **수십 분** | 데이터 복제·핵심 인프라(앱 서버는 미배포) | 교차 리전 복제본, IaC로 앱 기동 |
| Warm Standby | **초** | **분** | 축소판이지만 **완전 기능** 스택 | Aurora Global DB, DynamoDB 글로벌 테이블 |
| Multi-site Active-Active | 거의 0 | 초~분 | 양쪽 모두 프로덕션 | Route 53/Global Accelerator + 다중 리전 쓰기 |
(F-18, 숫자는 Well-Architected REL13-BP02; Active-Active RTO는 AWS 설명 페이지)
- **AWS Elastic Disaster Recovery(DRS)**: 연속 블록 수준 복제로 **RPO 초**, 복구 인스턴스 기동 **RTO 분**, 스테이징 영역 소규모 컴퓨팅. 대규모 시 한도(예: 동시 복제 소스 서버 계정당 300) (F-19).
- **대기(DR) 환경 Service Quotas**: 활성 리전에서만 한도를 늘리고 대기 리전을 놓치면 **전환 시 리소스 생성 실패** — Region switch가 컴퓨트·DB 쿼터 사전 점검 (F-20). 한도는 **계정·리전별**.
- 재시도 설계: **지수 백오프 + 지터 + 최대 재시도 제한**으로 "retry storm" 방지 (F-22).

### 2-7. 워크로드 가시성·레거시·관리형 서비스 (Knowledge/Skill 7·8)
- **AWS X-Ray**: 애플리케이션이 처리하는 요청의 데이터를 수집, 하위 AWS 리소스·마이크로서비스·DB·웹 API 호출까지 **트레이스 맵**으로 병목·오류 파악 (F-23).
- **레거시/비클라우드 앱 신뢰성 개선(앱 변경 불가)**: ELB+ASG(상태 외부화 불가 시 min=max=1), EC2 자동 복구, **RDS Multi-AZ/Proxy**, **EFS**/FSx 공유 스토리지, **Route 53 failover**, **AWS Elastic Disaster Recovery**, AWS Backup — 애플리케이션 코드 수정 없이 인프라 계층에서 이중화.
- **AWS Managed Services(AMS)**: AWS 인프라 **운영을 대행**하는 엔터프라이즈 서비스(모니터링·패치·백업·보안, 24/7). **AMS Advanced는 2027-06-30 지원 종료** 예고. 가이드가 든 예시 Comprehend·Polly는 AMS가 아니라 **관리형 AI 서비스** → 가이드 문구 모호(`99-gaps.md`) (F-24).
- **목적별 서비스**: 읽기 확장=Aurora 리더/ElastiCache, 큐=SQS, 이벤트=EventBridge, DB 연결=RDS Proxy 등(`2-1.md` §2-8).

## 3. 시험에서 묻는 방식 (패턴)
1. **표준 HA 설계**: "AZ 하나가 죽어도 웹 서비스 유지, 다운타임 수 분 허용" → Route 53 → ALB → **다중 AZ ASG** → **RDS Multi-AZ**(또는 Aurora).
2. **DB 선택**: "자동 장애 조치 + 읽기 확장 + 빠른 전환" → **Aurora 리더 / Multi-AZ DB 클러스터**. 함정: "Multi-AZ 인스턴스 스탠바이로 읽기 분산"(불가), "읽기 복제본으로 HA"(수동 승격).
3. **리전 DR 수치**: "RPO 초·RTO 분, 비용 합리" → **Warm Standby** + Aurora Global DB/DynamoDB 글로벌 테이블 + Route 53 failover. "RTO 24시간, 최저 비용" → Backup & Restore.
4. **온프레미스 서버 DR**: "서버 단위 연속 복제, 수 분 내 AWS 기동" → **Elastic Disaster Recovery**.
5. **레거시 단일 서버**: "앱 수정 불가, 단일 EC2 하드웨어 장애 자동 복구" → **EC2 자동 복구 경보** 또는 ASG min=max=1.
6. **트래픽 전환 속도**: "DNS 캐시 때문에 전환 지연" → TTL 단축/헬스 체크 간격 10초, 또는 Global Accelerator. 계산: TTL+간격×임계값.
7. **AZ 장애 우회**: "AZ 성능 저하 시 트래픽 일시 이탈" → ARC **zonal shift**(사전 prescale).
8. **병목 추적**: "마이크로서비스 호출 경로의 지연 구간 시각화" → **X-Ray**.
9. **DR 사전 점검**: "페일오버 때 인스턴스 생성 실패(한도)" → 대기 리전 **Service Quotas** 사전 증액.

## 4. 흔한 함정·혼동 짝
- **Multi-AZ 인스턴스 vs Multi-AZ 클러스터 vs 읽기 복제본**: 스탠바이 읽기 불가 / 읽기 가능 스탠바이 2 / 비동기·수동 승격. 장애 조치 60~120초 vs <35초.
- **Aurora 스토리지는 항상 3 AZ**지만 **인스턴스가 한 AZ뿐이면** AZ 장애 시 컴퓨트 장애 조치 불가(단일 AZ 클러스터 SLA 낮음).
- **HA vs FT vs DR**: 중단 허용 여부와 범위(AZ vs 리전).
- **Pilot Light vs Warm Standby**: 앱 서버 미배포 vs 축소판 상시 가동·즉시 처리 가능.
- **S3 One Zone-IA·EFS One Zone·EBS** 는 단일 AZ — 가용성 설계에서 SPOF.
- **글로벌 테이블 일관성**: 기본 MREC는 최종 일관, **강한 일관 리전 간 읽기는 MRSC**(생성 시 선택, 이후 변경 불가, 다중 계정 글로벌 테이블은 MREC만).
- **Route 53 HTTPS 헬스 체크는 인증서 만료를 못 잡는다**.
- **ARC zonal shift는 임시 완화**(최대 3일)이며 사전 용량이 없으면 무의미.
- **DR 환경 쿼터**: 활성 리전만 증액하면 전환 실패.
- **ASG 헬스 체크**: ELB 유형을 켜지 않으면 앱 장애 인스턴스를 교체하지 않음; 유예 기간 콘솔 300초 vs CLI 0초.
- **EC2 자동 복구**: 시스템 상태 검사 실패만 해당, 인스턴스 상태 검사 실패는 재부팅 필요; RAM·인스턴스 스토어 소실.
- **CLB**는 EC2-Classic 전용이 아님(EC2-Classic은 2022-08-15 이후 신규 불가) — 신규는 ALB/NLB (F-25).
- **AMS(관리 서비스) vs 관리형 AI 서비스**: 가이드의 "AWS Managed Services" 예시가 혼동 소지.

## 6. 자가 점검 문항 후보 (재료)
1. **표준 HA**: 단일 EC2+단일 RDS 웹 서비스를 AZ 장애에 견디게. → **ALB + 다중 AZ ASG(ELB 헬스 체크) + RDS Multi-AZ**, 세션은 ElastiCache/DynamoDB로 외부화. 근거 F-03·F-12.
2. **DB 장애 조치 시간**: 읽기 확장과 35초 미만 장애 조치를 동시에 요구하는 MySQL 호환 DB. → **Multi-AZ DB 클러스터(읽기 가능 스탠바이 2) 또는 Aurora**. 오답: Multi-AZ 인스턴스(스탠바이 읽기 불가·60~120초). 근거 F-03·F-04·F-06.
3. **리전 DR**: RPO 몇 초·RTO 몇 분, 전체 활성-활성은 비용 과다. → **Warm Standby + Aurora Global Database + Route 53 failover**. 근거 F-18·F-07.
4. **DNS 장애 조치 시간**: TTL 60초, 헬스 체크 간격 10초, 임계값 3일 때 전환 완료까지? → 60 + 10×3 = **90초**. 근거 F-15.
5. **앱 수정 불가 단일 서버**: 호스트 하드웨어 장애 시 자동 복구, 같은 IP·EBS 유지. → **CloudWatch `StatusCheckFailed_System` + recover 작업**(RAM 데이터 소실 주의). 근거 F-14.
6. **온프레미스 DR**: 서버 단위 연속 복제, 평시 최소 비용, 재해 시 수 분 내 AWS 기동. → **Elastic Disaster Recovery**. 근거 F-19.
7. **한도**: DR 리전으로 전환 시 인스턴스 시작이 `InstanceLimitExceeded`로 실패. → **대기 리전 Service Quotas를 사전에 활성 리전 수준으로 증액**. 근거 F-20.
8. **글로벌 테이블**: 두 리전에서 쓰기하며 어느 리전에서든 최신 값을 강한 일관성으로 읽어야 함. → **MRSC 모드 글로벌 테이블**(생성 시 선택). 근거 F-08.
