## 핵심 개념

### 컨테이너 기반 데이터 처리 최적화 (Skill 1.2.1)

**무엇·왜.** Fargate 태스크는 CPU·메모리를 태스크 수준에서 지정해 실행하고 [S1], EMR on EKS는 Spark 작업을 클러스터 프로비저닝 없이 EKS에 제출하는 배포 옵션이다 [S5]. 아래는 컨테이너 처리에서 조정할 수 있는 레버(크기·시작 시간·Spot·스케일링·오케스트레이터 선택)를 공식 문서 근거와 함께 정리한 것이다. 이 Skill이 시험에서 정확히 어디까지 묻는지는 공식 근거로 확정하지 못했다(gaps G-1.2-10).

**동작 원리·선택 기준**
- **크기**: Fargate 태스크 정의는 CPU와 메모리를 태스크 수준에서 지정해야 하고, 허용 조합은 표로 고정돼 있다(예: 0.25 vCPU는 0.5~2 GB, 32 vCPU는 60·120·244 GB 중 하나) [S1].
- **이미지 시작 시간**: Seekable OCI(SOCI) 인덱스가 있으면 이미지를 지연 로딩해 몇 초 만에 컨테이너가 시작되고, 인덱스가 없으면 이미지를 모두 내려받은 뒤 시작한다 [S1].
- **Spot**: Fargate Spot은 중단을 견디는 태스크용이다. 중단 2분 전에 EventBridge 이벤트와 SIGTERM이 전달되므로 컨테이너가 SIGTERM을 받아 정리 작업을 해야 하며(`stopTimeout`으로 정리 시간을 확보), 그러지 않으면 SIGKILL을 받아 데이터가 손상될 수 있다. Spot 용량이 없을 때는 On-Demand로 자동 대체되지 않고 서비스가 용량이 생길 때까지 재시도한다 [S2].
- **스케일링**: SQS 큐를 소비하는 ECS 서비스는 "태스크당 백로그(backlog per task)" 지표로 target tracking 정책을 걸어 스케일링한다 [S3].
- **ECS vs EKS**: ECS는 AWS 네이티브 컨테이너 오케스트레이션 서비스, EKS는 관리형 Kubernetes 서비스다 [S4].
- **EMR on EKS**: EKS 위에서 Spark 작업을 온디맨드로 제출하고, 다른 Kubernetes 애플리케이션과 같은 EKS 클러스터를 공유해 자원 활용률을 높인다. 한 EKS 클러스터에서 서로 다른 Spark 버전·구성의 애플리케이션을 함께 돌릴 수 있다 [S5].
- **AWS Batch와의 관계**: ETL에는 Glue를 우선 검토하고, 그 밖의 배치 지향 사용 사례(일부 ETL 포함)는 AWS Batch가 더 맞을 수 있다 [S16].

|---|---|---|---|

### JDBC·ODBC 연결과 연결 풀링 (Skill 1.2.2)

**무엇·왜.** JDBC·ODBC는 데이터베이스·웨어하우스에 SQL로 접속하는 표준 드라이버 방식이다. 아래는 이 연결과 관련해 공식 문서에서 확인되는 구성 요건이다.

**동작 원리·제약**
- **Glue → VPC 안의 JDBC**: Glue는 VPC 안의 JDBC 데이터 스토어에 접속할 때 내 계정에 탄력적 네트워크 인터페이스(ENI)를 만든다. 보안 그룹에는 모든 TCP 포트에 대한 자기참조 인바운드 규칙이 있어야 Glue 구성 요소끼리 통신한다. ENI에는 퍼블릭 IP가 없으므로 인터넷(또는 VPC 엔드포인트가 없는 AWS 서비스) 접근에는 NAT 인스턴스/게이트웨이가 필요하고, 인터넷 게이트웨이를 서브넷 라우트로 직접 쓸 수 없다 [S7].
- **JDBC 병렬 읽기(Glue)**: 테이블 속성이나 `create_dynamic_frame_from_options`/`from_catalog` 옵션에서 `hashfield`(값이 고르게 분포한 컬럼) 또는 `hashexpression`(정수를 반환하는 SQL 식)으로 논리 파티션을 나누고 `hashpartitions`로 병렬 쿼리 수를 정한다. 미지정이면 7이며, 이 속성은 Redshift·S3 테이블에는 무시된다 [S6].
- **Athena ODBC**: ODBC 1.x 드라이버는 쿼리 결과를 스트리밍하는 포트 444를 아웃바운드로 열어야 하고(PrivateLink 엔드포인트를 쓰면 그 보안 그룹도 444 인바운드 허용), 드라이버를 쓰는 IAM 주체에 `athena:GetQueryResultsStream` 권한이 필요하다. 이 권한은 API로 직접 노출되지 않고 ODBC·JDBC 드라이버의 결과 스트리밍에만 쓰인다 [S8].
- **연결 풀링 — RDS Proxy**: 풀링은 연결을 열고 닫는 오버헤드를 줄인다. 멀티플렉싱은 트랜잭션 단위로 DB 연결을 재사용해서, 클라이언트가 프록시에 많은 연결을 열어도 프록시는 DB로 더 적은 연결만 유지한다 [S9].

### 여러 소스 통합 — 페더레이션·Spectrum·Zero-ETL·AppFlow·Glue (Skill 1.2.3)

**무엇·왜.** 여러 소스를 하나의 분석 흐름에 묶는 방식은 "옮기지 않고 제자리에서 조회(Athena/Redshift 페더레이션, Spectrum)"와 "복제·전송으로 한곳에 모음(Zero-ETL, AppFlow, Glue ETL)"으로 나뉜다.

**동작 원리·제약**
- **Athena Federated Query**: S3가 아닌 소스를 제자리에서 쿼리하거나, 여러 소스에서 추출해 S3에 저장하는 파이프라인에 쓴다. 커넥터가 읽을 데이터를 판단하고 병렬성을 관리하며 필터 조건을 푸시다운한다 [S10]. Lambda 기반 커넥터는 내 계정의 Lambda를 호출하므로 Lambda 요금이 따로 붙는다 [S21]. 2026-04-21부터는 일부 신규 커넥터가 Glue Data Catalog로 자동 등록되어 내 계정의 Lambda를 쓰지 않는다 [S10].
- **Redshift Federated Query**: RDS/Aurora(PostgreSQL·MySQL)의 라이브 데이터를 Redshift 쿼리에서 직접 조회한다. 연산 일부를 원격 DB로 푸시다운해 네트워크 이동량을 줄인다 [S11].
- **Redshift Spectrum**: S3에 있는 데이터를 Redshift에서 직접 쿼리하며, 스캔한 바이트만큼 과금된다 [S27].
- **Zero-ETL**: 소스에서 Redshift로 복제 생성·관리를 자동화하는 완전관리형 통합이다. 지원 소스는 Aurora MySQL/PostgreSQL, DynamoDB, RDS for MySQL/Oracle/PostgreSQL, Oracle Database@AWS, SaaS 애플리케이션(Salesforce, SAP, ServiceNow, Zendesk 등), 자체 관리 DB(MySQL, PostgreSQL, SQL Server, Oracle)다 [S12]. 제약: 소스 테이블에 기본 키가 있어야 하고, 애플리케이션 소스는 최소 지연이 1시간이며, 값이 Redshift VARCHAR 한도(65,535바이트)를 넘으면 해당 테이블이 실패 상태가 된다(`TRUNCATECOLUMNS`로 잘라내기 가능) [S13].
- **AppFlow**: Salesforce 같은 SaaS와 S3·Redshift 등 AWS 서비스 사이에서 데이터를 안전하게 주고받는 완전관리형 통합 서비스로, 코드 없이 몇 분 안에 플로를 만든다 [S14].
- **Glue ETL(DynamicFrame)**: DataFrame은 스키마를 먼저 지정해야 하지만, DynamicFrame은 레코드가 자기기술적이라 스키마가 필요 없다. 같은 필드의 타입이 레코드마다 다른 스키마 불일치는 choice(union) 타입으로 표현했다가 `resolveChoice`로 해소해 고정 스키마 저장소에 맞춘다 [S15].

### 변환 서비스 선택 — Glue·EMR·Lambda·Redshift·Athena (Skill 1.2.5)

**무엇·왜.** 변환 엔진은 데이터 규모, 실행 시간, 필요한 프레임워크·통제 수준, 운영 부담으로 고른다. 공식 문서가 직접 제시하는 선택 기준은 다음과 같다.
- 배치 ETL에는 Glue 또는 EMR을 쓴다 [S22]. Glue는 Apache Spark 위에서 변환 잡을 스케일아웃하는 서버리스 환경이고, EMR은 Hadoop 환경에 직접 접근하게 해 Spark 밖의 도구까지 쓸 수 있는 하위 수준 접근과 유연성을 준다 [S16].
- Lambda는 S3·Kinesis 같은 이벤트로 트리거되는 변환에 쓸 수 있지만 함수당 900초 안에 끝나야 한다. 더 오래 걸리는 작업은 EC2·EKS·ECS를 권장하거나 Step Functions로 나눈다 [S20].
- Athena는 SQL로 S3 데이터를 변환할 수 있으나(CTAS·INSERT INTO·UNLOAD) 매우 큰 데이터셋의 ETL은 EMR/Glue를 쓰라고 안내한다 [S21][S32].
- Redshift는 데이터를 먼저 적재하고 웨어하우스 안에서 변환하는 ELT에 자주 쓰인다 [S22]. 참고로 Redshift Python UDF는 2026-06-30 이후 지원이 중단된다 [S51].

**Glue 작업 유형·버전(현행)**
- **Spark 잡**은 Python/Scala로 작성하며 여러 워커 노드로 수평 확장해 큰 데이터셋을 처리한다. **Streaming 잡**은 Spark Structured Streaming 마이크로배치로 exactly-once를 제공한다. **Python shell 잡**은 단일 머신에서 기본 ETL 스크립트를 돌리며 소·중규모(약 10 GB까지) 데이터에 맞다 [S19]. **Ray 잡**은 2026-04-30부터 신규 고객에게 닫혔고(기존 고객은 계속 사용, 신규 기능 없음) 대안으로 EKS + KubeRay를 안내한다 [S18].
- **버전**: 현재 최신은 Glue 6.0(Spark 4.1.1, Python 3.13)이며 Iceberg 최신 포맷 버전, Spark Declarative Pipelines, 실시간 모드 등이 추가됐다. 버전을 지정하지 않고 만든 잡은 5.1로 생성된다. Glue 1.0·2.0은 2026-04-01에 수명이 종료됐다 [S17][S25].
- **EMR 배포 옵션**: EC2는 구성에 대한 최대 통제·유연성이 필요할 때, EKS는 EKS로 클러스터를 표준화하거나 한 클러스터에서 프레임워크 버전을 달리 쓸 때, Serverless는 클러스터를 관리·운영하고 싶지 않을 때 적합하다. EMR Serverless는 자원을 자동으로 늘리고 줄이며 쓴 만큼만 낸다 [S23].

### 데이터 처리 비용 최적화 (Skill 1.2.4)

**무엇·왜.** 비용은 "얼마나 큰 자원을 얼마나 오래, 어떤 구매 방식으로 쓰는가"와 "처리·스캔하는 데이터가 얼마나 작은가"로 갈린다. 서비스별 레버는 다음과 같다.

**Glue**
- 과금: DPU-시간 기준으로 초 단위 올림, Glue 2.0 이상은 최소 1분이다 [S27]. 1 DPU는 4 vCPU·16 GB다 [S24].
- 워커 선택: 대부분의 워크로드는 G.1X·G.2X로 시작하고, 메모리 부족(OOM)이 잦으면 같은 크기 대비 메모리가 2배인 R 워커를 쓴다. G.12X·G.16X·R 워커는 시작 지연이 있을 수 있다 [S24].
- Auto Scaling: Glue 3.0 이상에서 "워커 수 자동 조절"을 켜고 최대 워커 수를 지정하면 Glue가 서버리스 컴퓨팅 자원을 자동으로 늘리고 줄여 비용을 낮춘다 [S26].
- Flex 실행 클래스: 시작·완료 시각이 달라도 되는 시간 비민감 잡에서 최대 35%를 절감한다. Glue 3.0 이상, Spark(glueetl) 잡만 가능하다 [S16][S25].
- 타임아웃: 잡별 Timeout을 지정할 수 있고, 비워 두면 Glue 4.0 이하는 2,880분, 5.0 이상은 480분이 기본이다 [S25].

**EMR**
- 장기 클러스터: core 노드(HDFS 보유)는 On-Demand, task 노드는 Spot으로 둔다. core를 Spot으로 두면 노드가 갑자기 사라질 때 성능 저하나 데이터 손실이 생길 수 있다 [S30].
- 인스턴스 플릿: 기본 설정은 플릿당 인스턴스 타입 5개, 할당 전략을 쓰면 30개까지 지정할 수 있고 더 빠른 프로비저닝·정확한 Spot 할당·적은 Spot 중단을 위해 할당 전략을 권장한다 [S29].
- Managed Scaling: 최소·최대 용량을 정하면 클러스터 크기를 자동 조절하고, core 상한과 On-Demand 상한 파라미터로 core/task, On-Demand/Spot 배분을 제어한다 [S30].
- Serverless: 쓴 만큼만 내며, 사전 초기화(pre-initialized) 워커는 유휴에도 비용이 든다 [S23][S28].
- Graviton: Spark에서 이전 세대 인스턴스 대비 추가 비용 절감(최대 30%)과 성능 향상을 제공한다 [S27].

**Lambda**
- CPU는 메모리에 비례해 할당되므로 메모리가 성능의 핵심 레버이고, 128 MB가 기본이자 최저값이라 단순한 이벤트 라우팅·변환에만 권장된다 [S31].
- 적정 메모리는 AWS Lambda Power Tuning(Step Functions로 여러 메모리 설정을 동시에 측정) 또는 Compute Optimizer 권장으로 찾는다. Compute Optimizer는 x86_64 함수만 지원한다 [S31].

**Athena·Redshift Spectrum**
- 스캔한 바이트로 과금되며(최소 10 MB), 압축·파티셔닝·컬럼형 변환으로 쿼리당 비용을 30~90% 줄일 수 있다 [S21]. 파일은 대략 128MB를 넘거나 분할 가능해야 효율적이고, 텍스트는 BZIP2·LZO만 분할 가능하다 [S27].
- Spectrum도 스캔한 바이트만 과금한다 [S27].

### 형식 변환 — CSV에서 Parquet로 (Skill 1.2.6)

**무엇·왜.** CSV/JSON 같은 텍스트 원본을 Parquet·ORC 같은 컬럼형으로 바꾸면 Athena가 필요한 컬럼만 읽어 스캔량과 비용이 줄어든다 [S21]. 변환 수단은 크게 네 가지다.

1. **Athena CTAS**: 한 문장에서 파티셔닝·압축·컬럼형 변환을 하고, 만들어진 테이블·파티션이 Glue Data Catalog에 자동 추가된다 [S32]. 쿼리당 파티션 100개 한도가 있어 더 많이 만들려면 CTAS 후 INSERT INTO를 나눠 실행한다 [S33].
2. **Athena UNLOAD**: SELECT 결과를 Parquet·ORC·Avro·JSON 파일로 쓰되 테이블은 만들지 않는다. 반면 CTAS는 테이블 생성이 필요하다 [S34].
3. **Glue/EMR의 Spark 잡**: 매우 큰 데이터셋의 ETL은 Athena보다 EMR/Glue가 맡는다 [S21][S22].
4. **Firehose 형식 변환**: JSON 입력을 Parquet/ORC로 바꿔 S3에 저장한다. CSV 같은 다른 입력은 Lambda 변환으로 먼저 JSON으로 만든다. Glue Data Catalog 스키마가 필요하고, JSON 문서를 배열로 묶은 입력은 유효하지 않다 [S35].

| 형식 | 저장 방식 | 적합한 경우 | 제약·특성 | 시험 단서 키워드 |
|---|---|---|---|---|
| CSV/JSON(텍스트) | 행 기반 텍스트(원본 형태) | 원천 수집 데이터 | 텍스트는 BZIP2·LZO 압축만 분할 가능하고, 분할 가능한 파일만 병렬로 읽힌다 [S27] | "원본", "gzip 단일 파일" |
| Parquet / ORC | 컬럼형 | 읽기가 잦은 분석 [S27] | 필요한 컬럼만 읽어 스캔량 감소 [S21], 압축 코덱과 무관하게 분할 가능 [S27] | "분석 쿼리", "스캔량·비용 감소" |
| Avro | 행 기반 | 쓰기가 잦은 워크로드 [S27] | Parquet/ORC보다 압축 효율이 낮음 [S27] | "쓰기 빈번", "행 기반" |

### 변환 실패·성능 문제 해결 (Skill 1.2.7)

**무엇·왜.** 증상에 맞는 원인과 조치를 짝짓는 영역이다. 공식 문서에서 확인되는 짝은 다음과 같다.

- **작은 파일이 너무 많아 Glue Spark가 불안정**: 입력 파일을 묶어 하나의 인메모리 파티션으로 읽는 `groupFiles`(`inPartition`)·`groupSize` 옵션이 작은 파일이 많을 때 특히 유용하다. 파일이 50,000개를 넘으면 Glue가 자동으로 그룹화한다 [S36].
- **메모리 부족(OOM)**: OOM이 잦거나 캐싱·셔플·집계가 많은 워크로드에는 같은 크기 대비 메모리가 2배인 R 워커를 쓴다 [S24].
- **데이터 스큐(일부 태스크만 오래 걸림)**: 단일 만능 해법은 없다. Glue 4.0은 AQE(Adaptive Query Execution)를 기본 활성화하고, 스큐 키를 따로 분리 처리(filter and perform)하거나, 키에 난수 접두사를 붙이는 솔팅, 작은 테이블을 브로드캐스트하는 조인(자동 브로드캐스트 임계 기본 10 MB)을 쓴다 [S37].
- **DPU(용량) 부족 판단**: Glue 잡 지표의 "maximum needed executors"(실행 중+대기 태스크 합 ÷ executor당 태스크)와 실제 할당 executor를 비교해 부족 비율을 계산한다 [S38].
- **로그·원인 분석**: Glue 4.0 이하는 continuous logging 옵션으로 실행 중 CloudWatch 로그를 보고, 5.0부터는 모든 잡이 실시간 로깅 기능을 갖는다 [S39]. Job run insights는 실패한 스크립트 줄 번호, 마지막 Spark action, 예외 이벤트, 근본 원인 분석과 권장 조치를 제공한다 [S40]. Spark UI와 CloudWatch 로그·지표로도 잡을 모니터링한다 [S40].
- **동시 실행/DPU/IP 한도**: 잡의 `MaxConcurrentRuns` 기본값은 1이고 초과하면 오류가 반환된다 [S42]. 계정 동시 실행·DPU 한도나 VPC IP 고갈로 실패하던 실행은 잡 큐잉을 켜면 Waiting 상태로 두었다가 재시도한다 [S41].
- **JDBC 연결 실패**: 보안 그룹의 자기참조 규칙과 NAT 경로를 점검한다 [S7].
- **EMR 로그 위치**: 기본으로 모든 노드의 `/mnt/var/log/`에 기록되고, 단계(step) 로그는 주 노드의 `/mnt/var/log/hadoop/steps/` 아래 단계별 하위 디렉터리에 쌓인다. EMR 6.9.0 이상은 클러스터 스케일다운 시 로그를 S3로 보관한다 [S43].
- **Lambda 시간초과·메모리**: 함수당 900초를 넘는 작업은 EC2·EKS·ECS로 옮기거나 Step Functions로 나눈다 [S20]. CPU·네트워크·메모리 바운드 함수는 메모리를 올리면 성능이 크게 개선될 수 있고, CloudWatch로 메모리 소비가 설정값에 근접하는지 감시한다 [S31].
- **Athena CTAS 파티션 한도**: `HIVE_TOO_MANY_OPEN_PARTITIONS` 오류는 CTAS가 파티션을 100개 넘게 만들 때 나며, CTAS + 100개씩 나눈 INSERT INTO로 우회한다 [S33].
- **스키마 불일치**: Glue는 DynamicFrame의 choice 타입과 `resolveChoice`로 처리한다 [S15]. Firehose 형식 변환은 Glue 카탈로그 스키마가 입력 구조와 맞아야 하며, 아니면 스키마에 없는 속성이 변환 결과에서 빠진다 [S35]. Zero-ETL은 값이 VARCHAR 한도를 넘으면 해당 테이블이 실패 상태가 된다 [S13].

### 데이터 API 만들기 (Skill 1.2.8)

**무엇·왜.** 다른 시스템이 HTTP로 데이터를 가져가게 하는 방법은 (a) API Gateway가 서비스를 직접 호출, (b) API Gateway/Lambda 뒤에서 Athena·Redshift 쿼리, (c) 서비스 자체 Data API(Redshift Data API)로 나뉜다.

- **API Gateway → DynamoDB 직접 통합**: REST API가 DynamoDB API와 직접 통합해 PutItem·Query 같은 작업을 코드 없이 노출하고, IAM 역할로 특정 테이블·인덱스 접근 권한을 준다 [S48].
- **Redshift Data API**: 비동기 API라 오래 걸리는 쿼리를 기다리지 않고 실행하고, 쿼리 ID로 상태와 결과를 확인한다 [S45]. 자격증명은 IAM 임시 자격증명 또는 Secrets Manager 비밀 두 가지이며, Lambda에서 쓸 때 함수를 VPC에 넣을 필요가 없다 [S45]. 한도: 쿼리 최대 24시간, 클러스터당 활성 쿼리 500개, 결과 500 MB(gzip 후), 결과 보존 24시간 [S44].
- **Athena 비동기 호출 패턴**: 쿼리를 시작(`start_query_execution`)한 뒤 Step Functions로 실행 상태를 폴링하고, 완료되면 Lambda가 결과의 presigned S3 URL을 만들어 돌려준다 [S47].
- **API Gateway 통합 타임아웃**: 기본 29초이고, 이를 넘기려면 서비스 쿼터 상향 요청이 필요하며 Regional·private REST API에서만 가능하다. 그래서 오래 걸리는 쿼리는 동기 응답 대신 비동기 시작 + 폴링/콜백으로 설계한다 [S46][S47].

### 데이터의 3V와 정형·반정형·비정형 (Skill 1.2.9)

**무엇·왜.** 빅데이터는 늘어나는 볼륨·속도·다양성 때문에 기존 데이터베이스로는 풀 수 없는 데이터 관리 문제로 설명되며, 이 세 요소가 서비스 선택을 가른다 [S49].
- **Volume(볼륨)**: 테라바이트에서 페타바이트 규모 [S49].
- **Velocity(속도)**: 데이터 생성부터 실행 가능한 인사이트 전달까지 수집·저장·처리·분석이 일 단위에서 실시간까지의 짧은 창 안에서 이뤄져야 한다는 요구 [S49].
- **Variety(다양성)**: 웹 로그, 소셜 미디어, 전자상거래·금융 거래 등 다양한 소스와 형식 [S49].
- **정형**은 미리 정의된 규칙(스키마)을 따르는 데이터로, 웨어하우스가 정형 데이터 저장에 가장 흔히 쓰인다. **비정형**은 정해진 데이터 모델이 없는 데이터(텍스트 문서, 이미지, 오디오, 비디오 등)이며 데이터 레이크가 원시·비정형 데이터를 대규모로 저장한다. **반정형**은 관계형·표 모델은 없지만 태그·메타데이터·중첩 같은 자기기술 요소가 있는 데이터(JSON, XML, HTML 등)다 [S50].

**서비스 선택에 미치는 영향(문서에서 확인되는 연결만)**
- 볼륨↑ → Spark로 스케일아웃하는 분산 처리(Glue, EMR) [S16].
- 속도↑ → 스트리밍 처리: Glue Streaming(마이크로배치, exactly-once) [S19].
- 다양성↑·반정형 → 스키마 불일치를 choice 타입으로 흡수하는 DynamicFrame [S15], Redshift는 JSON·Avro·Ion 같은 반정형 데이터를 정형 데이터와 함께 쿼리 [S51].
- 정형 → 웨어하우스(Redshift), 원시·비정형 → 데이터 레이크(S3) [S50]. 비정형 문서·이미지·오디오·비디오에서 정보를 뽑는 단계에는 생성형 AI 추출을 포함하는 Bedrock Data Automation을 쓴다 [S59].

### LLM으로 데이터 처리하기 — Amazon Bedrock (Skill 1.2.10, v1.1 신규)

**무엇·왜.** 파이프라인 안에서 텍스트를 번역·요약·생성·분류·감성 분석하거나 임베딩을 만드는 단계에 파운데이션 모델(FM) 호출을 끼워 넣는 영역이다 [S58][S54]. Amazon Bedrock은 모델 호출 API(Converse·InvokeModel), 배치 추론, 문서 추출(Data Automation), 다른 서비스와의 통합을 제공한다.

**호출 방식**
- **Converse**: 메시지를 지원하는 모든 모델에 일관된 인터페이스를 제공해 코드를 한 번 쓰고 모델을 바꿔 쓸 수 있으며, 모델 고유 파라미터는 추가로 전달할 수 있다 [S52].
- **InvokeModel**: 모델 고유(native) 요청 형식을 쓴다. 배치 추론의 입력은 InvokeModel 또는 Converse 형식 중에서 고르고, 배치에서 tool calling이 필요하면 InvokeModel 유형을 써야 한다(Converse 유형에서 `toolConfig`가 있는 레코드는 400 오류) [S53].
- **데이터 취급**: Bedrock은 입력 콘텐츠를 저장하지 않고 응답 생성에만 쓴다 [S52]. 데이터를 모델 제공자와 공유하지 않고 파운데이션 모델 학습에도 쓰지 않는다 [S60].

**배치 추론**: 여러 프롬프트를 파일로 S3에 올려 제출하면 비동기로 처리해 결과를 S3에 쓴다. 완료·상태 변경은 EventBridge로 통지받을 수 있어 폴링이 필요 없다 [S53]. 선택된 모델에서 On-Demand 추론 대비 50% 낮은 가격이며 [S54], 프로비저닝된 모델에는 지원되지 않는다 [S53].

**쿼터·쓰로틀링·비용**
- bedrock-runtime 엔드포인트의 모델별 토큰 쿼터는 분당 토큰(입력+출력 합산)으로 계산되고, 출력 토큰은 모델별 burndown rate로 환산돼 차감된다 [S61].
- 계정 쿼터를 넘으면 ThrottlingException이 발생한다. 지수 백오프(+랜덤 지터) 재시도가 권장되고, 예측 가능한 지속 처리량이 필요하면 Reserved Tier 또는 Provisioned Throughput을 고려한다 [S55].
- On-Demand 과금은 텍스트 생성 모델이 입력·출력 토큰 모두, 임베딩 모델은 입력 토큰만 대상이다. Provisioned Throughput은 시간당 과금에 1개월·6개월 약정 옵션이 있고, 커스터마이징한 모델을 쓰려면 반드시 구매해야 한다 [S54].

**ETL 통합 지점(공식 문서로 확인되는 것만)**
- **Lambda**: Step Functions 최적화 통합이 나오기 전에는 워크플로에서 Bedrock을 쓰려면 Lambda 함수를 호출해야 했다 [S56].
- **Step Functions**: InvokeModel(텍스트·이미지·임베딩 모델) 및 CreateModelCustomizationJob(파인튜닝) 최적화 통합 [S56].
- **Redshift ML**: `CREATE EXTERNAL MODEL`로 Bedrock 모델을 가리키면 연결된 SQL 함수로 번역·요약·분류·감성 분석 등을 호출한다. 모델 학습·프로비저닝이 필요 없다 [S57][S58].
- **Bedrock Data Automation(BDA)**: 오디오·비디오·이미지·문서에서 정보를 추출하며, 문서·이미지는 blueprint로 추출할 정보를 정의하는 custom output을 쓴다 [S59].
- Athena·Glue에서 Bedrock을 네이티브로 호출하는 기능은 공식 문서에서 확인하지 못했다(gaps G-1.2-08).

## 흔한 함정·혼동 짝

1. **Glue vs EMR** — Glue는 Spark 위의 서버리스 스케일아웃 ETL, EMR은 Hadoop 환경에 직접 접근해 Spark 밖의 도구까지 쓰는 유연성 → 시험 단서: "서버 관리 없이 ETL"=Glue / "Spark 외 도구·하위 수준 접근"=EMR [S16]
2. **EMR on EC2 vs EMR on EKS vs EMR Serverless** — 최대 통제·유연성 / EKS 표준화·한 클러스터 다중 버전 / 클러스터 관리 회피 → 시험 단서: "커스텀 통제", "기존 EKS", "클러스터를 운영하고 싶지 않다" [S23]
3. **Glue Spark vs Glue Python shell vs Lambda** — 분산 Spark / 단일 머신·소·중규모(약 10 GB) / 이벤트 기반·함수당 900초 → 시험 단서: "수 TB", "작은 스크립트", "15분 이내" [S19][S20]
4. **Glue Flex vs Glue Auto Scaling** — Flex는 시간 비민감 잡용 실행 클래스(Glue 3.0+ Spark, 최대 35% 절감), Auto Scaling은 워커 수를 최대치 안에서 자동 조절(Glue 3.0+) → 시험 단서: "지연 허용·비긴급"=Flex / "부하 변동"=Auto Scaling [S16][S25][S26]
5. **EMR core 노드 vs task 노드** — core는 HDFS를 가지므로 On-Demand, Spot은 task 노드에 → 시험 단서: "Spot 회수 시 데이터 손실" [S30]
6. **Fargate vs Fargate Spot** — Spot은 2분 경고 후 중단되고 On-Demand로 자동 대체되지 않음 → 시험 단서: "중단 허용 배치", "SIGTERM" [S2]
7. **Athena CTAS vs INSERT INTO vs UNLOAD** — CTAS는 새 테이블을 만들며 형식·파티션·압축을 한 번에 지정(Glue 카탈로그 자동 등록), INSERT INTO는 기존 대상 테이블에 적재, UNLOAD는 테이블 없이 파일만 출력 → CTAS·INSERT INTO는 쿼리당 100 파티션 한도 → 시험 단서: "테이블 없이 Parquet/JSON 파일", "HIVE_TOO_MANY_OPEN_PARTITIONS" [S32][S33][S34]
8. **Firehose 형식 변환 vs Glue/Athena 변환** — Firehose는 JSON 입력만 Parquet/ORC로 바꾸고(CSV는 Lambda로 JSON 선변환) Glue Data Catalog 스키마가 필요하다. 이미 쌓인 S3 데이터는 CTAS 또는 Spark 잡으로 변환 → 시험 단서: "스트림 적재 시점 변환", "CSV 입력" [S35][S32]
9. **Parquet/ORC vs Avro vs 텍스트(CSV/JSON)** — 컬럼형·읽기 중심 / 행 기반·쓰기 빈번 / 텍스트는 BZIP2·LZO만 분할 가능 → 시험 단서: "분석 쿼리 스캔량 감소", "gzip 단일 파일" [S27]
10. **Athena Federated Query vs Redshift Federated Query vs Redshift Spectrum** — 임의 소스 커넥터 / RDS·Aurora(PostgreSQL·MySQL) / S3 → 시험 단서: "S3 외 소스", "운영 DB 라이브 조회", "S3 외부 테이블" [S10][S11][S27]
11. **Zero-ETL vs Federated Query vs AppFlow** — 복제를 자동 관리 / 제자리 조회 / SaaS↔AWS 코드 없는 전송 → 시험 단서: "파이프라인 없이 복제", "데이터 이동 없이 조회", "Salesforce 노코드" [S12][S10][S14]
12. **Zero-ETL 제약** — 소스 테이블 기본 키 필수, 앱 소스 최소 지연 1시간, 값이 VARCHAR 65,535바이트를 넘으면 테이블 실패 → 시험 단서: "기본 키 없는 테이블", "SaaS 소스인데 분 단위 지연 요구" [S13]
13. **DynamicFrame vs DataFrame** — 자기기술적(스키마 불필요, choice 타입으로 불일치 표현) vs 스키마 선요구 → 시험 단서: "같은 필드 타입이 레코드마다 다름", "resolveChoice" [S15]
14. **groupFiles vs R 워커(메모리 상향)** — 작은 파일 폭증은 파일 그룹화, 캐싱·셔플·집계 같은 메모리 집약 OOM은 R 워커 → 시험 단서: "수백만 개의 작은 파일" vs "메모리 집약 연산 OOM" [S36][S24]
15. **데이터 스큐 vs 작은 파일 증상** — 스큐는 일부 태스크만 오래 걸림(AQE·솔팅·브로드캐스트), 작은 파일은 태스크 과다(그룹화) → 시험 단서: "일부 파티션만 느림" [S37][S36]
16. **continuous logging(4.0 이하 옵션) vs 5.0+ 기본 실시간 로깅 vs Job run insights** — 실행 중 CloudWatch 로그 vs 실패 줄 번호·근본 원인 요약 → 시험 단서: "실행 중 로그 확인", "실패한 스크립트 줄 번호" [S39][S40]
17. **MaxConcurrentRuns(기본 1) vs 잡 큐잉** — 한도 초과 시 오류 vs Waiting 후 재시도(최대 15분/10회, VPC IP 고갈도 포함) → 시험 단서: "ConcurrentRunsExceededException", "동시 실행 한도" [S42][S41]
18. **Redshift Data API vs JDBC/ODBC 직접 연결** — Data API는 비동기이며 쿼리 ID로 결과를 조회하고 IAM 임시 자격증명 또는 Secrets Manager를 쓰며 Lambda를 VPC에 넣을 필요가 없다 → 시험 단서: "연결 관리 없이", "Lambda에서 Redshift 호출" [S45][S44]
19. **API Gateway 29초 vs Lambda 900초 vs Athena 장시간 쿼리** — 동기 통합 타임아웃은 기본 29초이므로 긴 쿼리는 비동기 시작 + 폴링 → 시험 단서: "API가 타임아웃", "긴 쿼리를 API로 노출" [S46][S20][S47]
20. **RDS Proxy vs Glue JDBC 연결(VPC ENI)** — 연결 수 폭주를 풀링·멀티플렉싱으로 흡수 vs 네트워크 경로(ENI·보안 그룹·NAT) → 시험 단서: "too many connections" vs "VPC 안 DB 연결 실패" [S9][S7]
21. **Athena ODBC 드라이버 포트 444** — 결과 스트리밍 포트 444 아웃바운드와 `GetQueryResultsStream` 권한이 필요(일반 쿼리 API로는 노출되지 않는 권한) → 시험 단서: "ODBC 드라이버", "포트 444" [S8]
22. **Converse vs InvokeModel** — 모델과 무관한 일관된 인터페이스 vs 모델 고유 형식(배치에서 tool calling은 InvokeModel 유형) → 시험 단서: "모델 교체", "배치 + tool calling" [S52][S53]
23. **On-Demand vs 배치 추론 vs Provisioned Throughput** — 토큰 과금 / On-Demand 대비 50% 낮은 가격·비동기·프로비저닝 모델 미지원 / 시간당 과금·1·6개월 약정·커스텀 모델 필수 → 시험 단서: "지연 허용 대량", "쓰로틀링 회피", "커스텀 모델" [S53][S54]
24. **Bedrock Data Automation vs 범용 모델 호출(Converse/InvokeModel)** — BDA는 문서·이미지·오디오·비디오에서 표준/커스텀(blueprint) 출력으로 정보를 추출하는 기능 → 시험 단서: "PDF·이미지에서 필드 추출" [S59][S52]
25. **Redshift ML 외부 모델 vs Step Functions 통합 vs Lambda 경유** — SQL 함수로 호출 / 워크플로 태스크로 호출 / 함수 코드에서 호출 → 시험 단서: "SQL에서 LLM", "오케스트레이션", "Lambda" [S57][S56]
26. **정형(웨어하우스) vs 비정형(데이터 레이크) vs 반정형** — 정형은 미리 정의된 스키마, 비정형은 정해진 데이터 모델 없음, 반정형은 JSON·XML처럼 자기기술 요소 → 시험 단서: "JSON 로그", "문서·이미지" [S50][S51]
27. **Glue 버전·종료 혼동** — 최신 6.0, 버전 미지정 시 5.1, 1.0·2.0은 2026-04-01 종료, Glue for Ray는 2026-04-30부터 신규 고객 중단 → 시험 단서: "Glue 2.0 사용 중", "Ray 잡" [S17][S25][S18]
28. **Redshift ELT vs Glue ETL** — 적재 후 웨어하우스 안에서 SQL로 변환 vs 외부 엔진에서 변환 후 적재(배치 ETL은 Glue 또는 EMR) → 시험 단서: "적재 후 변환", "웨어하우스가 충분히 강력" [S22]

### 후보 1 — Skill 1.2.5 · associate
- **문제**: 하루 한 번 새벽에 약 1시간 동안만 실행되는 Apache Spark 변환 잡이 있다. 팀은 이미 작성한 Spark 코드를 그대로 쓰면서 클러스터를 구성·운영하는 부담 없이 사용한 만큼만 비용을 내길 원한다. 가장 적합한 선택은?
- **보기**: A. 상시 실행되는 Amazon EMR on EC2 클러스터 / B. Amazon EMR Serverless 애플리케이션 / C. 하나의 AWS Lambda 함수로 전체 변환 실행 / D. 새 EKS 클러스터를 구축해 Amazon EMR on EKS 사용
- **정답**: B
- **해설 초안**: EMR Serverless는 클러스터를 관리·운영하고 싶지 않은 고객에게 맞는 배포 옵션이고 자원을 자동으로 늘리고 줄이며 쓴 만큼만 비용을 낸다 [S23].
- **오답 근거**: A — EC2는 구성에 대한 최대 통제·유연성이 필요한 경우용이다 [S23] / C — Lambda 함수는 900초 안에 끝나야 한다 [S20] / D — EMR on EKS는 EKS로 클러스터를 표준화하려는 경우에 맞는다 [S23]
