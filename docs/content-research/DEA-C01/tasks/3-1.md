## 핵심 개념

### 이 문서의 범위와 1-3.md와의 분담 (Skill 3.1.1)

Task 3.1은 "이미 고른 서비스를 운영·자동화·문제 해결하는 관점"이다. 오케스트레이터를 고르는 비교 표(Step Functions vs MWAA vs EventBridge vs Glue 워크플로 vs Lambda), Standard/Express 선택, Retry/Catch/Redrive, SNS·SQS 알림은 1-3.md에 있고, 이 문서는 운영(업데이트·확장·로그·메트릭), 트러블슈팅, SDK 호출, 서비스 기능으로의 데이터 처리, 데이터 API, 변환 준비, Athena, Lambda 자동화, EventBridge 이벤트·스케줄러를 다룬다.

### MWAA 운영: DAG 배포·확장·업데이트·로그 (Skill 3.1.1, 3.1.2)

- DAG 배포: S3 버킷의 새 객체·변경 객체가 스케줄러·워커 컨테이너의 dags 폴더로 30초마다 동기화된다. 기존 DAG의 변경은 다음 DAG 처리 루프에서 반영된다 [S7].
- 워커 확장: (실행 중 작업 + 대기 작업) ÷ 워커당 작업 수 = 필요한 워커 수이고, 필요량이 현재보다 크면 Fargate 워커를 최대 워커 수까지 늘린다 [S4]. 콘솔에서 지정할 수 있는 최대 워커 수 기본 상한은 25이다 [S4]. 축소 중에도 작업을 하던 워커는 끝날 때까지 보호된다 [S4]. 예: mw1.small, 최대 워커 10, 워커당 5개이면 동시 작업 50개이고 나머지는 대기한다 [S4].
- 환경 업데이트의 워커 교체 전략: Forced(기본)는 활성 워커를 즉시 멈춰 실행 중 작업이 실패하고, Graceful은 워커가 최대 12시간 동안 작업을 계속하게 하며 새 작업은 갱신된 워커로 보낸다 [S5]. Graceful을 켜려면 Airflow 2.4.3 이상이어야 하고 기존 환경은 Forced 업데이트를 한 번 거쳐야 한다 [S5]. 환경의 VPC 네트워크는 생성 후 바꿀 수 없다 [S5].
- 로그: 활성화한 로깅 옵션마다 CloudWatch 로그 그룹이 생기며 이름 형식은 airflow-환경이름-로그유형이다. 유형은 DAGProcessing(스케줄러의 DAG 프로세서), Scheduler, Task, WebServer, Worker이다 [S1]. 콘솔에서 먼저 활성화해야 CloudWatch에서 볼 수 있고, 선택한 레벨 이상의 로그가 전송된다 [S1].
- 패키지 설치 로그는 스케줄러 로그 그룹의 requirements_install_ip 로그 스트림에서 확인한다 [S1].

### MWAA 트러블슈팅 (Skill 3.1.2)

스케줄러는 모든 작업과 DAG를 감시하며 의존성이 충족된 작업 인스턴스를 호출하고, 하트비트가 임계값 동안 없으면 비정상으로 본다 [S6]. 헬스 체크 임계값 기본은 30초이고 환경 구성에서 바꿀 수 있다 [S6].

| 증상 | 의심 원인·확인 위치 | 조치 | 근거 |
|---|---|---|---|
| "The scheduler does not seem to be running", DAG 목록 갱신 안 됨 | 메타데이터 DB(Aurora PostgreSQL) 접속용 보안 그룹 규칙, 의존성 설치 실패, 과부하 스케줄러, 깨진 DAG. DB 오류는 스케줄러 장애의 증상일 때가 많다 | 보안 그룹이 TCP 5432(와 HTTPS 443)를 허용하는지 확인, CloudWatch 로그 그룹에서 DAG·플러그인·requirements 점검 | [S2][S3][S6] |
| 작업이 멈추거나 끝나지 않음 | DAG가 너무 많음(환경 용량의 50% 초과 시 스케줄러 과부하, 비활성 DAG도 파싱), 큐에 작업 적체(대기 작업 증가) | DAG 수·동시 실행 작업 줄이기, 작업 시차 배치, 최소 워커 늘리기(update-environment의 min/max workers) | [S2][S4] |
| requirements.txt 업데이트가 20분 넘게 걸림 | 설치 실패로 환경 업데이트가 실패해 마지막 안정 이미지로 롤백 중 | 패키지 버전 고정 확인, 로그 그룹 생성·실행 역할의 CloudWatch/S3 권한 확인 | [S3] |
| 환경이 Creating에서 멈추거나 Create failed | VPC 네트워크: 퍼블릭 라우팅이면 보안 그룹이 자기 참조 규칙 또는 HTTPS 443과 TCP 5432 허용, 프라이빗 라우팅이면 서브넷에 NAT·인터넷 게이트웨이 경로가 없어야 함 | VPC·실행 역할·사용자 권한 점검 | [S3] |
| "No space left on device" | MWAA 컨테이너 저장소는 유한 | --no-cache-dir로 설치하는 시작 스크립트 또는 Python wheel 사용 | [S3] |
| 웹서버 5xx | Airflow 구성 옵션(예: Secrets Manager 설정) 오류, requirements와 Airflow 버전 비호환 | 구성 옵션·requirements 호환성 점검 | [S2] |

- DAG 파싱 부하를 줄이려면 DAG 폴더에 .airflowignore 파일(정규식·glob 패턴)을 두어 DAG가 아닌 파일을 파싱에서 제외한다 [S50]. 새 DAG가 UI에 나타나는 데 걸리는 시간은 scheduler.dag_dir_list_interval 설정이 정한다 [S7].

### Step Functions 운영·트러블슈팅 (Skill 3.1.1, 3.1.2)

- Standard는 실행 이력을 Step Functions에 기록하고, Express는 기록하지 않으므로 이력과 결과를 보려면 CloudWatch Logs 로깅을 구성해야 한다 [S8]. 콘솔에서 만든 Standard는 로깅이 기본 꺼져 있고 Express는 기본으로 켜져 있다 [S8]. 로그 레벨은 ALL·ERROR·FATAL·OFF이다 [S8].
- CloudWatch Logs 전달은 best-effort라 완전성·적시성이 보장되지 않는다. 로그 게시는 실행을 막거나 느리게 하지 않는다 [S8].
- 모든 상태 머신이 실행 메트릭을 내보낸다 [S9]. ExecutionsFailed(실패), ExecutionsTimedOut(어떤 이유로든 타임아웃) 등이 알람 대상이다 [S9].
- 오류 이름으로 원인을 좁힌다. States.DataLimitExceeded는 커넥터·상태의 출력 또는 입력이 페이로드 크기 할당량보다 클 때 발생하고 [S10], Lambda 호출이 최대 호출 수를 넘으면 Lambda.TooManyRequestsException으로 보고된다 [S10]. 프로덕션 코드는 Lambda 서비스 예외를 처리해야 한다 [S10].
- 재시도·Catch·Redrive 설정과 실패 알림 패턴은 1-3.md를 본다.

### SDK(boto3) 호출: 재시도·페이지네이터·waiter·자격 증명 (Skill 3.1.3)

| retry mode | 기본 최대 시도 | 특징 |
|---|---|---|
| legacy (현재 문서상 boto3 기본) | 5 (최초 요청 포함) | 제한된 오류·상태 코드 목록에서 재시도 [S11] |
| standard | 3 (최초 요청 포함) | 서킷 브레이킹, 확장된 오류 목록, 지수 백오프 최대 20초 [S11] |
| adaptive | standard와 동일 기능 + 클라이언트 측 속도 제한 | 실험적(experimental) 모드 [S11] |

- retry_mode는 AWS 설정 파일에서, 구성 객체에서는 mode라는 이름으로 지정한다. max_attempts는 설정 파일·환경 변수에서는 최초 요청을 포함하고 Config 객체에서는 최초 요청을 제외하므로, 일관성을 위해 Config의 total_max_attempts를 쓰는 편이 낫다 [S11].
- 변경 예정: AWS는 SDK 재시도 동작을 갱신해 2026년 11월에 기본값으로 만든다고 공지했다. 현재 legacy가 기본인 SDK(Python 포함)는 기본이 standard로 바뀌어 재시도 쿼터가 추가된다 [S12]. 시험 문항은 현행 문서의 legacy 기본값을 전제로 할 가능성이 높으므로 두 정보를 구분해 둔다.
- Paginator: 잘린(truncated) API 결과를 전부 순회하는 추상화이며 get_paginator()로 만든다. 예를 들어 S3 list_objects는 한 번에 최대 1000개 객체를 반환한다 [S13]. PaginationConfig의 MaxItems·PageSize·StartingToken으로 조절하고 JMESPath로 클라이언트 측 필터링이 가능하다 [S13].
- Waiter: 리소스 상태를 폴링하다가 원하는 상태에 도달하거나 실패하면 끝나는 헬퍼이며 get_waiter()로 얻어 wait()를 호출한다. waiter가 없는 클라이언트(예: SQS)도 있다 [S14].
- 자격 증명 탐색: 위치 목록을 위에서부터 찾다가 찾으면 즉시 중단한다. 순서는 client()/Session 매개변수 → 환경 변수 → assume role → web identity → IAM Identity Center → 공유 자격 증명 파일 → 콘솔 로그인 → config 파일 → Boto2 파일 → 컨테이너 자격 증명 공급자 → EC2 인스턴스 메타데이터이다 [S15].

### 서비스 기능으로 데이터 처리: EMR·Redshift·Glue (Skill 3.1.4)

| 서비스 | 자동화·운영 기능 | 핵심 사실 |
|---|---|---|
| EMR | 스텝(Steps), 클러스터 수명 주기, 자동 종료 | STARTING → BOOTSTRAPPING → RUNNING → WAITING → TERMINATING → TERMINATED(오류 종료는 TERMINATED_WITH_ERRORS) [S16]. 스텝은 클러스터당 PENDING·RUNNING 합 256개까지 [S17]. 스텝 실패 시 동작은 ActionOnFailure(TERMINATE_CLUSTER·CANCEL_AND_WAIT·CONTINUE) [S18]. 자동 종료 유휴 시간은 60초~604800초(7일) [S19] |
| EMR Serverless | 애플리케이션 단위 서버리스 | 사전 초기화(pre-initialized) 워커가 없으면 자원 결정·프로비저닝에 최대 120초, 워커는 15분 유휴 시 자동 종료(변경 가능) [S16] |
| Redshift | 예약 쿼리, 저장 프로시저, 구체화된 뷰 자동 새로 고침, Data API | 예약 쿼리는 EventBridge가 시작하고 Data API로 실행(쿼리 편집기 v2) [S20]. 저장 프로시저는 데이터 변환·검증 로직을 캡슐화하고 CALL로 실행 [S21][S51]. MV는 AUTO REFRESH를 설정하면 기반 테이블 변경 후 가능한 한 빨리 자동 새로 고침하지만 워크로드가 우선이라 지연·중단될 수 있음 [S22] |
| Glue | 트리거, 잡 북마크, 워크플로 | 트리거는 on demand·schedule·conditional [S23]. 북마크는 이미 처리한 데이터를 추적(기본 Disable) [S24]. 워크플로는 1-3.md 참조 |

- EMR 스텝의 취소는 EMR 5.28.0 이상에서 대기 중·실행 중 모두 가능하다 [S17].
- Redshift 쿼리 스케줄 정의에는 실행 역할(IAM), 인증(Secrets Manager 또는 임시 자격 증명), 클러스터/워크그룹, 데이터베이스, SQL, 빈도 또는 cron 값이 필요하고 SNS 알림을 선택할 수 있다 [S20].
- 저장 프로시저는 기본 INVOKER 보안(호출자 권한)이며 DEFINER를 지정하면 소유자 권한으로 실행된다 [S21].
- MV 자동 새로 고침 대신 결정적(deterministic) 새로 고침이 필요하면 REFRESH MATERIALIZED VIEW 수동 실행 또는 스케줄러 API/콘솔의 예약 새로 고침을 쓴다 [S22]. 2026-02-27부터 Auto REFRESH 쿼리는 백그라운드 자동 프로세스가 아니라 사용자 쿼리로 실행된다는 문서 공지가 있다 [S22].
- Glue 트리거: 하나의 트리거가 시작할 수 있는 크롤러는 2개까지이고, 의존 체인의 모든 잡·크롤러는 단일 scheduled 또는 on-demand 트리거의 후손이어야 한다 [S23].
- Glue 잡 북마크: Disable(기본)이면 매번 전체 데이터를 처리하고 이전 실행 출력 관리는 사용자 몫이다 [S24]. S3 소스는 객체의 마지막 수정 시간으로 처리 여부를 판단한다 [S24].
- Glue 잡 타임아웃 기본은 Glue 4.0 이하 2,880분, 5.0 이상 480분이고 7일(10080분) 미만이어야 한다 [S25]. MaxRetries는 잡이 실패할 때 다시 시도하는 최대 횟수이다 [S25].

### 데이터 API 사용·유지 관리 (Skill 3.1.5)

용어: 여기서 Data API는 영속 연결 없이 HTTPS 엔드포인트와 AWS SDK로 SQL을 실행하는 방식이다(Redshift Data API, RDS Data API). 1.1.4·1.2.8의 용어와 같은 의미로 쓴다.

- Redshift Data API: 드라이버·영속 연결 없이 SDK로 SQL을 실행한다. 호출은 비동기이고, 자격 증명은 Secrets Manager 또는 임시 DB 자격 증명(IAM Identity Center도 가능)을 쓰며 호출에 비밀번호를 넣지 않는다 [S26].
- 한도: 쿼리 최대 24시간, 클러스터당 활성(STARTED·SUBMITTED) 쿼리 500개, 결과 크기 500 MB(gzip 압축 후), 결과 보존 24시간, 쿼리문 크기 200 KB [S26].
- BatchExecuteStatement는 문장을 순서대로 실행하며 기본은 단일 트랜잭션이라 하나라도 실패하면 모두 롤백된다. ExecutionMode로 AUTO_COMMIT을 선택할 수 있다 [S26].
- 멱등성: ExecuteStatement·BatchExecuteStatement에는 선택적 ClientToken(멱등 토큰)이 있고 8시간 후 만료된다. AWS SDK로 호출하면 SDK가 재시도용 클라이언트 토큰을 자동 생성하므로 직접 지정하지 않는 편이 낫다 [S26]. 반면 Step Functions 상태 머신은 기본적으로 재시도가 꺼져 있고, 재시도를 쓴다면 ClientToken을 넣어 재시도 사이에 같은 값을 유지해야 한다 [S26]. 쓰로틀되면 ThrottlingException이 반환되므로 SDK 재시도 전략을 쓴다 [S26].
- RDS Data API(Aurora): 응답 크기 한도 1 MiB이고 라이터 인스턴스에서만 실행되며 T 계열 인스턴스 클래스는 지원하지 않는다 [S27].

### Athena로 데이터 쿼리: 워크그룹·저장 쿼리·결과 위치·파티션 프로젝션·페더레이션 (Skill 3.1.7)

- 워크그룹: 워크로드 분리, 팀 접근 제어, 설정 강제, 쿼리 지표 추적·비용 통제에 쓴다. 워크그룹은 IAM 리소스라 리소스 수준 정책으로 접근을 제어하고, 워크그룹마다 쿼리 기록과 저장 쿼리 목록이 따로 있다 [S33]. 워크그룹 전체 설정(결과 위치·암호화 등)은 선택적으로 모든 쿼리에 강제할 수 있다 [S33].
- 결과 위치: 쿼리 실행 전에 S3 쿼리 결과 위치를 지정하거나, 위치가 지정되고 클라이언트 설정을 덮어쓰는 워크그룹을 써야 한다 [S37].
- 데이터 사용량 제어: 쿼리당·워크그룹당 스캔 한도를 둘 수 있다. 한도 값은 10 MB~7 EB이고 기본 동작은 초과 쿼리 취소(변경 불가)이며 취소된 쿼리도 요금이 청구된다. 워크그룹에는 쿼리당 한도를 1개만 만들 수 있다 [S34].
- 파티션 프로젝션: 파티션 정보를 카탈로그 대신 테이블 속성의 규칙(값 범위·프로젝션 유형)으로 두고 Athena가 계산한다. 켜면 Glue 데이터 카탈로그/Hive 메타스토어에 등록된 파티션 메타데이터를 무시한다 [S35].
- 페더레이션: S3 외 데이터 소스를 제자리에서 쿼리하거나 파이프라인으로 S3에 적재한다. 쿼리 시 Athena가 커넥터를 호출해 읽을 데이터를 정하고 병렬성을 관리하며 필터를 푸시다운한다 [S36]. 2026-04-21부터 새로 만든 일부 커넥터는 Glue 데이터 카탈로그에 자동 등록되고 계정 내 Lambda 함수를 쓰지 않는다 [S36].
- 저장 쿼리(named queries)는 워크그룹별 목록으로 관리된다 [S33].

### Lambda로 데이터 처리 자동화: 트리거·동시성·타임아웃·이벤트 소스 (Skill 3.1.8)

| 호출 방식 | 대표 소스 | 재시도·실패 처리 |
|---|---|---|
| 동기 | API Gateway 등 호출자가 응답을 기다림 | 호출자(또는 서비스)가 재시도 결정 [S40] |
| 비동기 | S3, SNS 등이 이벤트를 큐에 넣고 Lambda가 처리 [S41] | 함수 오류 시 2회 재시도 [S40], 큐 보관 최대 6시간·재시도 0~2회로 조정 가능, DLQ 또는 대상(destination) 설정 [S42] |
| 이벤트 소스 매핑(폴링) | DynamoDB, Kinesis, SQS 등 [S43] | 스트림: 배치 전체 재시도, 오류가 해결되거나 항목이 만료될 때까지 샤드 처리 중단(Iterator Age로 감시). 큐: 가시성 제한 시간·redrive 정책으로 제어 [S40] |

- 한도: 함수 타임아웃 최대 900초(15분), 메모리 128 MB~10,240 MB, 페이로드 동기 6 MB·비동기 1 MB, 계정 리전별 동시 실행 기본 1,000, 함수별 확장 속도 10초마다 실행 환경 1,000개 [S38][S39].
- 동시성 제어: 예약 동시성은 함수가 쓸 수 있는 동시 인스턴스 최소·최대를 정하고 계정 동시성 한도에서 차감되며 추가 요금이 없다. 프로비저닝 동시성은 미리 초기화한 실행 환경 수로 콜드 스타트를 줄이며 추가 요금이 든다 [S39].
- 비동기 실패 처리는 대상(destination)을 선호한다(추가 대상 지원, 추가 정보 포함) [S42].
- 이벤트 소스 매핑은 이벤트를 최소 한 번 처리하므로 중복이 생길 수 있어 함수를 멱등으로 만든다 [S43].
- SQS 이벤트 소스: 함수 타임아웃은 큐 가시성 제한 시간 이하여야 하고, 가시성 제한 시간은 함수 타임아웃의 최소 6배를 권장한다. 오류가 나면 기본으로 배치 전체가 큐로 돌아가므로 부분 배치 응답으로 실패 메시지만 돌려보내고, 소스 큐 redrive 정책의 maxReceiveCount는 5 이상을 권장한다 [S44].

### EventBridge 규칙과 Scheduler: 이벤트·스케줄러 관리 (Skill 3.1.9)

| 구분 | EventBridge 규칙 | EventBridge Scheduler |
|---|---|---|
| 용도 | 이벤트 패턴에 맞는 이벤트를 대상으로 전달. 한 규칙이 여러 대상에 병렬 전달 [S45] | 시간 기반·일회성 호출 [S46] |
| 예약 | "예약 규칙"은 레거시이며 Scheduler 사용을 권장 [S45] | rate·cron·일회성(at) 3종, 시간대 지정 [S46] |
| 정밀도 | - | 60초 정밀도(유연 시간 창 미사용 시) [S46] |
| 재시도 기본 | 24시간·최대 185회, 이후 폐기 또는 DLQ [S49] | 24시간·최대 185회, DLQ 없으면 폐기. 설정 변경 가능 [S48] |
| DLQ | 실패한 이벤트를 받는 DLQ 구성 [S49] | SQS 표준 큐로 전달 [S47] |

- Scheduler 표현식: rate(값 단위)는 minutes·hours·days, cron은 분 시 일 월 요일 연 6개 필드, 일회성은 at(yyyy-mm-ddThh:mm:ss) [S46]. 일회성 스케줄도 완료 후 계정 할당량을 차지하므로 완료 후 삭제를 권장한다 [S46].
- 시간대: cron·일회성 스케줄을 원하는 시간대로 평가하며 일광절약시간을 자동 반영한다. 봄에 존재하지 않는 시각이면 그날 호출을 건너뛰고, 가을에 시각이 반복돼도 한 번만 실행한다 [S46].
- Scheduler는 at-least-once로 전달하고, 유연한 시간 창(flexible time window)으로 호출을 분산해 하위 서비스 부하를 줄인다 [S48]. 재시도를 모두 쓰고도 실패한 스케줄은 DLQ에 이벤트(호출 정보와 대상 응답 포함)를 전달한다 [S47].
- Redshift 쿼리 편집기 v2의 예약 쿼리는 내부적으로 EventBridge가 시작하고 Data API를 쓴다 [S20].

## 시험에서 묻는 방식

1. **패턴 1 — MWAA 증상별 원인 찾기** — "스케줄러가 실행 중이 아니라는 오류, DAG 목록이 갱신되지 않고 새 작업이 스케줄되지 않음"을 주면 → **메타데이터 DB용 보안 그룹 규칙(TCP 5432), 의존성(requirements) 설치 실패, 과부하 스케줄러, 깨진 DAG**를 CloudWatch 로그 그룹(DAGProcessing·Scheduler·Worker)으로 확인하는 것이 정답 방향이다. "작업이 멈추고 큐가 쌓임"이면 DAG 수·동시 작업을 줄이고 최소 워커를 늘린다. "requirements.txt 업데이트가 20분 넘게 걸림"이면 설치 실패로 롤백 중이므로 패키지 버전 고정과 로그를 본다. 오답 후보와 탈락 이유: 환경 클래스를 무작정 올림(원인 확인 없이 비용만 증가, 파싱 과부하는 DAG 수가 원인) / 웹서버를 퍼블릭으로 전환(스케줄러·DB 문제와 무관) / DB 오류 메시지만 보고 DB를 조치(DB 오류는 스케줄러 장애의 증상). 근거 [S1][S2][S3][S4][S6]
2. **패턴 2 — 서비스 기능으로 데이터 처리 자동화 수단 선택** — "Redshift에서 매일 SQL을 실행하되 연결·드라이버를 관리하기 싫음"을 주면 → **쿼리 편집기 v2 예약 쿼리**(EventBridge가 시작하고 Data API로 실행). 여러 SQL 단계를 한 단위로 묶어야 하면 **저장 프로시저**(CALL로 실행)가 맞다. "대시보드 MV가 정해진 시각에 반드시 갱신돼야 함"이면 **수동/예약 REFRESH**(AUTO REFRESH는 워크로드가 우선이라 지연·중단될 수 있음). "Glue 잡이 매번 전체 데이터를 재처리"면 **잡 북마크 Enable**(기본은 Disable). "임시 EMR 클러스터가 유휴로 남아 비용 발생"이면 **자동 종료 정책**(60초~7일 유휴 시간). 오답 후보와 탈락 이유: 상시 EC2 크론(관리형 기능 미사용) / AUTO REFRESH만 믿음(결정성 없음) / 북마크 Pause·Disable 오해. 근거 [S16][S18][S19][S20][S22][S24]
3. **패턴 3 — 트리거·이벤트 소스·스케줄러 선택** — "S3에 파일이 올라올 때마다 Lambda 실행, 실패 이벤트는 보관"을 주면 → **비동기 호출**(함수 오류 시 2회 재시도, 큐 보관 최대 6시간) + **DLQ 또는 대상(destination)**. "SQS 큐 소비 중 일부 메시지만 실패"면 **부분 배치 응답**, 큐 가시성 제한 시간을 함수 타임아웃의 6배 이상으로, redrive maxReceiveCount를 5 이상으로. "뉴욕 시간 기준 매일 정해진 시각 + 일회성 + 재시도·유실 방지"면 **EventBridge Scheduler**(시간대, 유연한 시간 창, DLQ). 오답 후보와 탈락 이유: 스트림 소스를 비동기 호출로 착각(스트림은 이벤트 소스 매핑이고 오류 시 샤드가 막힘) / 예약 규칙(레거시)으로 대규모 스케줄 / DLQ 없이 기본 재시도만 믿음(기본 재시도 소진 후 폐기). 근거 [S40][S41][S42][S43][S44][S45][S46][S47][S48]
4. **패턴 4 — 데이터 접근·쿼리 통제** — "서버나 드라이버 없이 SDK로 비동기 SQL을 실행하고 재시도해도 중복 실행이 없어야 함"을 주면 → **Redshift Data API + ClientToken(멱등 토큰)**. "팀별로 결과 위치를 강제하고 쿼리당 스캔량을 제한"하라면 → **Athena 워크그룹**(설정 강제 + 데이터 사용량 제어). "파티션이 매우 많아 카탈로그 파티션 등록이 부담"이면 **파티션 프로젝션**, "S3 밖의 데이터를 쿼리"면 **Athena 페더레이션**. 오답 후보와 탈락 이유: JDBC 직접 연결 + 자체 풀링(연결 관리 부담) / 클라이언트 측 설정만 사용(워크그룹 강제 없이는 팀별 통제 불가) / 파티션 프로젝션이 필요한데 크롤러만 반복 실행. 근거 [S26][S33][S34][S35][S36][S37]

## 흔한 함정·혼동 짝

1. **MWAA Forced vs Graceful 업데이트** — Forced(기본)는 활성 워커를 즉시 멈춰 실행 중 작업이 실패, Graceful은 최대 12시간 작업을 이어가고 새 작업은 갱신된 워커로 간다(Airflow 2.4.3 이상, 기존 환경은 Forced 1회 선행). → 시험 단서: "업데이트 중 실행 중인 작업이 실패하지 않게" [S5]
2. **스케줄러 오류 vs DB 오류** — DB 관련 오류는 스케줄러 장애의 증상일 때가 많다. 보안 그룹(TCP 5432)·의존성 설치·과부하·깨진 DAG를 확인한다. → 시험 단서: "The scheduler does not seem to be running" [S2][S3][S6]
3. **작업 큐 적체 vs DAG 파싱 과부하** — 큐 적체는 최소 워커 증가·동시 작업 감소·시차 배치, 파싱 과부하(환경 용량 50% 초과, 비활성 DAG도 파싱)는 DAG 수 감소·.airflowignore로 대응. → 시험 단서: "Queued Tasks 증가" vs "Total Parse Time 증가" [S2][S50]
4. **MWAA 로그 그룹 5종** — DAGProcessing(DAG 파일 처리) / Scheduler / Task / WebServer / Worker. 패키지 설치 결과는 스케줄러 로그 그룹의 requirements_install_ip. → 시험 단서: "패키지 설치 실패를 어디서 확인" [S1]
5. **Step Functions Standard vs Express 로깅** — Standard 이력은 Step Functions가 기록(콘솔 생성 시 CloudWatch 로깅은 기본 꺼짐), Express는 이력을 기록하지 않아 로깅이 필수(콘솔 생성 시 기본 켜짐). 로그 전달은 best-effort. → 시험 단서: "Express 실행 기록이 안 보임" [S8]
6. **boto3 legacy vs standard vs adaptive** — legacy(현행 문서 기본, 5회 시도), standard(3회, 서킷 브레이킹, 백오프 최대 20초), adaptive(standard + 클라이언트 속도 제한, 실험적). 2026-11부터 기본값이 standard로 바뀐다는 공지가 있다. → 시험 단서: "재시도 쿼터/서킷 브레이커", "클라이언트 측 속도 제한" [S11][S12]
7. **max_attempts의 두 가지 의미** — 설정 파일·환경 변수는 최초 요청 포함(총 시도), Config 객체는 최초 요청 제외(재시도 횟수). Config에는 총 시도를 뜻하는 total_max_attempts가 있다. → 시험 단서: "총 시도 횟수 계산" [S11]
8. **Paginator vs Waiter** — Paginator는 잘린 API 결과를 끝까지 순회, Waiter는 리소스가 원하는 상태가 될 때까지 폴링. → 시험 단서: "다음 페이지 토큰" vs "상태가 될 때까지 대기" [S13][S14]
9. **자격 증명 탐색 순서** — 코드의 매개변수가 환경 변수보다 먼저이고 EC2 인스턴스 메타데이터가 마지막이다. 찾는 즉시 중단한다. → 시험 단서: "환경 변수와 인스턴스 프로파일이 모두 있을 때 어느 쪽이 쓰이나" [S15]
10. **EMR ActionOnFailure 3종** — TERMINATE_CLUSTER(클러스터 종료) / CANCEL_AND_WAIT(대기 중 스텝 취소 후 WAITING) / CONTINUE(다음 스텝 진행). → 시험 단서: "스텝 실패 시 클러스터는 유지하고 이어서" [S18]
11. **EMR 클러스터 상태와 자동 종료** — WAITING은 활성이지만 실행할 스텝이 없는 상태, TERMINATED는 정상 종료, TERMINATED_WITH_ERRORS는 오류 종료. 자동 종료 유휴 시간은 60초~7일. → 시험 단서: "유휴 클러스터 비용" [S16][S19]
12. **Redshift MV AUTO REFRESH vs 수동·예약 REFRESH** — 자동 새로 고침은 가능한 한 빨리 하지만 워크로드가 우선이라 지연·중단될 수 있음. 결정적 갱신이 필요하면 수동 REFRESH 또는 스케줄러 API/콘솔의 예약 새로 고침. → 시험 단서: "정시에 반드시" [S22]
13. **Redshift 예약 쿼리 vs 저장 프로시저** — 예약 쿼리는 EventBridge가 시작하고 Data API로 SQL 하나를 실행, 저장 프로시저는 여러 SQL·로직을 DB 안에 캡슐화하고 CALL로 실행(기본 INVOKER, DEFINER는 소유자 권한). → 시험 단서: "여러 변환 단계를 한 번에" [S20][S21]
14. **Glue 잡 북마크 Enable vs Disable vs Pause** — Enable은 처리한 데이터를 추적, Disable(기본)은 매번 전체 처리, Pause는 상태를 갱신하지 않고 증분 처리. S3 소스는 객체 수정 시간으로 판단하므로 수정된 파일은 다시 처리된다. → 시험 단서: "증분 처리", "재처리 방지" [S24]
15. **Glue 트리거 3종과 의존 체인** — on demand / scheduled / conditional. 의존 체인의 모든 잡·크롤러는 단일 scheduled 또는 on-demand 트리거의 후손이어야 한다. 한 트리거가 시작할 수 있는 크롤러는 2개. → 시험 단서: "잡 A·B 성공 후 잡 C" [S23]
16. **Data API vs JDBC/ODBC + ClientToken** — Data API는 영속 연결·드라이버 없이 HTTPS로 비동기 실행, 결과는 24시간 보존. Step Functions에서 재시도하려면 ClientToken을 넣어 중복 실행을 막는다. → 시험 단서: "연결 관리 없이", "Lambda에서 Redshift" [S26]
17. **Redshift Data API vs RDS Data API** — Redshift: 결과 500 MB·쿼리 24시간·보존 24시간 / RDS(Aurora): 응답 1 MiB, 라이터 인스턴스 전용, T 클래스 미지원. → 시험 단서: "큰 결과 반환" [S26][S27]
18. **DataBrew vs Visual ETL vs Data Wrangler** — DataBrew는 코드 없는 시각적 정제(레시피·프로파일 잡, 250개 넘는 변환), Unified Studio Visual ETL은 Glue 대화형 세션 기반 시각적 ETL, Data Wrangler는 Canvas 안의 ML 데이터 준비. → 시험 단서: "프로파일", "ML용 피처화", "Unified Studio" [S28][S30][S31]
19. **Athena 워크그룹 강제 설정 vs 클라이언트 설정** — 워크그룹 설정을 강제하면(결과 위치·암호화 등) 클라이언트 설정이 무시된다. 결과 위치가 없으면 쿼리가 실패한다. → 시험 단서: "팀별 결과 버킷 강제" [S33][S37]
20. **파티션 프로젝션 vs 카탈로그 파티션 등록** — 프로젝션을 켜면 카탈로그에 등록된 파티션 메타데이터를 무시하고 규칙으로 계산한다. → 시험 단서: "파티션이 수만 개", "MSCK/크롤러 부담" [S35]
21. **Lambda 예약 동시성 vs 프로비저닝 동시성** — 예약: 함수 전용 최소·최대 동시 실행 보장(무료, 계정 한도에서 차감). 프로비저닝: 미리 초기화한 환경으로 콜드 스타트 감소(추가 요금). → 시험 단서: "다른 함수가 한도를 다 쓰지 못하게" vs "콜드 스타트" [S39]
22. **Lambda 비동기 호출 vs 이벤트 소스 매핑** — 비동기(S3·SNS)는 Lambda 큐에서 2회 재시도하고 DLQ/대상으로 보관, 스트림 매핑은 배치 전체를 재시도하며 오류가 해결될 때까지 샤드가 막히고, 큐 매핑은 가시성 제한 시간·redrive로 제어. → 시험 단서: "Iterator Age 증가" [S40][S41][S43]
23. **SQS 가시성 제한 시간(6배) vs maxReceiveCount(5 이상)** — Lambda 타임아웃의 6배 이상은 재시도 여유, maxReceiveCount는 DLQ 이동 전 시도 횟수. 함수 타임아웃은 큐 가시성 제한 시간 이하여야 한다. → 시험 단서: "메시지가 중복 처리됨" [S44]
24. **EventBridge 규칙 vs 예약 규칙 vs Scheduler** — 규칙은 이벤트 패턴 매칭, 예약 규칙은 레거시, 시간 기반은 Scheduler 권장. → 시험 단서: "정해진 시각", "일회성" [S45][S46]
25. **Scheduler rate vs cron vs 일회성(at)과 DST** — rate는 minutes·hours·days, cron은 6개 필드, at은 한 번. 일광절약시간은 자동 반영(봄: 존재하지 않는 시각이면 건너뜀, 가을: 한 번만 실행). → 시험 단서: "뉴욕 시간 02:30" [S46]
26. **Scheduler 재시도 vs DLQ** — 기본 재시도(24시간·185회) 후 DLQ가 없으면 폐기, DLQ는 SQS 표준 큐. 규칙의 기본 재시도도 같은 24시간·185회. → 시험 단서: "예약 호출 유실 방지" [S47][S48][S49]
