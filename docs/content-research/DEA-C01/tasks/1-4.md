## 핵심 개념

### 수집·변환 코드 최적화 (Skill 1.4.1)

런타임을 줄이는 방향은 세 가지다. ① 읽는 데이터 양 줄이기(푸시다운·파티션 프루닝), ② 태스크·셔플 줄이기(파일 그룹핑·브로드캐스트·버킷팅), ③ 재사용(캐시·연결 재사용). 서비스마다 같은 원리가 다른 설정으로 나타난다.

- **Glue 소파일 → 파일 그룹핑**: S3 파일이 매우 많으면 파일마다 태스크가 생겨 느려진다. `groupFiles`를 `inPartition`으로 주면 각 ETL 태스크가 입력 파일 묶음을 하나의 인메모리 파티션으로 읽고, 입력이 50,000개를 넘으면 Glue가 자동으로 켠다. `groupSize`(바이트)를 생략하면 클러스터의 모든 CPU 코어를 쓰도록 Glue가 크기를 계산한다 [S1].
- **Glue 푸시다운**: 푸시다운은 소스 가까이에서 먼저 거르는 기법이라 "데이터 스캔을 줄인다". S3 데이터는 `push_down_predicate`로 Data Catalog의 파티션 메타데이터에 필터를 적용해 필요한 경로만 읽는다. 파티션이 수백만 개면 파티션 목록 조회 자체가 병목이므로 파티션 인덱스와 `catalogPartitionPredicate`(서버 측 프루닝)를 쓴다. JDBC 소스는 `sampleQuery`로 소스 DB에서 먼저 필터한다 [S2].
- **Spark 셔플**: `join()`·`groupByKey()`는 셔플을 일으키고 디스크·네트워크·CPU 비용이 크다. 처방은 조인 전에 불필요한 행·열 제거, DynamicFrame/RDD 조인 대신 DataFrame·Spark SQL 조인(Catalyst 최적화 대상), 작은 쪽이 메모리에 들어가면 브로드캐스트 해시 조인(셔플 불필요), 같은 키로 자주 조인하면 버킷팅, 반복 사용하는 DataFrame은 `cache()`/`persist()`다 [S3].
- **데이터 스큐**: 일부 파티션에만 데이터가 몰려 소수 태스크가 오래 걸리는 현상이다. AQE(Adaptive Query Execution)가 런타임 통계로 셔플 후 파티션 병합, 정렬병합 조인→브로드캐스트 조인 전환, 스큐 조인 분할을 처리하며 Glue 4.0 이상에서 기본 활성이다. 조인 키는 카디널리티가 높은 키나 복합 키가 낫다 [S3][S4].
- **Athena**: 가장 흔한 질의를 기준으로 파티션 키를 설계한다(너무 많으면 작은 파일 조각, 너무 적거나 없으면 과다 스캔). 컬럼너 포맷과 정렬 유지로 스캔량을 줄인다 [S5].
- **Redshift 적재**: COPY에 여러 파일을 지정하면 병렬 적재된다. 파일 크기는 비슷하게(1 MB–1 GB), 파일 수는 슬라이스 수의 배수(Serverless는 128의 배수)가 권장이다 [S6].
- **Lambda 코드**: SDK 클라이언트·DB 연결은 핸들러 밖에서 초기화하고 정적 자산은 `/tmp`에 캐시해 실행 환경 재사용의 이득을 얻는다. 유휴 연결은 Lambda가 정리하므로 keep-alive를 쓴다 [S7].

### Lambda 동시성·성능 구성 (Skill 1.4.2)

Lambda 함수의 처리량·지연·비용은 메모리(=CPU), 동시성 설정, 이벤트 소스 매핑(ESM) 스케일링으로 정해진다. 공식 문서는 일반 Lambda 함수를 이제 "Lambda Event Functions(이전 명칭 Lambda functions)"라 부르며, Managed Instances·MicroVMs·Web Functions는 별도 컴퓨트 유형으로 쿼터를 따로 둔다 [S14][S8].

- **메모리·CPU·시간**: 메모리는 128–10,240 MB(1 MB 단위)이고 CPU는 메모리에 비례해 배분된다(1,769 MB에서 1 vCPU). 별도 CPU 설정은 없고 메모리 설정으로만 조절한다 [S61]. 한 번의 호출은 최대 15분까지 실행된다 [S8].
- **동시성 계산**: 동시성 = 평균 초당 요청 수 × 평균 처리 시간(초)이다. 같은 RPS에서 처리 시간이 짧아지면 필요한 동시성이 줄어든다 [S62].
- **서로 다른 한도 3종**: (a) 계정 동시 실행 기본 1,000(리전별)이며 증설 요청이 가능하다 [S9][S8], (b) 함수별 스케일링 속도는 10초마다 실행 환경 최대 1,000개 추가다 [S9], (c) 초당 요청 한도는 동시성 쿼터의 10배다(기본 계정이면 초당 10,000건) [S9]. 새 계정은 동시성·메모리 쿼터가 낮게 시작하고 사용량에 따라 자동 상향된다 [S8].
- **예약 vs 프로비저닝**: 아래 표. 예약 동시성은 함수의 최대·최소 동시 인스턴스를 정해 다른 함수가 침범하지 못하게 하고, 다운스트림 리소스(DB 연결 등) 과부하를 막는 상한으로도 쓰며 추가 요금이 없다. 프로비저닝 동시성은 환경을 미리 초기화해 콜드 스타트를 없애지만 추가 요금이 든다 [S9]. 함수별 예약은 기본 900까지이며 100은 예약 없는 함수 몫으로 항상 남는다 [S9]. 예약 동시성을 0으로 두면 의도적으로 모든 호출을 스로틀링할 수 있다 [S62].
- **SnapStart**: 콜드 스타트(INIT) 지연을 줄이는 또 다른 방법이다. Java 11+·Python 3.12+·.NET 8+ 런타임에서 발행된 함수 버전에만 쓸 수 있고(미발행 `$LATEST` 불가), 프로비저닝 동시성·EFS·S3 Files·기본값을 초과하는 임시 스토리지와는 함께 쓸 수 없다 [S10][S9].
- **SQS 소스 스케일링**: 표준 큐는 배치 5개(동시 호출 5)로 시작해 분당 최대 300개씩 늘리며 ESM당 최대 1,250개 동시 호출까지 간다. 트래픽이 줄면 5개로, 최적화되면 2개까지 줄어든다. 한 큐가 계정 동시성을 독점하지 못하게 하려면 ESM **maximum concurrency**(2–1,000)를 설정한다. 이 값은 함수 예약 동시성과 별개 설정이라 예약 동시성이 모든 SQS 소스의 최대 동시성 합 이상이어야 스로틀링을 피한다. 더 높은 처리량은 provisioned mode(최대 100,000 동시 호출, 추가 비용)이며 maximum concurrency와 함께 쓸 수 없다 [S11].
- **SQS FIFO**: 메시지 그룹 단위로 순서를 지키며 동시 호출은 메시지 그룹 ID 수와 maximum concurrency 중 낮은 값으로 제한된다 [S11].
- **Kinesis 소스 스케일링**: 샤드당 한 번에 한 배치를 순서대로 처리한다. 처리량을 올리려면 샤드를 늘리거나 `ParallelizationFactor`(1–10, 기본 1)로 샤드당 동시 배치를 늘린다. 파티션 키 단위 순서는 유지된다 [S13].
- **배치 크기·배칭 윈도우**: 배치 크기는 배치당 최대 레코드 수, 배칭 윈도우는 레코드를 모으는 최대 시간이다. 배치 크기를 키우면 호출 오버헤드를 더 많은 레코드에 분산해 처리량이 늘 수 있다 [S12]. Kinesis ESM은 배치가 가득 차거나 배칭 윈도우가 만료되거나 페이로드 6 MB에 도달하면 함수를 호출한다 [S13].

### 데이터 엔지니어링용 언어·프레임워크 (Skill 1.4.3)

시험 가이드는 대상 응시자에게 "언어 중립적인 프로그래밍 개념"과 SQL 작성 능력을 요구하고, 언어별 구문 지식 시연은 범위 밖으로 명시한다 [S59]. 따라서 이 Skill은 구문이 아니라 "어떤 서비스에서 어떤 언어를 쓸 수 있는가"를 짝으로 고르는 문제로 접근한다.

- **AWS Glue(Spark ETL)**: ETL 스크립트를 Python(PySpark)과 Scala로 작성한다 [S15].
- **Amazon EMR(Spark)**: Spark는 Scala·Python·Java 애플리케이션을 네이티브로 지원한다 [S16].
- **AWS Lambda**: 관리형 런타임은 Node.js·Python·Java·.NET(C#)·Ruby이고, Go·Rust 등 다른 언어는 OS 전용 런타임이나 사용자 지정 런타임으로 쓴다 [S14]. PowerShell 함수는 AWSLambdaPSCore 모듈로 배포 패키지를 만들어 배포하며, 해당 문서는 .NET 런타임 목록을 함께 제시한다 [S17]. Bash는 사용자 지정 런타임의 `bootstrap`과 핸들러를 Bash로 구현하는 튜토리얼이 공식 문서에 있다 [S18].
- **SQL**: Athena·Redshift의 질의 언어다. 파티션·컬럼너 최적화는 1.4.1 절, 재귀 CTE는 1.4.11 절에서 다룬다 [S5][S55].
- **IaC 언어**: CDK는 TypeScript·JavaScript·Python·Java·C#/.NET·Go로 인프라를 정의한다 [S27].
- **R**: 데이터 엔지니어링 서비스 개발자 가이드에서 지원 언어로 설명한 곳을 확인하지 못했다 → gaps G-1.4-04. (AWS SDK for pandas는 시험 가이드 페이지에 나오지 않으며, 관련 근거는 같은 항목에 정리했다.)

### 소프트웨어 공학 모범 사례: 버전 관리·테스트·로깅·모니터링 (Skill 1.4.4)

데이터 파이프라인 코드도 애플리케이션 코드처럼 버전 관리·자동 테스트·관측 가능성을 갖춰야 한다는 취지다. 공식 IaC 문서도 구성을 소스 관리 시스템에 저장하라고 한다 [S23].

- **버전 관리(Git)**: 시험 가이드는 소스 관리를 위한 Git 명령 사용을 일반 IT 지식으로 요구한다 [S59]. 메인 저장소를 직접 고치지 않고 작업 브랜치에서 작업한다. 원격 코드를 로컬로 가져오는 것이 clone, 브랜치 전환이 checkout이며, 커밋으로 저장하고 푸시로 공유한다. 병합 시 충돌은 개발자가 해결한다 [S20]. 저장소는 CodeCommit 또는 CodeConnections를 통한 외부 Git(GitHub 등)을 쓴다(현황은 1.4.9 절) [S45][S47].
- **테스트**: Glue 잡은 AWS가 제공하는 Docker 이미지로 로컬에서 개발·테스트한다 [S19]. Lambda는 핸들러와 핵심 로직을 분리해야 단위 테스트가 쉽다 [S7]. 배포 파이프라인 안에는 CodeBuild 기반 자동 테스트 단계를 둔다 [S48].
- **로깅**: Lambda는 JSON 구조화 로그를 지원하며, 로그 레벨 필터링을 쓰려면 함수가 JSON 형식 로그를 내야 한다 [S21]. Powertools for AWS Lambda는 구조화 로깅·EMF 메트릭·분산 트레이싱 유틸리티를 제공하고 Python·Java·TypeScript·.NET에서 쓸 수 있다 [S22].
- **모니터링**: 서버리스 관측은 CloudWatch와 X-Ray 기반으로 구성하고, Powertools가 그 코드를 단순화한다 [S22].

### IaC로 데이터 엔지니어링 솔루션 배포·반복 가능한 배포 — CloudFormation·CDK (Skill 1.4.5, 1.4.8)

IaC는 인프라를 애플리케이션 코드처럼 선언적으로 정의해 소스 관리하는 방식이라 환경을 반복 가능하게 만든다 [S23]. 데이터 파이프라인에서는 Glue 잡·크롤러·S3 버킷·역할 같은 리소스를 하나의 CloudFormation 템플릿으로 묶어 테스트 환경과 운영 환경에 같은 템플릿으로 배포한다 [S48]. Skill 1.4.8(v1.1 개정)은 v1.0의 지식 항목("반복 가능한 배포를 위한 IaC")이 v1.1에서 Skill로 바뀐 것이며 CloudFormation과 CDK를 예시로 든다 [S57]. v1.1 in-scope 목록에는 Developer Tools의 CloudFormation·CDK가, Compute의 AWS SAM이 들어 있다 [S58].

- **CloudFormation**: 스택은 한 단위로 관리되는 리소스 모음이며 생성·업데이트·삭제를 스택 단위로 한다. 업데이트는 **변경 세트**(미리보기 후 실행)와 **직접 업데이트**(즉시 배포) 중 고른다. 일부 리소스를 만들지 못하면 스택을 롤백하고 만들어진 리소스를 삭제한다 [S24]. **드리프트 감지**는 CloudFormation 밖에서 바뀐 구성을 찾아주며, 드리프트 감지를 지원하지 않는 리소스는 NOT_CHECKED가 된다 [S25]. **StackSets**는 관리자 계정이 템플릿 하나로 여러 계정·리전에 스택을 만들고 갱신하고 삭제한다 [S26].
- **CDK**: 범용 프로그래밍 언어로 인프라를 정의하고 CloudFormation으로 프로비저닝한다 [S27]. 구성 요소(construct)는 3단계다. L1은 `Cfn` 접두어의 CloudFormation 리소스 1:1 매핑, L2는 의도 기반 API에 기본값·보안 모범 설정을 얹은 것, L3는 여러 리소스를 묶은 패턴이다 [S28]. `cdk synth`는 스택별 CloudFormation 템플릿을 담은 클라우드 어셈블리를 만들고 [S30], `cdk bootstrap`은 환경마다 `CDKToolkit` 스택(S3 버킷·ECR 리포지토리)을 배포해 에셋 저장소를 준비한다 [S29].
- 선언형 vs 프로그래밍형: 같은 인프라를 CloudFormation·SAM은 선언적 템플릿으로, CDK는 프로그래밍 방식으로 정의한다 [S31].

| 도구 | 정의 방식 | 특징 | 배포 경로 | 시험 단서 키워드 |
|---|---|---|---|---|
| CloudFormation | 선언형 템플릿, 스택 단위 | 변경 세트·드리프트 감지·StackSets·롤백 [S24][S25][S26] | CloudFormation 자체 | "선언형", "변경 미리보기", "여러 계정·리전" |
| AWS CDK | 범용 프로그래밍 언어(construct L1/L2/L3), `cdk synth`로 템플릿 생성 | 환경당 `cdk bootstrap` 필요 [S27][S28][S29][S30] | CloudFormation으로 배포 | "프로그래밍 언어", "construct", "bootstrap" |
| AWS SAM | CloudFormation 확장 약식 문법 + SAM CLI | 서버리스 전용, `Transform`으로 변환, 로컬 테스트·sync [S31][S32] | CloudFormation으로 배포 | "서버리스", `AWS::Serverless-2016-10-31`, "sam local" |

### SAM으로 서버리스 데이터 파이프라인 패키징·배포 (Skill 1.4.6)

SAM은 서버리스 애플리케이션을 IaC로 만드는 오픈소스 프레임워크이며 ① SAM 템플릿(CloudFormation의 확장, 단순화된 서버리스 문법)과 ② SAM CLI(개발·로컬 테스트·배포)로 구성된다 [S31]. 템플릿 최상위에 `Transform: AWS::Serverless-2016-10-31`을 선언하면 CloudFormation이 SAM 문법을 일반 CloudFormation으로 변환한다 [S32].

- **리소스 유형**: Skill의 예시(Lambda 함수·Step Functions·DynamoDB 테이블)에 해당하는 유형은 `AWS::Serverless::Function`, `AWS::Serverless::StateMachine`, `AWS::Serverless::SimpleTable`이다 [S33]. SimpleTable은 단일 속성 기본 키의 DynamoDB 테이블을 만든다(더 복잡한 키·정책은 `AWS::DynamoDB::Table`을 함께 쓴다) [S34].
- **CLI 흐름**: `sam build`로 준비하고 `sam deploy`로 배포한다. `sam sync`는 로컬 변경을 감지해 클라우드에 빠르게 반영하는 개발용 명령이며 운영에는 `sam deploy`나 CI/CD를 권장한다 [S35].
- **점진 배포**: SAM은 CodeDeploy를 내장해 Lambda 점진 배포를 제공한다. 함수에 `AutoPublishAlias`와 `DeploymentPreference`(전환 유형, 경보, 사전·사후 트래픽 검증 함수)를 두면 새 버전으로 트래픽을 점진 전환하고 CloudWatch 경보 발생 시 자동 롤백한다 [S36].
- **SAM vs CDK**: 선언적 접근을 선호하면 SAM, 프로그래밍 방식을 선호하면 CDK다 [S31].

### Lambda 함수에서 스토리지 볼륨 사용·마운트 (Skill 1.4.7)

Lambda에서 파일 형태 저장소는 세 가지다.

- **`/tmp`(임시 스토리지)**: 실행 환경마다 고유한 임시 공간이며 512–10,240 MB(1 MB 단위)로 설정한다 [S37].
- **Amazon EFS**: 함수가 VPC의 로컬 네트워크로 EFS에 연결해 로컬 디렉터리로 마운트한다. 가용 영역마다 마운트 타깃이 있어야 하고, NFS 트래픽(포트 2049)을 보안 그룹이 허용해야 하며, 액세스 포인트를 통해 연결하고, 로컬 마운트 경로는 `/mnt/`로 시작한다. 성능 모드는 생성 후 바꿀 수 없다 [S39].
- **Amazon S3 Files**: S3 버킷의 객체를 표준 파일 연산으로 접근하게 하는 서버리스 파일 시스템이다. 같은 VPC·마운트 타깃·NFS 2049·`/mnt/` 경로가 필요하고 액세스 포인트가 없으면 Lambda가 자동 생성한다. 메모리 512 MB 이상이면 direct read가 기본(AUTO)이다 [S40]. 연결 버킷은 S3 버저닝이 필수이고 충돌 시 S3 버킷이 기준이다 [S41].
- **택일 규칙**: 한 함수는 EFS 또는 S3 Files 중 하나만 쓴다 [S38]. SnapStart는 두 파일 시스템 모두와 호환되지 않는다 [S10].

| 구분 | 성격 | 설정 요건 | 한도·특성 | 시험 단서 키워드 |
|---|---|---|---|---|
| `/tmp` | 실행 환경별 임시 스토리지 | 추가 인프라 없음 | 512–10,240 MB [S37] | "임시 스크래치", "ETL 중간 파일" |
| EFS | 공유 NFS 파일 시스템 | VPC, 마운트 타깃, 액세스 포인트, `/mnt/` 경로, NFS 2049 [S39] | EFS 또는 S3 Files 택일 [S38] | "여러 호출·함수가 공유", "영구 파일 시스템" |
| S3 Files | S3 버킷을 파일로 노출 | VPC, 마운트 타깃, 액세스 포인트(없으면 자동 생성), `/mnt/` [S40] | 버킷 버저닝 필수 [S41] | "S3 객체를 파일 경로로", "다운로드 코드 제거" |

### CI/CD — 데이터 파이프라인의 구현·테스트·배포 (Skill 1.4.9)

지속적 통합(CI)은 코드 변경을 자주 병합하고 자동 빌드·테스트를 돌리는 것이다. 지속적 전달은 빌드·테스트를 통과한 변경을 배포 가능한 상태로 준비(필요 시 수동 승인 단계 포함)하는 것이고, 지속적 배포는 개발자 승인 없이 운영 환경에 자동 배포까지 하는 것이다 [S49].

- **CodePipeline**: 릴리스 워크플로를 파이프라인으로 모델링한다. 파이프라인은 스테이지의 연속이고 스테이지는 직렬·병렬 액션으로 이뤄지며, 액션 유형은 source·build·test·deploy·approval·invoke다 [S42].
- **CodeBuild**: `buildspec`(YAML)이 빌드 명령과 설정을 정의한다. 단계는 install·pre_build·build·post_build다 [S43].
- **CodeDeploy**: Lambda 배포에서 새 함수 버전으로 트래픽을 옮기는 방식을 canary·linear·all-at-once 구성 중에서 고르며(Lambda·ECS 배포는 모두 blue/green) [S63], 사용자 정의 canary·linear 구성도 만들 수 있다 [S44]. canary는 트래픽 일부를 먼저 보낸 뒤 나머지를 정해 둔 시간 뒤에, linear는 일정 간격마다 같은 비율씩, all-at-once는 한 번에 전환한다 [S44].
- **소스 저장소와 시험 범위**: CodeCommit은 2024년 7월에 "de-emphasize" 계획이 공지됐다가 공식 DevOps 블로그가 "full General Availability 복귀"와 신규 고객 가입 재개를 알렸다 [S45]. AMS 문서는 신규 고객 접근 중단이 2024-07-25부터라고 적는다 [S46]. 그런데 CloudFormation 리소스 레퍼런스에는 여전히 "신규 고객 불가" 문구가 남아 있어 공식 페이지끼리 상충한다 [S60](gaps G-1.4-03). 시험 쪽에서는 v1.1이 CodeCommit을 in-scope 서비스 목록에서 **제거**했고 [S57], 현재 in-scope 목록의 Developer Tools 항목은 CLI·CloudFormation·CDK·CodeBuild·CodeDeploy·CodePipeline·Amazon Q다(목록은 비포괄적이며 변경될 수 있다) [S58]. 외부 Git(Bitbucket Cloud·GitHub·GitHub Enterprise Server·GitLab 등)은 CodeConnections 기반 소스 액션으로 연결한다 [S47].
- **데이터 파이프라인 CI/CD 패턴**: Glue ETL 예시는 ① 소스 관리(ETL 코드 + CloudFormation 템플릿) → ② LiveTest(템플릿으로 리소스 배포 → CodeBuild로 크롤러·잡 실행과 검증 테스트 → 필요 시 수동 승인 → 테스트 리소스 정리) → ③ 운영 배포 순서다 [S48]. SAM을 쓰면 점진 배포·자동 롤백이 CodeDeploy와 연동된다 [S36].

| 서비스 | 역할 | 핵심 개념 | 시험 단서 키워드 |
|---|---|---|---|
| CodePipeline | 릴리스 단계 오케스트레이션 | 스테이지·액션·전환(transition), 수동 승인 액션 [S42] | "파이프라인", "단계별 승인" |
| CodeBuild | 빌드·테스트 실행 | `buildspec.yml` 단계 정의 [S43] | "buildspec", "단위 테스트 실행" |
| CodeDeploy | 배포·트래픽 전환 | Lambda: canary / linear / all-at-once [S63][S44] | "일부 트래픽부터 점진 전환", "롤백" |
| CodeCommit | AWS 관리형 Git 저장소 | 신규 고객 중단 공지 후 재개 발표, 공식 페이지 간 표기 상충, v1.1 in-scope에서 제거 [S45][S46][S60][S57] | "AWS 안의 Git 저장소" |
| CodeConnections | 외부 Git 연결 | CodePipeline 소스 액션으로 GitHub·GitLab·Bitbucket 연결 [S47] | "GitHub 저장소를 파이프라인 소스로" |

### 분산 컴퓨팅 (Skill 1.4.10)

분산 컴퓨팅은 큰 작업을 여러 노드에 나눠(파티셔닝) 병렬로 처리하고 결과를 합치는 방식이다. 공식 문서에서 확인되는 모델로 정리한다.

- **MapReduce**: 작업을 여러 노드에 매핑해 각 노드가 병렬 처리하고, 출력은 단일 노드에서 리듀스해 최종 결과를 낸다. EMR의 Hadoop이 이 알고리즘을 구현한다 [S51].
- **EMR 노드**: 마스터(프라이머리) 노드가 클러스터를 관리하며 데이터·태스크 분배를 조율하고, 코어 노드는 태스크를 실행하면서 HDFS에 데이터를 저장하며, 태스크 노드는 태스크만 실행하고(HDFS 저장 안 함) 선택 사항이다 [S50].
- **Spark**: 드라이버가 애플리케이션을 태스크로 쪼개 실행 계획·스케줄링을 맡고, 익스큐터는 데이터를 보유하고 태스크를 실행한다. 데이터는 RDD 파티션으로 나뉘어 익스큐터에 분산되고 태스크는 RDD 파티션마다 만들어진다 [S4].
- **셔플과 지연 평가**: 셔플은 파티션 간 데이터를 재분배하는 비싼 단계다 [S3][S4]. Spark 변환(transformation)은 지연 평가되어 액션을 호출할 때 실행된다 [S4].
- **내결함성**: RDD는 불변이며 노드 간 복제되어 노드 장애에서 자동 복구된다 [S4].

### 데이터 구조·알고리즘: 그래프·트리 (Skill 1.4.11)

이 Skill이 시험에서 정확히 무엇을 묻는지는 공식 근거로 확정하지 못했다(gaps G-1.4-06). 아래는 AWS 공식 문서에서 그래프·트리가 실제로 등장하는 곳이다.

- **그래프**: 노드(엔티티)·엣지(관계)·속성으로 데이터를 표현한다. Amazon Neptune은 관계를 데이터 모델의 일급 요소로 저장해 관계 순회를 빠르게 하며 소셜 네트워킹·추천 엔진·사기 탐지에 쓴다 [S52]. Neptune Analytics는 경로 탐색(BFS 등)·중심성(PageRank 등)·유사도·커뮤니티 탐지 같은 그래프 알고리즘을 내장한다 [S53]. 그래프 DB 없이도 DynamoDB는 다대다 관계를 인접 리스트(adjacency list) 패턴(파티션 키=노드, 정렬 키=대상 노드)으로 모델링한다 [S56].
- **트리**: B-tree 인덱스는 정렬된 데이터를 유지하는 자기 균형 트리 구조로 동등·범위 질의를 처리하며 PostgreSQL의 기본 인덱스다 [S54]. 조직도·부품 목록(BOM) 같은 계층(트리) 데이터는 Redshift의 재귀 CTE로 질의하고, 무한 재귀를 막으려면 재귀 깊이를 WHERE로 제한해야 한다 [S55].

## 흔한 함정·혼동 짝

1. **예약 동시성 vs 프로비저닝 동시성** — 예약은 함수 전용 최대·최소 몫(콜드 스타트 가능, 추가 요금 없음), 프로비저닝은 사전 초기화된 환경(콜드 스타트 없음, 추가 요금) → 시험 단서: "다른 함수가 동시성을 소진·DB 연결 보호" ⇒ 예약, "콜드 스타트 지연" ⇒ 프로비저닝 [S9]
2. **계정 동시성 한도 vs 함수별 스케일링 속도 vs ESM 상한** — 계정 기본 1,000, 함수별 10초당 환경 1,000개 추가, SQS ESM은 기본 최대 1,250(계정 한도를 올려도 provisioned mode 없이는 1,250) → 시험 단서: "한도를 올렸는데도 SQS 동시 호출이 더 안 늘어남" [S8][S9][S11]
3. **SnapStart vs 프로비저닝 동시성** — 둘 다 콜드 스타트 대책이지만 같은 함수 버전에 동시 사용 불가, SnapStart는 Java 11+·Python 3.12+·.NET 8+의 발행 버전만이고 EFS·S3 Files·기본값을 초과하는 임시 스토리지와 비호환 → 시험 단서: "스냅샷", "발행된 버전/별칭" [S9][S10]
4. **SQS ESM maximum concurrency vs 함수 예약 동시성** — 서로 독립된 설정, 최대 동시성(2–1,000)은 예약 동시성 이하로 두어야 스로틀링을 피함, provisioned mode와는 병용 불가 → 시험 단서: "큐 단위로 호출 수 제한" [S11]
5. **Kinesis ParallelizationFactor vs 샤드 추가** — 둘 다 처리량을 올리지만 전자는 샤드당 동시 배치(1–10, 파티션 키 순서 유지), 후자는 샤드 수 자체를 늘림 → 시험 단서: "IteratorAge 증가", "샤드 수 고정" [S13]
6. **`/tmp`(임시 스토리지) vs EFS vs S3 Files** — `/tmp`는 실행 환경별 임시, EFS·S3 Files는 VPC 마운트형 공유 파일 시스템이며 한 함수에 둘 중 하나만 → 시험 단서: "호출 간 공유", "S3 객체를 파일 경로로" [S37][S38][S39][S40]
7. **Glue `push_down_predicate` vs `catalogPartitionPredicate`** — 전자는 파티션 목록을 가져온 뒤 필터, 후자는 파티션 인덱스로 서버 측 프루닝(파티션 수백만 개일 때) → 시험 단서: "파티션 목록 조회가 느림" [S2]
8. **파일 그룹핑(groupFiles) vs 푸시다운** — 그룹핑은 한 태스크가 읽는 파일 수를 늘려 태스크 수를 줄이고, 푸시다운은 읽는 파티션·행 자체를 줄임 → 시험 단서: "작은 파일 수만 개" vs "특정 파티션만 필요" [S1][S2]
9. **셔플 조인 vs 브로드캐스트 해시 조인** — 브로드캐스트는 작은 쪽을 각 노드에 보내 셔플을 없애지만 작은 쪽이 메모리에 들어갈 때만 적합 → 시험 단서: "작은 차원 테이블과 대형 팩트 조인" [S3]
10. **`cache()` vs 버킷팅** — 캐시는 같은 DataFrame의 반복 계산을 피하고, 버킷팅은 같은 키로 자주 조인하는 큰 테이블의 셔플·정렬 비용을 미리 줄임 → 시험 단서: "같은 데이터 반복 사용" vs "동일 키 반복 조인" [S3]
11. **Spark 드라이버 vs 익스큐터** — 드라이버는 실행 계획·태스크 스케줄링, 익스큐터는 데이터 보유·태스크 실행 → 시험 단서: "main() 실행, 태스크 요청" vs "데이터 보유" [S4]
12. **CloudFormation vs CDK vs SAM** — 선언형 템플릿 / 프로그래밍 언어로 정의해 CloudFormation으로 배포 / CloudFormation 확장 약식 문법(서버리스 전용) → 시험 단서: "프로그래밍 언어·construct" ⇒ CDK, "AWS::Serverless-2016-10-31" ⇒ SAM [S23][S27][S31][S32]
13. **변경 세트 vs 직접 업데이트 vs 드리프트 감지** — 변경 세트는 적용 전 미리보기, 직접 업데이트는 즉시 배포, 드리프트 감지는 CloudFormation 밖에서 바뀐 구성을 탐지 → 시험 단서: "먼저 영향 확인" vs "콘솔에서 수동 수정" [S24][S25]
14. **`cdk synth` vs `cdk bootstrap`** — synth는 CloudFormation 템플릿(클라우드 어셈블리) 생성, bootstrap은 환경에 `CDKToolkit` 스택(S3·ECR)을 만들어 에셋 저장소를 준비 → 시험 단서: "환경 준비" vs "템플릿 생성" [S29][S30]
15. **`sam sync` vs `sam deploy`** — sync는 로컬 변경을 감지해 빠르게 반영하는 개발용, 운영은 deploy나 CI/CD → 시험 단서: "개발 중 빠른 반영" [S35]
16. **CodePipeline vs CodeBuild vs CodeDeploy** — 단계 오케스트레이션 / buildspec으로 빌드·테스트 / 배포 구성(canary·linear·all-at-once)으로 트래픽 전환 → 시험 단서: "파이프라인 단계·승인", "buildspec", "일부 트래픽부터 점진 전환" [S42][S43][S63][S44]
17. **지속적 전달 vs 지속적 배포** — 전달은 배포 가능한 산출물까지 자동화(수동 단계 가능), 배포는 개발자 승인 없이 운영까지 자동 → 시험 단서: "명시적 승인 없이 운영 배포" [S49]
18. **CodeCommit 현황 혼동** — 신규 고객 중단 공지(AMS 문서: 2024-07-25부터) 후 DevOps 블로그가 GA 복귀를 발표했지만 CloudFormation 리소스 레퍼런스는 아직 "신규 불가"로 표기하고, 시험 v1.1 in-scope에서는 제거됨 → 시험 단서: "AWS 관리형 Git" [S45][S46][S57][S60]
19. **EMR 코어 노드 vs 태스크 노드** — 코어는 태스크 실행 + HDFS 저장, 태스크 노드는 태스크만 실행하고 HDFS에 저장하지 않으며 선택 사항 → 시험 단서: "HDFS에 데이터 저장" vs "태스크만 실행" [S50]
20. **Lambda "Event Functions" vs "Lambda functions"** — 같은 개념의 새 공식 명칭(이전 명칭이 Lambda functions)이며, Managed Instances·MicroVMs·Web Functions는 별개 컴퓨트 유형 → 시험 단서: 문서 표기가 달라져도 개념은 동일 [S14][S8]
21. **그래프(Neptune) vs 트리(B-tree·재귀 CTE)** — 그래프는 노드·엣지로 다대다 관계를 순회, 트리는 계층·정렬 인덱스(B-tree 검색, 재귀 CTE로 조직도 순회) → 시험 단서: "관계 순회·추천·사기 탐지" vs "계층·범위 검색" [S52][S54][S55]

### 후보 1 — Skill 1.4.2 · associate
- **문제**: Amazon SQS 표준 큐를 이벤트 소스로 쓰는 Lambda 함수가 메시지 폭주 때 계정의 동시 실행을 대부분 소진해, 같은 계정의 다른 핵심 함수들이 스로틀링된다. 이 큐가 일으키는 동시 호출만 제한하려면 어떻게 해야 하는가?
- **보기**: A. 함수에 프로비저닝 동시성을 설정한다 / B. SQS 이벤트 소스 매핑에 maximum concurrency를 설정한다 / C. 함수 메모리를 최대값으로 올린다 / D. 함수에 SnapStart를 켠다
- **정답**: B
- **해설 초안**: maximum concurrency는 SQS 이벤트 소스가 호출할 수 있는 함수의 동시 인스턴스 수를 제한해 한 큐가 계정 동시성을 독점하지 못하게 한다. 함수 예약 동시성과는 독립 설정이므로 예약 동시성이 모든 SQS 소스의 최대 동시성 합 이상이어야 스로틀링을 피한다 [S11].
- **오답 근거**: A — 프로비저닝 동시성은 환경을 미리 초기화해 콜드 스타트를 줄이는 기능이며 추가 요금이 든다 [S9]. C — 메모리는 CPU 배분을 바꿀 뿐 호출 동시성을 제한하는 장치가 아니다 [S61]. D — SnapStart는 콜드 스타트(INIT) 지연을 줄이는 기능이다 [S10].
- **근거**: [S11] https://docs.aws.amazon.com/lambda/latest/dg/services-sqs-scaling.html — "The maximum concurrency setting limits the number of concurrent instances of the function"

### 후보 2 — Skill 1.4.1 · associate
- **문제**: AWS Glue Spark 잡이 S3의 한 날짜 파티션에 있는 아주 작은 JSON 파일 수만 개를 읽는다. 파일마다 태스크가 생겨 드라이버가 수많은 태스크를 추적하느라 잡이 느리고 메모리가 부족해진다. 코드 변경만으로 가장 직접적인 개선은 무엇인가?
- **보기**: A. `groupFiles`를 `inPartition`으로 설정하고 필요하면 `groupSize`를 지정한다 / B. 읽은 DataFrame에 `persist()`를 호출한다 / C. 같은 날짜 파티션 하나만 읽도록 `push_down_predicate`를 추가한다 / D. 작은 쪽 테이블에 broadcast 힌트를 추가한다
- **정답**: A
- **해설 초안**: 파일 그룹핑은 각 ETL 태스크가 입력 파일 묶음을 하나의 인메모리 파티션으로 읽게 해, 작은 파일이 많을 때 태스크 수를 줄인다. 입력 파일이 50,000개를 넘으면 Glue가 자동으로 켠다 [S1].
- **오답 근거**: B — `persist()`는 반복 사용하는 DataFrame의 재계산·셔플을 피하는 기법이다 [S3]. C — 푸시다운은 읽을 파티션·행을 줄이는 기법이라 이미 한 파티션만 읽는 상황에서 그 안의 파일 수는 그대로다 [S2]. D — 브로드캐스트는 조인의 셔플을 피하는 기법이다 [S3].
- **근거**: [S1] https://docs.aws.amazon.com/glue/latest/dg/grouping-input-files.html — "input files into a single in-memory partition"

### 후보 3 — Skill 1.4.6 (1.4.5, 1.4.8 관련) · associate · 서비스 선택
- **문제**: 팀이 Lambda 함수, Step Functions 상태 머신, DynamoDB 테이블로 이뤄진 서버리스 데이터 파이프라인을 프로그래밍 언어가 아니라 선언적 YAML 약식 문법으로 정의하고, 로컬에서 함수를 테스트한 뒤 CloudFormation으로 배포하려 한다. 가장 적합한 도구는?

- **오답 근거**: A — CDK는 범용 프로그래밍 언어로 인프라를 정의하는 프로그래밍 방식이다 [S27]. C — StackSets는 한 템플릿으로 여러 계정·리전에 스택을 배포하는 기능이다 [S26]. D — CodeBuild는 buildspec으로 빌드·테스트를 실행하는 서비스다 [S43].

- **보기**: A. 임시 스토리지(`/tmp`)를 최대 크기로 늘린다 / B. 함수를 VPC에 연결하고 EFS 액세스 포인트를 `/mnt/` 아래 경로로 마운트한다 / C. 한 함수에 EFS와 S3 Files를 모두 마운트한다 / D. 함수를 VPC에 연결하지 않은 채 EFS를 마운트한다
- **정답**: B
- **해설 초안**: Lambda는 VPC의 로컬 네트워크로 EFS에 연결하며, 마운트 타깃과 NFS(포트 2049)를 허용하는 보안 그룹, 액세스 포인트가 필요하고 로컬 마운트 경로는 `/mnt/`로 시작한다 [S39].
- **오답 근거**: A — `/tmp`는 실행 환경마다 고유한 임시 공간이라 환경 간에 공유되지 않는다 [S37]. C — 한 함수는 EFS 또는 S3 Files 중 하나만 쓸 수 있다 [S38]. D — 함수는 VPC의 로컬 네트워크로 파일 시스템에 연결한다 [S39].
- **근거**: [S39] https://docs.aws.amazon.com/lambda/latest/dg/configuration-filesystem-efs.html — "A function connects to a file system over the local network in a VPC."

- **오답 근거**: B — buildspec은 빌드 명령·설정을 정의하는 파일이지 트래픽 전환 장치가 아니다 [S43]. C — StackSets는 다중 계정·리전 배포용이다 [S26]. D — all-at-once는 모든 트래픽을 한 번에 전환하므로 점진 확인이 불가능하다 [S44].
