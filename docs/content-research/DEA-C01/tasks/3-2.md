## 핵심 개념

### 데이터 시각화: DataBrew와 Amazon Quick Sight (Skill 3.2.1)

**DataBrew**는 코드 없이 데이터를 정리·정규화하는 시각적 데이터 준비 도구다. 프로젝트 워크스페이스에서 데이터를 격자형 시각 인터페이스로 보면서 값 분포와 차트로 데이터의 프로파일을 파악하고, 250개가 넘는 사전 제작 변환을 클릭으로 적용하며, 변환 단계는 레시피로 저장해 다른 데이터셋에 재사용·지속 배포할 수 있다. DataBrew는 서버리스라 클러스터를 만들거나 인프라를 관리하지 않는다 [S1].

**Amazon Quick과 Quick Sight(개명)**: 공식 문서는 Amazon Quick이 Amazon QuickSight에서 진화했고, QuickSight는 Quick 안의 기능인 Amazon Quick Sight로 계속되며, 기존 QuickSight API·SDK·통합은 변경 없이 동작한다고 설명한다 [S2]. Quick은 자연어 채팅으로 작업 자동화·데이터 분석·웹 앱 구축·리서치를 하는 AI 기반 서비스이고, 그중 Quick Sight가 상호작용형 데이터 시각화와 BI(데이터 소스 연결, 대시보드 구축, 분석 임베드)를 맡는다 [S2]. 이 노트는 시험 가이드 표기("Amazon QuickSight")와 현재 공식 표기("Amazon Quick Sight")를 모두 같은 BI 기능으로 취급한다.

- **SPICE vs 직접 쿼리**: 데이터셋을 만들거나 편집할 때 SPICE 또는 직접 쿼리 중 하나를 고른다(업로드한 파일 데이터셋은 예외) [S3]. SPICE(in-memory 엔진)로 가져오면(ingest) 분석 쿼리가 더 빨리 처리되고 직접 쿼리를 기다릴 필요가 없으며, 쿼리당 과금되는 데이터 소스라도 SPICE에서는 데이터셋을 처음 만들 때와 새로 고칠 때만 쿼리 비용이 든다 [S3]. SPICE 용량은 리전별로 따로 할당되고, 한 리전의 같은 AWS 계정 사용자들이 공유하며, 관리자가 용량을 더 구매하거나 미사용분을 반납한다 [S3].
- **데이터셋 새로 고침**: SPICE 데이터셋은 전체 새로 고침(full refresh)이 기본이고, Redshift·Athena·PostgreSQL·Snowflake 같은 SQL 기반 소스는 look-back 윈도우 안에서만 증분 새로 고침을 할 수 있다 [S4]. 데이터베이스 스키마가 바뀌면 Quick Sight가 이를 자동 감지하지 못해 ingestion이 실패하므로 데이터셋을 편집·저장해 스키마를 갱신해야 한다 [S4].
- **과금 모델 개요**: Quick은 aws.com/quick에서 가입(Free·Plus 플랜)하거나 AWS 콘솔로 프로비저닝(IAM Identity Center 또는 IAM Federation, 사용자별 구독, 표준 AWS 청구)할 수 있다 [S2]. SPICE 용량은 별도로 구매·반납하는 자원이다 [S3]. 사용자 유형별 단가 숫자는 문서마다 달라 이 노트에 싣지 않았다 — gaps [상충] 참고.

### 데이터 확인·정리 도구 (Skill 3.2.2)

- **Lambda(이벤트 기반 검증)**: Amazon S3는 객체가 생성·삭제될 때 Lambda 이벤트 함수로 이벤트를 보낼 수 있고, 버킷에 알림을 설정하고 S3에 함수 호출 권한을 주면 된다. 트리거한 버킷과 같은 버킷에 함수가 다시 객체를 쓰면 함수가 스스로를 재호출하는 루프가 생길 수 있어, 버킷을 둘로 나누거나 수신 객체용 프리픽스에만 트리거를 건다 [S6].
- **Athena(SQL·CTAS 정리)**: CTAS는 다른 쿼리의 SELECT 결과로 Athena에 새 테이블을 만들고 데이터 파일을 S3의 지정 위치에 저장한다. 원본을 반복 조회하지 않고 한 번에 테이블을 만들고, 쿼리 결과를 Parquet·ORC 같은 저장 형식(또는 Iceberg)으로 변환하며, 필요한 데이터만 담은 테이블 사본을 만드는 데 쓴다 [S8].
- **Quick Sight 데이터 준비**: 데이터 준비 경험은 열한 가지 단계 유형을 제공하고, 단계를 순서대로 조합해 SQL 전문성 없이 정교한 변환을 만든다 [S5].
- **DataBrew 레시피**: 250개가 넘는 변환(이상치 필터링, 표준 형식 변환, 잘못된 값 교정 등)을 레시피 단계로 저장해 재사용한다 [S1].
- **Jupyter 노트북**: PySpark engine version 3에서는 Athena 콘솔 안의 노트북이 Jupyter 노트북과 호환된다 [S13]. Apache Spark version 3.5에서는 SageMaker Unified Studio 노트북에서 Spark 코드를 실행한다 [S13].
- **SageMaker Data Wrangler(현재 상태)**: 데이터 import·준비·변환·featurize·분석을 하는 도구로, 원래 SageMaker Studio Classic의 기능이었으나 Amazon SageMaker Canvas로 통합되었다. Canvas 안의 새 Data Wrangler에서는 시각적 인터페이스에 더해 자연어 인터페이스로 데이터를 탐색·변환할 수 있다 [S7].

### Redshift·Athena SQL로 쿼리·뷰 만들기 (Skill 3.2.3, v1.1 개정)

v1.1에서 이 Skill의 문구가 개정되었다(위 Skill 표의 v1.1 열). 현재 문구는 Redshift와 Athena의 SQL을 함께 명시한다. 시험은 뷰·구체화된 뷰·CTAS 중 무엇이 요구사항에 맞는지를 가른다.

- **Redshift 뷰**: 물리적으로 구체화되지 않으며, 뷰를 정의한 쿼리가 뷰를 참조할 때마다 실행된다. 외부 테이블로 뷰를 만들려면 WITH NO SCHEMA BINDING(late-binding view)을 쓴다. late-binding 뷰는 기반 객체(테이블·UDF 등)에 바인딩되지 않아 의존성이 없고, Redshift는 뷰를 쿼리할 때까지 의존성을 확인하지 않으며, 참조 객체가 없어도 뷰를 만들 수 있고, 참조 객체를 삭제·변경해도 뷰에 영향이 없다 [S10].
- **Redshift 구체화된 뷰(MV)**: 쿼리 결과를 저장하는 데이터베이스 객체로, 사전 계산된 결과 집합을 돌려주므로 기반 테이블에 접근하지 않아 훨씬 빠르다. 예측 가능하고 반복되는 쿼리(대시보드를 채우는 쿼리 등)에 특히 유용하다 [S11]. MV의 내용은 만들 때 시점의 상태이며 기반 테이블이 바뀌어도 그대로이므로, REFRESH MATERIALIZED VIEW로 수동 새로 고침하거나 autorefresh를 켠다 [S12]. 새로 고침 방식은 가능하면 증분(incremental) 새로 고침, 불가능하면 전체(full) 새로 고침(쿼리를 다시 실행해 모든 데이터를 교체)이며, 어느 쪽을 쓸지는 Redshift가 MV 정의 SELECT에 따라 자동 선택한다 [S12]. autorefresh는 기반 테이블 변경 후 가능한 한 빨리 반영하지만 사용자 워크로드를 우선해 멈추거나 지연될 수 있어, 결정적 동작이 필요하면 수동 또는 스케줄 새로 고침을 고려한다 [S12]. 2026-02-27부터 Auto REFRESH 쿼리는 백그라운드 자율 프로세스가 아니라 사용자 쿼리로 실행되어 다른 사용자 쿼리와 같은 우선순위로 돈다 [S12].
- **Athena 뷰**: 뷰는 물리 테이블이 아닌 논리 테이블이며 뷰를 정의한 쿼리는 뷰를 참조할 때마다 실행된다. Athena에는 두 종류의 뷰가 있다 — Athena 뷰와 AWS Glue Data Catalog 뷰 [S9]. Athena 뷰의 용도는 데이터 일부만 조회, 여러 테이블 결합(UNION ALL), 복잡성 숨기기, 쿼리 최적화 실험, 하위 테이블·열 이름 숨기기다 [S9]. Data Catalog 뷰는 Athena와 Redshift 같은 여러 AWS 서비스에 걸친 하나의 공통 뷰이고, 접근 권한이 뷰를 조회하는 사용자가 아니라 만든 사용자 기준으로 정해지며(definer semantics), 정의가 AWS Glue Data Catalog에 저장되므로 Lake Formation의 리소스·열 grant나 태그 기반 접근 제어로 권한을 줄 수 있다 [S9].
- **CTAS**: 쿼리 결과로 새 테이블을 만드는 문장으로 위 [데이터 확인·정리]에서 설명했다 [S8]. 뷰는 매번 쿼리를 실행하는 논리 객체이고 CTAS는 결과를 S3의 새 테이블로 저장한다는 점이 다르다 [S8][S9].
- **공지(Python UDF 종료)**: Redshift 문서 상단에 "Amazon Redshift will no longer support the use of Python UDFs after June 30, 2026"라는 공지가 있다 [S11]. Redshift SQL UDF/뷰를 다루는 문제에서는 Python UDF에 의존하는 선택지를 경계한다.

**비교 표 ② 뷰 vs 구체화된 뷰 vs CTAS**

| 구분 | 저장되는 것 | 데이터 최신성 | 적합한 경우 | 시험 단서 키워드 |
|---|---|---|---|---|
| 뷰(Redshift·Athena) | 쿼리 정의만(논리 테이블) [S9][S10] | 참조할 때마다 정의 쿼리 실행 [S9][S10] | 복잡성 숨기기, 조회 단순화 | "논리 테이블", "매번 실행" |
| Redshift 구체화된 뷰 | 사전 계산된 결과 집합 [S11] | 새로 고침 전까지 그대로(수동/autorefresh) [S12] | 반복되는 무거운 집계·대시보드 | "반복 쿼리 가속", "사전 계산" |
| Glue Data Catalog 뷰 | 정의가 Glue Data Catalog에 저장, Athena·Redshift 공용 [S9] | 참조할 때마다 실행 [S9] | 엔진 간 공통 뷰 + Lake Formation 권한 | "definer", "여러 서비스에서 같은 뷰" |
| Athena CTAS | 쿼리 결과를 담은 새 테이블 파일(S3) [S8] | 실행 시점의 결과 | 변환 결과를 Parquet·ORC·Iceberg로 저장 | "쿼리 결과로 새 테이블" |

### Athena 노트북과 Apache Spark (Skill 3.2.4)

- **무엇이고 왜**: Amazon Athena는 리소스를 계획·구성·관리하지 않고 Apache Spark로 데이터 분석·탐색을 대화형으로 실행하게 해 준다. Athena 위의 Spark는 서버리스이며 변하는 데이터 양과 처리 요구에 맞춰 자동 on-demand 스케일링을 제공한다 [S13].
- **두 릴리스 버전(중요, 현재 상태)**: Athena for Apache Spark는 PySpark engine version 3(이전 버전)과 Apache Spark version 3.5(현재 버전) 두 가지다 [S15]. PySpark engine version 3에서는 Athena 콘솔의 단순화된 노트북 경험으로 Python이나 Athena 노트북 API를 써 Spark 애플리케이션을 개발하고, 콘솔 노트북은 Jupyter 노트북과 호환되는 셀 기반 노트북이다 [S13]. Apache Spark version 3.5에서는 SageMaker Unified Studio 노트북 또는 Spark Connect 호환 클라이언트에서 Spark 코드를 실행하며, 이 버전은 Athena 콘솔 노트북과 노트북 API를 지원하지 않는다. PySpark engine version 3 워크그룹은 Spark 3.5로 업그레이드할 수 없다 [S13][S16]. PySpark engine version 3은 2027-04-01에 수명이 끝나, 이후에는 새 워크그룹을 만들 수 없고 기존 워크그룹도 세션·계산을 실행할 수 없다 [S15].
- **시작 절차(PySpark engine version 3)**: 먼저 Spark 엔진을 쓰는 Spark 활성 워크그룹을 만든다. 노트북을 열면 새 세션이 자동으로 시작된다. Spark 활성 워크그룹은 노트북 에디터를 쓸 수 있지만 쿼리 에디터는 쓸 수 없고, 쿼리 에디터는 Athena SQL 워크그룹만 쓴다. 노트북을 만들기 전에 Spark 활성 워크그룹부터 만들어야 한다 [S14]. Apache Spark version 3.5는 SageMaker Notebooks의 시작 가이드를 따른다 [S14].
- **Athena SQL vs Spark의 용량 모델**: Athena SQL은 용량 예약(capacity reservation)으로 전용 서버리스 처리 용량(DPU)을 확보할 수 있다 — DPU는 컴퓨트·메모리 단위이며 DPU 하나는 보통 4 vCPU와 16 GB 메모리다 [S17]. Spark는 필요한 컴퓨트·메모리를 Athena가 자동 결정해 확장한다 [S13].

| 구분 | Athena SQL | Athena Spark — PySpark engine version 3 | Athena Spark — Apache Spark version 3.5 |

| 용량·확장 | 용량 예약(DPU)으로 전용 용량 확보 가능 [S17] | 자동 on-demand 스케일링 [S13] | 자동 on-demand 스케일링 [S13] |

### 프로비저닝 vs 서버리스 트레이드오프 (Skill 3.2.5)

공통 원칙은 서버리스가 용량 계획·클러스터 운영 부담을 줄이고 변동 부하에 맞춰 자동 확장하는 대신, 예측 가능하고 꾸준한 부하에서는 프로비저닝(또는 예약)으로 비용·제어를 얻는 구도다. 서비스별 공식 문구는 다음과 같다.

- **Redshift Serverless vs 프로비저닝 클러스터**: Redshift Serverless는 데이터 웨어하우스 용량을 자동 프로비저닝하고 기반 리소스를 지능적으로 확장하며 용량을 초 단위로 조정한다. 프로비저닝 클러스터를 설정·튜닝·관리하지 않고 데이터에 접근·분석한다 [S18]. 컴퓨트는 on-demand(쓴 만큼 지불, 사용 패턴을 모르는 초기에 적합, 가장 유연)와 reservation(미리 정한 컴퓨트를 일정 기간 구매해 할인, 꾸준히 쓸 때 적합) 중에서 골라 구매하며 둘을 함께 쓸 수 있다. 저장소는 컴퓨트와 별도로 과금된다 [S19].
- **EMR Serverless vs 클러스터 기반 EMR**: EMR Serverless는 EMR의 배포 옵션으로 서버리스 런타임을 제공해 클러스터를 구성·최적화·보안·운영하지 않아도 된다. 과소·과대 프로비저닝을 피하고, 필요한 리소스를 자동 결정해 작업이 끝나면 해제한다. 몇 초 안의 응답이 필요한 대화형 분석에는 애플리케이션 생성 시 리소스를 사전 초기화할 수 있다. 오픈소스 프레임워크 운영 편의를 원하는 고객에게 적합하다 [S20].
- **Kinesis Data Streams 용량 모드**: 모드는 데이터 스트림의 용량이 어떻게 관리되고 사용량이 어떻게 과금되는지를 정하며, On-demand Standard·On-demand Advantage·Provisioned가 있다 [S21]. On-demand는 용량 계획이 필요 없고 자동 확장하며, 예측 불가능하고 변동이 큰 트래픽에 적합하고, 기록·조회한 GB 단위로 과금한다. 이전 30일 동안 관측한 최대 쓰기 처리량의 두 배까지 수용한다 [S21]. Provisioned는 스트림의 샤드 수를 직접 지정하며, 예측 가능한 트래픽·쉬운 용량 예측·샤드 분산의 세밀한 제어가 필요할 때 적합하다. 파티션 키가 매우 불균등하면 granular shard split을 지원하는 provisioned 모드를 권장한다 [S21]. On-demand Advantage는 계정 수준 설정으로 더 많은 기능과 다른 요금 구조를 제공한다 [S21].
- **Athena**: Athena SQL과 Spark는 서버리스다 [S13][S17]. 용량 예약은 중요한 워크로드를 격리하고 예측 가능한 실행·비용을 주며, 예약 용량에서 도는 쿼리는 DDL·DML 쿼리 할당량에 포함되지 않는다 [S17].

**비교 표 ④ 프로비저닝/예약 vs 서버리스/온디맨드**

| 서비스 | 서버리스·온디맨드가 맞는 경우 | 프로비저닝·예약이 맞는 경우 | 요금·제약 | 시험 단서 키워드 |
|---|---|---|---|---|
| Amazon Redshift | 클러스터 설정·튜닝·관리를 피하고 예측 불가한 워크로드를 자동 확장 [S18] | 꾸준히 쓸 때는 reservation으로 할인 [S19] | on-demand=쓴 만큼, reservation=기간 약정 할인, 저장소 별도 [S19] | "관리 부담 최소", "사용 패턴 불명" |
| Amazon EMR | 클러스터 운영 없이 Spark/Hive 작업, 과소·과대 프로비저닝 회피 [S20] | (클러스터를 직접 구성·운영하는 EMR) | 필요 리소스를 자동 결정·해제, 대화형은 사전 초기화 [S20] | "클러스터 관리 없이" |
| Kinesis Data Streams | 용량 계획 없이 변동·예측 불가 트래픽 [S21] | 예측 가능 트래픽·세밀한 샤드 제어 [S21] | on-demand=GB 단위 과금, provisioned=샤드 수 지정 [S21] | "unpredictable", "shard 수 지정" |
| Amazon Athena | 리소스 계획·구성·관리가 필요 없는 서버리스 [S13] | 용량 예약(DPU)으로 전용 용량·예측 가능한 성능 [S17] | DPU = 4 vCPU/16 GB, 예약 워크그룹 쿼리는 DML 할당량 제외 [S17] | "워크로드 격리", "예측 가능한 비용" |

### 집계·롤링 평균·그룹화·피벗 (Skill 3.2.6)

- **집계와 그룹화(GROUP BY)**: 그룹 함수는 결과 행을 집계하는 반면 윈도 함수는 모든 행을 유지한다 [S22]. Athena에서 GROUP BY를 쓰면 SELECT의 모든 출력 식은 집계 함수이거나 GROUP BY 절에 있는 열이어야 한다. HAVING은 그룹과 집계가 계산된 뒤에 그룹을 걸러낸다 [S24].
- **GROUPING SETS·CUBE·ROLLUP**: 한 문장으로 여러 GROUP BY 연산을 수행하는 집계 확장이다. GROUPING SETS는 그룹화할 여러 열 목록을 지정하고, CUBE는 주어진 열 집합의 가능한 모든 그룹화 조합을, ROLLUP은 가능한 모든 소계를 만든다. 이런 복합 그룹화는 표현식이 아니라 열 이름만 허용한다 [S24].
- **윈도 함수와 롤링(이동) 평균**: 윈도 함수는 결과 집합의 파티션("윈도")에 대해 계산하되 윈도의 모든 행에 값을 돌려준다. 윈도 명세(OVER)는 PARTITION BY(그룹 나누기, GROUP BY와 비슷), ORDER BY(순서), 윈도 프레임(ROWS 명세, 각 행 기준으로 행 집합을 더 제한)으로 이루어진다. 윈도 함수는 쿼리의 마지막 연산이라 select list나 ORDER BY 절에서만 쓸 수 있다 [S22]. 집계 함수에 ORDER BY를 쓰면 명시적 frame 절이 필요하고, Redshift 문서는 날짜별 판매 수량의 rolling average 예제를 제공한다 [S23]. 즉 롤링 평균은 AVG() OVER (ORDER BY … ROWS …) 형태의 프레임 지정 윈도 함수다. (용어 정의 자체를 설명하는 공식 페이지는 찾지 못해 이 연결은 위 문서 두 곳을 근거로 한 정리다 — gaps [불확실].)
- **피벗**: Redshift의 PIVOT·UNPIVOT은 FROM 절의 파라미터로 쿼리 출력을 행→열, 열→행으로 회전한다 [S25]. Quick Sight 데이터 준비의 Pivot 단계는 행 값을 고유 열로 바꿔 long 형식을 wide 형식으로 만들며 값 필터링·집계·그룹화를 지정한다 [S5]. Athena SELECT 레퍼런스에는 PIVOT 절 설명이 없다 — Athena에서의 피벗 방법은 공식 근거를 찾지 못했다(gaps [불확실]) [S24].

**비교 표 ⑤ 집계·그룹화·윈도·피벗 구분**

| 개념 | 핵심 동작 | 구문 | 시험 단서 키워드 |
|---|---|---|---|
| 그룹화·집계 | 행을 그룹으로 묶어 그룹당 한 행 반환 [S22][S24] | GROUP BY + 집계 함수, HAVING은 집계 후 필터 [S24] | "그룹별 합계" |
| 소계·교차 집계 | 한 문장에 여러 GROUP BY [S24] | GROUPING SETS / CUBE / ROLLUP [S24] | "소계", "모든 조합" |
| 롤링(이동) 평균 | 모든 행을 유지하며 프레임 범위로 평균 [S22][S23] | AVG() OVER (ORDER BY …, ROWS 프레임) [S23] | "이동 평균", "최근 N행" |
| 피벗 | 행 값을 열로 회전(long→wide) [S25][S5] | Redshift PIVOT/UNPIVOT, Quick Pivot 단계 [S25][S5] | "행을 열로" |

## 시험에서 묻는 방식

1. **뷰·구체화된 뷰·CTAS 선택** — 시나리오 요지: 대시보드가 같은 복잡한 조인·집계 쿼리를 하루 종일 반복하고 응답이 느리다 / 분석가가 복잡한 쿼리를 숨긴 단순한 조회 객체가 필요하다 / Athena와 Redshift가 같은 뷰를 쓰고 Lake Formation으로 권한을 관리해야 한다 / 쿼리 결과를 Parquet 테이블로 저장해야 한다. 요구사항 키워드: "반복되는 쿼리", "사전 계산", "여러 서비스에서 공통", "결과를 새 테이블로". → 정답 방향: 첫째는 Redshift 구체화된 뷰(필요하면 autorefresh), 둘째는 일반 뷰, 셋째는 Glue Data Catalog 뷰(definer semantics, Lake Formation 권한), 넷째는 Athena CTAS. → 오답 후보와 탈락 이유: 일반 뷰는 참조할 때마다 정의 쿼리를 다시 실행하므로 반복 쿼리 가속이 안 됨, 구체화된 뷰는 새로 고침 전까지 기반 테이블 변경이 반영되지 않음, Athena 뷰는 Athena 안에서만 동작, CTAS는 결과를 한 번 저장할 뿐 쿼리를 재실행하는 뷰가 아님. 근거 [S8][S9][S10][S11][S12].
2. **서버리스 vs 프로비저닝 서비스 선택** — 시나리오 요지: 트래픽 변동이 크고 예측 불가하며 용량 계획·클러스터 운영 부담을 줄이고 싶다 / 사용량이 꾸준하고 예측 가능해 비용을 낮추고 제어하고 싶다. 요구사항 키워드: "예측 불가", "운영 오버헤드 최소", "꾸준한 사용", "세밀한 제어". → 정답 방향: 전자는 서버리스·온디맨드(Redshift Serverless, EMR Serverless, Kinesis on-demand 모드, Athena), 후자는 예약/프로비저닝(Redshift Serverless reservation, Kinesis provisioned 모드의 샤드 지정, Athena 용량 예약). → 오답 후보와 탈락 이유: provisioned Kinesis는 샤드 수를 직접 지정해야 해 변동 트래픽에 용량 계획 부담, on-demand Kinesis는 매우 불균등한 파티션 키에서는 쓰기 예외가 계속될 수 있어 granular shard split이 되는 provisioned를 권장. 근거 [S17][S18][S19][S20][S21].
3. **Athena Spark 노트북 사용 절차·버전 판별** — 시나리오 요지: Athena에서 PySpark 노트북으로 S3 데이터를 탐색하려 한다. 요구사항 키워드: "Athena 노트북", "Spark", "워크그룹". → 정답 방향: 먼저 Spark 엔진을 쓰는 Spark 활성 워크그룹을 만들고(PySpark engine version 3) 노트북 에디터에서 노트북을 연다(세션 자동 시작). Spark 3.5는 Athena 콘솔 노트북이 아니라 SageMaker Unified Studio 노트북·Spark Connect 클라이언트를 쓴다. → 오답 후보와 탈락 이유: Athena SQL 워크그룹의 쿼리 에디터(Spark 워크그룹은 쿼리 에디터 불가), 노트북부터 만들기(워크그룹이 먼저), 기존 PySpark engine version 3 워크그룹을 3.5로 업그레이드(불가). 근거 [S13][S14][S15][S16].
4. **시각화/BI와 SQL 분석 개념** — 시나리오 요지: (a) 쿼리당 과금되는 데이터 소스를 대시보드가 반복 조회해 비용·지연이 크다 → Quick Sight 데이터셋을 SPICE로 가져온다(소스가 바뀌면 새로 고침, SQL 기반 소스는 증분 가능). (b) 최근 N일 이동 평균을 각 행에 붙이되 행을 줄이지 않는다 → 윈도 함수 AVG() OVER (ORDER BY … ROWS …) (GROUP BY는 행을 집계해 줄임). (c) 행을 열로 회전 → Redshift PIVOT 또는 Quick Pivot 단계. 요구사항 키워드: "SPICE", "이동 평균", "행을 유지", "소계". → 오답 후보와 탈락 이유: 직접 쿼리는 매번 소스를 조회, GROUP BY는 그룹당 한 행으로 줄어듦, ROLLUP/CUBE는 소계·조합 집계용. 근거 [S3][S4][S22][S23][S24][S25].

## 흔한 함정·혼동 짝

1. **뷰 vs 구체화된 뷰(Redshift)** — 뷰는 정의 쿼리를 참조할 때마다 실행하는 논리 객체, 구체화된 뷰는 사전 계산된 결과를 저장해 새로 고침 전까지 기반 테이블 변경이 반영되지 않는다 → 시험 단서: "반복되는 쿼리 가속", "항상 최신 데이터" [S10][S11][S12]
2. **표준 뷰 vs late-binding 뷰(Redshift)** — late-binding(WITH NO SCHEMA BINDING)은 기반 객체와 의존성이 없어 객체가 없어도 뷰를 만들고 쿼리 시점에야 의존성을 확인하며, 외부 테이블로 뷰를 만들 때 필요하다 → 시험 단서: "외부 테이블 뷰", "참조 객체 삭제 후에도 뷰 유지" [S10]
3. **Athena 뷰 vs Glue Data Catalog 뷰** — Athena 뷰는 Athena 안에서 동작, Data Catalog 뷰는 Athena·Redshift 공통 하나의 뷰이며 정의가 Glue Data Catalog에 저장되고 definer semantics(뷰 생성자 권한)로 Lake Formation이 권한을 준다 → 시험 단서: "여러 서비스 공통 뷰", "기반 테이블 접근 없이 뷰만 접근" [S9]
4. **뷰 vs CTAS** — 뷰는 데이터를 담지 않고 매번 쿼리를 실행, CTAS는 결과를 S3의 새 테이블(파일)로 저장한다 → 시험 단서: "쿼리 결과를 Parquet로 저장" [S8][S9]
5. **MV 수동 새로 고침 vs autorefresh vs 증분/전체** — 새로 고침 전까지 MV 내용은 그대로이고, autorefresh는 가능한 한 빨리 반영하지만 사용자 워크로드를 우선해 지연될 수 있으며, 증분/전체 방식은 Redshift가 정의에 따라 자동 선택한다 → 시험 단서: "결정적(deterministic) 새로 고침", "스케줄 새로 고침" [S12]
6. **SPICE vs 직접 쿼리(Quick Sight)** — 데이터셋 생성·편집 시 둘 중 하나를 고른다(업로드한 파일 데이터셋은 선택 대상이 아님). SPICE는 가져온 스냅샷으로 빠르고 쿼리 비용은 생성·새로 고침 때만, 용량은 리전별로 구매·반납 → 시험 단서: "쿼리당 과금", "대시보드 응답 속도", "스냅샷 새로 고침" [S3][S4]
7. **Amazon QuickSight vs Amazon Quick vs Amazon Quick Sight** — Quick은 QuickSight에서 진화한 상위 서비스, QuickSight는 Quick 안의 기능 Quick Sight로 계속되며 기존 API·SDK는 그대로 동작 → 시험 단서: 시험 가이드/선택지 표기가 "QuickSight"여도 같은 BI 기능 [S2]
8. **DataBrew vs SageMaker Data Wrangler vs Quick 데이터 준비** — DataBrew=코드 없는 시각적 정리·정규화(레시피, 250+ 변환), Data Wrangler=ML 데이터 준비(SageMaker Canvas로 통합), Quick 데이터 준비=BI 데이터셋용 단계형 변환 → 시험 단서: "ML 피처 준비", "코드 없이 정리", "BI 데이터셋" [S1][S5][S7]
9. **Athena SQL 워크그룹 vs Spark 활성 워크그룹** — 쿼리 에디터는 Athena SQL 워크그룹만, 노트북 에디터는 Spark 활성 워크그룹만 쓴다. 노트북보다 워크그룹을 먼저 만든다 → 시험 단서: "노트북이 안 열림", "쿼리 에디터에서 Spark" [S14]
10. **PySpark engine version 3 vs Apache Spark version 3.5** — 콘솔 노트북은 engine version 3 한정(2027-04-01 수명 종료), 3.5는 SageMaker Unified Studio 노트북·Spark Connect이며 engine version 3 워크그룹은 3.5로 업그레이드 불가 → 시험 단서: "Athena 콘솔 노트북", "SageMaker Unified Studio로 이전" [S13][S15][S16]
11. **Redshift Serverless on-demand vs reservation** — on-demand는 쓴 만큼 지불·사용 패턴이 불명할 때, reservation은 꾸준히 쓸 때 할인(둘을 함께 사용 가능) → 시험 단서: "사용 패턴 불명", "꾸준한 사용", "할인" [S19]
12. **Kinesis on-demand vs provisioned** — on-demand는 용량 계획 불필요·예측 불가 트래픽·GB 단위 과금(이전 30일 피크의 두 배까지 수용), provisioned는 샤드 수 직접 지정·예측 가능 트래픽·세밀한 샤드 제어 → 시험 단서: "예측 불가 트래픽", "샤드 수 지정", "불균등 파티션 키" [S21]
13. **GROUP BY vs 윈도 함수** — GROUP BY/집계 함수는 행을 집계해 줄이고, 윈도 함수는 모든 행을 유지하며 select list·ORDER BY에서만 쓸 수 있다 → 시험 단서: "각 행에 이동 평균", "행 수 유지" [S22]
14. **ROLLUP vs CUBE vs GROUPING SETS** — ROLLUP=소계, CUBE=열 집합의 가능한 모든 그룹화, GROUPING SETS=지정한 열 목록들 → 시험 단서: "소계", "모든 조합" [S24]
15. **PIVOT vs UNPIVOT** — PIVOT=행→열(long→wide), UNPIVOT=열→행. Redshift는 FROM 절 파라미터, Quick은 데이터 준비 Pivot 단계. Athena SELECT 레퍼런스에는 PIVOT 절 설명이 없음 → 시험 단서: "행을 열로", "Athena 피벗" [S5][S24][S25]
16. **Lambda S3 트리거 재귀** — 같은 버킷에 결과를 쓰면 함수가 스스로를 호출하는 루프가 생긴다. 버킷을 분리하거나 프리픽스로 트리거 범위를 제한 → 시험 단서: "무한 호출", "정리 결과를 같은 버킷에 저장" [S6]

### 후보 1 — Skill 3.2.1 · associate
- **문제**: 한 회사가 Amazon Athena의 대용량 데이터를 Amazon Quick Sight 대시보드로 보여 준다. 사용자 수백 명이 같은 대시보드를 반복해서 열어 Athena 쿼리가 계속 실행되고, 응답이 느리며 쿼리 비용이 늘고 있다. 대시보드 응답 속도를 높이고 반복 쿼리 비용을 줄이려면 어떻게 해야 하는가?
- **보기**: A. 데이터셋을 직접 쿼리 모드로 유지한다. / B. 데이터셋을 SPICE로 가져오고(ingest) 필요할 때 새로 고침한다. / C. 대시보드마다 Athena 워크그룹을 따로 만든다. / D. 대시보드를 열 때마다 DataBrew 프로파일링을 실행한다.

- **해설 초안**: 데이터셋을 SPICE로 가져오면 분석 쿼리가 더 빨리 처리되고 직접 쿼리를 기다릴 필요가 없다. SPICE 데이터는 추가 비용 없이 여러 번 재사용되며, 쿼리당 과금되는 소스라도 쿼리 비용은 데이터셋을 만들 때와 새로 고칠 때만 든다. [S3]
- **오답 근거**: A — 직접 쿼리는 처리될 때까지 기다려야 하는 방식이라 반복 열람 응답 개선에 맞지 않음 / C — 워크그룹을 나눠도 같은 쿼리의 반복 실행 자체는 줄지 않음 / D — DataBrew는 데이터를 시각적으로 정리·정규화하는 도구로 BI 대시보드 가속과 무관
- **근거**: [S3] https://docs.aws.amazon.com/quick/latest/userguide/spice.html — "Data stored in SPICE can be reused multiple times without incurring additional costs."

### 후보 2 — Skill 3.2.3 · associate
- **문제**: Amazon Redshift에서 수십억 행 테이블을 조인·집계하는 동일한 쿼리를 BI 대시보드가 하루 종일 반복 실행한다. 응답 시간을 줄이고 기반 테이블의 변경 사항도 자동으로 반영하려 한다. 가장 적합한 방법은?
- **보기**: A. 일반 뷰(CREATE VIEW)를 만든다. / B. 구체화된 뷰를 만들고 autorefresh 옵션을 켠다. / C. Athena CTAS로 결과를 S3에 저장한다. / D. WITH NO SCHEMA BINDING 뷰를 만든다.
- **정답**: B
- **해설 초안**: 구체화된 뷰는 사전 계산된 결과 집합을 돌려주어 기반 테이블에 접근하지 않으므로 빠르며, 예측 가능하고 반복되는 쿼리(대시보드)에 특히 유용하다. autorefresh를 켜면 기반 테이블 변경 후 가능한 한 빨리 반영된다(워크로드에 밀려 지연될 수 있음). [S11][S12]
- **오답 근거**: A — 일반 뷰는 참조할 때마다 정의 쿼리를 다시 실행 / C — CTAS는 Athena 기능으로 쿼리 결과를 새 테이블로 저장하는 문장이며 Redshift 쿼리 가속·자동 반영이 목적이 아님 / D — late-binding 뷰도 뷰이므로 매번 실행되며 기반 객체와의 의존성을 끊는 용도
- **근거**: [S11] https://docs.aws.amazon.com/redshift/latest/dg/materialized-view-overview.html — "Materialized views are especially useful for speeding up queries that are predictable and repeated."

### 후보 3 — Skill 3.2.4 · associate
- **문제**: 데이터 엔지니어가 Athena 콘솔에서 PySpark 노트북으로 S3 데이터를 탐색하려 한다. PySpark engine version 3 환경에서 가장 먼저 해야 하는 일은?
- **보기**: A. Athena 쿼리 에디터에서 새 노트북을 만든다. / B. Spark 엔진을 쓰는 Spark 활성 워크그룹을 만들고 그 워크그룹으로 전환한다. / C. 기존 PySpark engine version 3 워크그룹을 Apache Spark version 3.5로 업그레이드한다. / D. SageMaker Data Wrangler 데이터 플로를 만든다.
- **정답**: B
- **해설 초안**: Apache Spark를 Athena에서 쓰려면 먼저 Spark 활성 워크그룹을 만들어야 하며, 그 워크그룹으로 전환한 뒤 노트북을 열면 새 세션이 자동으로 시작된다. Spark 활성 워크그룹은 노트북 에디터를 쓰고 쿼리 에디터는 Athena SQL 워크그룹만 쓴다. [S14]
- **오답 근거**: A — 쿼리 에디터는 Athena SQL 워크그룹 전용이고 노트북부터 만들 수 없음(워크그룹이 먼저) / C — PySpark engine version 3 워크그룹은 Apache Spark version 3.5로 업그레이드할 수 없음 / D — Data Wrangler는 SageMaker Canvas의 ML 데이터 준비 기능

### 후보 5 — Skill 3.2.6 · associate
- **문제**: 분석가가 일별 판매 테이블의 각 행에 같은 제품의 최근 일정 행 수 기준 이동(rolling) 평균을 붙이되, 결과의 행 수는 줄어들지 않아야 한다. Amazon Redshift SQL에서 적절한 방법은?
- **보기**: A. GROUP BY와 AVG()를 사용한다. / B. 프레임(ROWS …)을 지정한 AVG() OVER (PARTITION BY … ORDER BY …) 윈도 함수를 사용한다. / C. GROUP BY ROLLUP을 사용한다. / D. FROM 절에 PIVOT를 사용한다.
- **정답**: B
- **해설 초안**: 윈도 함수는 윈도의 모든 행을 유지하며 값을 돌려주고, ORDER BY를 쓰는 집계 윈도 함수에는 명시적 프레임 절이 필요하다. Redshift 문서가 날짜별 판매 수량의 rolling average 예제를 제공한다. [S22][S23]
- **오답 근거**: A — 그룹 함수는 결과 행을 집계해 행 수가 줄어듦 / C — ROLLUP은 소계를 만드는 집계 확장 / D — PIVOT는 행을 열로 회전
- **근거**: [S23] https://docs.aws.amazon.com/redshift/latest/dg/r_WF_AVG.html — "The following example computes a rolling average of quantities sold by date"
