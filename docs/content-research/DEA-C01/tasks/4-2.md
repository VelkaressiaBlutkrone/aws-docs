### 사용자 지정 IAM 정책 — 관리형 vs 고객 관리형 vs 인라인, 조건, 권한 경계 (Skill 4.2.1)

AWS 관리형 정책이 요구에 맞지 않을 때 직접 정책을 만드는 선택지와 그 범위를 좁히는 장치를 묻는다.

- **세 가지 ID 기반 정책**: AWS 관리형 정책은 AWS가 만들고 관리하며 권한을 바꿀 수 없다. [S1] AWS가 권한을 업데이트하면 정책이 붙은 모든 주체에 영향이 간다. [S1] 고객 관리형 정책은 내 계정에 만들어 여러 주체에 붙이는 독립 정책이며, 기존 AWS 관리형 정책을 복사해 시작하는 방법이 좋다. [S1] 인라인 정책은 단일 IAM 자격 증명(사용자·그룹·역할)에 일대일로 묶이고 자격 증명을 삭제하면 함께 삭제된다. [S1] 정책이 둘 이상의 엔터티에 적용될 수 있으면 관리형이 낫다. [S1]
- **왜 사용자 지정인가**: AWS 관리형 정책은 모든 고객이 쓰도록 만들어져 특정 사용 사례에 최소 권한이 아닐 수 있으므로, 고객 관리형 정책으로 권한을 더 줄이라고 권고한다. [S3]
- **조건(Condition)**: 정책 문이 유효한 조건을 지정할 수 있다. 예를 들어 모든 요청이 TLS로 와야 한다는 조건을 둘 수 있다. [S3] 한 Condition 블록의 모든 컨텍스트 키가 true로 평가되어야 Allow/Deny 효과가 발동하고 [S2], 연산자나 키가 여러 개면 AND, 한 키의 값이 여러 개면 OR로 평가된다. [S2]
- **권한 경계**: 관리형 정책으로 ID 기반 정책이 IAM 엔터티에 부여할 수 있는 최대 권한을 설정하는 고급 기능이며 권한 경계 자체는 권한을 주지 않는다. [S3] 개발자에게 역할 생성·관리를 위임하되 최대 권한을 제한할 때 쓴다. [S3]
- **조직 수준 가드레일**: SCP·RCP로 조직·OU·계정 수준 가드레일을 세우지만 SCP·RCP는 권한을 부여하지 못하므로 ID 기반 또는 리소스 기반 정책이 따로 필요하다. [S3]

| 구분 | 누가 관리·수정 | 적용 대상 | 시험 단서 | 근거 |
|---|---|---|---|---|
| AWS 관리형 정책 | AWS(수정 불가) | 여러 주체 | "빠른 시작", "최소 권한 아님" | [S1][S3] |
| 고객 관리형 정책 | 사용자(수정 가능) | 여러 주체 | "여러 역할에 같은 맞춤 권한", "AWS 관리형을 복사해 축소" | [S1][S3] |
| 인라인 정책 | 사용자(수정 가능) | 단일 ID와 일대일 | "이 역할에만 적용", "ID 삭제 시 함께 삭제" | [S1] |
| 권한 경계 | 사용자 | IAM 사용자·역할 | "개발자에게 역할 생성 위임 + 최대 권한 제한" | [S3] |
| SCP·RCP | 조직 관리자 | 조직·OU·계정 | "권한을 주지 않는 가드레일" | [S3] |

### 애플리케이션·DB 자격 증명 저장 — Secrets Manager vs Parameter Store (Skill 4.2.2)

"비밀을 코드에서 빼내 안전하게 저장한다"는 같은 목적을 두 서비스가 다른 기능·비용 구조로 푼다. 시험은 요구사항 키워드(자동 회전, 값 크기, 비용, 계정 간 공유)로 고르게 한다. 회전 메커니즘 자체(관리형 회전, Lambda 회전, 스테이징 레이블)와 교차 계정 비밀 접근은 4-1.md를 참조한다.

- **Secrets Manager**: 비밀을 회전하고 관리하고 조회하는 서비스다. [S7] 저장한 비밀 수와 API 호출 수로 과금하고 [S7], 회전으로 만든 새 버전에는 과금하지 않는다. [S7] 비밀 값은 텍스트·바이너리 모두 최대 65,536바이트까지 저장한다. [S8]
- **Parameter Store**: 표준과 고급 두 티어가 있다. [S5] 표준은 값 4 KB·계정/리전당 10,000개·추가 비용 없음·파라미터 정책 불가이고, 고급은 값 8 KB·계정/리전당 100,000개·요금 발생·파라미터 정책 가능이다. [S5] 표준→고급 변경은 언제든 가능하지만 고급→표준으로 되돌릴 수 없다. [S5]
- **파라미터 정책은 회전이 아니다**: 지원하는 정책 유형은 Expiration(만료 시 삭제), ExpirationNotification, NoChangeNotification(변경 없음 알림)뿐이다. [S5] 파라미터는 최근 100개 버전을 유지한다. [S5]
- **SecureString**: KMS 키로 암호화하며 키 ID를 지정하지 않으면 계정 기본 키를 쓰는데 사용자 지정 키보다 안전하지 않다고 안내한다. [S5]
- **계정 간 공유**: 고급 파라미터는 AWS RAM으로 다른 계정과 공유한다. [S6]
- **Glue 연결과 Secrets Manager**: 데이터 스토어 연결 자격 증명은 Secrets Manager에 두는 것을 권장하며, Glue가 ETL 작업·크롤러 실행 시점에 비밀을 조회한다. [S9] Glue용 IAM 역할에 비밀 조회 권한을 줘야 하고 AWSGlueServiceRole 관리형 정책에는 Secrets Manager 권한이 없다. [S9] 네트워크 구성에 따라 Secrets Manager VPC 엔드포인트가 필요할 수 있다. [S9]

| 항목 | Secrets Manager | Parameter Store 표준 | Parameter Store 고급 |
|---|---|---|---|
| 핵심 용도 | 비밀의 회전·관리·조회 [S7] | 일반 파라미터(값 4 KB 이하, 정책 불필요) [S5] | 큰 값·정책·계정 간 공유 [S5][S6] |
| 값 크기 | 최대 65,536바이트 [S8] | 4 KB [S5] | 8 KB [S5] |
| 개수 한도(계정·리전당) | 이 노트에서 수집하지 못함(gaps) | 10,000개 [S5] | 100,000개 [S5] |
| 자동 회전 | 비밀 회전 지원 [S7] | 회전 유형의 파라미터 정책은 없음(지원 유형은 만료·알림, gaps 참조) [S5] | 회전 유형의 파라미터 정책은 없음(지원 유형은 만료·알림, gaps 참조) [S5] |
| 요금 | 비밀 수 + API 호출 수 [S7] | 추가 비용 없음 [S5] | 요금 발생 [S5] |
| 파라미터 정책 | 해당 없음 | 불가 [S5] | 가능 [S5] |
| 계정 간 공유 | 4-1.md 참조(리소스 정책 + KMS 키) | 공유는 고급 파라미터 대상 [S6] | AWS RAM [S6] |
| 시험 단서 | "자동 교체", "DB 자격 증명", "Glue 연결 자격 증명" | "무료", "구성 값", "계층적 이름" [S5] | "4 KB 초과", "정책(만료·알림)", "계정 간 공유" |

### 데이터베이스 사용자·그룹·역할 권한 — Amazon Redshift 중심 (Skill 4.2.3)

- **RBAC(역할 기반)**: 권한을 역할에 모아 사용자에게 부여해 보안 권한 관리를 단순화하고, 권한 부여·회수를 개별 객체가 아니라 역할 수준에서 한다. [S10] 역할에 권한을 나눠 담으면 사용자는 역할이 허용한 작업만 할 수 있어 최소 권한 원칙이 적용된다. [S10]
- **열 수준 + 행 수준(RLS)**: 열 수준 보안으로 일부 열에만 권한을 주고, RLS 정책으로 보이는 열의 특정 행까지 추가로 제한한다. [S11] RLS는 사용자나 역할이 스키마·테이블 안의 어떤 레코드에 접근할 수 있는지를 객체 수준 보안 정책으로 정한다. [S11]
- **동적 데이터 마스킹(DDM)**: 데이터를 변형하지 않고 쿼리 시점에 민감 데이터가 보이는 방식을 바꾼다. [S12] 마스킹 정책은 특정 사용자나 역할에 적용하며 조건부 열로 셀 수준 마스킹도 가능하고, 같은 열에 여러 정책이 걸리면 적용 우선순위로 충돌을 해결한다. [S12]
- **IAM 기반 임시 DB 자격 증명**: GetClusterCredentials는 임시 DB 사용자 이름과 암호를 돌려주며, 기본 만료는 900초이고 900~3600초 범위에서 지정할 수 있다. [S13]
- **RDS IAM 데이터베이스 인증**: 암호 대신 인증 토큰을 쓰며 토큰은 생성 후 15분간 유효하고 코드에 암호를 넣지 않아도 된다. [S14]

| 제어 수단 | 무엇을 제한하나 | 부여 단위 | 시험 단서 | 근거 |
|---|---|---|---|---|
| RBAC | 역할에 모은 권한(사용자는 역할이 허용한 작업만 수행) | 역할 → 사용자 | "권한 변경을 역할 한 곳에서" | [S10] |
| 열 수준 권한 | 접근 가능한 열(열의 부분 집합) | 사용자에게 열 단위로 부여 | "일부 열만 조회" | [S11] |
| RLS | 접근 가능한 행 | 정책을 사용자/역할에 연결 | "팀·리전별로 보이는 행이 다름" | [S11] |
| DDM | 값이 보이는 방식(마스킹) | 마스킹 정책을 사용자/역할에 연결(우선순위) | "카드 번호 일부만 표시", "셀 단위 조건부" | [S12] |
| IAM 임시 자격 증명 | 로그인 자격 증명 | IAM 정책 + GetClusterCredentials | "암호 없이 IAM으로 DB 접속" | [S13] |

### Lake Formation 권한 관리 (Skill 4.2.4)

데이터 레이크의 Data Catalog 리소스와 S3 기반 데이터를 한 곳에서 GRANT/REVOKE로 관리하고 [S15], 통합 서비스(Athena·Redshift Spectrum·EMR·Glue)가 그 권한을 따른다. [S21]

- **두 종류 권한**: 메타데이터 접근(Data Catalog 권한)과 기반 데이터 접근(S3 위치의 데이터 접근·데이터 위치 권한)이다. [S15] 모델은 DBMS 스타일 GRANT/REVOKE 명령으로 구현된다. [S15]
- **IAM 권한과 Lake Formation 권한은 함께 필요**하다. 요청이 성공하려면 IAM과 Lake Formation 검사를 모두 통과해야 하고, IAM 권한은 Lake Formation·Glue API와 리소스 접근을, Lake Formation 권한은 Data Catalog 리소스·S3 위치·기반 데이터 접근을 통제한다. [S15] Lake Formation 권한은 부여한 리전에서만 유효하다. [S15]
- **S3 위치 등록**: Lake Formation이 기반 데이터 접근을 통제하려면 S3 위치를 등록하고, 등록할 때 읽기/쓰기 권한이 있는 IAM 역할을 지정한다. [S16] 통합 서비스가 접근을 요청하면 Lake Formation이 그 역할로 임시 자격 증명을 공급한다. [S16] 위치는 버킷이나 버킷 아래 프리픽스이고 개별 S3 객체는 아니다. [S16]
- **LF-TBAC(태그 기반)**: 속성(LF-Tag)에 따라 권한을 정하는 인가 전략으로, LF-Tag를 Data Catalog 리소스에 붙이고 그 태그로 주체에게 권한을 부여한다. [S17] 리소스가 많을 때 권장되는 방법이다. [S17] IAM 태그와 LF-Tag는 같지 않으며 서로 바꿔 쓸 수 없다. [S17]
- **데이터 필터(행·열·셀)**: 데이터 필터로 열 수준·행 수준·셀 수준 보안을 구현하고, 각 필터는 하나의 Data Catalog 테이블에 속한다. [S18] 한 테이블에 필터를 여러 개 만들어 두고 테이블 권한을 부여할 때 하나 이상을 골라 쓴다. [S18] 필터를 채우는 방식에 따라 보안 수준이 정해진다: "모든 열" 와일드카드 + 행 필터 표현식이면 행 수준, 특정 열 포함/제외 + "모든 행"이면 열 수준, 특정 열 포함/제외 + 행 필터 표현식이면 셀 수준이다. [S25] 필터는 읽기 작업에만 적용되므로 필터와 함께 부여할 수 있는 Lake Formation 권한은 SELECT뿐이다. [S25]
- **교차 계정 공유**: 명명된 리소스 방식이나 LF-Tag로 계정 간 공유를 하고 [S19], Lake Formation은 AWS RAM으로 계정 간 권한 부여를 처리한다. [S19] 수신 계정에서 Athena나 Redshift Spectrum으로 조회하려면 공유 리소스에 대한 리소스 링크가 필요하다. [S19]
- **하이브리드 접근 모드**: 같은 Data Catalog 객체에 두 가지 권한 경로를 제공한다. [S20] 선택해서 옵트인한 주체는 Lake Formation 권한과 IAM 권한을 모두 요구받고, 옵트인하지 않은 주체는 기존처럼 IAM 권한만으로 접근한다. [S20] 그래서 다른 기존 사용자·워크로드의 접근을 끊지 않고 일부 사용자에게만 점진 도입할 수 있다. [S20]
- **통합 서비스**: Lake Formation에 데이터를 등록하면 AWS Glue, Amazon Athena, Amazon Redshift Spectrum, Amazon EMR 등으로 조회하며 이 서비스들이 Lake Formation 권한을 따른다. [S21]

| 비교 | IAM 권한 | Lake Formation 권한 |
|---|---|---|
| 통제 대상 | Lake Formation·Glue API와 리소스 접근 [S15] | Data Catalog 리소스, S3 위치, 기반 데이터 [S15] |
| 표현 방식 | IAM 정책 [S15] | DBMS 스타일 GRANT/REVOKE [S15] |
| 세분화 | 특정 리소스·조건에서 허용할 작업을 정책 문으로 정의 [S3] | 데이터베이스·테이블·열, 데이터 필터로 행·셀 [S18] |
| 관계 | 둘 다 통과해야 접근 성공 [S15] | 둘을 조합해 사용 [S15] |
| 시험 단서 | "Glue API 호출 권한 오류" | "열·행·셀 단위", "LF-Tag", "교차 계정 공유(RAM)" |

| 구분 | 권한 부여 방식 | 적합한 경우 | 근거 |
|---|---|---|---|
| 명명된 리소스 방식 | 데이터베이스 전체나 일부 테이블 등 리소스를 지정해 IAM 주체·계정에 공유 | LF-TBAC가 권장되는 조건(리소스가 많음)이 아닐 때의 대안으로 이해한다(문서의 명시적 선택 기준은 gaps 참조) | [S17][S19] |
| LF-TBAC | LF-Tag를 리소스·주체에 붙이고 태그 표현식으로 부여 | 리소스·주체가 많고 빠르게 늘어나는 환경 | [S17] |
| 하이브리드 접근 모드 | 옵트인한 주체만 Lake Formation 권한, 나머지는 IAM | 기존 IAM 기반 워크로드를 끊지 않고 점진 도입 | [S20] |

### 권한 부여 방식 — 역할 기반·태그 기반·속성 기반 (Skill 4.2.5, v1.1 개정)

- **v1.1 변경 사실**: v1.0에서는 'Authorization methods (role-based, policy-based, tag-based, and attribute based)'라는 지식 항목이었으나, v1.1은 Skill 4.2.5 'Apply authorization methods that address business needs (role-based, tag-based, and attribute-based)'로 통합하면서 'policy-based'가 빠졌다. [S24] 이 변경의 이유는 개정 페이지에 적혀 있지 않다(gaps 참조).
- **역할 기반(RBAC)**: 역할(직무) 단위로 권한을 묶는 방식이다. IAM에서는 널리 쓰는 직무 기능에 맞춘 AWS 관리형 정책이 한 예이고 [S1], Redshift에서는 역할(RBAC)에 권한을 모아 사용자에게 부여한다. [S10]
- **속성 기반(ABAC)**: 속성에 따라 권한을 정의하는 인가 전략으로 AWS에서 속성은 태그이며 AWS 리소스, IAM 역할, 역할 세션에 정의한다. [S22] 역할이나 세션의 태그가 리소스의 태그와 일치하도록 요구해 세분화된 권한을 줄 수 있다. [S22] 빠르게 성장하는 환경에 유용하다. [S22]
- **태그 기반(Lake Formation)**: LF-TBAC가 데이터 레이크 쪽 태그 기반 방식이다(위 4.2.4). [S17]
- **ABAC의 가드레일**: ABAC는 태그에 의존하므로 의도치 않은 접근을 막는 가드레일이 중요하고, 조직 전체에서 태그 수정 조건을 제한하는 데 SCP를 쓸 수 있다. [S23]

| 방식 | 권한의 기준 | 예 | 장점 | 근거 |
|---|---|---|---|---|
| RBAC | 직무·역할 | IAM 직무 기능 관리형 정책, Redshift 역할 | 역할 수준에서 권한 관리를 단순화 | [S1][S10] |
| ABAC(IAM) | 주체·리소스의 태그(속성) 일치 | 역할/세션 태그 = 리소스 태그 | 새 리소스가 생겨도 정책 수정을 줄임 | [S22][S23] |
| LF-TBAC | LF-Tag 값 일치 | 분류(Confidential 등) 태그로 테이블·열 권한 부여 | 대규모 Data Catalog에서 관리 부담 감소 | [S17] |

### 최소 권한 정책 구성 (Skill 4.2.6, v1.1 개정)

v1.0의 지식 항목 'Principle of least privilege as it applies to AWS security'가 v1.1에서는 Skill 4.2.6 'Construct custom policies that meet the principle of least privilege'로 문구가 바뀌었다. [S24] 개정 페이지는 바뀐 이유를 적지 않는다(gaps 참조).

- **정의와 출발점**: 작업에 필요한 권한만 부여하는 것이 최소 권한이다. [S3] 처음에는 넓게 시작하고 사용 사례가 성숙하면 줄여 나간다. [S3] AWS 관리형 정책에서 시작해 고객 관리형 정책으로 줄인다. [S3]
- **정책 생성(Access Analyzer)**: CloudTrail에 기록된 접근 활동으로 정책을 생성한다. IAM Access Analyzer가 CloudTrail 로그를 검토해 지정한 기간에 엔터티가 쓴 권한을 담은 정책 템플릿을 만들고, 이를 테스트한 뒤 프로덕션에 배포한다. [S3][S4]
- **마지막 액세스 정보**: 필요 없는 사용자·역할·권한·정책·자격 증명을 찾아 제거하고, IAM 정책을 최소 권한에 맞게 다듬는 데 쓴다. [S3]
- **정책 검증(Access Analyzer)**: 정책 언어와 모범 사례를 점검하는 정책 검사를 100개가 넘게 제공하고 조치 가능한 권고를 준다. [S3]
- **공개·교차 계정 액세스 검증**: Access Analyzer가 공개·교차 계정 액세스를 허용하는 지원 리소스에 대해 결과(finding)를 생성한다. [S3]
- **조건·경계·가드레일**: 조건으로 허용 범위를 좁히고(예: TLS 요청만) [S3], 권한 경계로 위임 권한의 최대치를 정하며 [S3], SCP·RCP로 여러 계정에 가드레일을 세운다(권한 자체는 부여하지 않음). [S3]

| 도구 | 하는 일 | 쓰는 시점 | 시험 단서 | 근거 |
|---|---|---|---|---|
| Access Analyzer 정책 생성 | CloudTrail 활동 기반 정책 템플릿 | 과다 권한 역할을 실제 사용 내역에 맞게 축소 | "지난 N일 사용 내역으로 최소 권한 정책" | [S3][S4] |
| Access Analyzer 정책 검증 | 정책 문법·모범 사례 검사와 권고 | 정책 작성·저장 전 | "정책이 안전하고 기능적인지 점검" | [S3] |
| 마지막 액세스 정보 | 쓰지 않는 권한·자격 증명 식별 | 정기 검토·정리 | "사용하지 않는 권한 제거" | [S3] |
| 공개·교차 계정 findings | 외부 접근 허용 리소스 탐지 | 교차 계정/공개 공유 전후 | "의도치 않은 외부 접근" | [S3] |
| 권한 경계 / SCP·RCP | 최대 권한 제한 / 조직 가드레일 | 위임·다계정 운영 | "권한을 주지 않고 상한만" | [S3] |

## 시험에서 묻는 방식

1. **자격 증명 저장소 선택(Secrets Manager / Parameter Store / Glue 연결)** — "DB 암호를 정기적으로 자동 교체하고 Glue 작업이 실행 시점에 조회"를 요구하면 → 정답 방향: Secrets Manager에 저장하고 Glue 연결이 비밀을 참조하게 하며, Glue 역할에 비밀 조회 권한을 주고 필요하면 Secrets Manager VPC 엔드포인트를 둔다. "단순 구성 값을 추가 비용 없이"는 Parameter Store 표준, "4 KB 초과 값·만료/알림 정책·다른 계정과 공유"는 Parameter Store 고급(+AWS RAM)이다. 오답 후보와 탈락 이유: Parameter Store 파라미터 정책을 '회전'으로 착각(정책 유형은 Expiration·ExpirationNotification·NoChangeNotification뿐), 표준 파라미터에 큰 값·정책·공유를 기대(표준은 4 KB이며 정책 불가), AWSGlueServiceRole만 붙이면 비밀을 읽을 수 있다고 가정(이 관리형 정책에는 Secrets Manager 권한이 없음). 근거 [S5][S6][S7][S9].
2. **Redshift 세분화 접근 제어(RBAC / 열 / RLS / DDM / IAM 인증)** — "같은 테이블에서 팀마다 보이는 행이 다름" → RLS 정책을 역할에 연결. "원본은 그대로 두고 카드 번호만 가려서 표시" → DDM 마스킹 정책(여러 정책이면 우선순위). "일부 열만 조회" → 열 수준 권한. "권한 변경을 한 곳에서 관리" → RBAC 역할. "암호 없이 IAM으로 DB 로그인" → Redshift는 GetClusterCredentials 임시 자격 증명, RDS는 IAM 인증 토큰. 오답 후보와 탈락 이유: 마스킹을 위해 원본 데이터를 변형(DDM은 데이터를 변형하지 않고 쿼리 시점에 표시를 바꿈), RLS로 열을 숨기려 함(열은 열 수준 권한, RLS는 행), 임시 자격 증명 만료를 한 값으로 외움(Redshift 기본 900초·900~3600초, RDS 토큰 15분). 근거 [S10][S11][S12][S13][S14].
3. **Lake Formation 설계 선택(필터 / LF-TBAC / 교차 계정 / 하이브리드)** — "데이터 레이크 테이블에 열·행·셀 수준 접근" → 데이터 필터를 만들어 SELECT 권한 부여 시 선택. "분류(예: Confidential) 태그로 수많은 테이블 권한을 관리" → LF-TBAC. "다른 계정에 공유하고 Athena로 조회" → AWS RAM 공유 + 수신 계정의 리소스 링크. "기존 IAM·S3 권한 기반 ETL을 끊지 않고 일부 사용자에게만 Lake Formation 권한을 도입" → 하이브리드 접근 모드(옵트인). "Lake Formation 권한은 있는데 작업이 실패" → IAM 권한(Glue API 등)도 필요. 오답 후보와 탈락 이유: Lake Formation 권한만 주고 IAM 권한 생략(두 검사를 모두 통과해야 함), IAM 태그를 LF-Tag로 오인(서로 다르며 호환 불가), 리소스 링크 없이 수신 계정에서 직접 조회(Athena·Redshift Spectrum은 리소스 링크 필요), S3 위치 등록 없이 기반 데이터 통제를 기대(위치를 등록해야 Lake Formation이 임시 자격 증명으로 접근 통제). 근거 [S15][S16][S17][S18][S19][S20][S21].
4. **권한 부여 방식 선택과 최소 권한 구성(ABAC / RBAC / 경계 / Access Analyzer)** — "새 리소스가 계속 생기고 태그가 일치하는 리소스에만 접근시키되 정책 수정은 최소" → ABAC(주체와 리소스의 태그 일치). "직무별로 고정된 권한" → RBAC(직무 기능 관리형 정책·역할). "개발자에게 역할 생성을 위임하되 최대 권한을 제한" → 권한 경계. "과다 권한 역할을 실제 사용 내역에 맞게 축소" → Access Analyzer 정책 생성(CloudTrail 기반). "쓰지 않는 권한·자격 증명 정리" → 마지막 액세스 정보. 오답 후보와 탈락 이유: SCP·RCP·권한 경계를 붙이면 권한이 부여된다고 가정(권한을 주지 않는 상한/가드레일), ABAC에서 태그 수정 권한을 방치(태그가 곧 권한이므로 가드레일 필요), AWS 관리형 정책을 그대로 최소 권한이라고 가정(모든 고객용이라 특정 사례에 최소 권한이 아닐 수 있음). 근거 [S1][S3][S4][S22][S23].

## 흔한 함정·혼동 짝

1. **AWS 관리형 vs 고객 관리형 vs 인라인 정책** — AWS 관리형은 AWS가 관리하고 수정 불가, 고객 관리형은 직접 만들어 여러 주체에 재사용, 인라인은 단일 ID와 일대일이며 ID 삭제 시 함께 삭제. → 시험 단서: "수정 가능", "여러 역할에 재사용", "이 역할에만". [S1]
2. **권한 경계 vs SCP·RCP vs 정책 자체** — 권한 경계는 ID 기반 정책이 줄 수 있는 최대치, SCP·RCP는 조직 가드레일이며 둘 다 권한을 부여하지 않는다(부여는 ID/리소스 기반 정책). → 시험 단서: "상한", "위임", "가드레일". [S3]
3. **IAM 권한 vs Lake Formation 권한** — 데이터 레이크 접근은 둘 다 통과해야 한다. IAM은 Lake Formation·Glue API 접근, Lake Formation은 Data Catalog·S3 위치·기반 데이터. → 시험 단서: "Lake Formation 권한을 줬는데도 실패". [S15]
4. **LF-Tag vs IAM 태그** — 이름만 비슷할 뿐 서로 호환되지 않는다. LF-Tag는 Lake Formation 권한 부여용, IAM 태그는 IAM 정책 정의용. → 시험 단서: "ABAC(IAM)인가 LF-TBAC인가". [S17]
5. **LF-TBAC vs 명명된 리소스 방식** — LF-TBAC는 리소스가 많을 때 권장되는 속성(태그) 기반 부여, 명명된 리소스는 이름을 지정해 데이터베이스·테이블을 공유. → 시험 단서: "수백 개 테이블", "분류 태그". [S17][S19]
6. **데이터 필터의 행 vs 열 vs 셀** — 모든 열 + 행 표현식이면 행 수준, 특정 열 + 모든 행이면 열 수준, 특정 열 + 행 표현식이면 셀 수준. → 시험 단서: "특정 열과 특정 행 조합". [S25]
7. **교차 계정 공유: RAM 공유 vs 리소스 링크** — 공유 수락만으로는 부족하고 수신 계정에서 Athena·Redshift Spectrum으로 조회하려면 리소스 링크가 필요. → 시험 단서: "공유했는데 쿼리 못 함". [S19]
8. **Lake Formation 전면 집행 vs 하이브리드 접근 모드** — 하이브리드에서는 옵트인한 주체만 Lake Formation+IAM 둘 다 요구받고 나머지는 IAM만으로 계속 접근. → 시험 단서: "기존 워크로드를 중단하지 않고 점진 도입". [S20]
9. **Secrets Manager vs Parameter Store** — 회전·비밀 관리는 Secrets Manager(비밀 수·API 호출 과금, 값 최대 65,536바이트), 단순 구성 값은 Parameter Store(표준 무료 4 KB). → 시험 단서: "자동 교체", "추가 비용 없이". [S5][S7][S8]
10. **Parameter Store 표준 vs 고급** — 값 크기(4 KB/8 KB)·개수(10,000/100,000)·정책·계정 간 공유·요금이 다르고 고급→표준은 되돌릴 수 없다. → 시험 단서: "4 KB 초과", "정책", "RAM 공유". [S5][S6]
11. **Parameter Store 정책 vs 비밀 회전** — 정책은 만료 삭제와 알림(만료 알림, 무변경 알림)이며 회전이 아니다. → 시험 단서: "만료 알림"을 "자동 회전"으로 착각하지 말 것. [S5]
12. **Glue 연결: 자격 증명 직접 입력 vs Secrets Manager 참조** — Secrets Manager 사용을 권장하며 Glue 역할에 조회 권한이 필요하고 AWSGlueServiceRole에는 그 권한이 없다. → 시험 단서: "Glue가 비밀을 못 읽음". [S9]
13. **Redshift RLS vs 열 수준 권한 vs DDM** — RLS는 행, 열 수준 권한은 열, DDM은 값의 표시 방식(마스킹, 원본 불변). → 시험 단서: "행", "열", "마스킹". [S11][S12]
14. **GetClusterCredentials vs RDS IAM 인증 토큰** — Redshift 임시 자격 증명은 기본 900초(900~3600초), RDS 인증 토큰은 15분 유효. → 시험 단서: "만료 시간", "암호 없는 로그인". [S13][S14]
15. **역할 기반 vs 속성 기반(ABAC) vs LF-TBAC** — 직무 역할 단위 / 주체·리소스 태그 일치 / LF-Tag 값 일치. ABAC는 태그를 바꿀 수 있는 권한이 곧 접근 권한이므로 태그 수정 통제가 필요. → 시험 단서: "정책을 늘리지 않고 새 리소스에 자동 적용". [S22][S23][S17]
16. **Access Analyzer 정책 생성 vs 정책 검증 vs 마지막 액세스 정보** — 생성은 CloudTrail 활동 기반 정책 템플릿, 검증은 정책 문법·모범 사례 검사(100개 넘는 검사), 마지막 액세스는 안 쓰는 권한·자격 증명 식별. → 시험 단서: "사용 내역으로 정책 생성" vs "작성한 정책 점검" vs "미사용 정리". [S3][S4]

### 후보 1 — Skill 4.2.2 · associate (서비스 선택)
- **문제**: AWS Glue ETL 작업이 쓰는 JDBC 데이터베이스 자격 증명을 안전하게 저장하려 한다. 보안 팀은 암호를 정기적으로 자동 교체하고, 코드나 스크립트에 암호가 남지 않기를 요구한다. 가장 적절한 구성은?
- **보기**: A. 비밀을 Secrets Manager에 저장하고 Glue 연결이 비밀을 참조하게 하며 Glue 역할에 비밀 조회 권한을 부여한다. / B. 암호를 Parameter Store 표준 SecureString에 저장하고 파라미터 정책으로 자동 회전을 설정한다. / C. 암호화한 암호 파일을 S3 버킷에 두고 Glue 스크립트가 읽게 한다. / D. Glue 역할에 AWSGlueServiceRole 관리형 정책만 붙이고 Secrets Manager 비밀을 별도 권한 없이 참조한다.
- **정답**: A
- **해설 초안**: Glue는 연결 자격 증명을 실행 시점에 Secrets Manager에서 조회하도록 권장하고 [S9], Secrets Manager는 비밀 회전을 제공한다. [S7] Glue 역할에는 비밀 조회 권한이 있어야 한다. [S9]
- **오답 근거**: B — Parameter Store 파라미터 정책은 만료·알림이며 회전이 아니다 [S5] / C — 요구한 자동 교체를 제공하는 관리형 기능이 아니다 / D — AWSGlueServiceRole 관리형 정책에는 Secrets Manager 권한이 없다 [S9]
- **근거**: [S9] https://docs.aws.amazon.com/glue/latest/dg/connection-properties-secrets-manager.html — "use AWS Secrets Manager to supply connection credentials for your data store"

### 후보 2 — Skill 4.2.3 · associate
- **문제**: Amazon Redshift의 customers 테이블을 영업팀과 마케팅팀이 조회한다. 영업팀 분석가는 자기 리전의 행만 보아야 하고, 마케팅팀은 모든 행을 보되 신용카드 번호는 가려진 값으로 보아야 한다. 원본 데이터는 바꾸면 안 된다. 어떻게 구성하는가?
- **보기**: A. 영업팀 역할에 RLS 정책을, 마케팅팀 역할에 DDM 마스킹 정책을 연결한다. / B. 두 팀 모두에 열 수준 SELECT 권한만 부여한다. / C. 신용카드 번호 열을 해시 값으로 바꿔 원본 테이블을 갱신한다. / D. Lake Formation 권한 모델을 Redshift 내부 로컬 테이블에 직접 적용한다.
- **정답**: A
- **해설 초안**: RLS는 보이는 열의 특정 행으로 접근을 제한하고 [S11], DDM은 데이터를 변형하지 않고 쿼리 시점에 표시 방식을 바꾸는 마스킹 정책을 사용자·역할에 적용한다. [S12]
- **오답 근거**: B — 열 수준 권한은 열만 제한하며 행 제한·값 마스킹은 하지 못한다 [S11] / C — 원본 변경 금지 요구를 위반한다(DDM은 원본을 바꾸지 않는다) [S12] / D — Lake Formation 권한은 Data Catalog 리소스·S3 위치·기반 데이터를 통제하는 모델이다 [S15]
- **근거**: [S11] https://docs.aws.amazon.com/redshift/latest/dg/t_rls.html — "use RLS policies to further restrict access to particular rows of the visible columns"

### 후보 3 — Skill 4.2.4 · associate (서비스 선택)
- **문제**: 회사는 Glue Data Catalog 테이블에 IAM 정책과 S3 권한만으로 ETL 작업이 접근해 왔다. 이제 일부 분석가에게만 Lake Formation의 열·행 수준 권한을 적용하고 싶지만 기존 ETL 작업과 다른 사용자의 접근이 끊기면 안 된다. 어떻게 하는가?
- **보기**: A. 하이브리드 접근 모드를 사용하고 해당 분석가만 Lake Formation 권한을 쓰도록 옵트인한다. / B. 모든 주체에 대해 Lake Formation 권한을 즉시 필수로 전환하고 기존 IAM 기반 접근을 제거한다. / C. S3 버킷 정책만으로 분석가별 열·행 접근을 제한한다. / D. Glue 크롤러의 권한만 조정한다.
- **정답**: A
- **해설 초안**: 하이브리드 접근 모드는 같은 Data Catalog 객체에 두 가지 권한 경로를 제공한다. 옵트인한 주체만 Lake Formation 권한과 IAM 권한을 모두 요구받고, 다른 기존 사용자·워크로드는 접근이 끊기지 않는다. [S20]
- **오답 근거**: B — 전면 전환은 기존 사용자·워크로드 접근을 끊을 수 있어 하이브리드 모드를 쓰는 이유와 반대다 [S20] / C — 열·행·셀 수준 보안은 Lake Formation 데이터 필터로 구현한다 [S25] / D — 크롤러 권한 조정으로는 분석가별 열·행 수준 제한(데이터 필터)을 충족하지 못한다 [S25]
- **근거**: [S20] https://docs.aws.amazon.com/lake-formation/latest/dg/hybrid-access-mode.html — "opted in principals will require both Lake Formation permissions and IAM permissions"

### 후보 4 — Skill 4.2.5 · associate (서비스 선택)
- **문제**: 데이터 레이크 테이블에 분류 태그(예: Confidential)를 붙여 수백 개 테이블과 많은 분석가의 접근을 관리하려 한다. 새 테이블이 추가되어도 권한을 개별로 다시 부여하지 않고 태그 값 일치로 적용되길 원한다. 가장 적합한 방식은?
- **보기**: A. Lake Formation LF-TBAC: LF-Tag를 리소스와 주체에 붙이고 태그 값으로 권한을 부여한다. / B. 테이블마다 명명된 리소스 방식으로 SELECT를 개별 부여한다. / C. IAM 태그를 Data Catalog 테이블에 붙이면 Lake Formation이 그 태그로 권한을 집행한다. / D. S3 객체 태그를 붙이고 Lake Formation이 그 태그를 LF-Tag로 사용한다.
- **정답**: A
- **해설 초안**: LF-TBAC는 속성(LF-Tag)에 따라 권한을 정하는 인가 전략으로, Data Catalog 객체가 많을 때 권장되는 방법이다. [S17]
- **오답 근거**: B — 리소스가 많을수록 개별 부여 부담이 커져 LF-TBAC 권장 조건과 어긋난다 [S17] / C — IAM 태그와 LF-Tag는 같지 않으며 호환되지 않는다 [S17] / D — LF-Tag는 Data Catalog 리소스에 붙이는 태그다 [S17]
- **근거**: [S17] https://docs.aws.amazon.com/lake-formation/latest/dg/tag-based-access-control.html — "LF-TBAC is the recommended method to use to grant Lake Formation permissions"

### 후보 5 — Skill 4.2.6 · associate
- **문제**: Glue ETL 작업의 IAM 역할이 개발 초기에 AWS 관리형 정책으로 광범위한 권한을 받은 채 운영 중이다. 보안 팀은 최근 실제로 사용한 작업과 리소스에 맞춘 최소 권한 정책으로 교체하길 원한다. 어떻게 하는가?
- **보기**: A. IAM Access Analyzer 정책 생성으로 CloudTrail 접근 활동 기반 정책 템플릿을 만들고 테스트한 뒤 배포한다. / B. 역할에 권한 경계를 설정하고 기존 관리형 정책은 그대로 둔다. / C. 조직에 SCP를 적용해 필요한 권한을 부여한다. / D. Access Analyzer가 생성한 공개·교차 계정 액세스 결과를 정책으로 그대로 사용한다.
- **정답**: A
- **해설 초안**: Access Analyzer는 CloudTrail 로그를 검토해 엔터티가 쓴 권한을 담은 정책 템플릿을 만들고, 테스트한 뒤 프로덕션에 배포한다. [S3][S4]
- **오답 근거**: B — 권한 경계는 부여 가능한 최대 권한을 정할 뿐 사용 내역에 맞춘 정책을 만들지 않는다 [S3] / C — SCP·RCP는 권한을 부여하지 않는 가드레일이다 [S3] / D — 공개·교차 계정 접근 결과(finding)는 외부 접근을 허용하는 리소스를 알려 줄 뿐 정책이 아니다 [S3]
- **근거**: [S4] https://docs.aws.amazon.com/IAM/latest/UserGuide/access-analyzer-policy-generation.html — "generates a policy template that contains the permissions that the entity used"
