## 핵심 개념

### Amazon Redshift 테이블 설계: 분산 스타일·정렬 키·압축·제약조건 (Skill 2.4.1, 2.4.5)

Redshift는 테이블을 만들 때 정하는 분산 스타일·정렬 키·압축 인코딩이 쿼리 성능을 좌우한다. 분산 스타일은 AUTO·EVEN·KEY·ALL 중에서 고르며, 지정하지 않으면 AUTO가 적용된다 [S1]. Redshift는 객체 안에서 데이터를 파티셔닝하는 개념 자체를 지원하지 않으며 테이블스페이스나 파티션 스킴을 정의할 필요도 없다 — S3 데이터 레이크의 파티셔닝(Athena)과 혼동하지 말 것 [S1].

- **분산 스타일**
  - AUTO: 테이블 크기에 따라 서비스가 스타일을 정한다. 작은 테이블은 처음에 ALL, 커지면 KEY(기본 키 또는 복합 기본 키의 한 열을 분산 키로), 적합한 열이 없으면 EVEN으로 바뀌며 이 변경은 백그라운드에서 일어난다 [S1].
  - EVEN: 리더 노드가 열 값과 무관하게 슬라이스에 라운드 로빈으로 분산한다. 조인에 참여하지 않는 테이블이거나 KEY와 ALL 중 명확한 선택이 없을 때 적합하다 [S1].
  - KEY: 한 열의 값 기준으로 분산한다. 조인 키로 두 테이블을 분산하면 조인 열의 매칭 값이 물리적으로 함께 저장된다 [S1]. 팩트 테이블의 분산 키는 하나뿐이라, 조인 빈도와 필터 후 크기를 기준으로 팩트와 colocate할 디멘션 하나를 고르고, 분산 키는 필터링된 결과 집합에서 카디널리티가 높은 열로 고른다 [S2].
  - ALL: 전체 사본을 모든 노드에 두어 그 테이블이 참여하는 모든 조인에서 행이 colocate된다. 대신 저장 공간이 노드 수만큼 곱절이 되고 적재·갱신·삽입이 훨씬 느려지므로 거의 갱신되지 않는 테이블에만 적합하다 [S1][S2]. 팩트나 주요 조인 테이블과 colocate할 수 없는 디멘션에는 ALL이 성능을 크게 올릴 수 있지만, 쿼리 중 재분산 비용이 낮은 작은 디멘션 테이블은 ALL로 얻는 이점이 크지 않다고 문서는 설명한다 [S1][S2].
- **정렬 키**: 정렬하면 Redshift가 1 MB 디스크 블록마다 min/max를 메타데이터로 저장해 범위 조건 쿼리에서 블록을 대거 건너뛸 수 있다 [S3]. COMPOUND(기본값)는 정렬 키 열의 접두(prefix) 조건을 쓰는 쿼리에 효율적이고, INTERLEAVED는 키의 각 열에 같은 가중치를 주어 어떤 열 부분집합이든 순서와 무관하게 조건으로 쓸 수 있으며 최대 8열까지 지정한다. INSERT/UPDATE/DELETE로 테이블을 정기 갱신하면 COMPOUND가 권장된다 [S3].
- **자동 테이블 최적화(ATO)**: 쿼리가 테이블과 상호작용하는 방식을 지속 관찰하고 AI 기법으로 정렬 키·분산 키를 골라 관리자 개입 없이 적용하는 자가 튜닝 기능이다. 분산 스타일 또는 정렬 키가 AUTO인 기존 테이블은 이미 자동화 대상이고, 분산 스타일이 AUTO인 테이블은 KEY로 바뀔 수 있다 [S4]. 기존 테이블은 ALTER DISTSTYLE AUTO / ALTER SORTKEY AUTO로 전환하며, 분산 스타일을 ALL·EVEN·KEY로 직접 바꾸면 더 이상 ATO 후보가 아니다 [S7].
- **압축 인코딩**: ENCODE AUTO가 테이블의 기본값이며 Redshift가 전 열의 인코딩을 자동 관리한다. 한 열이라도 인코딩을 직접 지정하면 그 테이블은 ENCODE AUTO가 아니게 되고, 이때 지정하지 않은 열은 정렬 키·BOOLEAN·REAL·DOUBLE PRECISION → RAW, SMALLINT·INTEGER·BIGINT·DECIMAL·DATE·TIMESTAMP·TIMESTAMPTZ → AZ64, CHAR·VARCHAR → LZO로 배정된다 [S5].
- **제약조건**: UNIQUE·PRIMARY KEY·FOREIGN KEY는 정보용일 뿐 적재 시 강제되지 않지만, 쿼리 플래너가 계획 힌트(조인 순서 결정·중복 조인 제거 등)로 쓴다. 키가 실제로 유효하지 않으면 SELECT DISTINCT가 중복 행을 돌려주는 등 잘못된 결과가 나올 수 있어, 무결성이 보장될 때만 선언한다. NOT NULL은 강제된다 [S6].

**비교 표 ① Redshift 분산 스타일**

| 스타일 | 적합한 경우 | 제약·비용 특성 | 시험 단서 키워드 |
|---|---|---|---|
| AUTO | 기본값. 어떤 스타일이 맞는지 모를 때 [S1] | 작은 테이블 ALL → 커지면 KEY 또는 EVEN으로 자동 변경(백그라운드) [S1] | "기본", "자동", "관리 부담 최소" |
| EVEN | 조인에 참여하지 않는 테이블, KEY/ALL 선택이 불분명할 때 [S1] | 열 값과 무관한 라운드 로빈 — 조인 colocation 없음 [S1] | "조인 없음", "균등 분산" |
| KEY | 큰 팩트 + 큰 디멘션을 공통 조인 열로 colocate [S1][S2] | 팩트 테이블은 분산 키가 하나뿐 [S2] | "조인 열", "colocate" |
| ALL | 다른 테이블과 colocate할 수 없고 거의 갱신되지 않는 디멘션 [S1][S2] | 저장 공간 ×노드 수, 적재·갱신 느림 [S1][S2] | "slow moving", "모든 조인에서 colocate" |

### DynamoDB 데이터 모델링: 액세스 패턴 우선·키 설계·인덱스 (Skill 2.4.1, 2.4.5)

DynamoDB는 스키마리스라 속성을 미리 다 정의할 필요가 없고, 파티션 키 속성은 필수·정렬 키는 선택이다 [S10]. 기본 키는 파티션 키만 쓰는 simple 형태이거나 파티션 키+정렬 키의 composite 형태다 [S9]. 설계의 첫 단계는 시스템이 만족해야 할 쿼리 패턴을 식별하는 것이며, 데이터 크기·모양·속도(피크 부하)를 미리 파악한다. 그다음 관련 데이터를 함께 두고, 정렬 순서를 활용하고, 쿼리를 파티션에 고르게 분산하며(핫스팟 회피), 필요한 쿼리마다 GSI를 만든다 [S8]. 테이블은 가능한 한 적게 유지하는 것이 일반 원칙이고(단일 테이블 + 역 인덱스), 대용량 시계열 데이터나 액세스 패턴이 매우 다른 데이터셋은 예외다 [S8].

- **파티션 키 선택**: 카디널리티가 높은 파티션 키를 골라 자주 접근하는 항목이 같은 파티션에 몰리지 않게 한다(핫 파티션 방지) [S10]. 모든 파티션은 초당 최대 3,000 읽기 단위·1,000 쓰기 단위를 제공하도록 설계되고, 항목 크기가 클수록 한 항목에 동시에 보낼 수 있는 연산 수가 줄어든다 [S9]. 쓰기 샤딩으로 부하를 분산하는 방법이 별도 항목으로 안내된다 [S9].
- **항목 크기**: 항목당 최대 400 KB이며 속성 이름과 속성 값의 길이를 모두 합산한다. 항목이 이를 넘을 수 있으면, 직렬화한 항목을 S3에 JSON으로 저장하고 S3 위치를 속성으로 항목에 담는 우회책이 안내된다(키와 인덱스에 쓰이는 속성은 테이블에 그대로 둔다) [S10].
- **보조 인덱스**: GSI·LSI는 기본 키 외의 대체 키로 Query/Scan할 수 있게 해 준다. 아래 표가 핵심 차이다 [S11].

**비교 표 ② DynamoDB GSI vs LSI**

| 구분 | GSI (Global Secondary Index) | LSI (Local Secondary Index) | 시험 단서 키워드 |
|---|---|---|---|
| 키 구성 | 파티션 키·정렬 키 모두 base 테이블과 달라도 됨(simple 또는 composite) [S11] | 파티션 키는 base 테이블과 동일, 정렬 키만 다름(composite 필수) [S11] | "다른 파티션 키로 조회" vs "같은 파티션 키·다른 정렬" |
| 생성 시점 | 테이블 생성 시 또는 이후 추가·삭제 가능 [S11] | 테이블 생성 시에만; 기존 테이블에 추가·삭제 불가 [S11][S36] | "이미 운영 중인 테이블에 인덱스 추가" |
| 크기 제한 | 제한 없음 [S11] | 파티션 키 값당 인덱스 항목 총합 10 GB [S11][S36] | "item collection" |
| 읽기 일관성 | 최종 일관성만 [S11][S35] | 최종 또는 강한 일관성 선택 [S11][S36] | "강한 일관성 필요" |
| 처리량 | 인덱스 자체 프로비저닝(인덱스에서 용량 소비) [S11] | base 테이블 용량에서 소비 [S11] | "인덱스 쓰기 스로틀링" |
| 기본 개수 한도 | 테이블당 20개(기본 쿼터) [S11] | 테이블당 5개 [S11] | — |

### Lake Formation: Data Catalog 객체와 LF-Tag 설계 (Skill 2.4.1)

Lake Formation에서 "스키마 설계"는 Data Catalog의 데이터베이스·테이블·열을 어떻게 분류하고 어떤 LF-Tag(속성)를 붙여 권한을 줄지 정하는 일에 가깝다. LF-Tag는 Data Catalog 데이터베이스·테이블·열에 부여해 접근을 제어한다 [S13]. LF-TBAC(태그 기반 접근 제어)는 속성에 근거해 권한을 정의하는 전략으로, Data Catalog 객체가 많을 때 Lake Formation 권한을 주는 권장 방법이다 [S12]. 설계 제약은 다음과 같다.

- LF-Tag는 리소스에 부여하거나 보안주체에 허용하기 전에 미리 정의되어 있어야 한다 [S13].
- 한 리소스에 LF-Tag를 여러 개 달 수 있지만 같은 키에는 값을 하나만 지정할 수 있다(module=Orders,Customers 불가) [S13].
- 리소스를 만들 때 LF-Tag를 함께 지정할 수 없고, 이미 존재하는 리소스에만 추가할 수 있다 [S13].
- 보안주체에는 단일 태그뿐 아니라 LF-Tag 표현식을 부여할 수 있다. 표현식은 module=sales AND division=(consumer OR commercial)처럼 여러 키 조건을 AND로 묶으며, 서로 다른 키 조건을 OR로 허용하려면 한 grant에 넣지 말고 grant를 둘로 나눈다 [S13].
- IAM 태그와 LF-Tag는 서로 다른 것이며 호환되지 않는다 [S12].

### 데이터 특성 변경(스키마 진화·드리프트) 대응 (Skill 2.4.2)

Skill 문구("데이터 특성에 대한 변경 사항 해결")만으로는 무엇을 묻는지 범위를 확정하기 어렵다(gaps [불확실] 참고). 여기서는 공식 문서로 확인되는 스키마 진화·드리프트 대응 수단을 계층별로 정리한다 — 카탈로그(크롤러), 스트리밍 스키마 계약(스키마 레지스트리), 쿼리 엔진·테이블 포맷(Athena·Iceberg), 웨어하우스 DDL(Redshift), NoSQL(DynamoDB), 복제(DMS).

- **Glue 크롤러의 스키마 변경 정책**: 콘솔에서 크롤러가 스키마 변경을 어떻게 처리할지 고른다 — "Update the table definition in the data catalog"(메타데이터 테이블 갱신), "Add new columns only"(사용자가 직접 수정한 내용을 덮어쓰지 않고 새 컬럼만 추가), "Ignore the change and don't update the table in the data catalog"(테이블 메타데이터 미갱신). 파티션 메타데이터를 테이블과 같게 유지하려면 "Update all new and existing partitions with metadata from the table"도 켠다 [S14]. CLI 예시에서 "새 컬럼만 추가"는 UpdateBehavior=LOG에 테이블 AddOrUpdateBehavior=MergeNewColumns 설정으로 표현된다 [S14].
- **Glue Schema Registry(스트리밍 스키마 계약)**: 스키마마다 버전이 있고, 새 버전 등록 요청은 스키마에 적용된 호환성 규칙으로 검사된 뒤에만 성공한다. 호환성 모드는 8가지다 [S15]. 아래 비교 표 ③ 참고. 하드 한도는 리전당 레지스트리 100개·스키마 버전 10000개·스키마 페이로드 170KB이고, SchemaVersion당 메타데이터 키-값 쌍 10개는 소프트 한도다 [S15].
- **Athena(스키마 온 리드) + 파일 포맷**: Athena는 읽을 때 스키마를 적용할 뿐 기저 데이터를 바꾸거나 다시 쓰지 않는다. 포맷별로 가능한 스키마 변경이 다르며 [S17], Iceberg 테이블은 스키마 업데이트가 메타데이터만 바꾸는 작업이라 데이터 파일을 다시 쓰지 않고 컬럼 추가·삭제·이름 변경·순서 변경·타입 확장을 지원한다 [S16]. 아래 비교 표 ④ 참고.
- **Redshift ALTER TABLE**: ADD COLUMN·DROP COLUMN·RENAME COLUMN을 지원한다. ALTER COLUMN TYPE은 VARCHAR 크기 변경만 지원하며, 기존 데이터의 최대 크기보다 줄일 수 없고, 기본값/UNIQUE/PRIMARY KEY/FOREIGN KEY가 있는 열이나 트랜잭션 블록 안에서는 바꿀 수 없으며, BYTEDICT·RUNLENGTH·TEXT255·TEXT32K 인코딩 열도 불가하다 [S7].
- **DynamoDB**: 스키마리스라 항목마다 속성이 달라도 되므로 새 속성 추가에 DDL이 필요 없다(키 속성만 필수) [S10].
- **DMS의 소스 DDL 변경 처리**: CDC 중 대상 테이블의 DDL 처리 방식은 ChangeProcessingDdlHandlingPolicy 작업 설정이 결정한다 — HandleSourceTableDropped(소스 테이블 삭제 시 대상 테이블 삭제), HandleSourceTableTruncated(소스 truncate 시 대상 truncate), HandleSourceTableAltered(소스 ALTER 시 대상 ALTER) [S18].

### 스키마 변환: AWS SCT와 DMS Schema Conversion (Skill 2.4.3)

이기종 DB 마이그레이션은 "스키마·코드 객체 변환"과 "데이터 이동"이 분리된다. 스키마 변환 도구가 AWS SCT와 DMS Schema Conversion(DMS SC)이다.

- **DMS Schema Conversion**: AWS DMS의 기능으로, 소스 스키마를 Aurora·Amazon RDS·Amazon Redshift 대상에 맞는 형식으로 변환한다. 마이그레이션 프로젝트(소스·대상 데이터 프로바이더 + 인스턴스 프로파일)를 만들고, 평가 보고서로 자동 변환 가능한 부분과 수작업이 필요한 부분을 확인한 뒤 변환하고, 변환 코드를 대상에 적용하거나 SQL 스크립트로 내보낸다. 스키마만 변환하며 데이터 이동은 DMS의 데이터 마이그레이션 기능을 쓴다. 규칙 기반 엔진을 쓰고 일부 경로는 생성형 AI 변환도 지원한다. 완전 관리형·웹 기반이며 AWS SCT 변환 엔진 위에 구축되었다 [S19].
- **AWS SCT**: 기존 DB 스키마를 한 엔진에서 다른 엔진으로 변환하는 도구로, 관계형 OLTP 스키마와 데이터 웨어하우스 스키마를 모두 변환한다. 변환된 스키마는 RDS·Aurora·Redshift 등에 쓰거나 S3에 데이터로 저장할 수 있다 [S20]. 데이터 웨어하우스 변환의 소스에는 Teradata·Netezza·Vertica·Greenplum·Snowflake·BigQuery·Azure Synapse 등이 있고 대상은 Amazon Redshift다. NoSQL(Apache Cassandra → DynamoDB)과 ETL 스크립트(SSIS → AWS Glue, Teradata BTEQ → Glue/Redshift RSQL 등), 빅데이터 프레임워크(Hive → Hive on EMR, HDFS → S3, Oozie → Step Functions) 변환도 지원한다 [S20].
- **지원 경로 차이**: DMS SC가 문서에 나열한 변환 경로는 Oracle·SQL Server·PostgreSQL·MySQL·IBM Db2·SAP ASE 소스에 한정되며, Oracle → Amazon Redshift 경로도 있다. Db2 for z/OS 경로는 콘솔에 없고 DMS API/CLI로만 쓴다 [S19]. Teradata·Netezza 같은 DW 소스는 DMS SC 경로 표에는 없고 SCT 소스 목록에만 있다 [S19][S20].
- **둘의 형태 차이**: DMS SC는 AWS DMS 안의 완전 관리형·웹 기반 기능이고 [S19], AWS SCT는 프로젝트 기반 UI를 가진 독립 실행형 애플리케이션이자 명령줄 도구이며 Windows·Fedora Linux·Ubuntu Linux용으로 제공된다 [S34].
- **시험 범위 주의**: DEA-C01 v1.1 "범위 내 서비스" 목록의 Migration and Transfer에는 AWS DMS가 있지만 AWS SCT는 보이지 않는다 [S21]. 개정 이력(Revisions)도 AWS Schema Conversion Tool(AWS SCT)을 범위 내 목록에서 제거된 서비스로 적고 있다 [S38]. 그런데 Skill 2.4.3 예시에는 SCT가 남아 있다 — gaps [불확실] 참고.

**비교 표 ⑤ AWS SCT vs DMS Schema Conversion**

| 구분 | DMS Schema Conversion | AWS SCT | 시험 단서 키워드 |
|---|---|---|---|
| 형태 | AWS DMS 안의 완전 관리형·웹 기반 기능 [S19] | 독립 실행형 애플리케이션 + 명령줄 도구(Windows·Fedora·Ubuntu) [S34] | "설치 없이 콘솔", "완전 관리형" |
| 관계 | SCT 변환 엔진 위에 구축 [S19] | 변환 엔진의 원조 — OLTP + DW + NoSQL + ETL + 빅데이터 변환까지 폭넓음 [S19][S20] | — |
| 소스·대상 | Oracle/SQL Server/PostgreSQL/MySQL/Db2/SAP ASE → Aurora·RDS·Redshift(경로 표 한정) [S19] | DW(Teradata·Netezza·Vertica·Greenplum 등) → Redshift 포함, Cassandra → DynamoDB [S20] | "Teradata", "Netezza", "Cassandra → DynamoDB" |
| 공통·차이 | 스키마·코드 객체 변환 + 평가 보고서, 데이터는 옮기지 않음(데이터는 DMS 데이터 마이그레이션) [S19] | 스키마 변환 도구 — DW 소스(Teradata 등)·ETL·빅데이터 변환까지 문서화됨 [S20] | "스키마 vs 데이터" |

### 데이터 계보(Lineage) 설정 도구 (Skill 2.4.4, v1.1 개정)

계보는 데이터가 어디서 왔고 어떻게 변환되었는지 추적하는 기능이다. 공식 문서에서 확인되는 AWS 도구는 ML 워크플로용과 데이터 자산용으로 나뉜다.

- **Amazon SageMaker ML Lineage Tracking(ML 워크플로 계보)**: 데이터 준비부터 모델 배포까지 ML 워크플로 요소를 tracking entity로 표현해 모델 거버넌스·재현성에 쓴다. SageMaker AI는 학습·처리·배치 변환 같은 잡을 만들면 trial component와 관련 trial·experiment의 tracking entity를 자동 생성하고, 사용자 정의 단계는 수동으로 추가할 수 있다. 이미 있는 엔티티는 새로 만들지 않고 재사용한다 [S22]. 엔티티는 실험 엔티티(trial component, trial, experiment)와 계보 엔티티(trial component, context, action, artifact, association)로 나뉜다. artifact는 URI로 지정되는 객체나 데이터(데이터셋의 S3 URI 등)로 보통 trial component나 action의 입력 또는 출력이고, action은 활동(워크플로 단계, 모델 배포 등)으로 보통 입력/출력 artifact가 하나 이상 있으며, context는 다른 엔티티의 논리적 묶음(엔드포인트, 모델 패키지 등), association은 엔티티 사이를 잇는 연결이다. association은 선택적 AssociationType(ContributedTo, AssociatedWith, DerivedFrom, Produced, SameAs)을 가진다 [S22]. 크로스 어카운트 계보와 QueryLineage로 관계를 조회할 수 있다 [S22].
- **Amazon SageMaker Catalog(데이터 자산 계보)**: SageMaker Catalog는 Amazon DataZone 기반으로 구축되었다 [S25]. SageMaker Unified Studio의 데이터 계보는 OpenLineage 호환 기능으로, OpenLineage 지원 시스템이나 API에서 오는 계보 이벤트를 수집·시각화해 데이터 출처·변환·조직 간 소비를 추적한다 [S23]. Glue·Redshift 같은 데이터 소스와 Visual ETL·노트북 같은 도구에서는 실행이 데이터를 만들거나 바꿀 때 계보가 자동 수집되고, 카탈로그 안에서의 자산 이동(게시·구독)과 스키마 변경 시점도 기록된다 [S37]. 다만 자동화 수준은 소스마다 다르다 — Glue 크롤러(S3·DynamoDB·Iceberg/Delta/Hudi·JDBC·PostgreSQL·DocumentDB·MongoDB 대상)와 Amazon Redshift는 SageMaker Unified Studio에서 기본 자동이고, Glue 콘솔의 Glue 잡과 EMR은 기본 자동이 아니라 설정이 필요하다(Glue 잡은 "generate lineage events"+도메인 ID, EMR은 Spark conf로 이벤트 발행) [S24]. Visual ETL(호환 모드)과 JupyterLab 노트북(Spark DataFrame 한정)도 자동 수집된다 [S24].
- **Glue / Lake Formation은?** Glue 콘솔의 Glue 잡은 "generate lineage events" 옵션과 도메인 ID를 지정해야 계보 이벤트를 SageMaker Unified Studio로 보낸다(위 매트릭스 [S24]). Lake Formation 자체가 계보 기능을 제공한다고 확인되는 공식 문서는 찾지 못했다 — gaps [확인필요].

**비교 표 ⑥ 계보 도구 선택**

| 도구 | 적합한 경우 | 제약·특성 | 시험 단서 키워드 |
|---|---|---|---|
| SageMaker ML Lineage Tracking | 어떤 데이터셋·학습 잡·이미지로 어떤 모델/엔드포인트가 만들어졌는지 재현·감사 [S22] | SageMaker 잡 중심 tracking entity(trial component·artifact·action·context·association) [S22] | "모델 거버넌스", "워크플로 재현", "artifact/action/context" |
| SageMaker Catalog(DataZone 기반) 데이터 계보 | Glue·Redshift 등 데이터 자산의 출처·변환·소비를 비즈니스 카탈로그에서 시각화 [S23][S25] | OpenLineage 호환, 소스별 자동화 수준 상이 [S23][S24] | "OpenLineage", "카탈로그 자산", "downstream 영향 분석" |

### 인덱싱·파티셔닝·압축·최적화 모범 사례 (Skill 2.4.5)

- **Redshift**: 테이블 설계 선택으로 최적화한다 — 정렬 키(범위 조건 블록 스킵 [S3])·분산 스타일(조인 colocation [S1][S2])·압축(ENCODE AUTO [S5])·ATO [S4]. 앞의 "Amazon Redshift 테이블 설계" 소제목 참고.
- **DynamoDB**: 보조 인덱스(GSI·LSI)가 대체 키 조회를 지원하고 [S11], 고카디널리티 파티션 키와 균등 부하 설계가 핫 파티션을 막는다 [S9][S10].
- **Athena / S3 데이터 레이크 — 파티셔닝**: 파티션 키는 가상 컬럼이며, 파티션 키로 필터링하면 일치하는 파티션만 읽는다. 키가 너무 많으면 파일이 너무 잘게 쪼개지고, 너무 적거나 없으면 필요 이상을 스캔한다. 가장 흔한 쿼리에 맞추고 드문 쿼리를 위해 최적화하지 말 것 — 예: 일 단위 조회가 대부분이면 시간 단위로 파티셔닝하지 말고 타임스탬프로 정렬해 두면 짧은 구간 쿼리에 거의 동등한 효과를 낸다 [S26]. 파티션 키 타입은 항상 STRING을 쓴다(그래야 파티션 필터가 Glue로 푸시다운) [S26]. 모든 파티션 키에 동등(equality) 조건을 주는 쿼리가 더 빠르다 [S26]. Athena는 데이터 경로가 키=값 쌍(예: year=2021/month=01/day=26/)인 Apache Hive 스타일 파티션을 쓸 수 있고, MSCK REPAIR TABLE은 Hive 스타일 파티션에서만 동작한다. CloudTrail 로그·Firehose 전송 스트림처럼 날짜 부분이 별도 경로 요소(예: data/2021/01/26/us/...)인 non-Hive 스타일은 ALTER TABLE ADD PARTITION으로 수동 추가한다 [S27]. S3 경로는 소문자여야 하고(camel case면 MSCK가 파티션을 추가하지 못함), 서로 다른 테이블의 데이터는 별도 폴더 계층에 둔다 [S27]. Glue 테이블이 1천만 개 파티션을 가져도 질의는 가능하지만 한 번의 스캔에서 100만 개를 넘는 파티션은 읽지 못하므로 이런 경우 파티션 인덱싱이 도움이 된다 [S27].
- **파티션 메타데이터 관리**: MSCK REPAIR TABLE은 오래 걸릴 수 있고 새 파티션만 추가할 뿐 오래된 파티션은 제거하지 못해 파티션 관리에 비효율적이다. 대신 Glue Data Catalog API·ALTER TABLE ADD PARTITION·Glue 크롤러로 관리하거나, 파티션 프로젝션으로 관리 자체를 없앤다 [S26]. 파티션 프로젝션은 파티션 값·위치를 카탈로그 조회 대신 설정 규칙으로 메모리에서 계산한다 — 파티션이 매우 많은 테이블에 유리하지만 데이터가 듬성듬성한(sparse) 테이블에서는 오히려 느려질 수 있고, 모든 파티션 키에 조건을 주어야 한다 [S26]. Glue Data Catalog 파티션 인덱스는 파티션이 많은 테이블의 조회 성능을 올린다 [S26].
- **컬럼형 포맷 + 압축**: Parquet·ORC 같은 컬럼형은 필요한 컬럼만 읽고 압축 효율이 높으며 파일 메타데이터(min/max)로 불필요한 구간을 건너뛴다. 데이터를 정렬해 두면 이 메타데이터 활용이 커진다. Parquet row group 기본 128 MB·ORC stripe 기본 64 MB이며, 컬럼이 많으면 키우는 편이 낫고 기본값보다 줄이는 것은 권장되지 않는다. 압축 데이터는 스캔 바이트 기준 과금이라 더 빠르고 더 싸다. gzip은 압축률이 좋고 호환 범위가 넓으며 zstd는 성능과 압축률의 균형이 좋다. 압축 텍스트(JSON/CSV)는 대부분 병렬 처리가 불가하므로 파일 수와 크기의 균형이 필요하다 [S26].
- **버킷팅**: 카디널리티가 높은 키로 특정 값을 조회하는 쿼리가 많을 때 유용하나, 여러 값을 자주 조회하면 이점이 줄어든다 [S26].
- **작은 파일 병합**: 작은 파일이 많으면 파티션 위치 조회와 파일별 오버헤드 때문에 느리고, S3 요청 한도에 걸려 SlowDown 오류가 날 수 있다. 가장 좋은 시점은 쓰기 전에 합치는 것(쓰는 쪽에서 더 큰 파일 쓰기, Glue ETL로 합치기, 파티션 키 수 줄이기)이다 [S26]. 파티션 한 곳에 파일이 1000개를 넘으면 S3 목록 연산이 여러 번 필요하고, 파티션 아래에 추가 디렉터리 계층을 두지 않는 것이 좋다 [S26].

### 벡터화 개념과 Amazon Bedrock Knowledge Bases (Skill 2.4.6, v1.1 신규)

벡터 임베딩은 텍스트 청크를 나타내는 숫자열(벡터)이며, 모델이 각 청크를 벡터로 바꿔 텍스트를 수학적으로 비교(의미 유사도)할 수 있게 한다. 벡터는 부동소수점(float32) 또는 이진(binary)일 수 있다. 이진 벡터는 차원당 1비트만 써 부동소수점의 32비트보다 저장 비용이 낮지만 정밀도는 낮다. 이진 임베딩 모델을 고르면 이진 벡터를 지원하는 모델과 벡터 스토어를 함께 골라야 한다 [S28].

- **Bedrock Knowledge Bases 흐름**: 지식 베이스는 RAG(검색 증강 생성) — 데이터 저장소의 정보를 끌어와 LLM 응답을 보강하는 기법 — 을 구현하도록 돕는다 [S28]. 지식 베이스를 만들 때 데이터 소스 커넥터·임베딩 모델·벡터 스토어를 설정하고, 만든 뒤에는 데이터를 ingest(sync)해야 질의할 수 있다. ingestion은 데이터 소스의 원본 데이터를 지정한 임베딩 모델과 설정에 따라 벡터 임베딩으로 변환한다 [S32]. 전처리 단계에서 데이터를 텍스트로 변환하고 관리 가능한 청크로 나눈 뒤 임베딩으로 변환해 원본 문서와의 매핑을 유지한 채 벡터 인덱스에 기록한다 [S28]. 런타임에는 임베딩 모델로 사용자 질의를 벡터로 바꾸고, 벡터 인덱스에서 의미가 비슷한 청크를 찾아 프롬프트에 추가 컨텍스트로 붙인 뒤 모델에 보내 응답을 생성한다 [S28].
- **청킹 전략**: FIXED_SIZE(설정한 근사 크기), HIERARCHICAL(큰 청크 층 + 그로부터 파생한 작은 청크 층), SEMANTIC(NLP로 유사 내용끼리 묶음), NONE(파일 하나를 청크 하나로 취급 — 필요하면 사전에 문서를 쪼개 둠) [S31].
- **임베딩 모델**: 지식 베이스가 지원하는 임베딩 모델에는 Amazon Titan Embeddings G1 - Text, Titan Text Embeddings V2, Cohere Embed English/Multilingual v3와 멀티모달 모델(Titan Multimodal Embeddings G1, Cohere Embed v3 Multimodal, Amazon Nova Multimodal Embeddings)이 있다. 지원하는 벡터 유형(부동소수점/이진)과 차원 수는 모델마다 다르며 문서의 표로 정리되어 있다 [S29].
- **벡터 스토어**: API의 StorageConfiguration이 받는 벡터 스토어 값은 OPENSEARCH_SERVERLESS, PINECONE, REDIS_ENTERPRISE_CLOUD, RDS, MONGO_DB_ATLAS, NEPTUNE_ANALYTICS, OPENSEARCH_MANAGED_CLUSTER, S3_VECTORS이다 [S30]. (스토어별 선택 기준 비교는 이 노트에서 다루지 않음 — gaps 참고)
- **동기화(sync)**: 데이터를 추가·수정·삭제할 때마다 데이터 소스를 sync해야 지식 베이스에 다시 색인된다. sync는 증분이라 바뀐 문서만 처리하고, 변경 없는 문서는 건너뛰며, 삭제된 문서는 벡터 스토어에서 제거된다. 재처리는 파싱·청킹·임베딩 생성·벡터 스토어 색인을 모두 포함한다. API로는 StartIngestionJob 요청으로 sync를 시작하고 GetIngestionJob으로 상태(COMPLETE)를 추적한다. Amazon Aurora(RDS) 이외의 벡터 스토어는 sync가 끝난 뒤에도 새 임베딩이 질의에 반영되기까지 몇 분 걸릴 수 있다 [S32].
- **공지(신규 중단)**: 2026-09-30부터 customer-managed 지식 베이스에서 Confluence·SharePoint·Salesforce·Web Crawler 커넥터를 새로 만들 수 없다(기존 커넥터는 계속 동작). 이런 커넥터가 필요하면 Amazon Bedrock Managed Knowledge Base를 권장한다 [S33][S32].

## 시험에서 묻는 방식

1. **Redshift 테이블 설계 선택** — 시나리오 요지: 큰 팩트 테이블이 큰 디멘션 테이블과 자주 조인되고, 쿼리가 최근 N일 범위 조건을 자주 쓰며, 튜닝 인력이 부족하다. 요구사항 키워드: "조인", "범위 조건", "관리 부담 최소". → 정답 방향: 조인 열을 DISTKEY로 colocate(또는 분산 스타일을 맡기려면 AUTO)하고 날짜 열을 정렬 키로(또는 SORTKEY AUTO/ATO). → 오답 후보와 탈락 이유: 큰 테이블에 ALL(저장 공간이 노드 수만큼 곱절·적재 느림), EVEN(조인 colocation 없음), 팩트 테이블에 분산 키를 둘 이상(팩트 테이블은 분산 키가 하나뿐). 갱신이 잦으면 INTERLEAVED보다 COMPOUND 권장. 근거 [S1][S2][S3][S4].
2. **스키마 드리프트/스키마 진화 대응** — 시나리오 요지: 소스 스키마가 자주 바뀌어 파이프라인이 깨진다. (a) 크롤러가 수동 수정한 테이블 정의를 덮어쓰지 말고 새 컬럼만 반영해야 한다, (b) 스트리밍 프로듀서·컨슈머 사이의 스키마 변경 계약을 강제해야 한다, (c) S3의 컬럼 이름 변경·삭제·순서 변경을 재작성 없이 처리해야 한다. → 정답 방향: (a) 크롤러 "Add new columns only", (b) Glue Schema Registry 호환성 모드(BACKWARD 권장, 이전 스키마 소비자가 최신 스키마를 처리해야 하면 FORWARD, 둘 다면 FULL), (c) Iceberg(메타데이터 전용 스키마 변경) 또는 포맷별 가능 여부(Parquet 이름 기준 vs 인덱스 기준) 선택. → 오답 후보와 탈락 이유: "Ignore the change"(변경 미반영), NONE(검사 없음 — 계약 강제 불가), CSV(순서 변경·중간 삽입 불가), ORC 기본 인덱스 기준(삭제·중간 삽입 불가). 근거 [S14][S15][S16][S17].
3. **이기종 마이그레이션의 스키마 변환 도구 선택** — 시나리오 요지: Oracle(또는 SQL Server) DB의 스키마와 저장 코드를 Aurora PostgreSQL로 변환하고 평가 보고서를 받고 싶다. 설치 없이 콘솔에서 완전 관리형으로 하고 싶다 / Teradata DW를 Redshift로 옮기고 싶다. 요구사항 키워드: "스키마 변환", "평가 보고서", "설치 없음". → 정답 방향: 전자는 DMS Schema Conversion(스키마만 변환, 데이터는 DMS로), 후자(DMS SC 경로 표에 없는 DW 소스)는 AWS SCT. → 오답 후보와 탈락 이유: DMS의 데이터 마이그레이션 기능은 데이터를 옮기는 기능이고 스키마 변환은 별도 기능(DMS SC), Glue Schema Registry는 생산자·소비자 사이 스키마 계약용, Lake Formation은 권한 관리. 근거 [S12][S15][S19][S20][S34].
4. **계보·벡터화 개념 판별** — 시나리오 요지: (a) 배포된 모델이 어떤 학습 잡·데이터셋(S3 URI)에서 나왔는지 감사/재현해야 한다 vs Glue/Redshift 자산의 데이터 흐름을 OpenLineage 호환으로 시각화해야 한다, (b) 사내 문서를 임베딩해 RAG에 쓰고 원본이 바뀔 때 반영해야 한다. → 정답 방향: (a) 전자는 SageMaker ML Lineage Tracking(artifact·action·context·association), 후자는 SageMaker Catalog(DataZone 기반) 데이터 계보, (b) Bedrock Knowledge Bases(청킹 → 임베딩 모델 → 벡터 스토어)와 원본 변경 시 sync(증분) 실행. → 오답 후보와 탈락 이유: Lake Formation LF-Tag(권한을 주는 속성이지 계보 추적이 아님), "원본이 바뀌면 자동 재색인"(문서를 바꾼 뒤 sync를 실행해야 재색인됨), 이진 임베딩 모델 선택 시 이진 벡터를 지원하지 않는 벡터 스토어(모델과 스토어가 함께 이진 벡터를 지원해야 함). 근거 [S12][S22][S23][S25][S28][S31][S32].

## 흔한 함정·혼동 짝

1. **Redshift KEY vs ALL vs EVEN vs AUTO** — KEY=조인 열로 colocate(팩트 테이블은 분산 키 하나뿐), ALL=전체 사본(저장 ×노드 수·거의 갱신되지 않는 테이블만), EVEN=조인에 참여하지 않거나 불명확할 때, AUTO=기본값(크기에 따라 자동) → 시험 단서: "조인 열 colocate", "slow moving", "기본" [S1][S2]
2. **COMPOUND vs INTERLEAVED 정렬 키** — COMPOUND는 정렬 키 열의 접두 조건에 유리(기본값, 정기 갱신 시 권장), INTERLEAVED는 각 열에 동일 가중치로 임의 열 부분집합 조건에 유리(최대 8열) → 시험 단서: "접두(prefix) 조건", "어떤 열 조합으로 필터" [S3]
3. **정보용 제약조건 vs 강제 제약조건(Redshift)** — UNIQUE·PK·FK는 강제되지 않고 플래너 힌트로만 쓰이며, NOT NULL만 강제된다 → 시험 단서: "제약조건을 위반한 INSERT도 성공", "쿼리 계획 힌트" [S6]
4. **ENCODE AUTO vs 열별 수동 ENCODE** — 한 열이라도 인코딩을 직접 지정하면 테이블이 ENCODE AUTO가 아니게 되고 나머지 열은 RAW/AZ64/LZO 규칙으로 배정된다 → 시험 단서: "압축 인코딩을 직접 지정", "자동 관리" [S5]
5. **Redshift 분산 스타일 vs Athena/S3 파티셔닝** — Redshift는 객체 안 파티셔닝 개념이 없고 분산 스타일로 노드·슬라이스 배치를 정한다. Athena는 S3 경로(파티션 키)로 스캔 범위를 줄인다 → 시험 단서: "DISTKEY" vs "PARTITIONED BY" [S1][S27]
6. **DynamoDB GSI vs LSI** — GSI는 파티션 키·정렬 키 모두 다르게, 테이블 생성 후에도 추가·삭제 가능, 최종 일관성만. LSI는 같은 파티션 키+다른 정렬 키, 생성 시에만, 파티션 키 값당 10 GB, 강한 일관성 선택 가능 → 시험 단서: "이미 만든 테이블에 인덱스 추가", "강한 일관성" [S11]
7. **DynamoDB 액세스 패턴 우선 vs RDBMS식 정규화 우선** — DynamoDB는 데이터 모양을 쿼리에 맞춰 조직하고(쿼리 시 재구성하지 않음) 테이블 수를 최소화한다. 대용량 시계열·매우 다른 액세스 패턴은 예외 → 시험 단서: "쿼리 패턴", "single table", "핫 파티션" [S8][S9]
8. **LF-Tag vs IAM 태그** — LF-Tag는 Lake Formation 권한(LF-TBAC)용, IAM 태그는 IAM 정책용이며 서로 호환되지 않는다. LF-Tag는 같은 키에 값 하나만, 리소스 생성 시 지정 불가 → 시험 단서: "LF-TBAC", "속성 기반 권한" [S12][S13]
9. **크롤러 스키마 변경 정책(갱신/새 컬럼만/무시)** — "Update the table definition"(정의 갱신) vs "Add new columns only"(수동 수정 보존, 새 컬럼만) vs "Ignore the change"(테이블 미갱신) → 시험 단서: "수동으로 수정한 스키마를 덮어쓰지 않음" [S14]
10. **Schema Registry BACKWARD vs FORWARD vs FULL(+_ALL, NONE, DISABLED)** — BACKWARD: 현재+직전 버전 읽기(필드 삭제·선택 필드 추가, 권장), FORWARD: 현재+다음 버전(필드 추가·선택 필드 삭제), FULL: 이전 또는 다음 버전(선택 필드 추가/삭제), *_ALL은 모든 이전 버전 대상, NONE은 검사 없음, DISABLED는 새 버전 불가 → 시험 단서: "선택 필드", "모든 이전 버전" [S15]
11. **Parquet 이름 기준 vs 인덱스 기준(ORC는 기본이 반대)** — 이름 기준은 중간 추가·삭제·순서 변경 가능하지만 이름 변경 불가, 인덱스 기준은 이름 변경만 가능 → 시험 단서: "컬럼 이름 변경", "중간에 컬럼 추가" [S17]
12. **Iceberg 스키마 진화 vs 파일 재작성** — Iceberg 스키마 업데이트는 메타데이터 전용이라 데이터 파일이 바뀌지 않고, 추가·삭제·이름 변경·순서 변경·타입 확장을 지원한다 → 시험 단서: "재작성 없이 스키마 변경" [S16]
13. **DMS Schema Conversion vs DMS 데이터 마이그레이션** — DMS SC는 스키마(와 코드 객체)만 변환하고 데이터는 옮기지 않는다 → 시험 단서: "스키마 변환 + 평가 보고서" vs "데이터 이전/CDC" [S19]
14. **AWS SCT vs DMS Schema Conversion** — DMS SC는 DMS 안의 완전 관리형 웹 기반 기능(SCT 엔진 위), SCT는 독립 실행형 애플리케이션(+CLI)이며 DW 소스(Teradata 등)·ETL·빅데이터 변환 범위가 더 넓다 → 시험 단서: "설치 없이 콘솔", "Teradata/Netezza → Redshift" [S19][S20][S34]
15. **SageMaker ML Lineage Tracking vs SageMaker Catalog 데이터 계보** — 전자는 ML 워크플로 엔티티(artifact·action·context·association), 후자는 OpenLineage 호환 데이터 자산 계보(DataZone 기반) → 시험 단서: "모델 거버넌스·재현" vs "Glue/Redshift 자산 흐름·OpenLineage" [S22][S23][S25]
16. **파티션 프로젝션 vs Glue 파티션 인덱스 vs MSCK REPAIR TABLE** — 프로젝션은 파티션 값을 규칙으로 계산(관리 불필요), 파티션 인덱스는 카탈로그 파티션 조회 가속, MSCK는 Hive 스타일 파티션만·새 파티션만 추가(느릴 수 있음) → 시험 단서: "수만 개 파티션", "MSCK가 느림" [S26][S27]
17. **파티셔닝 vs 버킷팅 vs 정렬(Athena)** — 파티셔닝은 자주 쓰는 필터 키, 버킷팅은 고카디널리티 키의 단일 값 조회, 정렬은 시간 구간 쿼리를 파티션 없이 가속(드문 쿼리를 위한 과도한 파티셔닝은 작은 파일을 낳음) → 시험 단서: "user_id 조회", "시간 단위 파티션" [S26]
18. **임베딩 모델 vs 벡터 스토어 vs 청킹(Bedrock KB)** — 청킹은 문서 분할, 임베딩 모델은 청크·질의를 벡터로 변환, 벡터 스토어는 임베딩 저장·유사도 검색. 이진 임베딩 모델을 쓰면 이진 벡터를 지원하는 스토어도 필요 → 시험 단서: "차원", "청크", "벡터 DB" [S28][S29][S30][S31]
19. **KB 데이터 변경 반영(sync) vs 자동 재색인** — 소스 파일을 추가·수정·삭제한 뒤에는 sync를 실행해야 재색인되며, sync는 증분(바뀐 문서만 처리) → 시험 단서: "문서가 갱신되면", "StartIngestionJob" [S32]

### 후보 3 — Skill 2.4.3 · associate

- **해설 초안**: DMS Schema Conversion은 AWS DMS의 완전 관리형 웹 기반 기능으로 Oracle → Aurora PostgreSQL 변환 경로를 지원하고, 평가 보고서 생성·변환·적용(또는 SQL 내보내기)을 제공한다. 스키마만 변환하며 데이터는 DMS의 데이터 마이그레이션 기능으로 옮긴다. [S19]
- **오답 근거**: B — Schema Registry는 생산자·소비자 사이의 스키마 버전 계약용 / C — Lake Formation은 권한 관리 / D — 데이터를 옮기는 기능이며 스키마·코드 객체 변환은 DMS Schema Conversion 기능의 몫
- **근거**: [S19] https://docs.aws.amazon.com/dms/latest/userguide/CHAP_SchemaConversion.html — "a fully managed, web-based feature that builds on the AWS Schema Conversion Tool"
