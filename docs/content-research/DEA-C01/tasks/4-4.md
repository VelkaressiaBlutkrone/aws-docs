## 핵심 개념

> 이 문서는 감사 대응을 위한 로그 **준비·보존·무결성·중앙화** 관점이다. 파이프라인 운영·알림·성능 문제 해결(이벤트 유형·선택기·Insights, 메트릭/구독 필터 운영, 보존 자동화 등)은 Task 3.3 문서(3-3.md)가 다룬다. 두 문서에서 CloudTrail·CloudWatch Logs·로그 분석이 겹치는 부분은 이 문서가 "감사 준비·보존·중앙화"를 맡는다.

### CloudTrail로 API 호출 추적 — 감사 준비 (Skill 4.4.1)

감사에서 CloudTrail의 역할은 "누가·언제·무엇을 했는가"를 **변조되지 않은 상태로 오래 보관하고 증명**하는 것이다. 이벤트에는 요청자, 사용한 서비스, 수행한 작업, 작업 파라미터, 응답 요소가 담긴다 [S1].

- **이벤트 기록(Event history) ≠ 감사 기록**: 이벤트 기록은 현재 리전 최근 90일의 관리 이벤트만 보여 주며 [S1], 영구 기록이 아니므로 지속 기록에는 trail이 필요하다 [S2].
- **다중 리전·다중 계정 범위**: 모든 리전에 적용하는 trail은 새로 생기는 리전도 자동으로 기록한다 [S1]. 조직 trail은 관리 계정 또는 위임 관리자 계정에서 만들고 관리 계정과 모든 멤버 계정의 이벤트를 기록한다 [S5]. 조직 trail을 쓰지 않으면 모든 계정에 trail을 만들고 보관 버킷을 로그 아카이브 계정의 S3로 지정한다 [S2]. 여러 계정의 로그를 하나의 S3 버킷으로 모을 수도 있다 [S1].
- **보관 계정 분리**: 별도 AWS 계정을 로그 아카이브 계정으로 만들고(AWS Organizations를 쓰면 조직에 등록) 조직 trail 도입을 고려한다 [S2]. AWS SRA의 Log Archive 계정은 보안 관련 로그·백업을 수집·보관하는 전용 계정으로, 불변 스토리지이며 통제·자동화·모니터링되는 경로로만 접근하도록 설계한다 [S7].
- **무결성**: 로그 파일 무결성 검증을 켜면 CloudTrail이 digest 파일을 시간 단위로 전달한다 [S1]. 해시는 SHA-256, 디지털 서명은 SHA-256 with RSA이다 [S3]. digest 파일은 로그 파일과 별도 폴더에 놓여 세분화된 보안 정책을 적용할 수 있다 [S3]. AWS CLI는 CloudTrail이 전달한 위치의 파일을 검증하고 [S3], digest 파일이 참조하는 로그 파일만 검증하며 로컬로 내려받은 로그 파일은 CLI로 검증할 수 없다(옮긴 로그는 직접 만든 도구로 검증) [S4][S3]. CloudTrail 로그 객체의 무결성 보호·검증 수단은 로그 파일 무결성 검증과 S3 Object Lock 두 가지다 [S7].
- **암호화·접근 통제**: 기본적으로 로그 파일은 S3 서버 측 암호화(SSE)로 암호화되고, SSE-KMS는 추가 계층이다 [S1]. SSE-KMS를 쓰면 로그를 읽을 때 S3 읽기 권한과 KMS 복호화 권한이 모두 필요하다 [S7]. 암호화가 켜진 trail에서 KMS 키가 비활성화되었거나 키 정책이 CloudTrail에 맞게 구성되지 않으면 CloudTrail이 로그를 전달하지 못한다 [S6]. 버킷·KMS 정책에는 `aws:SourceArn` 조건 키를 넣는 것이 모범 사례다 [S2][S6].
- **삭제 방지·보관**: MFA Delete는 IAM 사용자 암호가 유출되어도 영구 삭제를 막는 추가 계층이지만 수명 주기 구성과 함께 쓸 수 없다 [S2]. trail 기본값은 로그를 S3에 무기한 보관하며 S3 수명 주기 규칙(예: 오래된 로그를 Glacier로 이동)으로 보존 정책을 정한다 [S2]. 로그 가용성은 S3 Object Lock, 객체 버전, 수명 주기 규칙으로 확보한다 [S7].
- **비용**: 데이터 이벤트는 trail 구성 시 기본 비활성이며 관리 이벤트와 달리 추가 비용이 들고, 리전별 관리 이벤트 첫 사본은 무료다 [S1].

|---|---|---|---|
| 로그 파일 무결성 검증 | 로그 파일이 변경·삭제되었는지 사후 확인 [S2] | digest는 시간당 전달 [S1], CLI는 원래 S3 위치의 파일만 검증 [S4] | "변조되지 않았음을 입증" |

### CloudWatch Logs에 애플리케이션 로그 저장 (Skill 4.4.2)

- **보존**: 기본은 무기한 저장이며 로그 그룹마다 언제든 보존 기간을 바꿀 수 있다 [S12]. 보존 자동화·메트릭 필터 운영은 3-3.md 참조.
- **암호화**: 로그 그룹 데이터는 항상 암호화되며 기본은 CloudWatch Logs의 서버 측 암호화이고, 대안으로 AWS KMS를 쓸 수 있다 [S13]. KMS는 로그 그룹 수준에서 연결하며(생성 시 또는 이후) 연결 후 새로 수집되는 데이터만 해당 키로 암호화된다 [S13]. 키를 나중에 분리해도 이미 그 키로 암호화된 데이터는 그대로 남고 CloudWatch Logs가 계속 읽을 수 있지만, 키가 나중에 비활성화되면 그 로그를 읽지 못한다 [S13]. 대칭 KMS 키만 지원한다 [S13].
- **로그 클래스**: Standard(전체 기능)와 Infrequent Access(IA, 기능 일부·낮은 수집 단가, 임시 쿼리와 사후 포렌식 분석에 적합)가 있고, 생성 후 클래스를 바꿀 수 없으며 두 클래스는 수집 비용만 다르다 [S14]. 구독 필터는 Standard 클래스 로그 그룹에서만 지원된다 [S15]. Lambda 로그를 S3나 Amazon Data Firehose로 보내는 용도의 Delivery 클래스는 Logs Insights 같은 기능을 제공하지 않는다 [S14].
- **교차 계정 공유**: 수신 계정이 Kinesis Data Streams를 감싸는 destination을 만들고 송신 계정이 구독 필터로 보낸다. 송신자는 단일 계정 또는 조직이 될 수 있고 로그 그룹과 destination은 같은 리전이어야 한다 [S16]. 한 조직의 여러 계정이 한 수신 계정으로 보내게 하는 정책을 줄 수 있지만 송신 계정마다 구독 필터는 따로 만들어야 한다 [S16].
- **조직 단위 중앙화**: AWS Organizations와 연동한 중앙화 규칙으로 여러 멤버 계정·리전의 로그를 조직 내 중앙 계정으로 복제하며, 목적지 계정에서 백업 리전을 둘 수 있고 소스의 고객 관리형 KMS 암호화 로그 처리 방식을 고를 수 있다 [S17]. 규칙 생성 이후 도착한 새 로그만 대상이며 과거 로그는 중앙화되지 않는다 [S17].
- **S3 내보내기와 구독**: 내보내기(`CreateExportTask`)는 KMS 암호화 버킷과 보존 기간이 지정된 Object Lock 버킷도 지원하지만, 지속 아카이브용으로 정기 내보내기를 쓰기보다 구독을 쓰라고 권고한다 [S18]. 구독 필터는 Kinesis Data Streams, Amazon Data Firehose, Lambda로 거의 실시간 전달한다 [S15].
- **데이터 보호**: 민감 데이터를 자동 탐지해 마스킹하며, 상승된 IAM 권한이 있으면 마스킹되지 않은 데이터를 볼 수 있다 [S12].

### CloudTrail Lake — 중앙 쿼리와 현재 상태 (Skill 4.4.3)

- **개념**: CloudTrail Lake는 이벤트에 SQL 기반 쿼리를 실행한다. 이벤트는 **이벤트 데이터 스토어(EDS)**에 모이고 EDS는 불변 컬렉션이며, 보존 기간은 1년 연장형 가격 옵션이면 최대 3,653일(약 10년), 7년형이면 최대 2,557일(약 7년)이다 [S9]. 조직의 이벤트(여러 리전·계정)를 조직 EDS에 둘 수 있다 [S9]. 쿼리 결과는 7일까지 볼 수 있고 [S9], 쿼리는 스캔한 데이터량으로 과금된다 [S9]. EDS를 AWS Glue Data Catalog에 연합(federate)하면 Athena로 SQL 쿼리도 할 수 있다 [S9]. 기본으로 EDS의 모든 이벤트는 CloudTrail이 암호화하며 자체 KMS 키를 선택할 수 있다(연결 후 키를 제거·변경할 수 없음) [S9].
- **현재 공식 상태(중요, 2026-10 확인)**: AWS는 **2026-05-31부터 CloudTrail Lake를 신규 고객에게 열지 않는다**. 기존 고객은 계속 사용하고 Lake에는 중요한 버그 수정·보안 업데이트만 제공되며, CloudTrail 자체(trail, Insights, 집계 이벤트)는 영향이 없다 [S8]. 조직 EDS가 있으면 신규 멤버 계정·리전 확장까지 계속 동작하지만, 계정 단위 EDS만 있으면 조직에 새로 추가되는 계정의 수집은 지원하지 않는다 [S8]. 문서는 Lake 로그를 Amazon CloudWatch로 이전하길 권고하고 2023년 이전 데이터는 이전되지 않는다 [S8]. 한편 Athena 문서의 CloudTrail 로그 쿼리 페이지는 여전히 Lake를 대안으로 소개한다 [S11](문서 간 시차 — gaps 참조). 시험 가이드 v1.1은 Skill 4.4.3에 Lake를 그대로 포함하므로 개념(EDS, SQL, 보존, 조직 통합, 비용 모델)은 알아 두되 "신규 고객 중단" 상태를 함께 기억한다.
- **비용 모델**: 수집과 저장을 함께 과금하며 수집은 비압축 데이터 기준, 저장은 압축 데이터 기준이고 쿼리는 선택해 분석한 압축 데이터량 기준이다(FAQ 설명) [S1]. 가격 옵션은 두 가지로, 1년 연장형은 월 사용량이 25 TB 미만이면, 7년형은 25 TB를 넘으면 권장된다 [S10]. 7년형에서 1년 연장형으로는 바꿀 수 있지만 1년 연장형에서 7년형으로는 바꿀 수 없다 [S1].
- **trail 로그를 Athena로 쿼리하는 방식과의 차이**: Athena는 S3에 쌓인 CloudTrail 로그 파일을 CloudTrail 콘솔 또는 Athena 콘솔에서 테이블을 만들어 직접 쿼리한다 [S11]. Lake는 S3 버킷 대신 데이터 레이크에 이벤트를 저장해 더 풍부하고 빠른 쿼리를 하며 Athena 없이 CloudTrail 콘솔에서 쿼리한다 [S11].

|---|---|---|---|
| 저장소 | 로그 파일 S3(Object Lock·수명 주기·무결성 검증으로 통제) [S2][S7] | EDS(불변 컬렉션) [S9] | CloudWatch Logs 등 통합 저장 [S8] |
| 보존 상한 | S3 정책에 따름(기본 무기한) [S2] | 최대 3,653일 / 2,557일 [S9] | 로그 그룹 보존 설정 [S12] |
| 쿼리 | Athena SQL(테이블 직접 생성) [S11] | CloudTrail 콘솔 SQL, Athena 연합 가능 [S9] | Logs Insights(Logs Insights QL·SQL·PPL), OpenSearch 기반 분석 [S8] |
| 비용 | Athena는 실행한 쿼리에 대해 과금 [S19] | 수집+저장 일체형 + 스캔량 과금 [S1][S9] | 문서는 비슷한 가격대라고 설명 [S8] |

### 로그 분석 서비스 선택 (Skill 4.4.4)

감사 로그 분석 서비스는 **데이터가 어디에 있는가**, **질의가 얼마나 자주·빨라야 하는가**, **검색 방식(SQL vs 전문 검색)**으로 고른다.

| 서비스 | 데이터 위치 | 적합한 경우 | 비용·제약 특성 | 시험 단서 키워드 |
|---|---|---|---|---|
| Amazon Athena | S3의 로그(CloudTrail 등) | S3 데이터를 표준 SQL로 임시(ad-hoc) 쿼리 [S19] | 서버리스, 실행한 쿼리에 대해서만 과금 [S19] | "S3 로그", "서버리스 SQL" |
| CloudWatch Logs Insights | CloudWatch Logs의 로그 | 대화형 로그 분석, 별도 설정·인프라 없이 즉시 시작 [S12] | 종량제, 쿼리가 스캔한 수집 로그량으로 과금 [S12] | "CloudWatch Logs의 로그를 바로 쿼리" |
| Amazon OpenSearch Service | 도메인에 인덱싱한 로그 | 실시간 로그 분석, 빈번한 쿼리, 전문(full-text) 검색 [S20] | 비실시간·가끔 쿼리는 Light Engine(SQL 유사 검색) 옵션 [S20]. 이 옵션이 속한 Centralized Logging with OpenSearch 솔루션은 2026-12 종료 예정 [S23] | "전문 검색", "실시간 대시보드" |
| CloudTrail Lake | CloudTrail 이벤트 데이터 스토어 | CloudTrail 이벤트 SQL 조사 [S9] | 신규 고객 중단 [S8] | "CloudTrail 이벤트 SQL" |

- 선택 규칙: S3에 이미 있고 가끔 조사 → Athena. CloudWatch Logs에 이미 있고 즉석 조사 → Logs Insights(지원 쿼리 언어는 3-3.md 참조). 실시간·반복 검색·전문 검색·시각화 대시보드 → OpenSearch Service. Athena에서 서비스 로그를 효율적으로 쓰는 요령(파티션 프로젝션 등)은 3-3.md 참조.

### 다양한 서비스 통합 로깅 (Skill 4.4.5)

여러 서비스의 로그를 한곳에 모으는 대표 패턴은 다음과 같다.

- **중앙 S3 로그 저장소**: CloudTrail, VPC Flow Logs, Elastic Load Balancing, GuardDuty, AWS Config, AWS WAF 같은 서비스가 S3에 로그를 남기므로, 전용 계정의 중앙 S3 버킷에 모아 소수 버킷에서 통제·접근·업무 분리를 강제한다 [S7].
- **CloudWatch Logs 중앙화**: 조직 단위 중앙화 규칙 또는 교차 계정 구독으로 모은다 [S16][S17].
- **스트리밍 적재**: 구독 필터가 Kinesis Data Streams·Amazon Data Firehose·Lambda로 전달하고 [S15], VPC Flow Logs는 CloudWatch Logs, S3, Amazon Data Firehose로 게시할 수 있다 [S1]. Firehose는 S3, Amazon Redshift, OpenSearch Service, Splunk 등으로 전달한다 [S21]. Firehose의 이전 이름은 Amazon Kinesis Data Firehose이다(개명) [S21].
- **OpenSearch로 AWS 서비스 로그 수집**: Centralized Logging with OpenSearch 솔루션이 AWS 서비스 로그를 OpenSearch 도메인으로 수집·정제하는 파이프라인과 시각화용 대시보드 템플릿을 제공한다 [S20]. 다만 이 AWS Solution은 2026년 12월에 종료될 예정이며 문서는 CloudWatch의 통합 데이터 관리·분석 기능을 권고한다(종료되는 것은 솔루션이고 OpenSearch Service 자체가 아니다) [S23].
- **대용량 후처리·분석**: 로그 파일 집합이 매우 크면 Amazon EMR 클러스터로 페타바이트급 분석을 수행한다 [S22]. 보존 요구사항을 정해 S3 수명 주기를 적용한다 [S22].

| 패턴 | 흐름 | 적합한 경우 | 제약 | 시험 단서 키워드 |
|---|---|---|---|---|
| 조직 trail → Log Archive S3 | 모든 계정 이벤트 → 전용 계정 버킷 [S5][S7] | 감사 증적 중앙 보관 | KMS 정책 오류 시 전달 실패 [S6] | "중앙 로그 보관 계정" |
| 구독 필터 → Firehose → 대상 | 로그 이벤트 → Firehose → S3·Redshift·OpenSearch·Splunk [S15][S21] | 관리형 적재·변환 | Standard 클래스만 [S15] | "서버 관리 없이 적재" |
| VPC Flow Logs → CloudWatch Logs·S3·Firehose | 게시 대상 선택 [S1] | 네트워크 트래픽 로그 | — | "Flow Logs를 OpenSearch에" |
| 중앙화 규칙 | 멤버 계정·리전 로그 → 중앙 계정 [S17] | 조직 전체 CloudWatch Logs 모으기 | 과거 로그 제외 [S17] | "조직 전체" |
| EMR | 거대한 로그 집합 분석 [S22] | 페타바이트급 분석 [S22] | EMR 클러스터를 직접 실행 [S22] | "수 PB 로그" |

## 시험에서 묻는 방식

1. **변조 방지 감사 로그 설계** — "여러 계정·리전의 API 활동을 한 곳에 보관하고, 로그가 사후에 바뀌거나 지워지지 않았음을 입증", "보안팀만 접근" 같은 요구 → **관리 계정(또는 위임 관리자)의 멀티 리전 조직 trail → 별도 Log Archive 계정의 S3 버킷 + 로그 파일 무결성 검증 + 최소 권한 버킷 정책**, 필요하면 SSE-KMS(키·키 정책 관리)·S3 Object Lock. 오답 후보: Event history(최근 90일·관리 이벤트만), CloudWatch Logs 보존 설정만(trail 대체 아님), 각 계정 단일 리전 trail, MFA Delete와 수명 주기 병용(병용 불가). 근거 [S1][S2][S3][S5][S7]
2. **CloudWatch Logs 저장·공유·보존 통제** — "앱 로그를 KMS 키로 암호화", "다른 보안 계정으로 실시간 전달", "조직 전체 로그를 중앙 계정으로", "S3로 장기 보관" → KMS는 **로그 그룹 수준·연결 이후 신규 수집분만**, 교차 계정은 **수신 계정 destination + 송신 계정 구독 필터(같은 리전)**, 조직 전체는 **중앙화 규칙(과거 로그 제외)**, 지속 아카이브는 **구독(내보내기 `CreateExportTask`는 일회성·비동기)**. 오답 후보: KMS 연결로 기존 로그까지 즉시 재암호화, IA 클래스에 구독 필터, 지속 아카이브에 정기 내보내기. 근거 [S13][S14][S15][S16][S17][S18]
3. **중앙 쿼리·분석 서비스 선택** — "여러 계정·리전 CloudTrail 이벤트를 SQL로 중앙 조사" → 개념상 CloudTrail Lake(EDS, 조직 EDS, 최대 3,653일/2,557일)이나 **현행 문서는 2026-05-31부터 신규 고객 중단**이므로 대안은 조직 trail → S3 → Athena 또는 CloudWatch(문서 권고). "S3 로그를 서버 없이 가끔 SQL" → Athena, "CloudWatch Logs의 로그를 즉석 쿼리" → Logs Insights, "실시간·반복 검색·전문 검색" → OpenSearch Service, "거대한 로그 집합 배치" → EMR, "로그를 관리형으로 S3·OpenSearch·Splunk에 적재" → Firehose. 근거 [S8][S9][S11][S12][S19][S20][S21][S22]

## 흔한 함정·혼동 짝

1. **Event history vs trail** — Event history는 설정 없이 현재 리전 최근 90일 관리 이벤트, trail은 S3 등으로 지속 기록·데이터 이벤트 포함 → 단서: "90일을 넘어", "영구 기록" [S1][S2]
2. **로그 파일 무결성 검증 vs S3 Object Lock vs MFA Delete** — 검증은 변경·삭제 여부를 사후 확인(digest 시간당), Object Lock은 무결성 보호/가용성 수단, MFA Delete는 삭제·버전 변경에 추가 인증이며 수명 주기와 병용 불가 → 단서: "입증" vs "방지" [S1][S2][S7]
3. **CLI 무결성 검증의 전제** — digest·로그 파일이 CloudTrail이 전달한 원래 S3 위치에 있어야 하고 로컬 다운로드본은 CLI로 검증 불가(다른 위치로 옮긴 로그는 직접 만든 검증 도구) → 단서: "다른 버킷으로 복사한 로그 검증" [S3][S4]
4. **기본 SSE vs SSE-KMS** — 기본은 S3 서버 측 암호화, SSE-KMS는 추가 계층이며 키 비활성·정책 오류 시 CloudTrail이 로그를 전달하지 못함 → 단서: "KMS 키를 비활성화했더니 로그가 안 쌓인다" [S1][S6]
5. **조직 trail vs 계정별 trail / 조직 EDS vs 계정 EDS** — 조직 trail은 관리 계정·위임 관리자에서 만들고 전 멤버 계정을 기록, Lake의 계정 EDS는 신규 멤버 계정 수집 미지원·조직 EDS는 지원 → 단서: "새 계정 자동 포함" [S5][S8]
6. **CloudWatch Logs 내보내기 vs 구독 필터** — 내보내기는 비동기 작업이며 지속 아카이브에는 구독을 권고, 구독은 거의 실시간·Standard 클래스만 → 단서: "계속 S3로 아카이브" [S18][S15]
7. **교차 계정 구독 vs 중앙화 규칙** — 구독은 수신 계정의 destination과 송신 계정의 구독 필터(같은 리전), 중앙화 규칙은 Organizations 연동 복제(규칙 생성 이후 로그만) → 단서: "조직 전체를 규칙 하나로" [S16][S17]
8. **KMS 연결 시점 vs 기존 로그** — CloudWatch Logs KMS는 연결 이후 신규 수집분만 암호화, 키 비활성화 시 그 키로 암호화된 로그는 읽을 수 없음 → 단서: "기존 로그도 재암호화?" [S13]
9. **Standard vs Infrequent Access vs Delivery 로그 클래스** — IA는 구독 필터 불가·클래스 변경 불가·수집 단가만 다름, Delivery는 Lambda 로그를 S3/Firehose로 보내는 용도(Logs Insights 불가) → 단서: "임시 쿼리·사후 포렌식" [S14][S15]
10. **CloudTrail Lake vs trail+Athena vs CloudWatch** — Lake는 데이터 레이크에서 SQL(EDS 불변·최대 3,653/2,557일), trail+Athena는 S3 로그 파일 쿼리, 문서는 Lake 신규 고객 중단(2026-05-31)과 CloudWatch 이전 권고 → 단서: "관리형 중앙 SQL" + "현재 상태" [S8][S9][S11]
11. **Lake 가격 옵션** — 1년 연장형(월 25 TB 미만 권장, 최대 3,653일)과 7년형(25 TB 초과 권장, 최대 2,557일), 1년 연장형→7년형 전환 불가·7년형→1년 연장형 가능, 보존은 이벤트 시간 기준 → 단서: "월 수집량 TB" [S10][S9][S1]
12. **Athena vs Logs Insights vs OpenSearch** — S3 로그 SQL / CloudWatch Logs 즉석 쿼리 / 실시간·빈번 쿼리·전문 검색 → 단서: 데이터 위치와 질의 빈도. 참고로 Centralized Logging with OpenSearch 솔루션은 2026-12 종료 예정이며 OpenSearch Service 자체와는 별개다 [S19][S12][S20][S23]
13. **Kinesis Data Firehose vs Amazon Data Firehose** — 같은 서비스의 개명(이전 이름이 Kinesis Data Firehose) → 단서: 구버전 표기가 보기에 섞여 나올 때 [S21]

### 후보 1 — Skill 4.4.1 · associate
- **문제**: 수십 개 AWS 계정을 가진 조직이 모든 계정·리전의 API 활동을 보안 계정만 접근하는 한 곳에 보관하고, 로그가 사후에 변경·삭제되지 않았음을 입증해야 한다. 가장 적절한 구성은?
- **보기**: A. 각 계정에서 CloudTrail 이벤트 기록(Event history)을 주기적으로 내려받아 보관한다. / B. 관리 계정(또는 위임 관리자)에서 멀티 리전 조직 trail을 만들어 별도 Log Archive 계정의 S3 버킷으로 전달하고 로그 파일 무결성 검증을 켠다. / C. 각 계정에 단일 리전 trail을 만들고 CloudWatch Logs 보존 기간을 무기한으로 둔다. / D. 계정마다 CloudTrail Lake 계정 이벤트 데이터 스토어를 만든다.
- **정답**: B
- **해설 초안**: 조직 trail은 관리 계정 또는 위임 관리자 계정에서 만들며 관리 계정과 모든 멤버 계정의 이벤트를 기록한다. 로그 아카이브 계정의 전용 S3 버킷에 보관하고, 로그 파일 무결성 검증(SHA-256 해시, SHA-256 with RSA 서명, digest 파일)으로 변경·삭제 여부를 확인한다. [S2][S3][S5]
- **오답 근거**: A — Event history는 현재 리전 최근 90일의 관리 이벤트만 다룬다 [S1] / C — 단일 리전 trail은 모든 리전을 기록하지 못하고 [S1], CloudWatch Logs 보존 설정은 digest 파일 기반 무결성 검증을 제공하지 않는다 [S3] / D — Lake는 2026-05-31부터 신규 고객에게 닫혔고 계정 EDS는 조직에 새로 추가되는 계정의 수집을 지원하지 않는다 [S8]
- **근거**: [S5] https://docs.aws.amazon.com/awscloudtrail/latest/userguide/creating-trail-organization.html — "Organization trails log events for the management account and all member accounts in the organization."

### 후보 2 — Skill 4.4.2 · associate
- **문제**: 애플리케이션 로그를 CloudWatch Logs에 저장 중이다. (1) 고객 관리형 KMS 키로 로그 그룹을 암호화하고, (2) 다른 AWS 계정(보안 계정)의 Kinesis Data Streams로 로그를 거의 실시간 전달해야 한다. 올바른 설명은?
- **보기**: A. KMS 키를 로그 그룹에 연결하면 기존에 저장된 로그도 즉시 모두 새 키로 재암호화된다. / B. 수신 계정이 destination을 만들고 송신 계정이 구독 필터를 만들며, 로그 그룹과 destination은 같은 리전에 있어야 한다. / C. 계정 간 전달은 `CreateExportTask`로만 가능하다. / D. Infrequent Access 로그 클래스의 로그 그룹에도 구독 필터를 만들 수 있다.

- **해설 초안**: 교차 계정 전달은 수신 계정의 destination(Kinesis Data Streams를 감쌈)과 송신 계정의 구독 필터로 구성하며 로그 그룹과 destination은 같은 리전이어야 한다. KMS는 로그 그룹 수준에서 연결하고 연결 후 새로 수집되는 데이터만 해당 키로 암호화된다. [S13][S16]
- **오답 근거**: A — 연결 후 새로 수집되는 데이터만 해당 키로 암호화된다 [S13] / C — 내보내기는 S3로의 비동기 작업이고 지속 전달에는 구독을 쓰라고 권고한다 [S18] / D — 구독 필터는 Standard 클래스에서만 지원된다 [S15]
- **근거**: [S16] https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/CrossAccountSubscriptions-Kinesis.html — "The log group and the destination must be in the same AWS Region."
