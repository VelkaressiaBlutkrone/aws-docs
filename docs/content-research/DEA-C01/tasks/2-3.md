## 핵심 개념

### Redshift COPY: S3에서 Redshift로 로드 (Skill 2.3.1)

COPY는 S3·EMR·SSH 호스트·DynamoDB의 데이터를 테이블에 적재하는 명령이며 테이블 이름·데이터 소스·인가(IAM 역할) 세 요소만 있으면 실행된다 [S1]. 기존 행에 새 행을 추가(append)하고 [S1], Redshift Spectrum 외부 테이블은 읽기 전용이라 COPY 대상이 될 수 없다 [S1]. S3 파일 적재에는 INSERT보다 COPY가 효율적이다: MPP로 여러 파일을 동시에 읽는다 [S7].

- **병렬 로드 설계**: 테이블 데이터를 여러 파일로 나누고 파일 수를 클러스터 슬라이스 수의 배수로 맞춘다. Redshift는 파일 크기를 고려해 분배하지 않으므로 압축 후 1MB~1GB의 비슷한 크기로 맞춘다 [S3]. 공통 접두사(폴더)로 지정하면 폴더 전체를, 매니페스트로 명시하면 서로 다른 버킷·폴더의 파일을 로드한다 [S3]. Redshift Serverless는 128의 배수를 권장하고, 압축하지 않은 단일 CSV·Parquet·ORC가 128MB보다 크면 Redshift가 자동 분할한다 [S7].
- **인가·암호화**: SSE-S3·SSE-KMS로 암호화된 파일은 COPY가 자동 인식해 적재하고 SSE-C는 지원하지 않는다 [S4]. 클라이언트 측 암호화(`ENCRYPTED`+`MASTER_SYMMETRIC_KEY`)는 신규 고객에게 2025-04-30부터 닫혔고 2026-04-30 이후에는 쓸 수 없다고 공지됐으며 서버 측 암호화 전환을 권고한다 [S1][S4].
- **오류 허용·검증**: `MAXERROR`는 허용 오류 수(기본 0, 상한 100000)이고 `NOLOAD`는 적재 없이 파일 유효성만 검사한다 [S2].
- **통계·압축**: `STATUPDATE`를 쓰지 않으면 테이블이 처음 비어 있을 때만 통계가 자동 갱신된다. 비어 있지 않은 테이블의 크기가 크게 바뀌면 `ANALYZE` 또는 `STATUPDATE ON`을 권장한다 [S2]. `COMPUPDATE`는 압축 인코딩 자동 적용을 제어한다 [S2].
- **컬럼형(ORC·Parquet)**: S3 버킷이 Redshift 데이터베이스와 같은 리전이어야 하고, 지원 파라미터가 제한되며(`MAXERROR` 미지원), 압축 인코딩이 자동 적용되지 않고, COPY가 Redshift Spectrum을 사용한다 [S5].
- **자동 수집(auto-copy)**: S3 이벤트 통합을 만들고 COPY JOB을 생성하면 지정 경로에 새 파일이 생길 때 자동으로 COPY를 실행한다. Redshift가 어떤 파일을 로드했는지 추적하고, 한 COPY 명령에 묶을 파일 수도 Redshift가 정한다 [S6].

### Redshift UNLOAD: Redshift에서 S3로 내보내기 (Skill 2.3.1)

- 기본 동작: SELECT 결과를 슬라이스 수에 따라 여러 파일로 병렬 기록해 재로드를 쉽게 한다. `PARALLEL OFF`는 결과를 순차(직렬)로 기록하며 한 파일로 쓰게 할 수 있고, 데이터 파일 최대 크기는 6.2GB이며 초과 시 파일이 추가로 만들어진다 [S8]. `MAXFILESIZE`로 파일 크기를 제한하고 기본값은 6.2GB다 [S8][S9].
- 암호화: UNLOAD는 기본으로 SSE-S3로 암호화해 기록한다 [S8][S4]. SSE-KMS도 가능하다 [S4].
- Parquet: 파일 수준 압축 없이 row group마다 SNAPPY로 압축하고, 32MB row group을 맞추려고 `MAXFILESIZE`를 32MB의 배수로 내림한다. 밑줄(`_`)이나 점(`.`)으로 시작하는 접두사의 파일은 Redshift Spectrum이 숨김 파일로 보고 무시한다 [S9].

| 항목 | COPY | UNLOAD |
|---|---|---|
| 방향 | S3 등 → Redshift 테이블 [S1] | Redshift 쿼리 결과 → S3 [S8] |
| 병렬성 | 입력 파일 수가 슬라이스 수의 배수일 때 균등 분배 [S3] | 기본 슬라이스 수만큼 여러 파일, `PARALLEL OFF`면 순차(직렬) 기록 [S8] |
| 오류·크기 한도 | `MAXERROR` 기본 0, 컬럼형은 `MAXERROR` 미지원 [S2][S5] | 파일 최대 6.2GB, Parquet는 32MB 배수 [S8][S9] |
| 암호화 | SSE-S3·SSE-KMS 자동, SSE-C 미지원 [S4] | 기본 SSE-S3 [S8] |
| 시험 단서 | "소형 파일 수천 개 적재 느림", "COPY vs INSERT" | "S3 데이터 레이크로 내보내기", "Parquet로 언로드" |

### S3 스토리지 클래스와 수명 주기 전환 (Skill 2.3.2)

수명 주기(Lifecycle) 구성은 버킷 단위로 하나이며 최대 1,000개 규칙(조정 불가)을 담는다 [S12]. 규칙은 필터(prefix·태그·객체 크기·조합)와 전환/만료 액션으로 구성되고 [S12], 기존 객체와 이후 추가되는 객체 모두에 적용된다 [S14]. 클래스 전환은 폭포(waterfall) 모델이라 아래 방향으로만 가능하다 [S11].

| 스토리지 클래스 | 설계 용도 | 가용성(설계)·AZ | 최소 보관 기간 | 최소 청구 객체 크기 | 조회 특성 | 시험 단서 |
|---|---|---|---|---|---|---|
| S3 Standard | 자주 접근, 밀리초 | 99.99%, ≥3 AZ | 없음 | 없음 | 즉시 | "기본 클래스", "자주 접근" [S10] |
| S3 Standard-IA | 오래 보관·드물게 접근(월 1회), 밀리초 | 99.9%, ≥3 AZ | 30일 | 128KB | GB당 조회 요금 | "백업 1차 사본", "드물게 접근" [S10] |
| S3 One Zone-IA | 재생성 가능·드물게 접근 | 99.5%, 1 AZ | 30일 | 128KB | GB당 조회 요금, AZ 손실 시 데이터 손실 | "재생성 가능한 데이터", "CRR 복제본" [S10] |
| S3 Intelligent-Tiering | 접근 패턴을 모르거나 변함 | 99.9%, ≥3 AZ | 없음 | 없음(128KB 미만은 모니터링·자동 계층 이동 제외) | 조회 요금 없음, 객체당 모니터링·자동화 요금 | "접근 패턴 불명" [S10] |
| S3 Glacier Instant Retrieval | 분기 1회 접근 아카이브, 밀리초 | 99.9%, ≥3 AZ | 90일 | 128KB | GB당 조회 요금 | "아카이브인데 즉시 조회" [S10] |
| S3 Glacier Flexible Retrieval | 연 1회 접근, 분~시간 복원 | 99.99%(복원 후), ≥3 AZ | 90일 | 객체당 40KB 메타 추가 | Expedited 1–5분, Standard 3–5시간, Bulk 5–12시간 | "분~시간 단위 복원 허용" [S10][S13] |
| S3 Glacier Deep Archive | 연 1회 미만, 시간 단위 복원 | 99.99%(복원 후), ≥3 AZ | 180일 | 객체당 40KB 메타 추가 | 복원 옵션 2가지, 12~48시간 범위 | "연 1회 미만 접근", "시간 단위 복원 허용" [S10][S13] |

표의 가용성·AZ 수·최소 보관 기간·최소 청구 크기는 [S10]의 비교표와 [S34]의 성능 비교표(열 순서: Standard, Intelligent-Tiering, Standard-IA, One Zone-IA, Glacier IR, Glacier FR, Glacier DA)에서 같은 값을 확인했다. Glacier FR·DA의 40KB는 [S34]가 최소 용량 청구로, [S10]이 객체당 추가 메타데이터로 서술한다. Reduced Redundancy Storage(`REDUCED_REDUNDANCY`)는 사용하지 않기를 권고한다 [S10].

- **전환 제약**: 2024-09부터 128KB 미만 객체는 기본으로 어떤 클래스로도 전환되지 않는다. 전환 요청 비용이 절감액보다 클 수 있어서이며, 허용하려면 객체 크기 필터(`ObjectSizeGreaterThan`/`ObjectSizeLessThan`)를 둔다 [S11]. 2024-09 이전에 만든 구성은 변경하기 전까지 이전 동작을 유지한다 [S11].
- **최소 보관 기간**: 최소 보관 기간이 있는 클래스에서 그 전에 전환·삭제하면 남은 기간만큼 요금이 붙는다. 한 규칙으로 최소 기간 이전의 연쇄 전환을 정의할 수 없다(예: Glacier Instant Retrieval 4일 후 전환, 20일 후 Deep Archive 전환은 불가 → Deep Archive는 최소 94일 이후) [S11].
- **Glacier 전환**: Flexible Retrieval은 Deep Archive로만 전환 가능하고 Deep Archive는 일방향이다 [S11]. 객체당 40KB 오버헤드(8KB는 Standard 요금, 32KB는 Glacier 요금)가 붙고, 전환은 비동기지만 도착 클래스 요금·최소 보관 기간은 규칙 충족일부터 적용된다 [S11]. 아카이브 객체는 실시간 접근이 불가능해 먼저 복원(임시 복사본 생성)해야 하며, 복원 중에는 아카이브와 임시 복사본(Standard 요금) 비용을 함께 낸다 [S11].
- **Intelligent-Tiering 자동 계층**: Frequent Access로 시작 → 30일 미접근 시 Infrequent Access → 90일 미접근 시 Archive Instant Access로 자동 이동하며, 비동기 접근이 가능하면 선택적으로 Archive Access(90일 이상)와 Deep Archive Access(180일 이상) 계층을 활성화한다 [S10].

### S3 만료와 정리 (Skill 2.3.3)

`Expiration` 액션은 객체 수명이 끝났을 때 버킷의 버전 관리 상태에 따라 다르게 동작한다 [S14]. 세부 동작은 아래 표와 같다.

| 액션 | 비버전 버킷 | 버전 활성 버킷 | 버전 중지 버킷 |
|---|---|---|---|
| `Transition` | 지정 클래스로 전환 [S12] | 현재 버전만 전환 [S12] | 활성과 동일 [S12] |
| `Expiration` | 객체를 영구 삭제(복구 불가) [S12] | 현재 버전이 삭제 마커가 아니면 삭제 마커를 만들고 기존 버전은 noncurrent로 보존 [S12][S14] | `null` 버전 ID 삭제 마커 생성, 현재 버전 ID가 `null`이면 영구 삭제 [S12] |
| `NoncurrentVersionTransition` | 효과 없음 [S12] | noncurrent 버전을 전환 [S12] | 활성과 동일 [S12] |
| `NoncurrentVersionExpiration` | 효과 없음 [S12] | noncurrent 버전 영구 삭제(복구 불가) [S12][S14] | 활성과 동일 [S12] |

- **noncurrent 정리**: `NoncurrentVersionExpiration`은 noncurrent가 된 뒤 일수(`NoncurrentDays`)와 유지할 최신 noncurrent 버전 수(`NewerNoncurrentVersions`, 1~100)를 함께 쓸 수 있고 둘 다 초과해야 삭제된다. 유지할 버전 수를 지정하려면 `Filter`가 있어야 하며 없으면 `InvalidRequest` 오류가 난다 [S12][S14]. noncurrent 일수는 후속 버전이 생성된 시점부터 센다 [S12].
- **삭제 마커 정리**: 버전 활성 버킷에서 noncurrent 버전이 0개인 삭제 마커가 expired object delete marker이며, `ExpiredObjectDeleteMarker` 액션으로 제거한다. 이 액션과 `AbortIncompleteMultipartUpload`는 객체 태그 필터가 있는 규칙에 쓸 수 없다 [S12].
- **불완전 멀티파트 업로드**: 객체 만료 규칙은 불완전 멀티파트 업로드를 지우지 못하므로 `AbortIncompleteMultipartUpload`로 일수 상한을 둔다 [S12].
- **충돌·예외**: 객체는 하루에 하나의 Lifecycle 액션만 대상이 되며 영구 삭제가 전환보다 우선한다 [S14]. S3 Object Lock이 적용된 noncurrent 버전에는 아무 동작도 하지 않고, 버킷 정책으로 Lifecycle 삭제·전환을 막을 수 없다 [S14]. 만료된 객체의 저장 요금은 부과되지 않지만 실제 삭제까지 지연될 수 있다 [S14]. Standard-IA/One Zone-IA 30일 미만, Glacier Flexible Retrieval 90일 미만, Deep Archive 180일 미만에 만료시키면 최소 보관 기간만큼 청구된다 [S14].

### S3 버전 관리와 MFA Delete (Skill 2.3.4)

- 버킷 상태는 비버전(기본)·버전 활성·버전 중지 세 가지이고, 한 번 버전을 활성화하면 비버전 상태로 돌아갈 수 없으며 중지만 가능하다 [S15]. 객체를 삭제하면 영구 삭제 대신 삭제 마커가 현재 버전이 된다 [S15]. 버전마다 객체 전체가 저장되어(diff 아님) 3개 버전이면 객체 3개로 청구된다 [S15].
- 버전 관리와 Lifecycle을 같이 써서 보존·비용을 조정하며, 비버전 버킷에 만료 규칙이 있었다면 버전 활성화 후 같은 영구 삭제 동작을 유지하려고 noncurrent 만료 규칙을 추가해야 한다 [S15].
- MFA Delete는 버킷 버전 상태 변경과 객체 버전의 영구 삭제에 추가 인증을 요구한다. 버킷 소유자(루트 계정)만 활성화할 수 있고 콘솔이 아니라 CLI/API로 설정하며, Lifecycle 구성과 함께 쓸 수 없다 [S16].

### DynamoDB TTL (Skill 2.3.4)

- 항목별 만료 타임스탬프 속성을 지정하면 DynamoDB가 만료 항목을 자동 삭제하며, 삭제에 쓰기 처리량을 쓰지 않는 비용 효율적인 방법이다 [S17]. TTL 속성은 Number 타입의 Unix epoch 초 단위여야 하고, Number가 아니면 TTL 프로세스가 무시한다 [S17].
- 삭제는 만료 후 보통 며칠 이내이고 정확한 시각이 보장되지 않는다. 만료됐지만 삭제 전 항목은 Scan·Query 결과에 남으므로 필터 표현식으로 제외한다. TTL을 미래 시각으로 갱신하거나 속성을 제거하면 삭제되지 않는다 [S17].
- TTL 삭제는 DynamoDB Streams에 사용자 삭제가 아닌 서비스 삭제로 기록되고 LSI·GSI에서도 일반 삭제처럼 제거된다. 글로벌 테이블에서는 TTL 삭제가 모든 복제본 테이블로 복제된다 [S17].

### 법적·비즈니스 요구에 따른 보존과 삭제 (Skill 2.3.5)

| 수단 | 적용 대상 | 동작·제약 | 시험 단서 |
|---|---|---|---|
| S3 Object Lock — Governance | 객체 버전 | 대부분의 사용자가 삭제·잠금 변경 불가, 특별 권한(`s3:BypassGovernanceRetention`)이 있는 사용자는 우회 가능 [S18] | "일부 관리자는 삭제 가능", "보존 기간 테스트" |
| S3 Object Lock — Compliance | 객체 버전 | 루트 포함 누구도 보존 기간 내 덮어쓰기·삭제 불가, 모드·기간 단축 불가. 유일한 우회는 계정 삭제 [S18] | "루트도 삭제 불가", "SEC 17a-4" |
| S3 Object Lock — Legal hold | 객체 버전 | 만료일 없이 명시적으로 제거할 때까지 보호, 보존 기간과 독립, `s3:PutObjectLegalHold` 권한자가 부여·해제 [S18] | "소송·감사 기간 불명" |
| AWS Backup Vault Lock | 백업 볼트 | Governance는 권한자가 해제 가능, Compliance는 grace time(최소 3일) 이후 변경·삭제 불가이며 락된 볼트의 백업은 수명 주기가 끝나기 전 삭제 불가 [S23] | "백업 WORM", "백업 조기 삭제 방지" |
| S3 Lifecycle 만료 | 객체 | 기간 경과 시 삭제(버전 상태에 따라 삭제 마커 또는 영구 삭제) [S14] | "N년 후 자동 삭제" |
| Iceberg DELETE + VACUUM (Athena) | Iceberg 행 | `DELETE`는 position delete 파일을 쓰는 merge-on-read 삭제, `VACUUM`이 스냅샷 만료·고아 파일 제거 [S19][S20] | "특정 사용자 행 삭제" |
| S3 Tables 유지 관리 | S3 Tables 테이블 | 스냅샷 관리가 기본 120시간 초과 스냅샷을 만료·제거하고, noncurrent 객체 삭제는 영구적 [S21] | "관리형 Iceberg 스냅샷 만료" |
| Redshift DELETE + VACUUM | 테이블 행 | 삭제 행은 표시만 되고 즉시 제거되지 않으며 백그라운드 VACUUM DELETE가 회수 [S22] | "삭제했는데 디스크 안 줄어듦" |
| DynamoDB TTL | 항목 | 만료 후 며칠 이내 삭제(정확한 시각 보장 안 함) [S17] | "자동 만료, 쓰기 비용 없음" |

- **Object Lock 전제**: 버전 관리가 켜진 버킷에서만 동작하며, 잠금은 지정한 객체 버전에만 적용된다. 새 버전 생성과 삭제 마커 추가는 막지 않는다 [S18]. 보존 기간은 고정(retain-until-date) 또는 가변(이벤트 보류+기간)이며 버킷 기본 보존 기간도 둘 수 있다 [S18]. 보호된 버전을 버전 ID로 삭제하면 403이 반환되고, 버전 ID 없는 단순 삭제는 삭제 마커를 만든다 [S18].
- **삭제 요청(right to erasure) 처리 시 고려**: 개인정보 삭제 요청은 백업·원천 시스템을 포함한 모든 저장소를 대상으로 하며, 삭제 대신 되돌릴 수 없는 마스킹도 방법이다 [S24]. 데이터 레이크에서는 사용자 데이터가 든 객체를 찾아 해당 행을 제거한 새 버전을 쓰고 이전 버전을 삭제해야 한다 [S25]. Athena Iceberg `DELETE`는 데이터 파일을 다시 쓰지 않고 position delete 파일만 쓰므로, 현재 테이블 상태에 없는 오래된 파일의 물리 제거는 `VACUUM`(스냅샷 만료·고아 파일 제거, 보존 기간 경과 후)이나 S3 Tables 스냅샷 관리에 달려 있다 [S19][S20][S21].
- **복제본·백업**: S3 복제는 버전 ID를 지정한 삭제를 대상 버킷에 복제하지 않는다. 최신 복제 구성(`Filter` 사용)에서는 삭제 마커도 기본으로 복제하지 않으며 삭제 마커 복제를 따로 추가할 수 있다 [S28]. 락된 AWS Backup 볼트의 백업은 수명 주기 종료 전 삭제할 수 없다 [S23]. Redshift 수동 스냅샷은 직접 삭제하거나 지정한 보존 기간이 끝날 때까지 유지된다 [S30]. 삭제 요청은 이런 복제본·백업까지 범위에 넣어야 한다 [S24].

## 시험에서 묻는 방식

1. **S3 계층화·비용 최적화** — "로그를 처음 30일은 자주 조회, 이후 드물게, 1년 뒤에는 감사용으로만 보관하며 복원에 시간이 걸려도 된다 / 접근 패턴을 알 수 없다 / 객체가 작다" → 정답 방향: 패턴이 예측되면 Lifecycle 규칙으로 Standard → Standard-IA(재생성 불가 1차 사본) 또는 One Zone-IA(재생성 가능) → Glacier Flexible Retrieval / Deep Archive 순으로 전환하고, 마지막에 `Expiration`을 둔다. 접근 패턴이 불명확하거나 변하면 Intelligent-Tiering(조회 요금 없음, 모니터링·자동화 요금), 128KB 미만 객체는 기본 전환 제외라 크기 필터를 쓰거나 묶어서 저장한다 → 오답 후보와 탈락 이유: One Zone-IA를 유일한 사본에 쓰면 AZ 손실에 취약하고, 최소 보관 기간(30/90/180일) 전에 전환·삭제하면 잔여 기간 요금이 붙으며, Glacier 클래스 객체는 복원 전에는 읽을 수 없고, Glacier Flexible Retrieval은 Deep Archive로만 전환된다 → 근거 [S10][S11][S12][S13].
2. **버전 관리 버킷의 정리·보호** — "버전 관리 버킷의 저장 비용이 늘었다 / 실수로 삭제해도 복구 가능해야 한다 / 삭제 마커와 불완전 업로드가 쌓인다" → 정답 방향: `NoncurrentVersionExpiration`(`NoncurrentDays` + 유지할 `NewerNoncurrentVersions`, `Filter` 필수), `ExpiredObjectDeleteMarker`, `AbortIncompleteMultipartUpload`를 Lifecycle에 둔다. 삭제 방지를 더 강하게 하려면 Object Lock(버전 관리 필수) → 오답 후보와 탈락 이유: `Expiration`만 쓰면 버전 활성 버킷에서는 삭제 마커만 추가되고 noncurrent 버전은 남으며, MFA Delete는 Lifecycle과 함께 쓸 수 없고 콘솔에서 켤 수 없으며 루트만 활성화할 수 있고, 버킷 정책으로는 Lifecycle 삭제를 막지 못한다 → 근거 [S12][S14][S15][S16][S18].
3. **Redshift 적재·내보내기** — "S3의 압축 파일을 Redshift로 빠르게 적재 / 일부 불량 행이 있어도 계속 적재 / Redshift 데이터를 Parquet로 데이터 레이크에 내보내기" → 정답 방향: COPY(INSERT 아님), 파일을 여러 개로 나눠 슬라이스 수의 배수(Serverless는 128의 배수)로 맞추고 매니페스트·접두사로 지정, 불량 행 허용은 `MAXERROR`(컬럼형 ORC·Parquet 제외), 사전 검증은 `NOLOAD`, 신규 파일 자동 적재는 auto-copy(S3 이벤트 통합 + COPY JOB), 내보내기는 `UNLOAD … PARQUET`(기본 병렬 다중 파일, `MAXFILESIZE`로 조정, 기본 SSE-S3) → 오답 후보와 탈락 이유: 큰 단일 파일은 병렬 이점이 없고, Parquet/ORC COPY는 `MAXERROR`를 지원하지 않으며 S3 버킷이 같은 리전이어야 하고, 클라이언트 측 암호화는 2026-04-30 이후 사용할 수 없다 → 근거 [S1][S2][S3][S5][S6][S7][S8][S9].
4. **보존·삭제·복원 요구 선택** — "규정상 N년간 아무도 삭제 못 하게(루트 포함)" / "소송 때문에 기간 미정으로 동결" / "고객의 삭제 요청 처리" / "리전 장애 대비 15분 이내 복제" / "실수로 지운 DynamoDB 항목 복구" → 정답 방향: 루트까지 막으려면 Object Lock Compliance(백업은 Backup Vault Lock Compliance), 기간 미정이면 Legal hold, 일부 관리자만 우회하려면 Governance, 삭제 요청은 Iceberg `DELETE` 후 `VACUUM`(또는 S3 Tables 스냅샷 관리)·Redshift `DELETE`+`VACUUM`과 복제본·백업 범위 고려, 15분은 CRR+S3 RTC, 항목 복구는 DynamoDB PITR(최근 35일, 초 단위) → 오답 후보와 탈락 이유: Governance는 권한이 있으면 우회되고, TTL은 삭제 시각을 보장하지 않으며 며칠 걸릴 수 있고, 복제는 새 객체만 대상이고 기존 객체는 Batch Replication이 필요하다 → 근거 [S17][S18][S19][S20][S21][S22][S23][S24][S26][S31].

## 흔한 함정·혼동 짝

1. **`Expiration` vs `NoncurrentVersionExpiration`** — 버전 활성 버킷에서 `Expiration`은 현재 버전에 삭제 마커를 얹을 뿐 noncurrent 버전은 건드리지 않고, 이전 버전의 영구 삭제는 `NoncurrentVersionExpiration`이 담당 → 시험 단서: "버전 관리 버킷인데 스토리지가 계속 늘어남" [S12][S14].
2. **삭제 마커 vs expired object delete marker** — 삭제 마커가 현재 버전이고 noncurrent 버전이 0개일 때가 expired object delete marker이며 `ExpiredObjectDeleteMarker`로 정리. 태그 필터가 있는 규칙에는 쓸 수 없음 → 시험 단서: "버전이 다 사라졌는데 삭제 마커만 남음" [S12][S14].
3. **객체 만료 vs 불완전 멀티파트 업로드** — 객체 만료 규칙은 불완전 멀티파트 업로드를 지우지 않으므로 `AbortIncompleteMultipartUpload`가 별도로 필요(태그 필터 불가) → 시험 단서: "미완료 업로드 파트 비용" [S12].
4. **Lifecycle Transition vs Intelligent-Tiering** — Transition은 정한 일수에 따른 규칙 기반, Intelligent-Tiering은 접근 패턴에 따른 자동 이동(조회 요금 없음, 모니터링·자동화 요금, 128KB 미만 제외) → 시험 단서: "접근 패턴을 모른다" = Intelligent-Tiering / "N일 후 보관" = Lifecycle [S10][S11].
5. **Standard-IA vs One Zone-IA** — 둘 다 30일·128KB 최소와 GB당 조회 요금이 있고 밀리초 접근이지만, One Zone-IA는 1개 AZ라 AZ 손실 시 데이터를 잃으며 가용성이 낮다(99.5% vs 99.9%) → 시험 단서: "재생성 가능"=One Zone-IA / "유일한 사본"=Standard-IA [S10].
6. **Glacier Instant vs Flexible vs Deep Archive** — 밀리초 vs 분~시간 vs 12~48시간. 최소 보관 90/90/180일. Flexible·Deep Archive는 복원 필요 → 시험 단서: "분기 1회 접근하지만 즉시 조회"=Instant Retrieval [S10][S13].
7. **최소 보관 기간 vs 최소 객체 크기** — 기간 전 삭제·전환은 잔여 기간 요금, 128KB 미만은 128KB로 청구(IA 클래스) 또는 Lifecycle 전환 기본 제외(2024-09 이후) → 시험 단서: "작은 객체가 많은데 IA로 옮기니 비용이 늘었다" [S10][S11].
8. **Glacier 스토리지 클래스 vs Amazon Glacier 서비스** — S3 Glacier 클래스 객체는 S3 안에 남아 있고 별도 Glacier 서비스 콘솔·API로 접근할 수 없다 → 시험 단서: "S3 객체를 Glacier로 전환" [S10][S11].
9. **비버전 vs 버전 중지 버킷** — 한 번 활성화하면 비버전으로 돌아갈 수 없고 중지만 가능. 중지 후에도 기존 버전은 남고 `null` 버전 ID 삭제 마커 동작이 다름 → 시험 단서: "버전 관리를 끄고 싶다" [S15][S12].
10. **MFA Delete vs Object Lock** — MFA Delete는 버전 상태 변경·버전 영구 삭제에 MFA 추가(루트가 CLI/API로 활성화, Lifecycle과 불가), Object Lock은 WORM 보존(버전 관리 필수) → 시험 단서: "삭제 시 MFA 요구" vs "일정 기간 삭제·덮어쓰기 불가" [S16][S18].
11. **Governance vs Compliance vs Legal hold** — Governance는 특별 권한자가 우회, Compliance는 루트 포함 불가·기간 단축 불가, Legal hold는 만료일 없이 명시적 해제 전까지이며 보존 기간과 독립 → 시험 단서: "루트도 못 지움"=Compliance / "기간 미정"=Legal hold [S18].
12. **Object Lock vs AWS Backup Vault Lock** — 전자는 S3 객체 버전, 후자는 백업 볼트(복구 지점). Vault Lock Compliance는 grace time 후 영구, 락된 볼트의 백업은 수명 주기 전 삭제 불가 → 시험 단서: "백업이 삭제되지 않도록" [S18][S23].
13. **DynamoDB TTL vs 즉시 삭제** — TTL 삭제는 만료 후 보통 며칠 이내, 시각 보장 없음, 만료 항목은 삭제 전까지 조회될 수 있어 필터 필요. 쓰기 처리량은 쓰지 않음 → 시험 단서: "만료 즉시 보이지 않아야 한다" = 필터 표현식 [S17].
14. **DynamoDB PITR vs 온디맨드 백업 vs 글로벌 테이블** — PITR은 최근 1~35일 내 초 단위 복원, 온디맨드 백업은 장기 보존·규정 준수용 전체 백업, 글로벌 테이블은 다중 리전 복원성(99.999% SLA) → 시험 단서: "실수로 삭제한 항목 복구" / "7년 보관" / "다중 리전" [S31].
15. **S3 라이브 복제 vs Batch Replication vs RTC** — 라이브 복제는 설정 이후 새·변경 객체만, 기존 객체는 Batch Replication, 15분 목표(99.99%)는 RTC이며 Batch Replication에는 RTC가 적용되지 않음 → 시험 단서: "기존 객체도 복제" [S26].
16. **복제 vs 백업** — 복제는 버전 관리 필수·비동기 사본(삭제 전파 규칙 있음), 백업(AWS Backup·스냅샷)은 보존 정책과 복구 지점 기반 → 시험 단서: "버전 ID 삭제는 복제되지 않는다" [S27][S28][S29].
17. **RDS Multi-AZ vs 읽기 복제본** — Multi-AZ의 대기 복제본은 읽기 트래픽을 처리하지 않는 고가용성용 → 시험 단서: "읽기 확장"은 Multi-AZ가 아님 [S33].
18. **Redshift 자동 스냅샷 vs 수동 스냅샷** — 자동은 기본 1일 보존·Redshift만 삭제, 수동은 직접 삭제할 때까지(또는 지정 기간) 보존 → 시험 단서: "장기 보존하려면 수동 스냅샷으로 복사" [S30].
19. **COPY vs INSERT, 단일 파일 vs 다중 파일** — COPY는 MPP로 병렬 적재, 파일 수는 슬라이스 배수(Serverless 128의 배수), 큰 비압축 단일 파일은 128MB 초과 시 자동 분할 → 시험 단서: "적재가 느리다" [S3][S7].
20. **COPY 텍스트 vs 컬럼형(ORC·Parquet)** — 컬럼형은 `MAXERROR`·`ACCEPTANYDATE` 미지원, 같은 리전 필요, 압축 인코딩 자동 적용 없음, Spectrum 사용 → 시험 단서: "Parquet COPY에서 불량 행 무시" = 불가 [S5][S2].
21. **UNLOAD 병렬 vs `PARALLEL OFF`** — 기본은 슬라이스별 다중 파일(최대 6.2GB), `PARALLEL OFF`는 직렬 기록 → 시험 단서: "내보낸 파일 수/크기 제어" [S8][S9].
22. **Iceberg `DELETE` vs `VACUUM`** — `DELETE`는 merge-on-read로 position delete 파일을 쓰는 논리 삭제, 물리 제거(오래된 스냅샷·고아 파일)는 `VACUUM`/스냅샷 관리 → 시험 단서: "삭제했는데 S3에 데이터 파일이 남음" [S19][S20][S21].
23. **Redshift `DELETE` vs `VACUUM`** — 삭제 행은 표시만 되고 즉시 제거되지 않으며 VACUUM DELETE가 회수(자동 백그라운드 실행) → 시험 단서: "삭제 후 디스크 사용량 그대로" [S22].
24. **클라이언트 측 vs 서버 측 암호화(COPY/UNLOAD)** — 클라이언트 측 암호화는 2026-04-30 이후 사용 불가로 공지되어 SSE-S3·SSE-KMS로 전환 권고 → 시험 단서: "COPY ENCRYPTED + MASTER_SYMMETRIC_KEY" [S1][S4].

## 자가 점검 문항 후보

### 후보 1 — Skill 2.3.1 · associate
- **문제**: S3에 있는 40GB짜리 gzip 압축 CSV 파일 하나를 슬라이스가 16개인 프로비저닝 Redshift 클러스터에 COPY하는데 적재가 너무 오래 걸린다. 가장 효과적인 개선은?
- **보기**: A. 데이터를 압축 후 1MB~1GB의 비슷한 크기로 16의 배수 개 파일로 나누고 공통 접두사로 COPY한다. / B. 파일을 행 단위 INSERT 문으로 나누어 적재한다. / C. MAXERROR를 100000으로 올린다. / D. 단일 파일을 유지하고 STATUPDATE OFF만 지정한다.
- **정답**: A
- **해설 초안**: COPY는 여러 파일을 병렬로 읽으며, 파일 수를 슬라이스 수의 배수로 맞추고 크기를 비슷하게(압축 후 1MB~1GB) 해야 슬라이스에 균등 분배된다. S3 파일 적재에는 INSERT보다 COPY가 효율적이다 [S3][S7].
- **오답 근거**: B — INSERT는 COPY의 MPP 병렬 적재보다 비효율적이다 [S7] / C — MAXERROR는 허용 오류 개수일 뿐 병렬성과 무관하다 [S2] / D — 단일 파일은 병렬 분배가 안 되고 STATUPDATE는 통계 갱신 여부만 제어한다 [S2][S3].
- **근거**: [S3] https://docs.aws.amazon.com/redshift/latest/dg/t_splitting-data-files.html — "the number of files is a multiple of the number of slices in your cluster"

### 후보 2 — Skill 2.3.2 · associate (서비스 선택)
- **문제**: 분석 로그를 S3에 저장한다. 객체별 접근 패턴을 예측할 수 없고 변할 수도 있으며, 조회 요금 없이 자동으로 비용을 줄이고 싶다. 대부분의 객체는 수 MB 이상이다. 가장 적합한 방법은?
- **보기**: A. S3 Intelligent-Tiering 스토리지 클래스를 사용한다. / B. 30일 후 S3 Standard-IA로 전환하는 Lifecycle 규칙을 둔다. / C. S3 One Zone-IA에 저장한다. / D. S3 Glacier Deep Archive에 저장한다.
- **정답**: A
- **해설 초안**: Intelligent-Tiering은 접근 패턴을 모니터링해 객체를 저비용 계층으로 자동 이동하며 조회 요금이 없다(대신 객체당 모니터링·자동화 요금) [S10].
- **오답 근거**: B — Standard-IA는 GB당 조회 요금과 30일 최소 보관 기간이 있고 접근 패턴 변화에 자동 대응하지 않는다 [S10] / C — 단일 AZ에 저장하는 재생성 가능 데이터용이며 조회 요금이 있다 [S10] / D — 복원에 12-48시간이 걸리고 180일 최소 보관 기간이 있어 변하는 접근 패턴에 맞지 않는다 [S13][S11].
- **근거**: [S10] https://docs.aws.amazon.com/AmazonS3/latest/userguide/storage-class-intro.html — "There are no retrieval fees for S3 Intelligent-Tiering."

### 후보 3 — Skill 2.3.3, 2.3.4 · associate
- **문제**: 버전 관리를 켠 S3 버킷에서 객체를 자주 덮어써 저장 비용이 급증했다. 최신 noncurrent 버전 3개만 유지하고, 그보다 오래된 noncurrent 버전은 noncurrent가 된 지 30일이 지나면 영구 삭제하려 한다. 올바른 구성은?
- **보기**: A. `Expiration` 액션을 30일로 설정한다. / B. `NoncurrentVersionExpiration`에 `NoncurrentDays`=30과 `NewerNoncurrentVersions`=3을 지정하고 `Filter`를 둔다. / C. 버킷에 MFA Delete를 활성화한다. / D. 버킷 정책에서 오래된 버전의 삭제를 허용한다.
- **정답**: B
- **해설 초안**: noncurrent 버전의 영구 삭제는 `NoncurrentVersionExpiration`이 담당하며, 경과 일수와 유지할 최신 noncurrent 버전 수(1~100)를 함께 지정할 수 있다. 유지할 버전 수를 지정하려면 `Filter`가 필요하다 [S12][S14].
- **오답 근거**: A — 버전 활성 버킷에서 `Expiration`은 현재 버전에 삭제 마커를 추가할 뿐 noncurrent 버전은 건드리지 않는다 [S14] / C — MFA Delete는 Lifecycle 구성과 함께 쓸 수 없다 [S16] / D — 버킷 정책으로는 Lifecycle 삭제·전환을 제어하지 못한다 [S14].
- **근거**: [S14] https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-expire-general-considerations.html — "a maximum number of noncurrent versions to retain (between 1 and 100)"

### 후보 4 — Skill 2.3.5 · associate (서비스 선택)
- **문제**: 금융 규정에 따라 거래 기록 객체를 7년 동안 루트 사용자를 포함한 어떤 사용자도 삭제·덮어쓸 수 없도록 보존해야 한다. 별도로 소송 때문에 일부 객체는 해제 시점을 정하지 않고 동결해야 한다. 알맞은 구성은?
- **보기**: A. 버전 관리를 켠 버킷에서 S3 Object Lock Compliance 모드로 7년 보존하고, 소송 대상 객체에는 Legal hold를 건다. / B. Object Lock Governance 모드로 7년 보존하고 MFA Delete를 활성화한다. / C. Lifecycle `Expiration`을 7년으로 설정하고 버킷 정책으로 삭제를 Deny한다. / D. 버전 관리만 켜고 Standard-IA 클래스에 저장한다.
- **정답**: A
- **해설 초안**: Compliance 모드는 루트를 포함한 모든 사용자의 삭제·덮어쓰기를 보존 기간 동안 막고 기간 단축도 허용하지 않는다. Legal hold는 만료일 없이 명시적으로 제거할 때까지 보호하며 보존 기간과 독립적이다. Object Lock은 버전 관리 버킷에서만 동작한다 [S18].
- **오답 근거**: B — Governance는 `s3:BypassGovernanceRetention` 같은 특별 권한이 있으면 우회할 수 있고, MFA Delete는 영구 삭제에 MFA를 요구할 뿐 WORM이 아니다 [S18][S16] / C — Lifecycle `Expiration`은 삭제 규칙이며 보존을 강제하는 WORM 보호는 Object Lock이 제공한다 [S14][S18] / D — 버전 관리는 삭제 시 삭제 마커를 만들 뿐 영구 삭제를 막지 못한다 [S15].
- **근거**: [S18] https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html — "if you never want any user, including the root user in your AWS account"

### 후보 5 — Skill 2.3.6 · associate (서비스 선택)
- **문제**: 주 리전 S3 버킷에 새로 쓰이는 객체를 다른 리전 버킷으로 복제해야 하고, 대부분의 객체가 15분 이내에 복제된다는 SLA 뒷받침이 필요하다. 소스 버킷에는 이미 객체가 많이 있다. 알맞은 구성은?
- **보기**: A. 소스·대상 버킷 모두 버전 관리를 켜고 CRR과 S3 Replication Time Control을 설정하며, 기존 객체는 Batch Replication으로 복제한다. / B. 같은 리전의 대상 버킷으로 SRR을 설정한다. / C. 대상 버킷에만 버전 관리를 켜고 CRR을 설정한다. / D. AWS Backup으로 일 1회 백업한다.
- **정답**: A
- **해설 초안**: CRR은 다른 리전 버킷으로 복사하고, S3 RTC는 새 객체의 99.99%를 15분 이내 복제하며 SLA가 뒷받침된다. 복제에는 소스·대상 모두 버전 관리가 필요하고, 설정 이전 객체는 on-demand 방식인 Batch Replication으로 복제한다 [S26][S27].
- **오답 근거**: B — SRR은 같은 리전 버킷 간 복사다 [S26] / C — 소스·대상 버킷 모두 버전 관리가 필요하다 [S27] / D — AWS Backup은 정책 스케줄 기반 백업이며 15분 복제 SLA를 제공하는 수단이 아니다 [S29][S26].
- **근거**: [S26] https://docs.aws.amazon.com/AmazonS3/latest/userguide/replication.html — "replicates 99.99 percent of new objects stored in Amazon S3 within 15 minutes"
