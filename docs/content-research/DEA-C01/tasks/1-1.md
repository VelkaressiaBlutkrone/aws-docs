### 스트리밍 수집 서비스 선택 (Skill 1.1.1, 1.1.10)

스트리밍 소스 문제는 "누가 읽는가 · 재처리가 필요한가 · 순서가 중요한가 · 코드를 쓸 것인가 · Kafka 호환이 필요한가"로 풀린다.

- **Kinesis Data Streams(KDS)** = 커스텀 소비자가 읽어 가는 스트림 저장소다. 소비자는 샤드 안에서 저장된 순서 그대로 읽고, 여러 애플리케이션이 같은 스트림을 동시에·독립적으로 소비할 수 있으며, 보존 기간 안에서는 같은 순서로 다시 읽을 수 있다 [S1]. 하나의 스트림이 수십만 개 소스의 쓰기를 받는다(팬인, #18) [S1].
- **Amazon Data Firehose** = 소비자 코드 없이 S3·Redshift·OpenSearch·Splunk·HTTP 엔드포인트 등으로 적재하는 완전 관리형 전달 서비스다. 데이터를 버퍼링해 묶어 전달하고, Lambda 변환·Parquet/ORC 형식 변환·동적 파티셔닝을 붙일 수 있다 [S8]. 예전 이름은 Amazon Kinesis Data Firehose다(#47) [S12].
- **Amazon MSK** = 관리형 Apache Kafka다. Provisioned는 브로커 단위로 확장하고 Serverless는 클러스터 확장·관리를 완전히 추상화한다(#54) [S14]. 기존 Kafka 애플리케이션이 있거나 오픈소스를 선호하면 MSK, 스트리밍이 처음이면 KDS를 쓰라는 것이 KDS FAQ의 기준이다(#16) [S1]. Kafka Connect 기반의 MSK Connect로 S3 등에 데이터를 전달하는 구성도 가능하다 [S14].
- **DynamoDB Streams** = DynamoDB 테이블의 항목 수준 변경 로그이며 24시간 동안 보관된다(#58) [S16].

선택 규칙(공식 근거에서 읽히는 것만):
- 목적지가 S3/Redshift 등이고 필요한 처리가 변환·형식 변환·파티셔닝 정도면 Firehose가 소비자 코드를 없애 준다 [S8]. 소비자가 둘 이상이면 KDS는 EFO를 권장한다(#17) [S1].
- KDS를 Firehose의 소스로 붙일 수 있고, 하나의 KDS를 여러 Firehose 스트림의 소스로 쓸 수도 있지만 Firehose의 읽기도 샤드 읽기 한도를 소모한다(#45) [S8].
- KDS와 MSK 비교(확장 속도·지연·보존)는 AWS 백서의 비교 표(#51~#53)가 근거다 [S13].

### Kinesis Data Streams: 용량 모드·샤드·소비자 (Skill 1.1.1, 1.1.9, 1.1.10)

KDS는 "샤드"가 용량 단위다. 시험은 샤드 한도, 용량 모드, 소비자 방식을 요구사항에 맞춰 고르게 한다.

- **프로비저닝 모드**: 샤드 수를 직접 정하며 스트림 한도는 샤드 한도(#1)의 합이다. 초기 샤드 수는 `max(쓰기 KB/1000, 읽기 KB/2000)`으로 산정한다(#11) [S1]. 확장은 샤드 분할(SplitShard)·병합(MergeShard) 또는 UpdateShardCount이며, 이 API들은 프로비저닝 전용이다 [S1][S2].
- **온디맨드 모드**: 용량을 자동 관리한다. 새 스트림의 기본 한도는 쓰기 4 MB/s·읽기 8 MB/s(#6) [S2]. 직전 30일 피크의 2배까지 수용하고, 15분 안에 그 이상으로 늘면 스로틀되므로 재시도가 필요하다(#7) [S1]. 모드 전환은 스트림당 24시간에 2회까지다(#8) [S2].
- **On-demand Advantage(신규)**: 계정 단위 설정이며 쓰기·읽기 각 25MB/s 이상 워크로드, 많은 EFO 소비자, 장기 보존에 유리하다. 최소 약정은 24시간이다(#12) [S1]. EFO 소비자는 최대 50개까지 등록할 수 있다(#9) [S2].
- **스트리밍 테이블·S3 전달(신규)**: KDS가 직접 S3/Iceberg로 전달하는 기능으로 온디맨드 모드가 필요하다(#13) [S2]. 원본 형식 그대로 로그 보관·이벤트 재생·배치 처리를 하는 용도다(#110) [S1].
- **쓰기 경로**: PutRecord/PutRecords, KPL, Kinesis Agent로 쓴다 [S1]. PutRecords는 요청당 500 레코드(#3) [S2], 데이터 블롭은 최대 10 MiB(#4) [S1]. 파티션 키로 레코드를 샤드에 분배하고 같은 키의 시퀀스 번호는 시간에 따라 증가한다 [S1]. 파티션 키 없이 균등 분배하는 서비스 관리형 분배는 순서가 필요 없는 무상태 워크로드용이다(#14) [S3]. KPL로 집계한 레코드는 Redshift 스트리밍 수집에서 파싱되지 않고 바이너리로 저장된다 [S27].
- **한도 초과**: 쓰기·읽기 모두 한도를 넘으면 스로틀되며 재시도로 처리하고, 지속적이면 샤드를 늘린다(#15) [S1].
- **보존**: 기본 24시간, 최대 365일이다(#5) [S1]. 기본보다 길게 보존한 데이터도 같은 읽기 API로 읽는다 [S1].

**비교 표 B — KDS 소비자: 공유 처리량 vs 향상된 팬아웃(EFO)**

| 항목 | 공유 처리량(기본) 소비자 | EFO 소비자 |
|---|---|---|
| 전달 방식 | GetRecords(소비자가 당겨 읽음) [S1] | SubscribeToShard — 지속 연결로 샤드에서 소비자에게 밀어 줌(HTTP/2) [S1] |
| 읽기 처리량 | 샤드의 2 MB/s·초당 5 읽기 트랜잭션을 소비자들이 나눠 씀(#1, #2) [S1][S2] | 소비자마다 샤드당 전용 2 MB/s(#10) [S1] |
| 지연 | 소비자가 늘수록 경합 [S1] | 통상 70 ms, GetRecords 대비 약 65% 빠름(#10) [S1] |
| 등록 가능 수 | 해당 없음 | 기본 20, On-demand Advantage 50(#9) [S2] |
| 시험 단서 | 소비자 1개 | 소비자 2개 이상(#17), "읽기 스로틀·지연" [S1] |

### Amazon Data Firehose (Skill 1.1.1, 1.1.3)

- **소스**: Direct PUT/API, KDS, MSK, AWS 서비스(CloudWatch·EventBridge·IoT 등), Kinesis Agent, Fluent Bit, Lambda를 소스로 쓴다 [S8]. KDS를 소스로 지정하면 Firehose의 PutRecord/PutRecordBatch는 비활성화되고 KDS 쪽 API로만 데이터를 넣는다 [S8].
  - KDS 소스: 샤드마다 초당 한 번 GetRecords를 호출하고, 시작 위치는 LATEST이며, 그 읽기는 샤드 한도를 소모한다(#45) [S8].
  - MSK 소스: 읽기 시작점은 Firehose 스트림 생성 시각이며 사용자 지정 오프셋을 지원하지 않는다(#46) [S8].
- **버퍼링(배치 수집 구성의 핵심)**: 버퍼 크기·간격 중 먼저 충족되는 조건에서 전달한다 [S9]. S3 목적지는 크기 1~128 MB, 간격 0~900초이고(#31) 기본값은 5 MB·300초다(#32) [S8][S9]. Parquet 변환·동적 파티셔닝을 켜면 크기가 64~128 MB 범위가 된다(#33) [S8]. 간격을 0으로 두면(제로 버퍼링) 수 초 안에 전달하지만 동적 파티셔닝에는 쓸 수 없다(#34) [S9]. 크기는 압축 전 기준이고, 전달이 밀리면 Firehose가 버퍼 크기를 자동으로 키운다(#35) [S8]. 작은 파일 문제는 이 버퍼 힌트와 파티셔닝으로 조절한다.
- **Lambda 변환**: 변환용 버퍼 힌트는 0.2~3MB(기본 1 MB)(#36)이고 Lambda 동기 호출 요청·응답은 각각 6 MB 한도다(#114) [S10]. 호출 실패는 기본 3회 재시도 후 그 배치를 건너뛰며(재시도 횟수는 0~300으로 설정), 처리 실패 레코드는 S3의 processing_failed 폴더로 간다(#37) [S8]. 변환 전 원본은 S3에 별도로 백업할 수 있다(#49) [S8].
- **동적 파티셔닝·형식 변환**: JSON에서 키를 추출(내장 jq 파서)하거나 Lambda로 만든 키로 S3 prefix를 나눠 전달하고, JSON을 Parquet/ORC로 변환할 수 있다 [S8]. 활성 파티션은 스트림당 기본 500개, 파티션당 1 GB/s다(#40) [S11].
- **전달·재시도**: 목적지 장애 시 Direct PUT 소스의 데이터는 최대 24시간 보관된다(#41) [S11]. S3 전달 실패는 5초 간격으로 재시도하며, Direct PUT은 최대 24시간, KDS 소스는 KDS에 설정한 보존 기간까지다(#42) [S8]. Redshift 목적지는 먼저 S3에 쓴 뒤 COPY를 실행하고, 실패 시 5분 간격으로 최대 120분 재시도한다(#43) [S8]. 전달은 at-least-once라 중복이 생길 수 있다(#44) [S8].
- **한도**: 레코드 1,000 KiB, PutRecordBatch 500개 또는 4 MiB(#38); Direct PUT 쿼터는 리전 그룹별로 다르다(#39) [S11]. 하나의 Firehose 스트림은 S3 버킷 하나에만 전달한다(#48) [S8].

### CDC·기타 스트리밍 소스: DynamoDB Streams, DMS, Glue, Redshift (Skill 1.1.1)

- **DynamoDB Streams**: 24시간 로그이고, 레코드는 한 번만 나타나며 항목별 순서가 보장된다(#58, #59) [S16]. 스트림 뷰 타입은 KEYS_ONLY / NEW_IMAGE / OLD_IMAGE / NEW_AND_OLD_IMAGES이며 설정 후에는 바꿀 수 없다(#61) [S16]. 샤드당 읽기 프로세스는 2개 이하로 둔다(#60) [S16].
- **KDS for DynamoDB**: 테이블 변경을 KDS로 복제한다. 순서·중복 제거를 보장하지 않으므로 ApproximateCreationDateTime으로 클라이언트가 처리해야 한다(#62) [S17]. 대신 보존 최대 1년, EFO 소비자 샤드당 최대 20개, KCL·Managed Flink·Firehose 등 Kinesis 생태계를 쓸 수 있다(#63) [S17].
- **AWS DMS**: 소스 DB의 트랜잭션 로그를 읽어 변경(CDC)을 전달한다. 전체 로드만, 전체 로드 후 CDC, CDC만의 세 가지 방식이 가능하다 [S18]. CDC는 실시간 복제가 아니며 지연 SLA가 없다(#64) [S18]. Kinesis 대상은 소스 레코드 갱신 하나를 데이터 레코드 하나로 보내고, 파티션 키 형태(스키마.테이블 / 속성값 / transaction-id / constant)를 고르며, 중복은 소비자가 처리해야 한다(#65) [S19].
- **AWS Glue 스트리밍 ETL**: KDS·Kafka·MSK를 읽어 정제·변환한 뒤 S3 또는 JDBC에 적재한다. 기본 100초 윈도로 처리하고, 북마크가 아니라 체크포인트로 읽은 위치를 추적하며, 실행 중 시간당 과금된다(#67) [S20].
- **Redshift 스트리밍 수집**: KDS 또는 MSK에서 구체화된 뷰로 직접 들어오며 S3 스테이징이 없다(#78) [S27]. 새로고침 한 번에 수백 MB/s를 수집할 수 있다(#78). 스트림/토픽당 구체화된 뷰 1개를 권장하며 증분 유지가 가능해야 한다(#79). KDS 24시간·MSK 7일이 기본 보존이라 전체 재계산이 불가능하다(#80) [S27].

### 배치 소스 · 배치 구성 옵션 · 데이터 API (Skill 1.1.2, 1.1.3, 1.1.4)

배치 수집 문제는 "무엇을 증분으로 읽는가 · 파일 크기·형식·파티션은 어떻게 둘 것인가 · 어떤 주기로 도는가"이다.

- **S3 → Glue**: 잡 북마크는 S3 객체의 수정 시각으로 처리 대상을 판별하므로, 이미 처리한 파일이라도 수정되면 다시 처리된다(#68) [S21]. 북마크 옵션의 기본값은 비활성(매번 전체 처리)이다(#68) [S21]. 입력 파일이 5만 개를 넘으면 Glue가 파일 그룹화를 자동으로 켠다(#76) [S54].
- **JDBC/DB → Glue**: 북마크는 기본키를 북마크 키로 쓰되 순증가/순감소해야 하고(#69) [S21], 병렬 읽기는 해시 필드·해시 표현식으로 나눈다(#77) [S55]. VPC 안 DB는 Glue가 ENI를 만들어 접근한다(#75) [S25].
- **AWS DMS**: 전체 로드 병렬도는 MaxFullLoadSubTasks로 조절하며 기본 8, 최대 49다(#66) [S53].
- **Amazon Redshift**: 적재는 COPY — 파일을 비슷한 크기(압축 후 1 MB~1 GB)로 나누고 파일 수를 슬라이스 수의 배수로 맞춘다(#81) [S28]. 추출은 UNLOAD — 파일 크기 128~512 MB를 권장하고 Parquet이 텍스트보다 저장 공간이 적다(#82) [S29].
- **Amazon AppFlow**: SaaS ↔ AWS 서비스 전송 서비스다. 트리거는 온디맨드 / 이벤트 / 스케줄 세 종류이고, 이벤트 트리거는 변경 이벤트를 제공하는 SaaS에서만 쓴다(#86) [S31]. 스케줄 플로는 전체 전송 또는 증분 전송을 고르며, 첫 증분 실행은 30일 치를 가져오고 시간 오프셋은 10시간 미만이다(#87) [S31]. AppFlow는 AWS IP 범위에서 동작한다(#88) [S32].
- **AWS Lambda**: 함수 제한 시간이 900초(15분)이므로(#89) [S33] 장시간 배치 읽기에는 부적합하다.
- **Amazon EMR**: S3DistCp로 S3의 대량 데이터를 HDFS로 효율적으로 복사한다(#90) [S34].
- **구성 옵션 체크리스트**: 파일 크기(Firehose 버퍼 #31~#35, COPY #81, UNLOAD #82), 형식·압축(Firehose Parquet/ORC·GZIP, UNLOAD Parquet), 파티션(Firehose 동적 파티셔닝 #40), 증분(Glue 북마크 #68~#70, AppFlow 증분 #87), 병렬도(DMS #66, Glue JDBC #77), 스케줄 간격(아래 「스케줄러」).

**데이터 API 소비 (Skill 1.1.4)** — 공식 가이드는 "Consume data APIs"라고만 쓰고 정의하지 않는다. 공식 문서가 "Data API"라 부르는 대표 사례와 REST 소스 커넥터를 정리하며, 정확한 의도는 확정되지 않았다(gaps G-1.1-02).
- **Amazon Redshift Data API**: 드라이버·연결·네트워크 구성을 관리하지 않고 SDK/HTTP 엔드포인트로 SQL을 실행한다. 호출은 비동기이며 자격은 Secrets Manager 자격 증명 또는 임시 DB 자격 증명을 쓴다(#83) [S30]. 한도: 쿼리 최대 24시간, 결과 500 MB(gzip 후)·결과 보관 24시간(#83, #84), 클러스터당 활성 쿼리 500개·문장 200 KB(#85) [S30].
- **AWS Glue REST API 커넥터**: REST API 기반 데이터 소스를 Glue ETL 소스로 연결한다 [S26].

### Kinesis → Lambda (Skill 1.1.7)

Lambda 이벤트 소스 매핑이 샤드를 읽어 배치로 함수를 동기 호출한다. 샤드당 한 번에 한 배치만 처리하며, 오류가 나면 그 샤드의 다음 레코드 처리를 멈춘다(#28) [S4].

- **소비자 유형**: 표준(공유 처리량) 반복자는 샤드를 기본 초당 한 번 폴링하고 다른 소비자와 읽기 처리량을 나눈다. EFO는 전용 연결로 레코드를 밀어 준다(#19) [S4].
- **처리량 튜닝**: BatchSize는 최대 10,000(#21) [S5]. 배치 윈도(최대 5분)를 두면 작은 배치 호출을 줄이고, 배치가 6 MB 페이로드에 닿으면 즉시 호출한다(#22) [S4]. ParallelizationFactor를 1(기본)~10으로 올리면 한 샤드를 여러 호출이 동시에 처리하며 파티션 키 수준의 순서는 유지된다(#20) [S4]. 샤드를 늘려도 동시 배치가 늘어 오류 영향이 줄어든다 [S4]. 시작 위치는 TRIM_HORIZON / LATEST / AT_TIMESTAMP다(#24) [S5].
- **실패 처리(poison pill)**: 재시도 횟수와 레코드 최대 연령의 기본값은 무제한이라 불량 레코드 하나가 샤드를 최대 1주까지 막을 수 있다(#23, #25) [S5][S6]. 대응은 ① MaximumRetryAttempts·MaximumRecordAgeInSeconds 제한, ② BisectBatchOnFunctionError(실패 배치를 둘로 쪼개 불량 레코드 격리)(#26), ③ 폐기 레코드 SQS/SNS 대상 지정(DestinationConfig), ④ 부분 배치 응답(ReportBatchItemFailures)이다 [S5][S6].
- **중복·멱등성**: 이벤트 소스 매핑은 각 이벤트를 최소 한 번 처리하므로 중복이 생길 수 있고, 함수 코드를 멱등하게 만들라는 것이 공식 권고다(#27) [S4].
- **상태 있는 집계**: 텀블링 윈도를 쓰면 호출 간 상태를 유지할 수 있다(아래 「스테이트풀」) [S7].

### IP 허용 목록 (Skill 1.1.8)

방향이 둘이다. ① 외부 시스템이 "우리 쪽 고정 IP"만 허용하는 경우, ② AWS 서비스가 우리 쪽 소스(VPC 안 DB·Redshift)에 접속하도록 우리가 허용하는 경우.

- **고정 출발 IP(①)**: Lambda를 VPC의 **프라이빗 서브넷**에 연결하고 퍼블릭 서브넷의 NAT 게이트웨이로 나가게 한 뒤, NAT 게이트웨이에 연결한 Elastic IP를 상대방 허용 목록에 넣는다(#101) [S42]. 퍼블릭 서브넷에 연결한 함수는 그것만으로 인터넷에 나가지 못한다 [S56]. Elastic IP는 퍼블릭 NAT 게이트웨이에만 연결되며 기본 2개까지다(#101) [S42].
- **Glue(①·②)**: Glue는 지정한 서브넷에서 프라이빗 IP의 ENI를 만들어 JDBC에 접속하고 퍼블릭 IP는 없다. 그래서 인터넷/다른 AWS 서비스 접근에는 NAT가 필요하고 IGW 직접 경로는 쓸 수 없다. Glue SG에는 자기 참조 인바운드 규칙이 필요하고, 소스 쪽 SG는 Glue SG를 허용한다(#75) [S25].
- **AWS 서비스가 소스에 접속(②)**: VPC 안 Redshift를 Firehose 목적지로 쓰려면 Firehose IP 주소를 VPC에서 차단 해제해야 한다(#50) [S8]. AppFlow는 AWS IP 범위에서 동작하므로 IP 제한이 있는 SaaS에는 해당 범위를 허용하고, AppFlow는 VPC 엔드포인트로 S3에 쓰기 때문에 S3 버킷 정책의 IP 허용으로 AppFlow만 통과시키는 방식은 쓸 수 없다(#88) [S32].
- **공개 IP 범위 파일**: AWS는 IP 범위를 JSON(ip-ranges.json)으로 공개한다. 모든 서비스가 아니라 egress 필터링에 흔히 쓰이는 서비스만 담는다(#100) [S41].
- **함정**: S3 버킷 정책의 `aws:SourceIp`는 VPC 엔드포인트를 통한 요청에는 쓸 수 없고 VPC 전용 키를 써야 한다(#102) [S43].

### 쓰로틀링·속도 제한 극복 (Skill 1.1.9)

- **공통 처방**: 재시도에 지수 백오프를 쓰고 지터로 재시도 시점을 분산한다. 대부분의 AWS SDK는 백오프·지터를 기본 재시도 동작에 포함한다(#106) [S46]. DynamoDB 배치 연산의 미처리 항목은 즉시 재시도하지 말고 지수 백오프로 재시도하라고 권고한다(#103) [S44].
- **DynamoDB**: 프로비저닝 모드는 미사용 용량을 최대 5분(300초)치 버스트로 보관하지만 보장되지 않는다(#104). 카디널리티가 낮은 파티션 키는 소수 파티션에 요청이 몰려 파티션 한도(3,000 RCU / 1,000 WCU)를 넘어 스로틀된다(#104) [S45]. 온디맨드 모드는 이전 피크의 2배까지 즉시 수용한다(#105) [S45].
- **Amazon RDS**: 병목이 DB 연결 수이면 RDS Proxy가 커넥션 풀링·멀티플렉싱으로 많은 클라이언트 연결을 적은 DB 연결로 줄인다(#107) [S47].
- **Kinesis**: 쓰기/읽기 한도 초과는 스로틀이며 재시도 + 샤드 증설(#15), 온디맨드 확장 규칙(#7), 다수 소비자의 읽기 경합은 EFO(#17)로 푼다 [S1]. Lambda 소비 쪽은 #20~#26.
- **Firehose Direct PUT**: 쿼터를 넘으면 Firehose가 스트림의 처리량 한도를 자동으로 올려 스로틀을 해소하려 하므로 실패한 수집 레코드는 계속 재시도한다(쿼터 #39) [S11].
- **Redshift Data API**: 호출 속도 한도를 넘으면 ThrottlingException이 오고 SDK 재시도 전략으로 대응한다 [S30].

### 팬인·팬아웃·재생 가능성 (Skill 1.1.10, 1.1.11)

**팬인·팬아웃(스트리밍 데이터 배포)**
- 팬인: 많은 생산자가 하나의 KDS 스트림에 쓴다(#18) [S1]. Kafka도 다수 생산자가 토픽에 게시하고 다수 소비자가 각자 속도로 읽는다 [S14].
- KDS 팬아웃: 공유 처리량 소비자는 샤드 읽기 한도를 나눠 쓰고, EFO 소비자는 각자 전용 처리량을 받는다(#9, #10, #17) [S1][S2].
- Firehose 팬아웃: 하나의 KDS를 여러 Firehose 스트림의 소스로 쓸 수 있고 읽기 한도를 공유한다(#45). 한 Firehose 스트림은 S3 버킷 하나에만 전달하므로 여러 버킷이면 스트림을 여러 개 만든다(#48) [S8].
- SNS → SQS: 토픽에 한 번 게시한 메시지를 여러 큐로 복제해 구독자들이 병렬·비동기로 처리하고, 큐가 완충한다(#108) [S48].
- EventBridge: 같은 이벤트를 규칙으로 여러 대상에 보낸다(#98) [S39].
- MSK: 컨슈머 그룹 안에서 파티션 하나는 한 번에 한 컨슈머만 읽는다(#56) [S15]. 서로 다른 소비자는 각자 속도로 읽는다 [S14].

**재생 가능성(replayability)**
- KDS: 보존 기간(기본 24시간, 최대 365일, #5) 안에서 같은 순서로 다시 읽을 수 있고 [S1], 소비자는 시작 위치를 TRIM_HORIZON·AT_TIMESTAMP 등으로 지정한다(#24) [S5]. 원본 보관·재생이 목적이면 S3 전달 기능도 있다(#110) [S1].
- Kafka/MSK: 소비자는 오프셋 위치에서 순차로 읽는다 [S15]. 기본 보존은 KDS 24시간·MSK 7일이다(#80) [S27]. Firehose는 MSK의 사용자 지정 오프셋을 읽지 못한다(#46) [S8].
- Firehose 자체는 재생 수단이 아니다: 대상 장애 시 보관은 Direct PUT 기준 24시간(#41)이므로 [S11], 변환 전 원본을 S3에 백업하거나(#49) KDS/MSK를 소스로 둔다 [S8].
- Glue 배치: 잡 북마크를 과거 실행 시점으로 되감거나(rewind) 초기화(reset)해 전체를 재처리할 수 있고, 타깃 파일은 자동으로 정리되지 않으므로 출력 중복을 따로 관리해야 한다(#70) [S21].
- SQS DLQ redrive: StartMessageMoveTask로 DLQ 메시지를 원본 큐(또는 지정 큐)로 돌려보낸다. 큐당 활성 작업은 1개이고 SQS 큐가 DLQ인 경우만 지원한다(#109) [S49].
- EventBridge Archive & Replay: 아카이브는 기본 무기한 보관이며 재생 전 10분 대기를 권고한다(#99) [S40].
- **멱등성**: 소비는 at-least-once이므로 중복에 안전하게 설계한다 — Lambda(#27) [S4], Firehose(#44) [S8], S3 알림(#94) [S38], DMS→Kinesis(#65) [S19].

### 스테이트풀 · 스테이트리스 (Skill 1.1.12)

공식 시험 가이드는 이 Skill을 정의하지 않는다(gaps G-1.1-03). 공식 문서가 stateless/stateful을 쓰는 용례를 모아 보면 "레코드·호출 사이에 기억해야 하는 정보(윈도 집계 상태, 체크포인트·오프셋, 북마크)가 있는가"로 갈린다. (이 요약은 용례에서 귀납한 정리이며 공식 정의가 아니다.)

- **Lambda**: 호출은 기본적으로 무상태이고, 연속 호출 사이에 상태가 필요하면 외부 DB가 필요하다. 텀블링 윈도를 쓰면 호출 간 상태를 유지할 수 있으나 상태는 샤드당 최대 1 MB이고 리샤딩은 지원하지 않는다(#29, #30) [S7].
- **KDS**: 같은 키의 레코드를 같은 처리기로 보내면 카운팅·집계가 쉬워지고(상태가 필요한 처리) [S1], 서비스 관리형 분배는 순서가 필요 없는 무상태 워크로드용이다(#14) [S3].
- **Managed Service for Apache Flink**: 상태 있는(stateful) 스트림 처리에 쓰며 체크포인트(자동)와 스냅샷(수동)으로 애플리케이션 상태를 백업·복구한다(#111, #112) [S50][S51]. MSK Serverless도 Flink와 stateful 스트림 처리로 통합된다(#57) [S14]. Kinesis Data Analytics는 Managed Service for Apache Flink로 개명되었고(#112) [S51], SQL 애플리케이션은 단종 절차에 들어갔다(#113) [S52].
- **Glue**: 배치 잡 북마크는 이전 실행의 상태 정보를 저장해 새 데이터만 처리하게 하고(#71), 북마크를 끄면 항상 전체를 처리(상태 없음)한다(#68) [S21]. 스트리밍 잡은 체크포인트를 쓴다(#67) [S20].

## 시험에서 묻는 방식

> 아래 패턴은 공식 문서의 선택 기준·제약에서 도출한 것이다. 실제 시험 문항을 재현한 것이 아니다.

1. **스트리밍 수집 서비스 선택** — 시나리오 요지: "애플리케이션 로그를 거의 실시간으로 S3 데이터 레이크에 Parquet으로 적재하고 싶다. 별도 소비자 코드와 서버 운영은 최소화." → 정답 방향: Amazon Data Firehose(버퍼링 + 형식 변환 + 필요 시 동적 파티셔닝). 오답 후보와 탈락 이유: KDS + Lambda/KCL(소비자 코드·샤드 운영이 필요), MSK(Kafka 호환 요구가 없음), DynamoDB Streams(DynamoDB 변경 전용). 변형: "여러 분석 애플리케이션이 같은 스트림을 독립적으로 소비 + 순서 + 이전 데이터 재처리" → KDS(EFO·보존 연장), "기존 Kafka 앱·Kafka Connect·오픈소스" → MSK, "DynamoDB 항목 변경 + 항목별 순서·중복 제거" → DynamoDB Streams, "장기 재생·Kinesis 생태계" → KDS for DynamoDB. 근거 [S1][S8][S9][S14][S16][S17]
2. **Kinesis → Lambda 지연·실패 튜닝** — 시나리오 요지: "Lambda 소비자의 IteratorAge가 커진다" 또는 "불량 레코드 하나 때문에 샤드 처리가 멈췄고, 데이터는 잃지 않고 격리하고 싶다." → 정답 방향: 지연은 ParallelizationFactor 상향(파티션 키 수준 순서 유지) 또는 샤드 증설(#20), 정체는 MaximumRetryAttempts·MaximumRecordAgeInSeconds 제한 + BisectBatchOnFunctionError + 폐기 레코드 실패 대상(SQS/SNS) 지정(#23, #25, #26). 오답 후보와 탈락 이유: 기본 설정 유지(재시도·연령이 무제한이라 샤드가 최대 1주 정체), 소비자만 늘리기(공유 처리량이라 읽기 한도를 나눠 쓴다 — 소비자가 둘 이상이면 EFO, #17). 근거 [S4][S5][S6][S1]
3. **수집 트리거 설계: 스케줄 vs 이벤트 vs 다중 대상** — 시나리오 요지: "매일 새벽 수집 작업을 시작하고 실패 시 재시도해야 한다" → EventBridge Scheduler(시간대·재시도 지원, 예약 규칙은 legacy), Glue 잡/크롤러만 주기 실행이면 Glue scheduled 트리거(UTC, 최소 5분, #73). "S3에 파일이 도착하면 처리하되 여러 소비자·FIFO 큐·객체 크기 조건 필터가 필요" → S3 → EventBridge 규칙(직접 S3 알림은 이벤트당 대상 유형 하나, SQS/SNS FIFO 불가, #95, #96, #98). "SaaS 데이터를 주기적으로 증분 동기화" → AppFlow 스케줄 + 증분 전송(#87). "크롤러 비용 절감" → 크롤러 S3 이벤트 모드. 오답 후보와 탈락 이유: S3 알림을 SQS FIFO 큐에 직접 연결(미지원), 예약 규칙 신규 구축(legacy 표기, Scheduler 권장). 근거 [S35][S36][S22][S23][S38][S39][S31][S24]
4. **연결·속도 제약과 재처리** — 시나리오 요지: ① "고객사 방화벽이 고정 IP만 허용하는데 Lambda에서 외부 API를 호출해야 한다" → VPC 프라이빗 서브넷의 Lambda + 퍼블릭 서브넷 NAT 게이트웨이의 Elastic IP(#101). 탈락: 퍼블릭 서브넷에 Lambda 연결(그것만으로 인터넷 불가), ip-ranges.json의 AWS 범위 등록(서비스 공용 범위이지 고객 고정 출구 IP가 아님, #100). ② "DynamoDB 쓰기 스로틀" → SDK의 지수 백오프+지터, 파티션 키 카디널리티·온디맨드 모드 검토(#103~#106); "Lambda → RDS 연결 폭증" → RDS Proxy(#107). ③ "소비자 버그 수정 후 이전 데이터 재처리" → KDS 보존 기간 내 TRIM_HORIZON/AT_TIMESTAMP 재소비(#5, #24), 이벤트는 EventBridge Archive 재생(#99), SQS는 DLQ redrive(#109). 탈락: Firehose는 재생 수단이 아님(보관 24시간, #41). 근거 [S42][S56][S41][S44][S45][S46][S47][S1][S5][S40][S49][S11]

## 흔한 함정·혼동 짝

1. **Kinesis Data Streams vs Amazon Data Firehose** — KDS는 소비자가 읽어 가는 저장소(보존·재처리·다중 소비), Firehose는 목적지로 밀어 주는 전달 서비스(버퍼링, Direct PUT 보관 24시간) → 단서: "코드 없이 S3/Redshift 적재" = Firehose, "여러 앱이 독립 소비·재처리" = KDS (#5, #41) [S1][S8][S11]
2. **KDS vs MSK** — Kafka API·Kafka Connect 호환·기존 Kafka 앱·오픈소스 선호 = MSK, AWS 네이티브·입문 = KDS. 백서 표: 확장은 KDS "초 단위"·MSK "분 단위", 지연은 MSK가 가장 낮음, 보존은 KDS 365일·MSK 구성 가능+티어드 스토리지 → 단서: "Apache Kafka", "기존 Kafka" (#16, #51~#53) [S1][S13]
3. **공유 처리량 소비자 vs EFO** — 공유 = GetRecords(pull), 샤드 2 MB/s·초당 5 읽기 트랜잭션을 나눔. EFO = SubscribeToShard(push), 소비자마다 2 MB/s·통상 70 ms, 등록 기본 20(On-demand Advantage 50) → 단서: "소비자를 추가했더니 읽기 스로틀·지연" (#1, #2, #9, #10) [S1][S2]
4. **프로비저닝 vs 온디맨드 vs On-demand Advantage** — 샤드를 직접 산정(#11) vs 자동(직전 30일 피크의 2배, 15분 안에 초과하면 스로틀, #7) vs ODA(25MB/s 이상·약정 24시간·EFO 다수, #12) → 단서: "예측 불가 트래픽" = 온디맨드, "소비자 수십 개·장기 보존" = ODA (#6~#12) [S1][S2]
5. **DynamoDB Streams vs KDS for DynamoDB** — Streams: 24시간·샤드당 소비자 2개·항목별 순서·한 번만 / KDS for DynamoDB: 순서·중복 제거 없음, 최대 1년·EFO → 단서: "항목 단위 순서" vs "장기 재생·Kinesis 생태계" (#58~#63) [S16][S17]
6. **Firehose 재시도 한도: Direct PUT vs KDS 소스 vs Redshift 목적지** — S3 전달 실패: Direct PUT은 최대 24시간 후 폐기, KDS 소스는 KDS 보존 기간까지(#41, #42). Redshift는 S3 경유 COPY를 5분 간격으로 최대 120분 재시도(#43) → 단서: "전달 실패 후 데이터 손실 시점" [S8][S11]
7. **S3 Event Notifications vs S3 → EventBridge** — 직접 알림은 SNS/SQS(Standard만)/Lambda/EventBridge 중 이벤트당 대상 유형 하나, FIFO 큐 불가, 순서 비보장·간헐적 중복. EventBridge는 고급 필터·다중 대상·아카이브/재생 → 단서: "FIFO 큐", "여러 대상", "객체 크기 필터" (#94~#99) [S38][S39][S40]
8. **EventBridge Scheduler vs 예약 규칙(legacy) vs Glue 일정** — 정밀도 60초(#91) / 1분(#92) / 5분(#73), 예약 규칙·Glue는 UTC 기준, Scheduler는 시간대를 지정한다 → 단서: "legacy", "재시도·유연한 시간 창" [S35][S36][S23]
9. **Glue 배치 잡 북마크 vs 스트리밍 체크포인트** — 배치는 북마크(S3 수정 시각 / JDBC 키), 스트리밍은 체크포인트로 위치를 추적. 북마크 기본값은 비활성(#67~#69) [S20][S21]
10. **북마크 Disable vs Enable vs Pause vs Reset(rewind)** — Disable = 항상 전체 처리, Reset/rewind = 과거 시점부터 재처리하되 타깃 파일은 자동으로 정리되지 않아 출력 중복 위험(#68, #70) → 단서: "재처리했더니 중복" [S21]
11. **BatchSize·배치 윈도 vs ParallelizationFactor vs 샤드 증설 vs EFO** — 각각 해결하는 병목이 다르다: 호출 횟수(BatchSize 최대 10,000·윈도 최대 5분, #21, #22) / 샤드당 동시 호출(1~10, 파티션 키 수준 순서 유지, #20) / 총 병렬도 / 읽기 경합(EFO, #17) [S4][S5][S1]
12. **재시도 제한 vs 배치 이등분 vs 실패 대상** — 기본(무제한 재시도·무제한 연령)이면 불량 레코드가 샤드를 최대 1주 막음. 제한으로 끊고(#23, #25), Bisect로 불량 레코드를 격리하고(#26), 폐기 레코드는 SQS/SNS로 보관 [S5][S6]
13. **프라이빗 서브넷 + NAT(Elastic IP) vs 퍼블릭 서브넷의 Lambda** — 고정 출발 IP는 NAT 게이트웨이의 Elastic IP(퍼블릭 NAT당 기본 2개). 퍼블릭 서브넷에 연결한 함수는 그것만으로 인터넷에 나가지 못함(#101) [S42][S56]
14. **ip-ranges.json vs 우리의 고정 IP / `aws:SourceIp` vs VPC 엔드포인트** — ip-ranges.json은 AWS 서비스의 공용 범위(일부 서비스만)이지 고객 고정 IP가 아님(#100). VPC 엔드포인트 경유 요청엔 `aws:SourceIp`를 못 쓰고 VPC 전용 키를 씀(#102) [S41][S43]
15. **DMS 전체 로드 vs CDC** — CDC는 실시간 복제가 아니고 지연 SLA가 없으며(#64), Kinesis 대상은 중복을 소비자가 처리(#65) → 단서: "거의 실시간 복제 보장" 오답 [S18][S19]
16. **Redshift 스트리밍 수집 vs Firehose → S3 → COPY** — 구체화된 뷰로 직접(스테이징 없음, 스트림/토픽당 MV 1개 권장, 증분 유지 필요, #78~#80) vs 버퍼링 후 S3 경유 COPY(#43). KPL 집계 레코드는 Redshift 스트리밍에서 파싱되지 않음 [S27][S8]
17. **DynamoDB 프로비저닝 스로틀 vs 온디맨드 스로틀** — 프로비저닝은 버스트(미사용 용량 최대 5분치)와 파티션 한도(3,000 RCU / 1,000 WCU)가 원인, 온디맨드는 이전 피크 2배 초과가 원인(#104, #105) [S45]
18. **지수 백오프 vs 지터** — 백오프는 재시도 간격을 늘리고, 지터는 클라이언트들의 재시도 시점을 흩뜨려 군집을 막는다. SDK가 기본 지원(#103, #106) [S44][S46]
19. **RDS Proxy vs DB 인스턴스 확대** — 병목이 연결 수이면 풀링·멀티플렉싱으로 해결(#107) [S47]
20. **Lambda 무상태 vs 텀블링 윈도 상태 vs Flink 상태** — 기본 무상태, 텀블링 윈도는 샤드당 1 MB 상태·리샤딩 미지원, 대규모 상태는 Flink의 체크포인트/스냅샷(#29, #30, #111) [S7][S50]
21. **SNS → SQS vs EventBridge vs KDS EFO (팬아웃)** — 큐로 완충하는 복제(#108) / 규칙 기반 다중 대상(#98) / 스트림 재읽기가 가능한 다중 소비자(#9, #10) [S48][S39][S1]
22. **Redshift Data API vs JDBC/ODBC 연결** — Data API는 연결을 관리하지 않고 비동기로 SQL 실행(#83) → 단서: "드라이버·연결 관리 없이", "Lambda에서 Redshift 호출" [S30]
23. **개명·종료** — Kinesis Data Firehose → Amazon Data Firehose(#47); Kinesis Data Analytics → Managed Service for Apache Flink(#112), SQL 애플리케이션은 단종(#113); EventBridge 예약 규칙은 legacy(#92) → 가이드/기출의 옛 이름에 속지 말 것 [S12][S51][S52][S36]

### 후보 1 — Skill 1.1.1 · associate
- **문제**: 웹 애플리케이션 서버의 JSON 로그를 거의 실시간으로 수집해 Parquet 형식으로 파티션된 S3 데이터 레이크에 적재해야 한다. 소비자 애플리케이션 코드와 서버 운영은 최소화하고 싶다. 어떤 구성이 가장 적합한가?
- **보기**: A. Kinesis Data Streams + KCL 소비자 애플리케이션이 S3에 기록 / B. Amazon Data Firehose(Parquet 형식 변환 + 동적 파티셔닝)로 S3에 직접 전달 / C. Amazon MSK 클러스터 + MSK Connect S3 싱크 / D. DynamoDB Streams + Lambda로 S3에 기록
- **정답**: B
- **해설 초안**: Firehose는 소비자 코드 없이 버퍼링 후 S3로 전달하고, JSON을 Parquet/ORC로 변환하고, 키별 S3 prefix로 동적 파티셔닝할 수 있는 완전 관리형 서비스다 [S8].
- **오답 근거**: A — KDS는 소비자가 읽어 가는 저장소라 KCL 같은 소비자 코드와 샤드 운영이 필요하다 [S1] / C — MSK는 기존 Kafka 앱·오픈소스 선호 같은 Kafka 호환 요구가 있을 때의 선택지다(#16) [S1] / D — DynamoDB Streams는 DynamoDB 테이블 변경을 담는 로그이지 애플리케이션 로그 수집용이 아니다 [S16]
- **근거**: [S8] https://aws.amazon.com/firehose/faqs/ — "dynamically partition your streaming data before delivery to S3"

### 후보 2 — Skill 1.1.7 · associate
- **문제**: Lambda 함수가 Kinesis 데이터 스트림의 레코드를 처리한다. 특정 샤드의 레코드 하나가 항상 함수 오류를 일으켜 그 샤드의 처리가 몇 시간째 멈춰 있다. 나머지 데이터는 계속 처리하면서 문제 레코드는 나중에 분석할 수 있게 보관하려면 어떻게 해야 하는가?
- **보기**: A. 이벤트 소스 매핑의 BatchSize를 최대값으로 늘린다 / B. MaximumRetryAttempts와 MaximumRecordAgeInSeconds를 제한하고 BisectBatchOnFunctionError를 켜며 실패 레코드 대상(SQS 또는 SNS)을 지정한다 / C. ParallelizationFactor를 10으로 올린다 / D. 스트림 보존 기간을 365일로 늘린다
- **정답**: B
- **해설 초안**: 기본값(재시도·레코드 연령 무제한)에서는 불량 레코드가 샤드를 최대 1주까지 막을 수 있다. 재시도·연령을 제한하고, 실패 배치를 둘로 쪼개 불량 레코드를 격리하고, 폐기 레코드를 SQS/SNS 대상으로 보낸다(#23, #25, #26) [S5][S6].
- **오답 근거**: A — 함수가 오류를 반환하면 그 샤드의 다음 레코드 처리가 멈추는 구조이므로 배치만 키워서는 정체 원인이 사라지지 않는다(#28) [S4] / C — ParallelizationFactor는 샤드당 동시 호출 수를 늘려 처리량을 높이는 설정이지 불량 레코드 격리 수단이 아니다(#20) [S4] / D — 기본 재시도는 레코드가 만료될 때까지 계속되므로(#23) 보존 기간을 늘려도 정체는 풀리지 않는다 [S5]
- **근거**: [S6] https://docs.aws.amazon.com/lambda/latest/dg/kinesis-on-failure-destination.html — "a bad record can block processing on the affected shard for up to one week"

### 후보 3 — Skill 1.1.6 · associate
- **문제**: S3 버킷에 새 객체가 생성되면 순서를 유지하는 SQS FIFO 큐로 이벤트를 보내고, 객체 크기 조건으로 필터링해 여러 소비자에게 전달해야 한다. 가장 적합한 방법은?
- **보기**: A. S3 Event Notifications에서 SQS FIFO 큐를 직접 대상으로 지정한다 / B. S3의 EventBridge 알림을 켜고 EventBridge 규칙에서 객체 크기를 필터링해 FIFO 큐를 대상으로 지정한다 / C. S3 Event Notifications에서 SNS FIFO 토픽을 대상으로 지정한다 / D. S3 Event Notifications로 Lambda를 호출해 Lambda가 S3에서 객체 크기를 조회한 뒤 큐로 보낸다

- **해설 초안**: S3 직접 알림은 SQS FIFO·SNS FIFO를 대상으로 지원하지 않고 FIFO 큐는 EventBridge를 거쳐야 한다(#95, #96) [S38]. EventBridge는 객체 크기·키 이름 등 고급 필터와 다중 대상을 지원한다(#98) [S39].
- **오답 근거**: A — SQS FIFO 큐는 S3 알림 대상으로 지원되지 않는다 [S38] / C — SNS는 Standard만 허용되고 FIFO는 불가다 [S38] / D — 동작은 하지만 S3로 되돌아가 메타데이터를 조회하는 Lambda보다 EventBridge의 필터링이 더 효율적이라는 것이 공식 설명이다 [S39]
