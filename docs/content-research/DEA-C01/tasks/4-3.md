## 핵심 개념

### 마스킹·익명화·가명처리와 수단 선택 (Skill 4.3.1)

법규·회사 정책 때문에 PII를 그대로 둘 수 없을 때 값을 가리거나(마스킹), 되돌릴 수 없게 바꾸거나(익명화), 추가 정보가 있어야만 되돌릴 수 있게 바꾼다(가명처리·토큰화). 시험은 용어 정의보다 "언제(질의 시 vs ETL 시) · 무엇으로(어느 서비스) · 되돌릴 수 있는가"를 묻는다.

- **용어 구분**: 익명화는 개인을 식별하지 못하는 형태로 바꾸는 과정이며 비가역이어야 한다 [S1]. 가명처리 데이터는 익명 데이터와 같지 않다. 추가 정보가 있어야만 특정 정보주체에 귀속시킬 수 있고 그 추가 정보는 별도로 보관해야 한다 [S1]. 토큰화는 민감 요소를 토큰(토큰화 시스템을 통해 원본에 매핑되는 참조값)으로 바꾸는 방식이다 [S1].
- **문서가 드는 적용 사례**: 프로덕션 백업을 개발·테스트 환경에 복원할 때는 내장 로직이나 DataBrew 같은 서비스로 PII를 난독화해야 한다 [S1]. 삭제권(잊힐 권리)은 삭제 대신 영구 마스킹(비가역)으로 처리할 수도 있다고 설명한다 [S1].
- **Redshift 동적 데이터 마스킹(DDM)**: 질의 시점에 사용자·역할(RBAC)별로 민감 데이터를 다르게 보여 주며 저장된 데이터는 바꾸지 않는다 [S2]. 정책은 부분/전체 redact 또는 해시(SQL·Python·Lambda UDF)를 수행하고, 해시로 마스킹하면 민감 값에 접근하지 않고도 조인할 수 있다 [S2]. 조건부 컬럼을 쓰면 셀 수준 마스킹도 가능하다 [S2]. 한 컬럼에 서로 다른 정책을 서로 다른 역할에 붙이고 PRIORITY로 충돌을 푼다 [S2][S4].
  - 제약: 시스템 테이블·외부 테이블·데이터셰어링 테이블·교차 DB 관계·임시 테이블·상관 쿼리에는 정책을 붙일 수 없다 [S3]. DDM은 predicate·projection보다 먼저 적용되므로 마스킹된 컬럼 값으로 필터하면 실패하거나 결과가 달라진다 [S3]. RLS가 DDM보다 먼저 적용된다 [S3]. 표현식 비용은 상수 연산 < HMAC 해시 < 외부 Lambda UDF 순이라 단순한 표현식을 권장한다 [S3].
  - 공지: DDM 문서는 UDF를 SQL·Python·Lambda로 작성할 수 있다고 설명하지만 [S2], Redshift는 2026-06-30 이후 Python UDF 지원을 중단한다고 공지한다(단계적 시행) [S22].
- **Glue DataBrew**: 코드 없이 PII를 변환한다 — 대체(substitution), 셔플, 결정적/확률적 암호화, 복호화, null·삭제, 마스킹, 해싱 [S5]. 사용자가 되돌릴 수 없게(비가역) 또는 되돌릴 수 있게(가역) 난독화를 고를 수 있고, 프로파일 잡으로 PII를 탐지한다 [S5].
- **Glue Studio 민감 데이터 탐지(Detect PII 변환)**: PII를 탐지·마스킹·제거한다 [S6]. 스캔 방식은 "각 셀 탐지(전체 행 스캔)"와 "PII 포함 필드 탐지(행 표본 스캔, 저비용)" 2가지이고 [S6], 액션은 탐지 결과 열 추가·redact·부분 redact·SHA-256 해시이다 [S6]. fine-grained 오버라이드로 열 포함/제외와 엔티티별 다른 액션을 줄 수 있지만 같은 열에 redact와 해시를 함께 쓸 수는 없다 [S6].
- **Lake Formation 데이터 필터**: Data Catalog 테이블에 권한을 줄 때 필터를 함께 지정해 쿼리 결과에서 열(column)·행(row)·셀(cell) 단위로 접근을 제한한다 [S7]. 셀 수준은 행 필터와 열 필터의 조합이다 [S7]. HR 부서가 아닌 사용자에게 사회보장번호·생일 같은 PII 열을 보이지 않게 하는 것이 문서의 예이다 [S7].
- **Macie**: S3 데이터를 머신러닝·패턴 매칭으로 스캔해 민감 데이터를 탐지하고 finding을 만든다 [S8]. 방식은 자동 민감 데이터 검색(표본 기반의 광범위한 가시성)과 민감 데이터 검색 작업(대상·깊이를 지정한 정밀 분석) 2가지이고 [S8], 관리형 식별자와 정규식 기반 사용자 지정 식별자를 쓴다 [S8].
- **해시와 솔트**: Redshift 문서의 마스킹 정책 예제는 해시 입력에 문자열(솔트)을 덧붙인다 — `sha2(credit_card + 'testSalt', 256)` [S4]. 솔트의 일반 정의는 AWS 공식 문서에서 확인하지 못했다(G-4.3-04).

| 수단 | 적용 시점 | 방식 | 제약·특이점 | 시험 단서 키워드 |
|---|---|---|---|---|
| Redshift DDM | 질의 시, 저장 데이터 불변 [S2] | 사용자·역할별 마스킹 정책(redact·해시 UDF), 조건부 컬럼(셀), PRIORITY [S2][S4] | 외부 테이블·데이터셰어링 테이블 등에 연결 불가, predicate보다 먼저 적용 [S3] | "원본은 그대로, 역할별로 다른 값", Redshift 컬럼 마스킹 |
| Lake Formation 데이터 필터 | 쿼리 결과(Lake Formation 연동 엔진) [S7] | 열·행·셀 접근 제한 [S7] | Data Catalog 테이블 권한 부여 시 지정 [S7] | "특정 열 숨김", "리전별 행만" |

| Glue DataBrew | 데이터 준비 단계(노코드) [S5] | 대체·셔플·결정적/확률적 암호화·null·마스킹·해시 [S5] | 암호화 방식은 복호화 가능(가역) [S5] | "코드 없이 PII 변환", "프로파일 잡으로 PII 탐지" |

### KMS 키 유형과 접근 제어 (Skill 4.3.2)

AWS 서비스의 저장 시 암호화는 대부분 KMS 키로 동작한다. 시험은 키 유형에 따라 통제·비용·교차 계정·회전이 갈리는 지점을 묻는다.

| 구분 | 소유·관리 | 비용 | 계정 간 사용 | 회전 | 요청 한도 |
|---|---|---|---|---|---|
| AWS 소유 키 | AWS 서비스가 소유·관리하며 여러 계정이 사용 [S9] | 무료 [S9] | (이 노트의 출처에서 직접 확인 못함) | 키를 소유한 서비스가 관리 [S10] | 계정 요청 한도에 미산입 [S14] |
| AWS 관리형 키 | 내 계정에 만들어지지만 AWS 서비스만 사용, 수명주기는 AWS가 관리 [S9] | 월 요금 없음(사용분은 과금될 수 있음) [S9] | 교차 계정 사용 불가 [S38] | 매년 자동, 사용자가 켜고 끌 수 없음 [S10] | 산입 [S14] |
| 고객 관리형 키 | 수명주기 전체를 내가 통제 [S9] | 월 요금 + 사용료 [S9] | 키 정책으로 다른 계정 허용 가능 [S27][S28] | 선택(자동/온디맨드) [S10][S11] | 산입 [S14] |

- **접근 제어 3종**: 모든 KMS 키는 키 정책을 정확히 하나 가지며 키 정책이 접근 제어의 기본 수단이다 [S12]. 키 정책이 허용하지 않으면 IAM 정책의 allow는 효력이 없고, 키 정책은 리전별로 적용된다 [S12]. grant는 키 정책·IAM 정책과 함께 평가되며, AWS 서비스가 사용자 대신 만들고 쓰고 폐기하는 임시 권한 위임에 흔히 쓰인다 [S13]. 하나의 grant는 정확히 하나의 KMS 키에 대한 allow만 가능하다(deny 불가) [S13].

### 키 회전·봉투 암호화·암호화 컨텍스트·요청 한도 (Skill 4.3.2)

- **자동 회전 규칙**: 대칭 암호화 KMS 키에서만 지원한다 — 비대칭 키, HMAC 키, 가져온 키 자료, 사용자 지정 키 스토어 키는 자동 회전 불가 [S10]. 기본 주기는 활성화 시점부터 1년(약 365일)이고 90~2560일 범위에서 지정할 수 있으며 [S10][S11], 온디맨드 회전은 키당 평생 10회까지다 [S11]. 회전해도 이전 키 버전이 유지되므로 데이터를 다시 암호화할 필요가 없다 [S11]. AWS 관리형 키는 항상 매년 회전하고 사용자가 켜고 끌 수 없으며(2022년 5월에 3년→1년으로 변경) [S10], AWS 소유 키의 회전은 소유 서비스가 관리한다 [S10].
- **봉투 암호화·데이터 키**: KMS는 최대 4KB 데이터를 직접 암호화할 수 있지만, 봉투 암호화는 작은 데이터 키만 네트워크로 오가므로 성능 이점이 크다 [S11]. 봉투 암호화는 평문 데이터를 데이터 키로 암호화한 뒤 그 데이터 키를 다른 키로 암호화하는 방식이며 [S16], 암호화된 데이터 키는 암호화된 데이터 옆에 안전하게 저장할 수 있다 [S16].
- **암호화 컨텍스트**: 비밀이 아닌 key-value 쌍으로 추가 인증 데이터(AAD)로 쓰이며 암호문에 암호학적으로 바인딩되어 복호화 때 같은 컨텍스트가 필요하다 [S15]. 암호화되지 않고 CloudTrail 로그에 평문으로 남으므로 민감 정보를 넣지 않는다 [S15].
- **요청 한도(스로틀링)**: 대칭 키 암호화 연산(Encrypt/Decrypt/GenerateDataKey 등)은 계정·리전 단위로 쿼터를 공유하고 기본값은 리전별로 다르며(일부 리전 100,000 rps), 모든 KMS 요청 쿼터는 조정 가능하다(CloudHSM 키 스토어 제외) [S14]. S3 SSE-KMS 업로드·다운로드처럼 AWS 서비스가 대신 보내는 요청도 쿼터를 소비한다 [S14]. AWS 소유 키 사용은 산입되지 않고 교차 계정 요청은 호출한 계정이 스로틀된다 [S14]. 대응: S3 Bucket Keys로 KMS 요청 비용을 최대 99% 줄이고 [S19], GenerateDataKey 한도가 문제면 AWS Encryption SDK의 data key caching으로 호출 빈도를 줄인다 [S14].

### S3 서버 측 암호화 선택 (Skill 4.3.2)

- 모든 신규 객체는 기본으로 SSE-S3로 암호화된다(2023-01-05~) [S17]. SSE-KMS는 키 사용 권한이 분리되고 누가 언제 어떤 객체에 키를 썼는지 감사 추적이 가능하다 [S17]. SSE-KMS 업로드는 kms:GenerateDataKey가, 멀티파트 업로드는 kms:Decrypt까지 필요하다 [S20].
- SSE-KMS 비용·한도 대책이 S3 Bucket Keys다(버킷 수준 키로 S3→KMS 요청 감소) [S19]. DSSE-KMS는 Bucket Keys를 지원하지 않는다 [S19].
- SSE-C는 S3가 암·복호화를 하되 키는 고객이 요청마다 제공한다 [S17][S18]. 2026-04부터 신규 범용 버킷(및 SSE-C 객체가 없는 기존 버킷)에서 기본 비활성이다 [S18]. EMR에서는 SSE-C를 쓸 수 없다 [S25].

| 옵션 | 키 관리 | 핵심 특징 | 제약·최신 변경 | 시험 단서 |
|---|---|---|---|---|
| SSE-S3 | S3가 키 관리·보호 [S17] | 2023-01-05부터 모든 신규 업로드의 기본 암호화 [S17] | KMS 키 권한·감사 추적은 SSE-KMS의 이점으로 설명됨 [S17] | "키 관리 부담 없는 기본 암호화" |
| SSE-KMS | KMS(고객 관리형 또는 aws/s3) [S17] | 별도 키 권한 + 사용 감사 추적 [S17] | 업로드 GenerateDataKey, 멀티파트는 Decrypt도 [S20]; 요청 한도·비용 → Bucket Keys [S19] | "키 사용 감사", "KMS 키 권한 분리" |
| DSSE-KMS | KMS | 서로 다른 AES-256-GCM 구현의 2계층 암호화 [S17] | Bucket Keys 미지원 [S19] | "두 겹 암호화 규제 요구" |
| SSE-C | 고객(요청마다 키 전달) [S17][S18] | S3가 암·복호화 수행 [S17] | 키를 매 요청 제공 → 공유 비현실적, 신규 버킷 기본 비활성 [S18] | "자체 키 유지, 클라이언트 라이브러리는 싫음" |
| 클라이언트 측(S3 Encryption Client) | 고객 | S3는 암호화에 관여하지 않음 [S37] | Bucket Keys와 상호작용하지 않음 [S37] | "전송 전에 암호화" |

### 분석 서비스별 저장 시 암호화 (Skill 4.3.2)

| 서비스 | 기본·선택지 | 제약·특이점 |
|---|---|---|
| Redshift(프로비저닝) | KMS 사용 시 4단계 키 계층(루트 키·CEK·DEK·데이터 암호화 키). 기본은 자동 생성된 AWS 소유 키를 루트 키로 선택하고, 고객 관리형 키를 고르면 생성·회전·비활성·접근 제어·감사 가능 [S21] | 다른 계정의 KMS 키를 쓰려면 사용 권한과 키 ARN 지정이 필요 [S21] |
| Redshift Serverless | KMS 키 암호화를 자동 적용(리소스와 스냅샷) [S22] | namespace의 KMS 키를 바꿀 수 있고 데이터는 그대로 [S22] |
| DynamoDB | 모든 테이블이 항상 암호화되며 켜고 끄는 옵션이 없음. 기본은 AWS 소유 키, AWS 관리형/고객 관리형 키 선택 가능 [S23] | 인덱스를 포함한 모든 테이블 데이터를 암호화 [S23] |
| Kinesis Data Streams | KMS 서버 측 암호화 [S24] | 활성화 이후 들어오는 데이터만 암호화 [S24] |
| EMR | 보안 구성으로 설정: EMRFS-S3(SSE-S3·SSE-KMS·CSE), 로컬 디스크(HDFS 암호화·LUKS·EBS 암호화) [S25] | SSE-C 불가, EBS 암호화는 KMS 키 공급자일 때만 [S25]; S3 CSE는 EMRFS 데이터만 암호화 [S25] |
| Glue | 보안 구성으로 S3 타깃·CloudWatch Logs·잡 북마크 암호화 [S26] | 보안 구성이 잡 파라미터의 SSE-S3 설정을 덮어씀 [S26] |

### 계정 경계 간 암호화 (Skill 4.3.3)

핵심 규칙은 **키 소유 계정의 키 정책(허용 범위) + 사용 계정의 IAM 정책(위임)** 둘 다 필요하다는 것이다.

- **KMS 교차 계정**: 키 정책이 외부 계정에 허용할 권한의 범위를 정하고, 외부 계정의 사용자·역할은 IAM 정책(또는 grant)이 있어야 키를 쓸 수 있다 [S27].
- **키 유형 제약**: 교차 계정으로 공유할 리소스의 키는 고객 관리형 키여야 한다. S3 SSE-KMS는 교차 계정 접근을 주려면 고객 관리형 키를 쓰고 [S28], 교차 계정 복제도 대상 계정의 고객 관리형 키를 지정해야 한다(AWS 관리형 키는 교차 계정 사용 불가) [S38]. Kinesis 스트림이 AWS 관리형 키였다면 리소스 정책으로 공유하려면 고객 관리형 키로 바꾸고, 키 정책과 외부 계정 IAM 정책 양쪽에 권한을 줘야 한다 [S24].
- **S3 세부**: 키 별칭을 쓰면 KMS가 요청자 계정에서 키를 해석하므로 정규화된 키 ARN을 권장한다 [S28]. 키와 다른 계정의 IAM 주체는 키 정책과 IAM 정책 양쪽에 권한이 필요하다 [S20].
- **S3 복제**: 기본적으로 SSE-KMS/DSSE-KMS 객체는 복제되지 않으므로 복제 규칙에서 명시적으로 opt-in하고 대상 리전의 KMS 키를 지정한다 [S38]. 대량의 KMS 암호화 객체가 CRR로 들어오면 KMS 쿼터 스로틀링이 날 수 있다 [S38]. 교차 계정 요청의 쿼터는 호출한 계정에서 소비된다 [S14].
- **Redshift 스냅샷 공유**: 암호화 스냅샷을 공유하려면 스냅샷 생성에 쓴 고객 관리형 키를 복원하는 계정과 공유해야 하며, 공유하지 않으면 복원 시 access-denied 오류가 난다 [S29]. 문서의 "기본 KMS 키" 예외 문구는 G-4.3-02 참조.
- **Lake Formation**: 다른 계정(B)의 KMS 암호화 S3 위치를 계정 A의 사용자 정의 역할로 등록하려면 A의 역할에 B 버킷 권한이, B의 버킷 정책에 A 역할 허용이 있어야 하고, 키가 B에 있으면 키 정책이 A 역할에 접근을 허용해야 한다 [S30]. 서비스 연결 역할로는 다른 계정의 위치를 등록할 수 없다 [S30]. 등록 역할이 키 권한을 가지므로 ETL·Athena로 데이터에 접근하는 주체에게 키 권한을 따로 주지 않아도 된다 [S30]. 고객 관리형·AWS 관리형 키를 지원하고 클라이언트 측 암호화는 지원하지 않는다 [S30].
- **다중 리전 키(MRK)**: 같은 키 ID·키 자료를 가진 키를 여러 리전에 두어 한 리전에서 암호화하고 다른 리전에서 재암호화나 교차 리전 호출 없이 복호화할 수 있다 [S31]. 각 키의 별칭·키 정책·grant는 독립적으로 관리한다 [S31]. 기존 단일 리전 키를 MRK로 바꿀 수 없다 [S31]. 대부분의 AWS 서비스는 MRK를 단일 리전 키처럼 취급한다(S3 CRR은 대상 리전 키로 데이터 키를 복호화 후 재암호화) [S31]. AWS 관리형 키는 항상 단일 리전 키다 [S31].

### 전송 중 암호화 (Skill 4.3.4)

전송 중 암호화는 TLS/SSL로 네트워크 구간을 보호한다. 서비스마다 "강제하는 방법"이 달라 시험은 그 설정 이름을 묻는다.

| 대상 | 강제·기본 동작 | 설정 키워드 |
|---|---|---|
| S3 | 버킷 정책으로 HTTP 요청을 명시적 Deny [S32] | aws:SecureTransport = false 조건 [S32] |
| Redshift | 2025-01-10 이후 신규·복원 클러스터와 서버리스 워크그룹은 SSL 기본 강제, 기존·사용자 지정 파라미터 그룹은 지정 값 유지 [S33] | require_ssl 파라미터 [S33] |
| MSK | 브로커 간 TLS(1.2) 기본, 클라이언트-브로커는 TLS만(기본)/TLS+평문/평문 중 선택 [S34] | ClientBroker: TLS, TLS_PLAINTEXT, PLAINTEXT [S34] |
| RDS PostgreSQL | rds.force_ssl=1이면 SSL 강제, v15 이상 기본 1·v14 이하 기본 0 [S35] | rds.force_ssl [S35] |
| Kinesis Data Streams | SSL 엔드포인트(HTTPS)로 put/get [S36] | HTTPS 엔드포인트 [S36] |
| EMR | EMRFS↔S3 구간은 S3 암호화 설정과 무관하게 TLS [S25]; 클러스터 노드 간 암호화는 보안 구성의 in-transit 설정 [S25] | security configuration [S25] |

- MSK는 전송 중 암호화를 켜면 CPU 오버헤드와 수 밀리초 지연이 추가될 수 있다고 안내한다 [S34].
- 리전 간 이동: AWS 글로벌 네트워크로 리전 사이를 오가는 데이터는 AWS가 물리 계층에서 자동으로 암호화한다 [S40].

### 전송 전(클라이언트 측) 암호화 (Skill 4.3.4)

- **해석**: 가이드의 "before transit"과 같은 표현은 공식 문서에서 찾지 못했다(G-4.3-09). 가장 가까운 공식 설명은 AWS 보안 블로그의 "Pre-encryption of data to be sent to AWS" 절로, 기업 네트워크의 애플리케이션에서 데이터를 AWS로 보내기 전에 암호화하는 것(클라이언트 측 암호화)을 말한다 [S39]. 문서들도 "클라이언트 측 암호화"를 데이터를 보내기 전에 로컬에서 암호화하는 것으로 설명한다 — S3(객체를 보내기 전에 S3 Encryption Client로 암호화) [S37], DynamoDB(테이블 데이터를 데이터베이스로 보내기 전에 암호화) [S23], Kinesis(스트림에 넣기 전에 클라이언트에서 암호화) [S36], EMRFS CSE(업로드 전에 암호화) [S25].
- **서비스는 암호화에 관여하지 않는다**: S3 Encryption Client로 암호화한 객체는 AWS를 포함한 제3자에게 노출되지 않으며 S3는 암·복호화에 관여하지 않는다 [S37]. S3는 이런 객체를 암호화된 객체로 인식하지 못하고 일반 객체로만 본다 [S37].
- **도구**: AWS Encryption SDK는 클라이언트 측 봉투 암호화 라이브러리를 제공하고 KMS와 연동한다 [S16]. Amazon S3 Encryption Client는 PutObject/GetObject 때 자동으로 암·복호화한다 [S37]. DynamoDB는 AWS Database Encryption SDK로 클라이언트 측 암호화를 한다 [S23].
- **제약**: S3 Encryption Client는 KMS 키를 래핑 키로 지정해도 Bucket Keys를 쓰지 않는다 [S37]. Lake Formation에 등록한 위치는 클라이언트 측 암호화를 지원하지 않는다 [S30]. EMR의 S3 CSE는 EMRFS로 주고받는 데이터만 암호화하며 클러스터 볼륨 전체를 암호화하지 않는다 [S25].

## 시험에서 묻는 방식

1. **PII 마스킹 수단 선택** — "저장 데이터는 바꾸지 않고 역할마다 다른 값(해시·부분 마스킹)을 보여 준다 / Redshift 컬럼 / 분석가는 마스킹, 감사자는 원문"을 요구하면 → **Redshift 동적 데이터 마스킹 정책을 역할에 연결하고 PRIORITY로 충돌 해소**가 정답 방향. 오답 후보: Lake Formation 열 필터(열·행·셀 접근을 제한할 뿐 값을 가려 보여 주는 용도가 아님), Glue Studio Detect PII·DataBrew(ETL/준비 단계에서 변환하는 방식이라 "질의 시점·원본 유지" 요구와 어긋남), Macie(S3 민감 데이터 탐지 서비스). 근거 [S2][S4][S7][S6][S5][S8]
2. **S3 암호화 방식·비용 선택** — "KMS 키 사용 감사와 키 권한 분리 + 대량 객체 접근으로 KMS 요청 비용/스로틀링 증가"를 요구하면 → **SSE-KMS + S3 Bucket Keys**(KMS 요청 비용 최대 99% 절감)가 정답 방향. 오답 후보: SSE-S3(KMS 권한·감사 이점 없음), SSE-C(요청마다 키를 제공해야 해 공유가 비현실적이고 2026-04부터 신규 버킷 기본 비활성), DSSE-KMS(Bucket Keys 미지원, 비용 증가). 멀티파트 업로드 AccessDenied는 kms:Decrypt 누락이 단서. 근거 [S17][S18][S19][S20]
3. **교차 계정 암호화** — "계정 B가 계정 A의 SSE-KMS 객체/암호화 스냅샷/Kinesis 스트림을 읽어야 한다"를 요구하면 → **고객 관리형 키 + 키 정책에서 외부 계정 허용 + 상대 계정 IAM 정책**이 정답 방향. 오답 후보: AWS 관리형 키(교차 계정 사용 불가), IAM 정책만(키 정책 허용 없이는 효력 없음), 키 정책만(상대 계정 IAM 위임 없음), 키 별칭 사용(요청자 계정에서 해석). Redshift 스냅샷은 복원 계정과 고객 관리형 키 공유가 필요. 근거 [S27][S28][S38][S29][S24]
4. **전송 중 / 전송 전 암호화** — "HTTP 접근을 거부"하면 → S3 버킷 정책 `aws:SecureTransport`=false Deny, "Redshift 클라이언트 SSL 강제" → `require_ssl`, "MSK 클라이언트-브로커 평문 금지" → ClientBroker=TLS. "AWS도 평문을 못 보게 / 보내기 전에 애플리케이션에서 암호화"를 요구하면 → **클라이언트 측 암호화(AWS Encryption SDK, S3 Encryption Client)**가 정답 방향이며, 서버 측 암호화(SSE)나 TLS만으로는 충족되지 않는다. 근거 [S32][S33][S34][S36][S37][S16][S39]

## 흔한 함정·혼동 짝

1. **Redshift DDM vs Lake Formation 데이터 필터** — DDM은 질의 시 값을 가리거나 해시해 역할별로 다르게 보여 주고, Lake Formation 필터는 테이블 권한에 열·행·셀 접근 제한을 지정한다 → 단서: "마스킹된 값을 보여 준다 / 해시" vs "열을 숨긴다 / 지역별 행만" [S2][S7]
2. **질의 시점 마스킹(DDM) vs ETL 단계 마스킹(Glue Detect PII·DataBrew)** — DDM은 저장 데이터를 바꾸지 않고, Glue·DataBrew는 변환 단계에서 redact·해시·암호화한다 → 단서: "원본 유지·역할별" vs "파이프라인에서 PII를 제거/해시한 뒤 적재" [S2][S6][S5]
3. **Macie vs 마스킹 도구** — Macie는 S3의 민감 데이터를 탐지해 finding을 만드는 서비스로 문서화되어 있고, 가리기는 DDM·Glue·DataBrew의 기능이다 → 단서: "S3에서 PII가 어디 있는지 찾기" vs "PII를 가려서 제공" [S8][S2][S6]
4. **익명화 vs 가명처리(토큰화)** — 익명화는 비가역, 가명처리·토큰화는 추가 정보/토큰화 시스템으로 원본에 연결될 수 있다 → 단서: "되돌릴 수 없게" vs "필요 시 복원·재식별 가능" [S1]
5. **해시 vs 암호화(DataBrew)** — 해시는 값을 복원하지 못하고(조인 키로는 사용 가능), 결정적/확률적 암호화는 복호화할 수 있다. 결정적 암호화는 같은 값이 같은 암호문이 된다 → 단서: "되돌릴 수 있어야 함" vs "조인용 의사 식별자" [S2][S5]
6. **AWS 소유 vs AWS 관리형 vs 고객 관리형 키** — 소유 키는 AWS가 보유·여러 계정 공유, 관리형 키는 내 계정 안에 있지만 수명주기·권한을 바꿀 수 없고 교차 계정 불가, 고객 관리형만 정책·회전·교차 계정을 통제한다 → 단서: "키 정책 직접 통제", "다른 계정과 공유", "aws/s3" [S9][S38][S10]
7. **키 정책 vs IAM 정책 vs grant** — 키 정책은 키마다 필수이며 이것이 허용하지 않으면 IAM allow는 무효, grant는 서비스가 쓰는 임시 allow 위임(deny 불가) → 단서: "IAM 권한을 줬는데 AccessDenied" [S12][S13]
8. **자동 회전 vs 수동 교체/가져온 키** — 자동 회전은 대칭 암호화 키에만, 회전해도 이전 버전이 남아 재암호화 불필요, AWS 관리형은 매년 고정(사용자가 켜고 끌 수 없음) → 단서: "회전 후 기존 데이터 복호화", "비대칭/HMAC 키 회전" [S10][S11]
9. **KMS 직접 Encrypt vs 봉투 암호화(데이터 키)** — 직접 암호화는 최대 4KB, 큰 데이터는 GenerateDataKey로 데이터 키를 받아 로컬 암호화 → 단서: "대용량 객체", "네트워크 지연", "GenerateDataKey 스로틀" [S11][S16][S14]
10. **암호화 컨텍스트 vs 비밀 값** — 컨텍스트는 비밀이 아니며 CloudTrail에 평문 기록되고 복호화 때 동일해야 한다 → 단서: "컨텍스트에 비밀번호 넣기(오답)" [S15]
11. **SSE-S3 vs SSE-KMS vs SSE-C vs DSSE-KMS** — 키 관리 주체·감사·비용이 갈린다: S3 관리(기본) / KMS 관리 + 감사 / 고객이 요청마다 제공 / KMS 2계층 → 단서: "키 사용 감사", "자체 키 제공", "두 겹" [S17][S18]
12. **S3 Bucket Keys가 되는 경우와 안 되는 경우** — Bucket Keys는 SSE-KMS의 KMS 요청을 줄이지만 DSSE-KMS는 미지원이고 클라이언트 측 암호화(S3 Encryption Client)도 Bucket Keys를 쓰지 않는다 → 단서: "KMS 비용 절감" 보기에 DSSE/CSE가 섞임 [S19][S37]
13. **서버 측 암호화(SSE) vs 클라이언트 측 암호화** — SSE는 서비스가 받은 뒤 암호화하고, 클라이언트 측은 보내기 전에 로컬에서 암호화해 서비스가 암호화에 관여하지 않는다. Lake Formation 등록 위치는 클라이언트 측 암호화 미지원 → 단서: "AWS도 평문 접근 불가", "전송 전" [S37][S24][S30]
14. **전송 중(TLS) vs 저장 시(SSE) 암호화** — TLS 강제는 `aws:SecureTransport`/`require_ssl`/ClientBroker 같은 전송 설정이고, SSE-KMS·Bucket Keys는 저장 시 설정이다 → 단서: "HTTP 요청 거부" [S32][S33][S34][S17]
15. **Glue 보안 구성 vs Data Catalog 암호화** — 보안 구성은 크롤러·잡·개발 엔드포인트가 쓰는 S3 타깃·CloudWatch Logs·잡 북마크를 암호화하는 설정이고, 보안 구성이 잡 파라미터의 SSE-S3 설정을 덮어쓴다 → 단서: "잡 북마크 암호화", "CloudWatch Logs 암호화" [S26]
16. **Kinesis SSE 활성화 시점** — SSE를 켜기 전에 이미 들어온 데이터는 암호화되지 않는다 → 단서: "기존 레코드도 암호화되나?" [S24]
17. **EMR에서 SSE-C / S3 CSE의 범위** — EMR은 SSE-C를 쓸 수 없고, S3 CSE는 EMRFS 데이터만 보호하며 로컬 볼륨은 별도 로컬 디스크 암호화가 필요 → 단서: "클러스터 전체 암호화" [S25]
18. **키 별칭 vs 정규화 ARN(교차 계정 S3)** — 별칭은 요청자 계정에서 해석되어 요청자 소유 키로 암호화될 수 있으므로 정규화된 ARN을 쓴다 → 단서: "교차 계정인데 객체를 못 읽음" [S28]
19. **다중 리전 키 vs 키 복제 오해** — MRK는 같은 키 ID·키 자료지만 키 정책·grant는 독립이며, 기존 단일 리전 키는 변환 불가, 대부분 AWS 서비스는 MRK를 단일 리전 키처럼 취급한다 → 단서: "리전 간 재암호화 없이 복호화" [S31]

- **근거**: [S36] https://aws.amazon.com/kinesis/data-streams/faqs/ — "encrypt data on the client side before putting the data into Kinesis"
