## 핵심 개념

### 오케스트레이션 서비스 선택 지도 (Skill 1.3.1)

ETL 파이프라인은 "수집 → 변환 → 적재 → 검증 → 알림"처럼 단계 사이에 의존 관계·재시도·분기·병렬 처리가 생긴다. 이 제어 흐름을 코드 안에 직접 짜지 않고 오케스트레이션 서비스에 맡기는 것이 Task 1.3의 전제이며, 시험은 요구사항(운영 부담·기존 자산·실행 시간·호출 대상)을 주고 서비스를 고르게 한다. 이 소제목이 서비스 간 비교의 정본이고, 운영·트러블슈팅 관점은 3-1.md가 다룬다.

- 공식 가이드는 Step Functions와 MWAA를 워크플로 오케스트레이터의 대표 선택지로 든다 [S16].
- Step Functions는 완전 관리형 서버리스라 미리 프로비저닝할 인프라와 유지 보수 창 예약이 필요 없다. MWAA는 미리 배포해야 하고 클러스터의 크기와 노드 수를 직접 고른다 [S16].
- 비용 구조도 다르다. Step Functions는 실행 중인 워크플로가 없으면 비용이 없고, MWAA는 DAG가 돌지 않아도 비용이 발생한다 [S16].
- 공식 FAQ의 선택 기준: 오픈소스·이식성이 우선이면 MWAA, 비용·성능이 우선이면 Step Functions [S15].
- Glue 워크플로는 여러 크롤러·잡·트리거가 얽힌 복잡한 ETL 활동을 만들고 시각화하는 Glue 내부 기능이다 [S21].
- EventBridge 이벤트로 Step Functions 실행을 시작할 수 있고 [S1], Glue 워크플로도 EventBridge 이벤트로 시작할 수 있다 [S21].
- Lambda는 짧게 끝나는 계산용이며 한 번 호출은 최대 15분이다 [S22]. 한 함수가 다른 함수를 순차 호출하며 응답 검증·오류 처리까지 떠안는 구조는 안티패턴이다 [S23].

|---|---|---|---|

### Step Functions: Standard vs Express (Skill 1.3.1, 1.3.2)

상태 머신은 만들 때 Standard(기본) 또는 Express를 고르며, 생성 후 유형을 바꿀 수 없다 [S1]. 시험의 핵심은 "실행 시간·실행 의미론(exactly-once vs at-least-once)·과금 단위·지원 통합 패턴"이다.

- Standard: 장기 실행·내구성·감사에 적합하다. 작업이 두 번 이상 실행되지 않는 exactly-once 모델이라 EMR 클러스터 시작·결제 같은 비멱등 작업에 맞다 [S1].
- Express: 고빈도 이벤트 처리(IoT 수집, 스트리밍 변환, 모바일 백엔드)에 적합하다. at-least-once 모델이라 실행이 두 번 이상 일어날 수 있어 DynamoDB PUT 변환 같은 멱등 작업에 맞다 [S1]. 상태 머신 로직 자체가 멱등이어야 한다 [S9].
- Express는 동기·비동기로 시작한다. 비동기는 시작 확인만 돌려주고 결과는 CloudWatch Logs로 확인한다. 동기는 완료를 기다려 결과를 돌려준다(API Gateway·Lambda·StartSyncExecution에서 호출) [S1].
- Standard는 실행 시간 1년, 실행당 이력 25,000 이벤트, 종료 후 90일 조회 한도가 있다 [S6]. Express는 최대 5분이고 이력을 보려면 CloudWatch Logs 로깅이 필요하다 [S1][S6].

| 항목 | Standard | Express |
|---|---|---|
| 최대 실행 시간 | 1년 [S6] | 5분 [S1][S6] |
| 실행 시작률(공식 비교표 수치) | 초당 2,000 [S2] | 초당 100,000 [S2] |
| 실행 의미론 | exactly-once [S1] | 비동기 at-least-once, 동기 at-most-once [S1] |
| 과금 | 상태 전이 수(재시도 포함) [S2][S5] | 실행 수·지속 시간·메모리 [S1][S2] |
| 이력 | Step Functions가 90일 보관, 실행당 25,000 이벤트 [S6] | 보관하지 않음. CloudWatch Logs 로깅 필요 [S1][S6] |
| 통합 패턴 | Request Response + .sync + .waitForTaskToken [S3] | Request Response만 [S1][S3] |
| Distributed Map | 지원 [S1] | 미지원 [S1] |
| Redrive | 지원(최근 14일 내 실패 실행) [S7] | 미지원 [S6] |

### Step Functions 서비스 통합 패턴과 Map 상태 (Skill 1.3.1, 1.3.3)

Task 상태의 Resource URI를 어떻게 쓰느냐로 통합 패턴이 정해진다 [S3].

- Request Response(기본): 서비스를 호출해 HTTP 응답을 받으면 바로 다음 상태로 간다. 작업 완료를 기다리지 않는다 [S3].
- Run a Job(.sync): 리소스 ARN 끝에 .sync를 붙이면 Step Functions가 작업이 끝날 때까지 기다린다 [S3]. Glue·Athena·EMR·EMR Serverless·Batch·ECS 등이 Standard에서 지원한다 [S3].
- Wait for Callback(.waitForTaskToken): 태스크 토큰이 SendTaskSuccess/SendTaskFailure로 돌아올 때까지 워크플로를 멈춘다. 사람 승인·타사·레거시 연동에 쓴다 [S3]. 토큰은 같은 AWS 계정의 주체가 보내야 한다 [S3]. Lambda·SQS·SNS·EventBridge 등이 Standard에서 지원한다 [S3][S23].
- Express는 같은 서비스 통합을 쓸 수 있지만 .sync·.waitForTaskToken 패턴은 지원하지 않는다 [S1][S3].
- 비동기 작업을 폴링 루프로 관리하면 상태 전이가 늘어 Standard 비용이 오른다. 콜백이나 .sync를 쓰면 전이 수와 비용이 줄어든다 [S9].

Map 상태는 데이터 집합의 각 항목에 같은 처리를 반복하며 처리 모드가 둘이다 [S4].

| 항목 | Inline(기본) | Distributed |
|---|---|---|
| 동시성 | 최대 40 [S4] | 최대 10,000 병렬 자식 워크플로 실행 [S4] |
| 입력 | JSON 배열만 [S4] | JSON 배열 또는 S3 데이터 소스(CSV 등) [S4] |
| 이력 | 부모 실행 이력에 추가 [S4] | 자식마다 별도 이력 [S4] |
| 선택 기준 | 이력이 25,000 항목 이하이거나 동시성 40이면 충분할 때 [S4] | 데이터 256 KiB 초과, 이력 25,000 항목 초과, 동시성 40 초과 중 하나라도 해당할 때 [S4] |
| 워크플로 유형 | Standard·Express | Standard 상태 머신에서만 사용 [S1] |

### 오류 처리: Retry·Catch·Redrive (Skill 1.3.2, 1.3.3)

- 상태가 오류를 보고하면 Step Functions는 기본적으로 실행 전체를 실패시킨다. 오류를 잡고(Catch) 실패한 상태를 재시도(Retry)하도록 구성해 이를 완화한다 [S5].
- Retry 필드(Task·Parallel·Map 상태): ErrorEquals(필수), IntervalSeconds(첫 재시도까지의 초), MaxAttempts(재시도 횟수), BackoffRate(간격 증가 배수), MaxDelaySeconds(간격 상한), JitterStrategy(FULL이면 대기 시간을 무작위화) [S5]. 간격 3초·배수 2이면 첫 재시도는 3초 뒤, 두 번째는 그 6초 뒤다 [S5].
- 지터는 동시 재시도를 무작위 지연으로 분산시킨다 [S5]. 재시도는 상태 전이로 취급되어 과금된다 [S5].
- States.ALL은 알려진 모든 오류 이름과 일치하는 와일드카드이며 ErrorEquals에서 단독으로 쓰고 마지막 Retrier에 둔다 [S5].
- Catch는 재시도로 해결되지 않은 오류를 Next에 지정한 폴백 상태로 보낸다 [S5].
- Lambda 서비스 예외(Lambda.ServiceException 등)는 프로덕션 코드에서 처리해야 하는 일시 오류로 안내된다 [S5].
- Redrive: Standard 실행 중 최근 14일 안에 실패·중단·타임아웃된 실행을, 실패한 단계부터 같은 입력으로 재개한다. 성공한 단계의 결과와 이력은 보존되고 다시 실행되지 않는다 [S7]. 같은 상태 머신 정의·실행 ARN을 쓰므로 정의를 고쳤다면 새 실행을 시작해야 하고 [S7], Express는 지원하지 않는다 [S6].
- Standard 실행의 이력이 25,000 이벤트에 닿으면 실행이 실패한다 [S6]. 이력이 그만큼 커질 작업은 Distributed Map(자식마다 별도 이력)이 선택 기준에 들어간다 [S4].

### Amazon MWAA와 MWAA Serverless (Skill 1.3.1)

- MWAA는 Apache Airflow 관리형이다. Airflow에서는 워크플로를 Python으로 DAG로 만든다 [S16]. DAG와 지원 파일을 환경에 연결된 S3 버킷에 복사하면 MWAA가 워커·스케줄러·웹서버에 동기화한다 [S13].
- S3 버킷은 퍼블릭 액세스 차단과 버전 관리가 필요하다. plugins.zip·requirements.txt는 갱신할 때마다 콘솔에서 사용할 버전을 지정한다 [S13].
- 구성요소: 스케줄러(Fargate, 최소 2·최대 5), 워커(Fargate 태스크, 최소~최대 범위에서 오토스케일), 웹서버(Airflow UI), 메타데이터 DB(AWS가 관리하는 단일 테넌트 Aurora PostgreSQL) [S12].
- 워커 오토스케일: 큐에 쌓인 작업과 실행 중 작업이 기존 워커 용량을 넘으면 늘리고, 합계가 0인 상태가 2분을 넘으면 최소 워커 수로 줄인다 [S12]. 네트워크는 서로 다른 AZ의 서브넷 두 개에서 동작해야 한다 [S18].
- 환경 클래스는 mw1.micro부터 mw1.2xlarge까지 있고 클래스가 클수록 기본 동시 작업 수가 늘어난다(micro 3 → 2xlarge 80). mw1.micro는 오토스케일링을 지원하지 않는다 [S11].
- 버전: 환경을 만들 때 지정하며, 지정하지 않으면 최신 지원 버전이 쓰인다 [S10]. 마이너 버전 업그레이드만 지원하고 [S10], 최소 3개 마이너 버전을 동시에 지원하며 종료일은 180일 이상 전에 공지한다 [S10]. v2.4.3·v2.5.1·v2.6.3은 2025-12-30에 지원이 종료됐다 [S10]. 지원 버전 표는 자주 바뀌므로 공식 표를 확인한다.
- 비용 구조: 환경(클래스)별 시간당 요금, 오토스케일로 늘어난 추가 워커, 추가 스케줄러·웹서버, 메타데이터 DB 사용량(GB-월) [S14].
- MWAA Serverless는 프로비저닝 없이 쓰는 MWAA 배포 옵션이다 [S17]. Airflow v3·Python 3.12를 쓰고, 워크플로는 YAML(DAG factory 형식)로 정의하며, 워크플로마다 자체 실행 역할과 워커를 가진다. Airflow UI에는 직접 접근할 수 없고 로그로 모니터링한다 [S17]. 요금은 AWS Managed Tasks 사용량을 1초 단위, 최소 1분으로 청구한다 [S14].
- 다음이 필요하면 프로비저닝된 MWAA를 고려하라는 것이 공식 안내다: 사용자 정의 Python 연산자·복잡한 DAG 로직, Airflow 웹 UI 직접 접근, 지속적으로 대량인 워크로드, Serverless 모델이 지원하지 않는 플러그인·설정 [S17].

### EventBridge: 이벤트 버스·Scheduler·Pipes (Skill 1.3.1, 1.3.2)

EventBridge는 오케스트레이션에서 "무엇을 언제 시작시킬지"를 맡는다. 이벤트 도착이나 시간 조건으로 Step Functions 실행·Glue 워크플로를 시작시키는 용도가 많다 [S1][S21].

- 이벤트 버스는 이벤트 서비스 사이의 다대다 라우팅에, Pipes는 이벤트 게시자와 소비자 사이의 점대점 통합(고급 변환·보강 지원)에 쓴다 [S19].
- Scheduler는 예약 규칙(scheduled rules)의 기능을 바탕으로 시간대·대규모·사용자 지정 페이로드·추가 시간 표현식·모니터링 대시보드를 지원한다 [S19]. 일정을 대규모로 예약할 때는 Scheduler가 더 적합하다 [S20].
- Scheduler는 at-least-once로 전달한다. 기본값은 최대 24시간·185회까지 재시도하고, DLQ를 설정하지 않으면 실패한 이벤트는 폐기된다 [S20].
- flexible time window를 쓰면 예약 호출을 시간 창에 분산시켜 하위 서비스 부하를 줄인다 [S20].

### AWS Glue 워크플로 (Skill 1.3.1, 1.3.2)

Glue 워크플로는 여러 크롤러·잡·트리거로 이루어진 ETL 활동을 만들고 시각화하며, 구성요소별 진행 상황과 상태를 기록한다 [S21].

- 워크플로 안의 트리거는 잡과 크롤러를 모두 시작할 수 있고, 잡·크롤러가 끝날 때 발화해 의존 체인을 만든다 [S21]. 정적 뷰(설계)와 동적 뷰(최신 실행 정보)가 있다 [S21].
- 워크플로 실행 속성(run properties)은 이름/값 쌍으로, 워크플로 안 모든 잡이 읽고 수정해 뒤 단계 잡에 상태를 전달할 수 있다 [S21].
- 동시 실행 상한은 워크플로를 만들 때 지정한다. 상한을 넘어 시작되지 못한 런은 Glue가 재시도하지 않으므로 예상 이벤트량에 맞춰 조정한다 [S21].
- 실패로 끝난 워크플로 런을 시작시킨 이벤트(묶음)는 다시 고려되지 않고 다음 이벤트가 도착해야 새 런이 시작된다 [S21].

| 시작 트리거 | 동작 | 시험 단서 |
|---|---|---|
| Schedule | 일/주/월 또는 cron 기반 사용자 정의 일정 [S21] | 정기 배치 |
| On demand | 콘솔·API·CLI에서 수동 시작 [S21] | 수동 실행·테스트 |
| EventBridge event | 이벤트 1건 또는 묶음(배치 크기·배치 창)이 도착하면 시작. 예: S3 PutObject. 배치 조건을 안 주면 배치 크기 기본 1 [S21] | 파일 도착 시 자동 시작 |

### Lambda 단독 오케스트레이션의 한계 (Skill 1.3.1)

- Lambda는 상태를 유지하지 않는 짧은 계산용으로 설계됐고 한 번 호출에 최대 15분이다 [S22].
- 안티패턴: 단일 Lambda 함수가 주문 처리 전체를 관리하며 다른 함수를 순차 호출하고, 응답을 파싱·검증하고, 오류 처리·복구 로직과 데이터 흐름까지 구현하는 구조 [S23]. 권장 구조는 작업별 함수를 따로 두고 Step Functions가 순서·데이터 전달·단계별 오류 처리를 맡는 것이다 [S23].
- Lambda에도 비동기 호출·이벤트 소스 매핑의 재시도가 있지만, 복잡한 워크플로의 오류 처리(오류 종류별 재시도 정책, 소진 시 Catch)는 Step Functions가 더 정교하다 [S23]. 사람 승인은 Choice 상태와 waitForTaskToken으로 처리한다 [S23].
- 코드로 워크플로를 쓰고 싶다면 Lambda durable functions가 있다. 체크포인트와 재생으로 최대 1년 실행되고 대기 중에는 컴퓨팅 요금이 없다. 애플리케이션 개발에는 durable functions, 여러 AWS 서비스를 시각적으로 조정하는 데는 Step Functions가 맞다 [S24].

### 복원력·내결함성 설계 원칙 (Skill 1.3.2)

Well-Architected Data Analytics Lens의 "6 – 분석 워크로드의 복원력 설계"가 시험 문구와 가장 가깝다. 데이터 흐름 의존성 도식화(BP 6.1) → 실패 모니터링(6.2) → 이해관계자 알림(6.3) → 복구 자동화(6.4) → DR 계획(6.5) 순으로 이어진다 [S26].

- 복구 자동화(6.4): 일시적 네트워크 중단에는 자동 재시도, 작업이 제때 끝나도록 관리형 스케일링을 구성한다. 자동 재실행 횟수는 제한하고 시도와 결과를 로그로 남긴다 [S25].
- 멱등성: 재실행 때 중복·오래된 데이터가 생기지 않도록 ETL을 멱등으로 설계한다. 덮어쓰기(예: Spark overwrite)와 삭제 후 쓰기(delete-write) 방법이 있으며 삭제는 신중히 적용한다 [S25].
- 재시도 원칙: 지수 백오프로 점점 긴 간격을 두고 지터로 간격을 무작위화하며 최대 재시도 횟수를 제한한다. 일부 AWS SDK의 기본 재시도·백오프를 활용하되 멱등한 호출에서 쓴다 [S27].
- 체크포인트·재개: Step Functions redrive는 실패 지점부터 재개한다 [S7]. Lambda durable functions는 체크포인트를 저장하고 재생해 재개한다 [S24].
- 실패 격리(DLQ): SQS DLQ [S32], EventBridge Scheduler DLQ [S20], SNS 구독 DLQ [S28].

| 축 | 구현 수단(출처 근거) |
|---|---|
| 재시도·백오프·지터 | Step Functions Retry(IntervalSeconds·BackoffRate·MaxDelaySeconds·JitterStrategy) [S5], Well-Architected 재시도 원칙 [S27] |
| 멱등성 | ETL 덮어쓰기/삭제 후 쓰기 [S25], Express 상태 머신 로직 멱등 [S9], Standard는 같은 이름 실행에 멱등 응답 [S1] |
| 실패 격리 | SQS DLQ(maxReceiveCount) [S32], Scheduler DLQ [S20], SNS 구독 DLQ [S28] |
| 체크포인트·재개 | Step Functions redrive [S7], Lambda durable functions [S24] |
| 모니터링·알림 | Lens BP 6.2·6.3 [S26], EventBridge → SNS [S35][S36] |
| 가용성(다중 AZ) | MWAA는 서로 다른 AZ의 서브넷 2개 [S18], 스케줄러 최소 2 [S12] |

### 서버리스 워크플로 구현·유지 관리 (Skill 1.3.3)

- 구현: 작업별로 작은 Lambda·Glue·Athena·EMR Serverless 태스크를 두고 Step Functions가 순서·분기·병렬·재시도를 맡는다 [S23]. Glue·Athena·EMR Serverless는 .sync로 완료까지 기다린다 [S3]. 폴링 루프보다 .sync/콜백이 전이 수를 줄인다 [S9].
- 유형 선택: 긴 ETL·비멱등 단계는 Standard, 짧은 고빈도 멱등 처리는 Express [S1].
- 대규모 병렬: S3의 많은 객체·큰 CSV는 Distributed Map. 상위 상태 머신은 Standard여야 한다 [S4][S1].
- 버전·별칭: 별칭은 상태 머신 두 버전 사이로 실행 트래픽을 나눈다. 새 버전에 작은 비율만 보내 위험을 줄이다가 안전을 확인하면 늘린다. 트래픽 비율 합은 100%여야 한다 [S8]. Redrive한 실행은 원래 실행의 버전·별칭을 그대로 쓴다 [S7].
- 로깅·모니터링: Standard는 Step Functions에서 실행 이력을 본다. Express는 CloudWatch Logs 로깅을 설정해야 이력을 볼 수 있다 [S6]. 실행 상태 변경은 EventBridge 이벤트로 받아 알림에 쓸 수 있다 [S36].
- 오류 처리: Retry/Catch와 redrive로 복구하고 실패 알림을 붙인다 (위 "오류 처리" 소제목) [S5][S7].

### 알림: SNS·SQS (Skill 1.3.4)

- SNS는 토픽에 게시하면 구독자에게 전달하는 pub/sub이다. 메시지는 필터링되어 Lambda·SQS·HTTP 엔드포인트 같은 구독자에게 전달되고, 전달 실패 메시지는 DLQ에 보관된다 [S28]. 목적지는 앱 간(A2A: Lambda·SQS·Amazon Data Firehose)과 앱→사람(A2P: SMS·이메일·모바일 푸시) 두 종류다 [S37].
- 구독 필터 정책이 없으면 구독자는 토픽의 모든 메시지를 받는다. 필터 정책은 JSON 객체이고, 구독의 필터 정책 범위 설정에 따라 메시지 속성 또는 메시지 본문에 적용된다 [S29].
- SNS FIFO 토픽은 SQS 표준·FIFO 큐로 전달할 수 있지만 이메일·모바일·SMS·HTTP(S) 엔드포인트는 구독할 수 없다. 엄격한 순서·중복 제거가 필요하면 SNS FIFO 토픽 + SQS FIFO 큐 조합을 쓴다 [S30].
- SQS는 소비자가 가져가는 큐이다. 큐 유형은 만든 뒤 바꿀 수 없다 [S34]. Standard는 처리량이 거의 무제한이고, FIFO는 정확히 한 번 전달·순서 보존이지만 처리량은 Standard보다 낮다 [S31].
- 가시성 제한 시간(visibility timeout): 한 소비자가 받은 메시지가 다른 소비자에게 보이지 않는 시간이다. 기본 30초, 범위 0초~12시간이다 [S34][S38]. 소비자가 이 시간 안에 처리·삭제하지 못하면 메시지가 다른 소비자에게 다시 보이므로, 보통 애플리케이션이 메시지를 처리하고 삭제하는 데 걸리는 최대 시간으로 설정한다 [S38].
- DLQ: redrive 정책의 maxReceiveCount를 넘으면 메시지를 DLQ로 옮긴다 [S32]. maxReceiveCount 기본은 10이고 [S34], FIFO 큐의 DLQ는 FIFO 큐여야 한다 [S34].
- 긴 폴링: ReceiveMessage 대기 시간을 0보다 크게 하면 활성화되고 최대 20초이다. 빈 응답을 줄여 비용을 낮춘다 [S33][S34].
- 알림 패턴: ① Glue 잡 실패 → EventBridge 규칙 → SNS 토픽 [S35]. ② Step Functions 실행 실패 → EventBridge 규칙(실행 상태 변경) → SNS 토픽 [S36]. ③ 실패 후 재시도·폴백은 Step Functions Retry/Catch에서 처리한다 [S5].

| 항목 | SQS Standard | SQS FIFO |
|---|---|---|
| 처리량 | 거의 무제한 [S31] | 높지만 Standard보다 낮음 [S31] |
| 전달·순서 | 최소 한 번 전달, 순서 보장 안 함 [S31] | 정확히 한 번 전달, 순서 보존 [S31] |
| DLQ | Standard 큐여야 함 [S34] | FIFO 큐여야 함 [S34] |
| SNS 연동 | 표준·FIFO 토픽 모두 구독 가능 [S30] | FIFO 토픽은 SQS 표준·FIFO 큐만 구독 가능 [S30] |

## 시험에서 묻는 방식

1. **패턴 1 — 오케스트레이터 선택** — "S3에 파일이 도착하면 Glue 잡 → Athena 검증 쿼리를 순서대로 실행하고, 실패하면 재시도 후 알림. 서버를 관리하기 싫고 실행하지 않을 때는 비용이 없어야 함"을 요구하면 → **Step Functions(Standard) + .sync(Glue·Athena) + Retry/Catch**가 정답 방향이다(시작 트리거는 EventBridge). 오답 후보와 탈락 이유: MWAA는 미리 배포해야 하고 DAG가 없어도 비용이 든다 / Lambda 한 개가 Glue와 Athena를 순차 호출하면 15분 한도에 걸리고 오류 처리를 직접 구현하는 안티패턴이다 / Glue 워크플로의 구성요소는 크롤러·잡·트리거로 설명되며 [S21], Athena 쿼리를 직접 호출하는 통합은 Step Functions 쪽에 있다 [S3]. 변형: "기존 Airflow DAG를 그대로·오픈소스 이식성"이면 MWAA, "Airflow 방식이지만 간헐적이고 유휴 비용을 없애고 싶다"면 MWAA Serverless, "크롤러가 끝나면 잡 시작" 정도면 Glue 워크플로. 근거 [S1][S3][S15][S16][S17][S21][S22][S23]
2. **패턴 2 — Standard vs Express 선택** — "초당 수만 건의 IoT 이벤트를 1분 안에 변환해 DynamoDB에 PUT, 멱등, 비용 최소화"를 요구하면 → **Express**(5분 이내·고빈도·멱등). "몇 시간 걸리는 ETL, EMR 클러스터 시작처럼 두 번 실행되면 안 되는 단계, 작업 완료 대기·사람 승인"을 요구하면 → **Standard**(1년·exactly-once·.sync/콜백). 오답 후보와 탈락 이유: Express는 .sync·콜백·Distributed Map을 지원하지 않고 at-least-once라 비멱등 작업에 위험하다 / Standard를 고빈도·짧은 작업에 쓰면 상태 전이 수로 과금되고 시작률 한도(표 기준 초당 2,000)가 Express(초당 100,000)보다 낮다. 근거 [S1][S2][S3]
3. **패턴 3 — 대규모 병렬 처리** — "S3의 수백만 객체(또는 큰 CSV)를 항목별로 병렬 처리, 동시성 40 초과, 실행 이력이 25,000 이벤트를 넘을 수 있음"을 요구하면 → **Distributed Map**(최대 10,000 병렬 자식 실행, 자식마다 별도 이력). 오답 후보와 탈락 이유: Inline Map은 동시성 40이고 이력이 부모에 쌓인다 / Express 상태 머신은 Distributed Map을 지원하지 않는다 / 단일 Lambda 반복문은 15분 한도에 걸린다. 근거 [S1][S4][S6][S22]
4. **패턴 4 — 실패 탐지·알림·복구** — "Glue 잡이 가끔 실패한다. 운영팀에 이메일 알림, 자동 재시도, 재실행해도 중복 데이터가 없어야 함"을 요구하면 → **EventBridge 규칙(Glue 잡 상태 변경) → SNS 토픽(이메일 구독)** + **Retry(백오프·지터·횟수 제한)** + **멱등 ETL(덮어쓰기/삭제 후 쓰기)**. 오답 후보와 탈락 이유: SQS는 이메일 같은 사람 대상 알림(A2P) 구독 대상이 아니다 / 재시도만 늘리면 멱등이 아닌 잡은 중복을 만들고 무한 재시도는 지양해야 한다. 변형: "같은 메시지가 소비자 오류로 계속 재처리" → SQS DLQ + maxReceiveCount, "처리가 오래 걸려 중복 소비" → 가시성 제한 시간 연장. 근거 [S5][S25][S27][S28][S32][S34][S35][S37]

## 흔한 함정·혼동 짝

1. **Step Functions Standard vs Express** — 최대 1년·exactly-once·상태 전이 과금·.sync/콜백/Distributed Map 지원 ↔ 최대 5분·at-least-once(비동기)·실행 수/시간/메모리 과금·Request Response만. → 시험 단서: "정확히 한 번", "비멱등(결제·EMR 클러스터 시작)" vs "IoT 고빈도", "5분 이내", "멱등" [S1][S2][S3]
2. **Step Functions vs MWAA** — 서버리스·실행이 없으면 비용 없음 ↔ 사전 배포·DAG가 없어도 비용·Python DAG. 기존 Airflow 자산/오픈소스 이식성이면 MWAA. → 시험 단서: "Airflow", "DAG", "이식성" vs "서버리스", "비용·성능" [S15][S16]
3. **MWAA vs MWAA Serverless** — 상시 가동 환경·시간당 과금·Airflow UI 접근 ↔ 사용 시간만 과금·YAML 정의·UI 직접 접근 없음·워크플로별 실행 역할. → 시험 단서: "유휴 비용 없는 Airflow", "워크플로별 IAM 격리" [S14][S17]
4. **Glue 워크플로 vs Step Functions** — Glue 크롤러·잡·트리거를 묶는 Glue 내부 체인 ↔ 여러 AWS 서비스를 직접 호출·콜백·Map까지 지원. → 시험 단서: "크롤러 완료 후 잡", "워크플로 실행 속성" vs "Athena·EMR·Lambda 혼합 흐름" [S21][S3]
5. **EventBridge 이벤트 버스 vs Pipes** — 다대다 라우팅 ↔ 점대점(단일 소스→단일 타깃)에 변환·보강 추가. → 시험 단서: "여러 대상으로 라우팅" vs "큐/스트림 → 하나의 타깃 + 보강" [S19]
6. **EventBridge Scheduler vs 예약 규칙** — Scheduler는 시간대·대규모·사용자 지정 페이로드·재시도·DLQ를 지원하고 대규모 예약에 더 적합 ↔ 예약 규칙(scheduled rules)이 원형. → 시험 단서: "수많은 개별 일정", "시간대", "일회성" [S19][S20]
7. **Lambda 안 오케스트레이션 vs Step Functions vs Lambda durable functions** — 15분 한도·오류 처리 직접 구현(안티패턴) ↔ 선언적 상태 머신 ↔ 코드로 쓰는 체크포인트·재생(최대 1년). → 시험 단서: "여러 Lambda를 순차 호출하며 재시도 코드를 직접 작성" [S22][S23][S24]
8. **Inline Map vs Distributed Map** — 동시성 40·부모 이력에 누적·JSON 배열만 ↔ 동시성 10,000·자식별 이력·S3 소스 입력 가능. → 시험 단서: "수백만 객체", "256 KiB 초과", "이력 25,000" [S4]
9. **Retry vs Catch** — Retry는 같은 상태를 백오프·지터·횟수 제한으로 재시도, Catch는 재시도로 해결 안 된 오류를 폴백 상태로 전환. States.ALL은 단독으로 쓰고 마지막에 둔다. → 시험 단서: "N번 재시도 후 다른 단계로" [S5]
10. **Request Response vs .sync vs .waitForTaskToken** — HTTP 응답 즉시 진행 ↔ 작업 완료까지 대기 ↔ 토큰이 돌아올 때까지 대기(같은 계정 주체, 사람 승인·외부 시스템). → 시험 단서: "Glue 잡이 끝나면 다음 단계"=.sync, "사람 승인/타사 시스템"=콜백 [S3]
11. **Redrive vs 새 실행 시작** — Redrive는 같은 정의·같은 실행 ARN으로 실패 단계부터 재개(Standard, 최근 14일) ↔ 정의를 고쳤다면 새 실행을 시작해야 한다. → 시험 단서: "실패 지점부터 재개" [S7]
12. **폴링 루프 vs 콜백/.sync** — 폴링 루프는 상태 전이를 늘려 Standard 비용을 올린다. → 시험 단서: "상태 전이 비용 절감" [S9]
13. **SNS vs SQS** — 푸시형 pub/sub(여러 구독자에 전달) ↔ 소비자가 ReceiveMessage로 가져가는 큐(버퍼링·재처리). → 시험 단서: "여러 시스템에 동시 통지" vs "작업 큐/버퍼" [S28][S33]
14. **SNS 표준 토픽 vs FIFO 토픽** — FIFO 토픽은 SQS 표준·FIFO 큐로만 전달하고 이메일·SMS·모바일·HTTP(S)는 구독할 수 없다. → 시험 단서: "엄격한 순서 + 이메일 알림"은 한 토픽에서 불가 [S30]
15. **SQS Standard vs FIFO** — 처리량 거의 무제한·중복·순서 어긋남 가능 ↔ 정확히 한 번·순서 보존·처리량은 더 낮음. DLQ 유형을 맞춰야 하고 큐 유형은 생성 후 변경 불가. → 시험 단서: "순서 보장", "중복 불가" [S31][S34]
16. **가시성 제한 시간 vs DLQ maxReceiveCount** — 가시성: 받은 메시지를 다른 소비자에게 숨기는 시간(기본 30초, 최대 12시간) ↔ DLQ: 수신 횟수가 maxReceiveCount를 넘은 메시지를 격리(기본 10). → 시험 단서: "처리 중 중복 소비" vs "계속 실패하는 메시지 격리" [S32][S34][S38]
17. **짧은 폴링 vs 긴 폴링** — 긴 폴링(대기 시간 > 0, 최대 20초)은 빈 응답을 줄여 비용을 낮춘다. → 시험 단서: "빈 응답 비용 절감" [S33][S34]
18. **SNS 필터 정책의 적용 대상(속성 vs 본문)** — 구독의 필터 정책 범위 설정에 따라 메시지 속성 또는 메시지 본문에 필터가 적용된다. 필터 정책이 없으면 모든 메시지를 받는다. → 시험 단서: "구독자별로 필요한 메시지만" [S29]
19. **재시도 vs 멱등성** — 재시도·재실행은 중복·오래된 데이터를 만들 수 있어 ETL을 멱등으로(덮어쓰기/삭제 후 쓰기) 설계하고 재실행 횟수를 제한한다. Express 로직도 멱등이어야 한다. → 시험 단서: "재실행 시 중복 데이터" [S25][S9][S1]
20. **Scheduler 재시도 vs DLQ** — 기본 재시도(최대 24시간·185회)가 끝나도 DLQ가 없으면 실패 이벤트는 폐기된다. → 시험 단서: "예약 호출 유실 방지" [S20]

## 자가 점검 문항 후보

### 후보 1 — Skill 1.3.1 · associate
- **문제**: 데이터 엔지니어는 S3에 파일이 도착하면 Glue ETL 잡을 실행하고, 완료 후 Athena 쿼리로 결과를 검증하고, 실패하면 정해진 횟수만큼 재시도한 뒤 SNS로 알림을 보내는 파이프라인을 만들어야 한다. 팀은 서버나 클러스터를 관리하고 싶지 않고, 파이프라인이 돌지 않을 때는 비용이 들지 않기를 원한다. 가장 적합한 오케스트레이션 방식은?
- **보기**: A. Amazon MWAA 환경을 만들고 Airflow DAG로 Glue·Athena 작업을 실행한다 / B. AWS Step Functions Standard 워크플로에서 Glue와 Athena를 .sync 통합으로 호출하고 Retry·Catch로 재시도와 SNS 알림을 구성한다 / C. 하나의 Lambda 함수 안에서 Glue 잡 시작, 상태 확인, Athena 쿼리, 재시도 로직을 모두 구현한다 / D. EventBridge 규칙만 사용해 Glue 잡 완료 이벤트마다 다음 서비스를 호출한다
- **정답**: B
- **해설 초안**: Step Functions는 서버리스이며 실행 중인 워크플로가 없으면 비용이 들지 않는다 [S16]. Glue·Athena는 .sync 통합으로 작업이 끝날 때까지 기다릴 수 있고 [S3], Retry/Catch로 재시도와 폴백(예: SNS 알림)을 구성한다 [S5].
- **오답 근거**: A — MWAA는 미리 배포해야 하고 DAG가 돌지 않아도 비용이 들며 [S16], 기존 Airflow 자산·이식성 요구도 없다 [S15] / C — Lambda는 호출당 최대 15분이고 한 함수가 순차 호출·오류 처리까지 맡는 구조는 안티패턴이다 [S22][S23] / D — EventBridge 이벤트 버스는 이벤트를 대상에 라우팅하는 역할이고 [S19], 단계 완료 대기·재시도·폴백은 Step Functions 기능이다 [S3][S5]
- **근거**: [S16] https://docs.aws.amazon.com/prescriptive-guidance/latest/modernization-integrating-microservices/orchestration.html — "With Step Functions, you incur no cost when there are no workflows running."

### 후보 2 — Skill 1.3.3 · associate
- **문제**: IoT 센서에서 초당 수만 건의 짧은 이벤트가 들어오고, 각 이벤트를 변환해 DynamoDB에 PUT 한다. 변환은 같은 입력으로 여러 번 실행해도 결과가 같고 한 건 처리는 수 초 안에 끝난다. 처리량이 매우 커서 비용을 최소화하고 싶다. 알맞은 Step Functions 구성은?
- **보기**: A. Standard 워크플로에서 각 단계를 .sync 통합으로 호출한다 / B. Standard 워크플로와 Distributed Map을 함께 사용한다 / C. Express 워크플로를 사용한다 / D. Standard 워크플로에서 waitForTaskToken으로 각 이벤트의 완료를 기다린다
- **정답**: C
- **해설 초안**: 고빈도 이벤트 처리(IoT 수집·스트리밍 변환)는 Express의 용도이고, at-least-once 모델이라 DynamoDB PUT 같은 멱등 작업에 맞다 [S1]. Express는 실행 수·지속 시간·메모리로 과금되고 시작률도 훨씬 높다 [S2].
- **오답 근거**: A — .sync는 작업 완료 대기용이며 Standard는 상태 전이 수로 과금되고 시작률 한도가 낮다 [S2][S3] / B — Distributed Map은 S3 같은 대규모 데이터 집합을 항목별로 병렬 처리할 때 쓴다 [S4] / D — 콜백은 사람 승인·외부 시스템 연동처럼 오래 기다리는 작업용이다 [S3]
- **근거**: [S1] https://docs.aws.amazon.com/step-functions/latest/dg/choosing-workflow-type.html — "The at-least-once model makes Express Workflows better suited for orchestrating"

### 후보 3 — Skill 1.3.2 · associate
- **문제**: 수백만 개의 S3 객체를 각각 Lambda로 처리하는 Step Functions 워크플로가 있다. 현재 Inline 모드 Map 상태는 동시 반복 수가 40으로 제한되어 처리 시간이 너무 길고, 실행 이력이 25,000 이벤트에 근접한다. 변경을 최소화하면서 확장성을 확보하려면?
- **보기**: A. Map 상태를 Distributed 모드로 바꾸고 S3 데이터 소스를 항목 입력으로 사용한다 / B. 상태 머신을 Express 워크플로로 다시 만들고 Inline Map을 유지한다 / C. Inline Map의 최대 동시성을 10,000으로 설정한다 / D. 하나의 Lambda 함수에서 모든 객체를 반복 처리한다
- **정답**: A
- **해설 초안**: Distributed 모드는 반복마다 자식 워크플로 실행을 만들어 최대 10,000개까지 병렬로 실행하고 자식마다 별도 이력을 가진다. 데이터가 256 KiB를 넘거나 이력이 25,000 항목을 넘거나 동시성이 40을 넘을 때 쓰는 모드다 [S4].
- **오답 근거**: B — Express는 최대 5분이고 Distributed Map을 지원하지 않는다 [S1] / C — Inline 모드는 최대 40개 동시 반복까지만 지원한다 [S4] / D — Lambda는 한 번 호출에 최대 15분이다 [S22]
- **근거**: [S4] https://docs.aws.amazon.com/step-functions/latest/dg/state-map.html — "which enables high concurrency of up to 10,000 parallel child workflow executions"

### 후보 4 — Skill 1.3.2 · associate
- **문제**: 야간 ETL 파이프라인에서 Glue 잡이 일시적인 오류로 가끔 실패해 자동으로 재시도한다. 그런데 재시도할 때마다 대상 S3 파티션에 중복 데이터가 쌓인다. 가장 적절한 개선은?
- **보기**: A. 재시도 횟수를 무제한으로 늘려 결국 성공하도록 한다 / B. 재시도를 없애고 실패하면 항상 수동으로 다시 실행한다 / C. 잡의 워커 수를 늘려 실행 시간을 줄인다 / D. 잡을 멱등으로 만들고(대상 파티션 덮어쓰기 또는 쓰기 전 기존 데이터 삭제) 자동 재실행 횟수는 제한한다
- **정답**: D
- **해설 초안**: 자동 재실행에서 중복·오래된 데이터를 막으려면 ETL을 멱등으로 설계한다. 덮어쓰기와 삭제 후 쓰기 방법이 있고, 자동 재실행 횟수는 제한하고 기록한다 [S25].
- **오답 근거**: A — 불필요한 재실행을 막기 위해 횟수를 제한해야 한다 [S25][S27] / B — 복구 자동화는 복원력 설계의 권장 사항이다 [S26] / C — 중복의 원인은 재실행의 비멱등성이라 워커 수와 무관하다 [S25]
- **근거**: [S25] https://docs.aws.amazon.com/wellarchitected/latest/analytics-lens/best-practice-6.4-automate-the-recovery-of-analytics-and-etl-job-failures..html — "Idempotent ETL jobs can be rerun with the same result or outcome."

### 후보 5 — Skill 1.3.4 · associate
- **문제**: 주문 이벤트가 하나 발생하면 분석 시스템, 감사 시스템, 알림 시스템이 각자 독립적으로 처리해야 하고, 각 시스템은 자신에게 필요한 유형의 이벤트만 받아야 한다. 어떤 구성이 맞는가?
- **보기**: A. 하나의 SQS 표준 큐에 모든 이벤트를 넣고 세 시스템이 같은 큐를 폴링한다 / B. SNS 토픽 하나에 시스템별 SQS 큐를 구독시키고 각 구독에 필터 정책을 설정한다 / C. EventBridge Pipes 하나로 세 시스템을 동시에 대상으로 지정한다 / D. SNS FIFO 토픽을 만들고 세 시스템의 이메일 주소를 구독시킨다
- **정답**: B
- **해설 초안**: SNS는 토픽에 게시된 메시지를 필터링해 구독자(Lambda·SQS·HTTP 등)에게 전달하며 [S28], 구독마다 필터 정책을 두면 필요한 메시지만 받는다. 정책이 없으면 모든 메시지를 받는다 [S29].
- **오답 근거**: A — SQS는 소비자가 폴링해 가져가는 큐이고 [S33] 구독자별 필터 정책은 SNS 기능이다 [S29] / C — Pipes는 단일 소스에서 단일 타깃으로 가는 점대점 통합이다 [S19] / D — SNS FIFO 토픽은 이메일 같은 엔드포인트로 전달할 수 없고 SQS 큐만 대상이다 [S30]
- **근거**: [S29] https://docs.aws.amazon.com/sns/latest/dg/sns-message-filtering.html — "If a subscription doesn't have a filter policy, the subscriber receives every message"
