### Redshift 배포 형태·비용 구조 (Skill 2.1.1)

- **무엇이고 왜**: Redshift는 프로비저닝 클러스터(RA3·RG·DC2 노드)와 Serverless 중 무엇을 쓰느냐가 곧 비용 모델이다.
- **RA3·RG(관리형 스토리지)**: 노드의 SSD를 빠른 로컬 저장소로 쓰고 장기 데이터는 S3에 둔다. 컴퓨트와 스토리지를 독립적으로 확장·과금하며, SSD 용량을 넘는 데이터는 자동으로 S3로 내려가고 요율은 같다 [S1].
- **DC2**: 데이터를 로컬 SSD에 두는 노드. 압축 기준 1 TB 미만이면 DC2, 데이터 증가가 예상되면 RA3를 권장한다. DS2는 더 이상 제공되지 않는다 [S1].
- **RG(신규 노드 유형)**: Graviton 기반이며 데이터 레이크 쿼리 엔진이 클러스터 자체 컴퓨트에서 돌아간다. RA3는 데이터 레이크 쿼리에 Spectrum을 쓴다 [S1].
- **프로비저닝 비용 레버**: 예약 노드는 steady-state 운영 워크로드에 적합하고, 클러스터를 일시 중지하면 백업 스토리지만 과금된다 [S1].
- **Serverless**: 용량 단위는 RPU(1 RPU = 16 GB 메모리). 기본 base capacity는 128 RPUs, 최대는 1024 RPUs(일부 리전, 그 외 리전은 512) [S2]. 쿼리가 실행되는 동안 RPU-시간을 초 단위(60초 최소)로 과금하고, 동시성 스케일링·Spectrum 요금이 따로 없다 [S3].
- **종료 공지**: 문서 상단에 Python UDF 지원 중단(2026-06-30 이후) 예고가 붙어 있다 [S1].

**표 B. Redshift 배포 선택 (초안)**

| 선택지 | 적합한 경우 | 비용·성능 특성 | 시험 단서 |
|---|---|---|---|
| RA3·RG 프로비저닝 | 상시 가동, 예측 가능한 대규모 워크로드, 데이터 성장 | 노드 수로 컴퓨트를 정하고 스토리지는 쓴 만큼 과금, 예약 노드, 일시 중지 가능 [S1] | "steady-state", "예약 노드" |
| DC2 | 압축 기준 1 TB 미만 소규모 데이터셋 | 로컬 SSD 포함, 최고 성능·최저 가격(소규모 한정) [S1] | "작은 데이터셋 최저가" |
| Serverless | 간헐적·예측 불가 워크로드, 관리 최소화 | 활성일 때만 RPU-시간 과금, base capacity로 성능 조정 [S2][S3] | "ad hoc", "유휴 시 비용 최소" |

### Redshift 접근 패턴별 구성 — 분산·정렬·WLM·동시성 스케일링 (Skill 2.1.2)

- **무엇을 하나**: 조인·필터·동시성 패턴에 맞춰 분산 스타일, 정렬 키, WLM, 동시성 스케일링을 설정한다. (스키마 설계 일반론은 Task 2.4와 겹친다.)
- **분산 스타일(DISTSTYLE)**: 지정하지 않으면 AUTO가 적용된다. AUTO는 작은 테이블을 ALL로 시작해 테이블이 커지면 KEY, 적합한 컬럼이 없으면 EVEN으로 바꿀 수 있다 [S4].
- **정렬 키**: 최근 데이터를 주로 조회하면 timestamp 컬럼을 정렬 키 선두에 둔다. 한 컬럼에 범위·등치 필터가 잦으면 그 컬럼을 정렬 키로 쓰고, 자주 조인하는 컬럼은 정렬 키이자 분산 키로 지정하면 옵티마이저가 sort merge join을 고를 수 있다 [S5].
- **WLM**: 프로비저닝 클러스터의 기본값은 자동 WLM(권장)이고 Serverless 워크그룹은 항상 자동 WLM이다. 수동 WLM은 정적이어서 대부분 권장하지 않는다 [S6]. 자동 WLM은 도착한 쿼리를 메인 클러스터·동시성 스케일링 클러스터·큐 중 하나로 동적으로 보내고, 큐에서는 짧은 쿼리를 우선한다 [S6].
- **동시성 스케일링**: 동시 쿼리가 몰릴 때 임시 클러스터를 추가한다. 쓰기 작업은 RG·RA3 노드에서만 지원되고, 메인 클러스터는 단일 노드가 아니어야 하며 노드 수 제한이 있다 [S7]. 클러스터는 하루 1시간의 무료 크레딧을 쌓는다 [S3]. 페더레이션 쿼리와는 함께 동작하지 않는다 [S42].

**표 C. DISTSTYLE 비교**

| DISTSTYLE | 동작 | 적합한 경우 | 주의 |
|---|---|---|---|
| AUTO | 테이블 데이터 크기에 맞춰 최적 스타일을 자동 할당(기본값) [S4] | 초기 선택이 불분명할 때 | 크기에 따라 ALL→KEY→EVEN으로 바뀔 수 있음 [S4] |
| EVEN | 리더 노드가 슬라이스에 라운드 로빈으로 분배 [S4] | 조인에 참여하지 않는 테이블, KEY와 ALL 중 선택이 불분명할 때 [S4] | — |
| KEY | 한 컬럼 값 기준으로 같은 값을 같은 슬라이스에 배치 [S4] | 조인 키 기준으로 두 테이블을 함께 배치(colocation) [S4] | — |
| ALL | 전체 테이블을 모든 노드에 복사 [S4] | 모든 조인에서 데이터가 같은 위치에 있어야 하는 작은 테이블 [S4] | 스토리지가 노드 수만큼 늘어남 [S4] |

### EMR 스토리지(HDFS vs EMRFS/S3)와 노드 구성 (Skill 2.1.1, 2.1.2)

- **무엇이고 왜**: EMR의 스토리지 계층은 HDFS(클러스터 로컬), EMRFS/S3 커넥터, 로컬 파일 시스템으로 나뉘고, 어디에 데이터를 두느냐가 비용·내구성을 좌우한다 [S8].
- **HDFS**: 인스턴스에 분산 저장하며 클러스터를 종료하면 회수되는 임시 저장소다. 중간 결과를 캐싱하거나 임의 I/O가 많은 워크로드, 같은 데이터셋을 반복해서 읽거나 Disk I/O가 큰 워크로드에 쓴다 [S8][S9].
- **EMRFS(S3)**: 데이터셋을 실행마다 한 번 읽을 때 적합하다. 컴퓨트와 스토리지를 분리하므로 데이터를 저장하려고 core 노드를 늘릴 필요도, HDFS 복제 비용도 없고 여러 클러스터가 같은 데이터를 쓸 수 있으며 클러스터를 종료해도 데이터가 남는다 [S9]. 흔한 구성은 입출력은 S3, 중간 결과는 HDFS다 [S8].
- **커넥터 변경**: EMR 7.10.0부터 S3A 파일 시스템이 기본 S3 커넥터로 EMRFS를 대체했다 [S8].
- **노드 유형**: task 노드는 HDFS 데이터 노드를 돌리지 않고 HDFS에 데이터를 저장하지 않으므로 임시 용량(Spot 인스턴스)에 적합하다. core 노드는 HDFS 데이터를 보유한다 [S10].

### Lake Formation의 역할과 구성 (Skill 2.1.1, 2.1.2)

- **무엇이고 왜**: Lake Formation은 S3의 데이터와 Glue Data Catalog 메타데이터에 대한 세밀한 접근 제어·공유를 중앙에서 관리한다. 스토리지가 아니다 [S11].
- **권한 모델**: RDBMS식 grant/revoke 메커니즘으로 IAM 권한 모델을 보강하며, 열·행·셀 수준 제어가 Athena·Amazon Quick·Redshift Spectrum·EMR·Glue에서 강제된다 [S11].
- **구성 선택**: LF-Tag(키-값 속성)를 Data Catalog 리소스에 붙이고 태그 기준으로 권한을 주는 LF-TBAC는 빠르게 성장하는 환경, 정책 관리가 번거로운 상황, Data Catalog 객체가 많을 때 권장되는 방법이다 [S12]. IAM 태그와 LF-Tag는 서로 다른 것이며 호환되지 않는다 [S12].
- **점진 도입·공유**: hybrid access mode를 쓰면 Lake Formation 권한과 IAM 정책을 병행하면서 유스케이스 하나씩 점진적으로 Lake Formation 권한을 도입할 수 있다 [S11]. 별개로 Lake Formation은 여러 AWS 계정·조직 사이, 또는 다른 계정의 IAM 보안 주체와 직접 데이터를 공유하는 기능도 제공한다 [S11].

### DynamoDB — 용량 모드·테이블 클래스·키/인덱스 설계·DAX (Skill 2.1.1, 2.1.2)

- **용량 모드**: on-demand는 기본이자 권장 옵션으로 요청 단위로 과금하고 용량 계획이 필요 없으며, 이전에 도달한 트래픽 수준까지는 즉시 확장한다 [S13]. 계정 단위 테이블 처리량 기본 한도(조정 가능)가 있다 [S13]. provisioned는 트래픽이 일정하거나 점진적으로 늘고 용량을 예측할 수 있을 때 비용을 통제하려고 쓴다 [S14].
- **테이블 클래스**: Standard는 기본이며 대부분의 워크로드에 권장, Standard-IA는 저장 비용이 지배적인 테이블에 쓴다. 저장 비용이 Standard 테이블 처리량 비용의 50%를 넘으면 Standard-IA가 총비용을 줄여 준다 [S15]. 클래스 전환에 애플리케이션 코드 변경이 필요 없고 보조 인덱스는 테이블과 같은 클래스를 쓴다 [S15]. (S3 스토리지 클래스와 다른 개념이다.)
- **키 설계**: 모든 파티션 키에서 균등한 활동이 나오도록 설계한다. 파티션 하나는 읽기 3,000 RU/초, 쓰기 1,000 WU/초가 한도라 한 키에 몰리면 핫 파티션이 된다 [S16].
- **인덱스**: GSI와 LSI의 차이는 표 D. 보조 인덱스에서도 균등 분산을 고려한다 [S16][S17].
- **DAX**: DynamoDB 앞단 인라인 캐시로, eventually consistent 읽기에서 마이크로초 응답이 필요할 때 쓴다 [S18].

**표 D. GSI vs LSI**

| 항목 | GSI | LSI |
|---|---|---|
| 키 | 파티션 키·정렬 키가 base table과 달라도 됨 [S17] | 파티션 키는 base table과 같고 정렬 키만 다름 [S17] |
| 처리량 | 자체 provisioned 설정(테이블과 분리) [S17] | 테이블과 처리량 공유 [S17] |
| 크기 | 제한 없음 [S17] | 파티션 키 값 하나당 인덱스 항목 총 크기 10 GB 이하 [S17] |
| 개수(기본) | 테이블당 20개(기본 한도) [S17] | 테이블당 5개 [S17] |

### 스트림 저장소 — Kinesis Data Streams vs MSK (Skill 2.1.1)

- **KDS 보존**: 스트림은 기본 24시간 레코드를 보관하고 최대 8760시간(365일)까지 늘릴 수 있다. 보존 기간을 줄이면 새 보존 기간보다 오래된 레코드가 거의 즉시 접근 불가가 되므로 주의한다 [S19].
- **KDS 용량 모드**: 샤드 하나는 쓰기 최대 1 MB/초(1,000 records/초)를 처리하며, provisioned 모드에서는 샤드 수를 직접 정한다. on-demand 모드는 샤드를 자동 관리하고 신규 스트림의 기본 처리량은 쓰기 4 MB/s·읽기 8 MB/s이며, 기본적으로 on-demand 스트림은 50개까지 만들 수 있다 [S20].
- **MSK 장기 보존**: tiered storage는 primary 스토리지와 저비용 스토리지의 두 티어로 보존 비용을 낮춘다. provisioned 모드 클러스터에서만 쓸 수 있고, 저비용 스토리지의 최소 보존은 3일이며, compacted topic은 지원하지 않는다 [S21].
- **선택 단서**: Kafka(MSK) 호환이 필요하고 오래 보존하면서 비용을 낮추려면 MSK tiered storage, AWS 네이티브 수집·샤드 단위 용량 제어가 목적이면 KDS를 먼저 떠올린다.

### RDS·Aurora 구성 — 읽기 확장과 스토리지 요금 모델 (Skill 2.1.1, 2.1.2)

- **Aurora 읽기 확장**: 한 클러스터 볼륨을 공유하는 Aurora Replica를 클러스터당 최대 15개 만들 수 있고, 복제본은 보통 100밀리초보다 훨씬 짧은 지연으로 같은 데이터를 반환한다 [S23].
- **Aurora 스토리지 구성**: Standard는 I/O 요청 단위 요금을 따로 내고, I/O-Optimized는 읽기·쓰기 I/O 추가 요금이 없다. I/O 지출이 전체 Aurora 지출의 25% 이상이면 I/O-Optimized, 그보다 적으면 Standard가 유리하다. Standard→I/O-Optimized 전환은 30일에 한 번 가능하다 [S22].
- **RDS 읽기 복제본 vs Multi-AZ**: 읽기 복제본은 비동기 복제로 읽기 트래픽을 분산한다. Multi-AZ standby는 동기 복제이지만 읽기 트래픽을 받지 못한다 [S24].

### 검색·로그 분석(OpenSearch)과 S3 스토리지 클래스 (Skill 2.1.1)

- **OpenSearch 로그 분석 비용**: 로그 분석용 데이터는 UltraWarm 또는 cold storage로 옮겨 비용을 줄이고, Index State Management(ISM)로 티어 간 이동과 보존을 관리한다. UltraWarm은 S3를 스토리지로 써서 데이터가 불변(immutable)이고 사본이 하나만 필요하며, hot 데이터가 약 2.5 TiB 규모일 때부터 비용 효율적이다. cold storage도 S3 기반이며, 쿼리할 때는 UltraWarm 노드에 선택적으로 연결한다 [S25].
- **S3 Intelligent-Tiering**: 접근 패턴이 변하거나 알 수 없을 때 객체 단위로 자동 이동한다. 30일 연속 미접근 객체는 Infrequent Access 티어로 옮기고 retrieval 요금이 없다. 128 KB 미만 객체는 모니터링·자동 티어링 대상이 아니다 [S26].
- **S3 Standard-IA·One Zone-IA**: 밀리초 접근이 필요하지만 드물게 읽는 데이터용이다. 128 KB보다 큰 객체를 30일 이상 저장하는 용도에 맞고 retrieval 요금이 있다 [S26]. (S3 라이프사이클 정책 관리는 Task 2.3.)

### 사용 사례 적용 — Aurora PostgreSQL pgvector(HNSW)·MemoryDB (Skill 2.1.3, v1.1 개정)

- **무엇이고 왜**: 2.1.3은 저장소를 사용 사례에 맞게 적용하는 Skill이며, v1.1에서 Aurora PostgreSQL의 HNSW 인덱싱과 MemoryDB의 빠른 key/value 접근 예시가 들어갔다.
- **pgvector(Aurora PostgreSQL)**: pgvector는 PostgreSQL 오픈소스 확장으로 Aurora PostgreSQL과 RDS for PostgreSQL에서 쓴다. 0.5.0 버전부터 IVFFlat과 HNSW 두 인덱스를 지원한다 [S32]. 인덱스 없이 전수 비교하면 정확하지만 큰 데이터셋에서는 성능이 부족할 수 있어, 정확도를 조금 양보하는 ANN 인덱스를 쓴다 [S32]. 관계형(SQL) 쿼리와 벡터 검색을 같은 DB에서 함께 해야 하면 Aurora PostgreSQL + pgvector가 권장된다 [S33].
- **HNSW 튜닝**: 인덱스 생성 시 m(노드당 최대 간선 수)·ef_construction, 검색 시 hnsw.ef_search를 조정한다. m이 클수록 메모리를 더 쓰고 근사 품질이 좋아질 수 있으며, ef_construction·ef_search를 키우면 지연이 늘지만 근사 품질이 좋아질 수 있다 [S32].
- **MemoryDB**: Valkey·Redis OSS 데이터 구조·API를 쓰는 내구성 있는 인메모리 DB로, 마이크로초 읽기·단일 자릿수 밀리초 쓰기를 제공하고 Multi-AZ 트랜잭션 로그로 내구성을 확보한다 [S29]. 초고속 주 DB가 필요할 때 쓰며 내구성을 위해 캐시와 DB를 따로 두는 구조를 대체할 수 있다 [S30]. ElastiCache는 기존 주 DB 앞단의 캐시 용도다 [S30]. MemoryDB는 벡터 검색도 지원하며 인덱스 알고리즘은 FLAT과 HNSW다 [S31].
- **캐시 혼동 주의**: DAX는 DynamoDB 전용 인라인 캐시다 [S18].

### 마이그레이션 도구 통합 — Transfer Family·DataSync·DMS·Snow Family (Skill 2.1.4)

- **무엇이고 왜**: 데이터 처리 시스템으로 데이터를 들여오는 경로를 "무엇을 옮기나(파일/DB)·어떤 프로토콜·소스인가·온라인/오프라인인가"로 고른다.
- **AWS Transfer Family**: 완전 관리형 서비스로 SFTP·FTPS·FTP·AS2와 브라우저로 S3 또는 EFS에 파일을 주고받는다. 최대 3개 AZ에 걸친 오토스케일링 플릿이 뒷받침한다 [S37]. 외부 파트너와 SFTP로 데이터를 교환하는 시나리오에 맞다 [S38].
- **AWS DataSync**: NFS·SMB 공유, HDFS, 자체 관리 객체 스토리지, 타 클라우드 스토리지, S3·EFS·FSx 사이에서 데이터를 옮기는 온라인 서비스로, 전송 스케줄링·진행 모니터링·암호화·검증을 처리한다. 활성 데이터셋의 온라인 마이그레이션, 지속 생성 데이터의 적시 전송, 복제용이다 [S38].
- **AWS DMS**: 데이터베이스를 AWS로 이전하며, 이전 중에도 소스 DB를 운영 상태로 둘 수 있고 변경분이 지속 복제된다. 일회성 이전 또는 지속 복제 작업을 설정할 수 있고 동종(Oracle→Oracle)·이종(Oracle→Aurora) 이전을 지원한다 [S39].
- **AWS Snow Family**: Snowball Edge는 신규 고객에게 더 이상 제공되지 않으며, 신규 고객에게는 온라인 전송은 DataSync, 안전한 물리 전송은 AWS Data Transfer Terminal, 또는 파트너 솔루션을 안내한다 [S40]. 2025-10-13 서비스 가용성 공지는 Snowball Edge Compute Optimized·Storage Optimized와 "Amazon Glacier"(공지 목록에는 이 이름만 있고 S3 스토리지 클래스 Glacier 항목은 없다)를 2025-11-07부터 신규 고객이 접근할 수 없는 maintenance 대상으로 분류했다 [S65].

**표 E. 마이그레이션 도구 선택 (초안)**

| 도구 | 주 용도 | 소스·대상 | 시험 단서 |
|---|---|---|---|
| Transfer Family | 표준 프로토콜로 외부 파트너와 파일 교환 [S37][S38] | SFTP·FTPS·FTP·AS2 ↔ S3·EFS [S37] | "partner SFTP", "서버 운영 제거" |
| DataSync | 대량 파일·객체의 온라인 이전, 정기 복제 [S38] | NFS·SMB·HDFS·객체 스토리지 ↔ S3·EFS·FSx [S38] | "NFS/SMB", "예약 전송·검증" |
| DMS | 데이터베이스 이전, 지속 복제(동종·이종) [S39] | DB 소스 → 목표 DB [S39] | "minimal downtime", "heterogeneous" |
| Snow Family | 오프라인 대용량 이전 | Snowball Edge는 신규 고객 제공 중단 [S40] | "신규 고객 불가 → DataSync" |

### Redshift 원격 액세스·데이터 이동 — 페더레이션 쿼리·구체화된 뷰·Spectrum·데이터 공유 (Skill 2.1.5)

- **페더레이션 쿼리**: RDS·Aurora(PostgreSQL·MySQL)의 라이브 데이터를 Redshift·S3 쿼리와 함께 조회한다 [S41]. 외부 데이터 소스는 읽기 접근만 되고 [S42], PostgreSQL 대상이면 리더 노드가 원격 DB 스냅샷을 만들고 영향받는 테이블에 읽기 잠금을 건다 [S42]. 동시성 스케일링과는 함께 동작하지 않으며, 다른 리전의 RDS·Aurora에 접근하면 네트워크 지연과 데이터 전송 요금이 생길 수 있다 [S42].
- **구체화된 뷰(MV)**: 쿼리 결과를 미리 계산해 저장하며, 기반 테이블이 바뀌어도 새로 고치기 전에는 내용이 그대로다 [S43]. 새로 고침은 증분(incremental)이 가능하면 증분으로, 불가능하면 전체(full)로 한다 [S43]. AUTO REFRESH를 켜면 기반 테이블 변경 후 자동으로 새로 고친다 [S43]. 같은 문서에 "Amazon Redshift가 사용자 워크로드를 우선해 자동 새로 고침을 멈출 수 있다"는 설명과 "2026-02-27부터 Auto REFRESH 쿼리가 사용자 쿼리로 실행된다"는 설명이 함께 있다 [S43].
- **Spectrum**: S3의 데이터를 로드·ETL 없이 쿼리한다 [S61]. 외부 테이블에는 UPDATE·DELETE를 할 수 없고, RA3·DC2 프로비저닝 클러스터는 클러스터와 S3 버킷이 같은 리전이어야 한다. RG 클러스터와 Serverless는 클러스터 자체 컴퓨트에서 도는 통합 데이터 레이크 쿼리 엔진을 쓰며 리전 간 S3 쿼리도 지원한다 [S44].
- **데이터 공유**: Redshift 클러스터·워크그룹·계정·리전 사이에서 복사나 이동 없이 라이브 데이터를 공유한다 [S45].
- **Zero-ETL**: Aurora의 트랜잭션 데이터를 Redshift에서 거의 실시간으로 분석하게 해 ETL 파이프라인 구축·유지를 없앤다 [S46].

**표 F. Redshift 원격 액세스·이동 방식별 선택 기준 (초안)**

| 방식 | 데이터 위치 | 핵심 특성 | 제약 | 선택 기준 키워드 |
|---|---|---|---|---|
| 페더레이션 쿼리 | 운영 RDS·Aurora(PostgreSQL·MySQL) | 라이브 데이터를 Redshift·S3 쿼리와 함께 조회 [S41] | 읽기 전용, 동시성 스케일링 미지원 [S42] | "운영 DB 최신 데이터와 조인" |
| 구체화된 뷰 | Redshift 내부 | 미리 계산된 결과, 증분/전체 새로 고침, AUTO REFRESH [S43] | 새로 고치기 전에는 최신이 아님 [S43] | "반복되는 무거운 집계 가속" |
| Spectrum | S3 외부 테이블 | 로드·ETL 없이 S3 쿼리 [S61] | UPDATE·DELETE 불가, RA3·DC2는 같은 리전 [S44] | "S3 데이터 레이크 쿼리" |
| 데이터 공유 | 다른 Redshift 클러스터·워크그룹 | 복사 없이 라이브 데이터 공유 [S45] | Redshift 간 공유 | "팀·계정 간 공유, 읽기 격리" |
| Zero-ETL | Aurora → Redshift | 거의 실시간 복제 [S46] | Aurora가 소스 | "ETL 파이프라인 제거" |

### 잠금 관리 — Redshift·RDS (Skill 2.1.6)

- **Redshift 테이블 잠금**: 쓰기 같은 명령은 덜 제한적인 잠금을 암묵적으로 잡는다. LOCK 명령은 트랜잭션 블록 안에서 ACCESS EXCLUSIVE 모드의 테이블 잠금을 얻어 다른 트랜잭션·세션의 읽기와 쓰기를 대기시키고, 이 잠금은 LOCK을 포함한 트랜잭션이 끝나면 풀린다. DROP TABLE·TRUNCATE 같은 일부 DDL도 독점 잠금을 만든다. 잠금 충돌이 나면 충돌한 트랜잭션이 중단되고 STL_TR_CONFLICT에 기록된다 [S47].
- **진단과 해제**: SVV_TRANSACTIONS 뷰로 열린 트랜잭션과 잠금 경합을 확인하고, STV_LOCKS는 현재 테이블 갱신(잠금)을 보여 주며 수퍼유저만 볼 수 있다 [S48]. 잠금을 쥔 세션을 PG_TERMINATE_BACKEND로 종료하면 실행 중인 트랜잭션이 롤백되고 모든 잠금이 풀린다. 트랜잭션 블록(BEGIN…END) 안이라 쿼리를 취소할 수 없으면 세션 자체를 종료한다 [S49].
- **격리 수준**: Redshift의 동시 쓰기는 직렬화 가능(serializable) 원칙을 따른다. SNAPSHOT 격리는 프로비저닝 클러스터와 Serverless 워크그룹의 기본값으로 더 많은 데이터를 더 짧은 시간에 처리하게 해 주고, SERIALIZABLE은 더 엄격하며 충돌하는 동시 트랜잭션을 serializable isolation violation 오류로 취소해 하나만 커밋한다 [S50].
- **데드락**: 스냅샷 격리에서 INSERT·COPY가 공유 잠금으로 함께 진행하는 중 한 트랜잭션이 UPDATE·DELETE·MERGE·DDL처럼 독점 잠금이 필요한 문장을 이어 실행하면 데드락이 날 수 있다. 독점 잠금 문장을 별도 트랜잭션으로 분리하거나 애플리케이션에 재시도 로직을 두어 피한다 [S51].
- **RDS for PostgreSQL**: 행 수준 잠금을 세밀하게 쓰기 때문에 같은 행에 동시 요청이 몰리면 충돌 확률이 커진다. COMMIT/ROLLBACK 없이 트랜잭션을 연 채 두는 idle in transaction 세션과 오래 걸리는 트랜잭션이 잠금을 오래 쥐어 Lock:transactionid 대기를 늘린다. pg_stat_activity와 pg_locks로 진단한다 [S52].
- **RDS for MySQL**: 잠금 대기가 innodb_lock_wait_timeout(기본 50초)을 넘으면 error 1205로 현재 문장이 롤백된다 [S53]. 잠금을 쥔 세션은 SHOW ENGINE INNODB STATUS로 확인한다(Aurora MySQL 문서의 InnoDB 락 대기 진단) [S54].
- **모니터링 도구 공지**: RDS Performance Insights는 2026-06-30에 end of life이며, 업그레이드하지 않으면 Database Insights의 Standard mode가 기본이 되고 실행 계획·온디맨드 분석은 Advanced mode에서만 지원된다 [S66].

### 오픈 테이블 형식 — Apache Iceberg·Amazon S3 Tables (Skill 2.1.7, v1.1 신규)

- **무엇이고 왜**: Apache Iceberg는 S3의 대용량 데이터셋을 위한 오픈 테이블 형식으로 빠른 쿼리 성능, 원자적 커밋, 동시 쓰기, SQL 호환 테이블 진화를 제공한다 [S57]. 스키마 진화·파티션 진화를 지원하고, 시간에 따른 데이터 변경을 추적해 time travel 쿼리와 과거 버전 롤백이 가능하다 [S60].
- **엔진 지원**: Glue 3.0 이상은 Iceberg와 함께 Hudi·Delta Lake도 지원한다 [S58]. EMR은 6.5.0부터 Spark 3에서 Iceberg를 쓴다 [S57]. Redshift는 Glue Data Catalog의 Iceberg 테이블을 트랜잭션 일관성으로 조회하고 [S55], S3와 S3 table bucket의 Iceberg 테이블을 만들고 쓸 수도 있다 [S56]. Athena·EMR 같은 ACID 서비스로 데이터를 바꾸는 동안 Redshift로 조회할 수 있다 [S55]. Iceberg 테이블 내용을 Redshift 로컬 테이블로 적재할 때는 INSERT INTO·CTAS를 쓰며 COPY는 쓸 수 없다 [S55].
- **직접 운영 시 테이블 유지 관리**: compaction(작은 파일 병합·delete 파일 병합), snapshot expiration(오래된 스냅샷 제거), unreferenced file removal(어떤 스냅샷도 참조하지 않는 파일 제거) 세 가지가 필요하다 [S63]. Athena에서는 OPTIMIZE가 bin-packing으로 작은 파일을 병합(compaction)하고, VACUUM이 스냅샷 만료와 고아 파일 제거를 수행한다 [S63]. 스냅샷을 만료하면 그 스냅샷으로는 더 이상 time travel할 수 없다 [S59]. Athena 테이블 속성 기본값은 최소 보존 스냅샷 1개, 최대 스냅샷 보존 432000초(5일)다 [S63].
- **자동 최적화**: Glue Data Catalog는 Iceberg 테이블의 compaction·스냅샷 보존·고아 데이터 관리를 자동으로 수행한다. compaction은 파일 수가 설정값(기본 5개)을 넘고 각 파일이 목표 크기의 75% 미만일 때 시작한다 [S64].
- **S3 Tables**: S3 table bucket은 테이블 전용 버킷으로, 테이블이 Iceberg 형식으로 저장되며 일반 버킷의 직접 관리 테이블보다 높은 TPS와 쿼리 처리량을 낸다 [S60]. compaction·스냅샷 관리·미참조 파일 제거를 자동으로 수행하고 테이블·버킷별로 설정을 바꿀 수 있다 [S60]. Iceberg V3 형식을 지원한다 [S60]. compaction 기본 목표 파일 크기는 512MB(64MB~512MB로 변경 가능)이고 스냅샷 관리 기본값은 MinimumSnapshots 1, MaximumSnapshotAge 120시간이다 [S61]. 일반 버킷의 Iceberg 테이블 대비 최대 10배 높은 TPS를 제공한다 [S62].

**표 G. 일반 버킷의 Iceberg vs S3 Tables (초안)**

| 항목 | 일반 S3 버킷의 Iceberg(직접 관리) | S3 Tables(table bucket) |
|---|---|---|
| 저장 방식 | 일반 버킷에 Iceberg 테이블을 두고 Glue Data Catalog 등으로 관리 [S55][S58] | 테이블 전용 table bucket에 Iceberg 형식으로 저장 [S60] |
| 유지 관리 | compaction·스냅샷 만료·고아 파일 정리를 직접(Athena OPTIMIZE·VACUUM 등) 하거나 Glue 자동 최적화 사용 [S63][S64] | compaction·스냅샷 관리·미참조 파일 제거 자동 수행 [S60] |
| 성능 | — | 높은 TPS·쿼리 처리량, TPS 최대 10배 [S60][S62] |
| 조회 엔진 | Athena·EMR·Glue·Redshift 등 [S55][S57][S58] | Athena·Redshift·Spark 등 [S61] |

### 벡터 인덱스 유형 — HNSW·IVF·FLAT (Skill 2.1.8, v1.1 신규)

- **정확 검색 vs 근사 검색**: 인덱스가 없으면 모든 벡터와 거리를 계산하는 정확(exact) 검색이라 정확하지만 큰 데이터셋에서는 느리다. ANN 인덱스(HNSW·IVF 계열)는 정확도를 조금 양보하고 속도를 얻는다 [S32][S34]. MemoryDB의 FLAT은 인덱스의 모든 벡터를 선형으로 처리하는 brute force 방식으로 정확한 답을 준다 [S31].
- **HNSW(Hierarchical Navigable Small World)**: 벡터를 다층 그래프로 조직한다 [S34]. IVFFlat보다 구축은 느리지만 쿼리 성능과 recall이 좋고, 훈련 단계가 없어 초기 데이터 적재 없이 인덱스를 만들 수 있다. DocumentDB 문서는 대부분의 사용 사례에 HNSW를 권한다 [S34]. 조정 값은 m·ef_construction(구축)과 ef_search(검색)이며, m이 크면 메모리가 늘고 근사 품질이 좋아질 수 있다 [S32]. MemoryDB에서는 M·EF_CONSTRUCTION을 인덱스 생성 시 정하며 바꿀 수 없고, EF_RUNTIME은 쿼리마다 덮어쓸 수 있다 [S31].
- **IVF(IVFFlat)**: 벡터 공간을 K-means로 영역(lists)으로 나누고, 쿼리 시 가장 가까운 영역 일부(probes)만 검색한다 [S32]. probes를 늘리면 recall이 좋아지지만 성능이 떨어지고, 중심점(centroid)을 정하려면 데이터가 먼저 있어야 해 테이블에 데이터를 적재한 뒤 인덱스를 만든다 [S32]. OpenSearch에서는 Faiss 엔진이 HNSW와 IVF를 모두 구현한다 [S35].
- **서비스별 지원**: 표 H. 벡터 저장소 선택은 관계형 쿼리와 함께면 Aurora PostgreSQL + pgvector, 초저지연이면 MemoryDB, 풀텍스트 검색과 함께면 OpenSearch, 수십억 벡터를 저비용으로 오래 두면 S3 Vectors, MongoDB API 기반이면 DocumentDB, 그래프와 함께면 Neptune Analytics가 단서다 [S33].

**표 H. 서비스별 벡터 인덱스·선택 단서 (초안)**

| 서비스 | 확인된 인덱스 유형 | 선택 단서 |
|---|---|---|
| Aurora PostgreSQL · RDS for PostgreSQL (pgvector) | IVFFlat, HNSW [S32] | 관계형(SQL) 쿼리와 벡터 검색을 같은 DB에서 [S33] |

## 시험에서 묻는 방식

1. **요구사항 키워드로 저장소 고르기 (Skill 2.1.1·2.1.3)** — 시나리오 요지: 트래픽 예측 불가·용량 계획 최소화, 저장 비용 지배, 마이크로초 읽기+내구성, 스트림 장기 재처리, 간헐적 분석 같은 요구가 나온다.
   - 정답 방향: 예측 불가한 key-value는 DynamoDB on-demand [S13], 저장 비용이 지배적이면 Standard-IA 테이블 클래스(앱 코드 변경 없음) [S15], 마이크로초 읽기+내구성 있는 주 DB는 MemoryDB [S29][S30], 스트림을 길게 재처리하면 KDS 보존 연장 [S19]·Kafka 호환이면 MSK tiered storage [S21], 간헐적 분석은 Redshift Serverless [S3], S3에서 접근 패턴을 모르면 Intelligent-Tiering [S26].
   - 오답 후보와 탈락 이유: provisioned는 트래픽이 일정하거나 점진적으로 늘고 예측 가능할 때의 비용 통제 수단 [S14]; on-demand 전환은 처리량 과금 방식을 바꿀 뿐 저장 비용을 줄이지 않음 [S13]; ElastiCache는 기존 주 DB 앞단 캐시 [S30]; DAX는 DynamoDB 전용 인라인 캐시 [S18]; 예약 노드는 steady-state 운영 워크로드에 적합해 간헐적 분석과 맞지 않음 [S1].

2. **이동·원격 액세스 방식 선택 (Skill 2.1.4·2.1.5)** — 시나리오 요지: 파트너 SFTP 교환, NFS/SMB 대량 이전, DB 이전+지속 복제, Redshift에서 운영 DB·S3·다른 클러스터 데이터 접근 같은 요구가 나온다.
   - 정답 방향: 외부 파트너와 SFTP·FTPS·FTP·AS2 교환은 Transfer Family [S37][S38], NFS·SMB·HDFS 대량 온라인 이전·복제는 DataSync [S38], DB 이전과 지속 복제는 DMS [S39]. Redshift에서 S3 데이터를 로드 없이 보려면 Spectrum [S61], 운영 RDS·Aurora의 최신 데이터를 ETL 없이 조인하려면 페더레이션 쿼리 [S41], 반복 집계를 빠르게 하려면 구체화된 뷰 [S43], 다른 Redshift 클러스터와 복사 없이 공유하려면 데이터 공유 [S45], Aurora를 거의 실시간으로 분석하려면 zero-ETL [S46].
   - 오답 후보와 탈락 이유: Snow Family(Snowball Edge)는 신규 고객 제공 중단 [S40]; Spectrum은 S3 외부 테이블용이며 UPDATE·DELETE 불가 [S44]; 페더레이션은 읽기 전용이고 동시성 스케일링 미지원 [S42]; MV는 새로 고치기 전에는 기반 테이블 변경이 반영되지 않음 [S43]; DMS·DataSync는 대상·프로토콜이 달라 파트너 SFTP 서버 대체가 아님 [S37][S38][S39].

3. **잠금·동시성 장애 해결 (Skill 2.1.6)** — 시나리오 요지: Redshift 쿼리·DDL이 멈춰 대기, serializable isolation violation, INSERT/COPY와 UPDATE/DELETE 데드락, RDS PostgreSQL idle in transaction, MySQL error 1205 같은 증상이 나온다.
   - 정답 방향: Redshift는 SVV_TRANSACTIONS로 열린 트랜잭션·잠금 경합을 확인하고 [S48], 잠금을 쥔 세션을 PG_TERMINATE_BACKEND로 종료해 롤백·잠금 해제 [S49]. 데드락은 독점 잠금 문장을 별도 트랜잭션으로 분리하거나 재시도 로직 [S51]. serializable 오류는 SNAPSHOT 격리(기본값) 사용을 검토 [S50]. RDS PostgreSQL은 pg_stat_activity·pg_locks로 장기·idle 트랜잭션 확인 [S52], MySQL은 잠금 대기 timeout과 SHOW ENGINE INNODB STATUS [S53][S54].
   - 오답 후보와 탈락 이유: WLM 큐 조정·동시성 스케일링은 큐·용량 문제이고, 테이블 잠금은 트랜잭션 종료 또는 세션 종료로 풀림 [S47][S49]; 트랜잭션 블록 안의 쿼리는 취소할 수 없어 세션 종료가 필요 [S49]; STV_LOCKS는 수퍼유저만 조회 가능 [S48].

4. **오픈 테이블 형식·벡터 인덱스 (Skill 2.1.7·2.1.8, v1.1 신규)** — 시나리오 요지: Iceberg 테이블의 작은 파일·오래된 스냅샷, 운영 부담 최소화, 관계형+벡터 검색, 초저지연 벡터, 수십억 벡터 저비용 같은 요구가 나온다.
   - 정답 방향: 직접 운영하는 Iceberg는 compaction(OPTIMIZE)과 스냅샷 만료·고아 파일 정리(VACUUM)가 모두 필요 [S63], 운영 부담을 줄이려면 Glue Data Catalog 자동 최적화 [S64] 또는 자동 유지 관리를 하는 S3 Tables [S60]. 관계형 쿼리와 벡터 검색을 함께 하면 Aurora PostgreSQL + pgvector(빈 테이블에도 만들 수 있는 HNSW, IVFFlat은 선적재 필요) [S32][S33], 초저지연이면 MemoryDB [S33], 풀텍스트+벡터면 OpenSearch [S33], 수십억 벡터·저비용·100 ms 이상 허용이면 S3 Vectors [S33].
   - 오답 후보와 탈락 이유: VACUUM만으로는 작은 파일이 병합되지 않고, 스냅샷을 만료하면 그 스냅샷으로 time travel할 수 없음 [S59][S63]; Redshift에서 COPY로 Iceberg 테이블을 적재할 수 없음 [S55]; IVFFlat은 중심점 계산에 데이터가 먼저 필요 [S32]; MemoryDB의 벡터 알고리즘은 FLAT·HNSW뿐 [S31].

## 흔한 함정·혼동 짝

1. **Redshift RA3·RG vs DC2** — RA3·RG는 컴퓨트·스토리지를 독립 확장(SSD+S3 관리형 스토리지), DC2는 로컬 SSD에 결합되고 압축 1 TB 미만 소규모에 권장 → 단서: "데이터 급증+비용 분리"는 RA3·RG, "작은 데이터셋 최저가"는 DC2 [S1]
2. **Redshift Serverless vs 프로비저닝** — Serverless는 RPU-시간 초 단위 과금·WLM 항상 자동·동시성 스케일링/Spectrum 별도 요금 없음, 프로비저닝은 노드 기반(예약 노드·일시 중지) → 단서: "간헐적·예측 불가"는 Serverless, "steady-state"는 예약 노드 [S1][S3][S6]
3. **DISTSTYLE KEY vs ALL vs EVEN** — KEY는 같은 값을 같은 슬라이스에(조인 colocation), ALL은 전체 복사(스토리지가 노드 수만큼 증가), EVEN은 라운드 로빈(조인 불참 테이블) → 단서: "조인 키 일치"는 KEY, "작은 테이블의 모든 조인"은 ALL [S4]
4. **자동 WLM vs 수동 WLM** — 자동 WLM은 기본·권장(Serverless는 항상 자동), 수동 WLM은 정적이라 대부분 권장하지 않음 → 단서: "워크로드 변동·예측 불가" [S6]
5. **동시성 스케일링의 읽기 vs 쓰기 지원** — 쓰기 작업의 동시성 스케일링은 RG·RA3 노드에서만 지원되고 단일 노드 클러스터는 대상이 아님 → 단서: "DC2에서 쓰기 급증" [S7]
6. **Spectrum vs 페더레이션 쿼리** — Spectrum은 S3 외부 테이블(UPDATE·DELETE 불가), 페더레이션은 운영 RDS·Aurora의 라이브 데이터(읽기 전용) → 단서: "S3 데이터 레이크" vs "운영 DB 최신 데이터" [S41][S42][S44][S61]
7. **구체화된 뷰 vs 원본 조회** — MV는 미리 계산된 결과라 새로 고치기 전에는 기반 테이블 변경이 반영되지 않고, 새로 고침은 증분 또는 전체 → 단서: "반복되는 무거운 집계 가속" [S43]
8. **데이터 공유 vs zero-ETL vs Spectrum** — 데이터 공유는 Redshift 간 복사 없는 라이브 공유, zero-ETL은 Aurora→Redshift 거의 실시간 복제, Spectrum은 S3 쿼리 → 단서: "다른 클러스터·계정과 공유" vs "운영 DB 복제" vs "S3" [S45][S46][S61]
9. **HDFS vs EMRFS(S3)** — HDFS는 종료 시 회수되는 임시 저장소(반복 읽기·Disk I/O 집약), S3는 컴퓨트와 분리되어 지속되고 HDFS 복제 비용이 없음(한 번 읽는 데이터) → 단서: "클러스터 종료 후에도 데이터 유지" [S8][S9]
10. **EMR core 노드 vs task 노드** — core는 HDFS 데이터를 보유하고, task는 HDFS에 데이터를 저장하지 않아 임시 용량·Spot에 적합 → 단서: "Spot으로 비용 절감" [S10]
11. **Lake Formation vs S3·Glue Data Catalog vs IAM** — Lake Formation은 권한·거버넌스 계층(IAM 모델을 보강), S3는 저장, Data Catalog는 메타데이터이며 LF-Tag는 IAM 태그와 다름 → 단서: "열·행·셀 수준 권한" [S11][S12]
12. **DynamoDB on-demand vs provisioned** — on-demand는 기본·권장이며 요청당 과금·용량 계획 불필요, provisioned는 트래픽이 일정하거나 점진적으로 늘고 예측 가능할 때 → 단서: "예측 불가 트래픽" vs "예측 가능·비용 통제" [S13][S14]
13. **DynamoDB 테이블 클래스 Standard vs Standard-IA** — Standard-IA는 저장 비용이 지배적일 때(저장 비용이 처리량 비용의 50% 초과), 전환에 코드 변경이 필요 없고 S3 스토리지 클래스와는 별개 → 단서: "오래된 이력, 거의 읽지 않음" [S15]
14. **GSI vs LSI** — GSI는 다른 파티션 키·정렬 키, 자체 처리량, 크기 제한 없음, 기본 20개 / LSI는 같은 파티션 키·다른 정렬 키, 테이블과 처리량 공유, 파티션 키 값당 10 GB, 5개 → 단서: "다른 파티션 키로 조회" = GSI [S17]
15. **DAX vs MemoryDB vs ElastiCache** — DAX는 DynamoDB 앞단 인라인 캐시(eventually consistent 읽기에서 마이크로초), MemoryDB는 내구성 있는 주 DB, ElastiCache는 다른 DB 앞단 캐시 → 단서: "DynamoDB 읽기 가속" vs "주 DB로 사용" [S18][S29][S30]
16. **KDS 보존 연장 vs MSK tiered storage** — KDS는 기본 24시간~최대 365일(줄이면 오래된 레코드가 거의 즉시 접근 불가), MSK tiered storage는 provisioned 전용·저비용 티어 최소 3일·compacted topic 불가 → 단서: "1년 재처리" vs "Kafka 장기 저비용 보존" [S19][S21]
17. **KDS on-demand vs provisioned** — on-demand는 샤드 자동 관리(신규 기본 쓰기 4 MB/s), provisioned는 샤드 수 직접 지정(샤드당 쓰기 1 MB/s) → 단서: "변동 큰 트래픽" vs "예측 가능한 처리량" [S20]
18. **RDS Multi-AZ standby vs 읽기 복제본** — standby는 동기 복제이지만 읽기 불가, 읽기 복제본은 비동기 복제로 읽기 확장 → 단서: "읽기 부하 분산" = 읽기 복제본 [S24]
19. **Aurora Replica vs RDS 읽기 복제본** — Aurora Replica는 클러스터 볼륨을 공유하고 최대 15개·지연 100ms 미만, RDS 읽기 복제본은 비동기 복제 → 단서: "공유 스토리지, 낮은 지연" = Aurora [S23][S24]
20. **Aurora Standard vs I/O-Optimized** — I/O 지출이 총 Aurora 지출의 25% 이상이면 I/O-Optimized, 미만이면 Standard, 전환은 30일에 한 번 → 단서: "I/O 비용 예측 가능성" [S22]
21. **OpenSearch UltraWarm vs cold storage** — UltraWarm은 S3 기반 불변 데이터로 약 2.5 TiB부터 비용 효율적, cold는 S3 기반이며 쿼리할 때만 UltraWarm 노드에 연결 → 단서: "오래된 로그 비용 절감" [S25]
22. **Transfer Family vs DataSync** — Transfer Family는 SFTP·FTPS·FTP·AS2 프로토콜로 외부 파트너와 교환, DataSync는 NFS·SMB·HDFS 등 대량 온라인 이전·복제 → 단서: "third parties와 SFTP" vs "NFS/SMB 마이그레이션" [S37][S38]
23. **DMS vs DataSync** — DMS는 DB 이전과 지속 복제(동종·이종), DataSync는 파일·객체 이동 → 단서: "database migration" vs "file/object transfer" [S38][S39]
24. **Snow Family vs DataSync** — Snowball Edge는 신규 고객에게 제공 중단이며 신규 고객은 DataSync·AWS Data Transfer Terminal·파트너를 안내받음 → 단서: 문항에 Snow가 보이면 최신성 확인 [S40]
25. **Iceberg vs Hudi vs Delta Lake** — Glue 3.0 이상은 세 가지 오픈소스 데이터 레이크 프레임워크를 모두 지원하며, 이 Skill의 예시는 Iceberg → 단서: "오픈 테이블 형식 = Iceberg" [S58]
26. **S3 Tables vs 일반 버킷의 Iceberg** — S3 Tables는 compaction·스냅샷 관리·미참조 파일 제거를 자동 수행하고 TPS가 최대 10배, 일반 버킷은 직접 운영(OPTIMIZE·VACUUM·Glue 자동 최적화) → 단서: "운영 부담 최소" = S3 Tables [S60][S62][S63][S64]
27. **Athena OPTIMIZE vs VACUUM** — OPTIMIZE는 작은 파일 병합(compaction), VACUUM은 스냅샷 만료·고아 파일 제거이며 만료한 스냅샷으로는 time travel 불가 → 단서: "작은 파일" vs "스토리지 증가" [S59][S63]
28. **HNSW vs IVFFlat vs FLAT** — HNSW는 다층 그래프(훈련 불필요·recall/쿼리 성능 우수·구축 느림), IVFFlat은 K-means 영역 분할(데이터 선적재 필요·probes로 recall 조정), FLAT은 전수 선형 비교(정확) → 단서: "빈 테이블에 인덱스" = HNSW [S31][S32][S34]
29. **벡터 저장소 선택** — 관계형+벡터는 Aurora pgvector, 초저지연은 MemoryDB, 풀텍스트+벡터는 OpenSearch, 수십억 벡터 저비용은 S3 Vectors, MongoDB API는 DocumentDB, GraphRAG는 Neptune Analytics → 단서: 요구 키워드와 서비스를 1:1 매칭 [S33]
30. **Redshift 쿼리 취소 vs 세션 종료** — 트랜잭션 블록(BEGIN…END) 안의 쿼리는 취소할 수 없어 PG_TERMINATE_BACKEND로 세션을 종료해야 잠금이 풀림 → 단서: "트랜잭션이 열린 채 멈춤" [S49]
31. **SNAPSHOT vs SERIALIZABLE 격리** — SNAPSHOT이 프로비저닝·Serverless 기본값이며 더 많은 데이터를 빠르게 처리, SERIALIZABLE은 더 엄격해 충돌 트랜잭션을 오류로 취소 → 단서: "serializable isolation violation" [S50]
32. **LOCK 명령 vs 암묵적 잠금** — LOCK은 ACCESS EXCLUSIVE 모드로 다른 세션의 읽기·쓰기를 대기시키고 트랜잭션 종료 시 해제, 쓰기 같은 명령은 덜 제한적인 잠금을 암묵적으로 잡음 → 단서: "DROP/TRUNCATE가 읽기를 막음" [S47]

### 후보 1 — Skill 2.1.1 · associate
- **문제**: 주문 이력을 저장하는 DynamoDB 테이블이 있다. 데이터 대부분은 오래되어 거의 읽지 않고, 월 비용에서 스토리지 비용이 읽기·쓰기 처리량 비용의 50%를 넘는다. 성능·내구성·가용성은 그대로 두고 애플리케이션 코드 변경 없이 총비용을 줄이려면 어떻게 해야 하는가?
- **보기**: A. 테이블을 on-demand 용량 모드로 전환한다 / B. 테이블 클래스를 DynamoDB Standard-IA로 변경한다 / C. 테이블 앞에 DAX 클러스터를 추가한다 / D. 오래된 항목을 애플리케이션 로직으로 S3로 옮기도록 개발한다
- **정답**: B
- **해설 초안**: 저장 비용이 Standard 테이블 처리량 비용의 50%를 넘으면 Standard-IA가 총비용을 줄여 주고, 테이블 클래스 전환에는 애플리케이션 코드 변경이 필요 없다 [S15].
- **오답 근거**: A — 용량 모드는 처리량 과금 방식을 바꿀 뿐 저장 비용을 낮추지 않는다 [S13] / C — DAX는 읽기 지연을 줄이는 인라인 캐시다 [S18] / D — 애플리케이션 변경이 필요해 "코드 변경 없음" 요구와 충돌한다 [S15].
- **근거**: [S15] https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/WorkingWithTables.tableclasses.html — "When storage exceeds 50% of the throughput (reads and writes)"

- **오답 근거**: A — IVFFlat은 테이블에 데이터를 먼저 적재한 뒤 만들어야 한다 [S32] / C — MemoryDB는 초저지연 실시간용이며 FLAT은 인덱스 전체를 선형 처리해 큰 인덱스에서 실행 시간이 매우 길 수 있다 [S31][S33] / D — S3 Vectors는 저비용·100 ms 이상 지연을 허용하는 드문 조회용이다 [S33].
- **근거**: [S33] https://docs.aws.amazon.com/prescriptive-guidance/latest/choosing-an-aws-vector-database-for-rag-use-cases/vector-db-options.html — "Choose Amazon Aurora PostgreSQL with pgvector"
