## 핵심 개념

### Data Catalog 구조와 엔진별 소비 방식 (Skill 2.2.1, 2.2.2)

AWS Glue Data Catalog는 테이블 정의·잡 정의 같은 제어 정보를 담는 영속 메타데이터 저장소이며 계정당 리전마다 하나가 있다 [S1]. 가격 페이지는 이를 모든 데이터 자산의 "기술(technical) 메타데이터" 저장소로 부른다 [S2]. v1.1에서 Skill 2.2.2의 문구가 "data catalog"에서 "technical data catalog"로 바뀌었고, 2.2.6(비즈니스 데이터 카탈로그)이 신규로 추가됐다 [S31].

- **구조**: 데이터베이스는 연관된 테이블 정의를 묶은 논리 그룹이고, 테이블은 컬럼 이름·데이터 타입·파티션 정보 등 데이터셋의 메타데이터 정의다 [S1]. 둘 다 메타데이터일 뿐 실제 데이터는 원래 저장소(S3 파일, RDS 테이블 등)에 그대로 남는다 [S1].
- **함께 관리되는 객체**: 파티션·테이블 버전·파티션 인덱스는 과금 대상 메타데이터 객체로 열거되고 [S2], 연결(Connection)도 Data Catalog 객체다 [S1].
- **스키마 버전**: `UpdateTable`은 기본으로 갱신 전 테이블의 아카이브 버전을 만든다 [S3].
- **소비 원리**: 엔진은 카탈로그의 테이블 메타데이터를 근거로 원천 데이터를 질의하고 [S4], 테이블은 Glue ETL 잡의 소스·타깃으로도 쓰인다 [S1].

| 소비 엔진 | 카탈로그 연결 방식 | 제약·비용 특성 | 시험 단서 키워드 |
|---|---|---|---|
| Amazon Athena | S3 데이터의 DB·테이블 스키마를 Glue Data Catalog에 저장한다. 스키마는 Glue 크롤러 또는 DDL(`CREATE TABLE`)로 만든다 [S4] | 외부 Hive 메타스토어는 Lambda 커넥터가 따로 필요 [S7] | "Athena로 S3 쿼리", "크롤러로 스키마 자동 추론" |
| Redshift Spectrum | `CREATE EXTERNAL SCHEMA`로 외부 스키마를 만들면 외부 데이터 카탈로그의 외부 DB를 참조한다. 카탈로그·S3 접근용 IAM 역할을 클러스터에 연결하고 ARN을 지정 [S5] | 외부 DB는 Athena·Glue Data Catalog·Hive 메타스토어(예: EMR) 중 어디든 둘 수 있다 [S5] | "Redshift에서 S3 데이터 직접 쿼리" |
| Amazon EMR (Hive) | Glue Data Catalog를 Hive 메타스토어로 지정(EMR 5.8.0 이상) [S6]. CLI/API에서는 `hive-site` 분류의 `hive.metastore.client.factory.class` 지정 [S6] | 영속·공유 메타스토어가 필요할 때 권장 [S6]. Hive 트랜잭션·테이블 이름 변경은 미지원 [S6] | "클러스터 간 공유 영속 메타스토어" |
| AWS Glue ETL | 카탈로그 테이블이 잡의 소스·타깃 [S1]. 쓰는 중 카탈로그를 갱신하는 옵션은 Skill 2.2.4 참조 [S23] | 카탈로그 갱신 옵션은 S3 타깃만 해당 [S23] | "ETL 잡이 카탈로그 테이블 참조" |

### Hive 메타스토어 호환과 외부 Hive 메타스토어 (Skill 2.2.2)

- Data Catalog는 Apache Hive 메타스토어와 호환되는 애플리케이션과 통합된다 [S6]. EMR 5.8.0 이상에서 Hive가 Glue Data Catalog를 메타스토어로 쓰게 설정하고 [S6], 다른 AWS 계정의 카탈로그는 EMR 5.16.0 이상의 설정 분류로 지정한다 [S6].
- EMR 함정: `LOCATION` 없이 Hive 테이블을 만들면 기본 위치가 HDFS라서, HDFS가 일시적 저장소이므로 클러스터가 종료되면 데이터가 사라진다. S3 `LOCATION`을 지정하라고 권고한다 [S6].
- 이미 쓰는 외부 Hive 메타스토어를 유지하려는 경우: Athena는 "S3 - Apache Hive metastore" 데이터 소스를 만들고 Lambda 함수를 만들어 구성해야 한다 [S7]. Redshift Spectrum 외부 스키마는 Hive 메타스토어(예: EMR)의 외부 DB도 참조할 수 있다 [S5].
- 크롤러가 크롤할 수 있는 데이터 스토어(S3, DynamoDB, Delta/Iceberg/Hudi, JDBC, MongoDB 계열) 목록에 Hive 메타스토어는 없다 [S8].

### 크롤러: 분류자·스키마 감지·지원 스토어 (Skill 2.2.3)

크롤러는 데이터 스토어(소스 또는 타깃)에 연결해 우선순위가 매겨진 분류자 목록을 거치며 스키마를 결정하고, Data Catalog에 메타데이터 테이블을 만드는 프로그램이다 [S1].

- **분류자 순서**: 사용자 정의(custom) 분류자를 지정한 순서대로 먼저 호출하고, 필요하면 내장 분류자도 호출한다 [S9]. certainty=1.0을 반환한 분류자의 결과를 쓰고, 없으면 가장 높은 certainty의 결과를, 0.0을 넘는 것이 없으면 `UNKNOWN`을 쓴다 [S9]. 직접 만드는 분류자는 예컨대 grok 패턴이나 XML row 태그로 정의할 수 있다 [S1].
- **지원 데이터 스토어**: 네이티브 클라이언트(S3, DynamoDB, Delta Lake, Iceberg, Hudi), JDBC(Redshift, Snowflake, RDS 안팎의 Aurora·MariaDB·SQL Server·MySQL·Oracle·PostgreSQL), MongoDB 클라이언트(MongoDB, Atlas, DocumentDB) [S8]. 데이터 스트림용 크롤러는 없다. 스트리밍 소스는 테이블을 직접 정의하고 스트림 속성을 지정한다 [S8][S1].
- **연결**: JDBC·MongoDB·DocumentDB는 Glue 연결이 필수이고, S3는 Network 유형 연결을 선택적으로 지정한다 [S8].
- **스키마 감지(샘플링)**: 첫 실행에서 파일마다 처음 1000 레코드 또는 첫 1MB를 읽어 스키마를 추정하고, 추정하지 못하면 1MB씩 늘려 최대 10MB까지 읽는다 [S17]. S3 대상에 `SampleSize`를 주면 리프 폴더당 일부 파일만 크롤한다(1~249, 미지정이면 전부) [S12].
- **실행 방식**: 수동(온디맨드) 재크롤 또는 cron 스케줄(UTC, 최소 5분) [S15][S16].
- **비용**: 크롤러는 DPU-hour 단가로 초 단위 과금된다 [S2].

### 스키마 변경 정책과 재크롤 모드 (Skill 2.2.3)

- 기본 동작은 크롤러가 카탈로그 스키마를 크롤 대상에 맞게 갱신하는 것이다 [S11]. 바꾸지 않으려면 "Add new columns only"(기존 정의 유지, 새 컬럼만 추가) 또는 "Ignore the change and don't update the table in the Data Catalog"를 고른다 [S11].
- API 표현: `SchemaChangePolicy` = `UpdateBehavior`(LOG | UPDATE_IN_DATABASE) + `DeleteBehavior`(LOG | DELETE_FROM_DATABASE | DEPRECATE_IN_DATABASE) [S12]. 새 컬럼만 추가는 `Configuration`의 `Tables.AddOrUpdateBehavior=MergeNewColumns`, 스키마 완전 고정은 `UpdateBehavior=LOG`(새 컬럼도 추가 안 함)이며, 파티션 스키마를 테이블에서 상속시키려면 `Partitions.AddOrUpdateBehavior=InheritFromTable` 또는 콘솔의 "Update all new and existing partitions with metadata from the table"을 쓴다 [S11].
- **함정**: 이 정책은 이미 존재하는 테이블에서 감지한 변경에만 적용된다. 신규 테이블·파티션은 정책과 상관없이 항상 생성된다 [S13].

| 재크롤 모드 (`RecrawlBehavior`) | 동작 | 제약·비용 특성 | 시험 단서 키워드 |
|---|---|---|---|
| 전체 (`CRAWL_EVERYTHING`, 콘솔 "Crawl all sub-folders") | 매 실행마다 데이터셋 전체를 다시 크롤 [S12] | 전체 처리를 피하는 방식이 증분·이벤트 모드다 [S14][S15]. 일회성 대폭 스키마 변경이 있으면 일시적으로 전체 크롤로 바꿨다가 증분으로 되돌리라고 권고 [S14] | "스키마 대폭 변경", "한 번만 전체 재크롤" |
| 증분 (`CRAWL_NEW_FOLDERS_ONLY`, "Crawl new sub-folders only") | 첫 실행은 전체 크롤, 이후 새로 생긴 파티션(폴더)만 추가 [S14] | 기존 파티션의 수정·삭제는 감지 못 함, 안정된 스키마에 적합, update/delete 동작을 `LOG`로 강제, S3 대상 변경 불가 [S14] | "새 폴더만 계속 추가", "스키마 안정" |
| S3 이벤트 (`CRAWL_EVENT_MODE`) | S3 이벤트를 SQS에서 소비해 변경이 생긴 하위 폴더만 리스팅. 첫 크롤은 전체 리스팅 [S15] | 크롤당 최대 100,000 메시지, 큐에 이벤트가 없으면 비용 없음, 크롤에 영향을 주는 속성을 바꾸면 다시 리스트 모드 [S15] | "객체 추가·삭제 반영", "SQS", "재크롤 시간·비용 절감" |

### 크롤러의 테이블·파티션 판정 (Skill 2.2.3, 2.2.4)

- 크롤러는 폴더 구조에서 테이블의 루트와 파티션 폴더를 판정한다. 폴더 수준 스키마 다수가 비슷하면 별도 테이블이 아니라 한 테이블의 파티션으로 만든다. 예컨대 `s3://sales/year=2019/month=Jan/day=1` 같은 4개 말단 폴더는 파티션 키 `year`·`month`·`day`를 가진 테이블 1개가 된다 [S10].
- 별도 테이블로 만들고 싶으면 각 테이블의 루트 폴더를 크롤러의 별도 데이터 스토어로 추가한다 [S10].
- 파일 포맷·압축 방식·스키마·S3 파티션 구조가 서로 다르면 크롤러는 테이블을 여러 개 만든다 [S17].

### 파티션 동기화 수단 (Skill 2.2.4)

S3에 새 파티션(프리픽스)이 생겨도 카탈로그에 등록되지 않으면 엔진이 보지 못한다. 등록 수단을 비교하면 다음과 같다.

| 수단 | 동작 | 제약·비용 특성 | 시험 단서 키워드 |
|---|---|---|---|
| 크롤러 재실행 (증분 / S3 이벤트) | 새 폴더·변경을 감지해 테이블·파티션을 카탈로그에 등록 [S14][S15] | 포맷·압축·스키마·파티션 구조가 다르면 별도 테이블이 생김 [S17]. 증분은 기존 파티션의 수정·삭제를 감지 못 함 [S14] | "자동 감지", "스케줄/이벤트" |
| `MSCK REPAIR TABLE` (Athena) | S3의 Hive 호환 파티션을 스캔해 카탈로그에 추가 [S18] | 추가만 하고 제거하지 않음(제거는 `ALTER TABLE DROP PARTITION`) [S18] | "Hive 스타일 key=value 프리픽스", "테이블 생성 직후 일괄 로드" |
| `ALTER TABLE ADD PARTITION` (Athena) | 지정한 파티션 값·위치만 추가. Hive 스타일이면 `LOCATION` 생략 가능, 아니면 필수 [S19] | 한 문장당 개수 제한은 없지만 대량이면 나눠 실행 권장. 단일 스캔에서 100만 파티션을 초과해 읽을 수 없음 [S19] | "비 Hive 스타일 경로", "특정 파티션만 추가" |
| `BatchCreatePartition` (Glue API) | 파티션 여러 개를 배치로 생성 [S22] | 호출당 `PartitionInputList` 최대 100개 [S22] | "프로그램으로 파티션 등록" |
| Athena 파티션 프로젝션 | 파티션 값 범위·프로젝션 타입을 테이블 속성에 정의해 쿼리 시 값을 계산하므로 파티션을 수동 생성할 필요가 없음 [S20] | 켜면 카탈로그에 등록된 파티션 메타데이터는 무시됨. Athena 쿼리에서만 유효하며 Redshift Spectrum·Athena for Spark·EMR은 표준 파티션 메타데이터를 사용. 프로젝션 파티션의 절반 넘게 비면 전통 파티션 권장 [S20] | "파티션 등록 작업 제거", "Athena 전용" |
| Glue ETL 잡이 쓰면서 갱신 | `enableUpdateCatalog`=True, `partitionKeys` 지정으로 테이블·파티션을 등록. `updateBehavior`는 기본 `UPDATE_IN_DATABASE`(스키마 덮어쓰기+파티션 추가), `LOG`면 스키마는 유지하고 파티션만 추가 [S23] | S3 타깃만, 형식은 json·csv·avro·parquet만, parquet은 Glue 최적화 parquet writer 필요 [S23]. `enableUpdateCatalog`가 true가 아니면 `updateBehavior`와 무관하게 갱신 안 됨 [S23] | "잡이 쓰는 즉시 카탈로그 반영" |

**파티션 인덱스는 "동기화"가 아니라 "조회 가속"이다** (프로젝션과 혼동 주의).
- 인덱스가 없으면 Glue가 테이블의 모든 파티션을 로드한 뒤 표현식으로 필터링한다 [S21]. 인덱스는 테이블 파티션 키의 부분 목록(순열)으로 만들며 테이블당 최대 3개다 [S21].
- 표현식에 인덱스의 첫 키가 있어야 인덱스를 쓴다 [S21]. 파티션마다 인덱스 항목이 생기고 과금 대상이다 [S21][S2].
- ACTIVE 상태의 인덱스는 Redshift Spectrum·EMR·Glue ETL Spark DataFrame이 자동 활용하고, Athena와 Glue ETL DynamicFrame은 추가 설정이 필요하다(Athena는 테이블 속성 `partition_filtering.enabled`=true) [S21].

### Glue 연결 (Skill 2.2.5)

연결(Connection)은 자격증명·URL·VPC 정보 등 접속 정보를 저장한 Data Catalog 객체다 [S8][S1]. 크롤러가 JDBC·MongoDB·DocumentDB를 크롤할 때는 연결이 필수이고, S3는 Network 유형 연결을 선택적으로 쓴다 [S8].

- **유형**: JDBC 또는 특정 유형(예: Amazon RDS), VPC 안의 데이터 소스에 접근하는 Network, Kafka(콤마로 구분한 부트스트랩 서버 URL과 포트, MSK는 다른 계정 클러스터 지정 가능) [S24].
- **VPC 네트워킹**: Glue는 연결의 서브넷에 사설 IP를 가진 ENI를 만든다 [S25]. 연결의 보안 그룹 중 하나는 모든 TCP 포트에 대한 self-referenced 인바운드 규칙이 있어야 하고, 하나는 아웃바운드가 열려 있어야 한다 [S25]. 서브넷의 여유 IP 수는 잡 worker 수보다 많아야 한다 [S25].
- **VPC 밖 데이터**: 온프레미스·퍼블릭 호스트명 RDS 같은 VPC 밖 데이터는 서브넷 라우트 테이블에 퍼블릭 서브넷의 NAT 게이트웨이가 있어야 하며, 없으면 연결이 시간 초과된다 [S25]. 연결에 Secrets Manager·STS 접근이 필요하면 엔드포인트를 붙이고, 서브넷에서 S3로 가는 엔드포인트나 NAT 경로를 제공해야 한다 [S25].

### 비즈니스 데이터 카탈로그: Amazon SageMaker Catalog (Skill 2.2.6, v1.1 신규)

**정의·위치**: SageMaker Catalog는 여러 프로젝트가 게시한 모든 자산의 카탈로그이며 범위는 도메인이다. 게시된 자산은 도메인의 모든 프로젝트가 발견할 수 있다 [S26]. SageMaker Unified Studio를 통해 접근하고 [S29], Amazon DataZone 위에 구축되어 같은 거버넌스 기능을 제공하며 DataZone 경험도 그대로 유지된다 [S29]. 프로젝트는 도메인 안에 존재하며, 프로젝트 안의 산출물은 SageMaker Catalog에 게시하기 전에는 프로젝트 밖에서 접근할 수 없다 [S26]. 도메인에는 Identity Center 기반과 IAM 기반 두 유형이 있으며 핵심 기능은 같고 인증 방식·설정 절차가 다르다 [S32]. 아래 게시·구독 흐름은 도메인 유형별 문서가 다르게 설명한다(IDC 기반 [S27], IAM 기반 [S28]).

**핵심 객체**
- 자산(Asset): 단일 물리 데이터 객체(테이블·대시보드·파일) 또는 가상 데이터 객체(뷰)를 나타낸다 [S26]. 카탈로그의 모든 자산에는 소유(생산자) 프로젝트가 있고, 소유 프로젝트가 구독 이행 정책을 통제한다 [S26].
- 비즈니스 용어집(Glossary)·용어: 자산·컬럼에 붙여 검색과 식별을 돕는다. 용어집은 만든 프로젝트가 소유해 그 프로젝트 멤버만 수정·삭제하지만 도메인 모든 사용자에게 보이고 모든 프로젝트가 용어를 자산에 붙일 수 있다 [S26].
- 메타데이터 폼: 자산을 인벤토리로 만들거나 게시할 때 수집·저장할 메타데이터를 정의한다. 필드 타입은 boolean·date·decimal·integer·string·business glossary 등이다 [S26].
- 데이터 제품(Data product): 데이터 자산을 특정 업무 용도에 맞게 묶은 독립 패키지 [S30]. 구독 요청(subscription request)은 데이터 제품 사용 요청이며 [S26], 구독 요청은 approved·rejected·revoked·granted 상태를 가진다 [S26].
- 데이터 소스: Glue Data Catalog·Redshift의 기술 메타데이터를 가져와 프로젝트 인벤토리에 자산을 만든다 [S26]. 도메인을 만들거나 갱신할 때 Glue Data Catalog 등에서 메타데이터를 자동 수집하기도 한다 [S29].

**게시·구독 흐름**: (IDC 기반 도메인) 프로젝트 인벤토리로 자산을 가져오고 → 비즈니스 이름·설명·README·용어·메타데이터 폼으로 큐레이션 → 게시해야 도메인 사용자가 발견한다. 인벤토리 자산은 게시 전에는 프로젝트 멤버만 볼 수 있고, 최신 버전만 게시할 수 있으며 갱신 후에는 다시 게시해야 한다 [S27]. (IAM 기반 도메인) Glue 테이블은 도메인에서 자동으로 발견되고, 접근 요청이 승인되면 필요한 Lake Formation 권한이 자동 부여된다 [S28]. 소비 프로젝트가 소유 프로젝트에 구독을 요청하고 승인되면 소유 프로젝트가 권한을 제공한다 [S26]. 비정형 S3 데이터는 S3 Object Collections 자산으로 카탈로그화할 수 있다 [S29].

## 시험에서 묻는 방식

1. **파티션 등록·조회 지연** — "S3에 일/시간 단위 파티션이 계속 추가되는데 Athena에서 새 데이터가 안 보인다" 또는 "파티션이 수십만 개라 쿼리 계획이 느리다" → 정답 방향: 단일 엔진(Athena)이고 경로가 Hive 스타일(`key=value`)이면 `MSCK REPAIR TABLE`, 비 Hive 스타일이거나 특정 파티션만 넣으면 `ALTER TABLE ADD PARTITION`(`LOCATION` 필수), 파티션 규칙이 예측 가능하고 Athena 전용이면 파티션 프로젝션, 여러 엔진이 같은 테이블을 읽고 등록된 파티션이 매우 많으면 크롤러(증분/이벤트)로 등록 + Glue 파티션 인덱스 → 오답 후보와 탈락 이유: 프로젝션은 Athena 쿼리에서만 유효하고 다른 엔진은 표준 파티션 메타데이터를 쓰며, `MSCK`는 추가만 하고 삭제는 반영하지 않으며, `BatchCreatePartition`은 등록 수단일 뿐 조회 가속이 아니다 → 근거 [S18][S19][S20][S21][S22][S14][S15].
2. **크롤러 동작 제어(스키마 보호·비용·테이블 분리)** — "ETL로 정제한 컬럼 정의를 크롤러가 덮어쓴다" / "대형 S3 테이블 재크롤이 느리고 비싸다" / "크롤러가 테이블을 여러 개 만든다" → 정답 방향: 새 컬럼만 허용하려면 "Add new columns only"(`MergeNewColumns`), 완전 고정은 `UpdateBehavior=LOG`/"Ignore the change…", 새 폴더만 쌓이는 데이터는 증분 크롤, 기존 폴더 안의 객체 추가·삭제까지 반영하고 싶으면 S3 이벤트 모드(SQS), 포맷·압축·스키마·파티션 구조를 맞추거나 루트 폴더를 별도 데이터 스토어로 분리 → 오답 후보와 탈락 이유: 증분 크롤은 기존 파티션의 수정·삭제를 감지하지 못하고 update/delete 동작을 `LOG`로 강제하며, 스키마 변경 정책은 신규 테이블·파티션 생성에는 영향이 없다(그래서 "정책으로 신규 테이블 생성을 막는다"는 오답), 데이터 스트림은 크롤러 대상이 아니다 → 근거 [S11][S12][S13][S14][S15][S17][S8].
3. **기술 카탈로그 vs 비즈니스 카탈로그 선택** — "Athena·EMR·Redshift Spectrum·Glue ETL이 스키마를 공유" → Glue Data Catalog. "현업이 비즈니스 용어로 검색하고, 메타데이터 폼·데이터 제품으로 설명하고, 사유를 적어 접근을 요청·승인" → Amazon SageMaker Catalog(게시→구독). "이미 쓰는 Hive 메타스토어를 옮기지 않고 Athena로 질의" → Athena 외부 Hive 메타스토어 Lambda 커넥터 → 오답 후보와 탈락 이유: 크롤러·분류자는 스키마 추론 도구이고 구독/승인 워크플로가 아니며, 크롤러 지원 스토어 목록에 Hive 메타스토어가 없다 → 근거 [S2][S26][S27][S29][S7][S8][S9].
4. **VPC 안 데이터 소스 연결** — "프라이빗 서브넷 RDS를 크롤/ETL하는데 Test connection이 시간 초과" → 정답 방향: JDBC 연결에 VPC·서브넷·보안 그룹을 지정, 연결 보안 그룹에 모든 TCP 포트 self-referenced 인바운드 규칙, 서브넷 여유 IP > worker 수, VPC 밖 데이터면 NAT 경로, Secrets Manager·STS는 엔드포인트, S3는 Network 유형 연결 → 오답 후보와 탈락 이유: 인바운드 전체 개방(0.0.0.0/0)은 문서가 요구한 해법이 아니라 self-referenced 규칙이 요구사항이다 → 근거 [S24][S25][S8].

## 흔한 함정·혼동 짝

1. **Glue Data Catalog vs SageMaker Catalog** — 전자는 엔진이 쓰는 기술 메타데이터(스키마·파티션), 후자는 도메인 단위 비즈니스 카탈로그(용어집·메타데이터 폼·데이터 제품·구독/승인) → 시험 단서: "비즈니스 용어로 검색", "접근 요청·승인", "게시(publish)" = SageMaker Catalog / "크롤러·파티션·ETL 소스" = Glue [S2][S26][S27].
2. **SageMaker Catalog vs Amazon DataZone** — SageMaker Catalog는 DataZone 위에 구축되어 같은 거버넌스 기능을 통합 사용자 경험으로 제공하고, 기존 DataZone 고객은 익숙한 DataZone 인터페이스를 계속 쓸 수 있다 → 시험 단서: "SageMaker Unified Studio에서 접근", "DataZone 기반" [S29].
3. **프로젝트 인벤토리 vs 카탈로그 게시** — 인벤토리 자산은 프로젝트 멤버에게만 보이고 게시해야 도메인 전체가 발견한다. 갱신하면 최신 버전을 다시 게시해야 한다 → 시험 단서: "다른 팀이 검색해도 안 보인다" = 게시 누락 [S27].
4. **크롤러 vs ETL 잡의 카탈로그 갱신** — 크롤러는 데이터 스토어를 스캔해 등록하고, ETL 잡은 `enableUpdateCatalog`=True로 쓰면서 등록한다(S3 타깃, json/csv/avro/parquet만). 이 옵션 없이는 `updateBehavior`를 줘도 갱신되지 않는다 → 시험 단서: "ETL 출력이 즉시 카탈로그에 반영" [S23][S8].
5. **`MSCK REPAIR TABLE` vs `ALTER TABLE ADD PARTITION`** — 전자는 테이블 위치를 스캔해 Hive 호환 파티션을 일괄 추가(제거는 안 함), 후자는 지정한 파티션만 추가하며 비 Hive 스타일이면 `LOCATION` 필수 → 시험 단서: "key=value 프리픽스" vs "임의 경로" [S18][S19].
6. **파티션 프로젝션 vs Glue 파티션 인덱스** — 프로젝션은 카탈로그를 조회하지 않고 설정으로 파티션을 계산(Athena 전용, 카탈로그의 등록 파티션은 무시). 인덱스는 카탈로그에 등록된 파티션의 `GetPartitions` 조회를 가속(Spectrum·EMR 등이 활용, 테이블당 최대 3개) → 시험 단서: "여러 엔진이 같은 테이블" = 인덱스 / "파티션 등록 관리 제거, Athena만" = 프로젝션 [S20][S21].
7. **증분 크롤 vs S3 이벤트 모드 vs 전체 재크롤** — 증분은 새 폴더만(기존 파티션의 수정·삭제 미감지), 이벤트 모드는 SQS 이벤트로 변경된 폴더만 리스팅(첫 크롤은 전체), 전체는 매번 전부 → 시험 단서: "기존 폴더에 파일 추가·삭제" = 이벤트 모드, "새 폴더만 증가" = 증분 [S14][S15][S12].
8. **UpdateBehavior=LOG vs "Add new columns only"** — LOG는 기존 스키마를 바꾸지도 새 컬럼을 추가하지도 않고, "Add new columns only"(`MergeNewColumns`)는 기존 정의를 유지하며 새 컬럼만 추가한다. 증분 크롤 옵션은 업데이트 동작을 LOG로 강제한다 → 시험 단서: "새 컬럼은 반영, 기존 컬럼 정의는 유지" [S11][S14].
9. **스키마 변경 정책 vs 신규 테이블/파티션 생성** — `SchemaChangePolicy`는 기존 테이블의 변경 감지에 대한 동작이고, 신규 테이블·파티션은 정책과 무관하게 항상 만들어진다 → 시험 단서: "정책을 LOG로 했는데 새 파티션이 추가됨" [S13].
10. **커스텀 분류자 vs 내장 분류자** — 커스텀을 지정한 순서로 먼저 호출하고, certainty=1.0이 없으면 가장 높은 certainty, 0.0 초과가 없으면 `UNKNOWN` → 시험 단서: "비표준 로그/CSV 헤더를 인식 못 함" [S9].
11. **Athena의 Glue Data Catalog vs 외부 Hive 메타스토어** — Glue는 네이티브 기본 카탈로그이고, 외부 Hive 메타스토어는 Lambda 함수를 만들어 구성하는 별도 데이터 소스 → 시험 단서: "Hive 메타스토어를 옮기지 않고 Athena로" [S4][S7].
12. **크롤러 대상 vs 스트리밍 소스** — 데이터 스트림용 크롤러는 없으므로 스트리밍 소스는 테이블을 직접 정의하고 스트림 속성을 지정한다 → 시험 단서: "Kinesis/Kafka 소스를 크롤러로 자동 스키마 추론" = 오답 [S8][S1].
13. **JDBC 연결 필수 vs S3 Network 연결 선택** — 크롤러는 JDBC·MongoDB·DocumentDB에 연결이 필수이고 S3는 Network 유형이 선택 사항(Network는 VPC 안의 데이터 소스 접근용) → 시험 단서: "RDS·Redshift 같은 JDBC 소스" = 연결 필수 [S8][S24].
14. **EMR에서 `LOCATION` 미지정 Hive 테이블** — 기본 위치가 HDFS라서 클러스터가 종료되면 데이터가 사라지고 테이블을 다시 만들어야 한다. 문서는 S3 `LOCATION` 지정을 권고한다 → 시험 단서: "클러스터 종료 후 테이블 데이터 소실" [S6].
15. **카탈로그 테이블 vs 실제 데이터** — 테이블·DB는 메타데이터일 뿐 데이터는 원래 저장소에 있다 → 시험 단서: "카탈로그 항목과 S3 객체는 별개" [S1].

## 자가 점검 문항 후보

### 후보 1 — Skill 2.2.3 · associate
- **문제**: Glue 크롤러가 S3 원천 데이터를 카탈로그화한다. ETL 팀이 카탈로그 테이블의 기존 컬럼 정의를 직접 보정해 두었는데 크롤러가 실행될 때마다 이 정의가 원본 파일 스키마로 덮어써진다. 원천에 새 컬럼이 생기면 테이블에 반영하되 기존 컬럼 정의는 그대로 유지하려면 어떻게 해야 하는가?
- **보기**: A. 크롤러 출력 옵션을 "Add new columns only"로 설정한다. / B. 기본 옵션을 유지하고 크롤러 스케줄 간격만 늘린다. / C. 데이터 소스의 재크롤 옵션을 "Crawl new sub-folders only"로 바꾼다. / D. 크롤러를 삭제하고 ETL 잡이 매번 테이블을 새로 만들게 한다.
- **정답**: A
- **해설 초안**: 크롤러의 기본 동작은 카탈로그 스키마를 소스에 맞게 갱신하는 것이다. "Add new columns only"(`MergeNewColumns`)는 기존 스키마는 바꾸지 않고 새 컬럼만 추가한다 [S11].
- **오답 근거**: B — 기본 동작이 덮어쓰기이므로 실행 빈도만 줄일 뿐 덮어쓰기는 계속된다 / C — 증분 크롤 옵션은 업데이트 동작을 `LOG`로 강제하는데, `LOG`는 기존 스키마도 안 바꾸고 새 컬럼도 추가하지 않는다 [S14][S11] / D — 요구사항(새 컬럼 반영)을 충족하는 설정이 이미 있는데 불필요한 재설계다.
- **근거**: [S11] https://docs.aws.amazon.com/glue/latest/dg/crawler-schema-changes-prevent.html — "configure a crawler to not change existing schema, only add new columns"

### 후보 2 — Skill 2.2.4 · associate
- **문제**: 연·월·일 파티션 키를 가진 하나의 Glue 테이블(등록된 파티션이 수십만 개)을 Athena, Redshift Spectrum, EMR이 함께 읽는다. 쿼리 계획 단계에서 파티션 목록을 가져오는 시간이 길다. 모든 엔진에서 이 지연을 줄이는 방법은?
- **보기**: A. Athena 파티션 프로젝션을 활성화한다. / B. 파티션 키에 대한 Glue 파티션 인덱스를 만든다(Athena는 `partition_filtering.enabled` 속성 추가). / C. 쿼리 전에 매번 `MSCK REPAIR TABLE`을 실행한다. / D. 파티션을 `BatchCreatePartition`으로 100개씩 다시 등록한다.
- **정답**: B
- **해설 초안**: 인덱스가 없으면 Glue는 테이블의 모든 파티션을 로드한 뒤 필터링한다. ACTIVE 인덱스는 Redshift Spectrum·EMR·Glue ETL Spark DataFrame이 자동 활용하고, Athena는 테이블 속성을 추가해야 한다 [S21].
- **오답 근거**: A — 프로젝션은 Athena 쿼리에서만 유효하고 Spectrum·EMR은 표준 파티션 메타데이터를 쓴다 [S20] / C — `MSCK`는 파티션을 추가할 뿐 조회 속도를 높이지 않는다 [S18] / D — 등록 수단일 뿐 조회 가속이 아니며 이미 등록된 파티션이다 [S22].
- **근거**: [S21] https://docs.aws.amazon.com/glue/latest/dg/partition-indexes.html — "AWS Glue loads all the partitions of the table"

- **문제**: 온프레미스 Apache Hive 메타스토어에 저장된 테이블 메타데이터를 Glue로 옮기지 않고 그대로 두면서 Athena로 S3 데이터를 쿼리하려 한다. 가장 적절한 방법은?
- **보기**: A. Athena에서 "S3 - Apache Hive metastore" 데이터 소스를 만들고 Lambda 함수 기반 커넥터를 구성한다. / B. Glue 크롤러로 Hive 메타스토어를 크롤한다. / C. Redshift Spectrum에서 `CREATE EXTERNAL SCHEMA … FROM DATA CATALOG`를 실행한다. / D. EMR 클러스터를 새로 띄워 Hive에서 쿼리한다.
- **정답**: A
- **해설 초안**: Athena를 Hive 메타스토어에 연결하려면 Lambda 함수를 만들어 구성해야 하고, Athena 콘솔에서 Hive 메타스토어 데이터 소스를 선택한다 [S7].
- **오답 근거**: B — 크롤러가 지원하는 데이터 스토어 목록(S3, DynamoDB, Delta/Iceberg/Hudi, JDBC, MongoDB 계열)에 Hive 메타스토어가 없다 [S8] / C — Redshift Spectrum 외부 스키마이며 Athena 쿼리 요구와 맞지 않는다 [S5] / D — "Athena로 쿼리" 요구를 충족하지 못한다.
- **근거**: [S7] https://docs.aws.amazon.com/athena/latest/ug/connect-to-data-source-hive-connecting-athena-to-an-apache-hive-metastore.html — "you must create and configure a Lambda function"

### 후보 4 — Skill 2.2.6 · associate (서비스 선택)
- **문제**: 현업 분석가가 비즈니스 용어로 데이터셋을 검색하고, 소유 팀에 사유를 적어 접근을 요청하며, 승인되면 접근 권한을 받는 사내 데이터 카탈로그를 만들려 한다. 데이터는 이미 Glue Data Catalog 테이블로 있다. 가장 적합한 방법은?
- **보기**: A. Amazon SageMaker Catalog에 자산을 게시하고 비즈니스 용어집·메타데이터 폼을 붙여 구독(subscribe) 요청·승인 흐름으로 접근을 부여한다. / B. Glue 크롤러에 분류자(classifier)를 추가한다. / C. Glue 테이블마다 Glue 연결(Connection)을 만든다. / D. Redshift Spectrum 외부 스키마를 팀별로 만든다.

### 후보 5 — Skill 2.2.5 · associate
- **문제**: VPC 프라이빗 서브넷의 RDS for PostgreSQL을 Glue 크롤러로 카탈로그화하려고 JDBC 연결을 만들었는데 Test connection이 실패한다. 서브넷 라우팅은 정상이고 DB 쪽 보안 그룹은 Glue 쪽 트래픽을 허용한다. Glue 연결 쪽에서 반드시 갖춰야 하는 보안 그룹 설정은?
- **보기**: A. 연결의 보안 그룹 중 하나에 모든 TCP 포트를 대상으로 하는 self-referenced 인바운드 규칙을 둔다. / B. 연결의 보안 그룹 인바운드에 0.0.0.0/0 전체 포트 허용 규칙을 둔다. / C. 서브넷의 여유 IP 수를 잡 worker 수보다 적게 유지한다. / D. 크롤러 IAM 역할에 관리자 권한을 부여한다.
- **정답**: A
- **해설 초안**: Glue는 연결의 서브넷에 ENI를 만들며, 연결에 연결된 보안 그룹 중 하나는 모든 TCP 포트에 대한 self-referenced 인바운드 규칙이 필요하고 하나는 아웃바운드가 열려 있어야 한다 [S25].
- **오답 근거**: B — 문서가 요구하는 것은 self-referenced 규칙이다 [S25] / C — 서브넷 여유 IP 수는 worker 수보다 많아야 한다 [S25] / D — 네트워크 연결 문제이며 IAM 권한으로 해결되지 않는다.
- **근거**: [S25] https://repost.aws/knowledge-center/glue-test-connection-failed — "must have a self-referenced inbound rule"
