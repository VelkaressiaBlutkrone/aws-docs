## 핵심 개념

### 처리 중 데이터 품질 검사 — AWS Glue Data Quality (Skill 3.4.1)

AWS Glue Data Quality는 오픈소스 DeeQu 프레임워크 위에 만든 관리형 서버리스 서비스이며, 규칙은 DQDL(Data Quality Definition Language)이라는 도메인 특화 언어로 정의한다 [S1]. 진입점은 두 가지다. Glue Data Catalog(카탈로그 테이블을 비코딩으로 평가)와 Glue ETL 잡(파이프라인 중간에서 검사)이다 [S1]. 규칙 묶음이 ruleset이며 Data Catalog 테이블에 연결된다 [S1].

- **빈 필드 검사**: `IsComplete` 규칙은 컬럼의 모든 값이 비어 있지 않은지(null 아님) 검사한다 [S6]. 규칙 추천 기능은 컬럼 데이터를 분석해 IsComplete·Uniqueness·ColumnValues·ColumnLength 같은 규칙을 제안해 주므로 코드 없이 시작할 수 있다 [S3].
- **ETL 잡 안에서**: Glue Studio의 **Evaluate Data Quality** 변환은 여러 부모(입력)를 지원해 여러 데이터셋에 걸친 규칙을 검증하고, 규칙을 통과하지 못한 레코드를 식별할 수 있다 [S2]. 원본 데이터를 그대로 내보내며 오류 표시 컬럼을 붙이는 `rowLevelOutcomes` 출력과, 규칙별 통과·실패 결과를 내보내는 출력이 있다. 행 단위로는 통과여도 전체 결과는 FAIL일 수 있다 [S2].
- **실패 시 잡 동작**: 기본값(None)은 규칙이 실패해도 잡이 계속 실행되는 것이다. 실패를 잡 실패로 연결하려면 옵션을 골라야 하며, "Fail job without loading to target data"는 데이터 품질 오류가 나는 즉시 잡을 실패시키고 어떤 타깃에도 쓰지 않는다 [S2]. 액션으로 CloudWatch 지표를 게시하거나 잡을 중단할 수 있고, 같은 지표가 EventBridge에도 게시된다 [S2].
- **S3 타깃 기본 규칙**: S3를 타깃으로 하는 ETL 잡에는 적재할 데이터에 컬럼이 하나 이상 있는지 보는 규칙이 자동으로 켜지며, 이 규칙이 실패해도 잡은 실패하지 않고 데이터 품질 점수만 내려간다 [S2].
- **점수·알림·스케줄**: 점수는 평가한 규칙 중 통과한 규칙의 비율이다 [S3]. 평가가 끝나면 EventBridge 이벤트가 게시되며 알림은 EventBridge 방식이 권장이다. CloudWatch의 사용자 지정 네임스페이스 `Glue Data Quality` 지표로 알람을 만들 수도 있다 [S4]. 카탈로그에서 정한 스케줄은 EventBridge에 만들어진다 [S4].

### 데이터 품질 규칙 정의 — DataBrew 규칙셋 (Skill 3.4.2)

DataBrew는 데이터 품질 규칙을 **ruleset**에 정의한다. ruleset은 데이터 지표를 기대값과 비교하는 규칙의 집합이며, 규칙의 기준을 하나라도 충족하지 못하면 ruleset 전체가 검증에 실패한다 [S7].

- 규칙은 컬럼 하나 또는 선택한 여러 컬럼에 적용할 수 있고, 한 규칙은 여러 단순 체크로 구성되어 모두 참이어야 할지 하나라도 참이면 될지 정할 수 있다 [S7].
- 컬럼 단위 규칙은 문자열·숫자 같은 단순 타입에만 정의할 수 있고 배열·구조체 같은 복합 타입에는 정의할 수 없다 [S7].
- **검증**: ruleset을 프로파일 잡에 추가하면 잡이 프로파일과 함께 검증 보고서를 만들고, 보고서는 프로파일 데이터와 같은 위치에 저장된다. 한 데이터셋에 ruleset을 여러 개 둘 수 있다(예: 최소 허용 기준용과 더 엄격한 기준용) [S7].
- **후속 조치**: 프로파일 잡이 끝나면 DataBrew가 CloudWatch 이벤트를 보내며 검증한 ruleset마다 이벤트가 하나씩 발행되므로, 실패한 검증만 골라 알림·자동화를 걸 수 있다 [S7].

| 구분 | AWS Glue Data Quality | DataBrew 데이터 품질 규칙 |
|---|---|---|
| 규칙 정의 | DQDL 규칙, 규칙 추천 지원 [S1][S3] | 콘솔의 ruleset(컬럼별 체크 조합) [S7] |
| 검증 실행 | Data Catalog 테이블 평가 또는 Glue ETL의 Evaluate Data Quality 변환 [S1][S2] | ruleset을 DataBrew 프로파일 잡에 붙여 검증 [S7] |
| 결과 | 점수(통과 규칙 비율), 행 수준 결과(ETL), EventBridge 이벤트·CloudWatch 지표 [S2][S3][S4] | 프로파일 데이터와 같은 위치의 검증 보고서, ruleset별 CloudWatch 이벤트 [S7] |
| 실패 처리 | ETL 잡 실패 옵션(None 기본) [S2] | ruleset 하나라도 미충족이면 전체 실패, 이벤트로 후속 조치 [S7] |
| 시험 단서 키워드 | "ETL 처리 중 검사", "빈 필드", "DQDL", "Evaluate Data Quality" | "프로파일 잡", "ruleset", "검증 보고서" |

### 데이터 일관성 조사 (Skill 3.4.3)

일관성 조사는 ① 프로파일링(중복·이상치·상관), ② 데이터셋 간 비교 규칙, ③ 시간 추이 기반 이상 탐지로 나뉜다.

- **DataBrew 프로파일 잡**: 데이터셋에 대한 일련의 평가를 실행해 결과를 S3에 출력한다 [S8]. 중복 행을 탐지·집계하는 기능과 컬럼 간 상관 행렬을 켤 수 있다 [S8]. 이상치는 개수와 z-score 샘플 목록으로 나오고 기본 임계값은 3이며, 상관은 기본으로 앞쪽 숫자 컬럼 10개를 계산한다 [S9].
- **Glue DQ의 데이터셋 간 비교**: 여러 데이터셋에 걸친 규칙은 ReferentialIntegrity와 DatasetMatch ruleset으로 설정한다 [S3].
- **Glue DQ 이상 탐지**: 규칙과 analyzer(규칙 없이 통계만 수집)가 시간에 따라 쌓은 통계를 ML로 분석해, 실제 값이 예측 범위를 벗어나면 이상 관측을 만든다 [S5]. 이상 탐지에는 최소 세 개의 데이터 포인트가 필요하고 이상이 생겨도 데이터 품질 점수에는 영향이 없으며, ETL과 Data Catalog 모두에서 지원한다 [S5].

### 데이터 샘플링 기법 (Skill 3.4.4)

샘플링은 큰 데이터를 전부 읽지 않고 일부로 탐색·프로파일링·스키마 추론을 하는 기법이다. 샘플이 작을수록 변환이 빠르고, 클수록 원본 구성을 더 정확히 반영한다는 트레이드오프가 있다 [S10].

| 서비스·기능 | 샘플링 방식 | 기본값·한도 | 근거 |
|---|---|---|---|
| DataBrew 프로젝트(대화형 편집) | 첫 n행(First n rows) 또는 무작위 행(Random rows) | 기본 첫 500행, 사용자 지정 크기는 최대 5,000행 | [S10] |
| DataBrew 프로파일 잡 | `JobSample`로 프로파일 대상 행 수 지정(전체 데이터셋 모드도 있음) | 기본은 CUSTOM_ROWS 모드, 크기 20,000행 | [S11] |
| Glue 크롤러(S3 대상) | 리프 폴더당 크롤링할 파일 수(`SampleSize`) 지정 | 1–249, 미설정이면 모든 파일 크롤링 | [S12] |
| Athena | `TABLESAMPLE BERNOULLI` / `SYSTEM` (percentage) | BERNOULLI는 모든 물리 블록을 스캔하며 행 단위 확률로 선택, SYSTEM은 논리 세그먼트 단위로 샘플링하며 독립 확률을 보장하지 않음 | [S13] |

무작위·체계적·층화 같은 일반 통계 기법명은 위 서비스(DataBrew·Glue·Athena) 문서에서 확인하지 못했다. 가장 가까운 공식 근거(SageMaker Data Wrangler·Canvas 문서)는 gaps G-3.4-01에 정리했다.

### 데이터 스큐 메커니즘 (Skill 3.4.5)

데이터 스큐는 일부 파티션·슬라이스·키·샤드에 데이터나 요청이 몰려 가장 느린 조각이 전체를 끌어내리는 현상이다. 이 Skill이 정확히 무엇을 구현하라는 것인지는 공식 근거로 확정하지 못해(gaps G-3.4-02), 공식 문서에서 "skew"·"hot"이 쓰이는 영역별로 정리한다.

- **Spark/Glue**: 스큐는 Spark 잡의 가장 흔한 병목 원인 중 하나이며, 스큐된 파티션의 태스크가 오래 걸려 전체 처리 시간을 늦춘다. Spark UI의 태스크 분포와 요약 지표 편향으로 확인한다 [S14]. AQE(Adaptive Query Execution)의 스큐 조인 최적화를 켜며 Glue 4.0부터 기본 활성이다. 조인 키는 카디널리티가 높은 키나 복합 키가 낫다 [S14]. **솔팅(salting)**은 스큐된 키에 임의 접두어를 붙여 파티션에 고르게 분산하고 처리 후 접두어를 제거하는 기법이며, 브로드캐스트나 스큐/일반 데이터 분리도 쓴다 [S15].
- **Redshift**: 분산 키는 조인 컬럼에 맞추되 팩트 테이블은 분산 키를 하나만 가질 수 있다. 날짜 컬럼을 분산 키로 하고 좁은 날짜 범위로 자주 필터하면 필터된 행이 일부 슬라이스에 몰려 쿼리 워크로드가 스큐된다 [S16]. 작은 차원 테이블은 ALL 분산으로 모든 노드에 두는 선택지가 있다 [S16]. 분포 스큐는 `SVV_TABLE_INFO` 시스템 뷰(`skew_rows` 등)로 진단한다 [S17].
- **DynamoDB**: 파티션 키 전반에 걸쳐 균일한 활동이 되도록 설계해야 한다 [S18]. 쓰기가 한 키에 몰리면 파티션 키에 임의 숫자(랜덤 접미사)를 붙이는 write sharding으로 분산하되, 읽을 때는 모든 접미사를 조회해 결과를 병합해야 한다 [S19].
- **Kinesis Data Streams**: 지표로 데이터를 훨씬 많이/적게 받는 hot/cold 샤드를 찾고, hot 샤드만 선택적으로 split해 해당 해시 키 범위의 용량을 늘린다(cold 샤드는 merge) [S20].

| 영역 | 스큐 증상·진단 | 완화 메커니즘 | 근거 |
|---|---|---|---|
| Spark/Glue | 소수 태스크만 오래 걸림(Spark UI 요약 지표 편향) | AQE 스큐 조인, 고카디널리티·복합 조인 키, 솔팅, 브로드캐스트 | [S14][S15] |
| Redshift | 일부 슬라이스에 행·쿼리 부하 집중(`SVV_TABLE_INFO`) | 분산 키 재선택, 작은 차원 테이블은 ALL 분산 | [S16][S17] |
| DynamoDB | 특정 파티션 키에 쓰기·읽기 집중(hot partition) | 균일한 파티션 키 설계, 랜덤 접미사 write sharding | [S18][S19] |
| Kinesis | 일부 샤드로 레코드 집중(hot shard) | hot 샤드 split / cold 샤드 merge | [S20] |

## 시험에서 묻는 방식

1. **ETL 처리 중 품질 검사 서비스·설정 선택 (Skill 3.4.1)** — 시나리오 요지: "Glue ETL 잡이 적재 전에 빈 필드·값 범위를 검사", "규칙을 어긴 레코드만 골라내기", "품질 오류가 나면 아무것도 쓰지 않고 잡을 즉시 실패", "평가 결과 알림" → 정답 방향: **Glue Studio의 Evaluate Data Quality 변환 + DQDL 규칙(예: IsComplete)**, 레코드 식별은 오류 표시 컬럼(`rowLevelOutcomes`) 출력, 즉시 실패는 "Fail job without loading to target data", 알림은 **EventBridge 이벤트**(권장) 또는 CloudWatch `Glue Data Quality` 지표 알람 → 오답 후보와 탈락 이유: 옵션을 건드리지 않은 기본 설정(기본은 규칙이 실패해도 잡이 계속 실행), DataBrew ruleset(프로파일 잡에 붙여 검증하는 방식), 카탈로그 테이블 평가만 설정(ETL 중간 검사가 아님) → 근거 [S1][S2][S4][S6][S7]
2. **규칙 정의·프로파일·일관성 도구 선택 (Skill 3.4.2, 3.4.3)** — 시나리오 요지: "데이터셋의 누락값 비율 등을 규칙으로 정의하고 검증 보고서를 S3에서 확인", "중복 행·이상치·컬럼 상관 조사", "두 데이터셋 간 키 일관성 점검", "과거 추세를 벗어난 값을 규칙 없이 탐지" → 정답 방향: **DataBrew ruleset을 프로파일 잡에 붙여 검증**(보고서는 프로파일 데이터와 같은 위치), 프로파일 잡의 중복 행·상관·이상치 통계, **Glue DQ의 ReferentialIntegrity·DatasetMatch**, **Glue DQ analyzer + 이상 탐지**(최소 세 개의 데이터 포인트) → 오답 후보와 탈락 이유: DataBrew ruleset 검증이 프로파일 잡 실행으로 이뤄진다는 점을 놓친 선택, 이상 탐지를 점수에 반영되는 규칙 실패로 오해(이상은 점수에 영향 없음) → 근거 [S3][S5][S7][S8][S9]
3. **샘플링 수단 선택 (Skill 3.4.4)** — 시나리오 요지: "대용량 데이터를 전부 읽지 않고 빠르게 탐색·프로파일링", "S3의 파일이 매우 많아 크롤러 실행이 오래 걸림", "Athena에서 테이블의 일부 행만 무작위로 질의" → 정답 방향: **DataBrew 프로젝트 샘플**(첫 n행/무작위 행), **프로파일 잡의 JobSample**, **크롤러 S3 대상 SampleSize**(리프 폴더당 파일 수), **Athena TABLESAMPLE BERNOULLI/SYSTEM** → 오답 후보와 탈락 이유: 샘플 크기를 키우면 원본 구성은 더 정확해지지만 변환·세션 초기화가 느려진다는 트레이드오프를 무시한 선택, SYSTEM이 독립 샘플링 확률을 보장한다는 오해 → 근거 [S10][S11][S12][S13]
4. **스큐 증상 → 영역별 완화책 (Skill 3.4.5)** — 시나리오 요지: "Glue/Spark 조인에서 일부 태스크만 오래 걸림", "Redshift에서 좁은 날짜 범위 쿼리가 일부 슬라이스에만 몰림", "DynamoDB 특정 파티션 키에 쓰기 집중으로 스로틀링", "Kinesis 일부 샤드만 과부하" → 정답 방향: Spark는 **AQE 스큐 조인·고카디널리티/복합 키·솔팅**, Redshift는 **분산 키 재선택(`SVV_TABLE_INFO`로 진단)**, DynamoDB는 **균일한 파티션 키 설계·랜덤 접미사 write sharding**, Kinesis는 **hot 샤드 split** → 오답 후보와 탈락 이유: 날짜 컬럼 분산 키를 유지한 채 좁은 날짜 범위로 계속 필터(일부 슬라이스에 행이 몰림), write sharding 후 읽기에서 접미사 전체 조회·병합이 필요하다는 비용을 무시한 선택 → 근거 [S14][S15][S16][S17][S18][S19][S20]

## 흔한 함정·혼동 짝

1. **AWS Glue Data Quality vs DataBrew 데이터 품질 규칙** — Glue DQ는 DQDL 규칙을 Data Catalog 테이블이나 ETL 잡 안에서 평가하고, DataBrew는 ruleset을 프로파일 잡에 붙여 검증한다 → 시험 단서: "ETL 처리 중 검사·DQDL" ⇒ Glue DQ, "프로파일 잡·ruleset·검증 보고서" ⇒ DataBrew [S1][S2][S7]
2. **Glue DQ의 Data Catalog 진입점 vs ETL 잡 진입점** — 카탈로그는 이미 등록된 테이블을 비코딩으로 평가(데이터 거버넌스 용도), ETL은 Evaluate Data Quality 변환으로 파이프라인 안에서 검사·행 수준 식별·잡 제어 → 시험 단서: "이미 카탈로그에 있는 데이터 정기 평가" vs "변환 도중 불량 레코드 분리" [S1][S2]
3. **규칙 실패 시 잡 동작: None(기본) vs 실패 옵션** — 기본은 규칙이 실패해도 잡이 끝까지 실행되며, 중단하려면 옵션을 골라야 한다. "Fail job without loading to target data"는 어떤 타깃에도 쓰지 않고 즉시 실패 → 시험 단서: "품질 오류 시 적재 금지" [S2]
4. **행 수준 통과 vs 전체 결과 FAIL** — 규칙(예: RowCount)은 데이터셋 단위로 평가되어 전체는 FAIL이어도 개별 레코드는 통과일 수 있다 → 시험 단서: "불량 레코드만 분리" 요구 시 rowLevelOutcomes [S2]
5. **데이터 품질 점수 vs 이상 탐지** — 점수는 통과한 규칙의 비율이고, 이상 탐지는 통계의 시간 추이를 보며(최소 세 개의 데이터 포인트) 이상이 생겨도 점수에 영향을 주지 않는다 → 시험 단서: "규칙 작성 없이 평소 범위 이탈 탐지" [S3][S5]
6. **DataBrew 프로젝트 샘플 vs 프로파일 잡 샘플** — 프로젝트는 대화형 편집용 샘플(기본 첫 500행, 최대 5,000행), 프로파일 잡은 JobSample로 대상 행 수 지정(기본 20,000행) → 시험 단서: "콘솔에서 변환 시험" vs "프로파일 통계 계산 범위" [S10][S11]
7. **크롤러 샘플링(파일 수) vs 질의 샘플링(행)** — 크롤러 SampleSize는 리프 폴더당 읽을 파일 수(1–249)를 정해 스키마 추론 시간을 줄이고, Athena TABLESAMPLE은 질의 결과 행을 확률로 선택 → 시험 단서: "크롤러 실행 시간" vs "질의에서 일부 행" [S12][S13]
8. **Athena TABLESAMPLE BERNOULLI vs SYSTEM** — BERNOULLI는 모든 물리 블록을 스캔하며 행마다 확률로 선택, SYSTEM은 논리 세그먼트 단위로 선택하고 독립 확률을 보장하지 않음 → 시험 단서: "행 단위 무작위" vs "세그먼트 단위" [S13]
9. **Spark 스큐 완화: AQE vs 솔팅 vs 브로드캐스트** — AQE는 런타임 통계로 스큐 조인을 자동 분할(Glue 4.0 기본), 솔팅은 스큐된 키에 임의 접두어를 붙여 분산 후 제거, 브로드캐스트는 작은 쪽을 각 워커에 복제해 셔플을 피함 → 시험 단서: "코드 변경 없이 자동" vs "키에 접두어" vs "작은 테이블" [S14][S15]
10. **영역별 "스큐" 용어 혼동** — Spark 파티션 스큐, Redshift 분산 스큐(슬라이스 편중, `SVV_TABLE_INFO`), DynamoDB hot partition(파티션 키 설계), Kinesis hot shard(샤드 split)는 증상은 같아도 해법이 다르다 → 시험 단서: 서비스 이름과 "슬라이스·파티션 키·샤드" 어휘 [S14][S16][S17][S18][S20]
11. **DynamoDB 랜덤 접미사 vs 계산된 접미사** — 랜덤 접미사는 쓰기를 고르게 퍼뜨리지만 읽을 때 모든 접미사를 조회해 병합해야 하고, 계산된 접미사는 질의 기준으로 접미사를 계산해 특정 항목을 읽기 쉽다 → 시험 단서: "쓰기 분산" vs "특정 항목 조회" [S19]

## 자가 점검 문항 후보

### 후보 1 — Skill 3.4.1 · associate · 서비스 선택
- **문제**: Glue ETL 잡이 S3로 적재하기 전에 필수 컬럼에 빈 값이 있는지 검사하고, 규칙을 어기는 데이터가 있으면 어떤 타깃에도 쓰지 않은 채 잡을 즉시 실패시켜야 한다. 가장 적합한 구성은?
- **보기**: A. Evaluate Data Quality 변환에 IsComplete 규칙을 넣고 실패 시 "Fail job without loading to target data"를 선택한다 / B. Evaluate Data Quality 변환을 추가하되 실패 동작은 기본값(None)으로 둔다 / C. DataBrew ruleset을 만들어 프로파일 잡에 붙인다 / D. Data Catalog 테이블에 ruleset을 연결해 EventBridge 스케줄로 평가한다
- **정답**: A
- **해설 초안**: Evaluate Data Quality 변환은 ETL 잡 안에서 DQDL 규칙을 평가하고, IsComplete는 컬럼의 모든 값이 null이 아닌지 검사한다. "Fail job without loading to target data" 옵션은 데이터 품질 오류가 나는 즉시 잡을 실패시키고 어떤 타깃에도 쓰지 않는다 [S2][S6].
- **오답 근거**: B — 기본(None)은 규칙이 실패해도 잡이 계속 실행된다 [S2]. C — DataBrew ruleset은 프로파일 잡에 붙여 검증하는 방식이다 [S7]. D — Data Catalog 진입점은 이미 카탈로그에 등록한 데이터셋을 평가하는 용도이고, 파이프라인 도중 제어는 ETL 진입점의 변환이 맡는다 [S1][S2].
- **근거**: [S2] https://docs.aws.amazon.com/glue/latest/dg/tutorial-data-quality.html — "This option fails the job immediately when a data quality error occurs"

### 후보 2 — Skill 3.4.2 · associate
- **문제**: 팀이 DataBrew에서 데이터셋 컬럼의 누락값 비율이 기준 이하인지 확인하는 규칙들을 ruleset으로 정의했다. 이 ruleset의 검증 결과를 얻으려면 어떻게 해야 하는가?
- **보기**: A. ruleset을 해당 데이터셋의 프로파일 잡에 추가해 실행하고, 프로파일 데이터와 같은 위치의 검증 보고서를 확인한다 / B. ruleset을 Glue ETL 잡의 Evaluate Data Quality 변환에 그대로 불러와 평가한다 / C. ruleset을 정의하기만 하면 별도 잡 없이 자동으로 검증된다 / D. CloudWatch 이벤트를 구독하면 검증 보고서가 생성된다
- **정답**: A
- **해설 초안**: DataBrew는 ruleset을 프로파일 잡에 추가해 검증한다. 잡이 실행되면 프로파일과 함께 검증 보고서가 만들어져 프로파일 데이터와 같은 위치에 저장되고, 한 데이터셋에 ruleset을 여러 개 둘 수 있다 [S7].
- **오답 근거**: B — Evaluate Data Quality 변환은 Glue Data Quality의 DQDL 규칙을 평가하는 기능이다 [S2]. C — 검증은 프로파일 잡을 실행할 때 일어난다 [S7]. D — 이벤트는 프로파일 잡이 끝난 뒤 검증 결과를 알리는 용도이며 보고서를 만들지 않는다 [S7].
- **근거**: [S7] https://docs.aws.amazon.com/databrew/latest/dg/profile.data-quality-rules.html — "After a ruleset is defined, you can add it to a profile job for validation."

### 후보 3 — Skill 3.4.3 · associate
- **문제**: 매일 적재되는 카탈로그 테이블의 통계가 평소 범위를 벗어나는지, 사람이 임계값을 일일이 정하지 않고 탐지하려 한다. AWS Glue Data Quality로 옳은 설명은?
- **보기**: A. analyzer로 통계를 수집하고 이상 탐지를 켠다. 이상을 판단하려면 최소 세 개의 데이터 포인트가 필요하다 / B. 이상이 탐지되면 데이터 품질 점수가 자동으로 내려간다 / C. 이상 탐지는 Glue ETL에서만 지원되고 Data Catalog에서는 쓸 수 없다 / D. 이상 탐지를 쓰려면 모든 통계마다 고정 임계값 규칙을 먼저 작성해야 한다
- **정답**: A
- **해설 초안**: analyzer는 명시적 규칙 없이 데이터 통계를 수집하고, Glue Data Quality는 시간에 따라 쌓인 통계로 이상을 탐지한다. 최소 세 개의 데이터 포인트가 필요하며 ETL과 Data Catalog를 모두 지원한다 [S5].
- **오답 근거**: B — 이상이 생겨도 데이터 품질 점수에는 영향이 없다 [S5]. C — ETL과 Data Catalog 모두에서 지원한다 [S5]. D — analyzer는 규칙을 정의하지 않고도 통계를 모으는 방법이다 [S5].
- **근거**: [S5] https://docs.aws.amazon.com/glue/latest/dg/data-quality-anomaly-detection.html — "AWS Glue Data Quality requires a minimum of three data points to detect anomalies."

### 후보 4 — Skill 3.4.4 · associate
- **문제**: S3 버킷의 각 리프 폴더에 파일이 수천 개씩 있고 모든 폴더의 스키마가 같다. Glue 크롤러 실행 시간이 너무 길다. 어떻게 줄이는가?
- **보기**: A. 크롤러의 S3 대상에 SampleSize를 설정해 리프 폴더당 일부 파일만 크롤링한다 / B. DataBrew 프로젝트의 샘플 크기를 최대값으로 늘린다 / C. Athena 질의에 TABLESAMPLE SYSTEM을 사용한다 / D. 크롤러 대상에 SampleSize를 설정하지 않아 모든 파일을 크롤링하게 한다
- **정답**: A
- **해설 초안**: 크롤러 S3 대상의 SampleSize는 리프 폴더당 크롤링할 파일 수(1–249)를 정하며, 설정하지 않으면 모든 파일을 크롤링한다 [S12].
- **오답 근거**: B — DataBrew 프로젝트 샘플은 대화형 데이터 편집용이며 기본 첫 500행, 사용자 지정 크기는 최대 5,000행이라 크롤러와 무관하다 [S10]. C — TABLESAMPLE은 Athena 질의에서 행을 고르는 연산자다 [S13]. D — 설정하지 않으면 모든 파일을 크롤링해 시간이 줄지 않는다 [S12].
- **근거**: [S12] https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-properties-glue-crawler-s3target.html — "A valid value is an integer between 1 and 249."

### 후보 5 — Skill 3.4.5 · associate
- **문제**: Redshift의 대형 팩트 테이블이 날짜 컬럼을 분산 키(DISTKEY)로 쓰는데 쿼리는 대부분 좁은 날짜 범위로 필터링한다. 필터된 행이 일부 슬라이스에만 몰려 쿼리가 느리다. 개선 방법은?
- **보기**: A. 분산 키를 차원 테이블 기본 키에 대응하는 팩트 테이블 외래 키처럼 조인에 쓰는 공통 컬럼으로 바꾼다 / B. 팩트 테이블에 분산 키를 둘 이상 지정한다 / C. 큰 팩트 테이블 자체에 ALL 분산을 적용한다 / D. SVV_TABLE_INFO로 스큐를 확인만 하고 분산 키는 그대로 둔다
- **정답**: A
- **해설 초안**: 날짜 컬럼 분산 키에 좁은 날짜 범위 필터가 겹치면 필터된 행이 일부 슬라이스에 몰려 쿼리 워크로드가 스큐된다. 권장은 팩트 테이블과 차원 테이블을 공통 컬럼(차원의 기본 키와 팩트의 외래 키)으로 분산하는 것이다 [S16].
- **오답 근거**: B — 팩트 테이블은 분산 키를 하나만 가질 수 있다 [S16]. C — ALL 분산은 저장 공간 요구량과 로드·유지보수 부담을 늘리므로 일부 차원 테이블에 고려하는 방식이다 [S16]. D — SVV_TABLE_INFO는 분포 스큐를 진단하는 뷰이지 해결책이 아니다 [S17].
- **근거**: [S16] https://docs.aws.amazon.com/redshift/latest/dg/c_best-practices-best-dist-key.html — "most of the filtered rows occur on a limited set of slices"
