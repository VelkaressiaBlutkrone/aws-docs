## 핵심 개념

### Redshift 데이터 공유와 권한 부여 (Skill 4.5.1)

Redshift 데이터 공유(data sharing)는 클러스터·워크그룹·AWS 계정·리전에 걸쳐 라이브 데이터를 수동 이동이나 복사 없이 공유하는 기능이다 [S1]. 시험은 "복사 없이 최신 데이터를 다른 팀·계정이 쿼리"에서 이 기능을 고르게 하고, 교차 계정에서 누가 무엇을 승인하는지를 묻는다.

- **프로듀서 쪽 권한 부여**: 프로듀서 관리자는 datashare를 만들어 객체를 추가하고, 다른 DB 사용자에게 datashare 변경(ALTER)·공유(SHARE) 권한을 위임한다. 위임은 클러스터 superuser와 datashare 소유자가 할 수 있다 [S3]. 소비자 추가는 GRANT USAGE ON DATASHARE로 하며 한 GRANT 문에는 소비자를 하나만 쓸 수 있다 [S3].
- **교차 계정 = 양방향 핸드셰이크**: 계정에 GRANT USAGE를 하면 datashare 상태가 pending_authorization이 되고, 프로듀서 계정 관리자가 소비자를 authorize해야 한다 [S3]. 소비 계정 관리자는 그 datashare를 계정 전체 또는 특정 클러스터에 associate하거나 거부한다 [S2]. 네임스페이스를 소비자로 추가할 때는 authorize가 필요 없다 [S3]. 교차 계정 공유에서는 프로듀서·소비자 클러스터가 모두 암호화되어야 하고 [S2], 같은 datashare를 계정 내 공유와 교차 계정 공유에 함께 쓸 수 있다 [S2].
- **쓰기 공유(신규 기능)**: 이전에는 datashare 객체가 항상 읽기 전용이었으나 쓰기가 추가됐다 [S1]. 프로듀서가 INSERT·CREATE 같은 쓰기 권한을 datashare에 명시적으로 부여한 객체만 쓰기가 가능하고, 교차 계정에서는 프로듀서가 쓰기용으로 authorize하고 소비자가 특정 클러스터·워크그룹을 쓰기용으로 associate해야 한다 [S1]. 일부 문서는 아직 "읽기 목적" 공유로만 서술한다(G-4.5-02).
- **Lake Formation 관리 datashare**: Lake Formation 관리자가 Redshift datashare를 발견·등록하면 DB·테이블·열·행 수준 접근 권한을 Lake Formation에서 중앙 정의·집행한다 [S4]. 같은 계정·교차 계정 공유를 지원하고 교차 리전 공유는 지원하지 않는다 [S4]. 제약: 셀 수준 Lake Formation 필터 미지원, 프로듀서·소비자 클러스터 모두 암호화 필요, 프로듀서의 Redshift 행·열 수준 접근 제어 정책은 Lake Formation으로 공유할 때 무시되므로 Lake Formation에서 설정해야 한다 [S5].

| 방식 | 권한을 정하는 곳 | 교차 계정 | 교차 리전 | 특이점 |
|---|---|---|---|---|
| Redshift 데이터 공유 | 프로듀서의 GRANT USAGE·SHARE 등 [S3] | 가능: 프로듀서 authorize + 소비자 associate, 양쪽 클러스터 암호화 [S2] | 가능 [S1] | 쓰기는 프로듀서가 쓰기 권한을 부여한 객체만 [S1] |
| Lake Formation 관리 datashare | Lake Formation에서 DB·테이블·열·행 권한을 중앙 정의 [S4] | 가능 [S4] | 미지원 [S4] | 셀 수준 필터 미지원, Redshift 행·열 정책은 무시 [S5] |

### PII 식별 — Amazon Macie와 Lake Formation (Skill 4.5.2)

Macie는 S3 객체를 내장 기준·기법(머신러닝, 패턴 매칭)으로 분석해 민감 데이터를 찾고 finding을 만드는 서비스다 [S6]. "찾기"(Macie)와 "가리기·접근 통제"(Glue·Redshift DDM·Lake Formation)를 구분하는 것이 핵심이다.

- **두 가지 검색 방식**: 자동 민감 데이터 검색은 버킷 인벤토리를 지속 평가하고 표본으로 대표 객체를 골라 광범위한 가시성을 주고, 민감 데이터 검색 작업은 대상 버킷·샘플링 깊이·사용자 정의 조건을 지정한 정밀 분석이며 1회성 또는 반복 실행을 선택한다 [S6].
- **식별자**: 관리형 데이터 식별자는 PII·금융 정보·자격 증명 같은 민감 데이터 유형을 내장 기준으로 탐지하고, 사용자 지정 데이터 식별자는 정규식(regex)을 기본으로 선택적 문자 시퀀스와 근접 규칙을 더해 직접 정의한다 [S6].
- **결과 처리**: Macie는 정책 finding과 민감 데이터 finding을 EventBridge로 자동 게시하고, 설정하면 AWS Security Hub CSPM으로도 게시한다 [S7]. EventBridge로 Lambda·SNS 등 대상에 연결해 자동화할 수 있다 [S7].
- **암호화된 객체**: SSE-S3와 AWS 관리형 KMS 키 객체는 서비스 연결 역할로 복호화·분석할 수 있고, 고객 관리형 KMS 키는 Macie가 키를 쓰도록 허용해야 하며 허용하지 않으면 객체의 메타데이터만 저장·보고한다 [S8]. SSE-C와 클라이언트 측 암호화 객체는 복호화할 수 없어 메타데이터만 저장·보고한다 [S8].
- **Lake Formation과의 결합(공식 근거 범위)**: 제품 문서에서 Macie–Lake Formation 직접 연동 설정은 확인하지 못했고(G-4.5-01), 근거는 AWS 보안 블로그의 참조 아키텍처다. Macie가 S3 객체를 분석해 민감 값을 식별하면 Glue 워크플로가 그 정보로 데이터를 익명화(마스킹·암호화)하고, Lake Formation이 설정한 태그에 권한을 매핑해 사용자별 세분화 접근을 적용한다 [S9]. 식별 결과는 EventBridge → Firehose → S3로 보내 Glue가 마스킹할 필드를 알게 한다 [S9].

| S3 객체 암호화 | Macie 분석 가능 여부 |
|---|---|
| SSE-S3 | 가능 [S8] |
| AWS 관리형 KMS 키(SSE-KMS/DSSE-KMS) | 가능 [S8] |
| 고객 관리형 KMS 키 | Macie에 키 사용을 허용했을 때만 가능, 아니면 메타데이터만 [S8] |
| SSE-C | 불가(메타데이터만) [S8] |
| 클라이언트 측 암호화 | 불가(메타데이터만) [S8] |

### 허용되지 않는 리전으로의 백업·복제 방지 (Skill 4.5.3)

핵심은 "리전 호출 자체를 막는 통제"와 "복제·복사 구성을 막는 통제"가 다르다는 점이다.

- **aws:RequestedRegion 조건 키**: 요청에서 호출된 리전과 정책에 지정한 리전을 비교하며 요청 가능한 리전을 제어하는 데 쓴다 [S10]. IAM 같은 일부 글로벌 서비스는 엔드포인트가 하나(us-east-1)라서 "요청 리전이 X가 아니면 모든 서비스 거부" 정책을 쓰면 IAM 호출이 항상 실패하므로 NotAction 예외가 필요하다 [S10].
- **한계**: 이 조건 키는 호출되는 엔드포인트를 통제할 뿐 작업의 영향은 통제하지 않는다. S3는 API 작업이 리전에 걸쳐 영향을 주며, 한 리전에서 호출한 s3:PutBucketReplication이 복제 구성에 따라 다른 리전에 영향을 준다 [S10].
- **Control Tower Region deny**: 랜딩존 전체에 적용하는 컨트롤(AWS-GR_REGION_DENY)과 특정 OU에 적용하는 컨트롤(CT.MULTISERVICE.PV.1) 두 가지가 있다 [S11]. 홈 리전은 거부할 수 없고, IAM·Organizations 같은 일부 글로벌 서비스는 예외이며, 적용 전에 거부 대상 리전에 리소스가 있으면 적용 후 접근할 수 없게 된다 [S11].
- **S3 교차 리전 복제 금지**: Control Tower 선택적 예방 컨트롤(SCP 기반)이 S3 데이터를 단일 리전에 가두기 위해 자동·비동기 객체 복사를 비활성화한다. 기본으로 꺼져 있다 [S12].
- **AWS Backup 교차 리전 복사**: 백업을 주문형 또는 백업 계획에 따라 여러 리전에 복사할 수 있고, 복사본은 대상 볼트의 고객 관리형 키로 재암호화된다 [S13]. 허용되지 않는 리전으로의 복사를 막는 공식 통제 문구는 이번 조회에서 확인하지 못했다(G-4.5-03).

| 수단 | 통제 대상 | 한계·주의 |
|---|---|---|
| SCP/IAM `aws:RequestedRegion` Deny | 호출 리전 기준 모든 서비스 호출 [S10] | 글로벌 서비스 NotAction 예외 필요, S3 복제 구성의 다른 리전 영향은 통제 못함 [S10] |
| Control Tower 랜딩존 Region deny | 랜딩존에서 거버넌스 대상이 아닌 리전 접근 [S11] | 홈 리전 거부 불가, 일부 글로벌 서비스 예외 [S11] |
| Control Tower OU Region deny | 지정한 OU의 리전 접근 [S11] | 랜딩존 컨트롤과의 상호작용은 이 노트의 출처로 확인하지 못함(G-4.5-06) |
| Control Tower S3 교차 리전 복제 금지 | S3 교차 리전 복제 구성 [S12] | 선택적 컨트롤, 기본 꺼짐 [S12] |

### 구성 변경 조회 — AWS Config (Skill 4.5.4, v1.1 개정)

- **구성 이력·타임라인**: 구성 이력은 한 리소스의 구성 항목들을 기간별로 모은 것이다. 콘솔에서 리소스를 골라 타임라인으로 이전 구성 항목을 탐색하고 API로도 조회한다 [S14]. Config는 기록 대상 리소스 유형별 구성 이력 파일을 지정한 S3 버킷으로 전달한다 [S14].
- **보존 기간**: 콘솔에서 보존 기간을 고르지 않으면 기본 7년(2557일)이고, 사용자 지정은 30~2557일이다 [S15].
- **aggregator**: 여러 소스 계정·리전(또는 조직)의 구성·컴플라이언스 데이터를 한 계정으로 모아 보며 추가 비용이 없다. 읽기 전용 뷰라서 집계자를 통해 규칙을 배포하거나 스냅샷 파일을 소스 계정에 푸시할 수 없다 [S14].
- **고급 쿼리 vs 과거 이력**: 고급 쿼리는 중앙 계정에서 리소스의 현재 구성 상태를 쿼리하며 계정·리전·조직에 걸쳐 동작한다. 현재 상태 데이터만 조회하므로 과거 이력은 Athena로 Config history files를 조회한다 [S16].
- **CloudTrail과의 관계**: Config는 CloudTrail과 통합해 구성 변경을 특정 이벤트에 상관시킨다. 요청자·시각·IP 같은 호출 세부 정보는 CloudTrail 로그에서 얻는다 [S17].

| 알고 싶은 것 | 도구 |
|---|---|
| 리소스의 과거 구성·변경 타임라인 | AWS Config 구성 이력 [S14] |
| 변경을 일으킨 API 호출 주체·시각·IP | CloudTrail 로그(Config 타임라인과 연계) [S17] |
| 여러 계정·리전의 현재 구성/컴플라이언스를 한곳에서 | Config aggregator(읽기 전용) [S14] |
| 현재 구성 상태를 쿼리로 조회 | Config 고급 쿼리 [S16] |
| 과거 구성 상태를 쿼리로 조회 | Athena + Config history files [S16] |

### 데이터 주권 유지 (Skill 4.5.5, v1.1 개정)

- **용어**: 데이터 상주(residency)는 데이터를 특정 관할권에 두어야 하는 요건이고, 데이터 주권(sovereignty)은 데이터가 물리적 위치의 법과 규정의 적용을 받는 것이다 [S19].
- **AWS의 기본 약속**: 고객이 콘텐츠를 저장할 AWS 리전을 선택하고, AWS는 서비스 제공이나 법적 의무 같은 예외를 제외하고 선택한 리전 밖으로 콘텐츠를 이동·복제하지 않는다. 여러 리전에 복제·백업하는 것은 고객의 선택이다 [S18].
- **S3의 리전 격리**: 리전에 저장된 객체는 명시적으로 전송·복제하지 않는 한 그 리전을 떠나지 않는다 [S20].
- **실행 수단**: 주권·상주 요건은 (1) 저장 리전을 선택하고 (2) 데이터가 리전 밖으로 나가는 경로를 통제하는 것으로 구현한다 — Region deny, S3 교차 리전 복제 금지, 백업 복사 대상 관리 [S11][S12][S13]. 암호화 키 제어(Skill 4.3)는 별도 Task 노트 참조.

### SageMaker Catalog 프로젝트를 통한 데이터 접근 관리 (Skill 4.5.6, v1.1 신규)

도메인·도메인 단위·프로젝트·프로젝트 프로필 구조와 게시/구독의 개요는 `tasks/2-2.md`(Skill 2.2.6)와 `tasks/4-1.md`(Skill 4.1.7)를 참조하고, 여기서는 **접근 요청 → 승인 → 이행**에 집중한다.

- **구독 승인**: 소비 프로젝트가 카탈로그의 자산을 구독하면 구독 요청이 생기고 승인자가 승인하거나 거부한다. 승인자는 소유(게시) 프로젝트의 멤버여야 한다 [S21]. 기본값은 데이터 소유자의 수동 승인이다 [S21]. 승인할 때 전체 접근 또는 행·열 필터를 적용한 제한 접근을 고를 수 있다 [S21].
- **자동 승인**: 게시할 때 승인을 요구하지 않도록 설정했거나, 요청자가 게시 프로젝트와 요청 프로젝트 양쪽의 owner 또는 contributor인 경우 자동 승인된다 [S21].
- **이행(fulfillment)**: 승인 후 접근을 실제로 만드는 방식은 자산 유형에 따라 다르다.
  - Lake Formation 관리 Glue 테이블: 승인되면 SageMaker Unified Studio가 Lake Formation을 통해 승인된 테이블에 대한 접근을 부여·관리한다 [S22]. Glue 테이블은 Lake Formation 관리 상태여야 하고 게시 프로젝트의 IAM 역할에 해당 DB·테이블 DESCRIBE·SELECT(GRANTABLE 포함) 권한이 있어야 한다 [S22]. Lake Formation LF-TBAC 방식의 접근 관리는 지원하지 않는다 [S22].
  - Redshift 테이블·뷰: 승인되면 필요한 grant와 datashare를 만든다. 같은 DB면 원본 테이블에 직접 권한, 같은 클러스터의 다른 DB면 대상 DB에 뷰를 만들어 뷰에 권한, 같은 계정의 다른 클러스터면 datashare와 뷰, 교차 계정이면 프로듀서 쪽 authorize와 소비자 쪽 associate 단계가 추가된다. 교차 리전 Redshift 데이터 공유는 지원하지 않는다 [S23].

| 자산 유형 | 이행 방식 | 제약 |
|---|---|---|
| Lake Formation 관리 Glue 테이블 | Lake Formation 권한 부여·관리 [S22] | LF-TBAC 방식 관리 미지원 [S22] |
| Redshift 테이블·뷰 | grant + datashare(+뷰) 생성 [S23] | 교차 계정은 authorize·associate 추가, 교차 리전 미지원 [S23] |

### 거버넌스 데이터 프레임워크와 데이터 공유 패턴 (Skill 4.5.7, v1.1 신규)

- **데이터 메시 참조 구조**: 소비자·생산자·중앙 거버넌스 계층은 각각 독립된 데이터 도메인이며 보통 별도 AWS 계정에 둔다 [S24]. 연합 거버넌스 계층은 카탈로깅, 자산 검색, 권한 관리, 감사 이력용 중앙 로그를 맡는 중앙 거버넌스 도메인이다 [S24].
- **Lake Formation 교차 계정 공유**: 다른 AWS 계정과 DB·테이블을 공유하는 방법은 두 가지다 — 이름 지정 리소스 방식과 LF-TBAC(태그 기반) 방식 [S26]. 이름 지정 리소스 방식은 외부 계정에 권한을 줄 때 AWS RAM으로 리소스를 공유한다 [S26]. 대상 Data Catalog 객체가 많을 때는 LF-TBAC가 권장되며 LF-Tag는 IAM 태그와 다르다 [S25].
- **Redshift 데이터 공유**: Redshift 간 라이브 공유(위 4.5.1) [S1], 열·행 수준 중앙 통제가 필요하면 Lake Formation 관리 datashare [S4].
- **S3 Access Points**: 버킷에 붙는 이름 있는 네트워크 엔드포인트로, 공유 데이터셋에 대해 앱·팀별로 서로 다른 권한과 네트워크 제어를 줄 때 쓴다. 버킷당 최대 10,000개이며 같은 계정 또는 신뢰된 다른 계정의 버킷과 연결할 수 있고, 접근점 정책은 기반 버킷 정책과 함께 평가된다 [S27].
- **AWS Data Exchange for Amazon Redshift**: 제3자 데이터를 구독해 Redshift에서 바로 쿼리하며, 구독하면 접근이 자동 부여되고 구독이 끝나면 자동 회수된다 [S28].

| 수단 | 적합한 경우 | 제약·특이점 | 시험 단서 |
|---|---|---|---|
| Redshift 데이터 공유 | 웨어하우스 간 복사 없는 라이브 공유 [S1] | 교차 계정은 authorize+associate, 양쪽 암호화 [S2] | "클러스터 간·계정 간 최신 데이터 공유" |
| Lake Formation 교차 계정 공유 | 데이터 레이크 Data Catalog 테이블을 다른 계정과 [S26] | 이름 지정 리소스(RAM) vs LF-TBAC(권장) [S26][S25] | "열·행 수준 중앙 통제, 다계정 레이크" |
| Lake Formation 관리 datashare | Redshift 객체에도 LF 열·행 권한 적용 [S4] | 교차 리전·셀 수준 필터 미지원 [S4][S5] | "Redshift 공유 + LF 중앙 권한" |
| S3 Access Points | 공유 S3 데이터셋에 앱별 접근 정책 분리 [S27] | 버킷당 10,000개, 버킷 정책과 함께 평가 [S27] | "수많은 앱이 같은 버킷, 정책 분리" |
| AWS Data Exchange | 제3자 데이터 라이선스 구독 [S28] | 구독 종료 시 접근 자동 회수 [S28] | "외부 공급자 데이터 구독" |

## 시험에서 묻는 방식

1. **데이터 공유 수단 선택** — "복사·ETL 없이 다른 클러스터/계정이 최신 데이터를 쿼리", "교차 계정이면 누가 무엇을 승인하나"를 요구하면 → **Redshift 데이터 공유**(프로듀서 GRANT USAGE → 프로듀서 계정 관리자 authorize → 소비 계정 관리자 associate, 양쪽 클러스터 암호화)가 정답 방향. "Redshift 공유 객체에도 열·행 단위를 중앙에서 통제"하면 Lake Formation 관리 datashare(교차 리전·셀 수준 필터 미지원), "데이터 레이크 Data Catalog 테이블을 다른 계정과 공유"하면 Lake Formation 교차 계정 공유(LF-TBAC 권장, 이름 지정 리소스는 RAM), "같은 버킷의 많은 앱에 접근 정책 분리"는 S3 Access Points, "외부 공급자 데이터 구독"은 AWS Data Exchange. 오답 후보: 스냅샷 복원·UNLOAD/COPY(데이터를 복사·이동하는 방식), S3 Access Points를 Redshift 테이블 공유 수단으로 오해. 근거 [S1][S2][S3][S4][S5][S25][S26][S27][S28]
2. **PII 식별과 거버넌스** — "S3 데이터 레이크에서 PII 위치를 찾고 이후 열 단위 접근을 통제"를 요구하면 → **Macie 검색 작업(정밀) 또는 자동 검색(광범위)으로 탐지 → finding을 EventBridge로 전달 → Glue로 마스킹/암호화 → Lake Formation 태그로 권한 매핑**(AWS 보안 블로그 참조 아키텍처)이 정답 방향. 오답 후보: Macie 단독으로 마스킹·접근 통제를 기대(Macie는 탐지·finding), SSE-C·클라이언트 측 암호화 객체를 Macie가 분석한다는 가정(복호화 불가, 메타데이터만), 고객 관리형 KMS 키 사용을 허용하지 않고 검색 작업을 돌림(메타데이터만 보고). 근거 [S6][S7][S8][S9]
3. **리전 통제와 데이터 주권** — "데이터가 허용된 리전 밖으로 복제·백업되면 안 된다 / 데이터 상주·주권 요건"을 요구하면 → **SCP/Control Tower Region deny로 비허용 리전 호출을 막고(홈 리전·일부 글로벌 서비스는 예외), S3 교차 리전 복제는 aws:RequestedRegion만으로 막히지 않으므로 복제 구성을 막는 컨트롤(Control Tower의 S3 교차 리전 복제 금지)을 추가**하는 것이 정답 방향. AWS는 고객이 선택한 리전 밖으로 콘텐츠를 이동·복제하지 않고, S3 객체는 명시적 전송·복제 전에는 리전을 떠나지 않는다. 오답 후보: aws:RequestedRegion 하나로 CRR까지 차단된다는 가정, 암호화(KMS)나 AWS Config 조회를 차단 수단으로 선택. 근거 [S10][S11][S12][S18][S19][S20]
4. **구성 변경 조회 / SageMaker Catalog 구독 접근** — (a) "어제 리소스 구성이 시점별로 어떻게 바뀌었나"는 **AWS Config 구성 이력·타임라인**, "누가 호출했나"는 **CloudTrail**(Config 타임라인과 연계). 오답 후보: 고급 쿼리(현재 상태만 조회 → 과거 이력은 Athena로 history files), aggregator(읽기 전용, 규칙 배포 불가). (b) "SageMaker Catalog에서 프로젝트가 게시된 자산에 접근"은 **구독 요청 → 소유(게시) 프로젝트 멤버 승인(기본 수동) → 자산 유형별 이행**(Lake Formation 관리 Glue 테이블은 Lake Formation 권한 부여, Redshift 테이블·뷰는 grant+datashare). 오답 후보: LF-TBAC로 접근 관리(미지원), 교차 리전 Redshift 공유(미지원). 근거 [S14][S16][S17][S21][S22][S23]

## 흔한 함정·혼동 짝

1. **Redshift 데이터 공유 vs Lake Formation 관리 datashare** — 앞은 프로듀서가 GRANT로 소비자를 정하고, 뒤는 Lake Formation에서 DB·테이블·열·행 권한을 중앙 정의한다. 뒤는 교차 리전·셀 수준 필터 미지원이고 Redshift 자체 행·열 정책은 무시된다 → 단서: "열·행 수준 중앙 통제", "교차 리전" [S1][S4][S5]
2. **같은 계정·네임스페이스 공유 vs 교차 계정 공유** — 교차 계정만 프로듀서 authorize + 소비자 associate의 양방향 핸드셰이크와 양쪽 클러스터 암호화가 필요하고, 네임스페이스를 소비자로 추가할 때는 authorize가 필요 없다 → 단서: pending_authorization, "계정 ID로 GRANT USAGE" [S2][S3]
3. **"datashare는 읽기 전용" vs 쓰기 공유** — 쓰기가 추가되어, 프로듀서가 쓰기 권한을 명시적으로 부여한 객체만 쓰기 가능하고 교차 계정은 쓰기용 authorize·associate가 따로 필요하다 → 단서: "소비자가 프로듀서 테이블에 INSERT" [S1]
4. **Macie vs 마스킹·접근 통제 도구** — Macie는 S3 민감 데이터를 탐지해 finding을 EventBridge/Security Hub CSPM으로 보내는 서비스로 문서화되어 있고, 마스킹은 Glue 등, 접근 통제는 Lake Formation이 맡는다 → 단서: "PII 위치 찾기" vs "PII 가리기·열 단위 접근" [S6][S7][S9]
5. **Macie가 분석할 수 있는 암호화 vs 못 하는 암호화** — SSE-S3·AWS 관리형 KMS는 분석 가능, 고객 관리형 KMS는 키 사용 허용이 있어야 하고, SSE-C·클라이언트 측 암호화는 복호화 불가(메타데이터만) → 단서: "검색 작업이 일부 객체를 건너뜀" [S8]
6. **자동 민감 데이터 검색 vs 민감 데이터 검색 작업** — 자동 검색은 인벤토리를 지속 평가하며 표본으로 광범위한 가시성, 검색 작업은 버킷·샘플링 깊이·조건을 정해 정밀 분석(1회성/반복) → 단서: "전체 가시성" vs "특정 버킷 정밀" [S6]
7. **aws:RequestedRegion vs S3 복제 목적지** — 조건 키는 호출되는 엔드포인트만 통제하고 작업 영향은 통제하지 않아, 한 리전에서 호출한 PutBucketReplication이 다른 리전에 영향을 줄 수 있다. 복제는 별도 컨트롤로 막는다 → 단서: "허용 리전에서 복제 설정이 가능한가" [S10][S12]
8. **글로벌 서비스·홈 리전 예외** — IAM 같은 글로벌 서비스는 단일 엔드포인트라 NotAction 예외가 없으면 전체 Deny 정책에서 호출이 항상 실패하고, Control Tower Region deny도 홈 리전은 거부할 수 없으며 IAM·Organizations 등은 예외다 → 단서: "모든 리전 Deny 후 IAM 호출 실패" [S10][S11]
9. **Control Tower 랜딩존 Region deny vs OU Region deny** — 앞은 랜딩존 전체, 뒤는 지정한 OU에 적용한다 → 단서: "일부 OU만 EU 리전으로 제한" [S11]
10. **AWS Config vs CloudTrail** — Config는 리소스 구성 이력·타임라인, CloudTrail 로그는 변경을 일으킨 요청자·시각·IP를 알려 주며 둘은 연동된다 → 단서: "어떻게 바뀌었나" vs "누가 바꿨나" [S14][S17]
11. **Config 고급 쿼리 vs Athena(history files)** — 고급 쿼리는 현재 상태만, 과거 상태는 Athena로 Config history files를 조회한다 → 단서: "지난달 구성 상태를 쿼리" [S16]
12. **Config aggregator의 권한 범위** — 읽기 전용 뷰이며 집계자를 통해 규칙을 배포하거나 스냅샷을 푸시할 수 없다 → 단서: "중앙 계정에서 모든 계정에 규칙 배포(오답: aggregator)" [S14]
13. **데이터 상주 vs 데이터 주권** — 상주는 특정 관할권에 데이터를 두는 요건, 주권은 데이터가 위치한 곳의 법·규정이 적용된다는 개념이며 AWS는 고객이 선택한 리전 밖으로 콘텐츠를 이동·복제하지 않는다(예외: 서비스 제공·법적 의무) → 단서: "법적 관할", "리전 선택" [S19][S18]
14. **SageMaker 구독 승인 주체와 자동 승인** — 승인자는 소유(게시) 프로젝트 멤버이고 기본은 수동 승인이며, 게시 시 승인 비활성화나 양쪽 프로젝트 owner/contributor 요청자는 자동 승인된다 → 단서: "누가 구독을 승인하나" [S21]
15. **SageMaker 이행: Glue(Lake Formation) vs Redshift(datashare)** — Glue 테이블은 Lake Formation 관리여야 하고 LF-TBAC 접근 관리는 미지원, Redshift 자산은 grant+datashare이며 교차 리전 미지원 → 단서: "승인 뒤 어떤 권한이 만들어지나" [S22][S23]
16. **Lake Formation 이름 지정 리소스 vs LF-TBAC** — 이름 지정 방식은 리소스에 직접 부여하며 외부 계정에는 AWS RAM으로 공유하고, 대상이 많으면 LF-TBAC가 권장된다. LF-Tag와 IAM 태그는 서로 다른 것이다 → 단서: "수백 개 테이블 권한을 확장 가능하게" [S25][S26]
17. **S3 Access Points vs 버킷 정책 한 장** — 접근점마다 권한·네트워크 제어를 따로 두고(버킷당 최대 10,000개), 접근점 정책은 기반 버킷 정책과 함께 평가된다 → 단서: "앱별 정책 분리" [S27]
18. **AWS Data Exchange vs 내부 데이터 공유** — Data Exchange는 제3자 데이터 구독·라이선스이고 구독 종료 시 접근이 자동 회수된다. 조직 내부 공유는 Redshift 데이터 공유·Lake Formation을 쓴다 → 단서: "외부 공급자", "구독" [S28][S1]

### 후보 1 — Skill 4.5.1 · associate
- **문제**: 계정 A의 Redshift 프로듀서 클러스터에 있는 sales 스키마를 계정 B의 분석 팀이 복사나 ETL 없이 항상 최신 상태로 쿼리해야 한다. 가장 적합한 구성은?
- **보기**: A. 프로듀서에서 datashare를 만들어 계정 B에 GRANT USAGE한 뒤, 프로듀서 계정 관리자가 소비자를 authorize하고 계정 B 관리자가 datashare를 associate한다. / B. 스냅샷을 계정 B와 공유해 새 클러스터로 복원한다. / C. 계정 A에서 S3로 UNLOAD하고 계정 B가 COPY로 적재한다. / D. S3 Access Point를 만들어 계정 B에 접근을 부여한다.
- **정답**: A
- **해설 초안**: 데이터 공유는 계정에 걸쳐 라이브 데이터를 수동 이동·복사 없이 공유한다. 교차 계정은 프로듀서의 authorize와 소비 계정 관리자의 associate로 이루어진 양방향 핸드셰이크가 필요하고 양쪽 클러스터가 암호화되어야 한다. [S1][S2][S3]
- **오답 근거**: B, C — 스냅샷 복원과 UNLOAD/COPY는 데이터를 복사·이동하는 방식이라 "복사 없이 라이브 공유"라는 데이터 공유의 취지와 다르다 [S1] / D — Access Points는 S3 버킷에 붙는 네트워크 엔드포인트로 Redshift 테이블 공유 수단이 아니다 [S27]
- **근거**: [S2] https://docs.aws.amazon.com/redshift/latest/dg/across-account.html — "that there is a two-way handshake required in sharing data across AWS accounts"

### 후보 2 — Skill 4.5.2 · associate
- **문제**: Macie 민감 데이터 검색 작업이 한 S3 버킷의 일부 객체를 분석하지 못하고 메타데이터만 보고한다. 해당 객체는 고객이 제공한 키(SSE-C)로 암호화되어 있다. PII를 탐지하려면 어떻게 해야 하는가?
- **보기**: A. 객체를 SSE-S3 또는 Macie가 사용할 수 있는 KMS 키로 다시 암호화한다. / B. 검색 작업의 샘플링 깊이를 높인다. / C. 자동 민감 데이터 검색을 끄고 검색 작업만 실행한다. / D. 객체 메타데이터에 태그를 추가한다.
- **정답**: A
- **해설 초안**: SSE-C 객체는 Macie가 복호화할 수 없어 메타데이터만 저장·보고한다. 분석 가능 여부는 암호화 유형으로 정해지며, SSE-S3와 AWS 관리형 KMS 키 객체는 복호화할 수 있고 고객 관리형 KMS 키는 Macie에 키 사용을 허용하면 된다. [S8]
- **오답 근거**: B, C — 샘플링 깊이나 검색 방식(자동/작업)을 바꿔도 SSE-C 객체는 복호화할 수 없다 [S8] / D — 태그는 객체 내용 분석 가능 여부와 무관하며 복호화 가능 여부는 암호화 유형에 달려 있다 [S8]
- **근거**: [S8] https://docs.aws.amazon.com/macie/latest/user/discovery-supported-encryption-types.html — "(SSE-C), Macie can't decrypt the object."

### 후보 3 — Skill 4.5.3 · associate
- **문제**: 유럽 법인의 데이터는 허용된 EU 리전 밖으로 복제되면 안 된다. 조직(AWS Organizations)에는 aws:RequestedRegion 조건으로 EU 이외 리전의 호출을 Deny하는 SCP가 이미 적용되어 있지만, 허용 리전의 S3 버킷에서 다른 리전으로 향하는 교차 리전 복제 구성을 막지 못할 수 있다는 지적이 나왔다. 복제 구성 자체를 막는 가장 직접적인 조치는?
- **보기**: A. SCP로 S3 복제 구성 작업(s3:PutReplicationConfiguration)을 Deny한다(예: Control Tower의 S3 교차 리전 복제 금지 컨트롤). / B. 모든 버킷의 기본 암호화를 SSE-KMS로 바꾼다. / C. AWS Config aggregator를 만들어 복제 구성을 조회한다. / D. Control Tower 랜딩존의 홈 리전을 Region deny 대상에 추가한다.
- **정답**: A
- **해설 초안**: aws:RequestedRegion은 호출되는 엔드포인트만 통제하고 작업의 영향은 통제하지 않아, 허용 리전에서 호출한 PutBucketReplication이 복제 구성에 따라 다른 리전에 영향을 줄 수 있다. 복제 구성을 막으려면 S3 교차 리전 복제를 금지하는 SCP 기반 컨트롤이 필요하다. [S10][S12]
- **오답 근거**: B — SSE-KMS는 저장 시 암호화 설정이며 복제 목적지를 제한하지 않는다 / C — aggregator는 읽기 전용 조회 수단이라 차단 기능이 없다 [S14] / D — 홈 리전은 거부할 수 없다 [S11]
- **근거**: [S10] https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_condition-keys.html — "Amazon S3 has API operations that extend across regions."

### 후보 4 — Skill 4.5.4 · associate
- **문제**: 보안 팀이 특정 S3 버킷의 구성이 어제 시점별로 어떻게 바뀌었는지 확인하고, 그 변경을 일으킨 API 호출 주체까지 알아내려 한다. 가장 적합한 조합은?
- **보기**: A. AWS Config의 구성 이력·타임라인으로 변경 전후 구성을 보고, 연계된 CloudTrail 로그에서 호출 주체를 확인한다. / B. Config aggregator로 대상 계정에 규칙을 배포한다. / C. Config 고급 쿼리로 지난주의 구성 상태를 조회한다. / D. Amazon Macie 검색 작업을 실행한다.
- **정답**: A
- **해설 초안**: Config는 리소스별 구성 항목의 이력과 타임라인을 제공하고, CloudTrail과 통합되어 구성 변경을 이벤트에 상관시키며 요청자 같은 호출 세부 정보는 CloudTrail 로그에서 얻는다. [S14][S17]
- **오답 근거**: B — aggregator는 읽기 전용이라 집계자를 통해 규칙을 배포할 수 없다 [S14] / C — 고급 쿼리는 현재 상태 데이터만 조회하고 과거 이력은 Athena로 Config history files를 조회한다 [S16] / D — Macie는 S3 민감 데이터를 탐지하는 서비스다 [S6]
- **근거**: [S17] https://docs.aws.amazon.com/config/latest/developerguide/service-integrations.html — "AWS Config integrates with AWS CloudTrail to correlate configuration changes"

- **보기**: A. 필요한 grant와 datashare를 만들고, 소비자가 다른 계정이면 프로듀서 쪽 authorize와 소비자 쪽 associate 단계가 추가된다. / B. 테이블 데이터를 S3로 복사한 뒤 소비 프로젝트에 Lake Formation LF-Tag를 부여한다. / C. 교차 리전 Redshift datashare를 자동으로 만든다. / D. 소비 프로젝트 멤버가 직접 Redshift 스냅샷을 복원하도록 안내한다.
- **정답**: A

- **근거**: [S23] https://docs.aws.amazon.com/sagemaker-unified-studio/latest/userguide/grant-access-to-redshift-asset.html — "Under the hood, Amazon SageMaker Unified Studio creates the necessary"
