### 보안 그룹 — 네트워크 수준의 접근 경로 통제 (Skill 4.1.1)

VPC 안에서 도는 데이터 서비스(Glue 작업의 ENI, VPC에 붙인 Lambda 등)가 "어디서 오는 연결을 받아들이는가"를 정하는 가상 방화벽이다. 시험은 규칙 문법이 아니라 **어떤 서비스가 어떤 보안 그룹(SG) 규칙을 필요로 하는가**를 묻는다.

- 규칙은 허용(allow)만 쓸 수 있고 거부(deny) 규칙은 없다. [S1] 새 SG는 인바운드 규칙이 없어 인바운드가 전부 막히고, 아웃바운드는 전체 허용 규칙 하나가 기본으로 들어 있다. [S1] 한 리소스에 여러 SG를 붙이면 규칙이 합쳐져 하나의 규칙 집합으로 평가된다. [S1]
- SG는 상태 저장(stateful)이라 응답 트래픽이 반대 방향 규칙과 무관하게 허용되고, 네트워크 ACL은 stateless라 응답 트래픽을 자동 허용하지 않는다. [S2] SG 규칙을 바꿔도 기존 연결은 타임아웃될 때까지 계속 허용된다. [S2]
- 다른 SG를 소스/대상으로 참조하면 그 SG에 속한 리소스 전체에 규칙이 적용되며, 참조된 SG의 규칙이 복사되지는 않는다. [S1] 자기 자신을 소스로 쓰면 자기 참조(self-referencing) 규칙이며 소스를 같은 SG로 한정하는 효과가 있다. [S3]
- **AWS Glue**: VPC 안에서 도는 작업은 지정한 서브넷에 ENI를 만들며 사설 IP만 받고 공인 IP는 받지 않는다. [S4] 연결(connection)에 지정한 SG가 각 ENI에 적용된다. [S4] Glue 구성 요소끼리 통신하려면 **모든 TCP 포트에 대한 자기 참조 인바운드 규칙**이 필요하고, 소스가 같은 SG로 한정되므로 VPC를 모든 네트워크에 여는 것이 아니다. [S3] 공식 절차는 RDS가 쓰는 SG에 모든 TCP 포트의 자기 참조 인바운드 규칙을 추가하는 것이다. [S3] 아웃바운드를 제한한다면 자기 참조 아웃바운드 규칙에 더해 S3 게이트웨이 엔드포인트의 관리형 prefix list를 대상으로 하는 HTTPS 규칙을 둔다. [S3]
- Glue 연결 실패 점검 항목: 서브넷의 여유 IP가 워커 수보다 많아야 하고 [S5], VPC 밖 데이터(온프레미스, 퍼블릭 호스트명의 RDS)는 퍼블릭 서브넷의 NAT 게이트웨이 경로가 없으면 연결이 타임아웃되며 [S5], Secrets Manager·STS가 필요하면 엔드포인트를 붙여야 한다. [S5] 작업은 한 번에 하나의 VPC(서브넷)만 접근하고 [S4], VPC에서 S3에 접근하려면 VPC 엔드포인트가 필요하다. [S4]
- **Lambda(VPC 연결)**: 인터넷 경로 없이는 VPC 안 리소스에만 연결할 수 있다. [S6] 공용 서브넷에 붙여도 인터넷이 열리지 않으므로 사설 서브넷 + 공용 서브넷의 NAT 게이트웨이를 쓰고, AWS 서비스는 인터페이스 VPC 엔드포인트로 접근할 수 있다. [S6]
- **Secrets Manager 회전용 Lambda**: 회전 함수의 SG는 DB로의 아웃바운드를, DB의 SG는 회전 함수로부터의 인바운드를 허용해야 한다. [S16] (4.1.3 참조)

|---|---|---|---|

### IAM 사용자 그룹·역할·서비스 역할 (Skill 4.1.2)

IAM의 "누구인가"는 사용자, 역할(assume하면 임시 보안 자격 증명을 받는다 [S9]), 서비스가 맡는 역할로 갈린다. DEA 시험에서는 사람을 그룹으로 묶는 문제보다 **워크로드(Glue, Lambda, Redshift, EMR)가 어떤 역할을 맡아 접근하는가**가 훨씬 자주 나온다.

- IAM 사용자 그룹은 IAM 사용자의 모음이며, 그룹에 ID 기반 정책을 붙이면 구성원 모두가 그 권한을 받는다. [S7] 그룹은 중첩할 수 없고(사용자만 포함 가능) [S7], 그룹은 인증이 아니라 권한과 관련되므로 정책의 Principal로 지정할 수 없다. [S7]
- AssumeRole은 AWS 리소스 접근에 쓰는 임시 보안 자격 증명을 반환하며, 같은 계정 내 또는 교차 계정 접근에 쓴다. [S9] 역할 신뢰 정책은 "누가 assume 할 수 있는가"를, 권한 정책은 "무엇을 할 수 있는가"를 정한다. [S9]
- **서비스 역할(service role)**은 서비스가 사용자 대신 작업하려고 맡는 IAM 역할이며 IAM 관리자가 만들고 수정·삭제할 수 있다. [S8] **서비스 연결 역할(SLR)**은 AWS 서비스에 직접 연결된 특수한 서비스 역할로, 서비스가 권한(신뢰 정책 포함)을 미리 정의하고 IAM 관리자는 권한을 볼 수만 있고 편집할 수 없다. [S8] SLR을 지우려면 먼저 관련 리소스를 삭제해야 한다. [S8]

| 구분 | 정의·수정 주체 | 대표 사례(이 시험) | 시험 단서 | 근거 |
|---|---|---|---|---|
| IAM 사용자 그룹 | 관리자. 구성원 사용자는 각자 보안 자격 증명을 가짐 | 사람 팀에 권한 일괄 부여 | "그룹에 정책", "그룹은 Principal 불가" | [S7] |
| IAM 역할 | 관리자. 신뢰 정책 + 권한 정책 | Lambda 실행 역할, Redshift COPY용 역할 | "임시 자격 증명", "AssumeRole" | [S9] |
| 서비스 역할 | IAM 관리자가 생성·수정·삭제 가능 | EMR 서비스 역할, CloudFormation 서비스 역할, Glue 작업 역할 | "서비스가 사용자 대신" | [S8][S25] |
| 서비스 연결 역할(SLR) | 서비스가 정의, 관리자는 보기만 | EMR의 Spot 인스턴스 요청용 SLR | "서비스가 소유한 역할", "편집 불가" | [S8][S25] |

### VPC 엔드포인트 — Gateway vs Interface (Skill 4.1.2, 4.1.5)

사설 서브넷의 워크로드가 인터넷 게이트웨이·NAT 없이 AWS 서비스에 사설 경로로 접근하게 하는 구성이다. 시험은 (1) 유형 선택(S3·DynamoDB는 Gateway·Interface 둘 다 지원 [S10]), (2) 엔드포인트 정책으로 범위 제한을 묻는다.

- **Gateway 엔드포인트**: S3·DynamoDB용이며 인터넷 게이트웨이나 NAT 장치 없이 연결을 제공하고 AWS PrivateLink를 쓰지 않는다. [S10] 추가 요금이 없다. [S10] 라우팅 테이블에 지정하는 게이트웨이 방식이라 [S11] 온프레미스, 다른 AWS 리전에서의 접근은 허용하지 않으며, 그런 경우에는 요금이 청구되는 인터페이스 엔드포인트를 써야 한다. [S11]
- **Interface 엔드포인트**(AWS PrivateLink 기반): 서브넷의 사설 IP를 받는 ENI로 구성되며, S3에서는 VPC 내부, VPN·Direct Connect로 연결된 온프레미스, 피어링/Transit Gateway로 연결한 다른 리전 VPC에서 접근할 수 있고 요금이 청구된다. [S11] 같은 VPC에 게이트웨이 엔드포인트가 이미 있어도 둘을 함께 쓸 수 있다. [S11] 프라이빗 DNS를 켜면 S3 클라이언트를 엔드포인트 전용 DNS 이름으로 바꾸지 않고도 리전 DNS 이름이 사설 IP로 해석되며, 게이트웨이 엔드포인트가 함께 있으면 VPC 내부 요청은 요금이 없는 게이트웨이로, 온프레미스 요청은 인터페이스 엔드포인트로 보내 비용을 줄일 수 있다(온프레미스는 인바운드 Resolver 엔드포인트가 DNS 질의를 전달). [S11]
- **엔드포인트 정책**: 엔드포인트에 붙이는 리소스 기반 정책으로 그 엔드포인트를 쓸 수 있는 주체와 접근 가능한 리소스를 제한한다. [S12] ID 기반 정책·대상 서비스의 리소스 기반 정책을 대체하지 않고 엔드포인트를 지나는 트래픽에만 적용되는 추가 경계이며, 사용자 정의 정책을 붙이지 않으면 전체 접근을 허용하는 기본 정책이 붙는다. [S12]

|---|---|---|---|
| 대상 서비스 | S3, DynamoDB | PrivateLink 기반(S3도 가능) | [S10][S11] |
| 접근 방식 | 라우팅 테이블 항목, S3 퍼블릭 IP·동일 DNS 이름 사용 | VPC 사설 IP 사용, 엔드포인트 전용 DNS 이름 필요(프라이빗 DNS 옵션을 켜면 기존 리전 DNS 이름으로도 사설 IP로 해석) | [S11] |
| 온프레미스 접근 | 불가 | 가능 | [S11] |
| 다른 리전 VPC | 불가 | VPC 피어링/Transit Gateway로 가능 | [S11] |

### 자격 증명 생성·회전 — AWS Secrets Manager (Skill 4.1.3)

DB 암호·API 키를 코드에 넣지 않고 Secrets Manager에 저장하고 **주기적으로 자동 교체(rotation)**하는 방법을 묻는다. 핵심은 "누가 회전을 수행하는가(관리형 vs Lambda)"와 "회전 중 무중단을 어떻게 보장하는가(single user vs alternating users)"이다.

- 회전 방식은 둘로 나뉜다. **관리형 회전**은 서비스가 회전을 설정·관리하며 Lambda 함수를 쓰지 않고 [S13], 그 밖의 비밀은 **Lambda 회전 함수**가 비밀과 DB/서비스의 자격 증명을 갱신한다. [S15] 관리형 회전은 Aurora·RDS·DocumentDB의 마스터 사용자 자격 증명과 Redshift 관리자 암호 등에서 제공된다. [S13]
- 관리형 회전은 보통 1분 안에 끝나며, 회전 중 새 연결이 이전 버전 자격 증명을 받을 수 있다. [S13] 애플리케이션 사용자에는 마스터 사용자 대신 최소 권한 DB 사용자를 쓰고, 최고 가용성이 필요하면 alternating users 전략을 쓰라고 권고한다. [S13]
- 회전 전략은 두 가지다. **single user**는 비밀에 든 사용자의 자격 증명을 갱신하고, **alternating users**는 한 비밀에서 두 사용자를 번갈아 갱신해 새 자격 증명을 테스트하는 동안에도 다른 사용자의 자격 증명이 유효하므로 가용성이 더 높다. [S14]
- Lambda 회전 함수는 4단계(createSecret → setSecret → testSecret → finishSecret)를 수행하며, 스테이징 레이블로 회전 중 비밀의 버전을 구분한다. [S15] createSecret이 새 값을 AWSPENDING 레이블로 저장하고, setSecret이 DB/서비스의 자격 증명을 AWSPENDING 값에 맞게 바꾸고, testSecret이 AWSPENDING 값으로 접속을 시험하며, finishSecret이 AWSCURRENT 레이블을 새 버전으로 옮기면서 이전 버전에 AWSPREVIOUS를 붙여 마지막으로 정상이던 버전을 보존한다. [S15]
- AWSPENDING이 AWSCURRENT와 다른 버전에 남은 채 회전이 끝나면, 이후 회전 호출은 이전 회전이 아직 진행 중이라고 보고 오류를 반환한다. [S15] 회전이 실패하면 AWSPENDING이 빈 비밀 버전에 붙어 있을 수 있다. [S15]
- 스케줄은 `rate()`/`cron()` 표현식(UTC 기준)이며 [S17] 최소 4시간 간격까지 설정할 수 있다. [S17] 일 단위 지정(AutomaticallyAfterDays)은 1~1000이다. [S17]
- 네트워크: 회전 Lambda는 Secrets Manager 엔드포인트(인터넷/NAT 경로 또는 VPC 인터페이스 엔드포인트)와 대상 DB에 모두 접근할 수 있어야 하고, 두 방향의 SG 규칙이 열려 있어야 한다. [S16]
- 교차 계정 접근: 리소스 정책과 ID 정책에서 **모두** 허용해야 하며 [S18], AWS 관리형 키(aws/secretsmanager)로는 교차 계정 접근이 불가하므로 직접 만든 KMS 키로 암호화하고 키 정책을 붙여야 한다. [S18]

| 구분 | 관리형 회전 | Lambda 회전 |
|---|---|---|
| 수행 주체 | 해당 서비스가 설정·관리(Lambda 불필요) [S13] | 사용자가 소유한 Lambda 회전 함수 [S15] |
| 대표 대상 | Aurora·RDS·DocumentDB 마스터 사용자, Redshift 관리자 암호 [S13] | 그 밖의 비밀(예: 애플리케이션 DB 사용자, API 키) [S13][S16] |
| 운영 부담 | 낮음 | 함수 코드·실행 역할·네트워크·SG 관리 [S15][S16] |
| 시험 단서 | "Lambda 없이", "운영 오버헤드 최소", "마스터 사용자 암호" | "애플리케이션 사용자", "사용자 정의 비밀·API 키" |

| 전략 | 동작 | 가용성 | 근거 |
|---|---|---|---|
| single user | 비밀에 든 한 사용자의 자격 증명 갱신 | alternating users보다 낮음(alternating이 "더 높은 가용성 옵션") | [S14] |
| alternating users | 한 비밀에서 두 사용자를 번갈아 갱신. 첫 회전에서 사용자를 복제해 두 번째 사용자 생성 | 더 높음(새 자격 증명을 테스트하는 동안 다른 사용자가 유효) | [S14] |

### 서비스용 IAM 역할 설정 (Skill 4.1.4)

질문은 늘 같다. **어떤 서비스/사용자가 어떤 역할을 맡아(assume) 무엇에 접근하는가**, 그리고 **그 역할을 누가 전달(PassRole)할 수 있는가**.

- **Lambda 실행 역할**: 함수가 AWS 서비스·리소스에 접근할 권한을 주는 IAM 역할이다. [S19] 함수를 호출하면 Lambda가 실행 역할을 자동으로 assume하므로 함수 코드에서 sts:AssumeRole을 직접 호출하지 않아야 한다. [S19] 콘솔이 기본 생성하는 역할에는 CloudWatch Logs 쓰기 권한을 주는 AWSLambdaBasicExecutionRole 관리형 정책이 들어간다. [S19]
- **API Gateway**: 메서드의 권한 부여 유형으로 IAM(AWS_IAM), Cognito 사용자 풀(COGNITO_USER_POOLS), Lambda 권한 부여자(CUSTOM)를 고를 수 있다. [S21] IAM 권한 부여를 쓰면 API Gateway가 호출자 자격 증명으로 서명된 요청을 검증하며 [S21], SigV4/SigV4a 서명을 지원한다. [S20] 호출자에게는 execute-api:Invoke 같은 작업을 허용하는 IAM 정책을 붙인다. [S20] 다른 계정의 사용자는 API 소유자 계정의 역할을 assume할 수 있을 때만 호출할 수 있다. [S21] API가 Lambda 같은 백엔드와 통합될 때는 API Gateway가 대신 접근하도록 apigateway.amazonaws.com을 신뢰하는 서비스 역할을 별도로 만든다. [S20]
- **AWS CLI**: config 파일의 프로파일에 role_arn과 source_profile(또는 credential_source)을 지정하면 CLI가 AssumeRole 호출을 자동으로 수행한다. [S22] 역할 설정 변수는 CLI config 파일에만 둘 수 있다. [S22]
- **CloudFormation**: 기본값은 호출한 IAM 주체의 자격 증명으로 스택 작업을 수행한다(그래서 주체가 템플릿의 리소스를 만들 권한도 있어야 한다). [S23] 서비스 역할을 전달하면 CloudFormation이 그 역할로 작업하므로 사용자에게 리소스 생성 권한을 직접 줄 필요가 없다. [S23] 이때 사용자는 스택 작업 권한과 해당 역할을 전달할 권한(iam:PassRole)이 있어야 한다. [S23]
- **Amazon Redshift COPY/UNLOAD**: 클러스터가 대신 assume할 IAM 역할(Amazon Redshift 서비스 역할 유형)을 만들어 클러스터에 연결하고, COPY에서 IAM_ROLE 파라미터로 지정한다. [S24] IAM 연합 세션으로 접속하면 클러스터 역할을 쓰는 대신 현재 세션의 자격 증명으로 적재하는 IAM_ROLE 'SESSION'도 가능하다. [S24]
- **Amazon EMR**: 클러스터마다 서비스 역할(EMR 역할: 리소스 프로비저닝·서비스 수준 작업), EC2 인스턴스 프로파일 역할(클러스터 인스턴스에서 도는 애플리케이션이 AWS 서비스를 호출할 때), 자동 확장 역할(자동 확장 클러스터만)이 있다. [S25] Spot 인스턴스를 요청하려면 서비스 연결 역할이 필요하다. [S25]
- **AWS Glue**: 작업이 쓰는 IAM 역할을 만들며, 콘솔 사용자가 역할을 서비스에 전달할 수 있도록 이름을 AWSGlueServiceRole로 시작하게 만드는 규칙이 있다. 다른 이름이면 사용자에게 iam:PassRole 권한 정책을 추가해야 한다. [S26]

| 서비스 | 필요한 역할 | 핵심 포인트 | 시험 단서 | 근거 |
|---|---|---|---|---|
| Lambda | 실행 역할 | Lambda가 자동 assume, 코드에서 AssumeRole 호출 금지 | "Lambda가 S3/DynamoDB에 접근" | [S19] |
| API Gateway | IAM 인증 / Cognito / Lambda 권한 부여자 + 백엔드용 서비스 역할 | IAM 인증은 SigV4 서명 + execute-api:Invoke | "서명된 요청", "다른 계정 호출" | [S20][S21] |
| AWS CLI | 프로파일의 role_arn + source_profile/credential_source | config 파일에서만 | "CLI에서 다른 역할로 전환" | [S22] |
| CloudFormation | 서비스 역할(선택) | 미지정 시 호출자 권한 사용, 지정 시 PassRole 필요 | "사용자에게 직접 권한을 주지 않고 배포" | [S23] |
| Redshift COPY/UNLOAD | 클러스터에 연결한 IAM 역할 또는 'SESSION' | 역할 ARN은 IAM_ROLE로 전달 | "COPY로 S3 데이터 적재" | [S24] |
| EMR | 서비스 역할 / EC2 인스턴스 프로파일 / 자동 확장 역할 | 모든 클러스터에 EMR 역할·인스턴스 프로파일 필요 | "EMR 클러스터 시작 오류", "노드에서 S3 접근" | [S25] |
| Glue | 작업 IAM 역할(AWSGlueServiceRole 접두 규칙) | 접두어 불일치 시 iam:PassRole 필요 | "콘솔 사용자가 Glue 역할 선택 불가" | [S26] |

### 역할·엔드포인트·서비스에 IAM 정책 적용 (Skill 4.1.5)

정책을 "어디에 붙이는가"에 따라 평가가 달라진다. 이 Skill의 예시로 든 S3 Access Points 정책 [S32]과 PrivateLink(VPC 엔드포인트) 정책 [S12]이 각각 리소스 기반 정책의 한 형태다.

- **ID 기반 정책**은 IAM 사용자·그룹·역할에 붙어 그 ID가 할 수 있는 일을 정하며 관리형 또는 인라인이다. [S27] **리소스 기반 정책**은 S3 버킷, SQS 큐, VPC 엔드포인트, KMS 키 등에 붙어 접근할 수 있는 주체와 작업을 정하며 인라인만 가능하다. [S27]
- 평가의 기본: 요청은 기본적으로 암시적 거부이고 명시적 허용이 있어야 통과하며, **명시적 거부는 명시적 허용을 이긴다**. [S28]
- S3 버킷 정책 예시: 같은 계정에서는 ID 기반 정책 **또는** 버킷 정책에 권한이 있으면 되고, 다른 계정에서는 버킷 정책 **그리고** ID 기반 정책 둘 다 필요하다. [S29]
- **S3 Access Points**: 버킷에 붙은 이름 있는 네트워크 엔드포인트로, 액세스 포인트마다 별도의 권한·네트워크 제어를 둘 수 있고 액세스 포인트 정책은 기본 버킷 정책과 함께 평가되는 리소스 기반 정책이다. [S32] 버킷 정책으로 접근 제어를 액세스 포인트에 위임해, 버킷에 대한 모든 접근을 액세스 포인트에 붙은 정책으로 통제할 수 있다(s3:DataAccessPointAccount 조건 키). [S30] 액세스 포인트는 하나의 버킷에만 연결되고 정책 크기는 20 KB로 제한되며 계정·리전당 최대 개수가 정해져 있다. [S31]
- **VPC 엔드포인트 정책(PrivateLink)**: 4.1.2의 엔드포인트 정책 항목 참조 — ID 기반·리소스 기반 정책을 대체하지 않는 추가 경계다. [S12]

| 정책 유형 | 붙는 곳 | Principal 요소 | 평가 포인트 | 근거 |
|---|---|---|---|---|
| ID 기반(관리형/인라인) | 사용자·그룹·역할 | 없음(붙은 ID가 주체) | 같은 계정 S3 예: 버킷 정책과 OR | [S27][S29] |
| 리소스 기반(인라인만) | S3 버킷, 큐, 키, 엔드포인트 등 | 지정 | 교차 계정: ID 기반 정책과 AND | [S27][S29] |
| VPC 엔드포인트 정책 | VPC 엔드포인트 | 지정 | 추가 경계(대체 아님), 기본값은 전체 허용 | [S12] |
| S3 액세스 포인트 정책 | 액세스 포인트 | 지정 | 버킷 정책과 함께 평가, 버킷 정책으로 위임 가능 | [S30][S32] |

### 관리형 서비스 vs 비관리형 서비스 (Skill 4.1.6)

판단 기준은 **공동 책임 모델에서 고객이 어디까지 책임지는가**다. 많이 관리해 주는 서비스일수록 운영·패치 책임은 줄지만 데이터·IAM 책임은 남는다.

- AWS는 인프라, 고객은 그 위의 보안(클라우드 "안")을 책임진다. 책임 범위는 고객이 고르는 서비스에 따라 달라진다. [S33]
- EC2는 IaaS라 게스트 OS(업데이트·보안 패치), 설치한 애플리케이션, 보안 그룹 구성은 고객 책임이다. [S33] S3·DynamoDB 같은 추상화된 서비스는 AWS가 인프라 계층·OS·플랫폼을 운영하고, 고객은 데이터 관리(암호화 옵션 포함)와 IAM 권한 적용을 책임진다. [S33]
- 관리형 서비스는 패치·취약점 관리 같은 일부 보안 작업을 AWS가 맡아 고객의 보안·규정 준수 의무를 줄여 주고, 관리형 서비스 사용은 Well-Architected 모범 사례다. [S34]
- Amazon EMR은 Apache Hadoop·Spark 같은 빅데이터 프레임워크 실행을 단순화하는 관리형 클러스터 플랫폼이다. [S35]

| 구분 | 비관리형(예: EC2에 직접 설치한 DB·Hadoop) | 관리형(예: S3·DynamoDB·EMR) |
|---|---|---|
| OS·패치 | 고객 [S33] | AWS가 인프라·OS·플랫폼 운영(추상화 서비스) [S33] |
| 네트워크 방화벽 | 고객이 보안 그룹 구성 [S33] | 서비스마다 다름(예: Glue VPC 연결은 고객이 지정한 SG가 ENI에 적용 — 4.1.1 참조) [S4] |
| 데이터·IAM | 고객 [S33] | 여전히 고객(데이터, 암호화 옵션, IAM 권한) [S33] |
| 시험 단서 | "게스트 OS 패치·애플리케이션 보안을 직접" | "패치·취약점 관리 부담을 줄이려면" → 관리형 서비스 [S34] |

### Amazon SageMaker Unified Studio — 도메인·도메인 단위·프로젝트 (Skill 4.1.7, v1.1 신규)

SageMaker Unified Studio는 데이터 분석·머신러닝·AI 개발 기능을 함께 제공하는 환경이며 [S36], 이 Skill은 그 **조직 구조(도메인 → 도메인 단위 → 프로젝트)**와 그 위의 권한 위임을 묻는다. 도메인 아래에 (상위/하위) 도메인 단위가 있고 [S38][S39], 프로젝트는 도메인 단위에 속하며 [S41] 프로젝트 프로필로 만든다. [S41]

- **도메인(domain)**: 자산·사용자·프로젝트를 연결하는 조직 단위(organizing entity)다. 전사에 하나만 두거나 사업부별로 여러 개를 둘 수 있다. [S36]
- 도메인 유형은 두 가지다. **IAM Identity Center 기반 도메인**은 IAM Identity Center로 사용자 인증·관리를 하며 SSO를 지원하고, **IAM 기반 도메인**은 IAM 역할과 IAM Identity Center로 인증·접근 제어를 하며 연합 IAM 역할을 실행(execution) IAM 역할로 쓴다. [S36] 두 유형은 같은 핵심 기능을 제공하지만 인증 방식과 설정 절차가 다르다. [S36]
- IAM 기반 도메인은 IAM 역할로 도메인을 만들고, 도메인 안 프로젝트도 IAM 역할로 데이터·인프라에 접근하며, 프로젝트마다 로그인용 IAM 역할이 하나 지정된다. [S37] IAM 기반 도메인은 계정(문서에 따라 "계정당" 또는 "계정·리전당")당 하나만 둘 수 있고 [S36][S37], 한 IAM 기반 도메인은 여러 프로젝트를 지원한다. [S37]
- **도메인 단위(domain unit)**: 자산과 기타 도메인 엔티티를 사업부·팀 단위로 조직한다. [S38] 새 도메인 단위를 만들 때 상위(parent) 도메인 단위를 지정하므로 계층 구조가 가능하다. [S39] 도메인 단위는 계정 소유자로부터 도메인 단위 소유자에게 위임된 권한을 제공해, 소유자가 프로젝트 프로필 같은 리소스에 대한 권한 설정을 대신 할 수 있다. [S38] 그래서 사업부별로 프로젝트 프로필을 만들고 쓸 수 있는 사람을 제한할 수 있고, 메타데이터 표준을 강제하는 데도 쓸 수 있다. [S38]
- 도메인 단위에서 사용자·그룹에 줄 수 있는 권한 정책: 도메인 단위 생성 정책, 프로젝트 생성 정책, 프로젝트 멤버십 정책, 도메인 단위 소유권 인수 정책, 프로젝트 소유권 인수 정책. 프로젝트에 줄 수 있는 정책: 용어집 생성, 메타데이터 폼 생성, 사용자 정의 자산 유형 생성 정책. [S38]
- **프로젝트 프로필(project profile)**: 프로젝트용 "상위 템플릿"이며 블루프린트(프로젝트 생성에 쓰는 구성)의 모음이다. 프로젝트 생성 시 특정 블루프린트를 켜 둘지, 나중에 사용자가 켜게 할지 정할 수 있다. [S40] 템플릿 프로필로 All capabilities, SQL analytics, Generative AI application development, Custom이 있다. [S40]
- **프로젝트(project)**: 도메인 안에서 사용자들이 비즈니스 용도로 협업하는 경계이며, 프로젝트에서 데이터와 리소스를 만들고 공유한다. [S41] 프로젝트에서 쓸 수 있는 도구·리소스는 만들 때 사용한 프로젝트 프로필에 따라 정해진다. [S41] 프로젝트에 참여하려면 직접 만들거나 프로젝트 소유자가 추가해야 하며 [S41], 프로젝트를 다른 도메인 단위로 옮길 수 있다. [S41]
- **멤버십**: 멤버 역할은 Contributor와 Owner 두 가지다. Owner는 기여에 더해 멤버 추가·제거, 설명 편집, 프로젝트 삭제가 가능하고 프로젝트를 만든 사람이 기본 Owner다. [S42] 멤버는 사용자·SSO 그룹·IAM 주체(역할/사용자)가 될 수 있으며 프로젝트당 최대 20명이다. [S42]
- **거버넌스 관점의 차이**: IAM Identity Center 기반 도메인은 개인 신원을 유지한 ID 기반 권한 부여, 사용자 간 세분화된 접근 제어, 승인 절차가 있는 게시자/구독자 데이터 공유 워크플로 등 거버넌스에 강점이 있고, IAM 기반 도메인은 연합 IAM 역할로 인증하여 한 프로젝트에 접근하는 모든 사용자가 같은 역할 권한을 공유한다. [S43]

## 시험에서 묻는 방식

1. **VPC 경로 진단(Glue 연결·보안 그룹)** — "사설 서브넷의 RDS에 Glue 작업(JDBC)이 연결하지 못함 / 연결 테스트 실패 / 보안 팀이 0.0.0.0/0 개방 금지"를 요구하면 → 정답 방향: 연결 SG에 **모든 TCP 포트 자기 참조 인바운드 규칙(소스=같은 SG)**을 두고, 아웃바운드를 제한했다면 자기 참조 아웃바운드 + S3 prefix list(HTTPS) 규칙, 그리고 서브넷 여유 IP·NAT/엔드포인트 경로를 점검한다. 오답 후보와 탈락 이유: 0.0.0.0/0 전체 TCP 허용(자기 참조 규칙은 VPC를 모든 네트워크에 열지 않는 대안), 네트워크 ACL에 거부 규칙 추가(SG에는 거부 규칙이 없고 NACL은 stateless라 응답을 자동 허용하지 않음), RDS·Glue에 공인 IP 할당(Glue ENI는 사설 IP만 받음). 근거 [S1][S2][S3][S4][S5].
2. **엔드포인트 유형·범위 선택(Gateway / Interface / 엔드포인트 정책 / S3 Access Points)** — "사설 서브넷에서 S3·DynamoDB를 NAT 없이, 추가 비용 없이" → Gateway 엔드포인트. "온프레미스 또는 다른 리전 VPC에서 S3에 사설 경로로" → Interface 엔드포인트(요금 발생). "엔드포인트를 지나는 요청을 특정 버킷/주체로 제한" → 엔드포인트 정책(기본값은 전체 허용이며 IAM·버킷 정책을 대체하지 않는 추가 경계). "수십 개 팀이 한 버킷을 공유하며 팀별 정책·네트워크 제어가 필요" → S3 Access Points + 버킷 정책의 접근 제어 위임. 오답 후보와 탈락 이유: 온프레미스에 Gateway 엔드포인트(온프레미스 접근 불가), 엔드포인트 정책만으로 권한 부여(ID·리소스 정책과 별개의 추가 경계), 정책의 Principal에 IAM 그룹 지정(그룹은 Principal 불가). 근거 [S7][S10][S11][S12][S30][S32].
3. **자격 증명 회전 설계(Secrets Manager)** — "RDS/Aurora/DocumentDB 마스터 사용자 또는 Redshift 관리자 암호를 최소 운영으로 자동 교체" → 관리형 회전(Lambda 없음). "애플리케이션 DB 사용자·API 키 등 그 외 비밀" → Lambda 회전 함수(회전 함수의 네트워크·SG·실행 역할 구성 필요). "회전 중에도 끊김 최소화" → alternating users 전략. "다른 계정 소비자가 비밀을 읽어야 함" → 리소스 정책 + ID 정책 + 직접 만든 KMS 키. 오답 후보와 탈락 이유: AWS 관리형 키(aws/secretsmanager)로 교차 계정 접근(불가), VPC 안 회전 Lambda에 Secrets Manager 엔드포인트 경로 누락(회전 함수가 비밀에 접근하지 못함), 관리형 회전 대상(마스터 사용자)에 굳이 사용자 정의 Lambda 작성(운영 부담만 증가). 근거 [S13][S14][S15][S16][S18].
4. **서비스 간 위임·SageMaker Unified Studio 설계** — "개발자에게 리소스 생성 권한을 직접 주지 않고 CloudFormation으로만 배포" → CloudFormation 서비스 역할 + 사용자에 iam:PassRole. "Redshift COPY로 S3 데이터 적재" → 클러스터에 연결한 IAM 역할(IAM_ROLE). "EMR 인스턴스에서 도는 애플리케이션이 S3 접근" → EC2 인스턴스 프로파일 역할. "SageMaker Unified Studio에서 사업부별로 프로젝트 생성 권한·프로젝트 프로필 사용을 위임" → 도메인 단위 + 도메인 단위 권한 정책. "SSO 없이 IAM 역할로 프로젝트 접근" → IAM 기반 도메인(계정당 하나). 오답 후보와 탈락 이유: 사용자에게 리소스 생성 권한을 직접 부여(서비스 역할 접근 방식의 반대), 모든 프로젝트 멤버를 Owner로 지정(Owner는 멤버 추가·제거와 삭제까지 가능), 사업부마다 IAM 기반 도메인을 추가(IAM 기반 도메인은 계정당 하나). 근거 [S23][S24][S25][S37][S38][S42].

## 흔한 함정·혼동 짝

1. **보안 그룹 vs 네트워크 ACL** — SG는 허용 규칙만 있고 stateful(응답 자동 허용), NACL은 stateless라 응답 트래픽을 자동 허용하지 않는다. → 시험 단서: "거부 규칙", "응답 트래픽". 규칙을 바꿔도 SG의 기존 연결은 타임아웃 전까지 유지된다. [S1][S2]
2. **Glue 자기 참조 규칙 vs 0.0.0.0/0 개방** — 자기 참조 규칙은 소스를 같은 SG로 한정해 VPC를 모든 네트워크에 열지 않는다. → 시험 단서: "Glue 구성 요소 간 통신", "전체 개방 금지". [S3]
3. **Glue 연결 SG 문제 vs 서브넷/경로 문제** — SG가 맞아도 서브넷 여유 IP 부족, NAT/엔드포인트 경로 부재(S3·Secrets Manager·STS)로 실패할 수 있다. → 시험 단서: "워커 수", "연결 타임아웃", "VPC 밖 데이터". [S4][S5]
4. **Gateway vs Interface 엔드포인트** — Gateway는 S3·DynamoDB 전용·무료·온프레미스 불가, Interface는 PrivateLink 기반·유료·온프레미스/다른 리전 VPC 가능. → 시험 단서: "추가 비용 없이" vs "온프레미스에서 사설 접근". [S10][S11]
5. **엔드포인트 정책 vs IAM(ID 기반) 정책** — 엔드포인트 정책은 ID 기반·리소스 기반 정책을 대체하지 않고 엔드포인트 경유 트래픽에만 겹쳐 적용되는 추가 경계이며 기본값은 전체 허용. → 시험 단서: "엔드포인트를 통한 요청만 특정 버킷으로 제한". [S12]
6. **서비스 역할 vs 서비스 연결 역할(SLR)** — 서비스 역할은 관리자가 만들고 수정할 수 있고, SLR은 서비스가 권한을 정의하며 관리자는 보기만 한다. → 시험 단서: "서비스가 소유", "편집 불가", "Spot 요청". [S8][S25]
7. **IAM 사용자 그룹 vs 역할** — 그룹은 사용자 묶음(중첩 불가, 정책 Principal 불가)이고, 역할은 assume하여 임시 자격 증명을 받는다. → 시험 단서: "리소스 정책에 그룹 지정", "임시 자격 증명". [S7][S9]
8. **같은 계정 접근 vs 교차 계정 접근(S3 예)** — 같은 계정은 ID 기반 정책 OR 버킷 정책, 교차 계정은 버킷 정책 AND ID 기반 정책. → 시험 단서: "다른 계정의 역할이 버킷 접근". [S29]
9. **명시적 거부 vs 암시적 거부** — 기본은 암시적 거부이고 명시적 거부는 어떤 허용도 이긴다. → 시험 단서: "허용했는데도 AccessDenied". [S28]
10. **관리형 회전 vs Lambda 회전** — 관리형은 서비스가 설정·관리(Lambda 없음, 마스터/관리자 자격 증명), 그 외 비밀은 Lambda 함수가 회전. → 시험 단서: "Lambda 없이", "운영 오버헤드 최소". [S13][S15]
11. **single user vs alternating users** — alternating은 두 사용자를 번갈아 갱신해 새 자격 증명 테스트 중에도 다른 쪽이 유효(가용성 높음). → 시험 단서: "회전 중 무중단". [S14]
12. **AWSCURRENT vs AWSPENDING vs AWSPREVIOUS** — PENDING은 검증 전 새 버전, finishSecret이 CURRENT를 새 버전으로 옮기고 이전 버전에 PREVIOUS를 붙인다. PENDING이 CURRENT와 다른 버전에 남으면 다음 회전은 오류. → 시험 단서: "회전이 이미 진행 중이라는 오류". [S15]
13. **AWS 관리형 KMS 키(aws/secretsmanager) vs 고객 관리형 키** — 교차 계정으로 비밀을 공유하려면 직접 만든 KMS 키와 키 정책이 필요하다. → 시험 단서: "다른 계정에서 비밀 조회 불가". [S18]
14. **EMR 서비스 역할 vs EC2 인스턴스 프로파일 vs 자동 확장 역할** — 서비스 역할은 프로비저닝 등 서비스 수준 작업, 인스턴스 프로파일은 노드에서 도는 애플리케이션의 AWS 호출, 자동 확장 역할은 자동 확장을 쓰는 클러스터만. → 시험 단서: "노드의 Spark가 S3 접근". [S25]
15. **CloudFormation 호출자 자격 증명 vs 서비스 역할** — 서비스 역할을 전달하지 않으면 호출자의 자격 증명으로 스택 작업을 수행하므로 호출자가 리소스 생성 권한도 가져야 한다. → 시험 단서: "개발자에게 직접 권한을 주지 않고". [S23]
16. **API Gateway IAM 인증 vs Cognito 사용자 풀 vs Lambda 권한 부여자** — AWS_IAM / COGNITO_USER_POOLS / CUSTOM 세 가지 권한 부여 유형. → 시험 단서: "SigV4 서명", "토큰 검증 로직". [S21][S20]
17. **S3 액세스 포인트 정책 vs 버킷 정책** — 액세스 포인트마다 정책이 있고 버킷 정책과 함께 평가되며, 버킷 정책으로 접근 제어를 액세스 포인트에 위임할 수 있다. → 시험 단서: "다수 팀이 한 버킷 공유". [S30][S32]
18. **VPC 연결 Lambda: 공용 서브넷 vs 사설 서브넷 + NAT** — 공용 서브넷에 붙여도 인터넷이 열리지 않는다. → 시험 단서: "VPC Lambda가 외부 API 호출 실패". [S6]
19. **IAM Identity Center 기반 도메인 vs IAM 기반 도메인(SageMaker Unified Studio)** — 인증이 IAM Identity Center(SSO)인가 연합 IAM 역할인가. IAM 기반은 계정당 하나이고 프로젝트마다 IAM 역할 하나. → 시험 단서: "SSO", "프로젝트 멤버가 같은 역할 권한 공유". [S36][S37]
20. **도메인 단위 vs 프로젝트(SageMaker Unified Studio)** — 도메인 단위는 사업부·팀 단위로 자산과 엔티티를 조직하고 권한을 위임하는 계층, 프로젝트는 그 안에서 협업하는 경계. → 시험 단서: "사업부별 위임", "프로젝트 프로필 사용 제한". [S38][S41]
21. **자가 관리(EC2) vs 관리형/추상화 서비스** — EC2는 OS·패치·SG 구성까지 고객 책임이고, 관리형 서비스는 일부를 AWS가 맡지만 데이터·IAM 책임은 남는다. → 시험 단서: "운영 오버헤드 감소", "패치 책임". [S33][S34]

### 후보 1 — Skill 4.1.1 · associate
- **문제**: AWS Glue ETL 작업이 사설 서브넷에 있는 Amazon RDS for PostgreSQL에 JDBC 연결로 접속해야 한다. 보안 정책상 0.0.0.0/0 인바운드는 허용할 수 없다. Glue 구성 요소 간 통신을 허용하면서 노출을 최소화하는 구성은?
- **보기**: A. Glue 연결의 보안 그룹에 소스가 0.0.0.0/0인 모든 TCP 인바운드 규칙을 추가한다. / B. Glue 연결의 보안 그룹에 소스가 같은 보안 그룹(자기 자신)인 모든 TCP 포트 인바운드 규칙을 추가한다. / C. 서브넷의 네트워크 ACL에 모든 인바운드 트래픽을 거부하는 규칙을 추가한다. / D. Glue 작업이 쓰는 ENI에 공인 IP를 할당한다.
- **정답**: B
- **해설 초안**: Glue 구성 요소끼리 통신하려면 모든 TCP 포트에 대한 자기 참조 인바운드 규칙이 필요하고, 소스가 같은 SG로 한정되므로 VPC를 모든 네트워크에 열지 않는다. [S3]
- **오답 근거**: A — 전체 개방이라 요구사항 위반(자기 참조 규칙이 그 대안) [S3] / C — 네트워크 ACL은 stateless이고 거부 규칙은 통신을 막을 뿐 Glue 통신을 허용하지 않는다 [S2] / D — Glue ENI는 서브넷의 사설 IP만 받는다 [S4]
- **근거**: [S3] https://docs.aws.amazon.com/glue/latest/dg/setup-vpc-for-glue-access.html — "specify a security group with a self-referencing inbound rule for all TCP ports"

### 후보 2 — Skill 4.1.3 · associate
- **문제**: Amazon Aurora MySQL 클러스터의 마스터 사용자 암호를 정기적으로 자동 교체해야 한다. 팀은 회전용 Lambda 코드를 직접 작성·운영하고 싶지 않다. 운영 부담이 가장 적은 방법은?
- **보기**: A. Secrets Manager에서 Aurora가 마스터 사용자 자격 증명에 제공하는 관리형 회전을 사용한다. / B. 사용자 정의 Lambda 회전 함수를 작성해 VPC 안에 배포한다. / C. 암호를 Lambda 환경 변수에 저장하고 EventBridge 일정으로 환경 변수를 갱신한다. / D. 비밀을 AWS 관리형 키로 암호화하고 교차 계정 접근을 설정한다.
- **정답**: A
- **해설 초안**: Aurora·RDS·DocumentDB의 마스터 사용자 자격 증명은 관리형 회전을 제공하며, 관리형 회전은 Lambda 함수를 쓰지 않는다. [S13]
- **오답 근거**: B — Lambda 코드·실행 역할·네트워크·SG를 직접 관리해야 해 요구사항에 어긋난다 [S15][S16] / C — Secrets Manager의 회전 기능을 쓰지 않고 회전을 직접 구현해야 한다 / D — 교차 계정 공유와 무관하며 AWS 관리형 키로는 교차 계정 접근이 불가하다 [S18]
- **근거**: [S13] https://docs.aws.amazon.com/secretsmanager/latest/userguide/rotate-secrets_managed.html — "offers managed rotation for master user credentials"

### 후보 3 — Skill 4.1.2 · associate (서비스 선택)
- **문제**: 온프레미스 데이터센터의 배치 서버가 이미 구성된 사설 연결로 VPC에 접속해 있고, 인터넷을 거치지 않고 Amazon S3 버킷에 접근해야 한다. 이 VPC에는 S3 게이트웨이 엔드포인트가 이미 있다. 무엇을 추가해야 하는가?
- **보기**: A. 게이트웨이 엔드포인트가 연결된 라우팅 테이블을 온프레미스 라우터로 전파한다. / B. S3용 인터페이스 VPC 엔드포인트를 추가하고 온프레미스에서 엔드포인트 전용 DNS 이름으로 접근한다. / C. 게이트웨이 엔드포인트 정책에 온프레미스 CIDR 범위를 허용 규칙으로 추가한다. / D. 퍼블릭 서브넷에 NAT 게이트웨이를 만들어 온프레미스 트래픽을 전달한다.
- **정답**: B
- **해설 초안**: 게이트웨이 엔드포인트는 온프레미스 접근을 허용하지 않고, 인터페이스 엔드포인트는 사설 IP로 온프레미스에서도 S3에 접근하게 해 준다(요금 청구). 두 유형은 같은 VPC에서 함께 쓸 수 있다. [S11]
- **오답 근거**: A — 게이트웨이 엔드포인트는 온프레미스 접근 자체가 불가하다 [S11] / C — 엔드포인트 정책은 접근 가능한 주체·리소스를 제한하는 추가 경계일 뿐 새 경로를 만들지 않는다 [S12] / D — NAT 게이트웨이는 인터넷 경로를 만드는 구성이며 사설 접근 요구에 맞지 않는다
- **근거**: [S11] https://docs.aws.amazon.com/AmazonS3/latest/userguide/privatelink-interface-endpoints.html — "Do not allow access from on premises"

### 후보 4 — Skill 4.1.5 · associate (서비스 선택)
- **문제**: 여러 팀이 하나의 S3 데이터 레이크 버킷을 공유한다. 팀마다 접근 가능한 프리픽스와 네트워크 경로(VPC 한정 여부)가 다르고, 단일 버킷 정책이 복잡해져 변경이 어렵다. 팀별로 정책을 분리하고 버킷 정책은 한 번만 설정하려면?
- **보기**: A. 팀별 S3 액세스 포인트를 만들고 버킷 정책으로 접근 제어를 액세스 포인트에 위임한다. / B. 버킷 정책의 Principal에 팀별 IAM 사용자 그룹 ARN을 지정한다. / C. VPC 엔드포인트 정책으로 팀별 프리픽스 접근 권한을 부여한다. / D. 팀마다 버킷을 따로 만들고 S3 복제로 데이터를 동기화한다.
- **정답**: A
- **해설 초안**: 액세스 포인트마다 별도의 정책이 있고, 버킷 정책에서 접근 제어를 액세스 포인트에 위임하면 버킷에 대한 접근이 액세스 포인트에 붙은 정책으로 통제된다. [S30][S32]
- **오답 근거**: B — 사용자 그룹은 정책의 Principal로 지정할 수 없다 [S7] / C — 엔드포인트 정책은 ID 기반·리소스 기반 정책을 대체하지 않는 추가 경계다 [S12] / D — 요구사항은 정책 분리이며 데이터 복제·버킷 증설은 불필요한 관리 부담이다
- **근거**: [S30] https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-points-policies.html — "all access to this bucket is controlled by the policies attached to its access points"
