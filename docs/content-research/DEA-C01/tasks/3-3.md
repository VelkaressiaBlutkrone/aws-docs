## 핵심 개념

> 이 문서는 파이프라인 **운영·모니터링·성능 문제 해결** 관점이다. 감사용 로그의 **준비·보존·중앙화·무결성**(CloudTrail 상세, CloudWatch Logs 보존·암호화·교차 계정, CloudTrail Lake)은 Task 4.4 문서가 다룬다. 두 문서에서 CloudTrail·CloudWatch Logs 내용이 겹치는 부분은 이 문서가 "운영·알림·분석"을, 4.4가 "감사 준비·보존"을 맡는다.

### 감사용 로그 추출 수단 (Skill 3.3.1)

감사 대응에서는 이미 쌓인 기록을 증거로 꺼낼 **경로**를 원천별로 고르는 것이 핵심이다. 원천마다 저장 위치·지연·완전성이 다르다.

- CloudTrail **이벤트 기록(Event history)**은 설정 없이 쓸 수 있지만, 현재 보고 있는 리전의 최근 90일, 그것도 생성·수정·삭제 API 호출 같은 **관리 이벤트로 한정**된다. 데이터 이벤트와 읽기 전용 활동까지 포함한 완전한 기록은 trail을 만들어야 한다 [S1]. trail이 없어도 콘솔·CLI·API(`lookup-events`)로 최근 90일을 조회할 수 있다 [S1].
- **trail**은 이벤트를 S3, CloudWatch Logs, CloudWatch Events(EventBridge)로 전달하며 [S1], 이벤트는 보통 API 호출 후 5분 안에 도착한다 [S1].
- **CloudWatch Logs → S3 내보내기**(`CreateExportTask`)는 비동기 호출로 시작하는 배치성 작업이다 [S6]. 동시에 활성인 내보내기 작업 수에는 계정·리전별 한도가 있다(quotas 표 참조) [S7]. API 문서는 로그를 계속 아카이브하는 용도로는 정기적 내보내기 대신 구독을 쓰라고 권고하며, 대상 S3 버킷이 KMS로 암호화되었거나 보존 기간이 지정된 Object Lock이 켜져 있어도 내보내기를 지원한다 [S6].
- **구독 필터**는 로그 이벤트를 Kinesis Data Streams·Amazon Data Firehose·Lambda로 거의 실시간 전달한다. 전달 데이터는 base64로 인코딩되고 gzip으로 압축되며, Standard 로그 클래스에서만 지원된다 [S5]. OpenSearch Service로의 준실시간 스트리밍도 구독으로 구성한다 [S5].
- **S3 요청 로그**는 두 갈래다. AWS는 버킷·객체 수준 동작 기록에는 CloudTrail을 권장한다 [S34]. 비교표상 CloudTrail은 로그 파일 무결성 검증(서명·해시)과 접두사(prefix) 단위 부분 로깅을 지원하지만 서버 액세스 로그는 지원하지 않고, 반대로 수명 주기 전환·만료와 인증 실패 요청은 서버 액세스 로그만 기록한다 [S34].
- **VPC Flow Logs**는 CloudWatch Logs, S3, Amazon Data Firehose로 게시할 수 있다 [S1].
- **Redshift**: 감사 로깅(연결 로그·사용자 로그·사용자 활동 로그)은 기본으로 꺼져 있고 켜면 CloudWatch Logs로 내보내거나 S3에 업로드한다. 사용자 활동 로그는 `enable_user_activity_logging` 파라미터도 켜야 남는다. 시스템 테이블 로깅은 선택이 아니라 자동이다 [S26].
- **Glue·EMR 작업 로그**는 각각 CloudWatch Logs(Glue)와 노드 로컬 → S3 아카이브(EMR)로 나간다. 상세는 Skill 3.3.6 소제목 참조.

| 로그 원천 | 꺼내는 수단 | 지연·제약 | 시험 단서 키워드 |
|---|---|---|---|
| CloudTrail 이벤트 | Event history(콘솔·`LookupEvents`) / trail → S3·CloudWatch Logs·EventBridge | 이벤트 기록은 리전별 90일·관리 이벤트만 / trail은 보통 5분 [S1] | "지난 90일", "데이터 이벤트", "장기 보관" |
| CloudWatch Logs | 구독 필터(준실시간) / `CreateExportTask`(배치) | 구독은 Standard 클래스만 [S5], 내보내기는 활성 작업 수 한도 [S7] | "실시간 전달", "S3로 아카이브" |
| S3 요청 로그 | CloudTrail 데이터 이벤트 / S3 서버 액세스 로그 | 무결성 검증은 CloudTrail만, 수명 주기 동작·인증 실패는 서버 액세스 로그만 [S34] | "객체 수준 감사", "무결성" |
| VPC 네트워크 | VPC Flow Logs → CloudWatch Logs·S3·Firehose | 게시 대상 선택 [S1] | "IP 트래픽 로그" |
| Redshift | 감사 로그(S3·CloudWatch Logs), 시스템 테이블 | 감사 로깅 기본 꺼짐 [S26] | "연결·사용자·사용자 활동 로그" |

### 감사·추적성을 위한 로깅/모니터링 배포 (Skill 3.3.2)

추적성은 세 질문으로 나누면 서비스가 갈린다. **누가 호출했나**(CloudTrail), **리소스 구성이 어떻게 바뀌었나**(AWS Config), **지금 상태·로그는 어떤가**(CloudWatch).

- **CloudTrail 배포**: 모든 리전에 적용하는 trail(`IsMultiRegionTrail`=true)은 새로 추가되는 리전도 자동으로 기록하고 [S1], 설정 복제는 보통 30초 안에 끝난다 [S1]. 리전당 trail은 최대 5개이며 모든 리전 trail은 각 리전에서 1개로 센다 [S1]. 조직 trail은 관리 계정과 모든 멤버 계정의 이벤트를 같은 S3 버킷·CloudWatch Logs·EventBridge로 전달하고 [S2], 콘솔에서 만든 조직 trail은 모두 멀티 리전이다 [S2]. 무결성 검증·KMS·버킷 정책은 Task 4.4.1에서 다룬다.
- **CloudTrail → CloudWatch Logs 통합**을 켜면 예를 들어 보안 그룹·네트워크 ACL을 만들고 바꾸고 지우는 API 호출에 대해 CloudWatch 경보를 만들어 SNS로 알림을 받을 수 있다 [S1]. 이때 표준 CloudWatch Logs·CloudWatch 요금이 별도로 붙는다 [S1].
- **AWS Config**: 지원 리소스가 바뀔 때마다 구성 항목(configuration item)을 만들고, 리소스 유형별 구성 이력 파일을 지정한 S3 버킷에 자동 전달한다 [S35]. 한 리소스가 짧은 시간에 연속 변경되면 최종 상태를 나타내는 구성 항목 하나만 생길 수 있어, CloudTrail 이벤트와 구성 항목을 시간·리소스 ID로 조회해도 누가 무엇을 바꿨는지 완전히 대응시키지 못할 수 있다 [S1].
- **CloudWatch**: 지표·경보·대시보드. 대시보드는 AWS 리소스와 사용자 지정 지표의 그래프를 만들고 저장하는 기능이다 [S4].
- **서비스별 로그 설정**: Glue는 4.0 이하에서 연속 로깅을 켜 CloudWatch Logs로 보내고 5.0부터는 모든 작업이 실시간 로깅 기능을 갖는다 [S17]. Spark UI를 켜면 Spark 이벤트 로그를 지정한 S3 경로에 쓴다 [S18]. EMR은 노드의 `/mnt/var/log/`를 S3로 아카이브하도록 클러스터에 로그 경로를 지정한다 [S22]. Redshift는 감사 로깅을 켠다 [S26].

| 서비스 | 답하는 질문 | 기록 단위 | 시험 단서 키워드 |
|---|---|---|---|
| CloudTrail | 누가·언제·어디서 어떤 API를 호출했나 | API 호출 이벤트(요청자, 사용 서비스, 작업, 파라미터, 응답 요소) [S1] | "누가 삭제", "API 호출 추적" |
| CloudWatch Logs | 애플리케이션·서비스가 무엇을 출력했나 | 로그 그룹/스트림의 로그 이벤트 [S4] | "애플리케이션 로그", "로그 패턴에 경보" |
| AWS Config | 리소스 구성이 시간에 따라 어떻게 바뀌었나 | 구성 항목(CI)·구성 이력 파일·구성 스냅샷 [S35] | "구성 변경 이력", "규정 준수 변화" |

### 모니터링 알림 (Skill 3.3.3)

알림 경로는 **지표 기반(CloudWatch 경보)**, **이벤트 기반(EventBridge 규칙)**, **로그 기반(메트릭 필터 → 경보 / 구독 필터)** 세 가지로 나뉜다.

- **CloudWatch 경보**: 지표를 고르고 평가 기간(분·시간 단위)과 통계(Average, Maximum 등), 비교 연산자·임계값을 정한다 [S4]. 작업으로 이메일, SQS 게시, EC2 중지·종료, Auto Scaling 정책 실행을 걸 수 있고 SNS와 통합되어 SNS가 지원하는 모든 알림 유형을 쓸 수 있다 [S4]. 임계값 위반이 이어지면 경보는 ALARM 상태를 유지하는데 정상 동작이다 [S4]. 복합 경보는 여러 경보를 계층으로 묶어 동시에 울리는 경보를 한 번만 알려 소음을 줄인다 [S4]. 고해상도 사용자 지정 지표에는 초 단위 주기의 고해상도 경보를 걸 수 있다 [S4].
- **누락 데이터 처리**: 경보는 누락된 데이터 포인트를 `notBreaching`, `breaching`, `ignore`, `missing` 중 하나로 취급한다. 기본값은 `missing`이다 [S11]. `AWS/DynamoDB` 네임스페이스 지표를 평가하는 경보는 기본이 `ignore`다 [S11]. 연속 보고되는 지표라면 누락을 `breaching`으로 볼 수 있지만, DynamoDB `ThrottledRequests`처럼 오류가 날 때만 데이터가 생기는 지표는 `notBreaching`이 맞다 [S11].
- **이벤트 기반(EventBridge → SNS·Lambda 등)**: Glue는 `Glue Job State Change`(SUCCEEDED, FAILED, TIMEOUT, STOPPED)와 지연 알림 임계값을 설정해야 받는 `Glue Job Run Status`(RUNNING, STARTING, STOPPING) 이벤트를 발행하고, 문서 예시는 ETL 작업 성공 시 Lambda 실행·실패 시 SNS 통지다 [S13]. Step Functions는 `Step Functions Execution Status Change` 이벤트를 보내며 status는 RUNNING, SUCCEEDED, FAILED, TIMED_OUT, ABORTED, PENDING_REDRIVE 중 하나다 [S14]. EMR은 `EMR Step Status Change`, `EMR Cluster State Change` 등을 발행한다 [S16]. Redshift는 이벤트 구독으로 SNS에 알리며 SNS 표준 주제만 쓸 수 있고(FIFO 불가) 소스 유형·ID·범주(Monitoring, Security 등)·심각도(INFO, ERROR)로 필터링한다 [S15].
- **로그 기반**: 메트릭 필터는 로그에서 찾은 용어·패턴을 CloudWatch 지표로 바꿔 그래프나 경보에 쓰게 한다 [S4]. 구독 필터는 로그 이벤트를 Lambda 등으로 실시간 전달한다 [S5].

| DynamoDB | `ThrottledRequests`, `ReadThrottleEvents`, `WriteThrottleEvents` | 요청 단위 지표(`ThrottledRequests`)는 규모를 가릴 수 있어 이벤트 단위 지표와 비교 | [S33] |

- **Athena**: 파일은 분할(split) 크기가 약 128 MB가 되도록 맞추는 것이 일반 지침이다. Parquet·ORC 같은 분석용 포맷은 항상 분할 가능하지만 압축된 텍스트 파일 대부분은 분할되지 않아 단일 split으로 처리된다 [S28]. 과도한 파티셔닝은 작은 파일을 낳고, 최악의 경우 S3 요청 한도 때문에 쿼리가 실패할 수 있다 [S28]. 파티션 프로젝션은 파티션 값·위치를 테이블 속성 설정으로 계산해 Data Catalog 조회를 피하며, 켜면 Glue Data Catalog에 등록된 파티션 메타데이터는 무시된다 [S29].
- **Redshift**: 자동 WLM은 ML로 메모리·동시성을 동적으로 관리한다. WLM 큐를 여러 개 정의해 워크로드를 분리하고 쿼리 우선순위를 줄 수 있으며, 단기 쿼리 가속(SQA)은 기본 파라미터 그룹에서 기본 활성이다 [S27]. 동시성 확장은 기본으로 꺼져 있고 WLM 큐별로 켠다(AUTO) [S27]. 최대 동시성 확장 클러스터 수는 1(기본)~10(소프트 한도)이다 [S27]. QMR 지표(`query_cpu_time` 등)는 규칙을 만들지 않아도 자동 수집되며 `SVL_QUERY_METRICS_SUMMARY` 등으로 본다 [S27]. 테이블 유지 관리는 서비스가 자동화하는 쪽으로 이동했고 Advisor가 통계 누락·오래됨에 ANALYZE를 권고한다 [S27].
- **Glue**: DPU는 4 vCPU와 16 GB 메모리의 상대 측정 단위다 [S21]. 최대 필요 executor는 실행 중 태스크와 대기 태스크 수를 더해 executor당 태스크 수로 나눠 계산하고, 활성 executor와 비교해 과소 할당 배율을 구한다 [S20]. 동시 실행 한도(`MaxConcurrentRuns`) 기본값은 1이고 초과하면 오류가 반환된다 [S21].
- **Kinesis**: 이터레이터 나이가 보존 기간(기본 24시간, 최대 365일)의 50%를 넘으면 레코드 만료로 인한 데이터 손실 위험이 있으며, 임시 방편은 보존 기간 연장이고 근본 해결은 소비 로직 점검과 샤드 증설을 통한 병렬성 확대다 [S38]. 이 지표는 Maximum 통계에 경보를 걸어 두는 것이 권장된다 [S31]. 읽기·쓰기 쓰로틀 지표는 소비자·생산자 쪽 처리량 한도 초과 여부를 가른다 [S31].

### CloudTrail로 API 호출 추적 (Skill 3.3.5)

CloudTrail은 "누가 어떤 API를 호출했는가"의 기록이다. 이벤트에는 요청자, 사용한 서비스, 수행한 작업, 작업 파라미터, 응답 요소가 담긴다 [S1]. 콘솔·SDK·CLI·상위 AWS 서비스가 부르는 API 호출은 모두 기록된다 [S1].

| 이벤트 유형 | 기본 로깅 | 내용 | 비용·특성 | 시험 단서 |
|---|---|---|---|---|
| 관리 이벤트 | trail·이벤트 데이터 스토어가 기본 기록 [S2] | 리소스 관리(control plane) 작업, `ConsoleLogin` 같은 비 API 이벤트 포함 [S2] | 리전별 첫 사본 무료, 추가 사본은 유료 [S1] | "IAM 정책 변경", "콘솔 로그인" |
| 데이터 이벤트 | 기본 비활성 [S3] | 리소스 안/위의 데이터 평면 작업: S3 객체 수준 API(`GetObject`, `DeleteObject`, `PutObject`), Lambda `Invoke`, SNS `Publish` 등 [S3] | 대용량이 많고 추가 요금 [S3] | "S3 객체 삭제 주체", "Invoke 기록" |
| Insights 이벤트 | trail 설정에서 켜야 기록 [S1] | API 호출량·오류율이 기준선에서 벗어난 비정상 활동 탐지 [S1] | 개별 trail에 구성, 이벤트는 콘솔·CloudWatch Events·S3·선택적으로 CloudWatch Logs로 전달 [S1] | "비정상 급증", "스크립트 오작동" |
| 네트워크 활동 이벤트 | 설정에서 명시적으로 켜야 기록 [S1] | VPC 엔드포인트로 AWS 서비스를 호출한 API 활동(허용·거부 모두) [S1] | 추가 요금, VPC 엔드포인트 소유자에게만 전달 [S1] | "VPC 엔드포인트 정책 거부" |

- **이벤트 선택기**: 데이터 이벤트는 고급 이벤트 선택기로 필드(예: `eventName`)를 필터링해 관심 있는 이벤트만 기록하면 비용을 통제할 수 있다 [S3]. trail에서는 S3 객체(범용 버킷)·Lambda 함수·DynamoDB 테이블 데이터 이벤트에 기본(basic)·고급(advanced) 선택기를 모두 쓸 수 있고, 나머지 리소스 유형은 고급 선택기만 쓰며 이벤트 데이터 스토어는 고급 선택기만 쓴다 [S3].
- **읽기/쓰기 구분**: trail이나 이벤트 데이터 스토어는 읽기 전용, 쓰기 전용, 둘 다 중 무엇을 기록할지 정할 수 있다 [S3].
- **Event history와 trail**: Event history는 현재 리전 최근 90일·관리 이벤트이며 무료다. 데이터 이벤트·읽기 전용 활동을 포함한 완전한 기록은 trail이 필요하다 [S1].
- **Insights**: 개별 trail에 구성하므로 trail이 먼저 있어야 한다. 관리·데이터 이벤트를 모니터링하며 비정상 이벤트는 기준선에서 벗어난 API 호출량으로 정의된다 [S1]. 조직 trail로 조직 전체에 켤 수도 있다 [S1].
- **중복 이벤트**: CloudTrail은 최소 1회 전달을 목표로 설계되어 같은 이벤트가 두 번 올 수 있으며 중복 이벤트는 같은 `eventID`를 갖는다 [S1]. 로그를 파이프라인으로 적재할 때 `eventID`로 중복 제거해야 한다.

### 파이프라인 트러블슈팅·유지 관리 — Glue·EMR (Skill 3.3.6)

**AWS Glue**
- **로그**: 4.0 이하는 연속 로깅(`--enable-continuous-cloudwatch-log`)을 켜야 하며 사용자 지정 로그 그룹·스트림 접두사·변환 패턴을 줄 수 있고 기본 로그 그룹은 `/aws-glue/jobs/logs-v2`다. 5.0부터는 모든 작업이 실시간 로깅 기능을 갖는다 [S17]. 버전을 지정하지 않고 만든 작업의 기본 Glue 버전은 5.1이다 [S21].
- **Spark UI**: Apache Spark 웹 UI로 Glue ETL 작업을 모니터링·디버깅할 수 있고, 콘솔에서 Spark 이벤트 로그를 쓸 S3 경로를 입력한다 [S18].
- **작업 북마크**: 처리한 소스 데이터를 추적해 재처리를 막는다. Enable은 상태를 갱신하며 새 데이터만 처리, **Disable이 기본값**이며 매번 전체 데이터셋을 처리, Pause는 상태를 갱신하지 않고 마지막 성공 실행 이후 증분을 처리한다 [S19]. S3 입력은 객체의 마지막 수정 시각으로 재처리 대상을 판단하므로 수정된 파일은 다시 처리된다 [S19].
- **재시도·시간 제한·동시 실행**: `MaxRetries`는 JobRun 실패 후 재시도 횟수, `Timeout`은 실행이 자원을 쓸 수 있는 최대 시간이며 초과하면 `TIMEOUT` 상태가 된다 [S21]. 작업 타임아웃은 7일(10,080분) 미만이어야 하고, 비워 두면 Glue 4.0 이하는 2,880분, 5.0 이상은 480분이 기본이다 [S21]. `ExecutionProperty.MaxConcurrentRuns` 기본 1을 넘기면 오류가 반환된다 [S21].
- **용량 진단**: 최대 필요 executor 대비 활성 executor를 보고 DPU 과소 할당 여부를 판단한다 [S20].

**Amazon EMR**
- **로그 위치**: 기본으로 모든 노드의 `/mnt/var/log/`에 쓰이며 [S22], 클러스터 종료 후에는 노드 로컬 로그를 못 쓰므로 S3 로그 경로를 지정해 아카이브한다 [S22]. 6.8.0 이하는 5분 간격으로 아카이브하고 6.9.0 이상은 스케일다운 시에도 아카이브한다 [S22]. 콘솔로 만든 클러스터는 기본으로 로그 아카이빙이 켜지고 CLI·API로 만든 클러스터는 수동으로 설정해야 한다 [S23].
- **단계 로그 4종**: `controller`(단계 처리 정보, 로딩 중 실패 시 스택 트레이스), `syslog`(Hadoop 잡 실행), `stderr`, `stdout` [S23].
- **단계 실패 정책**: 단계 제출 시 `ActionOnFailure`로 실패 동작을 지정한다. `TERMINATE_CLUSTER`·`TERMINATE_JOB_FLOW`를 고르면 단계 실패 때 클러스터가 종료되며, `CONTINUE` 또는 `CANCEL_AND_WAIT`로 이를 피한다 [S25].
- **자동 종료**: 자동 종료 정책은 유휴 시간이 지나면 클러스터를 종료한다. 유휴 판정은 활성 YARN 애플리케이션 없음, HDFS 사용률 낮음, 활성 노트북·EMR Studio 연결 없음, 온클러스터 UI 미사용, 대기 중 단계 없음 등을 보며 EMR 릴리스에 따라 기준이 다르다 [S24]. 유휴 시간 기본 60분이며 1분~7일 범위다 [S24]. Presto·Trino·HBase 같은 비 YARN 애플리케이션에서는 자동 종료가 지원되지 않는다 [S24].
- **알림**: 단계·클러스터 상태 변경은 EventBridge 이벤트로 감지한다 [S16].

### CloudWatch Logs로 애플리케이션 로깅 구성·자동화 (Skill 3.3.7)

로그는 **로그 그룹 → 로그 스트림 → 로그 이벤트** 구조이며, 이벤트는 로그 그룹·로그 스트림·시간으로 조회한다 [S4]. 보존, 로그 클래스, 메트릭 필터, 구독 필터는 **로그 그룹 단위**로 설정한다.

- **수집**: CloudWatch 에이전트로 AWS·온프레미스·멀티클라우드 호스트의 지표와 로그를 수집하고, Lambda를 포함한 많은 AWS 서비스는 CloudWatch와 직접 통합된다 [S4]. 로그 에이전트는 기본 주기로 로그를 전송하며 주기를 설정할 수 있다 [S4]. 텍스트 기반 일반 로그와 JSON 로그를 받는다 [S4].
- **보존**: 기본은 **무기한 저장**이며 로그 그룹마다 언제든 바꿀 수 있다 [S4].
- **로그 클래스**: Standard(전체 기능)와 Infrequent Access(IA, 부분 기능)이며 두 클래스는 **수집(ingestion) 비용만** 다르고 생성 후 클래스를 바꿀 수 없다 [S8]. IA는 구독 필터·메트릭 필터·Live Tail·`GetLogEvents`/`FilterLogEvents` 미지원, Logs Insights·교차 계정 기능은 지원한다 [S8]. IA의 S3 내보내기 지원 여부는 다른 공식 자료와 서술이 달라 확정하지 않는다(gaps 참조).
- **메트릭 필터**: 로그 데이터를 지표로 바꿔 경보에 쓴다. **소급 적용되지 않으며**(필터 생성 후 발생한 이벤트만 지표 포인트가 됨), Standard 클래스에서만 지원된다 [S9].
- **구독 필터**: Kinesis Data Streams·Firehose·Lambda(+OpenSearch)로 전달한다 [S5]. 계정 수준 구독 필터는 리전당 1개, 로그 그룹 수준은 로그 그룹당 최대 5개라고 사용자 가이드가 설명한다 [S5](API 레퍼런스는 다른 값으로 서술해 문서 간 상충 — gaps 참조).
- **자동화**: 새 로그 그룹마다 보존 기간을 맞추려면 EventBridge + Lambda로 로그 그룹 생성 시 보존 정책을 자동 적용하고, AWS Config 관리형 규칙 `cw-loggroup-retention-period-check`로 최소 보존 기간 미달 로그 그룹을 주기적으로 탐지한다 [S12]. CloudFormation 템플릿과 교차 리전을 포함한 구현 안내가 있다 [S12]. 로그 그룹 보존은 콘솔 또는 `put-retention-policy` CLI로도 설정한다 [S12].
- **서비스별 설정**: Glue 연속 로깅 인자(로그 그룹·스트림 접두사·변환 패턴)는 4.0 이하에서 지정 [S17]. EMR은 `--log-uri`로 S3 경로 [S22]. Redshift는 콘솔·API·CLI로 감사 로깅을 켠다 [S26].
- **한도**: 로그 이벤트 크기, `PutLogEvents` 배치 크기, 로그 그룹당 메트릭·구독 필터 개수, 활성 내보내기 작업 수 같은 기본 한도는 CloudWatch Logs quotas 표에서 확인하며, 일부는 조정 가능하고 일부는 조정할 수 없다. Service Quotas 콘솔·CLI로 조회하고 증설을 요청한다 [S7].

### 로그 분석 (Skill 3.3.8)

분석 도구는 **로그가 어디에 있는가**와 **질의 빈도·지연 요구**로 갈린다.

| 도구 | 데이터 위치 | 적합한 경우 | 제약·비용 특성 | 시험 단서 키워드 |
|---|---|---|---|---|
| CloudWatch Logs Insights | CloudWatch Logs의 로그 | 운영 문제 대응용 즉석 쿼리, 설정·인프라 불필요 [S4] | 쿼리가 스캔한 수집 로그량으로 과금(실패 쿼리 무과금, 취소 쿼리는 취소 시점까지 과금) [S4], 60분 타임아웃·동시 100개 [S10] | "CloudWatch Logs의 로그를 바로 쿼리" |
| Athena | S3의 로그(CloudTrail 등) | S3 로그를 SQL로 직접 쿼리 [S30] | 컬럼형·압축·파티션·파일 크기에 민감 [S28], 파티션 프로젝션 [S29] | "S3 로그", "서버리스 SQL" |
| OpenSearch Service | 인덱싱된 로그 | 실시간 로그 분석·빈번한 쿼리·전문(full-text) 검색 [S36] | 로그를 도메인에 적재(구독 필터 등) [S5] | "전문 검색", "실시간", "대시보드" |
| EMR | S3의 대용량 로그 | 거대한 로그 집합의 페타바이트급 분석 [S37] | 클러스터 운영 | "수 PB", "배치 분석" |

- **Athena로 S3 로그**: CloudTrail 로그는 CloudTrail 콘솔에서 만들거나 Athena 콘솔에서 수동으로 테이블을 만들어 쿼리하며, 파티션 프로젝션 방식도 있다 [S30]. AWS 서비스 로그는 보통 구조가 알려져 있어 AWS Glue에 파티션 스킴을 지정하고 Athena가 파티션 프로젝션에 쓰기 쉽다 [S29]. 파티션 프로젝션은 Glue Data Catalog(또는 외부 Hive 메타스토어) 테이블 속성에 값 범위와 프로젝션 유형을 설정하는 방식이다 [S29].
- **Logs Insights**: 쿼리 언어는 Logs Insights QL, OpenSearch PPL, OpenSearch SQL 세 가지다 [S4]. Lambda·CloudTrail·Route 53·VPC Flow Logs 같은 서비스 로그와 JSON 로그의 필드를 자동 탐지하고 `@message`, `@logStream`, `@timestamp` 시스템 필드를 만든다 [S4]. 사용하려면 `logs:DescribeLogGroups`와 `logs:FilterLogEvents` 권한이 필요하다 [S4]. 쿼리 한 번에 최대 50개 로그 그룹을 지정할 수 있다 [S10].
- **OpenSearch로 로그 수집·검색**: 구독 필터로 로그 그룹을 OpenSearch Service에 거의 실시간으로 스트리밍할 수 있다 [S5]. Centralized Logging with OpenSearch 솔루션은 AWS 서비스 로그를 OpenSearch 도메인으로 수집하는 파이프라인과 대시보드를 제공하며, 비실시간·가끔 쿼리용으로는 SQL 유사 검색을 하는 Light Engine 옵션도 있다 [S36]. 다만 이 AWS Solution은 2026년 12월에 종료될 예정이며 문서는 CloudWatch의 통합 데이터 관리·분석 기능을 권고한다(종료되는 것은 솔루션이고 OpenSearch Service 자체가 아니다) [S39].
- **EMR 로그 분석**: 대규모 로그 집합 분석에 EMR 클러스터를 쓴다 [S37]. 작은 파일 문제의 해법 하나로 EMR의 S3DistCp 유틸리티로 작은 파일을 큰 객체로 병합하는 방법이 소개된다 [S28].
- 서비스 선택 기준 비교 표 심화는 Task 4.4.4 문서 참조.

## 시험에서 묻는 방식

1. **작업 상태 알림** — "Glue ETL 작업이 FAILED/TIMEOUT이 되면 코드를 고치지 않고 운영팀에 즉시 알려라", "Step Functions 실행 실패·타임아웃을 알려라" 같은 요구 → 서비스가 발행하는 상태 변경 이벤트(Glue Job State Change, Step Functions Execution Status Change, EMR Step/Cluster 상태 변경)를 매칭하는 **EventBridge 규칙 → SNS(또는 Lambda)**가 정답 방향. 오답 후보: CloudTrail Insights(API 호출량·오류율 이상 탐지용이지 작업 상태 알림이 아님), 로그를 구독 필터로 받아 파싱하는 Lambda(상태 이벤트가 이미 있는데 간접 경로), 스크립트 안에서 SNS 호출(코드 수정 필요). 지표 기반이면 CloudWatch 경보 + SNS이고 누락 데이터 처리(`notBreaching` 등)를 함께 묻기도 한다. 근거 [S13][S14][S16][S11][S1]
2. **감사 증거 추적** — "특정 S3 객체를 누가 삭제했는지 1년간 추적", "IAM 정책 변경 주체", "여러 계정·리전 API 호출을 한곳에" 같은 요구 → **trail(조직 trail/멀티 리전) + S3 보관**, 객체 수준이면 **S3 데이터 이벤트**를 추가 활성화, 조회는 Athena. 오답 후보: CloudTrail Event history(최근 90일·관리 이벤트·현재 리전만), AWS Config(구성 상태 이력이지 호출자 기록이 아님), S3 서버 액세스 로그(로그 파일 무결성 검증 없음). 데이터 이벤트는 기본 꺼짐·추가 요금이라 고급 이벤트 선택기로 범위를 좁히는 것이 비용 정답. 근거 [S1][S3][S2][S34][S35]
3. **성능 저하 진단** — "스트림 소비가 뒤처진다/레코드가 만료될 수 있다", "Lambda 호출이 거부된다", "DynamoDB 쓰기가 쓰로틀된다", "Athena 쿼리가 느리고 비싸다", "Redshift 쿼리가 큐에서 대기한다", "Glue 작업이 오래 걸린다" → 서비스별 신호 지표를 고르는 문제: Kinesis `GetRecords.IteratorAgeMilliseconds`(Maximum, 보존 기간의 50%), `Read/WriteProvisionedThroughputExceeded`; Lambda `Throttles`·`ConcurrentExecutions`; DynamoDB `ThrottledRequests` + 이벤트 단위 지표; Athena는 컬럼형·압축·약 128 MB 파일·파티션(프로젝션); Redshift는 자동 WLM·동시성 확장(기본 꺼짐)·QMR; Glue는 최대 필요 executor 대비 활성 executor. 근거 [S31][S38][S32][S33][S28][S29][S27][S20]
4. **로그 보관·분석 서비스 선택** — "CloudWatch Logs의 로그를 가끔 SQL로 장기·저비용 분석", "실시간 전문 검색과 대시보드", "수 PB 로그 배치 분석", "S3에 쌓인 CloudTrail 로그를 서버 없이 쿼리" → 즉석 운영 쿼리는 **Logs Insights**, S3 로그 SQL은 **Athena(+파티션 프로젝션)**, 실시간·빈번 쿼리·전문 검색은 **OpenSearch Service**, 거대한 로그 집합 배치는 **EMR**. 보존 비용은 로그 그룹 보존 기간·로그 클래스(IA)·S3 아카이브(일회성·배치는 내보내기, 지속 아카이브는 구독)로 푼다. 근거 [S4][S10][S30][S29][S36][S37][S8][S12]

## 흔한 함정·혼동 짝

1. **CloudTrail 이벤트 기록(Event history) vs trail** — 이벤트 기록은 설정 없이 현재 리전 최근 90일·관리 이벤트만(무료), trail은 S3·CloudWatch Logs·EventBridge로 전달해 데이터 이벤트·읽기 전용 활동까지 영구 기록 → 시험 단서: "지난 90일", "1년 보관", "모든 활동" [S1]
2. **관리 이벤트 vs 데이터 이벤트** — 관리 이벤트(control plane)는 기본 기록, 데이터 이벤트(S3 객체 API, Lambda `Invoke`)는 기본 꺼짐·대용량·추가 요금 → 단서: "객체 수준", "누가 `DeleteObject`" [S2][S3][S1]
3. **CloudTrail vs AWS Config** — CloudTrail은 누가 어떤 API를 호출했나, Config는 리소스 구성이 어떻게 바뀌었나(구성 항목·이력). 빠른 연속 변경은 구성 항목 하나로 합쳐져 사용자 대응이 완전하지 않을 수 있다 → 단서: "구성 이력", "누가 변경" [S1][S35]
4. **CloudTrail Insights vs 일반 이벤트 로깅** — Insights는 API 호출량·오류율의 기준선 이탈을 탐지하며 개별 trail에 구성(trail 필요), 일반 이벤트 로깅은 개별 호출 기록 → 단서: "비정상 급증", "스크립트 반복 호출" [S1]
5. **CloudWatch Logs 내보내기(`CreateExportTask`) vs 구독 필터** — 내보내기는 비동기 배치성 작업(활성 작업 수 한도 있음)이고 지속 아카이브용으로는 비권장, 구독 필터는 거의 실시간(보통 3분 미만)으로 Kinesis·Firehose·Lambda에 전달하며 Standard 클래스만 → 단서: "실시간 스트리밍 전달" vs "S3로 한 번에 내보내기" [S6][S7][S5]
6. **메트릭 필터 vs Logs Insights** — 메트릭 필터는 앞으로 들어오는 로그를 지표로 바꿔 경보에 쓰고 과거 데이터에는 소급 적용되지 않음, Logs Insights는 저장된 로그에 대한 즉석 쿼리(스캔량 과금) → 단서: "로그 패턴에 경보" vs "원인 조사 쿼리" [S9][S4]
7. **Standard vs Infrequent Access 로그 클래스** — IA는 수집 단가가 낮은 대신 구독 필터·메트릭 필터·Live Tail·`GetLogEvents`/`FilterLogEvents`를 못 쓰고 클래스는 생성 후 변경 불가 → 단서: "저렴하게 보관 + 임시 쿼리" vs "실시간 경보" [S8]
8. **EventBridge 규칙 vs CloudWatch 경보** — EventBridge는 서비스 상태 변경 이벤트(Glue Job State Change 등)에 반응, CloudWatch 경보는 지표 임계값·평가 기간에 반응 → 단서: "작업이 FAILED 되면" vs "지표가 N분 연속 초과" [S13][S14][S4]
9. **누락 데이터 `notBreaching` vs `breaching` vs `ignore` vs `missing`** — 기본은 `missing`(평가 범위 전체가 누락이면 INSUFFICIENT_DATA), 오류 때만 데이터가 나오는 지표는 `notBreaching`, 계속 보고되는 지표(예: 롤백 경보)는 `breaching`을 고려, `AWS/DynamoDB` 지표는 기본 `ignore` → 단서: "경보가 INSUFFICIENT_DATA에 머문다" [S11]
10. **Glue 연속 로깅(4.0 이하) vs Glue 5.0** — 4.0 이하는 `--enable-continuous-cloudwatch-log`로 켜고 5.0부터 모든 작업이 실시간 로깅 기능을 가짐, 버전을 지정하지 않고 만든 작업의 기본 버전은 5.1 → 단서: "Glue 4.0 이하 작업에서 연속 로깅을 켜라" vs "5.0 이상 작업" [S17][S21]
11. **Glue 북마크 Enable vs Disable(기본) vs Pause** — Disable은 항상 전체 처리(기본), Enable은 마지막 체크포인트 이후만, Pause는 상태를 갱신하지 않고 증분 처리. S3는 마지막 수정 시각으로 판단해 수정된 파일은 다시 처리 → 단서: "매번 전체 재처리", "이미 처리한 파일 건너뛰기" [S19]
12. **Glue `Timeout` vs `MaxRetries` vs `MaxConcurrentRuns`** — 실행 시간 상한(초과 시 TIMEOUT), 실패 후 재시도 횟수, 동시 실행 수(기본 1, 초과 시 오류) → 단서: "작업이 TIMEOUT", "이전 실행이 안 끝났는데 시작 오류" [S21]
13. **EMR 노드 로컬 로그 vs S3 아카이브** — 로컬 `/mnt/var/log/`는 노드가 사라지면 사라지므로 S3 로그 경로 지정이 필요(콘솔 생성은 기본 켜짐, CLI·API는 수동) → 단서: "종료된 클러스터의 로그가 없다" [S22][S23]
14. **EMR `ActionOnFailure`: TERMINATE_CLUSTER vs CONTINUE/CANCEL_AND_WAIT** — 단계 실패 시 클러스터 종료 여부를 정하며 `SHUTDOWN_STEP_FAILED` 종료를 피하려면 CONTINUE 또는 CANCEL_AND_WAIT → 단서: "단계 하나 실패로 클러스터가 죽는다" [S25]
15. **Redshift 감사 로그 vs 시스템 테이블** — 감사 로깅은 기본 꺼짐·S3(SSE-S3만, Object Lock 불가) 또는 CloudWatch Logs, 시스템 테이블 로깅은 자동. 사용자 활동 로그는 `enable_user_activity_logging`도 필요, Serverless는 CloudWatch만 → 단서: "쿼리 텍스트까지 감사" [S26]
16. **Athena 파티션 vs 파티션 프로젝션** — 파티션은 Data Catalog 메타데이터를 조회·유지, 프로젝션은 테이블 속성에서 값·위치를 계산해 조회를 생략하며 켜면 등록된 파티션 메타데이터는 무시 → 단서: "파티션이 너무 많아 플래닝이 느리다" [S29][S28]
17. **Kinesis `IteratorAgeMilliseconds` vs `ReadProvisionedThroughputExceeded`** — 전자는 소비가 얼마나 뒤처졌나(보존 기간 50% 초과 시 만료 위험), 후자는 읽기 호출이 한도 초과로 쓰로틀됐는가 → 단서: "소비자 지연" vs "읽기 쓰로틀" [S31][S38]
18. **Lambda `Throttles` vs `Errors`** — 쓰로틀된 요청은 `Invocations`·`Errors`에 잡히지 않고 `Throttles`로만 보임, 동시성 한도 도달이 원인 → 단서: "TooManyRequestsException", "호출이 사라진다" [S32]
19. **DynamoDB `ThrottledRequests` vs `ReadThrottleEvents`/`WriteThrottleEvents`** — 요청당 1 증가라 GSI 등 여러 이벤트가 쓰로틀돼도 규모가 가려짐, 이벤트 단위 지표로 실제 규모 확인 → 단서: "GSI가 있는 테이블의 쓰로틀 규모" [S33]
20. **S3 서버 액세스 로그 vs CloudTrail 데이터 이벤트** — AWS는 버킷·객체 수준 동작 기록에 CloudTrail 권장. 무결성 검증·접두사 단위 로깅은 CloudTrail, 수명 주기 동작·인증 실패 기록은 서버 액세스 로그 → 단서: "수명 주기 만료 기록", "무결성 검증" [S34]
21. **Logs Insights vs Athena vs OpenSearch vs EMR** — CloudWatch Logs 안의 로그 즉석 쿼리 / S3 로그 SQL / 실시간·빈번 쿼리·전문 검색 / 거대한 로그 집합 배치 → 단서: 각 데이터 위치와 질의 빈도 [S4][S30][S36][S37]

### 후보 4 — Skill 3.3.7 · associate
- **문제**: 여러 팀이 수시로 CloudWatch Logs 로그 그룹을 새로 만든다. 기본 설정 그대로여서 로그가 계속 쌓여 비용이 늘고 있다. 새 로그 그룹이 만들어질 때마다 보존 기간을 자동으로 적용하면서 운영 부담을 최소화하는 방법은?
- **보기**: A. 모든 로그 그룹을 Infrequent Access 로그 클래스로 바꾼다. / B. 로그 그룹 생성 이벤트를 EventBridge 규칙으로 받아 Lambda가 보존 정책을 설정하게 하고, AWS Config 관리형 규칙으로 기준 미달 로그 그룹을 탐지한다. / C. 모든 로그 그룹에 메트릭 필터를 만들어 오래된 로그를 삭제한다. / D. 월 1회 담당자가 콘솔에서 로그 그룹을 점검해 보존 기간을 바꾼다.
- **정답**: B
- **해설 초안**: CloudWatch Logs의 기본 보존은 무기한이다. EventBridge + Lambda로 새 로그 그룹에 보존 정책을 자동 적용하고, AWS Config 관리형 규칙 `cw-loggroup-retention-period-check`가 최소 보존 기간에 못 미치는 로그 그룹을 주기적으로 탐지한다. [S4][S12]
- **오답 근거**: A — 로그 클래스는 생성 후 변경할 수 없고 두 클래스는 수집 비용만 다르다 [S8] / C — 메트릭 필터는 로그를 지표로 바꿀 뿐 데이터를 지우지 않는다 [S9] / D — 수동·사후 점검이라 "자동 적용" 요구를 충족하지 못한다 [S12]
- **근거**: [S12] https://aws.amazon.com/blogs/mt/a-practical-guide-to-amazon-cloudwatch-logs-cost-optimization/ — "to automatically apply a retention policy whenever a log group is created"

### 후보 5 — Skill 3.3.8 · associate (서비스 선택)
- **문제**: S3에 여러 계정·리전의 CloudTrail 로그가 수 TB 쌓여 있다. 분기에 몇 번 임시 SQL 조사만 하고 상시 클러스터는 운영하고 싶지 않다. 날짜 파티션이 계속 늘어 쿼리 플래닝이 느려진다. 가장 적절한 접근은?
- **보기**: A. OpenSearch Service 도메인을 만들어 모든 로그를 인덱싱한다. / B. Athena에서 CloudTrail 로그 테이블을 만들고 파티션 프로젝션을 구성한다. / C. 상시 EMR 클러스터를 띄워 Hive로 쿼리한다. / D. 로그를 CloudWatch Logs로 옮긴 뒤 Logs Insights로 쿼리한다.
- **정답**: B
- **해설 초안**: Athena는 S3의 CloudTrail 로그를 `LOCATION`으로 직접 쿼리할 수 있고, 파티션 프로젝션은 Data Catalog 조회 대신 테이블 속성 설정으로 파티션 값·위치를 계산해 파티션이 많은 테이블의 쿼리 시간을 줄이고 파티션 관리를 자동화한다. [S30][S29]
- **오답 근거**: A — OpenSearch Service는 실시간 로그 분석·빈번한 쿼리·전문 검색에 적합해 가끔의 임시 쿼리에는 과하다 [S36] / C — EMR은 거대한 로그 집합의 대규모 분석에 쓰며 클러스터 운영 부담이 있다 [S37] / D — Logs Insights는 CloudWatch Logs에 있는 로그를 질의하므로 로그를 먼저 옮겨야 한다 [S4]
- **근거**: [S29] https://docs.aws.amazon.com/athena/latest/ug/partition-projection.html — "Enabling partition projection on a table causes Athena to ignore any partition"
