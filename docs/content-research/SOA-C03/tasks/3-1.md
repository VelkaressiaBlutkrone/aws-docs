### 3.1.1 AMI와 컨테이너 이미지 만들기·관리 (EC2 Image Builder)
- **한 줄 요약**: AMI(와 컨테이너 이미지)를 "손으로 굽지 말고 파이프라인으로 굽는다" + "리전·계정·암호화 세 축으로 공유 가능 여부를 판단한다".
- **EC2 Image Builder 의 구성**: 이미지 파이프라인은 이미지 레시피(베이스 이미지 + 구성 요소), 인프라 구성(빌드용 임시 인스턴스의 위치·역할), 배포 설정(어느 리전·계정에 배포할지), 일정을 하나로 묶어 보안이 반영된 AMI·컨테이너 이미지를 자동 빌드하는 틀이다 [F1]. 같은 페이지에 따르면 테스트 구성 요소가 모두 성공해야만 이미지를 배포하고, 빌드 인스턴스는 실패 시 기본적으로 종료된다(문제 분석용으로 유지하도록 바꿀 수 있음) [F1]. AMI 출력은 여러 리전, 계정, Organizations 로 공유하도록 배포 설정할 수 있고, 컨테이너 이미지는 컨테이너 레시피로 만들어 ECR 로 배포한다 [F1]. 구성 요소·이미지·이미지 레시피·컨테이너 레시피는 AWS RAM 으로 공유할 수 있다 [F1].
- **일정과 "의존성 업데이트"**: 예약 빌드에서 의존성 업데이트가 있을 때만 실행하도록 하면 베이스 이미지나 레시피의 구성 요소가 바뀌지 않은 날은 빌드를 건너뛴다 [F2]. 일정 방식은 Schedule Builder(기본값: 생성 시각 기준 주 1회, UTC), cron, 수동 세 가지다 [F2].
- **AMI 경계 3가지**
  - 리전: AMI 는 리전 리소스이므로 다른 리전에서 쓰려면 그 리전으로 복사한 다음 공유한다 [F3].
  - 계정: 시작 권한(launch permission)을 지정한 계정에 공유한다. 공유받은 계정은 인스턴스를 시작할 수만 있고 삭제·재공유·수정은 못 한다 [F3].
  - 암호화: AMI 가 참조하는 EBS 스냅샷 자체를 따로 공유할 필요는 없지만, 스냅샷 암호화에 쓴 KMS 키는 공유해야 한다 [F4]. 같은 페이지: 기본 AWS 관리형 키로 암호화된 스냅샷을 쓰는 AMI 는 공유할 수 없다 [F4].
- **정리·비용**: AMI 를 deregister 해도 기본적으로 스냅샷은 남아 과금이 이어진다 [F5]. deregister 시 스냅샷을 함께 지우는 옵션이 있으나 여러 AMI 가 참조하는 스냅샷은 지워지지 않고, 실수 방지용 deregistration protection·Recycle Bin 복원도 있다 [F5]. 컨테이너 이미지는 ECR 수명 주기 정책으로 오래된 이미지를 자동 정리한다 [F6].

| 상황 | 필요한 조치 | 근거 |
|---|---|---|
| 같은 리전의 다른 계정이 AMI 로 인스턴스 시작 | AMI 시작 권한 공유 (스냅샷 공유는 불필요) | [F3][F4] |
| 다른 리전에서 사용 | 대상 리전으로 AMI 복사 → 필요하면 그 사본을 공유 | [F3] |
| 암호화 스냅샷 기반 AMI 를 다른 계정에 공유 | 대상 계정이 KMS 키를 쓸 수 있게 키 공유 | [F4] |
| 기본 AWS 관리형 키로 암호화된 AMI 공유 | 불가 → 고객 관리형 키로 다시 만들어야 함 | [F4] |
| 오래된 AMI 정리 후에도 스토리지 비용 지속 | 남은 스냅샷을 별도로 삭제 | [F5] |
| 정기 패치된 표준 이미지를 자동 빌드·배포 | Image Builder 파이프라인 + 일정(+의존성 업데이트) | [F1][F2] |

### 3.1.2 CloudFormation 과 AWS CDK 로 AWS 리소스 만들고 관리
- **변경 세트(Change Set)**: 스택 업데이트 전에 변경이 실행 중인 리소스에 미치는 영향을 미리 보는 기능이며, 삭제·교체되는 핵심 리소스가 있는지 확인한 뒤 "실행"을 선택해야 실제로 반영된다 [F7].
- **DeletionPolicy (스택 삭제 시 리소스 운명)**
  - 속성이 없으면 CloudFormation 은 리소스를 삭제한다 [F8]. 값은 Delete, Retain, RetainExceptOnCreate, Snapshot 이다 [F8].
  - Retain: 스택 삭제가 끝나 Delete_Complete 가 돼도 리소스는 남아 계속 과금된다. RetainExceptOnCreate: 생성 단계가 롤백될 때만 리소스를 지우고 그 밖의 작업에서는 유지한다 [F8].
  - **기본값의 예외**: AWS::RDS::DBCluster 와, DBClusterIdentifier 를 지정하지 않은 AWS::RDS::DBInstance 의 기본 정책은 Snapshot 이다 [F9]. 즉 기존 학습문서의 "RDS 는 기본 삭제" 서술은 현행 공식 문서와 다르다(98 조각 C 참조).
  - Snapshot 을 지원하는 리소스 타입 8종: DocDB 클러스터, EBS 볼륨, ElastiCache 캐시 클러스터·복제 그룹, Neptune 클러스터, RDS 클러스터·인스턴스, Redshift 클러스터 [F10].
  - 이 정책은 "스택 삭제(또는 템플릿에서 리소스 제거)" 때의 동작이다. 업데이트 중 리소스가 교체되는 경우에는 적용되지 않는다고 같은 페이지가 밝힌다 [F8].
- **드리프트(Drift)**: 콘솔·CLI 로 스택 밖에서 바꾼 설정을 찾아내는 기능이다. 찾은 뒤에는 사람이 시정 조치(리소스를 템플릿 정의에 맞게 되돌리거나 템플릿을 갱신)를 해야 한다 [F11]. 같은 페이지: 드리프트 감지를 지원하지 않는 리소스는 NOT_CHECKED 로 표시되고, 감지는 CREATE_COMPLETE, UPDATE_COMPLETE, UPDATE_ROLLBACK_COMPLETE, UPDATE_ROLLBACK_FAILED 상태의 스택에서 실행할 수 있으며 중첩 스택은 감지 대상에 포함되지 않는다 [F11].
- **AWS CDK**: 프로그래밍 언어로 인프라를 정의하고 `cdk synth` 로 스택마다 CloudFormation 템플릿(클라우드 어셈블리)을 만든 뒤 CloudFormation 으로 배포한다 [F13]. 즉 CDK 는 CloudFormation 을 대체하지 않고 앞단에서 템플릿을 생성하는 도구다.
  - `cdk bootstrap`: 배포 대상 환경에 부트스트랩 스택 CDKToolkit(S3 버킷·ECR 리포지토리 등)을 먼저 배포한다 [F12]. 부트스트랩이 안 된 환경에서는 자산이 없고 템플릿이 51,200바이트 미만인 스택만 배포된다(cdk deploy 레퍼런스).
  - `cdk diff`: 로컬 CDK 코드와 배포된 스택의 차이(인프라 변경)를 본다 [F14]. 스택 밖에서 바뀐 리소스를 찾는 것은 CloudFormation 드리프트를 호출하는 `cdk drift` 이며 별개 명령이다(cdk drift 레퍼런스).
  - 구성 요소 L1(CFN 리소스 1:1) · L2(의도 기반 API, 기본값 내장) · L3(패턴) 계층이 있고, CDK 스택은 배포의 최소 단위로 하나의 CloudFormation 스택이 된다(CDK Developer Guide: Constructs, Stacks).

| 하고 싶은 일 | 쓰는 기능 | 근거 |
|---|---|---|
| 적용 전에 어떤 리소스가 바뀌는지 확인 | 변경 세트 | [F7] |
| 스택을 지워도 데이터는 남기기(리소스 그대로) | DeletionPolicy: Retain | [F8] |
| 스택을 지울 때 스냅샷을 남기기 | DeletionPolicy: Snapshot (지원 8종만) | [F10] |
| 스택 밖에서 누가 바꿨는지 찾기 | 드리프트 감지 | [F11] |
| CDK 앱의 CloudFormation 템플릿 생성 | cdk synth | [F13] |
| 새 계정·리전에서 CDK 첫 배포 | cdk bootstrap 선행 | [F12] |

### 3.1.3 배포 문제 식별·해결 (서브넷 크기, CloudFormation 오류, 권한)
- **서브넷 크기**: IPv4 서브넷 CIDR 은 /28 ~ /16 이고, 서브넷마다 처음 4개와 마지막 1개, 합계 5개 IP 는 쓸 수 없다 [F15]. 그래서 /24(256개)는 251개만 쓴다. ALB 는 서브넷에 /27 이상 CIDR 과 여유 IP 8개 이상이 있어야 확장·노드 교체가 안정적이다 [F16]. 확장하는 동안 서브넷의 사용 가능한 IP 가 바닥나면 ALB 는 용량이 부족한 채로 동작하며 5xx·타임아웃이 날 수 있다 [F16].
- **CloudFormation 오류를 읽는 순서**: 스택 이벤트에서 실패 이벤트를 찾고 그 이벤트의 상태 이유(status reason)를 읽는다 [F17]. 대표 원인은 아래 표.

| 증상·상태 | 의미와 조치 | 근거 |
|---|---|---|
| ROLLBACK_COMPLETE | 생성 실패 후 정리가 끝난 상태. 이 상태에서는 삭제만 가능하다 → 삭제 후 원인 수정하고 다시 생성 | [F18] |
| UPDATE_ROLLBACK_FAILED | 롤백 대상 리소스를 원래 상태로 못 돌려서 발생. 스택 밖 변경이면 리소스를 원래 템플릿과 같게 수동으로 맞춘 뒤 롤백을 계속(ContinueUpdateRollback) | [F17] |
| 계속해도 해결 안 됨 | 롤백 강제 완료 또는 특정 리소스 건너뛰기 가능. 건너뛴 리소스는 템플릿과 불일치할 수 있어 다음 업데이트 전에 맞춰야 함 | [F17] |
| 권한 오류 | CloudFormation 권한뿐 아니라 템플릿이 쓰는 하위 서비스(S3, EC2 등) 권한도 필요 | [F19] |
| 한도 초과 / 의존성 오류 / 타임아웃 | 한도 증설·불필요 리소스 삭제, DependsOn 추가, 서비스 역할 지정으로 타임아웃 연장 등 | [F17][F19] |

  위 표 마지막 행의 세부(DependsOn, 서비스 역할로 타임아웃 연장 등)는 troubleshooting 페이지의 해당 소절에 있다.
- **권한 문제의 층**: (1) 호출자 IAM 권한, (2) 서비스 역할을 지정했다면 그 역할의 권한(역할을 넘기려면 iam:PassRole 필요, using-iam-servicerole 페이지), (3) 조직 SCP 가 막는지(SCP 는 권한을 부여하지 않고 상한만 정함, orgs_manage_policies_scps 페이지)를 위에서 아래로 확인한다. (2)(3)은 §5 에 인용하지 않았으니 98/99 조각의 출처 URL 로 확인한다.

### 3.1.4 여러 리전·계정에 프로비저닝하고 공유 (AWS RAM, StackSets)
- **AWS RAM = "리소스 하나를 만들고 여러 계정이 쓰게 한다"**. 리소스 공유(resource share)는 리전 단위이며, 한 공유에 서로 다른 리전의 리전 리소스를 섞을 수 없다 [F20]. 조직(OU 포함)에 공유하려면 먼저 RAM 에서 Organizations 공유를 활성화해야 하고 [F21], 그렇게 공유하면 초대 없이 접근 권한이 생긴다(getting-started-sharing 페이지).
- **서브넷 공유**: 서브넷은 같은 조직 안의 계정에만 공유할 수 있고 기본(default) 서브넷은 공유 불가이며 직접 만든 서브넷만 공유한다 [F22]. 공유받은 계정(참여자)은 자기 리소스만 보고 수정할 수 있고 다른 참여자·소유자의 리소스는 못 건드린다(vpc-sharing 페이지).
- **StackSets = "같은 템플릿을 여러 계정×리전에 각각 배포"**. 서비스 관리형 권한은 Organizations 계정을 대상으로 하며 IAM 역할을 StackSets 가 대신 만들고, 나중에 조직에 추가되는 계정에도 자동 배포를 켤 수 있다 [F23]. 셀프 관리형은 관리자·실행 IAM 역할을 직접 만들어 신뢰 관계를 맺는다(stacksets-concepts 페이지).
- 결정 규칙: 대상 계정에 **독립된 스택·리소스를 반복 생성**해야 하면 StackSets, **하나의 중앙 리소스를 공유**해야 하면 RAM, 이미지(AMI)는 **시작 권한 공유 + 리전 복사**(3.1.1) 로 구분한다.

### 3.1.5 배포 전략 및 서비스 구현 (가이드 문구가 모호함 — 99 조각 범위해석 참조)
- 가이드 문구에 예시가 없다. 이 문서는 "전략 개념 + 이를 구현하는 AWS 기능"을 중심으로 정리했고, 어느 범위가 출제되는지는 확인되지 않았다.
- **전략 비교**: 롤링은 보통 블루/그린보다 빠르지만 새·옛 버전 사이에 환경 격리가 없어 위험이 커지고 롤백이 복잡해진다 [F24]. 블루/그린은 동일한 두 프로덕션 환경(블루·그린)을 두고 새 서비스 리비전을 검증한 뒤 트래픽을 보내며 필요하면 빠르게 롤백할 수 있다(ECS API_DeploymentConfiguration 페이지의 BLUE_GREEN 설명, [F26] 와 같은 페이지). 카나리는 블루/그린의 위험 회피형 변형이다(whitepaper canary-deployments 페이지).
- **구현 수단**
  - EC2 Auto Scaling 인스턴스 새로 고침: 롤링 전략(기본)은 설정에 따라 인스턴스를 배치로 종료·새로 시작한다 [F25]. 기본값: 인스턴스 유지 정책이 없으면 최소 정상 비율 90%, 자동 롤백·체크포인트는 기본 꺼짐(understand-instance-refresh-default-values 페이지).
  - ECS 서비스 배포 전략: ROLLING, BLUE_GREEN, LINEAR, CANARY 중 선택하며 카나리는 소량 트래픽을 새 서비스 리비전에 먼저 보낸 뒤 나머지를 한 번에 전환한다 [F26]. 롤링에서는 minimumHealthyPercent·maximumPercent(REPLICA 기본 200%)로 배치 크기를 정하고 배포 서킷 브레이커는 롤링에만 쓴다(API_DeploymentConfiguration 페이지).
  - 트래픽 가중치로 점진 전환: Route 53 가중치 라우팅은 같은 이름의 레코드에 비율을 주어 새 버전 테스트에 쓸 수 있다 [F27]. ALB 는 forward 작업에서 대상 그룹마다 0~999 가중치를 주며, 한 대상 그룹이 비거나 비정상이어도 자동 장애 조치는 되지 않는다(rule-action-types 페이지). Lambda 는 별칭 라우팅 구성으로 두 버전 사이에 가중치를 둔다(configuring-alias-routing 페이지).
  - CloudFormation 롤링 업데이트(UpdatePolicy AutoScalingRollingUpdate)는 ASG 인스턴스 유지 정책을 따르지 않고 새 인스턴스를 먼저 띄우지도 않는다(aws-attribute-updatepolicy 페이지).
- CodeDeploy · CodePipeline · Elastic Beanstalk 은 v1.1 in-scope/out-of-scope 목록 어디에도 없다("목록은 non-exhaustive"). 개념 설명에 등장할 수는 있으나 비중은 낮게 두는 것이 안전하다(99 조각 참조).

### 3.1.6 서드 파티 도구(Terraform, Git)로 배포 자동화
- **Terraform + S3 백엔드**: 상태를 S3 에 두고 잠금을 켜서 동시 실행을 막는다. 현행 방식은 backend 설정의 use_lockfile 이며 DynamoDB 기반 잠금은 deprecated 이고 이후 마이너 버전에서 제거 예정이다 [F28]. Terraform 은 클라우드에 종속되지 않고 에이전트 설치가 필요 없지만 상태 관리는 사용자가 책임진다(AWS Prescriptive Guidance: choose-iac-tool/terraform 페이지). 상태 파일에 민감정보가 평문으로 들어갈 수 있으므로 접근 통제가 필요하다(AWS Prescriptive Guidance: secure-sensitive-data 페이지).
- **Git 기반 워크플로**: CloudFormation Git sync 는 연결한 저장소의 템플릿·스택 배포 파일 커밋을 감지해 스택을 자동 업데이트한다 [F30]. 저장소는 AWS CodeConnections 로 GitHub, GitHub Enterprise, GitLab, Bitbucket, GitLab 자체 관리형과 연결한다 [F30].
- **CodeCommit 현황(주의)**: 2024-07-25 에 신규 고객 대상 종료가 공지됐으나 2025-11-25 에 다시 신규 고객에게 열렸다 [F29]. 오래된 학습자료의 "신규 사용 불가" 서술은 현행과 다르다.

## 3. 시험에서 묻는 방식 (가이드 Skill 문구 기반 추정 — 실제 문항 아님)
아래는 AWS 가 공개한 Skill 문구와 동사에서 추론한 출제 패턴이며, 실제 기출을 안다고 주장하지 않는다.
1. **AMI 를 다른 리전·계정에서 쓰려 한다** — 근거 문구: "Create and manage AMIs and container images". 판단 기준: 리전이 다르면 복사, 계정이 다르면 시작 권한 공유, 스냅샷이 고객 관리형 키로 암호화돼 있으면 KMS 키까지 공유, 기본 AWS 관리형 키 암호화면 공유 불가 [F3][F4]. 정리 문항은 deregister 후 남은 스냅샷 비용 [F5].
2. **스택 변경·삭제 때 데이터를 지키거나 영향을 미리 본다** — 근거 문구: "Create and manage AWS resources by using CloudFormation and the AWS CDK". 판단 기준: 적용 전 미리보기=변경 세트 [F7], 삭제 시 보존=DeletionPolicy(기본 Delete, RDS 예외 Snapshot, Snapshot 지원 8종) [F8][F9][F10], 스택 밖 변경 탐지=드리프트 [F11], CDK 는 synth 로 템플릿 생성·최초에 bootstrap [F12][F13].
3. **배포가 실패했다, 원인을 찾아 해결하라** — 근거 문구: "Identify and remediate deployment issues (for example, subnet sizing issues, CloudFormation errors, permissions issues)". 판단 기준: 스택 상태 코드별 조치(ROLLBACK_COMPLETE 는 삭제만, UPDATE_ROLLBACK_FAILED 는 원인 해결 후 롤백 계속) [F17][F18], 서브넷 IP 5개 예약·ALB 여유 IP 8개 [F15][F16], 하위 서비스 권한 [F19].
4. **여러 계정·리전에 같은 구성을 배포하거나 한 리소스를 공유한다** — 근거 문구: "Provision and share resources across multiple Regions and accounts". 판단 기준: 반복 배포=StackSets(서비스 관리형+자동 배포) [F23], 공유=RAM(Organizations 공유 활성화, 리전별 공유, 서브넷은 조직 내만) [F20][F21][F22].

참고: 3.1.5 는 예시 없는 모호한 문구라 추정 근거가 약하다. 전략(롤링 vs 블루/그린 vs 카나리)과 가중치 기반 전환 수단을 구분하는 문제가 가장 가능성 높은 후보다 [F24][F26][F27]. 3.1.6 은 Terraform 상태 잠금과 Git 연동 개념이 후보다 [F28][F30].

## 4. 흔한 함정 · 혼동 짝
| 혼동 짝 | 구분 기준 | 근거 |
|---|---|---|
| 변경 세트 생성 vs 실행 | 생성은 미리보기, 실행해야 반영 | [F7] |
| DeletionPolicy 기본값: 모든 stateful 리소스는 삭제 vs RDS 는 Snapshot | 속성이 없으면 삭제이나 DBCluster·DBInstance(클러스터 식별자 없음)는 Snapshot | [F8][F9] |
| Retain vs Snapshot | Retain 은 리소스를 그대로 남김, Snapshot 은 지원 8종에서만 스냅샷 생성 후 삭제 | [F8][F10] |
| 드리프트 감지 vs 자동 복구 | 감지는 차이 탐지, 시정 조치는 사람이 수행 | [F11] |
| ROLLBACK_COMPLETE vs UPDATE_ROLLBACK_FAILED | 전자는 생성 실패 후 삭제만 가능, 후자는 원인 해결 후 롤백 계속 | [F18][F17] |
| 서브넷 5개 예약 vs ALB 8개 여유 | 모든 서브넷에서 5개는 못 쓰고, ALB 는 추가로 8개 여유 필요 | [F15][F16] |
| AMI 복사 vs 공유 | 복사=리전 이동, 공유=계정에 시작 권한 | [F3] |
| 암호화 AMI: 스냅샷 공유 vs 키 공유 | 스냅샷은 안 줘도 되고 KMS 키는 줘야 함 | [F4] |
| AMI deregister vs 스냅샷 삭제 | deregister 만으로 스냅샷 비용이 사라지지 않음 | [F5] |
| RAM vs StackSets | RAM=한 리소스 공유, StackSets=대상별 스택 인스턴스 배포 | [F20][F23] |
| RAM 조직 공유 vs 개별 계정 공유 | 조직·OU 공유는 Organizations 공유 활성화 선행 | [F21] |
| 롤링 vs 블루/그린 vs 카나리 | 롤링=환경 격리 없음, 카나리=소량 트래픽 먼저 | [F24][F26] |
| Terraform 잠금: DynamoDB vs 락파일 | DynamoDB 방식은 deprecated, use_lockfile 가 현행 | [F28] |
| CodeCommit 상태: 구(신규 불가) vs 현행 | 2025-11-25 에 신규 고객 재개방 | [F29] |
| cdk bootstrap vs cdk synth | bootstrap=환경 준비(CDKToolkit), synth=템플릿 생성 | [F12][F13] |

## 6. 자가 점검 문항 후보 (3~5) — 후보일 뿐, 검증 아님
### Q1 (Skill 3.1.1 · intermediate)
문제: 중앙 이미지 계정이 서울 리전에서 고객 관리형 KMS 키로 스냅샷을 암호화한 골든 AMI 를 만들었다. 같은 리전의 개발 계정에 AMI 시작 권한을 이미 공유했는데, 개발 계정에서 인스턴스를 시작하면 암호화 키 접근 오류로 실패한다. 무엇을 해야 하는가?
- A) 개발 계정에 AMI 가 참조하는 EBS 스냅샷을 추가로 공유한다.
- B) 개발 계정이 해당 KMS 키를 사용할 수 있도록 키를 공유한다.
- C) AMI 를 다른 리전으로 복사한 뒤 다시 공유한다.
- D) AMI 를 퍼블릭으로 전환한다.

정답: B
정답 근거: 스냅샷은 따로 공유하지 않아도 되지만 암호화에 쓴 KMS 키는 공유해야 한다 [F4] — https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/sharingamis-explicit.html
오답 이유: A) 스냅샷 공유는 필요 없다 [F4] / C) 같은 리전에서 이미 공유할 수 있어 복사는 필요 없다 [F3] / D) 공개 전환은 키 접근 문제를 해결하지 못하고 노출만 키운다.

### Q2 (Skill 3.1.2 · intermediate)
문제: CloudFormation 템플릿에 데이터용 AWS::EC2::Volume 이 DeletionPolicy 없이 정의돼 있다. 운영팀은 스택을 삭제할 때 이 볼륨의 스냅샷을 남기고 싶다. 올바른 구성은?
- A) 아무 설정도 필요 없다. 스택을 삭제하면 CloudFormation 이 자동으로 스냅샷을 만든다.
- B) 볼륨 리소스에 DeletionPolicy: Snapshot 을 지정한다.
- C) 볼륨 리소스에 DeletionPolicy: Retain 을 지정하면 스냅샷이 자동 생성된다.
- D) 스택에서 드리프트 감지를 실행한다.

정답: B
정답 근거: 속성이 없으면 삭제가 기본이고 [F8], AWS::EC2::Volume 은 Snapshot 지원 8종에 들어 있다 [F10] — https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-attribute-deletionpolicy.html
오답 이유: A) 기본 동작은 삭제이며 EC2 Volume 은 RDS 같은 Snapshot 기본 예외가 아니다 [F8][F9] / C) Retain 은 리소스를 그대로 남길 뿐 스냅샷을 만들지 않고 남은 리소스는 계속 과금된다 [F8] / D) 드리프트 감지는 스택 밖 변경을 찾는 기능이다 [F11].

### Q3 (Skill 3.1.3 · intermediate)
문제: 스택 업데이트가 실패한 뒤 롤백도 UPDATE_ROLLBACK_FAILED 로 멈췄다. 이벤트를 보니 이전 구성으로 되돌려야 하는 데이터베이스 인스턴스를 누군가 콘솔에서 이미 삭제한 상태다. 가장 적절한 조치는?
- A) 아무 조치 없이 기다리면 CloudFormation 이 롤백을 자동으로 마무리한다.
- B) 삭제된 DB 를 원래 이름·속성으로 수동 재생성해 템플릿과 맞춘 뒤 업데이트 롤백을 계속한다.
- C) 드리프트 감지를 실행해 롤백을 자동 완료시킨다.
- D) 같은 템플릿으로 새 변경 세트를 만들어 즉시 실행한다.

정답: B
정답 근거: 스택 밖에서 바뀐 리소스는 원래 스택 템플릿과 같게 수동으로 맞춘 뒤 롤백을 계속한다 [F17] — https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/troubleshooting.html
오답 이유: A) 원인이 해결되지 않으면 롤백이 스스로 끝나지 않는다 [F17] / C) 드리프트 감지는 차이를 탐지할 뿐 롤백을 완료시키지 않는다 [F11] / D) 롤백이 끝나지 않은 스택에 새 변경을 적용하는 것은 해결책이 아니다 [F17].

### Q4 (Skill 3.1.4 · intermediate)
문제: 조직의 네트워크 계정이 소유한 VPC 서브넷에 같은 조직의 여러 멤버 계정이 EC2 인스턴스를 직접 시작하게 하고 싶다. 서브넷을 계정마다 복제하지 않으려면?
- A) AWS RAM 으로 서브넷을 공유하되, 먼저 RAM 에서 Organizations 공유를 활성화한다.
- B) CloudFormation StackSets 로 각 멤버 계정에 같은 서브넷 스택을 배포한다.
- C) 서브넷을 AMI 로 만들어 멤버 계정에 공유한다.
- D) 서브넷을 다른 리전으로 복사한다.

정답: A
정답 근거: 서브넷은 같은 조직 계정에 RAM 으로 공유하며 [F22], 조직 공유는 Organizations 공유를 켜야 가능하다 [F21] — https://docs.aws.amazon.com/ram/latest/userguide/getting-started.html
오답 이유: B) StackSets 는 계정마다 별도 스택 인스턴스를 만들어 서브넷이 복제된다 [F23] / C) AMI 는 인스턴스 이미지이며 서브넷과 무관하다 [F3] / D) 서브넷은 복사 대상이 아니며 RAM 공유는 리전 단위다 [F20].

### Q5 (Skill 3.1.5 · advanced)
문제: 새 버전 웹 애플리케이션을 별도 로드 밸런서 뒤 환경에 배포했다. 팀은 DNS 수준에서 전체 트래픽의 5% 만 새 환경으로 보내 검증하고 점차 비율을 올리려 한다. 어떤 Route 53 라우팅 정책을 쓰는가?
- A) 가중치(Weighted) 라우팅
- B) 지연 시간(Latency) 라우팅
- C) 장애 조치(Failover) 라우팅
- D) 단순(Simple) 라우팅

정답: A
정답 근거: 가중치 라우팅은 한 이름에 여러 리소스를 연결해 트래픽 비율을 정하며 새 버전 테스트에 유용하다 [F27] — https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy-weighted.html
오답 이유: B) 사용자와의 지연 시간을 기준으로 고르므로 비율 제어가 목적이 아니다 / C) 기본 리소스가 비정상일 때만 보조 리소스로 넘기는 용도다 / D) 하나의 리소스로 응답하는 단순 방식이라 비율을 나눌 수 없다. (B~D 는 Route 53 정책 일반 개념이며 §5 에 별도 인용하지 않았다.)
