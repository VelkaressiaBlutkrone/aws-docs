## 2. 핵심 개념 (한국어)

### 4.1.1 IAM 기능 구현 — 암호 정책·MFA·역할·ID 페더레이션·리소스 정책·정책 조건

**이 Skill의 핵심 난점**: IAM에는 "권한을 부여하는 정책"과 "상한만 정하는 정책"이 겹쳐 있고, 어떤 조건 키는 요청 종류에 따라 아예 존재하지 않는다. 그래서 *정책이 맞아 보이는데도 결과가 다르게 나오는* 상황이 생기고, 시험은 정의보다 "이 설정이면 실제로 어떻게 되는가"를 묻는다.

**(1) 평가 규칙 — 거부가 이기고, 상한은 교집합이다**
- 어느 정책 유형에서든 명시적 거부(Deny) 하나가 Allow를 이긴다 [F7]. 요청은 암묵적 거부에서 시작한다(S6).
- 권한 경계는 권한을 주지 않고 "ID 기반 정책이 줄 수 있는 최대치"만 정한다. 그래서 유효 권한은 ID 기반 정책과 경계의 교집합이다 [F8].
- 역할 세션에 전달하는 세션 정책도 같은 성격이다 — 역할의 권한을 넓히지 못하고 좁히기만 한다(S4).
- 같은 계정 안에서는 리소스 기반 정책이 주체를 직접 허용하면 ID 기반 정책이 따로 필요 없다(S4). 반면 **주체와 리소스가 서로 다른 계정이면 리소스 기반 정책(리소스 쪽)과 ID 기반 정책(주체 쪽) 둘 다** 있어야 한다 [F6]. 역할 신뢰 정책은 IAM이 지원하는 유일한 리소스 기반 정책 유형이다(S5).
- 리소스 기반 정책은 인라인 정책뿐이며 "관리형 리소스 기반 정책"은 없다(S5).

| 정책 유형 | 부착 대상 | 권한 부여? | 시험 포인트 |
|---|---|---|---|
| ID 기반(관리형/인라인) | 사용자·그룹·역할 (인라인도 그룹에 붙일 수 있음, S7) | 부여 | 가장 기본 |
| 리소스 기반 | 리소스(S3 버킷, KMS 키, 역할 신뢰 정책 …) | 부여 | 교차 계정은 양쪽 필요 [F6] |
| 권한 경계 | 사용자·역할 | 상한만 | 교집합 [F8] |
| SCP | Organizations 계정·OU | 상한만 | 4.1.3 참조 [F17] |
| 세션 정책 | AssumeRole 세션 | 상한만 | 권한 확대 불가 (S4) |

**(2) 암호 정책** (S1)
| 설정 | 값 | 비고 |
|---|---|---|
| 최소 길이(사용자 지정) | 6~128자 [F1] | 기본 정책(미설정 시)은 최소 8자 |
| 구성 규칙 | 대문자·소문자·숫자·비영숫자 중 선택 | 기본 정책은 4종 중 3종 이상 |
| 만료 | 1~1,095일 | 기본 정책은 만료 없음 |
| 재사용 방지 | 직전 암호 1~24개 | |
| 사용자 본인 변경 허용 | 계정 전체 설정 | 개별 사용자에게 정책을 붙이는 방식이 아님 |
- 암호 정책은 **IAM 사용자의 콘솔 암호**에만 해당한다. 사람 사용자는 임시 자격 증명 + IAM Identity Center를 권장한다(S2).

**(3) MFA** (S2, S3, S9)
- MFA 유형: 패스키·보안 키(FIDO), 가상 인증 앱(TOTP), 하드웨어 TOTP 토큰. **SMS MFA는 지원이 종료**됐다(S2). 루트 사용자와 IAM 사용자는 각각 최대 8개의 MFA 장치를 등록할 수 있다 [F2]. 루트 사용자 MFA는 모든 계정 유형에서 강제된다(S2).
- `aws:MultiFactorAuthPresent` 키는 **임시 자격 증명으로 한 요청**에만 요청 컨텍스트에 들어간다(S9). 장기 액세스 키로 서명한 CLI/API 호출에는 이 키가 없어서, `Bool` 연산자로 "false면 거부"를 쓰면 *키가 없는 요청은 조건이 불일치해 Deny가 적용되지 않는다*. 그래서 MFA 강제 Deny는 `BoolIfExists`를 쓴다(키가 없으면 조건을 참으로 취급) [F3].
- 판단 규칙: "MFA 없이는 MFA 등록 관련 작업만 허용하고 나머지는 Deny" → `Effect: Deny` + `NotAction`(MFA 등록·세션 토큰 관련 작업) + `BoolIfExists: aws:MultiFactorAuthPresent = false`(S3b). `IfExists`는 키가 요청에 없으면 조건을 참으로 평가하므로, 장기 자격 증명으로 CLI를 쓰는 사용자는 *거부*되고 MFA로 인증한 세션을 받아야 한다(S3b).

**(4) 역할과 STS** (S4)
- 역할 수임 세션 길이: `DurationSeconds` 유효 범위 900~43200초(15분~12시간) [F5]. 단 *해당 역할에 설정한 최대 세션 시간(1~12시간)* 이하여야 하고, 기본값은 3600초다(S4).
- **역할 체이닝**(역할 세션으로 다른 역할을 다시 수임)이면 AWS CLI·API 역할 세션이 최대 1시간으로 제한되고, 1시간을 넘는 값을 요청하면 작업이 실패한다 [F4]. 즉 "역할의 최대 세션 시간을 12시간으로 올렸는데 체이닝에서는 12시간 요청이 실패한다"가 전형적인 함정이다.
- 다른 계정의 역할을 수임할 때 역할 소유 계정의 관리자가 **ExternalId**를 요구하면 그 값을 함께 전달해야 한다(S4). (ExternalId의 목적 설명은 99-P5-G05 참조.) EC2에 역할을 붙일 때는 인스턴스 프로파일을 쓰고, 인스턴스 프로파일에는 IAM 역할을 **1개만** 담을 수 있다(S10b).

**(5) ID 페더레이션**
- SAML 2.0 기반 콘솔 SSO: 사용자는 조직 포털에서 인증받고, AWS 로그인 엔드포인트가 사용자를 대신해 임시 보안 자격 증명을 요청한 뒤 콘솔 URL로 리디렉션한다 [F9]. OIDC IdP는 OIDC 호환 IdP와 AWS 계정 사이의 신뢰를 설정한다(S8b).
- 여러 계정에 걸친 사람 사용자 접근은 IAM Identity Center로 중앙 관리하는 것이 권장 경로다 (4.1.3 참조).

**(6) 정책 조건 키 — 시험에서 자주 걸리는 것**
| 키 | 용도 | 함정 |
|---|---|---|
| `aws:MultiFactorAuthPresent` | MFA 사용 여부 | 임시 자격 증명 요청에만 존재 → `BoolIfExists` [F3] |
| `aws:SourceIp` | 요청자의 공인 IP 범위 | VPC 엔드포인트로 요청하면 키가 포함되지 않음 [F10]; 사설 IP 범위에는 쓸 수 없음(S9) → 엔드포인트 경로는 `aws:SourceVpce`/`aws:SourceVpc`(S9c) |
| `aws:RequestedRegion` | 요청 대상 리전 제한 | IAM 같은 글로벌 서비스 호출은 us-east-1 → 4.1.5 [F28][F29] |
| `aws:PrincipalOrgID` | 조직 소속 주체만 허용 | 계정 ID를 일일이 나열하는 대안. 조직 관리 계정에도 적용됨(S9) |

### 4.1.2 접근 문제 해결과 감사 — CloudTrail · IAM Access Analyzer · IAM 정책 시뮬레이터

**질문 → 도구 결정표** (아래가 이 Skill의 핵심 판단 규칙이다)
| 묻는 것 | 도구 | 핵심 사실 |
|---|---|---|
| 누가·언제·어떤 API를 호출했나(최근) | CloudTrail **이벤트 기록**(Event history) | 리전별 최근 90일 관리 이벤트의 조회·검색·다운로드가 가능한 불변 기록 [F11]; 조회 비용 없음(S10) |
| 이 정책 조합이 이 요청을 허용/거부하나(변경 전 검증) | IAM **정책 시뮬레이터** | SCP가 허용/거부하는지 알려 줌 [F13]; 권한 경계는 한 번에 1개만 시뮬레이션(S11); 일부 고급 구성에서는 실제 동작과 결과가 다를 수 있음(S11b) |
| 리소스가 외부(다른 계정·공개)에 열려 있나 | Access Analyzer **외부 액세스** 분석기 | 논리 기반 추론으로 리소스 기반 정책을 분석 [F12]; 신뢰 영역(조직/계정) 안의 공유는 결과로 안 나옴(S12) |
| 안 쓰는 역할·키·권한이 뭔가 | Access Analyzer **미사용 액세스** 분석기, 서비스 **마지막 액세스 정보** | 마지막 액세스 정보의 서비스 추적 기간은 최소 400일 [F15]; 작업 수준 정보는 데이터 영역 이벤트에는 없음(S13) |
| 최소 권한 정책을 만들고 싶다 | Access Analyzer **정책 생성** | CloudTrail 활동을 기반으로 최대 90일 기간을 분석(S12b) |
| 계정 전체의 암호·키·MFA 상태 스냅샷 | IAM **자격 증명 보고서** | 최대 4시간마다 1회 생성 [F14]; 대상은 암호·처음 2개 액세스 키·MFA 장치·X.509 인증서(S14) |
| 왜 AccessDenied인가 | 오류 메시지 문구 + `sts:DecodeAuthorizationMessage` | 디코드 결과에 명시적 거부인지, 명시적 허용 부재인지가 들어 있음 [F16] |

**AccessDenied 진단 절차** (이해 중심)
1. 오류 문구가 "with an explicit deny in a *type* policy"이면 명시적 거부다. 예: `with an explicit deny in a service control policy` → SCP에서 해당 작업의 Deny 문을 찾는다(S15). 문구가 "because no … policy allows …"이면 암묵적 거부 = Allow 부재(S15b).
2. 일부 AWS 작업은 인코딩된 권한 부여 메시지를 함께 돌려주며, 이는 `sts:DecodeAuthorizationMessage` 권한이 있는 주체만 풀 수 있다 — 디코드 결과에는 거부 원인(명시적 거부 vs 명시적 허용 부재), 요청한 주체·작업·리소스, 조건 키 값이 들어 있다 [F16].
3. 정책 시뮬레이터로 재현하되, 시뮬레이션과 실제가 다를 수 있음을 전제로 실환경에서 재확인한다(S11b).
4. 외부 노출·미사용 권한 점검은 사고 대응이 아니라 **지속 감사**이므로 Access Analyzer 결과를 EventBridge 등으로 연결해 운영한다.

### 4.1.3 다중 계정 전략의 안전한 구현 — AWS Organizations · SCP · IAM Identity Center (v1.1 변경)

**SCP가 하는 일과 하지 않는 일** (S16~S17)
| 사실 | 의미 | 근거 |
|---|---|---|
| 권한을 부여하지 않는다 | 허용하려면 ID/리소스 기반 정책이 따로 필요. SCP는 상한(가드레일) | [F17] |
| 관리 계정의 사용자·역할에는 영향 없음 | 워크로드를 관리 계정에 두면 가드레일이 안 먹힘 | [F18] |
| 서비스 연결 역할에 부착된 권한으로 수행하는 작업은 제한 못 함 | SLR 동작은 SCP 대상이 아님 | [F19] |
| 평가는 기본 거부 | 루트~OU~계정 경로의 **모든 수준**에 Allow가 있어야 허용(기본 `FullAWSAccess`가 이를 채워 줌) | [F20] |
| 모든 기능이 켜진 조직에서만 사용 | 통합 청구 전용 조직에서는 SCP 불가 | (S16) |
- 설계 전략: **거부 목록**(기본 `FullAWSAccess` 유지 + 필요한 Deny 추가) vs **허용 목록**(`FullAWSAccess` 제거 후 허용 서비스만 열거). 허용 목록은 한 수준에서 Allow가 빠지면 하위 전체가 막힌다(S17).
- **RCP(리소스 제어 정책)** 는 SCP의 쌍둥이로, 주체가 아니라 *리소스*의 최대 권한을 정하며 마찬가지로 권한을 부여하지 않는다(S18). 요청 평가에서 SCP와 함께 평가된다(S6). v1.1 Skill 문구에는 SCP만 나오므로 RCP는 보조 지식이다(99 참조).

**조직 차원의 감사·접근 통합**
- 조직 추적(organization trail)은 관리 계정과 모든 멤버 계정의 이벤트를 기록하고(S19), 멤버 계정은 볼 수는 있어도 수정·삭제할 수 없다(S19b).
- **IAM Identity Center**: 권한 세트(IAM 정책 묶음 템플릿)를 사용자/그룹에 할당하면 각 대상 계정에 IAM Identity Center가 제어하는 IAM 역할이 만들어진다 [F21]. 하나의 권한 세트를 여러 계정에 할당할 수 있다(S20). 외부 IdP(SAML 2.0)를 연결하고 SCIM으로 동기화하는 구성이 가능하다(S20b).
- **AWS Control Tower** 컨트롤은 세 종류다 — 예방(SCP 등으로 구현), 탐지(AWS Config 규칙), 사전(CloudFormation hooks) (S21). 예방 컨트롤(SCP)은 관리 계정에는 효과가 없다(S21b).
- **루트 자격 증명 중앙 관리**: 멤버 계정의 루트 자격 증명을 관리 계정/위임 관리자가 제거할 수 있고(S22), Organizations에서 새로 만든 계정에는 기본적으로 루트 자격 증명이 없다(S22).

### 4.1.4 Trusted Advisor 보안 검사 결과 기반 교정

**무엇이 열려 있는가(플랜) — 최근에 바뀐 영역이다**
- Trusted Advisor 전체 점검은 **Business Support+, Enterprise Support, Unified Operations** 플랜 고객에게 제공된다 [F22]. Developer Support와 Business Support는 2027-01-01에 종료 예고(S23). 따라서 시험 문구가 옛 이름(Business/Enterprise)을 써도 "유료 상위 플랜 = 전체 점검"이라는 구조로 읽는다.
- Basic(및 Developer) 플랜은 콘솔에서 **Service Limits 전 항목**과 보안·내결함성 일부(EBS 공개 스냅샷, RDS 공개 스냅샷, S3 버킷 권한, 루트 MFA, 특정 포트 무제한 보안 그룹, STS 글로벌 엔드포인트 사용)만 본다 [F23](S24). Basic에서는 자동 갱신이 없어 보안 점검을 **수동 새로고침**해야 한다(S23).

**점검 결과 → 교정 매핑** (S25)
| 점검(보안 범주) | 위험 | 교정 |
|---|---|---|
| Amazon S3 Bucket Permissions | 공개/인증된 모든 AWS 사용자에게 열린 버킷 | 개방 필요성 검토 후 권한 축소, **S3 Block Public Access** 사용 |
| Exposed Access Keys | 공개 저장소 등에 노출된 키 | **해당 액세스 키를 즉시 삭제**하고 계정의 비인가 사용 점검 [F25] |
| MFA on root account | 루트 MFA 미설정 | 독립/관리 계정은 MFA 장치 활성화, **멤버 계정은 중앙 루트 액세스 관리**로 루트 자격 증명 제거(S25) |

**자동화·조직 운영**
- 점검 상태 변화는 EventBridge로 감지할 수 있다 — 예: S3 버킷 권한이 바뀌면 해당 점검 상태가 바뀌고, EventBridge가 이를 감지해 알린다 [F24]. 이 모니터링은 유료 플랜 기능이다(S23). TA 이벤트의 detail-type은 `Trusted Advisor Check Item Refresh Notification` 등이다(S26).
- **조직 보기(Organizational view)**: 모든 기능이 켜진 조직의 관리 계정(유료 플랜 필요)에서 활성화하면 멤버 계정 점검 결과를 보고서(최대 50개)로 집계한다(S27).
- Security Hub CSPM을 켜 두면 그 결과를 Trusted Advisor 콘솔에서도 볼 수 있다(S25).

### 4.1.5 규정 준수 요구 사항 적용과 지속적 모니터링 — 리전·서비스 선택 · AWS Config conformance packs (v1.1 변경)

**리전·서비스 선택 — "예방"으로 강제하는 방법**
- 규정(데이터 거주 등)이 걸린 워크로드는 **규정 준수가 다른 리전 선택 요소(지연, 비용, 서비스 가용성)보다 우선**한다(S28).
- SCP로 리전을 제한할 때는 `aws:RequestedRegion`을 쓴다 — 허용 리전 목록 밖의 요청을 `Deny`하는 방식(`StringNotEquals`) [F28](S29). 단 **IAM 같은 글로벌 서비스의 엔드포인트는 us-east-1**이라서 "us-west-2가 아니면 전부 거부"하면 IAM 호출이 항상 실패한다 [F29]. 그래서 글로벌 서비스(공식 예시: cloudfront:*, iam:*, organizations:*, route53:*, support:*)를 `NotAction`으로 예외 처리한다(S9, S29).
- **Control Tower 리전 거부 컨트롤**: 랜딩 존 전체에 적용되는 컨트롤은 개별 OU에 설정할 수 없고(S30), 홈 리전은 거부할 수 없다 [F30]. OU 단위로 리전을 지정하는 별도 컨트롤이 있다(S30).
- 서비스 선택: AWS가 공개하는 "규정 준수 프로그램별 범위 서비스" 목록에 없다는 사실이 곧 *그 서비스를 쓸 수 없다*는 뜻은 아니다(S31). 보고서·약관은 **AWS Artifact**에서 내려받고 수락한다(S32).

**탐지·교정으로 "지속적으로" 맞추는 방법 — AWS Config**
- 관리형 규칙(미리 정의된 규칙)으로 시작한다(S33). 규칙 평가 트리거는 **구성 변경 / 주기적 / 하이브리드** 3종이다(S34).
- **적합성 팩(conformance pack)** = AWS Config 규칙과 교정 작업을 묶어 한 단위로 배포하는 모음 [F26]. YAML 템플릿으로 만들고(S35), 조직 내 멤버 계정에 중앙에서 배포·갱신·삭제한다(S35b). 여러 계정·리전 결과는 **집계자(aggregator)** 로 모아 본다(S36).
- 비준수 리소스의 교정은 Systems Manager Automation 문서로 수행한다 [F27].
- 운영 루프: (예방) SCP/Control Tower 리전·서비스 가드레일 → (탐지) Config 규칙·적합성 팩 → (교정) SSM Automation / EventBridge → (집계) Config 집계자·Security Hub (4.2.5).

## 3. 시험에서 묻는 방식 (가이드 Skill 문구 기반 추정 — 실제 문항 아님)
이 절은 AWS가 공개한 Skill 문구에서 추론한 것이며, 실제 기출을 안다는 주장이 아니다.
1. **정책 평가 결과 맞히기** — 근거 문구: 4.1.1 "policy conditions", 4.1.3 "service control policies". 판단 기준: 명시적 Deny 우선 [F7]; SCP·권한 경계는 상한일 뿐 부여하지 않음 [F17][F8]; 관리 계정은 SCP 제외 [F18]; 교차 계정은 양쪽 정책 필요 [F6]; MFA 조건은 `BoolIfExists` [F3].
2. **접근 문제에 맞는 진단 도구 고르기** — 근거 문구: 4.1.2 "Troubleshoot and audit access issues by using AWS tools (CloudTrail, IAM Access Analyzer, IAM policy simulator)". 판단 기준: 누가/언제=CloudTrail [F11]; 정책 효과 사전 검증=시뮬레이터 [F13]; 외부 노출=Access Analyzer [F12]; 미사용 권한=마지막 액세스 정보 [F15]; 키·MFA 상태=자격 증명 보고서 [F14].
3. **Trusted Advisor 결과를 교정으로 연결하기** — 근거 문구: 4.1.4 "Implement remediation based on the results of AWS Trusted Advisor security checks". 판단 기준: 노출된 키는 삭제 [F25]; S3 권한은 Block Public Access; 플랜별 점검 범위 [F22][F23]; 상태 변화 자동 감지는 EventBridge [F24].
4. **규정 요구를 지속적으로 강제하는 구성 고르기** — 근거 문구: 4.1.5 "Region and service selections, AWS Config conformance packs". 판단 기준: 예방(SCP/Control Tower 리전 거부, 글로벌 서비스 예외 [F29][F30]) vs 탐지·교정(Config 적합성 팩 [F26], SSM Automation 교정 [F27]).

## 4. 흔한 함정 · 혼동 짝
| 혼동 짝 | 구분 기준 | 근거 |
|---|---|---|
| SCP vs 권한 경계 vs ID 기반 정책 | 둘 다 상한(교집합)일 뿐 부여는 ID/리소스 기반 정책. 경계=개별 사용자·역할, SCP=Organizations 계정·OU | [F8][F17] |
| SCP vs RCP | SCP=주체(IAM 사용자·역할)의 최대 권한, RCP=리소스의 최대 권한. 둘 다 부여 안 함 | [F17] (S18) |
| Bool vs BoolIfExists | 키가 없는 요청(장기 키 CLI)에서 Bool은 불일치 → Deny 미적용, BoolIfExists는 키 부재를 참으로 처리 | [F3] |
| aws:SourceIp vs aws:SourceVpce/aws:SourceVpc | 공인 IP 기반 vs VPC 엔드포인트 경유. 엔드포인트 요청에는 SourceIp가 없음 | [F10] |
| 역할 최대 세션(1~12시간) vs 역할 체이닝(1시간) | 체이닝 시 CLI/API 세션은 1시간 상한 | [F4][F5] |
| 교차 계정 접근: 리소스 정책만 vs 양쪽 | 다른 계정이면 ID 기반 정책도 필요, 같은 계정이면 리소스 정책만으로 충분 | [F6] |
| CloudTrail 이벤트 기록 vs 추적(trail) | 이벤트 기록=최근 90일·관리 이벤트·리전별, 장기 보관은 trail/Lake | [F11] |
| 정책 시뮬레이터 vs DecodeAuthorizationMessage | 시뮬레이터=가상 시나리오로 사전 검증, Decode=이미 발생한 거부의 원인 | [F13][F16] |
| Access Analyzer(외부) vs 마지막 액세스 vs 자격 증명 보고서 | 외부 노출 / 미사용 권한(서비스·작업 단위) / 자격 증명 상태(키·MFA·암호) | [F12][F15][F14] |
| Trusted Advisor 전체 점검 vs Basic 점검 | 전체=Business Support+/Enterprise/Unified Operations. Basic=Service Limits 전체 + 보안 일부 | [F22][F23] |
| SCP/Control Tower 예방 vs Config 탐지·교정 | 예방=애초에 못 하게 막음(관리 계정 제외), 탐지·교정=발생 후 평가·수정 | [F18][F26][F27] |
| Control Tower 랜딩 존 리전 거부 vs OU 리전 거부 | 랜딩 존용은 OU별 설정 불가, 홈 리전은 거부 불가 | [F30] (S30) |
| 리전 제한 SCP vs 글로벌 서비스 | IAM 호출은 us-east-1로 가므로 NotAction 예외 없이는 실패 | [F28][F29] |

## 6. 자가 점검 문항 후보 (3~5) — 후보일 뿐, 검증 아님

### Q1 (Skill 4.1.1 · intermediate)
문제: 보안팀은 "MFA로 인증하지 않은 사용자는 MFA 등록 관련 작업을 제외한 모든 작업을 거부"하는 ID 기반 정책을 만들었다. 조건은 `{"Bool": {"aws:MultiFactorAuthPresent": "false"}}`다. 그런데 장기 액세스 키로 AWS CLI를 호출하는 IAM 사용자는 MFA 없이도 S3 작업을 계속 수행한다. 가장 적절한 수정은?
- A) 조건 연산자를 `BoolIfExists`로 바꾼다.
- B) 조건 연산자를 `StringEquals`로 바꾼다.
- C) 해당 사용자에게 권한 경계를 부여한다.
- D) 정책을 관리형 정책에서 인라인 정책으로 옮긴다.
정답: A
정답 근거: 장기 자격 증명(액세스 키) 요청에는 MFA 컨텍스트 키가 없어 `Bool`로는 평가할 수 없고, 그래서 Deny가 적용되지 않는다. 키가 없을 때도 조건을 참으로 처리하는 `BoolIfExists`를 써야 한다. [F3] — https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_examples_ec2_require-mfa.html
오답 이유: B) 연산자 종류를 바꿔도 "키 부재" 문제는 해결되지 않는다 / C) 권한 경계는 권한 상한을 정할 뿐 MFA 여부를 강제하지 않는다 [F8] / D) 정책 부착 방식(관리형/인라인)은 조건 평가와 무관하다.

### Q2 (Skill 4.1.2 · foundational)
문제: 감사팀은 조직 전체에서 다른 AWS 계정이나 인터넷에 공유된 S3 버킷, IAM 역할, KMS 키를 지속적으로 찾아내려 한다. 어떤 기능을 사용해야 하는가?
- A) IAM 자격 증명 보고서
- B) IAM Access Analyzer의 외부 액세스 분석기
- C) CloudTrail 이벤트 기록(Event history)
- D) IAM 정책 시뮬레이터
정답: B
정답 근거: 외부 액세스 분석기는 논리 기반 추론으로 리소스 기반 정책을 분석해, 신뢰 영역 밖의 외부 주체에게 열린 리소스를 찾는다. [F12] — https://docs.aws.amazon.com/access-analyzer/latest/APIReference/Welcome.html
오답 이유: A) 자격 증명 보고서는 IAM 사용자의 암호·키·MFA 상태를 나열할 뿐 리소스 정책 노출은 보지 않는다 [F14] / C) 이벤트 기록은 최근 90일 관리 이벤트 조회 도구다 [F11] / D) 시뮬레이터는 특정 정책 조합의 허용 여부를 가상으로 검증하는 도구다 [F13].

### Q3 (Skill 4.1.3 · intermediate)
문제: 조직의 한 OU에 "ec2:* 거부" SCP를 연결했다. OU의 멤버 계정에서는 EC2 인스턴스를 만들 수 없는데, 관리 계정의 IAM 관리자는 여전히 인스턴스를 만든다. 이유로 가장 적절한 것은?
- A) SCP는 관리 계정의 사용자와 역할에는 영향을 주지 않는다.
- B) SCP는 Allow 문이 있을 때만 평가되므로 Deny SCP는 동작하지 않는다.
- C) 관리 계정에는 SCP 대신 RCP가 자동 적용된다.
- D) SCP 변경은 관리 계정에 24시간 후에 반영된다.
정답: A
정답 근거: SCP는 멤버 계정에만 적용되고 관리 계정의 사용자·역할에는 영향이 없다. 그래서 워크로드를 관리 계정에 두지 않는 것이 원칙이다. [F18] — https://docs.aws.amazon.com/organizations/latest/userguide/orgs_manage_policies_scps.html
오답 이유: B) 명시적 Deny는 항상 유효하며 SCP는 권한을 부여하지 않는다 [F7][F17] / C) RCP는 SCP가 아니라 리소스 쪽 상한이며 관리 계정의 리소스에도 영향을 주지 않는다(S20b) / D) 관리 계정에서 SCP가 안 먹는 것은 반영 지연이 아니라 SCP의 적용 범위 규칙 때문이다 [F18].

### Q4 (Skill 4.1.4 · intermediate)
문제: Enterprise Support 플랜을 쓰는 회사가 Trusted Advisor의 "Amazon S3 Bucket Permissions" 점검 상태가 바뀔 때 자동으로 SNS 알림을 받으려 한다. 가장 적절한 구성은?
- A) Trusted Advisor 점검 상태 변화를 감지하는 EventBridge 규칙을 만들고 SNS 토픽을 대상으로 지정한다.
- B) CloudTrail Insights를 켜서 S3 버킷 정책 변경 이벤트를 감지한다.
- C) IAM 자격 증명 보고서를 매일 생성해 S3 권한 변경을 비교한다.
- D) 정책 시뮬레이터를 예약 실행해 S3 접근 결과를 비교한다.
정답: A
정답 근거: S3 버킷 권한이 바뀌면 Trusted Advisor 점검 상태가 바뀌고, EventBridge로 이를 감지해 알림을 보낼 수 있다. 상태 모니터링은 유료 플랜(Business Support+/Enterprise/Unified Operations)에서 쓰는 기능이다. [F24][F22] — https://docs.aws.amazon.com/awssupport/latest/user/cloudwatch-ta.html
오답 이유: B) Insights는 비정상 API 호출량 탐지이며 Trusted Advisor 점검 상태와 무관하다 / C) 자격 증명 보고서는 IAM 사용자 자격 증명 상태 도구다 [F14] / D) 시뮬레이터는 가상 검증 도구다 [F13].

### Q5 (Skill 4.1.5 · advanced)
문제: 한 OU에 "eu-west-1 이외의 리전 요청은 모두 거부"하는 SCP(`aws:RequestedRegion`이 eu-west-1이 아니면 Deny, 서비스 예외 없음)를 적용했다. 적용 후 해당 OU의 계정에서 IAM 역할을 만들 수 없게 되었다. 가장 적절한 수정은?
- A) IAM 같은 글로벌 서비스 작업을 `NotAction`으로 제외한다.
- B) SCP를 계정이 아닌 조직 루트에 이동한다.
- C) SCP 대신 권한 경계를 사용한다.
- D) eu-west-1 외에 모든 리전을 `aws:RequestedRegion` 허용 목록에 넣는다.
정답: A
정답 근거: IAM은 글로벌 서비스로 엔드포인트가 us-east-1이라 IAM 호출은 항상 us-east-1로 요청된다. 따라서 리전 제한 Deny에서 글로벌 서비스 작업을 NotAction으로 제외해야 한다. [F29] [F28] — https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_condition-keys.html
오답 이유: B) 적용 범위를 넓혀도 us-east-1 요청은 계속 거부된다 / C) 권한 경계는 리전 거부 문제를 해결하지 못한다 [F8] / D) 리전 제한 의도를 무력화한다.
