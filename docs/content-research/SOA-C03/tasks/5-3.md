> 읽는 법: `[F#]`는 §5 사실 번호. `(추가 ①…)`은 §5(최대 30행)에 싣지 못한 보조 확인 사실로, 각 소절 끝 "추가 확인 사실" 목록에 URL을 병기했다. 추가 확인 사실은 원문 인용 기계검증 대상이 아니므로 저작 전 URL에서 재확인할 것.

### 5.3.1 VPC 구성 문제 해결 (서브넷·라우팅 테이블·NACL·SG·TGW·NAT GW)
- **먼저 도구를 구분한다.** Reachability Analyzer는 구성(보안 그룹·네트워크 ACL·라우팅 테이블·로드 밸런서 등)을 모델링해 도달 가능 여부를 판정하고, 도달할 수 없으면 **차단 구성요소**를 알려 준다 [F1]. 패킷을 실제로 보내지도 데이터 플레인을 분석하지도 않으므로 [F2], "구성은 맞는데 실제로 안 되는" 문제(대상 헬스, 애플리케이션 오류 등)는 이 도구로 잡히지 않는다(추가 ①). 실제로 오간 트래픽의 흔적은 Flow Logs(→ 5.3.2)로 본다.
- **SG vs NACL = 응답 트래픽을 다루는 방식.** NACL은 stateless라서 허용된 요청의 **응답도 NACL 규칙 평가를 받는다** [F3](같은 페이지: 보안 그룹은 stateful이라 응답이 자동 허용). 그래서 커스텀 NACL에서는 요청 방향 규칙과 별개로 응답(이페머럴 포트) 방향 규칙이 필요하고, 그 포트 범위는 요청을 시작한 **클라이언트의 운영체제 등에 따라 다르다** [F4].
- **라우팅 테이블 = 더 구체적인 경로가 이긴다.** NAT 게이트웨이를 통한 인터넷 접속이 안 될 때 공식 점검 항목에 "인터넷 트래픽을 NAT가 아닌 다른 장치(VGW·IGW)로 보내는 **더 구체적인 경로**가 없는가"가 있다 [F5]. (경로 우선순위 전체: 추가 ②)
- **NAT 게이트웨이 장애 패턴.** 유휴 연결이 350초 이상이면 타임아웃된다 [F7]. 그 밖의 원인(IP 단편화·IPsec 미지원·포트/연결 한도)과 지표는 추가 ③, 신규 리전 NAT 게이트웨이는 추가 ⑤.
- **Transit Gateway.** TGW 라우팅 테이블의 `blackhole` 경로는 일치하는 트래픽을 폐기한다 [F6]. 어태치먼트 연관·전파·정적/전파 우선순위·폐기 지표는 추가 ④.

**표 초안 — 증상 → 먼저 볼 곳**
| 증상 | 먼저 의심 | 확인 도구·지표 | 근거 |
|---|---|---|---|
| 요청은 들어오는데 응답이 안 돌아옴(커스텀 NACL) | NACL의 응답 방향(이페머럴 포트) 규칙 누락 | Flow Logs의 응답 방향 REJECT, 서브넷 NACL 규칙 | [F3][F4][F9] |
| 어느 구성요소가 막는지 모름 | SG·NACL·라우팅 중 하나 | Reachability Analyzer 설명 코드 | [F1][F2] |
| 프라이빗 서브넷이 NAT를 안 타고 엉뚱한 경로로 나감 | 더 구체적인 경로가 NAT 경로를 가로챔 | 서브넷 라우팅 테이블 | [F5] |
| NAT 경유 연결이 일정 시간 뒤 끊김 | NAT GW 유휴 타임아웃 350초 | TCP keepalive, 지표 IdleTimeoutCount(추가 ③) | [F7] |
| TGW 경유 트래픽이 사라짐 | blackhole 경로·경로 부재·연관 누락 | TGW 라우팅 테이블, 폐기 지표(추가 ④) | [F6] |

**추가 확인 사실(§5 미등록 — URL 재확인):**
- ① Reachability Analyzer 제약: IPv4 리소스만 분석, 출발지·도착지는 같은 Region, 등록된 대상(target)의 헬스는 고려하지 않음, TGW Connect 어태치먼트는 그 지점까지만 분석 — https://docs.aws.amazon.com/vpc/latest/reachability/how-reachability-analyzer-works.html . 설명 코드 예: ENI_SG_RULES_MISMATCH, SUBNET_ACL_RESTRICTION, NO_ROUTE_TO_DESTINATION, TGW_ATTACH_MISSING_TGW_RTB_ASSOCIATION, NGW_REQUIRES_SOURCE_IN_VPC(NAT GW는 피어링·VPN·Direct Connect에서 시작된 트래픽을 전달 못 함) — https://docs.aws.amazon.com/vpc/latest/reachability/explanation-codes.html
- ② 경로 우선순위: 가장 구체적인 경로(최장 접두사) → 정적 경로 → 프리픽스 리스트 경로 → 전파 경로(Direct Connect BGP → VPN 정적 → VPN BGP) — https://docs.aws.amazon.com/vpc/latest/userguide/route-tables-priority.html
- ③ NAT GW: TCP·ICMP IP 단편화 미지원, IPsec 직접 미지원(NAT-T로 UDP 캡슐화), 350초 유휴 시 RST 반환(조치: 트래픽 유지 또는 TCP keepalive를 350초 미만으로), 새 IPv4 주소마다 동시 연결 최대 55,000, 지표 ErrorPortAllocation(>0이면 소스 포트 할당 실패=동시 연결 과다)·IdleTimeoutCount·PacketsDropCount — https://docs.aws.amazon.com/vpc/latest/userguide/nat-gateway-troubleshooting.html , https://docs.aws.amazon.com/vpc/latest/userguide/metrics-dimensions-nat-gateway.html
- ④ TGW: 어태치먼트는 라우팅 테이블 1개에만 연관(여러 테이블로 전파는 가능), 같은 목적지의 정적 경로가 전파 경로보다 우선, VPC 어태치먼트 후 VPC 서브넷 라우팅 테이블에도 TGW 경로 필요, 폐기 지표 PacketDropCountNoRoute(경로 미일치)·PacketDropCountBlackhole(blackhole 일치) — https://docs.aws.amazon.com/vpc/latest/tgw/how-transit-gateways-work.html , https://docs.aws.amazon.com/vpc/latest/tgw/transit-gateway-cloudwatch-metrics.html
- ⑤ 리전 NAT 게이트웨이(신규 유형): 워크로드가 있는 AZ로 자동 확장(새 AZ 반영에 최대 60분), 기존 NAT는 "zonal NAT gateway"로 구분, 프라이빗 연결용으로는 zonal 권장 — https://docs.aws.amazon.com/vpc/latest/userguide/nat-gateways-regional.html
- ⑥ 로드 밸런서 서브넷·NACL: 인터넷 연결 ALB는 퍼블릭 서브넷에 배치해야 하고, 대상→ALB 노드 방향 이페머럴 포트(1024-65535)를 NACL이 막으면 504 — https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-troubleshooting.html

### 5.3.2 네트워킹 로그 수집·해석 (Flow Logs·ELB·WAF·CloudFront·컨테이너)
- **Flow Logs 해석 규칙.** `action=REJECT`는 "보안 그룹 또는 네트워크 ACL이 허용하지 않은 트래픽"이다 [F9]. 보안 그룹이 인바운드를 거부해도 REJECT 레코드가 남는다 [F10]. 따라서 **REJECT만으로 SG와 NACL을 구분할 수 없다.** 단서는 패턴이다: 같은 페이지 예시에서 요청은 ACCEPT, 응답이 REJECT이면 NACL(stateless)이 응답을 막은 경우였다 [F3].
- **로그에 없는 트래픽이 있다.** Amazon DNS 서버로의 질의 같은 트래픽은 Flow Logs에 기록되지 않는다 [F8] — "로그에 흔적이 없다"가 곧 "막혔다/없었다"는 아니다(제외 목록 전체: 추가 ①).
- **ELB 액세스 로그.** ALB의 `target_status_code`는 대상과 연결이 맺어지고 대상이 응답한 경우에만 기록되고 아니면 `-`이다 [F11]. LB가 만든 응답 코드는 `elb_status_code`에 남는다(추가 ③). 로그는 기본 비활성이라 먼저 켜야 한다(추가 ③).
- **AWS WAF 웹 ACL 로그.** CloudWatch Logs로 보낼 때 로그 그룹 이름은 `aws-waf-logs-`로 시작해야 한다 [F12] (S3 버킷·Firehose도 같은 접두; 추가 ④).
- **CloudFront 로그.** 표준 로그는 legacy(S3 전용)와 v2(CloudWatch Logs·Firehose·S3)가 있다 [F13]. 지연·실시간 로그는 추가 ⑤.
- **컨테이너 로그.** ECS의 `awslogs` 로그 드라이버는 컨테이너의 STDOUT/STDERR 로그를 Docker에서 CloudWatch Logs로 전달한다 [F14]. EKS 컨트롤 플레인 로그는 기본 비활성이다(추가 ⑥).

**표 초안 — 로그 종류 비교**
| 로그 | 기록 대상 | 보내는 곳 | 해석·설정 포인트 | 근거 |
|---|---|---|---|---|
| VPC Flow Logs | VPC·서브넷·ENI의 IP 트래픽 메타데이터 | CloudWatch Logs·S3·Amazon Data Firehose(추가 ①) | REJECT=SG 또는 NACL 불허 / 일부 트래픽 비기록 | [F8][F9][F10] |
| ELB 액세스 로그 | LB가 처리한 요청 | S3(레거시), ALB는 신규 CloudWatch Logs 통합(추가 ③) | target_status_code `-` 의미 | [F11] |
| WAF 웹 ACL 로그 | 웹 ACL이 평가한 요청 | CloudWatch Logs·S3·Firehose(추가 ④) | 대상 이름 `aws-waf-logs-` 접두 | [F12] |
| CloudFront 로그 | 뷰어 요청 | 표준 v2: CloudWatch Logs·Firehose·S3 / legacy: S3 / 실시간: Kinesis Data Streams(추가 ⑤) | legacy는 S3 전용 | [F13] |
| 컨테이너 로그 | ECS 컨테이너 STDOUT/STDERR | CloudWatch Logs(awslogs), EKS는 별도(추가 ⑥) | 드라이버가 로그를 그대로 전달 | [F14] |

**추가 확인 사실(§5 미등록 — URL 재확인):**
- ① Flow Logs: 대상 CloudWatch Logs·S3·Amazon Data Firehose — https://docs.aws.amazon.com/vpc/latest/userguide/flow-logs.html ; 최대 집계 간격 기본 10분(1분 선택 가능), 전달은 보통 CloudWatch Logs 약 5분·S3 약 10분이며 best effort, log-status가 SKIPDATA면 용량 제약 등으로 일부 레코드 누락, 원본 IP는 pkt-srcaddr·pkt-dstaddr로 확인 — https://docs.aws.amazon.com/vpc/latest/userguide/flow-log-records.html ; 생성 후 구성·레코드 형식 변경 불가(삭제 후 재생성), 비기록 트래픽에 169.254.169.254(메타데이터)·169.254.169.123(Time Sync)·DHCP·Windows 라이선스 활성화·기본 VPC 라우터 예약 IP·ARP 등 포함 — https://docs.aws.amazon.com/vpc/latest/userguide/flow-logs-limitations.html
- ② CloudWatch Logs Insights에서 Flow Logs를 조회하는 샘플 쿼리(상위 전송량, SKIPDATA 확인 등) — https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/CWL_QuerySyntax-examples.html
- ③ ELB: 액세스 로그는 기본 비활성이며 S3에 압축 저장, 로드 밸런서 노드별 5분 간격 게시, `request_processing_time`=-1은 LB가 요청을 대상에 보내지 못했다는 뜻 — https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-access-logs.html ; ALB는 CloudWatch Logs·Firehose·S3로 보내는 신규 통합(access/connection/health check 로그)도 제공하고 레거시 로그는 유지 — https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-cloudwatch-logs.html ; NLB 액세스 로그는 TLS 리스너가 있을 때 TLS 요청만 기록 — https://docs.aws.amazon.com/elasticloadbalancing/latest/network/load-balancer-access-logs.html
- ④ WAF: 대상은 CloudWatch Logs 로그 그룹·S3 버킷·Firehose 전송 스트림 — https://docs.aws.amazon.com/waf/latest/developerguide/logging.html ; 필드 가림(URI path·Query string·Single header·HTTP method)과 로그 필터링 지원, 전달은 best effort라 100% 미만일 수 있음 — https://docs.aws.amazon.com/waf/latest/developerguide/logging-management.html
- ⑤ CloudFront: 표준 로그는 시간당 여러 번 전달되며 보통 1시간 이내(최대 24시간 지연 가능) — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/standard-logs-reference.html ; 실시간 로그는 수초 내 Kinesis Data Streams로 전달되고 샘플링 비율을 지정 — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/real-time-logs.html
- ⑥ 컨테이너: Fargate는 task definition에 awslogs `logConfiguration` 필요, EC2 시작 유형은 컨테이너 에이전트 1.9.0 이상과 `logs:CreateLogStream`·`logs:PutLogEvents` 권한 필요 — https://docs.aws.amazon.com/AmazonECS/latest/developerguide/using_awslogs.html ; EKS 컨트롤 플레인 로그는 기본으로 CloudWatch Logs에 보내지지 않으며 로그 유형별로 켜고 로그 그룹은 `/aws/eks/<cluster>/cluster` — https://docs.aws.amazon.com/eks/latest/userguide/control-plane-logs.html

### 5.3.3 CloudFront 캐싱 문제 식별·해결
- **식별(무엇이 캐시를 못 타는가).** 로그의 `x-edge-result-type` 중 `RefreshHit`는 "캐시에 있었지만 만료되어 오리진에 최신 여부를 확인한 요청"이다 [F15] (Hit·Miss와 구분). 적중률 자체는 추가 지표 Cache hit rate로 본다 — 별도 활성화·추가 비용이 필요하다 [F16].
- **적중률이 낮을 때.** 캐시 키에는 응답을 실제로 바꾸는 값만 넣는다 [F17]. 불필요한 쿼리 문자열·쿠키·헤더를 키에 넣으면 같은 객체가 여러 개로 쪼개져 캐시된다(구체 요령: 추가 ①).
- **옛 콘텐츠가 보이거나 TTL이 기대와 다를 때.** 캐시 정책을 쓰지 않으면 기본 TTL은 24시간이다 [F18]. 최소 TTL=0이고 오리진이 `Cache-Control: max-age`를 보내면 max-age와 CloudFront **최대 TTL 중 작은 값**만큼 캐시한다 [F19]. 최소 TTL>0이면 계산이 달라지고 `no-store`도 무시될 수 있다(추가 ②). 즉시 갱신 수단(무효화·버전 파일명)은 soa-t5-3에서 다루며 보강은 추가 ④.
- **오리진 오류가 한동안 계속 보일 때.** 4xx/5xx 응답도 엣지에 캐시되고 오류 캐싱 최소 TTL의 기본값은 10초다 [F20] (캐시 대상 상태 코드: 추가 ③).

**표 초안 — 증상 → 원인 → 조치**
| 증상 | 가능한 원인 | 조치 | 근거 |
|---|---|---|---|
| 오리진 요청이 많고 Cache hit rate가 낮음 | 캐시 키에 불필요한 값(쿼리·쿠키·헤더) 포함 | 캐시 정책에서 필요한 값만 포함, 쿼리 대소문자·순서 통일(추가 ①) | [F16][F17] |
| 파일을 바꿨는데 최대 24시간 옛 버전 | 캐시 정책 미사용이면 기본 TTL 24시간 / 오리진 헤더 없음 | Cache-Control 설정, 무효화 또는 버전 파일명(추가 ④) | [F18][F19] |
| 로그에 RefreshHit가 많음 | 객체가 만료되어 재검증 | max-age 연장, stale 지시자(추가 ②) | [F15][F19] |
| 오리진 복구 후에도 잠시 같은 오류 | 오류 응답 캐싱 | 오류 캐싱 최소 TTL 확인·조정 | [F20] |

**추가 확인 사실(§5 미등록 — URL 재확인):**
- ① 적중률 개선: 오리진이 서로 다른 객체를 돌려주는 쿼리 문자열만 전달, 같은 매개변수는 같은 대소문자·같은 순서로 사용, 필요한 쿠키만 전달, 정적/동적 콘텐츠는 캐시 동작 분리, `User-Agent` 대신 CloudFront 기기 유형 헤더 사용, Origin Shield로 오리진 요청 집약 — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cache-hit-ratio.html
- ② TTL 상호작용: 최소 TTL>0이면 오리진이 `no-cache`·`no-store`·`private`을 보내도 정책의 최소 TTL이 적용(경고 박스), `max-age`와 `Expires`를 둘 다 보내면 `max-age`만 사용, 뷰어 요청의 `Cache-Control`·`Pragma`로 오리진 재요청 강제 불가, `stale-while-revalidate`·`stale-if-error` 지원(최대 TTL까지) — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Expiration.html
- ③ 오류 캐싱: 404·414·500·501·502·503·504를 캐시, `CachingDisabled` 관리형 캐시 정책이면 이 오류들도 캐시하지 않음 — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/HTTPStatusCodes.html
- ④ 무효화: 자주 갱신하면 파일 버전 관리를 우선 권장, 월 첫 1,000개 무효화 경로 무료이며 `*` 와일드카드 경로는 파일 수와 무관하게 1경로, 신규 캐시 태그 무효화 — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/Invalidation.html , https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/PayingForInvalidation.html , https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/invalidation-by-tags.html
- ⑤ 확인 수단: 로그 `x-edge-result-type` 값(Hit·RefreshHit·Miss·Error·LimitExceeded·CapacityExceeded·Redirect 등) — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/standard-logs-reference.html ; 콘솔 캐시 통계는 Hit·Miss·Error 비율(RefreshHit 제외) — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cache-statistics.html ; 응답 헤더 정책의 Server-Timing 헤더(cdn-cache-hit·cdn-cache-refresh·cdn-cache-miss) — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/understanding-response-headers-policies.html ; `X-Cache` 헤더는 공식 개발자 가이드에서 설명 페이지를 찾지 못함(99 조각 참조).

### 5.3.4 하이브리드·프라이빗 연결 문제 식별·해결
- **VPN 상태 지표.** `TunnelState`는 터널 상태(정적 VPN: 0=DOWN, 1=UP / BGP VPN: 1=ESTABLISHED, 그 외 0)이며 0과 1 사이 값은 **하나 이상의 터널이 UP이 아님**을 뜻한다 [F21].
- **"터널은 UP인데 통신이 안 된다" = 라우팅.** 가상 프라이빗 게이트웨이를 쓰고 VPC 라우팅 테이블에서 경로 전파를 켜면 동적·정적 경로가 VPN용으로 자동 추가된다 [F22] → 전파 설정 또는 정적 경로 누락을 확인한다. (TGW 경유면 TGW 라우팅 테이블: 5.3.1)
- **원인 추적은 VPN 로그.** Site-to-Site VPN 로그는 CloudWatch Logs로 게시할 수 있다 [F23] (내용·점검 순서: 추가 ①②).
- **인터페이스 엔드포인트(PrivateLink) = DNS가 핵심.** 프라이빗 DNS 이름을 쓰려면 VPC의 DNS 호스트 이름과 DNS 확인을 **둘 다** 활성화해야 한다 [F24]. 엔드포인트 ENI의 보안 그룹은 별도 점검 대상이다(추가 ④).
- **게이트웨이 엔드포인트(S3·DynamoDB) = 라우팅이 핵심.** prefix list는 리전 단위라 **다른 리전의 서비스로 가는 트래픽은 인터넷 게이트웨이로 간다** [F25] (추가 ④).
- 그 밖: VPC 피어링(추가 ⑤), 하이브리드 DNS(추가 ⑥), Client VPN(추가 ⑦), Direct Connect(범위 불명 — 99 조각).

**표 초안 — 증상 → 먼저 볼 곳**
| 증상 | 먼저 의심 | 확인 도구·지표 | 근거 |
|---|---|---|---|
| VPN 터널 DOWN / 불안정 | IKE·IPsec·BGP 협상 실패, 고객 게이트웨이 설정 | TunnelState, VPN 로그, 점검 순서 IKE→IPsec→터널→BGP(추가 ①) | [F21][F23] |
| 터널 UP인데 통신 불가 | 경로 전파·정적 경로 누락 | VPC(또는 TGW) 라우팅 테이블 | [F22] |
| 엔드포인트를 만들었는데 서비스 이름이 퍼블릭 IP로 해석 | 프라이빗 DNS 미활성, VPC DNS 속성 비활성 | 엔드포인트 설정, VPC DNS 속성 | [F24] |
| 게이트웨이 엔드포인트가 있는데 다른 리전 버킷 접근이 인터넷 경유 | prefix list는 리전 한정 | 대상 서비스의 리전 | [F25] |

**추가 확인 사실(§5 미등록 — URL 재확인):**
- ① VPN 점검 순서: IKE SA 존재 → IPsec SA(터널 자체) → 터널(방화벽 규칙·IP 연결) → BGP(Active/Established, 기본 경로 광고) — https://docs.aws.amazon.com/vpn/latest/s2svpn/Generic_Troubleshooting.html
- ② VPN 지표·로그: TunnelDataIn·TunnelDataOut은 터널이 DOWN이어도 주기적 상태 확인·ARP·BGP 때문에 값이 보일 수 있음 — https://docs.aws.amazon.com/vpn/latest/s2svpn/monitoring-cloudwatch-vpn.html ; 터널 활동 로그에 IKE Phase 1·2 상태(Established·Rekeying·Negotiating·Down), BGP 로그에 BGPStatus·RouteStatus — https://docs.aws.amazon.com/vpn/latest/s2svpn/monitoring-logs.html
- ③ VPN 한도·MTU: 표준 터널 최대 1.25 Gbps·140,000 PPS(큰 대역폭 터널 5 Gbps는 TGW·Cloud WAN 연결 한정), MTU 1446·MSS 1406, Path MTU Discovery 미지원 — https://docs.aws.amazon.com/vpn/latest/s2svpn/vpn-limits.html , https://docs.aws.amazon.com/vpn/latest/s2svpn/VPNTunnels.html
- ④ 엔드포인트: 인터페이스 엔드포인트 SG 규칙이 엔드포인트 ENI로 오는 트래픽을 통제, 프라이빗 DNS 활성화 후 IP가 쓰이기까지 몇 분 걸릴 수 있음 — https://docs.aws.amazon.com/vpc/latest/privatelink/interface-endpoints.html ; 게이트웨이 엔드포인트: 선택한 라우팅 테이블에 prefix list 경로가 자동 추가되고 그 테이블과 연결되지 않은 서브넷은 퍼블릭 엔드포인트 사용, 인스턴스 SG·서브넷 NACL이 서비스 트래픽을 허용해야 함, 정확한 IP 범위 경로가 있으면 엔드포인트 경로보다 우선 — https://docs.aws.amazon.com/vpc/latest/privatelink/gateway-endpoints.html
- ⑤ VPC 피어링: 양쪽 서브넷 라우팅 테이블 경로 → SG → NACL 순으로 확인하고 그래도 안 되면 Reachability Analyzer — https://docs.aws.amazon.com/vpc/latest/peering/troubleshoot-vpc-peering-connections.html ; IPv4 CIDR이 겹치면 피어링 생성 불가 — https://docs.aws.amazon.com/vpc/latest/peering/vpc-peering-basics.html
- ⑥ 하이브리드 DNS: Resolver 인바운드 엔드포인트=온프레미스→VPC 질의, 아웃바운드 엔드포인트=VPC→온프레미스 질의, Direct Connect 또는 VPN 연결 필요. 문서 명칭은 "Route 53 VPC Resolver"로 바뀜(구 Route 53 Resolver) — https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/resolver.html
- ⑦ Client VPN: 클라이언트가 피어링 VPC·S3·인터넷에 접근하지 못하면 대상별 권한 부여 규칙(인터넷은 0.0.0.0/0)과 연결 서브넷 라우팅 테이블 경로를 확인 — https://docs.aws.amazon.com/vpn/latest/clientvpn-admin/no-internet-access.html
- ⑧ Direct Connect(두 서비스 목록 모두에 없음 — 99 조각): CloudWatch 지표 ConnectionState·VirtualInterfaceBgpStatus — https://docs.aws.amazon.com/directconnect/latest/UserGuide/monitoring-cloudwatch.html

### 5.3.5 CloudWatch 네트워크 모니터링 서비스 구성·분석 (C03 신규 Skill)
- **정의(후보).** 가이드에는 서비스 정의가 없다. CloudWatch 문서는 "CloudWatch Network Monitoring"으로 네트워크·인터넷 모니터링 기능을 제공한다고 설명하며 [F26], 그 구성은 Internet Monitor·Network Flow Monitor·Network Synthetic Monitor 3종이다(해석 범위: 99 조각).
- **서비스 선택 규칙.**
  - Internet Monitor: 애플리케이션과 **최종 사용자 사이의 인터넷** 성능·가용성 [F27].
  - Network Flow Monitor: 인스턴스에 설치한 **경량 에이전트**가 수집한 TCP 흐름 지표 [F28].
  - Network Synthetic Monitor: Direct Connect 연결 시 **VPC ↔ 온프레미스** 합성 테스트 [F29]. 에이전트 설치 불필요(추가 ②).
  - NHI(network health indicator): 성능 저하가 AWS 네트워크 안에 있는지 알려 주는 이진 값(0 또는 100) [F30] — NSM뿐 아니라 NFM도 NHI를 제공한다(추가 ③).
- **알람 연동.** 세 서비스 모두 CloudWatch 지표를 게시하므로 CloudWatch 경보를 걸 수 있다(추가 ①②③).

**표 초안 — 서비스 선택 기준**
| 서비스 | 보는 구간 | 수집 방식 | 대표 지표·개념 | 쓰는 상황 | 근거 |
|---|---|---|---|---|---|
| Internet Monitor | 최종 사용자 ↔ AWS(VPC·NLB·CloudFront·WorkSpaces 디렉터리) | AWS 측정 데이터, 클라이언트·앱에 측정 코드 불필요 | 성능·가용성 점수, health event(기본 임계값 95%) | 특정 지역·ISP 사용자의 체감 저하 | [F27] (추가 ①) |
| Network Flow Monitor | 워크로드의 TCP 흐름(서브넷·AZ·VPC·AWS 서비스 간) | 인스턴스 에이전트 | 재전송·타임아웃·RTT·전송량, NHI | 지연·손실의 원인이 앱인지 AWS인지 | [F28] (추가 ③) |
| Network Synthetic Monitor | VPC 서브넷 ↔ 온프레미스 IP | AWS 관리형 프로브(ICMP·TCP) | RTT·PacketLoss·HealthIndicator(NHI) | 하이브리드(Direct Connect 등) 경로 감시 | [F29][F30] (추가 ②) |

**추가 확인 사실(§5 미등록 — URL 재확인):**
- ① Internet Monitor: 모니터에 VPC·NLB·CloudFront 배포·WorkSpaces 디렉터리를 추가, 성능·가용성 점수가 임계값(기본 95%) 이하이면 health event 생성 후 EventBridge로 전송, 측정값을 5분마다 CloudWatch Logs(상위 500 city-network)에 게시(선택: S3), 의미 있는 결과를 위해 VPC에는 인터넷 게이트웨이 필요, VPC·NLB·WorkSpaces는 last-mile 지연 미포함 — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-InternetMonitor.what-is-cwim.html , https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-IM-inside-internet-monitor.html , https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/IMMonitorResources.html
- ② Network Synthetic Monitor: AWS 관리형이라 별도 에이전트 불필요, 프로브=소스 VPC 서브넷+온프레미스 목적지(IP·프로토콜·포트·패킷 크기), 프로토콜 ICMP·TCP, 집계 간격 30초 또는 60초, 지표 HealthIndicator·PacketLoss·RTT(네임스페이스 AWS/NetworkMonitor)로 경보 생성 가능, NHI는 Direct Connect 또는 TGW 리전 간 피어링을 지나는 경로에 적용, 자동 장애 조치는 제공하지 않음 — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/what-is-network-monitor.html , https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/nw-monitor-how-it-works.html , https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/cw-nwm-create-alarm.html
- ③ Network Flow Monitor: EC2·EKS에 에이전트 설치(페이로드 접근 불가), 지표 DataTransferred·Retransmissions·Timeouts·RoundTripTime·HealthIndicator(네임스페이스 AWS/NetworkFlowMonitor), NHI=100(degraded) 또는 0(healthy), Workload insights에서 흐름을 골라 monitor 생성 — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-NetworkFlowMonitor-inside-network-flow-monitor.html , https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-NetworkFlowMonitor-cw-metrics.html
- ④ 네트워크 서비스 권장 경보 예: NAT ErrorPortAllocation(Sum>0)·PacketsDropCount, PrivateLink PacketsDropped(8500바이트 초과 패킷은 드롭), VPN TunnelState(Minimum<1), CloudFront 5xxErrorRate·OriginLatency — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/Best_Practice_Recommended_Alarms_AWS_Services.html

1. **원인 계층을 고르는 시나리오.** 로그 레코드나 도구 출력이 주어지고 SG/NACL/라우팅/NAT/TGW 중 원인을 고른다. 근거 문구: 5.3.1 "Troubleshoot VPC configurations …", 5.3.2 "Collect and interpret …". 판단 기준: 응답 방향만 REJECT이면 NACL(stateless) [F3][F4]; 구성상 어디가 막는지는 Reachability Analyzer [F1][F2]; REJECT만으로 SG/NACL 구분 불가 [F9][F10]; NAT 경유 연결이 일정 시간 뒤 끊기면 350초 [F7]; TGW 경유 실패는 라우팅 테이블·blackhole [F6].
2. **어떤 로그를 켜고 어디서 읽는가.** "로그를 수집한다"는 설정·전제 지식을 묻는다. 근거 문구: 5.3.2 "(for example, VPC flow logs, ELB access logs, AWS WAF web ACL logs, CloudFront logs, container logs)". 판단 기준: Flow Logs에 안 남는 트래픽 [F8]; ALB `target_status_code`의 `-` [F11]; WAF 로그 그룹 이름 접두 [F12]; CloudFront legacy는 S3 전용 [F13]; ECS는 awslogs 드라이버 [F14].
3. **CloudFront 적중률·갱신·오류 지속 문제.** 근거 문구: 5.3.3 "Identify and remediate CloudFront caching issues." 판단 기준: 캐시 키 최소화 [F17]와 지표 [F16]; TTL 기본값·계산 규칙 [F18][F19]; RefreshHit 의미 [F15]; 오류 캐싱 기본 10초 [F20].
4. **하이브리드·프라이빗 연결 장애 + 모니터링 서비스 선택.** 근거 문구: 5.3.4 "Identify and troubleshoot hybrid connectivity issues and private connectivity issues.", 5.3.5 "Configure and analyze CloudWatch network monitoring services." 판단 기준: TunnelState·경로 전파·VPN 로그 [F21][F22][F23]; 인터페이스 엔드포인트는 DNS 속성 [F24], 게이트웨이 엔드포인트는 리전 한정 prefix list [F25]; 사용자-인터넷 구간은 Internet Monitor [F27], 에이전트 기반 흐름 지표는 Network Flow Monitor [F28], VPC-온프레미스 합성 테스트는 Network Synthetic Monitor [F29], NHI는 AWS 네트워크 귀책 판별 [F30].

## 4. 흔한 함정 · 혼동 짝
| 혼동 짝 | 구분 기준 | 근거 |
|---|---|---|
| Flow Logs REJECT = "NACL만 거부" (기존 soa-t5-4 서술) ↔ 실제 | REJECT는 SG 또는 NACL 불허를 모두 포함하고 SG 인바운드 거부도 REJECT 1건을 남긴다. 로그만으로 둘을 구분할 수 없다. | [F9][F10] |
| Reachability Analyzer ↔ Flow Logs | RA=구성 정적 분석(패킷 안 보냄, 차단 구성요소 지목) / Flow Logs=실제 트래픽 레코드 | [F1][F2][F9] |
| SG(stateful) ↔ NACL(stateless) | NACL은 응답도 규칙 평가 대상 → 응답(이페머럴 포트) 규칙 필요, 범위는 클라이언트 OS마다 다름 | [F3][F4] |
| "로그에 없다" ↔ "트래픽이 없다/막혔다" | Amazon DNS 서버 접촉 트래픽 등은 Flow Logs 비기록 대상 | [F8] |
| elb_status_code ↔ target_status_code | target_status_code는 대상과 연결·응답이 있을 때만 기록, 아니면 `-` | [F11] |
| WAF 로그 대상 이름 | CloudWatch Logs 로그 그룹은 `aws-waf-logs-` 접두 필수 | [F12] |
| CloudFront 표준 로그 legacy ↔ v2 | legacy는 S3 전용 | [F13] |
| Hit ↔ RefreshHit ↔ Miss | RefreshHit=캐시에 있으나 만료되어 오리진 재검증 | [F15] |
| 캐시 키에 값을 많이 넣기 ↔ 적중률 | 필요한 값만 포함해야 적중률↑, 지표는 Cache hit rate(추가 활성화) | [F16][F17] |
| 기본 TTL ↔ max-age ↔ 최대 TTL | 정책 미사용 시 24시간 / 최소 TTL=0이면 max-age와 최대 TTL 중 작은 값 | [F18][F19] |
| 오류 캐싱 ↔ 객체 TTL | 오류 응답은 오류 캐싱 최소 TTL(기본 10초)을 따로 가짐 | [F20] |
| TunnelState 값 | 0~1 사이=하나 이상의 터널이 UP이 아님(둘 다 DOWN만이 아님) | [F21] |
| 터널 UP ↔ 통신 가능 | 라우팅(전파·정적)이 없으면 UP이어도 통신 불가 | [F22] |
| 인터페이스 ↔ 게이트웨이 엔드포인트 장애 원인 | 인터페이스=DNS 속성·프라이빗 DNS / 게이트웨이=라우팅·리전 한정 prefix list | [F24][F25] |
| Internet Monitor ↔ Network Flow Monitor ↔ Network Synthetic Monitor | 사용자-인터넷 / 에이전트 기반 TCP 흐름 / VPC-온프레미스 합성 프로브 | [F27][F28][F29] |

## 6. 자가 점검 문항 후보 (3~5) — 후보일 뿐, 검증 아님
### Q1 (Skill 5.3.2 · intermediate)
문제: 운영자가 프라이빗 서브넷에 있는 EC2 웹 서버의 ENI에 VPC Flow Logs(트래픽 유형 ALL)를 켰다. 온프레미스 클라이언트가 TCP 443으로 접속하지 못하는 동안 이 ENI의 목적지 포트 443 인바운드 레코드가 모두 action=REJECT로 기록된다. 로그만으로 내릴 수 있는 가장 정확한 결론은?
- A) REJECT는 네트워크 ACL이 거부한 경우에만 기록되므로 NACL 규칙부터 수정하면 된다.
- B) 보안 그룹 또는 네트워크 ACL이 트래픽을 허용하지 않은 것이다. 로그만으로는 둘을 구분할 수 없으므로 두 규칙을 점검하거나 Reachability Analyzer로 차단 구성요소를 확인한다.
- C) 보안 그룹이 거부한 트래픽은 Flow Logs에 남지 않으므로, REJECT가 보인다면 보안 그룹은 정상이며 NAT 게이트웨이를 점검해야 한다.
- D) REJECT는 패킷이 인스턴스에 도달한 뒤 애플리케이션이 연결을 거부했다는 뜻이므로 웹 서버 프로세스를 점검해야 한다.
정답: B
정답 근거: action=REJECT는 보안 그룹 또는 네트워크 ACL이 허용하지 않은 트래픽을 포함하고 [F9], 공식 예시에서 보안 그룹이 인바운드를 거부해도 REJECT 레코드 1건이 남는다 [F10]. 차단 구성요소를 구성 기준으로 지목하는 도구는 Reachability Analyzer다 [F1] — https://docs.aws.amazon.com/vpc/latest/userguide/flow-log-records.html , https://docs.aws.amazon.com/vpc/latest/userguide/flow-logs-records-examples.html
오답 이유: A) REJECT가 NACL만의 신호라는 서술은 공식 정의·예시와 다르다 [F9][F10] / C) 보안 그룹 거부도 REJECT로 남는다 [F10] / D) REJECT는 보안 그룹·네트워크 ACL 불허 등 네트워크 계층의 거부를 가리키며 애플리케이션 거부가 아니다 [F9].

### Q2 (Skill 5.3.1 · advanced)
문제: 웹 서브넷에 새 커스텀 NACL을 연결한 뒤 외부 사용자가 웹 서버(TCP 443)에 접속하지 못한다. NACL 인바운드는 443 허용, 아웃바운드는 443만 허용하고 나머지는 기본 거부다. 보안 그룹은 인바운드 443을 허용한다. Flow Logs에는 클라이언트→서버 443이 ACCEPT, 서버→클라이언트 방향 레코드가 REJECT로 남는다. 가장 적절한 조치는?
- A) 보안 그룹 아웃바운드 규칙에 이페머럴 포트 범위를 추가한다.
- B) NACL 아웃바운드에 클라이언트가 사용하는 이페머럴 포트 범위로 나가는 응답을 허용하는 규칙을 추가한다.
- C) NACL 인바운드의 443 허용 규칙을 이페머럴 포트 범위 허용으로 바꾼다.
- D) 서브넷에 NAT 게이트웨이를 추가한다.
정답: B
정답 근거: NACL은 stateless라서 허용된 요청의 응답도 NACL 규칙의 평가를 받으므로 응답 방향 규칙이 필요하고 [F3], 열어야 할 이페머럴 포트 범위는 클라이언트의 운영체제에 따라 다르다 [F4]. 응답 방향 REJECT는 그 증거다 [F9] — https://docs.aws.amazon.com/vpc/latest/userguide/flow-logs-records-examples.html , https://docs.aws.amazon.com/vpc/latest/userguide/custom-network-acl.html
오답 이유: A) 보안 그룹은 stateful이라 허용된 요청의 응답이 자동 허용되므로 SG 변경이 필요 없다(F3 페이지) / C) 인바운드 443은 이미 ACCEPT이고 문제는 응답 방향이다 / D) NAT 게이트웨이는 프라이빗 서브넷의 아웃바운드 인터넷용이며 NACL 응답 차단과 무관하다.

### Q3 (Skill 5.3.3 · intermediate)
문제: 정적 콘텐츠를 CloudFront로 제공하는데 오리진 요청이 많고 Cache hit rate 지표가 낮다. 확인해 보니 캐시 정책이 모든 쿼리 문자열·쿠키·헤더를 캐시 키에 포함하고 있으며, 오리진은 이 값들에 따라 응답을 바꾸지 않는다. 적중률을 높이는 가장 적절한 조치는?
- A) 오리진 응답을 실제로 바꾸는 값만 캐시 키에 포함하도록 캐시 정책을 수정한다.
- B) 배포 전체 경로를 매시간 무효화한다.
- C) 기본 TTL과 최소 TTL을 0으로 낮춘다.
- D) 오리진이 모든 응답에 Cache-Control: no-store를 붙이게 한다.
정답: A
정답 근거: 캐시 적중률은 캐시 키에 꼭 필요한 최소한의 값만 포함할 때 높아지고 [F17], 적중률은 추가 지표 Cache hit rate로 확인한다 [F16] — https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/understanding-the-cache-key.html
오답 이유: B) 무효화는 캐시된 객체를 지우는 작업이라 적중률 개선 수단이 아니다 [F17] / C) TTL을 줄이면 객체가 더 자주 만료되어 RefreshHit·Miss가 늘어난다 [F15][F19] / D) no-store는 캐싱 자체를 막는다(Expiration 페이지의 헤더 표, F18·F19와 같은 페이지).

### Q4 (Skill 5.3.4 · intermediate)
문제: 프라이빗 서브넷의 EC2에서 NAT 게이트웨이 없이 Amazon SQS를 호출하려고 SQS 인터페이스 VPC 엔드포인트를 만들고 프라이빗 DNS 이름을 활성화했다. 그런데 인스턴스에서 SQS 서비스 도메인 이름을 조회하면 계속 퍼블릭 IP가 반환된다. 가장 먼저 확인할 것은?
- A) 엔드포인트가 속한 VPC의 DNS 호스트 이름과 DNS 확인 속성이 모두 활성화되어 있는지
- B) 프라이빗 서브넷 라우팅 테이블에 SQS용 prefix list 경로가 있는지
- C) 인스턴스에 퍼블릭 IP가 할당되어 있는지
- D) 서브넷 NACL의 규칙 번호가 올바른 순서인지
정답: A
정답 근거: 프라이빗 DNS 이름을 쓰려면 VPC의 DNS 호스트 이름과 DNS 확인을 모두 활성화해야 한다 [F24] — https://docs.aws.amazon.com/vpc/latest/privatelink/interface-endpoints.html
오답 이유: B) prefix list 경로는 게이트웨이 엔드포인트(S3·DynamoDB)의 방식이며 [F25] 인터페이스 엔드포인트는 DNS로 엔드포인트 ENI에 연결된다 / C) 퍼블릭 IP는 엔드포인트 사설 경로와 무관하다 / D) 규칙 번호는 이름 해석과 무관하다.

### Q5 (Skill 5.3.5 · intermediate)
문제: 데이터센터와 VPC가 Direct Connect로 연결되어 있다. 서버에 에이전트를 설치하지 않고 VPC 서브넷에서 온프레미스 IP까지의 왕복 지연과 패킷 손실을 지속적으로 측정해 CloudWatch 경보를 설정하려 한다. 가장 적합한 서비스는?
- A) CloudWatch Internet Monitor
- B) CloudWatch Network Flow Monitor
- C) CloudWatch Network Synthetic Monitor
- D) VPC Reachability Analyzer
정답: C
정답 근거: Direct Connect 연결 시 Network Synthetic Monitor로 VPC와 온프레미스 엔드포인트 사이에 합성 테스트를 실행해 연결성을 선제적으로 모니터링한다 [F29]. 이 모니터의 지표(RTT·PacketLoss·HealthIndicator)로 CloudWatch 경보를 만들 수 있다(§2 5.3.5 추가 ②) — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/WhatIsCloudWatch.html , https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/cw-nwm-create-alarm.html
오답 이유: A) Internet Monitor는 애플리케이션과 최종 사용자 사이의 인터넷 구간을 본다 [F27] / B) Network Flow Monitor는 인스턴스에 에이전트를 설치해야 한다 [F28] / D) Reachability Analyzer는 구성 정적 분석이라 지속적 측정을 하지 않는다 [F2].
