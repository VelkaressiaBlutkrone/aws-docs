### 1.2.1 성능 지표 분석과 교정 자동화 (CloudWatch · Lambda · Systems Manager · CloudTrail · Kiro · AWS DevOps Agent) — v1.1 변경

**무엇을 묻는 Skill인가.** `analyze performance metrics`(지표 분석)와 `automate remediation strategies`(교정 전략 자동화)다. v1.1에서 예시가 바뀌었다 — AWS User Notifications와 auto scaling이 빠지고 Kiro와 AWS DevOps Agent가 들어왔다 [B1][B2][B5][B6]. 해석: '경보 → 알림·스케일링' 중심이던 예시에 에이전트가 조사·제안하는 운영 방식이 더해졌다. 두 신규 서비스를 시험이 얼마나 깊게 묻는지는 공식 근거가 없다(P2-G04, P2-G05).

**자동 교정은 항상 '신호 → 라우팅 → 교정' 3칸이다.** 신호가 지표인지·API 활동인지·AWS 상태 변화인지에 따라 라우팅 수단이 갈리고, 교정이 단순(호스트 이전)인지·맞춤(코드)인지·다단계(런북)인지에 따라 교정 수단이 갈린다(해석). 아래 표가 그 대응이다.

| 신호 | 라우팅(어떻게 전달되나) | 교정 수단 | 꼭 알아둘 것 |
|---|---|---|---|
| CloudWatch 지표 경보 | 경보 작업(직접) 또는 경보 상태 변경 이벤트 → EventBridge [F1][F5] | Lambda(맞춤 로직), EC2 작업, Auto Scaling, OpsItem·Incident Manager [F1][C34][C45] | Lambda 호출은 함수 리소스 정책이 필요 [F3]. 경보 작업은 상태 전이 때만 실행(Auto Scaling 제외) [F2] |
| EC2 호스트(하드웨어) 장애 | `StatusCheckFailed_System` 경보 | EC2 `recover` 작업 | recover는 System 지표에만 가능, Instance 지표에는 불가 [F4]. 지원 인스턴스는 간소화된 자동 복구가 기본 활성 [C33] |
| CloudTrail API 활동 | EventBridge 규칙이 `AWS API Call via CloudTrail` 이벤트를 매칭 → Lambda 등 | 맞춤 교정(Lambda)·알림 | AWS 서비스는 CloudTrail로 이벤트를 best effort로 전달 [F6] — 전달 보장형 경보 이벤트 [F5]와 대비 |
| AWS 측 상태 변화(AWS Health) | 모든 고객이 EventBridge로 추가 비용 없이 수신 [F7] | SNS 알림·Lambda·Automation | 콘솔 명칭은 Service health / Your account health [F8][C25]. 조직 단위 뷰 별도 [C28] |
| 인시던트(알람·티켓) | AWS DevOps Agent: 내장 통합·웹훅·수동으로 조사 시작 [F10] | 자율 조사, 완화 계획 제시 [F9][C46] | 코드 개선은 Kiro 같은 다른 에이전트가 구현할 수 있는 지침으로 제공 [F12] |

**경보 작업(직접) vs 경보 이벤트(EventBridge, 간접)**
- 경보는 SNS 알림·Lambda 호출·EC2 작업(중지·종료·재부팅·복구)·Auto Scaling·OpsItem/Incident Manager 등을 직접 호출하고 [F1][C34][C45], 별개로 상태 변경 이벤트를 EventBridge에도 보낸다(전달 보장) [F5].
- 직접 작업은 설정이 짧지만 **상태가 바뀔 때만** 실행된다 — 조건이 며칠 지속돼도 다시 실행되지 않는다(Auto Scaling 제외) [F2]. 해석: 교정 함수가 한 번 실패하면 경보가 ALARM에 머무는 동안 재호출되지 않으므로, 재시도·멱등성은 함수 쪽에서 챙기거나 다른 경로로 보완해야 한다.
- Lambda는 임의 코드를 경보에서 바로 실행하는 가장 쉬운 방법이다 [F1]. 대신 CloudWatch가 함수를 호출할 수 있게 함수 리소스 정책을 줘야 한다 [F3]. 가장 흔한 '경보는 울렸는데 함수가 안 돈다' 원인이다.
- 경보의 Systems Manager 작업은 OpsItem 또는 Incident Manager 인시던트 **생성**이다 [C45]. Automation 런북은 경보의 직접 작업이 아니라 EventBridge 규칙의 대상으로 실행한다 [F30]. (soa-t1-1 L197 표현 정리는 P1-C17.)

**EC2 recover 작업**
- `recover`는 `StatusCheckFailed_System`에만 쓸 수 있고 `StatusCheckFailed_Instance`에는 쓸 수 없다 [F4]. 복구된 인스턴스는 인스턴스 ID 등이 원래와 같다 [C32]. EC2 상태 확인은 현재 system·instance·attached EBS·application의 4종이며 1분마다 수행된다 [C29][C30].
- 해석: '호스트 문제는 recover, 인스턴스(OS) 문제는 다른 수단(재부팅·교체 등)'이라는 책임 경계로 외우면 보기 4개 중 오답이 쉽게 걸러진다. 지원 인스턴스에서는 경보 없이도 간소화된 자동 복구가 기본으로 켜져 있다 [C33].

**CloudTrail과 AWS Health는 '이벤트를 받는 법'이 핵심이다**
- CloudTrail에 기록된 API 호출은 EventBridge 규칙으로 매칭해 교정을 트리거할 수 있다. 다만 AWS 서비스가 CloudTrail로 이벤트를 전달하는 방식은 best effort다 [F6]. 해석: 반드시 실행돼야 하는 교정의 유일한 트리거로 삼기보다, 전달이 보장되는 경보 이벤트 [F5]나 상태 기반 신호와 함께 설계한다.
- AWS Health 이벤트는 모든 고객이 EventBridge로 추가 비용 없이 받을 수 있다 [F7]. Health API 호출은 Business Support+ 이상 계열 플랜이 필요하다 [C26]. 콘솔은 로그인 없이 공개 서비스 상태를 보는 `AWS Health Dashboard – Service health`와, 로그인 시 내 계정 이벤트를 보는 `AWS Health Dashboard – Your account health`로 나뉜다 [F8][C25]. AWS Health Dashboard는 v1.1 in-scope 목록에 신규로 올랐다 [B3].

**AWS DevOps Agent와 Kiro (v1.1 신규 예시)**
- AWS DevOps Agent는 AI 기반의 상시 가용 에이전트로, 문제가 생기는 즉시 자율적으로 조사를 시작한다 [F9]. 조사는 내장 통합(예: ServiceNow)·웹훅(예: PagerDuty, Grafana 알람)·수동의 세 방법으로 시작한다 [F10]. 완화는 '제안'이며 사용자가 검토·수정 후 적용 여부를 고른다 [C46]. 코드 개선처럼 다른 에이전트가 구현할 일은 지침 형태로 넘기고 그 예로 Kiro를 든다 [F12].
- Kiro는 AWS의 에이전트형 개발 시스템으로 IDE·CLI·자율 웹 에이전트로 제공된다 [F11]. 운영 관점의 쓰임(예: Kiro CLI가 CloudWatch MCP 서버로 지표·로그를 질의)은 공식 블로그 사례만 확인했고 시험 출제 형태는 불확실하다(P2-G04).
- 해석: 시험 문항이 이 둘을 묻는다면 '무엇이 조사·제안을 하고(DevOps Agent), 무엇이 코드를 구현하며(Kiro), 무엇이 AWS 리소스를 실제로 바꾸는가(Lambda·Systems Manager Automation)'의 역할 구분일 가능성이 높다. 이 구분은 [F9][F12]와 §1.2.3의 Automation 설명에서 도출한 해석이며 기출 정보가 아니다.

### 1.2.2 EventBridge로 이벤트 라우팅·강화·전달 및 이벤트 버스 규칙 문제 해결

**무엇을 묻는 Skill인가.** route(규칙으로 대상 선택) · enrich(대상에 보내기 전 가공·보강) · deliver(대상 호출과 실패 처리) 세 동사와, 규칙이 기대대로 동작하지 않을 때의 문제 해결이다. 해석: 'event bus rules'라는 표현은 규칙·대상 모델(default 버스, Custom Event Bus - Classic)을 가리킨다. 2026-09 출시된 신규 Custom Event Bus(구독자 모델)는 v1.1 발행(2026-06-01) 이후라 출제 범위 여부가 불명이다(B8, P2-G07).

| 단계 | 수단 | 핵심 사실 |
|---|---|---|
| 라우팅 | 이벤트 버스 + 규칙(이벤트 패턴) | AWS 서비스 이벤트는 default 버스로 들어온다 [C44]. 규칙은 한 버스에 속하며 그 버스가 받은 이벤트에만 적용 [F14]. 이벤트는 여러 규칙과 일치할 수 있고 규칙당 대상 최대 5개 [F15] |
| 버스 종류 | default / Custom Event Bus - Classic / (신규) Custom Event Bus | 신규 앱은 Custom Event Bus로 시작을 권장하나 Classic도 계속 제공 [F13][C36] |
| 강화 ① | 규칙의 입력 변환기 | JSON path로 원본 이벤트 값을 변수(최대 100개)에 담아 템플릿으로 가공 [F16] |
| 강화 ② | EventBridge Pipes의 강화 단계 | 소스 데이터를 대상으로 보내기 전에 외부 호출로 보강(Lambda·API Gateway·API destination·Step Functions Express) [F17]. Pipes는 점대점 연동 [C47] |
| 전달 | 대상 호출 + 재시도 + DLQ | 기본 24시간·최대 185회 재시도 [F18]. 소진된 이벤트는 폐기되므로 DLQ로 보존 [F19]. 이벤트를 보관해 다시 보내려면 아카이브·재생 [C48] |
| 교차 계정 | 수신 계정 버스에 권한 부여 + 송신 계정 규칙 | 수신 계정에서 이벤트 버스 권한을 편집해 허용할 계정 지정 [C49] |
| 문제 해결 | 지표·권한·패턴·리전 | 지표 [F22], Lambda 리소스 정책 [F20], 글로벌 서비스 이벤트는 us-east-1 [F21], ARN은 정확 일치 [C51], Sandbox로 패턴 테스트 [C50] |

**이해 포인트**
- **'강화'가 둘로 갈리는 이유(해석).** 입력 변환기는 이벤트 안에 이미 있는 값을 꺼내 재배치하는 도구이고, Pipes의 강화는 부족한 데이터를 외부 호출로 가져오는 단계다. 문서 예시도 티켓 생성 이벤트에 전체 티켓 데이터가 없을 때 Lambda가 API를 호출해 채우는 경우를 든다 [F17].
- **스케줄 규칙은 legacy다.** 주기 작업은 EventBridge Scheduler를 쓰라고 권장하고 스케줄 규칙은 legacy로 분류된다 [C37]. 스케줄 규칙은 UTC+0 시간대만 쓴다 [C38]. 기존 학습문서는 스케줄 규칙을 기본 수단처럼 서술한다(P2-G07 참고).
- **재시도 소진 = 이벤트 소실.** DLQ가 없으면 24시간·185회가 지난 이벤트는 사라진다 [F18][F19]. 대상이 오래 제한되면 재시도가 이뤄지지 않을 수도 있다는 점도 공식 문제 해결 문서에 있다.

**문제 해결 순서 (결정 규칙)**
1. 이벤트가 실제로 규칙이 있는 버스·리전에 도착했는가? — IAM·Route 53 같은 글로벌 서비스의 API 호출 이벤트는 us-east-1에서만 제공되므로 다른 리전의 규칙은 일치하지 않는다 [F21]. 규칙은 자기 버스의 이벤트에만 적용된다 [F14].
2. 패턴이 일치하는가? — ARN은 정확 일치로 비교한다 [C51]. 규칙 변경 직후에는 반영에 잠시 걸리며, EventBridge Sandbox로 샘플 이벤트에 패턴을 시험할 수 있다 [C50].
3. 규칙은 실행됐는데 대상이 호출되지 않는가? — 지표 `TriggeredRules`·`Invocations`·`FailedInvocations`로 어느 구간에서 끊겼는지 가른다 [F22]. Lambda 대상이면 함수 리소스 기반 정책을 본다: `SourceAccount` 조건이 있으면 EventBridge가 함수를 호출할 수 없다 [F20]. 지표 해석(TriggeredRules만 있고 Invocations가 없으면 대상 설정 문제, Invocations와 FailedInvocations가 모두 있으면 대상 쪽 문제)은 AWS re:Post 지식 센터 문서의 설명이다 [3자 아님·AWS 공식 지식 센터].
4. 호출은 했으나 실패하는가? — 재시도 정책과 DLQ [F18][F19]. 대상이 SQS·SNS이고 암호화돼 있다면 KMS 키 정책에 `events.amazonaws.com`을 허용해야 한다는 항목도 공식 문제 해결 문서에 있다.

### 1.2.3 Systems Manager Automation 런북 만들기·실행 (AWS SDK·사용자 지정 스크립트 포함)

**무엇을 묻는 Skill인가.** `create or run custom and predefined runbooks` — 사전 정의 런북을 골라 실행하거나, 사용자 지정 런북(YAML/JSON, 필요 시 스크립트 단계)을 작성해 실행하는 능력이다. 해석: 주 쟁점은 ① 어떤 런북·작업(action)을 쓰는가 ② 어떤 IAM 역할로 도는가 ③ 여러 대상에 안전하게 도는가 ④ 무엇이 트리거하는가의 네 가지다.

| 구성 요소 | 핵심 사실 | 근거 |
|---|---|---|
| 런북 | YAML 또는 JSON, 단계(steps)와 매개변수 포함. Automation은 유지 관리·배포·교정 작업을 자동화 | [F23][C41] |
| 사전 정의 런북 | 이름이 `AWS-*`인 런북(예: AWS-RestartEC2Instance). 사용자 지정 런북과 마찬가지로 서비스 역할에 대상 서비스 호출 권한이 필요 | [F24][C42] |
| 승인 | 이름에 WithApproval이 들어가면 `aws:approve` 포함 — 지정 주체가 승인·거부할 때까지 일시 중지 | [F25] |
| 스크립트 단계 | `aws:executeScript`: Python 또는 PowerShell 스크립트. 단계당 최대 600초. AWS API 호출 시 IAM 서비스 역할 필수 | [F26][F27][C52] |
| 대기 | `aws:waitForAwsResourceProperty`: 리소스 상태가 될 때까지 대기(기본 타임아웃 3600초) | [C56] |
| 대량 실행 | 동시성(Concurrency)과 오류 임계값(error threshold)을 합쳐 rate controls | [F28][F29] |
| 동시 실행 한도 | 계정당 100개 동시 실행(적응형 동시성으로 최대 500) | [C53][C54] |
| 다중 계정·리전 | 중앙에서 여러 계정·리전의 리소스에 실행 | [C55] |
| 트리거 | EventBridge 규칙의 대상(target) 유형으로 지원 | [F30] |

**이해 포인트**
- **런북은 '순서가 있는 단계 목록'이고 각 단계는 하나의 작업(action)이다.** 단계 결과를 다음 단계 입력으로 넘기고, 승인·대기·분기 같은 제어 작업도 단계다. 스크립트가 필요할 때만 `aws:executeScript`를 쓴다(해석: 표준 작업은 전용 작업/사전 정의 런북으로 충분하고, 맞춤 로직만 스크립트로 보완).
- **IAM 역할이 두 군데서 문제 된다.** ① 런북이 다른 서비스를 호출하면 서비스(assume) 역할에 그 권한이 있어야 한다 — 사전 정의 `AWS-*` 런북도 마찬가지 [F24]. ② `aws:executeScript`가 AWS API를 호출하면 서비스 역할이 항상 필요하다 [F27]. 역할을 지정하지 않은 일반 런북은 실행을 시작한 사용자의 권한으로 돈다(공식 스크립트 고려사항 문서). 가장 흔한 실패 원인으로 추정되나 기출 정보는 아니다.
- **동시성과 오류 임계값은 독립 손잡이다.** 동시성은 '한 번에 몇 개 리소스'(절대 수 또는 비율) [F28], 오류 임계값은 '몇 건 실패하면 중단'이다. 임계값 0은 첫 오류 이후 추가 대상 실행을 중단한다 [F29].
- **트리거 경로.** 이벤트(예: EC2 상태 변경)나 일정으로 런북을 시작하려면 EventBridge 규칙의 대상으로 Systems Manager Automation을 고른다 [F30]. 경보 → 런북은 직접 연결이 아니라 EventBridge 등을 경유한다 [C43][C45].
- **SDK/스크립트로 실행.** CLI/SDK로는 `start-automation-execution`에 런북 이름과 매개변수를 넘긴다(승인 런북 실행 예시가 공식 문서에 있음). 이 서술은 승인 런북 실행 문서의 예시에서 확인했다.

## 3. 시험에서 묻는 방식 (가이드 Skill 문구 기반 추정 — 실제 문항 아님)
아래는 AWS가 공개한 Skill 문구(동사·예시 서비스)에서 추론한 출제 패턴이다. 실제 기출을 안다는 주장이 아니다.

1. **교정 경로 고르기 (Skill 1.2.1 `automate remediation strategies`).**
   - 패턴: 시나리오가 신호(지표 임계 초과·호스트 장애·API 호출·AWS 상태 이벤트)와 교정 요구(맞춤 코드·동일 인스턴스 유지·다단계)를 주고 구성을 고르게 한다.
   - 근거 문구: CloudWatch, Lambda, AWS Systems Manager, CloudTrail 나열.
   - 판단 기준: 신호가 지표면 경보(직접 작업 또는 EventBridge), 호스트 장애면 System 지표 + recover [F4], 맞춤 로직이면 Lambda [F1], API 활동이면 EventBridge + CloudTrail 이벤트 [F6], AWS 측 변화면 Health → EventBridge [F7].
2. **EventBridge 규칙이 동작하지 않는 이유 (Skill 1.2.2 `troubleshoot any issues with event bus rules`).**
   - 패턴: '규칙을 만들었는데 대상이 안 돈다' 계열. 원인 후보로 권한·리전·패턴·재시도가 섞여 나온다.
   - 판단 기준: 글로벌 서비스 이벤트면 us-east-1 [F21], 규칙 실행 후 Lambda 미호출이면 리소스 정책의 SourceAccount [F20], 지표로 구간 판별 [F22], 유실 방지는 DLQ [F19].
3. **런북 설계·실행 (Skill 1.2.3 `create or run custom and predefined runbooks`).**
   - 패턴: 수백 대에 안전하게 실행, 사람이 승인한 뒤 실행, 스크립트 단계 포함, 이벤트로 트리거.
   - 판단 기준: 속도·중단은 동시성/오류 임계값 [F28][F29], 승인은 WithApproval/`aws:approve` [F25], 스크립트는 `aws:executeScript` + 서비스 역할 [F27], 트리거는 EventBridge 대상 [F30].
4. **새 서비스 역할 구분 (Skill 1.2.1 예시의 Kiro·AWS DevOps Agent).**
   - 패턴: 인시던트 조사 자동화, 개발 에이전트와의 구분. 출제 깊이는 불확실(P2-G04, P2-G05).
   - 판단 기준: 조사·원인 분석·완화 제안은 DevOps Agent [F9], 코드 구현은 Kiro [F12], 실제 리소스 변경 실행은 Lambda·Automation.

## 4. 흔한 함정 · 혼동 짝
| 혼동 짝 | 구분 기준 | 근거 |
|---|---|---|
| 경보 작업(직접) ↔ 경보 이벤트(EventBridge) | 직접은 대상 종류가 정해져 있고 상태 전이 때만 실행. EventBridge는 패턴·변환·다중 대상 | [F1][F2][F5][F15] |
| recover ↔ 재부팅·교체 | recover는 StatusCheckFailed_System 전용 | [F4] |
| 경보 이벤트(전달 보장) ↔ CloudTrail 이벤트(best effort) | 보장이 필요한 자동화의 트리거 선택 | [F5][F6] |
| 경보의 Systems Manager 작업 ↔ Automation 런북 실행 | 경보 작업은 OpsItem·인시던트 생성. 런북은 EventBridge 대상 | [C45][F30] |
| Service health ↔ Your account health | 공개 서비스 상태(로그인 불필요) ↔ 내 계정 이벤트(로그인) | [F8] |

| 신규 Custom Event Bus ↔ Custom Event Bus - Classic ↔ default 버스 | 구독자가 만드는 모델 ↔ 규칙·대상 모델 ↔ AWS 서비스 이벤트가 자동 도착하는 기본 버스 | [F13][F14][C44] |
| 입력 변환기 ↔ Pipes 강화 | 이벤트 내부 값 재구성 ↔ 외부 호출로 데이터 보강 | [F16][F17] |
| TriggeredRules ↔ Invocations ↔ FailedInvocations | 규칙 실행 ↔ 대상 호출 시도 ↔ 영구 실패 | [F22] |
| 스케줄 규칙 ↔ EventBridge Scheduler | 스케줄 규칙은 legacy, Scheduler 권장 | [C37] |
| 동시성 ↔ 오류 임계값 | 몇 개 동시 ↔ 몇 건 실패하면 중단 | [F28][F29] |
| 일반 런북 단계 ↔ aws:executeScript | 스크립트가 AWS API를 호출하면 서비스 역할 필수 | [F27] |

## 6. 자가 점검 문항 후보 (3~5) — 후보일 뿐, 검증 아님
### Q1 (Skill 1.2.1 · foundational)
문제: 단일 EC2 인스턴스에서 기반 호스트의 하드웨어 문제로 시스템 상태 확인이 실패할 때 자동으로 복구 작업이 실행되도록 CloudWatch 경보를 구성한다. 어떤 구성이 맞는가?
- A) `StatusCheckFailed_Instance` 지표에 대한 경보에 EC2 recover 작업을 연결한다.
- B) `StatusCheckFailed_System` 지표에 대한 경보에 EC2 recover 작업을 연결한다.
- C) `CPUUtilization` 경보에 EC2 recover 작업을 연결한다.
- D) EventBridge 스케줄 규칙으로 5분마다 인스턴스를 재부팅한다.

정답: B
정답 근거: recover 작업은 `StatusCheckFailed_System`에만 쓸 수 있다 [F4] — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/UsingAlarmActions.html
오답 이유: A) recover는 StatusCheckFailed_Instance에는 사용할 수 없다 [F4]. C) 호스트 장애를 가리키는 지표가 아니다(해석). D) 상태와 무관하게 재부팅하며 호스트 문제를 가리키는 신호를 쓰지 않는다(해석).

### Q2 (Skill 1.2.1 · intermediate)
문제: CloudWatch 경보의 ALARM 작업으로 Lambda 교정 함수를 지정했다. 경보는 ALARM 상태로 전이되지만 함수가 한 번도 실행되지 않는다. 함수 코드에는 오류가 없다. 가장 가능성 높은 원인은?
- A) 경보 작업은 Lambda를 직접 호출할 수 없어 항상 SNS를 거쳐야 한다.
- B) 함수의 리소스 기반 정책이 CloudWatch 서비스 주체의 호출을 허용하지 않는다.
- C) 경보가 ALARM 상태에 머무는 동안은 작업이 반복 실행되므로 첫 호출이 건너뛰어졌다.
- D) 경보 작업은 같은 계정의 Lambda 함수 별칭만 호출할 수 있다.

정답: B
정답 근거: Lambda를 경보 작업으로 쓰려면 함수 리소스 정책이 CloudWatch 서비스 주체의 호출을 허용해야 한다 [F3] — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/alarms-and-actions-Lambda.html
오답 이유: A) Lambda 호출은 경보 작업으로 직접 지정할 수 있다 [F1]. C) 경보 작업은 상태 전이 때만 실행되며 반복되지 않는다 [F2]. D) 같은 계정뿐 아니라 다른 계정의 함수도, 이름·별칭·버전으로 지정할 수 있다 [F3].

### Q3 (Skill 1.2.2 · intermediate)
문제: 운영팀이 IAM 사용자 생성 API 호출을 감지해 알림을 보내려고 서울 리전(ap-northeast-2)의 default 이벤트 버스에 `AWS API Call via CloudTrail` 이벤트 패턴 규칙을 만들었다. 사용자를 만들어도 규칙이 한 번도 일치하지 않는다. 원인과 해결은?
- A) 서울 리전의 CloudTrail 추적이 꺼져 있으므로 추적을 켠다.
- B) IAM 같은 글로벌 서비스의 API 호출 이벤트는 us-east-1에서만 제공되므로 해당 규칙을 us-east-1에 만든다.
- C) 규칙당 대상이 5개를 넘어 일치가 중단됐으므로 대상을 줄인다.
- D) 이벤트 패턴의 ARN 구분자를 콜론으로 통일한다.

정답: B
정답 근거: 글로벌 서비스의 API 호출 이벤트는 us-east-1에서만 제공된다 [F21] — https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-troubleshooting.html
오답 이유: A) 추적 설정이 아니라 이벤트가 제공되는 리전이 문제다 [F21]. C) 대상 수는 일치 여부와 무관하다 [F15]. D) ARN은 정확 일치로 비교되지만 이 시나리오의 원인은 리전이다 [C51].

### Q4 (Skill 1.2.2 · advanced)
문제: CLI로 만든 EventBridge 규칙이 이벤트와 일치해 실행(TriggeredRules 증가)되는데 Lambda 대상 함수가 호출되지 않는다. 함수의 리소스 기반 정책을 확인했더니 `events.amazonaws.com`을 허용하는 문장에 SourceAccount 조건이 들어 있다. 어떻게 해결하는가?
- A) 규칙의 이벤트 패턴을 더 넓게 고친다.
- B) 규칙에 DLQ를 추가한다.
- C) 정책에서 SourceAccount 설정을 제거해 EventBridge가 함수를 호출할 수 있게 한다.
- D) 대상의 재시도 정책을 24시간으로 늘린다.

정답: C
정답 근거: SourceAccount 설정이 있으면 EventBridge가 함수를 호출할 수 없다 [F20] — https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-troubleshooting.html
오답 이유: A) 규칙은 이미 일치해 실행됐다. B) DLQ는 실패 이벤트 보존용이며 권한 문제를 고치지 않는다 [F19]. D) 재시도는 호출 자체가 가능할 때 의미가 있고 기본값이 이미 24시간이다 [F18].

### Q5 (Skill 1.2.3 · intermediate)
문제: 태그로 선택한 수백 대의 인스턴스에 Systems Manager Automation 런북을 실행한다. 오류가 한 건이라도 발생하면 추가 인스턴스에는 더 이상 실행되지 않도록 하려 한다. 무엇을 설정하는가?
- A) Concurrency를 0으로 설정한다.
- B) 오류 임계값(error threshold)을 0으로 설정한다.
- C) 런북의 `aws:executeScript` 제한 시간을 600초로 설정한다.
- D) 런북 이름을 WithApproval이 들어간 이름으로 바꾼다.

정답: B
정답 근거: 오류 임계값을 0으로 지정하면 첫 오류 이후 추가 대상에 실행을 멈춘다 [F29] — https://docs.aws.amazon.com/systems-manager/latest/userguide/running-automations-scale-controls.html
오답 이유: A) Concurrency는 동시에 실행할 리소스 수를 정하는 값이며 오류 시 중단 조건이 아니다 [F28]. C) 스크립트 단계 하나의 최대 실행 시간이다 [F26]. D) 승인 런북은 사람의 승인을 기다리게 할 뿐 오류 기반 중단과 무관하다 [F25].
