### 2.3.1 AWS 서비스를 이용한 스냅샷·백업 자동화

**먼저 구분할 것 — 서비스 고유의 자동화 vs 중앙 정책(AWS Backup).**

| 대상 | 서비스 고유 수단 | AWS Backup으로 할 때 | 시험 포인트 |
|---|---|---|---|
| EBS 볼륨·AMI | 스냅샷(증분 저장). Amazon Data Lifecycle Manager(DLM)가 EBS 스냅샷과 EBS 기반 AMI의 생성·보존·삭제를 정책으로 자동화한다 [F6] | 볼륨·EC2 인스턴스 백업 계획에 할당 | 중간 스냅샷을 지워도 이후 스냅샷으로 볼륨을 만들 수 있다 [F5]. DLM은 추가 비용 없이 쓸 수 있다 (보조(미인용): snapshot-lifecycle.html) |
| RDS | 자동 백업(보존 기간 0~35일) [F7] + 수동 스냅샷 | 스냅샷 백업과 연속 백업(PITR) 규칙 | 보존 기간을 0으로 바꾸면 자동 백업이 꺼진다. 0과 0이 아닌 값 사이 변경은 중단을 일으킨다 (보조(미인용): USER_WorkingWithAutomatedBackups.BackupRetention.html) |
| DynamoDB | 온디맨드 백업은 프로비저닝 처리량을 쓰지 않는다 [F8], PITR은 최근 35일 [F15] | 백업 계획으로 일정·보존·교차 리전 복사 | AWS Backup으로 만든 백업은 DynamoDB 콘솔에서 삭제할 수 없다 (보조(미인용): CreateBackup.html) |
| S3 | 버전 관리·복제 | 버킷에 S3 버전 관리를 반드시 켜야 한다 [F1]. 연속 백업은 최근 35일 내 임의 시점 복원 [F2] | S3 백업은 콜드 스토리지 전환이 지원되지 않는다 (보조(미인용): s3-backups.html) |
| FSx | 기본으로 하루 한 번 자동 백업 [F9] | 계획에 할당 가능 | Lustre는 스크래치 파일 시스템 백업 불가 (보조(미인용): LustreGuide using-backups-fsx.html) |
| EFS | One Zone 파일 시스템은 AWS Backup으로 자동 백업된다 (보조(미인용): efs features.html) | 계획에 할당 가능 | — |

**AWS Backup 구성 요소(개념).** 백업 계획(plan)→규칙(rule: 일정·보존·수명 주기·복사 대상)→백업 볼트(vault)→리소스 할당(태그 또는 리소스 ID). 태그 기반 할당은 새 리소스가 태그만 달면 자동으로 계획에 들어와 관리 부담이 줄어든다 (보조(미인용): whatisbackup.html "Tag-based backup policies", AWS Storage Blog).

- **수명 주기 규칙.** 콜드 스토리지로 전환한 백업은 최소 90일을 그곳에 보관해야 하므로 보존 기간은 전환 일수보다 90일 이상 커야 한다 [F3].
- **볼트 잠금(Vault Lock).** 거버넌스 모드는 적절한 IAM 권한을 가진 사용자가 관리·삭제할 수 있고, 규정 준수(compliance) 모드는 어떤 사용자도 AWS도 변경·삭제할 수 없다 [F4] (보조(미인용): vault-lock.html — 거버넌스 모드 설명). 규정 준수 모드는 쿨링오프(유예) 기간이 지나야 불변이 되며 AWS Backup은 72시간의 쿨링오프를 강제한다 (보조(미인용): CloudFormation LockConfigurationType 문서 `ChangeableForDays`).
- **교차 리전·교차 계정 복사.** AWS Backup은 백업을 다른 리전(예: DR 리전)으로 복사할 수 있고, 교차 계정 복사는 내부자 위협·계정 침해에 대비한다 (보조(미인용): disaster-recovery-options-in-the-cloud.html).
- **복원 테스트.** AWS Backup 복원 테스트 계획은 일정에 따라 복원 작업을 시작하고 완료 시간을 측정한다. 결과로 규정 준수와 RTO 달성 여부를 보여 줄 수 있다 (보조(미인용): restore-testing.html).
- **지원 리소스 범위 확인.** EC2·EBS·S3·DynamoDB·RDS·Aurora·EFS·FSx·Storage Gateway 볼륨·DocumentDB·Neptune·Redshift 등이 나열된다 (보조(미인용): whatisbackup.html). 단 가이드의 in-scope 목록에는 Neptune·FSx for OpenZFS가 out-of-scope로 표기되어 있으므로 문항 범위에서는 제외로 본다.

### 2.3.2 RTO·RPO·비용에 맞는 데이터베이스 복원 방법

**복원 방법은 "얼마나 최근 시점까지(RPO)", "얼마나 빨리(RTO)", "얼마의 추가 비용으로"의 세 축으로 고른다.**

| 방법 | 되돌리는 시점(RPO 성격) | 속도·방식(RTO 성격) | 비용·제약 | 근거 |
|---|---|---|---|---|
| RDS 특정 시점 복원(PITR) | 보존 기간 안의 임의 시점. 트랜잭션 로그를 5분마다 S3에 올리므로 최신 복원 가능 시점은 그 주기에 좌우된다 | 원본을 건드리지 않고 새 DB 인스턴스를 만든다. 가장 가까운 백업을 복원한 뒤 로그를 적용하므로 로그가 많을수록 오래 걸린다 (보조(미인용): repost 지식 센터 rds-point-in-time-restore-issues) | 자동 백업 스토리지. 복원 인스턴스는 기본 파라미터·옵션 그룹에 연결된다 | [F10][F11][F12] |
| RDS 스냅샷 복원 | 스냅샷 시점 | 새 DB 인스턴스를 만든다. 기존 인스턴스로 복원할 수 없다 (보조(미인용): repost 지식 센터 restore-rds-instance-from-snapshot) | 수동 스냅샷은 인스턴스를 삭제해도 지워지지 않고 리전당 100개 한도가 있다 (보조(미인용): USER_WorkingWithAutomatedBackups.html) | 보조 |
| Aurora 백트랙(MySQL 호환) | 지정 시점(대상 백트랙 창 안) | 백업에서 복원하지 않고 클러스터를 되감는다 — 새 클러스터 없이 분 단위 | 변경 레코드를 저장하는 시간당 요금. 백업·복원의 대체가 아니다 (보조(미인용): 같은 페이지) | [F13] |
| Aurora 복제(clone) | 복제 시점 | 스냅샷 복원보다 빠르고 공간 효율적 | 변경분에만 추가 스토리지 | [F14] |
| DynamoDB PITR | 최근 35일 안의 임의 시점 (최신 복원 가능 시점은 보통 5분 전 — 보조(미인용): API_UpdateContinuousBackups.html) | 항상 새 테이블로 복원 | PITR 요금. 복원 후 auto scaling·IAM·알람·TTL·PITR 설정 등은 수동 재설정 (보조(미인용): GettingStartedBackupsAWS.html) | [F15][F16] |
| AWS Backup 연속 백업(RDS·S3 등) | 최근 35일 내 시점, 가장 최근 복원 지점과 현재 사이 최대 5분 (보조(미인용): help-panel continuous-backups-rds.html) | 복원 작업으로 새 리소스 생성 | 스냅샷 규칙과 한 계획에 함께 둘 수 있다 | [F2] |

- **결정 규칙.** RPO가 분 단위(실수로 지운 직후 되돌리기)라면 PITR·연속 백업·백트랙. 복원 속도가 최우선이면 새 리소스를 만들지 않는 백트랙(Aurora MySQL)이나 사전 복제본·스탠바이(Task 2.2.2, 2.3.4). 비용을 줄이려면 보존 기간을 필요한 만큼만 두고 장기 보관은 스냅샷/AWS Backup 수명 주기로 넘긴다.
- **복원 후 체크리스트.** 새 인스턴스·새 테이블이므로 엔드포인트·연결 문자열 전환, 보안 그룹·파라미터 그룹, DynamoDB의 auto scaling 정책·알람·TTL·PITR 설정 재구성, 복원 직후 성능 저하(백그라운드 로딩) 가능성 (보조(미인용): USER_PIT.html — 복원 후 볼륨이 백그라운드로 데이터 블록을 계속 로드).
- **복원 테스트.** 복원이 되는지, 얼마나 걸리는지를 정기적으로 측정해야 RTO를 말할 수 있다. 백서도 복원은 control plane 작업이므로 주기적 복원이 좋다고 한다 (보조(미인용): disaster-recovery-options-in-the-cloud.html).

### 2.3.3 스토리지 서비스 버전 관리 (S3, FSx)

**S3 버전 관리는 "덮어쓰기·삭제를 되돌릴 수 있는 능력"이고, 켜는 순간 비용과 운영 규칙이 바뀐다.**

| 주제 | 사실 | 근거 |
|---|---|---|
| 상태 | 버킷 상태는 unversioned(기본)·versioning-enabled·versioning-suspended 3가지. 한 번 켜면 unversioned로 돌아갈 수 없고 suspended만 가능 | [F17] (3가지 상태 목록은 보조(미인용): Versioning.html) |
| 삭제 동작 | 삭제하면 객체를 영구 삭제하지 않고 삭제 마커를 삽입한다. 영구 삭제하려면 버전 ID를 지정한다 | [F18] (보조(미인용): DeletingObjectVersions.html) |
| 비용 | 각 버전은 객체 전체이며 diff가 아니다 → 3개 버전이면 3개 객체로 과금 | [F19] |
| MFA Delete | 버전 영구 삭제·버전 관리 상태 변경에 추가 인증을 요구. 버킷 소유자(루트 계정)만 켤 수 있고 콘솔로는 켤 수 없다 | [F20] (콘솔 불가는 보조(미인용): MultiFactorAuthenticationDelete.html) |
| 수명 주기 | MFA Delete는 수명 주기 구성과 함께 쓸 수 없다. 오래된(noncurrent) 버전 만료는 NoncurrentVersionExpiration으로 하며 NewerNoncurrentVersions로 보존 개수를 유지할 수 있다 | [F21] (보조(미인용): API_NoncurrentVersionExpiration.html, lifecycle-configuration-examples.html) |
| 연관 기능 | S3 복제는 소스·대상 버킷 모두 버전 관리 필요 [F29]. Object Lock도 버전 관리가 켜진 버킷에서만 동작 (보조(미인용): object-lock.html). AWS Backup for S3도 버전 관리 필요 [F1] | [F29][F1] |

- **운영 체크리스트.** ① 버전 관리를 켜기 전에 기존 수명 주기에 만료 규칙이 있다면 noncurrent 만료를 추가해야 같은 영구 삭제 동작이 유지된다 (보조(미인용): Versioning.html Important 박스). ② 버전이 쌓이면 저장 비용이 늘므로 수명 주기로 이전 버전을 저비용 클래스로 보내거나 만료시킨다 [F19]. ③ 삭제된 것처럼 보이는 객체는 삭제 마커를 지우거나 이전 버전을 복원해서 되살린다 [F18].
- **FSx.** FSx for Windows File Server는 Windows 섀도 복사본(shadow copies)으로 사용자가 파일·폴더를 이전 버전으로 되돌릴 수 있다 (보조(미인용): shadow-copies-fsxW.html, aws.amazon.com/fsx/windows/features/). 파일 시스템당 최대 500개까지 저장하며 [F22], 기본 저장 한도는 파일 시스템 용량의 10%(보조(미인용): setting-up-fsx-shadow-copies.html), 기본 일정은 평일 오전 7시·정오(UTC) (같은 페이지). 섀도 복사본은 파일 시스템 내부에 저장되는 반면 FSx 백업은 S3에 저장되고 새 파일 시스템으로 복원한다 (보조(미인용): AWS Storage Blog "Enabling Microsoft shadow copies with Amazon FSx for Windows File Server"). FSx for OpenZFS는 가이드 out-of-scope에 있다.
- **S3·FSx 외 스토리지.** Skill 예시는 S3와 FSx다. 참고로 EBS는 스냅샷으로 시점 복원하고 [F5], EFS는 AWS Backup으로 백업한다 (보조(미인용): efs features.html — One Zone 파일 시스템은 AWS Backup으로 자동 백업).

### 2.3.4 재해 복구 절차·모범 사례 (백업 및 복원 / 파일럿 라이트 / 예열 대기 / 액티브-액티브)

**v1.1에서 추가된 부분이다 — 4전략을 "무엇이 상시 가동되는가"와 "재해 시 무엇을 하는가"로 구분한다.**

| 전략 | 상시 상태 | 재해 시 작업 | 비용·복잡도 | 근거 |
|---|---|---|---|---|
| 백업 및 복원 (Backup and restore) | 백업 데이터만 (필요하면 다른 리전으로 복제) | 데이터에 더해 인프라·구성·애플리케이션 코드를 복구 리전에 재배포 (IaC 권장) | 가장 낮음. 데이터 손실·손상 완화에 적합 | [F23] (보조(미인용): 백서 Backup and restore 절) |
| 파일럿 라이트 (Pilot light) | 데이터 복제 + 핵심 인프라 사본. DB·스토리지는 상시 가동, 앱 서버는 꺼짐 | 서버를 켜고(deploy) 확장. 요청을 처리하려면 추가 조치가 선행되어야 함 | 낮음~중 | [F24] |
| 예열 대기 (Warm standby) | 축소됐지만 완전히 동작하는 사본이 항상 실행 | 확장만 하면 됨. 즉시 (축소된 용량으로) 트래픽 처리 | 중~높음 | [F25][F24] |
| 멀티 사이트 액티브/액티브 (Multi-site active/active) | 여러 리전이 동시에 서비스 | 장애 조치 개념이 없고 손실 리전으로의 트래픽 우회가 핵심 | 가장 복잡하고 비쌈 | [F26] (보조(미인용): 백서 — 가장 복잡하고 비싼 접근, 복구 시간을 0에 가깝게 가능) |

- **파일럿 라이트와 예열 대기 구분.** 둘 다 DR 리전에 주 리전 자산의 사본을 두지만, 파일럿 라이트는 추가 조치 없이는 요청을 처리할 수 없고 예열 대기는 즉시 처리한다 [F24]. 예열 대기는 완전한 기능을 하는 축소 사본이다 [F25]. 시험은 RTO·RPO 수치와 "즉시 트래픽 처리" 문구로 가른다.
- **데이터 복제 수단(RPO를 낮추는 도구).** S3 복제(소스·대상 버전 관리 필요 [F29]), Aurora 글로벌 데이터베이스(보조 리전으로 일반적으로 1초 미만 지연 [F27]), RDS 교차 리전 읽기 복제본(재해 시 직접 승격 [F28]), DynamoDB 글로벌 테이블(기본 모드는 최종적 일관성이고 강한 일관성 모드는 RPO 0 [F30]), AWS Backup 교차 리전 복사 (보조(미인용): 백서).
- **DynamoDB 글로벌 테이블 모드.** MREC(기본, 변경이 보통 1초 안에 다른 복제본으로 복제)와 MRSC(동기 복제로 RPO 0) 두 모드가 있다 [F30] (보조(미인용): HowItWorks.ReadConsistency.html). 기존 레포 문서의 "최종 일관성"만 있는 설명은 MRSC 이전 기준이다.
- **절차·모범 사례(백서 기준).** ① 복구 리전에서 인프라를 빠르고 오류 없이 재배포하도록 IaC(CloudFormation·CDK)를 쓴다 (보조(미인용): 백서 Backup and restore 절). ② 백업 전략에는 백업 테스트가 포함되어야 하고, 복원은 control plane 작업이므로 주기적 복원이 필요하다 (보조(미인용): 같은 백서). ③ 활성/수동 구성의 트래픽 전환에는 Route 53 또는 AWS Global Accelerator를 쓴다 (보조(미인용): 같은 백서 Multi-site 절 — Route 53 상태 확인은 Task 2.2.1, ARC는 Task 2.2.2 참조). ④ 장애 조치에는 가능하면 control plane이 아니라 data plane 작업만 쓴다 (보조(미인용): 같은 백서 도입부).
- **AWS Elastic Disaster Recovery(DRS).** 백서는 이 서비스를 파일럿 라이트 구현으로 소개한다 (보조(미인용): 백서 "AWS Elastic Disaster Recovery" 절). v1.1 in-scope·out-of-scope 목록 어디에도 이름이 없으므로 출제 범위는 99 조각에 범위해석으로 기록했다.

## 3. 시험에서 묻는 방식 (가이드 Skill 문구 기반 추정 — 실제 문항 아님)

아래는 AWS가 공개한 Skill 문구(동사 "Automate", "Use various methods ... to meet RTO, RPO, and cost", "Implement versioning", "Follow ... procedures and best practices")에서 추론한 출제 패턴이며, 실제 기출을 아는 것이 아니다.

- 패턴 1 — 백업 자동화 수단·전제 조건 고르기: "여러 서비스 리소스를 정책으로 자동 백업하고 보존한다 / S3 버킷이 백업되지 않는다." 근거 Skill 문구: "Automate snapshots and backups ... by using AWS services (for example, AWS Backup)". 판단 기준: 다중 서비스 중앙 정책 → AWS Backup, EBS·AMI 한정 → DLM [F6], S3는 버전 관리 필수 [F1], 콜드 스토리지는 90일 규칙 [F3], 불변성은 Vault Lock 규정 준수 모드 [F4].
- 패턴 2 — 복원 방법 선택: "실수로 잘못된 변경을 한 직후, RPO·RTO·비용 제약에서 가장 적절한 복원은?" 근거: "Use various methods to restore databases (for example, point-in-time restore) to meet RTO, RPO, and cost requirements". 판단 기준: PITR은 새 인스턴스 [F10]·5분 로그 주기 [F11], Aurora MySQL 백트랙은 새 클러스터 없이 되감기 [F13], 복제(clone)는 빠르고 공간 효율 [F14], DynamoDB는 PITR 35일 [F15]·새 테이블만 [F16].
- 패턴 3 — 버전 관리 동작 이해: "버전 관리 버킷에서 삭제·복원·영구 삭제·비용." 근거: "Implement versioning for storage services (for example, Amazon S3, Amazon FSx)". 판단 기준: 되돌릴 수 없는 활성화 [F17], 삭제 마커 [F18], 버전당 전체 객체 과금 [F19], MFA Delete 제약 [F20][F21], FSx 섀도 복사본 [F22].
- 패턴 4 — DR 전략 선택·절차: "주어진 RTO·RPO·비용에 맞는 전략과 재해 시 수행 절차." 근거(v1.1 신규 문구): "backup and restore, pilot light, warm standby, active/active". 판단 기준: 상시 가동 범위 [F23]·[F24]·[F25]·[F26], 복제 수단 [F27][F28][F29][F30].

## 4. 흔한 함정 · 혼동 짝

| 혼동 짝 | 구분 기준 | 근거 |
|---|---|---|
| AWS Backup vs DLM | AWS Backup=다중 서비스 정책, DLM=EBS 스냅샷·EBS 기반 AMI 한정 | [F6] |
| EBS 중간 스냅샷 삭제 | 삭제해도 이후 스냅샷으로 볼륨 생성 가능(참조 블록 보존) | [F5] |
| RDS 자동 백업 보존 기간 | 0~35일(0=끔), 콘솔 생성 기본 7일 vs CLI·API 기본 1일. Multi-AZ DB 클러스터·Aurora는 1~35일 | [F7] (기본값·클러스터 범위는 보조(미인용): BackupRetention.html, Aurora.Managing.Backups.html) |
| AWS Backup S3 전제 | 버킷 버전 관리가 켜져 있어야 하며 연속 백업은 최근 35일 | [F1][F2] |
| 콜드 스토리지 규칙 | 전환 후 최소 90일 보관 → 보존 기간 ≥ 전환일수+90 | [F3] |
| Vault Lock 모드 | 거버넌스=권한 있는 사용자는 관리·삭제 가능, 규정 준수=누구도(AWS 포함) 변경·삭제 불가 | [F4] |
| RDS PITR vs 스냅샷 복원 | 둘 다 새 DB 인스턴스. PITR은 로그 5분 주기로 임의 시점, 스냅샷은 스냅샷 시점 | [F10][F11] |
| Aurora 백트랙 vs PITR 복원 vs clone | 백트랙=제자리 되감기(새 클러스터 없음, MySQL), PITR=새 클러스터, clone=빠른 복사 | [F13][F14] |
| 복원 후 설정 | RDS는 기본 파라미터·옵션 그룹에 연결되고, DynamoDB 복원은 auto scaling·알람·TTL 등을 다시 설정해야 한다 | [F12][F16] |
| DynamoDB PITR vs 온디맨드 백업 | PITR=최근 35일 임의 시점, 온디맨드 백업=처리량 소모 없는 전체 백업 | [F15][F8] |
| S3 삭제 vs 영구 삭제 | 삭제는 삭제 마커, 영구 삭제는 버전 ID 지정 | [F18] |
| 버전 관리 비용 | 버전마다 객체 전체 과금 | [F19] |
| MFA Delete 활성화 주체·제약 | 버킷 소유자(루트)만, 수명 주기와 함께 사용 불가 | [F20][F21] |
| FSx 섀도 복사본 vs 백업 | 섀도 복사본=파일 시스템 내부·사용자 복원, 백업=S3·새 파일 시스템 | [F22][F9] |
| 파일럿 라이트 vs 예열 대기 | 파일럿 라이트=추가 조치 필요(서버 켜기), 예열 대기=즉시 처리(축소 용량) | [F24][F25] |
| 액티브/액티브의 장애 조치 | 장애 조치 개념 없음(트래픽 우회). 데이터 손상은 백업에 의존 | [F26] |
| 교차 리전 읽기 복제본 | 재해 시 운영자가 직접 승격 | [F28] |
| S3 복제 전제 | 소스·대상 버킷 모두 버전 관리 | [F29] |
| DynamoDB 글로벌 테이블 일관성 | 기본 MREC(최종적 일관성) vs MRSC(RPO 0) | [F30] |

## 6. 자가 점검 문항 후보 (3~5) — 후보일 뿐, 검증 아님

### Q1 (Skill 2.3.1 · intermediate)
문제: 팀이 AWS Backup 계획으로 여러 S3 버킷을 백업하려 하는데 한 버킷만 백업 작업이 실패한다. 그 버킷은 일반 용도 버킷이고 권한도 충분하다. 가장 먼저 확인해야 할 사항은?
- A) 버킷에 S3 버전 관리가 켜져 있는지
- B) 버킷에 MFA Delete가 켜져 있는지
- C) 버킷이 S3 Glacier Deep Archive에 있는지
- D) 버킷에 Transfer Acceleration이 켜져 있는지
정답: A
정답 근거: AWS Backup으로 S3를 백업하려면 버킷에서 S3 버전 관리를 켜야 한다 [F1]. — https://docs.aws.amazon.com/aws-backup/latest/devguide/s3-backups.html
오답 이유: B) MFA Delete는 백업 전제가 아니며 수명 주기와도 함께 쓸 수 없는 별도 기능이다 [F21]. C) 객체 스토리지 클래스 제약은 부차적이다. D) Transfer Acceleration은 업로드 성능 기능이다.

### Q2 (Skill 2.3.2 · intermediate)
문제: RDS for PostgreSQL DB 인스턴스(자동 백업 보존 7일)에서 30분 전 배포가 데이터를 손상시켰다. 가장 최근 정상 시점인 35분 전 상태를 확인하면서 기존 DB는 그대로 두고 싶다. 무엇을 해야 하는가?
- A) 기존 DB 인스턴스에 자동 백업을 덮어써 복원한다.
- B) 35분 전 시점으로 특정 시점 복원을 수행해 새 DB 인스턴스를 만들고 검증 후 엔드포인트를 전환한다.
- C) Aurora 백트랙으로 35분 전으로 되감는다.
- D) 읽기 전용 복제본을 기본 인스턴스로 승격한다.
정답: B
정답 근거: 특정 시점 복원은 원본 DB 인스턴스를 수정하지 않고 새 DB 인스턴스를 만들고 [F10], 트랜잭션 로그가 5분마다 올라가므로 보존 기간 안의 임의 시점을 고를 수 있다 [F11]. 복원 인스턴스는 기본 파라미터 그룹에 연결되므로 필요하면 사용자 지정 그룹을 지정한다 [F12]. — https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html
오답 이유: A) 복원은 기존 인스턴스에 덮어쓰지 않고 새 인스턴스를 만든다 [F10]. C) 백트랙은 Aurora MySQL 호환 에디션 기능이며 RDS for PostgreSQL에는 해당하지 않는다 [F13]. D) 읽기 복제본은 손상된 데이터도 복제한다.

### Q3 (Skill 2.3.2 · advanced)
문제: 백트랙이 켜진 Aurora MySQL 클러스터에서 WHERE 없는 DELETE가 실수로 실행되었다. 복구는 새 클러스터를 만들지 않고 몇 분 안에 끝나야 한다. 가장 적절한 방법은?
- A) 클러스터 스냅샷에서 새 클러스터로 복원한다.
- B) 클러스터를 DELETE 이전 시점으로 백트랙한다.
- C) 클러스터를 복제(clone)한 뒤 애플리케이션을 전환한다.
- D) 읽기 복제본을 새 기본 인스턴스로 승격한다.
정답: B
정답 근거: 백트랙은 백업에서 데이터를 복원하지 않고 DB 클러스터를 특정 시점으로 되감는다 [F13]. — https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/AuroraMySQL.Managing.Backtrack.html
오답 이유: A) 스냅샷/PITR 복원은 새 클러스터를 만든다 [F13]. C) 복제는 빠르지만 새 클러스터이며 시점을 되돌리는 도구가 아니다 [F14]. D) 승격은 장애 조치용이다.

### Q4 (Skill 2.3.3 · intermediate)
문제: 보안팀이 S3 버킷에 버전 관리를 켜고, 영구 삭제에 MFA를 요구하며(MFA Delete), 90일 지난 이전 버전은 수명 주기로 만료시키려 한다. 어떤 설명이 맞는가?
- A) 세 가지를 모두 한 버킷에서 함께 구성할 수 있다.
- B) MFA Delete는 수명 주기 구성과 함께 쓸 수 없으므로 이전 버전 만료와 MFA Delete 중 하나를 선택해야 한다.
- C) MFA Delete는 IAM 관리자라면 콘솔에서 켤 수 있다.
- D) 버전 관리는 켠 뒤에도 언제든 unversioned로 되돌릴 수 있다.
정답: B
정답 근거: MFA Delete는 수명 주기 구성과 함께 사용할 수 없다 [F21]. MFA Delete는 버킷 소유자(루트 계정)만 켤 수 있다 [F20]. 버전 관리는 켜면 unversioned로 돌아갈 수 없다 [F17]. — https://docs.aws.amazon.com/AmazonS3/latest/userguide/MultiFactorAuthenticationDelete.html
오답 이유: A) 수명 주기와 MFA Delete는 함께 구성할 수 없다 [F21]. C) 켤 수 있는 주체는 루트 계정이다 [F20]. D) 일시 중지만 가능하다 [F17].

### Q5 (Skill 2.3.4 · intermediate)
문제: 회사가 파일럿 라이트 전략을 쓴다. 주 리전에 RDS가 있고 DR 리전에는 교차 리전 읽기 복제본과 꺼져 있는(배포되지 않은) 앱 서버 구성이 준비되어 있다. 주 리전 전체 장애가 선언되었을 때 운영자가 해야 하는 작업은?
- A) 아무 조치 없이 파일럿 라이트가 즉시 트래픽을 처리한다.
- B) 읽기 복제본을 기본 인스턴스로 승격하고, 앱 서버를 켜서 확장한 뒤 트래픽을 DR 리전으로 전환한다.
- C) DR 리전의 읽기 복제본이 자동으로 승격되므로 앱 서버만 확인한다.
- D) AWS Backup 교차 리전 복사본이 자동으로 복원되기를 기다린다.
정답: B
정답 근거: 파일럿 라이트는 추가 조치 없이는 요청을 처리할 수 없다 [F24]. DR 리전에서 읽기/쓰기를 하려면 RDS 읽기 복제본을 직접 기본 인스턴스로 승격해야 한다 [F28]. — https://docs.aws.amazon.com/whitepapers/latest/disaster-recovery-workloads-on-aws/disaster-recovery-options-in-the-cloud.html
오답 이유: A) 즉시 처리는 예열 대기의 특징이다 [F24][F25]. C) 읽기 복제본 승격은 자동이 아니다 [F28]. D) 백서는 AWS Backup이 복원 기능은 제공하지만 예약·자동 복원은 현재 제공하지 않는다고 설명한다 (보조(미인용): 같은 백서 Backup and restore 절).
