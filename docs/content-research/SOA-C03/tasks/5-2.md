## 2. 핵심 개념 (한국어)

### 5.2.1 DNS 구성 — Route 53 Resolver·프라이빗 호스팅 영역
**큰 그림.** VPC 안의 DNS 질의는 먼저 VPC에 내장된 리졸버(Amazon DNS 서버)로 간다. 이 리졸버는 VPC 기본 IPv4 CIDR의 기준 주소 +2(예: 10.0.0.2)와 링크-로컬 주소(169.254.169.253, fd00:ec2::253)로 접근된다 [F1]. 그래서 운영자가 직접 '구성'해야 하는 일은 세 가지로 좁혀진다.
1. VPC 안의 사설 이름을 풀어 주는 프라이빗 호스팅 영역(PHZ)을 쓰도록 VPC 속성을 맞춘다 [F6].
2. VPC 밖(온프레미스·다른 VPC)과 이름을 주고받는 하이브리드 DNS — Resolver 엔드포인트와 전달 규칙 [F2][F3][F4].
3. 같은 이름을 두 군데에서 정의했을 때 어느 쪽이 이기는지 [F7].

> 이름 주의 — 현행 Route 53 개발자 가이드는 이 서비스를 'Route 53 VPC Resolver'(이전 이름 Route 53 Resolver)로 부르지만, 시험 가이드 Skill 문구는 'Route 53 Resolver'다. 같은 서비스이며 표기 차이는 99 조각에 정리했다. (DNS Firewall은 Task 5.1.3 파일에서 다룬다.)

**Resolver 엔드포인트 — 방향이 곧 정답**
| 구분 | 인바운드 엔드포인트 | 아웃바운드 엔드포인트 |
|---|---|---|
| 질의 방향 | 온프레미스·다른 VPC → 이 VPC [F2] | 이 VPC → 온프레미스·다른 VPC [F3] |
| 만드는 것 | 엔드포인트(VPC 안의 IP 주소로 보이는 ENI) + 온프레미스 DNS에 '이 도메인은 이 IP로 전달' 설정 | 엔드포인트 + 도메인별 전달 규칙(대상 DNS IP) + 규칙을 VPC에 연결 [F4] |
| 규칙 | 없음 — 전달 판단은 온프레미스 DNS가 한다 | 있어야 한다. 규칙은 VPC에 적용되고 여러 계정이 공유할 수 있다 [F4] |
| 가용성 | IP 최소 2개(가능하면 2개 이상의 AZ) [F5] | 같은 리전의 여러 VPC가 엔드포인트 하나를 공유할 수 있음(보조 확인) |
| 증상 → 점검 | 온프레미스에서 PHZ 이름이 안 풀림 → 인바운드 엔드포인트 IP·온프레미스 전달 설정 | VPC에서 온프레미스 이름이 안 풀림 → 규칙·VPC 연결·대상 DNS IP 도달성 |

**결정 규칙**
| 상황 | 선택 | 근거 |
|---|---|---|
| 온프레미스가 VPC(PHZ) 이름을 풀어야 한다 | 인바운드 엔드포인트 + 온프레미스 DNS의 조건부 전달 | [F2] |
| VPC 인스턴스가 온프레미스 도메인을 풀어야 한다 | 아웃바운드 엔드포인트 + 전달 규칙(대상 = 온프레미스 DNS) + VPC 연결 | [F3][F4] |
| 여러 계정의 VPC가 같은 전달 규칙을 써야 한다 | 규칙을 AWS RAM으로 공유하고 각 계정이 자기 VPC에 연결 | [F4] |
| 같은 이름의 PHZ와 전달 규칙이 둘 다 있다 | 규칙이 이긴다 → 의도한 쪽인지 점검 | [F7] |
| PHZ 이름이 VPC에서 안 풀린다 | enableDnsHostnames·enableDnsSupport 둘 다 true인지, 그 VPC가 PHZ에 연결됐는지 | [F6] |
| 엔드포인트 장애에 대비하고 싶다 | IP를 2개 이상(AZ를 나눠서) | [F5] |

- **왜 규칙이 PHZ를 이기는가.** 같은 이름의 PHZ와 전달 규칙이 한 VPC에 함께 걸려 있으면 규칙이 우선하므로 질의가 온프레미스로 나간다 [F7]. 그래서 PHZ에 레코드를 분명히 만들었는데도 VPC에서는 '그 레코드가 무시되는' 것처럼 보인다. 이때는 한쪽을 지우거나 도메인 이름을 나누는 쪽으로 푼다.
- **왜 PHZ에 두 속성이 모두 필요한가.** PHZ 이름은 VPC의 리졸버가 풀어 주고, 리졸버 사용 여부를 정하는 것이 VPC 속성이다. 공식 요건은 enableDnsHostnames·enableDnsSupport 둘 다 true이므로 [F6], 하나라도 false이면 PHZ를 쓸 수 있는 VPC 설정이 아니다. (Task 5.1의 VPC DNS 속성 설명과 같은 속성이다.)
- **도메인 이름과 위임(Task 제목의 'domains').** Skill 문구에는 도메인 등록·네임서버 위임이 직접 나오지 않지만 Task 제목에는 있다(99 조각 참조). 보조 확인: 도메인을 Route 53에 등록하면 같은 이름의 퍼블릭 호스팅 영역이 자동으로 만들어지고, 다른 호스팅 영역에 레코드를 만들었다면 도메인의 네임서버를 그 영역의 네임서버로 바꿔야 한다(§7: How internet traffic is routed to your website or web application / Registering a new domain).

**보조 확인(§5 한도로 표 미수록)**
- 엔드포인트 보안 그룹: 인바운드 엔드포인트는 TCP·UDP 53 인바운드, 아웃바운드 엔드포인트는 TCP·UDP 53 아웃바운드를 허용해야 한다. 엔드포인트 IP는 공인 주소가 아니라서 DX·VPN(아웃바운드는 NAT 게이트웨이도)으로 네트워크가 이어져 있어야 한다 (§7: How DNS resolvers on your network forward DNS queries / How Resolver endpoints forward DNS queries from your VPCs / Forwarding inbound DNS queries / Forwarding outbound DNS queries).
- 질의가 여러 규칙에 일치하면 가장 구체적인 규칙이 선택된다. 온프레미스에서 VPC CIDR+2 주소로 직접 전달하는 구성은 지원되지 않으며 인바운드 엔드포인트를 쓰라고 안내한다 (§7: Resolving DNS queries between VPCs and your network).
- Amazon DNS 서버로 오가는 트래픽은 네트워크 ACL·보안 그룹으로 거를 수 없고, 링크-로컬 서비스(리졸버·IMDS·NTP 합산)에는 네트워크 인터페이스당 초당 1,024패킷 한도가 있으며 증설할 수 없다 (§7: Understanding Amazon DNS).
- 일치하는 PHZ가 있는데 그 안에 해당 레코드가 없으면 공용 리졸버로 넘기지 않고 NXDOMAIN을 돌려준다. 공용 영역과 PHZ를 같은 이름으로 두면 스플릿 뷰(split-view) DNS가 된다 (§7: Considerations when working with a private hosted zone).
- 다른 계정에서 만든 VPC를 PHZ에 연결하려면 연결을 승인(authorize)한 뒤 프로그래밍 방식(CLI·API)으로 연결한다 (§7: Creating a private hosted zone).
- S3 인터페이스 엔드포인트의 프라이빗 DNS를 'inbound Resolver endpoint에만' 적용하는 옵션이 있다. 이 경우 온프레미스의 S3 요청은 인터페이스 엔드포인트로, VPC 안의 요청은 게이트웨이 엔드포인트로 가서 비용을 줄인다 (§7: Gateway endpoints for Amazon S3; Task 5.1 파일의 엔드포인트 비용 항목과 연결).

### 5.2.2 Route 53 라우팅 정책·구성·쿼리 로깅
**큰 그림.** 레코드(이름+유형+값)에 '라우팅 정책'을 붙이면 Route 53이 같은 이름·유형의 레코드 묶음 중 어느 값으로 응답할지 규칙이 생긴다. 시험은 대개 '요구 한 줄 → 정책 이름'으로 묻기 때문에, 정책마다 '무엇을 기준으로 고르는가'만 정확히 갈라 두면 된다. 현행 공식 문서의 정책은 8종이다.

**라우팅 정책 8종 비교**
| 정책 | 고르는 기준 | 구성 포인트 | 근거 |
|---|---|---|---|
| Simple | 단일 리소스(웹 서버 하나 등) | 한 레코드에 값을 여러 개 넣을 수 있으나 헬스 체크 대상이 아니다(보조 확인) | — |
| Weighted | 비율 분배·점진 배포(카나리) | 가중치는 0~255 정수, 0이면 그 리소스로 라우팅 중단 | [F8] |
| Latency | 사용자에게 지연이 가장 낮은 AWS 리전 | 리전마다 레코드를 만든다. 지연 데이터는 AWS 데이터센터 기준이라 리소스가 없는 리전은 실제와 다를 수 있다(보조 확인) | [F9] |
| Failover | active-passive(평소 primary, 비정상일 때 secondary) | primary·secondary 레코드에 헬스 체크 또는 Evaluate Target Health | [F10][F11] |
| Geolocation | 사용자 위치(대륙·국가·미국 주) | 매핑 불가/미지정 지역을 받을 default 레코드가 없으면 그 질의엔 응답이 없다 | [F12] |
| Geoproximity | 리소스 위치(리전·로컬 영역·위도/경도) + 트래픽 범위 조정 | bias 양수(1~99)는 범위 확대, 음수(-1~-99)는 축소 | [F13] |
| IP-based | 사용자 IP 대역(CIDR 컬렉션) → 엔드포인트 직접 매핑(예: 특정 ISP) | 프라이빗 호스팅 영역에서는 쓸 수 없다 | [F14] |
| Multivalue answer | DNS로 헬스 체크된 정상 값을 여러 개 돌려줌 | 정상 레코드를 최대 8개까지 응답. 로드 밸런서 대체가 아님(보조 확인) | [F15] |

**요구 → 정책 결정 규칙**
| 요구 | 정책 | 근거 |
|---|---|---|
| 평소엔 A, A가 비정상일 때만 B로 | Failover(active-passive) | [F10] |
| 모든 리소스를 늘 활성으로 두고 비정상만 응답에서 제외 | failover 이외의 정책 + 헬스 체크(active-active) | [F10] |
| 신버전 5%, 기존 95% | Weighted(예: 5/95), 롤백은 가중치 0 | [F8] |
| 사용자에게 가장 빠른 리전 | Latency | [F9] |
| 국가별 콘텐츠·규제 | Geolocation(+ default 레코드) | [F12] |
| 리소스 위치 기준으로 가까운 쪽 + 범위 미세 조정 | Geoproximity(bias) | [F13] |
| 특정 ISP·CIDR를 특정 엔드포인트로 | IP-based(퍼블릭 영역 전용) | [F14] |
| DNS로 정상 IP 여러 개를 돌려 가용성을 조금 높이기 | Multivalue answer | [F15] |

**별칭(alias) vs CNAME**
| 항목 | 별칭 레코드 | CNAME 레코드 |
|---|---|---|
| zone apex(example.com) | 만들 수 있다 [F16] | 만들 수 없다 [F16] |
| 대상 | 일부 AWS 리소스·같은 호스팅 영역의 다른 레코드(보조 확인) | 임의의 DNS 이름(보조 확인) |
| 쿼리 요금 | AWS 리소스 대상이면 무료(보조 확인) | 과금(보조 확인) |
| TTL | AWS 리소스 대상이면 설정 불가, 리소스 기본 TTL 사용(보조 확인) | 설정 |
| 헬스 체크 | AWS 리소스는 헬스 체크 대신 Evaluate Target Health = Yes [F11] | 별칭을 만들 수 없는 리소스는 레코드에 헬스 체크를 연결(보조 확인) |

- **구성 순서(장애 조치 예).** ① 별칭을 만들 수 없는 대상(온프레미스 서버 등)에는 엔드포인트 헬스 체크를 만들어 레코드에 연결, ② 별칭 가능한 AWS 리소스(ALB 등)는 헬스 체크를 만들지 말고 별칭 레코드에서 Evaluate Target Health를 Yes로 [F11], ③ 정책은 Failover로 Primary/Secondary 지정 [F10].
- **헬스 체크 3+1종.** 엔드포인트 점검, 다른 헬스 체크를 묶는 계산형, CloudWatch 경보 기반, 그리고 ARC 라우팅 컨트롤(보조 확인). 경보 기반은 '경보가 ALARM이 되길 기다리는' 방식이 아니라 같은 데이터 스트림과 경보 조건으로 판정한다 [F17]. 그래서 SetAlarmState로 상태를 강제로 바꿀 수 없다(보조 확인).
- **TTL과 장애 조치 속도.** 레코드를 헬스 체크와 연결할 때는 TTL을 60초 이하로 두라고 권장한다(보조 확인). TTL이 길면 리졸버가 캐시한 옛 값이 그만큼 오래 남기 때문이다.

**쿼리 로깅 — 두 종류를 혼동하지 말 것**
| 구분 | 무엇이 기록되나 | 어디로 | 제약 |
|---|---|---|---|
| 퍼블릭 DNS 쿼리 로깅 | 퍼블릭 호스팅 영역이 받은 질의(리졸버 캐시에서 응답된 질의는 안 남음) | CloudWatch Logs 로그 그룹 | 로그 그룹은 us-east-1 [F19] |
| Resolver 쿼리 로깅 | VPC에서 시작한 질의, 인바운드·아웃바운드 엔드포인트 질의, DNS Firewall이 처리한 질의 [F20] | CloudWatch Logs·S3·Firehose 중 선택 [F18] | 로깅 구성은 리전별로 만든다(보조 확인) |

- 호스팅 영역 쿼리 로그는 'Route 53이 받은 질의'만 담으므로 VPC 인스턴스의 질의를 감사하려면 Resolver 쿼리 로깅이 맞다 [F19][F20].
- 호출량이 많은 워크로드는 S3로 보내야 로그 전송이 조절(throttle)되지 않는다고 안내한다(보조 확인).

**보조 확인(§5 한도로 표 미수록)**
- 정상 판정: 엔드포인트 점검은 응답한 헬스 체커가 18%를 넘으면 정상, 간격은 10초 또는 30초, 계산형 헬스 체크는 자식을 최대 255개까지 묶는다 (§7: How Route 53 determines whether a health check is healthy).
- 프라이빗 호스팅 영역에서는 IP 기반을 뺀 나머지 7종을 쓸 수 있다 (§7: Choosing a routing policy / Considerations when working with a private hosted zone).
- 퍼블릭 DNS 쿼리 로깅의 API(CreateQueryLoggingConfig)는 '퍼블릭 호스팅 영역만' 대상이라고 적는다 (§7: Route 53 API Reference).

### 5.2.3 콘텐츠·서비스 배포 구성 — CloudFront·Global Accelerator
**큰 그림.** 둘 다 AWS의 엣지·글로벌 네트워크를 쓰지만 푸는 문제가 다르다. CloudFront는 콘텐츠 사본을 여러 엣지 로케이션에 캐시해 지연을 줄이고 가용성을 높이는 CDN이고, Global Accelerator는 TCP/UDP 패킷을 엣지에서 프록시해 정상인 리전 엔드포인트로 보내는 네트워크 가속 서비스다 [F30]. 'HTTP 콘텐츠 + 캐시'면 CloudFront, '비-HTTP 또는 고정 IP'면 Global Accelerator가 출발점이다.

**CloudFront 구성 항목별 결정 규칙**
| 구성 항목 | 규칙 | 근거 |
|---|---|---|
| S3 오리진을 CloudFront로만 열기 | OAC(OAI는 구형). 버킷 정책으로 CloudFront 서비스 주체를 배포 조건과 함께 허용 | [F21] |
| S3를 정적 웹사이트 엔드포인트로 쓰는 경우 | 커스텀 오리진으로 설정 → OAC·OAI 사용 불가 | [F22] |
| 캐시 기본 수명 | 기본 24시간(헤더·캐시 정책으로 조정) | [F23] |
| 콘텐츠 즉시 갱신 | 자주 바꾸면 버전 파일명(권장), 급할 땐 무효화 | [F24] |
| 무효화 비용 | 경로 단위 과금, 와일드카드 경로는 1개로 계산 | [F25] |
| 접근 제어(비공개 콘텐츠) | 개별 파일·쿠키 미지원 클라이언트 → 서명 URL / 여러 제한 파일·URL 유지 → 서명 쿠키 | [F26] |
| HTTPS 사용자 지정 도메인 | ACM 인증서를 us-east-1에서 요청·가져오기 | [F27] |
| 오리진 가용성 | 오리진 그룹(primary/secondary). GET·HEAD·OPTIONS 요청에만 넘어감 | [F28] |

- **캐시 갱신: 무효화 vs 버전 파일명.** 무효화는 엣지 캐시에서 객체를 지워 다음 요청이 오리진에서 최신본을 받게 하는 방법이고, 버전 파일명은 새 이름이 곧 새 객체라 캐시를 건드릴 필요가 없는 방법이다. 공식 권장은 자주 갱신할 때 버전 파일명이다 [F24]. 무효화 요금은 경로 수 기준이라 `/*` 한 번이 파일 수천 개를 지워도 경로 1개다 [F25]. 그래서 '전체 무효화는 파일 수만큼 비싸다'는 통념은 맞지 않다. 보조 확인: 월 1,000경로까지는 무료이고 초과분만 경로 단위로 과금되며, 공식 문서가 버전 파일명을 권하는 이유는 사용자 로컬·프록시 캐시에 옛 버전이 남는 문제, 접근 로그 분석, 버전별 제공·롤백의 용이함, 무효화 요금이 없다는 점이다(§7: Invalidate files to remove content / Pay for file invalidation).
- **기본 TTL 주의.** 24시간 [F23]은 캐시 정책 없이 쓸 때 공식 문서가 말하는 기본값이다(Expiration 페이지). 정책을 쓰면 정책의 Minimum/Default/Maximum TTL과 오리진의 Cache-Control 헤더가 함께 작용한다(보조 확인, 99 조각 참조).
- **서명 URL vs 서명 쿠키.** 파일 하나(설치 파일 다운로드)나 쿠키를 못 쓰는 클라이언트는 URL, 영상 세그먼트 전체·구독자 영역처럼 파일이 많고 URL을 바꾸기 싫으면 쿠키다 [F26]. 둘을 같이 쓰면 서명 URL이 우선한다(보조 확인).
- **오리진 장애 조치.** 오리진 그룹의 secondary로 넘어가는 조건은 상태 코드뿐 아니라 요청 메서드다. POST·PUT 등 다른 메서드는 넘어가지 않는다 [F28]. 쓰기 요청은 이 기능으로 장애 조치되지 않는다고 기억하면 된다.

**Global Accelerator 핵심**
- 가속기 하나가 정적 애니캐스트 IP를 준다. IPv4는 2개, 듀얼 스택은 IPv4 2개 + IPv6 2개다 [F29]. 보조 확인: 이 IP만 클라이언트 방화벽 허용 목록에 한 번 넣어 두면 뒤쪽 리전·엔드포인트를 추가·제거해도 클라이언트를 고치지 않아도 된다(§7: Understanding AWS Global Accelerator use cases).
- 표준 가속기의 엔드포인트는 NLB·ALB·EC2 인스턴스·Elastic IP이고 리스너는 TCP·UDP(둘 다 가능)다(보조 확인).
- 상태 확인을 통과한 엔드포인트로만 보내며, 리전 단위 엔드포인트 그룹의 트래픽 다이얼(기본 100)과 엔드포인트 가중치(기본 128, 최대 255)로 비율을 조정한다(보조 확인).

**CloudFront vs Global Accelerator 선택표**
| 기준 | CloudFront | Global Accelerator |
|---|---|---|
| 대상 트래픽 | HTTP(S) 정적·동적 콘텐츠(보조 확인) | TCP·UDP — 게임(UDP) 같은 비-HTTP, 고정 IP·빠른 리전 장애 조치가 필요한 HTTP [F30] |
| 동작 방식 | 콘텐츠 사본을 엣지에 캐시 | TCP/UDP 패킷을 엣지에서 프록시 [F30] |
| 진입점 | 배포 도메인 이름(*.cloudfront.net 또는 사용자 도메인) | 정적 애니캐스트 IP [F29] |
| 장애 조치 | 오리진 그룹(GET·HEAD·OPTIONS 한정) [F28] | 엔드포인트 상태 기반 리전 간 전환(보조 확인) |
| DDoS 보호 | AWS Shield와 통합(보조 확인) | 같음 |

**보조 확인(§5 한도로 표 미수록)**
- 지역 제한(geo restriction)은 차단된 국가에서 오면 HTTP 403을 돌려주고 배포 전체에 적용된다 (§7: Restrict the geographic distribution of your content).
- 뷰어 프로토콜 정책 'Redirect HTTP to HTTPS'는 HTTP GET·HEAD를 301로 HTTPS로 보낸다 (§7: Require HTTPS for communication between viewers and CloudFront).
- 오리진에서 CloudFront로 가는 데이터 전송은 S3·ELB·API Gateway 같은 AWS 오리진이면 무료이고, 뷰어로 나가는 전송만 과금된다 (§7: What is Amazon CloudFront?).
- Global Accelerator에 정상 엔드포인트가 하나도 없을 때의 동작은 'fail open'(요청을 계속 흘려 보냄)으로 서술되는데, 두 공식 페이지의 문구가 조금 다르다 (§7: How failover works for unhealthy endpoints / Ensure health check access for your accelerator; 99 조각 참조).

## 3. 시험에서 묻는 방식 (가이드 Skill 문구 기반 추정 — 실제 문항 아님)
> AWS가 공개한 Skill의 동사·예시 목록에서 추론한 출제 패턴이다. 실제 기출을 안다는 뜻이 아니다.

1. **하이브리드 DNS 방향 판별형 (Skill 5.2.1).** 패턴: 온프레미스↔VPC 이름 해석이 한쪽만 되는 시나리오에서 엔드포인트·규칙 조합을 고른다. 근거 문구: 'Configure DNS (for example, Route 53 Resolver)'. 판단 기준: 질의가 어디서 시작하는가 — 온프레미스→VPC는 인바운드 [F2], VPC→온프레미스는 아웃바운드 + 규칙 + VPC 연결 [F3][F4], PHZ가 안 풀리면 VPC 속성 [F6], 같은 이름이 겹치면 규칙 우선 [F7].
2. **라우팅 정책 선택·구성형 (Skill 5.2.2).** 패턴: 요구 한 줄(대기 리소스, 비율, 지연, 국가, 헬스 체크된 다중 IP)과 apex·ALB 같은 제약을 주고 정책과 레코드 유형을 고른다. 근거 문구: 'Implement Route 53 routing policies, configurations'. 판단 기준: active-passive는 Failover [F10], ALB는 Evaluate Target Health [F11], apex는 별칭 [F16], 비율은 Weighted [F8], 지연은 Latency [F9], 국가는 Geolocation + default [F12].
3. **쿼리 로깅 구성형 (Skill 5.2.2).** 패턴: 'DNS 질의를 로깅하려는데 안 된다/어디에 쌓이나'를 묻는다. 근거 문구: '... and query logging'. 판단 기준: 퍼블릭 호스팅 영역은 CloudWatch Logs + us-east-1 [F19], VPC·엔드포인트·DNS Firewall 질의는 Resolver 쿼리 로깅과 목적지 3종 [F18][F20].
4. **콘텐츠 전송 구성·선택형 (Skill 5.2.3).** 패턴: S3 오리진 보호, 캐시 갱신, 인증서 리전, 비-HTTP/고정 IP 요구가 섞인 시나리오에서 CloudFront와 Global Accelerator 중 무엇을 어떻게 구성할지 고른다. 근거 문구: 'Configure content and service distribution (for example, CloudFront, AWS Global Accelerator)'. 판단 기준: OAC 권장·웹사이트 엔드포인트는 OAC 불가 [F21][F22], 버전 파일명 권장 [F24], 인증서 us-east-1 [F27], UDP·고정 IP는 Global Accelerator [F29][F30].

## 4. 흔한 함정 · 혼동 짝
| 혼동 짝 | 구분 기준 | 근거 |
|---|---|---|
| 인바운드 ↔ 아웃바운드 엔드포인트 | 질의를 받는 쪽(온프레미스→VPC) vs 내보내는 쪽(VPC→온프레미스). 전달 규칙은 아웃바운드 쪽에 둔다 | [F2][F3][F4] |
| 프라이빗 호스팅 영역 ↔ Resolver 전달 규칙(같은 이름) | 규칙이 PHZ보다 우선한다 | [F7] |
| PHZ가 안 풀림: 영역 문제 ↔ VPC 속성 문제 | enableDnsHostnames·enableDnsSupport 둘 다 true여야 한다 | [F6] |
| 별칭 ↔ CNAME | apex에는 별칭만 가능 | [F16] |
| Failover ↔ 나머지 정책(active-active) | active-passive만 Failover, 나머지는 헬스 체크와 조합해 active-active | [F10] |
| 별칭 대상 헬스 체크 ↔ Evaluate Target Health | AWS 리소스에는 헬스 체크를 만들지 말고 Evaluate Target Health = Yes | [F11] |
| CloudWatch 경보 헬스 체크 ↔ 경보 상태 | 경보 상태가 아니라 데이터 스트림·경보 조건 기준 | [F17] |
| Latency ↔ Geolocation ↔ Geoproximity | 측정된 지연 / 사용자 위치(default 필요) / 리소스 위치 + bias | [F9][F12][F13] |
| IP 기반 ↔ Geolocation | IP 기반은 CIDR 컬렉션 매핑이며 PHZ 불가 | [F14] |
| Multivalue ↔ 로드 밸런서 | 정상 레코드 최대 8개를 DNS로 돌려줄 뿐 | [F15] |
| 가중치 0 ↔ 레코드 삭제 | 0은 라우팅 중단(레코드는 유지) | [F8] |
| 퍼블릭 DNS 쿼리 로깅 ↔ Resolver 쿼리 로깅 | 호스팅 영역이 받은 질의(CloudWatch Logs, us-east-1) / VPC 질의(CloudWatch Logs·S3·Firehose) | [F19][F18] |
| Resolver 쿼리 로그의 DNS Firewall 항목 | 차단·허용·모니터링 처리된 질의도 같은 로그에 남는다 | [F20] |
| OAC ↔ OAI | OAC가 권장, OAI는 구형 | [F21] |
| S3 REST 엔드포인트 ↔ 웹사이트 엔드포인트 | 웹사이트 엔드포인트는 커스텀 오리진 → OAC 불가 | [F22] |
| 무효화 ↔ 버전 파일명 | 자주 바꾸면 버전 파일명. 무효화 요금은 경로 단위 | [F24][F25] |
| 서명 URL ↔ 서명 쿠키 | 파일 하나·쿠키 미지원 / 파일 여러 개·URL 유지 | [F26] |
| CloudFront 인증서 리전 | ACM 인증서는 us-east-1 | [F27] |
| 오리진 장애 조치 한계 | GET·HEAD·OPTIONS만 secondary로 넘어간다 | [F28] |
| CloudFront ↔ Global Accelerator | HTTP 캐시 / TCP·UDP·고정 IP | [F29][F30] |

정답 근거: Global Accelerator는 정적 애니캐스트 IP(IPv4 2개)를 제공하고 [F29], 게임(UDP) 같은 비-HTTP 사용 사례와 고정 IP·빠른 리전 장애 조치가 필요한 사용 사례에 적합하다 [F30] — https://aws.amazon.com/global-accelerator/faqs/
오답 이유: A) CloudFront는 HTTP 콘텐츠 전송용이라 UDP 게임 트래픽의 대상이 아니고, 오리진 장애 조치도 GET·HEAD·OPTIONS 요청에 한정된다 [F28][F30]. C) Route 53 응답은 각 리전 리소스의 주소이지 고정된 진입점 IP가 아니며, 고정 IP는 Global Accelerator가 제공한다 [F29]. D) NAT 게이트웨이는 아웃바운드 변환용이라 사용자가 접속하는 진입점이 아니며 리전 간 전환 기능도 없다.
