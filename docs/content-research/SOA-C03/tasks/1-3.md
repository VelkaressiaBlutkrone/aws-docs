### 1.3.1 컴퓨팅 리소스 최적화와 성능 문제 해결 (성능 지표 · 리소스 태그 · AWS 도구)

**무엇을 묻는 Skill인가.** `Optimize compute resources and remediate performance problems` — 지표(`performance metrics`), 태그(`resource tags`), 도구(`AWS tools`) 세 수단으로 컴퓨팅 리소스를 최적화(크기·유형·구성 변경)하고 성능 문제를 해결하는 능력이다. 해석: '지표로 병목을 찾고 → 도구로 알맞은 크기를 판정하고 → 태그로 대상을 좁혀 → 변경한 뒤 다시 측정'하는 반복 루프로 읽는 것이 자연스럽다.

- **① 지표 — 해상도가 먼저다.** EC2 기본 모니터링은 상태 확인 지표만 1분, 나머지는 5분 주기이고, 상세 모니터링을 켜면 1분 주기로 받는다(상세 모니터링은 지표당 요금)(인용 행 없음: EC2 manage-detailed-monitoring). 해석: 짧은 스파이크가 5분 평균에 묻힌 상황이면 첫 조치는 상세 모니터링이다. 메모리 사용률은 인스턴스에 CloudWatch 에이전트가 있어야 Compute Optimizer 가 분석에 쓴다 [F1].
- **② AWS 도구 — Compute Optimizer 가 중심이다.**
  - 동작: 옵트인한 뒤 사양(vCPU·메모리·스토리지)과 CloudWatch 지표를 지난 14일(기본) 분석하고, 향상된 인프라 지표(유료) 추천 설정을 켜면 최대 93일까지 본다. 분석 완료에 최대 24시간이 걸리고, 사용률은 5분 구간의 최대 사용률 지점을 기준으로 삼는다(인용 행 없음: Compute Optimizer metrics 페이지). 룩백 옵션은 14일(기본)·32일·93일(유료)이다(인용 행 없음: EC2 lookback 도움말 페이지).
  - 지원 대상: EC2 인스턴스, Auto Scaling 그룹, EBS 볼륨, Lambda 함수(메모리 크기 권장), ECS on Fargate, 상용 소프트웨어 라이선스(SQL Server on EC2), Aurora·RDS(인스턴스·스토리지). NAT Gateway·DynamoDB·ElastiCache 등에는 유휴 리소스 권장이 나온다(인용 행 없음: Compute Optimizer supported resources).
  - 판정은 세 가지다 [F2]: 아래 표.
  - 다른 도구: Trusted Advisor 에는 애플리케이션의 속도와 응답성을 높이는 권장을 모은 Performance 범주가 있고(인용 행 없음: Trusted Advisor 시작하기), Lambda 는 오픈소스 AWS Lambda Power Tuning 도구로 메모리 설정별 성능을 측정할 수 있다 [F4].
- **③ 태그.** 태그는 리소스를 다양한 방식으로 분류하는 키-값 메타데이터다(인용 행 없음: EC2 태그 페이지). 공식 문서로 확인된 성능 최적화 연계는 Compute Optimizer 권장 사항을 `tag:Owner=TeamA`(키+값) 또는 `tag-key`(키만, 값 무시)로 필터링하는 기능이다 [F3]. 가이드가 태그의 용도를 더 구체적으로 밝히지 않으므로 출제 범위는 불확실하다(P2-G16).
- **④ Lambda 는 메모리가 곧 CPU 다.** Lambda 는 구성한 메모리에 비례해 CPU 를 할당하므로, CPU·네트워크·메모리 어느 쪽이 병목이든 메모리 설정을 올리면 성능이 크게 좋아질 수 있다 [F4]. 메모리가 병목인지는 CloudWatch 에서 메모리 사용량이 구성값에 가까워지는지 경보로 본다(같은 페이지).

| Under-provisioned | 사양(CPU·메모리·네트워크 등) 중 하나라도 워크로드의 성능 요구를 못 맞춘다 → 성능 저하 위험 | 부족한 사양을 키운 유형으로 변경 | [F2] |
| Over-provisioned | 부족한 사양은 없고, 하나 이상을 줄여도 요구를 맞춘다 → 불필요한 비용 | 더 작은 유형으로 변경 | [F2] |

### 1.3.2 EBS 성능 지표 분석 · 문제 해결 · 볼륨 유형 최적화

**무엇을 묻는 Skill인가.** `Analyze ... metrics, troubleshoot issues, and optimize volume types to improve performance and reduce cost` — 지표를 읽어 병목이 '볼륨 한도 · 인스턴스 한도 · 크레딧 · 초기화' 중 어디인지 가르고, 볼륨 유형을 바꿔 성능은 올리고 비용은 내리는 능력이다. 해석: '성능 개선 및 비용 절감'이 함께 나오므로 정답 후보는 대개 gp2→gp3 전환이거나, 워크로드 성격(IOPS형 vs 처리량형)에 맞는 유형 선택이다.

| 유형 | 성능 모델 | 핵심 수치 | 어울리는 용도 | 근거 |
|---|---|---|---|---|
| gp3 (범용 SSD) | 성능을 용량과 독립적으로 프로비저닝, 버스트 없음 | 기준선 3,000 IOPS·125 MiB/s(가격 포함), 최대 80,000 IOPS(500 IOPS/GiB, 160 GiB 이상에서 최대)·2,000 MiB/s(8,000 IOPS 이상·16 GiB 이상에서 최대), 1 GiB~64 TiB, gp2 보다 GiB 당 20% 저렴 | 대부분의 워크로드. 기본 선택지 | [F5][F6] |
| gp2 (범용 SSD) | 성능이 용량에 비례 | 3 IOPS/GiB(최소 100, 최대 16,000 — 5,334 GiB 에서 도달). 1 TiB 미만이면서 3,000 IOPS 미만 기준선인 볼륨은 3,000 IOPS 까지 버스트(크레딧 한도 540만) | 기존 볼륨. gp3 로 전환 대상 | [F7] |
| io2 Block Express | 프로비저닝 IOPS, 지속 성능 | Nitro 인스턴스에서 최대 256,000 IOPS(IOPS:GiB 1,000:1), 처리량 최대 4,000 MiB/s, 평균 지연 500 마이크로초 미만(16 KiB), 최대 64 TiB. 2025-04-30 부터 모든 io2 가 Block Express (인용 행 없음: provisioned-iops 페이지) | gp3 한도(80,000 IOPS·2,000 MiB/s) 초과 또는 일관된 서브밀리초 지연 | [F6] |
| st1 (처리량 최적화 HDD) | 처리량 중심, 버스트 버킷 | 빅데이터·데이터 웨어하우스·로그 처리용. 최대 500 MiB/s. 부트 볼륨 불가 (인용 행 없음: ebs-volume-types 페이지) | 큰 순차 I/O | [F8] |
| sc1 (콜드 HDD) | 처리량 중심, 버스트 버킷 | 드물게 접근하는 데이터, 가장 낮은 비용. 최대 250 MiB/s. 부트 볼륨 불가 (인용 행 없음: ebs-volume-types 페이지) | 아카이브성 순차 I/O | [F8] |

**지표로 병목 가르기**

| 신호 | 의미 | 방향(해석) | 근거 |
|---|---|---|---|
| BurstBalance 감소 | gp2 는 I/O 크레딧, st1·sc1 은 처리량 크레딧의 잔량(%). 지표는 이 세 유형에만 있다 | 크레딧 소진 → gp3 로 전환하거나 용량·유형 조정 | [F8] |
| VolumeQueueLength 증가 | 완료를 기다리는 읽기·쓰기 요청 수 | 볼륨 IOPS/처리량 부족 신호 → 증설 또는 유형 변경 | [F8] |
| VolumeIOPSExceededCheck / VolumeThroughputExceededCheck = 1 | 애플리케이션이 볼륨의 프로비저닝 성능을 넘겨 요청하려 했다(Nitro 인스턴스에 연결된 대부분의 유형) | 볼륨의 IOPS·처리량 상향 | [F8] |
| InstanceEBSIOPSExceededCheck = 1 | 인스턴스의 EBS IOPS 한도를 넘겨 요청하려 했다 | 볼륨이 아니라 인스턴스 유형 상향 | [F8][F30] |
| 스냅샷에서 만든 볼륨의 첫 접근 지연 | 각 블록을 처음 읽을 때 지연이 크게 늘어난다 | 초기화(전 블록 읽기) 또는 Fast Snapshot Restore | [F9] |

- **지표는 연결된 볼륨에서만 나온다.** 모든 EBS 볼륨 유형은 1분 지표를 CloudWatch 로 보내지만 인스턴스에 연결돼 있을 때만이다 [F8].
- **Fast Snapshot Restore.** 스냅샷에 켜 두면 그 스냅샷으로 만든 볼륨이 생성 즉시 초기화돼 프로비저닝 성능을 낸다 [F9]. 켜지 않았다면 프로덕션 투입 전 모든 블록을 읽어 초기화(구 pre-warming)한다 [F9].
- **Elastic Volumes — 사용 중 변경.** 볼륨 크기·유형·IOPS·처리량을 인스턴스를 분리하거나 재시작하지 않고 바꿀 수 있다. gp2→gp3 마이그레이션의 표준 경로다 [F5](같은 페이지). 변경은 롤링 24시간 안에 최대 4번이며 이전 변경이 completed 상태여야 다음을 시작할 수 있고, 변경 자체는 무료이며 변경 시작 후 새 구성 요금이 붙는다(인용 행 없음: ebs-modify-volume 페이지). gp2→gp3 로 바꾸면서 IOPS·처리량을 지정하지 않으면 원래 gp2 성능과 gp3 기준선 중 높은 쪽으로 자동 프로비저닝된다(같은 페이지). 루트 볼륨(io1·io2·gp2·gp3·standard)은 st1·sc1 로 바꿀 수 없다(같은 페이지).
- **HDD 최적화.** st1·sc1 은 1 MiB 순차 I/O 에서 큐 길이를 4 이상 유지해야 일관된 성능이 나고, 스냅샷을 만드는 동안 성능이 기준선까지 떨어질 수 있다(인용 행 없음: ebs-performance 페이지 — F9 와 같은 페이지).
- **결정 규칙(해석).** ① 소규모 트랜잭션·DB 인데 gp2 크레딧이 문제 → gp3. ② 80,000 IOPS·2,000 MiB/s 초과 또는 서브밀리초 지연 → io2 Block Express. ③ 대용량 순차 스트리밍·로그 → st1, 가장 싼 콜드 데이터 → sc1. ④ 볼륨 지표는 정상인데 느림 → 인스턴스 EBS 대역폭 한도를 의심 [F30].

### 1.3.3 S3 성능 전략 (DataSync · Transfer Acceleration · 멀티파트 업로드 · 수명 주기)

**무엇을 묻는 Skill인가.** `Implement and optimize S3 performance strategies ... to enhance data transfer, storage efficiency, and access patterns` — 전송(data transfer), 저장 효율(storage efficiency), 접근 패턴(access patterns) 세 목적에 예시 네 가지(DataSync · Transfer Acceleration · 멀티파트 · 수명 주기)가 대응한다. 해석: 각 수단이 '무슨 병목에 듣는가'를 짝짓는 문제가 중심이다.

| 목적 | 수단 | 핵심 사실 | 근거 |
|---|---|---|---|
| 접근 패턴 | 접두사(prefix) 병렬화 | 파티션된 접두사당 PUT/COPY/POST/DELETE 최소 3,500, GET/HEAD 최소 5,500 요청/초. 접두사 수는 제한이 없어 10개 접두사면 읽기 55,000 요청/초까지 확장할 수 있다. 확장은 점진적이라 그동안 503 Slow Down 이 날 수 있다 | [F10] |
| 접근 패턴 | 바이트 범위·파트 병렬 다운로드 | 큰 객체는 특정 바이트 범위 또는 멀티파트 객체의 파트를 동시에 내려받으면 단일 전체 요청보다 총 처리량이 높다. 업로드 때 쓴 파트 크기·경계에 맞추면 좋다 | [F13] |
| 전송(업로드) | 멀티파트 업로드 | 객체가 100 MB 에 이르면 고려. 파트 1~10,000개, 파트 크기 5 MiB~5 GiB(마지막 파트는 최소 없음). 단일 PUT 은 최대 5 GB 이므로 그보다 크면 멀티파트가 필수이고, 최대 객체 크기는 50 TB 다(인용 행 없음: upload-objects 페이지 · 50 TB 수치는 P2-G11) | [F11] |
| 저장 효율(비용) | 미완료 멀티파트 정리 | 완료·중지하지 않은 업로드의 파트는 계속 저장 요금이 붙는다. 수명 주기 AbortIncompleteMultipartUpload 규칙(예: 시작 후 7일)으로 자동 정리 | [F14] |
| 전송(원거리) | Transfer Acceleration | CloudFront 엣지 로케이션으로 데이터를 받아 최적화된 경로로 S3 에 전달하는 버킷 수준 기능. 가상 호스팅 방식 요청만 지원, 버킷 이름은 DNS 규격이고 마침표 금지, 추가 요금 가능. 멀리 있을수록 개선 폭이 크고 업로드 성능을 개선할 가능성이 있는 전송에 대해서만 과금한다. 속도 비교 도구로 사전 측정 | [F12][F13] |
| 전송(대량 이동) | AWS DataSync | 온프레미스(NFS·SMB·HDFS·객체 스토리지)·타 클라우드와 S3·EFS·FSx 사이의 온라인 대량 이동 서비스(인용 행 없음: DataSync what-is 페이지). 태스크 모드 중 Enhanced 는 파일·객체를 사실상 무제한 처리하고 나열·준비·전송·검증을 병렬 수행, Basic 은 이를 순차 수행해 느리다. 전송 중 항상 무결성 검사를 수행한다(인용 행 없음: how-datasync-transfer-works 페이지) | [F15] |
| 저장 효율(비용) | S3 수명 주기 전환·만료 | 스토리지 클래스 전환은 폭포식(waterfall) 모델이다(해석: 위에서 아래 단계로만). 기본값으로 128 KB 미만 객체는 전환되지 않고, 최소 저장 기간 전에 옮기면 남은 기간 요금이 붙으며, 전환·만료는 비동기로 처리된다(인용 행 없음: lifecycle-transition-general-considerations · troubleshoot-lifecycle 페이지) | [F14] (Abort 규칙 부분만) |

- **병목 짝짓기(해석).** 요청이 몰려 503 → 접두사 병렬화 [F10]. 클라이언트가 멀어 느림 → Transfer Acceleration [F12]. 큰 파일 업로드 실패·재시도 비용 → 멀티파트 [F11]. 큰 객체 다운로드 처리량 → 범위/파트 병렬 [F13]. 파일 서버·스토리지 사이 대량 이전 → DataSync [F15]. 쌓이는 비용 → 수명 주기·미완료 정리 [F14].
- **Transfer Acceleration 반영 시간.** 활성화 직후 속도가 바로 오르지 않을 수 있고, 사용자 가이드는 최대 20분, API 레퍼런스는 최대 30분으로 다르게 쓴다(P2-G14).
- **캐시와의 구분.** 한 연결에서 더 높은 전송률이나 한 자릿수 밀리초 지연이 필요하면 CloudFront·ElastiCache 로 캐싱한다 — Transfer Acceleration 은 거리 문제용이다 [F13](같은 페이지).

### 1.3.4 공유 스토리지 평가·선택과 최적화 (Amazon EFS · Amazon FSx · Amazon S3 Files) — v1.1 변경

**무엇을 묻는 Skill인가.** `Evaluate and select shared storage solutions ... and optimize the solutions ... for specific use cases and requirements` — 요구에 맞는 공유 스토리지를 '고르고(evaluate and select)' 그 서비스 안의 설정(예: EFS 수명 주기 정책)을 '조정하는(optimize)' 능력이다. v1.1 에서 예시에 Amazon S3 Files 가 새로 들어왔다. S3 Files 가 In-scope 목록에 별도 항목으로 없다는 점은 P2-G06, FSx 중 OpenZFS 는 Out-of-scope 목록에 있다는 점은 P2-G15.

**선택 기준 — AWS 가 직접 비교한 문장 (S3 FAQ)**

| 요구 | 선택 | 핵심 문장(요지) | 근거 |
|---|---|---|---|
| 데이터가 이미 S3 에 있고 파일 기반 애플리케이션·AI 에이전트·팀이 표준 파일 작업으로 바로 써야 함. 데이터를 복제하거나 별도 스토리지를 관리하고 싶지 않음 | Amazon S3 Files | S3 가 원본(authoritative)으로 남고 그 위에 파일 시스템 접근을 얹는다 | [F16] |
| 데이터가 파일 시스템에서 생기고 주로 파일 시스템으로 접근. 공유 홈 디렉터리·콘텐츠 관리·애플리케이션 구성·개발 환경 | Amazon EFS | 완전관리형 클라우드 네이티브 공유 파일 시스템을 기본(primary) 스토리지로 | [F17] |
| 네트워크 연결 파일 스토리지에서 돌던 기존 파일 기반 애플리케이션을 그대로 옮김 | Amazon FSx | NetApp ONTAP·Windows File Server·OpenZFS·Lustre 의 완전관리형 배포 | [F18] |

**Amazon S3 Files (v1.1 신규)**
- 정의: S3 버킷(또는 버킷 안의 접두사)에 연결하는 공유 파일 시스템이다. Amazon EFS 를 기반으로 만들어졌고, EC2·Lambda·EKS·ECS 에서 마운트하며 NFS 4.2/4.1 을 지원하고 읽기 후 쓰기 일관성·파일 잠금·POSIX 권한을 제공한다(인용 행 없음: s3-files 페이지 · P2-G06).
- 동작: 처음 디렉터리를 열면 메타데이터를 가져오고, 기본 128 KiB 미만 파일 데이터를 고성능 스토리지로 비동기 가져온다. 큰 읽기(1 MiB 이상)와 고성능 스토리지에 없는 데이터는 S3 에서 바로 스트리밍한다. 일정 기간(1~365일, 기본 30일) 읽지 않은 파일 데이터는 파일 시스템에서 만료되고 원본은 S3 에 남는다(인용 행 없음: s3-files 페이지).
- 동기화 규칙: 연결된 버킷에 S3 Versioning 이 켜져 있어야 한다 [F19]. 파일 시스템에서 수정하면 60초 동안 쓰기가 없을 때 새 객체 버전으로 S3 에 내보내지고, S3 쪽 변경은 S3 이벤트 알림으로 파일 시스템에 반영된다. 같은 파일을 양쪽에서 바꾸는 충돌이 나면 S3 버킷이 기준이 되고 파일 시스템의 변경본은 lost+found 디렉터리로 옮겨진다 [F19](같은 페이지). 디렉터리 이름 변경·이동은 객체마다 복사·삭제를 하므로 객체가 수천만 개인 디렉터리에서는 비용·시간이 크다 [F19](같은 페이지).
- 범위·성능 수치: 일반 목적 버킷의 모든 스토리지 클래스를 지원하고 S3 Tables·S3 Vectors·디렉터리 버킷은 지원하지 않는다. FAQ 의 성능 수치(파일 시스템당 쓰기 최대 5 GiB/s, 읽기 IOPS 최대 250K 등)는 변경될 수 있다 [F16](같은 페이지).

**Amazon EFS 최적화**
- **성능 모드.** General Purpose 가 기본이자 권장(가장 낮은 연산 지연)이다. Max I/O 는 이전 세대 유형으로 지연이 크고 One Zone 이나 Elastic 처리량 파일 시스템에서는 지원되지 않는다. One Zone 은 항상 General Purpose [F20](같은 페이지).
- **처리량 모드 선택 [F20]:**

| 모드 | 언제 | 비고 |
|---|---|---|
| Elastic (기본·권장) | 스파이크가 크거나 예측하기 어려운 워크로드, 평균 대 피크 비율 5% 이하 | 처리량이 자동으로 늘고 준다. 읽고 쓴 데이터·메타데이터 양만큼 과금하고 버스트 크레딧을 쓰지 않는다 |
| Provisioned | 요구 성능을 알고 있거나 평균 대 피크 비율 5% 이상 | 파일 시스템 크기·크레딧과 무관하게 처리량을 지정한다. 활성화한 처리량(기본 포함분 초과)에 과금 |
| Bursting | 저장 용량에 비례하는 처리량이면 충분할 때 | 기준 처리량은 Standard 용량에 비례(50 KiBps/GiB). 크레딧이 있으면 100 MiBps/TiB(최소 100 MiBps), 없으면 50 MiBps/TiB(최소 1 MiBps). 허용 처리량의 80% 초과 사용이나 크레딧 소진이면 Elastic 또는 Provisioned 로 옮기라고 안내 |

- **수명 주기 정책 [F21].** 정책 셋(Transition into IA / Archive / Standard)을 파일 시스템 전체에 적용한다. 콘솔 권장 설정의 기본값은 IA 30일, Archive 90일, Standard 복귀 None 이다 [F21]. 전환 기준은 Standard 클래스에서 마지막으로 접근한 시점이고 접근하면 타이머가 초기화된다. 메타데이터(이름·소유자·디렉터리 구조)는 항상 Standard 에 있어 디렉터리 목록 조회는 접근으로 치지 않는다. 지연에 민감한 워크로드(작은 파일이 많은 경우)는 Standard 복귀를 On first access 로 설정한다(인용 행 없음: EFS lifecycle-management-efs 페이지).

**Amazon FSx (유형별 선택 — 인용 행 없음: FSx 유형별 what-is 페이지)**
- FSx for Windows File Server: 완전 네이티브 Windows 파일 시스템 위의 관리형 Windows 파일 서버. SMB 와 Windows 기능이 필요할 때.
- FSx for Lustre: 머신러닝·HPC·영상 처리 같은 속도가 중요한 워크로드. 서브밀리초 지연, 최대 수 TBps 처리량, POSIX 호환, S3 데이터 리포지토리 연결.
- FSx for NetApp ONTAP: NFS·SMB·iSCSI·NVMe 다중 프로토콜 접근.
- FSx for OpenZFS: Out-of-scope 서비스 목록에 있다(P2-G15).

### 1.3.5 RDS 지표 모니터링과 구성 수정 (성능 개선 도우미/Database Insights · CloudWatch 경보 · RDS Proxy)

**명칭 시차 — 반드시 먼저 알 것.** Skill 문구(v1.0·v1.1 동일)는 Amazon RDS Performance Insights 와 Performance Insights proactive recommendations 를 쓰지만, 현행 문서는 Performance Insights 의 종료일이 2026-07-31 이고 사용자를 CloudWatch Database Insights 로 이전했다고 쓴다 [F22]. 사전 권장 사항(proactive recommendations)도 RDS 문서에서 이제 'Database Insights proactive recommendations' 절이다. 가이드(2026-06-01 발행)는 종료일 이전이라 문구가 갱신되지 않았다(P2-G01). 사전 권장 사항의 조건은 P2-G02, API 존속 여부는 P2-G03.

| 기능 | Standard | Advanced |

### 1.3.6 EC2 인스턴스와 관련 스토리지·네트워킹 구현·모니터링·최적화 (배치 그룹)

**무엇을 묻는 Skill인가.** `Implement, monitor, and optimize EC2 instances and their associated storage and networking capabilities` — 인스턴스를 만들고(implement), 지표로 보고(monitor), 인스턴스 자체와 곁에 붙은 스토리지(EBS · 인스턴스 스토어)와 네트워킹(향상된 네트워킹 · 배치 그룹)을 조정(optimize)하는 능력이다. 예시는 배치 그룹 하나뿐이다.

| 전략 | 목적 | 규칙·한도 | 근거 |
|---|---|---|---|
| Cluster | 낮은 네트워크 지연·높은 처리량이 필요한 워크로드(HPC 등). 같은 고대역폭 네트워크 구간에 배치 | 단일 AZ(여러 AZ 불가). 향상된 네트워킹 인스턴스의 단일 흐름 최대 10 Gbps(그룹 밖은 5 Gbps). 한 번의 시작 요청·같은 인스턴스 유형 권장(용량 부족 오류 방지). 용량 부족 오류 시 그룹의 모든 인스턴스를 중지·시작 | [F27] |
| Partition | 대규모 분산·복제 워크로드(HDFS·HBase·Cassandra). 파티션마다 별도 랙 집합(전용 네트워크·전원)이라 장애 영향 범위를 파티션으로 한정 | 한 AZ 당 최대 7개 파티션(여러 AZ 가능). 인스턴스 수는 계정 한도까지. 파티션 정보를 애플리케이션이 볼 수 있다 | [F29] |
| Spread | 소수의 핵심 인스턴스를 서로 다른 하드웨어에 분리 | 랙 수준은 한 AZ 당 실행 인스턴스 최대 7개(여러 AZ 가능, 예: 3개 AZ 면 최대 21개). 인스턴스 유형을 섞어도 된다 | [F28] |
| Precision time | 마이크로초 단위 시계 동기화(분산 DB 트랜잭션 순서 등) | 지원 하드웨어에 한정, 추가 요금 없음 (인용 행 없음: placement-strategies 페이지 — F27 과 같은 페이지) | [F27] |

- **공통 규칙.** 인스턴스는 한 번에 하나의 배치 그룹에만 속하고 배치 그룹을 합칠 수 없다. 배치 그룹은 선택 사항이며 사용하지 않으면 EC2 가 상관 장애를 줄이도록 하드웨어에 분산한다. 생성 요금은 없다(인용 행 없음: placement-groups 페이지).
- **스토리지 — EBS 와 인스턴스 스토어.** 인스턴스의 EBS 성능은 인스턴스 유형의 성능 한도에 묶인다 [F30]. EBS 최적화 인스턴스는 EBS 트래픽을 일반 네트워크 트래픽과 분리한다 [F9](같은 페이지 ebs-performance). 인스턴스 스토어는 재부팅에는 데이터가 남지만 중지·최대 절전·종료 때 사라지므로 장기 보관용이 아니다(인용 행 없음: instance-store-lifetime 페이지).
- **네트워킹.** 향상된 네트워킹(ENA)은 SR-IOV 로 더 높은 대역폭·PPS·낮은 지연을 주며 추가 요금이 없다. ENA 는 지원 인스턴스에서 최대 100 Gbps 다(인용 행 없음: enhanced-networking 페이지). 클러스터 배치 그룹 효과를 보려면 향상된 네트워킹을 지원하는 인스턴스 유형을 고른다 [F27](같은 페이지). EFA 는 OS 우회 기능을 제공해 HPC·ML 의 노드 간 통신에 쓴다(인용 행 없음: efa 페이지).
- **모니터링.** 상세 모니터링 1분 주기 지표는 1.3.1 참조. 버스터블(T) 인스턴스의 기본 모드 변화는 P2-G17.

## 3. 시험에서 묻는 방식 (가이드 Skill 문구 기반 추정 — 실제 문항 아님)
아래는 AWS 가 공개한 Skill 문구(동사·예시 서비스)에서 추론한 출제 패턴이다. 실제 기출을 안다는 주장이 아니다.

1. **지표 신호로 병목 위치 가르기 (Skill 1.3.1 · 1.3.2 · 1.3.5 `Analyze ... metrics`, `Monitor ... metrics`).**
   - 패턴: 시나리오가 BurstBalance 0, VolumeQueueLength 증가, DatabaseConnections 한계, Compute Optimizer 판정 같은 신호를 주고 원인과 처방을 고르게 한다.
   - 근거 문구: performance metrics, troubleshoot issues, Monitor Amazon RDS metrics.
   - 판단 기준: 어느 한도에 걸렸는가 — 크레딧 [F8], 볼륨 [F8], 인스턴스 [F30], DB 연결 [F25], 사양 부족/과잉 [F2].
2. **요구에 맞는 서비스·기능 고르기 (Skill 1.3.3 · 1.3.4 `Evaluate and select`, `Implement and optimize`).**
   - 패턴: 거리·대량 이동·큰 객체·파일 접근 요구를 주고 Transfer Acceleration · 멀티파트 · DataSync · S3 Files · EFS · FSx 중 고르게 한다.
   - 판단 기준: 데이터의 원천이 S3 인가 파일 시스템인가 [F16][F17][F18], 병목이 거리인가 요청률인가 [F10][F12], 큰 객체인가 [F11].
3. **볼륨 유형·모드·정책 바꾸기 (Skill 1.3.2 · 1.3.4 `optimize volume types`, `optimize the solutions`).**
   - 패턴: 성능은 올리고 비용은 내리라는 요구에서 gp2→gp3, EFS 처리량 모드, EFS 수명 주기 정책(IA/Archive) 중 하나를 고르게 한다.
   - 판단 기준: 용량과 성능을 분리해야 하면 gp3 [F5][F6], 스파이크·예측 불가는 EFS Elastic [F20], 오래 안 쓰면 수명 주기 [F21].
4. **배치 그룹·인스턴스 한도 선택 (Skill 1.3.6 `EC2 placement groups`).**
   - 패턴: 낮은 지연 HPC, 랙 장애 격리 분산 DB, 소수 핵심 인스턴스 분리 중 알맞은 전략을 고르게 한다. 숫자 7 이 spread 와 partition 에 모두 나오는 점이 함정이다.
   - 판단 기준: 지연이면 Cluster [F27], 대규모 복제 분산이면 Partition [F29], 소수 분리면 Spread [F28].
5. **v1.1 신규·시차 항목.** S3 Files 와 Database Insights(구 Performance Insights)가 문항에 어떤 이름·깊이로 나올지는 공식 근거가 없다(P2-G01, P2-G06).

## 4. 흔한 함정 · 혼동 짝
| 혼동 짝 | 구분 기준 | 근거 |
|---|---|---|
| gp2 ↔ gp3 | gp2 는 용량에 비례(3 IOPS/GiB)하고 소용량은 버스트, gp3 는 성능을 용량과 독립적으로 프로비저닝하고 20% 저렴 | [F5][F6][F7] |
| gp3 최대 성능의 옛 값 ↔ 현행 값 | 현행 문서는 80,000 IOPS·2,000 MiB/s. 16,000·1,000 은 Outposts 주석이나 옛 자료의 값 | [F6] P2-G12 |
| 볼륨 한도 ↔ 인스턴스 한도 | VolumeIOPS/ThroughputExceededCheck 는 볼륨, InstanceEBSIOPSExceededCheck 는 인스턴스. 처방이 다름 | [F8][F30] |
| BurstBalance ↔ VolumeQueueLength | 크레딧 잔량(gp2·st1·sc1 한정) ↔ 대기 요청 수(전 유형) | [F8] |
| 크레딧 소진 ↔ 스냅샷 초기화 지연 | 시간이 지나며 떨어짐 ↔ 새 볼륨의 블록 첫 접근 때 느림 | [F8][F9] |
| 요청률 한도 ↔ 거리 ↔ 큰 객체 | 접두사 병렬화 ↔ Transfer Acceleration ↔ 멀티파트·범위 요청 | [F10][F12][F11][F13] |
| 미완료 멀티파트 정리 ↔ 객체 전환·만료 | AbortIncompleteMultipartUpload 규칙은 파트 정리, 전환·만료는 완료된 객체 대상 | [F14] |
| DataSync ↔ Transfer Acceleration | 스토리지 시스템 간 대량 이동·스케줄·검증 ↔ 클라이언트에서 버킷으로의 원거리 업로드 가속 | [F15][F12] |
| S3 Files ↔ EFS ↔ FSx | 원본이 S3 ↔ 원본이 파일 시스템 ↔ 기존 파일 서버·특수 파일 시스템 이전 | [F16][F17][F18] |
| S3 Files 충돌 해결 ↔ 일반 파일 시스템 | 충돌하면 S3 버킷이 기준이고 파일 시스템 변경본은 lost+found 로 이동. 버킷 Versioning 필수 | [F19] |
| EFS 처리량 모드 3종 | Elastic(예측 불가·기본) ↔ Provisioned(요구를 알거나 평균/피크 5% 이상) ↔ Bursting(용량 비례) | [F20] |
| EFS 수명 주기 기본값 ↔ 첫 접근 복귀 | 기본은 IA 30일·Archive 90일·Standard 복귀 None, 지연 민감 시 On first access | [F21] |
| Performance Insights ↔ Database Insights ↔ Enhanced Monitoring ↔ CloudWatch RDS 지표 | 구 명칭(종료일 2026-07-31) ↔ 현행(사용자 이전됨) ↔ OS 에이전트 지표 ↔ 하이퍼바이저 기반 지표 | [F22][F24] |
| RDS Proxy ↔ 읽기 복제본 ↔ 스토리지 자동 조정 | 연결 폭주 ↔ 읽기 부하 ↔ 저장 공간 부족 | [F25][F26] |
| 클러스터 ↔ 파티션 ↔ 스프레드 | 지연·처리량 ↔ 랙 단위 장애 격리(AZ당 7 파티션) ↔ 소수 분리(AZ당 7 인스턴스) | [F27][F29][F28] |
| Under-provisioned ↔ Over-provisioned | 성능 위험 ↔ 비용 낭비. 메모리는 에이전트가 있어야 판정에 반영 | [F1][F2] |

### Q1 (Skill 1.3.2 · intermediate)
문제: 소규모 트랜잭션 데이터베이스가 100 GiB gp2 볼륨을 쓴다. 배치 작업이 시작되면 수십 분 동안은 빠르다가 IOPS 가 급격히 떨어지고, 같은 시점에 그 볼륨의 BurstBalance 가 0% 근처다. 용량을 늘릴 필요는 없고 비용은 줄이면서 성능을 일정하게 유지하려 한다. 인스턴스 중단 없이 적용할 가장 적절한 조치는?
- A) Elastic Volumes 로 볼륨 유형을 gp3 로 바꾸고 필요한 IOPS 를 직접 프로비저닝한다.
- B) 같은 패밀리에서 한 단계 큰 EC2 인스턴스 유형으로 변경한다.
- C) 볼륨 유형을 st1 으로 변경한다.
- D) 볼륨의 원본 스냅샷에 Fast Snapshot Restore 를 켠다.

정답: A
정답 근거: BurstBalance 는 gp2 의 I/O 크레딧이 버스트 버킷에 남은 비율이다 [F8]. gp2 는 3 IOPS/GiB 로 용량에 비례하므로 100 GiB 볼륨의 기준선은 낮고 크레딧을 다 쓰면 기준선으로 떨어진다 [F7]. gp3 는 성능을 용량과 독립적으로 프로비저닝할 수 있고 버스트를 쓰지 않으며 gp2 보다 20% 저렴하다 [F5][F6]. Elastic Volumes 는 인스턴스를 중지하지 않고 유형을 바꾼다 [F5](같은 페이지) — https://docs.aws.amazon.com/ebs/latest/userguide/general-purpose.html
오답 이유: B) 크레딧 소진은 볼륨 성능 모델의 문제이며 인스턴스 한도는 별도 지표로 확인한다 [F30] / C) st1 은 처리량 지향 HDD 이고 BurstBalance 가 st1·sc1 에도 있어(처리량 크레딧) 버스트 모델이 사라지지 않으며 소규모 임의 I/O DB 에 맞지 않는다(후반은 해석) [F8] / D) Fast Snapshot Restore 는 스냅샷에서 만든 볼륨의 첫 접근 지연을 없애는 기능이다 [F9].

### Q2 (Skill 1.3.3 · intermediate)
문제: 전 세계 지사의 사용자가 us-east-1 의 단일 S3 버킷으로 수 GB 영상 파일을 업로드한다. 먼 지역에서 업로드가 느리지만 클라이언트의 인터넷 대역폭은 충분히 남고, 버킷에서 503 Slow Down 오류는 없다. 최소 변경으로 가장 큰 개선을 내는 방법은?
- A) 버킷에 S3 Transfer Acceleration 을 켜고 클라이언트가 가속 엔드포인트를 쓰게 한다.
- B) 버킷에 접두사를 여러 개 만들어 요청 한도를 늘린다.
- C) 완료되지 않은 멀티파트 업로드를 정리하는 수명 주기 규칙을 추가한다.
- D) 각 지사에 DataSync 에이전트를 배치한다.

정답: A
정답 근거: Transfer Acceleration 은 CloudFront 엣지 로케이션으로 데이터를 받아 최적화된 경로로 S3 에 전달하며, 멀리 있을수록 개선 폭이 크다 [F12][F13] — https://docs.aws.amazon.com/AmazonS3/latest/userguide/transfer-acceleration.html
오답 이유: B) 접두사 병렬화는 요청률(503) 문제의 해법인데 증상이 거리에 따른 속도다 [F10] / C) AbortIncompleteMultipartUpload 규칙은 미완료 파트의 저장 비용 정리다 [F14] / D) DataSync 는 온프레미스·타 클라우드 스토리지와 AWS 스토리지 사이의 대량 이동 서비스이며 최종 사용자 업로드 경로 가속이 아니다 [F15](DataSync what-is 페이지, 인용 행 없음).

### Q3 (Skill 1.3.4 · advanced)
문제: ML 팀의 학습 데이터 수백 TB 가 S3 버킷에 객체로 있고, 다른 팀이 S3 API 로 계속 새 객체를 넣는다. 새 학습 도구는 POSIX 파일 경로만 지원한다. 데이터를 다른 파일 시스템으로 복제하지 않고 S3 를 원본으로 유지하면서 EC2 와 EKS 에서 파일처럼 접근하려 한다. 가장 적절한 구성은?
- A) EFS 파일 시스템을 만들고 DataSync 로 버킷 데이터를 주기적으로 복사한다.
- B) 버킷에 S3 Versioning 을 켠 뒤 S3 Files 파일 시스템을 만들어 버킷에 연결하고 컴퓨트에 마운트한다.
- C) FSx for Windows File Server 를 만들어 SMB 로 마운트한다.
- D) S3 Files 파일 시스템을 만들되 버킷 Versioning 은 끄고 동기화는 수동으로 한다.

정답: B
정답 근거: 이미 S3 에 있는 데이터를 복제 없이 파일로 쓰려면 S3 Files 다 [F16]. S3 Files 는 연결 버킷에 S3 Versioning 이 켜져 있어야 하고 S3 버킷이 기준이다 [F19] — https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-files-synchronization.html (EC2·EKS 마운트 지원은 s3-files 페이지, P2-G06)
오답 이유: A) EFS 는 데이터가 파일 시스템에서 생기는 경우의 기본 스토리지이고 복사는 중복과 동기화 부담을 만든다 [F17] / C) FSx 는 기존 네트워크 파일 스토리지 앱을 옮길 때의 선택이며 Windows File Server 는 SMB 기반이다 [F18] / D) S3 Files 는 Versioning 이 필수다 [F19].

### Q4 (Skill 1.3.5 · intermediate)
문제: Lambda 로 구현한 API 가 호출마다 RDS for PostgreSQL 에 새 연결을 연다. 트래픽이 급증하면 DatabaseConnections 가 한계에 닿고 DB CPU 가 치솟아 오류가 난다. 애플리케이션 코드 변경은 최소화하려 한다. 가장 적절한 조치는?
- A) RDS Proxy 를 만들고 Lambda 가 프록시 엔드포인트로 연결하게 한다.
- B) Enhanced Monitoring 을 1초 간격으로 켠다.
- C) 스토리지 자동 조정을 켠다.
- D) 읽기 복제본을 추가하고 모든 연결을 복제본으로 보낸다.

정답: A
정답 근거: RDS Proxy 는 연결을 풀링·공유해 확장성을 높이고 연결 급증을 완화하며 대부분의 애플리케이션에 코드 변경 없이 적용할 수 있다 [F25] — https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/rds-proxy.html
오답 이유: B) Enhanced Monitoring 은 OS 지표를 보는 진단 도구이지 연결 폭주를 해결하지 않는다 [F24] / C) 스토리지 자동 조정은 여유 공간 부족에 대응한다 [F26] / D) 읽기 복제본은 읽기 부하 분산용이며 연결 풀링을 제공하지 않고(해석), RDS Proxy 도 쓰기 가능한 라이터에 연결한다 [F25].

### Q5 (Skill 1.3.6 · intermediate)
문제: 세 개의 AZ 에 걸쳐 Cassandra 노드 60대(AZ 당 20대)를 운영한다. 랙 단위 하드웨어 장애가 복제본 전체에 동시에 영향을 주지 않도록, 애플리케이션이 각 인스턴스가 속한 파티션(랙 집합)을 알 수 있게 배치하려 한다. 알맞은 배치 그룹은?
- A) 클러스터 배치 그룹
- B) 파티션 배치 그룹
- C) 스프레드 배치 그룹
- D) 배치 그룹 없이 시작한다

정답: B
정답 근거: 파티션 배치 그룹은 AZ 당 최대 7개 파티션에 인스턴스를 분산하고 파티션마다 별도 랙 집합을 쓰며, 인스턴스 수는 계정 한도까지 허용하고 파티션 정보를 애플리케이션에 공유할 수 있다 [F29] — https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/placement-strategies.html
오답 이유: A) 클러스터 배치 그룹은 단일 AZ 에서 낮은 지연을 얻는 용도다 [F27] / C) 스프레드는 AZ 당 실행 인스턴스가 최대 7개라 AZ 당 20대를 담을 수 없다 [F28] / D) 배치 그룹이 없으면 파티션 정보를 얻을 수 없다(해석).
