### 3.2.1 AWS 서비스(예: Systems Manager)로 운영 프로세스 자동화
- **한 줄 요약**: Systems Manager 는 "관리형 노드"로 등록된 서버 군에 대해 명령(Run Command), 상태 유지(State Manager), 패치(Patch Manager), 시간 창 작업(Maintenance Windows), 접속(Session Manager), 구성값(Parameter Store), 준수 확인(Compliance)을 SSH 없이 제공한다. 무엇이 즉시·일회성이고 무엇이 지속·반복인지가 판단의 축이다.
- **관리형 노드 전제**: SSM Agent 가 Systems Manager 로 모든 연결을 먼저 시작하므로(아웃바운드) 인스턴스 쪽 인바운드 방화벽 규칙이 필요 없다 [F10]. 인터넷 대신 ssm, ssmmessages, ec2messages 인터페이스 VPC 엔드포인트를 쓰거나 이 세 엔드포인트로 HTTPS(443) 아웃바운드를 열어 둔다 [F10]. 권한은 인스턴스 프로파일(AmazonSSMManagedInstanceCore 계열)로 주거나, Default Host Management Configuration(DHMC)을 켜서 인스턴스 프로파일 없이 EC2 를 관리형 인스턴스로 만들 수 있다(IMDSv2 와 SSM Agent 3.2.582.0 이상 필요) [F11]. 하이브리드 서버는 hybrid activation 으로 등록하며 Systems Manager 가 관리하는 모든 기계를 "관리형 노드"라고 부른다(hybrid-activation-managed-nodes 페이지).
- **Run Command vs State Manager**
  - Run Command: 태그, 리소스 그룹 이름, 관리형 노드 ID 로 대상을 지정해 즉시 실행한다. 동시성 제어(한 번에 처리할 노드 수)와 오류 제어(허용 오류 수, 초과 시 명령 취소)로 대규모 실행을 안전하게 한다 [F8].
  - State Manager: 연결(association) = 유지하려는 상태를 담은 구성 + 일정 + 대상이다. 예: 안티바이러스가 항상 설치·실행 중, 특정 포트 닫힘 [F7]. 생성 즉시 한 번 실행하고 이후 일정대로 반복하므로 부팅·드리프트 뒤에도 상태가 다시 수렴한다(systems-manager-state 페이지, [F7] 와 같은 페이지).
- **패치(Patch Manager)**
  - 현행 권장 방식은 Quick Setup 의 **패치 정책**이다. 하나의 정책으로 조직 전체, 선택한 계정·리전, 또는 단일 계정-리전 쌍의 패치를 정의한다 [F1]. 전통적인 유지 관리 기간 기반 패치는 단일 계정의 단일 리전으로 제한된다 [F2].
  - 전통 방식(패치 베이스라인 + 패치 그룹 + 유지 관리 기간): 패치 그룹은 관리형 노드에 붙인 태그 키 Patch Group 또는 PatchGroup 으로 정의한다 [F3]. 노드는 하나의 패치 그룹에만 속하고, 패치 정책 기반 패치에서는 패치 그룹을 쓰지 않는다 [F4].
  - 실행 문서 AWS-RunPatchBaseline: Scan 은 누락 패치를 보고만 하고, Install 은 승인된 누락 패치를 설치한다(설치 후 재부팅, RebootOption 으로 NoReboot 가능) [F5].
  - AWS 는 패치를 제공 전에 테스트하지 않으며 OS 주 버전 업그레이드는 지원하지 않는다(patch-manager 페이지, [F1] 와 같은 페이지).
- **유지 관리 기간(Maintenance Windows)**: 정해진 일정·최대 기간·대상·작업을 가지며 Run Command, Automation, Lambda, Step Functions(Standard 만) 네 가지 작업 유형을 실행한다 [F6]. 여러 종류의 작업을 순서대로 엮거나 "언제 실행할지"를 통제해야 하면 유지 관리 기간, 규정 준수 상태를 계속 맞추거나 신규 노드에 자동 적용하려면 State Manager 가 맞다(state-manager-vs-maintenance-windows 페이지, [F2] 와 같은 페이지).
- **Session Manager**: 인바운드 포트 개방, 배스천 호스트, SSH 키 관리가 필요 없고 IAM 정책으로 접근을 통제한다 [F9]. 감사·기록은 같은 페이지에 따라 CloudTrail(Session Manager API 호출), S3·CloudWatch Logs(세션 로그, KMS 암호화 선택), EventBridge+SNS(세션 시작·종료 알림)로 구성하며, 포트 포워딩이나 SSH 로 연결한 세션은 로깅할 수 없다 [F9]. "배스천 제거" 단서가 나오면 후보 1순위.
- **Parameter Store**: 표준 파라미터는 값 4 KB, 계정·리전당 최대 10,000개, 추가 비용 없음이며 파라미터 정책을 쓸 수 없다 [F12]. 고급 파라미터는 값 8 KB, 최대 100,000개, 파라미터 정책 지원, 비용 청구이며 표준→고급으로만 바꿀 수 있고 되돌릴 수 없다 [F13]. 고급 파라미터는 계정 간 공유(AWS RAM)도 된다(parameter-store-advanced-parameters 페이지, 3.1.4 의 RAM 공유 목록).
- **Compliance·Inventory**: Compliance 는 패치 준수와 State Manager 연결 준수를 모아 보여 주고 여러 계정·리전에서 집계한다 [F14]. Inventory 설정은 State Manager 연결로 저장되며 메타데이터만 수집한다(inventory-about 페이지).
- **서비스 현황(참고)**: Systems Manager 의 Change Manager·Incident Manager 는 2025-11-07 부터 신규 고객에게 닫혔고 Application Manager 도 신규 고객 대상 종료다(출처는 99 조각 참조). 시험 범위인지는 확인되지 않았다.

### 3.2.2 이벤트 기반 자동화 (Lambda, S3 이벤트 알림, EventBridge, AWS DevOps Agent)
- **한 줄 요약**: "무엇이 이벤트를 만들고(소스) → 누가 라우팅·필터링하고 → 무엇이 실행하는가(대상)"를 소스별 전달 규칙(최소 1회, 재시도, 대상 수)과 함께 외운다.
- **S3 이벤트 알림**: 알림은 최소 1회 전달이라 중복이 있을 수 있고, 보통 수 초 안이지만 1분 이상 걸리기도 한다 [F15]. 대상은 SNS 주제, SQS 큐, Lambda, EventBridge 이며 하나의 알림 설정에는 한 종류의 대상만 지정할 수 있다 [F16]. 대상 쪽에 S3 가 게시·호출할 권한이 있어야 한다(같은 페이지). 접두사·접미사로 객체 키를 필터링할 수 있다(AWS Compute Blog: avoiding recursive invocation, 보조 자료). 같은 버킷에 쓰는 알림은 실행 루프를 만들 수 있으므로 버킷을 나누거나 접두사로 범위를 제한한다(S3 콘솔 도움말).
- **S3 → EventBridge**: EventBridge 대상으로 켜면 이벤트 유형을 선택하지 않고 모든 유형이 전달되고 EventBridge 규칙으로 다른 대상에 보낸다 [F17]. 한 이벤트를 여러 소비자에게 팬아웃해야 할 때의 선택지다.
- **Lambda 의 이벤트 소스 두 갈래**
  - 직접 트리거(예: S3, SNS): 서비스가 이벤트를 Lambda 로 밀어 넣어 비동기로 호출하며 트리거 설정은 이벤트를 만드는 서비스 쪽에 저장된다(invocation-async·invocation-eventsourcemapping 페이지). 기본 재시도는 2회, 큐 보관은 최대 6시간이며 실패 이벤트는 DLQ 또는 on-failure 대상에 보낼 수 있다 [F18].
  - 이벤트 소스 매핑(SQS, Kinesis, DynamoDB, MSK 등): Lambda 가 큐·스트림에서 읽어 배치로 호출하고 각 이벤트를 최소 1회 처리하므로 중복에 대비해 함수를 멱등하게 만든다 [F19].
- **EventBridge 규칙**: 규칙은 이벤트 패턴(일치 시) 또는 일정으로 동작하고, 규칙 하나에 대상을 최대 5개 둘 수 있다 [F20]. 전달 실패 시 기본 24시간·최대 185회 재시도하고 그래도 실패하면 버리므로 DLQ 로 보존한다 [F22]. **예약 규칙은 legacy 기능이며 EventBridge Scheduler 를 권장한다** [F21] — 기존 학습문서의 "스케줄 규칙" 서술은 시험 선택지에 따라 Scheduler 로 읽어야 할 수 있다.
- **EventBridge 신규 변화(시험 범위 미확인)**: EventBridge 는 이제 이벤트를 보존하고 순서·재생을 지원하는 Custom Event Bus 와 규칙·대상 기반 Custom Event Bus - Classic 두 종류를 제공하며 신규 애플리케이션은 Custom Event Bus 로 시작하라고 안내한다 [F23]. 규칙 하나의 대상 5개 같은 서술은 Classic 기준이다 [F20].
- **AWS DevOps Agent (v1.1 신규 예시)**
  - 정체: 릴리스 관리와 프로덕션 운영에 걸친 AI 기반 상시 에이전트이며 경보나 지원 티켓이 들어오는 즉시 자동 조사를 시작한다 [F24]. 프리뷰(2025-12)를 거쳐 2026-03 에 GA 됐다(What's New 글, 99 조각 참조). 릴리스 관리 기능은 문서상 프리뷰 표기다 [F24].
  - 이벤트 기반 연동 두 방향: (1) 들어오는 쪽 — 모니터링·티켓 도구가 웹훅으로 조사를 자동 시작시킨다 [F26]. (2) 나가는 쪽 — 조사·완화 상태가 바뀔 때 EventBridge 기본 이벤트 버스로 source aws.aidevops 이벤트를 보내고, 규칙이 Lambda 호출·SNS 알림·Step Functions 시작 등을 수행한다 [F25].
  - 범위와 통제: Agent Space 가 접근 가능한 계정·연동·권한의 경계이며 독립적으로 동작한다 [F28]. 리소스를 바꾸는 작업은 운영자 승인 없이는 실행되지 않는다 [F27]. 즉 "조사·권고는 자동, 변경은 승인 후"가 기본 설계다.
- **Step Functions**: Standard 워크플로의 상태 변화만 EventBridge 로 이벤트가 나간다(Express 는 CloudWatch Logs 로 모니터링) [F29]. 유지 관리 기간 작업으로도 Standard 만 쓸 수 있다 [F6].

| 요구 | 맞는 조합 | 근거 |
|---|---|---|
| S3 업로드 → 한 개 Lambda 로 처리 | S3 이벤트 알림(Lambda 대상), 비동기 재시도 2회 | [F16][F18] |
| S3 업로드 이벤트를 여러 소비자에게 | S3 → EventBridge → 규칙(대상 최대 5) | [F17][F20] |
| 큐·스트림 레코드 처리 | Lambda 이벤트 소스 매핑(멱등 처리 필수) | [F19] |
| 전달 실패 이벤트 보존 | EventBridge 대상 DLQ / Lambda DLQ·on-failure 대상 | [F22][F18] |
| 매일 새벽 정기 작업 | EventBridge Scheduler(예약 규칙은 legacy) | [F21] |
| 경보 발생 시 자동 원인 조사 | AWS DevOps Agent(웹훅·경보 연동) | [F24][F26] |
| 조사 완료 시 후속 자동화 | EventBridge 규칙(source aws.aidevops) → Lambda/SNS | [F25] |

## 3. 시험에서 묻는 방식 (가이드 Skill 문구 기반 추정 — 실제 문항 아님)
아래는 AWS 가 공개한 Skill 문구와 동사에서 추론한 출제 패턴이며, 실제 기출을 안다고 주장하지 않는다.
1. **SSH·배스천 없이 서버 군을 운영한다** — 근거 문구: "Use AWS services to automate operational processes (for example, Systems Manager)". 판단 기준: 접속=Session Manager, 즉시 대량 명령=Run Command, 상태 유지=State Manager. 노드가 목록에 안 보이면 아웃바운드 경로(엔드포인트)·권한(인스턴스 프로파일 또는 DHMC)·에이전트를 점검한다 [F7][F8][F9][F10][F11].
2. **정기·대규모 패치를 설계한다** — 근거 문구 동일(운영 프로세스 자동화). 판단 기준: 여러 계정·리전이면 패치 정책, 단일 계정·리전의 시간 창이면 유지 관리 기간+패치 그룹, 점검만이면 Scan [F1][F2][F3][F4][F5].
3. **S3 업로드·큐 메시지 등 이벤트로 자동 처리한다** — 근거 문구: "Implement event-driven automation by using AWS services and features (for example, Lambda, S3 Event Notifications, EventBridge, ...)". 판단 기준: 소스가 푸시(직접 트리거, 재시도 2회)인지 폴링(이벤트 소스 매핑, 최소 1회)인지, 대상이 한 종류인지(S3 알림) 팬아웃인지(EventBridge) 구분한다 [F15][F16][F17][F18][F19][F20].
4. **정기 작업·AI 에이전트 연동을 고른다** — 근거 문구: "... EventBridge, AWS DevOps Agent". 판단 기준: 정기 실행은 EventBridge Scheduler(예약 규칙은 legacy), 사고 자동 조사는 AWS DevOps Agent(웹훅·EventBridge 연동, 변경은 승인 필요) [F21][F24][F25][F26][F27].

참고: AWS DevOps Agent 는 v1.1 신규 예시일 뿐 문항 깊이는 알 수 없다. 서비스가 무엇을 하는지(자동 조사·권고), 어떤 이벤트로 시작되고 어떤 이벤트를 내보내는지 수준이 가장 가능성 높은 후보다.

## 4. 흔한 함정 · 혼동 짝
| 혼동 짝 | 구분 기준 | 근거 |
|---|---|---|
| Run Command vs State Manager | 전자는 즉시 실행(동시성·오류 제어), 후자는 일정으로 상태를 반복 적용 | [F7][F8] |
| 패치 그룹(태그) vs 패치 정책(Quick Setup) | 패치 정책이 현행 권장, 패치 정책 기반에서는 패치 그룹을 쓰지 않음 | [F1][F4] |
| 패치 그룹 태그 키 철자 | Patch Group 과 PatchGroup 둘 다 가능, 키는 대소문자 구분 | [F3] |
| 유지 관리 기간 vs 패치 정책 | 유지 관리 기간 패치는 단일 계정·단일 리전으로 제한 | [F2] |
| AWS-RunPatchBaseline Scan vs Install | Scan 은 보고만, Install 은 설치(재부팅 포함) | [F5] |
| 인스턴스 프로파일 vs DHMC | DHMC 는 인스턴스 프로파일 없이 관리형으로 만듦(IMDSv2 필요) | [F11] |
| Session Manager vs 배스천·SSH | 인바운드 포트·키·배스천 불필요, 아웃바운드 연결 | [F9][F10] |
| Parameter Store 표준 vs 고급 | 4 KB·10,000개·정책 불가 vs 8 KB·100,000개·정책 가능·유료 | [F12][F13] |
| 유지 관리 기간 작업 유형 | Run Command, Automation, Lambda, Step Functions(Standard 만) | [F6] |
| S3 알림 직접 대상 vs EventBridge | 직접은 한 알림에 한 종류, EventBridge 는 규칙으로 팬아웃 | [F16][F17] |
| Lambda 직접 트리거 vs 이벤트 소스 매핑 | 직접=비동기 재시도 2회, 매핑=최소 1회 처리(중복 가능) | [F18][F19] |
| EventBridge 예약 규칙 vs Scheduler | 예약 규칙은 legacy, 정기 작업은 Scheduler 권장 | [F21] |
| EventBridge 규칙당 대상 수 | 최대 5개(Classic 기준) | [F20] |
| Classic vs 신규 Custom Event Bus | 규칙·대상 vs 보존·구독자 | [F23] |
| DevOps Agent: 조사·권고 vs 자동 변경 | 변경 작업은 운영자 승인 필수 | [F27] |
| Step Functions Standard vs Express | Standard 만 EventBridge 로 이벤트 전달, 유지 관리 기간 작업은 Standard 만 | [F29][F6] |

- A) 각 계정에서 리전마다 유지 관리 기간을 만들어 패치 작업을 등록한다.
- B) Quick Setup 의 패치 정책으로 조직 전체 계정·리전의 패치를 한 번에 정의한다.
- C) 모든 인스턴스에 Patch Group 태그를 붙이고 한 계정의 유지 관리 기간에서 실행한다.
- D) State Manager 연결로 AWS-RunPatchBaseline 의 Scan 만 실행한다.

정답: B
정답 근거: 패치 정책은 현행 권장 방식이며 하나의 정책으로 조직 전체 계정·리전을 정의한다 [F1]. 유지 관리 기간 패치는 단일 계정·단일 리전으로 제한된다 [F2] — https://docs.aws.amazon.com/systems-manager/latest/userguide/patch-manager.html
오답 이유: A) 계정·리전마다 반복 구성하는 방식으로 부담이 줄지 않는다 [F2] / C) 유지 관리 기간 패치는 단일 계정·리전 범위이고 패치 정책 기반에서는 패치 그룹을 쓰지 않는다 [F2][F4] / D) Scan 은 보고만 하고 설치하지 않는다 [F5].

### Q3 (Skill 3.2.1 · intermediate)
문제: 애플리케이션 구성값 하나가 6 KB 이고, 만료 시점을 자동으로 관리하는 파라미터 정책도 쓰고 싶다. 어떤 Parameter Store 구성이 필요한가?
- A) 표준 파라미터로 저장하고 값을 두 개로 나눈다.
- B) 고급(Advanced) 파라미터로 저장한다.
- C) 표준 파라미터에 파라미터 정책을 붙인다.
- D) 파라미터 정책은 어떤 티어에서도 지원하지 않으므로 Lambda 로 만료를 구현한다.

정답: B
정답 근거: 표준 파라미터는 4 KB 이고 파라미터 정책을 쓸 수 없으며 [F12], 고급 파라미터는 8 KB 이고 파라미터 정책을 지원한다 [F13] — https://docs.aws.amazon.com/systems-manager/latest/APIReference/API_PutParameter.html
오답 이유: A) 요구사항(값 하나 6 KB)을 충족하지 못하고 정책도 불가하다 [F12] / C) 표준 파라미터는 파라미터 정책을 쓸 수 없다 [F12] / D) 고급 파라미터가 정책을 지원한다 [F13].

### Q4 (Skill 3.2.2 · intermediate)
문제: S3 버킷에 객체가 업로드될 때마다 같은 이벤트를 이미지 처리 Lambda, 감사 로깅 SQS 큐, 알림 SNS 주제 세 곳에 동시에 전달해야 한다. 중간에 별도 SNS 팬아웃 토픽을 두지 않고 S3 쪽 설정만으로 해결하려 한다. 가장 적절한 구성은?
- A) 하나의 S3 이벤트 알림 설정에 Lambda, SQS, SNS 를 모두 대상으로 지정한다.
- B) 버킷의 EventBridge 전송을 켜고 EventBridge 규칙 하나에 세 대상을 모두 연결한다.
- C) Lambda 이벤트 소스 매핑으로 S3 버킷을 폴링하도록 설정한다.
- D) S3 이벤트 알림 대상으로 SQS 큐 하나만 지정하고 그 큐가 나머지 두 대상을 호출하게 한다.

정답: B
정답 근거: S3 알림은 한 설정에 한 종류의 대상만 지정할 수 있고 [F16], EventBridge 를 켜면 모든 이벤트 유형이 전달되어 규칙으로 라우팅할 수 있으며 [F17], 규칙 하나에는 대상을 최대 5개 둘 수 있다 [F20] — https://docs.aws.amazon.com/AmazonS3/latest/userguide/notification-how-to-event-types-and-destinations.html
오답 이유: A) 한 알림에는 한 종류의 대상만 지정 가능하다 [F16] / C) 이벤트 소스 매핑은 SQS, Kinesis, DynamoDB 같은 큐·스트림 소스를 읽는 방식이며 S3 버킷은 그 목록에 없다 [F19] / D) SQS 큐는 메시지를 보관할 뿐 다른 대상을 호출해 주는 팬아웃 수단이 아니며, 이 방식은 한 알림 한 대상 종류 제약의 해법이 되지 못한다 [F16].

### Q5 (Skill 3.2.2 · intermediate)
문제: AWS DevOps Agent 가 인시던트 조사를 마치면 결과를 후처리하는 Lambda 함수를 자동으로 호출하려 한다. 어떻게 구성하는가?
- A) EventBridge 규칙에서 source 가 aws.aidevops 이고 조사 완료 이벤트(Investigation Completed)에 일치하는 패턴을 만들고 대상으로 Lambda 를 지정한다.
- B) Lambda 이벤트 소스 매핑으로 DevOps Agent 를 폴링한다.
- C) S3 이벤트 알림에 DevOps Agent 를 대상으로 지정한다.
- D) DevOps Agent 가 운영자 승인 없이 Lambda 를 직접 호출하도록 승인 설정을 끈다.

정답: A
정답 근거: DevOps Agent 는 조사·완화 상태 변화를 EventBridge 기본 이벤트 버스로 보내며 규칙으로 Lambda 호출 등을 구성한다 [F25] — https://docs.aws.amazon.com/devopsagent/latest/userguide/configuring-integrations-and-knowledge-integrating-devops-agent-into-event-driven-applications-using-amazon-eventbridge-index.html
오답 이유: B) 이벤트 소스 매핑은 스트림·큐 소스용이다 [F19] / C) S3 알림의 대상 목록에 DevOps Agent 는 없다 [F16] / D) 승인 요구는 리소스 변경 작업에 대한 통제이며 후처리 호출과 무관하고 끌 수 있다는 근거도 없다 [F27].
