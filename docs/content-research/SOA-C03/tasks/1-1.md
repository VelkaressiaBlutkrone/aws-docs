### 1.1.1 워크로드(서버리스·컴퓨팅·AI)에 대한 모니터링·로깅 구성 — v1.1 변경

**무엇을 묻는 Skill인가.** v1.0은 "AWS 모니터링과 로깅을 구성"이었고 v1.1은 "워크로드(서버리스·컴퓨팅·AI)에 대한 모니터링과 로깅을 구성"이다. 서비스 이름 암기보다 *워크로드 유형마다 지표·로그·감사 기록이 어디에서 나오고, 무엇을 직접 켜야 하는가*를 묻는다.

**이해 포인트 (왜 그렇게 동작하는가)**
- **지표(무슨 일이?)** 는 서비스가 자동 게시한 것을 읽는 모델이다. 지표는 만들어진 리전에만 존재하고 [C25], 해상도가 낮을수록 오래 보관된다 — 1분 미만 3시간, 1분 15일, 5분 63일, 1시간 455일 [F5][C6][C7][C8][C9].
- **로그(왜?)** 는 *비용이 기본값에 숨어 있다.* 로그 그룹의 기본 보존은 만료 없음이므로 보존 기간을 직접 정해야 하고 [F1], 보존·모니터링·접근 제어 설정은 로그 그룹 단위로 공유된다 [C29]. 보존 값은 정해진 목록에서만 고른다 [D1][D2].
- **감사(누가?)** 는 CloudTrail 몫이다. 추적을 만들지 않아도 리전별 최근 90일 관리 이벤트를 Event history에서 볼 수 있지만 [F2], S3 객체 수준·Lambda 호출 같은 데이터 이벤트는 기본으로 기록되지 않는다 [F3].
- **로그 가공의 두 갈래.** 지표 필터(로그→숫자 지표→경보)와 구독 필터(로그 이벤트 자체를 실시간 전달)는 모두 Standard 로그 클래스에서만 지원된다 [F4][B10]. 지표 필터는 생성 이후 이벤트에만 적용된다 [C32]. 로그 그룹당 구독 필터 상한은 공식 출처 간 값이 다르므로(5 vs 2) 문항 숫자로 쓰지 않는다 [C35][P1-G02].

### 1.1.2 CloudWatch 에이전트 구성·관리 (EC2·ECS·EKS)

**왜 에이전트인가.** AWS/EC2 지표는 하이퍼바이저 쪽에서 보이는 값이라 게스트 OS 안의 메모리·디스크 사용률은 포함되지 않는다. 에이전트가 OS 안에서 값을 읽어 게시하므로 [C27] 그 지표는 사용자 지정 지표 취급이고 기본 네임스페이스는 CWAgent다 [F10].

**플랫폼별 구성 요약 (표 초안)**
| 대상 | 설치·구성 방식 | 권한 | 결과 | 근거 |
|---|---|---|---|---|
| EC2·온프레미스 | 마법사로 구성 파일 생성 → Parameter Store 저장(마법사 질문에 Yes) → Run Command로 패키지 설치(AWS-ConfigureAWSPackage) 후 AmazonCloudWatch-ManageAgent(Action=configure, 소스=ssm)로 적용 | 인스턴스 역할에 CloudWatchAgentServerPolicy [F12]. Parameter Store에 저장하는 인스턴스에는 CloudWatchAgentAdminRole, SSM Agent 2.2.93.0 이상 | 지표는 기본 CWAgent 네임스페이스 [F10], 로그는 지정한 로그 그룹 | [F10][F11][F12][B13][C39] |
| EKS | Amazon CloudWatch Observability 애드온(또는 Helm 차트)이 CloudWatch Agent와 Fluent Bit를 클러스터에 설치 | 에이전트가 지표·로그·트레이스를 보낼 IAM 권한을 별도로 부여 | Container Insights와 Application Signals가 기본 활성화 | [F13][B3] |
| ECS (EC2 시작 유형) | 인스턴스 수준 지표는 에이전트 컨테이너를 클러스터에 배포(IMDS 접근 필요) / 클러스터·서비스·태스크 수준은 Container Insights 설정 | 에이전트 태스크·인스턴스에 필요한 IAM 권한 | 인스턴스 수준 지표 + Container Insights 지표·성능 로그 | [F14][B3] |
| ECS (Fargate) | 에이전트 배포 절차 문서는 EC2 시작 유형을 전제로 함 → 시험 범위는 불명 | - | - | [F14][P1-G10] |

**결정 규칙**
- *다수 EC2에 같은 구성을 일괄 적용* → Parameter Store에 구성을 저장하고 Run Command(ManageAgent)로 배포 [F11][C39]. 인스턴스마다 수작업 편집은 비효율.
- *에이전트가 지표를 못 올림* → ① 인스턴스 역할에 CloudWatchAgentServerPolicy [F12] ② 네임스페이스를 기본(CWAgent)으로 찾고 있는지 [F10] ③ SSM으로 배포한다면 SSM Agent 버전 [B13].
- *에이전트 지표 목적지* — 구성 파일의 metrics_destinations로 CloudWatch, Amazon Managed Service for Prometheus, 또는 둘 다 지정(1.1.1의 AMP와 연결되는 고리) [B5].
- *세부 모니터링과의 구분* — 세부 모니터링은 AWS/EC2 지표의 게시 주기를 1분으로 바꿀 뿐 메모리·디스크 지표를 추가하지 않는다 [F6][C27].

### 1.1.3 CloudWatch 경보 구성·식별·문제 해결 (복합 경보와 호출 가능한 작업)

**경보는 상태 기계다.** 지표(또는 수식) → 임계값 비교 → 상태(OK/ALARM/INSUFFICIENT_DATA) → *상태가 바뀔 때* 작업 실행. 문제 해결은 "상태가 왜 그 값인가"와 "상태가 바뀌었는데 작업이 왜 안 돌았나"의 두 갈래다.

**평가 설정 요약 (표 초안)**
| 설정 | 의미 | 근거 |
|---|---|---|
| Period | 10·20·30초(고해상도 경보, 추가 요금) 또는 60의 배수. 개념 페이지는 10·30초로만 서술 | [F21][C3][C4][P1-G03] |
| EvaluationPeriods(N)·DatapointsToAlarm(M) | 최근 N개 데이터 포인트 중 M개가 위반이면 ALARM (M out of N) | [F17][C11] |
| TreatMissingData | breaching / notBreaching / ignore / missing. 기본은 missing | [C13] |
| missing의 동작 | 평가 범위의 모든 데이터가 누락되면 INSUFFICIENT_DATA로 전이 | [F18] |
| 예외 | AWS/DynamoDB 지표 경보는 설정과 무관하게 항상 ignore. EC2 stop·terminate·reboot·recover 경보는 missing 권장 | [C14][C15] |

**경보가 호출할 수 있는 작업 — 지표 경보 vs 복합 경보 (Skill 1.1.3 핵심 비교표)**
| 작업 | 지표 경보 | 복합 경보 | 근거 |
|---|---|---|---|
| SNS 알림 | 가능 | 가능 | [C16][C24] |
| EC2 stop·terminate·reboot·recover | 가능 | **불가** | [C16][F15][F19] |
| Auto Scaling 정책 | 가능 | **불가** | [C16][F15] |
| Lambda 호출 | 가능 | 가능(Add Lambda action) ※ Alarms 개요 페이지에는 빠져 있음 | [C19][F16][P1-G01] |
| Systems Manager OpsItem·인시던트 | 가능 | 가능 | [C17][C24] |
| 조사(investigation) 시작 | 가능 | 가능 | [C16][C24] |

- **EventBridge는 '경보 작업'이 아니라 경보 상태 변경이 자동으로 흘러가는 *이벤트 경로*다.** CloudWatch는 경보가 생성·수정·삭제되거나 상태가 바뀔 때 EventBridge로 이벤트를 보내므로 [F20][C18], 규칙(이벤트 패턴)의 대상으로 Lambda·SSM Automation·SNS 등을 연결하면 경보가 서비스를 *간접 호출*한다(Skill 문구의 "through Amazon EventBridge").
- **복합 경보의 용도는 알림 노이즈 감소**이며 규칙 식은 ALARM/OK/INSUFFICIENT_DATA 함수를 AND·OR·NOT으로 묶어 만든다 [C22][C23]. 복합 경보는 다른 경보의 *상태*만 본다(지표를 직접 감시하지 않음). 그래서 "복합 경보로 묶은 뒤 EC2 작업까지" 같은 선지는 [F15]로 걸러진다.
- **EC2 상태 점검 경보 패턴:** recover는 시스템 상태 점검(StatusCheckFailed_System) 전용이고 인스턴스 상태 점검(StatusCheckFailed_Instance)에는 쓸 수 없다 [F19]. reboot은 인스턴스 상태 점검 실패에 권장되며 [C21], recover된 인스턴스는 인스턴스 ID·프라이빗 IP가 그대로다 [C20].

**문제 해결 체크리스트**
1. *INSUFFICIENT_DATA가 계속된다* → 지표가 게시되지 않는다(기간이 게시 주기보다 짧음 [F6]) 또는 누락 데이터 처리(missing은 전부 누락이면 INSUFFICIENT_DATA) [F18].
2. *ALARM인데 작업이 안 돈다* → 작업은 상태가 바뀔 때만 호출되고(Auto Scaling 작업만 매분 재호출), 작업 비활성화·존재하지 않는 대상은 CloudWatch가 검증하지 않는다 [B18].
3. *SNS로 알림이 안 온다* → 주제 권한·구독 확인·암호화 키 [F27][F28][B11] (→1.1.5).
4. *복합 경보에 EC2 작업이 안 붙는다* → 설계 오류다. 지표 경보에 붙이거나 EventBridge 경로를 쓴다 [F15][F20].

### 1.1.4 사용자 지정·공유 대시보드 (여러 계정·리전)

**핵심 구분.** 대시보드는 계정 단위 *글로벌* 리소스지만 [F22], 지표는 만들어진 리전에 있고 [C25], 경보는 다른 리전의 지표를 볼 수 없다 [F24]. 그래서 "한 화면에서 여러 리전을 본다"와 "한 경보로 여러 리전을 감시한다"는 다른 문제다. 위젯 JSON에는 accountId·region을 위젯 또는 지표 단위로 지정할 수 있다 [B7].

**여러 계정을 묶는 세 가지 방식 (비교표 초안)**
| 방식 | 구성 | 교차 리전 | 데이터 이동 | 근거 |
|---|---|---|---|---|
| CloudWatch cross-account observability (OAM) | 모니터링 계정이 sink, 소스 계정이 link를 만든다. 단일 리전 내 관측성 | 불가(리전별로 구성) | 없음(공유) | [F26][B8] |
| 교차 계정·교차 리전 CloudWatch 콘솔 | 공유(소스) 계정에 CloudWatch-CrossAccountSharingRole을 만들고, 모니터링 계정에서 기능을 활성화 | 가능(경보 제외) | 없음 | [F23][F24][B7] |
| 교차 계정·교차 리전 중앙화 | Organizations 신뢰된 액세스 + 중앙화 규칙으로 로그·지표를 한 곳에 복사 | 가능 | 복사됨 | [B7] |

- 공식 문서는 계정 간 관측성에는 OAM을 권장하고, 교차 리전이 필요하면 콘솔 방식을 쓴다는 구조다 [F26][B7]. 모니터링 계정에서 소스 계정으로 *경보*를 만드는 지원 범위는 페이지 간 서술이 달라 주의한다 [P1-G04].
- **공유(shareable).** 단일 대시보드를 최대 5개 이메일 주소에 공유하거나, 공개 링크로 공유하거나, 계정 전체 대시보드를 SAML 지원 타사 SSO로 공유할 수 있다 [F25][B7]. 공유 시 Amazon Cognito 리소스가 미국 동부(버지니아 북부)에 생성된다 [B7].
- **권한.** 조회는 GetDashboard·ListDashboards, 생성·수정은 PutDashboard 권한이 필요하다 [B7].

### 1.1.5 SNS로의 알림 구성 (서비스 → SNS, 경보 → SNS)

**세 칸 점검 모델.** SNS로 알림이 안 갈 때는 ① *누가 Publish하는가*(서비스 주체/IAM 역할) ② *그 발행자를 주제가 허용하는가*(주제 액세스 정책) ③ *주제가 암호화돼 있다면 키가 그 발행자를 허용하는가*(KMS 키 정책)를 순서대로 본다.

**소스별 요건 요약 (표 초안)**
| 소스 | 필요한 것 | 근거 |
|---|---|---|
| CloudWatch 경보 | 경보 작업에 주제 ARN 지정. 표준·FIFO 주제 모두 게시 보장(FIFO는 드물게 순서 뒤바뀜). 이메일 구독은 확인 필요. 주제 정책에서 aws:SourceArn은 경보 ARN이어야 함 | [F27][B11] |
| S3 이벤트 알림 | 대상 SNS 주제에 S3가 게시할 수 있도록 정책을 첨부 | [F29] |
| EventBridge 규칙 | IAM 실행 역할 또는 SNS 주제의 리소스 기반 정책(events.amazonaws.com) 중 하나 | [F30] |
| Auto Scaling 그룹 | SNS 알림은 켜고 끄는 것만 가능, 세밀한 조건 알림은 EventBridge | [B11] |
| Amazon Managed Service for Prometheus Alert Manager | 수신자로 SNS만 지원, 같은 계정의 주제로 라우팅 | [B5] |
| 암호화(SSE-KMS) 주제로 위 소스들이 게시 | 고객 관리형 KMS 키 필수 + 키 정책에서 서비스 주체(cloudwatch / events / s3 …)에 kms:GenerateDataKey*·kms:Decrypt 허용. Auto Scaling·AWS Config 등 일부는 서비스 주체 대신 IAM 역할 | [F28][B11] |
| 구독 단위의 장애 대비 | 구독별 DLQ는 같은 계정·리전의 SQS 큐 | [B11] |

**결정 규칙**
- 알림 경로는 *경보→SNS 직접* 또는 *경보 상태 변경→EventBridge→SNS(·Lambda·SSM)* 두 가지다. 직접 경로는 경보 하나의 상태별 작업 수 한도(PutMetricAlarm 기준 최대 5개)에 주제가 포함된다 [B18]. 경보 이벤트를 EventBridge로 받아 알리는 AWS User Notifications 구성은 이 한도에 포함되지 않는다고 문서가 명시한다 [B16][F20].
- 암호화 주제 + 서비스 발행 = 고객 관리형 키 + 키 정책 [F28]. AWS 관리형 기본 키(alias/aws/sns)는 정책을 고칠 수 없어 이 시나리오에 쓸 수 없다는 점이 단골 함정이다 [F28][P1-G13].

## 3. 시험에서 묻는 방식 (가이드 Skill 문구 기반 추정 — 실제 문항 아님)
이 절은 AWS가 공개한 Skill 문구에서 *추론*한 출제 패턴이다. 실제 기출을 안다고 주장하지 않는다.

1. **워크로드별 모니터링 선택/누락 구성 찾기** — 근거 문구: 1.1.1 "configure monitoring and logging for workloads (serverless, compute, AI)". 판단 기준: 기본 제공되는 것(Lambda 지표, EC2 기본 지표, AWS/Bedrock 지표)과 직접 켜야 하는 것(Bedrock 모델 호출 로깅 [F8], CloudTrail 데이터 이벤트 [F3], Lambda 로그 권한 [F7], 로그 보존 [F1], 에이전트 지표)을 가른다.
2. **에이전트 배포 방식 고르기/트러블슈팅** — 근거 문구: 1.1.2 "Configure and manage the CloudWatch agent … EC2 instances, Amazon ECS clusters, or Amazon EKS clusters". 판단 기준: EC2=Parameter Store + ManageAgent + CloudWatchAgentServerPolicy [F11][F12], EKS=Observability 애드온 [F13], ECS=EC2 시작 유형 데몬/Container Insights [F14], 기본 네임스페이스 CWAgent [F10].
3. **복합 경보가 호출할 수 있는 작업 식별 + 알림 미수신 해결** — 근거 문구: 1.1.3 "creating composite alarms and identifying their invokable actions", 1.1.5 "invoke alarms that send notifications to Amazon SNS". 판단 기준: 복합 경보는 EC2·Auto Scaling 작업 불가 [F15], 경보→EventBridge 이벤트 경로 [F20], recover는 System 점검 전용 [F19], 암호화 주제는 고객 관리형 키 [F28], 소스별 발행 권한 [F27][F29][F30].
4. **여러 계정·리전 대시보드 구성 선택** — 근거 문구: 1.1.4 "across multiple accounts and AWS Regions", "shareable". 판단 기준: 대시보드 글로벌 [F22], 교차 리전 경보 불가 [F24], OAM은 단일 리전 [F26], 공유 역할 [F23], 공유 방식 [F25].

## 4. 흔한 함정 · 혼동 짝
| 혼동 짝 | 구분 기준 | 근거 |
|---|---|---|
| 복합 경보 vs 지표 경보의 작업 | 복합 경보는 EC2·Auto Scaling 작업 불가, 지표 경보는 가능 | [F15][C16][C24] |
| EC2 recover vs reboot | recover=StatusCheckFailed_System 전용, reboot=인스턴스 상태 점검 실패에 권장 | [F19][C21] |
| missing vs notBreaching vs ignore | missing은 전부 누락일 때 INSUFFICIENT_DATA, ignore는 현재 상태 유지. DynamoDB 지표는 항상 ignore | [F18][C13][C14] |
| 경보 Period vs 지표 게시 주기 | EC2 기본 모니터링은 상태 점검 1분·그 외 5분. 게시 주기보다 짧은 기간은 INSUFFICIENT_DATA 위험 | [F6][C10] |
| 고해상도 경보 기간 | API 허용값은 10·20·30초, 개념 페이지는 10·30초로 서술 | [F21][C4][P1-G03] |
| 지표 필터 vs 구독 필터 | 둘 다 Standard 클래스 전용. 지표 필터는 숫자 지표화(소급 안 됨), 구독 필터는 이벤트 자체를 실시간 전달 | [F4][B10][C32] |
| 로그 보존 기본값 | 기본은 만료 없음. 보존 값은 정해진 목록에서 선택 | [F1][D1][D2] |
| Event history vs 추적(데이터 이벤트) | Event history는 관리 이벤트 90일. 데이터 이벤트는 기본 미기록 | [F2][F3] |
| 대시보드 vs 경보의 범위 | 대시보드는 글로벌·교차 리전 가능, 경보는 교차 리전 불가 | [F22][F24] |
| OAM vs 교차 계정 콘솔 vs 중앙화 | OAM=단일 리전·공유, 콘솔=교차 리전(경보 제외), 중앙화=복사 | [F26][F23][B7] |
| SNS 암호화 주제의 키 | 서비스 발행에는 고객 관리형 키 + 키 정책 | [F28] |
| Bedrock 지표 vs 호출 로깅 vs CloudTrail | 지표=수치, 호출 로깅=입력·출력 전문(기본 꺼짐), CloudTrail=API 감사 | [F8][B4] |
| AMP 보관 vs CloudWatch 지표 보관 | AMP 기본 150일, CloudWatch 지표는 해상도별 계단식 최대 455일 | [F9][F5] |

## 6. 자가 점검 문항 후보 (3~5) — 후보일 뿐, 검증 아님
### Q1 (Skill 1.1.3 · intermediate)
문제: 운영팀은 EC2 인스턴스 하나에 지표 경보 CpuHigh와 StatusFailedInstance(StatusCheckFailed_Instance 기반)를 두고 있다. 두 경보가 모두 ALARM일 때만 온콜 담당자에게 SNS로 알려 알림 노이즈를 줄이고, 인스턴스 재부팅은 StatusFailedInstance가 ALARM이 되면 자동으로 수행하려 한다. 올바른 구성은?
- A) CpuHigh와 StatusFailedInstance를 AND로 묶은 복합 경보 하나에 SNS 알림과 EC2 reboot 작업을 모두 지정한다.
- B) 복합 경보에는 SNS 알림만 지정하고, EC2 reboot 작업은 StatusFailedInstance 지표 경보에 직접 지정한다.
- C) 복합 경보에 SNS 알림을 지정하고, 재부팅은 같은 복합 경보에 Auto Scaling 작업으로 지정한다.
- D) 복합 경보는 어떤 작업도 지정할 수 없으므로 SNS 알림도 EventBridge 규칙으로만 보내야 한다.

정답: B
정답 근거: 복합 경보는 EC2 작업과 Auto Scaling 작업을 수행할 수 없고 SNS 알림 등은 가능하다 [F15][C24]. EC2 reboot는 인스턴스 단위 지표 경보에 붙이며 인스턴스 상태 점검 실패에 권장된다 [C16][C21] — https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch_Alarms.html
오답 이유: A) 복합 경보는 EC2 작업을 수행할 수 없다 [F15]. C) Auto Scaling 작업도 복합 경보에는 지정할 수 없다 [F15]. D) 복합 경보도 SNS 알림을 보낼 수 있다 — EventBridge는 필수 경로가 아니다 [C24].

### Q2 (Skill 1.1.1 · intermediate)
문제: 한 회사가 Amazon Bedrock의 Converse API로 사내 챗봇을 운영한다. 보안팀이 지난주 사용자 프롬프트와 모델 응답 전문을 CloudWatch Logs에서 찾으려 하지만 관련 로그 그룹이 없다. CloudWatch의 AWS/Bedrock 지표에서는 호출 횟수와 토큰 수만 보인다. 원인과 조치로 올바른 것은?
- A) 모델 호출 로깅이 기본적으로 꺼져 있다. Bedrock에서 모델 호출 로깅을 켜고 같은 계정·리전의 CloudWatch Logs 또는 S3를 대상으로 지정한다.
- B) 로그 그룹의 기본 보존 기간이 지나 삭제됐으므로 보존 기간을 늘려야 한다.
- C) AWS/Bedrock 네임스페이스의 InputTokenCount 지표의 통계를 조회하면 프롬프트 텍스트 전문을 볼 수 있다.
- D) CloudWatch Logs 지표 필터를 만들면 과거 호출의 프롬프트가 소급해서 지표로 수집된다.

정답: A
정답 근거: 모델 호출 로깅은 기본적으로 꺼져 있고, 켜면 CloudWatch Logs 또는 S3로 입력·출력 전문을 수집한다 [F8] — https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html
오답 이유: B) 로그 그룹 보존의 기본값은 만료 없음이며 [F1], 애초에 로깅이 꺼져 있어 로그가 만들어지지 않았다 [F8]. C) InputTokenCount는 입력 토큰의 개수를 나타내는 수치 지표다 [B4]. D) 지표 필터는 생성 이후 이벤트에만 적용되고 [C32] 로그가 존재해야 하는데 로그가 수집된 적이 없다 [F8].

### Q3 (Skill 1.1.5 · intermediate)
문제: CloudWatch 경보가 SSE로 암호화된 SNS 주제(키: AWS 관리형 키 alias/aws/sns)로 알림을 게시하지 못하고, 경보 이력에는 주제 암호화 키에 접근할 권한이 없다는 오류가 남는다. 올바른 해결 방법은?
- A) 주제를 표준 주제에서 FIFO 주제로 교체한다.
- B) 고객 관리형 KMS 키로 주제를 암호화하고, 키 정책에서 cloudwatch.amazonaws.com 서비스 주체에 kms:GenerateDataKey*와 kms:Decrypt를 허용한다.
- C) AWS 관리형 키 alias/aws/sns의 키 정책을 편집해 CloudWatch를 허용한다.
- D) 경보 작업을 SNS에서 EventBridge로 바꾸면 키 권한이 필요 없어진다.

정답: B
정답 근거: AWS 서비스가 암호화된 SNS 주제에 이벤트를 게시하려면 고객 관리형 키를 쓰고 키 정책에서 해당 서비스 주체에 kms:GenerateDataKey*·kms:Decrypt를 허용해야 한다 [F28] — https://docs.aws.amazon.com/sns/latest/dg/sns-key-management.html
오답 이유: A) CloudWatch는 표준·FIFO 주제 모두에 게시를 보장하므로 주제 유형이 원인이 아니다 [F27]. C) 문서화된 절차는 고객 관리형 키를 쓰는 것이다 [F28]. D) EventBridge(events.amazonaws.com)도 암호화 주제에는 키 정책 허용이 필요하다 [F28][F30].

- A) 각 멤버 계정에서 CloudWatch 데이터를 모니터링 계정과 공유(CloudWatch-CrossAccountSharingRole 생성)하고, 모니터링 계정에서 교차 계정·교차 리전 기능을 켠 뒤 대시보드를 만든다.
- B) 계정·리전마다 대시보드를 따로 만들고 URL을 모아 공유한다.
- C) 모니터링 계정의 us-east-1에서 eu-west-1 지표를 감시하는 경보를 만들어 대시보드에 추가한다.
