## 2. 핵심 개념 (한국어)

### 4.2.1 데이터 분류 체계의 구현과 적용

**핵심 아이디어**: "분류"는 문서가 아니라 *태그·정책·자동 탐지·모니터링으로 실제 리소스에 표시하고 강제하는 일*이다. 이 Skill의 동사는 "implement and **enforce**"이므로, 시험은 (a) 민감 데이터가 어디 있는지 찾기, (b) 분류 표시를 표준화·강제하기, (c) 분류에 맞는 보호 통제 연결하기를 묻는다고 추정된다.

1. **데이터 이해가 첫 단계** [F1]: 워크로드가 처리하는 데이터의 분류, 취급 요건, 저장 위치, 소유자를 파악한다(S1). 데이터 카탈로그에 위치·민감도·보호 통제를 매핑해 두면 점검이 쉬워진다(S1).
2. **리소스 태그로 표시**: 예컨대 `Classification=PHI`, `Sensitivity=High` 같은 태그를 붙이고, 태그 키·값에는 민감한 정보를 넣지 않는다(S1).
3. **표준화·강제 — Organizations 태그 정책** [F2]: 조직 계정의 리소스에 붙는 태그를 표준화한다(S2). 다만 사용자가 표준 태그 키를 수정하거나 규격에 안 맞는 태그로 리소스를 만들 수 있으므로 SCP로 권한을 제한해 보완한다(S2c).
4. **자동 탐지 — Amazon Macie** [F3]: S3 객체에서 자격 증명·금융 정보·개인 정보(PHI/PII)를 관리형 데이터 식별자로 탐지한다(S3). 결과(정책 결과·민감 데이터 결과)는 EventBridge로 자동 게시되고 Security Hub CSPM에도 보낼 수 있으며(S3b), Macie는 결과를 90일 동안 저장한다(S3c).
5. **분류별 통제 연결**: 분류 태그 기반 접근 제어(ABAC)는 리소스와 주체에 붙은 태그를 비교해 권한을 준다(S2b). AWS Config로 분류된 리소스의 암호화 설정 변경 같은 이탈을 감시한다(S1).

| 요구 | 쓰는 것 | 한 줄 이유 |
|---|---|---|
| S3에 PII가 어디 있는지 찾기 | Macie | S3 객체의 민감 데이터 탐지 [F3] |
| 분류 태그 키·값을 조직 전체에 표준화 | Organizations 태그 정책 | 태그 표준 강제 [F2] |
| 태그가 일치하는 주체만 접근 | ABAC(IAM 조건) | 태그 기반 권한(S2b) |
| 분류 리소스의 구성 이탈 감시 | AWS Config | 변경 감시·알림(S1) |

### 4.2.2 저장 시 암호화 구현·구성·문제 해결 (AWS KMS)

**(1) KMS 키 3종 비교** (S5)
| 항목 | AWS 소유 키 | AWS 관리형 키 (`aws/<서비스>`) | 고객 관리형 키 |
|---|---|---|---|
| 관리 주체 | 서비스가 소유·관리, 여러 계정이 공용 | 내 계정에 존재하지만 수명·권한은 관리 불가 | 내가 수명주기 전체를 통제 |
| 자동 교체 | 서비스가 관리(S4) | **매년 자동, 켜고 끌 수 없음** [F6] | **선택**, 기본 365일, 90~2560일 지정 [F4][F5] |
| 다른 계정과 리소스 공유 | — | **불가** [F7] | 가능(키 공유) |
- AWS 관리형 키는 2021년 이후 새 AWS 서비스용으로 더는 만들지 않는 레거시 유형이다(S5).

**(2) 키 교체 — 레포 '검수 대기' 항목의 공식 값**
- 고객 관리형 키의 자동 교체 주기는 **90~2560일 범위에서 지정**하고 [F4], 지정하지 않으면 **기본 365일**이다 [F5]. 둘을 구분해 외운다: *기본값 365 / 범위 90~2560*.
- 자동 교체는 AWS KMS가 키 자료를 생성한(AWS_KMS 출처) **대칭 암호화 키**만 지원한다(S4). 가져온 키 자료(EXTERNAL) 대칭 키는 **온디맨드 교체**가 가능하고, 비대칭 키·HMAC 키·커스텀 키 스토어 키는 **수동 교체**(새 키를 만들고 별칭/참조를 전환)만 된다(S4).
- 교체는 *키 자료만* 바꾼다 — 키가 만든 데이터 키를 교체하거나 데이터를 재암호화하지 않고(S4), 복호화 시 올바른 키 자료를 KMS가 자동으로 고른다(S4). 그래서 애플리케이션은 코드 변경이 없다.
- AWS 관리형 키는 매년 교체되며(2022년 5월에 3년에서 1년으로 변경) 끌 수 없다 [F6](S4).

**(3) 접근 제어 — 키 정책이 중심이다**
- 모든 KMS 키는 키 정책을 정확히 1개 가진다(S6). **키 정책이 허용하지 않으면 IAM 정책의 Allow는 효력이 없다** [F8]. 기본 키 정책에는 계정에 대해 IAM 정책을 활성화하는 문장이 있어, 그 문장이 있으면 IAM 정책으로 접근을 줄 수 있다(S6).
- 같은 계정이면 키 정책만으로 접근을 통제할 수 있지만, 다른 계정의 호출자는 키 정책만으로는 안 되고 호출자 쪽 IAM 정책도 필요하다(S6b). 키 정책은 리전 단위로만 효력이 있다(S6).
- **그랜트(grant)** 는 키 정책·IAM 정책을 바꾸지 않고 임시 권한을 위임하는 정책 수단이다(S6d). `kms:ViaService` 조건 키는 지정한 AWS 서비스를 통한 요청에서만 키를 쓰도록 제한한다(S6c).
- 봉투 암호화: 데이터를 데이터 키로 암호화하고 그 데이터 키를 다른 키로 암호화한다(S7b). KMS 직접 호출(Encrypt)로 암호화할 수 있는 평문은 4 KB까지다(S7c).

**(4) 서비스별 적용 — 새 리소스 vs 이미 있는 비암호화 리소스**
| 서비스 | 새 리소스 | 이미 있는 비암호화 리소스 |
|---|---|---|
| S3 | 모든 새 객체는 SSE-S3 기본 암호화(2023-01-05~)(S8). SSE-KMS는 **버킷 키**로 KMS 요청 비용을 최대 99% 줄일 수 있다(S8b). **2026-04부터 신규 범용 버킷은 SSE-C가 기본 비활성** [F10] | 기본 암호화 설정은 새 쓰기에 적용 |
| EBS | 기본 암호화는 **리전 단위 설정**이며 기존 볼륨·스냅샷에는 영향 없음(S10) | 스냅샷 생성 → **암호화된 복사본** → 새 볼륨(S10c) |
| RDS | 인스턴스 **생성 시에만** 암호화 지정 [F11] | 스냅샷 생성 → 암호화된 복사 → 복원(S9); Aurora는 스냅샷 복사 대신 복원 시 암호화를 선택(S9b) |
- 교차 계정 EBS 스냅샷 공유: **고객 관리형 키로 암호화한 스냅샷만** 공유할 수 있고 키도 함께 공유해야 한다(S10b). AWS 관리형 키(aws/ebs)로 암호화된 리소스는 다른 계정과 공유할 수 없다 [F7].

**(5) 삭제와 문제 해결**
- 키 삭제는 **7~30일 대기(기본 30일)** 후 실행되고, 대기 중에는 키가 사용 불가 상태가 되어 모든 암호화 작업이 실패한다 [F9](S7). → 삭제 전에 비활성화로 영향을 먼저 확인한다.
| 증상 | 가능한 원인 | 조치 |
|---|---|---|
| 다른 계정 사용자가 SSE-KMS 객체를 읽지 못함 | 키 정책에 주체가 없거나 호출자 IAM 정책 누락 — 교차 계정은 키 정책만으로 불가(S6b) | 키 정책 허용 + 호출자 IAM 정책 |
| 암호화된 EBS 스냅샷을 다른 계정과 공유 불가 | 기본 키(aws/ebs)로 암호화됨 [F7] | 고객 관리형 키로 복사 후 키 공유(S10b) |
| `ThrottlingException` | 계정·리전 요청 쿼터 초과 또는 같은 키의 상태 변경 폭주("hot key") | 백오프·재시도, S3 버킷 키 사용, 쿼터 증가(KMS 쿼터는 조정 가능)(S11, S11b) |
| 키로 암호화/복호화가 모두 실패 | 키가 삭제 대기 중이거나 비활성 [F9] | 삭제 취소 또는 키 활성화 |
| 운영 중인 RDS를 암호화하고 싶다 | 생성 후 변경 불가 [F11] | 스냅샷 → 암호화 복사 → 복원 |

### 4.2.3 전송 중 암호화 구현·구성·문제 해결 (ACM 중심)

**(1) ACM 공인 인증서 — 검증·갱신·유효 기간**
- **DNS 검증**: ACM이 주는 CNAME 레코드를 한 번 추가하면 되고, 인증서가 사용 중이고 CNAME이 유지되는 한 자동 갱신된다(S12c). DNS 검증으로 발급한 인증서의 관리형 갱신은 완전 자동이다 [F12]. **이메일 검증으로 만든 인증서는 DNS 검증으로 전환할 수 없다** — 삭제 후 새로 요청해야 한다(S12c).
- **가져온 인증서(imported)는 관리형 갱신 대상이 아니다** [F13] → 만료일을 직접 추적해 교체한다. 반대로 AWS 서비스(ELB, CloudFront 등)에 연결된 ACM 발급 인증서는 갱신 대상이다(S12). DNS 갱신 검증이 실패하면 만료 30·15·7·3·1일 전에 AWS Health 이벤트와 EventBridge 이벤트가 온다(S12b).
- **유효 기간**: 2026-02-18 이후 신규·갱신 공인 인증서는 **198일**이며 ACM은 만료 45일 전에 갱신을 시도한다 [F14](S12d). 기존 395일 인증서는 만료 60일 전에 갱신되며 198일로 갱신된다(S12b). 업계 일정상 2027-03-15부터는 100일 미만, 2029-03-15부터는 47일 미만으로 줄어든다(S13).
- **요금**: 통합 서비스용 ACM 인증서는 무료(S13b), 내보내기 가능(exportable) 공인 인증서는 추가 요금(S13c). 사설 PKI는 **AWS Private CA**를 쓴다(S15b).

**(2) 서비스별 인증서 위치(리전)**
| 대상 | ACM 인증서 리전 | 비고 |
|---|---|---|
| Amazon CloudFront | **US East (N. Virginia, us-east-1)** [F15] | 인증서가 엣지 로케이션으로 배포됨 |
| API Gateway — 엣지 최적화 사용자 지정 도메인 | us-east-1 [F16] | |
| API Gateway — 리전 사용자 지정 도메인 | API와 같은 리전(S14) | |
| ELB(ALB/NLB) | 로드 밸런서와 같은 리전(S13d) | ALB HTTPS 리스너는 기본 인증서 정확히 1개 + SNI로 추가 인증서(S14b) |

**(3) 구간별 TLS 강제 방법**
| 구간 | 강제 방법 | 근거 |
|---|---|---|
| 클라이언트 → S3 | 버킷 정책에서 `aws:SecureTransport`가 `false`인 요청을 Deny — 이 키는 요청이 HTTP로 왔는지 알려 준다 | [F17]; Config 관리형 규칙 `s3-bucket-ssl-requests-only`도 같은 목적(S16f) |
| 뷰어 → CloudFront | 뷰어 프로토콜 정책: HTTP/HTTPS 허용, **Redirect HTTP to HTTPS**(301), **HTTPS only**(HTTP 요청에 403) | (S16d) |
| 클라이언트 → RDS | MySQL: `require_secure_transport`를 ON, PostgreSQL: `rds.force_ssl`=1(15 이상 기본값) | [F18]; (S16c) |

**(4) 트러블슈팅**
| 증상 | 원인 | 조치 |
|---|---|---|
| 인증서가 계속 Pending validation | CNAME이 **공용 DNS**에서 조회되지 않음(VPC 프라이빗 호스팅 영역·VPN 뒤 DNS 포함), 오타, CAA 레코드가 발급을 차단 | 공용 DNS의 CNAME 확인, CAA 점검(S15). ACM은 72시간 동안 검증을 시도한 뒤 시간 초과(S15) → 삭제 후 재요청 |
| CloudFront 설정 화면에 인증서가 안 보임 | 인증서가 us-east-1에 없음 | us-east-1에서 다시 요청/가져오기 [F15] |
| 가져온 인증서 만료 임박 | 관리형 갱신 대상 아님 [F13] | 새 인증서를 가져와 교체 |
| 이메일 검증 인증서를 DNS로 바꾸고 싶음 | 전환 불가(S12c) | 삭제 후 DNS 검증으로 재요청 |
| ALB가 기대와 다른 인증서를 반환 | SNI 없이 접속했거나 일치하는 SAN 인증서가 목록에 없으면 기본 인증서 사용(S14b) | 호스트명에 맞는 인증서를 목록에 추가 |

### 4.2.4 시크릿의 안전한 저장 (Secrets Manager · Parameter Store)

**(1) AWS Secrets Manager**
- 하드코딩된 자격 증명을 코드에서 없애고 런타임에 조회하며, 자동 회전 일정을 구성할 수 있다(S17).
- **회전 방식 2가지**: *관리형 회전*(지원되는 관리형 시크릿)은 **Lambda를 쓰지 않는다** [F20]. 그 외 시크릿은 **Lambda 함수가** 시크릿과 데이터베이스/서비스를 갱신한다 [F19]. 회전 함수는 시크릿을 직접 회전해야 하며 다른 Lambda를 호출해 대신 회전시킬 수 없다(S17c). 회전 중 버전은 스테이징 라벨(AWSCURRENT·AWSPENDING·AWSPREVIOUS)로 식별한다(S17c, S17d).
- **삭제**: 복구 기간은 최소 7일·기본 30일 [F21]. 삭제 예약된 시크릿의 값은 조회할 수 없고, 복원(RestoreSecret)해야 다시 조회된다(S17e).
- **비용**: AWS 관리형 키 `aws/secretsmanager`로 암호화하면 무료, 자체 KMS 키를 쓰면 KMS 요금. 관리형 회전을 제외한 자동 회전은 Lambda 요금이 붙는다. 삭제 예약된 시크릿에는 요금이 없다(S17).
- **교차 계정**: 시크릿에 리소스 정책을 붙이고, 호출자가 시크릿을 암호화한 KMS 키도 쓸 수 있게 키 정책에 권한을 줘야 한다. 필요한 KMS 권한은 수행하는 작업에 따라 다르다(예: 값 읽기)(S17f).

**(2) AWS Systems Manager Parameter Store**
| 항목 | 표준(Standard) | 고급(Advanced) |
|---|---|---|
| 값 크기 | 4 KB [F22] | 8 KB [F23] |
| 리전·계정당 파라미터 수 | 10,000(S18b) | 100,000(S18b) |
| 파라미터 정책 | 불가(S18b) | 가능(S18b) |
| 요금 | 추가 요금 없음(S18) | 요금 부과(S18) |
- 표준 → 고급 변경은 언제든 가능하지만 **고급 → 표준은 불가**하다(S18). Parameter Store 파라미터로 Secrets Manager 시크릿을 참조할 수 있고(`/aws/reference/secretsmanager/` 접두어, 조회 API만 지원)(S18c), 참조는 통과(pass-through) 방식이다(S18c).

**(3) 선택 규칙** (S17, S18d)
| 상황 | 선택 |
|---|---|
| 자동 회전이 필요한 시크릿(DB 자격 증명 등) | Secrets Manager(자동 회전이 이점인 시크릿에 사용) |
| 단순 설정값·교체 불필요·비용 민감 | Parameter Store 표준 |
| 4 KB 초과~8 KB 또는 파라미터 정책 필요 | Parameter Store 고급 |
| AWS 자격 증명 | IAM(Secrets Manager 문서가 권장)(S17) |
| 암호화 키 / 개인 키·인증서 | KMS / ACM(S17) |
- 주의: KMS 키 교체는 *데이터 키나 자격 증명의 값을 바꾸는 것이 아니다* — 키 교체는 KMS 키가 보호하는 데이터에 영향이 없다(S4).

### 4.2.5 보고서 구성과 보안 결과(findings) 교정 (v1.1: AWS Security Agent 추가)

**서비스 지도 — "무엇을 보고, 어떤 결과를 내고, 어떻게 교정하나"**
| 서비스 | 보는 것 | 결과·보고서 | 교정 연결 |
|---|---|---|---|
| AWS Security Hub (신규) | 여러 서비스의 보안 신호를 상관시켜 노출(exposure) 판단 | OCSF 결과 [F25], 노출 결과, 대시보드(S19b) | 자동화 규칙·티켓 연동(S19b) |
| Security Hub CSPM | 보안 표준(FSBP·CIS·NIST 등) 대비 구성 점검 [F24] | 컨트롤 결과, 보안 점수 0~100(S19f) | 새 결과·업데이트를 EventBridge로 [F26] |
| Amazon GuardDuty | 위협·악성 활동 | 결과(심각도 1.0~10.0, Low/Medium/High/Critical)(S20c) | EventBridge 규칙, S3 내보내기(S20d) |
| Amazon Inspector | 소프트웨어 취약점·의도치 않은 네트워크 노출 [F28] | 결과, CSV/JSON 보고서(S21) | 수정 확인 시 자동 종료, EventBridge/Security Hub CSPM(S21) |
| AWS Config | 구성 준수 | 규칙 평가·적합성 팩 | Systems Manager Automation 교정(S23) |
| Amazon Macie | S3 민감 데이터 [F3] | 정책/민감 데이터 결과(S3b) | EventBridge(S3b) |
| AWS Security Agent | 애플리케이션 설계·코드·침투 테스트 [F29] | 침투 테스트 결과(CVSS 점수·재현 단계·수정 제안)(S22c), 보고서 PDF(S22d) | 교정 요청 → PR/MR 또는 diff [F30] |

**Security Hub의 개편 — 이름이 바뀐 점이 함정이다**
- 구 Security Hub의 기능(표준·컨트롤 기반 구성 점검)은 이제 **Security Hub CSPM**이다 [F24]. 2025-12에 일반 제공된 **Security Hub**는 GuardDuty·Inspector·Macie·CSPM의 신호를 상관시켜 노출 결과를 만드는 통합 솔루션이다(S19b). 결과 형식은 신 Security Hub가 **OCSF** [F25], CSPM 이벤트 문서는 **ASFF**를 가리킨다(S19c).
- CSPM 결과는 Security Hub로 자동 전달된다(S19). 둘 다 켜는 것이 권장이지만 구성 오류 평가만 필요하면 CSPM만으로도 된다(S19).
- CSPM 표준: AWS Foundational Security Best Practices, CIS AWS Foundations Benchmark, NIST SP 800-53 Rev. 5 등(S19e); PCI DSS 등 규제 표준도 지원(S19f).
- **교차 리전 집계**: 홈 리전을 지정하면 여러 리전의 결과·인사이트·컨트롤 준수 상태·보안 점수를 한 곳에서 관리한다(S19d).
- **자동 교정(EventBridge)**: CSPM은 새 결과와 기존 결과의 업데이트를 EventBridge로 보내고 [F26], 대상으로 Lambda, EC2 Run Command, Kinesis, Step Functions, SNS/SQS, 서드파티 도구를 호출할 수 있다(S19c).

**GuardDuty**
- 활성화하면 CloudTrail 관리 이벤트, VPC 흐름 로그, DNS 로그의 분석이 자동 시작된다(기초 위협 탐지) [F27]. S3·EKS·Runtime Monitoring·Malware·RDS·Lambda·AI 보호 플랜은 선택 기능이며, 처음 활성화하면 Runtime Monitoring을 뺀 모든 보호 플랜이 30일 무료 체험과 함께 자동 활성화된다(S20). **Extended Threat Detection**은 활성화하면 자동으로 켜진다(S20).
- 결과 관리: 신뢰 목록(trusted)의 항목에는 결과를 만들지 않고, 위협 목록(threat)에는 결과를 만든다(S20b). 계정·리전당 신뢰 목록은 엔티티 목록 1개와 IP 목록 1개다(S20b). 억제 규칙으로 자동 보관된 결과는 EventBridge로 전송되지 않는다(S20e).
- 결과 알림은 EventBridge 규칙과 대상을 만들어야 받는다(S20e). 내보내기(S3/EventBridge) 기본 주기는 6시간이며 15분·1시간으로 줄일 수 있다(S20d).

**Amazon Inspector**
- 대상은 EC2 인스턴스, ECR 컨테이너 이미지, Lambda 함수 [F28]. 새 패키지 설치·패치·새 CVE 공개에 따라 자동으로 **재스캔**하고(S21), 취약점을 수정하면 결과를 자동으로 닫는다(S21).
- EC2는 SSM 에이전트 기반 스캔이 기본이며, 하이브리드 모드에서는 에이전트 없는 인스턴스를 EBS 스냅샷으로 스캔하되 24시간마다 한 번만 재스캔한다(S21c). **억제 규칙은 결과를 숨길 뿐 닫거나 교정하지 못한다**(S21b).

**AWS Config (4.1.5와 공유)**: 관리형 규칙 → 비준수 판정 → Systems Manager Automation 문서로 교정(S23). 조직 단위는 적합성 팩과 집계자로 묶는다(S23b).

**AWS Security Agent (v1.1 신규 예시)**
- **무엇**: 개발 수명주기 전반에서 애플리케이션을 선제적으로 보호하는 "프런티어 에이전트"다 [F29]. 조직 보안 요구 사항에 맞춘 설계·코드 보안 검토, 위협 모델링, 온디맨드 침투 테스트를 수행한다(S22).
- **결과 교정**: 침투 테스트 결과에서 AWS Security Agent에 교정을 요청할 수 있고 [F30], 연결된 비공개 저장소에는 풀 리퀘스트(GitLab은 머지 리퀘스트)가 열리며 S3 소스는 내려받아 적용하는 코드 diff로 제공된다(S22b). 교정 기능은 콘솔에서 사용자가 시작할 수 있도록 먼저 활성화해야 한다(S22b).
- **구분**: Inspector = 실행 중인 워크로드의 패키지 취약점(CVE)·네트워크 노출, GuardDuty = 위협 활동, Security Agent = 애플리케이션 설계·코드·침투 테스트. (명칭은 문서에서 "AWS Security Agent (now part of AWS Continuum)"로 표기됨 — 99-P5-G08.)

## 3. 시험에서 묻는 방식 (가이드 Skill 문구 기반 추정 — 실제 문항 아님)
이 절은 AWS가 공개한 Skill 문구에서 추론한 것이며, 실제 기출을 안다는 주장이 아니다.
1. **저장 시 암호화 시나리오 해결** — 근거 문구: 4.2.2 "Implement, configure, and troubleshoot encryption at rest (for example, AWS KMS)". 판단 기준: 키 유형별 교체·공유 가능 여부 [F6][F7]; 교체 주기 90~2560일·기본 365일 [F4][F5]; 키 정책이 IAM보다 먼저 [F8]; 이미 있는 RDS는 스냅샷 경유 [F11]; 삭제 대기 7~30일 [F9]; 신규 S3 버킷의 SSE-C 기본 비활성 [F10].
2. **인증서·전송 중 암호화 문제 진단** — 근거 문구: 4.2.3 "(for example, AWS Certificate Manager [ACM])". 판단 기준: CloudFront·엣지 최적화 API Gateway는 us-east-1 [F15][F16]; 가져온 인증서는 자동 갱신 안 됨 [F13]; DNS 검증은 자동 갱신 [F12]; S3 HTTPS 강제는 `aws:SecureTransport` Deny [F17]; RDS는 파라미터로 SSL 강제 [F18].
3. **시크릿 저장소 선택** — 근거 문구: 4.2.4 "Securely store secrets by using AWS services". 판단 기준: 자동 회전이면 Secrets Manager [F19][F20]; 단순 설정·4 KB는 Parameter Store 표준, 8 KB·정책은 고급 [F22][F23]; 삭제 복구 기간 [F21].
4. **보안 결과(finding)를 만드는 서비스 고르기와 교정 흐름** — 근거 문구: 4.2.1 "Implement and enforce a data classification scheme", 4.2.5 "Configure reports and remediate findings (… AWS Security Agent)". 판단 기준: 민감 데이터=Macie [F3]; 취약점=Inspector [F28]; 위협=GuardDuty [F27]; 표준 대비 구성=Security Hub CSPM [F24]; 통합·노출=Security Hub [F25]; 앱 침투 테스트·코드 검토=Security Agent [F29]; 자동 교정=EventBridge [F26]/Security Agent 교정 요청 [F30].

| 관리형 회전 vs Lambda 회전 | Lambda 불필요 vs Lambda 함수가 갱신 | [F19][F20] |

| GuardDuty vs Inspector vs Macie vs Security Agent | 위협 / 워크로드 취약점 / S3 민감 데이터 / 앱 설계·코드·침투 테스트 | [F27][F28][F3][F29] |
| GuardDuty 신뢰 목록 vs 억제 규칙 | 신뢰 목록=결과 자체를 만들지 않음, 억제 규칙=결과를 자동 보관(알림 제외) | (S20b, S20e) |

## 6. 자가 점검 문항 후보 (3~5) — 후보일 뿐, 검증 아님

### Q1 (Skill 4.2.1 · foundational)
문제: 한 기업이 수백 개 S3 버킷에 고객 개인 정보(PII)가 저장되어 있는지 파악하고, 발견 즉시 EventBridge로 알림을 받아 분류 태그를 붙이는 워크플로를 자동화하려 한다. 가장 적절한 서비스는?
- A) Amazon Macie
- B) Amazon Inspector
- C) Amazon GuardDuty
- D) AWS Config 관리형 규칙
정답: A
정답 근거: Macie는 S3 객체의 민감 데이터를 탐지하고, 정책·민감 데이터 결과를 EventBridge로 자동 게시한다. [F3] — https://docs.aws.amazon.com/macie/latest/user/managed-data-identifiers.html (EventBridge 게시: https://docs.aws.amazon.com/macie/latest/user/findings-monitor.html)
오답 이유: B) Inspector는 EC2·ECR·Lambda의 소프트웨어 취약점을 스캔한다 [F28] / C) GuardDuty는 CloudTrail·VPC 흐름 로그·DNS 로그 기반 위협 탐지다 [F27] / D) Config는 리소스 구성 준수 평가이며 객체 내용의 민감 데이터를 보지 않는다.

### Q2 (Skill 4.2.2 · intermediate)
문제: 규정상 암호화 키 자료를 180일마다 교체해야 한다. 데이터를 암호화하는 S3 SSE-KMS 키에 대해 가장 적절한 구성은?
- A) 고객 관리형 대칭 KMS 키에서 자동 키 교체를 켜고 교체 주기를 180일로 지정한다.
- B) AWS 관리형 키(aws/s3)의 교체 주기를 180일로 변경한다.
- C) 비대칭 KMS 키를 만들고 자동 교체를 180일로 켠다.
- D) 고객 관리형 키의 교체 주기를 30일로 지정한다.
정답: A
정답 근거: 고객 관리형 키의 자동 교체 주기는 90~2560일에서 지정할 수 있고(기본 365일), 자동 교체는 대칭 암호화 키가 대상이다. [F4][F5] — https://docs.aws.amazon.com/kms/latest/APIReference/API_EnableKeyRotation.html
오답 이유: B) AWS 관리형 키는 매년 교체되며 주기를 바꾸거나 끌 수 없다 [F6] / C) 비대칭 키는 자동·온디맨드 교체 대상이 아니라 수동 교체만 가능하다 (S4) / D) 30일은 허용 범위(90~2560일) 밖이다 [F4].

### Q3 (Skill 4.2.3 · intermediate)
문제: 서울 리전에서 ACM 공인 인증서를 발급(DNS 검증 완료, 상태 Issued)했는데, CloudFront 배포의 사용자 지정 도메인(CNAME) 설정 화면에서 이 인증서를 선택할 수 없다. 해결책은?
- A) US East (N. Virginia, us-east-1)에서 같은 도메인으로 인증서를 새로 요청하거나 가져와 CloudFront에 연결한다.
- B) 서울 리전 인증서를 내보내기(export) 후 CloudFront에 수동 업로드하는 대신 ACM 갱신을 기다린다.
- C) 인증서를 이메일 검증으로 다시 발급한다.
- D) CloudFront 배포를 서울 리전으로 옮긴다.
정답: A
정답 근거: CloudFront에 ACM 인증서를 쓰려면 US East (N. Virginia) 리전에서 요청하거나 가져와야 한다. [F15] — https://aws.amazon.com/certificate-manager/faqs/
오답 이유: B) 갱신이나 내보내기는 리전 요건과 무관하다 / C) 검증 방식은 리전 문제와 무관하며 이메일→DNS 전환이 불가능한 것과도 별개다 (S12c) / D) CloudFront는 글로벌 서비스이며 배포를 리전으로 옮기는 개념이 아니다(리전 요건은 인증서 위치).

### Q4 (Skill 4.2.4 · intermediate)
문제: 애플리케이션이 쓰는 RDS 데이터베이스 자격 증명을 30일마다 자동 교체하고, 코드에 자격 증명을 하드코딩하지 않으려 한다. 운영 부담이 가장 적은 방법은?
- A) AWS Secrets Manager에 시크릿을 저장하고 자동 회전 일정을 구성한다.
- B) Systems Manager Parameter Store 표준 파라미터에 저장하고 수동 스크립트로 갱신한다.
- C) 자격 증명을 KMS로 암호화해 환경 변수에 넣고 KMS 키 자동 교체를 켠다.
- D) Parameter Store 고급 파라미터로 승급하고 파라미터 정책으로 값을 자동 생성한다.
정답: A
정답 근거: Secrets Manager는 자동 회전 일정을 구성할 수 있고, 관리형 회전은 Lambda 없이, 그 외에는 Lambda 함수로 시크릿과 DB를 갱신한다. [F19][F20] — https://docs.aws.amazon.com/secretsmanager/latest/userguide/rotating-secrets.html
오답 이유: B) 표준 파라미터는 값 저장소일 뿐 자동 회전 기능이 없어 수동 부담이 크다(자동 회전이 이점인 시크릿에는 Secrets Manager — S18d) / C) KMS 키 교체는 키 자료 교체일 뿐 자격 증명 값이나 데이터 키를 바꾸지 않는다(S4) / D) 고급 파라미터는 큰 값(8 KB)과 정책을 지원하지만 시크릿 값을 교체하는 기능이 아니다 [F23].

### Q5 (Skill 4.2.5 · intermediate)
문제: 보안팀은 신규 애플리케이션의 설계 문서와 코드를 조직 보안 요구 사항에 맞춰 검토하고, 배포 전에 온디맨드 침투 테스트를 수행해 확인된 취약점에 대한 코드 수정(풀 리퀘스트) 제안을 받고 싶다. 가장 적절한 서비스는?
- A) AWS Security Agent
- B) Amazon Inspector
- C) Amazon GuardDuty
- D) AWS Security Hub CSPM
정답: A
정답 근거: AWS Security Agent는 개발 수명주기 전반에서 애플리케이션을 선제적으로 보호하며 침투 테스트 결과에 대해 교정(PR/diff)을 요청할 수 있다. [F29][F30] — https://docs.aws.amazon.com/securityagent/latest/userguide/what-is.html
오답 이유: B) Inspector는 EC2·ECR 이미지·Lambda의 패키지 취약점과 네트워크 노출을 지속 스캔한다 [F28] / C) GuardDuty는 로그 기반 위협 탐지다 [F27] / D) Security Hub CSPM은 보안 표준 대비 구성 점검이다 [F24].
