이 Task는 "무엇이 정상인지 판정하는 장치(상태 확인)를 올바르게 설정·진단하고, 한 가용 영역(AZ)이 사라져도 서비스가 유지되도록 각 계층을 다중 AZ로 구성한다"이다. [F#]는 §5 사실 번호이며, §5에 넣지 못한 보조 사실은 "보조(미인용)"으로 표시하고 공식 페이지를 적었다.

### 2.2.1 ELB·Route 53 상태 확인 구성·문제 해결

**먼저 잡을 구조** — 상태 확인은 "누가(LB 노드/Route 53 헬스 체커) → 무엇을(대상 인스턴스·엔드포인트) → 얼마나 자주·몇 번 연속 → 어떤 응답을 정상으로" 보는지의 4요소다. 장애 시나리오는 이 4요소 중 하나가 어긋난 것이다.

**(1) ELB 대상 그룹 상태 확인 동작**

| 항목 | ALB | NLB | 근거 |
|---|---|---|---|
| 요청을 보내는 주체 | 각 로드 밸런서 노드가 자기 설정으로 대상을 점검 | 분산·합의 방식이라 대상이 설정한 횟수보다 더 많은 점검을 받는다 (보조(미인용): network target-group-health-checks.html) | — |
| 프로토콜 | HTTP·HTTPS (HTTP GET) | HTTP·HTTPS·TCP, 기본 TCP (보조(미인용): 같은 페이지) | — |
| 간격 기본값 | instance·ip 대상 30초 (lambda는 35초) | 30초 (보조(미인용)) | [F1] |
| 비정상 임계값 기본값 | 2 (범위 2~10), 정상 임계값은 5 (보조(미인용): 같은 표) | 2, 정상 임계값 5 (보조(미인용)) | [F2] |
| 성공 응답 코드(Matcher) | 기본 200 (HTTP/1.1·HTTP/2에서 200~499 지정 가능, 보조(미인용)) | 범위 200~599, 기본 200-399 | [F4][F5] |
| 타임아웃 기본값 | instance·ip 대상 5초 (보조(미인용)) | HTTP 6초, TCP·HTTPS 10초 (보조(미인용)) | — |
| 교차 영역 부하 분산 | LB 수준에서 항상 켜짐(끌 수 없음), 대상 그룹 수준에서만 끌 수 있음 | LB 수준 기본 꺼짐, 언제든 켤 수 있음 (켜면 EC2 데이터 전송 요금 적용 — 보조(미인용): network edit-target-group-attributes.html) | [F11][F12] |

- **fail-open.** 대상 그룹의 모든 대상이 모든 활성 AZ에서 동시에 상태 확인에 실패하면 ALB는 "전부 unhealthy니까 아무 데도 안 보낸다"가 아니라 건강 상태와 무관하게 모든 대상으로 요청을 보낸다 [F3]. 상태 확인 설정이 잘못돼 전체가 실패하는 사고에서 서비스가 완전히 끊기지 않는 이유이자, 반대로 "전부 unhealthy인데도 트래픽이 간다"는 현상의 이유다.
- **DNS 장애 조치(영역 수준).** 대상 그룹 상태 요구 사항(최소 정상 대상 수/비율)을 정하면, 한 AZ의 정상 대상이 임계값 아래로 내려갈 때 그 AZ의 LB IP 주소가 DNS 호스트명에서 제거된다 [F13]. 교차 영역이 꺼져 있으면 각 노드가 자기 AZ의 대상에만 분산하므로 AZ별 정상 대상 수가 의미를 가진다. 빈 AZ가 생기면 503이 날 수 있다 (보조(미인용): application edit-target-group-attributes.html "Best practices").
- **등록 취소 지연.** 종료 중인 대상으로 새 요청을 보내지 않고 진행 중 요청이 끝나도록 기다리는 시간이며 기본 300초다 [F10]. ASG 스케일 인 시 인스턴스가 바로 사라지지 않는 이유다.
- **대상 상태값(ALB).** initial → healthy / unhealthy / unused / draining / unavailable. 사유 코드는 Elb.*(LB 쪽), Target.*(대상 쪽)로 나뉜다 (보조(미인용): application target-group-health-checks.html).

**(2) 증상 → 원인 진단표 (ALB)**

| 증상·사유 | 가장 흔한 원인 | 확인·조치 | 근거 |
|---|---|---|---|
| 대상이 계속 unhealthy, 타임아웃 | 대상 보안 그룹이 LB의 상태 확인 포트·프로토콜 트래픽을 막음 / 네트워크 ACL이 상태 확인 포트(인바운드)·임시 포트(아웃바운드)를 막음 | 인스턴스 SG에서 LB SG로부터의 트래픽 허용, ACL 임시 포트 1024-65535 허용 (보조(미인용): load-balancer-troubleshooting.html) | [F6] |
| unhealthy, ResponseCodeMismatch | 애플리케이션이 상태 확인 경로에서 기본 성공 코드 200이 아닌 코드를 반환 (예: 리다이렉트) | 경로를 200을 반환하는 엔드포인트로 바꾸거나 성공 코드를 추가 지정 | [F4] |
| 간헐적 502 Bad gateway | 대상의 keep-alive 시간이 LB 유휴 제한 시간보다 짧아 대상이 먼저 연결을 닫음 | 대상(웹 서버)의 keep-alive를 LB idle timeout보다 길게 | [F7] |
| 503 Service unavailable | 대상 그룹에 등록된 대상이 없음(또는 모두 unused) | 대상 등록·AZ 활성화·리스너 규칙 연결 확인 | [F8] |
| 504 Gateway timeout | LB가 연결은 맺었으나 대상이 idle timeout 안에 응답하지 못함 | 대상 응답 시간·idle timeout 조정, 네트워크 ACL 임시 포트 확인 | [F9] |

**(3) Route 53 상태 확인**

- **유형.** 엔드포인트 점검(HTTP·HTTPS·TCP), 다른 상태 확인을 묶는 계산형(부모 하나가 최대 255개 자식 점검 — 보조(미인용): dns-failover-determining-health-of-endpoints.html), CloudWatch 경보 상태를 쓰는 점검 (보조(미인용): health-checks-creating-values.html).
- **요청 간격·임계값.** 간격은 10초 또는 30초 중 지정한다 [F14]. 실패 임계값을 정하지 않으면 기본 3회이며 허용 범위는 1~10이다 [F15]. 총 장애 조치 시간은 대략 `TTL + (간격 × 임계값)`으로 어림한다 (보조(미인용): AWS News Blog "Route 53 Health Check Improvements" — 예: TTL 60 + 10×5 = 110초).
- **판정.** 여러 위치의 헬스 체커 결과를 합산해 18%를 넘게 healthy라고 보고하면 healthy, 18% 이하면 unhealthy다 [F16]. 일부 리전에서만 안 보이는 상황으로 오탐되지 않게 하려는 값이다 (같은 페이지 설명). HTTP·HTTPS 점검은 4초 안에 TCP 연결, 연결 후 2초 안에 2xx·3xx 응답이 있어야 정상이다 (보조(미인용): 같은 페이지).
- **방화벽.** 엔드포인트의 라우터·방화벽(AWS에서는 보안 그룹·네트워크 ACL)이 Route 53 헬스 체커 IP에서 오는 인바운드를 허용해야 점검이 성공한다 [F17]. AWS 관리형 접두사 목록(com.amazonaws.<region>.route53-healthchecks)을 쓰면 필요한 범위가 자동 추가된다 (보조(미인용): dns-failover-router-firewall-rules.html).
- **장애 조치 라우팅.** 기본·보조 레코드 구성에서 AWS 리소스(별칭 레코드 대상)에는 별도 상태 확인을 만들지 않고 별칭 레코드의 Evaluate Target Health를 Yes로 둔다 (보조(미인용): dns-failover-types.html).

### 2.2.2 내결함성 시스템(다중 AZ 배포) 구성

**원칙: 계층마다 "AZ 하나가 통째로 사라져도 남는 쪽으로 계속 동작하는가"를 점검한다.** 한 계층만 다중 AZ로 만들면 단일 AZ로 남은 계층이 전체의 SPOF가 된다.

| 계층 | 다중 AZ 구성 | 복제/동작 | 장애 조치 | 시험 포인트 | 근거 |
|---|---|---|---|---|---|
| RDS Multi-AZ DB 인스턴스 | 다른 AZ에 동기식 스탠바이 복제본 | 동기 복제 | 보통 60~120초 | 스탠바이는 읽기를 처리하지 않는다 → 읽기 확장은 클러스터·읽기 복제본 | [F18][F19][F21] |
| RDS Multi-AZ DB 클러스터 | 읽기 가능한 스탠바이 2개 | — | 보통 35초 미만 | 장애 조치 지원 + 읽기 처리 | [F20][F22] |
| Aurora | 클러스터 볼륨이 AZ 간 동기 복제(스토리지 노드 6개) | 인스턴스와 별개 | 복제본 있으면 보통 60초 미만·대개 30초 미만 | 복제본을 서로 다른 AZ 2곳 이상에 만들 것을 권고(보조(미인용): Concepts.AuroraHighAvailability.html). 승격 우선순위 0(높음)~15(낮음) | [F23][F24] |
| ElastiCache (Valkey·Redis OSS) | 복제본을 다른 AZ에, Multi-AZ+자동 장애 조치 | 비동기 | 복제본 승격 | 비동기라 소량 손실 가능. Memcached는 복제·장애 조치 없음 (보조(미인용): elasticache/faqs) | [F25] |
| EFS | Regional 파일 시스템 | 여러 AZ에 중복 저장 | — | One Zone은 단일 AZ에 저장되어 AZ 손실 시 데이터 유실 가능 (보조(미인용): 같은 페이지) | [F26] |
| NAT 게이트웨이 | 영역(zonal) 방식은 AZ당 1개 + AZ별 라우팅, 리전(regional) 방식은 AZ를 자동 확장 | — | — | 신규: 리전 NAT 게이트웨이는 워크로드가 있는 AZ로 자동 확장 | [F27] |
| EC2 Auto Scaling | 활성화한 AZ 전체에 용량을 고르게 분산, 불균형이면 재조정 | AZ 재조정 시 새 인스턴스를 먼저 시작한 뒤 종료 (보조(미인용): as-instance-termination.html) | — | AZ 복구 후 다른 AZ의 인스턴스가 종료될 수 있음 | [F30] |
| 트래픽 이동(운영) | ARC 영역 이동·영역 자동 이동 | — | — | ALB(교차 영역 켬/끔 모두)·NLB·ASG·EKS 지원 | [F28][F29] |

- **RDS Multi-AZ 두 종류.** Multi-AZ DB 인스턴스는 동기 스탠바이가 장애 조치만 지원하고 읽기 트래픽은 못 받는다 [F18][F19]. 읽기까지 필요하면 Multi-AZ DB 클러스터(읽기 가능한 스탠바이) 또는 읽기 전용 복제본이다 [F19][F20]. 장애 조치는 DNS(CNAME) 전환 방식이라 애플리케이션이 연결 재시도를 구현해야 한다 (보조(미인용): rds/faqs). 재부팅 시 장애 조치 옵션으로 수동 장애 조치를 강제할 수 있다 (보조(미인용): Concepts.MultiAZ.Failover.html).
- **Aurora는 스토리지가 AZ에 걸쳐 있어** 인스턴스 장애는 복제본 승격으로 짧게 복구되고 [F23][F24], 복제본을 두는 AZ를 분산할수록 AZ 단위 손실에 강하다.
- **ElastiCache 복제는 비동기라서** 장애 조치 시 데이터 일부를 잃을 수 있다 [F25]. 세션 저장소로 쓰는 설계에서는 이 손실을 허용하거나 지속성이 있는 저장소와 병행해야 한다.
- **NAT.** 영역 NAT는 단일 AZ에 있으므로 AZ별로 두고 라우팅을 같은 AZ로 맞춰야 했다. 리전 NAT 게이트웨이는 이 작업을 자동화한다 [F27] (보조(미인용): nat-gateways-regional.html — 영역 NAT는 단일 AZ에서 동작).
- **ARC 영역 이동.** 손상된 AZ에서 트래픽을 빼내는 기능이다. 사람이 시작하는 영역 이동(zonal shift)과 AWS가 자동으로 하는 영역 자동 이동(zonal autoshift)이 있다 [F28]. 지원 리소스는 ASG·EKS·ALB·NLB다 [F29]. ARC의 준비 상태 점검(readiness check) 기능은 2026-04-30부터 신규 고객 접근이 막힌 유지 관리 상태가 되었다 (보조(미인용): aws.amazon.com/about-aws/whats-new/2026/03/aws-service-availability/).
- **ASG의 AZ 균형.** ASG는 활성 AZ에 용량을 고르게 분산하고 [F30], 한 AZ가 복구되면 재조정하며 이때도 새 인스턴스를 먼저 시작한 뒤 오래된 것을 종료해 가용성을 지킨다 (보조(미인용): as-instance-termination.html).

## 3. 시험에서 묻는 방식 (가이드 Skill 문구 기반 추정 — 실제 문항 아님)

아래는 AWS가 공개한 Skill 문구(동사 "Configure and troubleshoot", "Configure"와 예시 "Multi-AZ deployments")에서 추론한 출제 패턴이며, 실제 기출을 아는 것이 아니다.

- 패턴 1 — ALB 오류·unhealthy 원인 진단: "특정 HTTP 오류나 Target.* 사유가 보이는 장애에서 원인과 조치를 고르라." 근거 Skill 문구: "troubleshoot ... ELB ... health checks". 판단 기준: 502=keep-alive 불일치·연결 문제 [F7], 503=등록 대상 없음 [F8], 504=대상 무응답·idle timeout [F9], unhealthy=보안 그룹 [F6]·성공 코드 [F4].
- 패턴 2 — 상태 확인 설정이 서비스 동작에 미치는 영향: "모든 대상이 unhealthy인데 요청이 가는 이유", "AZ가 빠지는 시점", "대상 종료 시 요청 끊김". 근거: "Configure ... health checks". 판단 기준: fail-open [F3], DNS 장애 조치 [F13], 등록 취소 지연 [F10], 교차 영역 설정 [F11][F12].

## 4. 흔한 함정 · 혼동 짝

| 혼동 짝 | 구분 기준 | 근거 |
|---|---|---|
| 502 vs 503 vs 504 | 502=대상이 연결을 먼저 끊음·잘못된 응답, 503=등록된 대상 없음, 504=대상이 시간 내 응답 못함 | [F7][F8][F9] |
| 전부 unhealthy일 때 "트래픽 차단" vs fail-open | ALB는 대상 그룹이 전부 unhealthy이면 모든 대상으로 보낸다 | [F3] |
| ALB vs NLB 성공 코드 기본값 | ALB 기본 200, NLB 기본 200-399(범위 200~599) | [F4][F5] |
| ALB vs NLB 교차 영역 | ALB는 LB 수준 항상 켜짐(대상 그룹 수준에서만 끌 수 있음), NLB는 기본 꺼짐 | [F11][F12] |
| 상태 확인 간격 vs 등록 취소 지연 | 간격 30초(ALB instance·ip 기본)는 점검 주기, 등록 취소 지연 300초는 종료 중 대상의 요청 마무리 시간 | [F1][F10] |
| Route 53 간격 10초 vs 30초 | 둘 중 선택. 실패 임계값 기본 3 | [F14][F15] |
| Route 53 "일부 위치에서만 실패" | 18% 초과가 healthy로 보고하면 healthy | [F16] |
| 상태 확인 실패 원인: 서비스 vs 방화벽 | 서비스는 정상인데 점검만 실패하면 헬스 체커 IP 차단부터 의심 | [F17] |
| RDS Multi-AZ 인스턴스 vs 클러스터 | 인스턴스: 스탠바이 읽기 불가·60~120초, 클러스터: 읽기 가능 스탠바이·35초 미만 | [F19][F20][F21][F22] |
| RDS Multi-AZ vs Aurora 장애 조치 | RDS 인스턴스 60~120초, Aurora 보통 60초 미만 | [F21][F24] |
| ElastiCache 장애 조치와 데이터 손실 | 비동기 복제라 소량 손실 가능 | [F25] |
| EFS Regional vs One Zone | Regional만 여러 AZ에 중복 저장 | [F26] |
| 영역 NAT vs 리전 NAT 게이트웨이 | 리전 NAT는 AZ를 자동 확장 | [F27] |
| ARC 영역 이동 vs 자동 이동 | 수동(사람이 시작) vs AWS가 자동 시작 | [F28] |

문제: 레거시 애플리케이션이 상태 확인 경로 /에서 HTTP 301 리디렉션을 반환한다. ALB 상태 확인 기본 설정을 쓰고 있는데 모든 대상이 Target.ResponseCodeMismatch 사유로 unhealthy다. 가장 적절한 조치는?
- A) 상태 확인 간격을 5초로 줄인다.
- B) 상태 확인 경로를 HTTP 200을 반환하는 엔드포인트로 바꾸거나 성공 코드에 301을 추가로 지정한다.

정답 근거: ALB 상태 확인의 성공 코드는 기본 200이며 필요하면 성공 코드를 추가 지정할 수 있다 [F4]. — https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-troubleshooting.html

### Q2 (Skill 2.2.1 · advanced)
문제: ALB 뒤 웹 서버(keep-alive 5초)에서 가끔 502가 발생한다. ALB 유휴 제한 시간은 기본값이다. 로그에는 대상이 TCP FIN으로 연결을 먼저 닫은 흔적이 있다. 무엇을 조정해야 하는가?
- A) 대상의 keep-alive 지속 시간을 ALB 유휴 제한 시간보다 길게 설정한다.
- B) 대상 그룹을 NLB로 교체한다.
- C) 상태 확인 비정상 임계값을 10으로 올린다.
- D) 서브넷에 NAT 게이트웨이를 추가한다.

### Q3 (Skill 2.2.1 · intermediate)
문제: EC2 웹 서버에 Route 53 HTTP 상태 확인(10초 간격)을 만들었다. 인터넷에서 사이트에 정상 접속되는데 상태 확인은 계속 unhealthy다. 인스턴스 보안 그룹은 사용자 IP 대역의 80 포트만 허용한다. 가장 적절한 조치는?
- A) 실패 임계값을 10으로 올린다.
- B) Route 53 헬스 체커 IP 범위(또는 route53-healthchecks 관리형 접두사 목록)에서 오는 인바운드 트래픽을 보안 그룹에 허용한다.
- C) 요청 간격을 30초로 바꾼다.
- D) 상태 확인 유형을 TCP로 바꾼다.
정답: B
정답 근거: 상태 확인이 성공하려면 라우터와 방화벽 규칙이 Route 53 헬스 체커 IP 주소에서 오는 인바운드 트래픽을 허용해야 한다 [F17]. — https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/dns-failover-router-firewall-rules.html
오답 이유: A) 임계값(기본 3 [F15])을 올려도 차단은 해소되지 않는다. C) 간격은 점검 빈도일 뿐이다 [F14]. D) TCP도 같은 방화벽에 막힌다.

### Q4 (Skill 2.2.2 · intermediate)
문제: 운영 DB가 AZ 장애에도 35초 이내에 복구되어야 하고, 대기(standby) 인스턴스에서 읽기 쿼리도 처리하고 싶다. 가장 적절한 RDS 구성은?
- A) Multi-AZ DB 인스턴스 배포
- B) Multi-AZ DB 클러스터 배포
- C) 같은 AZ에 읽기 전용 복제본 추가
- D) Single-AZ + 자동 백업
정답: B
정답 근거: Multi-AZ DB 클러스터의 스탠바이는 장애 조치와 읽기를 모두 처리하고 [F20], 장애 조치 시간은 보통 35초 미만이다 [F22]. — https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZ.html
오답 이유: A) 인스턴스 배포의 스탠바이는 읽기를 못 받고 [F19] 장애 조치가 보통 60~120초다 [F21]. C) 읽기 복제본은 자동 장애 조치가 아니다. D) 가용성 구성이 아니다.

### Q5 (Skill 2.2.2 · intermediate)
문제: 3개 AZ의 프라이빗 서브넷이 하나의 NAT 게이트웨이(AZ-a)를 거쳐 인터넷으로 나간다. AZ-a 장애 시 다른 AZ도 아웃바운드가 끊기는 문제를 AZ마다 NAT와 라우팅을 따로 관리하지 않고 해결하고 싶다. 가장 적절한 방법은?
- A) NAT 게이트웨이에 탄력적 IP를 추가한다.
- B) 리전(regional) 모드 NAT 게이트웨이를 만들어 프라이빗 서브넷이 쓰게 한다.
- C) 인터넷 게이트웨이를 AZ마다 만든다.
- D) 프라이빗 서브넷을 하나의 AZ로 합친다.
정답: B
정답 근거: 리전 NAT 게이트웨이는 워크로드가 있는 AZ에 따라 자동으로 여러 AZ로 확장된다 [F27]. — https://docs.aws.amazon.com/vpc/latest/userguide/nat-gateways-regional.html
오답 이유: A) EIP를 더해도 AZ 단위 SPOF가 해소되지 않는다. C) 인터넷 게이트웨이는 VPC 단위이며 NAT를 대체하지 않는다. D) 단일 AZ로 합치면 그 AZ 장애 시 전체가 중단되어 가용성이 오히려 떨어진다.
