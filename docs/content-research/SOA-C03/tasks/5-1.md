## 2. 핵심 개념 (한국어)

### 5.1.1 VPC 구성 — 서브넷·라우팅 테이블·NACL·SG·NAT·IGW·송신 전용 IGW
**큰 그림.** VPC의 트래픽 길은 "라우팅 테이블이 어디로 보낼지 정한다 → 게이트웨이(IGW·NAT·EIGW)가 변환·전달한다 → 서브넷 경계의 NACL과 ENI 경계의 SG가 통과 여부를 정한다" 순서로 좁혀 보면 된다. 이 순서는 문제 해결(Task 5.3)에서도 그대로 쓰이므로, 구성 지식은 곧 진단 순서다.

- **서브넷 주소.** 서브넷 CIDR의 처음 4개 IP와 마지막 1개 IP는 EC2 같은 리소스에 줄 수 없다 → /24는 256−5=251개 [F1].
- **퍼블릭/프라이빗은 라우팅의 결과.** 서브넷에 연결된 라우팅 테이블에 IGW 경로가 있으면 퍼블릭, 없으면 프라이빗이다. IPv4로 인터넷과 통신하려면 인스턴스에 공인 IPv4 또는 EIP도 있어야 하고, IGW가 인스턴스 대신 1:1 NAT를 해 준다. IGW는 가용성·대역폭 제약을 만들지 않으며 IGW 자체 요금은 없다(EC2 데이터 전송 요금은 별개) [S:igw].
- **경로 선택.** 가장 구체적인 경로(최장 접두사 일치)가 이기고, 같은 길이일 때는 정적 경로 > 접두사 목록 경로 > 전파 경로(DX BGP·VPN) 순으로 우선한다 [S:route-priority].

**SG vs NACL — 응답 트래픽 처리가 핵심 차이**
| 구분 | 보안 그룹(SG) | 네트워크 ACL(NACL) |
|---|---|---|
| 적용 단위 | 인스턴스(ENI) 수준 | 서브넷 수준 [S:vpc-security] |
| 규칙 종류 | 허용 규칙만(거부 규칙 불가) [S:sg-rules] | 허용 + 거부 [S:vpc-security] |
| 평가 방식 | 모든 규칙을 평가한 뒤 허용 여부 결정 [S:vpc-security] | 낮은 번호부터 평가, 일치하는 순간 적용 [S:nacl-rules] |
| 응답(반환) 트래픽 | 자동 허용 — 상태 저장 [F2] | 응답을 허용하는 규칙이 별도로 있어야 함 — 상태 비저장 [F3] |
| 새로 만들었을 때 기본값 | 인바운드 규칙 없음(전부 차단), 아웃바운드 전체 허용 [S:sg-rules] | 기본 NACL은 전부 허용 [S:nacl-default]; 사용자 지정 NACL은 별표(*) 규칙 때문에 일치 규칙이 없으면 거부 [S:nacl-custom] |

- **이페머럴 포트.** 응답이 돌아가는 포트는 요청을 보낸 클라이언트가 고른다. 범위는 OS마다 다르다(Linux 32768–61000, Windows Server 2008 이상 49152–65535, ELB·NAT 게이트웨이·Lambda 1024–65535). 실무에서는 1024–65535를 열고, 막을 포트는 더 낮은 규칙 번호의 deny로 앞에 둔다 [S:nacl-custom]. 한 지점만 열고 다른 한 방향을 잊는 것이 NACL의 전형적 실수다 [F3].
- **NAT 게이트웨이.** 프라이빗 서브넷의 인스턴스가 밖으로 나가기만 하게 해 준다(밖에서 먼저 연결 시작 불가). 연결 유형은 퍼블릭(기본, 퍼블릭 서브넷에 두고 EIP 필수)과 프라이빗(EIP 불가, 다른 VPC·온프레미스 방향)이다 [S:nat-overview]. 특정 AZ에 만들어지고 그 AZ 안에서 이중화된다. 그래서 AZ를 넘어 NAT 하나를 공유하면 그 AZ 장애 때 다른 AZ도 인터넷을 잃는다 → AZ마다 NAT를 두고 같은 AZ 것을 쓰도록 라우팅한다 [F4]. 보안 그룹은 붙일 수 없고(인스턴스 SG와 서브넷 NACL로 제어) [F5], 5 Gbps로 시작해 100 Gbps까지 자동 확장되며 목적지 1곳당 IP 1개가 55,000 동시 연결을 지원한다 [S:nat-basics].
- **리전형(Regional) NAT 게이트웨이 — 신규.** 가용 영역마다 NAT를 따로 만들지 않고 하나의 NAT가 워크로드가 있는 AZ로 자동 확장·축소된다. 퍼블릭 서브넷이 필요 없고 자동/수동 모드가 있으며, 새 AZ로 확장되기까지 최대 60분 걸릴 수 있고 프라이빗 NAT는 지원하지 않는다 [F7][S:nat-regional]. 기존 학습문서(soa-t5-1·soa-t2-2)는 'NAT는 단일 AZ 리소스'라고만 적는다 → 영역형(zonal) NAT에 한해 맞는 설명이다 [98-C2]. 출제 가능성은 [99-G07].
- **송신 전용 인터넷 게이트웨이(EIGW).** IPv6 주소는 전역 고유라 기본적으로 공인이므로, 인스턴스가 밖으로만 나가고 밖에서 먼저 연결하지 못하게 하려면 EIGW를 쓰고 라우팅 테이블에 `::/0 → EIGW`를 넣는다. EIGW는 상태 저장이며 SG를 붙일 수 없어 NACL로 서브넷을 통제한다 [F6][S:eigw]. NAT 게이트웨이는 DNS64+NAT64로 IPv6→IPv4 변환도 한다 [S:nat-basics].

**결정 규칙**
| 상황 | 선택 | 근거 |
|---|---|---|
| 퍼블릭 서브넷 IPv4 인스턴스가 인터넷과 양방향 통신 | IGW 경로 + 공인 IPv4/EIP | [S:igw] |
| 프라이빗 서브넷 IPv4 인스턴스가 인터넷으로 나가기만 | 퍼블릭 NAT(AZ별) 또는 리전형 NAT | [F4][F7] |
| IPv6 인스턴스가 나가기만 | EIGW(`::/0` 경로) | [F6][S:eigw] |
| 특정 IP를 서브넷 전체에서 차단 | NACL deny 규칙(낮은 번호) — SG는 거부 불가 | [S:sg-rules][S:vpc-security] |
| NAT 게이트웨이 트래픽을 통제 | 서브넷 NACL + 클라이언트 인스턴스 SG | [F5][S:nat-basics] |

**운영 점검 순서(문제 해결의 전제).** ① 라우팅 테이블(대상·타깃, 최장 접두사) → ② IGW/NAT 위치(NAT는 퍼블릭 서브넷, 프라이빗 서브넷 경로가 NAT를 가리키는지) → ③ NACL 양방향·이페머럴 → ④ SG → ⑤ DNS 속성(5.2.1). 서브넷 IP 고갈은 예약 5개를 빼고 센다 [F1].

**가이드 문구 밖이지만 in-scope 서비스 목록에 있는 것.** Amazon VPC IPAM(IP 계획·추적·모니터링)과 Elastic IP addresses는 in-scope 목록에 있으나 Skill 문구에는 이름이 없다 [S:guide-scope][99-G03]. EIP는 사용 중이든 유휴이든 요금이 있다 [S:eip][F29].

### 5.1.2 프라이빗 네트워킹 연결 — VPC 엔드포인트·PrivateLink·VPC 피어링 (+ VPN)
**수단 선택 매트릭스**
| 목적 | 1순위 수단 | 핵심 제약·주의 | 근거 |
|---|---|---|---|
| VPC 안에서 S3·DynamoDB에 IGW/NAT 없이 접근 | 게이트웨이 엔드포인트 | 라우팅 테이블에 접두사 목록 경로가 자동 추가, 추가 요금 없음 | [F8][F9] |
| 온프레미스·다른 리전 피어링 VPC에서 S3에 프라이빗 접근 | S3 인터페이스 엔드포인트 | 게이트웨이 엔드포인트는 이 경로를 허용하지 않음 | [F10] |
| 그 밖의 AWS 서비스 API를 VPC 안에서 | 인터페이스 엔드포인트 | 서브넷에 ENI+SG, 프라이빗 DNS는 두 DNS 속성 필요, 시간·GB 요금 | [F11][F28] |
| 다른 VPC·계정의 서비스 1개를 소비자에게만 단방향 노출 | AWS PrivateLink(엔드포인트 서비스) | 제공자 NLB(또는 GWLB), VPC CIDR이 겹쳐도 됨 | [F12] |
| 두 VPC 전체 대역끼리 사설 통신 | VPC 피어링 | 비전이, CIDR 중복 불가, 양쪽 라우팅 필요 | [F13][F14] |
| VPC 다수·온프레미스를 한 허브로 | Transit Gateway | 첨부 시간당+처리 GB당 요금 | [S:tgw][S:tgw-pricing] |
| 온프레미스↔VPC IPsec(인터넷 경유) | Site-to-Site VPN | 터널 2개(서로 다른 AZ), 표준 터널 1.25 Gbps | [F15][F16] |
| 개별 사용자 원격 접속 | AWS Client VPN | 인증 3종, ACM 서버 인증서 | [S:cvpn-auth][S:cvpn-rules] |

- **게이트웨이 엔드포인트.** 대상은 S3·DynamoDB뿐이다. 엔드포인트를 만들면 선택한 라우팅 테이블에 `대상=서비스 접두사 목록 → 타깃=엔드포인트` 경로가 자동 생성되고, 그 라우팅 테이블을 쓰는 서브넷은 자동으로 이용한다 [F8][S:gw-endpoints]. 같은 서비스의 엔드포인트 경로는 라우팅 테이블당 1개이며, 다른 리전 서비스는 접두사 목록이 리전 단위라 IGW로 간다 [S:gw-endpoints]. PrivateLink를 쓰지 않는 방식이고, 인스턴스의 SG·NACL은 서비스 접두사 목록(또는 서비스 CIDR)으로 나가는 트래픽을 허용해야 한다 [S:gw-endpoints]. 온프레미스·타 리전 피어링·전송 게이트웨이를 거친 접근은 불가하여 인터페이스 엔드포인트가 필요하다 [F10][S:gw-s3]. S3와 DynamoDB는 두 방식 모두 지원한다 [S:gw-endpoints].
- **인터페이스 엔드포인트.** 서브넷에 ENI(사설 IP)를 만들고 SG로 접근을 통제한다. 프라이빗 DNS 이름을 쓰려면 VPC의 DNS 호스트 이름과 DNS 확인을 모두 켜야 한다 [F11]; 켜면 SDK가 쓰는 공용 서비스 엔드포인트 이름이 VPC 엔드포인트로 해석된다 [S:if-endpoints]. 엔드포인트 정책의 기본값은 전체 접근 허용이며 [S:endpoint-policy], IAM·버킷 정책을 대체하지 않는 추가 경계다 [S:iam-vpce]. 요금은 프로비저닝된 AZ별 시간당 + 처리 GB당이다 [F28].
- **AWS PrivateLink.** 제공자는 NLB(또는 GWLB) 뒤에 서비스를 올려 엔드포인트 서비스로 노출하고, 소비자가 자기 VPC에 인터페이스 엔드포인트를 만든다 — 연결은 소비자 쪽에서만 시작된다. 소비자·제공자 VPC의 IP 대역이 겹쳐도 된다 [F12][S:privatelink-wp]. 그래서 CIDR이 겹치는 VPC 사이에서 서비스 하나만 공유할 때가 PrivateLink의 자리다.
- **VPC 피어링.** 1:1 관계이며 전이 라우팅을 지원하지 않는다(A–B, A–C가 있어도 B–C 불가, B–C는 별도 피어링) [F13]. 두 VPC의 CIDR이 겹치면 피어링할 수 없다 [F14]. 피어링을 만든 뒤 양쪽 서브넷의 라우팅 테이블에 상대 CIDR → 피어링 ID 경로를 넣어야 한다 [S:peering-routes]. 기본 설정에서는 피어 인스턴스의 공용 DNS 이름이 공인 IP로 해석되고, DNS 해석 옵션을 켜야 사설 IP로 해석된다 [S:peering-dns]. 피어 VPC의 IGW·NAT·VPN·DX·게이트웨이 엔드포인트를 대신 쓰는 에지-투-에지 라우팅은 불가하고 피어 VPC의 Amazon DNS 서버에 질의할 수도 없다 [S:peering-basics]. VPC당 활성 피어링은 기본 50개(최대 125개까지 증설) [S:peering-quota].
- **Transit Gateway(보조).** 첨부 대상은 VPC·VPN·DX 게이트웨이·타 TGW 피어링·Connect·Client VPN 등이고, 각 첨부는 정확히 하나의 TGW 라우팅 테이블에 연결된다. VPC 첨부는 VPC 쪽 라우팅 테이블에 TGW로 향하는 정적 경로가 필요하다 [S:tgw]. 요금은 첨부당 시간 + 처리된 트래픽 [S:tgw-pricing]. 가이드는 '하이브리드·다중 VPC 네트워킹 설계'를 범위 밖 직무로 둔다 → 구성·운영 수준에서만 묻는 것으로 해석 [S:guide][99-G04].
- **Site-to-Site VPN.** 연결 하나는 터널 2개이고 각 터널은 서로 다른 AZ에서 종단된다. AWS 쪽 장치 장애 시 두 번째 터널로 자동 전환되므로 고객 게이트웨이 장치는 두 터널을 모두 구성해야 한다 [F15][S:vpn-resilience]. 표준 터널은 최대 1.25 Gbps, Large Bandwidth Tunnel은 최대 5 Gbps(Transit Gateway·Cloud WAN 첨부 한정) [F16][S:vpn-tunnels][98-D2]; 대역폭을 더 키우려면 TGW에서 ECMP로 터널을 묶되 동적(BGP) 라우팅이어야 한다 [S:vpn-limits]. 고객 게이트웨이 장치가 BGP를 지원하면 동적 라우팅을 쓰며 BGP는 활성도 검사로 장애 조치를 돕는다 [S:vpn-routing]. 터널 엔드포인트의 공인 IPv4도 요금이 있다 [S:vpc-pricing].
- **AWS Client VPN.** 인증은 Active Directory, 상호(인증서) 인증, SAML 기반 SSO 중 선택·조합하고, 어느 방식이든 서버 인증서를 ACM에 프로비저닝해야 한다 [S:cvpn-auth]. 네트워크마다 권한 부여 규칙으로 접근을 허용한다 [S:cvpn-rules]. 요금은 엔드포인트 연결(association)과 VPN 연결을 시간당으로 부과한다 [S:cvpn-whatis].
- **Direct Connect.** in-scope·out-of-scope 어느 목록에도 없다 [S:guide-scope][S:guide-scope-out][99-G01]. 기본적으로 전송 암호화가 없고, 암호화는 MACsec 또는 DX 위의 Site-to-Site VPN으로 한다 [S:dx-encryption].

### 5.1.3 네트워크 보호 서비스 감사 — DNS Firewall·WAF·Shield·Network Firewall
**'감사'의 범위(가이드 문구 기반 추정).** 가이드는 'Audit ... in a single account'라고만 쓴다. 공식 문서로 확인되는 점검 수단은 ① 구성 상태(규칙 그룹 연결·기본 작업·로깅 대상) ② 로깅 활성 여부와 로그 확인 ③ AWS Config 관리형 규칙·Security Hub CSPM 제어로 하는 지속 점검이다. 여러 계정을 중앙 관리하는 AWS Firewall Manager는 in-scope 서비스 목록에 없다 [S:guide-scope][99-G02].

| 서비스 | 막는 대상(계층) | 감사 포인트 | 근거 |
|---|---|---|---|
| Route 53 Resolver DNS Firewall | VPC에서 나가는 DNS 질의(도메인 기준) | 규칙 그룹이 VPC에 연결됐는지, 규칙 작업(허용·경고·차단), 장애 시 모드(기본 fail-closed), 로그(Resolver 쿼리 로그) | [F17][F18][F19] |
| AWS WAF | HTTP(S) 요청(L7) | 웹 ACL(새 콘솔 표기 protection pack)이 리소스에 연결됐는지, 기본 작업, 규칙 작업, 로깅 대상·이름, Config 규칙 | [F20][F21] |
| AWS Shield | DDoS (Standard=기본 보호, Advanced=구독형) | Advanced 구독·자동 갱신·SRT 접근 역할 | [F22][F23] |
| AWS Network Firewall | VPC 경계 트래픽(상태 저장·비저장 규칙) | 방화벽 서브넷·경로, 정책의 규칙 그룹, 로깅(stateful 엔진만), Config 규칙 | [F24][F25] |

- **DNS Firewall.** SG·NACL은 Route 53 Resolver로 가는 DNS 질의를 막지 못한다 — 이 틈을 메우는 것이 DNS Firewall이다 [F17]. 규칙 그룹(재사용 가능한 규칙 집합)을 여러 VPC에 연결하고, 규칙 하나는 도메인 목록 1개와 작업(허용·차단·경고)을 가진다 [F18]. 차단 응답은 NODATA·NXDOMAIN·OVERRIDE 중 선택, 새 차단 규칙은 Alert로 먼저 시험한다 [S:dnsfw-actions]. 도메인 목록은 직접 관리하거나 AWS 관리형(무료)을 쓴다 [S:dnsfw-managed]; DNS Firewall Advanced는 DGA·DNS 터널링 같은 위협을 탐지한다 [S:dnsfw-adv]. 규칙 그룹은 리전 리소스이며 규칙·연결의 우선순위 값이 낮은 쪽이 먼저 평가된다 [S:dnsfw-overview]. 장애 시 기본은 fail-closed(질의 차단·SERVFAIL, 보안 우선)이고 fail-open을 켜면 가용성 우선이다 [F19][S:dnsfw-config]. 차단·경고 기록은 Resolver 쿼리 로그에 남는다 [S:dnsfw-actions][5-2:F20]. 규칙 그룹은 AWS RAM으로 계정 간 공유하고 [S:dnsfw-sharing], Firewall Manager로 조직 전체를 중앙 관리할 수 있다 [S:dnsfw].
- **AWS WAF.** 웹 ACL이 규칙·규칙 그룹·기본 작업(규칙이 걸러내지 않은 요청을 허용/차단)을 담고 리소스에 연결된다 [S:waf-works]. 보호 대상은 CloudFront, API Gateway REST API, ALB, AppSync, Cognito 사용자 풀, App Runner, Verified Access 등이다 [S:waf-overview]. 새 규칙은 Count로 먼저 관찰한다 [S:waf-overview]. 새 콘솔은 웹 ACL을 'protection pack (web ACL)'로 부르지만 표준 콘솔·API에서는 여전히 웹 ACL이다 [S:waf-works][99-G06]. 로깅은 CloudWatch Logs 로그 그룹·S3 버킷·Firehose 중 하나로 보내고 [S:waf-logging], 대상 이름은 `aws-waf-logs-`로 시작해야 하며 로그 그룹은 웹 ACL과 같은 리전·계정에 둔다 [F20][S:waf-cwlogs]. CloudFront에 연결한 글로벌 웹 ACL의 로그 그룹은 us-east-1이어야 한다 [S:waf-kc]. 감사는 Config 관리형 규칙 wafv2-logging-enabled [F21] — Security Hub CSPM 제어 WAF.11이 같은 규칙을 쓴다 [S:sechub-waf]. 기본 요금에는 최대 1,500 WCU가 포함되고 웹 ACL 최대 용량은 5,000 WCU이다 [S:waf-wcu].
- **AWS Shield.** Standard는 모든 고객에게 자동 포함되며 추가 요금이 없다 [F22]. Advanced는 월 $3,000(조직당)에 데이터 전송 사용료가 더해지고 1년 약정이며 EC2·ELB·CloudFront·Global Accelerator·Route 53 보호를 확장한다; SRT에 연락하려면 Business 이상 Support가 필요하다 [F23][S:shield-pricing]. 감사는 Config 규칙 shield-advanced-enabled-autorenew(Advanced 활성+자동 갱신 — API 엔드포인트가 us-east-1에만 있어 그 리전에서 실행)와 shield-drt-access(SRT 접근 역할) [S:cfg-shield-renew][S:cfg-shield-drt].
- **AWS Network Firewall.** 상태 저장·관리형 네트워크 방화벽이자 침입 탐지·방지 서비스이며 Suricata 호환 규칙을 쓴다. firewall(보호할 VPC와 AZ별 전용 방화벽 서브넷), firewall policy, rule group(stateless/stateful)으로 구성되고 VPC 라우팅 테이블로 트래픽을 방화벽 엔드포인트로 보낸다 [S:nfw-overview]. 로깅은 stateful 엔진으로 넘긴 트래픽에만 가능하고 로그 유형은 flow·alert·TLS, 대상은 S3·CloudWatch Logs·Firehose이다 [F24][S:nfw-logging]. 감사는 Config 규칙 netfw-logging-enabled [F25]와 Security Hub CSPM NetworkFirewall.2 [S:sechub-nfw].

**감사 체크리스트(정리)**
| 서비스 | 확인 항목 | 도구 |
|---|---|---|
| DNS Firewall | 규칙 그룹↔VPC 연결, 규칙 작업, 실패 모드 | 콘솔·API, Resolver 쿼리 로그 |
| WAF | 웹 ACL↔리소스 연결, 기본 작업, 로깅 켜짐·대상 이름 | Config wafv2-logging-enabled, 로그 |
| Shield | Advanced 구독·자동 갱신·SRT 접근 | Config shield-advanced-enabled-autorenew, shield-drt-access |
| Network Firewall | 로깅 켜짐, 방화벽 경로·서브넷 | Config netfw-logging-enabled, Security Hub NetworkFirewall.2 |

### 5.1.4 네트워크 아키텍처 비용 최적화
**비용 요소와 줄이는 법**
| 요소 | 과금 방식 | 줄이는 방법 | 근거 |
|---|---|---|---|
| NAT 게이트웨이 | 켜져 있는 시간당 + 처리 GB당(표준 전송 요금 별도) | 엔드포인트가 있는 서비스는 우회, 같은 AZ NAT 사용, 불필요한 NAT 삭제 | [F26][F27][S:nat-pricing] |
| 게이트웨이 엔드포인트 | 추가 요금 없음 | S3·DynamoDB 트래픽을 NAT에서 분리 | [F9][F27] |
| 인터페이스 엔드포인트 | 프로비저닝된 AZ별 시간당 + 처리 GB당 | 필요한 AZ·서비스에만, 트래픽이 큰 서비스 위주로 | [F28] |
| 공인 IPv4 | 사용 중·유휴 모두 시간당 부과 | 불필요한 공인 IP·유휴 EIP 제거, IPv6(+EIGW) 활용 | [F29][F6] |
| AZ 간 데이터 전송 | 같은 AZ 안은 무료, AZ를 넘으면 과금 | AZ 인식 라우팅(같은 AZ NAT·엔드포인트·대상) | [F30][S:cur-dt] |
| VPC 피어링 | AZ를 넘는 전송은 GB당 $0.01(in·out 각각) | 같은 AZ 유지 | [S:vpc-pricing] |
| Transit Gateway | 첨부 시간당 + 처리 GB당 | 필요한 첨부만 | [S:tgw-pricing] |

- **엔드포인트 vs NAT.** NAT 요금표에 직접 적힌 완화책: AZ를 넘는 트래픽이 많으면 NAT와 같은 AZ에 리소스를 두거나 AZ마다 NAT를 만들고, 트래픽 대부분이 인터페이스·게이트웨이 엔드포인트를 지원하는 AWS 서비스로 가면 엔드포인트를 만든다 [F27][S:nat-pricing]. S3·DynamoDB는 게이트웨이 엔드포인트가 요금 없이 NAT 데이터 처리 요금을 없앤다 [F9][S:vpc-pricing]. 인터페이스 엔드포인트는 AZ·서비스 수에 비례한 시간당 요금이 생기므로 NAT 처리량과 비교해 판단한다 [F28][F26].
- **공인 IPv4 요금.** 공인 IPv4는 연결 여부와 무관하게 시간당 요금이 붙는다(VPC 요금 페이지: 사용 중 $0.005, 유휴 $0.005). Site-to-Site VPN 터널·Global Accelerator 엔드포인트도 사용 중 공인 IPv4로 과금된다. BYOIP는 부과되지 않는다 [F29][S:vpc-pricing].
- **데이터 전송 계층.** 같은 AZ 안 통신은 무료이고 AZ를 넘으면 과금된다 [F30]. 청구서·CUR의 사용 유형으로는 Region-DataTransfer-Regional-Bytes가 AZ 간 전송, Region-DataTransfer-Out-Bytes가 인터넷 아웃바운드이다 [S:cur-dt].
- **비용 추적 도구.** Cost Explorer는 서비스·AWS 리전·사용 유형(usage type) 등으로 필터·그룹화한다 [S:cost-explorer]. CUR는 공인 IPv4 사용량을 시간·일·월 단위로 집계한다 [S:vpc-pricing]. IPAM의 Public IP Insights(무료 티어)로 공인 IPv4 사용을 모니터링해 쓰지 않는 주소를 반납한다 [S:vpc-pricing].
- **깊이 한계.** 가이드는 '비용·총소유비용(TCO) 분석'을 범위 밖 직무로 명시한다 → 5.1.4는 알려진 절감 패턴(엔드포인트·AZ 일치·공인 IP 감축)을 적용하는 수준으로 해석 [S:guide][99-G05].

## 3. 시험에서 묻는 방식 (가이드 Skill 문구 기반 추정 — 실제 문항 아님)
> AWS가 공개한 Skill의 동사·예시 목록에서 추론한 출제 패턴이다. 실제 기출을 안다는 뜻이 아니다.

1. **방화벽 계층 판별형 (Skill 5.1.1).** 패턴: '연결이 안 된다' 시나리오에서 SG·NACL·라우팅·NAT 중 어느 계층을 고칠지 고른다. 근거 문구: 'Configure a VPC (for example, ... network ACLs, security groups, NAT gateways ...)'. 판단 기준: SG는 상태 저장(응답 자동 허용) [F2], NACL은 상태 비저장(응답 규칙·이페머럴 필요) [F3], NAT는 AZ 단위·SG 불가 [F4][F5], IPv6 아웃바운드는 EIGW [F6].
2. **프라이빗 연결 수단 선택형 (Skill 5.1.2).** 패턴: 대상 서비스·접근 주체·CIDR 겹침·전이성 조건을 주고 엔드포인트/PrivateLink/피어링 중 고른다. 근거 문구: 'Configure private networking connectivity (for example, VPC endpoints, AWS PrivateLink, VPC peering)'. 판단 기준: 게이트웨이 엔드포인트=S3·DynamoDB·무료·온프레미스 불가 [F8][F9][F10], 프라이빗 DNS=두 DNS 속성 [F11], CIDR 겹침+서비스 단방향=PrivateLink [F12], 비전이·CIDR 중복 불가=피어링 [F13][F14].
3. **감사·점검형 (Skill 5.1.3).** 패턴: '모든 웹 ACL/방화벽에 로깅이 켜져 있는지 지속 점검' 또는 '장애 시 DNS 동작을 가용성 우선으로' 같은 점검·설정 시나리오. 근거 문구: 'Audit AWS network protection services ... in a single account'. 판단 기준: Config 관리형 규칙 [F21][F25], 실패 모드 [F19], SG로는 DNS를 막을 수 없음 [F17], 로그 대상 이름 규칙 [F20].
4. **비용 절감형 (Skill 5.1.4).** 패턴: 월 청구 증가 원인(NAT 처리 요금·AZ 간 전송·공인 IPv4)을 보고 최소 비용 변경을 고른다. 근거 문구: 'Optimize the cost of network architectures.' 판단 기준: 게이트웨이 엔드포인트 무료 [F9][F27], AZ별 NAT+같은 AZ 라우팅 [F4][F30], 인터페이스 엔드포인트는 유료 [F28], 공인 IPv4 과금 [F29].

## 4. 흔한 함정 · 혼동 짝
| 혼동 짝 | 구분 기준 | 근거 |
|---|---|---|
| 보안 그룹 ↔ 네트워크 ACL | SG: ENI 단위·허용만·응답 자동 허용 / NACL: 서브넷 단위·허용+거부·번호 순·응답 규칙 필요 | [F2][F3][S:vpc-security] |
| 게이트웨이 ↔ 인터페이스 엔드포인트 | 게이트웨이=S3·DynamoDB·라우팅·무료·온프레미스 불가 / 인터페이스=ENI+SG·시간+GB 과금·온프레미스 가능 | [F8][F9][F10][F28] |
| 게이트웨이 엔드포인트 ↔ PrivateLink | 게이트웨이 엔드포인트는 PrivateLink를 쓰지 않는다(인터페이스 엔드포인트가 PrivateLink 기반) | [S:gw-endpoints] |
| 피어링 ↔ Transit Gateway ↔ PrivateLink | 피어링=1:1 비전이·CIDR 중복 불가 / TGW=허브 / PrivateLink=서비스 단방향·CIDR 겹침 허용 | [F13][F14][F12] |
| 퍼블릭 NAT ↔ 프라이빗 NAT | 퍼블릭=퍼블릭 서브넷+EIP+IGW / 프라이빗=EIP 불가·IGW로 보내면 폐기 | [S:nat-overview] |
| 영역형 NAT ↔ 리전형 NAT | 영역형=AZ마다 생성·라우팅 분리 / 리전형=하나가 AZ 자동 확장·퍼블릭 서브넷 불필요·프라이빗 NAT 미지원 | [F4][F7] |

| WAF 로그 대상 이름 | 반드시 aws-waf-logs- 로 시작 | [F20] |
| Network Firewall 로깅 범위 | stateful 엔진에 넘긴 트래픽만 로그 대상 | [F24] |
| 공인 IPv4 요금 | 사용 중·유휴 모두 시간당 과금(EIP 포함) | [F29][S:eip] |

## 6. 자가 점검 문항 후보 (3~5) — 후보일 뿐, 검증 아님
### Q1 (Skill 5.1.1 · intermediate)
문제: 퍼블릭 서브넷의 EC2 웹 서버(HTTPS 443)에 인터넷 사용자가 접속하지 못한다. 보안 그룹은 인바운드 TCP 443(0.0.0.0/0)을 허용하고 아웃바운드는 기본값이다. 서브넷에 연결된 사용자 지정 네트워크 ACL에는 인바운드 규칙 100(TCP 443 허용)만 있고 아웃바운드에는 허용 규칙이 하나도 없다. 요청은 서버에 도착하지만 응답이 클라이언트에 도달하지 않는다. 가장 적절한 조치는?
- A) 보안 그룹에 아웃바운드 TCP 1024-65535 허용 규칙을 추가한다.
- B) 네트워크 ACL의 아웃바운드에 클라이언트의 이페머럴 포트 범위(예: TCP 1024-65535)로 나가는 허용 규칙을 추가한다.
- C) 네트워크 ACL의 인바운드에 TCP 1024-65535 허용 규칙을 추가한다.
- D) 프라이빗 서브넷 라우팅 테이블에 0.0.0.0/0 → NAT 게이트웨이 경로를 추가한다.
정답: B
정답 근거: NACL은 상태 비저장이라 응답 트래픽을 허용하는 규칙이 따로 필요하다 [F3]; 보안 그룹은 상태 저장이라 응답이 아웃바운드 규칙과 무관하게 나간다 [F2] — https://docs.aws.amazon.com/vpc/latest/userguide/custom-network-acl.html
오답 이유: A) 보안 그룹은 이미 응답을 자동 허용하므로 원인이 아니다 [F2]. C) 서버의 응답은 아웃바운드 방향이다. 인바운드에 이페머럴을 열어도 서버 응답은 나가지 못한다. D) 문제의 서브넷은 퍼블릭이고 증상은 응답 차단이므로 NAT 경로와 무관하다.

- A) 게이트웨이 엔드포인트 하나를 만들고 온프레미스 트래픽도 그 엔드포인트로 보낸다.

오답 이유: A) 작업 변경은 규칙에 일치한 질의의 처리 방식을 바꿀 뿐 장애 시 모드를 바꾸지 않는다 [F18][F19]. C·D) 보안 그룹·NACL은 Resolver로 가는 DNS 질의를 걸러내는 계층이 아니므로 해법이 아니다 [F17].

### Q5 (Skill 5.1.4 · intermediate)
문제: 월 청구서에서 NAT 게이트웨이 비용이 크게 늘었다. 분석 결과 NAT 트래픽의 대부분은 같은 리전의 S3·DynamoDB 호출이고, AZ-b의 인스턴스들이 AZ-a의 NAT 게이트웨이를 경유해 AZ 간 전송 요금도 발생한다. 가용성을 유지하면서 비용을 줄이는 방법은?
- A) NAT 게이트웨이를 AZ-a에 하나만 남기고 모든 AZ가 공유하게 한다.
- B) S3·DynamoDB용 게이트웨이 엔드포인트를 만들고, AZ마다 NAT 게이트웨이를 두어 각 AZ의 라우팅 테이블이 같은 AZ의 NAT를 가리키게 한다.
- C) S3·DynamoDB용 인터페이스 엔드포인트를 모든 AZ에 만든다.
- D) 인스턴스를 퍼블릭 서브넷으로 옮기고 EIP를 붙인다.
정답: B
정답 근거: 게이트웨이 엔드포인트는 추가 요금이 없고 NAT 처리량을 줄이는 공식 전략이다 [F9][F27]; 같은 AZ 안의 전송은 무료이므로 AZ별 NAT로 AZ 간 전송을 없앤다 [F4][F30] — https://docs.aws.amazon.com/vpc/latest/userguide/nat-gateway-pricing.html
오답 이유: A) AZ 장애 시 다른 AZ가 인터넷을 잃고 AZ 간 전송 요금도 그대로다 [F4][F30]. C) 인터페이스 엔드포인트는 AZ별 시간당+GB당 요금이 붙어 무료인 게이트웨이 엔드포인트보다 비싸다 [F28][F9]. D) 공인 IPv4마다 시간당 요금이 붙고 [F29] 보안 경계도 약해진다.
