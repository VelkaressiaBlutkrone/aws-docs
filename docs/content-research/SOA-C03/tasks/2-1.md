### 2.1.1 컴퓨팅 환경에서 스케일링 메커니즘 구성·관리

**먼저 잡을 3개의 질문** — 무엇이 용량을 바꾸는가(정책) / 바뀐 용량이 안정될 때까지 얼마나 기다리는가(쿨다운·워밍업) / 새 인스턴스가 "준비됐다"를 누가 판정하는가(헬스 체크·유예 기간·수명 주기 후크). 시험 문항은 대부분 이 세 질문 중 하나가 어긋난 장애 시나리오로 나온다.

**(1) 조정 정책 선택표 (EC2 Auto Scaling)**

| 정책 | 동작 | 경보 관리 주체 | 대기 방식 | 시험 관점 |
|---|---|---|---|---|
| 타깃 추적 | 지표 하나를 목표값 근처로 유지하도록 증감량을 스스로 계산 | EC2 Auto Scaling이 경보를 만들고 관리한다 [F4] | 인스턴스 워밍업 [F7] | 비례형 조정의 기본 선택. 공식 문서도 단순 조정·쿨다운 대신 타깃 추적 또는 단계 조정을 권장한다 [F5] |
| 단계(step) | 경보 위반 크기 구간별로 다른 증감량 | 사용자가 경보·임계값·단계를 직접 정의 (공식 단계·단순 조정 페이지) | 인스턴스 워밍업 [F7] | 구간별 세밀한 제어가 필요할 때 |
| 단순(simple) | 경보 하나 → 한 번 조정 → 쿨다운 동안 대기 | 사용자가 정의 | 쿨다운(그룹 기본 300초) [F6] | 공식 권장 사항에서 제외 [F5] |
| 예약(scheduled) | 정해 둔 시각에 용량 변경 | 해당 없음 | — | 시각이 정해진 이벤트(보조(미인용): ec2-auto-scaling-scheduled-scaling.html — 예측 가능한 부하 변화에 맞춰 원하는 용량을 특정 시각에 증감) |
| 예측(predictive) | 과거 지표로 미래 부하를 예측해 선제 확장 | 해당 없음 | 사전 시작(선택) | 규칙적 일·주 패턴 + 기동 오래 걸리는 앱. 24시간 이상의 지표 필요 [F1], 처음엔 예측만 하는 모드 [F2], 스케일 인은 하지 않음 [F3] |

- 예측 조정이 켜지면 처음에는 forecast only 모드로 동작해 예측만 만들고 그룹을 실제로 확장하지 않는다. 예측이 맞는지 검증한 뒤 forecast and scale로 전환한다 [F2]. 전환 후에도 "부하 감소 예측" 때는 스케일 인하지 않으므로 용량을 줄이는 일은 동적 조정 정책이 맡아야 한다 [F3]. 따라서 예측+동적 병행이 정석이다.
- 데이터 요건: 정책이 보는 지표에 최소 24시간치 데이터가 있어야 예측이 시작된다 [F1]. 14일치 이력이 있으면 예측이 더 정확하다 (근거: GetPredictiveScalingForecast API 레퍼런스 — 98 조각 D절 D1에 인용).
- 보조(미인용): 웜 풀·사전 시작 등을 쓰려면 "기본 인스턴스 워밍업(default instance warmup)"을 켜라는 권고가 예측 조정 문서에 있다 (predictive-scaling-policy-overview.html).

**(2) 쿨다운 vs 워밍업 — 왜 둘이 따로 있나**

- 쿨다운은 단순 조정 정책에서 "직전 조정 효과가 지표에 나타날 때까지 다음 조정을 막는" 장치다. 그룹 기본값은 300초이며 따로 정의하지 않으면 300초가 쓰인다 [F6].
- 타깃 추적·단계 조정은 쿨다운 종료를 기다리지 않고 바로 스케일 아웃할 수 있다. 대신 새로 시작한 인스턴스마다 워밍업 기간이 적용된다 [F7]. 같은 페이지에 따르면 스케일 아웃이 진행되는 동안 타깃 추적·단계의 스케일 인은 인스턴스들이 워밍업을 끝낼 때까지 막힌다.
- 결정 규칙: 문제에 "쿨다운"이 나오면 단순 조정, "워밍업"이 나오면 타깃 추적·단계 조정이다. 기본 인스턴스 워밍업은 기본으로 꺼져 있다 (보조(미인용): ec2-auto-scaling-default-instance-warmup.html — 켜고 구성할 것을 강하게 권장).

**(3) 헬스 체크·유예 기간·수명 주기 후크 — "준비됐다"의 판정**

| 장치 | 무엇을 판정/제어하나 | 숫자·기본값 | 근거 |
|---|---|---|---|
| EC2 상태 확인(기본) | 인스턴스 실행 여부, 하드웨어·소프트웨어 문제 | ASG의 기본 헬스 체크 유형 (health-checks-overview.html 표) | — |
| ELB 상태 확인 | 로드 밸런서가 인스턴스를 healthy로 보고하는지 → 앱 계층 장애까지 반영 | ASG에서 켜야 동작한다 (같은 표) | [F8] |
| 헬스 체크 유예 기간 | 새 인스턴스가 InService가 된 뒤 헬스 체크로 비정상 판정·교체하기 전에 기다리는 시간 | 콘솔로 그룹 생성 시 기본 300초 [F9], CLI·SDK로 생성 시 기본 0초 [F10] | [F9][F10] |
| 수명 주기 후크 | 시작·종료 시점에 사용자 작업(설치·로그 수집)을 끼워 넣는 대기 | 기본 대기 1시간(하트비트 타임아웃) [F11], 전체 상한은 48시간 또는 하트비트의 100배 중 작은 값 [F12] | [F11][F12] |

- 시험의 전형: "CLI로 만든 ASG에 ELB 헬스 체크를 켰더니 부팅 중인 인스턴스가 계속 종료·재생성된다" → 유예 기간이 0초라서다 [F10]. 콘솔에서 만들었다면 기본이 300초였을 것이다 [F9]. 후크를 시작 후크로 쓰면 초기화 완료를 후크가 보장하므로 유예 기간을 0으로 둘 수 있다는 설명이 공식 페이지에 있다 (보조(미인용): health-check-grace-period.html).
- 보조(미인용): 시작 후크를 쓰면 유예 기간은 인스턴스가 InService에 도달한 뒤부터 시작한다 (lifecycle-hooks.html). 스케일 인 보호는 헬스 체크 실패에 따른 교체를 막지 못한다 (ec2-auto-scaling-instance-protection.html).

**(4) 웜 풀·시작 구성**

- 웜 풀은 Auto Scaling 그룹 옆에 두는 사전 초기화된 EC2 인스턴스 풀이다 [F13]. 부팅·초기화가 오래 걸려 스케일 아웃 직후 지연이 길 때 쓴다 (예측 조정과 달리 "미리 예측"하지 않고 "미리 준비해 둔 것을 즉시 투입"한다).
- 시작 구성(launch configuration): 2024-10-01 이후 만들어진 계정은 신규 시작 구성을 만들 수 없고 시작 템플릿으로 옮기라는 것이 공식 방향이다 (보조(미인용): create-launch-config.html, environments-cfg-autoscaling-launch-templates.html).
- 보조(미인용): 인스턴스 새로 고침은 인스턴스 유지 관리 정책이 없으면 최소 정상 비율 기본값이 90%다 (understand-instance-refresh-default-values.html). 배포 성격이 강해 Task 3.1과 겹친다.

### 2.1.2 캐싱으로 동적 확장성 향상 (CloudFront · ElastiCache · DAX)

**캐시는 "요청이 원본까지 가는 횟수"를 줄여 원본 확장의 필요를 줄인다.** 위치별로 세 가지를 구분한다.

| 계층 | 서비스 | 맞는 상황 | 핵심 사실 |
|---|---|---|---|
| 엣지(콘텐츠 전송) | CloudFront | 정적·반정적 콘텐츠, 오리진 부하 감소 | 캐시 정책을 쓰지 않으면 기본 TTL은 24시간 [F16]. 캐시 히트율을 올리려면 캐시 키에 꼭 필요한 값만 넣는다 [F17] |
| 애플리케이션 인메모리 | ElastiCache | 세션·쿼리 결과·계산 결과 캐시, DB 읽기 감소 | 전략 선택(지연 로딩/write-through) [F18], 엔진 선택(Memcached vs Valkey·Redis OSS) [F19], 자동 확장 [F20] |
| DynamoDB 앞단 | DAX | DynamoDB 읽기를 마이크로초로, 반복 읽기·핫 키 완화 | 최종적 일관된 읽기만 가속 [F21], 강한 일관된 읽기는 통과(캐시 안 됨) [F22] |

- **CloudFront.** 오브젝트 캐시 수명은 캐시 정책의 Minimum/Default/Maximum TTL과 오리진의 Cache-Control 헤더로 정해진다. 정책을 쓰지 않는(레거시 설정) 경우 기본 TTL은 24시간이다 [F16]. 캐시 키(헤더·쿼리 문자열·쿠키)에 응답을 바꾸지 않는 값까지 넣으면 같은 객체가 중복 저장되어 히트율이 떨어지므로 필요한 최소 값만 넣는다 [F17]. 즉시 갱신은 무효화(invalidation)로 하지만, 파일 이름에 버전을 넣는 편이 보통 더 저렴하다는 공식 블로그 설명이 있다 (보조(미인용): networking-and-content-delivery 블로그 "Cost-Optimizing your AWS architectures by utilizing Amazon CloudFront features"). 무효화·캐시 문제 해결은 Task 5.3.3(별도 패키지)과 겹친다.
- **ElastiCache 캐싱 전략.** 지연 로딩은 읽힌 데이터만 캐시에 넣지만 오래된(stale) 데이터가 남을 수 있고, write-through는 쓸 때마다 캐시를 채워 항상 신선하지만 빈 노드(예: 새 노드·재시작 후)에서는 실패할 수 있고 읽히지 않을 데이터도 채운다 [F18]. 둘의 약점은 쓰기에 TTL(만료 시간)을 붙여 상쇄한다 (보조(미인용): Strategies.html "Adding TTL" 절).
- **ElastiCache 엔진 선택.** Memcached는 "가장 단순한 모델", "멀티 코어·스레드를 쓰는 큰 노드", "노드를 늘리고 줄이는 수평 확장"이 필요한 객체 캐시에 맞는다 [F19]. 복제·자동 장애 조치·영속성·풍부한 자료구조가 필요하면 Valkey 또는 Redis OSS다 (보조(미인용): SelectEngine.html 비교표 — Memcached는 복제·자동 장애 조치 없음).
- **ElastiCache 자동 확장.** Valkey·Redis OSS는 Application Auto Scaling을 이용해 샤드 또는 복제본 수를 정책(타깃 추적·예약)으로 자동 조정한다 [F20]. 퇴출(eviction)이 잦으면 노드를 키우거나(scale up) 늘리는(scale out) 신호다 (보조(미인용): database-caching-strategies-using-redis 백서 evictions.html). 기본 퇴출 정책은 volatile-lru다 (보조(미인용): aws.amazon.com/caching/best-practices/).
- **DAX.** DAX는 DynamoDB와 API가 호환되는 캐시로 애플리케이션 변경이 거의 없다. 최종적 일관된 읽기를 마이크로초 지연으로 제공한다 [F21]. 강한 일관된 읽기는 DynamoDB로 통과하고 그 결과는 DAX에 캐시되지 않으므로 [F22], 강한 일관성이 필수인 읽기에는 효과가 없다. 보조(미인용): DAX는 쓰기 집약 워크로드·반복 읽기가 적은 워크로드에는 적합하지 않고, 캐시 히트율이 90%를 넘을 때 가장 잘 동작한다고 문서가 명시한다 (DAX.html). 항목 캐시 TTL 기본값은 5분이다 (DAX.concepts.html).

### 2.1.3 AWS 관리형 데이터베이스 스케일링 (RDS · Aurora · DynamoDB)

**원칙: 읽기를 늘릴 것인가, 쓰기·용량을 늘릴 것인가, 저장 공간을 늘릴 것인가에 따라 수단이 다르다.**

| DB | 읽기 확장 | 컴퓨팅(수직) 확장 | 스토리지 확장 | 자동화 |
|---|---|---|---|---|
| RDS (MySQL·MariaDB·PostgreSQL 등) | 읽기 전용 복제본: MySQL·MariaDB·PostgreSQL은 소스당 최대 15개 [F24] (Oracle·SQL Server는 5개 — 같은 FAQ) | 인스턴스 클래스 변경 시 DB가 일시적으로 사용 불가 [F25] | 스토리지 자동 조정(스토리지 오토스케일링): 여유 공간이 할당 스토리지의 10% 이하 등 조건에서 자동 증설 [F23] | 스토리지 오토스케일링 |
| Aurora | Aurora 복제본 (클러스터당 최대 15개 — 보조(미인용): Aurora.Managing.Performance.html) | 인스턴스 클래스 변경 또는 Serverless v2 | 클러스터 볼륨이 10GB 단위로 최대 256 TiB까지 자동 증가 (보조(미인용): rds/latest/auroraextendedcontent/aurora-features-scalability.html) | Aurora Auto Scaling이 정책으로 복제본 수를 조정 [F26] |
| Aurora Serverless v2 | — | 용량을 ACU 단위로 자동 증감: 최소 0 ACU ~ 최대 256 ACU [F27] | — | 용량 범위(min/max ACU)를 지정 |
| DynamoDB | 용량 모드로 처리량 확장 | — | 자동 | on-demand/provisioned + provisioned용 auto scaling [F28][F29] |

- **RDS 스토리지 오토스케일링.** 조건: 여유 공간이 할당 스토리지의 10% 이하 [F23]이고 저스토리지 상태가 5분 이상 지속, 이전 스토리지 수정 후 최적화가 끝난 상태 등 (보조(미인용): USER_PIOPS.Autoscaling.html). 스토리지 용량 증설은 DB 인스턴스 가용성을 유지한 채 할 수 있다는 점이 컴퓨팅 변경과의 핵심 차이다 (보조(미인용): 같은 RDS FAQ 페이지의 "Will my DB instance remain available during scaling?" 문답 — F25와 같은 페이지). 자동 조정의 상한이 되는 최대 스토리지 임계값(maximum storage threshold)을 지정해야 하며, 현재 할당 스토리지보다 최소 10% 커야 한다 (보조(미인용): USER_PIOPS.Autoscaling.html).
- **RDS 컴퓨팅.** 인스턴스 클래스를 바꾸면 그동안 DB를 쓸 수 없다. 보통 몇 분이고, 즉시 적용을 지정하지 않으면 유지 관리 기간에 적용된다 [F25]. Multi-AZ 구성이면 대기본을 먼저 바꾼 뒤 페일오버하므로 중단이 짧다 (보조(미인용): repost 지식 센터 rds-performance-impact).
- **Aurora.** 읽기 규모는 복제본으로 확장하고 Aurora Auto Scaling이 평균 CPU·평균 연결 수 같은 지표(RDSReaderAverageCPUUtilization, RDSReaderAverageDatabaseConnections)에 따라 복제본 수를 조정한다 [F26]. 서버리스 v2는 용량 범위만 정하면 부하에 맞춰 ACU가 증감하며 최소 0으로 설정하면 자동 일시 중지를 쓸 수 있다 [F27] (보조(미인용): aurora-serverless-v2.setting-capacity.html). 최소 용량이 클수록 확장 속도가 빠르다 (같은 페이지).
- **DynamoDB 용량 모드.** on-demand는 요청 수만큼 과금, 직전 최고 처리량의 최대 2배까지 즉시 수용 (보조(미인용): CostOptimization_TableCapacityMode.html — F28과 같은 페이지). provisioned는 직접 RCU/WCU를 정하거나 auto scaling을 쓴다. 모드 전환은 provisioned→on-demand가 24시간 롤링 윈도우에서 최대 4번이고 on-demand→provisioned는 언제든 가능하다 [F28].
- **DynamoDB auto scaling.** Application Auto Scaling이 정책에 따라 프로비저닝 용량을 조정하며 목표 사용률은 20~90%에서 지정한다 [F29]. 갑작스러운 급증은 auto scaling이 따라잡기 전에 스로틀될 수 있어 on-demand나 버스트·적응형 용량 이해가 필요하다.
- **파티션 한도·적응형 용량.** 한 파티션이 읽기 3000 또는 쓰기 1000을 넘으면 스로틀된다 [F30]. 적응형 용량은 모든 테이블에서 자동으로 켜져 있고 추가 요금이 없으며, 총 프로비저닝 용량 또는 파티션 최대 용량을 넘지 않는 한 핫 파티션 읽기·쓰기를 계속 받게 해 준다 (보조(미인용): burst-adaptive-capacity.html).

## 3. 시험에서 묻는 방식 (가이드 Skill 문구 기반 추정 — 실제 문항 아님)

아래는 AWS가 공개한 Skill 문구(동사와 예시 서비스)에서 추론한 출제 패턴이며, 실제 기출이나 문항 풀을 아는 것이 아니다.

- 패턴 1 — 정책 선택: "트래픽 패턴(규칙적/불규칙/시각 고정)과 기동 지연이 주어지고 가장 운영 효율적인 조정 방식을 고르라." 근거 Skill 문구: "Configure and manage scaling mechanisms in compute environments". 판단 기준: 지표 비례 → 타깃 추적(경보를 서비스가 관리 [F4], 단순 조정은 비권장 [F5]), 규칙적 패턴+느린 기동 → 예측 조정(24시간 이상 데이터 [F1], 검증은 forecast only [F2], 스케일 인은 별도 [F3]) 또는 웜 풀 [F13].
- 패턴 2 — 장애 원인 진단: "인스턴스가 반복적으로 종료·교체되거나 앱이 죽었는데도 교체되지 않는다." 근거: "Configure and manage" (구성+관리). 판단 기준: ELB 상태 확인이 꺼져 있나 [F8], 유예 기간이 0초인가(CLI·SDK 기본) [F10], 수명 주기 후크 타임아웃(기본 1시간, 상한 48시간 또는 100배) [F11][F12].
- 패턴 3 — 캐시 계층 선택: "읽기 지연·원본 비용 문제에 대해 CloudFront/ElastiCache/DAX 중 무엇을 쓰는가." 근거: "Implement caching ... (for example, Amazon CloudFront, Amazon ElastiCache)". 판단 기준: 엣지 정적 콘텐츠 → CloudFront [F16][F17], 앱 레벨 세션·결과 → ElastiCache(엔진: [F19], 전략: [F18]), DynamoDB 마이크로초 읽기(최종적 일관 허용) → DAX [F21][F22].
- 패턴 4 — DB 확장 수단과 영향: "스토리지 부족·읽기 과다·갑작스러운 쓰기 증가에 어떤 변경이 중단 없이 가능한가." 근거: "Configure and manage scaling in AWS managed databases (for example, Amazon RDS, DynamoDB)". 판단 기준: 스토리지는 무중단 자동 조정 [F23], 컴퓨트 변경은 일시 중단 [F25], 읽기는 복제본 [F24][F26], DynamoDB는 용량 모드 [F28]·auto scaling [F29]·파티션 한도 [F30].

## 4. 흔한 함정 · 혼동 짝

| 혼동 짝 | 구분 기준 | 근거 |
|---|---|---|
| 쿨다운 vs 인스턴스 워밍업 | 쿨다운=단순 조정(기본 300초), 워밍업=타깃 추적·단계(쿨다운을 기다리지 않고 즉시 스케일 아웃) | [F6][F7] |
| 타깃 추적 vs 단계·단순 | 타깃 추적은 서비스가 경보를 관리, 단계·단순은 사용자가 경보를 정의. 공식 권고는 단순 조정·쿨다운 비권장 | [F4][F5] |
| 헬스 체크 유예 기간 기본값 | 콘솔=300초, CLI·SDK=0초. 문서의 "기본 300초"만 외우면 CLI 시나리오에서 틀린다 | [F9][F10] |
| 수명 주기 후크 시간 | 기본 대기 1시간 vs 전체 상한 48시간(또는 하트비트의 100배 중 작은 값) | [F11][F12] |
| EC2 상태 확인 vs ELB 상태 확인 | ELB 상태 확인은 켜야 동작하며 앱 계층(로드 밸런서가 보는 healthy 여부)까지 반영 | [F8] |
| 예측 조정 vs 웜 풀 | 예측은 미래 부하를 예측해 미리 시작(24시간 이상 지표 필요), 웜 풀은 미리 초기화된 인스턴스를 즉시 투입 | [F1][F13] |
| 예측 조정 "forecast only" vs "forecast and scale" | 처음엔 예측만 하며 확장하지 않는다. 켠 뒤에도 스케일 인은 하지 않는다 | [F2][F3] |
| CloudFront 기본 TTL | 캐시 정책을 쓰지 않을 때 24시간. 캐시 키에는 필요한 값만 | [F16][F17] |
| ElastiCache 전략 | 지연 로딩=stale 가능, write-through=빈 노드에서 실패 가능·불필요한 데이터 적재 | [F18] |
| ElastiCache 엔진 | Memcached=단순·멀티스레드·노드 추가/제거, Valkey·Redis OSS=복제·자동 확장(샤드·복제본) | [F19][F20] |
| DAX vs ElastiCache | DAX=DynamoDB 전용 API 호환 캐시, 최종적 일관된 읽기만 가속. 강한 일관 읽기는 통과 | [F21][F22] |
| RDS 스토리지 확장 vs 컴퓨팅 확장 | 스토리지=무중단 자동 조정, 컴퓨팅(인스턴스 클래스)=일시 중단 | [F23][F25] |
| RDS 복제본 개수 | MySQL·MariaDB·PostgreSQL 15개 vs Oracle·SQL Server 5개 (FAQ 같은 문장). Aurora는 별도 정책으로 복제본 수 조정 | [F24][F26] |
| DynamoDB 모드 전환 횟수 | provisioned→on-demand는 24시간에 최대 4번, 반대는 언제든 | [F28] |

## 6. 자가 점검 문항 후보 (3~5) — 후보일 뿐, 검증 아님

### Q1 (Skill 2.1.1 · intermediate)
문제: 평일 오전 9시마다 트래픽이 급증하는 웹 애플리케이션이 Auto Scaling 그룹에서 실행된다. 인스턴스 초기화에 몇 분이 걸려 급증 직후 응답이 느리다. 운영팀은 용량을 선제적으로 확보하되, 예측이 맞는지 확인하기 전에는 실제 용량 변경이 일어나지 않기를 원하고, 예측하지 못한 급증도 처리해야 한다. 가장 적절한 구성은?
- A) 단순 조정 정책을 만들고 쿨다운을 600초로 늘린다.
- B) 예측 조정 정책을 forecast only 모드로 만들어 예측을 검증한 뒤 forecast and scale로 전환하고, 타깃 추적 정책을 함께 둔다.
- C) 헬스 체크 유예 기간을 0초로 설정한다.
- D) 최소 용량을 최대 용량과 같게 설정한다.
정답: B
정답 근거: 예측 조정은 처음에 용량 예측만 만들고 그룹을 확장하지 않는 모드로 동작하며 [F2], 부하 감소는 스케일 인하지 않으므로 동적(타깃 추적) 정책이 용량 감축과 예측 못한 변동을 맡는다 [F3]. 예측에는 최소 24시간치 지표가 필요하다 [F1]. — https://docs.aws.amazon.com/autoscaling/ec2/userguide/predictive-scaling-policy-overview.html
오답 이유: A) 단순 조정은 반응형이고 쿨다운을 늘리면 오히려 대응이 늦으며 공식 권고에서도 제외된다 [F5]. C) 유예 기간은 헬스 체크 판정 시점의 문제이지 선제 확장 수단이 아니다 [F9][F10]. D) 항상 최대로 운영하는 것은 탄력성이 아니라 과다 프로비저닝이다.

### Q2 (Skill 2.1.1 · intermediate)
문제: ALB 뒤의 Auto Scaling 그룹에서 한 인스턴스의 애플리케이션 프로세스가 멈춰 5xx를 반환하지만 EC2 상태 확인은 모두 통과한다. ASG가 이 인스턴스를 교체하지 않는다. 무엇을 해야 하는가?
- A) ASG의 헬스 체크 유예 기간을 줄인다.
- B) ASG에서 Elastic Load Balancing 상태 확인을 켠다.
- C) 대상 그룹의 등록 취소 지연(deregistration delay)을 0으로 설정한다.
- D) 교차 영역 부하 분산을 끈다.
정답: B
정답 근거: ASG는 기본적으로 EC2 상태 확인만 쓰고, 로드 밸런서가 인스턴스를 healthy로 보고하는지 확인하는 ELB 상태 확인은 그룹에서 켜야 동작한다 [F8]. — https://docs.aws.amazon.com/autoscaling/ec2/userguide/health-checks-overview.html
오답 이유: A) 유예 기간은 새 인스턴스에 대한 대기이지 앱 장애 감지 수단이 아니다 [F9]. C) 등록 취소 지연은 종료 중인 대상의 연결 정리 시간이다. D) 교차 영역 설정은 트래픽 분산 범위만 바꾼다.

### Q3 (Skill 2.1.1 · advanced)
문제: 엔지니어가 AWS CLI로 Auto Scaling 그룹을 만들고 ELB 상태 확인을 활성화했다. 애플리케이션 초기화에 4분이 걸리는데 새 인스턴스가 시작되자마자 비정상으로 판정되어 계속 종료·재생성된다. 가장 가능성이 높은 원인과 해결책은?
- A) 그룹 기본 쿨다운이 300초로 너무 짧다. 쿨다운을 늘린다.
- B) 헬스 체크 유예 기간이 CLI 생성의 기본값 0초다. 초기화 시간보다 긴 유예 기간을 설정하거나 시작 수명 주기 후크로 초기화 완료를 보장한다.
- C) 수명 주기 후크의 기본 대기 시간이 48시간이다. 줄인다.
- D) 예측 조정이 꺼져 있다. 켠다.
정답: B
정답 근거: CLI·SDK로 그룹을 만들면 유예 기간 기본값은 0초다 [F10] (콘솔이면 300초 [F9]). 후크는 기본 1시간 대기이며 [F11], 전체 상한이 48시간 또는 하트비트의 100배 중 작은 값이다 [F12]. — https://docs.aws.amazon.com/autoscaling/ec2/userguide/health-check-grace-period.html
오답 이유: A) 쿨다운은 조정 활동 사이의 간격이며 헬스 체크 판정과 무관하다 [F6]. C) 후크 기본 대기는 1시간이며 48시간은 상한이다 [F11][F12]. D) 예측 조정은 헬스 체크 오탐과 무관하다.

### Q4 (Skill 2.1.2 · intermediate)
문제: 상품 카탈로그를 읽는 DynamoDB 테이블에서 인기 상품 몇 개에 읽기가 몰려 읽기 용량 비용이 높다. 애플리케이션은 최종적 일관된 읽기로 충분하고 마이크로초 응답이 필요하며 코드 변경은 최소화하고 싶다. 가장 적절한 해결책은?
- A) DynamoDB 앞에 DAX 클러스터를 둔다.
- B) 모든 읽기를 강한 일관된 읽기로 바꾼다.
- C) 테이블을 on-demand에서 provisioned로 전환한다.
- D) CloudFront로 DynamoDB를 직접 캐시한다.
정답: A
정답 근거: DAX는 DynamoDB와 API가 호환되는 캐시로 최종적 일관된 읽기를 마이크로초 지연으로 제공한다 [F21]. — https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/DAX.html
오답 이유: B) 강한 일관된 읽기는 DAX가 DynamoDB로 통과시키고 캐시하지 않으므로 효과가 없다 [F22]. C) 모드 전환은 반복 읽기를 줄이지 못한다 [F28]. D) CloudFront는 HTTP 콘텐츠 캐시이며 DynamoDB API 읽기를 캐시하는 용도가 아니다.

### Q5 (Skill 2.1.3 · intermediate)
문제: 예측하기 어려운 속도로 데이터가 늘어나는 RDS for MySQL DB 인스턴스의 여유 스토리지가 10% 아래로 내려가 있다. 운영팀은 가용성 영향 없이 용량 부족을 자동으로 막고 싶다. 가장 적절한 조치는?
- A) 인스턴스 클래스를 더 큰 클래스로 변경한다.
- B) 스토리지 오토스케일링을 켜고 최대 스토리지 임계값을 설정한다.
- C) 읽기 전용 복제본을 15개 추가한다.
- D) 자동 백업 보존 기간을 늘린다.
정답: B
정답 근거: 스토리지 오토스케일링은 여유 공간이 할당 스토리지의 10% 이하일 때 스토리지를 자동으로 늘린다 [F23]. 인스턴스 클래스 변경은 DB를 일시적으로 사용 불가로 만든다 [F25]. — https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIOPS.Autoscaling.html
오답 이유: A) 컴퓨팅 변경은 중단을 유발하고 스토리지 부족의 직접 해결책이 아니다 [F25]. C) 읽기 복제본은 읽기 확장용이다 [F24]. D) 백업 보존 기간은 스토리지 부족과 무관하다.
