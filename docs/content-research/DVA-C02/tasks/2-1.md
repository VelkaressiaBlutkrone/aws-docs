### Cognito 두 구성요소 — 사용자 풀 vs 자격 증명 풀 (Skill 2.1.1)

- Amazon Cognito는 웹·모바일 앱용 ID 플랫폼이다. 사용자 디렉터리, 인증 서버, 그리고 OAuth 2.0 액세스 토큰과 AWS 자격 증명을 위한 인가 서비스를 겸한다 [S1].
- 두 구성요소는 서로를 필수로 요구하지 않는다. 사용자 풀은 자체 백엔드에 JWT만 발급할 수 있고, 자격 증명 풀은 이미 가진 IdP의 토큰만으로 AWS 자격 증명을 중개할 수 있다 [S1].

| 구분 | 사용자 풀 (User pool) | 자격 증명 풀 (Identity pool) |
|---|---|---|
| 답하는 질문 | 이 사용자는 누구인가 (인증) | 이 사용자가 어떤 AWS 리소스에 접근할 수 있나 (권한 부여) [S1] |
| 정체 | 사용자 디렉터리 + OIDC IdP + OAuth 2.0 인가 서버 [S1] | 신뢰된 토큰을 STS 임시 자격 증명으로 바꿔 주는 중개자. 토큰 없는 게스트 자격도 발급 가능 [S1] |
| 결과물 | JWT(ID·액세스 토큰) + 리프레시 토큰 [S4] | AWS 임시 자격 증명(액세스 키 ID·비밀 키·세션 토큰) [S20] |
| 입력 | 비밀번호·SRP·패스키, 소셜/SAML/OIDC 로그인 [S1][S2] | 사용자 풀 ID 토큰, OIDC ID 토큰, SAML assertion, 소셜 access 토큰 [S15] |
| 권한 부여 수단 | 스코프(액세스 토큰), `cognito:groups`, 커스텀 클레임 [S4][S6] | IAM 역할 선택(RBAC)과 주체 태그(ABAC) [S1][S16] |
| 이쪽에만 있는 기능 | managed login, MFA, 맞춤 인증 흐름, 토큰 커스터마이징, 그룹, WAF 웹 ACL, 사용자 속성 [S1] | 게스트(비인증) 자격, 역할 기반·속성 기반 접근 제어, 자격 증명 중개 [S1] |

- 함께 쓰는 표준 3단계: ① 사용자 풀로 로그인해 OAuth 2.0 토큰을 받는다 → ② 그 토큰을 자격 증명 풀에 제시해 임시 AWS 자격 증명을 받는다 → ③ 앱이 그 자격 증명으로 S3·DynamoDB 요청에 서명한다 [S1][S15].
- 원리: AWS API 요청은 SigV4 서명으로 인증 정보를 싣는다 [S37]. JWT는 그 서명 재료가 아니므로 "JWT → IAM 역할 세션(STS) 자격 증명"으로 바꿔 주는 중개 단계가 필요하고, 그 중개자가 자격 증명 풀이다 [S1][S15].

### 사용자 풀 기능 플랜과 로그인 UI (Skill 2.1.1)

| 플랜 | 포함(요지) | 비고 |
|---|---|---|
| Lite | 가입·로그인, 소셜/SAML/OIDC 로그인, 그룹, OAuth 2.0/OIDC 인가 서버, M2M client credentials, 리소스 서버, ID 토큰 클레임 커스터마이징, classic hosted UI [S2] | 액세스 토큰 커스터마이징·패스키 등 신규 기능 제외 [S2] |
| Essentials | Lite + managed login, 액세스 토큰 스코프·클레임 런타임 커스터마이징, 패스키·일회용 코드 로그인, 이메일 MFA [S2] | 신규 사용자 풀의 기본값 [S2] |
| Plus | Essentials + 침해 비밀번호·의심 로그인 탐지, 활동·위험 로그 생성과 내보내기 [S2] | 무료 티어 없음 [S3] |

- 로그인 페이지: managed login은 Essentials·Plus, classic hosted UI는 전 플랜이다 [S2]. managed login을 쓰면 브라우저 쿠키가 1시간 유효해, 토큰 수명을 1시간 미만으로 줄여도 재인증 없이 재진입 가능한 시간은 줄지 않는다 [S6].
- 과금: 플랜별 MAU 기반, SAML/OIDC 연동 MAU는 별도, M2M은 활성 M2M 앱 클라이언트·토큰 요청량 기준 [S2][S11]. 무료 티어는 Lite·Essentials의 직접/소셜 로그인 월 10,000 MAU와 SAML/OIDC 연동 월 50 MAU이며, 자격 증명 풀 인증은 무료다 [S3].
- 과거의 "고급 보안 기능(ASF)" 요금 구조가 Essentials/Plus로 재편되었다(기준일 2024-11-22) [S2][S3]. 시험 문항이 구 명칭(Hosted UI, ASF)을 쓸 수 있다 → 확인 필요 참조.

### 외부 IdP 페더레이션 경로 비교 (Skill 2.1.1)

| 경로 | 주 용도 | 지원 소스 | 결과 |
|---|---|---|---|
| IAM Identity Center | 여러 계정(Organizations)에 걸친 직원(사람) 접근 | SAML 2.0, Managed AD, Identity Center 디렉터리 | 단기 자격 증명(CLI SSO 프로필 등) [S19] |
| IAM IdP 엔터티(SAML/OIDC) | 단일 계정·소규모 사람 사용자·머신(예: GitHub Actions) | SAML 2.0, OIDC | `AssumeRoleWithSAML` / `AssumeRoleWithWebIdentity`로 역할 수임 [S19] |
| Cognito 자격 증명 풀 | 앱 사용자가 IAM 권한이 필요한 경우 | SAML 2.0, OIDC, 일부 OAuth 2.0 소셜 | enhanced/basic 흐름으로 STS 자격 증명 [S19][S15] |
| Cognito 사용자 풀 연동 | 앱이 하나의 JWT 포맷만 다루고 싶은 경우 | 소셜·SAML·OIDC | 풀이 앱에는 IdP, 외부 IdP에는 SP로 동작해 자체 토큰 발급 [S14] |

- `AssumeRoleWithWebIdentity`: 호출에 AWS 자격 증명이 필요 없고(토큰으로 신원 검증), 기본 1시간이며, 역할 신뢰 정책에 해당 IdP가 명시돼야 한다. 모바일 앱에는 Cognito를 권장한다 [S20].
- `AssumeRoleWithSAML`: 호출에 AWS 자격 증명이 필요 없고, 세션은 지정 기간과 SAML 응답의 `SessionNotOnOrAfter` 중 짧은 쪽이다. IAM Identity Center가 관리하는 역할(`AWSReservedSSO_`)에는 쓸 수 없다 [S21].
- 사용자 풀 페더레이션은 IdP의 클레임을 사용자 풀 프로필 속성으로 매핑한다. 이 기능은 자격 증명 풀 페더레이션과 독립적이다 [S14].
- IdP가 세션 태그(SAML `PrincipalTag` 속성, OIDC 토큰)를 넘기면 ABAC에 쓸 수 있다 → 앱 수준 권한 소주제 [S28].
- 원리: 외부 신원을 AWS가 믿게 하려면 먼저 신뢰 관계(IdP 엔터티·신뢰 정책)를 만들고, 토큰/assertion을 STS에 내고 임시 자격 증명을 받는다. 그래서 앱에 장기 키를 배포할 필요가 없다 [S19][S24].

### 자격 증명 풀 — 인증 흐름·역할 선택·게스트 (Skill 2.1.1, 2.1.7)

| 구분 | Enhanced(단순화) 흐름 | Basic(classic) 흐름 |
|---|---|---|
| 호출 순서 | `GetId` → `GetCredentialsForIdentity` | `GetId` → `GetOpenIdToken` → `AssumeRoleWithWebIdentity` |
| 역할 선택 주체 | 자격 증명 풀 설정(기본 역할·RBAC·ABAC) | 앱(신뢰 정책을 만족하는 역할 중 선택) |
| 자격 증명 수명 | 1시간 | 세션 기간을 지정해 요청 가능 |
| 제약 | 권장 흐름 | RoleMappings가 있는 풀에서는 오류. 신규 풀에서 기본 활성화 비권장 |

- 위 표는 [S15]. 풀이 받는 증명물: 사용자 풀·OIDC = ID 토큰, SAML = assertion, 소셜 = access 토큰 [S15].
- 역할 매핑 3가지: ① 기본 역할(인증/비인증) ② 규칙(`Equals`·`NotEqual`·`StartsWith`·`Contains`, 순서대로 첫 일치, 제공자당 25개) ③ 토큰(`cognito:preferred_role`·`cognito:roles`). 일치하지 않거나 모호하면 `AuthenticatedRole` 또는 `Deny`로 해소한다 [S16].
- 토큰 방식에서 그룹 역할을 쓰려면 풀에서 "토큰에서 역할 선택"을 설정해야 한다. `cognito:preferred_role`은 Precedence 최저값 그룹의 역할이다 [S16][S13].
- 인증 역할 신뢰 정책 패턴: Principal `Federated: cognito-identity.amazonaws.com`, Action `sts:AssumeRoleWithWebIdentity`, 조건 `cognito-identity.amazonaws.com:aud`(풀 ID)와 `:amr`(authenticated) [S16].
- 사용자가 직접 바꿀 수 있는 클레임을 높은 권한 역할에 매핑하면 누구나 그 역할을 얻는다. 사용자 풀에서는 앱별 속성 읽기/쓰기 권한을 제한할 수 있다 [S16].
- 게스트: 토큰 없이 제한된 자격 증명을 받는다. 풀 ID는 비밀이 아니라 풀 ID를 아는 누구나 게스트 자격을 요청할 수 있으므로, 기본은 비활성이고 켜면 최소 권한만 준다 [S17].
- 개발자 인증 ID: 자체 인증 시스템을 쓰고 `GetOpenIdTokenForDeveloperIdentity`로 진행한다. IdP 검증을 건너뛰는 지름길이므로 해당 시크릿을 보호한다 [S15].

### 전달자 토큰(JWT)과 OAuth 2.0 (Skill 2.1.2)

| 토큰 | 목적 | 핵심 클레임 | 기본 만료 / 설정 범위 | 서명·형식 |
|---|---|---|---|---|
| ID | 사용자 신원·속성 전달, 자격 증명 풀 입력 | `aud`=앱 클라이언트 ID, `iss`, `token_use=id`, `cognito:groups` [S4][S5] | 60분 / 5분~1일 [S7] | JWT, RS256 [S5] |
| 액세스 | API 인가(스코프), 사용자 셀프서비스 API, userInfo | `client_id`, `scope`, `cognito:groups`, `token_use=access`, `username`. `aud`는 리소스 바인딩을 요청한 경우에만 존재 [S6] | 60분 / 5분~1일 [S7] | JWT, RS256, ID 토큰과 다른 키로 서명 [S6] |
| 리프레시 | 새 ID·액세스 토큰 발급, 폐기 대상 | 사용자 풀만 읽을 수 있는 암호화·불투명 토큰 [S4] | 30일 / 60분~10년(3,650일) [S7][S8] | 불투명 |

- 검증 순서(앱·Lambda 오소라이저): 구조(`header.payload.signature`) → 서명(JWKS의 `kid` 일치) → `exp` → `iss`(풀 URL) → `aud`(ID)·`client_id`(액세스) → `token_use` → 폐기 여부 [S5]. JWKS는 `https://cognito-idp.<Region>.amazonaws.com/<userPoolId>/.well-known/jwks.json`이며, 서명 키가 교체될 수 있으므로 `kid`로 캐시하고 모르는 `kid`가 오면 갱신한다 [S5].
- 원리: 서명은 헤더·페이로드를 해시해 RSA(RS256)로 서명한 값이라, 토큰을 변조하면 공개 키로 대조할 때 불일치한다 [S5]. JWT는 자체 완결형이라 `exp`는 네트워크 호출 없이 검사할 수 있지만, 폐기(로그아웃·RevokeToken)는 오프라인으로 알 수 없다. 폐기를 반영하려면 Cognito에 확인하거나 액세스 토큰 수명을 짧게 한다 [S5].
- 라이브러리: Node.js는 `aws-jwt-verify`가 서명·만료·발급자·클라이언트·스코프를 검증한다 [S5]. Amplify는 토큰 조회·갱신 함수를 제공한다 [S5].

| OAuth 2.0 grant | 시작 엔드포인트 | 받는 토큰 | 비고 |
|---|---|---|---|
| Authorization code (+PKCE) | Authorize → Token 교환 | ID·액세스·리프레시 모두 | 가장 안전. 토큰 내용이 사용자에게 직접 노출되지 않음. PKCE 지원 [S10] |
| Implicit | Authorize | ID·액세스(리프레시 없음) | 레거시. 토큰이 사용자에게 노출/가로채기 가능 [S10] |
| Client credentials(M2M) | Token | 액세스(커스텀 스코프만) | 같은 앱 클라이언트에서 위 두 grant와 동시 활성화 불가. 앱 클라이언트 시크릿 필요 [S10][S11] |

- 서버 측이 있는 앱·모바일은 Authorization code + PKCE를 쓰고, 리프레시 토큰은 클라이언트 측 환경에 저장하지 않는다 [S67]. 토큰은 전송·저장 모두 보호한다 [S4].
- 스코프: `aws.cognito.signin.user.admin`은 사용자 셀프서비스 API(속성 읽기/쓰기, MFA 설정 등) 권한이고, `openid`는 userInfo 엔드포인트 접근, `profile`·`email`은 그 범위를 넓힌다. 외부 API용은 리소스 서버의 커스텀 스코프(`resourceServerIdentifier/scopeName`)다 [S6][S11][S67].

### API Gateway에서 토큰·자격을 검증하는 방식 비교 (Skill 2.1.2, 2.1.4, 2.1.7)

| 방식 | API 유형 | 클라이언트가 보내는 것 | 검증·결정 주체 | 핵심 포인트 |
|---|---|---|---|---|
| IAM (`AWS_IAM`) | REST·HTTP | SigV4(또는 SigV4a) 서명 요청 | IAM — 호출자 정책의 `execute-api:Invoke` | 호출자가 IAM 자격 증명(예: 자격 증명 풀 자격)을 가진 경우 [S61][S63] |
| Cognito 사용자 풀 오소라이저 | REST (HTTP API는 JWT 오소라이저로 Cognito 사용) | `Authorization` 헤더의 ID 또는 액세스 토큰 | API Gateway가 풀 ARN(`providerARNs`)으로 검증 | ID 토큰=신원 클레임 기반, 액세스 토큰=커스텀 스코프 기반. 메서드에 스코프를 지정하면 액세스 토큰 필요 [S57][S56][S76] |
| Lambda 오소라이저 TOKEN | REST | 단일 bearer 토큰(JWT·OAuth) | 내 Lambda → IAM 정책+principalId | 캐시 키=토큰 헤더 이름. 정규식 사전 검증은 TOKEN 전용 [S55] |
| Lambda 오소라이저 REQUEST | REST·HTTP | 헤더·쿼리·stage 변수·context 조합 | 내 Lambda | 다중 identity source가 캐시 키(캐시 사용 시 하나라도 없으면 Lambda 호출 없이 401). AWS 권장 유형(REST) [S55][S56][S59] |
| JWT 오소라이저 | HTTP | JWT(`Bearer` 접두 허용) | API Gateway가 issuer·audience·scope 검증 | RSA만 지원. 공개 키 최대 2시간 캐시. ID/액세스 토큰 구분 불가 → 스코프 요구 권장 [S58] |
| 리소스 정책 | REST만(HTTP 불가) | — | API Gateway가 IP·VPC 엔드포인트·계정 조건 평가 | 교차 계정은 IAM과 리소스 정책 모두 allow 필요 [S54][S61][S64] |
| API 키 + 사용량 계획 | REST | API 키 | 식별·사용량 제한용 | 인증·인가 수단이 아님 [S62] |
| mTLS | REST(Regional 커스텀 도메인) | 클라이언트 X.509 인증서 | TLS 핸드셰이크(truststore) | 폐기 검증 없음, private API 불가, 다른 방식과 병용 가능 [S65] |

- Lambda 오소라이저 흐름: 호출 → (캐시 있으면 재사용) → Lambda가 호출자를 인증 → IAM 정책과 principal 식별자를 반환 → API Gateway가 정책을 평가(거부 403, 허용 시 메서드 호출). 반환 `context`는 통합 백엔드로 전달할 수 있다 [S55]. 캐시를 켜면 정책이 API 전체 리소스·메서드에 적용 가능해야 한다 [S55].
- 캐시 TTL: 기본 300초, 최대 3600초 [S56]. 문서 간 불일치(0 허용 여부)는 확인 필요 참조 [S66].
- HTTP API의 Lambda 오소라이저는 payload 형식 1.0/2.0 중 선택하고 REST 호환은 1.0이다 [S59]. IAM 정책 대신 `isAuthorized` Boolean 단순 응답을 쓸 수 있으며, 캐시는 identity source가 최소 1개 필요하고 최대 1시간이다. 단순 응답과 캐시를 함께 쓰면 같은 identity source 값에 대한 허용/거부가 모든 라우트에 적용될 수 있어 `$context.routeKey`를 identity source에 추가한다 [S60].
- 리소스 정책 평가: 같은 계정이면 IAM 정책(또는 Lambda 오소라이저)과 리소스 정책 중 하나만 allow여도 되고 어느 쪽이든 명시적 deny면 deny다. 교차 계정이면 둘 다 명시적 allow여야 하며 한쪽이 무언급이면 암묵적 거부다 [S64].
- Cognito로 로그인한 뒤 API Gateway 접근을 승인하는 3패턴: ① 액세스 토큰(유효·미만료·올바른 스코프) + Cognito 오소라이저 ② ID 토큰 유효성(앱 서버에서 추가 검증 가능) ③ 토큰의 그룹·클레임·속성·역할을 Lambda 오소라이저가 평가하거나 Amazon Verified Permissions를 호출 [S18].
- 원리: REST 오소라이저는 "인증 결과 → IAM 정책 문서"로 귀결되고 API Gateway가 그 정책을 평가하므로 캐시도 정책 단위로 재사용된다 [S55]. HTTP API JWT 오소라이저는 정책 없이 토큰 검증과 스코프 일치만 한다 [S58].

### 프로그래밍 방식 접근 구성 — 자격 증명 공급자 체인 (Skill 2.1.3)

| 순위 | AWS CLI 인증 소스(위가 우선) [S43] |
|---|---|
| 1 | 명령줄 옵션(`--profile`·`--region` 등) |
| 2 | 환경 변수 |
| 3~4 | Assume role / Assume role with web identity |
| 5 | AWS IAM Identity Center(`aws configure sso` → `aws sso login`) |
| 6~8 | 자격 증명 파일 / 사용자 지정 프로세스 / 구성(config) 파일 |
| 9~10 | 컨테이너 자격 증명 / EC2 인스턴스 프로파일 |

- 환경 변수의 `AWS_ACCESS_KEY_ID`·`AWS_SECRET_ACCESS_KEY`는 `AWS_PROFILE` 프로필의 자격 증명을 덮어쓴다 [S44].
- SDK 체인: 정해진 소스를 순서대로 확인하고 유효한 자격 증명을 찾으면 중단한다. 표준 공급자는 만료 시 자동 갱신하지만, 환경 변수에 넣어 둔 임시 자격 증명은 만료 후 자동 갱신되지 않는다 [S39][S36]. SDK마다 체인 순서가 다를 수 있다 [S39].

| 실행 환경 | 자격 증명 출처 | 참고 |
|---|---|---|
| 로컬 개발 | `aws login`(콘솔 자격 증명 → 15분 단기 자격 증명을 최대 12시간 자동 갱신), 또는 IAM Identity Center SSO 프로필 [S42][S45] | 장기 IAM 사용자 키는 비권장 [S43] |
| EC2 | 인스턴스 프로파일 역할을 IMDS로 제공 [S43] | IMDSv2는 PUT으로 토큰을 받아 GET에 첨부, TTL 최대 6시간, 토큰 필수 설정 시 토큰 없으면 401 [S46] |
| ECS | 작업 역할 → `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` [S41] | |
| EKS | Pod Identity → `AWS_CONTAINER_CREDENTIALS_FULL_URI` + `AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE` [S41] | IRSA는 서비스 계정 토큰으로 SDK가 `AssumeRoleWithWebIdentity`를 호출하는 web identity 방식(`web_identity_token_file`) [S53][S40] |
| Lambda | 실행 역할의 임시 자격 증명이 환경 변수로 제공 [S48][S49] | |
| 온프레미스 | 프로세스 공급자(IAM Roles Anywhere 포함) [S39] | |

- 역할 수임 프로필: `role_arn`에 더해 `source_profile` / `credential_source` / `web_identity_token_file` 중 하나가 필요하고, `credential_source`와 `source_profile`은 같은 프로필에 동시에 쓸 수 없다. `credential_source` 값은 `Environment`·`Ec2InstanceMetadata`·`EcsContainer`다. `duration_seconds` 기본 3600, 그 밖에 `mfa_serial`·`external_id`·`role_session_name`이 있다 [S40]. 프로필이 다른 assume-role 프로필을 source로 삼으면 역할 체이닝이라 1시간 상한이 걸린다 [S40].
- IAM Identity Center 프로필은 `sso_session`·`sso_account_id`·`sso_role_name`과 `[sso-session]` 블록(`sso_region`·`sso_start_url`)을 쓴다. 레거시(비갱신) 구성은 자동 토큰 갱신이 안 되므로 SSO 토큰 구성이 권장된다 [S45].
- 원리: 자동 갱신되는 공급자(역할·SSO·컨테이너·IMDS)를 쓰면 코드·이미지에 장기 키를 두지 않아도 된다 [S24][S39].

### 인증된 AWS 호출 — SigV4와 서명이 필요한 경로 (Skill 2.1.4)

- SDK·CLI는 제공된 자격 증명으로 요청에 자동 서명하므로 직접 서명 코드를 쓰는 것은 SDK가 없거나 완전 제어가 필요할 때뿐이다 [S37].
- SigV4 3단계: 정규 요청 생성 → 자격 증명으로 서명 계산 → 서명을 `Authorization` 헤더(또는 쿼리 문자열)에 추가. 서비스가 같은 과정을 재현해 서명을 비교한다. 비밀 키로 직접 서명하지 않고 날짜·리전·서비스로 파생한 서명 키를 쓰며, 임시 자격 증명이면 세션 토큰도 필요하다 [S37].
- 서명 요소: 알고리즘 `AWS4-HMAC-SHA256`, 자격 범위 `액세스키ID/YYYYMMDD/리전/서비스/aws4_request`, UTC 타임스탬프 [S38]. SigV4a는 다중 리전 요청용이며 SDK·CLI가 필요 시 자동 전환한다 [S37].
- 원리: 요청 해시로 변조를, 타임스탬프로 재전송(대개 5분 이내 도달 필요)을 막고, 비밀 키 자체는 전송하지 않는다 [S37].
- 서명이 필요한 대표 경로: API Gateway `AWS_IAM`(SigV4·SigV4a 지원) [S63], Lambda 함수 URL `AWS_IAM`(호출자는 SigV4 서명과 `lambda:InvokeFunctionUrl`·`lambda:InvokeFunction` 필요, `NONE`은 IAM 인증 없이 리소스 기반 정책으로 공개) [S50], S3 presigned URL. AppSync도 IAM 권한 기반 인가 유형 `AWS_IAM`을 제공한다 [S71].
- presigned URL 수명은 만든 자격 증명이 결정한다: IAM 사용자 키(SigV4)는 최대 7일, 역할·STS 임시 자격 증명은 그 자격 증명이 만료되면 URL도 만료, EC2 역할 자격 증명은 보통 6시간이다 [S47].

### IAM 역할 수임 (Skill 2.1.5)

- 역할은 비밀번호·액세스 키 같은 장기 자격 증명이 없는 IAM 자격 증명이며, 수임하면 임시 자격 증명을 받는다. 수임 주체: 같은/다른 계정의 IAM 사용자, 같은 계정의 역할, 서비스 주체(EC2·Lambda 등), SAML/OIDC 외부 사용자 [S25].
- 역할에는 정책이 2종이다: 신뢰 정책(누가 수임하나, 리소스 기반 정책)과 권한 정책(수임 후 무엇을 하나) [S22].
- 같은 계정: 사용자에게 `sts:AssumeRole` 허용 정책을 붙이거나(신뢰 정책이 계정을 신뢰할 때) 신뢰 정책에 사용자를 직접 Principal로 넣는다. 교차 계정: 역할 쪽 신뢰 정책이 상대 계정을 신뢰하고, 상대 계정 관리자가 호출자에게 `AssumeRole` 권한을 위임한다 [S22].

| STS API | 호출자 | 수명(최소–최대, 기본) | MFA | 세션 정책 |
|---|---|---|---|---|
| AssumeRole | IAM 사용자, 또는 임시 자격 증명을 가진 IAM 역할 | 15분–역할 최대 세션(1~12시간), 기본 1시간 | 가능 | 가능 |
| AssumeRoleWithSAML | 누구나(SAML 응답 제시) | 동일 | 불가 | 가능 |
| AssumeRoleWithWebIdentity | 누구나(OIDC JWT 제시) | 동일 | 불가 | 가능 |
| GetFederationToken | IAM 사용자·루트 | IAM 사용자 15분–36시간(기본 12시간), 루트 15분–1시간 | 불가 | 가능 |
| GetSessionToken | IAM 사용자·루트 | 위와 동일 | 가능 | 불가 |

- 위 표는 [S23]. 결과 자격 증명은 `GetFederationToken`·`GetSessionToken`을 호출할 수 없다 [S22].
- 수명 규칙: `DurationSeconds`는 900초부터 역할의 최대 세션 설정까지이고 기본 3600초이며, 초과하면 실패한다. 역할 체이닝(역할로 또 다른 역할을 수임)은 AWS CLI·API 세션을 최대 1시간으로 제한하고 늘릴 수 없으며 콘솔 역할 전환에는 해당하지 않는다. 체이닝에서 1시간을 넘기면 "exceeds the 1 hour session limit for roles assumed by role chaining" 계열 오류가 난다 [S22][S25][S35]. 서비스가 수임한 세션에는 최대 세션 설정이 적용되지 않는다 [S34].
- 보조 파라미터: `ExternalId`(서드파티 접근·confused deputy 방지, 비밀이 아님, 신뢰 정책 `sts:ExternalId` 조건) [S27][S22] / MFA(신뢰 정책 `aws:MultiFactorAuthPresent` + `SerialNumber`·`TokenCode`) [S22] / 세션 정책(인라인 1개 + 관리형 최대 10개, 합계 2,048자, 결과 권한은 역할 정책과의 교집합이며 확대 불가) [S22] / 세션 태그(최대 50개, `sts:TagSession` 필요, 전이적 태그는 체이닝으로 전달) [S22][S28] / `SourceIdentity`(체이닝 유지) [S22] / `RoleSessionName`(CloudTrail에 기록) [S22][S40].
- 용어: 서비스 역할(서비스가 대신 수임), 서비스 연결 역할(서비스가 소유·편집 불가), 실행 역할(예: Lambda) [S25][S48].
- PassRole vs AssumeRole: `iam:PassRole`은 사람이 서비스(EC2·ECS·Lambda 등)를 설정할 때 서비스에 역할을 넘기는 권한이다(같은 계정의 서비스에만, `iam:PassedToService`로 범위 제한, 역할 태그로 PassRole을 통제하는 방식은 신뢰할 수 없음). `sts:AssumeRole`은 주체가 직접 임시 자격 증명을 요청하는 호출이다 [S26][S22].
- 원리: 신뢰 정책("누가")과 권한 정책("무엇을")을 분리해 키를 공유하지 않고 위임하며, 임시 자격 증명은 만료되므로 별도 폐기가 필요 없다 [S22][S24].

### IAM 보안 주체 권한 정의 — 정책 유형과 평가 (Skill 2.1.6)

| 정책 유형 | 붙이는 곳 | 권한 부여? | 요점 |
|---|---|---|---|

| 리소스 기반 | 리소스(S3 버킷 정책, 역할 신뢰 정책 등) | 부여 | 인라인뿐. 같은 계정이면 ID 정책 불필요, 교차 계정이면 ID 정책도 필요 [S30] |

| RAM 리소스 공유 | 공유 리소스 | (공유) | 정책을 따로 쓰지 않고 계정·OU·조직 간 공유 [S30] |
| 세션 정책 | AssumeRole·연합 사용자 세션 생성 시 | 제한 | 세션 권한 = ID 정책 ∩ 세션 정책. 리소스 기반 정책이 세션 ARN을 Principal로 지정하면 세션 정책의 제한을 받지 않음 [S30] |

- 평가 순서: 인증 → 요청 컨텍스트 처리 → 정책 평가 [S31]. 기본은 암묵적 거부이고, 명시적 Deny는 어떤 Allow도 이기며, 조건이 맞지 않으면 default deny다 [S31][S32].
- 같은 계정의 ID 기반+리소스 기반 정책은 합집합(하나라도 허용이면 허용), 권한 경계는 ID 정책과 교집합, SCP·RCP는 모두 허용해야 한다 [S31].
- 최소 권한 도구: IAM Access Analyzer의 정책 검증(100개 이상 검사), CloudTrail 활동 기반 정책 생성, 외부·미사용 접근 분석, 마지막 액세스 정보 [S30][S33]. Lambda 실행 역할도 동일 방식으로 줄인다 [S48].
- 정책 크기 한도: 역할 인라인 합계 10,240자(사용자 2,048, 그룹 5,120), 고객 관리형 정책 1개 6,144자(공백 제외) [S34].
- 자주 나오는 조건 키: `aws:PrincipalTag`·`aws:RequestTag`·`aws:ResourceTag`·`aws:TagKeys` [S28], `sts:ExternalId` [S27], `aws:MultiFactorAuthPresent` [S22], `iam:PassedToService` [S26], `aws:SourceArn`·`aws:SourceAccount` [S51], `aws:SourceIp`·`aws:SourceVpc`·`aws:SourceVpce`(API Gateway 리소스 정책) [S64], `dynamodb:LeadingKeys` [S68].
- IAM 사용자·그룹 관리 업무는 시험 범위 밖이다 [S75]. 사람 사용자는 IdP 페더레이션이 권장된다 [S19].

### 앱 수준 세분화 권한 부여 (Skill 2.1.7)

| 결정 위치 | 수단 | 메모 |
|---|---|---|
| IdP 토큰 | Cognito 그룹(`cognito:groups`, 그룹별 IAM 역할·Precedence), 스코프, 커스텀 클레임 | 그룹은 ID·액세스 토큰 모두에 실린다 [S4][S13] |
| 토큰 가공 | 사전 토큰 생성 Lambda: V1_0(ID 토큰), V2_0(ID+액세스), V3_0(+M2M) | 기본 V1_0, V2_0·V3_0은 Essentials/Plus [S12] |
| API 경계 | 메서드별 스코프(Cognito/JWT 오소라이저), Lambda 오소라이저 `context` | [S57][S58][S55] |
| 앱 정책 엔진 | Amazon Verified Permissions(Cedar) | 앱이 인가 API로 허용/거부 판단을 요청 [S70] |
| AWS 리소스 | IAM 정책 변수·조건 키, ABAC(`aws:PrincipalTag`) | [S29][S28] |
| 데이터 계층 | DynamoDB `dynamodb:LeadingKeys`(항목), `Attributes`·`Select`(속성) | [S68] |

- 그룹 Precedence: 값이 낮을수록 우선(0이 최고). 여러 그룹이면 최저값 그룹의 역할이 `cognito:preferred_role`에 들어가고, 같은 Precedence에 서로 다른 역할이면 `cognito:preferred_role`이 설정되지 않는다 [S13]. 한도: 풀당 그룹 10,000개, 사용자당 100개 [S9].
- 사전 토큰 생성 Lambda는 ID·액세스 토큰의 클레임·스코프·그룹을 추가·수정·억제한다. 사용 예: 런타임에 사용자가 요청할 IAM 역할 변경, 외부 소스 속성 추가 [S12]. `cognito:`로 시작하는 일부 클레임·`sub`·`iss` 등은 변경할 수 없다 [S12].
- 리소스 서버·스코프: 리소스 서버는 API가 요구하는 커스텀 스코프를 정의하고, M2M 액세스 토큰은 리소스 서버의 커스텀 스코프만 인가한다 [S11]. 스코프 형식은 `resourceServerIdentifier/scopeName`이다 [S67].
- Verified Permissions: 앱이 만든 리소스를 위한 세분화 권한 부여 서비스로, 정책은 Cedar로 쓰고 인가 로직을 비즈니스 로직에서 분리한다. 주체가 이미 인증됐다고 전제하며 Cognito·OIDC·IAM Identity Center와 연계한다. API 연동 정책 저장소는 Lambda 오소라이저로 ID/액세스 토큰을 정책에 대조한다 [S70][S11]. 시험 범위 여부는 확인 필요 참조.
- ABAC: 속성을 태그로 보고 "주체 태그 = 리소스 태그"일 때 허용한다. 새 리소스에 정책 수정 없이 적용되고 정책 수가 적다 [S29]. 속성 출처: 세션 태그(AssumeRole `Tags`, SAML `PrincipalTag`, OIDC 토큰) [S28], 자격 증명 풀의 클레임→주체 태그 매핑 [S1], EKS Pod Identity 세션 태그 [S53].
- DynamoDB: `dynamodb:LeadingKeys`는 파티션 키를 뜻하며 반드시 `ForAllValues` 한정자와 쓴다. `Scan`은 모든 항목을 반환하므로 LeadingKeys 정책에 허용하지 않는다. 속성 제한은 요청에 `ProjectionExpression`이 없으면 우회되므로 `dynamodb:Select`·`ReturnValues`도 함께 제한한다 [S68]. Cognito 변수 예: `${cognito-identity.amazonaws.com:sub}` [S69].
- AppSync 인가 유형 5가지: `API_KEY`·`AWS_LAMBDA`·`AWS_IAM`·`OPENID_CONNECT`·`AMAZON_COGNITO_USER_POOLS` [S71].
- 멀티테넌트 데이터 접근 패턴 상세 → Task 2.3.
- 원리: 인증(누구)과 인가(무엇)를 분리하고 토큰 클레임·태그(속성)로 정책을 일반화하면, 사용자·리소스가 늘어도 정책 수가 늘지 않는다 [S29].

### 마이크로서비스 서비스 간 인증 (Skill 2.1.8)

| 서비스가 대신 호출하는 경우(교차 서비스) | 리소스 정책의 `aws:SourceArn`·`aws:SourceAccount` | confused deputy 방지 [S51] |

## 시험에서 묻는 방식

> 문제 저작자를 위한 제안이며 "시험이 반드시 이렇게 낸다"는 단정이 아니다.

1. **앱 사용자 로그인 + AWS 리소스 직접 접근 (Skill 2.1.1, 2.1.7)**
   - 상황: 모바일/웹 앱이 소셜·기업 계정으로 로그인한 뒤 사용자별 S3 prefix나 DynamoDB 항목에만 접근해야 하고, 앱에 장기 키를 넣을 수 없다.
   - 정답 단서: "앱 사용자 + 임시 자격 증명 + 사용자별 격리" → Cognito 사용자 풀(+IdP 연동) + 자격 증명 풀(enhanced 흐름의 인증 역할), 정책 변수 `${cognito-identity.amazonaws.com:sub}` / `dynamodb:LeadingKeys`. "그룹별로 다른 권한" → 그룹에 IAM 역할 연결 + 풀의 "토큰에서 역할 선택". 오답 유인: IAM 사용자 생성, 앱 내 액세스 키, API 키.
2. **API Gateway API 보호 방식 선택 (Skill 2.1.2, 2.1.4)**
   - 상황: REST API를 로그인한 사용자만 호출하게 하되 읽기/쓰기를 스코프로 구분하거나, 서드파티 토큰·DB 조회 같은 자체 규칙으로 검증하고, 인증 호출 횟수도 줄이고 싶다. HTTP API라면 JWT를 검증하고 싶다.
   - 정답 단서: "Cognito 로그인 + 스코프" → `COGNITO_USER_POOLS` 오소라이저 + 리소스 서버 커스텀 스코프 + 액세스 토큰. "자체 규칙·헤더/쿼리 조합·외부 IdP 토큰" → Lambda 오소라이저(REQUEST 권장), 결과 캐시(TTL 기본 300초). "HTTP API + JWT" → JWT 오소라이저(issuer·audience·scopes). "호출자가 IAM 자격 증명 보유" → `AWS_IAM`(SigV4). 오답 유인: API 키만으로 인증, ID 토큰으로 스코프 검사.
3. **교차 계정·서드파티 접근과 역할 수임 오류 (Skill 2.1.5, 2.1.6)**
   - 상황: 외부 업체나 다른 계정이 우리 계정 리소스에 접근해야 한다. 역할 수임 시 `DurationSeconds` 오류가 나거나, 서비스에 역할을 지정할 때 `iam:PassRole` AccessDenied가 난다.
   - 정답 단서: "교차 계정/서드파티 + 장기 키 금지" → 역할 + 신뢰 정책 + `ExternalId`(confused deputy). "DurationSeconds 오류" → 역할 체이닝 1시간 상한 또는 역할 최대 세션 설정. "권한의 상한을 두고 위임" → 권한 경계/세션 정책(교집합). "서비스에 역할 지정 시 AccessDenied" → `iam:PassRole`(+ `iam:PassedToService`) 허용.
4. **실행 환경별 자격 증명과 서비스 간 인증 (Skill 2.1.3, 2.1.8)**
   - 상황: ECS·EKS·Lambda·EC2·로컬 CLI에서 장기 키 없이 AWS를 호출하고, 사용자가 없는 서비스 간 API 호출을 인증해야 한다.
   - 정답 단서: ECS → 작업 역할(≠ 실행 역할) / EKS → Pod Identity(`pods.eks.amazonaws.com`) 또는 IRSA / Lambda → 실행 역할 / EC2 → 인스턴스 프로파일 + IMDSv2 / 로컬 → IAM Identity Center SSO 프로필·`aws login`. 서비스 간: IAM 역할 + SigV4(`AWS_IAM`), 또는 Cognito client credentials + 커스텀 스코프, 클라이언트 인증서 요구 → mTLS. 오답 유인: 환경 변수/이미지에 액세스 키 하드코딩.

## 흔한 함정·혼동 짝

| A vs B | 혼동 이유 | 구분 기준 한 줄 | 출처 |
|---|---|---|---|
| 사용자 풀 vs 자격 증명 풀 | 둘 다 "Cognito 로그인"으로 보임 | 사용자 풀=인증·JWT 발급, 자격 증명 풀=토큰→AWS 임시 자격 증명(IAM 역할) 교환 | [S1] |
| ID 토큰 vs 액세스 토큰 | 둘 다 JWT이고 Authorization 헤더로 보낼 수 있음 | ID=사용자 신원 클레임, 액세스=스코프 기반 API 인가(메서드 스코프 지정 시 액세스 토큰 필요) | [S6][S57][S76] |
| 액세스 토큰의 `aud` vs `client_id` | ID 토큰은 `aud`로 검증하므로 같은 방식을 기대함 | 액세스 토큰은 `client_id`로 검증, `aud`는 리소스 바인딩 요청 시에만 존재 | [S5][S6] |
| Cognito 오소라이저 vs Lambda 오소라이저 vs JWT 오소라이저 | 모두 "토큰 검증" | REST=`COGNITO_USER_POOLS` 또는 Lambda(TOKEN·REQUEST), HTTP=JWT(issuer·audience) 또는 Lambda | [S57][S55][S58][S61] |
| Lambda TOKEN vs REQUEST 오소라이저 | 둘 다 Lambda 오소라이저 | TOKEN=단일 bearer 토큰·정규식 사전 검증, REQUEST=헤더·쿼리·stage·context 다중 소스(AWS 권장) | [S55] |
| API 키 vs 인증·인가 | 사용량 계획+API 키가 "접근 제어"처럼 보임 | API 키는 식별·사용량 제한용이며 인증·인가에 쓰지 않음 | [S62] |
| AssumeRole vs AssumeRoleWithWebIdentity vs AssumeRoleWithSAML | 모두 임시 자격 증명을 줌 | 호출자 차이: IAM 주체(서명 호출) / OIDC JWT 제시(자격 증명 불필요) / SAML 응답 제시(자격 증명 불필요) | [S22][S20][S21] |
| `iam:PassRole` vs `sts:AssumeRole` | 둘 다 "역할을 쓸 권한" | PassRole=서비스 구성 시 역할을 서비스에 넘김, AssumeRole=주체가 직접 임시 자격 요청 | [S26][S22] |
| 권한 경계 vs SCP vs 세션 정책 | 셋 다 "최대 권한 제한"이고 권한을 부여하지 않음 | 경계=개별 사용자·역할, SCP=Organizations 계정·OU, 세션 정책=AssumeRole 때 전달(세션 한정) | [S30] |

- 정답: A
- 정답 근거: ECS 작업 IAM 역할은 컨테이너의 애플리케이션 코드가 다른 AWS 서비스를 사용하게 하는 역할이며 Fargate에서도 인스턴스 프로파일 없이 쓸 수 있고, 신뢰 정책은 `ecs-tasks.amazonaws.com`을 지정한다 [S51]. 근거 URL: https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-iam-roles.html
- 오답 해설:
  - B: 작업 실행 역할은 ECS·Fargate 에이전트가 이미지를 pull하고 작업을 실행하는 데 쓰며, 앱 코드의 AWS 호출용은 작업 역할이다 [S51].
  - C: IAM 사용자 장기 키는 비권장이다 [S43].
  - D: Fargate의 작업 컨테이너에는 EC2 인스턴스 프로파일이 제공되지 않는다 [S51].

### 후보 5
- 대응 Skill: 2.1.7 / 난이도: advanced
- 문제: 하나의 DynamoDB 테이블에 모든 사용자의 항목이 저장돼 있고 파티션 키가 사용자 ID이다. 웹 ID 페더레이션(Cognito 자격 증명 풀)으로 받은 임시 자격 증명을 쓰는 클라이언트가 자기 항목만 읽고 쓰게 하려 한다. IAM 정책에서 사용할 접근 방식은?
- 보기:
  - A. `dynamodb:LeadingKeys` 조건 키를 `ForAllValues:StringEquals`와 `${cognito-identity.amazonaws.com:sub}` 정책 변수로 사용하고, 이 정책에는 `Scan`을 허용하지 않는다.
  - B. `dynamodb:Select` 조건 키를 `ALL_ATTRIBUTES`로 제한한다.
  - C. `aws:SourceIp` 조건 키로 사용자 IP를 제한한다.
  - D. Principal을 `*`로 설정해 모든 클라이언트를 허용한다.
- 정답: A
- 정답 근거: `dynamodb:LeadingKeys`는 테이블의 파티션 키를 뜻하며 `ForAllValues` 한정자와 함께 써야 하고, `Scan`은 리딩 키와 무관하게 모든 항목을 반환하므로 허용 목록에서 제외한다 [S68]. Cognito 자격 증명 ID를 정책 변수로 쓰는 예는 `${cognito-identity.amazonaws.com:sub}`다 [S69]. 근거 URL: https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/specifying-conditions.html , https://aws.amazon.com/blogs/mobile/understanding-amazon-cognito-authentication-part-3-roles-and-policies/
- 오답 해설:
  - B: `dynamodb:Select`는 요청의 `Select` 파라미터(반환 속성 범위)를 나타내며 항목 소유자를 구분하지 못한다 [S68].
  - C: `aws:SourceIp`는 요청자의 IP 주소를 확인하는 AWS 전역 조건 키이며 항목 소유자와는 무관하다 [S68].
  - D: 조건 없이 `*`를 허용하면 사용자별 격리가 전혀 없다(항목 수준 제한은 `LeadingKeys` 같은 조건 키로 구현한다) [S68].
