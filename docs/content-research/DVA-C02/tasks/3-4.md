### 1. Lambda 배포 패키지 — .zip · 컨테이너 이미지 · 계층 (Skill 3.4.1)

| 구분 | .zip 파일 아카이브 | 컨테이너 이미지 | 계층(layer) |
|---|---|---|---|
| 크기 한도 | API/SDK 직접 업로드 50 MB(zip), 더 크면 S3 경유 · 압축 해제 합계 250 MB(계층·커스텀 런타임 포함) [S1][S2] | 압축 해제 기준 10 GB(모든 이미지 계층 합계) [S1][S4] | 함수당 최대 5개, 크기는 위 250 MB에 합산 [S1][S3] |
| 코드 저장 | 기본은 Lambda 관리 저장소(`COPY`), 선택적으로 내 S3 버킷을 참조(`REFERENCE`, 자체 관리 S3 코드 저장) [S2] | Amazon ECR — 함수와 같은 Region의 리포지토리 [S4] | 계층 버전은 불변 스냅샷, 함수에는 정확한 버전 ARN으로 지정 [S3] |
| 의존성 | zip에 포함하거나 계층으로 분리 | 이미지 안에 전부 포함(계층 사용 불가) [S3] | 코드와 분리해 여러 함수가 공유, 내장 SDK 버전 고정 [S3] |
| 제약 | 패키지 유형(zip↔이미지)은 생성 후 변경 불가 [S2] | Linux 전용, 함수 이미지는 단일 아키텍처만(멀티 아키텍처 불가) [S4] | .zip 함수 전용, 실행 환경의 `/opt`로 추출 [S3] |

- **업로드 경로**: 콘솔 코드 편집기는 스크립트 언어(Node.js·Python·Ruby)에서 쓰며, 코드가 3 MB 초과이거나 라이브러리를 추가하거나 Java·Go·C#이면 .zip을 올려야 한다. .zip이 50 MB 미만이면 로컬에서, 초과면 S3에서 올린다 [S2]. 직접 업로드한 zip은 base64로 변환돼 크기가 약 30% 커지므로 Lambda는 실제 요청 한도를 더 크게 잡고 50 MB는 근사값이다 [S5].
- **컨테이너 이미지 만드는 3가지**: AWS 기본 이미지(런타임·RIC·RIE 내장) / AWS OS 전용 기본 이미지(Go·Rust 등) / 비AWS 기본 이미지(Alpine·Debian 등). 뒤의 두 가지는 런타임 인터페이스 클라이언트(RIC)를 직접 넣어야 한다 [S4]. 매니페스트는 Docker V2 schema 2 또는 OCI(v1.0.0 이상) [S4]. 함수를 만드는 주체에게 ECR 권한(GetRepositoryPolicy·SetRepositoryPolicy·BatchGetImage·GetDownloadUrlForLayer)이 필요하다 [S4].
- **태그는 digest로 고정된다**: Lambda는 이미지 태그를 digest로 해석하므로, ECR에서 같은 태그에 새 이미지를 올려도 함수가 자동으로 바뀌지 않는다 — 코드 업데이트를 다시 해야 한다 [S6].
- **계층**: Go·Rust에는 권장하지 않는다(의존성을 계층에 두면 초기화 때 따로 로드해 콜드 스타트가 늘 수 있음) [S3]. 합계 250 MB에 포함되므로 크기 우회 수단이 아니다 — 원리: 계층은 실행 환경에 풀려 코드와 같은 한도로 계산된다 [S1][S3].
- **IaC·CLI 연계**: `sam deploy`는 .zip이면 S3에, 이미지면 ECR에 올린 뒤 CloudFormation 변경 세트로 배포한다 [S34].

### 2. API Gateway 단계(stage)·배포·카나리 (Skill 3.4.2)

- 배포(deployment)는 API의 스냅샷이고, 단계(stage)는 특정 배포를 가리키는 이름 있는 참조다. 단계에 캐시·스로틀링·로깅·WAF·클라이언트 인증서·스테이지 변수·카나리를 붙인다 [S11][S12]. REST API는 변경을 반영하려면 **재배포**해야 하고, 이전 배포를 다시 활성화해 롤백한다 [S12]. HTTP API도 배포해야 반영되며 자동 배포를 켤 수 있고, `$default` 단계는 URL 루트에서 서비스된다 [S14].
- 재배포가 필요한 업데이트: 메서드·통합·리소스·권한 부여자 같은 **리소스** 업데이트는 필요, **구성** 업데이트는 불필요 [S13]. (단, 로깅 설정 저장 뒤 재배포를 안내하는 문서도 있다 → `확인 필요`.)
- 단계 세부: 이름은 영숫자·하이픈·밑줄, 최대 128자 [S11]. 스로틀링은 최선 노력(비용·차단 수단이 아님)이고 단계 값은 계정 한도를 넘길 수 없다 [S11]. 캐시는 프리티어 비대상 [S11]. CloudWatch Logs를 켜려면 계정 설정에 CloudWatch 로그 역할 ARN이 필요하다 [S11].
- **카나리 릴리스(단계 수준)**: 단계가 운영 릴리스이고, 거기에 `canarySettings`(배포 ID, 트래픽 비율 0.0~100.0, 카나리 전용 스테이지 변수, 스테이지 캐시 사용 여부)를 붙여 요청을 무작위로 나눈다 [S15]. 카나리를 끄고 설정을 제거하기 전에는 단계를 다른 비카나리 배포에 연결할 수 없다 [S15]. 카나리 요청은 `/Canary` 접미어 로그 그룹으로 따로 쌓인다 [S15]. **승격**은 ① 단계의 배포 ID를 카나리 것으로 교체 ② 스테이지 변수 갱신 ③ 카나리 비율 0.0%이며, 승격만으로 카나리가 해제되지는 않는다 [S16]. 원리: 비율이 작고 선택이 무작위라 특정 사용자만 계속 피해를 보지 않는다 [S15].

### 3. 사용자 지정 도메인 (Skill 3.4.2)

| 유형 | 연결 가능 API | ACM 인증서 위치 | 알아둘 점 |
|---|---|---|---|
| 엣지 최적화 | REST API만 [S18] | **us-east-1(버지니아 북부)** [S19] | API Gateway가 CloudFront 배포를 만들어 요청을 받음, 준비에 약 40분, DNS는 `distribution-id.cloudfront.net`으로, `cloudfront:updateDistribution` 권한 필요 [S19] |
| Regional | REST·HTTP API를 같은 도메인에 연결, mTLS, 다단계 경로 매핑 [S18] | **API와 같은 Region** [S20] | 다단계 매핑은 TLS 1.2 보안 정책 필요 [S17], 서비스 연결 역할 `AWSServiceRoleForAPIGateway` 생성 [S20], DNS는 Route 53이면 A 별칭·타사 DNS면 CNAME [S20] |
| 프라이빗 | 프라이빗 API [S22] | ACM(와일드카드 인증서 가능) [S22] | 프로비저닝 약 15분, 호출하려면 VPC 엔드포인트와 도메인 이름 액세스 연결 필요, 보안 정책 TLS-1-2 고정, 와일드카드 도메인 이름·다단계 base path 매핑 미지원 [S22] |

- 공통: 도메인을 미리 등록(Route 53 또는 타사)하고 ACM 인증서를 준비한다(ACM이 없는 Region이면 가져오기) [S17]. 퍼블릭 도메인 이름은 Region 안에서 모든 계정에 걸쳐 고유해야 하나 프라이빗은 계정 간 중복 가능 [S17][S22]. 기본 `execute-api` 엔드포인트를 끌 수 있고 이때 접근하면 403 [S17]. 와일드카드(`*.example.com`)로 고객별 서브도메인을 무제한에 가깝게 지원 [S17]. 엣지↔Regional은 마이그레이션 가능하지만 퍼블릭→프라이빗은 불가 [S17][S21].
- 원리(문서의 설명): 엣지 최적화 도메인에 쓰는 us-east-1 ACM 인증서는 모든 지리적 위치로 배포되고, Regional 도메인은 API가 있는 Region의 인증서를 쓴다. us-east-1이 아닌 Region의 API를 엣지에서 Regional 도메인으로 옮길 때는 API가 있는 Region에서 새 ACM 인증서를 요청한다 [S21].
- **경로 연결 방식**: API 매핑(기본 경로 매핑)으로 도메인+기본 경로를 `API+단계`에 연결하거나, 라우팅 규칙(예: Host 헤더 조건으로 `*.example.com`을 서로 다른 REST API로 분배)으로 대상 API를 고른다 [S17]. 프라이빗 도메인은 다단계 base path 매핑이 없어 규칙의 경로 조건으로 대신한다 [S22]. 라우팅 모드는 `API_MAPPING_ONLY`(기본, 기존·신규 도메인 모두) / `ROUTING_RULE_THEN_API_MAPPING`(규칙이 매핑보다 우선) / `ROUTING_RULE_ONLY` [S23]. `apigateway`로 도메인을 만들 때(AWS CLI·CloudFormation·SDK, 콘솔 제외)는 `API_MAPPING_ONLY`가 `BASE_PATH_MAPPING_ONLY`, `ROUTING_RULE_THEN_API_MAPPING`이 `ROUTING_RULE_THEN_BASE_PATH_MAPPING`으로 불린다 [S23].

### 4. IaC 템플릿 업데이트 — CloudFormation · SAM (Skill 3.4.3)

| CloudFormation 업데이트 동작 | 의미 [S29] |
|---|---|
| Update with No Interruption | 중단·물리 ID 변경 없이 갱신 |
| Updates with Some Interruption | 일시 중단이 있을 수 있음(예: EC2 인스턴스 일부 속성) |
| Replacement | 새 물리 ID로 리소스를 다시 만듦 — 보통 새 리소스를 먼저 만들고 참조를 옮긴 뒤 옛 리소스를 삭제 |

- 변경 세트(change set): 만들기 → 보기(추가·수정·삭제·교체 미리보기) → (선택) 다른 세트 만들기 → 실행. 실행하면 그 스택의 다른 변경 세트는 제거된다. 성공을 보장하지 않는다 — 생성 때 구문 오류·이름 충돌·쿼터를 검사하지만 사용자 지정 리소스 같은 런타임 실패는 실행 중 날 수 있다 [S30].
- 롤백: 업데이트가 실패하면 롤백하며, 롤백까지 실패하면 `UPDATE_ROLLBACK_FAILED`(업데이트 불가)가 되고 원인을 고친 뒤 ContinueUpdateRollback으로 `UPDATE_ROLLBACK_COMPLETE`로 돌린다 [S32]. **롤백 트리거**는 CloudWatch 경보가 `ALARM`이면 스택 작업 전체를 롤백하며(`INSUFFICIENT_DATA`는 기본적으로 롤백 사유가 아님), 모니터링 시간은 기본 0분~최대 180분, 트리거는 최대 5개 [S31].
- **CodePipeline의 CloudFormation 배포 작업**: `CREATE_UPDATE`(없으면 생성·있으면 갱신, 실패 상태 스택은 그대로 둠) / `CHANGE_SET_REPLACE`+`CHANGE_SET_EXECUTE`(변경 세트 생성 → (사이에 승인 작업을 둘 수 있음) → 실행) / `REPLACE_ON_FAILURE`(실패 상태면 삭제 후 재생성, 테스트 전용 권장) / `DELETE_ONLY` [S63]. 환경별 값은 `TemplateConfiguration`(템플릿 구성 파일: 파라미터 값·스택 정책)과 `ParameterOverrides`(실행 중에야 알 수 있는 값에만 권장)로 넣는다. IAM 리소스·매크로가 있으면 `Capabilities`(`CAPABILITY_IAM` 등)가 필요하다 [S63].
- **SAM**: CloudFormation을 확장한 축약 구문 + 로컬 개발·배포 CLI [S36]. `sam deploy --guided`가 대화형으로 설정을 받아 `samconfig.toml`에 저장하고, 이후 `sam deploy`만으로 재배포한다. 흐름은 패키징(S3/ECR 업로드) → 변경 세트 생성 → 스택 배포이며, "Confirm changes before deploy"(변경 세트 미리보기)·"Allow SAM CLI IAM role creation"(`CAPABILITY_IAM`)·"Disable rollback" 프롬프트가 있다 [S34]. `sam sync`는 로컬 변경을 클라우드로 동기화해 개발·테스트 속도를 높이는 도구다 [S36].
- SAM의 점진 배포: 함수에 `AutoPublishAlias`(새 코드를 감지하면 버전 발행 + 별칭 이동)와 `DeploymentPreference`(Type·Alarms·Hooks 등)를 쓰면 CodeDeploy 리소스가 자동 생성된다 [S33][S35]. 첫 점진 배포는 CodeDeploy가 옮길 이전 버전이 필요해 **2단계**(① `AutoPublishAlias`만 배포 ② `DeploymentPreference` 추가)로 한다 [S33].

### 5. 애플리케이션 환경 관리 (Skill 3.4.4)

| 서비스 | '환경'을 나누는 단위 | 포인트 |
|---|---|---|
| CodePipeline | 단계(stage) — 환경을 격리하고 그 환경에 동시에 들어가는 변경 수를 제한하는 논리 단위 [S57] | 한 단계는 한 번에 하나의 실행만 처리(단계 잠금), 진입 전환(transition)을 꺼 두면 실행이 대기 [S57] |
| Elastic Beanstalk | 환경 — 웹 서버/워커 티어, 단일 인스턴스 vs 로드 밸런싱 [S56] | dev·test는 단일 인스턴스로 비용 절감, 운영은 로드 밸런싱으로 [S56]. 환경을 복제해 새 버전 배포 후 URL 교체 = blue/green [S54]. 애플리케이션 버전 라벨·수명 주기 정책 [S55] |
| API Gateway | 단계 + 스테이징 변수 [S11][S24] | 같은 API 정의에 단계별 백엔드·값을 바꿔 연결(3.4.10) |
| Lambda | 버전 + 별칭(예: live·beta) [S7][S8] | 별칭은 함수 **버전**만 가리키며 별칭→별칭은 불가, 이벤트 소스·권한 정책에 별칭 ARN을 쓰면 버전이 바뀌어도 수정 불필요 [S10] |
| CloudFormation | 스택 + 템플릿 구성 파일(`TemplateConfiguration`)·`ParameterOverrides` [S63] | 같은 템플릿에 환경별 파라미터 값을 주입 |
| Amplify Hosting | Git 분기별 배포(main=운영, develop=통합 등) [S74] | 패턴 기반 기능 분기(feature branch) 배포 지원 [S74] |

환경 구성값(AppConfig·Parameter Store 등) 관리는 Task 3.1·2.3 노트 참조.

### 6. 배포 전략 한눈에 보기 (Skill 3.4.5 · 3.4.11)

| 롤링 / in-place | 배치 단위로 기존 인스턴스에 순차 배포 | Beanstalk `Rolling` [S52], CodeDeploy EC2 in-place(`OneAtATime`·`HalfAtATime`) [S38], ECS 롤링(`minimumHealthyPercent`·`maximumPercent`) [S46] |
| 추가 배치 롤링 | 먼저 새 배치를 띄워 용량 유지 | Beanstalk `RollingWithAdditionalBatch` [S52] |

| Blue/green | 새 환경을 병렬로 만들고 트래픽만 전환 | CodeDeploy(EC2는 대체 인스턴스, Lambda·ECS는 항상 blue/green) [S37], ECS 내장 [S47], Beanstalk CNAME 교체 [S54] |
| Canary | 소량 먼저 → 대기 → 나머지 일괄 | CodeDeploy Lambda/ECS [S38], SAM [S33], Lambda 가중치 별칭 [S9], API Gateway 단계 카나리 [S15], Beanstalk Traffic splitting [S52], ECS 내장 [S50] |
| Linear | 같은 비율을 같은 간격으로 반복 | CodeDeploy Lambda/ECS [S38], SAM [S33], ECS 내장 [S50] |

| Lambda | `LambdaCanary10Percent5Minutes`/`10Minutes`/`15Minutes`/`30Minutes` · `LambdaLinear10PercentEvery1Minute`/`2Minutes`/`3Minutes`/`10Minutes` · `LambdaAllAtOnce` |
| ECS | `ECSCanary10Percent5Minutes`/`15Minutes` · `ECSLinear10PercentEvery1Minutes`/`3Minutes` · `ECSAllAtOnce`(Network Load Balancer는 이것만 지원) |

### 7. CodeDeploy 상세 — 플랫폼·AppSpec·훅 (Skill 3.4.5 · 3.4.7 · 3.4.11)

- **3개 컴퓨트 플랫폼**: EC2/온프레미스, Lambda, ECS [S37]. 배포 유형은 in-place(EC2/온프레미스 전용)와 blue/green이며, Lambda·ECS 배포는 항상 blue/green이다. EC2 blue/green은 EC2 인스턴스만 되고 온프레미스는 불가 [S37]. EC2/온프레미스는 인스턴스의 CodeDeploy 에이전트가 CodeDeploy를 폴링해 S3/GitHub의 개정(revision)을 가져와 AppSpec대로 배포한다(blue/green 요건으로 에이전트 실행과 IAM 인스턴스 프로파일이 명시됨) [S37].
- **EC2 blue/green 흐름**: 대체 인스턴스 준비(ASG 복사 또는 수동 지정) → 개정 설치 → (선택) 대기 시간 → 대체 인스턴스를 로드 밸런서에 등록해 트래픽 이동 → 원래 인스턴스는 등록 해제 후 종료 또는 유지. 대기 시간 안에 수동 전환하지 않으면 배포가 중지된다 [S37].
- **AppSpec**: EC2/온프레미스는 `appspec.yml`을 개정 **루트**에 두고(아니면 배포 실패), 구조는 `version`(0.0 고정)·`os`(linux/windows)·`files`·`permissions`·`hooks` [S42][S40]. Lambda·ECS는 `Resources` 섹션과 `hooks`(Lambda 검증 함수) — Lambda의 `Resources`는 `Name`·`Alias`·`CurrentVersion`·`TargetVersion` [S41]. Lambda·ECS의 개정은 AppSpec 파일 자체다 [S37].
- **훅(수명 주기 이벤트)**: 

| 플랫폼 | 사용할 수 있는 훅 | 메모 |
|---|---|---|
| EC2/온프레미스 | `ApplicationStop` → (`DownloadBundle`) → `BeforeInstall` → (`Install`) → `AfterInstall` → `ApplicationStart` → `ValidateService`, 로드 밸런서를 지정하면 `BeforeBlockTraffic`·`AfterBlockTraffic`·`BeforeAllowTraffic`·`AfterAllowTraffic` 추가 | 괄호 항목은 에이전트 예약(스크립트 불가). `ApplicationStop`은 이전 성공 개정의 AppSpec·스크립트를 쓰므로 인스턴스에 **처음 배포할 때는 실행되지 않음**. 훅 `timeout` 기본 3600초(최대 1시간) [S39] |
| Lambda | `BeforeAllowTraffic`, `AfterAllowTraffic`(검증용 Lambda 함수 1개씩, 배포당 1회) | 검증 함수가 `putLifecycleEventHookExecutionStatus`로 Succeeded/Failed를 알려야 하고 1시간 안에 통지가 없으면 배포 실패 [S39] |
| ECS | `BeforeInstall`·`AfterInstall`·`AfterAllowTestTraffic`·`BeforeAllowTraffic`·`AfterAllowTraffic` | `BeforeInstall` 시점엔 롤백 불가, 나머지 훅 결과는 롤백을 유발할 수 있음 [S39] |

- **ECS용 CodeDeploy**: AppSpec에 작업 정의 전체 ARN과 컨테이너 이름·포트를 적고, ALB 또는 NLB에 프로덕션 리스너(+선택적 테스트 리스너)와 대상 그룹이 필요하다 [S48]. 새 작업 세트(task set)에 트래픽을 옮기고 성공하면 원래 작업 세트를 종료한다 [S37]. 오토 스케일링 중 배포가 시작되면 green 작업 세트가 안정 상태가 될 때까지 최대 1시간 기다린다 [S48].
- **모니터링·롤백 설정**(배포 그룹): CloudWatch 경보를 최대 10개 연결해 울리면 배포를 중지, SNS 알림 트리거, 자동 롤백 두 가지(배포 실패 시 / 경보 임계 충족 시), 롤백 설정은 배포 단위로 재정의 가능, 경보 상태를 못 읽어도 계속할지 선택(`ignorePollAlarmFailure`) [S44][S45]. EC2는 배포 중 ASG에 뜬 인스턴스에 옛 개정이 들어갈 수 있어 후속 배포로 갱신하는 `outdatedInstancesStrategy`(UPDATE/IGNORE)가 있다 [S44].

### 8. Lambda 점진 배포 — 버전·별칭·가중치·SAM·CodePipeline (Skill 3.4.5 · 3.4.9 · 3.4.11)

- 게시된 버전은 코드·런타임·계층·메모리 등 대부분의 설정이 불변이고 `$LATEST`만 바꿀 수 있다. 번호는 재사용되지 않는다 [S7]. 별칭은 버전 하나를 가리키는 갱신 가능한 포인터이고, **가중치 별칭**은 최대 2개 버전을 가리키며 두 버전 모두 게시되어야 하고 `$LATEST` 불가, 같은 실행 역할·같은 DLQ 설정이 필요하다 [S9].
- 가중치 별칭은 카나리 배포의 기반 기능이다 — CodeDeploy와 SAM의 점진 배포가 이 기능 위에서 동작한다 [S9]. 어떤 버전이 실행됐는지는 `START` 로그의 Version 값과 동기 호출 응답의 `x-amz-executed-version` 헤더로 안다 [S9].

| 방법 | 자동 롤백 | 사전·사후 검증 | 설정 위치 |
|---|---|---|---|
| 가중치 별칭 직접 조작(`AdditionalVersionWeights`) | 없음 — `update-alias`로 직접 되돌림 | 직접 구현 | CLI·콘솔 [S9] |
| SAM `DeploymentPreference` | 경보·훅 실패 시 CodeDeploy가 롤백 | `Hooks`의 `PreTraffic`·`PostTraffic` | SAM 템플릿 [S33] |
| CodeDeploy 직접 | 배포 그룹의 자동 롤백 설정 | AppSpec `hooks` | AppSpec [S41][S44] |
| CodePipeline Lambda 배포 작업 | 경보(최대 10개)가 `ALARM`이면 작업 실패 | — | `DeployStrategy`(기본 `AllAtOnce`), 총 대기 최대 2일 [S64] |

- CodePipeline Lambda 배포 작업의 `FunctionAlias`는 작업 시작 시 이미 존재하고 버전이 하나 있어야 하며(롤백 대상 버전), 생략하면 `$LATEST`에 배포하고 새 버전을 만든다(전략·대상 버전 옵션 불가) [S64]. 이 작업은 2025-05에 추가됐다 [S65].

### 9. ECS 배포 전략 (Skill 3.4.5 · 3.4.8 · 3.4.11)

| 방식 | 핵심 | 근거 |
|---|---|---|
| 롤링(`ECS`) | `minimumHealthyPercent`(올림)·`maximumPercent`(내림)로 교체 속도 결정. 실패 감지는 **회로 차단기**(작업이 시작되지 못할 때)와 **CloudWatch 경보**(애플리케이션 지표) — 함께 쓰면 먼저 충족한 쪽이 실패 처리, 둘 다 이전 서비스 리비전으로 롤백 가능 | [S46] |
| 내장 blue/green(`BLUE_GREEN`) | green 서비스 리비전을 병렬로 띄워 테스트 트래픽으로 검증 후 전환. bake time(전환 후 blue·green 동시 유지) 동안 blue를 유지해 빠르게 롤백. 수명 주기 훅은 Lambda 훅과 일시 중지(pause) 훅(`ContinueServiceDeployment`). NLB 사용 시 `TEST_TRAFFIC_SHIFT`·`PRODUCTION_TRAFFIC_SHIFT` 단계에 10분 추가. 배포 중 자원 사용이 일시적으로 2배가 될 수 있음 | [S47] |
| 내장 linear·canary | 2025-10 출시. step 비율·bake time 설정, 훅·경보로 검증·자동 롤백. ALB·Service Connect 지원, NLB는 2026-02 추가 | [S50][S51] |
| CodeDeploy blue/green(task set) | AppSpec+배포 그룹, 미리 정의된 canary/linear/all-at-once 구성, NLB는 `ECSAllAtOnce`만 | [S38][S48] |

- ECS 개발자 가이드의 CodeDeploy 방식 페이지는 첫머리에서 ECS 내장 blue/green 배포 사용을 권장한다고 안내한다 [S48]. 내장 blue/green은 2025-07 출시 [S49].
- 컨테이너 이미지 태그는 기본으로 digest로 해석돼 서비스의 모든 작업이 같은 이미지를 쓴다(`versionConsistency`) [S46].

### 10. Elastic Beanstalk 배포 정책 (Skill 3.4.5 · 3.4.8 · 3.4.11)

| 정책 | 중단 | 속도 | 실패 시 영향 | 롤백 | 코드가 배포되는 곳 | 지원 환경 |
|---|---|---|---|---|---|---|
| All at once | 있음 | 가장 빠름 | 다운타임 | 수동 재배포 | 기존 인스턴스 | 전부 |
| Rolling | 없음 | 보통 | 한 배치 중단, 성공 배치는 신버전 | 수동 재배포 | 기존 | 로드 밸런싱만 |
| Rolling with additional batch | 없음 | 느림 | 첫 배치 실패면 최소 | 수동 재배포 | 신규+기존 | 로드 밸런싱만 |
| Immutable | 없음 | 가장 느림 | 최소 | 새 인스턴스 종료 | 신규 | 단일·로드 밸런싱 |
| Traffic splitting | 없음 | 가장 느림(평가 시간에 좌우) | 일부 트래픽만 잠시 영향 | 트래픽 복귀 + 새 인스턴스 종료 | 신규 | 로드 밸런싱(**ALB** 필요) |
| Blue/green(URL 교체) | 없음 | 가장 느림 | 최소 | URL(CNAME) 교체 | 신규 | 별도 환경 필요, DNS 변경 있음 |

위 표 출처 [S53]. 옵션 이름은 `aws:elasticbeanstalk:command` 네임스페이스의 `DeploymentPolicy`(`AllAtOnce`·`Rolling`·`RollingWithAdditionalBatch`·`Immutable`·`TrafficSplitting`), 트래픽 분할은 `aws:elasticbeanstalk:trafficsplitting`이다 [S52].

- 기본은 all-at-once이고, EB CLI로 만든 확장 가능(scalable) 환경은 rolling이다 [S52]. 배치 크기는 비율 또는 고정 수. **Ignore health check**(실패해도 롤백하지 않음)·**Healthy threshold**·**Command timeout**으로 헬스 체크 동작을 조절한다 [S52].
- Immutable은 부분적으로 끝난 롤링 배포의 문제를 막는다(새 인스턴스가 헬스 체크에 실패하면 새 인스턴스만 종료, 기존은 그대로). Traffic splitting은 Immutable처럼 새 인스턴스를 띄운 뒤 일정 비율을 평가 시간 동안 보내며, 중단(Abort current operation·`AbortEnvironmentUpdate`)하면 트래픽을 되돌린다 [S52]. Immutable·트래픽 분할은 EC2 버스트 잔액이 사라진다 [S52].
- Blue/green(CNAME 교체): 환경 복제 → 새 버전 배포·테스트 → "Swap environment URLs". 호환되지 않는 플랫폼 버전으로 올릴 때도 필요하다. 환경 안에 Beanstalk이 만든 DB가 있으면 보존되지 않으므로 외부 DB(RDS)와 분리해야 하고, DNS 캐시가 만료되기 전에는 옛 환경을 종료하지 않는다 [S54].
- 소스 번들(애플리케이션 버전)의 파일 크기 한도는 500 MB [S55].

### 11. 커밋 → 빌드·테스트·배포 (Skill 3.4.6)

- **CodePipeline 구조**: 파이프라인 = 단계(stage)들, 단계 = 직렬·병렬 작업(action)들. 작업 유형은 `source`·`build`·`test`·`deploy`·`approval`·`invoke` 6가지 [S57]. 작업 사이의 산출물은 아티팩트 버킷을 거쳐 전달된다 [S57]. 소스 리비전은 GitHub·CodeCommit이면 커밋, S3면 객체 버전이다 [S57].
- **변경 감지(트리거)**: CodeCommit·S3는 EventBridge 규칙이 권장이고(콘솔 마법사가 만든다) 폴링은 비권장 [S60][S61]. Bitbucket Cloud·GitHub·GitHub Enterprise Server·GitLab은 **연결(connection)** 작업이 변경 감지를 관리해 웹훅·폴링 설정이 필요 없다 [S61]. ECR 소스도 EventBridge [S61]. 소스 작업당 트리거는 1개 [S60]. 그 밖에 수동 시작·일정(schedule)·소스 리비전 재지정·스테이지 롤백 트리거가 있다 [S60]. 문서에는 CloudWatch Events와 EventBridge 표기가 섞여 있다 [S57][S61].
- **V2 파이프라인 트리거**: push는 Git 태그·브랜치·파일 경로로, 풀 리퀘스트는 이벤트(opened/updated/closed)·브랜치·파일 경로로 필터한다 [S57][S59]. `WebhookV2`가 Git 태그 시작 트리거다 [S60]. 30일 넘게 비활성인 파이프라인은 폴링이 꺼진다 [S57].
- **CodeCommit 상태**: 공식 사용자 가이드 문서 이력에 2025-11-25 "신규 고객 이용 가능"으로 기록되어 있고 DevOps 블로그도 GA 복귀를 알렸다(2024-07의 'de-emphasize' 방침을 되돌림) [S70][S71].
- **CodeBuild `buildspec`**: 기본 파일명은 소스 루트의 `buildspec.yml`(다른 이름·위치, 같은 Region의 S3도 가능, 프로젝트당 1개) [S68]. 구조: `version`(0.2 권장)·`run-as`·`env`·`phases`·`reports`·`artifacts`·`cache`.

| phase | 용도(문서의 예) [S68] |
|---|---|
| `install` | 빌드 환경 패키지 설치, `runtime-versions`(버전 명시 권장) |
| `pre_build` | ECR 로그인, 의존성 설치 |
| `build` | 테스트·컴파일 실행 |
| `post_build` | JAR/WAR 패키징, Docker 이미지 ECR 푸시, SNS 알림 |

- phase마다 `on-failure`(`ABORT`·`CONTINUE`·`RETRY…`)와 `finally`(앞 명령이 실패해도 실행)가 있다 [S68]. `env`: `variables`(평문)·`parameter-store`(서비스 역할에 `ssm:GetParameters` 필요)·`secrets-manager`·`exported-variables`·`git-credential-helper`. 같은 변수가 여러 곳에 있으면 StartBuild 호출 > 프로젝트 정의 > buildspec 순으로 우선한다 [S68].
- CodeBuild는 소스 저장소 웹훅으로 직접 시작할 수도 있다 — 필터 `EVENT`(PUSH·PULL_REQUEST_*)·`HEAD_REF`·`BASE_REF`·`FILE_PATH`·`COMMIT_MESSAGE`·`ACTOR_ACCOUNT_ID`, 정규식 패턴과 `excludeMatchedPattern` [S69].

### 12. 오케스트레이션된 워크플로 — 환경별 배포·승인 (Skill 3.4.7)

- 환경마다 단계를 두는 전형: Source → Build(CodeBuild) → Deploy(dev) → (테스트) → **Approval** → Deploy(prod). 단계는 한 번에 하나의 실행만 처리하고(잠금), 기본 실행 모드 `SUPERSEDED`에서는 새 실행이 대기 중 실행을 대체한다. 다른 모드는 `QUEUED`·`PARALLEL`(V2) [S57][S59].
- **수동 승인 작업**: 파이프라인이 그 작업에서 멈추고, 같은 Region의 SNS 주제로 알림·검토 URL·코멘트를 줄 수 있다. 승인하면 재개, 거부하거나 **7일** 안에 응답이 없으면 실패 처리 [S58].
- 환경별 설정 주입: CloudFormation 작업의 `TemplateConfiguration`·`ParameterOverrides` [S63], V2 파이프라인 변수(`#{variables.이름}` 표기)·단계 조건(conditions)·단계 자동 재시도 [S57][S59][S64].
- 배포 작업 provider 예: Amazon EC2·EKS·S3·AppConfig·CloudFormation·CloudFormation StackSets·ECS·Elastic Beanstalk·CodeDeploy 등 [S67]. ECS는 "CodeDeployToECS"(blue/green) 작업과 표준 ECS 배포 작업이 따로 있다 [S66].
- 원리(단계=환경 경계): 단계가 환경을 격리하고 그 환경에 동시에 들어가는 변경 수를 제한하므로, dev 통과 → 승인 → prod 같은 순차 승격을 파이프라인 구조로 표현할 수 있다 [S57].

### 13. 롤백 (Skill 3.4.8)

| 대상 | 롤백 방식 | 근거 |
|---|---|---|
| CodeDeploy 공통 | 이전에 배포한 개정을 **새 배포(새 배포 ID)** 로 재배포. 자동(배포 실패·경보)·수동 | [S43] |
| CodeDeploy EC2 in-place | 직전 성공 설치가 만든 파일을 정리(cleanup 파일)한 뒤 재배포. 스크립트가 만든 파일은 되돌리지 않음, 콘텐츠 처리 옵션(실패/덮어쓰기/유지)에 따라 유지하려던 파일이 사라질 수 있음 | [S43] |
| CodeDeploy EC2 blue/green | 원래 인스턴스가 종료 전이면 트래픽을 되돌려 더 빠르고 안정적 | [S37] |
| CodeDeploy Lambda·ECS | 사전·사후 훅 실패나 경보로 롤백, ECS `BeforeInstall`에선 롤백 불가 | [S33][S39][S44] |
| ECS 롤링 | 회로 차단기·경보가 이전 서비스 리비전으로 롤백 | [S46] |
| ECS 내장 blue/green | bake time 동안 blue 유지, 다운타임 없는 롤백 | [S47][S50] |
| Beanstalk | 정책별: 수동 재배포 / 새 인스턴스 종료 / 트래픽 복귀 / URL 교체. 롤링 중 실패하면 일부 배치만 신버전이므로 알려진 정상 버전을 재배포 | [S52][S53] |
| Lambda 별칭 | 별칭을 이전 버전으로 되돌림(가중치 별칭 문서는 소량 트래픽으로 새 버전을 시험하다 필요하면 빠르게 롤백하는 용도로 설명) | [S9] |
| API Gateway | 이전 배포를 다시 활성화, 카나리는 해제(Turn off) | [S12][S15] |
| CloudFormation | 실패 시 롤백, `UPDATE_ROLLBACK_FAILED`→ContinueUpdateRollback, 롤백 트리거(경보) | [S31][S32] |
| CodePipeline(V2) | 단계를 이전의 성공 실행으로 롤백(수동·자동). 롤백 실행(rolled-back execution)으로 기록되며 대상 실행의 소스 리비전·변수를 다시 사용. 자동 롤백은 현재 파이프라인 구조 버전에서 시작된 성공 실행이 있어야 함 | [S57][S62] |

원리: CodeDeploy는 롤백을 상태 되감기가 아니라 이전 개정을 새 배포로 다시 내보내는 방식으로 구현하므로 EC2에서는 스크립트가 만든 부수 효과가 남을 수 있다. 반대로 blue/green·bake time·URL 교체는 옛 환경(또는 옛 리비전)을 살려 둔 채 트래픽만 돌리므로 되돌림이 단순하다 [S43][S37][S47][S53].

### 14. 레이블·분기·태그로 버전·릴리스 관리 (Skill 3.4.9)

> 공식 가이드는 'labels'가 가리키는 서비스를 지정하지 않는다. 이 노트는 Git 분기·태그, 컨테이너 이미지 태그, Lambda 버전·별칭, Beanstalk 애플리케이션 버전 라벨, Amplify 분기로 해석했다(`확인 필요`).

- **Git 분기·태그 → 배포**: V2 파이프라인은 Git 태그·브랜치·파일 경로로 시작을 필터하고(`WebhookV2`=태그) [S57][S60], CodeBuild 웹훅은 `HEAD_REF`·`BASE_REF`(예 `^refs/heads/main$`)·이벤트로 필터하며 `excludeMatchedPattern`으로 태그 이벤트를 제외할 수 있다 [S69]. Amplify Hosting은 feature branch·GitFlow 워크플로에 맞춰 분기를 연결할 때마다 새 배포를 만들며, 보통 main=운영·develop=통합으로 쓰고 패턴 기반 기능 분기 배포도 지원한다 [S74].
- **컨테이너 이미지 태그**: ECR 태그 불변성을 켜면 같은 태그로 푸시할 때 `ImageTagAlreadyExistsException`이 난다. 예외 필터(`IMMUTABLE_WITH_EXCLUSION`)로 일부 태그만 덮어쓰기를 허용할 수 있다 [S72]. `latest`처럼 덮어써지는 태그보다 커밋 해시 등 서술적 태그가 낫다 [S73]. Lambda·ECS는 태그를 digest로 해석해 고정한다 [S6][S46].
- **Lambda**: 게시 버전은 불변 스냅샷, 별칭은 이동 가능한 포인터 — 새 코드마다 버전을 발행하고 별칭을 옮겨 릴리스한다(SAM `AutoPublishAlias`가 이를 자동화) [S7][S8][S33].
- **Beanstalk**: 애플리케이션 버전 = 라벨이 붙은 배포 가능한 반복(소스 번들은 S3). 수명 주기 정책으로 개수(예: 25개 초과 시 가장 오래된 것 삭제)·기간(예: 90일)을 정해 오래된 버전을 정리하되 S3 소스 번들은 자동 삭제되지 않는다 [S55].
- 원리: 태그·`$LATEST`는 덮어쓸 수 있는 가변 참조이고 버전 번호·digest는 불변 식별자이므로, 추적·롤백이 필요한 릴리스는 불변 식별자를 기준으로 배포한다 [S6][S7][S72].

### 15. 스테이징 변수로 동적 배포 (Skill 3.4.10)

| 스테이징 변수를 쓸 수 있는 곳 [S25] | 예 |
|---|---|
| HTTP 통합 URI | URI의 도메인·서브도메인·경로·쿼리 문자열 자리에 `${stageVariables.url}` 형태로 삽입 |
| Lambda 함수 이름 또는 버전/별칭 | `…function:${stageVariables.fn}/invocations`, `…function:<이름>:${stageVariables.alias}/invocations` |
| 매핑 템플릿·파라미터 매핑 | `$stageVariables.이름`, `stageVariables.이름` |
| Cognito 사용자 풀(`COGNITO_USER_POOLS` 권한 부여자), AWS 통합 자격 증명 ARN | `userpool/${stageVariables.이름}` |

- 쓰임: 단계마다 다른 백엔드 엔드포인트나 Lambda 이름·별칭을 가리키고, 매핑 템플릿으로 단계별 값(예: DynamoDB 테이블 이름)을 Lambda에 넘긴다. 한 단계에서 HTTP 프록시와 Lambda 프록시처럼 통합 **유형** 자체를 바꿀 수는 없다 [S24].
- **권한**: Lambda 이름을 스테이징 변수 값으로 지정하면 Lambda 함수의 리소스 기반 권한을 **직접** 설정해야 한다(`aws lambda add-permission --principal apigateway.amazonaws.com --source-arn arn:aws:execute-api:…`). 콘솔에서 지정하면 필요한 권한을 설정하는 CLI 명령이 팝업으로 안내된다 [S24]. 스테이징 변수로 지정하는 Lambda는 API와 **같은 계정**이어야 한다 [S25].
- **민감 정보 금지**: 자격 증명 같은 값은 넣지 말고 Lambda 권한 부여자(authorizer) 출력으로 전달한다 [S24].
- Lambda 함수 안에서 읽기: 프록시 통합이면 API Gateway가 보내는 이벤트에 `stageVariables` 필드가 있다(문서 예시 이벤트에서는 null) [S26].
- 이름·값 형식: CloudFormation `AWS::ApiGateway::Stage`는 변수 이름을 영숫자로 제한하고 값은 `[A-Za-z0-9-._~:/?#&=,]+` 패턴이어야 한다 [S27].
- 카나리와 결합: 카나리 설정의 스테이지 변수 override로 같은 단계 안에서 일부 요청만 다른 Lambda 별칭을 호출하게 만들 수 있다 [S15].
- 표준 패턴: 단계마다 `alias` 변수(`prod`·`dev`)를 두고 통합을 `…function:이름:${stageVariables.alias}`로 구성 → 배포 때는 변수 값만 바꿔 별칭을 전환한다. AWS 백서도 스테이징 변수+Lambda 별칭으로 통합을 분리해 배포를 단순화한다고 설명한다 [S28]. 함수 **환경 변수**는 게시 버전에 고정(불변)되는 별개의 설정이다 [S7].

## 시험에서 묻는 방식

> 문제 저작자를 위한 제안이며 '시험이 반드시 이렇게 낸다'는 단정이 아니다.

1. **Lambda 점진 배포·자동 롤백 (3.4.3·3.4.5·3.4.8·3.4.11)**
   - 상황: "SAM으로 배포하는 함수의 새 버전에 트래픽을 일부만 먼저 보내고, 경보가 울리면 자동으로 이전 버전으로 되돌리되 설정은 최소화하고 싶다. 배포 전·후 검증 함수도 돌리고 싶다."
   - 정답 단서: `AutoPublishAlias` + `DeploymentPreference`(`Canary…`·`Linear…`) + `Alarms` + `Hooks`(`PreTraffic`/`PostTraffic`) → CodeDeploy가 자동 생성 [S33]. 오답 단서: 가중치 별칭 수동 조작(자동 롤백 없음) [S9], API Gateway 카나리(API 배포 간 분할) [S15].
2. **Beanstalk 배포 정책 선택 (3.4.5·3.4.8·3.4.11)**
   - 상황: "중단 없이 배포하고, 새 버전이 실패해도 기존 인스턴스를 건드리지 않으며 롤백이 쉬워야 한다" / "새 버전에 트래픽 일부만 먼저 보내 평가하고 싶다" / "운영 URL을 DNS로 한 번에 바꾸고 즉시 되돌리고 싶다" / "가장 빠르게, 짧은 중단은 허용".
   - 정답 단서: Immutable(기존 인스턴스 그대로, 새 인스턴스만 종료) / Traffic splitting(ALB·평가 시간) / blue/green(환경 복제 + Swap environment URLs, DNS 변경) / All at once [S52][S53][S54].
3. **커밋→파이프라인→승인→롤백 (3.4.6·3.4.7·3.4.8)**
   - 상황: "커밋하면 자동으로 빌드·테스트하고, 스테이징 배포 뒤 사람이 승인해야 운영에 배포되며, 실패한 단계는 직전 성공 상태로 되돌리고 싶다." / "Git 태그를 푸시할 때만 파이프라인을 시작하고 싶다."
   - 정답 단서: CodePipeline(Source → CodeBuild(`buildspec.yml`) → Deploy → **Manual approval**(SNS 알림, 7일) → Deploy), V2의 단계 롤백·Git 태그 트리거(`WebhookV2`), GitHub·GitLab 소스는 연결(connection), CodeCommit·S3는 EventBridge [S57][S58][S59][S60][S61][S62].
4. **API Gateway 단계·도메인·스테이징 변수 (3.4.2·3.4.4·3.4.10)**
   - 상황: "같은 API 정의로 dev·prod 단계가 서로 다른 Lambda 별칭을 호출해야 하는데 호출이 실패한다" / "전 세계 사용자를 위한 엣지 최적화 사용자 지정 도메인에 쓸 ACM 인증서는 어디에 만드나?" / "한 도메인으로 여러 API를 경로별로 나누고 싶다."
   - 정답 단서: 스테이징 변수(`${stageVariables.alias}`) + Lambda 리소스 기반 권한 수동 추가(`add-permission`) [S24][S25]; 엣지=us-east-1, Regional=API와 같은 Region [S19][S20]; API 매핑·라우팅 규칙(라우팅 모드) [S17][S23].

### 문항 후보 1
- 대응 Skill: 3.4.1 / 난이도: foundational
- 문제: 한 팀이 Python Lambda 함수를 만들고 있다. 의존 라이브러리를 포함한 배포 패키지가 압축을 풀면 약 600 MB이다. 가장 적절한 패키징·배포 방식은?
- 보기:
  - A. .zip으로 묶어 Amazon S3에 올린 뒤 S3 위치로 함수 코드를 배포한다.
  - B. 의존 라이브러리를 Lambda 계층 5개에 나누어 담는다.
  - C. 컨테이너 이미지로 패키징해 Amazon ECR에 푸시하고 이미지 URI로 함수를 만든다.
  - D. Service Quotas에서 배포 패키지 크기 한도 상향을 요청한다.
- 정답: C
- 정답 근거: .zip 패키지는 계층을 포함해 압축 해제 후 250 MB가 한도이고, 컨테이너 이미지는 압축 해제 기준 10 GB까지 지원한다. 해당 한도는 표에 명시된 경우를 제외하고 변경할 수 없다. [S1] https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html
- 오답 해설: A) S3 경유는 50 MB 직접 업로드 제한만 피할 뿐 압축 해제 250 MB 한도는 그대로다. B) 계층 크기도 같은 250 MB 합계에 포함된다. D) 이 배포 패키지 한도는 상향 요청 대상이 아니다.

- 보기:
  - A. 서울(ap-northeast-2) 리전
  - B. 미국 동부(버지니아 북부, us-east-1) 리전
  - C. 서울과 us-east-1 두 리전 모두
  - D. 인증서는 필요 없다 — API Gateway가 도메인용 인증서를 자동 발급한다
- 정답: B
- 정답 근거: 엣지 최적화 사용자 지정 도메인은 인증서를 us-east-1에서 요청하거나 가져와야 하며, API Gateway가 CloudFront 배포를 만들어 요청을 받는다. [S19] https://docs.aws.amazon.com/apigateway/latest/developerguide/how-to-edge-optimized-custom-domain-name.html

### 문항 후보 3
- 대응 Skill: 3.4.5 · 3.4.8 · 3.4.11 (3.4.3) / 난이도: intermediate
- 문제: AWS SAM으로 배포하는 Lambda 함수의 새 버전에 트래픽의 10%를 먼저 보내고 5분 뒤 나머지 90%를 옮기려 한다. CloudWatch 경보가 울리면 자동으로 이전 버전으로 되돌려야 한다. 가장 적은 구성으로 구현하는 방법은?
- 보기:
  - A. `AutoPublishAlias`를 지정하고 `DeploymentPreference`에 `Type: Canary10Percent5Minutes`와 `Alarms`를 설정한다.
  - B. `AutoPublishAlias`를 지정하고 `DeploymentPreference`에 `Type: Linear10PercentEvery1Minute`를 설정한다.
  - C. API Gateway 단계에 카나리 설정을 추가하고 `percentTraffic`을 10으로 둔다.
  - D. Lambda 별칭의 가중치를 직접 설정하고, 스크립트로 5분 뒤 `update-alias`를 호출한다.
- 정답: A
- 정답 근거: SAM은 CodeDeploy와 내장 통합되어 `AutoPublishAlias`가 새 버전을 발행·별칭 이동하고, `DeploymentPreference`의 Canary 유형이 첫 증분 비율과 나머지 이동 시점을, `Alarms`가 경보 시 자동 롤백을 담당한다. [S33] https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/automating-updates-to-serverless-apps.html
- 오답 해설: B) Linear는 같은 비율을 일정 간격으로 반복한다(10% 후 5분 뒤 나머지 일괄이 아님). C) API Gateway 카나리는 한 단계의 두 API 배포 사이를 나눌 뿐 Lambda 버전 전환·자동 롤백을 대신하지 않는다 [S15]. D) 가중치 별칭 자체로 카나리는 가능하지만 시간 경과·롤백 자동화는 직접 구현해야 해 '가장 적은 구성'이 아니다 [S9].

  - A. All at once
  - B. Rolling
  - C. Rolling with additional batch
  - D. Immutable
- 정답: D

- 오답 해설: A) 전체를 동시에 교체해 다운타임이 있다. B) 기존 인스턴스를 배치로 갱신하며 용량이 줄고 롤백은 수동 재배포다. C) 용량은 유지하지만 기존 인스턴스에 배포하므로 실패 시 롤백이 수동 재배포이다 [S53].

### 문항 후보 5

- 문제: REST API의 `dev`·`prod` 단계가 같은 API 정의를 쓰며, Lambda 통합 URI를 `…function:myFunc:${stageVariables.alias}/invocations`로 구성했다. 각 단계에 `alias` 스테이징 변수(`dev`, `prod`)를 설정하고 배포했는데 API가 Lambda를 호출하지 못한다. 가장 가능성 높은 원인과 조치는?
- 보기:
  - A. 스테이징 변수는 Lambda 별칭 지정에 쓸 수 없으므로 Lambda 환경 변수로 바꾼다.
  - B. Lambda 함수(별칭)에 API Gateway가 호출할 수 있는 리소스 기반 권한을 `aws lambda add-permission`으로 직접 추가한다.
  - C. API를 다시 배포하면 API Gateway가 Lambda 호출 권한을 자동으로 추가해 준다.
  - D. 스테이징 변수에 민감 정보가 들어 있어서 호출이 막힌 것이므로 Secrets Manager로 옮긴다.
- 정답: B

- 오답 해설: A) 스테이징 변수는 Lambda 함수 이름·버전/별칭 자리에 쓸 수 있다 [S25]. C) 재배포로 권한이 자동 추가되지 않는다 — 수동 설정이 필요하다. D) 민감 정보 사용 금지는 권고이며 호출 실패의 원인이 아니고, 문제 상황에 그런 값도 없다.
