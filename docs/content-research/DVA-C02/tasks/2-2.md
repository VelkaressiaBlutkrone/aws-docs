## 핵심 개념

### 저장 중 암호화 vs 전송 중 암호화 — 서비스별 기본값과 옵션 (Skill 2.2.1)

- **저장 중(at rest)** 암호화는 스토리지에 정적으로 놓인 데이터만 보호한다. 네트워크 구간(**전송 중, in transit**)은 TLS 등으로 따로 보호해야 한다. [S9]
- 원리: SQS·EBS처럼 KMS와 통합된 서비스는 **봉투 암호화**로 저장 중 암호화를 한다. 서비스가 데이터 키로 데이터를 암호화하고, 그 데이터 키를 KMS 키로 암호화해 데이터와 함께 보관한다. SQS는 데이터 키를 일정 기간 재사용해 KMS 호출 횟수를 줄인다. [S7][S13]
- KMS API 호출 자체도 서명 + TLS 필수이며 TLS 1.2를 요구한다(1.3 권장). [S15]

| 서비스 | 저장 중 | 전송 중 | 시험 포인트 | 출처 |
|---|---|---|---|---|
| S3 | 새 객체에 **SSE-S3가 자동 적용**(2023-01-05~, 추가 비용·성능 영향 없음). 선택: SSE-KMS, DSSE-KMS, SSE-C(2026-04부터 신규 버킷에서 기본 차단) | HTTPS. 버킷 정책에서 `aws:SecureTransport`가 `false`인 요청을 Deny해 강제 | KMS 키를 지정하지 않은 SSE-KMS는 AWS managed key `aws/s3` 사용 | [S1][S2][S5] |
| EBS | KMS 키로 볼륨·스냅샷 암호화. "기본 암호화"는 **Region 단위** 설정이며 기존 볼륨엔 영향 없음 | 인스턴스↔볼륨 구간도 암호화(EC2 호스트에서 수행) | 볼륨을 attach할 때 EC2가 KMS에 `CreateGrant` 요청 | [S12][S13][S14] |

| SQS | SSE-SQS 또는 SSE-KMS. **본문만** 암호화(큐·메시지 메타데이터 제외), 활성화 이전 백로그는 소급 암호화 안 됨 | SSE 큐 요청은 HTTPS + Signature V4 필수 | 데이터 키 재사용 기간 60~86,400초(기본 300초) | [S7] |

### 인증서 관리 — ACM과 AWS Private CA (Skill 2.2.2)

| 구분 | ACM 공개 인증서 | ACM에 가져온(imported) 인증서 | AWS Private CA 사설 인증서 |
|---|---|---|---|
| 신뢰 범위 | 공개 신뢰(publicly trusted) [S21] | 발급처(외부 CA 서명 또는 자체 서명)에 따름 [S26] | 조직 내부에서만 신뢰(인터넷 신뢰 아님) [S30] |
| 도메인 소유 검증 | **필요** — DNS(권장)·이메일·HTTP(CloudFront용) [S21] | 없음 [S21] | 없음 [S21] |
| 유효기간 | 198일, 만료 45일 전 자동 갱신 시도 [S20] | 인증서 자체 기간 | 일반 목적 모드=임의 기간, 단기 모드=최대 7일 [S29] |
| 자동 갱신 | 통합 서비스에 연결된(사용 중) DNS 검증 인증서 [S22][S23] | **불가** [S22] | `IssueCertificate` API로 직접 발급한 인증서는 ACM 관리형 갱신 대상 아님 [S22] |
| 개인 키 | 일반 공개 인증서는 개인 키 반출 불가(통합 서비스에서만 사용) [S27] | 사용자가 제공(암호 없는 PEM, 5 KB 이하) [S26] | 접근 불가 키 인증서(ELB·CloudFront·API GW용)는 무료 [S28] |

- **DNS 검증 vs 이메일 검증**: DNS는 CNAME 레코드가 있는 한 자동 갱신(Route 53이면 ACM이 직접 레코드 추가). 이메일 검증은 만료 45일 전부터 알림이 가고 도메인 소유자가 직접 갱신해야 한다. 이메일로 만든 인증서를 DNS 검증으로 바꿀 수 없다(삭제 후 재생성). [S21][S23]
- **통합 서비스에서만**: ELB·CloudFront·API Gateway 등에 연결해 쓴다. ACM 공개 인증서를 EC2 인스턴스에 직접 설치할 수 없으므로 로드 밸런서 뒤에 인스턴스를 둔다. [S25][S27] 새 옵션인 "내보내기 가능한 공개 인증서"는 **요청 시** 내보내기를 켜야 하고 기존 인증서는 내보낼 수 없다. [S31]
- **ACM vs Private CA**: ACM은 인증서 요청·검증·갱신·배포 자동화, Private CA는 내부 PKI(루트·하위 CA 계층)를 운영하는 서비스다. ACM에서 사설 PKI 인증서를 요청할 때 CA로 Private CA를 쓴다. [S20][S30]
- Private CA 요금: 일반 목적 모드 월 $400, 단기 인증서 모드 월 $50(CA 단위, 인증서 발급 요금 별도). 계정 간 공유는 AWS RAM. [S29][S28][S30]
- 원리(해석): ACM이 직접 발급한 인증서는 갱신본도 ACM이 발급해 통합 서비스에 다시 연결할 수 있지만, 외부에서 가져온 인증서는 관리형 갱신 대상이 아니므로 사용자가 새 인증서를 가져와 교체해야 한다. [S22]

### 클라이언트측 vs 서버측 암호화 (Skill 2.2.3)

| 구분 | 서버측 암호화(SSE) | 클라이언트측 암호화 |
|---|---|---|
| 암호화 주체 | 서비스(S3·DynamoDB 등)가 저장할 때 | 애플리케이션(라이브러리)이 전송 **전에** |
| 서비스의 평문 접근 | 요청 처리 중 서비스가 평문 접근 | 서비스는 암호문만 받음(AWS 포함 제3자에 비노출) [S6] |
| 키 관리 | SSE-S3(서비스)·SSE-KMS(KMS 키)·SSE-C(고객 제공) | 사용자가 래핑 키(KMS 키 등)를 정하고 암호화 과정·도구를 관리 [S6] |
| 서비스의 인식 | 암호화 객체임을 앎 | 일반 객체/이진 속성으로만 인식 [S6][S34] |
| AWS 도구 | S3 SSE, EBS, DynamoDB encryption at rest | S3 Encryption Client, AWS Encryption SDK, AWS Database Encryption SDK |

- **S3 Encryption Client**: `PutObject`/`GetObject`에서 자동 암·복호화, 객체마다 고유 데이터 키, 버킷 키는 사용하지 않음. 서버측 암호화와 함께 써도 된다. [S6]
- **AWS Encryption SDK**: 메시지마다 고유 데이터 키를 만들고 그 키를 래핑 키로 암호화해 암호문과 함께 보관한다. 같은 데이터 키를 여러 래핑 키로 암호화할 수 있다(수신자별 복호화). [S35]
- **DynamoDB**: 클라이언트측 라이브러리는 2023-06-09에 **AWS Database Encryption SDK**로 개명(옛 이름 DynamoDB Encryption Client). 속성 값을 암호화하고 서명하며, **기본 키(파티션·정렬 키)의 이름·값은 평문**으로 남는다. DynamoDB 저장 중 암호화와 병행 가능하고, 구버전이 암호화한 항목도 읽을 수 있다. [S32][S33][S34]
- 선택 키워드: "AWS도 평문을 볼 수 없어야 / 종단 간 / 속성(필드) 단위" → 클라이언트측. "코드 변경 최소, KMS 키 정책·CloudTrail 감사" → SSE-KMS.
- 원리: 서버측은 서비스가 키를 써야 하므로 키 정책·권한으로 통제·감사할 수 있고, 클라이언트측은 서비스가 키를 전혀 쓰지 않아 노출면이 줄지만 키·코드 관리 책임이 개발자에게 넘어온다.

### KMS 키 유형·키 정책·권한 모델 (Skill 2.2.4, 2.2.6)

| 구분 | 고객 관리형 키 | AWS managed key | AWS owned key |
|---|---|---|---|
| 소유·위치 | 내 계정, 내가 생성·관리 | 내 계정에 있으나 서비스가 생성·관리·사용 | 서비스 계정(여러 계정 공용) |
| 키 정책 | 고객이 전적으로 통제 | 서비스가 통제, 고객은 조회만 | 서비스만 조회·통제 |
| 로깅 | CloudTrail | CloudTrail | 고객이 볼 수 없음 |
| 자동 회전 | 선택(기본 꺼짐) | 필수, 매년(약 365일), 변경 불가 | 서비스가 결정 |
| 요금 | 월 $1(시간 비례) + 사용료 | 월 요금 없음, 호출 사용료 | 없음 |
| 식별 | 사용자 별칭 | 별칭 `aws/<서비스>`, `KeyManager`=`AWS` | — |
| 공유 | 교차 계정 가능 | **다른 계정과 공유 불가** | 서비스가 처리 |

(출처: [S37] 표, 요금 [S40])

- **key spec**: 기본은 대칭 `SYMMETRIC_DEFAULT`(256비트 AES-GCM). 비대칭(RSA·ECC)·HMAC도 있고 key spec은 **생성 후 변경 불가**(틀리면 삭제 후 재생성). 모든 KMS 키는 HSM 밖으로 평문 반출이 안 되며 비대칭 키의 공개 키만 `GetPublicKey`로 가져온다. SNS는 대칭 암호화 키만 지원한다. [S38][S39][S8]
- **키 정책** = KMS 키의 리소스 정책. 키마다 **정확히 1개**, 접근 통제의 1차 수단이며 Region 단위다. 계정 루트·키 생성자도 명시적으로 허용되지 않으면 권한이 없다. [S41]
- **IAM 정책은 키 정책이 허용할 때만** Allow로 작동한다(Deny는 키 정책 허용 없이도 유효). 기본 키 정책의 `Principal: 계정 root` 문장은 IAM 주체에게 직접 권한을 주는 게 아니라 "계정이 IAM 정책으로 위임할 수 있게" 해 준다. [S41][S42]
- **그랜트(grant)**: 한 그랜트는 KMS 키 1개에 대해 허용만 가능(거부 불가), 임시 권한에 적합하며 AWS 서비스가 만들어 쓰고 회수한다. 생성·회수 직후엔 일관성 지연이 있어 grant token을 쓴다. [S43]
- 범위 제한 조건: `kms:ViaService`(특정 AWS 서비스를 통한 요청만 허용/거부), 암호화 컨텍스트 조건. [S44][S45]
- 원리: KMS는 "키 정책이 최종 게이트"라서 IAM만 열어서는 안 되고, 반대로 키 정책만으로 같은 계정 접근을 끝낼 수도 있다.

### 데이터 암호화·복호화 API와 봉투 암호화 (Skill 2.2.4)

| 상황 | 쓸 API | 핵심 | 출처 |
|---|---|---|---|
| 4 KB 이하 소량(식별자·DB 암호 등) | `Encrypt` / `Decrypt` | 평문 최대 4,096바이트(대칭). RSA_2048+OAEP_SHA_256은 190바이트 | [S46] |
| 큰 데이터 | `GenerateDataKey` → 로컬 암호화 → `Decrypt`(데이터 키) | 평문 키는 쓰고 나서 메모리에서 지우고, 암호화된 키는 데이터와 함께 저장 | [S48] |
| 암호화된 데이터 키만 먼저(나중에 복호화해 사용) | `GenerateDataKeyWithoutPlaintext` | EBS가 볼륨 생성 시 사용 | [S13][S48] |
| 암호문을 다른 KMS 키(또는 컨텍스트)로 교체, 평문 비노출 | `ReEncrypt` | 수동 회전·키 교체. Encryption SDK·S3 암호화 클라이언트가 만든 암호문은 못 풂 | [S49] |

- 원리: KMS는 HSM에서 저지연 연산을 하도록 설계돼 직접 암호화 평문을 4 KB로 제한한다. 큰 데이터는 로컬 대칭 키로 암호화하고 KMS는 그 키만 래핑하는 것이 봉투 암호화다. [S47]
- `GenerateDataKey`는 **대칭** 암호화 KMS 키만 쓸 수 있다(비대칭 KMS 키로 데이터 키 생성 불가). [S48]
- **복호화 시 키 식별**: 대칭 키 암호문은 메타데이터가 들어 있어 `KeyId`·알고리즘이 선택 사항이다. 비대칭 키는 `KeyId`와 알고리즘을 반드시 줘야 한다. [S49][S46]
- **암호화 컨텍스트**: 비밀이 아닌 키-값 쌍(AAD). 암호문에 암호학적으로 결합되어 복호화 때 대소문자까지 **정확히 일치**해야 하고(불일치 시 `InvalidCiphertextException`), CloudTrail에 평문으로 남는다. 비대칭·HMAC 키는 지원하지 않는다. [S45][S46]
- **스로틀·비용 완화**: 대칭 키 암호화 연산은 계정·Region 단위로 요청 쿼터를 공유해 쓴다. 완화책은 ① S3 Bucket Keys(SSE-KMS 요청 비용 최대 99%↓, DSSE-KMS 미지원) ② AWS Encryption SDK 데이터 키 캐싱(기본은 암호화마다 새 키, 캐싱은 신중히) ③ 쿼터 증액. [S66][S4][S36]

### 개발용 인증서·SSH 키 생성 (Skill 2.2.5)

- **자체 서명/CA 서명 인증서(openssl)**: 개인 키 `openssl genrsa 2048 > privatekey.pem` [S56] → CSR `openssl req -new -key <개인키> -out <파일>.csr` → `openssl x509 -req`로 서명 [S58]. 로컬 생성은 단일 인스턴스 HTTPS나 백엔드 재암호화 같은 경우에만 필요하고, 도메인이 있으면 ACM이 무료. [S56]
- **사설 CA + 클라이언트 인증서(예: API Gateway mTLS)**: `openssl genrsa -out RootCA.key 4096` → `openssl req -new -x509 -days 3650 -key RootCA.key -out RootCA.pem` → 클라이언트 키(2048)·CSR → `openssl x509 -req ... -CA RootCA.pem -CAkey RootCA.key`로 서명. truststore는 `.pem`(S3), 체인 길이 최대 4. [S58][S57]
- **ACM으로 가져오기**: 자체 서명 인증서도 인증서+개인 키를 주면 가져온다. PEM, 개인 키는 암호 없음·5 KB 이하, 유효기간 내, 알고리즘은 RSA 1024/2048/3072/4096·ECDSA 256/384/521(통합 서비스별로 허용 알고리즘 상이: CloudFront는 EC prime256v1까지). 가져온 인증서는 관리형 갱신 없음. [S26][S22]
- **EC2 키 페어 — AWS가 생성**: `aws ec2 create-key-pair --key-name my-key-pair --key-type rsa --key-format pem --query "KeyMaterial" --output text > my-key-pair.pem` 후 `chmod 400`. 공개 키는 EC2가 저장하고 **개인 키는 생성 시 한 번만** 받을 수 있다. [S54]
- **EC2 키 페어 — 외부 도구로 생성 후 가져오기**: `ssh-keygen`(PEM이 필요하면 `-m PEM`)으로 만든 뒤 `aws ec2 import-key-pair --key-name my-key-pair --public-key-material fileb://path/my-key-pair.pub`. **공개 키만** AWS에 전달되고 개인 키는 전송되지 않는다. [S54][S55]

| 항목 | 규칙 | 출처 |
|---|---|---|
| 지원 키 종류 | RSA(Linux·Windows), ED25519(Linux만), DSA 불가 | [S54] |
| 개인 키 형식 | PEM 또는 PPK(OpenSSH는 .pem, PuTTY는 .ppk) | [S54] |
| 리전당 키 페어 | 최대 5,000개(증액 가능) | [S54] |
| CloudFormation 생성 | 개인 키가 Parameter Store `/ec2/keypair/key_pair_id`에 저장 | [S54] |

- 원리: EC2 키 페어에서 AWS(EC2)가 저장하는 것은 공개 키이고 개인 키는 사용자가 보관한다. 그래서 개인 키는 생성 시 한 번만 받을 수 있고, 가져오기(import) 방식에서는 공개 키만 AWS로 전송된다. [S54][S55] (CloudFront 필드 수준 암호화용 RSA 키 생성 → 2-3.md의 Skill 2.3.5)

### 계정 경계 간 암호화 (Skill 2.2.6)

- **두 정책이 모두 필요**: ① 키 소유 계정의 **키 정책**이 외부 계정(또는 특정 주체)을 허용 ② 외부 계정의 **IAM 정책**이 그 권한을 사용자·역할에 위임. 키 정책은 "가질 수 있는 권한", IAM 정책은 "실제로 가진 권한"을 정한다. [S52]
- 같은 계정이면 키 정책 한 문서로 접근 범위를 전부 정할 수 있지만, 다른 계정의 호출자는 **키 정책만으로는 안 되고** 호출자 쪽 IAM 정책이 해당 API 호출을 명시적으로 허용해야 한다. [S68]
- 키 정책이 특정 외부 사용자·역할만 지정했다면 IAM 정책도 그 안의 주체·동작만 줄 수 있고, 키 정책에 없는 동작은 IAM에 써도 무효다. [S52]
- 교차 계정으로 **효력이 있는 동작**은 암호화 연산·`CreateGrant`·`DescribeKey`·`GetKeyRotationStatus`·`GetPublicKey`·`ListGrants`·`RetireGrant`·`RevokeGrant`뿐이다(예: `ScheduleKeyDeletion`은 외부 계정에서 무효). [S52]
- 다른 계정의 키는 API에서 **키 ARN 또는 별칭 ARN**으로 지정해야 한다(키 ID·별칭 이름 불가). [S46][S48]
- **AWS managed key는 공유 불가** → 교차 계정은 고객 관리형 키가 필수. S3에서는 별칭이 **요청자 계정에서 해석**되므로 전체 KMS 키 ARN을 권장한다. [S37][S1]

| 시나리오 | 필요한 것 | 출처 |
|---|---|---|
| 다른 계정이 SSE-KMS S3 객체 접근 | 고객 관리형 키 + 키 정책(상대 계정) + 상대 계정 IAM + 전체 키 ARN, 요청자가 키에 `Encrypt` 권한 | [S1][S52] |
| 암호화 EBS 스냅샷 공유 | 고객 관리형 키로 암호화한 스냅샷만 가능, **키도 함께 공유**(DescribeKey·CreateGrant·GenerateDataKey·ReEncrypt·Decrypt 등), `CreateGrant`는 `kms:GrantIsForAWSResource` 조건 권장 | [S53] |
| 기본 키로 암호화한 SQS 큐 | `aws/sqs` 기본 키 큐는 **다른 계정의 Lambda를 호출할 수 없음** → 고객 관리형 키 | [S7] |

- 요금·로그: 다른 계정 키를 쓰면 **요청한 계정**이 사용 요금을 내고, CloudTrail에는 호출 계정과 키 소유 계정 양쪽에 기록된다. 외부 계정이 키의 Region에서 활성화(opt-in Region)돼 있어야 한다. [S40][S52]
- **다중 리전 키 ≠ 교차 계정**: 다중 리전 기본·복제 키는 key ID와 키 자료를 공유(리전 간 상호 복호화)하지만 각 복제 키의 키 정책·별칭 등은 독립이다. 계정 간 허용 문제와 별개다. [S50][S51]
- 원리: KMS 키는 소유 계정의 리소스이므로 소유자 동의(키 정책)가 상한이고, 호출자 계정이 자기 주체에게 위임(IAM)해야 비로소 사용된다.

### 키 회전 사용·사용 중지, 비활성화·삭제 (Skill 2.2.7)

| 키 종류 | 자동 회전 | 온디맨드 회전 | 수동 회전 |
|---|---|---|---|
| AWS managed key | 필수·매년, 변경 불가(2022-05에 3년→1년) | 불가 | — |
| AWS owned key | 서비스가 결정 | — | — |
| 고객 관리형 대칭(`AWS_KMS` 키 자료) | **선택(기본 꺼짐)**, 90~2560일(기본 365) | 가능(키당 최대 25회) | — |
| 고객 관리형 대칭(가져온 키 자료 `EXTERNAL`) | 불가 | 가능(새 키 자료를 먼저 가져와 `PENDING_ROTATION`) | — |
| 비대칭·HMAC·사용자 지정 키 스토어 | 불가 | 불가 | 새 KMS 키 생성 후 별칭 이동 |

(출처: [S59][S39][S61][S62])

- **명령**: `aws kms enable-key-rotation --key-id <키> --rotation-period-in-days 180`, `disable-key-rotation`, `get-key-rotation-status`, `rotate-key-on-demand`, `list-key-rotations`. 기간을 안 주면 365일. 조건 키 `kms:RotationPeriodInDays`로 값 범위를 제한할 수 있다. [S60][S59]
- **회전이 바꾸는 것**: **현재 키 자료**만 교체한다. 키 ID·ARN·정책은 그대로이고 이전 키 자료는 키를 삭제할 때까지 보관되어, 복호화는 KMS가 알맞은 키 자료를 자동으로 골라 쓴다(코드 변경 불필요). [S59]
- **회전이 바꾸지 않는 것**: 데이터 키를 회전하거나 데이터를 재암호화하지 않으며, 유출된 데이터 키의 위험을 줄여 주지 않는다. [S59]
- 회전 비활성화 → 그 시점의 키 자료를 계속 사용, 다시 켜면 새 활성화일 기준. 비활성(Disabled)·삭제 대기 키는 회전하지 않고 상태도 못 바꾸며, 복구 시 기한이 지났으면 즉시 회전. 온디맨드는 자동 일정에 영향 없음. 다중 리전 키는 기본(primary) 키에서만 설정. [S59]
- 비용: 자동·온디맨드 회전 1·2번째에 각각 월 $1 추가, 이후 무과금. [S40]

| 구분 | 비활성화(`DisableKey`) | 삭제 예약(`ScheduleKeyDeletion`) |
|---|---|---|
| 가역성 | 언제든 재활성화 | 대기 기간 안에는 취소 가능, 끝나면 영구 삭제 |
| 대기 기간 | 없음 | 7~30일(기본 30), 실제는 최대 24시간 더 길 수 있음 |
| 효과 | 암호화 연산 불가 | 연산 불가 + 기간 후 키·별칭·메타데이터 삭제, 데이터 복구 불가 |
| 요금 | 계속 청구 | 삭제 예약 중에는 청구 없음 |

(출처: [S63][S64][S65][S40])

- 확신이 없으면 **먼저 비활성화**하고, 삭제 대기 중 사용 시도를 CloudTrail/CloudWatch 알람으로 탐지한다. 가져온 키 자료는 `DeleteImportedKeyMaterial`로 대기 없이 즉시 삭제되고 키 상태가 "Pending import"가 된다. 다중 리전 기본 키는 복제 키를 먼저 삭제해야 한다. [S65][S64]
- 원리: 키가 없으면 그 키로 감싼 데이터 키를 풀 수 없어 데이터가 영구 소실되므로, KMS는 삭제에 대기 기간이라는 안전장치를 둔다.

## 시험에서 묻는 방식

(문제 저작자를 위한 제안이다. 시험이 반드시 이렇게 낸다는 단정이 아니다.)

1. **서버측 암호화 + 키 통제·감사 필요**: "S3에 저장하는 데이터를 AWS KMS로 암호화하고 키 사용 이력과 키 정책으로 접근을 통제해야 한다. KMS 호출 비용과 스로틀링도 문제다." → 정답 단서: "키 정책·CloudTrail 감사" ⇒ **SSE-KMS(고객 관리형 키)**, "KMS 요청 비용·스로틀" ⇒ **S3 Bucket Keys**(또는 Encryption SDK 데이터 키 캐싱). 기본 SSE-S3로는 키를 통제할 수 없다. [S1][S4][S36]
2. **교차 계정 AccessDenied**: "계정 B의 역할이 계정 A의 암호화된 S3 객체·EBS 스냅샷·SQS 큐에 접근하려는데 `AccessDenied`/KMS 오류가 난다." → 단서: "다른 계정", "`aws/s3`·`aws/ebs`·`aws/sqs`" ⇒ 키 정책에 외부 계정 허용 + 외부 계정 IAM 정책 허용(**둘 다**), AWS managed key라면 **고객 관리형 키로 교체**(공유 불가). [S52][S37][S53][S7]
3. **큰 데이터의 KMS 암호화**: "수 MB 파일을 KMS 키로 암호화하려는데 `Encrypt` 호출이 실패한다." → 단서: "4,096바이트 초과" ⇒ `GenerateDataKey`로 **봉투 암호화**(평문 키로 로컬 암호화, 암호화된 키를 데이터와 함께 저장, 평문 키는 즉시 삭제) 또는 AWS Encryption SDK. [S46][S48][S35]
4. **키 회전·삭제·비활성화**: "규정상 180일마다 키를 회전해야 하며 애플리케이션 코드는 바꾸지 않는다." / "더 이상 안 쓰는 키를 정리하되 복구 가능성은 남기고 싶다." → 단서: 대칭 고객 관리형 키 ⇒ **자동 회전(`--rotation-period-in-days`)**, 비대칭·HMAC ⇒ 새 키 + 별칭 이동(수동), 삭제는 **대기 7~30일·취소 가능**, 확신이 없으면 **비활성화 먼저**. [S59][S60][S63][S65]

## 흔한 함정·혼동 짝

| A vs B | 혼동 이유 | 구분 기준 한 줄 | 출처 |
|---|---|---|---|
| SSE-S3 vs SSE-KMS | 둘 다 "S3가 서버에서 암호화"이고 기본 암호화 설정에서 고른다 | SSE-S3=기본 자동(키 통제 없음), SSE-KMS=키 정책·CloudTrail·회전 통제 가능하나 KMS 요청 비용·쿼터 발생(Bucket Keys로 완화) | [S1][S4] |
| SSE-KMS vs SSE-C | 둘 다 "내 키로 암호화"처럼 보인다 | SSE-C는 요청마다 키를 제공하고 HTTPS 필수, S3가 키를 저장하지 않으며(분실=객체 분실) 2026-04부터 신규 버킷 기본 차단 | [S2][S3] |
| 키 정책 vs IAM 정책 | 다른 서비스는 IAM만 열면 된다 | KMS는 키 정책이 허용해야 IAM Allow가 유효(Deny는 항상 유효), 교차 계정은 둘 다 필요 | [S41][S52] |
| AWS managed key vs 고객 관리형 키 | 둘 다 내 계정 KMS 콘솔에 보인다 | AWS managed(`aws/*`)는 정책·회전·삭제 통제 불가, **공유 불가**. 고객 관리형은 전부 통제, 교차 계정 가능 | [S37] |
| Encrypt vs GenerateDataKey | 둘 다 "KMS로 암호화" | Encrypt=4,096바이트 이하 직접 암호화, GenerateDataKey=큰 데이터용 봉투 암호화(데이터는 로컬에서 암호화) | [S46][S48] |
| 자동 vs 온디맨드 vs 수동 회전 | 셋 다 "회전" | 자동=일정(90~2560일), 온디맨드=즉시(키당 25회, 자동 일정 불변), 수동=새 키+별칭 이동(비대칭·HMAC·키 스토어) | [S59][S61] |
| 키 회전 vs 데이터 재암호화 | 회전하면 기존 데이터도 새 키로 바뀐다고 착각 | 회전은 현재 키 자료만 교체, 기존 암호문은 이전 키 자료로 계속 복호화됨(재암호화는 `ReEncrypt`로 별도) | [S59][S49] |
| 비활성화 vs 삭제 예약 | 둘 다 "키를 못 쓰게" 한다 | 비활성화=즉시·재활성화 가능·요금 유지, 삭제 예약=7~30일 뒤 영구 삭제(대기 중에는 취소 가능) | [S63][S65] |
| 다중 리전 키 vs 교차 계정 공유 | "다른 곳에서 같은 키 사용"이라는 공통점 | 다중 리전=같은 key ID·키 자료를 Region 간 복제(복제 키 정책은 독립), 교차 계정=키 정책+IAM 정책 허용 | [S50][S51][S52] |
| ACM 공개 vs 가져온 vs Private CA 인증서 | 모두 ACM 콘솔에 나타난다 | 공개=도메인 검증·198일·자동 갱신, 가져온=관리형 갱신 없음, Private CA=내부 신뢰·CA당 월 요금 | [S20][S22][S29] |
| CloudFront 인증서 Region vs ALB·API GW Regional | "ACM 인증서는 리소스와 같은 Region" 규칙의 예외 | CloudFront(엣지 최적화 API 포함)=us-east-1, ALB·Regional API=같은 Region | [S24][S27][S19] |
| EC2 create-key-pair vs import-key-pair | 둘 다 키 페어를 만든다 | create=AWS가 생성하고 개인 키를 1회 내려받음, import=외부(`ssh-keygen`)에서 만든 **공개 키만** 전달 | [S54][S55] |

## 자가 점검 문항 후보

> **초안·미검수** — 사람 검수 전 후보이며 `verified` 전환 대상이 아니다.

**문항 1** — 대응 Skill 2.2.4 · 난이도 intermediate
- 문제: 애플리케이션이 사용자가 올린 50 MB 동영상 파일을 저장 전에 AWS KMS 고객 관리형 키로 보호해야 한다. 개발자가 파일 전체를 `Encrypt` API에 넣었더니 오류가 났다. KMS 키를 밖으로 내보내지 않고 요구를 충족하는 방법은?
- 보기: A. 키 정책에서 `Encrypt`의 최대 평문 크기를 50 MB로 올린다. / B. `GenerateDataKey`로 받은 평문 데이터 키로 파일을 로컬에서 암호화하고, 암호화된 데이터 키를 파일과 함께 저장한 뒤 평문 키는 메모리에서 지운다. / C. `GenerateDataKeyWithoutPlaintext`로 받은 암호화된 데이터 키로 파일을 로컬에서 직접 암호화한다. / D. KMS 키를 비대칭 RSA 키로 바꿔 `Encrypt` 한도를 늘린다.
- 정답: B
- 정답 근거: `Encrypt`는 최대 4,096바이트까지 암호화하며, 큰 데이터는 `GenerateDataKey`의 평문 키로 로컬 암호화 → 암호화된 키 보관 → 평문 키 삭제 패턴을 쓴다. 근거: https://docs.aws.amazon.com/cli/v1/reference/kms/encrypt.html , https://docs.aws.amazon.com/kms/latest/APIReference/API_GenerateDataKey.html
- 오답 해설: A — 4 KB 한도는 KMS가 설계상 두는 값이며 키 정책은 권한을 정하는 문서다. C — 이 호출은 평문 사본 없이 암호화된 사본만 돌려주므로 그 키로 바로 암호화할 수 없다. D — 비대칭 RSA 키는 한도가 더 작다(RSA_2048 + OAEP_SHA_256은 190바이트).

**문항 2** — 대응 Skill 2.2.6 · 난이도 intermediate
- 문제: 계정 A의 S3 버킷은 계정 A의 고객 관리형 KMS 키(SSE-KMS)로 암호화돼 있고, 계정 A는 그 키의 키 정책에 계정 B를 이미 허용했다. 그런데 계정 B의 EC2 인스턴스 역할이 `GetObject`를 호출하면 KMS 관련 `AccessDenied`가 난다. 추가로 필요한 조치는?
- 보기: A. 계정 B의 역할 IAM 정책에서 계정 A의 키 ARN에 대한 `kms:Decrypt`를 허용한다. / B. 계정 A의 키 정책 `Principal`을 `*`로 바꾼다. / C. 버킷을 AWS managed key `aws/s3`로 다시 암호화한다. / D. 계정 B에서는 할 일이 없으며 설정이 전파될 때까지 기다린다.
- 정답: A
- 정답 근거: 교차 계정에서는 키 소유 계정의 키 정책과 호출자 계정의 IAM 정책 둘 다 필요하며 둘 중 하나만으로는 충분하지 않다. 근거: https://docs.aws.amazon.com/kms/latest/developerguide/key-policy-modifying-external-accounts.html
- 오답 해설: B — 조건 없는 `*` Principal은 모든 계정에 권한을 열어 주므로 쓰지 말라고 권고하며, 호출자 쪽 IAM 위임 요건도 대체하지 못한다. C — AWS managed key는 다른 계정과 공유할 수 없다. D — 키 정책만으로는 다른 계정 호출자가 키를 쓸 수 없다.

**문항 3** — 대응 Skill 2.2.7 · 난이도 intermediate
- 문제: 규정상 대칭 고객 관리형 KMS 키(키 자료는 AWS KMS가 생성)를 180일마다 회전해야 한다. 키 ID·별칭과 애플리케이션 코드는 바꿀 수 없다. 가장 적절한 방법은?
- 보기: A. `aws kms enable-key-rotation --key-id <키> --rotation-period-in-days 180` / B. 180일마다 새 KMS 키를 만들어 모든 애플리케이션의 키 ID를 교체한다. / C. 키를 AWS managed key로 바꿔 180일 회전을 설정한다. / D. 키를 비활성화했다가 180일 뒤 다시 활성화한다.
- 정답: A
- 정답 근거: 자동 회전은 기간을 90~2560일로 지정할 수 있고(기본 365일), 회전해도 키 ID·ARN이 그대로이며 복호화는 KMS가 알맞은 키 자료를 자동으로 고른다. 근거: https://docs.aws.amazon.com/kms/latest/developerguide/rotate-keys.html
- 오답 해설: B — 새 키를 만드는 수동 회전은 자동·온디맨드를 쓸 수 없는 키용이며 참조 변경이 필요하다. C — AWS managed key는 매년 회전이 고정이고 바꿀 수 없다. D — 비활성화는 회전이 아니며, 비활성 키는 회전하지 않는다.

**문항 4** — 대응 Skill 2.2.3 · 난이도 intermediate
- 문제: DynamoDB 테이블에 주민등록번호 속성을 저장한다. 보안팀은 AWS 서비스도 이 값을 평문으로 볼 수 없어야 하며, 파티션 키로 하는 조회는 그대로 가능해야 한다고 요구한다. 어떤 접근이 맞는가?
- 보기: A. 테이블 암호화 키를 AWS managed key에서 고객 관리형 키로 바꾼다. / B. 해당 속성 값을 AWS Database Encryption SDK(구 DynamoDB Encryption Client)로 클라이언트에서 암호화·서명해 저장한다. / C. DynamoDB 엔드포인트에 TLS만 강제한다. / D. 테이블을 SSE-C로 암호화한다.
- 정답: B
- 정답 근거: 클라이언트측 암호화는 속성 값을 DynamoDB로 보내기 전에 암호화·서명하고 기본 키는 평문으로 남겨 조회가 가능하다. DynamoDB 저장 중 암호화는 서버측이라 서비스가 접근 시 복호화한다. 근거: https://docs.aws.amazon.com/database-encryption-sdk/latest/devguide/client-server-side.html
- 오답 해설: A — 키 종류를 바꿔도 여전히 서버측 암호화여서 서비스가 복호화한다. C — TLS는 전송 구간만 보호하며 저장 상태·서비스 측 평문 접근과 무관하다. D — SSE-C는 S3 일반 목적 버킷의 암호화 옵션이지 DynamoDB 옵션이 아니다.

**문항 5** — 대응 Skill 2.2.5 · 난이도 foundational
- 문제: 개발자가 노트북에서 `ssh-keygen`으로 RSA 키 쌍을 만들었고 개인 키는 AWS로 보내고 싶지 않다. 이 키로 EC2 Linux 인스턴스에 접속하려면?
- 보기: A. `aws ec2 create-key-pair`로 새 키 쌍을 만들고 로컬 키는 버린다. / B. `aws ec2 import-key-pair --key-name my-key --public-key-material fileb://my-key.pub`로 공개 키만 가져온다. / C. 개인 키 `.pem` 파일을 `import-key-pair`로 업로드한다. / D. 공개 키를 ACM에 가져온 뒤 인스턴스에 연결한다.
- 정답: B
- 정답 근거: ImportKeyPair는 RSA·ED25519 키 쌍의 공개 키만 받고 개인 키는 AWS로 전송되지 않으며, CLI에서는 `fileb://`로 공개 키 파일을 지정한다. 근거: https://docs.aws.amazon.com/AWSEC2/latest/APIReference/API_ImportKeyPair.html , https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/create-key-pairs.html
- 오답 해설: A — `create-key-pair`는 AWS가 키 쌍을 생성하고 개인 키를 한 번 내려주는 방식이라 "로컬에서 만든 키 사용" 요건과 다르다. C — 가져오기는 공개 키만 받는다. D — ACM은 TLS 인증서 서비스이며 EC2 SSH 키 가져오기와 무관하다.
