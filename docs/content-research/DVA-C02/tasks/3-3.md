## 핵심 개념


### 테스트 이벤트와 Lambda 콘솔의 비공개·공유 가능 이벤트 (Skill 3.3.1)
- 테스트 이벤트 = 함수에 넣는 JSON 입력이다. 입력이 필요 없으면 `{}`도 된다. 콘솔의 Test는 함수를 **동기 호출**하고, 런타임이 이벤트 JSON을 객체로 바꿔 핸들러에 넘긴다. [S3]
- 저장 흐름: 콘솔 Test 탭 → Template 선택 → 이름·JSON 입력 → 공유 설정(Private/Shareable) → Save. 저장하지 않고 Test하면 임시 이벤트가 세션 동안만 유지된다. Node.js·Python·Ruby는 Code 탭의 TEST EVENTS 섹션에서도 만들고 실행할 수 있다. [S3]

| 구분 | 비공개(Private) | 공유 가능(Shareable) |
|---|---|---|
| 누가 쓰나 | 만든 사람만 | 같은 AWS 계정의 사용자(타인의 이벤트 편집·호출 포함) |
| 한도·권한 | 함수당 최대 10개 저장, 추가 권한 불필요 | EventBridge 스키마 레지스트리 API 9개 동작(`schemas:CreateRegistry`·`CreateSchema`·`DescribeSchema`·`UpdateSchema` 등) 권한 필요 |
| 저장 위치 | — | EventBridge 스키마 레지스트리 `lambda-testevent-schemas`에 스키마로 저장 |
| 주의점 | — | 편집 저장은 덮어쓰기. 함수를 지워도 스키마는 남아 수동 정리 필요(마지막 이벤트를 지우면 레지스트리 삭제) |
| CLI 연계 | — | `sam remote test-event get/put/list/delete`, `sam remote invoke --test-event-name` [S6][S7] |

(표 근거 [S3]) 원리: 공유 가능 이벤트는 계정 공용 저장소(EventBridge 스키마 레지스트리)를 쓰므로 팀 공유·CLI 접근이 되는 대신 그 저장소에 대한 IAM 권한이 따로 필요하다. [S3]

### 서비스별 이벤트 페이로드 만들기 (Skill 3.3.1)
- 이벤트 소스마다 JSON 구조가 다르므로 손으로 짜기보다 생성기를 쓴다. `sam local generate-event <서비스> <이벤트> [옵션]`은 실제 서비스 이벤트와 같은 구조의 샘플(자리표시자 값)을 만들며, `sam local generate-event`만 실행하면 지원 서비스 목록(alb, apigateway, appsync, batch, cloudformation …)이 나온다. [S4]
- 파일로 저장해 재사용: `sam local generate-event s3 put --bucket <버킷> > events/s3.json` → `sam local invoke --event events/s3.json <함수논리ID>`. S3 put 샘플의 핵심 경로는 `Records[].s3.bucket.name`, `Records[].s3.object.key`, `eventName=ObjectCreated:Put`. [S4]
- HTTP API용 샘플: `sam local generate-event apigateway http-api-proxy > events/apigateway_event.json` 후 `sam local invoke --event …`. [S5]
- REST API Lambda 프록시 **입력** 이벤트의 주요 키: `resource`, `path`, `httpMethod`, `headers`, `multiValueHeaders`, `queryStringParameters`, `multiValueQueryStringParameters`, `requestContext`, `pathParameters`, `stageVariables`, `body`, `isBase64Encoded`. **출력**은 `statusCode`·`headers`·`multiValueHeaders`·`body`·`isBase64Encoded` 형식이어야 하며 다르면 API Gateway가 502를 반환한다. [S9]
- HTTP API는 페이로드 형식 버전 1.0/2.0이 있다. 2.0은 `multiValueHeaders`·`multiValueQueryStringParameters`가 없고 `rawPath`·`cookies`가 있다. 버전을 정하지 않으면 콘솔은 최신 버전을 쓰고, CLI·CloudFormation·SDK는 `payloadFormatVersion`을 반드시 지정해야 한다. 2.0에서는 함수가 유효 JSON만 반환해도(statusCode 없음) API Gateway가 200 등을 추정해 채운다. [S10]
- 스테이지 변수와 스테이지 이름은 프록시 이벤트의 `stageVariables`, `requestContext.stage`로 전달된다. [S9][S10]
- 원리: 프록시 통합은 클라이언트 요청 전체를 `event`로 매핑하므로, 테스트 이벤트도 같은 모양이어야 실제 호출과 같은 코드 경로를 탄다. [S9]

### REST API 배포 = Deployment + Stage (Skill 3.3.2, 3.3.5)
- 호출 가능하게 하려면 배포(Deployment)를 만들어 **스테이지(Stage)**에 연결한다. 스테이지는 API 수명주기 상태(`dev`·`prod`·`beta`·`v2` 등)를 가리키는 논리적 참조이고 호출 URL에 들어간다: `https://{restapi-id}.execute-api.{region}.amazonaws.com/{stageName}`. [S13]
- 스테이지는 '배포(=API 스냅샷)를 가리키는 이름 있는 참조'다. 스테이지 이름은 영숫자·하이픈·밑줄만, 최대 128자이고, API당 스테이지 기본 한도는 10(증가 가능)이다. [S14][S23]
- **재배포가 필요한 변경**: 라우트·메서드·통합·권한 부여자·리소스 정책 등(스테이지 설정 제외). 반대로 Stage·UsagePlan·DomainName·BasePathMapping·Account 갱신은 재배포가 필요 없는 구성으로 분류돼 있다. [S13][S19] (스테이지 설정 저장 후 재배포 안내가 다른 페이지에 있음 → 확인 필요)
- **승격**: `test` 스테이지로 검증한 뒤 `prod`에 재배포하거나 스테이지 변수 값을 test→prod로 바꾸는 방식으로 승격할 수 있다. [S13]
- 스테이지별로 캐싱(과금·프리 티어 제외)·스로틀링(rate/burst는 계정 수준 한도를 넘을 수 없고 best-effort)·CloudWatch 로깅(역할 ARN 필요; Off/Errors only/Errors and info)·상세 메트릭·액세스 로그·X-Ray·WAF·클라이언트 인증서·스테이지 변수·카나리를 설정하고 메서드별로 덮어쓸 수 있다. 데이터 트레이싱은 프로덕션에 권장되지 않는다. [S14]
- CLI: `aws apigateway create-deployment --rest-api-id <id> --stage-name prod --variables sv0=val0,sv1=val1`. [S18]
- IaC: CloudFormation `AWS::ApiGateway::Deployment`는 REST API를 스테이지에 배포하며 "스테이지가 환경 역할"을 하고, 같은 템플릿에 메서드가 있으면 `DependsOn`이 없을 때 "The REST API doesn't contain any methods" 오류가 난다. [S25] SAM `AWS::Serverless::Api`는 RestApi·Stage·Deployment를 항상 생성한다. [S51]
- 원리: 배포가 '그 시점의 API 스냅샷'이라서, 스냅샷 이후 바뀐 리소스 정의는 새 배포를 스테이지에 연결해야 반영된다. [S13][S14] (커스텀 도메인·베이스 경로 매핑 상세 → Task 3.4, Skill 3.4.2)

### 스테이지 변수로 환경별 백엔드 분리 (Skill 3.3.2, 3.3.5)
- 스테이지 변수 = 스테이지에 붙는 key-value 구성값(환경 변수처럼 동작). API 설정·매핑 템플릿에서 `${stageVariables.<이름>}`로 참조하며 호출 시점에 치환된다. 민감 정보(자격 증명) 전달용이 아니다(민감 정보는 Lambda 권한 부여자 출력 사용). [S15]
- 대표 용도: ① 스테이지별 다른 HTTP 백엔드(`http://${stageVariables.url}`) ② 스테이지별 다른 Lambda 함수 이름·버전/별칭 ③ 매핑 템플릿으로 설정값(예: DynamoDB 테이블 이름) 전달. 단, 스테이지 변수로 '통합 유형' 자체(HTTP 프록시↔Lambda 프록시)를 바꿀 수는 없다. [S15]
- 사용 가능한 곳: 파라미터 매핑 식, 매핑 템플릿, HTTP 통합 URI, AWS 통합 URI, Lambda 함수 이름/버전·별칭, Cognito 사용자 풀 권한 부여자 ARN, 통합 자격 증명 ARN. [S16]
- Lambda를 스테이지 변수로 지정하면 호출 권한을 `aws lambda add-permission`으로 **수동** 설정해야 하고, Lambda는 API와 **같은 계정**이어야 한다(교차 계정 미지원). [S15][S16]
- 한도: 스테이지당 100개, 키 64자, 값 512자(REST·HTTP 동일). SAM `Variables`의 값은 `[A-Za-z0-9._~:/?#&=,-]+` 패턴. [S23][S24][S50]
- 테스트 호출은 `stageVariables`를 시뮬레이션해 특정 스테이지 상황을 흉내 낼 수 있고 [S12], 프록시 이벤트에는 `stageVariables`·`requestContext.stage`가 들어와 Lambda가 읽을 수 있다. [S9] (Lambda에서 스테이지 변수 활용 상세 → Task 3.4, Skill 3.4.10)
- 패턴 예: 스테이지 `dev`/`test`/`prod`마다 변수 `alias`=`dev`/`test`/`prod`를 두고 통합 URI를 `…function:<함수명>:${stageVariables.alias}/invocations` 형태로 둔다(문서가 보여 주는 'version/alias' 형식). [S16]
- 원리: 같은 API 정의에 환경별 값을 '런타임 치환'으로 주입하므로 스테이지가 늘어도 API 정의는 하나다. [S15]

### HTTP API의 스테이지·자동 배포와 REST와의 차이 (Skill 3.3.2, 3.3.5)
- HTTP API도 스테이지(`dev`·`prod`·`beta`·`v2` …)를 쓰고, API URL 루트에서 제공되는 `$default` 스테이지를 만들 수 있다. 배포는 API 구성의 스냅샷이며, 자동 배포를 켜면 변경이 자동 반영된다. [S20]
- 자동 배포 기본값은 만드는 방식에 따라 다르다: CloudFormation `AWS::ApiGatewayV2::Stage`의 `AutoDeploy` 기본 `false`, 관리형 오버라이드(`StageOverrides`)의 `AutoDeploy` 기본 `true`. [S26][S27] (콘솔 빠른 생성의 기본값은 미확인 → 확인 필요)
- SAM `AWS::Serverless::HttpApi`: `StageName`을 주면 `<LogicalId><이름>Stage`, 안 주면 `<LogicalId>ApiGatewayDefaultStage`(`$default`) 스테이지 리소스가 생긴다. [S52] HTTP API도 스테이지 변수를 지원한다(통합 엔드포인트·Lambda 지정). [S21]

| 기능 | REST API | HTTP API |
|---|---|---|
| 사용자 제어 배포(수동) | 예 | 예 |
| 자동 배포 | 아니오 | 예 |
| 카나리 릴리스 배포 | 예 | 아니오 |
| 테스트 호출(Test) | 예 | 아니오 |
| 캐싱 · 실행(Execution) 로그 | 예 | 아니오 |
| 스테이지 변수 | 예 [S15] | 예 [S21] |

(표 근거 [S22]) 원리: HTTP API는 기능을 줄여 단순·저가로 설계됐기 때문에 REST API의 관리형 기능(캐싱·카나리·테스트 호출 등)이 빠져 있고 대신 자동 배포를 제공한다. [S22]

### API Gateway 캐나리 릴리스 요약 (Skill 3.3.2)
- 캐나리 = 스테이지(프로덕션 릴리스)에 새 버전의 배포를 '캐나리'로 붙여 일부 트래픽만 보내는 방식. `canarySettings`에 배포 ID, 트래픽 비율(0.0~100.0), 캐나리 전용 스테이지 변수 오버라이드(`stageVariableOverrides`), 스테이지 캐시 사용 여부(`useStageCache`)를 지정한다. [S17]
- 캐나리가 켜져 있으면 캐나리를 끄고 설정을 제거하기 전에는 스테이지를 다른 비캐나리 배포에 연결할 수 없다. 캐나리 요청은 전용 로그 그룹(`…/{stage-name}/Canary`)에도 기록된다. [S17]
- CLI: `aws apigateway create-deployment --rest-api-id <id> --stage-name prod --canary-settings percentTraffic=10.5,stageVariableOverrides={sv1='val2'},useStageCache=false`. [S18] (승격·롤백·전략 비교 → Task 3.4)

### Lambda 버전·별칭: '승인된 버전' 환경 (Skill 3.3.3, 3.3.5)
- `$LATEST`(비게시)는 코드를 배포할 때마다 덮어써진다. 게시(publish)하면 `$LATEST`의 복사본이 새 버전이 되고, 게시 후에는 코드·런타임·아키텍처·메모리·레이어 등이 불변이다(바꾸려면 `$LATEST`를 고치고 재게시). 트리거·대상(destinations)·프로비저닝된 동시성·비동기 호출 설정·DB 연결/프록시는 게시 버전에도 설정할 수 있다. 버전 번호는 단조 증가하며 재사용되지 않는다. [S28] 환경 변수도 게시된 버전에서는 바꿀 수 없다. [S32]
- 호출 대상 지정: 한정(qualified) ARN `…:function:helloworld:42`은 특정 버전, 비한정 ARN은 `$LATEST`를 암묵 호출한다. [S28]
- **별칭** = 버전을 가리키는 '갱신 가능한 포인터'(고유 ARN). 별칭은 버전만 가리키고 다른 별칭은 가리킬 수 없다. 이벤트 소스 매핑·리소스 정책에 별칭 ARN을 쓰면 버전이 바뀌어도 매핑·정책을 고칠 필요가 없다. [S29][S31] CLI: `create-alias`·`update-alias`·`delete-alias`. [S29]
- **가중 별칭(카나리)**: 별칭 하나가 최대 2개 버전을 가리키며 둘 다 게시된 버전이어야 하고(`$LATEST` 불가) 같은 실행 역할·같은 DLQ 구성이어야 한다. `--routing-config AdditionalVersionWeights={"2"=0.03}`이면 버전 2가 3%, 첫 버전이 나머지(97%)를 받는다. 전체 전환은 `update-alias --function-version 2 --routing-config AdditionalVersionWeights={}`. 낮은 트래픽에서는 실제 비율이 설정값과 크게 다를 수 있다(확률 모델). [S30]
- 어느 버전이 응답했는지: 동기 호출 응답 헤더 `x-amz-executed-version`, 로그 `START … Version: N`, 별칭 메트릭의 `ExecutedVersion` 차원. [S30]
- SAM: `AutoPublishAlias: live`가 새 코드를 감지해 버전을 게시하고 `live` 별칭을 새 버전으로 옮기며, `DeploymentPreference`(예: `Linear10PercentEvery2Minutes`)로 CodeDeploy가 트래픽을 점진 이동한다. 생성 리소스는 `AWS::Lambda::Alias`·`AWS::Lambda::Version`. [S30][S53] (CodeDeploy·롤백 상세 → Task 3.4)
- 환경 매핑 예: dev/test/prod 별칭 → 서로 다른 게시 버전. API Gateway는 스테이지 변수(`:${stageVariables.alias}`)로, 이벤트 소스는 별칭 ARN으로 참조한다. [S16][S31]
- 원리: 게시 버전은 불변 스냅샷이라 '테스트를 통과한 바로 그것'을 보존하고, 환경은 별칭이 가리키는 버전만 바꿔 재빌드 없이 승격한다. [S28][S29][S39]

### 컨테이너 이미지 태그·다이제스트로 '승인된 이미지' 고정 (Skill 3.3.3)
- ECR 저장소의 태그 가변성 기본값은 `MUTABLE`(덮어쓰기 허용)이고, `IMMUTABLE`이면 이미 있는 태그로 푸시할 때 `ImageTagAlreadyExistsException`이 반환된다. `IMMUTABLE_WITH_EXCLUSION`/`MUTABLE_WITH_EXCLUSION`과 와일드카드 제외 필터도 있다(문서 서술 상충 → 확인 필요). [S34][S35]
- **재태깅(승격)**: `aws ecr batch-get-image`로 매니페스트를 얻고 `aws ecr put-image --image-tag <새 태그> --image-manifest …`로 새 태그를 붙이면 Docker pull/push 없이 가능하다(결과: 한 이미지에 `latest`와 `2017.03`처럼 태그가 여러 개). [S36]
- Lambda 컨테이너 이미지 함수는 배포 시 태그를 다이제스트로 **해석**한다. ECR에서 태그가 새 이미지를 가리키도록 바꿔도 함수는 자동 갱신되지 않는다(`update-function-code --image-uri` 재실행). [S37] Docker Buildx로 `latest`를 푸시하면 이미지 인덱스가 만들어져 배포가 실패할 수 있어, 단일 플랫폼 이미지의 `@sha256:` 다이제스트를 지정해 해결한다. [S38]
- 원리: 태그는 옮겨 다니는 라벨이고 다이제스트는 특정 이미지를 가리키므로, 승인된 이미지를 환경에 고정하려면 불변 태그(또는 다이제스트 참조)를 써야 한다. [S34][S37][S38]

### Amplify Hosting 브랜치 = 환경 (Skill 3.3.3, 3.3.5)
- Amplify는 Git 브랜치를 연결할 때마다 새 배포를 만든다. 보통 `main`=프로덕션(릴리스 코드), `develop`=통합 브랜치로 두어 베타 테스터가 프로덕션 사용자에게 영향 없이 `develop` 배포를 테스트한다. 기본 도메인 예: `https://main.appid.amplifyapp.com`, `https://dev.appid.amplifyapp.com`. [S40]
- 패턴 기반 자동 감지: `*`(모든 브랜치), `release*`처럼 패턴을 쉼표로 여러 개 지정해 맞는 브랜치를 자동 연결·배포하고, 자동 생성 브랜치에 접근 제어(비밀번호)를 걸 수 있다. Gen 2는 삭제된 브랜치를 자동 해제(auto-disconnection)하는 옵션이 있다. [S41][S43]
- 환경 변수는 기본적으로 모든 브랜치에 적용되며 브랜치별 override를 추가할 수 있다. [S42]
- 풀 리퀘스트 프리뷰: PR이 열리면 고유 미리보기 URL로 배포되고, 풀스택이면 임시 백엔드가 만들어졌다가 PR이 닫히면 삭제된다. [S44] Gen 1 백엔드 앱은 브랜치마다 새 백엔드 환경을 만들지 기존 백엔드를 공유할지 고를 수 있다. [S41]
- 원리: 브랜치마다 별도 배포가 생기므로 브랜치(develop/main)가 곧 환경 경계다. [S40]

### AWS Copilot 환경 — 개념과 현재 상태 (Skill 3.3.3)
- 개념: 환경은 그 안에 배포된 모든 서비스가 공유하는 리소스 집합(네트워크·ECS 클러스터·로드 밸런서 등)이다. `copilot env init`(이름·AWS 프로필 → 계정/리전 결정) → `copilot env deploy`(환경 인프라 생성, 서비스는 아직 배포되지 않음) → `copilot deploy`로 서비스 배포. 같은 서비스를 환경마다 다른 설정(예: 프로덕션에 컨테이너 더 많이)으로 둘 수 있다. [S45][S46] 환경마다 별도 네트워킹 스택과 ECS 클러스터가 CloudFormation 스택(`<앱>-<환경>`, 예 `pubsub-test`)으로 만들어진다. [S47]
- **현황**: Copilot CLI는 2026-06-12에 지원 종료 — 오늘(2026-10-17) 기준 이미 종료. GitHub에 오픈소스로 남지만 새 기능·보안 업데이트가 없고, AWS는 ECS Express Mode 또는 CDK L3 구성으로의 이전을 안내한다. Copilot이 만든 것은 표준 CloudFormation 스택이라 계속 관리할 수 있다. [S45] 시험 가이드 v2.1의 In-Scope 목록에는 Copilot이 없다. [S2]
- 문항화 팁: '환경 = 네트워크+공유 인프라, 환경별 서비스 설정' 같은 개념만 다루고 '현재 권장 도구'로 Copilot을 정답 처리하지 않는다. (WebFetch 요약본 [S46]은 원문 인용 불가 → 사실 표에는 블로그 [S45][S47]만 사용)

### SAM 템플릿 구조와 생성되는 리소스 (Skill 3.3.4)
- 기본 골격: `AWSTemplateFormatVersion` · `Transform: AWS::Serverless-2016-10-31`(최상위, 리터럴 문자열만 가능 — 파라미터·함수로 지정 불가) · `Globals`(여러 리소스가 공유할 Runtime·Timeout·Environment 등을 한 번에 선언) · `Resources` · `Outputs`. [S59][S57] CloudFormation 템플릿에서 필수 섹션은 `Resources` 하나뿐이고, `Parameters`·`Mappings`·`Conditions`는 환경별 값 분기에 쓴다. [S60]
- SAM 전용 리소스 유형(조회 시점 14종): `Api`, `Application`, `CapacityProvider`, `Connector`, `Function`, `GraphQLApi`, `HttpApi`, `WebSocketApi`, `LayerVersion`, `MicrovmImage`, `NetworkConnector`, `SimpleTable`, `StateMachine`, `WebFunction` (일반 CloudFormation 리소스도 함께 사용). [S49]
- 변환 결과: `AWS::Serverless::Function` → Lambda 함수 + 실행 역할(IAM Role) [S59]; 스트리밍 이벤트(`DynamoDB`·`Kinesis`·`MQ`·`MSK`·`SQS`) → `AWS::Lambda::EventSourceMapping` [S53]; `AutoPublishAlias` → `AWS::Lambda::Alias`+`AWS::Lambda::Version` [S53]; `AWS::Serverless::Api` → `AWS::ApiGateway::RestApi`+`Stage`+`Deployment` [S51]; `AWS::Serverless::HttpApi` → `AWS::ApiGatewayV2::Api`(+Stage) [S52].
- `AWS::Serverless::Api` 포인트: `StageName` 필수(암묵적 API의 스테이지는 `Prod`), `Variables`(스테이지 변수), `CanarySetting`, `MethodSettings`(로깅·메트릭·캐시 TTL·스로틀링), `CacheClusterEnabled`, `TracingEnabled`, `AlwaysDeploy`(변경이 없어도 항상 배포). `OpenApiVersion`을 지정하면 기본 스테이지 `Stage`가 만들어지지 않는다는 서술이 있다. [S50]
- 원리: SAM 템플릿은 곧 CloudFormation 템플릿이라 CloudFormation이 변환(Transform)을 처리하고, 그 결과 리소스를 스택이 관리한다. [S59]

### SAM·CloudFormation 배포 흐름과 환경별 배포 (Skill 3.3.4, 3.3.5)
- SAM 흐름: `sam build` → 최초 `sam deploy --guided`(스택 이름·리전·변경 확인 여부·IAM 역할 생성 허용·롤백 비활성·구성 파일 저장을 묻는다) → 이후 `sam deploy`는 `samconfig.toml` 값을 사용. 내부 단계: zip을 S3(SAM 관리 버킷)에 업로드하거나 컨테이너 이미지를 ECR에 업로드 → **CloudFormation 변경 세트 생성** → 스택으로 배포 → 배포된 템플릿의 `CodeUri`를 새 값으로 갱신. [S54]
- 환경별 설정: `samconfig` 파일은 환경 > 명령 > 파라미터 구조(TOML 기본, YAML 가능)이며 `[prod.global.parameters] stack_name = "prod-app"` 후 `sam deploy --config-env prod`로 고른다(기본 환경 `default`). 우선순위: 명령줄 > 구성 파일(`parameter_overrides` 포함) > 템플릿 `Parameters`, 구성 파일 안에서는 명령별 항목이 global보다 우선. [S55][S56]
- `sam sync`는 개발 환경용(로컬 변경을 빠르게 클라우드에 반영)이고, 프로덕션은 `sam deploy` 또는 CI/CD 파이프라인을 쓰라고 권고한다. [S58]
- CloudFormation **변경 세트**는 적용 전 영향을 미리 보여 주고 실행 전까지 스택을 바꾸지 않는다. [S61] `aws cloudformation deploy`는 변경 세트를 만들고 실행하며(`--no-execute-changeset`으로 검토만 가능), 템플릿이 51,200바이트를 넘으면 `--s3-bucket`이 필요하고, `--parameter-overrides`로 환경별 파라미터를 준다. [S65]
- **Capabilities**: IAM 리소스가 있으면 `CAPABILITY_IAM`(이름 지정 시 `CAPABILITY_NAMED_IAM`)이 필요하고 없으면 `InsufficientCapabilities` 오류. 매크로·변환(`AWS::Serverless`·`AWS::Include`)이 든 템플릿을 변경 세트 검토 없이 직접 생성/갱신하면 `CAPABILITY_AUTO_EXPAND` 승인이 필요하며, 변경 세트 생성에는 영향이 없다. [S64][S65]
- **드리프트 감지**: 스택 밖(콘솔 등)에서 바뀐 실제 구성이 템플릿의 기대값과 다른지 비교한다. 리소스가 하나라도 드리프트면 스택이 DRIFTED, 미지원 리소스는 NOT_CHECKED, 중첩 스택은 자동 포함되지 않으며(별도 실행), 템플릿·파라미터로 명시한 속성만 비교한다. [S62]
- 한도: 템플릿당 리소스 500·파라미터 200·출력 200·매핑 200, 템플릿 본문 크기는 요청 51,200바이트 / S3 객체 1 MB. [S63]
- 원리: 변경 세트 = '적용 전 미리보기', 드리프트 = '적용 후 현실과의 차이' — 서로 다른 시점의 점검이다. [S61][S62]

### Amazon Q Developer로 자동화 테스트 생성 (Skill 3.3.6) — 현황 변화 큼
- 기능: IDE 채팅에서 코드(파일·폴더·워크스페이스를 컨텍스트로 지정 가능)를 바탕으로 **단위 테스트를 생성**해 SDLC 전반의 테스트 자동화를 돕는다. 이 기능은 문서·IDE에서 예전에 `/test`로 불렸으나 지금은 그렇게 지칭하지 않는다. [S72]
- 2024년경 소개된 `/test` 에이전트 설명: 필요한 테스트 케이스를 식별하고, 격리 테스트용 목(mock)·스텁을 만들고, 테스트 코드를 생성한다. 당시 Java·Python 프로젝트를 VS Code·JetBrains에서 지원(게시 시점 정보 — 현재 지원 범위는 확인 필요). [S74]
- 활용 요령(공식 블로그): 명확한 프롬프트와 컨텍스트 제공, 테스트 시나리오를 먼저 제안받기, boto3 같은 의존성은 Moto 등으로 모킹하도록 지시, 큰 작업은 작게 쪼개기. 출력은 비결정적이므로 개발자가 검토·판단한다. [S75]
- **현황(2026-10-17 기준)**: Q Developer **IDE 플러그인과 유료 구독**은 2027-04-30에 지원 종료, 신규 가입(Free Tier·구독)은 2026-05-15부터 차단, 후속은 Kiro. AWS 콘솔·문서 사이트·모바일 앱·Slack/Teams 챗 앱 등 first-party 경험은 영향이 없다. [S71][S73]
- 시험 관점: 공식 가이드 v2.1은 Skill 3.3.6과 In-Scope 목록에 Q Developer를 유지한다. [S1][S2] → 문항은 '단위 테스트 자동 생성에 Q Developer를 사용한다'는 개념 수준으로 제한하고 `/test` 명령어·지원 언어 같은 세부에 의존하지 않는다.
- 원리: 생성형 AI 출력은 비결정적이므로 생성된 테스트는 '초안'이고, 사람이 검토해 채택해야 자동화 테스트가 된다. [S75]

## 시험에서 묻는 방식

> 문제 저작자를 위한 제안이며, 시험이 반드시 이렇게 낸다는 단정이 아니다.

1. **테스트 자산 만들기 (Skill 3.3.1·3.3.6)** — "같은 AWS 계정의 팀원들이 S3 업로드 이벤트로 트리거되는 Lambda 함수를 동일한 JSON으로 반복 테스트하고, 같은 이벤트를 CLI에서도 재사용하려 한다."
   → 정답 단서: *공유 가능(Shareable) 테스트 이벤트*(EventBridge 스키마 레지스트리) → `sam remote test-event` / `sam remote invoke --test-event-name`. 변형: 샘플 JSON이 필요 → `sam local generate-event s3 put`; HTTP API는 페이로드 형식 1.0/2.0 차이; IDE에서 단위 테스트 초안 자동 생성 → Amazon Q Developer(현황 주의: 확인 필요). [S3][S4][S6][S7][S10][S72]
2. **환경별 API 배포 (Skill 3.3.2·3.3.5)** — "REST API의 통합을 수정했는데 클라이언트에는 이전 동작이 보인다. 같은 API 정의로 dev/test/prod마다 다른 백엔드(Lambda 별칭)를 호출하게 하고 싶다."
   → 정답 단서: *API를 스테이지에 재배포(Deployment)* + *스테이지 변수 `${stageVariables.x}`* → Lambda 호출 권한은 수동 추가, Lambda는 같은 계정. 변형: HTTP API는 *자동 배포* 옵션, 카나리·테스트 호출·캐싱은 REST만. [S13][S15][S16][S19][S22]
3. **승인된 버전 기반 환경 (Skill 3.3.3)** — "통합 테스트를 통과한 바로 그 빌드를 운영에 쓰고, 신규 빌드는 일부 트래픽에만 먼저 노출하고 싶다. 컨테이너·프런트엔드에도 같은 원칙을 적용하려 한다."
   → 정답 단서: Lambda *게시 버전(불변) + 별칭*, *가중 별칭*(최대 2개 게시 버전, `$LATEST` 불가); ECR *불변 태그·다이제스트·재태깅(`put-image`)*, Lambda 이미지는 태그를 갱신해도 함수가 자동 갱신되지 않음; Amplify *브랜치 배포*(main=프로덕션, develop=통합, 패턴 자동 감지). Copilot 환경은 개념만(지원 종료). [S28][S30][S34][S36][S37][S40][S41][S45]
4. **IaC 배포 (Skill 3.3.4)** — "SAM 템플릿으로 Lambda·API Gateway를 환경별 스택에 배포하면서 적용 전에 변경을 확인하고 싶다. 배포 명령이 InsufficientCapabilities 오류를 낸다. 누군가 콘솔에서 리소스를 직접 수정했는지도 확인하려 한다."
   → 정답 단서: `Transform: AWS::Serverless-2016-10-31` · `sam deploy`(변경 세트, `--config-env`) · `--capabilities CAPABILITY_IAM`(이름 지정 시 NAMED_IAM, 변환·매크로를 변경 세트 없이 쓰면 AUTO_EXPAND) · *드리프트 감지*. [S54][S55][S59][S61][S62][S64][S65]

## 흔한 함정·혼동 짝

| # | A vs B | 혼동 이유 | 구분 기준 한 줄 | 출처 |
|---|---|---|---|---|
| 1 | 비공개 vs 공유 가능 테스트 이벤트 | 둘 다 콘솔 Test 탭에서 '저장'한다 | 비공개=작성자만·함수당 10개·추가 권한 불필요 / 공유 가능=같은 계정 공유·EventBridge 스키마 레지스트리 저장·schemas 권한 필요 | [S3] |
| 2 | Deployment vs Stage | 둘 다 'API 버전'처럼 보인다 | Deployment=API 스냅샷, Stage=그 배포를 가리키는 이름 있는 참조(URL에 포함); 스테이지 설정만 바꾸는 갱신은 재배포 불필요 구성으로 분류됨 | [S13][S14][S19] |
| 3 | REST API 수동 재배포 vs HTTP API 자동 배포 | 둘 다 'API Gateway 스테이지' | REST=변경 후 재배포 필요(자동 배포 없음), HTTP=자동 배포 옵션; 카나리·테스트 호출·캐싱은 REST만 | [S13][S20][S22] |
| 4 | 스테이지 변수 vs Lambda 환경 변수 | 둘 다 '환경 변수'로 불린다 | 스테이지 변수=API Gateway 스테이지에 붙고 호출 시 `${stageVariables.x}`로 치환 / Lambda 환경 변수=함수 구성(게시 버전에선 변경 불가) | [S15][S32] |
| 5 | Lambda 버전 vs 별칭 | 둘 다 ARN 끝에 붙는 한정자 | 버전=불변 번호, 별칭=가리키는 버전을 바꿀 수 있는 포인터(다른 별칭은 못 가리킴) | [S28][S29][S31] |
| 6 | Lambda 가중 별칭 vs API Gateway 카나리 | 둘 다 '신규 버전에 일부 트래픽' | 가중 별칭=한 별칭이 게시 버전 2개(`$LATEST` 불가), 카나리=스테이지에 `canarySettings`(0.0~100.0) 부착·REST만 | [S30][S17][S22] |
| 7 | 가변 태그(`latest`) vs 불변 태그·다이제스트 | 같은 이름 태그가 다른 이미지를 가리킬 수 있다 | ECR 불변이면 재푸시 시 `ImageTagAlreadyExistsException`; Lambda는 배포 시 태그→다이제스트로 해석하고 태그를 바꿔도 자동 갱신 안 됨 | [S34][S35][S37] |
| 8 | SAM vs CloudFormation vs CDK | 셋 다 결국 CloudFormation 스택으로 배포 | SAM=CFN 템플릿 확장(Transform), CDK=코드→`cdk synth`→CFN 템플릿, CFN=원본 템플릿 | [S48][S59][S67] |
| 9 | `sam deploy` vs `sam sync` vs `aws cloudformation deploy` | 셋 다 클라우드에 반영한다 | `sam sync`=개발 환경용 빠른 동기화, `sam deploy`=변경 세트 기반 정식 배포(프로덕션·CI/CD), `cloudformation deploy`=일반 템플릿의 변경 세트 생성+실행 | [S58][S54][S65] |
| 10 | CAPABILITY_IAM/NAMED_IAM vs CAPABILITY_AUTO_EXPAND | 모두 `--capabilities` 값처럼 보인다 | IAM 계열=IAM 리소스(이름 지정은 NAMED), AUTO_EXPAND=매크로·변환 템플릿을 변경 세트 없이 직접 생성할 때(변경 세트 생성엔 영향 없음); `cloudformation deploy` 문서는 IAM 계열 두 값만 명시 | [S64][S65] |
| 11 | 변경 세트 vs 드리프트 감지 | 둘 다 '스택 변경 확인' | 변경 세트=적용 전 미리보기, 드리프트=스택 밖에서 바뀐 실제 구성과 템플릿 비교 | [S61][S62] |
| 12 | Q Developer IDE 플러그인 vs 콘솔·챗 앱의 Q Developer | 같은 이름의 서비스 | IDE 플러그인·유료 구독은 2027-04-30 지원 종료(신규 가입 2026-05-15 차단), 콘솔·문서 사이트·챗 앱 등 first-party는 영향 없음 | [S71] |

## 자가 점검 문항 후보

> **초안·미검수** — 노트 작성자가 만든 초안이다. 사람의 검수와 `verified` 전환 전에는 사용하지 않는다. 정답 근거는 모두 이번 세션에 열어 본 공식 페이지다.

### 문항 1 (Skill 3.3.1 · intermediate)
**문제**: 같은 AWS 계정의 개발자 여러 명이 S3 업로드 이벤트로 트리거되는 Lambda 함수를 동일한 JSON 이벤트로 반복 테스트한다. 이 이벤트를 팀이 공유하고 CLI에서도 불러 쓰려면 어떻게 해야 하는가?
- A. 콘솔에서 이벤트를 비공개(Private)로 저장하고 각자 JSON을 복사해 사용한다
- B. 콘솔에서 이벤트를 공유 가능(Shareable)으로 저장하고 `sam remote invoke <함수> --test-event-name <이름>`으로 호출한다
- C. 이벤트 JSON을 함수의 환경 변수에 저장하고 핸들러가 읽어 처리하도록 코드를 바꾼다
- D. 이벤트를 포함해 함수 버전을 게시하고 버전 번호로 호출한다

**정답**: B
**정답 근거**: 공유 가능 테스트 이벤트는 같은 계정의 다른 사용자와 공유되고 EventBridge 스키마 레지스트리에 스키마로 저장되며, SAM CLI는 `--test-event-name`으로 이 이벤트를 클라우드의 함수에 전달한다. 근거: https://docs.aws.amazon.com/lambda/latest/dg/testing-functions.html , https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/using-sam-cli-remote-invoke.html
**오답 해설**: A) 비공개 이벤트는 작성자만 쓸 수 있어 공유되지 않는다. C) 환경 변수는 호출 입력(테스트 이벤트)을 대신하지 못하고 코드 변경까지 요구한다. D) 게시 버전은 코드와 구성의 불변 스냅샷일 뿐 테스트 이벤트를 담지 않는다(https://docs.aws.amazon.com/lambda/latest/dg/configuration-versions.html).

### 문항 2 (Skill 3.3.2·3.3.5 · intermediate)
**문제**: 하나의 REST API 정의를 dev·test·prod 스테이지에 배포하고, 각 스테이지가 같은 계정의 서로 다른 Lambda 별칭(dev, test, prod)을 호출하게 하려 한다. 올바른 설계는?
- A. 통합의 Lambda 대상에 스테이지 변수(`${stageVariables.…}`)를 쓰고 스테이지마다 값을 다르게 지정하며, 해당 Lambda에 API Gateway 호출 권한을 `aws lambda add-permission`으로 추가한다
- B. 스테이지 변수로 dev 스테이지는 HTTP 프록시 통합, prod 스테이지는 Lambda 프록시 통합처럼 통합 유형 자체를 전환한다
- C. 환경별 데이터베이스 암호를 스테이지 변수에 저장해 Lambda로 전달한다
- D. prod 스테이지가 다른 AWS 계정의 Lambda 별칭을 스테이지 변수로 호출하게 한다

**정답**: A
**정답 근거**: 스테이지 변수는 Lambda 함수 이름이나 버전/별칭 자리에 쓸 수 있으며, 스테이지 변수로 지정한 Lambda는 권한을 수동으로 설정해야 하고 API와 같은 계정이어야 한다. 근거: https://docs.aws.amazon.com/apigateway/latest/developerguide/stage-variables.html , https://docs.aws.amazon.com/apigateway/latest/developerguide/aws-api-gateway-stage-variables-reference.html
**오답 해설**: B) 스테이지 변수로 한 스테이지는 HTTP 프록시, 다른 스테이지는 Lambda 프록시처럼 통합 유형을 바꿀 수 없다. C) 스테이지 변수는 자격 증명 같은 민감 정보 전달용이 아니다. D) 스테이지 변수는 교차 계정 Lambda를 지원하지 않는다.

### 문항 3 (Skill 3.3.3 · intermediate)
**문제**: 별칭 `prod`가 통합 테스트를 통과한 게시 버전 5를 가리킨다. 새 게시 버전 6을 트래픽의 5%에만 먼저 노출해 검증하려 한다. 올바른 방법은?
- A. `aws lambda update-alias --function-name my-function --name prod --routing-config AdditionalVersionWeights={"6"=0.05}`를 실행한다
- B. 별칭 `prod`가 `$LATEST`와 버전 5를 5:95로 가리키도록 가중치를 설정한다
- C. 버전 5에 새 코드를 다시 배포해 같은 버전 번호로 점진 반영한다
- D. 새 별칭 `prod-canary`를 만들어 `prod` 별칭과 버전 6을 5:95로 가리키게 한다

**정답**: A
**정답 근거**: 별칭은 최대 2개의 게시된 버전을 가리킬 수 있고 `routing-config`의 `AdditionalVersionWeights`로 추가 버전의 비율을 지정하며 첫 버전이 나머지 비율을 받는다. 근거: https://docs.aws.amazon.com/lambda/latest/dg/configuring-alias-routing.html
**오답 해설**: B) 가중 별칭은 게시된 버전만 가리킬 수 있어 `$LATEST`는 쓸 수 없다. C) 게시된 버전의 코드는 불변이다(https://docs.aws.amazon.com/lambda/latest/dg/configuration-versions.html). D) 별칭은 버전만 가리키며 다른 별칭을 가리킬 수 없다(https://docs.aws.amazon.com/lambda/latest/dg/using-aliases.html).

### 문항 4 (Skill 3.3.4 · intermediate)
**문제**: 개발자가 `Transform: AWS::Serverless-2016-10-31`을 쓰는 SAM 템플릿(Lambda 함수와 자동 생성되는 실행 역할 포함)을 `aws cloudformation deploy --template-file template.yaml --stack-name my-stack`으로 배포했더니 `InsufficientCapabilities` 오류가 발생했다. 해결 방법은?
- A. `--capabilities CAPABILITY_IAM`을 추가한다
- B. `--no-execute-changeset`을 추가한다
- C. `--disable-rollback`을 추가한다
- D. `--force-upload`를 추가한다

**정답**: A
**정답 근거**: deploy 명령은 IAM 리소스가 있는 스택에서 capability를 명시해야 하며(사용자 지정 이름이 있는 IAM 리소스는 `CAPABILITY_NAMED_IAM`) 지정하지 않으면 `InsufficientCapabilities` 오류를 반환한다. SAM 변환은 함수에 실행 역할(IAM Role)을 만든다. 근거: https://docs.aws.amazon.com/cli/latest/reference/cloudformation/deploy.html , https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/transform-aws-serverless.html
**오답 해설**: B) 변경 세트를 만들고 실행하지 않은 채 종료할 뿐 capability 승인과 무관하다. C) 실행 실패 시 이전에 프로비저닝된 상태를 보존하는 옵션이다. D) S3에 있는 기존 파일을 덮어써 업로드하는 옵션이다.
