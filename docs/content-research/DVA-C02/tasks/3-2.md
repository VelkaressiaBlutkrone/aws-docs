## 핵심 개념

### 클라우드 테스트가 기준이다 — 테스트 유형과 기법 (Skill 3.2.1, 3.2.2)

- 서버리스에서도 테스트 유형은 같다. 단위 테스트는 격리된 코드 블록(예: 배송비 계산 로직), 통합 테스트는 둘 이상의 구성 요소·서비스가 상호작용하는 경우(예: 큐의 이벤트를 함수가 처리하는지, 보통 클라우드 환경), 종단 간(E2E) 테스트는 애플리케이션 전체 동작을 검증한다 [S1].
- AWS는 클라우드에 배포한 코드·서비스를 대상으로 하는 테스트가 품질을 가장 정확하게 보여 준다고 안내한다. 큐·테이블·이벤트 버스·보안 정책은 로컬에서 완전히 복제할 수 없고, 로컬과 클라우드의 차이가 버그 재현·수정 시간을 늘리기 때문이다(원리) [S1].
- 다른 서비스를 호출하지 않는 순수 계산 함수도 클라우드에서 확인해야 한다. 타임아웃·메모리 설정과 CloudWatch Logs 기록 권한(IAM)이 결과를 좌우하고 이는 모의·에뮬레이션으로 정확히 재현되지 않는다 [S1].
- CI는 코드를 QA·스테이징·프로덕션으로 승격하기 전에 클라우드에 프로비저닝한 리소스에 대해 테스트를 실행해야 한다 [S1].
- 테스트하기 쉬운 코드: 핸들러는 이벤트·컨텍스트에서 필요한 값만 꺼내 비즈니스 로직 메서드에 넘기는 얇은 어댑터로 두고 Lambda 세부와 로직을 분리한다 [S1].

### 배포된 코드를 테스트하는 AWS 서비스·도구 (Skill 3.2.1)

### 통합 테스트와 외부 종속성 모의 (Skill 3.2.2 ✏️)

- 통합 테스트에 집중하는 것이 모범 사례다. 앱을 클라우드 환경에 배포(로컬이나 CI/CD)한 뒤 테스트가 시스템을 호출해 기대 동작을 검증한다. 예: API Gateway 엔드포인트에 합성 HTTP 호출을 보내 응답 페이로드를 확인하면 Lambda 코드뿐 아니라 각 서비스 구성과 서비스 간 IAM 권한까지 검증된다 [S1].
- 자동화 패턴: 테스트가 배포된 스택의 출력(API 엔드포인트·함수 ARN·보안 역할)을 먼저 가져온 뒤 엔드포인트로 요청을 보낸다(`tests/integration` 예제, `python -m pytest -s tests/integration -v`) [S1].
- 같은 테스트를 로컬·클라우드에 재사용: `sam local start-lambda`가 `http://127.0.0.1:3001`에서 Lambda 호출 엔드포인트를 흉내 내므로 SDK 클라이언트의 `endpoint_url`만 바꿔 같은 테스트를 로컬 함수와 배포된 함수에 수정 없이 실행할 수 있다 [S15].
- 격리된 환경: 개발자별 전용 AWS 계정이 이상적이다. 계정을 공유하면 스택 이름 접두사(개발자 ID)나 코드 브랜치별 스택으로 소유권을 나누고, `sam deploy`·`sam sync`가 고유 접두사 스택을 쓰도록 TOML 설정을 둔다. 사전 프로덕션·프로덕션은 계정 단위로 경계를 두며(할당량 간섭·고객 데이터 접근 방지) 부하 테스트는 프로덕션 스택과 분리한다 [S1].
- 모의를 쓸 곳: 복잡한 내부 비즈니스 로직의 빠른 단위 테스트, 통제할 수 없는 서드파티 API·SaaS 대체, 서비스 장애처럼 재현하기 어려운 실패. 통합 테스트에서는 효과가 줄고 종단 간 테스트에는 쓰지 않는다. 서비스 호출 구현이 맞는지는 모의가 아니라 클라우드 호출로 검증한다 [S1].

| 모의 수단 | 용도 | 핵심 사실 |
|---|---|---|
| API Gateway MOCK 통합 | 백엔드 없이 API Gateway가 응답을 직접 생성(미구현 API를 의존 팀에 먼저 제공, 랜딩 페이지) | 통합 요청 매핑 템플릿이 `{"statusCode": 200}`을 만들면 같은 상태 코드의 통합 응답 매핑 템플릿이 본문을 만든다. 쿼리 파라미터 등 조건으로 성공·오류 응답을 분기할 수 있다. 큰 응답 템플릿에는 부적합 → Lambda 통합 [S21] |
| 코드 수준 모의·페이크 | 단위 테스트에서 SDK·외부 서비스 대체 | 코드 안의 객체. Moto(Python 라이브러리) 같은 프레임워크가 모의 객체를 생성 [S1] |

- AWS IATK(Integrated Application Test Kit): 비동기·이벤트 기반 앱의 클라우드 통합 테스트를 돕는 Python 라이브러리(2023년 공개 프리뷰 공지). 논리 ID+스택 이름으로 물리 ID 조회, EventBridge 출력 이벤트를 듣는 테스트 하니스(규칙이 이벤트를 SQS로 전달), 폴링+타임아웃으로 비동기 SLA 검증, X-Ray 트레이스 단언을 제공한다. 현재 상태는 확인 필요 [S20].

### 개발 엔드포인트 — API Gateway 스테이지·스테이지 변수·카나리 (Skill 3.2.3)

- 배포(deployment)는 API 구성의 스냅샷이고, 스테이지(stage)는 배포를 가리키는 이름 붙은 참조(dev·prod·beta·v2 등)다. API ID와 스테이지 이름이 호출 URL에 들어간다: `https://{restapi-id}.execute-api.{region}.amazonaws.com/{stageName}` [S25][S26].
- 라우트·메서드·통합·권한 부여자·리소스 정책 등 스테이지 설정 외의 API를 바꿀 때마다 기존·새 스테이지에 다시 배포해야 반영된다 [S25]. (스테이지 설정을 바꾼 뒤 재배포가 필요한지는 문서가 엇갈린다 — [S26]의 콘솔 절차는 재배포를 안내하지만 [S25]는 스테이지 설정 변경을 "API 업데이트"에서 제외한다. 확인 필요)
- 스테이지 설정: 캐싱, 스로틀링(스테이지 한도는 계정 한도 이하, 최선 노력), WAF 웹 ACL·클라이언트 인증서, CloudWatch Logs·상세 지표·액세스 로그, X-Ray 추적, 스테이지 변수, 카나리. 메서드별로 재정의할 수 있고 Data tracing은 프로덕션에 권장하지 않는다 [S26].
- 승격 예: `test` 스테이지로 검증한 뒤 `prod` 스테이지로 재배포하거나 스테이지 변수 값을 test에서 prod 쪽으로 바꿔 승격한다 [S25]. (환경 승격 자동화 상세 → Task 3.3)
- 스테이지 변수는 REST API 배포 스테이지에 붙는 키-값 구성 속성이며 환경 변수처럼 쓴다. 용도: ① 스테이지별 다른 백엔드 엔드포인트(프로덕션 `example.com`, 베타 `beta.example.com`)나 다른 Lambda 함수 이름 ② 매핑 템플릿으로 설정 값(예: DynamoDB 테이블 이름) 전달 [S27].
- 사용법: 변수를 정의하고 값을 준 뒤 통합 요청에서 `${stageVariables.<이름>}`으로 참조한다. Lambda는 `...:function:${stageVariables.<함수이름변수>}/invocations` 또는 `...:function:<함수이름>:${stageVariables.<별칭변수>}/invocations` 형태다 [S28]. 통합 유형 자체(HTTP 프록시 ↔ Lambda 프록시)는 스테이지 변수로 바꿀 수 없다 [S27].
- 패턴: 스테이지 변수 + Lambda 별칭으로 API와 함수를 느슨하게 결합한다. 배포할 때 스테이지 변수 값만 별칭 이름으로 바꾸면 그 스테이지가 별칭 뒤의 버전을 실행한다 [S33].
- 주의: 스테이지 변수로 Lambda를 지정하면 Lambda 리소스 기반 권한(`lambda:InvokeFunction`)을 직접 설정해야 하고, 같은 계정의 함수만 가능하다(교차 계정 불가). 스테이지 변수는 자격 증명 같은 민감 정보용이 아니다(민감 값은 Lambda 권한 부여자 출력으로 전달) [S27][S28].
- 한도(REST API): API당 스테이지 10(증설 가능), 스테이지당 스테이지 변수 100(증설 불가), 변수 키 64자, 값 512자 [S30]. 스테이지 이름은 영숫자·하이픈·밑줄만, 최대 128자 [S26].
- 카나리 릴리스: 같은 스테이지에서 전체 API 트래픽을 무작위로 프로덕션 릴리스와 카나리 릴리스로 나눈다. `canarySettings`에 배포 ID, 트래픽 비율(0.0~100.0), 카나리용 스테이지 변수(프로덕션 변수를 재정의), 스테이지 캐시 사용 여부를 둔다. 지표가 기준을 통과하면 카나리를 프로덕션으로 승격하고 카나리를 끈다. 카나리가 켜져 있는 동안 스테이지는 다른 비카나리 배포와 연결할 수 없고, 카나리 전용 로그 그룹(`.../{stage}/Canary`)이 따로 생긴다 [S29]. (배포 전략 전반 → Task 3.4)
- HTTP API: `$default` 스테이지는 URL 기본 경로(`https://{api_id}.execute-api.{region}.amazonaws.com/`)에서 제공되어 URL에 스테이지 이름이 없을 수 있다. 배포해야 변경이 반영되지만 자동 배포를 켜면 변경이 자동 릴리스된다 [S31][S36].
- SAM: `AWS::Serverless::Api`의 `StageName`(SAM에서는 필수, API Gateway에서는 선택)·`Variables`(스테이지 변수)·`CanarySetting`·`AlwaysDeploy`(변경이 없어도 항상 배포)·`TracingEnabled`. 암시적(implicit) API의 스테이지 이름은 `Prod`다 [S32].

### 기존 환경에 스택 업데이트 배포 (Skill 3.2.4)

**`sam deploy`가 하는 일** [S37][S39]
1. zip 패키지는 압축해 S3 버킷에 업로드(필요하면 버킷 생성), 컨테이너 이미지는 ECR에 업로드(필요하면 리포지토리 생성).
2. CloudFormation 변경 세트(change set)를 만들어 스택으로 배포한다(`--confirm-changeset`이면 변경 세트를 보여 주고 확인).
3. 배포된 템플릿의 함수 `CodeUri`를 새 위치로 갱신한다.

- SAM의 배포 메커니즘은 CloudFormation이며 `sam build` 산출물이 입력이다 [S39].
- 처음에는 `--guided`로 대화형 설정(스택 이름·Region·변경 확인·IAM 역할 생성 허용·롤백 비활성·설정 환경 이름)을 입력하면 `samconfig.toml`에 저장되고, 이후에는 `sam deploy`만으로 같은 값을 쓴다 [S37].
- `--stack-name`(필수): 기존 스택이면 업데이트하고 새 스택이면 생성한다 [S38].
- CloudFormation은 로컬 파일을 먼저 접근 가능한 서비스(예: S3)에 올려야 하므로, `sam deploy`·`sam package`는 템플릿이 참조하는 로컬 파일을 자동으로 업로드하고 템플릿의 파일 경로를 새 위치로 바꾼다 [S48].

| `sam deploy` 옵션 | 의미 |
|---|---|
| `--config-env <이름>`·`--config-file` | `samconfig`의 환경(기본 `default`)·파일 선택 → 같은 템플릿에 staging·prod 값을 분리(예: `sam deploy --config-env "prod"`) [S38][S41][S42] |
| `--parameter-overrides` | `ParameterKey=이름,ParameterValue=값` 쌍(공백으로 구분)으로 템플릿 Parameters 덮어쓰기 [S38] |
| `--capabilities` | IAM 리소스를 만들 때 `CAPABILITY_IAM`·`CAPABILITY_NAMED_IAM`(사용자 지정 이름이면 NAMED), 중첩 앱은 `CAPABILITY_AUTO_EXPAND`. 빠지면 `InsufficientCapabilities` 오류 [S38] |
| `--confirm-changeset` | 계산된 변경 세트를 적용하기 전에 확인 [S38] |
| `--no-execute-changeset` | 변경 세트를 만들고 적용하지 않은 채 종료(옵션 없이 같은 명령을 다시 실행하면 적용) [S38] |
| `--fail-on-empty-changeset` | 변경이 없으면 0이 아닌 종료 코드를 반환(기본 동작) [S38] |
| `--disable-rollback`·`--on-failure` | 기본은 오류 시 마지막 안정 상태로 롤백, `--disable-rollback`이면 오류 전에 만들거나 바꾼 리소스를 되돌리지 않음. `--on-failure`는 생성 실패 시 `ROLLBACK`·`DELETE`·`DO_NOTHING`이며 둘 중 하나만 지정 [S38] |
| `--resolve-s3`·`--s3-bucket` | 아티팩트 버킷 자동 생성/지정. 템플릿이 51,200바이트를 넘으면 둘 중 하나가 필요하고 동시에 지정하면 오류 [S38] |
| `--image-repository`·`--image-repositories`·`--resolve-image-repos` | Image 패키지 함수의 ECR 리포지토리 지정/자동 생성 [S38] |
| `--role-arn`·`--tags`·`--notification-arns` | 변경 세트 적용 시 CloudFormation이 맡는 IAM 역할, 스택 태그, SNS 알림 [S38] |
| `--express` | CloudFormation Express 모드(리소스 구성 적용 시점에 스택 작업을 완료, 최대 4배 단축, 기본 `--no-express`) — 신규 기능, 확인 필요 [S38] |

- 환경별 예시: `samconfig.toml`에 `[staging.global.parameters] stack_name = "myapp-staging"` 같은 환경 섹션을 두고 `sam deploy --config-env staging`으로 같은 템플릿을 기존 staging 스택에 업데이트한다(예시이며 형식은 [S41]·[S42]). 템플릿 Parameters·Mappings·Conditions 상세는 → Task 3.1.

**변경 세트와 스택 업데이트 동작** [S43][S44][S45][S47]
- 변경 세트는 스택에 제출할 변경(수정된 템플릿 또는 파라미터 값)이 실행 중인 리소스에 미칠 영향(추가·수정·삭제·교체, 속성 전후 비교)을 미리 보여 주며, 실행(execute)을 결정할 때만 스택을 바꾼다. 변경 세트가 업데이트 성공을 보장하지는 않는다(런타임 조건에 따른 실패 가능) [S43].
- 리소스 업데이트 동작 3종: 중단 없음(No interruption, 물리 ID 유지) / 일부 중단(Some interruption) / 교체(Replacement — 새 리소스를 만들고 참조를 옮긴 뒤 이전 리소스를 삭제, 새 물리 ID) [S45].
- 교체 예: RDS 인스턴스 이름을 바꾸면 새 DB를 만들고 이전 DB를 삭제하므로 백업이 없으면 데이터를 잃는다. 변경 세트로 교체 여부를 미리 확인한다(원리) [S44].
- `UpdateReplacePolicy`는 교체될 때 이전 리소스를 보존(Retain)하거나 스냅샷을 남기고, `DeletionPolicy`는 스택·리소스 정의가 삭제될 때 적용된다 — 적용 시점이 다르다 [S47].
- 업데이트가 실패하면 기본적으로 롤백된다. 롤백까지 실패하면 `UPDATE_ROLLBACK_FAILED`가 되며 이 스택은 업데이트할 수 없고, 오류를 고친 뒤 `ContinueUpdateRollback`으로 `UPDATE_ROLLBACK_COMPLETE`로 되돌린다 [S46].

**`sam sync`(SAM Accelerate)** [S40][S58]
- 개발 환경용이다. 로컬 변경을 감지(`--watch`)해 가장 빠른 방법으로 클라우드에 동기화한다. 서비스 API로 갱신할 수 있는 리소스(예: Lambda 코드)는 API로 바로 갱신해 CloudFormation 변경 세트 절차를 건너뛰고, 그렇지 않으면 CloudFormation 배포를 수행한다. 프로덕션은 `sam deploy`나 CI/CD를 권장하며, 실행 시 "개발 스택에만 사용" 확인을 묻는다.
- 옵션: `--code`(코드 변경만), `--resource-id`, `--no-watch`(1회 CloudFormation 배포), `--skip-deploy-sync`(템플릿 변경이 없으면 CloudFormation 배포 생략 — 단 마지막 배포 후 7일 이상이거나 코드 변경이 많으면 배포), `--watch-exclude` [S40].

### 이벤트 기반 애플리케이션 테스트 (Skill 3.2.5 🆕)

- 어려운 이유: 이벤트가 서비스 사이를 흐르고 일부 상호작용은 비동기여서 하위 구성 요소에 생기는 부수 효과를 따로 확인해야 한다. 큐·이벤트 버스·IAM을 로컬에서 완전히 복제할 수 없다 [S1].
- 로컬에서 JSON 페이로드를 핸들러에 직접 넣는 테스트는 "SQS가 배포 환경에서 실제로 함수를 호출하는지"를 검증하지 못한다. 흔한 구성 오류: SQS 가시성 제한 시간이 너무 낮아 한 번만 의도했는데 여러 번 호출됨, 실행 역할에 `sqs:ReceiveMessage`·`sqs:DeleteMessage`·`sqs:GetQueueAttributes` 누락, 테스트 이벤트가 SQS 메시지 크기 한도 초과 [S1].

| 이벤트 소스·대상 | 테스트 방법 | 핵심 사실 |
|---|---|---|
| 서비스별 이벤트 형식 | `sam local generate-event <서비스> <이벤트>`(예: `s3 put`·`s3 delete`·`apigateway http-api-proxy`)로 샘플 페이로드를 만들어 `sam local invoke -e` 또는 `sam remote invoke --event-file`에 사용 | 지원 서비스는 `sam local generate-event`, 서비스별 옵션은 `--help` [S13][S16][S17] |
| Lambda 직접 | 콘솔 테스트 이벤트, `aws lambda invoke`, `sam remote invoke` | `Event`(비동기) 호출은 상태 코드 202만 반환 → 로그·트레이스로 결과 확인 [S2][S5] |
| SQS → Lambda | `sam remote invoke <큐>`로 메시지 전송(메시지 ID·본문 MD5 반환). 부분 배치 응답 | 배치 처리 오류 시 기본은 성공한 메시지 포함 배치 전체가 다시 보임 → 이벤트 소스 매핑 `FunctionResponseTypes`에 `ReportBatchItemFailures`를 켜고 함수가 `batchItemFailures`를 반환. 예외를 던지면 배치 전체 실패 [S6][S55] |
| Kinesis | `sam remote invoke <스트림> --event ...`로 레코드 전송(샤드 ID·시퀀스 번호 반환) | [S6] |
| SNS | 토픽에 메시지를 게시해 구독자 동작 확인 | 구독에 필터 정책이 없으면 모든 메시지를 받고, 필터 정책 변경은 완전히 반영되기까지 최대 15분 [S56][S57] |
| EventBridge 패턴 | 규칙을 만들기 전에 Sandbox(또는 `aws events test-event-pattern`·`TestEventPattern` API)로 샘플 이벤트가 패턴에 맞는지 확인 | 결과 `true`면 일치. 규칙은 패턴의 모든 필드가 이벤트와 맞아야 동작하므로 적은 필드부터 시작 [S50][S51][S52] |
| EventBridge 아카이브·재생 | 원본 이벤트를 아카이브해 두었다가 새·수정 로직을 과거 이벤트로 검증(재생) | 아래 표 [S49] |
| Step Functions | `sam remote invoke`로 실행(완료까지 대기), TestState API로 단일 상태 검증(모의 포함) | 3.2.2 표 참조 [S6][S22] |

| EventBridge 아카이브·재생 항목 | 규칙 |
|---|---|
| 아카이브 | 아카이브마다 단일 원본 이벤트 버스(생성 후 변경 불가), 버스당 여러 아카이브, 이벤트 패턴으로 필터, 보존 기간은 일수로 지정(기본 무기한) [S49] |
| 재생 대상 | 원본 이벤트 버스로만 재생. 시간 범위를 지정하고 선택적으로 특정 규칙만 지정 [S49] |
| 동시 재생·기록 | 계정·Region당 활성 동시 재생 10개, 재생은 90일 후 삭제 [S49] |
| 순서 | 원래 순서와 다를 수 있음(이벤트 시각 기준 1분 간격으로 재생) [S49] |
| 지연 | 아카이브 도착 지연이 있어 10분 뒤에 재생하라고 권장 [S49] |
| 식별 | 재생된 이벤트에 메타데이터 `replay-name` 추가, 재생 이벤트가 아카이브에 다시 들어가지 않게 관리형 규칙이 걸러냄 [S49] |
| 재생해도 | 아카이브의 이벤트는 지워지지 않음(보존 기간 경과·아카이브 삭제 시에만 제거) [S49] |

- 비동기 호출(`Event`, S3·SNS·EventBridge 등)의 의미: Lambda가 이벤트를 큐에 넣고, 함수 오류 시 기본 최대 2회 더 재시도하며(0~2 설정 가능), 큐에는 최대 6시간 보관한다. 모든 시도가 실패하거나 너무 오래되면 폐기하므로 DLQ(SQS·SNS) 또는 실패 대상(destination)으로 보존한다. 대상은 성공·실패 호출 기록을 SQS·SNS·EventBridge·다른 함수로 보낼 수 있고 실패 처리에는 DLQ보다 대상이 권장된다 [S5][S53][S54].
- 추적: X-Ray `Active` 추적이면 SQS 같은 업스트림 생산자의 트레이스가 하위 Lambda 트레이스와 연결돼 종단 간 뷰를 준다 [S10].
- 비동기 시스템 테스트 요령: 합리적 타임아웃(SLA)을 정해 폴링으로 완료를 확인하고, 하위 구성 요소의 부수 효과(큐 메시지·DB 항목)를 조회해 단언한다. 테스트 전용 하니스(EventBridge 규칙이 출력 이벤트를 SQS로 전달)를 둘 수 있다 [S1][S20].

## 시험에서 묻는 방식

> 문제 저작자를 위한 제안이다. 시험이 반드시 이렇게 낸다는 단정이 아니다.

1. **배포 후 검증과 외부 종속성 모의 (Skill 3.2.1, 3.2.2)**
   - 상황: "방금 배포한 Lambda 함수에 샘플 이벤트를 보내 결과와 실행 로그를 바로 확인하고 싶다." / "프런트엔드 팀이 아직 구현되지 않은 주문 API를 먼저 호출해 통합해야 한다." / "서드파티 결제 API 장애 상황을 단위 테스트에서 재현하고 싶다." / "상태 머신의 분기·재시도 로직을 실제 서비스를 호출하지 않고 검증하고 싶다."
   - 정답 단서: 콘솔 테스트 이벤트·`aws lambda invoke --log-type Tail`·`sam remote invoke`(클라우드), 로그는 CloudWatch Logs·`sam logs`, 추적은 X-Ray / 백엔드 없이 고정 응답 → API Gateway MOCK 통합 / 서드파티·장애 재현 → 코드 수준 모의 / 상태 머신 단위 검증 → Step Functions TestState(모의). 로컬 테스트는 IAM·할당량·서비스 설정을 검증하지 못한다는 점이 함정 선지의 근거.

2. **개발 엔드포인트와 스테이지 (Skill 3.2.3)**
   - 상황: "한 REST API를 dev·prod 스테이지로 나눠 dev는 Lambda 별칭 `dev`, prod는 별칭 `prod`를 호출하게 하고 싶다." / "API Gateway 통합을 수정했는데 호출 결과가 그대로다." / "신규 API 버전을 트래픽 10%에만 먼저 노출하고 싶다."
   - 정답 단서: 스테이지 변수(`${stageVariables.…}`)+Lambda 별칭(Lambda 호출 권한은 직접 추가) / API 변경은 재배포해야 반영 / 같은 스테이지의 카나리 릴리스(`canarySettings`, 트래픽 비율, 카나리 전용 로그 그룹). 스테이지 변수에 자격 증명을 두는 선지는 오답.

3. **기존 환경에 스택 업데이트 (Skill 3.2.4)**
   - 상황: "같은 SAM 템플릿을 이미 있는 staging 스택에 배포하되 파라미터 값은 환경마다 다르게 하고 싶다." / "실제 적용 전에 어떤 리소스가 바뀌고 교체되는지 확인하고 싶다." / "개발 중 Lambda 코드 변경을 빠르게 클라우드에 반영하고 싶다." / "스택 업데이트가 실패한 뒤 롤백도 실패했다."
   - 정답 단서: `sam deploy --config-env staging`(또는 `--stack-name`·`--parameter-overrides`) / 변경 세트 미리 보기(`--no-execute-changeset`·`--confirm-changeset`) / `sam sync`(개발 환경 전용, 프로덕션은 `sam deploy`·CI/CD) / `UPDATE_ROLLBACK_FAILED` → 오류를 고치고 `ContinueUpdateRollback`. 교체(Replacement)가 있는 리소스는 데이터 손실 위험.

4. **이벤트 기반 앱 테스트 (Skill 3.2.5)**
   - 상황: "EventBridge 규칙을 만들기 전에 이벤트 패턴이 샘플 이벤트와 맞는지 확인하고 싶다." / "새로 배포한 처리 로직을 과거에 들어온 이벤트로 다시 검증하고 싶다." / "SQS 배치 중 한 메시지만 실패했는데 성공한 메시지까지 다시 처리된다." / "S3 업로드 이벤트를 받는 함수를 로컬에서 확인하고 싶다."
   - 정답 단서: EventBridge Sandbox·`test-event-pattern` / 아카이브에서 원본 이벤트 버스로 재생(replay) — 다른 버스로는 불가 / 이벤트 소스 매핑에 `ReportBatchItemFailures` / `sam local generate-event s3 put`으로 이벤트 생성 후 `sam local invoke -e`. 비동기 호출은 재시도(기본 2회)·DLQ·destination 단서와 함께 출제될 수 있다.

## 흔한 함정·혼동 짝

| A vs B | 혼동 이유 | 구분 기준 한 줄 | 출처 |
|---|---|---|---|
| `sam local invoke` vs `sam remote invoke` | 이름이 비슷하고 둘 다 함수를 호출 | local은 내 PC의 Docker 컨테이너에서 실행, remote는 클라우드에 배포된 리소스(Lambda·SQS·Kinesis·Step Functions)를 호출 | [S6][S13] |
| `sam deploy` vs `sam sync` | 둘 다 로컬 변경을 클라우드에 반영 | deploy는 CloudFormation 변경 세트(프로덕션·CI/CD), sync는 서비스 API로 빠르게 반영하는 개발 환경 전용 | [S38][S40][S58] |
| 모의(mock) vs 에뮬레이터 | 둘 다 로컬에서 서비스를 흉내 | 모의는 테스트 코드 안의 객체, 에뮬레이터(LocalStack 등)는 같은 기능을 노출하는 독립 앱 — 둘 다 IAM·할당량은 검증 못 함 | [S1] |
| API Gateway MOCK 통합 vs 코드 수준 모의 vs TestState 모의 | 모두 "모의"라 부름 | MOCK 통합은 배포된 API가 직접 응답, 코드 모의는 단위 테스트 객체, TestState 모의는 상태 머신 상태 단위 테스트 | [S21][S1][S22] |
| 배포(deployment) vs 스테이지(stage) | 둘 다 "API를 내보내는 단위"처럼 보임 | 배포는 스냅샷, 스테이지는 그 배포를 가리키는 이름 붙은 참조(URL에 스테이지 이름 포함) | [S25][S26] |
| 스테이지 변수 vs Lambda 환경 변수 | 둘 다 환경별 설정 값 | 스테이지 변수는 API Gateway 스테이지 구성(매핑 템플릿·통합 URI에서 `${stageVariables.x}`, 민감 정보 금지), 환경 변수는 함수 구성 | [S27][S28] |
| 카나리 릴리스 vs 별도 스테이지 | 둘 다 새 버전을 먼저 노출 | 카나리는 같은 스테이지 트래픽을 비율로 분할(승격 후 끔), 별도 스테이지는 URL이 다름 | [S29][S25] |
| `--no-execute-changeset` vs `--confirm-changeset` | 둘 다 변경 내용을 확인 | 전자는 변경 세트를 만들고 적용하지 않은 채 종료, 후자는 계산된 변경 세트를 보여 주고 적용 여부를 묻는다 | [S38] |
| `UpdateReplacePolicy` vs `DeletionPolicy` | 둘 다 리소스 보존 정책 | 전자는 업데이트로 교체될 때만, 후자는 스택·리소스 정의가 삭제될 때 적용 | [S47] |
| EventBridge Sandbox·`TestEventPattern` vs 아카이브·재생 | 둘 다 "이벤트 테스트" | 전자는 패턴이 샘플 이벤트와 맞는지 검증, 후자는 실제 과거 이벤트를 원본 이벤트 버스로 다시 보낸다 | [S50][S49] |
| 비동기 `Event`(202) vs 동기 `RequestResponse`(200) | 둘 다 함수 호출 | Event는 큐에 넣고 상태 코드만 반환하며 오류 시 기본 2회 재시도·최대 6시간 보관, 결과는 로그·DLQ·destination으로 확인 | [S5][S53] |
| SQS 부분 배치 응답 켜짐 vs 꺼짐 | 한 메시지만 실패해도 전체가 재처리됨 | 꺼져 있으면 성공 메시지 포함 배치 전체가 다시 보이고, `ReportBatchItemFailures`를 켜면 실패 메시지만 다시 보인다 | [S55] |

### Q1 — 배포된 함수 호출과 실행 로그
- 대응 Skill: 3.2.1 / 난이도: foundational
- 문제: 개발자가 배포된 Lambda 함수를 AWS CLI로 동기 호출하면서, 응답에 실행 로그의 마지막 부분을 함께 받아 디버깅하려 한다. 어떤 설정을 사용해야 하는가?
- 보기:
  - A. `InvocationType`을 `Event`로 지정한다.
  - B. `LogType`을 `Tail`로 지정한다.
  - C. `InvocationType`을 `DryRun`으로 지정한다.
  - D. `Qualifier`를 `$LATEST`로 지정한다.
- 정답: B
- 정답 근거: `LogType`을 `Tail`로 지정하면 동기 호출 응답에 실행 로그가 포함되며, `LogResult`는 base64로 인코딩된 마지막 4 KB다. 근거: https://docs.aws.amazon.com/lambda/latest/api/API_Invoke.html
- 오답 해설:
  - A: `Event`는 비동기 호출이라 상태 코드(202)만 돌려주며 `LogType`은 동기 호출에만 적용된다.
  - C: `DryRun`은 파라미터와 호출 권한만 검증하고(204) 함수를 실행하지 않는다.
  - D: `Qualifier`는 호출할 버전이나 별칭을 고르는 값이며 로그 반환과 무관하다.

### Q2 — 외부 종속성 모의(API Gateway MOCK 통합)
- 대응 Skill: 3.2.2 / 난이도: intermediate
- 문제: 프런트엔드 팀이 아직 구현되지 않은 주문 조회 API를 미리 호출해 UI를 통합해야 한다. 백엔드 코드를 작성하지 않고 API Gateway가 미리 정한 상태 코드와 JSON 본문을 직접 반환하게 하려면 어떻게 해야 하는가?
- 보기:
  - A. 메서드의 통합 유형을 MOCK으로 설정하고 통합 요청·통합 응답 매핑 템플릿으로 응답을 정의한다.
  - B. 메서드를 HTTP 프록시 통합으로 설정하고 존재하지 않는 URL을 지정한다.
  - C. 스테이지 변수에 응답 본문을 저장해 두고 매핑 템플릿에서 반환한다.
  - D. Lambda 권한 부여자가 응답 본문을 반환하도록 구성한다.
- 정답: A
- 정답 근거: API Gateway는 통합 백엔드 없이 API Gateway가 직접 응답을 생성하는 MOCK 통합을 지원한다. 통합 요청 매핑 템플릿이 `{"statusCode": 200}`처럼 상태 코드를 정하고 해당 통합 응답 매핑 템플릿이 본문을 만든다. 근거: https://docs.aws.amazon.com/apigateway/latest/developerguide/how-to-mock-integration.html
- 오답 해설:
  - B: HTTP 프록시 통합은 실제 백엔드 엔드포인트를 호출하므로 존재하지 않는 URL에서는 응답을 만들 수 없다.
  - C: 스테이지 변수는 값이 512자까지인 구성 속성이며 응답을 생성하는 통합 유형이 아니다.
  - D: Lambda 권한 부여자는 호출자 인증·인가를 위한 구성 요소이며 메서드 응답 본문을 만드는 수단이 아니다.

### Q3 — 스테이지 변수와 Lambda 별칭
- 대응 Skill: 3.2.3 / 난이도: intermediate
- 문제: 하나의 REST API를 dev와 prod 스테이지로 배포한다. dev 스테이지는 Lambda 함수의 별칭 `dev`를, prod 스테이지는 별칭 `prod`를 호출해야 하며 API의 통합 설정은 하나만 유지하려 한다. 가장 적절한 구성은?
- 보기:
  - A. 통합 URI에 `${stageVariables.lambdaAlias}`를 쓰고 각 스테이지에 `lambdaAlias`를 `dev`·`prod`로 정의하며, API Gateway가 함수를 호출할 권한을 Lambda에 직접 추가한다.
  - B. Lambda 함수 환경 변수에 스테이지 이름을 저장하고 API Gateway가 이를 읽어 별칭을 정하게 한다.
  - C. 스테이지마다 별도의 REST API를 만들고 통합을 각각 구성한다.
  - D. 사용 계획(usage plan)으로 스테이지별 별칭을 선택한다.
- 정답: A
- 정답 근거: 스테이지 변수는 Lambda 함수 이름이나 별칭 자리에 `${stageVariables.<이름>}`으로 쓸 수 있고, 배포할 때 변수 값만 바꿔 스테이지별 별칭을 가리킬 수 있다. 스테이지 변수로 Lambda를 지정하면 Lambda 권한을 직접 설정해야 한다. 근거: https://docs.aws.amazon.com/apigateway/latest/developerguide/stage-variables.html , https://docs.aws.amazon.com/apigateway/latest/developerguide/aws-api-gateway-stage-variables-reference.html , https://docs.aws.amazon.com/whitepapers/latest/serverless-multi-tier-architectures-api-gateway-lambda/iterate-rapidly-stay-agile.html
- 오답 해설:
  - B: 환경 변수는 Lambda 함수 구성이며 API Gateway의 통합 URI가 스테이지별로 참조하는 값은 스테이지 변수다.
  - C: 동작은 하겠지만 "통합 설정 하나로 스테이지를 구분"하라는 요구를 어기고, 스테이지·스테이지 변수라는 문서의 표준 방식을 쓰지 않는다.
  - D: 사용 계획은 이 요구(스테이지별 별칭 선택)를 해결하는 방법으로 문서에 나오지 않으며 통합 URI를 바꾸지 않는다.

### Q4 — 기존 스택 업데이트 전 변경 확인
- 대응 Skill: 3.2.4 / 난이도: intermediate
- 문제: 팀이 같은 SAM 템플릿을 이미 운영 중인 staging 스택에 업데이트하려 한다. 적용 전에 어떤 리소스가 추가·변경·교체되는지 검토하고, 검토 후 같은 설정으로 실제 배포하려 한다. 가장 적절한 방법은?
- 보기:
  - A. `sam sync --stack-name myapp-staging`을 실행한다.
  - B. `sam deploy --config-env staging --no-execute-changeset`으로 변경 세트를 확인한 뒤 같은 명령에서 옵션만 빼고 다시 실행한다.
  - C. `sam local start-api`로 변경을 시험한 뒤 스택을 삭제하고 새로 만든다.
  - D. `sam build --use-container`만 실행하면 스택이 업데이트된다.
- 정답: B
- 정답 근거: `--config-env`는 `samconfig`의 환경을 고르고, `--no-execute-changeset`은 CloudFormation 변경 세트를 만든 뒤 적용하지 않고 종료하며 옵션 없이 같은 명령을 실행하면 적용된다. 변경 세트는 교체 여부를 포함한 영향을 미리 보여 준다. 근거: https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/sam-cli-command-reference-sam-deploy.html , https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/using-cfn-updating-stacks-changesets.html
- 오답 해설:
  - A: `sam sync`는 개발 환경용이며 변경 세트 절차를 건너뛰어 사전 검토 요구에 맞지 않는다.
  - C: 로컬 테스트는 클라우드 스택을 바꾸지 않으며, 스택을 삭제하고 다시 만드는 것은 불필요하고 교체 리소스의 데이터를 잃을 수 있다.
  - D: `sam build`는 배포용 산출물을 준비하는 단계이고 스택 업데이트는 `sam deploy`가 수행한다.

### Q5 — EventBridge 아카이브 재생
- 대응 Skill: 3.2.5 / 난이도: intermediate
- 문제: EventBridge 이벤트 버스로 들어오는 주문 이벤트를 아카이브하고 있다. 새로 배포한 처리 로직이 과거 이벤트에서도 올바르게 동작하는지 검증하려 한다. 올바른 방법은?
- 보기:
  - A. 아카이브의 이벤트를 원하는 시간 범위에 대해 원본 이벤트 버스로 재생(replay)하고, 필요하면 특정 규칙만 대상으로 지정한다.
  - B. 아카이브의 이벤트를 다른 계정의 새 이벤트 버스로 재생한다.
  - C. `aws events test-event-pattern`으로 과거 이벤트를 모두 다시 전송한다.
  - D. EventBridge Sandbox에서 과거 이벤트를 선택해 처리 로직을 실행한다.
- 정답: A
- 정답 근거: 재생은 시간 범위와 선택적으로 특정 규칙을 지정해 수행하며, 아카이브 이벤트는 원본 이벤트 버스로만 재생할 수 있다. 근거: https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-archive.html
- 오답 해설:
  - B: 아카이브 이벤트는 원본 이벤트 버스로만 재생할 수 있다.
  - C: `test-event-pattern`은 이벤트가 패턴과 일치하는지 true/false를 돌려줄 뿐 이벤트를 전송하지 않는다.
  - D: Sandbox는 이벤트 패턴이 샘플 이벤트와 맞는지 확인하는 도구이며 처리 로직을 실행하거나 과거 이벤트를 재처리하지 않는다. 근거: https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-event-pattern-sandbox.html
