## 핵심 개념

### 용어 먼저 — 문서의 "Event Function" (Skill 1.2.2)
- 2026-10-17 현재 Lambda 개발자 가이드는 기존 Lambda 함수를 **Event Functions**라는 이름으로 부른다(콘솔 라벨도 Event function). 같은 문서에 새 컴퓨팅 형태인 Lambda Web Functions(HTTP 서버형)·Lambda MicroVMs(최대 8시간), 그리고 Durable functions·Lambda Managed Instances가 함께 나온다. API(`CreateFunction`·`Invoke`)·SDK·CLI·`AWS::Lambda::Function`·ARN은 계속 "function"을 쓰므로 코드·IAM·템플릿 변경은 없다. [S44][S5]
- 이 노트의 설명은 모두 Event Function(= 전통적인 Lambda 함수) 기준이다. 가이드 v2.1 Skill 문구는 "Lambda functions"이므로 문항·학습문서는 "Lambda 함수"로 쓰고 필요할 때만 "(문서상 Event Function)"을 병기하면 된다. 새 컴퓨팅 형태가 DVA-C02 범위인지는 불명이라 본문에서 다루지 않는다(`확인 필요` 4·5번). [S44]

### VPC 연결 Lambda의 구조와 필요한 권한 (Skill 1.2.1)
- 모든 Lambda 함수는 Lambda 서비스가 소유·관리하는(고객에게 보이지 않는) VPC 안에서 실행된다. 계정의 VPC에 연결해도 이 관리형 VPC에는 영향이 없다. [S1]
- 계정 VPC의 프라이빗 리소스(RDS·ElastiCache·EC2 등)에 닿으려면 **프라이빗 서브넷 + 보안 그룹**에 함수를 연결한다(콘솔 Enable VPC / CLI `--vpc-config SubnetIds=…,SecurityGroupIds=…` / SAM `VpcConfig`). 연결 해제는 빈 서브넷·보안 그룹 목록으로 `update-function-configuration`을 실행한다. [S1]
- 원리: Lambda는 보안 그룹:서브넷 조합마다 **Hyperplane ENI**(Lambda가 관리하는 공유 네트워크 인터페이스)를 만들고 여러 실행 환경이 이를 공유한다. ENI는 함수 생성·VPC 설정 변경 시점에 미리 만들어지므로 호출 때는 터널만 연결하면 되고(콜드 스타트마다 ENI를 만들던 예전 방식이 아님), 같은 조합을 쓰는 계정 내 다른 함수도 같은 ENI를 재사용한다. [S3][S1]

| 주체 | 필요한 것 | 메모 |
|---|---|---|
| 함수 실행 역할 | AWS 관리형 정책 `AWSLambdaVPCAccessExecutionRole`(또는 `ec2:CreateNetworkInterface`·`DescribeNetworkInterfaces`·`DescribeSubnets`·`DeleteNetworkInterface`·`AssignPrivateIpAddresses`·`UnassignPrivateIpAddresses`, Resource `*`) | ENI를 만들기 위한 권한이며 호출 자체에는 필요 없다. 콘솔에서 VPC 함수를 만들면 자동으로 붙는다 [S1] |
| 함수를 구성하는 사용자/역할 | `ec2:DescribeSecurityGroups`·`DescribeSubnets`·`DescribeVpcs`·`GetSecurityGroupsForVpc` | VPC 연결 시 Lambda가 네트워크 리소스를 검증한다 [S1] |
| 최소 권한 | 실행 역할에 `lambda:SourceFunctionArn` 조건을 건 EC2 API Deny 문 | 위 EC2 권한은 함수 코드에도 암묵적으로 부여되므로, 코드가 EC2 API를 못 부르게 막는 용도 [S1] |
| 조직 통제 | IAM 조건 키 `lambda:VpcIds`·`lambda:SubnetIds`·`lambda:SecurityGroupIds` | `CreateFunction`·`UpdateFunctionConfiguration`에 적용(예: VPC 연결 함수만 배포 허용) [S1] |

- ENI 수명주기: 새 함수는 ENI가 준비되는 동안 Pending(호출 불가, 수 분 소요 가능)이고 Active가 되면 호출할 수 있다. 14일간 호출이 없으면 미사용 ENI를 회수하고 함수가 Inactive가 되며 다음 호출은 실패한 뒤 다시 Pending을 거친다. VPC 설정을 제거하면 ENI 삭제에 최대 20분이 걸리고, 실행 역할을 먼저 지우면 Lambda가 ENI를 지우지 못한다. ENI 하나는 최대 65,000개 연결/포트를 지원하며 넘으면 Lambda가 ENI를 자동으로 늘린다. [S1]
- 제약: dedicated tenancy VPC에는 직접 연결할 수 없다(기본 tenancy VPC와 피어링). 다른 계정 VPC의 리소스는 VPC 피어링으로 접근한다. [S1][S4]
- VPC 관련 호출 오류는 `ENILimitReachedException`(ENI 한도)·`ENINotReadyException`(ENI 준비 전)·`EC2AccessDeniedException`(권한 부족) 등 HTTP 502로 나타난다. [S21]

### VPC 연결 후 인터넷·AWS 서비스로 나가는 경로 (Skill 1.2.1)
- 원리: VPC에 연결하지 않은 함수는 인터넷이 열려 있는 Lambda 관리형 VPC에서 나가므로 인터넷에 닿지만, VPC에 연결하면 그 VPC 안의 리소스에만 닿는다. 그래서 외부로 나가려면 VPC 쪽에 경로(NAT·엔드포인트)를 따로 만들어야 한다. [S1][S2]

| 가려는 곳 | 필요한 구성 | 함정·메모 |
|---|---|---|
| 같은 VPC의 RDS·ElastiCache 등 | 프라이빗 서브넷 연결 + 보안 그룹 규칙(예: 함수와 DB가 같은 SG면 그 SG를 인바운드 source·아웃바운드 destination으로) | [S1][S63] |
| 퍼블릭 인터넷의 외부 API | **프라이빗** 서브넷에 연결 + 퍼블릭 서브넷의 NAT 게이트웨이 + 프라이빗 서브넷 라우팅 테이블의 `0.0.0.0/0 → NAT` | 퍼블릭 서브넷에 연결해도 인터넷·퍼블릭 IP가 생기지 않는다. 경로가 없으면 호출이 "Task timed out"으로 끝난다 [S1][S2] |
| AWS 서비스(S3·DynamoDB 등) | VPC 엔드포인트 — 게이트웨이 엔드포인트는 추가 요금이 없다(S3·DynamoDB). DynamoDB는 IGW·NAT 없이 VPC에서 접근 가능 | DynamoDB 게이트웨이 엔드포인트는 온프레미스·다른 리전 피어링·Transit Gateway 경유 접근이 안 돼 그 경우엔 인터페이스 엔드포인트(추가 요금) [S2][S60][S3] |
| IPv6 | 이중 스택 서브넷만 선택 + `Ipv6AllowedForDualStack=true`, IPv6 인터넷은 egress-only 인터넷 게이트웨이 | IPv6 전용 서브넷, VPC 미연결 함수는 IPv6 아웃바운드 미지원 [S1][S2] |
| EFS 파일 시스템 | VPC 연결 필수, 같은 VPC의 접근 지점, 마운트 경로는 `/mnt/`로 시작, NFS(2049) 허용 | [S58] |
| DB 연결 폭주 | RDS Proxy(연결 풀링)가 짧은 연결을 반복하는 Lambda에 적합 | [S59] |

### 환경 변수와 비밀 값 (Skill 1.2.2)
- 환경 변수는 코드를 바꾸지 않고 동작(예: 로그 레벨, 대상 버킷 이름)을 조정하는 문자열 쌍으로 함수의 **버전별 설정**에 저장된다. 미게시 버전($LATEST)에서 정의하고 **버전을 게시하면 그 버전에 잠긴다.** [S9]
- 값은 평가·확장되지 않는 리터럴 문자열이다(치환은 코드에서). 키는 영문자로 시작하고 2자 이상, 영문·숫자·`_`만, Lambda 예약 키는 불가, 전체 합계 4 KB 이하. [S9]
- CLI `update-function-configuration --environment`는 `Variables` 전체를 **교체**하므로 기존 값을 모두 함께 보내야 한다. [S9]
- 런타임이 설정하는 예약 키 예: `_HANDLER`·`AWS_REGION`·`AWS_LAMBDA_FUNCTION_NAME`·`AWS_LAMBDA_FUNCTION_MEMORY_SIZE`·`AWS_LAMBDA_FUNCTION_VERSION`·`AWS_LAMBDA_INITIALIZATION_TYPE`(on-demand·provisioned-concurrency·snap-start·lambda-managed-instances)·`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`AWS_SESSION_TOKEN`(실행 역할 자격 증명)·`LAMBDA_TASK_ROOT`. 예약 키는 함수 설정으로 바꿀 수 없다. [S9]
- 저장 시 암호화되며 다른 KMS 키(`KMSKeyARN`)를 지정할 수 있다. 그래도 DB 자격 증명·API 키 같은 민감 정보는 환경 변수 대신 **Secrets Manager**를 쓰라고 권장한다. Parameters and Secrets Lambda Extension은 기본으로 비밀을 300초 캐시한다. [S9][S57]
- 운영 파라미터(예: 쓰기 대상 버킷 이름)는 하드코딩 대신 환경 변수로 넘기는 것이 모범 사례다. [S50]

### 런타임·핸들러 (Skill 1.2.2)
- 런타임은 언어별 실행 환경이며 주 언어 버전마다 식별자(`nodejs24.x`·`python3.14` 등)가 따로 있다. Lambda가 주 버전 간 호환성을 보장하지 않으므로 버전 상향은 고객이 식별자를 바꾸는 작업이다. .zip은 함수 생성 때 런타임을 고르고 설정 업데이트로 바꾸며, 컨테이너 이미지는 이미지를 새로 만들어야 한다. [S6]
- 모든 지원 런타임이 x86_64·arm64를 지원한다. Lambda는 LTS 단계에 이른 언어 버전만 관리형 런타임으로 제공하고, 지원 종료는 단계적이다(새 함수 생성 차단 → 이후 기존 함수 업데이트 차단). 종료 후에도 **호출은 계속 동작**한다. [S6][S68]
- 지원 런타임 스냅샷(2026-10-17 조회, 모두 [S6]):

| 언어 | 현재 지원 식별자(OS) | 지원 종료 일정·메모 |
|---|---|---|
| Node.js | nodejs24.x, nodejs22.x (AL2023) | 22는 2027-04-30, 24는 2028-04-30 예정. nodejs20.x(2026-04-30)·nodejs18.x(2025-09-01)는 이미 종료 |
| Python | python3.14·3.13·3.12 (AL2023), python3.11·3.10 (AL2) | 3.10은 2026-10-31, 3.11은 2027-06-30 예정. 3.9(2025-12-15)·3.8은 이미 종료 |
| Java | java25·java21, java17/11/8의 `.al2023` 변종(AL2023), java17·java11·java8.al2(AL2) | AL2 계열 2027-06-30, AL2023 계열 2029-06-30 예정 |
| .NET | dotnet10, dotnet8 (dotnet9은 컨테이너 전용) | dotnet8·dotnet9은 2026-11-10 예정. dotnet6은 종료 |
| Ruby | ruby4.0·ruby3.4·ruby3.3 | ruby3.2(2026-03-31)는 종료 |
| OS 전용(Go·Rust 등) | provided.al2023 | provided.al2는 2026-07-31 종료. Amazon Linux 2 자체 EOL은 2026-06-30 |
| 미리보기 | nodejs26.x, python3.15 | SLA·기술 지원 대상이 아니며 프로덕션 사용 금지, GA 목표는 2026-11(예정) |

- SDK: Node.js·Python·Ruby 런타임에는 AWS SDK가 포함돼 있지만, 호환성과 의존성 통제를 위해 코드가 쓰는 SDK 모듈을 배포 패키지나 계층에 **직접 포함**하라고 권장한다(콘솔 편집기·CloudFormation 인라인 코드처럼 패키지를 못 넣을 때만 런타임 포함 SDK 사용). [S6]
- 핸들러: 함수 설정의 `handler` 값이 진입점을 알려 준다(예: `function.handler` = 파일 이름.메서드 이름). 핸들러 밖의 정적 코드는 실행 환경(인스턴스)당 한 번 실행되고, 한 인스턴스는 한 번에 이벤트 하나만 처리한다 — 동시에 처리 중인 인스턴스 수가 곧 함수의 동시성이다. [S64]

### 계층(Layers)·확장(Extensions) (Skill 1.2.2)
- 계층은 보충 코드·데이터를 담은 .zip이다(의존성 라이브러리·커스텀 런타임·설정 파일). 용도는 배포 패키지 축소, 로직과 의존성 분리, 여러 함수 간 공유, 콘솔 코드 편집기 사용, 내장 SDK 버전 고정이다. [S11]
- 동작·제약: 함수당 최대 5개, **.zip 배포 함수에서만** 사용(컨테이너 이미지는 이미지 안에 포함), 내용은 `/opt`에 추출, 계층 버전은 변경 불가능한 스냅샷이라 ARN에 버전 번호까지 지정해 추가한다. 계층도 압축 해제 합계 250 MB 한도에 포함된다. Go·Rust는 초기화 중 별도 어셈블리 로드가 늘어 콜드 스타트가 길어질 수 있어 계층을 권장하지 않는다. [S11][S5]
- 확장은 **외부**(별도 프로세스, 함수 호출이 끝난 뒤에도 계속 실행, 다른 언어로 작성 가능)와 **내부**(런타임 프로세스의 일부, wrapper script·`JAVA_TOOL_OPTIONS`로 접근)로 나뉜다. 모든 런타임이 지원하며, 계층으로 `/opt/extensions/`에 두면 Init 단계에서 병렬로 시작한다. [S12]
- 영향: 확장은 함수와 CPU·메모리·스토리지를 공유해 실행 시간이 늘 수 있고, 확장 초기화가 끝나야 함수가 호출된다. 확장이 쓴 실행 시간은 1 ms 단위로 과금되지만 자체 확장 설치 비용은 없다. `PostRuntimeExtensionsDuration` 지표로 호출 후 확장 소요 시간을 잰다. [S12]
- Shutdown 단계 한도는 확장 없음 0 ms·내부 확장 500 ms·외부 확장 2,000 ms이며 초과하면 SIGKILL이다. [S13]

### 동시성 — 정의·예약·프로비저닝 (Skill 1.2.2·1.2.6)
- 정의: 동시성은 동시에 처리 중인 요청 수이고 요청마다 별도 실행 환경이 필요하다. 계정 기본 한도는 리전당 1,000이며, 필요량 ≈ 초당 요청 수 × 평균 실행 시간(초)(예: 5,000 rps × 0.2초 = 1,000). 상세 정의·메모리 최적화 관점은 Task 4.3. [S14]
- 원리: 이미 초기화된 실행 환경이 비어 있으면 재사용하고, 없으면 새로 만든다. 그래서 재사용 가능한 환경이 있으면 Init 없이 빨리 끝난다. [S14]

| 구분 | 예약 동시성 | 프로비저닝된 동시성 | SQS ESM 최대 동시성 |
|---|---|---|---|
| 목적 | 함수 전용 용량 보장 + 상한(하류 DB 보호) | 미리 초기화된 환경으로 콜드 스타트 제거(두 자릿수 ms 응답) | 큐 하나가 함수·계정 동시성을 독점하는 것 방지 |
| 비용 | 무료 | 추가 요금 | 무료 |
| 적용 대상 | 함수 | 버전·별칭(**$LATEST 불가**) | 이벤트 소스 매핑(2–1,000) |
| 제약 | 미예약 풀 − 100까지, 0이면 호출 차단 | 예약 동시성 이하, 이벤트 소스가 해당 별칭·버전을 가리켜야 함 | 함수 예약 동시성보다 크게 두면 스로틀 가능, 프로비저닝 모드와 동시 사용 불가 |
| 출처 | [S15] | [S16] | [S27] |

- 예약 동시성은 하한이자 상한이다(해당 용량을 다른 함수가 못 쓰고, 그 이상 확장되지도 않는다). 계정 한도 1,000이면 한 함수에 1,000 전부를 예약할 수 없다(100은 예약 없는 함수용으로 남김). [S15]
- 프로비저닝된 동시성 초과분은 on-demand 환경이 처리하고, 필요량에 10% 버퍼를 권장하며, Application Auto Scaling(예약 스케일링·목표 추적)으로 자동 조정할 수 있다. 초기화 코드는 핸들러 밖에 두면 할당 시점에 실행된다. [S16][S50]
- 함수당 스케일링 속도는 10초마다 실행 환경 1,000개이고, 동기 호출 요청 한도는 동시성의 10배(초당)다. [S5]
- 재귀 호출 등으로 호출이 폭주하면 예약 동시성을 0으로 두어 즉시 차단하고 코드를 고친다. [S50]

### 트리거와 Destinations 연결 위치 (Skill 1.2.2·1.2.5)
- **트리거(push)**: S3·SNS·API Gateway처럼 서비스가 Lambda를 직접 호출한다. 트리거 설정은 이벤트를 만드는 서비스가 저장·관리하고, 콘솔에서 만들면 함수의 **리소스 기반 정책**에 호출 권한이 자동 추가된다. [S23][S40]
- **이벤트 소스 매핑(ESM, poll)**: Lambda가 큐·스트림을 폴링해 배치로 함수를 호출하는 Lambda 리소스다(SQS·Kinesis·DynamoDB Streams·MSK/Kafka·MQ·DocumentDB). 소스를 읽는 권한은 함수 **실행 역할**에서 나온다(예: SQS는 `ReceiveMessage`·`DeleteMessage`·`GetQueueAttributes`). [S23][S62]
- 함수 하나에 트리거를 여러 개 둘 수 있고, 한 호출의 이벤트에는 한 트리거의 데이터만 들어간다. [S40]
- Destinations는 콘솔 Add destination에서 Source를 "Asynchronous invocation" 또는 "Event source mapping invocation"으로 고르고(CLI는 `update-function-event-invoke-config`), DLQ는 `update-function-configuration --dead-letter-config`로 설정한다. 상세 비교는 아래 소주제. [S19][S33]
- 함수 URL: 전용 HTTPS 엔드포인트(`https://<url-id>.lambda-url.<region>.on.aws`), 인증 `AWS_IAM`/`NONE`, CORS 설정 가능, 별칭 또는 $LATEST에만 붙일 수 있고 IPv4·IPv6 듀얼스택이지만 PrivateLink는 지원하지 않는다. [S45]

### 호출 유형별 이벤트 수명주기와 오류 처리 (Skill 1.2.3)
| 호출 유형 | 대표 호출자 | 오류 시 재시도 | 실패 이벤트 보존 | 메모 |
|---|---|---|---|---|
| 동기(`RequestResponse`) | API Gateway·ALB·Cognito·Firehose·SDK/CLI `Invoke` | Lambda는 자동 재시도하지 않는다. 직접 호출이면 호출자가, 서비스 경유면 그 서비스가 재시도 여부를 정한다(API Gateway는 오류 응답을 요청자에게 그대로 전달, S3 Batch Operations는 `TemporaryFailure` 응답이면 재시도) | 호출자 책임 | 코드가 일부만 실행됐을 수 있어 재시도 시 멱등성 필요 [S20][S40] |
| 비동기(`Event`) | S3·SNS·EventBridge·CloudWatch Logs·CLI `--invocation-type Event` | 함수 오류(코드·런타임 오류, 타임아웃)는 기본 2회 추가 시도(1분, 2분 대기). 스로틀(429)·시스템 오류(5xx)는 이벤트를 큐로 되돌려 기본 최대 6시간, 간격은 1초부터 최대 5분까지 지수 증가 | 재시도 소진·연령 초과 시 폐기 → **DLQ** 또는 **Destinations** | 재시도 0–2회, 최대 이벤트 연령 60–21,600초로 조정. 큐가 eventually consistent라 중복 전달 가능 [S18][S22] |
| ESM — 큐(SQS) | SQS | 배치 오류 시 가시성 제한시간이 지나면 메시지가 다시 보인다(기본은 배치 전체). 재시도 간격·실패 대상은 큐의 가시성 제한시간·redrive 정책으로 정한다 | 큐의 DLQ | 부분 배치 응답으로 실패한 메시지만 되돌릴 수 있다 [S20][S24][S26] |
| ESM — 스트림 | Kinesis·DynamoDB Streams | 배치 전체를 재시도하며 오류가 해결되거나 레코드가 만료될 때까지 그 샤드 처리가 멈춘다(순서 보장). 배치가 함수에 닿지 못한 스로틀·서비스 오류는 재시도 횟수에 세지 않는다 | ESM의 on-failure destination | `IteratorAge`로 막힌 샤드를 감지 [S20][S23] |

- 응답 코드: `Invoke`의 StatusCode는 `RequestResponse` 200·`Event` 202·`DryRun` 204이며 **함수 오류를 반영하지 않는다**(함수 오류는 `X-Amz-Function-Error` 헤더+응답 본문, 상태 코드 오류는 권한·할당량처럼 실행 자체를 막는 문제 — 예: `TooManyRequestsException`). [S21]
- 오류 범주: 함수 오류(코드가 반환한 오류와 타임아웃 같은 런타임 오류)와 호출 오류(스로틀 429·시스템 5xx)는 비동기 재시도 규칙이 다르다. [S18]
- 원리(비동기): Lambda가 이벤트를 내부 큐에 넣고 곧바로 성공(202)을 돌려준 뒤 별도 프로세스가 큐에서 읽어 호출한다. 호출자는 결과를 기다리지 않고, 큐가 eventually consistent라 오류가 없어도 같은 이벤트를 여러 번 받을 수 있다. [S17][S18]
- 원리(스트림): 샤드 안에서 레코드를 순서대로 처리하므로 오류가 나면 뒤 레코드로 못 넘어가고 같은 배치를 다시 시도한다 → 샤드가 막힌다. 샤드를 늘리면 영향 범위가 줄 뿐 막힌 샤드는 풀리지 않는다. [S29][S20]
- 코드에서의 처리: 중복 이벤트는 오류 없이 정상 종료해야 한다(오류로 끝나면 호출 서비스가 추가 재시도할 수 있다). SQS·스트림 배치는 코드가 모든 예외를 잡아 `batchItemFailures`로 실패 항목을 보고한다. 남은 실행 시간은 컨텍스트 객체(예: Python `context.get_remaining_time_in_millis`)로 얻어 멱등성 레코드의 만료 시각 계산에 쓴다. [S55][S26]

### Destinations vs DLQ (Skill 1.2.3)
| 비교 | DLQ(dead-letter queue) | Destinations(비동기 호출) | ESM 실패 대상(스트림) |
|---|---|---|---|
| 적용 대상 | 비동기 호출 | 비동기 호출 | 이벤트 소스 매핑 |
| 대상 종류 | SQS **표준** 큐·SNS **표준** 토픽만(FIFO 불가) | SQS(표준)·SNS(표준)·Lambda 함수·EventBridge 버스·S3 버킷(**실패 전용**) | SNS·SQS·S3·Kafka 토픽 |
| 조건 | 실패(재시도 소진·연령 초과)만 | on-success / on-failure 각각 지정 | on-failure만 |
| 전달 내용 | 이벤트 본문만 + 속성(RequestID·ErrorCode·ErrorMessage 첫 1 KB) | 요청·응답 세부가 든 JSON 호출 레코드(`condition`·`approximateInvokeCount`·`responsePayload` 등) | 실패 호출의 메타데이터(S3는 전체 호출 레코드 포함) |
| 설정 단위 | 함수 레벨만(버전은 $LATEST 설정을 따름) | 함수·버전·별칭 | ESM 단위 |
| 실행 역할 권한 | `sqs:SendMessage` / `sns:Publish` | `sqs:SendMessage`·`sns:Publish`·`lambda:InvokeFunction`·`events:PutEvents`·`s3:PutObject`+`s3:ListBucket`(KMS 암호화 버킷은 `kms:GenerateDataKey`) | SQS·SNS·S3 동일, Kafka는 `kafka-cluster:WriteData` |
| 전달 실패 지표 | `DeadLetterErrors`(전달 못 하면 이벤트 삭제) | `DestinationDeliveryFailures` | — |
| 출처 | [S19] | [S19][S22] | [S33] |

- 예약 동시성을 0으로 두면 비동기 이벤트는 재시도 없이 곧바로 DLQ·on-failure 대상으로 간다(나중에 거기서 꺼내 처리). [S19]
- SNS 대상은 메시지 최대 256 KB라 비동기 페이로드가 1 MB에 가까우면 호출 레코드가 한도를 넘는다 → 큰 페이로드는 SQS·S3 대상을 쓴다. [S19]
- SQS를 **이벤트 소스**로 쓰면 DLQ는 함수가 아니라 **큐**에 설정한다. DLQ에 쌓인 이벤트는 그 큐를 이벤트 소스로 삼아 재처리하거나 수동으로 꺼낸다. [S19]
- S3 대상 버킷을 삭제하고 설정을 남겨 두면 다른 계정이 같은 이름으로 버킷을 만들어 실패 기록을 받을 위험이 있다 → `s3:ResourceAccount` 조건으로 같은 계정 버킷만 허용. [S19]

- ESM은 함수를 **동기**로 호출하며, 배치 윈도우 도달·배치 크기 도달·페이로드 6 MB 도달 중 먼저 만족하는 조건에서 호출한다(6 MB는 변경 불가). SQS는 기본 최대 10건씩 가져가며, 저트래픽에서 배치 윈도우를 쓰면 윈도우를 20초보다 짧게 잡아도 최대 20초까지 기다릴 수 있다. [S23][S24]
- SQS 표준 큐 스케일링: 처음 5개 배치(동시 호출 5)로 시작해 분당 최대 300 동시 호출씩 늘리며 ESM 하나가 동시에 처리할 수 있는 호출은 최대 1,250이다. FIFO는 메시지 그룹 순서를 지키고, 동시 호출은 메시지 그룹 ID 수와 최대 동시성 중 작은 값으로 제한된다. [S27]
- **부분 배치 응답(SQS)**: ESM에 `ReportBatchItemFailures`를 켜고 함수가 `{"batchItemFailures":[{"itemIdentifier":"<messageId>"}]}`를 반환하면 그 메시지만 큐에 다시 보인다. 함수가 예외를 던지면 배치 **전체**가 실패로 간주된다. FIFO는 첫 실패 이후 처리를 멈추고 실패·미처리 메시지를 모두 반환해야 순서가 유지된다. 켜 두면 실패가 있어도 폴링 속도를 줄이지 않는다. [S26]
- **부분 배치 응답(스트림)**: `itemIdentifier`는 레코드의 SequenceNumber이고 여러 개를 반환하면 가장 낮은 sequence number가 체크포인트가 된다(그 지점부터 재시도). 설정을 켜지 않으면 응답을 무시한다. `BisectBatchOnFunctionError`를 켜면 배치를 이등분해 재시도하며, 둘 다 켜면 반환된 sequence number 지점에서 이등분한다. [S31]
- 스트림 ESM 오류는 두 갈래다. 호출 전(스로틀 등으로 함수를 못 부름)에는 레코드가 만료되거나 `MaximumRecordAgeInSeconds`를 넘을 때까지 재시도하고, 호출 중(함수 오류)에는 만료·최대 연령·`MaximumRetryAttempts` 중 먼저 오는 조건까지 재시도한다. 기본 설정이면 문제 레코드가 해당 샤드를 **최대 1주일**까지 막을 수 있어 재시도 횟수와 최대 레코드 연령을 설정하라고 권장하며, 배치 이등분(`BisectBatchOnFunctionError`)은 재시도 횟수를 소모하지 않는다. [S33]
- SQS 구성 팁: 큐 가시성 제한시간을 함수 타임아웃의 **6배 이상**으로(함수 타임아웃은 큐 가시성 제한시간 이하여야 하며 Lambda가 검증), redrive `maxReceiveCount`는 5 이상으로 둔다. DLQ는 소스 큐에 붙인다. [S28]
- 필터링: ESM당 기본 5개 필터를 OR로 결합(요청하면 10개), EventBridge 패턴 문법을 쓴다. 필터에서 걸러진 SQS 메시지는 큐에서 자동 삭제되고 Kinesis·DynamoDB는 iterator가 그냥 넘어간다. [S36]
- Powertools for AWS Lambda의 Batch Processor 유틸리티(Python·Java·TypeScript·.NET)가 부분 배치 응답 로직을 대신 처리한다. [S26]

### 멱등성과 중복 처리 (Skill 1.2.3)
- 왜 필요한가: 비동기 큐는 eventually consistent라 오류가 없어도 같은 이벤트를 다시 받을 수 있고, ESM은 각 이벤트를 **최소 한 번** 처리하므로 중복 처리가 일어날 수 있다. 동기 직접 호출도 재시도하면 코드가 일부/전체 실행됐을 수 있다. [S18][S23][S20]
- 패턴: 이벤트의 고유 속성(거래·구매 ID 등)을 키로 DynamoDB에 **조건부 쓰기**를 한다 → 상태 `IN_PROGRESS`와 만료 시각(현재 시각 + 남은 실행 시간)을 기록 → `ConditionalCheckFailedException`이면 다른 호출이 처리 중이거나 이미 끝난 것 → 처리 후 `COMPLETE`로 갱신, TTL 속성으로 만료. [S55]
- 중복 이벤트는 오류 없이 종료한다(오류로 끝나면 호출 서비스가 추가 재시도). 멱등성 저장소 호출 시간을 고려해 타임아웃을 3초 기본값보다 넉넉히 잡는다. [S55]
- Powertools for AWS Lambda의 idempotency 유틸리티(Python·TypeScript·Java·.NET)가 이 패턴을 제공한다. [S50][S55]

- 콜드 스타트: 새 실행 환경을 준비할 때 코드 다운로드·환경 시작·핸들러 밖 초기화 코드 실행이 일어나며, 보통 호출의 1% 미만에서 발생하고 100 ms 미만~1초 이상이다. 가장 큰 지연 요인은 초기화 코드(패키지·계층·의존성 크기, 초기화 작업량, 라이브러리·외부 연결 속도)다. [S13]

| Kinesis Data Streams → Lambda | 표준 이터레이터(샤드당 기본 초당 1회 폴링, 샤드 읽기 처리량 공유) 또는 enhanced fan-out(전용 연결·HTTP/2 푸시, 지연↓) | 샤드당 한 배치씩 순서대로 처리. `ParallelizationFactor` 1–10으로 샤드당 동시 배치를 늘려도 partition key 단위 순서 유지. 샤드를 늘리면 동시 호출·처리량 증가. 배치 윈도우는 최대 5분 | [S29] |
| 집계(tumbling window) | `TumblingWindowInSeconds`(0–900)로 고정 시간 창 집계 | 함수 응답에 `state` 필수(없으면 실패), 상태는 샤드당 최대 1 MB(초과 시 창이 일찍 종료), `isFinalInvokeForWindow`로 마지막 호출 구분, 리샤딩 미지원 | [S32][S30] |
| DynamoDB Streams → Lambda | 변경 이벤트(INSERT·MODIFY·REMOVE)를 ESM으로 처리 | 샤드를 초당 4회 폴링, 스트림 보존 24시간, 항목 단위 순서 보장, 샤드당 동시 읽기 함수는 2개 이하(전역 테이블은 1개 권장). `LATEST`는 생성·갱신 중 이벤트를 놓칠 수 있어 누락 방지엔 `TRIM_HORIZON` | [S34][S35] |
| SQS → Lambda | 큐를 버퍼로 한 배치 소비 | 표준 큐는 순서 비보장, FIFO는 메시지 그룹 내 순서. 배치 윈도우 최대 5분 | [S24][S27] |
| Firehose → Lambda 변환 | Firehose가 버퍼링한 배치를 Lambda를 **동기** 호출해 변환한 뒤 목적지로 전달 | 버퍼 크기 힌트 0.2–3 MB(기본 1 MB)·간격 0–900초(기본 60초), 요청·응답 6 MB 이하, 함수는 최대 5분. 반환은 `recordId`(입력과 동일)·`result`(`Ok`/`Dropped`/`ProcessingFailed`)·`data`(base64). 호출 실패 시 기본 3회 재시도 후 배치 건너뜀, 실패 레코드는 S3 `processing-failed` 폴더 | [S52][S53][S54] |
| S3 객체 이벤트 → Lambda | 객체 생성·삭제 알림으로 비동기 호출(파일 단위 변환) | 같은 버킷 쓰기 루프 주의, 비동기 재시도·DLQ 규칙 적용 | [S43] |

- 이벤트 필터링으로 필요한 레코드만 함수에 보내 호출 수·비용을 줄인다(필터는 배치를 채우기 전에 적용). [S36]
- 스트림에서 문제 레코드(poison pill)가 샤드를 막으면: `BisectBatchOnFunctionError` + `MaximumRetryAttempts`·`MaximumRecordAgeInSeconds` 제한 + 실패 대상(SQS·SNS·S3) 지정, 부분 배치 응답으로 처리된 지점까지 체크포인트를 옮긴다. 확장은 다음 배치를 기다리지 않아 동시성이 순간적으로 샤드 수를 넘을 수 있다. [S31][S33][S29]
- Kinesis·DynamoDB 레코드는 **최소 한 번** 전달되므로 위 멱등성 패턴을 함께 쓴다. [S29][S34]

## 시험에서 묻는 방식
> 문제 저작자를 위한 제안이며 시험이 반드시 이렇게 낸다는 뜻이 아니다.

**패턴 A — VPC 안 함수의 네트워크 경로 (Skill 1.2.1)**
- 문제 상황: 프라이빗 서브넷에 연결한 함수가 같은 VPC의 RDS에는 붙지만 외부 SaaS API(또는 S3)를 부르면 타임아웃이 난다. VPC에는 인터넷 게이트웨이가 있다.
- 정답 단서: 타임아웃 + "퍼블릭 서브넷에 연결해 보자"는 오답 유도 → **프라이빗 서브넷 + 퍼블릭 서브넷의 NAT 게이트웨이 + 라우트**. AWS 서비스(S3·DynamoDB)만 필요하고 비용을 줄이려면 **게이트웨이 VPC 엔드포인트**. ENI 권한 오류 → `AWSLambdaVPCAccessExecutionRole`. 연결 수 고갈 → RDS Proxy·예약 동시성. [S1][S2][S60][S59]

**패턴 B — 비동기 호출의 실패 이벤트 처리 (Skill 1.2.3·1.2.2)**
- 문제 상황: S3·SNS 이벤트로 비동기 호출되는 함수가 가끔 실패한다. 실패 이벤트를 잃지 않고 오류 응답 정보까지 보관하고, 성공 기록은 다른 대상으로 보내고 싶다. 또는 재시도 때문에 중복 처리가 문제다.
- 정답 단서: 성공/실패 분기·응답 정보 → **Destinations**(on-success/on-failure). 실패 이벤트 본문만, SQS/SNS 표준 → **DLQ**. 재시도 줄이기 → `MaximumRetryAttempts`(0–2)·`MaximumEventAgeInSeconds`. SQS가 이벤트 소스 → DLQ는 **큐**에(redrive). 중복 → **멱등성**(DynamoDB 조건부 쓰기·Powertools). [S19][S22][S28][S55]

**패턴 C — 스트림·큐 소비 오류와 지연 (Skill 1.2.3·1.2.5·1.2.7)**
- 문제 상황: Kinesis(또는 DynamoDB Streams) 한 레코드가 계속 실패해 샤드가 막히고 `IteratorAge`가 오른다. 또는 SQS 배치 10건 중 1건만 실패했는데 전체가 재처리된다. 또는 스트림 데이터를 변환해 S3에 적재하고 싶다.
- 정답 단서: **`BisectBatchOnFunctionError` + `MaximumRetryAttempts`/`MaximumRecordAgeInSeconds` 유한값 + 실패 대상**. 부분 실패 → **`ReportBatchItemFailures`**(SQS는 messageId, 스트림은 SequenceNumber). 가시성 제한시간 ≥ 함수 타임아웃의 6배·`maxReceiveCount` ≥ 5. 시간 창 집계 → **tumbling window**. 변환 후 적재 → **Firehose + Lambda**(`recordId`·`result`·`data`). [S30][S31][S33][S28][S32][S53]

**패턴 D — 콜드 스타트·성능 (Skill 1.2.6·1.2.2)**
- 문제 상황: API 응답 지연이 들쭉날쭉하고(프레임워크 로딩 등 초기화가 수 초), 프로비저닝된 동시성을 설정했는데도 콜드 스타트가 보인다. 또는 CPU 바운드 함수가 느리다.
- 정답 단서: 엄격한 지연 요건 → **프로비저닝된 동시성**(이벤트 소스가 **별칭·버전**을 가리켜야 함, $LATEST 불가). Java·Python 3.12+·.NET 8+의 초기화 지연 → **SnapStart**(게시 버전만, PC·EFS와 함께 불가). CPU 바운드 → **메모리 증가(CPU 비례) + Power Tuning**. SDK 클라이언트·DB 연결은 **핸들러 밖**, 필요한 모듈만 import, arm64 검토. [S16][S37][S7][S50][S51]

**보조 단서 (패턴으로 만들기엔 짧은 것)**
- 테스트 도구: 배포 전 로컬 컨테이너 → `sam local invoke -e event.json`, 배포된 함수 → `sam remote invoke`, 권한·파라미터 검증만 → `--invocation-type DryRun`(204), 콘솔 Test는 동기 호출. [S48][S49][S21][S46]
- 통합 모델: API Gateway·ALB는 동기(프록시 응답 형식 오류 → 502), S3·SNS·EventBridge는 비동기, SQS·Kinesis·DynamoDB Streams는 ESM(폴링, 실행 역할 권한). [S40][S61][S62]
- 환경 변수: 4 KB 합계·버전 게시 시 잠김·민감 정보는 Secrets Manager. [S9]

## 흔한 함정·혼동 짝
| 짝 (A vs B) | 혼동 이유 | 구분 기준 한 줄 | 출처 |
|---|---|---|---|
| DLQ vs Destinations | 둘 다 비동기 호출의 실패 이벤트를 보관한다 | DLQ = SQS·SNS **표준**만·실패만·이벤트 본문만·함수 레벨 / Destinations = 성공·실패 선택·대상 5종·응답 정보 포함·함수/버전/별칭 | [S19] |
| 예약 동시성 vs 프로비저닝된 동시성 | 둘 다 "동시성을 확보"한다는 이름 | 예약 = 용량 보장 + 상한(무료, 함수) / 프로비저닝 = 사전 초기화(유료, 버전·별칭, $LATEST 불가, 예약 이하) | [S15][S16] |
| 함수의 DLQ vs SQS 큐의 DLQ(redrive) | SQS 소비 실패에도 "DLQ"라는 같은 말을 쓴다 | SQS가 이벤트 소스면 DLQ는 **큐**에 설정(`maxReceiveCount` ≥ 5), 함수 DLQ는 비동기 호출용 | [S19][S28] |
| 퍼블릭 서브넷 연결 vs 프라이빗 서브넷 + NAT | 퍼블릭 서브넷이면 인터넷이 될 것 같다 | 퍼블릭 서브넷에 연결해도 인터넷·퍼블릭 IP가 없다 → 프라이빗 서브넷 + 퍼블릭 서브넷의 NAT 게이트웨이 | [S1][S2] |
| 동기 vs 비동기 vs ESM의 재시도 주체 | 모두 "Lambda가 알아서 재시도"한다고 오해 | 동기 = 호출자·서비스 / 비동기 = Lambda(함수 오류 2회, 스로틀·5xx 최대 6시간) / ESM = 큐는 가시성 제한시간·redrive, 스트림은 만료까지 반복(샤드 막힘) | [S20][S18] |
| SQS 부분 배치 vs 스트림 부분 배치 | 같은 `batchItemFailures` 응답 형식 | SQS = `itemIdentifier`는 messageId, 예외를 던지면 전체 실패 / 스트림 = SequenceNumber, 가장 낮은 값이 체크포인트 | [S26][S31] |
| SnapStart vs 프로비저닝된 동시성 | 둘 다 콜드 스타트를 줄인다 | SnapStart = 게시 버전의 init 스냅샷 복원(Java 11+·Python 3.12+·.NET 8+) / PC = 환경 상시 유지. 서로 함께 못 쓰고 둘 다 $LATEST 불가 | [S37][S16] |
| `sam local invoke` vs `sam remote invoke` vs `DryRun` | 모두 함수를 "호출해 테스트"하는 방법 | local = Docker 컨테이너(배포 전) / remote = 배포된 함수 / DryRun = 권한·파라미터 검증용(응답 204) | [S48][S49][S21] |
| 콘솔 Test vs 실제 비동기 트리거 | 콘솔에서 성공하면 S3·SNS 트리거도 같다고 생각 | 콘솔 Test는 항상 **동기** 호출 — 비동기 재시도·DLQ·Destinations 동작은 실제 트리거에서만 | [S46][S43] |
| `ParallelizationFactor` vs 샤드 증설 | 둘 다 Kinesis 처리량을 올린다 | PF = 기존 샤드를 최대 10배 동시 처리(partition key 순서 유지) / 샤드 증설 = 스트림 구조 변경(파티션 키 분산 필요) | [S29][S50] |
| 환경 변수 암호화 vs 비밀 관리 | 환경 변수가 암호화되니 비밀도 안전하다고 생각 | 저장 시 암호화되지만 DB 자격 증명 등은 Secrets Manager 권장, 환경 변수는 합계 4 KB | [S9] |
| Firehose 결과 `Dropped` vs `ProcessingFailed` | 둘 다 레코드를 전달하지 않는다 | Dropped = 의도적 폐기(성공으로 간주) / ProcessingFailed = 변환 실패(실패로 간주, S3 `processing-failed` 폴더) | [S53][S54] |

**Q1 · 대응 Skill 1.2.1 · 난이도 intermediate**
- 문제: 개발자가 Lambda 함수를 VPC의 프라이빗 서브넷 두 곳에 연결해 같은 VPC의 Amazon RDS 인스턴스에 접속하도록 구성했다. RDS 접속은 정상이지만 함수가 외부 SaaS의 HTTPS API를 호출하면 "Task timed out"으로 실패한다. VPC에는 인터넷 게이트웨이가 연결된 퍼블릭 서브넷이 있고, 함수는 계속 RDS에 접속해야 한다. 가장 적절한 해결 방법은?
- 보기: A. 함수의 VPC 설정을 인터넷 게이트웨이가 연결된 퍼블릭 서브넷으로 바꾼다. / B. 퍼블릭 서브넷에 NAT 게이트웨이를 만들고, 함수가 연결된 프라이빗 서브넷의 라우팅 테이블에 `0.0.0.0/0 → NAT 게이트웨이` 경로를 추가한다. / C. 함수 실행 역할에 `AWSLambdaVPCAccessExecutionRole` 정책을 추가로 연결한다. / D. 함수의 VPC 설정을 제거해 Lambda 관리형 VPC에서만 실행되게 한다.
- 정답: B
- 정답 근거: 프라이빗 서브넷의 인터넷 경로는 퍼블릭 서브넷에 연결된 NAT 게이트웨이로 가는 `0.0.0.0/0` 라우트이며, 퍼블릭 서브넷에 연결해도 인터넷 접근이 생기지 않는다. https://docs.aws.amazon.com/lambda/latest/dg/configuration-vpc-internet.html · https://docs.aws.amazon.com/lambda/latest/dg/configuration-vpc.html
- 오답 해설: A는 퍼블릭 서브넷에 연결해도 인터넷 접근·퍼블릭 IP가 생기지 않는다. C의 정책은 ENI를 만드는 권한이며 VPC 연결·RDS 접속이 이미 되므로 충족돼 있고 라우팅 문제는 풀지 못한다. D는 VPC 설정을 제거하면 인터넷은 되지만 VPC 안의 RDS에 접속할 수 없어 조건을 어긴다. [S1][S2]

**Q2 · 대응 Skill 1.2.2·1.2.6 · 난이도 intermediate**

- 보기: A. 버전을 게시하고 그 별칭(또는 버전)에 프로비저닝된 동시성을 설정한 뒤, API 통합이 그 별칭을 호출하도록 바꾼다. / B. 함수의 예약 동시성을 0으로 설정한다. / C. `$LATEST`에서 SnapStart를 활성화해 프로비저닝된 동시성을 대체한다. / D. 함수 메모리를 10,240 MB로 올려 초기화 시간을 줄인다.

**Q4 · 대응 Skill 1.2.3·1.2.7 · 난이도 advanced**
- 문제: Kinesis 데이터 스트림을 기본 설정의 이벤트 소스 매핑으로 소비하는 Lambda 함수가 있다. 특정 레코드의 파싱 오류로 함수가 계속 예외를 던지고, 해당 샤드의 처리가 멈춰 `IteratorAge`가 계속 증가한다. 정상 레코드는 계속 처리하면서 문제 레코드는 따로 보관하고 싶다. 가장 적절한 구성은?
- 보기: A. 함수 타임아웃을 최대값으로 늘리고 메모리를 높인다. / B. 이벤트 소스 매핑에서 `BisectBatchOnFunctionError`를 켜고, `MaximumRetryAttempts`(또는 `MaximumRecordAgeInSeconds`)를 유한 값으로 제한하며, 실패 대상(예: SQS 큐)을 지정한다. / C. 함수에 SQS 표준 큐를 DLQ로 구성한다. / D. 스트림의 샤드 수를 늘린다.
- 정답: B
- 정답 근거: 기본값(-1)에서는 실패 레코드가 만료될 때까지 무한 재시도되어 샤드가 막힌다. 배치 이등분으로 문제 레코드를 분리하고, 재시도·연령을 제한하고, 버려지는 레코드를 실패 대상에 보관한다. https://docs.aws.amazon.com/lambda/latest/dg/services-kinesis-parameters.html · https://docs.aws.amazon.com/lambda/latest/dg/services-kinesis-batchfailurereporting.html · https://docs.aws.amazon.com/lambda/latest/dg/kinesis-on-failure-destination.html
- 오답 해설: A는 원인이 예외이므로 시간·메모리와 무관하다. C의 함수 DLQ는 비동기 호출용이고 ESM이 버리는 레코드는 ESM의 실패 대상으로 보낸다. D는 샤드 증설이 오류 영향 범위를 줄일 뿐 문제 레코드가 있는 샤드는 계속 막힌다. [S20][S19][S23][S29]

**Q5 · 대응 Skill 1.2.4 · 난이도 foundational**
- 문제: 개발자가 SAM 템플릿에 정의한 Lambda 함수를 배포하기 전에, 로컬(Docker 설치됨)에서 이벤트 JSON 파일을 입력으로 실행해 보고 싶다. 사용할 명령은?
- 보기: A. `sam remote invoke MyFunction --stack-name my-app --event-file event.json` / B. `aws lambda invoke --function-name MyFunction --invocation-type DryRun out.json` / C. `sam local invoke MyFunction -e event.json` / D. 콘솔 Test 탭에서 공유 가능한 테스트 이벤트를 실행한다.
- 정답: C
- 정답 근거: `sam local invoke`는 함수의 논리 ID와 이벤트 파일로 함수를 로컬에서 호출하며, 로컬 테스트에는 Docker가 필요하다. https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/serverless-sam-cli-using-invoke.html · https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/using-samcli-terraform.html
- 오답 해설: A는 이미 배포된 클라우드의 함수를 호출한다. B의 `DryRun`은 파라미터·권한만 검증하며 로컬 실행이 아니다. D는 클라우드에 배포된 함수를 동기 호출한다. [S49][S21][S46]
