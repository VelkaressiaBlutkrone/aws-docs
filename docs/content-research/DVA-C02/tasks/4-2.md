### 효과적인 로깅 전략 (Skill 4.2.2)

**무엇을 어떻게 남기나** — 애플리케이션 팀의 로깅 모범 사례 [S4]
- **상관 ID**: 요청에 ID가 이미 있으면 재사용하고 없으면 생성한다. 다른 서비스를 호출할 땐 `traceId`를 넘겨 구성요소별 로그를 한 요청으로 묶는다. 예: ALB가 `X-Amzn-Trace-Id` 헤더를 추가한다.
- **핵심(비즈니스 크리티컬) 메서드의 소요 시간**을 정해진 패턴으로 기록한다(AOP로 로깅 관심사 분리 가능).
- **적절한 로그 레벨**: `WARNING`·`ERROR` = 조사가 필요한 중요 이벤트, `INFO`·`DEBUG` = 상세 추적·대량 이벤트. 운영에서는 필요한 레벨만 수집하고, INFO 과다는 백엔드에 부담이며 DEBUG는 대량 데이터가 생기므로 신중히 쓴다.
- 팀이 **공통 로깅 라이브러리**와 사전에 정한 로그 패턴을 공유한다.
- **민감 정보**: Powertools Logger의 '들어온 이벤트 로깅(`log_event`)'은 민감 정보 유출을 막으려고 기본 비활성이다 [S16]. API Gateway **Data tracing**(전체 요청·응답 기록)은 운영 API에 비권장이다 [S10].

**어디로 보내나 (Lambda)** [S5]

| 목적 | 선택 | 근거 |
|---|---|---|
| 실시간 조회·경보·Logs Insights·Live Tail | CloudWatch Logs(기본 대상) | 설정 없이 바로 동작 |
| 장기 보관 비용 절감, Athena 분석 | Amazon S3 | 가장 경제적이나 지연이 큼 |
| OpenSearch Service·Redshift·Datadog·New Relic·Splunk 등 연계 | Firehose | 사전 통합으로 설정 단순화 |

로그 그룹은 선택할 수 있고 기본은 `/aws/lambda/<함수명>`이다. [S13]

**보존·비용·전달**
- CloudWatch Logs는 기본적으로 로그를 무기한 보관한다. 로그 그룹마다 1일~10년 또는 무기한으로 보존 기간을 정하며, 만료·삭제된 로그는 AWS도 복구하지 못한다. [S6] 개발 환경은 짧게, 운영은 길게 두고 장기 보관은 S3로 내보낸다(`create-export-task`). [S7]
- JSON 형식은 메타데이터 때문에 로그 메시지 크기가 커질 수 있다(저장 비용 ↑). [S11]
- 한도: 로그 그룹당 메트릭 필터 100개, 구독 필터 5개. [S8] 구독 필터는 로그를 Kinesis Data Streams·Lambda·Firehose·OpenSearch Service로 실시간 전달한다. [S9]

### 애플리케이션 이벤트·사용자 작업의 구조화 로깅 (Skill 4.2.7)

- **왜 JSON인가**: 검색·필터가 쉽고 태그·컨텍스트를 붙여 대량 로그를 자동 분석할 수 있다. 기존 도구가 일반 텍스트를 소비하는 경우가 아니면 JSON을 권장한다. [S11] 같은 구조화 로그 하나로 Logs Insights·EMF(다차원 지표)·Contributor Insights를 모두 쓸 수 있다. [S14] Lambda의 JSON 형식은 OpenTelemetry Logs Data Model을 따른다. [S15]
- **Lambda 고급 로깅 제어(advanced logging controls)** — 로그 형식·로그 수준·로그 그룹 3가지를 코드 변경 없이 설정한다. [S5]

| 설정(API 이름) | 값 | 기본 | 핵심 |
|---|---|---|---|
| 로그 형식 `LogFormat` | `JSON` / `Text` | 모든 관리형 런타임 기본은 일반 텍스트 [S11] | Lambda Managed Instances는 JSON 고정 [S11] |
| 애플리케이션 로그 수준 `ApplicationLogLevel` | `TRACE`(가장 상세)·`DEBUG`·`INFO`·`WARN`·`ERROR`·`FATAL`(가장 간략) [S12][S13] | `INFO` [S12] | **JSON 형식일 때만** 필터링. 고른 수준과 그보다 덜 상세한 수준만 전송(예: WARN → WARN·ERROR·FATAL) [S12] |
| 시스템 로그 수준 `SystemLogLevel` | `DEBUG`·`INFO`·`WARN` [S13] | `INFO`(`start`·`report` 로그 전송) [S12] | Lambda가 만드는 플랫폼 이벤트 로그 필터 |
| 로그 그룹 `LogGroup` | 기존·신규 로그 그룹 이름 | `/aws/lambda/<함수명>` [S13] | 함수별 그룹 분리·공유 선택 |

- JSON 애플리케이션 로그 키: `timestamp`, `level`, `message`, `requestId`(Java는 `AWSrequestId`). 시스템 로그 키: `time`, `type`, `record`. [S11]
- JSON 애플리케이션 로그를 코드 변경 없이 받는 런타임·방법: Java(Java 8 on AL1 제외, `LambdaLogger`·Log4j2), .NET 8+(`ILambdaLogger`), Node.js 16+(`console.*`), Python 3.8+(`logging`), Ruby 4.0+(`Logger`), Rust(`tracing`). 그 밖 런타임은 시스템 로그만 JSON이고, 애플리케이션 로그는 Powertools 등으로 JSON을 직접 출력한다. [S11]
- 그 밖의 방법: stdout·stderr에 `level` 키가 있는 JSON을 출력하면 필터링되며, Lambda가 시간을 쓰려면 RFC 3339 `timestamp`도 필요하다. `level`이 없거나 잘못되면 INFO, 유효한 timestamp가 없으면 INFO로 보고 Lambda가 timestamp를 붙인다. [S12]
- 함정: 코드에서 로그 수준을 직접 지정(예: Python `logging.setLevel()`)하면 콘솔·API 설정보다 우선한다. [S12] JSON으로 바꾸면서 수준을 안 정하면 앱·시스템 수준이 모두 INFO가 되고, Python 일반 텍스트 형식의 기본 수준은 WARN이다. [S11] 텍스트→JSON 전환은 기존 텍스트 파싱 파이프라인을 깨뜨릴 수 있다. [S15] 이미 JSON인 로그는 이중 인코딩하지 않는다. [S11]
- 설정 예: `aws lambda update-function-configuration --function-name myFunction --logging-config LogFormat=JSON,ApplicationLogLevel=ERROR,SystemLogLevel=WARN`. 커스텀 런타임은 `AWS_LAMBDA_LOG_LEVEL`·`AWS_LAMBDA_LOG_FORMAT` 환경 변수를 읽어 따른다. [S12]
- **Powertools for AWS Lambda(Python) Logger**: JSON 출력, 표준 키 `level`·`location`·`message`·`timestamp`·`service`·`xray_trace_id`(트레이싱 시)·`sampling_rate`·`exception`. `inject_lambda_context`가 `cold_start`·`function_name`·`function_memory_size`·`function_arn`·`function_request_id`를 덧붙이고, 상관 ID는 `correlation_id_path`(JMESPath)로 지정하며, 요청 일부에서만 DEBUG를 켜는 로그 샘플링을 지원한다. 기본 수준은 INFO(`POWERTOOLS_LOG_LEVEL`), 서비스 이름은 `POWERTOOLS_SERVICE_NAME`. [S16] Lambda 고급 로깅 제어가 켜져 있으면 `AWS_LAMBDA_LOG_LEVEL`보다 낮은 수준으로 내릴 수 없다(우선순위: `AWS_LAMBDA_LOG_LEVEL` > 코드 설정 > `POWERTOOLS_LOG_LEVEL`). [S17]
- 이벤트·사용자 작업 로그 필드 설계(저작자 제안): `timestamp`, `level`, `message`, `requestId`·`correlationId`·`traceId`, `event`(예: order_placed), `userId`(식별자는 해시·가명 처리), `outcome`, `durationMs`. 값이 매우 다양한 키(요청 ID 등)는 로그 필드로만 두고 지표 차원으로 쓰지 않는다.
- 분석 쪽: Logs Insights는 JSON 필드를 점 표기로 바로 질의하되, Lambda 로그는 이벤트당 첫 JSON 조각만 자동 발견하고 JSON 로그에서 최대 200개 필드를 추출한다. [S18]

### 사용자 지정 지표를 내보내는 코드 (Skill 4.2.3)

| 방식 | 생성 경로 | 필요 권한 | 핵심 한도·특징 | 선택 기준 |
|---|---|---|---|---|
| `PutMetricData` API | 코드가 동기 API 호출 | `cloudwatch:PutMetricData` | 요청당 1 MB(HTTP POST)·지표 1,000개 이하, `Values`/`Counts`로 지표당 150값, 지표당 차원 30개, 타임스탬프는 과거 2주~미래 2시간, 네임스페이스는 `AWS/`로 시작 금지 [S19] | 소량·단순 수집. 기본 쿼터 500 TPS(KC 표기) [S25] |
| EMF(로그에 지표 정의를 심음) | JSON 로그 → CloudWatch가 비동기 추출 | `logs:PutLogEvents`만 [S20] | 이벤트 1 MB, 정의 100개, 차원 키 30개 [S21] | 호출이 많거나 소스가 많을 때(예: 수백 개 Lambda 동시 실행), 풍부한 이벤트를 로그에도 남길 때 [S23][S20] |
| 메트릭 필터 | 이미 있는 로그 이벤트의 패턴 → 지표 | 로그 그룹에 필터 설정 | 값은 숫자·명명 식별자·로그에서 추출한 값, 로그 그룹당 100개, 기본값(default value) 지정 가능(차원을 주면 불가), 매분 집계·보고 [S27][S61][S8] | 코드를 못 바꾸거나 기존 로그에서 지표를 뽑을 때 |

- **고빈도·다중 소스**: `PutMetricData` 처리량 쿼터에 자주 근접하거나 수백 개 Lambda 같은 동시 소스가 지표를 낼 때는 `PutMetricData` 대신 EMF를 쓴다. [S23]
- **EMF 필수 요소**: 루트의 `_aws.CloudWatchMetrics[]`(`Namespace`·`Dimensions`·`Metrics`)와 `_aws.Timestamp`(과거 14일·미래 2시간 이내), 지표 값은 루트 멤버로 둔다. [S21] Lambda·ECS에서는 추가 설정 없이 로그 JSON 루트에 `_aws`(안에 `CloudWatchMetrics`)만 있으면 CloudWatch가 비동기로 지표를 만든다. [S24] 클라이언트 라이브러리나 직접 만든 로그를 `PutLogEvents`·CloudWatch 에이전트로 보낸다. [S20] 고해상도 EMF 지표에 경보를 걸면 로그를 5초 이하로 flush한다. [S22]
- **Powertools Metrics(Python)**: `add_metric`·`add_dimension`·`@metrics.log_metrics`(응답/실패 시 flush)·`capture_cold_start_metric`. EMF는 배치당 최대 100개 지표를 지원하며 100번째에서 flush하고 101번째부터 새 EMF 객체로 묶는다. 고해상도는 `resolution=MetricResolution.High`(값 1 또는 60). 핸들러 밖(전역)에서 만든 지표·차원은 콜드 스타트에만 추가된다. 환경 변수: `POWERTOOLS_METRICS_NAMESPACE`·`POWERTOOLS_SERVICE_NAME`. [S26]
- **해상도·보존**: 표준 해상도 60초(1분 데이터 15일 보존), 고해상도 1초 미만 주기는 3시간 보존. [S28] 고해상도 지표 경보는 10·20·30초 주기가 가능하다. [S52]
- **차원 설계**: 차원 조합마다 별도 지표가 생기므로 비용이 늘 수 있다(EMF 문서도 `requestId` 같은 고카디널리티 차원을 경고). [S21]
- 새 지표는 `ListMetrics`에 보이기까지 최대 15분 걸릴 수 있다. [S19] 사용자 지정 지표가 만들어지기 전에도 경보를 만들 수 있으나, 유효하려면 그 지표의 모든 차원을 포함해야 한다. [S51]
- 분석 관점의 EMF 사양 상세(요소 규칙·`AWS/Logs` 처리 지표) → 4-1.md Skill 4.1.4.

### 추적 서비스용 어노테이션 추가 (Skill 4.2.4)

| 항목 | 어노테이션(annotations) | 메타데이터(metadata) |
|---|---|---|
| 색인 | **색인됨** → 필터 식·그룹·`GetTraceSummaries`로 검색 [S29] | 색인 안 됨, 저장만 [S29] |
| 값 형식 | 문자열·숫자·불리언(객체·배열 불가) [S30] | 객체·리스트 포함 모든 형식 [S29] |
| 한도 | 트레이스당 최대 50개 색인 [S29], 값 ≤ 1,000 유니코드 문자 [S31] | (개수 한도는 확인하지 못함) |
| 키 규칙 | 영숫자+밑줄 [S30]. SDK 문서는 ≤500자·영숫자, 점(.) 허용·공백/기호 불가로 서술 → `확인 필요` [S31] | Python `put_metadata(key, value, namespace)`처럼 네임스페이스와 키 [S32] |
| 용도 | 트레이스를 그룹화·검색할 값(고객 등급·주문 유형·기능 플래그) | 저장만 필요한 상세(검색 불필요) |

- 어노테이션·메타데이터는 트레이스 수준으로 집계되며 세그먼트·서브세그먼트 어디에나 추가할 수 있다. [S29]
- SDK 호출: Java `putAnnotation`, Node.js `addAnnotation`, Python `put_annotation`·`put_metadata`, Go `xray.AddAnnotation`, .NET `AddAnnotation`. 같은 세그먼트·서브세그먼트에 같은 키를 두 번 기록하면 덮어쓴다. 검색은 필터 식의 `annotation[key]`를 쓴다. [S31][S32][S33]
- **Lambda 안에서**: 세그먼트·서브세그먼트를 Lambda 런타임이 관리하므로 .NET은 함수 안에서 서브세그먼트를 만들고 어노테이션을 추가한 뒤 종료해야 한다. [S33] Lambda 문서(구 구조)는 X-Ray SDK로 `Invocation` 서브세그먼트를 확장해 하위 호출·어노테이션·메타데이터를 기록할 수 있고 함수 세그먼트에는 직접 접근할 수 없다고 한다. 신 구조에서는 고객 서브세그먼트가 `AWS::Lambda::Function` 세그먼트에 바로 붙고 그 세그먼트에 `aws.responseLatency`·`aws.responseDuration`·`aws.runtimeOverhead`·`aws.extensionOverhead` 어노테이션이 자동으로 달린다. [S34]
- Powertools Tracer는 `ColdStart` 어노테이션을 자동 추가해 `annotation.ColdStart = true`로 콜드 스타트 트레이스를 걸러 볼 수 있다. [S36]
- OpenTelemetry에서는 어노테이션·메타데이터가 **속성(attributes)** 으로 대응되며, 기본은 메타데이터로 변환되고 `aws.xray.annotations` 목록에 키를 넣어야 어노테이션이 된다. [S35]

### AWS 서비스·도구로 추적 구현 (Skill 4.2.6)

**X-Ray 동작과 Lambda·API Gateway 설정**
- 클라이언트 SDK는 JSON 세그먼트 문서를 UDP로 데몬에 보내고 데몬이 배치로 X-Ray에 업로드한다. 데몬은 Elastic Beanstalk·Lambda 플랫폼에 포함돼 있다. [S37]

| 구분 | Active | PassThrough |
|---|---|---|
| 동작 | Lambda가 호출 세그먼트를 만들어 X-Ray로 전송(샘플링된 요청만) | 추적 컨텍스트만 다운스트림에 전달, 트레이스는 안 보냄 |
| 기본값 | 아님 | **Active를 켜지 않으면 기본** |
| 비고 | 업스트림(API Gateway 등)의 샘플링 결정 헤더를 따름 | 업스트림이 헤더를 안 주면 Lambda가 '샘플링 안 함' 헤더 생성 |
[S34]
- 실행 역할에 `xray:PutTraceSegments`·`xray:PutTelemetryRecords`가 필요하다(관리형 정책 `AWSXRayDaemonWriteAccess`, 콘솔에서 활성화하면 자동 추가). 함수의 X-Ray 샘플링 비율은 설정할 수 없고(요청 1/초 + 추가 요청 5%), **게시된 버전의 트레이싱 모드는 바꿀 수 없다**. Lambda는 트레이스당 세그먼트 2개(`AWS::Lambda`·`AWS::Lambda::Function`)를 만든다. MSK·자체 관리 Kafka·Amazon MQ·DocumentDB 이벤트 소스 매핑은 X-Ray 추적을 지원하지 않는다. [S34]
- CLI·IaC: `aws lambda update-function-configuration --tracing-config Mode=Active`, CloudFormation `TracingConfig.Mode: Active`, SAM `Tracing: Active`. [S34]
- **API Gateway**: 스테이지에서 X-Ray 추적을 켜며(콘솔 Logs/Tracing 탭 후 배포) 가능한 것은 **REST API뿐**이다. X-Ray 콘솔의 샘플링 규칙으로 기록 대상을 정하고, 헤더가 없는 요청에는 추적 헤더를 추가한다. HTTP 통합에서는 URL 경로마다 노드가 생겨 트레이스 맵 한도(10,000)에 닿을 수 있다. [S40]

**전파·샘플링**
- 추적 헤더 `X-Amzn-Trace-Id: Root=1-5759e988-bd862e3fe1be46a994272793;Parent=53995c3f42cd8ad8;Sampled=1`에 트레이스 ID·부모 세그먼트 ID·샘플링 결정이 실린다. 사용자가 헤더로 트레이스 ID·샘플링 결정을 조작하지 못하게 애플리케이션이 들어오는 헤더를 제거할 수 있다. [S29]
- SQS: HTTP 호출은 `X-Amzn-Trace-Id` 헤더, 메시지에는 예약된 시스템 속성 `AWSTraceHeader`를 쓰며 둘 다 있으면 시스템 속성이 우선한다. 트레이스 헤더는 SQS 메시지 크기·속성 한도에 포함되지 않는다. Lambda 소비자는 업스트림 트레이스와 자동 연결된다(세그먼트당 최대 20개, 트레이스당 최대 100개 링크). [S41][S42]
- 샘플링: 기본은 '초당 첫 요청 + 이후 요청의 5%'. 기본 규칙(우선순위 10000, 고정 비율 0.05, 예약 크기 1)은 가장 낮은 우선순위라 삭제할 수 없고 비율·예약 크기만 바꿀 수 있다. [S29][S38] 예: 예약 50·고정 비율 10%에서 초당 100건이 규칙에 맞으면 초당 55건이 샘플링된다. [S39]
- 규칙 설계 힌트: 상태를 바꾸는 호출·사용자·거래는 샘플링 없이 모두 추적하고, 헬스 체크·백그라운드 폴링 같은 대량 읽기는 낮은 비율로 둔다. [S29]
- VPC 안의 리소스는 인터페이스 VPC 엔드포인트(AWS PrivateLink)로 인터넷 게이트웨이·NAT 없이 X-Ray에 보낼 수 있다. [S43]
- 보기·분석: X-Ray 서비스 맵과 ServiceLens 맵은 CloudWatch 콘솔의 **트레이스 맵**으로 합쳐졌고, 인사이트가 오류율 이상을 탐지해 EventBridge로 알린다. [S47][S48]

**현재 상태 — X-Ray SDK·데몬 vs OpenTelemetry** (시험 문구와 현황이 어긋날 수 있는 부분)
- X-Ray **SDK·데몬은 2026-02-25부터 maintenance mode**: 보안 수정만 릴리스하고 신규 기능은 없다. [S44] X-Ray **서비스**는 계속 지원되고 기존 SDK·데몬이 보낸 트레이스도 계속 받아 처리하며, 신규 개발은 OpenTelemetry 기반이다. [S45] AWS는 OpenTelemetry를 주 계측 표준으로 권장한다. [S35]
- AWS의 OpenTelemetry 경로: ADOT(트레이스를 X-Ray 세그먼트로 내보냄), CloudWatch Application Signals(OTel 트레이스·지표로 앱 상태 모니터링), CloudWatch OTel 엔드포인트(HTTP로 X-Ray에 직접). [S35] Application Signals는 Java·Python·Node.js·.NET을 지원한다. [S49]
- Lambda: 권장은 'AWS Lambda Layer for OpenTelemetry'(트레이싱만 쓰려면 `OTEL_AWS_APPLICATION_SIGNALS_ENABLED=false`), 대안은 ADOT 관리형 레이어. `AWS_LAMBDA_EXEC_WRAPPER=/opt/otel-instrument`로 자동 계측을 로드한다. [S35][S46]
- X-Ray 데몬은 CloudWatch 에이전트나 OpenTelemetry 콜렉터로 대체한다. [S35] ADOT SDK는 CloudWatch 에이전트 또는 ADOT Collector와 함께 쓰는 구성을 권장한다. [S50]

| X-Ray 개념 | OpenTelemetry 대응 [S35] |
|---|---|
| 세그먼트 / 서브세그먼트 | (서버) 스팬 / (비서버) 스팬 |
| 어노테이션·메타데이터 | 속성(attributes) |
| 샘플링 규칙 | OpenTelemetry 샘플링(원격 샘플러로 X-Ray 규칙 사용 가능, 일부 언어) |
| 이미터 / 데몬 | 스팬 익스포터 / OpenTelemetry 콜렉터 |
| X-Ray 추적 헤더 전파 | W3C Trace Context(기본), X-Ray 전파자로 AWS 서비스와 호환 |

|---|---|---|

| 애플리케이션 이상 | X-Ray 인사이트 → EventBridge | 오류율이 예상 범위를 넘으면 인사이트가 생성되고, 알림은 EventBridge로 연동해 이메일·경보 등으로 전달 [S48] |

- 경보는 지표 값이 임계를 넘었는지를, EventBridge 규칙은 '상태 변경 이벤트'를 패턴으로 잡는다(저작자 정리).
- 쿼터 알림 주의: 사용량 지표를 Service Quotas와 연동하는 서비스는 일부(CloudWatch·CloudWatch Logs·DynamoDB·EC2·ELB·Fargate·KMS·Data Firehose 등)이며 목록에 Lambda는 없다. [S53] Service Quotas 콘솔에서 만든 경보에는 알림(SNS 등)을 따로 추가해야 한다. [S54] Lambda 동시성은 `ConcurrentExecutions`·`ClaimedAccountConcurrency`(리전에서 온디맨드 호출에 쓸 수 없는 동시성) 지표로 직접 경보를 만든다. [S59]
- CloudWatch는 지정한 동작이 실제로 존재·유효한지 검증하지 않는다 → 경보 동작(SNS 주제 등)을 먼저 만들고 테스트한다(`SetAlarmState`로 상태 강제 가능). [S51]

### 애플리케이션 상태 확인·준비 프로브 구성 (Skill 4.2.8)

| 메커니즘 | 확인 주체 | 실패 시 | 핵심 설정·기본값 |
|---|---|---|---|
| ALB 대상 그룹 상태 확인 | 로드 밸런서가 등록 대상에 HTTP(S) GET | 대상을 서비스에서 제외(전부 비정상이면 'fail open'으로 전체에 라우팅) [S62] | 경로 `/`, 간격 30초(instance·ip)/35초(lambda), 타임아웃 5초/30초, 정상 임계 5, 비정상 임계 2, 성공 코드 200, WebSocket 미지원 [S62] |
| ECS 컨테이너 상태 확인 | ECS 에이전트가 컨테이너에서 `command` 실행(`CMD`/`CMD-SHELL`, 종료 코드 0=성공) | 서비스의 태스크면 UNHEALTHY → 중지 후 교체 [S63] | 간격 30초(5~300), 타임아웃 5초(2~60), 재시도 3(1~10), `startPeriod` 기본 꺼짐(0~300) [S63] |
| ECS 서비스 유예 `healthCheckGracePeriodSeconds` | 서비스 스케줄러가 ELB 상태 확인 실패를 무시 | 태스크가 뜨기 전에 중지되는 것을 방지 [S64] | LB 정의 시 기본 0, 최대 2,147,483,647초. LB를 안 쓰면 태스크 정의의 `startPeriod` 권장 [S64] |
| EKS/Kubernetes 프로브 | kubelet | 프로브가 응답하지 않으면 파드를 비정상으로 표시하고 SIGTERM을 보내며(연속 실패 시 종료·교체), readiness는 트래픽 수신 준비 여부를 판단 [S65][S66] | 유형 HTTP·명령(exec)·gRPC·TCP(`httpGet`·`tcpSocket` 등) [S65][S67] |
| Route 53 상태 확인 | 전 세계 헬스 체커가 엔드포인트에 요청 | DNS 페일오버 | 간격 30초(빠른 10초), 실패 임계 1~10(기본 3), 체커의 18% 초과가 정상이면 healthy [S68][S69][S70] |
| Elastic Beanstalk 상태 | 기본: 로드 밸런서 응답, 향상: 인스턴스의 health agent | 환경 색 Grey·Green·Yellow·Red와 상태(Ok·Warning·Degraded·Severe 등) [S71][S73] | 향상된 상태 보고를 환경에 켜야 함 [S72] |

- **세 프로브의 역할**(Kubernetes): liveness = 애플리케이션이 살아 있는지, readiness = 트래픽을 받을 준비가 됐는지, startup = 느리게 시작하는 앱 보호(구성하면 성공 전까지 liveness·readiness를 검사하지 않음). 프로브를 하나도 정의하지 않으면 kubelet은 파드를 무기한 정상으로 간주한다. [S65]
- **liveness는 파드 밖 의존성에 묶지 않는다**: 외부 DB가 응답하지 않는다고 파드가 liveness를 실패하면 모든 파드가 동시에 교체되어 앱이 내려갈 수 있다. [S66] HTTP 프로브는 200~399 응답을 정상으로 본다. [S66]
- ECS는 컨테이너 상태 확인에 에이전트 1.17.0 이상이 필요하고(Fargate는 플랫폼 1.1.0 이상), 이미지의 Docker `HEALTHCHECK`는 태스크 정의에 명시하지 않으면 모니터링하지 않으며 태스크 정의 값이 이미지 값을 덮어쓴다. [S63]
- Route 53 HTTP·HTTPS 상태 확인: TCP 연결 4초 이내 + 연결 후 2초 이내 2xx·3xx 응답. HTTPS 확인은 인증서를 검증하지 않는다. [S70]
- 원리(저작자 정리): '건강하지 않으면 라우팅에서 빼기'(ELB·Route 53)와 '건강하지 않으면 교체·재시작'(ECS·Kubernetes liveness)을 구분하고, 느리게 뜨는 앱에는 유예(grace)·startPeriod·startup 프로브로 오탐을 막는다.

## 시험에서 묻는 방식

> 문제 저작자를 위한 제안이며, 시험이 반드시 이렇게 낸다는 단정이 아니다.

1. **검색 가능한 트레이스 데이터** — 문제 상황: 고객 등급·주문 유형별로 X-Ray 트레이스를 검색·그룹화하고 싶고, 요청 본문 일부는 저장만 하면 된다. → 정답 단서: "검색·필터 표현식·그룹" ⇒ **어노테이션**(색인, 트레이스당 50개, 문자열·숫자·불리언), "저장만·객체·리스트" ⇒ **메타데이터**.
2. **Lambda 트레이스가 X-Ray에 안 보임** — 문제 상황: API Gateway 뒤 Lambda에서 X-Ray를 쓰는데 Lambda 노드가 트레이스 맵에 나오지 않는다. → 정답 단서: Active 추적을 켜지 않으면 기본이 PassThrough ⇒ Active 활성화, 실행 역할에 `xray:PutTraceSegments`·`xray:PutTelemetryRecords`(`AWSXRayDaemonWriteAccess`), API Gateway는 **REST API** 스테이지에서 추적 활성, 샘플링(초당 1건+5%)으로 일부만 보일 수 있음, 게시된 버전의 트레이싱 모드는 변경 불가.
3. **쿼터·배포 알림** — 문제 상황: (a) 서비스 쿼터의 80%에 도달하면 알림을 받고 싶다 (b) CodeDeploy 배포가 실패·완료되면 이메일을 받고 싶다. → 정답 단서: (a) Service Quotas의 CloudWatch 경보(또는 사용량 지표 + `SERVICE_QUOTA()` 수식 경보) + SNS 주제 (b) 배포 그룹 **트리거**(SNS) 또는 EventBridge 규칙(`aws.codedeploy`·`aws.codepipeline` 상태 변경 이벤트) → SNS.
4. **헬스 체크·프로브 설계** — 문제 상황: ALB 뒤 ECS 태스크가 시작 직후 계속 비정상으로 교체된다 / Kubernetes 앱이 느리게 시작한다. → 정답 단서: ECS 서비스 `healthCheckGracePeriodSeconds`(LB 미사용이면 `startPeriod`), ALB 상태 확인 경로·성공 코드 일치, Kubernetes **startup probe**; liveness를 외부 DB 같은 의존성에 묶지 말 것; "트래픽만 막고 재시작은 원치 않음" ⇒ readiness.

## 자가 점검 문항 후보

> **초안·미검수.** 아래 문항은 노트 작성자가 만든 초안이며 사람의 검수·`verified` 전환 전에는 사용하지 않는다.

**문항 1** — 대응 Skill: 4.2.4 / 난이도: intermediate
- 문제: 전자상거래 API(Lambda)에서 X-Ray를 쓴다. 운영팀은 `customerTier=gold`인 요청의 트레이스만 골라 지연을 비교하고 싶다. 주문 품목 목록(JSON 배열)은 디버깅용으로 트레이스에 저장해 두되 검색할 필요는 없다. 가장 적절한 구현은?
- A. `customerTier`와 품목 목록을 모두 메타데이터로 기록한다.
- B. `customerTier`는 어노테이션으로, 품목 목록은 메타데이터로 기록한다.
- C. `customerTier`는 메타데이터로, 품목 목록은 어노테이션으로 기록한다.
- D. 둘 다 어노테이션으로 기록한다.
- 정답: B
- 정답 근거: 어노테이션은 필터 표현식 검색용으로 색인되는 단순 키-값이고, 메타데이터는 모든 형식을 담지만 색인되지 않는다. https://docs.aws.amazon.com/xray/latest/devguide/xray-concepts.html [S29]
- 오답 해설: A는 메타데이터가 색인되지 않아 `customerTier`로 필터할 수 없다. C는 용도가 거꾸로다. D는 품목 목록 같은 배열을 어노테이션에 쓸 수 없고(문자열·숫자·불리언만) 트레이스당 색인 한도(50개)도 소모한다. [S30][S29]

**문항 2** — 대응 Skill: 4.2.6 / 난이도: intermediate
- 문제: API Gateway(REST API) → Lambda 구조에서 X-Ray를 쓰려 한다. API Gateway 스테이지에서 추적을 켰는데 트레이스 맵에 Lambda 함수 노드가 나타나지 않는다. Lambda 함수의 추적 설정은 한 번도 바꾼 적이 없다. 가장 가능성이 높은 원인과 조치는?
- A. Lambda 추적 모드가 기본값인 PassThrough이므로 Active로 바꾸고 실행 역할에 X-Ray 쓰기 권한을 부여한다.
- B. Lambda 함수 설정에서 X-Ray 샘플링 비율을 100%로 올린다.
- C. API Gateway를 HTTP API로 교체한다.
- D. X-Ray 데몬을 Lambda 계층(layer)으로 별도 설치한다.
- 정답: A
- 정답 근거: Active 추적을 켜지 않으면 Lambda는 PassThrough가 기본이며, 이 모드는 추적 헤더만 전달하고 트레이스를 보내지 않는다. Active로 켜면 세그먼트를 만들어 전송하며 실행 역할에 `xray:PutTraceSegments`·`xray:PutTelemetryRecords`가 필요하다. https://docs.aws.amazon.com/lambda/latest/dg/services-xray.html [S34]
- 오답 해설: B는 함수의 X-Ray 샘플링 비율을 설정할 수 없다 [S34]. C는 X-Ray가 API Gateway의 REST API만 지원해 오히려 반대다 [S40]. D는 X-Ray 데몬이 Lambda 플랫폼에 이미 포함돼 있다 [S37].

**문항 3** — 대응 Skill: 4.2.5 / 난이도: intermediate
- 문제: 개발팀은 DynamoDB 사용량이 계정 서비스 쿼터의 80%에 도달하면 이메일로 알림을 받고 싶다. 가장 적절한 구현은?
- A. CloudWatch 사용량(Usage) 지표를 `SERVICE_QUOTA()` 수식으로 쿼터와 비교하는 경보를 만들고 SNS 주제를 동작으로 지정한다.
- B. CloudTrail 이벤트 기록에서 스로틀 오류를 검색하는 Lambda를 매일 실행한다.
- C. DynamoDB 요청에 X-Ray 어노테이션을 추가한다.
- D. CloudWatch Logs Insights 쿼리를 대시보드에 추가한다.
- 정답: A
- 정답 근거: 사용량 지표를 `m1/SERVICE_QUOTA(m1)*100`으로 비율화해 임계 80에 경보를 걸고 SNS 주제를 지정하는 방법이 안내되며, DynamoDB는 사용량 지표를 Service Quotas와 연동하는 서비스 목록에 있다. https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-Quotas-Visualize-Alarms.html [S53]
- 오답 해설: B는 한도에 닿은 뒤의 사후 탐지이고 사전(80%) 알림이 아니다(저작자 정리). C의 어노테이션은 트레이스 검색용 데이터일 뿐 알림 수단이 아니다 [S29]. D의 대시보드는 시각화이며 알림 동작을 수행하는 것은 경보다(저작자 정리).

**문항 4** — 대응 Skill: 4.2.8 / 난이도: intermediate
- 문제: Amazon EKS의 한 서비스는 시작하는 데 수 분이 걸린다. 시작 도중 liveness 프로브가 실패해 파드가 계속 종료·교체된다. 시작이 끝난 뒤에는 기존 liveness·readiness 설정을 그대로 쓰고 싶다. 가장 적절한 조치는?
- A. startup 프로브를 추가한다.
- B. liveness 프로브를 제거하고 어떤 프로브도 정의하지 않는다.
- C. liveness 프로브를 외부 데이터베이스 연결 확인으로 바꾼다.
- D. ECS 서비스의 `healthCheckGracePeriodSeconds`를 늘린다.
- 정답: A
- 정답 근거: startup 프로브는 느리게 시작하는 앱용이며, 구성하면 시작이 성공으로 판정될 때까지 liveness·readiness 프로브가 파드를 검사하지 않는다. https://repost.aws/knowledge-center/eks-liveness-readiness-probe [S65]
- 오답 해설: B는 프로브가 없으면 kubelet이 파드를 무기한 정상으로 간주해 장애를 감지하지 못한다 [S65]. C는 liveness를 파드 밖의 외부 의존성에 묶으면 모든 파드가 동시에 실패해 앱이 내려갈 수 있다 [S66]. D는 ECS 서비스 스케줄러의 설정이며 EKS 프로브와 무관하다 [S64].

**문항 5** — 대응 Skill: 4.2.7 / 난이도: intermediate
- 문제: Node.js Lambda 함수가 `console.debug`로 상세 로그를 대량 출력해 CloudWatch Logs 비용이 늘었다. 로그 형식은 기본값이다. 코드를 바꾸지 않고 운영에서는 WARN 이상만 CloudWatch Logs로 보내려 한다. 올바른 설정은?
- A. 로그 형식을 JSON으로 바꾸고 애플리케이션 로그 수준을 WARN으로 설정한다.
- B. 로그 형식은 Text로 두고 애플리케이션 로그 수준만 WARN으로 설정한다.
- C. 로그 그룹의 보존 기간을 1일로 줄인다.
- D. 시스템 로그 수준을 DEBUG로 설정한다.
- 정답: A
- 정답 근거: 로그 수준 필터링은 JSON 로그 형식에서만 쓸 수 있고(기본 형식은 일반 텍스트), 고른 수준 이하(덜 상세한 수준)만 전송한다. https://docs.aws.amazon.com/lambda/latest/dg/monitoring-cloudwatchlogs-log-level.html [S12]
- 오답 해설: B는 일반 텍스트 형식에서는 수준 필터링이 적용되지 않는다 [S12]. C의 보존 기간은 저장 기간일 뿐 전송량을 줄이지 않는다(저작자 정리). D의 시스템 로그 수준은 Lambda 플랫폼 로그용이며 DEBUG는 오히려 더 많은 로그를 보낸다 [S12].
