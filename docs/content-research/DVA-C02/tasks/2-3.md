## 핵심 개념

### 데이터 분류와 PII·PHI (Skill 2.3.1)

- **데이터 분류**: 데이터를 중요도(criticality)와 민감도(sensitivity)로 식별·범주화해 알맞은 보호·보존 통제를 정하는 과정이다. 범주 예는 highly confidential / confidential / non-confidential / public이며 등급 이름은 조직마다 다르다. Well-Architected 보안 축 SEC 7("데이터를 어떻게 분류하는가")의 항목이다. [S1][S2]
- 분류가 끝나면 등급별 암호화 전략을 짠다(예: 최고 기밀은 비대칭 암호화, 공개 데이터는 암호화 불필요). [S1]
- **PII**: "개인의 신원을 구별하거나 추적하는 데 쓸 수 있는 정보"(이름·사회보장번호·생체 기록 등, 다른 정보와 결합해 특정 개인에 연결되는 정보 포함). **PHI**: NIST 정의로 "개인 식별 가능한 건강 정보"이며 미국 HIPAA 맥락에서 쓴다. 정의는 국가·지역마다 달라 서비스 운영 국가와 사용자 기반에 맞춰 해석한다. [S3]
- GDPR·CCPA·HIPAA 등은 소비자·환자에게 PII·PHI 처리에 대한 권리를 주므로, 분류 체계와 태깅이 있어야 열람·삭제 요청 등에 제때 대응할 수 있다. [S4]
- 발견 도구(범위 밖, 한 줄): Amazon Macie는 managed data identifiers로 S3 객체에서 자격 증명·금융 정보·PHI·PII를 탐지한다. [S5]

| 분류(예시) | 대표 데이터 | 저작 제안 — 적용 통제(공식 매핑표 아님) |
|---|---|---|
| Public | 공개 문서 | 암호화는 선택, 전송 중 TLS는 유지 |
| Internal/Confidential | 내부 운영 데이터 | SSE-KMS + IAM 최소 권한 |
| Restricted | PII·PHI·자격 증명 | 고객 관리형 키, 필드/클라이언트측 암호화, 로그 마스킹, Secrets Manager |

### 민감한 환경 변수 암호화 — Lambda 중심 (Skill 2.3.2)

- **저장 중**: Lambda는 환경 변수를 항상 KMS로 서버측 암호화한다. 기본은 AWS managed key(설정·요금 없음)이고, 키 회전 통제나 조직 요건이 있으면 고객 관리형 키를 쓴다. 고객 관리형 키를 쓰면 키 접근 권한이 있는 계정 내 사용자만 환경 변수를 보고 관리할 수 있다. [S6]
- **전송 중(콘솔 암호화 도우미)**: 콘솔의 "Enable helpers for encryption in transit"로 변수 값을 고객 관리형 키로 **클라이언트측 암호화**한다. 함수 코드가 직접 복호화하므로 실행 역할에 `kms:Decrypt` 권한이 필요하고, 복호화 때 암호화 컨텍스트로 `LambdaFunctionName`을 넘긴다. [S6][S7]
- **권한 구분**: 기본 키는 KMS 권한이 필요 없다. 고객 관리형 키는 구성 시 `kms:CreateGrant`·`kms:Encrypt`, 조회·관리 시 `kms:Decrypt`가 필요하다. `Decrypt`가 없는 사용자는 함수는 관리해도 환경 변수는 못 보며, 조회를 막으려면 `kms:Decrypt`를 Deny한다. [S6]
- **크기**: 환경 변수 객체 전체(이름·값·따옴표·쉼표·괄호 포함)가 4,096바이트를 넘을 수 없다. [S8]
- **권고**: DB 자격 증명은 환경 변수 대신 Secrets Manager를 쓰라고 안내한다. [S6]
- 원리(해석): 환경 변수 암호화는 "저장·조회 권한" 통제이며, 함수가 값을 읽어 로그·응답으로 내보내는 것까지 막지 못한다. 그래서 코드에서 값을 출력하지 않는 것과, 더 민감한 값을 시크릿 서비스로 옮기는 것이 짝으로 필요하다.
- ECS·CodeBuild·CloudFormation에서의 주입 방식은 아래 "런타임 조회·캐싱·주입" 소절에서 다룬다.

### 회전과 버전 스테이지 (Skill 2.3.3)

- **회전 방식**: ① 관리형 회전(Lambda 불필요, 관리 서비스가 만든 시크릿) ② 파트너가 보유한 managed external secrets 회전(Lambda 불필요) ③ 그 밖의 시크릿은 **Lambda 회전 함수**. [S11]
- **Lambda 회전 4단계**: 같은 함수를 단계별로 여러 번 호출한다 — `createSecret`(새 버전 생성) → `setSecret`(DB·서비스 자격 증명 변경) → `testSecret`(새 버전 시험) → `finishSecret`(마무리). 한 단계라도 실패하면 열린 회전 창 동안 전체 회전을 여러 번 재시도한다. [S12][S59]
- **일정**: `rate()`(시간·일) 또는 `cron()`, UTC 기준, 최소 4시간 간격. 회전을 설정하면 즉시 한 번 회전하고, 수동으로 값을 바꿔도 유효한 회전으로 보고 다음 회전일을 계산한다. [S13][S14][S59]
- **버전 스테이지**: `AWSCURRENT`는 항상 존재하며 기본으로 반환, `AWSPREVIOUS`는 직전, `AWSPENDING`은 회전 중. 라벨 없는 버전은 deprecated로 보고 100개를 넘으면 정리한다(생성 24시간 이내 제외). [S9]
- **RDS 연동**: `ManageMasterUserPassword`=true이면 RDS가 마스터 비밀번호를 Secrets Manager에서 수명주기 전체에 걸쳐 관리하며, KMS 키는 `MasterUserSecretKmsKeyId`로 지정한다(관리 시작 후 키 변경 불가). [S29]
- 원리(해석): 회전은 시크릿과 대상 시스템 두 곳을 함께 바꾸는 작업이라, 새 버전을 만들고 적용·시험한 뒤 마무리하는 단계로 쪼개 실패 시 재시도할 수 있게 한다. [S12]

### 런타임 조회·캐싱·주입 — Lambda·ECS·CodeBuild·CloudFormation (Skill 2.3.3, 2.3.2)

- **SDK 직접 조회**는 호출마다 비용·지연이 생기므로(시크릿당 월 요금과 별개로 API 호출 요금) 캐싱을 쓴다. [S18][S28]
- **캐싱 클라이언트**(Java 문서 기준, .NET·Go 등도 별도 문서가 있음): LRU 정책, 기본 1시간마다 갱신, 필요 권한 `secretsmanager:DescribeSecret`·`GetSecretValue`. Lambda에서는 핸들러 밖에서 캐시를 만든다. [S28]
- **Lambda 확장(AWS Parameters and Secrets Lambda Extension)**: 어떤 런타임에서도 쓰는 HTTP 인터페이스, 기본 300초 캐시·최대 1,000개, TTL은 0~300초에서 조정. [S26][S27]
- **ECS**: 작업 정의의 `secrets`로 Secrets Manager 시크릿(또는 Parameter Store 파라미터)을 컨테이너 환경 변수로 주입한다. **컨테이너가 시작될 때 1회 주입**되므로 시크릿을 갱신·회전해도 자동 반영되지 않고, 새 태스크를 시작하거나 서비스 **Force new deployment**가 필요하다. 태스크 실행 역할에 `ssm:GetParameters`·`secretsmanager:GetSecretValue`·`kms:Decrypt`가 필요하다. [S30][S31]
- **CodeBuild**: 환경 변수 `type`은 `PLAINTEXT`(기본값, 민감 값에는 강력히 비권장) / `PARAMETER_STORE` / `SECRETS_MANAGER`. buildspec `env`의 `parameter-store`·`secrets-manager`로도 정의한다. 해당 값은 빌드 로그에서 가려지지만 변환한 값(Base64 등)은 가려지지 않는다. [S32][S33]
- **CloudFormation**: 템플릿에 자격 증명을 직접 쓰지 말고 Parameter Store·Secrets Manager의 **동적 참조(dynamic references)**를 쓴다. CloudFormation은 참조된 실제 값을 저장하지 않는다. [S34]

### 민감 데이터 정제(sanitize) — 로그·API 호출·빌드 출력 (Skill 2.3.4)

- **CloudWatch Logs 데이터 보호 정책**은 로그 이벤트의 민감 데이터를 **감사(Audit)** 하고 **마스킹(Deidentify)** 한다. 정책에서 식별 대상을 managed data identifier(금융·PHI·PII 사전 정의 유형, 발표 블로그는 100개 이상으로 소개)나 사용자 정의 정규식 식별자로 지정하고, 동작(Operation)으로 Audit 또는 Deidentify를 고른다. [S35][S37][S38]
- **적용 범위**: 계정 전체 또는 개별 로그 그룹에 만들 수 있고, 둘 다 있으면 누적 적용된다. 로그 그룹당 그룹 수준 정책은 1개이며 정책 크기는 30,720자 이하. [S35][S36]
- **시점**: 수집(ingest) 시점에 탐지·마스킹하므로 **정책을 만들기 전에 이미 수집된 이벤트는 마스킹되지 않는다.** 마스킹은 Logs Insights·지표 필터·구독 필터 등 모든 출구에 적용되고, 원문은 `logs:Unmask` 권한자만 볼 수 있다. [S35][S36]
- 감사 결과는 CloudWatch Logs 그룹·Firehose·S3로 보낼 수 있고, 탐지 시 `LogEventsWithFindings` 지표가 발행된다. 감사(Audit)는 수집을 막지 않는다. [S35][S38]
- **로깅 습관**: Lambda 회전 함수의 디버그·로그 문장이 CloudWatch Logs에 남을 수 있으니 민감 정보를 넣지 않는다. Secrets Manager API는 CloudTrail에 기록되므로 요청 파라미터에 민감 정보를 넣지 않는다. [S12][S58]
- **빌드 출력**: CodeBuild는 Parameter Store·Secrets Manager 값을 로그에서 가리지만 **정확히 같은 문자열만** 가린다(변환하면 노출). [S33]
- 발견 도구(한 줄): Macie는 S3 객체, Amazon Comprehend는 텍스트의 PII를 탐지하며 PII **redaction은 비동기 배치 작업**으로만 가능하다. [S5][S39]
- 원리: 민감 데이터는 로그·지표·구독 같은 "출구"로 새는 일이 많아서, CloudWatch는 수집 시점에 마스킹하고 모든 출구에 같은 마스킹을 적용한다. [S35]

### 애플리케이션 수준 데이터 마스킹·삭제 (Skill 2.3.5)

| 기법 | 원본 복원(해석) | 설명 | AWS 예 | 출처 |
|---|---|---|---|---|
| 삭제·가림(redact) | 불가 | 값을 제거하거나 기호·엔터티 유형으로 대체 | Comprehend redaction(엔터티 유형 또는 문자로 대체), DataBrew redact·substitute·hash | [S39][S41] |
| 토큰화 | 토큰 볼트가 있으면 가능 | 민감 값을 무의미한 토큰으로 바꾸고 원본과의 관계는 별도 저장 | 토큰 생성 API + (선택) 조회 API로 구성한 토큰화 서비스 | [S40] |
| 필드(속성) 암호화 | 키가 있으면 가능 | 필요한 필드만 암호화·서명 | DB-ESDK(`ENCRYPT_AND_SIGN`/`SIGN_ONLY`/`DO_NOTHING`), CloudFront 필드 수준 암호화 | [S42][S43][S44] |

- **토큰화 vs 암호화**: 토큰화는 컴플라이언스 범위 축소·형식/분석 속성 유지·키 관리 부담 감소에 유리하고, 암호화는 대용량·비정형 데이터나 제3자에게 원본 값을 공유해야 할 때 낫다. 토큰화는 토큰 생성 API 1개와 선택적 조회 API 1개만으로 단순하다. [S40]
- **DB-ESDK(DynamoDB)**: 속성 값을 암호화하고 서명한다. 암호화 대상은 `ENCRYPT_AND_SIGN`, 서명만은 `SIGN_ONLY`, 처리 없음은 `DO_NOTHING`이며 **파티션 키·정렬 키는 항상 `SIGN_ONLY`**(기본 키는 평문). [S42][S43]
- **CloudFront 필드 수준 암호화**: POST 요청의 지정한 필드를 엣지에서 **RSA 공개 키**로 암호화해 오리진·내부 시스템을 지나도 암호화 상태를 유지한다(최대 10필드·필드당 16 KB·요청 본문 1 MB, RSA 2048비트, 오리진은 청크 인코딩 지원 필요). CloudFront가 가진 공개 키로는 복호화할 수 없고 개인 키 보유 컴포넌트만 복호화한다. [S44][S45]
- **마스킹은 fail-closed로**: Powertools for AWS Lambda(Python) 데이터 마스킹 유틸리티의 fail-open 처리 오류(CVE-2026-104002, 영향 3.6.0~3.34.0)가 공지됐고 3.35.0은 마스킹 오류 시 `DataMaskingError`를 던진다. 마스킹이 실패하면 원본을 돌려주지 말고 예외로 멈춰야 한다. [S46]
- 선택 기준: 원본이 나중에 필요 → 암호화·토큰화 / 영구히 불필요 → 삭제·가림 / 형식·분석 유지 → 토큰화.
- 원리: 필드 수준 암호화는 "복호화 권한(개인 키) 보유자"를 분리하고, 삭제·가림은 복원 가능성 자체를 없애며, 토큰화는 원본↔토큰 관계를 별도 저장소에 가둔다. [S40][S44]

### 멀티테넌트 애플리케이션의 데이터 접근 패턴 (Skill 2.3.6)

| 모델 | 구조 | 장점 | 단점 | 출처 |
|---|---|---|---|---|
| Silo | 테넌트별 별도 DB 인스턴스(인프라) | 격리 최대 | 비용·테넌트 온보딩 복잡 | [S47] |
| Pool | 공유 인스턴스·공유 네임스페이스, 테이블에 테넌트 ID 같은 파티션 키 | 운영 비용 최저 | 데이터 접근 정책 강제가 어려움(WHERE 절 누락 위험) | [S47] |
| Bridge | silo와 pool의 혼합(예: 같은 인스턴스에 테넌트별 스키마·테이블) | 일부 격리 + 공유 | 유지보수·설정 복잡 | [S47][S48] |

- **IAM 격리 방법 3가지**: RBAC(테넌트마다 전용 역할 → 역할 수 = 역할 정의 수 × 테넌트 수) / 동적 생성 IAM 정책 / **ABAC**(속성으로 접근 제어, 단일 역할로 임의 개수 테넌트 지원). [S49]
- **ABAC 흐름**: JWT의 `TenantID` 클레임 → 서비스가 `sts:AssumeRole` 때 **세션 태그**(`Tags=[TenantID]`)를 전달 → 역할 신뢰 정책에 `sts:TagSession` 허용 → 접근 정책에서 `${aws:PrincipalTag/TenantID}` 변수로 범위 지정. 세션 태그는 세션 요청 때 지정하는 principal 태그다. [S49]
- **DynamoDB(풀)**: 테넌트 ID를 파티션 키로 두고 `ForAllValues:StringEquals`의 `dynamodb:LeadingKeys`를 `${aws:PrincipalTag/TenantID}`로 지정해 해당 파티션 키 항목만 허용한다. 정책이 특정 테넌트에 묶이지 않아 신규 테넌트에 IAM 변경이 필요 없다. 보조 인덱스도 정책 리소스에 추가해야 한다. [S49][S50][S51]
- **S3(prefix-per-tenant) + 테넌트별 KMS 키**: 객체 키 prefix를 `${aws:PrincipalTag/TenantID}/*`로 제한하고, KMS 키에 `TenantID` 리소스 태그를 붙여 `aws:PrincipalTag/TenantID`와 `aws:ResourceTag/TenantID`가 같을 때만 `kms:Decrypt`를 허용한다. 한계: 테넌트별 고객 관리형 키를 쓰면 Region당 KMS 키 수(기본 100,000개, 조정 가능)에 묶인다. [S49][S54][S57]
- **테넌트별 KMS 키 전략**: 키는 월 $1이고 회전이 쌓이면 최대 월 $3다. 중앙 계정이 테넌트당 고객 관리형 키 1개를 관리하고 별칭 `alias/customer-<tenant-id>`로 구분하며, 호출 서비스는 역할 위임 + 세션 정책으로 해당 별칭만 쓰게 한다. DB-ESDK의 계층형(Hierarchical) 키링은 레코드마다 KMS를 호출하지 않고도 암호화 재료를 보호한다. [S52][S53]
- **애플리케이션 로직만 믿지 않기**: 쿼리 필터만으로 격리하면 설정 실수 한 번에 새 나갈 수 있어, DynamoDB 테이블에 IAM 정책으로 최소 권한 가드레일을 더한다. [S51]
- **계산·큐 계층(데이터 접근과 별개 축)**: Lambda **tenant isolation mode**(2025-11 발표)는 테넌트 ID별로 실행 환경을 분리하며 함수 생성 때만 설정할 수 있다. SQS **fair queues**(2025-07 발표)는 표준 큐에서 message group ID로 noisy neighbor를 완화한다. [S55][S56][S60]
- 원리: 풀 모델은 "정책으로 강제"해야 안전하고, ABAC는 역할 수를 테넌트 수와 분리해 준다. 키 격리(테넌트별 KMS 키)는 암호학적 격리를 더하지만 키 수·비용과 교환 관계다. [S49][S52]

## 시험에서 묻는 방식

(문제 저작자를 위한 제안이다. 시험이 반드시 이렇게 낸다는 단정이 아니다.)

1. **시크릿 저장소 선택·회전**: "Lambda 환경 변수에 평문으로 넣은 DB 비밀번호를 30일마다 자동으로 교체하고 코드 변경은 최소화해야 한다." → 단서: "자동 회전" ⇒ **Secrets Manager**(관리형 회전 또는 Lambda 회전 함수, `AWSCURRENT`), 호출 비용·지연 ⇒ **캐싱 클라이언트·Lambda 확장**. "단순 설정값·무료·4 KB 이하" ⇒ Parameter Store 표준 티어. [S11][S25][S26][S28]
2. **ECS 시크릿 반영**: "Fargate 태스크에 `secrets`로 주입한 값을 회전했는데 컨테이너가 옛 값을 쓴다." → 단서: "컨테이너 시작 시 1회 주입" ⇒ 새 태스크 시작 또는 **Force new deployment**, 태스크 **실행 역할**에 `secretsmanager:GetSecretValue`·`kms:Decrypt`. [S30][S31]
3. **로그의 민감 정보**: "애플리케이션 로그에 신용카드 번호가 평문으로 남는다. 코드를 고치지 않고 기록 시점에 가리고 싶다." → 단서: "수집 시점·앱 수정 없음" ⇒ **CloudWatch Logs 데이터 보호 정책**(managed data identifier + Deidentify), 원문은 `logs:Unmask` 최소 권한, 정책 이전 로그는 마스킹 안 됨. [S35][S36][S38]
4. **멀티테넌트 격리**: "단일 DynamoDB 테이블에 모든 테넌트 데이터를 저장하며 하나의 IAM 역할로 각 테넌트가 자기 항목만 접근해야 한다." → 단서: "테넌트 수와 무관한 단일 역할" ⇒ **ABAC**(세션 태그 `TenantID` + `dynamodb:LeadingKeys`가 `${aws:PrincipalTag/TenantID}`), 테넌트별 암호화 분리가 필요하면 테넌트별 KMS 키. [S49][S50][S52]

## 흔한 함정·혼동 짝

| A vs B | 혼동 이유 | 구분 기준 한 줄 | 출처 |
|---|---|---|---|
| Secrets Manager vs Parameter Store `SecureString` | 둘 다 KMS로 암호화해 시크릿을 저장 | 자동 회전·버전 라벨·Region 복제는 Secrets Manager(유료), 단순 보관·표준 티어 무료는 Parameter Store | [S25][S9][S18][S24] |
| Parameter Store 표준 vs 고급 티어 | 같은 서비스의 두 티어 | 표준=4 KB·10,000개·무료·정책 불가, 고급=8 KB·100,000개·유료·정책·교차 계정 공유 가능 | [S20][S23] |
| Lambda 환경 변수 서버측 암호화 vs 암호화 도우미 | 둘 다 "환경 변수 암호화" | 서버측=항상 적용(저장 중, 기본 키), 도우미=선택·클라이언트측(전송 중)이며 코드에서 `kms:Decrypt` 필요 | [S6] |
| `AWSCURRENT` vs `AWSPREVIOUS` vs `AWSPENDING` | 라벨 이름이 비슷 | CURRENT=기본 반환, PREVIOUS=직전 버전, PENDING=회전 중인 버전 | [S9] |
| ECS 시작 시 주입 vs 실시간 갱신 | 시크릿을 바꾸면 컨테이너에 반영된다고 착각 | 시작 때 1회 주입 → 새 태스크 또는 Force new deployment 필요 | [S30] |
| CodeBuild `PLAINTEXT` vs `SECRETS_MANAGER`·`PARAMETER_STORE` | 환경 변수 기본 타입이 PLAINTEXT | PLAINTEXT는 콘솔·CLI에 평문 노출 → 민감 값은 시크릿 타입 | [S32] |
| CloudWatch Logs 데이터 보호 정책 vs Amazon Macie | 둘 다 민감 데이터를 찾는다 | 데이터 보호 정책=로그 **수집 시점** 감사·마스킹(정책 이전 이벤트는 소급 안 됨), Macie=S3 객체 분석(범위 밖) | [S35][S5] |
| 삭제·가림 vs 암호화 vs 토큰화 | 모두 "민감 데이터 보호" | 삭제·가림=복원 불가(해석), 암호화=키로 복원, 토큰화=토큰 볼트로 복원·형식 유지 | [S39][S40] |
| DB-ESDK vs CloudFront 필드 수준 암호화 | 둘 다 "필드 단위 암호화" | DB-ESDK=애플리케이션이 DynamoDB 속성을 암호화, FLE=엣지가 POST 필드를 RSA 공개 키로 암호화 | [S42][S44] |
| Silo vs Pool vs Bridge | 모델 이름이 추상적 | silo=테넌트별 인프라, pool=공유 인프라+파티션 키, bridge=혼합(공유 인스턴스+테넌트별 스키마·테이블) | [S47][S48] |
| RBAC vs ABAC(세션 태그) | 둘 다 IAM 기반 테넌트 격리 | RBAC=테넌트마다 역할(역할 수 증가), ABAC=단일 역할+`aws:PrincipalTag` | [S49] |
| Lambda tenant isolation mode vs `dynamodb:LeadingKeys` vs SQS fair queues | 모두 "멀티테넌트 기능" | 계산 환경 분리 / 데이터 항목 접근 통제 / 큐 처리 공정성(noisy neighbor) — 계층이 다르다 | [S55][S50][S56] |

## 자가 점검 문항 후보

**문항 1** — 대응 Skill 2.3.2 · 난이도 intermediate
- 문제: 개발자 IAM 그룹이 Lambda 콘솔에서 함수의 환경 변수 값을 볼 수 없어야 하지만 함수 설정 관리는 계속 할 수 있어야 한다. 해당 함수의 환경 변수는 기본 설정(AWS managed key)으로 암호화돼 있다. 가장 적절한 조치는?
- 보기: A. 환경 변수는 이미 서버측 암호화돼 있으므로 추가 조치가 필요 없다. / B. 개발자 IAM 정책에 해당 키(기본 키 포함)에 대한 `kms:Decrypt`를 Deny하는 문장을 추가한다. / C. 환경 변수 값을 Base64로 인코딩해 저장한다. / D. 함수 실행 역할에서 `kms:Decrypt` 권한을 제거한다.
- 정답: B
- 정답 근거: `Decrypt` 권한이 없는 사용자는 함수는 관리해도 환경 변수는 볼 수 없으며, 조회를 막으려면 기본 키·고객 관리형 키·모든 키에 대한 접근을 Deny하는 문장을 사용자 권한에 추가한다. 근거: https://docs.aws.amazon.com/lambda/latest/dg/configuration-envvars-encryption.html
- 오답 해설: A — 기본 키는 사용자에게 별도 KMS 권한이 필요 없어 그대로 조회된다. C — Base64는 인코딩이지 접근 통제가 아니다. D — 실행 역할은 함수가 쓰는 주체의 권한이며 콘솔에서 값을 보는 개발자 사용자의 권한이 아니다.

**문항 2** — 대응 Skill 2.3.3 · 난이도 intermediate
- 문제: 회사는 RDS 데이터베이스 자격 증명을 30일마다 자동으로 교체하길 원한다. 이 자격 증명을 Lambda 함수가 호출마다 읽으므로 API 호출 비용도 줄여야 한다. 가장 적절한 구성은?
- 보기: A. 자격 증명을 Parameter Store의 `String` 파라미터에 저장하고 Lambda가 매번 조회한다. / B. Secrets Manager 시크릿에 자동 회전을 설정하고 Lambda에서 Parameters and Secrets Lambda 확장 같은 캐싱을 사용한다. / C. Lambda 환경 변수에 저장하고 30일마다 배포 파이프라인이 값을 바꾼다. / D. 자격 증명을 암호화해 S3 객체로 두고 Lambda가 호출마다 `GetObject`한다.
- 정답: B
- 정답 근거: 자동 회전이 이득인 시크릿은 Secrets Manager를 쓰도록 안내하며, Lambda 확장은 기본 300초 동안 시크릿을 캐시해 호출 횟수를 줄인다. 근거: https://docs.aws.amazon.com/prescriptive-guidance/latest/aws-startup-security-baseline/wkld-03.html , https://docs.aws.amazon.com/lambda/latest/dg/with-secrets-manager.html
- 오답 해설: A — `String` 타입은 KMS 암호화 대상이 아니고(`SecureString`만 값이 암호화됨) 자동 회전은 Secrets Manager 쪽 기능으로 안내된다. C — 환경 변수는 4 KB 한도가 있고 배포로 값을 바꾸는 것은 대상 DB와 맞춰 주는 자동 회전이 아니다. D — 회전·캐싱을 직접 구현해야 하며 시크릿 관리 서비스를 쓰는 요건에서 벗어난다.

**문항 3** — 대응 Skill 2.3.3 · 난이도 intermediate
- 문제: Fargate 서비스의 작업 정의가 `secrets`로 Secrets Manager 시크릿을 컨테이너 환경 변수로 주입한다. 시크릿이 회전된 뒤에도 실행 중인 컨테이너는 이전 값을 쓴다. 새 값을 적용하는 가장 적절한 조치는?
- 보기: A. 태스크 역할에 `secretsmanager:GetSecretValue`를 추가한다. / B. 서비스를 업데이트하면서 Force new deployment로 새 태스크를 시작한다. / C. 시크릿의 `AWSPREVIOUS` 라벨을 최신 버전으로 옮긴다. / D. 환경 변수 갱신 주기(TTL)를 1분으로 설정한다.
- 정답: B
- 정답 근거: 시크릿은 컨테이너가 처음 시작될 때 주입되므로 갱신·회전 후 자동으로 반영되지 않으며, 새 태스크를 시작하거나 서비스에서 Force new deployment를 해야 한다. 근거: https://docs.aws.amazon.com/AmazonECS/latest/developerguide/secrets-envvar-secrets-manager.html
- 오답 해설: A — 주입에는 태스크 실행 역할이 쓰이고 이미 주입에 성공한 상황이라 권한 문제가 아니다. C — 라벨 이동은 새로 시작하는 태스크가 받을 버전에 영향을 줄 뿐 실행 중 컨테이너의 값은 바꾸지 못한다. D — 환경 변수는 시작 시 주입되는 값이며 TTL로 다시 읽는 구성이 없다.

**문항 4** — 대응 Skill 2.3.4 · 난이도 intermediate
- 문제: 결제 서비스의 Lambda 로그에 신용카드 번호가 평문으로 기록된다. 코드를 바꾸지 않고, 앞으로 수집되는 로그에서 카드 번호가 가려지게 하며 보안팀만 원문을 볼 수 있게 하려 한다. 가장 적절한 방법은?
- 보기: A. 로그 그룹에 CloudWatch Logs 데이터 보호 정책(managed data identifier로 카드 번호 마스킹)을 만들고 `logs:Unmask`를 보안팀에만 허용한다. / B. 로그를 S3로 내보낸 뒤 Amazon Macie로 분석한다. / C. 로그 그룹 보존 기간을 1일로 줄인다. / D. Lambda 실행 역할에서 `logs:PutLogEvents` 권한을 제거한다.
- 정답: A
- 정답 근거: 데이터 보호 정책은 수집 시점에 민감 데이터를 감지·마스킹하고, `logs:Unmask` 권한이 있는 사용자만 원문을 볼 수 있다. 근거: https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/mask-sensitive-log-data.html
- 오답 해설: B — Macie는 S3 객체에서 민감 데이터를 탐지하는 서비스이며 수집 시점에 마스킹하지 않는다. C — 보존 기간 단축은 마스킹이 아니어서 기간 내 평문 노출이 그대로 남는다. D — 로그 기록 자체가 중단되어 관측성을 잃고 요구와도 맞지 않는다.

**문항 5** — 대응 Skill 2.3.6 · 난이도 advanced
- 문제: SaaS 애플리케이션이 단일 DynamoDB 테이블(파티션 키=테넌트 ID)에 모든 테넌트 데이터를 저장한다. 서비스는 사용자 JWT의 `TenantID` 클레임을 읽는다. 테넌트가 늘어도 IAM 역할·정책을 추가하지 않고 각 요청이 자기 테넌트 항목만 접근하게 하려면?
- 보기: A. 테넌트마다 IAM 역할과 정책을 만들어 전환한다. / B. `sts:AssumeRole` 호출 때 `TenantID` 세션 태그를 전달하고, 단일 역할 정책에서 `dynamodb:LeadingKeys` 조건 값을 `${aws:PrincipalTag/TenantID}`로 지정한다. / C. 애플리케이션 코드에서 조회 결과를 `TenantID`로 필터링하고 역할은 테이블 전체 접근을 허용한다. / D. 테넌트마다 별도 DynamoDB 테이블을 만들고 테이블 ARN별 정책을 작성한다.
- 정답: B
- 정답 근거: ABAC는 세션 태그와 `aws:PrincipalTag`로 단일 역할이 임의 개수의 테넌트를 지원하며, `dynamodb:LeadingKeys`로 해당 파티션 키 항목만 허용한다. 근거: https://aws.amazon.com/blogs/security/how-to-implement-saas-tenant-isolation-with-abac-and-aws-iam/ , https://repost.aws/knowledge-center/dynamodb-table-restrict-attributes
- 오답 해설: A — RBAC는 테넌트 수만큼 역할이 늘어 요구("추가하지 않고")에 맞지 않는다. C — 쿼리 필터만으로는 설정 실수 한 번에 격리가 깨지므로 IAM 정책 가드레일이 권장된다. D — silo 모델이라 테이블과 정책이 테넌트 수에 따라 늘어난다.
