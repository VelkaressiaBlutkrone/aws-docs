### 파티션 키와 균형 잡힌 파티션 액세스 — 높은 카디널리티 (Skill 1.3.1)

- 파티션 키 값은 DynamoDB 내부 해시 함수의 입력이고, 출력이 항목이 저장될 파티션(내부 물리 저장소)을 정한다. 같은 파티션 키 값의 항목은 한곳에 정렬 키 순으로 저장된다 [S6].
- 파티션 하나는 읽기 최대 3,000 read units/s, 쓰기 최대 1,000 write units/s를 처리하도록 설계돼 있다. 항목이 크면 읽기 1회가 여러 단위를 쓰므로 한 항목에 동시에 보낼 수 있는 요청 수가 준다(예: 20 KB 항목의 일관된 읽기 = 5 read units → 초당 600회) [S1].
- **원리**: 테이블 총 용량이 남아도 요청이 소수의 파티션 키 값에 몰리면 그 파티션의 상한에서 스로틀된다. 접근하는 고유 파티션 키 값이 많을수록(높은 카디널리티·균등 분포) 요청이 넓게 퍼져 프로비저닝 처리량을 효율적으로 쓴다 [S2]. 높은 카디널리티 키를 고르면 자주 접근하는 항목이 같은 파티션에 몰리지 않아 핫 파티션을 피한다 [S10].

| 파티션 키 후보 | 균등성 | 판단 근거 [S2] |
|---|---|---|
| 사용자 ID(사용자가 많음) | 좋음 | 고유 값이 많고 분산됨 |
| 상태 코드(가능한 값이 몇 개뿐) | 나쁨 | 고유 값이 적어 한 키로 쏠림 |
| 생성일(일·시·분 단위로 반올림) | 나쁨 | 같은 기간의 모든 새 항목이 한 키로 감 |
| 디바이스 ID(접근 간격이 비슷) | 좋음 | 접근이 고르게 분산됨 |
| 디바이스 ID(많아도 하나가 압도적 인기) | 나쁨 | 인기 디바이스 키에 쏠림 |

- 쓰기 샤딩(write sharding) [S3]: ① 랜덤 접미사 — 날짜 키 뒤에 1~200 난수를 붙여(`2014-07-09.1` … `.200`) 쓰기를 분산한다. 읽을 때는 모든 접미사를 Query해 앱이 병합해야 한다. ② 계산 접미사 — OrderId 같은 조회 값으로 해시를 계산해 접미사로 붙인다 → 특정 항목은 GetItem이 가능하지만, 하루치 전체 조회는 여전히 모든 접미사를 Query해 병합해야 한다.
- 완충 장치(근본 해법은 아님): 적응형 용량은 모든 테이블에 자동·무료로 켜져 있고, 트래픽이 테이블 총 프로비저닝이나 파티션 최대 용량을 넘지 않는 한 핫 파티션을 스로틀 없이 처리한다 [S4]. 버스트 용량은 미사용 용량을 최대 300초 분량 best-effort로 보관할 뿐 파티션 수준 스로틀은 막지 못한다 [S5]. 읽기 쏠림(인기 키)은 DAX가 흡수할 수 있다 [S41].
- GSI에서는 멀티 속성 파티션 키가 분포·고유성을 높인다 [S59] (Skill 1.3.4).

### 일관성 모델 — 최종적 일관성 vs 강력한 일관성 (Skill 1.3.2)

| 읽기 대상 | 최종적 일관성 | 강력한 일관성 |
|---|---|---|
| 테이블 | 지원(기본값) | 지원 — `ConsistentRead=true` [S11] |
| LSI | 지원 | 지원 [S11] |
| GSI | 지원(유일) | 불가 — `ConsistentRead=true`로 Query하면 `ValidationException` [S11][S13] |
| DynamoDB Streams | 지원(유일) | 불가 [S11] |
| 글로벌 테이블 | MREC(기본): 보통 1초 내 비동기 복제, Region 간 최종적 일관 | MRSC: 동기 복제, 어느 복제본에서든 최신 값 읽기 [S11][S15] |
| DAX 캐시 | 히트 시 캐시 값(최종적 일관 데이터) | `ConsistentRead=true`는 DynamoDB로 패스스루, 캐시 안 함 [S42][S43] |

- 쓰기가 HTTP 200으로 성공하면 내구성 있게 저장된 것이다. DynamoDB는 read-committed 격리를 제공해 커밋된 값만 읽히지만, 읽은 직후의 수정까지 막지는 않는다 [S11].
- 최종적 일관성 읽기는 방금 쓴 값을 못 볼 수 있고 잠시 뒤 재시도하면 최신 값이 보인다. 강력한 일관성 읽기는 지연이 더 클 수 있고 처리량을 2배 쓴다(비용 2배) [S12]. **원리**: 쓰기가 모든 저장 위치에 전파되는 데 시간이 걸린다(보통 수 초 내 일치) [S43].
- `GetItem`·`Query`·`Scan`에 `ConsistentRead` 옵션이 있다. `Scan`도 기본은 최종적 일관성이며 `ConsistentRead=true`면 RCU를 2배 소모한다 [S11][S18]. 트랜잭션 읽기는 4 KB당 2 read units를 쓴다 [S24].
- GSI는 베이스 테이블 변경을 비동기로 반영하며 보통 1초 미만이지만 드물게 더 길어질 수 있어 앱이 오래된 결과를 가정해야 한다 [S8]. **원리**: GSI는 베이스 테이블과 별도 파티션 공간에 저장되고 따로 확장된다 [S7].
- 글로벌 테이블: MREC는 last writer wins로 동시 갱신을 수렴시킨다 [S14]. MRSC(2025-06 GA)는 쓰기가 다른 Region에 동기 복제된 뒤 반환되고, 정확히 3개 Region(복제 3개 또는 복제 2개 + witness)으로 구성하며, 트랜잭션 API·TTL·LSI는 지원하지 않고, 다른 Region에서 같은 항목을 동시에 수정하면 `ReplicatedWriteConflictException`이 날 수 있다 [S15][S61]. 일관성 모드는 생성 시 정하며(미지정 시 MREC) 이후 바꿀 수 없다 [S15].
- DAX: 캐시된 항목은 TTL이 지나기 전에는 DAX를 우회해 DynamoDB에 직접 쓴 값과 다를 수 있다. DAX는 DynamoDB와 느슨하게 결합돼 있어 강력한 일관성 읽기를 자체 처리하지 못한다 [S43].

### Query와 Scan의 차이 (Skill 1.3.3)

| 구분 | GetItem | Query | Scan |
|---|---|---|---|
| 필요한 입력 | 전체 기본 키(PK[+SK]) [S26] | PK 동등 조건 필수, SK 조건 선택 [S16] | 없음(전체 읽기) [S18] |
| 읽는 범위 | 항목 1개(테이블 대상, GSI에는 사용 불가) [S8] | 같은 PK 값의 항목들(테이블·LSI·GSI) [S7] | 테이블 또는 인덱스의 모든 항목 [S18] |
| 결과 순서 | — | 항상 SK 순(기본 오름차순, `ScanIndexForward=false`면 역순) [S16] | PK 값 간은 임의 순서, 같은 PK 안은 SK 오름차순 [S18] |
| 1회 응답 한도 | — | 1 MB(필터·프로젝션 적용 전) [S16] | 1 MB(필터 적용 전) [S18] |
| 필터 | — | FilterExpression(PK·SK 속성 사용 불가) [S17] | FilterExpression(키 속성도 사용 가능) [S18] |
| RCU 계산 | 항목 크기를 4 KB로 올림 [S24] | 읽은(필터 전) 항목 크기의 합을 한 번에 4 KB로 올림 [S24][S17] | 평가한(읽은) 항목 크기 기준 [S24] |

- Query의 키 조건에는 비키 속성을 쓸 수 없고, SK 조건 연산자는 `=`·`<`·`<=`·`>`·`>=`·`BETWEEN`·`begins_with`다 [S16].
- **FilterExpression은 읽은 뒤에 적용된다**: 소모 RCU는 필터 유무와 같고 1 MB 한도도 필터 전에 적용된다. 필터는 "덜 돌려받게" 할 뿐 "덜 읽게" 하지 않는다 [S17][S18]. 많이 읽어 대부분 버리는 Query는 피하라고 권고한다 [S17].
- 페이지네이션: 응답에 `LastEvaluatedKey`가 있으면 그 값을 다음 요청의 `ExclusiveStartKey`로 넣어 반복하며, `LastEvaluatedKey`가 없을 때만 끝이다 [S18]. `Limit`은 필터 적용 전에 평가할 최대 항목 수라 필터 후 결과는 `Limit`보다 적을 수 있다 [S18]. `ScannedCount`(필터 전)가 `Count`(필터 후)보다 훨씬 크면 비효율적 Scan 신호다 [S18].
- 병렬 Scan: 워커마다 `Segment`(0부터)와 `TotalSegments`를 지정해 구간을 나눠 읽는다. 순차 Scan은 한 번에 한 파티션만 읽어 처리량이 단일 파티션 최대치에 묶이기 때문이다. 다만 프로비저닝 처리량을 모두 소모할 수 있어 `Limit`으로 조절하고, PK가 고르지 않으면 세그먼트를 늘려도 빨라지지 않을 수 있다 [S18].
- 읽기 단위 계산: 프로젝션을 써도 크기 계산은 그대로이고, 존재하지 않는 항목을 읽어도 소모된다. `BatchGetItem`은 항목별로 4 KB 올림 후 합산한다 [S24].
- **원리**: Query는 PK 해시로 한 파티션 안의 정렬된 구간만 읽는다 [S16]. Scan은 모든 항목을 읽으므로 테이블이 커질수록 느려지고 비싸진다 [S8].
- 대안: 키를 아는 여러 항목 → `BatchGetItem`(Skill 1.3.6), 다른 속성으로 조회 → GSI/LSI(Skill 1.3.4).

### DynamoDB 키와 인덱싱 (Skill 1.3.4)

- 기본 키는 두 종류다. ① 단순 키(파티션 키만, "해시 속성") ② 복합 키(파티션 키 + 정렬 키, "범위 속성") — 복합 키에서는 같은 파티션 키 값의 항목이 여럿이어도 정렬 키 값이 서로 달라야 한다. 키 속성 타입은 문자열·숫자·이진만 가능하다 [S6]. 값 길이 한도는 파티션 키 2048 B, 정렬 키 1024 B다 [S35].
- 보조 인덱스는 대체 키로 Query할 수 있게 해 주고, DynamoDB가 자동으로 유지한다. 인덱스에는 베이스 테이블 키·인덱스 키·투영 속성이 복사된다 [S7].

| 특성 | GSI | LSI |
|---|---|---|
| 키 구성 | 단순 또는 복합, 베이스 테이블의 임의 S/N/B 속성 | 반드시 복합: PK는 베이스 테이블과 동일, SK만 다른 속성 |
| 생성 시점 | 테이블 생성 시 또는 이후 추가·삭제 가능 | 테이블 생성 시에만(추가·삭제 불가) |
| 쿼리 범위 | 전체 테이블(모든 파티션) | 쿼리에 지정한 PK 값의 단일 파티션 |
| 읽기 일관성 | 최종적 일관성만 | 최종적 또는 강력 선택 |
| 처리량 | 인덱스 자체 RCU/WCU(쿼리·인덱스 갱신 모두 인덱스 용량 소모) | 베이스 테이블 용량 사용 |
| 크기 제한 | 없음 | PK 값당 인덱싱 항목 총합 10 GB 이하 |
| 투영 밖 속성 | 요청 불가(베이스 테이블에서 안 가져옴) | 요청하면 DynamoDB가 테이블에서 가져옴 |
| 테이블당 개수 | 기본 20 [S20] | 5 [S20] |

(표의 GSI/LSI 비교는 [S7])

- 투영(projection): `KEYS_ONLY`(가장 작음) / `INCLUDE`(지정 속성 추가) / `ALL`(가장 큼). 필요한 속성만 투영하면 저장·쓰기 비용이 줄고, 자주 쓰는 속성을 빼면 베이스 테이블을 추가 조회해야 한다 [S8]. `INCLUDE` 투영 속성은 테이블의 모든 인덱스 합쳐 최대 100개이며 같은 속성을 두 인덱스에 넣으면 2개로 센다 [S19].
- 희소 인덱스: GSI는 자신의 키 속성이 존재하는 항목만 담는다. GSI 키 값은 유일할 필요가 없다 [S8].
- GSI 주의: ① `GetItem`·`BatchGetItem` 불가(Query·Scan만) ② 프로비저닝 테이블에서 GSI 쓰기 용량이 부족하면 베이스 테이블 쓰기가 스로틀되므로 GSI 쓰기 용량은 베이스 테이블 이상으로 ③ 키 속성 타입이 인덱스 정의와 다르면 `ValidationException` ④ GSI는 베이스 테이블의 용량 모드·테이블 클래스를 따른다 [S8].
- LSI 주의: 같은 PK의 항목 컬렉션(테이블 + 투영된 LSI 항목)이 10 GB를 넘으면 `ItemCollectionSizeLimitExceededException`이 난다 [S19][S29]. LSI가 있는 테이블은 항목 데이터와 모든 LSI 항목의 합도 400 KB 이하여야 한다 [S19]. **원리**: LSI 항목은 베이스 테이블 항목과 같은 파티션에 함께 저장되고 PK를 공유하므로, 항목 컬렉션이 여러 파티션으로 나뉘지 못해 10 GB 한도가 생긴다 [S19].
- **멀티 속성 키(2025-11)**: GSI 키를 PK 최대 4개 + SK 최대 4개 속성(총 8개)으로 구성할 수 있어 합성 키 문자열이 필요 없다. PK 속성은 모두 동등 조건으로 지정하고, SK 속성은 왼쪽부터 순서대로만 조건을 줄 수 있으며(중간 건너뛰기 불가), 부등호·`begins_with`는 마지막 조건이어야 한다 [S8][S59]. 가이드 v2.1(2024-12)보다 늦은 기능이라 시험은 고전 모델(PK+SK)을 전제할 가능성이 높다(`확인 필요`).
- 설계 원칙: 데이터 크기·형태·속도 같은 접근 패턴을 먼저 정하고, 관련 데이터를 함께 두고, 정렬 순서를 활용하고, 질의를 분산하고, 필요한 질의마다 GSI를 만든다 [S9]. 테이블 수에 대한 강조점은 문서마다 다르다(`확인 필요`) [S9][S72].

### 직렬화·역직렬화로 데이터 스토어에 지속성 제공 (Skill 1.3.5)

| 분류 | 타입(저수준 API 기술자) | 비고 [S35] |
|---|---|---|
| 스칼라 | 문자열 `S`, 숫자 `N`, 이진 `B`, 불리언 `BOOL`, 널 `NULL` | 숫자는 네트워크에서 문자열로 전송·정밀도 38자리, 이진은 base64로 인코딩해 전송 |
| 문서 | 리스트 `L`, 맵 `M` | 중첩 32단계까지 [S19], 요소 타입 혼합 가능 |
| 세트 | `SS`, `NS`, `BS` | 같은 타입만, 값은 유일하고 순서 보존 안 됨, 빈 세트 불가 |

- DynamoDB는 스키마리스지만 속성마다 타입이 있어, 저수준 API는 타입 기술자 토큰으로 해석 방법을 알려 준다 [S35]. 표준 JSON `{"mykey":"v"}`은 DynamoDB JSON `{"mykey":{"S":"v"}}`로 표현된다 [S37].
- 저수준 클라이언트는 DynamoDB JSON을 그대로 다루고 전체 API(`ExportTableToPointInTime`·`ImportTable`·PartiQL 포함)를 제공한다. 고수준 클라이언트(Node.js `DynamoDBDocumentClient`, Boto3 `resource`)는 타입 주석을 숨기고 네이티브 값으로 변환한다. 변환 유틸은 Node.js `marshall`/`unmarshall`, Boto3 `serialize`/`deserialize`다. Boto3 resource 인스턴스는 스레드 안전하지 않다 [S37].
- Boto3 Table 리소스 타입 매핑: `str`→S, `int`/`decimal.Decimal`→N, `boto3.dynamodb.types.Binary`→B, `bool`→BOOL, `None`→NULL, set→SS/NS/BS, list→L, dict→M. 유효 타입 표에 float은 없다(`확인 필요`) [S38].
- Java: Enhanced Client가 자바 속성을 DynamoDB 속성 타입으로 변환한다(`@DynamoDbBean`, 기본 변환기, 미지원 타입은 `AttributeConverter` 구현). 속성 타입은 원시형이 아닌 객체형(`Long`, `Integer`)을 써야 한다 [S39].
- 날짜·시간은 전용 타입이 없다 → ISO 8601 문자열(읽기 쉬움) 또는 에포크 초 숫자(저장 공간이 적고 TTL에 사용 가능) [S35][S40].
- 400 KB 초과 데이터: 큰 속성을 압축하거나, 여러 항목으로 쪼개 정렬 키로 색인하거나, S3에 객체로 저장하고 S3 식별자를 항목에 저장한다 [S34]. S3에는 직렬화한 항목을 JSON으로 저장하고, 키·인덱스에 쓰는 속성과 `S3Location` 속성은 테이블에 두며, 앱이 `S3Location`을 확인해 S3에서 전체 데이터를 가져오는 로직을 가져야 한다 [S10].
- SDK가 요청 파라미터 직렬화·서명·응답 추출·기본 재시도를 대신한다 [S36]. 전송되는 DynamoDB JSON 표현은 저장 크기(400 KB)보다 클 수 있어 `BatchWriteItem`은 전송 데이터 16 MB 한도를 따로 갖는다 [S25].
- **원리**: 항목마다 속성 구성이 다르고 타입이 있는 저장소라 전송 시 타입 태그가 필요하다. 고수준 클라이언트는 태그 변환(마샬링)을 자동화할 뿐 저장 모델은 같다 [S37].
- (일반 개념, 공식 문서에서 형식 규정 미확인) S3 같은 바이트 저장소에 객체를 지속하려면 앱이 직렬화 형식(JSON 등)을 정하고 읽을 때 같은 형식으로 역직렬화해야 한다.

### 데이터 스토어 사용·관리·유지 (Skill 1.3.6)

- 기본 CRUD 4종(`PutItem`·`GetItem`·`UpdateItem`·`DeleteItem`)은 모두 원자적이며 전체 기본 키가 필요하다. `PutItem`은 같은 키가 있으면 교체하고, `UpdateItem`은 키가 없으면 새 항목을 만든다 [S26].

| 작업 | 한도·특성 | 용량 소모 | 출처 |
|---|---|---|---|
| `BatchGetItem` | 100항목·16 MB, 실패분은 `UnprocessedKeys`, 전부 실패해야 전체 실패 | 항목별로 4 KB 올림 후 합산 | [S19][S29][S24] |
| `BatchWriteItem` | put/delete 25개·16 MB, update·조건식 불가, 개별 요청은 원자적이나 전체는 아님, 실패분은 `UnprocessedItems` | 항목별로 1 KB 올림 후 합산 | [S19][S25][S24] |
| `TransactWriteItems`·`TransactGetItems` | 고유 항목 100개·4 MB, 같은 항목에 액션 2개 불가, 단일 계정·Region, all-or-nothing | 일반의 2배(취소돼도 소모) | [S19][S24][S28] |

- 배치 재시도: `UnprocessedKeys`/`UnprocessedItems`는 지수 백오프로 재시도한다(바로 재시도하면 같은 스로틀에 다시 걸린다). Java Enhanced Client와 Boto3 `batch_writer`는 자동 재시도한다 [S29][S25].
- 트랜잭션 멱등성: `TransactWriteItems`에 클라이언트 토큰을 주면 같은 요청이 여러 번 와도 한 번만 적용된다. 토큰은 요청 완료 후 10분 유효하고, 같은 토큰에 다른 파라미터면 `IdempotentParameterMismatch`다 [S28].
- 조건부 쓰기: `PutItem`·`UpdateItem`·`DeleteItem`에 조건식을 줄 수 있고, false면 `ConditionalCheckFailedException`(그대로 재시도 불가)이며 실패해도 쓰기 용량을 소모한다 [S24][S29].
- 낙관적 잠금: 버전 속성을 두고 `ConditionExpression`으로 읽었던 버전과 같을 때만 갱신하며 버전을 올린다. 충돌하면 `ConditionalCheckFailedException` → 다시 읽고 재시도(횟수 제한). Java Enhanced Client는 `@DynamoDbVersionAttribute`를 지원한다 [S27]. **원리**: 충돌을 미리 막는 잠금이 아니라 쓰기 시점에 감지하는 방식이다 [S27].
- 원자 카운터: `UpdateItem`으로 무조건 증감한다. 멱등이 아니라 재시도 시 과다·과소 집계가 날 수 있으므로 정확성이 필요하면(예: 은행) 조건부 업데이트를 쓴다 [S26]. `UpdateItem`의 쓰기 단위는 갱신 전·후 항목 중 큰 크기 기준이다 [S24].
- 표현식: `ProjectionExpression`·`ConditionExpression`·`UpdateExpression`·`FilterExpression`이 있고, 표현식 문자열은 최대 4 KB다. 예약어를 표현식에 쓰면 `ExpressionAttributeNames`(별칭)를 함께 지정해야 한다 [S19].

| 구분 | 온디맨드 | 프로비저닝 |
|---|---|---|
| 과금 | 요청 단위당 과금, 트래픽이 0이면 처리량 요금 없음 [S23] | 프로비저닝한 시간당 RCU/WCU 과금(실사용 무관) [S22] |
| 용량 계획 | 불필요, "기본이자 권장" 모드 [S23] | 필요(예측 가능한 꾸준한 워크로드) [S21] |
| 스케일링 | 이전 피크의 2배까지 즉시 수용, 신규 테이블 쓰기 4,000/s·읽기 12,000/s, 2배 초과를 30분 안에 하면 스로틀 가능 → 사전 워밍·30분 이상 분산 [S23] | Auto Scaling(최소/최대·목표 사용률 권장 70%, 2분 연속 목표 초과 시 작동) 또는 `UpdateTable` [S22] |
| 상한 제어 | 테이블·GSI별 최대 처리량 설정 가능, 테이블 기본 한도 40,000 RRU/WRU [S23][S20] | 테이블 40,000 / 계정 80,000 RCU·WCU 기본(증설 가능) [S20] |
| 전환·변경 | 프로비저닝→온디맨드 24시간 롤링 4회(과거 1회), 온디맨드→프로비저닝은 언제든 [S19][S64] | 용량 감소는 하루 4회 + 매시간 1회 추가(최대 27회/일) [S20] |

- **원리**: 온디맨드는 직전 피크를 기준으로 용량을 늘려 가므로, 직전 피크의 2배를 넘는 급증이 30분 안에 오면 스로틀될 수 있다 [S23]. 프로비저닝은 설정한 RCU/WCU와 Auto Scaling 반응 속도(목표 초과 2분 연속 후 작동)가 처리 한계를 정한다 [S22].
- 단위 계산(파생 정리) [S22][S24]: 읽기 = ⌈항목 크기/4 KB⌉ × 초당 읽기 수(강력), ×0.5(최종적), ×2(트랜잭션). 쓰기 = ⌈항목 크기/1 KB⌉ × 초당 쓰기 수, 트랜잭션 ×2. 예: 3 KB 항목 80회/s 강력 읽기 = 80 RCU, 512 B 항목 100회/s 쓰기 = 100 WCU [S22]. 8 KB 항목 읽기 1회 = 강력 2 / 최종적 1 / 트랜잭션 4 read units, 10 KB는 12 KB로 올림, 2 KB 쓰기 = 2 write units(트랜잭션 4) [S24].
- 백업: 온디맨드 백업(스냅샷, 장기 보관·규정 준수, 크기·기간 과금) vs PITR(연속 백업, 초 단위, 복구 기간 1~35일, 새 테이블로 복원) [S31]. PITR은 활성화 시점부터이며 소급되지 않고, 복원된 테이블에는 Auto Scaling·Streams·TTL 등 일부 설정이 자동 복사되지 않는다 [S32].
- 테이블 클래스: Standard(기본, 처리량 비용이 낮음) vs Standard-IA(저장 비용이 낮음). Standard-IA는 저장 비용이 약 60% 낮은 대신 읽기·쓰기 비용이 약 25% 높고, 저장 비용이 월 총비용의 약 50% 이상인 테이블에 맞는다 [S73]. 성능·내구성·가용성은 같고 코드 변경 없이 바꿀 수 있으며 변경은 30일에 최대 2회다 [S33][S73]. 삭제 보호는 `DeletionProtectionEnabled`로 켠다 [S30].
- 오류·재시도: SDK가 자동 재시도(+지수 백오프)한다. `ProvisionedThroughputExceededException`은 재시도 가능하고 `ConditionalCheckFailedException` 같은 4xx는 요청을 고쳐야 한다. 재시도는 약 1분에서 멈추고 그 뒤엔 용량·요청 크기를 조사하며, 동시 클라이언트가 많으면 지터가 도움이 된다 [S29]. 소모량 확인에는 `ReturnConsumedCapacity`(`NONE`·`TOTAL`·`INDEXES`)를 쓴다 [S18]. 항목이 400 KB에 근접하는지도 이 값으로 모니터링한다(초과 시 `ValidationException`) [S34].
- 다른 스토어(개발자 관점): S3 사전 서명 URL은 만든 주체의 권한으로 시간 제한 접근을 주며 만료는 SDK·CLI 최대 7일, 콘솔 1분~12시간이고 임시 자격 증명으로 만들면 그 자격 증명 만료 시 같이 만료된다 [S53]. S3 멀티파트 업로드는 100 MB 즈음부터 고려하며 파트 5 MiB~5 GiB·최대 10,000파트·최대 객체 48.8 TiB다 [S52]. Lambda처럼 짧은 연결을 많이 여는 클라이언트는 RDS Proxy로 연결을 풀링하며(프로덕션 권장) [S66], 관계형 vs DynamoDB 선택은 Skill 1.3.9 표를 본다 [S67].

### 데이터 수명 주기 관리 (Skill 1.3.7)

| 스토어 | 수명 주기 수단 | 핵심 규칙 |
|---|---|---|
| DynamoDB | TTL | 항목별 만료 시각 속성(Number, Unix epoch 초). 만료 항목은 보통 수일 내 자동 삭제되며 쓰기 처리량을 쓰지 않는다 [S40] |
| DynamoDB | PITR·온디맨드 백업·테이블 클래스 | PITR 보존 1~35일, 장기 보관은 온디맨드 백업, 드물게 읽는 데이터는 Standard-IA [S31][S33] |
| S3 | Lifecycle 구성(전환·만료 규칙) | 기존+신규 객체 모두에 적용, 하향식 전환, 128 KB 미만은 기본 전환 제외 [S48][S49] |
| S3(버전 관리) | `Expiration` / `NoncurrentVersionExpiration` | 현재 버전은 delete marker 추가, 비현재 버전은 영구 삭제 [S51] |
| ElastiCache | 키별 TTL(초) | 만료 키는 "없음"으로 취급 → DB 재조회 후 캐시 갱신 [S44] |
| DAX | 항목·쿼리 캐시 TTL(기본 5분) + LRU | TTL 0이면 항목 캐시는 LRU·write-through로만 갱신, 쿼리 캐시는 캐시 안 함 [S42] |

- DynamoDB TTL [S40]: TTL 속성이 Number가 아니면 무시된다. 만료됐어도 아직 안 지워진 항목은 읽기·갱신이 되고, 미래 시각으로 갱신하거나 속성을 지우면 삭제되지 않는다 → Scan/Query에서 만료 항목은 FilterExpression으로 제외하고, 만료 항목을 갱신할 때는 조건식을 쓰도록 권장한다. TTL 삭제는 Streams에 서비스 삭제로 기록되고 GSI·LSI에서도 제거된다. 글로벌 테이블에서는 TTL 삭제가 복제되며 복제본 Region에서 복제 쓰기 단위를 소모한다(단 MRSC 글로벌 테이블은 TTL 미지원 [S15]). TTL 활성·비활성 변경은 테이블당 시간당 1회다 [S19]. **원리**: 삭제는 백그라운드로 처리돼 즉시가 아니다.
- S3 Lifecycle [S48][S49]: 전환 액션(예: 30일 후 Standard-IA, 1년 후 Glacier Flexible Retrieval)과 만료 액션(S3가 대신 삭제). 전환은 하향식(예: Standard-IA → Standard 불가)이고, 접근 패턴을 모르면 Intelligent-Tiering을 쓴다. 128 KB 미만 객체는 기본적으로 전환되지 않으며 `ObjectSizeGreaterThan`/`ObjectSizeLessThan` 필터로 허용한다. 최소 저장 기간이 있는 클래스에서 일찍 옮기거나 만료하면 남은 기간만큼 과금된다. 버킷 정책으로 Lifecycle의 삭제·전환을 막을 수 없다. 규칙이 겹치면 영구 삭제가 전환보다 우선한다 [S50].
- 버전 관리 버킷 [S50][S51]: 버전 ID 없는 삭제는 delete marker를 추가한다. `Expiration`은 현재 버전을 비현재로 남기고 delete marker를 만들며, `NoncurrentVersionExpiration`(`NoncurrentDays`·`NewerNoncurrentVersions`)은 비현재 버전을 영구 삭제한다(복구 불가). 비현재 버전이 없는 delete marker가 "expired object delete marker"이며 정리 규칙으로 제거한다.
- DynamoDB export to S3(예: zero-ETL 초기 스냅샷)를 쓰려면 PITR 활성화가 필요하다 [S58].

### 데이터 캐싱 서비스 (Skill 1.3.8)

| 전략 | 동작 | 장점 | 단점 |
|---|---|---|---|
| 지연 로딩(lazy loading, cache-aside) | 캐시 조회 → 미스면 DB 조회 후 캐시에 저장 | 요청된 데이터만 캐시, 노드 장애에도 앱 동작(지연만 증가), 새 노드에 자동으로 채워짐 | 미스 시 3번 왕복(캐시 조회·DB 조회·캐시 쓰기) 페널티, stale 데이터 |
| write-through | DB에 쓸 때 캐시도 갱신 | 캐시가 항상 최신, 지연을 쓰기 쪽으로 이전 | 새·교체 노드의 누락 데이터, 읽히지 않는 데이터로 캐시 낭비(churn) |
| TTL 추가 | 키마다 만료 시간(초) 부여 | 두 전략의 단점 완화, 캐시 비대화 방지 | 값이 여전히 stale일 수 있음 |

(전략 표는 [S44], 보완 설명은 [S46])

- 실무 조합: 지연 로딩을 기반으로 깔고 특정 데이터에만 write-through를 얹으며, write-through로 갱신하는 키를 뺀 모든 키에 TTL을 주고 변화가 빠른 데이터는 몇 초짜리 짧은 TTL을 쓴다 [S46]. 캐시해도 안전한 데이터인지(일관성 요구)부터 판단한다 [S46]. **원리**: 캐시는 원본의 복사본이라 신선도는 갱신 전략과 TTL이 정한다 — 지연 로딩은 DB가 바뀌어도 캐시를 갱신하지 않아 stale해질 수 있다 [S44].
- thundering herd(많은 프로세스가 같은 키의 미스를 동시에 겪어 같은 DB 질의를 병렬 실행)는 TTL 만료나 새 캐시 노드(빈 메모리)에서 악화되며 사전 워밍으로 완화한다. 같은 TTL을 일괄 적용하면 키들이 같은 시간대에 만료되므로 TTL에 무작위 값(지터)을 더한다 [S46].

| 항목 | Memcached | Valkey / Redis OSS |
|---|---|---|
| 데이터 타입 | 단순(문자열·객체) | 복합(문자열·집합·정렬 집합·리스트·해시·비트맵·HyperLogLog 등) |
| 멀티스레드 | 예 | 아니오(공식 비교표 기준) |
| 복제·고가용성 | 없음 | 있음(클러스터 모드 활성 시 자동 장애 조치 필수) |
| Pub/Sub·정렬 집합 | 없음 | 있음 |
| 데이터 분할(샤딩) | 예 | 클러스터 모드 활성이면 예, 비활성이면 아니오 |
| 백업·복원 | 서버리스 캐시만 | 예 |

(엔진 비교는 [S45])

- Memcached 선택 기준(공식): 가장 단순한 모델, 멀티코어 큰 노드, 노드 추가·제거로 스케일 인·아웃, 객체 캐싱 [S45]. Valkey는 ElastiCache의 "권장 엔진"이며 Redis OSS·Memcached도 계속 지원한다 [S45][S47]. Valkey 9.0은 전문 검색·하이브리드 검색·해시 필드 만료 등을 추가했다 [S45][S47].
- DAX = DynamoDB 호환 인메모리 캐시. 애플리케이션이 DAX 클라이언트로 클러스터 엔드포인트를 쓰면 되고(API 호환 → 최소 변경), VPC 안에서 실행되며 Go·Java·Node.js·Python·.NET 클라이언트를 지원한다. 최종적 일관성 읽기 지연을 밀리초에서 마이크로초로 줄인다 [S41].
- DAX 읽기·쓰기 [S42][S43]: `GetItem`·`BatchGetItem`·`Query`·`Scan` 중 최종적 일관성 읽기만 캐시하고, 강력한 일관성·트랜잭션 읽기는 패스스루(캐시 안 함). 쓰기(`PutItem`·`UpdateItem`·`DeleteItem`·`BatchWriteItem`·`TransactWriteItems`)는 write-through로, DynamoDB에 먼저 쓰고 성공해야 DAX에 반영한다. 대량 적재처럼 쓰기 지연·캐시 오염이 걱정되면 DynamoDB에 직접 쓰는 write-around를 쓰되 캐시와 불일치가 생긴다.
- DAX 두 캐시 [S42][S43]: 항목 캐시(`GetItem`·`BatchGetItem`, 기본 키로 저장)와 쿼리 캐시(`Query`·`Scan`, 파라미터로 저장)는 독립이다 — 항목 쓰기는 쿼리 캐시를 무효화하지 않고, Scan으로 항목 캐시를 데울 수 없다. 항목 캐시 TTL 기본 5분(쿼리 캐시 기본값은 `확인 필요`) + LRU(설정 불가)이며, TTL 0이면 항목 캐시는 LRU·write-through로만 갱신되고 쿼리 캐시는 캐시하지 않는다. 항목이 없어도 빈 결과를 캐시한다(음수 캐싱).
- DAX 적합·부적합 [S41]: 최소 지연 읽기, 일부 항목의 반복 읽기(핫 키), 읽기 집약·비용 민감 워크로드에 적합. 강력한 일관성이 필요하거나, 마이크로초가 불필요하거나, 쓰기 집약이거나, 반복 읽기가 적으면 부적합(적중률 90% 초과일 때 최적). 최상위 속성 이름이 무제한이면(타임스탬프·UUID 등) 메모리가 고갈될 수 있다.
- DAX 가용성: 3개 이상 노드·여러 AZ 권장 [S43], 클러스터는 프라이머리 1 + 읽기 복제본 0~10 [S19].

| 질문 | DAX | ElastiCache |
|---|---|---|
| 대상 | DynamoDB 전용 [S41] | DB 앞단의 범용 인메모리 키-값 저장소 [S44] |
| 코드 변경 | DynamoDB API 호환 → 엔드포인트·클라이언트 교체 [S41] | 앱이 조회·채움·무효화 로직 구현(지연 로딩 등) [S44] |
| 일관성 | 최종적 일관성 읽기만 캐시 [S42] | 전략·TTL에 따라 stale 가능 [S44] |
| 쓰기 처리 | write-through 내장 [S42] | 앱이 write-through 구현 [S44] |

### 액세스 패턴에 맞는 특수 데이터 스토어 (Skill 1.3.9)

- 선택 원칙: 접근 패턴(어떻게 조회·집계·검색하는가)이 먼저이고 스토어는 그에 맞춘다. DynamoDB는 키 기반 접근에 맞춰져 있어 JOIN과 count·sum·min·max 같은 집계를 제공하지 않는다 [S70]. SQL 능력이 필요하면 RDS가 대안으로 제시된다 [S67]. **원리**: 키 설계 밖의 임의 조건 검색·분석은 DynamoDB가 아니라 목적에 맞는 스토어(OpenSearch 등)에 데이터를 복제해 처리한다 [S58].

| 접근 패턴 | 적합한 스토어 | 근거 |
|---|---|---|
| 키로 단건·범위 조회, 서버리스, 일관된 한 자릿수 ms | DynamoDB | [S67] |
| 정규화된 관계형 데이터, SQL | RDS(Aurora 포함; Lambda에서는 RDS Proxy) | [S67][S66] |
| 자유 텍스트(전문) 검색, 로그·클릭스트림 분석 | OpenSearch Service / Serverless | [S74][S55][S57] |
| DynamoDB 앞단의 마이크로초 반복 읽기 | DAX | [S41] |
| DB 앞단의 범용 인메모리 캐시 | ElastiCache | [S44] |
| S3 데이터에 표준 SQL로 대화형 질의(서버리스; 파티션·컬럼형으로 스캔량 감소) | Athena | [S74][S68][S75] |
| 벡터 유사도 검색(임베딩) | DynamoDB 벡터 인덱스(2026-08 GA), ElastiCache Valkey 8.2+, OpenSearch Serverless 벡터 엔진 | [S60][S45][S74] |

- Amazon OpenSearch Service: OpenSearch 클러스터(=도메인)를 배포·운영·확장하는 관리형 서비스. 로그 분석·실시간 애플리케이션 모니터링·클릭스트림 분석에 쓰는 검색·분석 엔진이며, 실패 노드 자동 교체, Multi-AZ, 자동 스냅샷, IAM·VPC·암호화, S3·Kinesis·DynamoDB로부터의 적재 통합을 제공한다. 규모는 최대 1002 data nodes·25 PB다 [S55]. 전문(full-text) 검색도 대표 용도로 꼽히며, OpenSearch Serverless는 클러스터 관리 없이 쓰는 서버리스 옵션이고 벡터 엔진(벡터 저장·검색)을 제공한다 [S74].
- 개념: 인덱스 ≈ 테이블, 문서 ≈ 행, 필드 ≈ 열. 인덱스를 만들 때 주 샤드 수를 정하고, 복제본 샤드는 중복성과 읽기 용량을 더하며 최소 1개를 권장한다 [S56]. OpenSearch Serverless는 컬렉션을 만들 때 용도(로그 분석 / 전문 검색)를 고른다 [S57].
- DynamoDB ↔ OpenSearch zero-ETL [S58]: DynamoDB 플러그인(OpenSearch Ingestion, 관리형 no-code)이 초기에는 export to S3 스냅샷으로 적재하고 이후 DynamoDB Streams로 변경을 near real time 복제한다. PITR 활성화와 Streams(new & old images)가 필요하며, 테이블의 읽기·쓰기 처리량을 쓰지 않는다. 중단이 24시간을 넘으면 업데이트가 유실될 수 있다. → DynamoDB를 원본으로 두고 OpenSearch는 검색용 복제본으로 쓰는 패턴이다.
- 벡터 검색(최신): DynamoDB는 벡터 인덱스를 만들고 `SearchVectors`로 근사 최근접 검색을 하며, 키 조회용 보조 인덱스(Query·Scan)와는 다른 계열이다 [S7][S60]. ElastiCache for Valkey는 8.2부터 벡터 검색, 9.0부터 전문·하이브리드 검색을 지원한다 [S45]. v2.1 가이드(2024-12)보다 늦은 기능이라 출제 가능성은 불명이다(`확인 필요`).
- RDS Proxy: 연결 풀을 공유해 함수가 높은 동시성에서도 DB 연결을 고갈시키지 않게 한다 [S66].
- Athena: S3 데이터를 표준 SQL로 분석하는 서버리스 대화형 질의 서비스다 [S74]. 파티셔닝·버케팅은 질의가 스캔할 데이터 양을 줄여 성능을 높이고 비용을 낮춘다 [S68]. 압축·컬럼형 포맷(Parquet·ORC)으로 변환해도 스캔량이 줄어 비용·성능이 좋아진다 [S75]. 요금은 질의가 스캔한 데이터량 기준(TB당 과금, 최소 10 MB)이며 DDL·실패한 질의는 무료다 [S75].

## 시험에서 묻는 방식

> 문제 저작자를 위한 제안이며 "시험이 반드시 이렇게 낸다"는 단정이 아니다.

1. **핫 파티션·키 설계 (Skill 1.3.1·1.3.4)** — 문제 상황: "IoT 센서 이벤트를 날짜(YYYY-MM-DD)를 파티션 키로 저장한다. 하루 중 모든 쓰기가 오늘 키로 몰려 일부 요청이 `ProvisionedThroughputExceededException`을 받는데 테이블 총 WCU는 충분하다." → 정답 단서: 고유 값이 적거나 날짜형인 파티션 키 + "일부만 스로틀" → 고카디널리티 키(센서 ID 등) 또는 쓰기 샤딩(난수·계산 접미사). 테이블 용량 증설·DAX는 오답 유도 선지로 쓰기 좋다.
2. **일관성 + 인덱스 선택 (Skill 1.3.2·1.3.4)** — 문제 상황: "방금 저장한 항목이 GSI Query 결과에 안 보인다. GSI Query에 강력한 일관성을 요청했더니 오류가 난다." → 정답 단서: GSI + 강력한 일관성 → GSI는 최종적 일관성만 지원, 최신 값이 꼭 필요하면 기본 테이블·LSI에서 `ConsistentRead=true`(비용 2배). "같은 PK에서 다른 정렬 기준 + 강력한 일관성 + 테이블 생성 시점" → LSI, "나중에 추가·전혀 다른 PK" → GSI.
3. **Query vs Scan 비용 (Skill 1.3.3)** — 문제 상황: "큰 테이블에서 Scan + FilterExpression이 느리고 RCU를 많이 쓴다. 필터를 더 엄격하게 바꿔도 소모량이 그대로다." → 정답 단서: 필터는 읽은 뒤 적용·RCU 동일·프로젝션도 무관 → 접근 패턴에 맞는 키 설계 또는 GSI + Query. 전체 순회가 불가피하면 병렬 Scan(`Segment`/`TotalSegments`) + `Limit`.
4. **캐시·수명 주기·특수 스토어 선택 (Skill 1.3.7~1.3.9)** — (a) "DynamoDB 읽기 폭주, 마이크로초 지연, 코드 변경 최소" → DAX(강력한 일관성 읽기는 패스스루). (b) "RDS 조회 결과 캐시, 데이터 변경 시 신선도" → ElastiCache 지연 로딩 + TTL(+write-through). (c) "만료된 세션 항목을 쓰기 용량 소모 없이 자동 삭제" → DynamoDB TTL(Number, epoch 초), 읽을 때 필터로 만료 항목 제외. (d) "S3 로그를 30일 뒤 IA, 1년 뒤 삭제" → Lifecycle 전환·만료 규칙(버전 관리 버킷이면 `NoncurrentVersionExpiration`). (e) "여러 속성에 걸친 전문 검색 + DynamoDB 변경 반영" → OpenSearch + DynamoDB zero-ETL(OpenSearch Ingestion, PITR·Streams 필요).

## 흔한 함정·혼동 짝

| 짝 (A vs B) | 혼동 이유 | 구분 기준 한 줄 | 출처 |
|---|---|---|---|
| Query vs Scan | 둘 다 FilterExpression·1 MB 페이지네이션을 쓴다 | Query = PK 동등 조건으로 한 파티션 구간만, Scan = 전체. 필터는 읽은 뒤 적용이라 RCU가 같다 | [S16][S17][S18] |

| 지연 로딩 vs write-through | 캐시를 채우는 시점만 다르다고 본다 | 지연 로딩 = 미스 페널티·stale, write-through = 항상 최신이지만 불필요 데이터·노드 교체 시 누락. TTL로 보완 | [S44] |

### 후보 Q1
- 대응 Skill: 1.3.1 / 난이도: intermediate
- 문제: 물류 회사가 배송 이벤트를 DynamoDB 테이블에 저장한다. 파티션 키는 이벤트 날짜(`2026-10-17`), 정렬 키는 이벤트 ID다. 날짜가 바뀌면 그날의 모든 쓰기(한 키에 초당 수천 건)가 한 키로 몰려, 테이블 전체 프로비저닝 WCU는 충분한데도 일부 쓰기가 `ProvisionedThroughputExceededException`으로 스로틀된다. 주된 읽기 패턴은 하루 단위 조회다. 가장 적절한 해결책은?
- 보기:
  - A. 테이블의 프로비저닝 WCU를 두 배로 늘린다.
  - B. 날짜 뒤에 1~200 범위의 난수 접미사를 붙여 파티션 키를 만들어 쓰기를 분산하고, 하루치를 읽을 때는 모든 접미사를 Query해 합친다.
  - C. 쓰기 앞에 DAX 클러스터를 두어 쓰기를 캐시한다.
  - D. 파티션 키를 배송 상태 코드(5가지 값)로 바꾼다.
- 정답: B
- 정답 근거: 파티션 하나의 쓰기 상한은 1,000 write units/s라서 한 키에 몰리면 총 용량과 무관하게 스로틀되고, 난수 접미사로 키 공간을 넓히는 것이 공식 쓰기 샤딩 방법이다(읽을 때는 모든 접미사 Query 후 병합). 근거 URL: https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-partition-key-sharding.html , https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-partition-key-design.html
- 오답 해설: A) 총 WCU를 늘려도 단일 파티션 상한(1,000 write units/s)은 넘지 못한다. C) DAX는 읽기 캐시이고 쓰기는 DynamoDB로 동기 전달(write-through)되므로 쓰기 쏠림을 해소하지 못한다. D) 상태 코드처럼 고유 값이 적은 키는 균등성이 나쁜 대표 사례다.

- 문제: `GameScores` 테이블에 `PutItem`으로 점수를 저장한 직후 GSI `GameTitleIndex`를 Query하면 방금 저장한 점수가 안 보인다. 개발자가 그 Query에 `ConsistentRead=true`를 넣자 `ValidationException`이 발생했다. 올바른 설명과 대응은?

  - A. GSI는 강력한 일관성 읽기를 지원하지 않는다. 최신 값이 반드시 필요한 조회는 기본 테이블(또는 LSI)에서 `ConsistentRead=true`로 읽고, GSI 결과는 약간 늦을 수 있음을 허용한다.

### 후보 Q5

- 보기:
  - A. 검색 요청마다 `contains()` FilterExpression을 붙인 Scan을 실행한다.
  - B. 테이블에 PITR과 Streams를 켜고 OpenSearch Ingestion 파이프라인(DynamoDB zero-ETL)으로 Amazon OpenSearch Service에 복제한 뒤 검색은 OpenSearch에 질의한다.
  - C. 이름을 정렬 키로 하는 LSI를 만들고 `begins_with`로 검색한다.

- 정답: B
- 정답 근거: DynamoDB는 OpenSearch Ingestion 플러그인으로 export to S3 스냅샷 + Streams 변경을 OpenSearch에 near real time 복제하며(PITR·Streams 필요) 테이블 읽기·쓰기 처리량을 쓰지 않고, OpenSearch는 전문 검색 용도에 쓰인다. 근거 URL: https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/OpenSearchIngestionForDynamoDB.html , https://docs.aws.amazon.com/whitepapers/latest/aws-overview/analytics.html
