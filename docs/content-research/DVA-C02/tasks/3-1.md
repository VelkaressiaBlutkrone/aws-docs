## 핵심 개념

### Lambda 배포 패키지 — .zip 파일 vs 컨테이너 이미지 (Skill 3.1.1)

Lambda는 함수 코드와 의존성을 "배포 패키지"로 받고, 형태는 .zip 파일 아카이브와 컨테이너 이미지 두 가지다 [S2].

| 비교 | .zip 파일 아카이브 | 컨테이너 이미지 |
|---|---|---|
| 크기 한도 | 압축본 50 MB(API·SDK·콘솔 업로드), 풀었을 때 250 MB(계층·사용자 지정 런타임 포함). 50 MB를 넘는 압축본은 S3에 올려 지정 [S1][S7] | 압축 해제 기준 이미지 10 GB(모든 레이어 포함) [S1][S2] |
| 런타임 | 함수에 Lambda 런타임을 지정 [S9] | 런타임·OS를 이미지에 포함(AWS 기본 이미지·OS 전용 이미지·비-AWS 이미지) [S2] |
| 계층(layers) | 사용 가능, 함수당 최대 5개 [S3] | 사용 불가 — 의존성은 이미지 빌드 때 포함 [S3] |
| 저장 위치 | Lambda 관리 스토리지(Region당 풀린 크기 300 GB, 증설 불가) [S1] | Amazon ECR(함수와 같은 Region) [S2] |
| 빌드 | zip 유틸리티·pip·npm, `sam build`(PackageType: Zip) [S6][S9] | Dockerfile·`docker build`, `sam build`(PackageType: Image + Metadata) [S9] |
| 아키텍처 | 함수 단위로 x86_64(기본) 또는 arm64 [S55] | 이미지는 한 아키텍처만 대상(멀티 아키텍처 이미지 함수 미지원) [S2] |
| 실행 제약 | `/tmp` 쓰기 512–10,240 MB [S1] | 읽기 전용 파일시스템에서 동작해야 함, Linux 기반 이미지만 지원 [S2] |
| 유형 전환 | 기존 함수의 패키지 유형은 변경 불가(새 함수를 만들어야 함) [S2] | 동일 [S2] |

- 원리: zip은 풀린 크기 기준 250 MB 상한(계층 포함)이 걸린다. 이미지는 이미지 자체가 실행 환경이라 10 GB까지 허용되지만, AWS 기본 이미지가 갱신돼도 직접 다시 빌드하고 함수 코드를 업데이트해야 반영된다 [S1][S2].
- 압축본 50 MB는 "대략적인" 값이다. 직접 업로드하면 바이너리 ZIP이 base64로 변환돼 약 30% 커지므로 Lambda가 적용하는 실제 요청 한도는 이보다 크다 [S8].

### 의존성을 패키지에 넣는 방법 — 번들링 (Skill 3.1.1)

- 핸들러와 의존성은 zip 루트에 둔다. Python 예: `pip install --target ./package`로 의존성을 설치하고 그 내용물을 zip 루트에 놓은 뒤 핸들러 .py도 루트에 추가한다. 핸들러가 루트에 없으면 Lambda가 코드를 실행하지 못한다 [S6].
- AWS SDK는 런타임에 들어 있지만(Python은 Boto3) 콘솔 편집기·SAM/CloudFormation 인라인 코드처럼 의존성을 넣을 수 없는 경우를 위한 장치다. 런타임의 SDK가 갱신되면 패키지에 든 하위 의존성(예: urllib3)과 버전이 어긋날 수 있으므로, SDK를 포함해 모든 의존성을 패키지에 넣을 것을 권장한다 [S6]. SDK 버전을 고정하는 용도로 계층을 쓸 수도 있다 [S3].
- 네이티브(C/C++) 코드가 든 패키지는 Linux(Amazon Linux)에서 동작하는 빌드여야 한다. macOS·Windows에서는 `pip install --platform manylinux2014_x86_64 --only-binary=:all:`처럼 Linux용 휠을 받거나, Docker·`sam build --use-container`로 Lambda와 유사한 컨테이너에서 빌드한다 [S6][S9][S59].
- 함수를 arm64로 옮기면 의존성도 ARM 명령어 집합용으로 다시 컴파일한 새 패키지가 필요하다 [S55].
- Go·Rust는 의존성이 컴파일된 단일 실행 파일에 들어가므로 계층을 권장하지 않는다. 계층에 두면 초기화 단계에서 추가 어셈블리를 따로 로드해야 해서 콜드 스타트가 느려질 수 있다 [S3][S4].
- 파일 권한: 비실행 파일은 644, 디렉터리·실행 파일은 755가 필요하다 [S7].
- Node.js: `package.json`으로 의존성을 선언한다. SAM에서는 `Metadata.BuildProperties.UseNpmCi: True`(+ `package-lock.json` 필요)로 `npm ci`를 쓸 수 있다 [S9].

### Lambda 계층(Layers) (Skill 3.1.1, 3.1.2)

- 계층은 추가 코드·데이터를 담은 .zip 아카이브이며, 보통 라이브러리 의존성·사용자 지정 런타임·구성 파일을 담는다. 쓰는 이유는 ① 배포 패키지 축소 ② 함수 로직과 의존성 분리 ③ 여러 함수가 의존성 공유 ④ 콘솔 코드 편집기 사용(패키지가 작아야 함) ⑤ 내장 SDK 버전 고정이다 [S3].
- 함수당 최대 5개, .zip 함수에서만 쓴다. 계층 버전은 변경 불가능한 스냅샷이며 함수에는 정확한 버전 ARN(예: `...:layer:my-layer:1`)을 지정한다 [S3].
- 계층 내용은 실행 환경의 `/opt`에 풀리고, 각 런타임은 `/opt` 아래 정해진 경로를 이미 검색 경로(PATH·NODE_PATH·CLASSPATH 등)에 넣어 둔다. 그래서 계층 zip 안의 폴더 구조가 규칙에 맞아야 라이브러리가 인식된다(원리) [S3][S4].

| 런타임 | 계층 zip 안의 경로 |
|---|---|
| Node.js | `nodejs/node_modules` |
| Python | `python` (또는 `python/lib/python3.x/site-packages`) |
| Java | `java/lib` |
| Ruby | `ruby/gems/3.4.0`, `ruby/lib` |
| 모든 런타임 | `bin`(PATH), `lib`(LD_LIBRARY_PATH) |

- 250 MB(풀린 크기) 한도는 계층을 포함한 합계다 [S1][S7].
- SAM: `AWS::Serverless::LayerVersion`의 `ContentUri`(S3 URI 또는 로컬 폴더)에 `Metadata.BuildMethod`(Lambda 런타임 식별자 또는 `makefile`)를 더하면 `sam build`가 계층도 빌드한다. `Metadata`가 없으면 빌드하지 않고 CodeUri 산출물을 그대로 복사한다 [S14][S15]. 빌드 산출물의 폴더 구조(`python/` 등)도 런타임 규칙에 맞춰야 한다 [S15].

### 컨테이너 이미지 구성 — 기본 이미지·Dockerfile·ECR (Skill 3.1.1)

- 이미지를 만드는 방법은 세 가지다 [S2].
  1. AWS 기본 이미지: 언어 런타임, 런타임 인터페이스 클라이언트(RIC), 로컬 테스트용 런타임 인터페이스 에뮬레이터(RIE)가 미리 들어 있다. 코드·의존성만 더한다.
  2. AWS OS 전용 기본 이미지(`provided.al2023`): Amazon Linux와 RIE만 있다. Go·Rust 같은 컴파일 언어, AWS가 기본 이미지를 주지 않는 언어·버전, 사용자 지정 런타임에 쓰며 RIC를 직접 포함해야 한다.
  3. 비-AWS 기본 이미지(Alpine·Debian·사내 이미지): 역시 RIC를 직접 포함해야 한다. 이미지 매니페스트는 Docker V2 schema 2 또는 OCI 규격이어야 한다.
- 흐름: 로컬에서 빌드 → ECR 리포지토리에 push(`aws ecr get-login-password` 결과를 `docker login --username AWS --password-stdin`에 전달, 토큰 유효 12시간) → 함수 생성 시 리포지토리 URI 지정. ECR 리포지토리는 함수와 같은 Region이어야 한다 [S2][S57].
- 권한: 함수를 만드는 주체에 `GetRepositoryPolicy`·`SetRepositoryPolicy`·`BatchGetImage`·`GetDownloadUrlForLayer`가 필요하다. 같은 계정은 역할(ID 기반) 정책 또는 ECR 리포지토리 정책 중 한쪽만 허용해도 되지만, 교차 계정은 양쪽 모두 허용해야 한다 [S2].
- SAM: `PackageType: Image`와 `Metadata`(`Dockerfile`, `DockerContext`, 선택 `DockerTag`·`DockerBuildArgs`·`DockerImage`)를 선언한다. `DockerBuildArgs`는 가려지지 않으므로 비밀을 넣지 않는다 [S9].
- 알아 둘 점: Node.js 20·Python 3.12·Java 21·.NET 8·Ruby 3.3 이후 AWS 기본 이미지는 Amazon Linux 2023 기반(패키지 관리자 `microdnf`)이다. 이미지 활성화 시간을 줄이려면 멀티 스테이지 빌드를 쓰라고 안내한다 [S2].

### 환경 변수와 패키지 내 구성 파일 (Skill 3.1.1, 3.1.5)

- Lambda 환경 변수는 함수 "버전별 구성"이다. 미게시(`$LATEST`) 버전에서 정의하고, 버전을 게시하면 그 버전에 잠긴다. 게시된 버전의 환경 변수는 바꿀 수 없으므로 `$LATEST`를 바꾼 뒤 새 버전을 게시해야 하며, 앱이 특정 버전을 하드코딩하지 않도록 별칭(alias)을 쓴다 [S5][S45].
- 제약: 모든 환경 변수 합계 4 KB(조정 불가), 키는 문자로 시작하고 두 글자 이상이며 영숫자·밑줄만 가능, Lambda 예약 이름 금지. 값은 리터럴 문자열이고 평가·확장되지 않는다 [S5][S58].
- `update-function-configuration`으로 환경 변수를 적용하면 `Variables` 구조 전체가 교체된다(기존 값을 유지하려면 모두 다시 보낸다). 암호화 KMS 키는 `--kms-key-arn`으로 지정한다 [S5].
- 민감 정보는 환경 변수 대신 Secrets Manager를 쓰라고 권장한다 [S5]. CodeBuild도 `PLAINTEXT` 환경 변수에는 민감 값을 두지 말고 `PARAMETER_STORE`·`SECRETS_MANAGER` 유형을 쓰라고 한다 [S60].
- 4 KB를 넘는 구성은 Parameter Store·S3 같은 외부 저장소를 쓴다 [S58].
- 같은 코드에 다른 구성: 테스트용 함수는 테스트 DB 호스트를, 운영용 함수는 운영 DB 호스트를 환경 변수로 받게 하고, 환경별 로그 수준(`LOG_LEVEL`)도 환경 변수로 분기한다 [S5].
- 패키지에 포함된 구성 파일(예: `config.json`)은 코드와 함께 배포되므로 값이 바뀌면 새 패키지가 필요하다. 환경마다 다르거나 자주 바뀌는 값은 환경 변수·Parameter Store·AppConfig 같은 외부 구성으로 분리한다 [S5][S27].

### SAM 프로젝트 구조·템플릿·빌드 (Skill 3.1.2, 3.1.1)

`sam init`(Hello World, Zip 패키지)이 만드는 기본 구조 [S12]:

```
sam-app/
├── README.md
├── events/event.json        # 로컬 테스트용 이벤트
├── hello_world/             # 함수 코드(CodeUri) + 의존성 매니페스트
│   ├── app.py
│   └── requirements.txt
├── samconfig.toml           # SAM CLI 설정(환경별 값)
├── template.yaml            # SAM 템플릿
└── tests/                   # unit, integration
```

- Image 패키지를 고르면 함수 폴더에 `Dockerfile`이 생긴다 [S12].
- 템플릿 섹션: `Transform`(필수, 값은 `AWS::Serverless-2016-10-31`), `Globals`(SAM 전용 — Function·Api·HttpApi·SimpleTable·StateMachine 등이 상속하는 공통 속성), `Description`, `Metadata`, `Parameters`, `Mappings`, `Conditions`, `Resources`(필수), `Outputs`. `Globals`와 `Transform` 외 섹션은 CloudFormation과 같다 [S11].
- 원리: SAM 리소스는 CloudFormation으로 배포할 때 CloudFormation 리소스로 변환된다. 그래서 CloudFormation의 Parameters·Mappings·Conditions를 그대로 쓴다 [S11][S14].
- `sam build`: 의존성 매니페스트(`requirements.txt`·`package.json`) 또는 함수의 `Layers` 속성으로 의존성을 모아, 로컬 테스트·패키징·배포에 맞는 형식과 위치(`.aws-sam` 빌드 디렉터리)에 배치한다. 결과 형식은 함수의 `PackageType`(Zip 또는 Image)이 결정한다 [S9].
- 주요 옵션: `--use-container`(네이티브 컴파일 의존성을 Lambda 유사 컨테이너에서 빌드, 기본 빌드 이미지는 ECR Public), `--build-image`(대체 빌드 이미지), `--cached`(변경 없는 산출물 재사용, 기본은 캐시 안 함), `--parallel`(함수·계층 병렬 빌드), `--build-in-source`(소스 폴더에서 직접 빌드, Node.js·Makefile·esbuild 대상), `--use-buildkit`(이미지 빌드에 BuildKit) [S9][S13].
- 이미 빌드한 산출물을 쓰려면 함수 `Metadata`에 `SkipBuild: True`를 두고 `CodeUri`에 경로를 지정한다 [S9].
- `--cached`는 버전을 고정하지 않은 서드파티 모듈(예: `requests=1.x`)의 최신 버전 변경을 감지하지 못하므로 비캐시 빌드로 갱신한다 [S13].
- 아키텍처를 지정하지 않으면 `x86_64`로 빌드한다 [S9].
- `sam init --location`으로 Git·Mercurial·HTTP(S)·zip 위치의 사용자 지정 템플릿에서 프로젝트를 시작할 수도 있다 [S12].

### 코드 저장소와 아티팩트 저장소 (Skill 3.1.3)

배포 환경(파이프라인·빌드·배포)은 "소스·패키지·이미지가 어디에 있는지"를 알아야 한다. 저장 대상에 따라 서비스가 다르다.

| 저장소 | 저장 대상 | 배포 환경에서의 쓰임·핵심 사실 |
|---|---|---|
| AWS CodeCommit | 관리형 Git 리포지토리 | IAM 접근 통제, 전송·저장 암호화, 풀 리퀘스트. 기본 리포지토리 5,000개 [S18]. CodePipeline 소스 액션·CodeBuild 소스로 연결 [S20][S23]. 신규 고객 제한(2024-07-25)은 2025-11-25에 해제 [S16][S17] |
| 외부 Git(GitHub·GitHub Enterprise Server·GitLab.com·GitLab self-managed·Bitbucket Cloud) — AWS CodeConnections | 외부에서 호스팅하는 Git 소스 | "연결(connection)" 리소스(ARN)를 CodePipeline·CodeBuild·CodeDeploy에 부여하며 템플릿에 비밀·파라미터를 따로 두지 않는다 [S19]. 옛 이름 AWS CodeStar Connections(리소스 네임스페이스 `codestar-connections` 유지, CodePipeline 액션 유형 이름은 `CodeStarSourceConnection`) [S19][S20] |
| AWS CodeArtifact | 패키지(npm·PyPI·Maven·NuGet·Swift·Ruby·Cargo·generic) | 빌드 시 의존성 조회, 사내 패키지 공유 [S24][S26] |
| Amazon ECR | 컨테이너 이미지 | Lambda 이미지 함수·컨테이너 서비스의 이미지 소스. 함수와 같은 Region [S2] |
| Amazon S3 | zip 번들·CodeDeploy 리비전 | CodePipeline 소스 액션, CodeDeploy 리비전 위치 [S20][S49] |

- CodePipeline 소스 액션 제공자: Amazon ECR, Amazon S3, Connections(Bitbucket Cloud·GitHub(GitHub App)·GitHub Enterprise Server·GitLab.com·GitLab self-managed), CodeCommit, GitHub(OAuth app) [S20]. GitHub는 GitHub App 방식(connections)이 권장이고 OAuth app 방식은 권장되지 않는다(기존 파이프라인은 계속 동작) [S21].
- CodeBuild의 소스 접근: GitHub·GitHub Enterprise Server는 개인 액세스 토큰·Secrets Manager 비밀·connection·OAuth 앱 중 하나로, Bitbucket은 액세스 토큰·앱 비밀번호·API 토큰·Secrets Manager 비밀·connection·OAuth 앱 중 하나로 접근하며 GitLab 접근 항목도 있다 [S22].
- CodeArtifact 개념: 리포지토리(여러 패키지 유형 혼합 가능)는 하나의 도메인에 속하고, 도메인이 패키지 자산·메타데이터를 한 번만 저장하며 같은 KMS 키로 암호화한다 [S26]. 업스트림 관계를 걸면 상위 리포지토리의 패키지(공개 저장소 외부 연결로 가져온 것 포함)가 하위 리포지토리에서 보인다. npmjs.com·Maven Central·PyPI 같은 공개 저장소와 외부 연결을 만들면 요청 시 가져와 저장해 두므로 빌드에서 항상 쓸 수 있다. CodeArtifact의 패키지는 공개할 수 없다 [S24].
- CodeArtifact 인증: AWS 자격 증명으로 권한 토큰을 발급한다(`aws codeartifact login`은 npm·pip·twine·dotnet·nuget·swift 설정까지 한 번에, 그 밖의 패키지 관리자는 `get-authorization-token`). 토큰 기본 유효 12시간, 15분~12시간으로 설정 가능, 루트 사용자는 `GetAuthorizationToken`을 호출할 수 없다 [S25].
- 정리: "소스를 어디서 가져오나(CodeCommit·외부 Git+CodeConnections·S3·ECR)", "의존성을 어디서 가져오나(CodeArtifact)", "무엇을 배포 단위로 보관하나(S3 zip·ECR 이미지)"를 분리해서 생각한다. 파이프라인·CodeDeploy 상세는 → Task 3.4.

### 리소스 요구 사항 적용 — 메모리·CPU·스토리지 (Skill 3.1.4)

**Lambda**
- 메모리 128–10,240 MB(1 MB 단위). CPU는 메모리에 비례해 선형 할당되며 별도의 CPU 설정은 없다. 1,769 MB에서 1 vCPU에 해당한다 [S1][S52]. (원리: CPU를 따로 팔지 않고 메모리에 묶어 배분하므로, CPU가 모자라면 메모리를 올린다.)
- 타임아웃 최대 900초(15분), `/tmp` 512–10,240 MB, 동기 호출 요청·응답 페이로드 각 6 MB [S1]. SAM에서는 `MemorySize`·`Timeout`·`EphemeralStorage`·`Architectures`로 지정한다 [S5].
- 신규 AWS 계정은 동시성·메모리 한도가 축소돼 있고 사용량에 따라 자동으로 상향된다 [S1].
- 적정 크기 찾기: AWS Compute Optimizer(14일 호출 이력 분석, 메모리 과다 할당 함수와 CPU 집약 함수 두 범주를 권고)와 Lambda Power Tuning으로 메모리별 성능·비용 균형점을 본다. 메모리를 과소 할당하면 실행 시간이 길어져 오히려 비용이 늘 수 있고, CPU 한계를 넘어선 증설은 효과가 떨어진다 [S53][S54].
- 아키텍처: x86_64(기본) 또는 arm64(Graviton2). arm64는 x86보다 비용이 낮다고 안내되지만 네이티브 의존성은 arm64용으로 다시 빌드해야 한다 [S55][S54].

**Amazon ECS**
- Fargate: 작업(task) 수준에서 CPU·메모리를 지정하며 유효한 조합만 허용된다 [S46].

| CPU 값 | 메모리 값 |
|---|---|
| 256 (.25 vCPU) | 512 MiB, 1 GB, 2 GB |
| 512 (.5 vCPU) | 1·2·3·4 GB |
| 1024 (1 vCPU) | 2~8 GB (1 GB 단위) |
| 2048 (2 vCPU) | 4~16 GB (1 GB 단위) |
| 4096 (4 vCPU) | 8~30 GB (1 GB 단위) |
| 8192 (8 vCPU) | 16~60 GB (4 GB 단위) |
| 16384 (16 vCPU) | 32~120 GB (8 GB 단위) |
| 32768 (32 vCPU) | 60 GB, 120 GB, 244 GB |

  8 vCPU 이상은 Linux 플랫폼 1.4.0 이상이 필요하다 [S46]. CPU 값은 CPU 단위(`1024`)나 vCPU(`1 vCPU`)로, 메모리는 MiB 또는 GB로 쓸 수 있다 [S46].
- EC2 시작 유형: 컨테이너 수준 `memory`(하드 한도, 초과하면 컨테이너가 종료됨)와 `memoryReservation`(소프트 한도). 둘 다 지정하면 `memory`가 `memoryReservation`보다 커야 한다 [S47].

**EC2 인스턴스**
- 인스턴스 유형은 CPU·메모리·스토리지·네트워크 용량의 조합이며 범주는 범용, 컴퓨팅 최적화, 메모리 최적화, 스토리지 최적화, 가속 컴퓨팅, HPC 등이다. 대용량 데이터를 메모리에서 처리하면 메모리 최적화, 고성능 프로세서가 필요한 계산이면 컴퓨팅 최적화를 고른다 [S56].

### 환경별 구성 준비 — 템플릿 파라미터·Mappings·Conditions·samconfig (Skill 3.1.5)

같은 템플릿·같은 아티팩트를 dev·staging·prod에 쓰고, 달라지는 값만 환경별로 주입한다. 환경별 스택 배포 자체는 → Task 3.2(3.2.4)·Task 3.3.

| 도구 | 역할 | 비고 |
|---|---|---|
| Parameters | 스택 생성·업데이트 시 값을 주입(예: `EnvironmentType`에 prod/test) | `sam deploy --parameter-overrides`·설정 파일 값이 템플릿 기본값보다 우선 [S10][S11]. 템플릿당 최대 200개, 값 최대 4,096바이트 [S42] |
| Mappings | 키-값 조회표(`Fn::FindInMap`)로 환경·Region별 값 선택 | 템플릿당 최대 200개 [S11][S42][S44] |
| Conditions | 조건이 참일 때만 리소스·출력을 만들거나 속성 값을 분기(`Fn::Equals`·`Fn::If` 등) | 입력·의사 파라미터, 다른 조건, 매핑 값으로 평가. 리소스 논리 ID·속성은 참조 불가 [S41] |
| SSM 파라미터 타입 | 템플릿 파라미터가 Parameter Store 값을 가리킴(`AWS::SSM::Parameter::Value<String>` 등) | `AWS::SSM::Parameter::Name`은 존재 확인용이며 값은 가져오지 않음 [S43]. 동적 참조는 템플릿당 60개 [S42] |
| samconfig (`samconfig.toml`) | 환경 이름별 SAM CLI 인자 묶음 | 아래 설명 |

- samconfig: 환경(environment)은 이름 붙은 설정 묶음이며 기본 이름은 `default`다. 명령별(`global`·`build`·`deploy`·`local_invoke` …)로 파라미터를 지정하고 `--config-env <이름>`으로 환경을 고른다. 위치는 `template.yaml`과 같은 프로젝트 루트, 기본 형식은 TOML(YAML도 지원)이며 `sam init`이 기본 파일을 만든다 [S10]. 형태 예: `[default.deploy.parameters]`, `[prod.deploy.parameters]` [S10].
- 우선순위(높음 → 낮음): 명령줄 값 > 설정 파일 값 > 템플릿 `Parameters` 기본값. 설정 파일 안에서는 명령별 항목이 `global`보다 우선한다 [S10].
- 원리: 환경 차이는 "코드"가 아니라 "값"이므로, 파라미터·설정 파일이 같은 템플릿에 다른 값을 주입하게 하면 환경마다 템플릿을 복제하지 않아도 된다.

### AWS AppConfig — 코드 재배포 없이 안전하게 구성 배포 (Skill 3.1.5 🆕)

**무엇인가**: 운영 중인 애플리케이션 동작을 코드 재배포 없이 안전하게 바꾸게 해 주는 서비스. 기능 플래그와 자유 형식(free-form) 동적 구성을 다루며, 허용·차단 목록, 스로틀링 한도, 로그 수준 같은 값을 즉시 조정하는 데 쓴다 [S27]. 시험 가이드 v2.1에서 새로 추가된 Skill이므로 직접 출제 가능성을 염두에 둔다.

**리소스 계층**: Application(네임스페이스, 폴더 같은 조직 단위) → Environment(배포 대상의 논리 그룹, 예: Beta·Production·Lambda 함수·컨테이너. 환경마다 CloudWatch 경보를 연결하면 배포 중 경보 시 자동 롤백) → Configuration profile(데이터 위치 URI + 유형 + 선택적 검증기) → Deployment strategy(배포 속도·베이크 타임) → Deployment(프로파일 버전 + 환경 + 전략) [S27][S33][S38].

| 프로파일 유형 | 데이터 위치 | 크기 한도(구성 저장소별) |
|---|---|---|
| Feature flags | AppConfig 호스팅 구성 저장소만(URI `hosted`) | 호스팅: 기본 2 MB, 최대 4 MB |
| Free-form | 호스팅 저장소, S3, CodePipeline, Secrets Manager, Parameter Store, SSM 문서 저장소 | S3 2 MB(AppConfig가 강제), Parameter Store 4 KB(표준)·8 KB(고급), Secrets Manager 64 KB, SSM 문서 64 KB, CodePipeline 2 MB |

[S33][S35]. 호스팅 저장소는 가능하면 우선 쓰라고 권장한다(기능이 가장 많음) [S33]. 다중 변형(multi-variant) 기능 플래그는 요청 컨텍스트와 사용자 정의 규칙에 따라 서로 다른 플래그 값을 반환한다 [S33].

**검증기(validators)** [S34][S27]
- 프로파일에 최대 2개. 쓰려면 프로파일보다 먼저 만들어야 한다.
- 유형: Lambda 함수(기능 플래그·free-form 모두 지원), JSON Schema(free-form 지원; 기능 플래그는 AppConfig가 자동으로 JSON Schema 검증).
- 배포 때 검증기를 평가하고 검증에 실패하면 변경을 자동 롤백한다 [S27].

**배포 전략의 구성 요소** [S28]

| 설정 | 의미 |
|---|---|
| 배포 유형 | Linear(증가분을 균등 간격으로) / Exponential(`G*(2^N)`, G는 단계 비율, N은 단계 수) |
| 단계 비율(step percentage, API·SDK에서는 growth factor) | 각 단계에서 대상으로 삼는 호출자 비율 |
| 배포 시간(deployment time) | 간격을 두고 배포를 처리하는 시간 창 — 타임아웃이 아니다 |
| 베이크 타임(bake time) | 100% 배포 후 CloudWatch 경보를 감시하는 시간. 이 안에 경보가 울리면 롤백(롤백 권한 설정 필요) |

- 원리: 베이크 타임이 있어야 100% 배포 직후가 아니라 시간이 지나 드러나는 오류도 자동 롤백으로 잡을 수 있다 [S28].

| 사전 정의 전략 | 동작 | 용도 |
|---|---|---|
| `AppConfig.Linear20PercentEvery6Minutes` | 6분마다 20%, 30분 배포, 30분 감시 | AWS 권장(프로덕션) |
| `AppConfig.Canary10Percent20Minutes` | 지수 방식 10% 성장 계수, 20분, 10분 감시 | AWS 권장(프로덕션) |
| `AppConfig.AllAtOnce` | 모든 대상에 즉시, 10분 감시 | 빠른 배포 |
| `AppConfig.Linear50PercentEvery30Seconds` | 30초마다 50%, 1분 배포, 1분 감시 | 테스트·데모 전용 |

[S29]. Agent(버전 2.0.136060 이상)는 특정 세그먼트·개별 사용자 단위 점진 배포(엔티티 기반)도 지원한다 [S28].

**롤백** [S37][S38]
1. 배포 중 환경에 연결된 CloudWatch 경보가 `ALARM`이면 자동 롤백(AppConfig가 경보를 읽을 IAM 역할 구성 필요).
2. 진행 중인 배포에 `StopDeployment`를 호출하면 상태 `ROLLED_BACK`.
3. 완료된 배포는 `StopDeployment`에 `AllowRevert`를 주어 되돌릴 수 있으나 성공 후 72시간 안에만 가능하다(결과 상태 `REVERTED`, 알람 모니터는 무시). 72시간 이후에는 새 배포를 만들어야 한다.

**구성 가져오기** [S27][S30][S31][S32][S39][S61]
- 권장 방식은 AppConfig Agent다. Lambda에서는 "AppConfig Agent Lambda extension"을 함수의 계층으로 추가한다. 함수는 `localhost:2772`의 HTTP 엔드포인트를 호출하고, 확장이 로컬 캐시를 두고 백그라운드에서 갱신한다. 그 결과 AppConfig API 호출·함수 처리 시간·비용이 줄고 스로틀링 위험이 없다(원리) [S30][S31][S61].
- 함수 실행 환경(동시성 단위)마다 확장 인스턴스와 캐시가 따로 있다. 변경이 함수에 반영되는 데 걸리는 시간은 배포 전략과 폴링 간격에 달려 있다 [S31].

| 확장 환경 변수 | 기본값 | 의미 |
|---|---|---|
| `AWS_APPCONFIG_EXTENSION_POLL_INTERVAL_SECONDS` | 45 | 갱신 폴링 주기 |
| `AWS_APPCONFIG_EXTENSION_POLL_TIMEOUT_MILLIS` | 3000ms | 응답 대기 한도(초과하면 이번 폴링을 건너뛰고 캐시 값 반환) |
| `AWS_APPCONFIG_EXTENSION_HTTP_PORT` | 2772 | 로컬 HTTP 서버 포트 |
| `AWS_APPCONFIG_EXTENSION_PREFETCH_LIST` | 없음 | 시작 시 미리 가져올 구성(콜드 스타트 단축) |
| `AWS_APPCONFIG_EXTENSION_ROLE_ARN` | 없음 | 다른 계정의 구성을 읽을 때 가정할 IAM 역할(한 계정에서만 읽을 수 있음) |

[S32]
- Agent가 맞지 않으면 앱이 직접 `StartConfigurationSession` → `GetLatestConfiguration`을 호출한다. 응답의 `NextPollConfigurationToken`을 다음 호출에 써야 하고, 토큰은 한 번만 쓰며 최대 24시간 유효하다(만료되면 `BadRequestException`) [S39].
- 요금은 구성 조회(호출·수신) 횟수에 따른 종량제이며, Lambda 콜드 스타트마다 호출이 발생해 비용에 반영된다 [S27][S30][S61].
- AppConfig Agent는 Lambda뿐 아니라 EC2·ECS·EKS에서도 쓴다 [S27].
- 구분: Lambda 별칭을 이용한 코드 점진 배포(CodeDeploy canary·linear)는 "코드" 배포이고, AppConfig 배포 전략은 "구성" 배포다 → CodeDeploy 상세는 Task 3.4.

## 시험에서 묻는 방식

> 문제 저작자를 위한 제안이다. 시험이 반드시 이렇게 낸다는 단정이 아니다.

1. **패키지 형태·번들 구조 선택 (Skill 3.1.1, 3.1.2)**
   - 상황: "머신러닝 라이브러리를 포함해 풀면 수 GB인 함수를 Lambda로 옮긴다. 기존 Docker 빌드 파이프라인을 재사용하고 싶다." / "여러 함수가 같은 라이브러리를 쓰는데 각 배포 패키지가 250 MB에 가깝다." / "CodeDeploy(또는 Elastic Beanstalk) 배포가 번들 구조 때문에 실패한다."
   - 정답 단서: 풀린 크기 250 MB 초과·Docker 재사용 → 컨테이너 이미지(10 GB, ECR, 계층 불가) / 공유·분리·SDK 버전 고정 → 계층(zip 전용, 최대 5개, 합산 250 MB, `/opt`, `python/` 같은 규정 경로) / `appspec.yml`이 루트에 없음 → 번들 루트로 이동 / EB 번들에 부모 폴더 포함 → 부모 폴더 없이 압축(`.ebextensions`는 명령줄 `zip`) / macOS에서 빌드한 네이티브 휠 → `--platform manylinux2014…` 또는 `sam build --use-container`.

2. **코드·패키지·이미지 저장소 선택 (Skill 3.1.3)**
   - 상황: "사내 npm 패키지를 팀 간에 공유하고 공개 레지스트리 의존성도 빌드에서 안정적으로 받아야 한다. 패키지는 외부에 공개되면 안 된다." / "GitHub에 푸시하면 파이프라인이 시작되게 하되 저장된 토큰은 두지 않으려 한다." / "IAM·VPC 엔드포인트로 통제되는 AWS 관리형 Git이 필요하다."
   - 정답 단서: 사설 패키지 + 공개 저장소 캐시 → CodeArtifact(도메인·리포지토리·업스트림/외부 연결, 토큰 12시간) / 외부 Git + 토큰 비저장 → CodeConnections(GitHub App 방식, connection ARN) / AWS 관리형 Git → CodeCommit(현재 신규 고객도 사용 가능) / 컨테이너 이미지 보관 → ECR.

3. **리소스 요구 사항 (Skill 3.1.4)**
   - 상황: "CPU 집약적인 Lambda 함수가 기본 설정에서 느리다. 코드는 바꾸지 않는다." / "Fargate 작업 정의에 CPU 1 vCPU, 메모리 1 GB를 지정했더니 등록이 거부된다." / "EC2 시작 유형 컨테이너가 메모리 초과로 종료된다."
   - 정답 단서: Lambda는 CPU 설정이 없고 메모리에 비례(1,769 MB ≈ 1 vCPU) → 메모리 증설(적정 크기는 Compute Optimizer·Power Tuning) / Fargate는 작업 수준의 유효한 CPU·메모리 조합만 허용(1 vCPU는 2~8 GB) / 컨테이너 `memory`는 하드 한도(초과 시 종료), `memoryReservation`은 소프트 한도.

4. **환경별 구성·AppConfig (Skill 3.1.5)**
   - 상황: "운영 구성 변경을 서서히 적용하다가 오류율 경보가 울리면 자동으로 되돌리고 싶다. 코드는 재배포하지 않는다." / "잘못된 JSON 구성이 배포되는 것을 막고 싶다." / "Lambda에서 구성 조회 API 호출 횟수와 지연을 줄이고 싶다." / "한 SAM 템플릿으로 dev와 prod에 서로 다른 값을 넣고 싶다."
   - 정답 단서: 점진 배포 + 경보 롤백 + 재배포 없음 → AppConfig(환경에 CloudWatch 경보, `Canary10Percent20Minutes`·`Linear20PercentEvery6Minutes`, 베이크 타임) / 구성 사전 검증 → 검증기(JSON Schema·Lambda) / 조회 비용·지연 절감 → AppConfig Agent Lambda extension(계층, `localhost:2772`, 로컬 캐시) / 환경별 값 → 템플릿 Parameters·Mappings·Conditions + `samconfig.toml` 환경과 `--config-env`.

| Lambda 메모리 vs CPU | CPU 설정 항목이 없어 찾게 됨 | CPU는 메모리에 비례해 자동 배분(1,769 MB ≈ 1 vCPU), 메모리를 올려 CPU를 올린다 | [S1][S52] |
| ECS `memory` vs `memoryReservation` | 둘 다 컨테이너 메모리 한도 | `memory`는 하드(초과하면 컨테이너 종료), `memoryReservation`은 소프트(경합 시 기준) | [S47] |

| 명령줄 vs `samconfig.toml` vs 템플릿 Parameters 기본값 | 같은 값이 여러 곳에 있을 때 | 명령줄 > 설정 파일(명령별 > global) > 템플릿 기본값 | [S10] |

### Q1 — 패키지 형태 선택
- 대응 Skill: 3.1.1 / 난이도: intermediate
- 문제: 한 팀이 이미지 처리 함수를 Lambda로 옮긴다. 머신러닝 라이브러리를 포함한 의존성을 풀면 약 3 GB이고, 기존 Docker 빌드 파이프라인을 재사용하려 한다. 코드는 최대한 바꾸지 않으려 한다. 가장 적절한 배포 패키지 방식은?
- 보기:
  - A. 의존성을 포함한 .zip 파일을 S3에 올린 뒤 함수 코드 위치로 지정한다.
  - B. 의존성을 Lambda 계층 5개로 나누어 함수에 연결한다.
  - C. 컨테이너 이미지로 빌드해 같은 Region의 Amazon ECR에 올리고 이미지 기반 함수를 만든다.
  - D. 라이브러리 파일을 함수의 환경 변수에 저장해 실행 시 불러온다.
- 정답: C
- 정답 근거: 컨테이너 이미지는 압축 해제 기준 최대 10 GB까지 지원하고, ECR에 올려 이미지 URI로 함수를 만든다. 반면 zip은 계층을 포함해 풀린 크기 250 MB가 상한이다. 근거: https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html , https://docs.aws.amazon.com/lambda/latest/dg/images-create.html
- 오답 해설:
  - A: S3 경유는 압축본 50 MB 업로드 한도만 우회할 뿐 풀린 크기 250 MB 한도는 그대로여서 3 GB는 올릴 수 없다.
  - B: 계층도 함수당 5개까지이며 계층 크기를 합쳐 250 MB(풀린 크기) 한도에 포함된다.
  - D: 환경 변수는 모든 값을 합쳐 4 KB까지만 허용되므로 라이브러리를 담을 수 없다.

### Q2 — AppConfig 점진 배포와 자동 롤백
- 대응 Skill: 3.1.5 / 난이도: intermediate
- 문제: 운영 중인 Lambda 함수가 읽는 기능 플래그 값을 한 번에 100% 적용하면 위험하다. 일부 트래픽에 먼저 적용하다가 오류율 경보가 울리면 자동으로 이전 값으로 되돌리고 싶고, 애플리케이션 코드는 재배포하지 않으려 한다. 무엇을 구성해야 하는가?
- 보기:
  - A. Lambda 환경 변수 값을 수정하고 새 함수 버전을 게시한다.
  - B. AppConfig 환경에 CloudWatch 경보를 연결하고 `AppConfig.Canary10Percent20Minutes` 같은 점진 배포 전략으로 구성을 배포한다.
  - C. Systems Manager Parameter Store 파라미터를 `put-parameter`로 덮어쓴다.
  - D. Secrets Manager 시크릿의 자동 교체를 켠다.
- 정답: B
- 정답 근거: AppConfig는 코드 재배포 없이 구성을 바꾸게 해 주며, 배포 전략으로 점진 배포하고 환경에 연결한 CloudWatch 경보가 울리면 자동으로 이전 버전으로 롤백한다. 근거: https://docs.aws.amazon.com/appconfig/latest/userguide/what-is-appconfig.html , https://docs.aws.amazon.com/appconfig/latest/userguide/appconfig-creating-deployment-strategy-predefined.html , https://docs.aws.amazon.com/appconfig/latest/userguide/appconfig-creating-environment.html
- 오답 해설:
  - A: 환경 변수는 버전별 구성이라 게시한 버전에서는 바꿀 수 없고 새 버전을 게시하는 방식이며, 배포 전략·베이크 타임·경보 롤백은 AppConfig가 제공하는 안전 기능이다.
  - C: Parameter Store는 구성 값 저장소이고 점진 배포·검증·경보 롤백은 AppConfig의 기능이다(AppConfig는 Parameter Store에 있는 데이터를 가져와 배포할 수도 있다).
  - D: Secrets Manager는 데이터베이스 자격 증명 같은 민감 정보를 저장하는 용도로 권장되는 서비스이며 기능 플래그를 점진 배포하는 수단이 아니다.

### Q3 — Lambda CPU 조정
- 대응 Skill: 3.1.4 / 난이도: foundational
- 문제: CPU 집약적인 Lambda 함수가 기본 설정(128 MB)에서 느리다. 코드를 바꾸지 않고 CPU 성능을 높이는 가장 직접적인 방법은?
- 보기:
  - A. 함수의 메모리 설정 값을 늘린다.
  - B. 함수의 타임아웃을 900초로 늘린다.
  - C. 임시 스토리지(`/tmp`) 크기를 10,240 MB로 늘린다.
  - D. 환경 변수 `CPU_COUNT`에 원하는 vCPU 수를 지정한다.
- 정답: A
- 정답 근거: Lambda는 CPU를 메모리에 비례해 선형으로 할당하며(1,769 MB에서 1 vCPU), 별도의 CPU 설정 항목은 없다. 근거: https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html , https://docs.aws.amazon.com/help-panel/lambda/latest/console/configuration-memory.html
- 오답 해설:
  - B: 타임아웃은 함수가 실행될 수 있는 최대 시간(최대 900초)일 뿐 CPU 할당 기준이 아니다.
  - C: `/tmp` 임시 스토리지는 디스크 공간 설정이며 CPU 할당은 메모리에 비례한다.
  - D: 환경 변수는 코드가 읽는 문자열 쌍으로 함수 동작을 조정하는 설정일 뿐 CPU 할당을 바꾸지 않는다.

### Q4 — 패키지 저장소 선택
- 대응 Skill: 3.1.3 / 난이도: intermediate
- 문제: 여러 팀이 사내 npm 패키지를 공유하고, 빌드에서는 npmjs.com의 공개 패키지도 안정적으로 받아야 한다. 패키지는 외부에 공개되면 안 되며 IAM으로 접근을 통제하려 한다. 가장 적절한 서비스는?
- 보기:
  - A. CodeCommit 리포지토리에 `node_modules` 폴더를 커밋한다.
  - B. Amazon ECR 리포지토리에 패키지를 이미지로 저장한다.
  - C. CodeArtifact 도메인에 리포지토리를 만들고 npmjs.com에 대한 외부 연결을 설정한다.
  - D. S3 버킷을 정적 웹 사이트로 호스팅해 패키지 파일을 배포한다.
- 정답: C
- 정답 근거: CodeArtifact는 npm 등을 지원하는 관리형 패키지 저장소로, 사설 패키지를 게시·공유하고 공개 저장소와 외부 연결을 만들어 요청 시 패키지를 가져와 저장한다. 패키지는 공개할 수 없고 AWS 자격 증명으로 만든 토큰으로 인증한다. 근거: https://docs.aws.amazon.com/codeartifact/latest/ug/welcome.html
- 오답 해설:
  - A: CodeCommit은 Git 리포지토리 호스팅(소스 관리) 서비스이고, npm 같은 패키지 관리자용 저장소는 CodeArtifact가 제공한다.
  - B: ECR은 컨테이너 이미지 저장소이며 npm 패키지 저장소 역할은 CodeArtifact가 맡는다.
  - D: S3 정적 웹 사이트 호스팅은 인증 토큰·업스트림·공개 저장소 외부 연결을 갖춘 패키지 저장소가 아니며, 이 기능은 CodeArtifact가 제공한다.

### Q5 — 배포 번들 구조
- 대응 Skill: 3.1.2 / 난이도: foundational
- 문제: 개발자가 EC2 인스턴스에 CodeDeploy로 배포하려고 번들을 만들었는데, AppSpec 파일을 `deploy/appspec.yml`처럼 하위 폴더에 넣었더니 배포가 실패한다. 올바른 조치는?
- 보기:
  - A. `appspec.yml`을 번들(리비전)의 루트 디렉터리로 옮긴다.
  - B. 파일 확장자를 `.yaml`로 바꾼다.
  - C. 번들을 S3 대신 Amazon ECR에 올린다.
  - D. `appspec.yml` 대신 `buildspec.yml`을 사용한다.
- 정답: A
- 정답 근거: EC2/온프레미스 배포의 AppSpec은 `appspec.yml`이라는 이름의 YAML 파일이며 애플리케이션 소스 구조의 루트에 두어야 하고, 그렇지 않으면 배포가 실패한다. 근거: https://docs.aws.amazon.com/codedeploy/latest/userguide/reference-appspec-file.html , https://docs.aws.amazon.com/codedeploy/latest/userguide/application-revisions-appspec-file.html
- 오답 해설:
  - B: 파일 이름은 `appspec.yml`이어야 하며 확장자 변경은 위치 문제를 해결하지 못한다.
  - C: EC2/온프레미스 리비전은 S3 버킷 또는 Git 리포지토리에 올리며, ECR은 컨테이너 이미지를 위한 저장소다.
  - D: `buildspec.yml`은 CodeBuild 빌드 명세이며 CodeDeploy 배포 명세를 대체하지 못한다.
