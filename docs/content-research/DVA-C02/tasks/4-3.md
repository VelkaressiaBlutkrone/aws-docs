### Lambda 동시성의 정의·계산·한도 (Skill 4.3.1)
- **정의**: 동시성 = 함수가 *동시에 처리 중인(in-flight) 요청 수*. 동시 요청 하나마다 별도 실행 환경이 만들어지고, 일을 끝낸 환경은 다음 요청에 재사용된다(재초기화 없음) [S1].
  - 원리: 기본 컴퓨트 유형에서 실행 환경 하나는 한 번에 요청 하나만 처리한다 → 동시 요청 수 = 필요한 실행 환경 수 [S1, S10].
- **계산식**: `동시성 = 평균 RPS × 평균 처리시간(초)`. 100 RPS × 0.5 s = 50, 200 RPS × 0.25 s = 50 — RPS가 2배여도 처리시간이 절반이면 동시성은 같다 [S1]. 현재 값은 `ConcurrentExecutions`(통계 MAX) [S6], 필요량 추정은 `Invocations`·`Duration` 메트릭 [S5]. 의존 서비스가 느려져 duration이 늘면 같은 RPS에서도 동시성이 늘어난다(S1 공식 + S42의 타임아웃 부하 테스트 권고에서 유도).
- **동시성 ≠ RPS**: 동기 호출의 RPS 한도 = 동시성 한도 × 10. 20 ms 함수가 30,000 RPS를 받으면 동시성은 600이라 기본 한도 1,000으로 충분해 보이지만 RPS 한도(10,000)에 걸려 스로틀 → 계정 한도를 3,000 이상으로 증설해야 한다 [S1].
- **한도 두 층**: 계정 한도 기본 1,000(리전별·증설 가능, 상한 표기 "Tens of thousands", 신규 계정은 축소 쿼터) [S3]. 함수 단위로 예약할 수 있는 양은 기본 900 — 항상 100은 예약 없는 함수 몫 [S1].
- **스케일링 속도(= 증가 속도, 한도와 별개)**: 함수마다 10초당 실행 환경 1,000개(또는 10,000 RPS)씩 늘릴 수 있고 함수끼리 독립이다. 안 쓴 몫은 누적되지 않으며, 더 빨리 몰리면 429로 스로틀된다 [S2]. 이전 모델은 계정 공유 500~3,000 + 분당 500이었다 [S14].
- **스로틀 시 동작**: 동기 호출 → 호출자에 429 `TooManyRequestsException` [S2, S15]. 비동기 호출 → 큐로 되돌려 최대 6시간(기본) 재시도, 간격은 1초에서 최대 5분까지 지수 증가 [S9]. 1분 단위 그래프에서 `Throttles` 스파이크 + `ConcurrentExecutions` 계단 모양이면 스케일링 속도 한계다 [S15].

- **SQS 표준 큐 기본 확장**: 처음엔 배치 5개를 동시 호출 5개로 시작 → 분당 최대 300개씩 호출 추가 → 이벤트 소스 매핑 하나의 상한 1,250. 한가하면 5개로, 최소 2개까지 줄어든다(최대 동시성을 켜면 이 절감 최적화는 없음). **FIFO**는 `min(메시지 그룹 ID 수, 최대 동시성)` [S7]. 동시 호출을 제한하려면 예약 동시성 대신 최대 동시성을 쓰라는 권고가 있고, 최대 동시성은 함수의 예약 동시성 이하로 둔다 [S7, S16].
- **Kinesis·DynamoDB 스트림**: 동시 호출 수 = 샤드 수 × `ParallelizationFactor`(기본 1, 최대 10). 같은 파티션 키의 순서는 유지된다 [S12].
- **API Gateway 쪽 스로틀**: 계정·리전 단위 10,000 RPS + 버스트(토큰 버킷 용량 5,000), 초과 시 429 [S13].
- **프로비저닝된 동시성 운영 요점**:
  - 할당은 1~2분 준비 후 함수당 분당 최대 6,000환경씩 진행되고, 요청한 수가 모두 할당될 때까지 사용할 수 없다 [S1]. 필요량 = 평균 RPS × 평균 duration, +10% 버퍼 권장 [S4].
  - 초기화 코드는 **할당 시점**에 실행되므로 핸들러 밖 초기화가 효과적이다. 환경 종류는 `AWS_LAMBDA_INITIALIZATION_TYPE`(`provisioned-concurrency`/`on-demand`)으로 확인 [S4]. 같은 버전에서 SnapStart와 동시 사용 불가 [S4, S81].
  - Application Auto Scaling: 예측 가능 → **예약(scheduled)**, 예측 불가 → **목표 추적**(`LambdaProvisionedConcurrencyUtilization`, 10~90%, 예 70% → 70% 초과 시 증가·63% 미만 시 감소). 초기값을 먼저 지정, 평균 통계는 짧은 버스트를 놓치므로 Maximum 통계가 낫고, 비활성 구간엔 메트릭이 안 나와 `INSUFFICIENT_DATA`가 되어 예상 밖 과금이 생길 수 있다 [S4].
  - 메트릭: `ProvisionedConcurrentExecutions`(MAX), `ProvisionedConcurrencyInvocations`(SUM), `ProvisionedConcurrencySpilloverInvocations`(SUM, 높으면 증설 신호), `ProvisionedConcurrencyUtilization`(낮으면 과할당). 계정 사용량은 `ClaimedAccountConcurrency` = 비예약 실행 + 할당된 동시성 [S6].
- **참고(가이드 v2.1 이후 신기능)**: Lambda Managed Instances는 실행 환경 하나가 여러 호출을 동시에 처리하는 다중 동시성 모델이고, 기본 최대 동시성은 vCPU당 Node.js 64·Java/.NET 32·Python 16이다 [S10, S11]. 시험 범위 여부는 미확인.

### 애플리케이션의 최소 메모리·컴퓨트 파워 결정 (Skill 4.3.3)
- **Lambda는 메모리 하나가 CPU까지 정한다**: 128~10,240 MB(1 MB 단위), CPU는 메모리에 비례(1,769 MB ≈ vCPU 1개). 메모리가 성능의 핵심 레버이고 기본값 128 MB는 최저값이다 [S34].
  - 원리: CPU·네트워크·메모리 바운드 함수는 메모리를 올리면 CPU가 함께 늘어 duration이 줄 수 있다 [S34]. duration 요금은 할당 메모리에 따라 달라지고 [S41], 비용은 속도와 균형을 맞추는 최적화 문제라 비용 최저점이 최고 메모리가 아닐 수 있다(공식 예시: 1024·1536 MB가 최저 비용, 3008 MB가 최고 속도). CPU 바운드는 효과가 크고 네트워크 바운드는 작다 [S33].
- **결정 도구 비교**

| 접근 | 근거 데이터 | 특징·한계 |
|---|---|---|

| Power Tuning | 여러 메모리 값으로 **실제 호출** | 비용·속도 곡선, CI/CD에 넣어 신규 함수 자동 측정 가능 [S34] |
| Compute Optimizer | 최근 14일 실사용 | opt-in(관리자 권한), 메모리 ≤ 1,792 MB·14일간 ≥ 50회 호출, 매일 갱신. 결과: Not optimized(Memory under/over-provisioned)·Optimized·Unavailable [S34,S35,S36] |
| Lambda Insights | 시간축 CPU·메모리 | 추가 비용 [S24] |

- **컨테이너·VM**: Fargate는 *태스크 수준* CPU·메모리가 필수이고 유효 조합만 허용(예: CPU 256 → 512 MiB/1 GB/2 GB) [S38]. 컨테이너 수준은 `memoryReservation`(소프트 한도)·`memory`(하드 한도)이며 `memoryReservation`은 Linux 컨테이너에서만 쓸 수 있다 [S39]. Compute Optimizer는 Fargate 서비스에 CPU·메모리 크기를 추천하고(24시간 이상 메트릭, 스텝 스케일링 없음, CPU·메모리 둘 다에 타깃 트래킹 없음) [S35,S37], EC2는 14일 중 30시간 이상 메트릭이 필요하다 [S35].
- **비용에 영향을 주는 최근 변화**: arm64(Graviton2)는 duration 요금 20% 낮고 최대 19% 성능 향상 [S40]. 2025-08-01부터 INIT 단계가 모든 구성에서 과금되어 관리형 런타임 ZIP 온디맨드도 Billed Duration에 INIT가 포함된다 → 콜드 스타트가 곧 비용 [S41].

### SNS 구독 필터 정책으로 메시징 최적화 (Skill 4.3.4)
- **기본 동작**: 구독에 필터 정책이 없으면 토픽의 모든 메시지를 받는다. 정책이 있으면 속성/본문이 조건을 모두 만족할 때만 전달하고 아니면 그 구독자에게 보내지 않는다 [S45]. 구독자 쪽 필터링 코드·불필요한 호출을 SNS로 넘기는 것이 목적이다.
  - 원리: 발행 시점에 SNS가 토픽의 구독마다 속성/본문을 정책과 비교한다 [S45].
- **스코프 비교** (`FilterPolicyScope` 구독 속성)

| 구분 | 속성 기반 `MessageAttributes` (기본) | 페이로드 기반 `MessageBody` |
|---|---|---|
| 대상 | 메시지 속성(String·String.Array·Number, Binary 무시) [S44] | 메시지 본문 JSON(올바른 JSON이어야 함) [S44,S45] |
| 중첩 정책 | 불가 [S44] | 가능, 리프 키만 5개 제한에 계산 [S44] |
| 설정 | 미설정이면 이쪽 [S46] | `FilterPolicyScope=MessageBody` (`set-subscription-attributes`) [S46,S51] |
| 반드시 이쪽 | 발행자가 속성을 붙이는 경우 | EventBridge·S3·SES·RDS·CloudTrail 이벤트(세부가 본문에 있음) [S52] |

- **연산자**(S43 목록): 문자열 — exact, `anything-but`(+prefix/suffix/wildcard), prefix, suffix, `equals-ignore-case`, wildcard, `cidr`(IP) [S47]; 숫자 — `=`, `anything-but`, `<` `<=` `>` `>=` 범위 [S48]; 키 — `exists`(리프만, true는 non-null·non-empty) [S49]; 논리 — 같은 키의 값 배열 = **OR**, 서로 다른 키 = **AND**, 같은 속성의 값끼리 AND는 불가, `$or` 배열(객체 2개 이상·예약어 없음)로 키 간 OR [S50].
- **한도**: 키 5개, 값 조합 150(키별 값 개수의 곱; 페이로드는 중첩 레벨도 곱함), 정책 256 KB, 토픽당 200개·계정당 10,000개, 와일드카드 복잡도 100점(패턴당 와일드카드 3개 이하), 문자열 비교는 대소문자 구분, 숫자는 ±10⁹·소수점 아래 5자리 [S44]. 정책 추가·변경은 반영에 최대 15분 [S43].
- **관측**: 걸러진 메시지는 `NumberOfNotificationsFilteredOut`(속성 불일치), `-InvalidAttributes`, `-MessageBody`, `-InvalidMessageBody` 메트릭으로 확인 [S53]. 필터 적용은 `FilterPolicy`/`FilterPolicyScope` 속성 설정, 제거는 `{}` [S51]. Raw message delivery는 필터의 전제 조건이 아니다 [S51].
- **비슷한 기능 구분**: Lambda 이벤트 소스 매핑의 `FilterCriteria`는 SQS·Kinesis·DynamoDB 등 소스 매핑 단위 필터다. SQS는 불일치 메시지를 큐에서 자동 삭제하고 스트림은 반복자가 넘어간다 [S54].

### CloudFront: 요청 헤더 기반 캐싱 (Skill 4.3.5)
- **캐시 키가 적중을 결정**: 같은 캐시 키를 만든 요청 = 캐시 적중. 기본 캐시 키는 배포 도메인 + URL 경로(OPTIONS는 메서드도 포함)이고 헤더·쿠키·쿼리 문자열은 기본적으로 키에 없다 [S56].
  - 원리: 키에 값을 더할수록 같은 객체의 사본이 늘어 적중률이 떨어지고 원본 요청이 늘어난다 → 응답을 실제로 바꾸는 값만 키에 넣는다 [S56, S62].
- **캐시 정책** = 캐시 키(헤더·쿠키·쿼리·압축) + TTL(Min/Default/Max). 헤더는 *이름*으로 지정하지만 값 전체가 키·원본 요청에 들어간다. 헤더 설정은 None / Include the following headers(정책당 기본 한도 10개, 증설 요청 가능) [S55,S63]. 캐시 정책에서는 "모든 헤더"를 지정할 수 없다 [S60].
- **원본 요청 정책** = 캐시 키에 넣지 않고 원본에만 보낼 값. 캐시 정책이 붙은 캐시 동작에서만 사용 가능 [S59,S60]. 캐시 키에 넣은 값은 자동으로 원본에도 전달된다 [S59].

| 구분 | 캐시 정책 | 원본 요청 정책 |
|---|---|---|
| 역할 | 캐시 키 + TTL(+압축) | 원본으로 보낼 헤더·쿠키·쿼리(캐시 키 제외) |
| 캐시 키 포함 | 예 (→ 원본에도 자동 전달) | 아니오 |
| 단독 사용 | 가능 | 불가(캐시 정책 필수) |
| 예 | `Accept-Language`처럼 응답이 바뀌는 값 | 분석·텔레메트리용 헤더 |

- **CloudFront가 추가하는 헤더**(디바이스 `CloudFront-Is-*-Viewer`, 위치 `CloudFront-Viewer-Country` 등)는 캐시 키에 넣어 변형별로 캐시할 수 있다. 단 `CloudFront-Viewer-Address`·`-ASN`과 TLS·JA3/JA4 계열은 원본 요청 정책에만 추가 가능 [S58].
- **TTL 상호작용** [S61]

| 원본 응답 | Min TTL = 0 | Min TTL > 0 |
|---|---|---|
| `Cache-Control: max-age` | min(max-age, Max TTL) | max-age가 [Min, Max] 안이면 max-age, 밖이면 가까운 경계값 |
| max-age 없음 | Default TTL | max(Min TTL, Default TTL) |
| `s-maxage` + `max-age` | min(s-maxage, Max TTL) (브라우저는 max-age) | s-maxage 기준으로 같은 클램프 |
| `Expires` | 그 날짜 또는 Max TTL 중 빠른 쪽 | 같은 클램프 |
| `no-cache`/`no-store`/`private` | 존중 | **무시하고 Min TTL만큼 캐시** |

- **헤더 캐싱의 성능 영향**: 값이 여러 개인 헤더를 키에 넣으면 같은 객체의 원본 요청이 늘어 느려지고 원본 부하가 커진다. 헤더 이름 대소문자·순서는 무관하지만 *값* 대소문자는 구분(`Acme` ≠ `acme` → 사본 2개) [S62]. `Accept-Language`는 `en-US,en`/`en,en-US` 같은 변형 때문에 중복 캐시가 생기므로 언어별 URL 경로 분리가 대안, `User-Agent`는 변형이 수천 가지라 부적합 [S56].
- **레거시·원본별 주의**: 레거시 설정에서 "모든 헤더 전달"을 고르면 캐싱이 일어나지 않는다 [S62]. S3 원본은 CORS·Lambda@Edge 개인화가 아니면 헤더 전달을 피하고, 사용자 지정 원본은 `Connection`·`Cookie`·`Proxy-Authorization`·`TE`·`Upgrade`(및 S3 원본의 `Host`)를 제외한 헤더로 캐시 가능, `Date`·`User-Agent`는 비권장 [S62].
- **압축**: gzip/Brotli 캐싱을 켜면 `Accept-Encoding`을 정규화해 키에 포함하며(원본 요청 정책에 따로 넣지 말 것), 원본이 압축본을 주지 않으면 켜지 않는다(적중률↓) [S55].
- **관리형 정책**: CachingOptimized(Min 1 s·Default 86,400 s·Max 31,536,000 s, 헤더·쿠키·쿼리 없음), CachingDisabled(전부 0), UseOriginCacheControlHeaders(Default 0, `Host`·`Origin` 등 헤더 + 모든 쿠키) [S57]. `stale-while-revalidate`·`stale-if-error`도 지원(상한은 Max TTL) [S61].

### 애플리케이션 수준 캐싱 구현 (Skill 4.3.6)
**① 캐시 채우기 전략 (ElastiCache)**

| 전략 | 동작 | 장점 | 단점 | 보완 |
|---|---|---|---|---|
| Lazy loading (= cache-aside) | 캐시 먼저 조회 → 미스면 DB 조회 후 캐시에 적재 [S64,S87] | 요청된 데이터만 캐시, 노드 장애에도 앱은 동작(지연만↑) | 미스 한 번에 왕복 3회, 데이터가 오래될 수 있음 | TTL, write-through |
| Write-through | DB에 쓸 때마다 캐시도 갱신 | 캐시가 항상 최신, 쓰기 지연엔 사용자가 더 관대 | 쓰기 왕복 2회, 신규·교체 노드는 데이터 누락, 안 읽히는 데이터가 캐시를 차지 | lazy loading 병행, TTL |
| + TTL | 키마다 만료 초 지정, 만료된 키는 "없음"으로 취급 | 오래됨에 상한, 캐시 정리 | 최신성 보장은 아님 | |

- 전략 출처 [S64]. 엔진 선택: **Memcached** = 가장 단순한 모델·멀티코어(멀티스레드) 큰 노드·노드 추가/제거로 스케일, 객체 캐시 [S65]. **Valkey/Redis OSS** = 고급 자료구조·스냅샷(지속성)·복제·트랜잭션·pub/sub·Lua·지리공간(Memcached에는 없음) [S86]. 적중률은 `CacheHits`/`CacheMisses` → `CacheHitRate`로 보고 0.8 이상이 모범 [S74].

**② DAX (DynamoDB 전용 인라인 캐시)**
- DAX는 **write-through** 캐시. 아이템 캐시(`GetItem`/`BatchGetItem`)와 쿼리 캐시(`Query`/`Scan` 결과)가 따로 있고 각각 기본 TTL 5분(파라미터 그룹 `record-ttl-millis`·`query-ttl-millis`로 변경) [S66,S67].
- 읽기: 미스 → 최종적 일관성 `GetItem`으로 DynamoDB 조회 후 적재. **강한 일관성 읽기·`TransactGetItems`는 캐시하지 않고 통과** [S66]. 쓰기: DAX 클라이언트로 쓰면 DynamoDB 성공 후 아이템 캐시를 갱신하지만 쿼리 캐시는 무효화하지 않아 TTL까지 오래된 결과가 남는다. DAX를 우회한 쓰기도 TTL까지 불일치 [S66]. 음성 캐시(없는 항목) 지원, 클러스터는 3노드 이상·다중 AZ 권장 [S66].
- 적합: 최단 읽기 지연, 소수 항목(핫 키)에 읽기 편중, 읽기 집중+비용 민감, 반복 대량 읽기. 부적합: 강한 일관성 필수, 마이크로초 불필요, 쓰기 집중, 반복 읽기 적음 [S68].

**③ API Gateway 캐시 (REST API, 스테이지 단위)**
- 기본 TTL 300초·최대 3,600초·TTL 0 = 비활성, 기본으로 **GET만** 캐시, 응답 최대 1,048,576바이트, 생성·삭제 약 4분, 용량 변경 시 캐시 재생성(데이터 삭제), 시간당 과금(프리 티어 아님) [S69]. 용량 값은 0.5/1.6/6.1/13.5/28.4/58.2/118/237(SDK 레퍼런스 `cacheClusterSize`) [S70]이고 크기는 GB 단위로 지정한다 [S88].
- 캐시 키: 메서드/통합 파라미터(헤더·경로·쿼리)를 최소 1개 지정, 값별로 따로 캐시 [S69]. 무효화: 스테이지 flush 또는 클라이언트의 `Cache-Control: max-age=0`(권한 `execute-api:InvalidateCache` 필요, 정책이 없으면 누구나 가능) [S69]. 모니터링: `CacheHitCount`/`CacheMissCount` [S69,S71].

**④ Lambda 수준 캐시**
- 실행 환경 재사용: SDK 클라이언트·DB 연결은 핸들러 밖에서 초기화하고 정적 자산은 `/tmp`에 캐시한다. 사용자 데이터 등 민감 정보는 두지 않고, 유휴 연결은 Lambda가 정리하므로 keep-alive를 쓴다 [S42].
- **Parameters and Secrets Lambda Extension**: 로컬 HTTP 엔드포인트의 메모리 캐시, 기본 TTL 300초(0~300초 설정, 0이면 캐시 우회), 시크릿 최대 1,000개 [S72,S73].
- (정리) 계층 선택: 정적·전 세계 → CloudFront / REST API 응답 → API Gateway 캐시 / DynamoDB 읽기 → DAX / 범용 DB·세션·복잡한 자료구조 → ElastiCache / 시크릿·파라미터 → 확장 / 인프로세스 → 실행 환경 재사용.

### 애플리케이션 성능 문제 분석 (Skill 4.3.8)
1. **증상 → 지표로 구간 좁히기**: Lambda `Duration`·`Throttles`·`ConcurrentExecutions`(1분 단위로 보면 스케일링 한계 판별) [S15], API Gateway `Latency`(클라이언트 요청 수신~응답, 통합 지연 포함) vs `IntegrationLatency`(백엔드 왕복) [S71], 스트림 `IteratorAge`(30,000 ms 알람 예) [S42].
2. **trace map에서 문제 노드 찾기**: CloudWatch 콘솔의 *Trace Map*(과거 X-Ray service map + ServiceLens map이 통합됨) [S28,S29]. 노드 윤곽 색 — 빨강 = 5xx 서버 오류, 노랑 = 4xx 클라이언트 오류, 보라 = 429 스로틀 [S29]. 노드·엣지를 고르면 응답시간 분포가 나오고 구간을 선택해 느린 트레이스만 필터링 [S29].
3. **트레이스 타임라인·로그로 내려가기**: 느린 세그먼트를 보고 "View logs"로 해당 노드 로그를 연다 [S29] (세그먼트 계측 → Task 4.2).
4. **이상 징후 자동 탐지**: X-Ray Insights는 오류율이 기대 범위를 넘으면 insight를 만들어 영향을 추적하고 EventBridge로 알린다 [S30]. Application Signals는 SLO·표준 지표·서비스 맵 [S26,S27].
5. (정리) 원인별 처방: 스로틀·동시성 → 4.3.1 / 메모리·CPU → 4.3.3 / 콜드 스타트 → PC·SnapStart / 반복 읽기 → 4.3.6 / 다운스트림·연결 → 4.3.7. 참고: Amazon DevOps Guru는 sunset(2027-09-30 종료) 공지가 났다 [S22].

### 애플리케이션 로그로 성능 병목 식별 (Skill 4.3.9)
- **REPORT 줄 필드** [S83]: `Duration`(핸들러 총 시간, INIT 제외) · `Billed Duration`(과금용 올림) · `Memory Size`(할당) · `Max Memory Used`(호출 중 최대 사용) · `Init Duration`(핸들러 밖 INIT 코드 시간 — 콜드 스타트 호출에만 나타남). 호출마다 START/END/REPORT 3줄이 자동 생성되고, 실행 환경마다 로그 스트림이 따로 생긴다.
- **Logs Insights 자동 필드**: `@timestamp @logStream @message @requestId @duration @billedDuration @type @maxMemoryUsed @memorySize`, X-Ray가 켜져 있으면 `@xrayTraceId`·`@xraySegmentId`도 포함 [S83].
- **공식 예제 쿼리**(발췌) [S83]

| 목적 | 쿼리 |
|---|---|
| 청구 시간 상위 호출 | `filter @type = "REPORT" \| fields @requestId, @billedDuration \| sort by @billedDuration desc \| limit 100` |
| 콜드 스타트 비율 | `filter @type = "REPORT" \| stats sum(strcontains(@message, "Init Duration"))/count(*) * 100 as coldStartPct, avg(@duration) by bin(5m)` |
| duration 백분위 | `filter @type = "REPORT" \| stats avg(@billedDuration) as Average, percentile(@billedDuration, 99) as NinetyNinth, percentile(@billedDuration, 95) as NinetyFifth, percentile(@billedDuration, 90) as Ninetieth by bin(30m)` |
| 메모리 100% 사용 호출 | `filter @type = "REPORT" and @maxMemoryUsed=@memorySize \| stats count_distinct(@requestId) by bin(30m)` |
| 타임아웃 호출 | `filter @message like /Task timed out/ \| stats count() by bin(30m)` |
| 메모리 과다 할당 | `filter @type = "REPORT" \| stats max(@memorySize / 1024 / 1024) as provisonedMemMB, min(@maxMemoryUsed / 1024 / 1024) as smallestMemReqMB, avg(@maxMemoryUsed / 1024 / 1024) as avgMemUsedMB, max(@maxMemoryUsed / 1024 / 1024) as maxMemUsedMB, provisonedMemMB - maxMemUsedMB as overProvisionedMB` |

- **해석 표**(정리 — 신호 → 의미 → 후속)

| 신호 | 의미 | 후속 |
|---|---|---|
| `Max Memory Used` ≈ `Memory Size` (`@maxMemoryUsed=@memorySize` 빈도↑) | 메모리 한계 근접 [S83,S42] | 메모리 증설·누수 점검 |
| `Max Memory Used` ≪ `Memory Size`, duration 길고 CPU 바운드 | 메모리는 남아도 CPU 부족일 수 있음 → 올리면 duration↓ [S34,S33] | Power Tuning으로 균형점 |
| `Init Duration`이 있는 호출 비율↑ | 콜드 스타트 [S83] | 프로비저닝된 동시성·SnapStart·초기화 경량화 [S4,S81] |
| `Task timed out` 증가 | 타임아웃(최대 900초) [S83,S3] | 타임아웃·다운스트림 점검 |
| `Billed Duration` > `Duration` | 올림 + (2025-08-01 이후) INIT 포함 [S83,S41] | 과거 데이터와 비교 시 주의 |

- 구조화(JSON) 로그는 Logs Insights가 필드를 자동 인식해 `filter uploadTimeMS > 1000`처럼 바로 조건을 걸 수 있다 [S83]. 커스텀 지표는 동기 API 호출 대신 EMF로 로그에 실어 지연을 줄인다 [S42].
- **쿼리 제약**: 타임아웃 60분, 쿼리당 로그 그룹 최대 50개 [S84]. 동시 쿼리 한도는 자료마다 30 [S84] vs 100 [S85] → 확인 필요 #10.

## 시험에서 묻는 방식

> 문제 저작자를 위한 제안이다. 시험이 반드시 이렇게 낸다는 뜻이 아니다.

1. **동시성 제어 고르기** — "평일 오전 9시마다 트래픽이 몰려 첫 몇 분 동안 콜드 스타트로 응답이 느리다. 피크 시간이 예측 가능하고 비용도 아끼고 싶다." → 단서: *예측 가능한 피크 + 지연 민감 + 콜드 스타트* → **프로비저닝된 동시성**(버전/별칭) + Application Auto Scaling **예약(scheduled) 스케일링** [S4]. 변형 ① "SQS를 소비하는 Lambda가 급증해 RDS 연결이 폭주한다" → *다운스트림 보호·큐 소비* → **SQS 이벤트 소스 최대 동시성**(또는 예약 동시성)·**RDS Proxy** [S5,S7,S77]. 변형 ② "20 ms 짜리 함수가 초당 수만 건에서 스로틀된다" → *RPS 한도 = 동시성 한도 × 10* → **계정 동시성 한도 증설** [S1].
2. **캐시 계층 고르기** — "DynamoDB 핫 키 읽기를 마이크로초로, 코드 변경은 최소, 최종적 일관성 허용" → **DAX**(강한 일관성 읽기는 통과) [S66,S68]. "세션·리더보드·복잡한 자료구조" → **ElastiCache**(Valkey/Redis OSS) [S86]. "REST API 응답이 반복되고 TTL로 충분" → **API Gateway 스테이지 캐시**(기본 300초, 최대 3,600초) [S69]. "Lambda가 매 호출 Secrets Manager/Parameter Store를 호출한다" → **Parameters and Secrets 확장 캐시**(기본 300초) [S72,S73].
3. **메시지 필터링·헤더 캐싱** — "SNS 구독자 3개가 서로 다른 이벤트만 필요" → **구독 필터 정책**(속성 기반), "S3/EventBridge 이벤트라 속성이 없다" → `FilterPolicyScope=MessageBody` + 중첩 키 [S44,S52]. "언어·디바이스별 응답이 달라야 하는데 캐시 적중률이 낮다" → 응답을 바꾸는 헤더만 **캐시 정책**에, 분석용 값은 **원본 요청 정책**에, 값 변형이 큰 헤더는 키에서 빼고 URL로 분리 [S55,S56,S59].
4. **로그·트레이스로 병목 진단과 크기 결정** — "가끔 느린 Lambda — 콜드 스타트인가?" → Logs Insights로 REPORT의 `Init Duration` 유무 집계 [S83]. "메모리가 부족한가, 과한가?" → `Max Memory Used` vs `Memory Size`, Power Tuning, Compute Optimizer [S34,S36,S83]. "마이크로서비스 체인에서 어느 호출이 느린가?" → X-Ray trace map·응답시간 분포 → 트레이스 [S29]. "어느 메서드가 CPU를 쓰는가?" → 코드 수준 프로파일러(CodeGuru Profiler, 현황은 확인 필요 #6) [S17].

## 흔한 함정·혼동 짝

| # | A vs B | 혼동 이유 | 구분 기준 한 줄 | 출처 |
|---|---|---|---|---|
| 1 | 예약 동시성 vs 프로비저닝된 동시성 | "예약"이라는 말에서 미리 준비(초기화)됐다고 오해 | 예약 = 상한+독점 보장(무료, 콜드 스타트 가능) / 프로비저닝 = 사전 초기화(유료, 콜드 스타트 제거, 버전·별칭 대상) | [S1,S4] |
| 2 | 동시성 vs RPS | 둘 다 "처리량"처럼 보임 | 동시성 = RPS × duration(초), 동기 RPS 한도 = 동시성 한도 × 10 → 짧은 함수는 RPS 한도가 먼저 막힘 | [S1] |
| 3 | 계정 동시성 한도 vs 스케일링 속도 | 둘 다 "스케일 한계" | 한도 = 총량(기본 1,000), 속도 = 함수당 10초에 환경 1,000개 증가(함수별 독립) | [S2] |
| 4 | SQS 최대 동시성 vs 함수 예약 동시성 | 둘 다 동시 실행 제한 | 최대 동시성 = 이벤트 소스 단위(2~1,000, 무료), 예약 동시성 = 함수 전체. 최대 동시성 ≤ 예약 동시성으로 설정 | [S7,S16] |
| 5 | SNS `MessageAttributes` vs `MessageBody` 스코프 | 같은 FilterPolicy JSON인데 비교 대상이 다름 | 기본 = 속성(중첩 불가), 본문 = 중첩 가능(리프 키만 5개 제한), AWS 서비스 이벤트는 본문 | [S44,S46,S52] |
| 6 | SNS 필터 AND vs OR | 값 배열·여러 키·`$or`가 섞임 | 서로 다른 키 = AND, 같은 키의 값 배열 = OR, 같은 속성 값끼리 AND 불가, 키 간 OR는 `$or` | [S50] |
| 7 | SNS 구독 필터 정책 vs Lambda 이벤트 소스 필터 | 둘 다 "불필요한 호출 줄이기" | SNS = 토픽 구독 단위, Lambda `FilterCriteria` = 소스 매핑 단위(SQS는 불일치 메시지를 큐에서 삭제) | [S45,S54] |
| 8 | CloudFront 캐시 정책 vs 원본 요청 정책 | 둘 다 "헤더 전달" 설정 | 캐시 정책 = 캐시 키+TTL(키에 넣으면 원본에도 전달), 원본 요청 정책 = 키에 안 넣고 원본에만, 캐시 정책 없이는 불가 | [S55,S59,S60] |
| 9 | 캐시 키에 헤더 넣기 vs 적중률 / 최소 TTL > 0 vs `no-cache` | "정확히 서빙하면 더 좋다", "원본 지시가 우선일 것" | 변형 많은 헤더는 키 폭증→적중률↓, 헤더 이름은 지정하되 값 전체가 키. 최소 TTL > 0이면 `no-cache`/`no-store`/`private`도 무시하고 캐시 | [S55,S56,S62] |
| 10 | Lazy loading vs Write-through | 둘 다 캐시를 채우는 전략 | 지연 로딩 = 읽을 때 채움(미스 3왕복·오래됨 가능·노드 장애에 강함) / 쓰기 통과 = 쓸 때 채움(최신·쓰기 2왕복·새 노드 누락·낭비) → TTL로 보완 | [S64] |
| 11 | DAX 아이템 캐시 vs 쿼리 캐시 | 둘 다 DAX 캐시 | 아이템 = `GetItem`/`BatchGetItem`, 쿼리 = `Query`/`Scan` 결과. 쓰기는 아이템 캐시만 갱신(쿼리 캐시는 TTL까지 유지), 강한 일관성 읽기는 캐시 안 함 | [S66] |
| 12 | X-Ray vs CodeGuru Profiler vs Lambda Insights | 모두 "성능 분석 도구" | X-Ray = 요청 경로별 구간 지연 / Profiler = 코드 수준 CPU·힙 / Lambda Insights = 함수 시스템 지표·콜드 스타트 | [S17,S24,S28] |

## 자가 점검 문항 후보

> **초안·미검수** — 사람이 검수하기 전에는 `verified: true`로 쓰지 말 것. 정답 근거는 이번 세션에 열람한 공식 페이지다.

**Q1 — 대응 Skill 4.3.1 · 난이도 advanced**
- 문제: 어떤 Lambda 함수의 평균 실행 시간은 20 ms이고 피크 때 초당 30,000건의 동기 요청을 받는다. 계정 동시성 한도는 기본값(1,000)이며 이 함수에는 예약·프로비저닝된 동시성이 없다. 스로틀링 없이 처리하려면 무엇이 필요한가?
- A. 함수에 예약 동시성 600을 설정한다.
- B. 계정 동시성 한도를 3,000 이상으로 증설 요청한다.
- C. 함수에 프로비저닝된 동시성 600을 설정한다.
- D. 함수 메모리를 늘려 평균 실행 시간을 10 ms로 줄이면 기본 한도로 충분하다.
- 정답: **B**
- 정답 근거: 동시성은 30,000 × 0.02 = 600이지만 동기 호출의 RPS 한도는 동시성 한도의 10배(기본 10,000)라서 30,000 RPS를 받으려면 한도를 3,000 이상으로 올려야 한다. 근거: https://docs.aws.amazon.com/lambda/latest/dg/lambda-concurrency.html [S1]
- 오답 해설: A — 예약 동시성은 계정 한도 안에서 몫을 떼어 두는 것일 뿐 한도(및 RPS 한도)를 늘리지 못한다 [S1]. C — 프로비저닝된 동시성도 계정 한도에 포함되고 같은 RPS 제한을 받으며, 목적은 콜드 스타트 제거다 [S1]. D — duration을 10 ms로 줄이면 동시성은 300이 되지만 RPS 한도는 그대로 10,000이라 여전히 스로틀된다 [S1].

**Q2 — 대응 Skill 4.3.3 · 난이도 intermediate**
- 문제: CPU 집약 연산을 하는 Lambda 함수가 512 MB로 구성돼 있다. CloudWatch Logs의 REPORT 줄이 `Duration: 12000.00 ms  Billed Duration: 12001 ms  Memory Size: 512 MB  Max Memory Used: 35 MB`로 나온다. 실행 시간을 줄이면서 비용 대비 효과를 측정하려면 어떻게 해야 하는가?
- A. `Max Memory Used`가 낮으므로 메모리를 128 MB로 줄인다.
- B. 메모리를 늘려 CPU를 함께 늘려 보고, AWS Lambda Power Tuning으로 비용·시간 균형점을 찾는다.
- C. 프로비저닝된 동시성을 추가한다.
- D. 예약 동시성을 늘린다.
- 정답: **B**
- 정답 근거: Lambda는 메모리에 비례해 CPU를 할당하고(1,769 MB ≈ vCPU 1개), CPU 바운드 함수는 메모리를 올리면 성능이 크게 좋아질 수 있으며, Power Tuning은 여러 메모리 값에서 실제 호출을 측정해 준다. 근거: https://docs.aws.amazon.com/lambda/latest/dg/configuration-memory.html [S34]
- 오답 해설: A — 메모리를 줄이면 CPU도 줄어 duration이 더 길어질 수 있고, `Max Memory Used`는 메모리 부족 여부만 알려 줄 뿐 CPU 병목은 알려 주지 않는다 [S34]. C — 프로비저닝된 동시성은 초기화(콜드 스타트)를 줄이는 수단이라 핸들러 `Duration`을 줄이지 못한다 [S1,S4]. D — 예약 동시성은 동시 실행 수의 상한·보장일 뿐 개별 호출 속도와 무관하다 [S1].

**Q3 — 대응 Skill 4.3.4 · 난이도 intermediate**
- 문제: Amazon S3 이벤트 알림이 SNS 토픽으로 발행되고, 한 SQS 구독자는 `uploads/` 접두사 아래의 `ObjectCreated:` 이벤트만 받아야 한다. S3가 발행한 메시지에는 사용자 정의 메시지 속성이 없다. 구독 필터 정책을 어떻게 구성해야 하는가?
- A. 기본 스코프(`MessageAttributes`)에서 `eventName`과 `key` 속성을 조건으로 하는 정책을 적용한다.
- B. `FilterPolicyScope`를 `MessageBody`로 바꾸고 `Records.eventName`과 `Records.s3.object.key`를 중첩 키로 지정한 정책을 적용한다.
- C. 구독에 `RawMessageDelivery`를 켜서 필터링되도록 한다.
- D. 스코프는 그대로 두고 `prefix` 연산자로 `Records` 아래 값을 조건에 건다.
- 정답: **B**
- 정답 근거: S3 이벤트 알림은 세부 정보를 메시지 본문에 담으므로 `MessageBody` 스코프 필터가 필요하고, 중첩 정책은 페이로드 기반 필터링에서만 허용된다. 근거: https://repost.aws/knowledge-center/sns-troubleshoot-message-filtering [S52], https://docs.aws.amazon.com/sns/latest/dg/subscription-filter-policy-constraints.html [S44]
- 오답 해설: A — 속성이 없는데다 속성 기반 필터는 속성만 비교하고 중첩 정책을 받지 않는다 [S44]. C — Raw message delivery는 필터의 전제 조건이 아니고 필터링 기능과 직접 관련이 없다 [S51]. D — 스코프가 `MessageAttributes`인 동안은 연산자 종류와 무관하게 메시지 속성만 평가한다 [S45].

**Q4 — 대응 Skill 4.3.5 · 난이도 intermediate**
- 문제: 웹 앱이 `Accept-Language` 요청 헤더에 따라 언어별 HTML을 반환한다. CloudFront 캐시 정책의 캐시 키에 `Accept-Language`를 넣었더니 `en-US,en`, `en,en-US`, `en-US`처럼 값 변형이 많아 캐시 적중률이 크게 떨어졌다. 언어별 콘텐츠는 계속 제공하면서 적중률을 높이는 가장 적절한 방법은?
- A. 캐시 키에 `User-Agent` 헤더도 추가한다.
- B. 언어별로 URL 경로를 분리(`/en-US/...`)하고 `Accept-Language`를 캐시 키에서 뺀다.
- C. 캐시 정책의 최소 TTL을 0으로 낮춘다.
- D. 레거시 설정에서 모든 헤더를 원본에 전달한다.
- 정답: **B**
- 정답 근거: 값 변형이 많은 헤더를 키에 넣으면 같은 객체가 여러 번 캐시되어 적중률이 떨어지며, 공식 문서는 헤더를 키에서 빼고 언어별로 다른 URL을 쓰도록 앱을 구성하는 것을 대안으로 제시한다. 근거: https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/understanding-the-cache-key.html [S56]
- 오답 해설: A — `User-Agent`는 변형이 수천 가지라 캐시 키 후보로 부적합하다 [S56]. C — TTL은 객체가 캐시에 머무는 기간이라 키 변형으로 생기는 사본 중복을 해결하지 못한다 [S55]. D — 레거시 설정에서 모든 헤더를 전달하면 캐싱이 일어나지 않는다 [S62].

**Q5 — 대응 Skill 4.3.6 · 난이도 intermediate**
- 문제: DynamoDB 상품 테이블에서 일부 인기 상품 키에 읽기가 몰려 읽기 지연이 늘었다. 해당 읽기는 최종적 일관성이면 충분하고, 마이크로초 단위 읽기 지연과 최소한의 코드 변경을 원한다. 가장 적절한 해법은?
- A. DAX 클러스터를 배포하고 DAX 클라이언트로 읽는다.
- B. 모든 읽기를 `ConsistentRead=true`로 바꾼다.
- C. ElastiCache를 추가하고 애플리케이션 코드에서 lazy loading 로직을 구현한다.
- D. API Gateway 스테이지 캐시를 켠다.
- 정답: **A**
- 정답 근거: DAX는 최종적 일관성 데이터를 마이크로초 지연으로 제공하는 DynamoDB용 인메모리 캐시이고, 소수 항목(핫 키)에 읽기가 몰리는 앱에 적합하다. 근거: https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/DAX.html [S68]
- 오답 해설: B — DAX는 강한 일관성 읽기를 캐시하지 않고 DynamoDB로 통과시킨다 [S66]. C — ElastiCache lazy loading은 캐시 조회·적재 로직을 코드로 구현해야 하므로 "최소 코드 변경"에 맞지 않는다(DAX 클라이언트는 `GetItem` 등 DynamoDB와 같은 API 작업을 지원) [S64,S66]. D — API Gateway 캐시는 REST API 응답을 스테이지 단위로 캐시하므로 DynamoDB 직접 읽기와 무관하다 [S69].
