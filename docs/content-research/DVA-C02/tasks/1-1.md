### 코레오그래피 vs 오케스트레이션 (Skill 1.1.1)

| 구분 | 코레오그래피 | 오케스트레이션 |
|---|---|---|
| 제어 | 중앙 조정 없음. 컴포넌트가 작업을 받아 처리하고 필요하면 다음 작업을 발행 [S3] | 단일 오케스트레이터가 각 마이크로서비스를 호출하고 순차/병렬 여부 결정, 응답 가공, 최종 결과 취합 [S4] |
| AWS 대표 | EventBridge: 중앙 조정 없이 서비스 사이로 이벤트가 흐름 [S5] | Step Functions(서비스 호출 순서·상호작용을 조율), Amazon MWAA [S4][S5] |
| 강점 | 서비스를 독립 확장, 각 서비스가 자기 오류 처리·동시성 제어 [S3] | 분기 로직을 한곳에 캡슐화, 모니터링·관측성 향상, 콜백 대기(claim check) 구현 [S4] |
| 선택 단서 | "이벤트에 각자 반응", "소비자 추가 시 기존 코드 무변경" | "분기·재시도·사람 승인이 섞인 다단계", "한곳에서 진행 추적" |

- Step Functions Standard 워크플로는 최대 1년 장기 실행을 지원하고, Express는 짧고 대량인 워크로드에 유리하다 [S4]. 둘을 함께 쓰는 앱이 많다(예: EventBridge 이벤트·스케줄로 워크플로 시작) [S5].
- 원리: 코레오그래피는 "이벤트가 흐름을 만든다", 오케스트레이션은 "지휘자가 흐름을 만든다". 흐름을 한눈에 봐야 하거나 분기·실패 처리가 많으면 지휘자가 낫다.

### 팬아웃 (Skill 1.1.1, 1.1.8)

- 팬아웃 = 게시된 메시지 하나를 여러 엔드포인트로 복제·푸시해 병렬 비동기 처리하는 패턴 [S12].
- SNS→SQS 팬아웃(topic-queue chaining): 구독 서비스 앞마다 SQS 큐를 둔다. 큐가 메시지를 내구적으로 버퍼링하므로 구독 프로세스가 몇 시간~며칠 장애여도 유실이 없고, 큐가 "버퍼링 로드밸런서"가 되어 구독자를 쉽게 스케일 인/아웃한다 [S12].
- EventBridge는 한 이벤트가 여러 규칙에 일치할 수 있고 규칙당 최대 5개 대상으로 전달한다 [S80].
- 원리: SNS는 "복제·푸시", SQS는 "분리·버퍼링"을 맡는다 [S12]. SNS 구독자가 바로 엔드포인트이면 전달 실패를 SNS의 재시도 정책에 의존하지만 [S56], 큐를 끼우면 구독자가 자기 속도로 큐에서 가져간다.

### 스테이트풀 vs 스테이트리스 (Skill 1.1.2)

| 구분 | 스테이트풀 | 스테이트리스 |
|---|---|---|
| 정의 | 한 세션의 데이터가 다음 세션으로 이어짐 [S7] | 세션 간 데이터를 보존하지 않고 DB·캐시 같은 외부 개체에 상태 관리를 맡김 [S7] |
| 특징 | 배포가 단순하고 서버에 세션을 저장해 처리가 빠름 [S7] | 수평 확장·동적 배포에 유리, 트래픽 급증·장애에 탄력적 [S7]. 서버를 마음대로 교체해도 가용성 영향 없음 [S6] |
| 상태 위치 | 서버 로컬 메모리·디스크 | 외부 저장소로 오프로드. 세션 데이터는 ElastiCache·DynamoDB·EFS·MemoryDB, 큰 비정형 데이터는 S3 [S6] |

- 스테이트리스로 설계하면 어떤 컴퓨트(EC2, Lambda 등)도 어떤 요청이든 처리할 수 있어 수평 확장이 쉽고, 그래서 Lambda·Fargate 같은 서버리스 컴퓨트를 쓸 수 있다 [S6].
- Lambda: 실행 환경이 "한 번의 호출에만 존재한다고 가정"하고, 영구 데이터는 S3·DynamoDB·SQS 같은 내구 저장소에 커밋한 뒤 종료한다. 로컬 데이터 구조·임시 파일·호출 간 내부 상태에 의존하지 않는다 [S8].
- 다만 실행 환경은 재사용될 수 있어, 전역(초기화) 코드에서 DB 연결·라이브러리를 만들어 초기화 비용을 여러 호출에 분할상환할 수 있다. 호출별 데이터를 전역에 넣지는 말 것 [S8].
- 원리: 상태가 서버에 있으면 그 서버가 "대체 불가능한 서버"가 되어 교체·확장이 막힌다. 상태를 밖으로 빼면 서버는 대체 가능한 소모품이 된다 [S6].

### 강결합 vs 느슨한 결합 (Skill 1.1.3)

| 구분 | 강결합 | 느슨한 결합 |
|---|---|---|
| 정의 | 한 컴포넌트가 바뀌면 의존하는 컴포넌트도 바꿔야 함 [S9] | 의존 컴포넌트는 버전 관리되고 게시된 인터페이스만 알면 됨 [S9] |
| 장애·변경 | 변경·장애가 연쇄되어 컴포넌트 전반의 성능이 저하 [S9] | 한 컴포넌트의 장애가 다른 컴포넌트로 번지지 않게 격리 [S9] |
| 수단 | 직접 점대점 호출 [S9] | SQS 큐·Kinesis·Step Functions 같은 중간 내구 계층, EventBridge(생산자를 소비자로부터 추상화), SNS(고처리량 푸시 기반 다대다) [S9] |

- 즉시 응답이 필요 없고 "요청이 등록되었다"는 확인이면 충분한 상호작용은 비동기로 바꾸고 중간 계층(큐 등)을 둔다 [S9].
- 주의: 하드 리얼타임 시스템에서는 임계 시간(보통 수 초)보다 오래된 큐 요청은 클라이언트가 이미 포기했을 수 있어 stale로 보고 처리하지 않는 편이 낫다 [S9].
- 흔한 안티패턴(강결합 신호): 모놀리식 워크로드 배포, 장애 조치·비동기 처리 능력 없이 워크로드 계층끼리 API를 직접 호출, 공유 데이터베이스로 데이터를 공유해 결합, 백프레셔(처리 속도를 못 맞출 때 유입을 늦추거나 멈추는 능력) 무시 [S9].

### 동기 vs 비동기 (Skill 1.1.4)

| 구분 | 동기 | 비동기 |
|---|---|---|
| 정의 | 호출자가 응답을 기다린 뒤 진행(실시간 HTTP REST 호출) [S10] | 호출자가 기다리지 않고 계속 진행(메시지 큐) [S10] |
| 호출자가 받는 것 | 결과 | 보통 "요청 접수" 확인만 [S11] |
| 장점 | 단순, 즉시 결과 | 이벤트 기반에 적합, 용량 기준 처리, 장애 격리, 큐로 피크 흡수 [S11] |
| 단점 | 지연·실패가 호출 사슬로 연쇄될 수 있음 [S25] | 결과 회수 방법 필요, 여러 시스템 로그 추적·테스트가 어려움 [S11] |
| 구현 방식 | — | fire and forget, claim check, callback, bidirectional [S11] |

| 호출 경로 | 동기 | 비동기 |
|---|---|---|
| Lambda Invoke API | 기본값(`RequestResponse`): 응답을 기다림. Lambda가 함수를 실행할 수 있었다면 함수가 오류를 반환해도 상태 코드 200 [S13] | `InvocationType=Event`: 이벤트를 큐에 넣고 성공 응답(CLI 예시 202) 반환 [S14] |
| 페이로드 한도 | 6 MB | 1 MB [S15] |
| API Gateway→Lambda | 별도 설정이 없으면 Invoke API 기본값인 동기 [S15] | Integration request에 `X-Amz-Invocation-Type` 헤더를 `'Event'`로 고정(또는 클라이언트가 `InvocationType` 헤더로 선택) [S37] |

- 오류·재시도 책임: 동기 호출은 호출자가 응답의 오류를 확인해 재시도해야 한다(AWS CLI·SDK는 클라이언트 타임아웃·스로틀링·서비스 오류에서 자동 재시도) [S13]. 비동기 호출은 Lambda가 함수 오류 시 최대 2회 더 실행하고, 처리하지 못한 이벤트는 DLQ로 보존한다 [S15].
- 원리: 비동기는 "접수 확인"만 즉시 돌려주므로 호출자 지연이 줄지만, 결과·실패는 별도 경로(DLQ·콜백·이벤트)로 받아야 한다.

### 내결함성·복원력 있는 애플리케이션 코드 (Skill 1.1.5)

복원력 도구 상자: 타임아웃 → 재시도(백오프+지터) → 멱등성 → 재시도 한도·서킷 브레이커 → DLQ·우아한 실패.

- "To build resilient systems, we employ three essential tools: timeouts, retries, and backoff." [S21].
- 타임아웃: 서비스 의존 호출마다 연결 타임아웃과 요청 타임아웃을 모두 설정한다. 프레임워크 기본값이 무한이거나 과도할 수 있다. 너무 길면 기다리는 동안 자원을 소모하고, 너무 짧으면 재시도가 늘어 최악엔 전면 장애가 난다 [S23].
- 재시도는 "서버 용량을 더 쓰는 행위"다. 호출 스택의 여러 계층이 각자 재시도하면 하위 서비스 부하가 곱절로 늘어나므로 한 지점에서만 재시도하고, 로컬 토큰 버킷으로 재시도를 제한하는 편이 낫다는 것이 Builders' Library의 논지다(요약본 기준, [S20]).
- 지터가 없으면 같은 시점에 실패한 클라이언트가 같은 시점에 재시도해 재시도 폭주(thundering herd)가 생긴다. 전체 지터는 재시도를 백오프 구간 전체에 균등 분산한다 [S16]. REL05-BP03은 지수 백오프·지터·최대 재시도 횟수 제한을 함께 쓰라고 한다 [S22].
- 멱등성: 재시도는 같은 호출을 여러 번 해도 상태가 같은(멱등) 작업에서만 안전하다. 그렇지 않으면 부분 갱신이 시스템 상태를 망친다 [S24].

| 항목 | SDK·Tools 공통 레퍼런스(새 동작, opt-in 필요) [S16] | Boto3 가이드(현행 문서) [S18] |
|---|---|---|
| 모드 | standard(기본)·adaptive·legacy | legacy가 기본, standard·adaptive 선택 |
| 최대 시도(최초 포함) | 3 (DynamoDB·DynamoDB Streams는 4) | 5 (standard로 바꾸면 3) |
| 백오프 | 전체 지터 `random(0,1) × min(20,000 ms, base × 2^retry)`, base는 일시 오류 50 ms·스로틀링 1,000 ms | 지수 백오프(밑 2), standard의 최대 백오프 20초 |
| 재시도 제한 | 재시도 쿼터(토큰 500, 일시 재시도 14·스로틀링 재시도 5 소모, 성공 시 복원) | standard 모드에 서킷 브레이킹 기능 |

- 새 동작은 `AWS_NEW_RETRIES_2026=true`로 opt-in해야 적용되고 2026년 11월에 기본값이 된다. 그때까지 Java·Python·Ruby·PHP·C++·CLI는 legacy가 기본(재시도 쿼터 없음)이다 [S16][S17].
- 재시도 대상: 일시 오류(RequestTimeout, 연결 끊김, HTTP 500/502/503/504)와 스로틀링 오류(Throttling, ThrottlingException, ProvisionedThroughputExceededException 등)는 재시도하고, AccessDenied·ValidationException·ResourceNotFound 같은 비재시도 오류는 즉시 반환한다 [S16].
- adaptive 모드: 클라이언트 측 속도 제한기가 초기 요청도 지연시킬 수 있다. 단일 리소스·스로틀링 잦은 워크로드용이며 범용 기본값으로는 비권장 [S16]. Boto3 문서는 experimental로 표기 [S18].
- Boto3 함정: `max_attempts`는 설정 파일·환경변수에서는 최초 요청 포함, `Config` 객체에서는 최초 제외(재시도 횟수만)다. 일관되게 쓰려면 `total_max_attempts` [S18]. botocore의 connect/read 타임아웃 기본은 각 60초 [S19].
- 배치 API의 부분 실패: HTTP 200이어도 일부 항목이 실패할 수 있다. EventBridge `PutEvents`는 `FailedEntryCount` [S93], Kinesis `PutRecords`는 레코드별 `ErrorCode`(`ProvisionedThroughputExceededException`·`InternalFailure`) [S70], SQS `SendMessageBatch`는 `Failed` 목록 [S54]을 확인해 실패분만 재시도한다.
- 실패 보존: SQS DLQ [S51], EventBridge 대상 DLQ [S82], Lambda 비동기 호출 DLQ [S15].
- 멱등성 구현: ① SQS FIFO 중복 제거 ID(5분 구간) [S53]. ② Lambda 함수는 "같은 이벤트로 여러 번 호출돼도 부작용 위험이 없을 때" 멱등이다. 이벤트에서 멱등 키(예: `orderId`, 필드 조합, 페이로드 해시)를 뽑아 영속 계층(DynamoDB·ElastiCache)에서 이미 처리했는지 확인하고, 있으면 트랜잭션을 다시 적용하지 않고 반환한다. Powertools 멱등성 유틸리티가 이를 대신하며(DynamoDB 영속 계층, TTL로 기간 제한, 기본 1시간) 같은 이벤트가 수 ms 안에 동시에 오는 경합은 수신 즉시 락을 거는 방식으로 막는다. SQS 표준 큐는 최소 1회 전달이라 서드파티 결제 호출처럼 중복되면 안 되는 처리에 특히 필요하다 [S27]. ③ Kinesis는 생산자·소비자 재시도로 중복 레코드가 생길 수 있어 레코드에 기본키를 넣거나 멱등 처리 [S69].
- 오케스트레이션 쪽 재시도: Step Functions `Retry`(IntervalSeconds 기본 1, MaxAttempts 기본 3, BackoffRate 기본 2.0, JitterStrategy 기본 NONE)와 `Catch`로 대체 경로 [S26].
- 원리: 재시도는 "일시적" 오류에만 효과가 있다. 일시 오류는 짧게·지터와 함께, 스로틀링은 길게, 영구 오류는 바로 포기해야 부하가 늘지 않는다 [S16].

### 서드파티 서비스 통합의 복원력 (Skill 1.1.13)

- 서드파티·원격 호출은 네트워크 단절, 스로틀링(429), 일시 불가용으로 실패한다. 재시도가 일시 오류를 흡수하지만 빈번한 재시도는 네트워크·스레드 풀을 잠식해 장애를 키운다 [S24][S25].

| 패턴 | 언제 | 핵심 동작 |
|---|---|---|
| 타임아웃 | 모든 외부 호출 | 연결·요청 타임아웃을 명시 [S23] |
| 재시도 + 지수 백오프 + 지터 | 일시 오류(429, 504, 타임아웃) | 한도 내 재시도. 그 외 상태 코드는 즉시 중단(PG 샘플은 429·504만 재시도) [S24] |
| 서킷 브레이커 | 호출이 반복해서 실패·지연 | 실패가 임계치를 넘으면 회로 개방 → 호출을 보내지 않고 즉시 실패 반환, 주기적으로 시험 호출해 성공하면 닫음 [S25] |
| 우아한 성능 저하 | 의존성 불가용 | 핵심 기능은 오래된 데이터·대체 데이터·무데이터로라도 계속 수행 [S94] |
| DLQ·재처리 | 재시도 소진 | 실패 이벤트를 큐에 보존해 나중에 분석·재처리 [S82][S51] |

- 서킷 브레이커 구현 예(PG): Step Functions Express + DynamoDB 상태 테이블(만료 시각은 TTL로 정리), 성능이 필요하면 ElastiCache. 멀티스레드에서는 첫 실패가 정한 만료 시각을 후속 호출이 계속 연장하지 않게 하고, 관리자가 회로를 강제로 열고 닫을 수 있게 하며, 회로가 열려 실패한 호출을 로깅하라고 권고한다 [S25].
- 재시도 vs 서킷 브레이커: 일시 오류는 백오프 재시도, 원인을 알 수 있는 비일시 오류는 서킷 브레이커로 빨리 실패(fail fast) [S24][S25]. Builders' Library는 서킷 브레이커가 테스트를 어렵게 하고 복구를 늦출 수 있다고 지적하며 SDK식 로컬 재시도 쿼터를 선호한다(요약본 기준, [S20]); SDK의 재시도 쿼터(토큰 500)가 그 구현이다 [S16].
- 멱등 키: 재시도되는 호출이 부작용을 만들 수 있으면(결제·리소스 생성) 멱등 토큰·중복 제거 키를 함께 보낸다(EC2 `RunInstances`의 토큰 기반 멱등성이 예, [S20] 요약본 기준).
- EventBridge API destinations(서드파티 SaaS·HTTPS): 요청 타임아웃 최대 5초, 초과 시 재시도 정책 한도까지 재시도하고 소진되면 DLQ(없으면 드롭) [S87]. API destination당 호출 속도 쿼터 기본 300/초이며 초과분은 지연되어 전달 [S84].
- 원리: 재시도(빠른 회복 시도)와 서킷 브레이커(포기 결정)는 반대 방향의 안전장치다. 둘을 함께 써야 "일시 오류는 흡수하고 지속 장애는 전파하지 않는다".

### API 만들기·확장·유지 — API Gateway (Skill 1.1.6)

| 기능 | REST API | HTTP API |
|---|---|---|
| 요청 유효성 검사 | 지원 | 미지원 |
| 요청 변환 | 파라미터·본문 모두(매핑 템플릿) | 파라미터 변환만 |
| 커스텀 게이트웨이 응답 | 지원 | 미지원 |
| API 키·클라이언트별 제한·AWS WAF·Private 엔드포인트 | 지원 | 미지원 |
| JWT 권한 부여 | 직접 지원 안 함(Lambda 권한 부여자로 검증 가능) | 지원 |
| 포지셔닝 | 기능이 많음 | 최소 기능·낮은 가격 |

(표 출처: [S28])

- 요청 변환(매핑 템플릿): 메서드 요청 데이터를 통합 요청 형식으로 바꾼다. 해당 Content-Type에 템플릿이 정의된 경우에만 변환하고, 없으면 본문을 그대로 통과(passthrough)시킨다 [S33]. 통과 정책은 `WHEN_NO_MATCH`·`WHEN_NO_TEMPLATES`(콘솔 권장)·`NEVER`이며, 템플릿과 맞지 않는 Content-Type은 `WHEN_NO_TEMPLATES`(템플릿이 있을 때)·`NEVER`에서 415 Unsupported Media Type [S34].
- Lambda 프록시 통합: 요청이 통째로 Lambda에 전달되고, 함수는 `statusCode`·`headers`·`body`(+`isBase64Encoded`) JSON을 반환해야 한다. 형식이 다르면 502 Bad Gateway. CORS는 응답 `headers`에 `Access-Control-Allow-Origin`을 직접 넣는다 [S32]. 비프록시(커스텀) 통합에서는 함수가 상태 코드를 직접 전달할 수 없고 통합 응답 매핑으로 정한다. 프록시에서는 함수의 상태 코드가 그대로 전달된다 [S38].
- 상태 코드 재정의: 통합 응답 매핑 템플릿에서 `$context.responseOverride.status`를 설정한다(예: 통합 응답 본문에 `error`가 있으면 400). 재정의는 최종적이며 같은 파라미터를 여러 번 재정의하면 5XX가 나므로 변수에 모았다가 템플릿 끝에서 한 번 적용한다 [S31]. 매핑 템플릿 또는 정규식으로 상태 코드를 매핑할 수 있다 [S38].
- 요청 유효성 검사(REST): 검증기(validator)를 만들어 메서드에 연결한다. ① 필수 URI·쿼리·헤더 파라미터가 있고 비어 있지 않은지(존재 여부만 보고 타입·형식은 안 봄) ② 본문이 메서드 모델의 JSON 스키마에 맞는지. 실패하면 즉시 400, 백엔드 호출 없음, 결과는 CloudWatch Logs. Content-Type과 맞는 모델이 없으면 검증을 안 하므로 모든 타입에 같은 모델을 쓰려면 `$default` [S29].
- 게이트웨이 응답: API Gateway가 요청 처리에 실패해 통합을 호출하지 못했을 때 만드는 오류 응답(예: `Missing Authentication Token`)을 API 수준에서 커스터마이징한다. 헤더 매핑과 비-VTL 본문 템플릿(단순 변수 치환)을 쓰며, VTL 매핑은 유효한 요청·성공 응답에서만 동작한다 [S30].
- 타임아웃: REST API 통합 타임아웃은 기본 29초(50~29,000 ms)이고 Regional·Private REST API는 쿼터 증가로 더 늘릴 수 있다 [S35]. HTTP API는 최대 30초(증가 불가), 페이로드 10 MB [S36].
- AppSync(GraphQL, 간단히): 데이터 소스(Lambda·DynamoDB·OpenSearch·Aurora·HTTP 엔드포인트)와 리졸버로 GraphQL 필드를 해석한다 [S39]. 구독은 WebSocket 기반 실시간 갱신이고, 2025-03-13부터 WebSocket pub/sub용 AppSync Events가 있다 [S40].
- 원리: 검증·변환·상태 코드를 게이트웨이에서 처리하면 잘못된 요청이 백엔드에 닿기 전에 걸러지고(비용·부하 절감), 백엔드 코드를 바꾸지 않고 API 계약을 조정할 수 있다 [S29][S31].

### 개발 환경 단위 테스트와 AWS SAM (Skill 1.1.7)

- 테스트 기법은 섞어 쓴다: 콘솔 대화형 디버깅, 비즈니스 로직 자동화 단위 테스트, 외부 서비스를 흉내 내는 모의(mock), 에뮬레이터, SAM CLI 로컬 호출, 클라우드 테스트. 클라우드 테스트가 코드 품질을 가장 정확히 측정한다 [S46].
- 단위 테스트는 서버리스라고 달라지지 않는다(로컬에서 수정 없이 실행 가능). 통합 테스트는 통제할 수 없는 서비스를 모의하지 말고 실제 서비스로 한다 [S47]. 핸들러 밖에 모듈화한 함수로 로직을 분리하면 단위 테스트가 쉬워진다 [S47].
- AWS SAM = 서버리스 애플리케이션을 IaC로 만드는 오픈소스 프레임워크(SAM 템플릿 + SAM CLI) [S41]. SAM CLI 로컬 테스트는 Lambda와 같은 런타임 환경의 Docker 컨테이너에서 함수를 호출해 클라우드 배포 없이 로직·이벤트 처리를 확인한다 [S46][S44].

| 명령 | 용도 |
|---|---|
| `sam local invoke` | 함수를 로컬에서 1회 호출(이벤트 파일 `-e event.json` 또는 stdin). `aws lambda invoke`에 대응 [S43] |
| `sam local start-api` | 로컬 HTTP 서버로 API Gateway→Lambda 호출을 에뮬레이션(개발용 서버, 프로덕션 사용 금지 경고) [S44] |
| `sam local start-lambda` | AWS CLI·SDK로 호출할 수 있는 로컬 Lambda 엔드포인트 [S42] |
| `sam local generate-event` | 서비스별 샘플 이벤트 생성(예: `sam local generate-event s3 put`) [S45] |

- 한계·주의: 로컬 Lambda 권한 부여자는 클라우드와 100% 동일하다고 보장되지 않는다 [S44]. 신뢰할 수 없는 코드에는 로컬 호출을 쓰지 말 것 [S43].
- 원리: 핸들러의 입력은 결국 이벤트 JSON이므로, `generate-event`로 실제 이벤트 모양을 받아 단위 테스트 입력으로 쓰면 핸들러를 로직 단위로 검증할 수 있다 [S45].

### 메시징 ① Amazon SQS (Skill 1.1.8)

| 항목 | Standard | FIFO |
|---|---|---|
| 전달 | 최소 1회(at-least-once), 사본이 둘 이상 전달될 수 있음 [S52] | 중복 제거로 정확히 1회 처리(5분 중복 제거 구간) [S53] |
| 순서 | 최선 노력, 가끔 순서 뒤바뀜 [S52] | 같은 메시지 그룹 안에서 엄격한 순서·한 번에 하나씩 처리 [S53] |
| 처리량 | 사실상 무제한 [S48] | 파티션·API 액션당 300 TPS(비-고처리량 모드), 배치 시 3,000 msg/s, 고처리량 모드로 상향 [S48] |
| 필수 파라미터 | — | `MessageGroupId` 필수(없으면 실패) [S48], `MessageDeduplicationId` 또는 콘텐츠 기반 중복 제거(본문 해시) [S53] |
| DLQ | 가능 | 가능하나 DLQ로 보내면 순서가 깨질 수 있어 주의 [S51] |

- 가시성 제한 시간(visibility timeout): 수신한 메시지가 다른 소비자에게 일시적으로 안 보이는 시간. 기본 30초, 0~12시간. 이 안에 `DeleteMessage`하지 못하면 다시 보여 재처리된다. `ChangeMessageVisibility`로 연장(하트비트)하거나 0으로 즉시 반환한다 [S49][S48]. 너무 길면 실패 메시지 재시도가 늦어진다 [S49]. 최소 1회 모델이라 가시성 시간 안에도 중복 전달 가능성이 남으므로 멱등 처리 [S49].
- 폴링: 짧은 폴링(기본)은 서버 일부만 조회해 즉시 응답(빈 응답 가능). 긴 폴링(`WaitTimeSeconds`>0, 최대 20초)은 모든 서버를 조회하고 메시지가 생기면 응답해 빈 응답·비용을 줄인다 [S50].
- 크기·시간: 메시지 최대 1 MiB(1,048,576 bytes). 더 큰 페이로드는 SQS Extended Client Library(Java·Python)로 S3 참조(최대 2 GB, 동기 클라이언트만). 보존 기본 4일(60초~14일), 메시지 타이머(지연) 0~15분, 배치 최대 10개, 메시지 속성 최대 10개 [S48].
- DLQ·재처리: 리드라이브 정책의 `maxReceiveCount`번 수신되고도 삭제되지 않으면 DLQ로 이동한다. DLQ는 원본과 같은 계정·리전의 큐다. 표준 큐는 원래 enqueue 시각 기준으로 만료되므로 DLQ 보존 기간을 원본보다 길게 둔다 [S51].
- 소비자 코드 원칙: ① 긴 폴링 ② 처리 성공 후에만 삭제 ③ 중복 대비 멱등 처리 ④ 배치 전송은 `Failed` 목록 확인 [S54] ⑤ 처리 시간 변동이 크면 `ChangeMessageVisibility`.
- 신규: 표준 큐에서도 `MessageGroupId`를 쓰면 공정 큐(fair queues)가 활성화된다(시험 가이드 v2.1 이후 기능) [S48].
- 원리: SQS는 "받아 가는 쪽이 속도를 정하는" 버퍼다. 처리 실패는 "삭제 안 함 → 가시성 만료 → 재노출 → 횟수 초과 시 DLQ"의 흐름으로 자동 재시도된다 [S49][S51].

### 메시징 ② Amazon SNS와 서비스 선택 (Skill 1.1.8)

- SNS는 토픽에 게시하면 구독자 전체로 푸시하는 pub/sub이다. 고처리량·푸시 기반 다대다 메시징에 적합하다 [S9].
- 한도: 표준 토픽 계정당 100,000개·FIFO 토픽 1,000개, 구독은 표준 12,500,000/토픽·FIFO 100/토픽, `PublishBatch` 10 entries, 필터 정책 200/토픽, 기본 최대 메시지 256 KiB(`MaximumMessageSize` 속성으로 최대 1 MiB, 1 MiB 초과는 Extended Client Libraries로 최대 2 GB) [S55].
- 구독 필터 정책: 구독자는 자기에게 맞는 메시지만 받는다. 범위(`FilterPolicyScope`)는 `MessageAttributes`(기본) 또는 `MessageBody` [S57].
- 전달 재시도: Lambda·SQS 같은 AWS 관리형 엔드포인트는 총 100,015회·23일 동안 재시도(즉시 3회 → 1초 간격 2회 → 지수 백오프 10회(1~20초) → 20초 간격 100,000회)하며 지터를 적용한다. HTTP/S만 사용자 정의 전달 정책을 쓸 수 있고 총 재시도 시간은 3,600초 이하다 [S56]. 구독에 SQS DLQ를 달면 전달하지 못한 메시지를 보존한다 [S95].
- FIFO 토픽: 게시 메시지에 중복 제거 ID가 필요(또는 콘텐츠 기반 중복 제거), 5분 구간. 구독에 필터를 쓰면 필터로 걸러질 수 있어 at-most-once가 된다 [S58].
- raw message delivery: SQS·HTTP/S·Firehose 구독에서 켜면 SNS 메타데이터(JSON 포장)가 제거되어 메시지가 그대로 전달된다. SDK는 `SetSubscriptionAttribute`로 `RawMessageDelivery=true` [S59].

| 기준 | SQS | SNS | EventBridge(Classic) |
|---|---|---|---|
| 모델 | 큐: 소비자가 폴링해 가져가고 삭제 [S49][S50] | 토픽 pub/sub: 구독자 전원에게 푸시 [S9][S12] | 버스+규칙(이벤트 패턴)+대상 [S80] |
| 전달 대상 수 | 소비자 풀이 메시지를 나눠 처리(메시지당 소비자 하나) [S12] | 구독자마다 사본 [S12] | 규칙당 최대 5개 대상 [S80] |
| 필터링 | 없음(소비자 코드) | 구독 필터 정책(속성/본문) [S57] | 이벤트 패턴(source·detail-type·detail) [S80] |
| 실패 처리 | 가시성 제한 + DLQ [S51] | 전달 재시도 + 구독 DLQ [S56][S95] | 대상별 재시도 정책 + DLQ [S82] |

### API·AWS SDK로 AWS 서비스와 상호작용 (Skill 1.1.9)

- SDK vs CLI vs 직접 호출: SDK·CLI는 요청 서명(SigV4)을 자동 처리하므로 서명 과정을 건너뛸 수 있다. 직접 HTTP로 호출하면 SigV4(표준 요청 생성 → 자격 증명으로 서명 계산 → `Authorization` 헤더 추가)를 직접 구현해야 한다. 서명 키는 서비스·리전·날짜 범위다 [S65].
- 자격 증명 공급자 체인: 정해진 순서로 탐색하다 처음 유효한 자격 증명에서 멈춘다. 코드에서 직접 지정 > 환경 변수 > 공유 config/credentials 파일 순으로 우선한다. 표준 공급자: 액세스 키, 웹 ID 연합, IAM Identity Center, Assume role, 컨테이너(ECS·EKS), 프로세스, IMDS(EC2 인스턴스 프로파일). 만료되면 SDK가 자동 갱신한다 [S60].
- Boto3의 탐색 순서(12단계): 클라이언트 파라미터 → Session 파라미터 → 환경 변수 → assume role → web identity → IAM Identity Center → 공유 자격 증명 파일 → console login → config 파일 → boto2 config → 컨테이너 → EC2 인스턴스 메타데이터 [S62].
- 리전: 코드에서 지정하지 않으면 `region` 설정(`AWS_REGION`)을 쓰며 기본값은 없어 명시해야 한다. Boto3는 `AWS_DEFAULT_REGION`, CLI v2는 `AWS_REGION`을 우선한다. 클라이언트 생성 시 지정한 리전이 전역 설정보다 우선한다 [S61].
- 페이지네이션: 일부 작업은 불완전한 결과를 주므로 이어 받는 요청(마커/토큰)이 필요하다. Boto3 paginator가 이를 추상화한다(S3 `list_objects`는 한 번에 최대 1000개) [S63].
- 웨이터(waiter): 리소스가 원하는 상태가 되거나 실패할 때까지 폴링·대기한다(`get_waiter(...).wait(...)`) [S64].
- 재시도·타임아웃 설정: 우선순위는 코드 > 환경 변수 > 공유 config > SDK 기본값 [S16]. 재시도·타임아웃 상세는 Skill 1.1.5 참조.
- 원리: SDK는 서명·재시도·자격 증명 갱신·페이지네이션을 대신 처리하는 얇은 클라이언트이므로, 직접 호출은 "서명 도구가 없을 때"의 예외 수단이다 [S65].

### 스트리밍 데이터 처리 (Skill 1.1.10)

| 개념 | 규칙 |
|---|---|
| 샤드 | 쓰기 1 MB/s·1,000 records/s, 읽기 2 MB/s·5 TPS(GetRecords) [S67] |
| 파티션 키 | 최대 256자 유니코드. MD5로 128비트 정수화해 샤드의 해시 키 범위에 매핑 → 같은 키는 같은 샤드 [S67] |
| 시퀀스 번호 | 쓰기 후 부여, 같은 파티션 키에서 대체로 증가 [S67] |
| 보존 | 기본 24시간, 최대 365일(8,760시간). 24시간 초과분은 추가 요금 [S67] |
| 용량 모드 | Provisioned(샤드 수 지정·시간당 과금) / On-demand(자동 관리, 신규 스트림 기본 4 MB/s 쓰기·8 MB/s 읽기) [S67][S66] |
| 레코드 크기 | 문서 불일치(Concepts 1 MB vs Quotas 10 MiB) → 확인 필요 [S66][S67] |

| 소비자 | 공유 처리량(shared) | 향상된 팬아웃(EFO) |
|---|---|---|
| 읽기 처리량 | 샤드당 총 2 MB/s를 모든 소비자가 나눠 씀(`GetRecords`는 샤드당 5 TPS) [S68][S67] | 등록한 소비자마다 샤드당 최대 2 MB/s를 독립적으로 받음 [S68] |
| 전파 지연 | 평균 약 200 ms(소비자 1개) → 소비자 5개면 약 1000 ms [S68] | 소비자 수와 무관하게 평균 약 70 ms [S68] |
| 전달 방식 | `GetRecords` 풀(HTTP) [S68] | `SubscribeToShard`로 HTTP/2 푸시, 폴링 불필요 [S68] |
| 비용 | 해당 없음 | 데이터 조회 비용 + 소비자-샤드 시간 비용 [S68] |
| 등록 한도 | — | 스트림당 20(Standard·Provisioned), 50(On-demand Advantage) [S68] |
| KCL | — | KCL 2.0 이상은 모든 샤드를 EFO로 구독하도록 설정 [S68] |

- KCL(Kinesis Client Library): 샤드마다 레코드 프로세서가 하나씩 돌게 보장하며, 소비 메타데이터를 DynamoDB 테이블(애플리케이션당 3개)에 저장한다 [S67].
- 중복: 생산자가 `PutRecord` 타임아웃 후 재전송하거나 소비자가 재시도하면 중복 레코드가 생긴다. 엄격한 보장이 필요하면 레코드에 기본키를 넣어 처리 단계에서 제거(멱등) [S69]. `PutRecords`는 레코드별 실패를 확인해 재시도 [S70].
- Amazon Data Firehose(오래된 블로그에는 "Kinesis Data Firehose"로 표기 [S12]): 스트리밍 데이터를 메모리에 버퍼링한 뒤 목적지로 전달한다. 버퍼 크기(MB)와 간격(초) 중 먼저 충족되는 조건이 전달을 트리거하고, 값을 주지 않으면 목적지별 기본값(S3: 5 MB·300초, 범위 1~128 MB·0~900초)을 쓴다. 간격 0이면 버퍼링 없이 수 초 안에 전달하지만 애플리케이션 대상에서만 가능하고 S3 백업 대상은 60~900초다 [S71][S72].
- DynamoDB Streams: 테이블 항목 수준 변경을 시간순으로 최대 24시간 로그에 저장하고, 각 스트림 레코드는 정확히 한 번 나타나며 항목별 수정 순서가 보장된다. 전/후 이미지 캡처 설정 가능 [S73].

| 요구 | 선택 | 근거 |
|---|---|---|
| 실시간 수집 + 여러 커스텀 소비자 + 보존 기간 내 재처리 | Kinesis Data Streams | [S67][S68] |
| 버퍼링 후 S3·Redshift·OpenSearch 등으로 관리형 적재 | Amazon Data Firehose | [S67][S71] |
| DynamoDB 테이블 변경(CDC) 소비 | DynamoDB Streams | [S73] |
| 단순 작업 큐·버퍼(샤드·순서 불필요) | SQS | [S52] |

- 원리: 파티션 키가 샤드를 결정하므로 "순서는 샤드(=파티션 키) 안에서만" 보장된다. 핫 키는 핫 샤드(스로틀링)가 된다 [S67].

### Amazon EventBridge로 이벤트 기반 패턴 구현 (Skill 1.1.12)

먼저 알아둘 변화(2026-09-24 게시): EventBridge 이벤트 버스가 두 종류가 되었다. 신규 **Custom Event Bus**는 소비자가 직접 만드는 구독자(subscriber)로 라우팅하고 이벤트 보존·순서 배달·재생을 지원한다. 규칙+대상 방식은 **Custom Event Bus - Classic**으로 계속 제공되며, 새 애플리케이션은 신규 버스로 시작하라고 안내한다 [S79]. 기존 custom 버스는 "classic"으로 이름이 바뀌었고 신규 버스는 출시 시 14개 리전에서만 제공된다 [S85]. 시험 가이드 v2.1(2024-12)은 이 변경 이전 문서라 규칙·대상 중심의 Classic 모델을 전제했을 것으로 보인다(추정 → 확인 필요).

| 구분 | Classic(+default 버스) | 신규 Custom Event Bus |
|---|---|---|
| 라우팅 | 버스 소유자가 작성한 규칙(이벤트 패턴)이 일치 이벤트를 대상(규칙당 최대 5)으로 전달 [S80] | 소비자가 만든 구독자(Subscriber)가 이벤트를 필터링해 AWS 서비스(250개 이상)로 전달 [S79][S85] |
| 보존·재생 | 별도 Archive/Replay(소스 버스로만 재생) [S89] | 버스 자체에 보존(기본 24시간, 최대 1년·`RetentionPeriodInDays` 1~365일)하고 재생을 지원 [S85][S84][S79] |
| 재시도 기본값 | 24시간·185회 [S82] | 5회·300초(범위 0~185회, 60~86,400초) [S83] |
| 공유 | 리소스 정책으로 교차 계정 [S88] | AWS RAM으로 조직·계정 공유 [S85] |

- 이벤트 흐름(Classic): 소스(AWS 서비스·자체 앱·SaaS)가 버스로 이벤트를 보내면 버스의 규칙이 이벤트 패턴으로 평가하고, 일치하면 대상으로 전달(필요 시 입력 변환)한다. 일치 규칙이 없으면 아무 일도 하지 않는다. default 버스는 AWS 서비스 이벤트를 자동 수신한다 [S80]. 예: EC2 상태가 running으로 바뀌면 Lambda 호출(`source`·`detail-type`·`detail.state` 패턴) [S80].
- 규칙 종류: 이벤트 패턴 규칙과 예약 규칙. 예약 규칙은 legacy이며 cron·rate·일회성 스케줄, 유연한 시간 창, 재시도 한도, 실패 이벤트 보존 시간을 지원하는 EventBridge Scheduler를 권장한다 [S81][S79]. Scheduler 스케줄 수 기본 쿼터는 리전당 10,000,000 [S92].
- 재시도·DLQ: 대상별 재시도 정책. 기본 24시간·최대 185회(지수 백오프+지터), 소진되면 이벤트가 드롭되므로 SQS DLQ를 구성한다 [S82].
- Pipes: 점대점(소스 1개 → 필터·보강 → 대상 1개). 소스는 DynamoDB 스트림·Kinesis·Amazon MQ·MSK·자체 관리 Kafka·SQS [S79][S91]. 파이프의 대상으로 이벤트 버스를 두어 다대다로 확장할 수 있다 [S79].
- Archive/Replay: 아카이브는 단일 소스 버스의 이벤트를 받고(이벤트 패턴으로 선별 가능, 보존 기간 기본 무기한), 재생은 원래 받은 소스 버스로만 보낸다. 계정·리전당 동시 재생 10개, 재생 기록은 90일 후 삭제, 보존 기간이 지나면 이벤트 삭제. 재생은 이벤트 시각 기준 1분 단위로 진행되어 원래 순서를 보장하지 않고, 아카이브 반영 지연 때문에 10분 뒤 재생을 권장하며, 재생 이벤트에는 `replay-name` 필드가 붙는다 [S89].
- API destinations: 규칙·파이프 대상으로 HTTPS 엔드포인트 호출. 연결(connection)이 인증·네트워크를 정의하고 CONNECT·TRACE 외 모든 HTTP 메서드를 쓴다 [S87].
- 교차 계정·리전: 수신 계정 버스의 권한(리소스 정책)으로 송신 계정·조직을 허용 → 송신 계정에 수신 버스를 대상으로 하는 규칙 → 수신 계정에서 규칙으로 처리. 송신 버스는 IAM 역할이 필요(콘솔은 자동 생성), 교차 계정 이벤트는 송신 계정에 커스텀 이벤트로 과금 [S88].
- 스키마 레지스트리: 이벤트 스키마에서 Go·Java·Python·TypeScript 코드 바인딩을 생성한다 [S90].
- 이벤트 게시 코드: `PutEvents`(Classic)는 요청당 엔트리 최대 10개, 엔트리 총 크기 1 MB 미만(2026-01에 256 KB→1 MB 상향)이며 HTTP 200이어도 `FailedEntryCount`와 엔트리별 오류를 확인한다 [S93][S86].
- 원리: 버스는 라우터, 규칙은 "필터+연결"이다. 생산자는 대상을 몰라도 되고 대상을 늘리는 일은 규칙 추가로 끝난다(느슨한 결합) [S80].

## 시험에서 묻는 방식

> 문제 저작자를 위한 제안이며, 시험이 반드시 이렇게 낸다는 단정이 아니다.

1. **팬아웃·결합도 (1.1.1 · 1.1.3 · 1.1.8)** — 상황: 주문 접수 이벤트를 재고·결제·알림 시스템이 각자 독립적으로 받아야 하고, 한 시스템이 몇 시간 장애여도 다른 시스템에 영향이 없고 메시지도 유실되면 안 된다. → 단서: "여러 구독자에 동시 전달", "구독자 장애 시 유실 방지" → SNS 토픽 + 구독자별 SQS 큐(팬아웃, 필요하면 DLQ). 단서가 "이벤트 패턴으로 라우팅", "AWS 서비스·SaaS 이벤트"면 EventBridge 규칙.
2. **재시도 폭주·서드파티 장애 (1.1.5 · 1.1.13)** — 상황: SDK 호출이 간헐적으로 스로틀링되는데 모든 인스턴스가 같은 간격으로 즉시 재시도해 장애가 길어진다. 또는 서드파티 결제 API가 오래 느려져 호출 스레드가 타임아웃 대기에 계속 묶인다. → 단서: "동시 재시도", "연쇄 장애" → 지수 백오프 + 지터(SDK standard 모드)·재시도 상한·멱등성. 지속 장애면 타임아웃 + 서킷 브레이커(즉시 실패).
3. **API 계약 제어 (1.1.6)** — 상황: API Gateway 비프록시 통합에서 백엔드는 항상 200을 주지만 본문에 오류가 있으면 클라이언트에 400을 돌려줘야 한다(백엔드 코드 변경 불가). 또는 스키마에 맞지 않는 요청이 Lambda까지 도달하지 않아야 한다. → 단서: "상태 코드 재정의" → 통합 응답 매핑 템플릿의 `$context.responseOverride.status`. "요청 본문 스키마 검증" → REST API 요청 검증기 + 모델(실패 시 400, HTTP API는 미지원).
4. **스트리밍 소비자·메시지 처리·로컬 테스트 (1.1.10 · 1.1.8 · 1.1.7)** — 상황 A: 같은 Kinesis 스트림을 여러 애플리케이션이 폴링해 `ProvisionedThroughputExceededException`이 난다 → "소비자별 전용 처리량" → 향상된 팬아웃(EFO). 상황 B: 순서와 중복 제거가 모두 필요한 주문 이벤트 큐 → SQS FIFO(`MessageGroupId`·중복 제거 ID). 상황 C: 개발자가 Docker로 Lambda를 로컬에서 돌려 S3 이벤트로 테스트 → `sam local invoke` + `sam local generate-event`.

- 오답 해설:
  - B — 파티션 키는 레코드를 샤드에 분배하는 필수 값이며 읽기 처리량과 무관하다 [S67].
  - C — 보존 기간은 데이터를 읽을 수 있는 기간이지 읽기 처리량이 아니다 [S67].
  - D — Firehose는 버퍼링한 데이터를 대상으로 전달하는 서비스이며 소비자별 전용 읽기 처리량을 주는 방법이 아니다 [S71].
