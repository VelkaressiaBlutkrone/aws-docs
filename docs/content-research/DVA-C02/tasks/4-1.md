### 결함 식별을 위한 코드 디버깅 (Skill 4.1.1)

**Lambda의 '오류'가 보이는 방식**
- 함수 코드나 런타임이 오류를 반환해도 Lambda 응답의 상태 코드는 200이고, 오류 여부는 응답 헤더 `X-Amz-Function-Error`로 알린다. 400·500번대 상태 코드는 '호출 오류'(스로틀·권한·잘못된 요청 등)에 쓰인다. [S1]
  - 원리: Invoke API 호출 자체는 성공했고 실패는 '함수 실행 결과'이므로 두 층위를 나눈다. 직접 호출이면 응답에서, 비동기·이벤트 소스 매핑·타 서비스 경유 호출이면 로그·DLQ·실패 시 대상(on-failure destination)에서 오류를 찾는다. [S1]
- 호출마다 START·END·REPORT 3줄이 자동 기록된다. 타임아웃은 로그에 "Status: timeout"으로 남으므로 "Error"만 검색하면 코드 예외만 잡히고 타임아웃은 놓친다. [S2][S3]
- 기본 타임아웃은 3초, 1초 단위로 최대 900초(15분)까지 조정한다. [S4]
- "runtime exited" 류 오류의 점검 순서: 코드의 명시적 종료 호출(`exit()` 등) 제거 → 로그로 메모리 한도 도달 여부 확인 후 메모리 증설(128~10,240 MB) → DB 연결을 핸들러 밖에서 초기화 → 파일 디스크립터·스레드 한도(1,024) 확인. [S5]

**재현·디버거 도구 선택**

| 상황 | 도구 | 핵심 |
|---|---|---|
| 로컬에서 재현하고 한 줄씩 실행 | AWS SAM CLI의 `sam local invoke` + 디버거 | 디버그 모드로 호출한 함수에 디버거를 붙여 단계 실행·변수 확인 [S6] |
| 클라우드에서 돌고 있는 함수를 그대로 | AWS Toolkit for VS Code의 Lambda remote debugging | 클라우드 함수에 중단점·변수 검사·단계 실행 [S7] |
| 빌드 실패를 로컬에서 재현 | CodeBuild 에이전트(로컬 빌드) | `codebuild_build.sh`로 빌드 이미지를 로컬에서 실행 [S8] |

### 지표·로그·추적 해석 (Skill 4.1.2)

**Lambda 핵심 지표** (네임스페이스 `AWS/Lambda`) [S11]

| 지표 | 의미 | 보는 통계 | 해석 단서 |
|---|---|---|---|
| `Invocations` | 코드가 호출된 횟수(성공+함수 오류). 스로틀·호출 오류는 미기록, 값 = 청구 요청 수 | Sum | |
| `Errors` | 함수 오류로 끝난 호출 수(예외, 타임아웃·구성 오류 포함). 오류율 = Errors ÷ Invocations, 타임스탬프는 '호출 시각' | Sum | |
| `Throttles` | 스로틀된 요청 수(`TooManyRequestsException`). `Invocations`·`Errors`에는 안 잡힘 | Sum | 동시성 한도·예약 동시성 |
| `Duration` | 코드가 이벤트 처리에 쓴 시간(콜드 스타트 제외), 백분위(p95 등) 지원 | Average/Max/p95 | 느려짐·타임아웃 근접 |
| `ConcurrentExecutions` | 이벤트를 처리 중인 인스턴스 수 | Max | 동시성 한도 근접도 |
| `IteratorAge` | 스트림 소스(DynamoDB·Kinesis·DocumentDB): 레코드가 스트림에 들어온 뒤 함수로 전달되기까지의 시간 | Max | 증가 = 처리 지연 |
| `DeadLetterErrors` | 비동기 호출에서 DLQ 전송 실패 횟수 | Sum | DLQ 리소스·크기 한도 문제 |
| `DestinationDeliveryFailures` | 목적지(destination) 전송 실패 횟수 | Sum | 권한·잘못된 리소스·FIFO 미지원 |

**API Gateway 핵심 지표** (네임스페이스 `AWS/ApiGateway`) [S12]
- `4XXError`/`5XXError`: 클라이언트/서버 오류 수. `Sum` = 개수, `Average` = 오류율(분모는 `Count`).
- `Latency` = 요청 수신~응답 반환 전체(통합 지연 + 기타 API Gateway 오버헤드), `IntegrationLatency` = 백엔드로 넘긴 뒤 응답을 받기까지. `Latency`가 `IntegrationLatency`와 비슷하면 병목은 백엔드(저작자 정리).
- 메서드·리소스·스테이지 차원 지표는 **상세 지표(detailed metrics)** 를 켜야 전송되며 추가 요금이 든다.

**지표 보존** — 1초 미만 주기 3시간, 1분 15일, 5분 63일, 1시간 455일(오래될수록 집계되어 해상도 하락). [S13]

**로그 읽기** — Lambda `REPORT` 줄에서 Logs Insights는 `@duration`, `@billedDuration`, `@maxMemoryUsed`, `@memorySize`를 자동 발견한다. 콜드 스타트 호출의 REPORT 줄에는 "Init Duration"이 들어 있어 비율 계산에 쓴다. [S20][S22]

**트레이스 읽기 (X-Ray)** [S14][S15][S16]
- 서비스가 보낸 **세그먼트**를 같은 요청끼리 묶은 것이 **트레이스**, 이를 시각화한 것이 서비스 그래프(트레이스 맵). 서비스 맵과 CloudWatch ServiceLens 맵은 CloudWatch 콘솔의 **트레이스 맵**으로 통합됐다.
- 오류 분류: `Error` = 4xx, `Fault` = 5xx, `Throttle` = 429. 맵 색: 초록(정상)·빨강(5xx)·노랑(4xx)·보라(429).
- Lambda는 트레이스당 세그먼트 2개를 만든다: `AWS::Lambda`(실행 환경 준비 등 Lambda 서비스) / `AWS::Lambda::Function`(함수 코드). 전자에 오류면 Lambda 서비스 문제, 후자에 오류면 함수 문제.
- 트레이스를 '읽는' 방법은 그대로지만, 트레이스를 '만드는' 계측은 변했다: X-Ray SDK·데몬은 2026-02-25부터 maintenance mode(보안 수정만)이고 AWS는 OpenTelemetry를 권장한다 [S69]. 계측 상세 → 4-2.md Skill 4.2.4·4.2.6.

### 로그 쿼리로 관련 데이터 찾기 (Skill 4.1.3)

**CloudWatch Logs Insights 기본기**
- 지원 언어 3종: 전용 **Logs Insights QL**, **OpenSearch PPL**, **OpenSearch SQL**. [S18] 학습의 중심은 QL(저작자 정리).
- 명령은 파이프(`|`)로 잇고 주석은 `#`. 한 쿼리에 최대 50개 로그 그룹을 지정한다(`logGroupNames`/`logGroupIdentifiers`). [S17][S19]
- 시스템 필드(Standard 클래스): `@message`, `@timestamp`, `@ingestionTime`, `@logStream`, `@log`(계정ID:로그그룹명), `@entity`. Lambda 로그는 `@requestId`, `@duration`, `@billedDuration`, `@type`, `@maxMemoryUsed`, `@memorySize`(+ 로그에 X-Ray ID가 있으면 `@xrayTraceId`, `@xraySegmentId`)를 자동 발견하되 **로그 이벤트당 첫 JSON 조각만** 발견한다 → 그 밖은 `parse`. JSON 필드는 점 표기(`userIdentity.type`), JSON 로그에서 최대 200개 필드까지 추출. [S20]

| 명령 | 하는 일 |
|---|---|
| `fields` / `display` | 표시 필드 선택 + 함수·연산으로 새 필드 생성 / 결과에 보일 필드 지정 [S17] |
| `filter` (`where`는 별칭) | 조건에 맞는 이벤트만 남김 [S17] |
| `stats` ... `by bin(5m)` | 집계(count·avg·max·sum·countDistinct·percentile 등) + 시간 구간 묶기 [S17][S21] |
| `sort` / `limit` | 정렬 / 개수 제한("상위 20개"용) [S17] |
| `dedup` | 지정 필드 값 기준 중복 제거(재시도로 중복된 requestId 제거 등) [S17][S21] |
| `parse` | 필드에서 값을 뽑아 임시 필드 생성(글롭 `*` 또는 정규식) [S17] |
| `pattern` / `diff` / `anomaly` | 로그 패턴 군집화 / 이전 동일 길이 기간과 비교 / ML 이상 탐지 [S17] |
| `unnest`, `join`, `lookup`, 하위 쿼리 | 목록 펼치기 / 다른 로그 그룹·쿼리 결과와 결합 / 조회 테이블로 값 보강 — join·lookup·하위 쿼리는 2026년 신규 [S17][S27] |
| `SOURCE` | 로그 그룹을 접두어·계정·클래스·태그로 지정. **CLI·API에서만**(콘솔 불가) [S17] |
| `estimate` | 실행 없이 스캔될 바이트 추정 [S17] |

공식 예시 쿼리(축약) [S21][S22]:
```
# Lambda: 1초 넘은 호출을 requestId 중복 제거 후 최신 20건 (@duration 단위 ms)
fields @timestamp, @requestId, @message, @logStream
| filter @type = "REPORT" and @duration > 1000
| sort @timestamp desc
| dedup @requestId
| limit 20

# 시간당 예외 수
filter @message like /Exception/
| stats count(*) as exceptionCount by bin(1h)
| sort exceptionCount desc

# API Gateway 액세스 로그: 최근 4XX 10건
fields @timestamp, status, ip, path, httpMethod
| filter status>=400 and status<=499
| sort @timestamp desc
| limit 10

# parse(글롭)로 값을 뽑아 평균 지연
parse @message "user=*, method:*, latency := *" as @user, @method, @latency
| stats avg(@latency) by @method, @user

# Lambda 콜드 스타트 비율
filter @type = "REPORT"
| stats sum(strcontains(@message, "Init Duration"))/count(*) * 100 as coldStartPct, avg(@duration) by bin(5m)
```

**한도·비용** (상세 수치는 `## 사실·숫자`)
- 쿼리 60분 타임아웃(시간 범위 축소·분할), 결과 7일 보존, 한 쿼리 최대 50 로그 그룹, `limit` 최대 100,000(한 번의 `GetQueryResults`는 10,000건, `nextToken`으로 페이징). [S18][S19]
- 과금은 **스캔한 비압축 로그량** 기준이다 → 로그 그룹·시간 범위를 최소화, 콘솔을 닫기 전 쿼리 취소, 대시보드 위젯 새로고침 빈도 주의. 필드 인덱스를 만들어 `filterIndex`를 쓰면 스캔량이 준다. [S17][S18]
- 동시 쿼리: 최신 공식 문서는 계정당 100(QL)이나 KC 문서는 30 → `확인 필요`. [S18][S26][S27]
- 로그 그룹 생성 시점 이전 타임스탬프는 조회 불가, 2018-11-05 이후 로그만 대상. [S18]

| Contributor Insights | 로그 필드 기준 top-N 기여자 상시 집계 | 실시간 | 4.1.5 [S36] |
| S3 + Athena | S3·Firehose로 보낸 로그의 장기 보관·분석 | 사후 | Lambda는 로그 대상을 CloudWatch Logs·S3·Firehose 중 선택 [S23] |

### 사용자 지정 지표 구현 — 임베디드 지표 형식(EMF) (Skill 4.1.4)

- EMF는 **구조화 로그 안에 지표 정의를 심으면 CloudWatch가 자동으로 지표를 추출**하는 JSON 사양이다. 지표는 비동기로 생성되고, 같은 로그 이벤트를 Logs Insights로 조회해 근본 원인 분석에 쓸 수 있다. [S31]
- 필요한 권한은 `logs:PutLogEvents`뿐, `cloudwatch:PutMetricData`는 필요 없다. 클라이언트 라이브러리로 로그를 만들거나 사양대로 직접 만들어 `PutLogEvents` API·CloudWatch 에이전트로 보낸다. [S31]
- Lambda·ECS 같은 단명 리소스에서 추가 설정 없이 가능하며, 로그 JSON 루트에 `_aws`(안에 `CloudWatchMetrics`)가 있어야 한다. [S33]
- 원리: 지표 생성을 '로그 기록'으로 대체해 호출 경로에서 CloudWatch API 호출·지연을 없애고, 원본 이벤트(고카디널리티 값 포함)를 로그에 남긴다.

| EMF 요소 | 규칙 [S30] |
|---|---|
| `_aws.Timestamp` | epoch 밀리초. 과거 14일·미래 2시간을 벗어나면 지표가 게시되지 않음 |
| `_aws.CloudWatchMetrics[]` (MetricDirective) | `Namespace`(1~255자 ASCII), `Dimensions`(DimensionSet 배열), `Metrics`(MetricDefinition 배열) |
| DimensionSet | 차원 키 최대 30개. 키는 루트 멤버를 참조, 값은 문자열(1~1,024자). **DimensionSet마다 별도 지표가 생성**됨 |
| MetricDefinition | `Name`(값은 숫자 또는 숫자 배열), `Unit`(기본 NONE), `StorageResolution`(1=고해상도, 60=표준, 기본 60) |
| 한도 | 로그 이벤트당 MetricDefinition 총 100개 이하, 숫자 배열 100개 이하, 이벤트 1 MB 이하 |

- 고카디널리티 값(`requestId` 등)을 **차원**으로 쓰면 고유 조합마다 사용자 지정 지표가 생겨 비용이 늘어난다 → 속성(루트 멤버)으로 기록. [S30][S31]
- 전달은 '최소 1회(at-least-once)'라 중복 지표 값이 가끔 생길 수 있다. EMF 처리 결과는 `AWS/Logs` 네임스페이스 지표(생성 실패·파싱/검증 실패 구분)로 추적한다. [S30][S31]
- 고해상도 EMF 지표에 경보를 걸 땐 로그를 5초 이하 간격으로 flush한다(CloudWatch 에이전트 `force_flush_interval` 기본 5초). 플랫폼에서 제어 못 하면 "M out of N" 경보. [S32]
- Lambda Insights도 EMF로 지표를 추출한다(→ 4.1.5). 코드 구현 상세·Powertools Metrics·`PutMetricData` 비교 → 4-2.md Skill 4.2.3.

### 서비스 통합 문제 디버깅 (Skill 4.1.7)

**API Gateway 로깅 두 종류** [S53][S54]
- **실행 로그(execution)**: API Gateway가 요청을 처리하며 한 일(오류·실행 트레이스·요청/응답 값 등)을 기록 — 디버깅용. 레벨 `ERROR`/`INFO`. 표준 방식은 로그 그룹 `API-Gateway-Execution-Logs_{rest-api-id}/{stage_name}`에 자동 생성되고 이벤트가 1 KB로 잘림. 신규 **CloudWatch Logs delivery**를 쓰면 이벤트 최대 1 MB, 대상(CloudWatch Logs·S3·Firehose)을 직접 선택(표준 방식 로그 그룹은 더 이상 안 쌓임). **Data tracing**(전체 요청·응답 기록)은 운영 API에 비권장.
- **액세스 로그(access)**: 호출자 기록, 형식을 직접 정의. 형식에 `$context.requestId` 또는 `$context.extendedRequestId`가 반드시 포함돼야 한다.
- 둘 다 계정·리전마다 `cloudWatchRoleArn`에 `apigateway.amazonaws.com`을 신뢰하는 IAM 역할(관리형 정책 `AmazonAPIGatewayPushToCloudWatchLogs`)을 설정해야 한다. 로그가 안 나오면 먼저 이 설정을 확인.

| 통합 경로 | 증상 | 먼저 볼 곳 | 원인·해결 |
|---|---|---|---|
| API Gateway → Lambda(프록시) | **502** | 실행 로그(INFO), CloudWatch 지표 | 함수 응답이 필수 JSON(`statusCode`, `headers`, `body`, `isBase64Encoded`) 형식이 아니거나 Lambda 리소스 정책이 API Gateway 호출을 허용하지 않음 [S55] |
| 〃 | **504** | `IntegrationLatency`, Lambda `Duration` | 통합 타임아웃 초과(기본 29초, 50~29,000 ms로 설정, Regional·private REST API는 쿼터 상향으로 29초 초과 가능). 처리 단축·비동기 호출로 분리 [S57][S68] |
| 〃 | **500** + `Lambda invocation failed with status: 429` / `Rate Exceeded` | Lambda `Throttles`·`ConcurrentExecutions` | 동시성 부족 [S56] |
| API Gateway → Lambda 권한 | `Execution failed due to configuration error: Invalid permissions on Lambda function` | Lambda **리소스 기반 정책** | 정책에 `apigateway.amazonaws.com` 주체 + `lambda:InvokeFunction` + 소스 ARN 조건. 콘솔·SAM 템플릿으로 API를 연결하면 정책이 자동 갱신되고 [S58], Lambda 권한 부여자(authorizer)를 CloudFormation·CDK 같은 IaC로 구성하면 권한을 직접 추가해야 한다 [S74]. 수동 관리 API: `AddPermission`·`RemovePermission`·`GetPolicy` [S58] |
| 비동기 호출(S3·SNS·EventBridge → Lambda) | 이벤트 유실 | `DeadLetterErrors`, `DestinationDeliveryFailures` | 함수 오류 시 기본 2회 재시도·큐에 최대 6시간 보관 후 폐기 → DLQ(SQS·SNS) 또는 on-failure destination 구성 [S59][S11] |
| SQS → Lambda(이벤트 소스 매핑) | 같은 메시지 반복·DLQ로 이동 | 큐 가시성 타임아웃, 재드라이브(DLQ) 정책 | 가시성 타임아웃 ≥ 함수 타임아웃의 6배, `maxReceiveCount` ≥ 5 권장, 배치 부분 실패는 `ReportBatchItemFailures` + `batchItemFailures` 응답 [S60][S61] |
| SNS → SQS·HTTP 등 | 전달 실패 | 전달 상태 로깅(CloudWatch Logs의 `providerResponse`), 구독 DLQ | 구독 DLQ는 같은 계정·리전의 SQS [S64] |
| EventBridge → 대상 | 이벤트가 대상에 안 감 | `FailedInvocations`, `InvocationsSentToDlq`, `InvocationAttempts`·`RetryInvocationAttempts` | 기본 24시간·185회 재시도(지수 백오프+지터) 후 폐기 또는 DLQ. 대상별 재시도 정책·DLQ 설정, 대상마다 DLQ 권장 [S62][S63] |
| Step Functions | 실행 실패 | 실행 이력 이벤트를 CloudWatch Logs로 남기는 로깅 레벨(`OFF` 기본, `ALL`/`ERROR`/`FATAL`) [S65] | 상태 정의의 Retry·Catch로 재시도·오류 처리(저작자 정리) |
| 권한 거부 전반 | AccessDenied | CloudTrail 이벤트 기록(관리 이벤트 최근 90일) | 누가 어떤 API를 호출해 거부됐는지 확인 [S66] |

Lambda 통합 오류를 Logs Insights로 좁히는 공식 쿼리(요지) [S56]:
```
parse @message '(*) *' as reqId, message
| filter message like /Method completed with status: \d\d\d/
| parse message 'Method completed with status: *' as status
| filter status != 200
| sort @timestamp asc
| limit 50
```
먼저 통합 유형(프록시 vs 커스텀)을 확인한다 — 타임아웃 로그 형태가 다르다(커스텀: "Execution failed due to a timeout error", 프록시: "Task timed out after ..."). [S56]

## 시험에서 묻는 방식

> 문제 저작자를 위한 제안이며, 시험이 반드시 이렇게 낸다는 단정이 아니다.

1. **지표를 호출 경로 지연 없이 남기기** — 문제 상황: Lambda 함수가 주문 유형별 건수·처리 시간 같은 비즈니스 지표를 남기되, 호출 경로에 CloudWatch API 호출을 늘리지 않고 같은 이벤트를 나중에 로그로도 조회해야 한다. → 정답 단서: "비동기 생성 / 구조화 로그에 지표 정의 / `_aws` 객체 / `cloudwatch:PutMetricData` 불필요" ⇒ EMF(클라이언트 라이브러리·Powertools Metrics). 반면 "CPU·메모리·콜드 스타트 같은 시스템 수준 진단" ⇒ Lambda Insights.
2. **API Gateway 5xx 분해** — 문제 상황: REST API(Lambda 프록시 통합)가 간헐적으로 502/504를 반환한다. → 정답 단서: 502 ⇒ 함수 응답이 `statusCode`/`headers`/`body` JSON 형식이 아님 또는 Lambda 리소스 정책 부재; 504 ⇒ 통합 타임아웃(기본 29초) 초과·`IntegrationLatency`; 500+`429`/`Rate Exceeded` ⇒ Lambda 동시성. 확인 수단 ⇒ 실행 로그(INFO)·CloudWatch 지표·Logs Insights.
3. **로그에서 답 찾는 도구 고르기** — 문제 상황: (a) 여러 로그 그룹에서 특정 요청 ID를 찾아 집계 (b) 배포 직후 로그 흐름을 실시간 확인 (c) 요청이 가장 많은 IP·URL 순위를 상시 확인 (d) 특정 오류 문자열 발생 건수에 경보. → 정답 단서: (a) Logs Insights(최대 50개 로그 그룹) (b) Live Tail (c) Contributor Insights (d) 메트릭 필터 + 경보.
4. **배포 실패 원인 위치 찾기** — 문제 상황: CodeDeploy(EC2) 배포가 `HEALTH_CONSTRAINTS`로 모든 수명주기 이벤트를 건너뜀 / CloudFormation 스택이 `UPDATE_ROLLBACK_FAILED` / CodeBuild가 특정 단계에서 실패. → 정답 단서: CodeDeploy ⇒ 에이전트 실행 여부·443 아웃바운드·서비스 역할·`scripts.log`; CloudFormation ⇒ Events의 *Detect root cause*, 문제 리소스를 바로잡은 뒤 `ContinueUpdateRollback`; CodeBuild ⇒ Phase details + CloudWatch Logs 전체 로그.

## 흔한 함정·혼동 짝

| A vs B | 혼동 이유 | 구분 기준 한 줄 | 출처 |
|---|---|---|---|
| 함수 오류 vs 호출 오류 | 둘 다 '실패'로 보임 | 함수 오류 = HTTP 200 + `X-Amz-Function-Error` 헤더, 호출 오류 = 400·500번대 상태 코드 | [S1] |
| `Errors` vs `Throttles` | 둘 다 실패 신호 | 스로틀·호출 오류는 `Invocations`·`Errors`에 집계되지 않음 | [S11] |
| `Duration` vs 콜드 스타트(`Init Duration`) | 느려 보이는 원인이 다름 | `Duration`은 콜드 스타트 시간을 포함하지 않으며 REPORT 줄에 별도 표기 | [S11][S22] |
| `Latency` vs `IntegrationLatency` | 둘 다 지연 지표 | `Latency` = 전체(통합 + 오버헤드), `IntegrationLatency` = 백엔드 구간만 | [S12] |
| 실행 로그 vs 액세스 로그(API Gateway) | 둘 다 'API 로그' | 실행 = 처리 과정 디버깅(레벨 ERROR/INFO), 액세스 = 호출자 기록(형식 정의·`requestId` 필수) | [S53][S54] |
| Logs Insights vs Live Tail vs 메트릭 필터 | 모두 '로그를 본다' | 과거 로그 임의 질의 / 들어오는 로그 실시간 스트림 / 로그 패턴을 지표로 변환 | [S18][S24][S28] |
| 502 vs 504(API Gateway) | 둘 다 5xx | 502 = 응답 형식·권한 문제, 504 = 통합 타임아웃(기본 29초) | [S55][S57] |
| EMF vs `PutMetricData` | 둘 다 사용자 지정 지표 | EMF = 로그 기반 비동기 추출(`logs:PutLogEvents`만), `PutMetricData` = 동기 API | [S31] |
| Contributor Insights vs Logs Insights의 `stats count(*) by` | 둘 다 top-N | 전자 = 규칙 기반 상시·실시간(매칭 이벤트당 과금), 후자 = 임시 질의(스캔량 과금) | [S36][S18] |
| `ROLLBACK_COMPLETE` vs `UPDATE_ROLLBACK_FAILED` | 둘 다 '롤백' 상태 | 전자 = 생성 실패 후 정리 완료(삭제만 가능), 후자 = 업데이트 롤백 실패(원인 수정 후 `ContinueUpdateRollback`) | [S43][S44] |
| CodeDeploy 에이전트 로그 vs 스크립트 로그 | 둘 다 인스턴스 로그 | `codedeploy-agent.log` = 에이전트 동작, `scripts.log` = 수명주기 훅 스크립트 출력 | [S46] |
| 함수 DLQ(비동기) vs SQS 원본 큐 DLQ | 둘 다 '데드레터 큐' | 비동기 호출은 함수에 DLQ·destination 설정, SQS 이벤트 소스는 큐의 재드라이브 정책(`maxReceiveCount`) | [S59][S60] |

**문항 1** — 대응 Skill: 4.1.4 / 난이도: intermediate
- 문제: 주문 처리 Lambda 함수가 초당 수백 건씩 호출된다. 개발자는 주문 유형별 건수와 처리 시간을 사용자 지정 지표로 남기고 싶다. 호출 경로에 CloudWatch API 호출을 추가하지 않아야 하고, 같은 이벤트를 나중에 CloudWatch Logs Insights로도 조회해야 한다. 가장 적절한 방법은?
- A. 핸들러에서 호출마다 `PutMetricData` API를 동기로 호출한다.
- B. 지표 정의(`_aws` 객체의 Namespace·Dimensions·Metrics)를 담은 JSON 로그를 표준 출력으로 기록한다(임베디드 지표 형식).
- C. 모든 로그 이벤트를 X-Ray 메타데이터로 기록한다.
- D. 함수에 CloudWatch Lambda Insights 확장을 추가한다.
- 정답: B
- 정답 근거: EMF는 로그로 지표를 비동기 생성하고 같은 로그 이벤트를 Logs Insights로 조회할 수 있으며 `logs:PutLogEvents` 권한만 필요하다. https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch_Embedded_Metric_Format.html [S31]
- 오답 해설: A는 호출 경로에 동기 API 호출을 추가하므로 요구사항에 어긋난다(EMF는 비동기). C의 X-Ray 메타데이터는 색인되지 않는 트레이스 부가 정보일 뿐 CloudWatch 지표를 만들지 않는다 [S14]. D의 Lambda Insights는 CPU·메모리 같은 시스템 수준 지표와 콜드 스타트 진단 정보를 수집하는 도구이지 비즈니스 지표를 정의하는 도구가 아니다 [S37].

**문항 2** — 대응 Skill: 4.1.7 / 난이도: intermediate
- 문제: API Gateway REST API(Lambda 프록시 통합)가 일부 요청에 502를 반환한다. 실행 로그(INFO)에는 "Execution failed due to configuration error"가 남고, 함수 코드는 오류 없이 끝나지만 결과 문자열만 `return`한다. 올바른 조치는?
- A. 통합 타임아웃을 29초 이상으로 늘린다.
- B. 함수가 `statusCode`, `headers`, `body`(및 `isBase64Encoded`)를 가진 JSON 객체를 반환하도록 수정한다.
- C. API 스테이지에서 캐시를 켠다.
- D. Lambda 함수의 예약 동시성을 높인다.
- 정답: B
- 정답 근거: Lambda 함수의 권한이 잘못됐거나 API 요청에 대한 응답 형식이 올바르지 않으면 API Gateway가 502를 반환하며, 프록시 통합 출력은 지정된 JSON 형식이어야 한다. https://repost.aws/knowledge-center/malformed-502-api-gateway [S55]
- 오답 해설: A는 통합 타임아웃 초과(504) 대응이다 [S68]. C의 캐시는 성능 기능으로 응답 형식 오류와 무관하다(저작자 정리). D의 동시성 부족은 `Lambda invocation failed with status: 429` 계열(500)의 원인이다 [S56].

**문항 3** — 대응 Skill: 4.1.3 / 난이도: intermediate
- 문제: 마이크로서비스 8개의 로그가 서로 다른 CloudWatch Logs 로그 그룹에 있다. 지난 3시간 동안 특정 요청 ID가 들어 있는 이벤트를 모든 로그 그룹에서 한 번에 찾아 시간순으로 보려 한다. 가장 적절한 도구는?
- A. CloudWatch Logs Live Tail
- B. CloudWatch Logs Insights에서 8개 로그 그룹을 선택하고 `filter` 쿼리를 실행한다.
- C. 로그 그룹마다 메트릭 필터를 만든다.
- D. Contributor Insights 규칙을 만든다.
- 정답: B
- 정답 근거: Logs Insights는 쿼리 하나에 최대 50개 로그 그룹을 지정해 저장된 로그를 질의한다. https://docs.aws.amazon.com/AmazonCloudWatchLogs/latest/APIReference/API_StartQuery.html [S19]
- 오답 해설: A의 Live Tail은 새로 수집되는 로그 이벤트를 스트리밍으로 보는 도구다 [S24]. C의 메트릭 필터는 로그 패턴을 지표로 바꾸는 기능이다 [S28]. D의 Contributor Insights는 로그 필드 기준 top-N 기여자를 집계한다 [S36].

**문항 4** — 대응 Skill: 4.1.6 / 난이도: intermediate
- 문제: EC2 인스턴스 대상 CodeDeploy 배포가 모든 수명주기 이벤트가 건너뛰어진 채 `HEALTH_CONSTRAINTS` 오류로 실패했다. 가장 먼저 확인할 것은?
- A. 인스턴스에서 CodeDeploy 에이전트가 설치·실행 중인지, 그리고 CodeDeploy·S3 엔드포인트(443)에 접근할 수 있는지
- B. 애플리케이션의 단위 테스트 통과 여부
- C. CloudFront 배포의 캐시 정책
- D. DynamoDB 테이블의 읽기 용량
- 정답: A
- 정답 근거: 모든 수명주기 이벤트가 건너뛰어졌을 때의 원인으로 에이전트 미설치·미실행, 443 접근 불가, 서비스 역할 권한 등이 제시된다. https://docs.aws.amazon.com/codedeploy/latest/userguide/troubleshooting-deployments.html [S47]
- 오답 해설: B는 훅 스크립트·앱 단계에 도달하기 전의 문제를 설명하지 못한다(저작자 정리). C·D는 CodeDeploy 에이전트 통신과 무관하다.

**문항 5** — 대응 Skill: 4.1.6 / 난이도: advanced
- 문제: 스택 업데이트가 실패한 뒤 롤백까지 실패해 CloudFormation 스택이 `UPDATE_ROLLBACK_FAILED` 상태가 되었다. 이벤트를 보니 롤백 대상이던 DB 인스턴스가 스택 밖에서 삭제된 것이 원인이다. 스택을 정상 상태로 되돌리는 올바른 방법은?
- A. 같은 템플릿으로 `UpdateStack`을 다시 호출한다.
- B. 삭제된 DB 인스턴스를 원래 스택 템플릿과 같은 이름·속성으로 수동 복구한 뒤 `ContinueUpdateRollback`을 실행한다.
- C. 스택 생성 작업을 취소해 `ROLLBACK_COMPLETE` 상태로 바꾼다.
- D. 변경 세트(change set)를 삭제한다.
- 정답: B
- 정답 근거: 스택 밖에서 리소스를 바꾼 것이 원인이면 원래 스택 템플릿과 일치하도록 리소스를 맞춘 뒤 롤백 계속을 실행한다. https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/troubleshooting.html [S45]
- 오답 해설: A는 `UPDATE_ROLLBACK_FAILED` 상태의 스택이 업데이트될 수 없어 불가능하다 [S44]. C의 `ROLLBACK_COMPLETE`는 스택 생성이 실패한 뒤에만 존재하는 상태다 [S43]. D는 롤백 실패 상태를 해소하지 못한다(저작자 정리).
