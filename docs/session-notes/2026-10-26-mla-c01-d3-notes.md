## 2. 문서 간 `#앵커` 링크도 가드가 보지 않는다

가드는 **문항 `section` ↔ 같은 Task md의 `{#앵커}}`**만 짝을 맞춘다. 다른 문서로 거는
`[...](mla-t2-2.md#distributed-spot)` 같은 링크는 **아무도 검사하지 않는다.** 도메인 3에서
끊긴 링크 1건이 나왔다(실제 앵커는 `#speedup`). 전수 검증:

```sh
cd /d/workspace/awc-docs
for f in mla-t4-1 mla-t4-2 mla-t4-3; do
  grep -oE '\(mla-t[0-9]-[0-9]\.md#[a-z0-9-]+\)' flutter_app/assets/content/mla/$f.md \
    | tr -d '()' | sort -u | while IFS='#' read -r tgt anc; do
      grep -q "{#$anc}" "flutter_app/assets/content/mla/$tgt" || echo "BROKEN in $f: $tgt#$anc"
    done
done
```

## 3. ⚠️ 앵커 이름이 기존 문서와 충돌할 수 있다 (중복 정본의 신호)

t3-1에 `service-status` 앵커를 두려다 **`mla-t2-1` 8) `{#service-status}`가 이미 수명 주기
정본**인 것을 외부 지적으로 알았다. 가드는 앵커를 **문서 단위로만** 보므로 같은 이름이 두
문서에 있어도 통과한다. 그런데 **앵커 이름이 겹치면 거의 항상 내용도 겹친다.**

```sh
grep -ohE '\{#[a-z0-9-]+\}' /d/workspace/awc-docs/flutter_app/assets/content/mla/mla-t*.md \
  | sort | uniq -c | sort -rn | head -20
```

`mla-t2-1` 8)이 소유한 것: Maintenance·Sunset·Full Shutdown 정의 · 시험 범위에 남아 있지만
상태가 다른 서비스 13행 표 · "날짜가 둘 적힌 행은 공지일 → 발효일" 읽는 법. **도메인 4는

용어와 표는 `mla-t2-1` 8)로 링크하고 그 Task 관점의 영향만 쓸 것.** t3-1이 쓴 방식:

## 4. 분량 추정 — Skill 수만으로는 모자라고 소절 수 × 표 밀도를 봐야 한다

도메인 2 메모 §2의 Skill 항목 수 기준에 **소절 수**를 더해야 맞는다. 도메인 3 실측:

| Task | Skill(K+SK) | 조사 노트 | 소절 | 추정 | **실제** |
|---|---|---|---|---|---|
| 3-1 | 13 | 874줄 | 15 | 420~470 | **454줄** ✅ |
| 3-2 | 11 | 748줄 | 13 | 390~430 | **463줄** (초과) |
| 3-3 | 12 | 1,001줄 | 14 | 440~490 | **576줄** (초과) |

초과 이유가 분명하다 — **소절마다 독립적인 표가 붙으면 Skill 수와 무관하게 늘어난다.**
3-3은 CodePipeline·CodeBuild·CodeDeploy 세 서비스가 각각 구조·할당량·훅·배포 구성 표를
요구했고, 3-2는 소절 13개 각각에 API 파라미터·한도 표가 붙었다.

**도메인 4 가늠법:** `grep -cE '^- \*\*(K|SK)[0-9]+\.'`로 Skill 수를 세고, 노트의
`grep -cE '^### 2\.[0-9]+'`로 소절 수를 센 뒤 **소절당 30~40줄**로 잡는 편이 Skill 수
기준보다 정확하다. 사실을 덜어내 줄이지 말고 PR 본문에 이유를 적는다(3배치 연속 그렇게 했다).
