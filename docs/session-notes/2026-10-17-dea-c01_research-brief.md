## 2. 도구와 출처

### 2.1 도구 로드(처음에 한 번에)
`ToolSearch` 로 `select:mcp__plugin_aws-startup-advisor_aws-mcp__aws___search_documentation,mcp__plugin_aws-startup-advisor_aws-mcp__aws___read_documentation,WebFetch,WebSearch` 를 **한 번에** 로드한다.

### 2.2 우선순위
1. **`aws___search_documentation`** — 결과 `context`가 **페이지 원문(chunk, verbatim)**이라 인용 근거로 가장 좋다. 주제(`topics`)는 보통 `["general"]`, API/한도 질문은 `["reference_documentation"]`. 검색어에 서비스명+핵심어(예: `Kinesis Data Streams quotas write throughput per shard`)를 넣는다.
2. **`aws___read_documentation`** — 특정 페이지를 읽는다(`max_length`·`start_index`로 분할, 한 번에 2~5 URL 배치). 검색 chunk에 필요한 내용이 없을 때만 전체를 읽는다.
3. **`WebFetch`** — 위 둘로 못 읽는 URL(aws.amazon.com 제품/요금 페이지 등)에만. ⚠️ WebFetch는 **요약 모델을 거치므로 출력의 따옴표 문장이 원문이 아닐 수 있다.** 인용문으로 쓰기 전에 원문(read_documentation 등)에서 다시 확인하라.
4. **`WebSearch`** — 공식 페이지 URL을 찾는 용도(allowed_domains에 `docs.aws.amazon.com`, `aws.amazon.com` 사용). 검색 결과 요약을 사실 근거로 쓰지 말라.

### 2.3 출처 등급
- **1차(필수)**: docs.aws.amazon.com(서비스 개발자 가이드·API 레퍼런스·백서·Prescriptive Guidance·Well-Architected 데이터 분석 렌즈), aws.amazon.com(제품·FAQ·요금), AWS 공식 블로그, repost.aws/knowledge-center.
- **3자 자료**는 보조로만, 항목에 `[3자]` 표시. **숫자·한도·기본값의 근거로 쓰지 말라.**
- URL은 **도구가 실제로 반환한 URL만** 사용한다. URL을 추측해 조립하지 말라. `#fragment` 없이 `.html` 정식 URL로 적는다(`.md` 아님).

### 2.4 최신성 — 매우 중요
데이터 서비스는 2024~2026에 변경이 잦다(예: Kinesis Data Firehose → Amazon Data Firehose 개명, Kinesis Data Analytics → Managed Service for Apache Flink, QuickSight → Amazon Quick, SageMaker 개편(SageMaker AI / Unified Studio / Catalog), Glue 버전, Redshift Serverless, Zero-ETL, S3 Tables, MWAA 버전, CodeCommit 신규 고객 중단 등). **기억으로 단정하지 말고 현재 공식 페이지로 확인**한다. 개명·종료·신규 고객 중단·maintenance mode·deprecated 공지를 발견하면 반드시 노트에 기록(출처 포함).

### 2.5 조회일
모든 조회일은 **`2026-10-17`** 로 적는다.

## 3. 인용 규칙 (핵심 — 컨트롤러가 **자동 대조**한다)

- "사실·숫자" 표의 **인용 칸**은 출처 페이지에 실제로 있는 **영어 원문 문장 일부를 한 글자도 바꾸지 않고** 복사한다. **15단어 이내**, 큰따옴표(`"`)로 감싼 한 덩어리. 생략은 `…`. 번역·요약·단어 교체·어순 변경 금지.
- 컨트롤러가 각 인용문을 해당 URL의 원문과 **문자열 대조**한다. 원문에 없으면 **환각으로 간주하고 그 행을 삭제**한다. 확신이 없으면 쓰지 말고 gaps로.
- **숫자**(한도·기본값·보존 기간·크기·시간·비율·요금 단위·개수 등)는 반드시 인용을 동반한다. 인용 없는 숫자 금지.
- 출처끼리 값이 다르면 **둘 다** 기록하고 gaps에 `[상충]`으로 올린다.
- 설명은 네 말(한국어)로 쓴다. 긴 문장을 통째로 옮기지 말라(저작권) — 인용은 짧게.
- 서비스 한도(quotas)는 리전·시기·계정에 따라 다를 수 있다 → "조정 가능(adjustable) 여부"와 "기본값" 문구를 함께 기록.

## 4. 파일 작성 방식

- 스켈레톤 `tasks/<n>.md`가 이미 있다. **먼저 Read**한다.
- **헤더 영역(제목 ~ "공식 Skill 항목 원문" 표와 그 아래 `>` 주석)은 수정 금지.** (컨트롤러가 diff로 검사한다.)
- 6개의 `<!-- TODO(...) -->` 주석을 `Edit`으로 **순서대로** 채운다: 핵심 개념 → 시험에서 묻는 방식 → 흔한 함정·혼동 짝 → 사실·숫자 → 자가 점검 문항 후보 → 출처 목록. 채운 뒤 TODO 주석은 남기지 않는다. 섹션 제목(`##`)은 그대로 둔다. 진행 상황이 사라지지 않도록 **섹션 하나를 끝낼 때마다 저장**한다.
- 출처 번호는 파일 안에서 `S1, S2, …`. 본문 사실 문장 끝에 `[S3]` 식으로 단다.
- 한국어로 쓴다. 서비스·기능 고유명사와 코드/API 이름은 영문 원형 유지.
- 파일에 `<!-- -->` 주석 외의 임시 메모를 남기지 말라.

## 5. 섹션별 요구

### 5.1 핵심 개념
- Skill 군집별 `###` 소제목. 제목에 해당 Skill 번호를 단다(예: `### 스트리밍 수집 (Skill 1.1.1, 1.1.10)`).
- **스켈레톤 표의 모든 Skill이 최소 한 소제목에서 다뤄져야 한다.** 섹션 끝에 `#### Skill 커버리지` 표(Skill 번호 | 다룬 소제목)를 넣어 확인한다.
- 각 소제목 구성: ① 무엇이고 왜 쓰는가(1~2줄) ② 동작 원리·선택 기준·제약(시험 시나리오를 풀 수 있는 수준, 3~8줄) ③ 서비스 선택·비교가 걸리면 **비교 표 초안**(열 예: 서비스 | 적합한 경우 | 제약·비용 특성 | 시험 단서 키워드).
- 사실 문장마다 `[S번호]`. 공식 문서로 확인하지 못한 일반 지식은 쓰지 말라.
- v1.1 **신규/개정** Skill(스켈레톤 표의 `v1.1` 열)은 특히 충실하게: 공식 문서에서 정의·핵심 동작·사용처를 확인해 적는다.
- 분량 가이드: 소제목 6~12개, 비교 표 2~5개. 길이를 채우려고 부풀리지 말고 "시험에서 갈리는 지점"에 집중.

### 5.2 시험에서 묻는 방식
- 시나리오 패턴 **2~4개**. 형식: `패턴명 — 시나리오 요지(요구사항 키워드) → 정답 방향(서비스/설정) → 오답 후보와 탈락 이유 → 근거 [S번호]`.
- 패턴은 **공식 문서의 선택 기준·제약**에서 도출한다. 실제 시험 문항을 재현하거나 시험 덤프에서 가져오지 말라. 표현은 "…를 요구하면 …가 정답 방향" 형태.

### 5.3 흔한 함정·혼동 짝
- 6개 이상(서비스가 많은 Task는 10개 이상). 형식: `A vs B — 구분 기준 한 줄 → 시험 단서(키워드) [S번호]`. 예: Kinesis Data Streams vs Firehose.

### 5.4 사실·숫자
- 표 열: `# | 항목 | 값·내용 | 인용(영어 원문, 큰따옴표, ≤15단어) | 출처([S번호] + URL)`.
- 최소 10행(서비스가 많은 Task는 20행 이상). 한도·기본값·보존 기간·최소/최대·요금 구조·성능 특성·개명/종료 공지.
- **출처 칸에는 평문 URL**을 적는다(마크다운 링크 `[..](..)` 금지) — 자동 대조 때문.
- 한 행에 인용은 1개(최대 2개).

### 5.5 자가 점검 문항 후보 (3~5개)
완성 문항이 아니라 **재료**다(최종 문항은 취합 세션이 쓰고 사람이 검수). 형식:

```
### 후보 N — Skill x.y.z · foundational|associate
- **문제**: (한국어 시나리오형, 1~3문장)
- **보기**: A. … / B. … / C. … / D. …   (정확히 4개, 오답은 그럴듯한 혼동 짝)
- **정답**: B
- **해설 초안**: (왜 정답인가 1~3문장) [S번호]
- **오답 근거**: A — … / C — … / D — … (각 한 줄)
- **근거**: [S번호] URL — "짧은 영어 인용(≤15단어)"
```
- 정답은 반드시 위 "사실·숫자"/"핵심 개념"에서 근거가 확인된 내용으로만 만든다.
- 서로 다른 Skill을 골고루 다루고, 최소 1개는 "서비스 선택" 시나리오로 한다.

### 5.6 출처 목록
- 열: `번호 | 제목 | URL | 조회일 | 유형(공식/공식블로그/[3자])`.
- 본문의 모든 `[S번호]`는 목록에 있어야 하고, 목록의 모든 항목은 본문에서 한 번 이상 참조되어야 한다.
- 규모: 보통 12~30개. 개수를 채우려 쓸모없는 출처를 넣지 말고, 같은 사실을 가장 직접적으로 뒷받침하는 페이지를 고른다.

## 6. gaps 파일 (`dea-gaps-<ID>.md`)

각 항목 한 블록:
```
- G-<Task>-<nn> [상충|불확실|확인필요|수정제안|분할제안|개명·종료] <내용>
  - 확인 시도: <무엇을 검색/읽었는가>
  - 후속: <누가/무엇으로 확인해야 하나>
```
- 확인하지 못한 사실은 **노트 본문에 넣지 말고** 여기에만 쓴다.
- Skill 정의가 모호해 "무엇을 묻는지 공식 근거로 확정할 수 없는" 항목(예: 스테이트풀/스테이트리스 트랜잭션, 데이터 스큐 메커니즘)은 네가 찾은 가장 가까운 공식 근거와 함께 `[불확실]`로 남긴다.
- 가이드의 서비스명과 현재 공식 서비스명이 다르면 `[개명·종료]`.
- Skill이 많아 학습문서 1개로는 과한 Task는 `[분할제안]`: 어떤 Skill들을 어느 문서로 묶을지와 이유(제안만, 결정은 취합 세션).
- 레포 `flutter_app/assets/exam_guides/DEA-C01.json`(읽기 전용)과 관련된 수정 제안이 있으면 `[수정제안]`.

## 7. 제출 전 자가 점검 (모두 통과해야 보고)

1. 헤더 영역을 수정하지 않았다.
2. `<!-- TODO` 주석이 하나도 남지 않았다.
3. 모든 Skill 번호가 "핵심 개념"에서 다뤄졌고 `Skill 커버리지` 표가 있다.
4. 본문 `[S번호]` ↔ 출처 목록이 일치한다.
5. "사실·숫자" 모든 행에 인용(영어 원문 verbatim, ≤15단어)과 평문 URL이 있다.
6. 숫자가 들어간 문장은 모두 인용이 붙은 사실 행으로도 존재한다.
7. 문항 후보가 3~5개이고 정답·근거가 있다.
8. 확인 못 한 내용은 본문에서 제거하고 gaps에 옮겼다. 추측 문장이 없다.
9. 개명·종료·신규 중단 공지를 반영했다.
