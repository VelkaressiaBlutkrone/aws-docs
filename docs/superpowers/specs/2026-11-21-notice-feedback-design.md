# 공지·피드백 설계 (로드맵 D2)

_작성: 2026-11-21 · 상태: **승인 대기** · 범위: 로드맵 `docs/plans/2026-11-18-productization-roadmap.md` 단계 D 의 D2_
_빌더 관점 리뷰 1회 반영(2026-11-21) — 리뷰가 §6 의 제약 9개를 전부 레포에서 재확인했고, 집어낸 6건 중 5건을 §5-3·§7 에 결정으로 넣었다. 나머지 1건(신고 진입점 범위)은 사용자 결정이다._

---

## 1. 의도와 왜

비공개 테스트 14일(12-01 ~ 12-08 사이 시작)의 목적은 **테스터 피드백 수집**이다. 그런데 지금 앱 안에 창구가 하나도 없다.

- 테스터 의견이 Play 스토어 리뷰나 개인 연락으로만 오고, **문항 오류 신고가 이 레포의 검수 흐름(보고 → 공식 문서 실측 → 전수 가드)에 들어오지 못한다.** 그 흐름은 지금까지 외부 검수 보고를 붙여넣기로 받아 왔다.
- 운영자가 테스터에게 알릴 수단이 Play Console 의 테스트 안내 문구뿐이다. 「이 빌드의 알려진 문제」, 「이번 주 바뀐 것」을 앱 안에서 말할 자리가 없다.

로드맵 §5-③ 이 범위를 이미 좁혀 두었다 — **운영자 → 사용자 공지**와 **사용자 → 운영자 피드백** 두 방향만 만들고, 사용자끼리 보이는 글은 UGC 정책(약관 동의·신고·차단·모더레이션)을 끌고 오므로 출시 후로 둔다.

## 2. 목표

1. 로그인한 사용자가 앱 안에서 의견을 보낸다. 유형에 **문항 오류·학습문서 오류**가 있고, 문항 해설에서 보내면 **그 문항 ID 와 보기 제시 순서가 자동 첨부**된다.
2. 운영자 공지를 사용자가 앱 안에서 읽는다. 읽지 않은 공지가 있으면 홈에서 알린다.
3. 운영자는 **Firebase 콘솔의 컬렉션 그룹 쿼리**(`feedback`)로 전원의 피드백을 모아 읽는다. 앱에 운영자 화면을 만들지 않는다.
4. 처리방침과 Data safety 답안이 새 수집 항목을 정확히 적고, **계정 삭제가 피드백까지 지우며 지워지지 않는 사본은 공시한다.**
5. **Firestore 규칙을 바꾸지 않는다** — 기존 `users/{uid}/**` 규칙이 이 설계의 쓰기를 이미 허용한다.

## 3. 비목표

- 사용자끼리 보이는 글·댓글·좋아요·투표 (UGC 정책 범위)
- 앱 안의 운영자 전용 화면 (콘솔로 충분하다)
- 비로그인 피드백 (사용자 결정 2026-11-21 — §5-2)
- 공지 푸시 알림 (FCM 미도입이고 로드맵 범위 밖)
- 피드백 1:1 답장 (답이 필요하면 처리방침의 연락처 메일로 받는다)
- 공지 본문의 마크다운 렌더 (문항·해설 렌더 경로가 평문 `Text` 인 것과 같은 규율)
- **학습문서 본문 화면의 신고 진입점** (사용자 결정 2026-11-21 — 후속 PR)

## 4. 반목표 — 기술적으로 동작해도 실패인 것

1. **사용자에게 Firebase 콘솔 작업을 요구하는 것.** 지금 병목은 사람 몫(Play 계정 확인·테스터 모집)이고, 규칙 배포를 요구하면 그것을 빠뜨린 채 릴리스될 수 있다. 그러면 라이브에서 피드백이 **조용히 거부**된다.
2. **공지·피드백이 동기 화해 경로에 끼어드는 것.** 동기는 삼방향 화해와 삭제 표식을 쓰는 가장 섬세한 코드다. 피드백은 단방향 쓰기이고 화해 대상이 아니다. (리뷰 확인: `SyncService` 는 명시된 컬렉션 리터럴만 건드려 `feedback` 과 구조적으로 무관하다.)
3. **계정 삭제가 피드백을 남기는 것.** 사용자는 지워졌다고 믿는다. 클라이언트 SDK 가 서브컬렉션을 나열할 수 없어 목록을 돌 수밖에 없고, 목록이 낡으면 조용히 남는다.
4. **처리방침·Data safety 답안과 실제 수집이 어긋나는 것.** 지금 초안은 「메시지: 없음」과 「자유 텍스트 입력은 없다」를 적는다 — 피드백은 **그 두 줄을 동시에 거짓으로 만든다**(리뷰 발견).
5. **전송 결과가 화면에 닿지 않는 것** (A4 선례 — 호출부가 `Future` 를 버려 로그인 실패가 조용히 사라졌다). 오프라인에서 **끝나지 않는 스피너**를 보이는 것도 이 실패에 든다(§7-2).

## 5. 접근 — 고려한 것과 선택

### 5-1. 공지를 어디에 두는가

| | A: Firestore 전역 컬렉션 | **B: 번들 JSON (선택)** |
|---|---|---|
| 경로 | `announcements/{id}`, 읽기 전체 허용·쓰기 금지 | `assets/notices.json` |
| 규칙 변경 | **필요** (현재 규칙은 `users/{uid}/**` 하나라 그 밖은 기본 거부) | **없음** |
| 사람 몫 | 콘솔 규칙 배포 1회 + 공지 작성 | 없음 |
| 즉시성 | 앱 업데이트 없이 당장 | 릴리스 필요 (웹은 main 머지로 자동 배포 = 사실상 즉시, Android 는 다음 테스트 빌드) |
| 오프라인 | 안 보인다 | 보인다 |
| 검증 | 없음 (콘솔에서 손으로 쓰는 글) | 가드로 형식·평문 규율 검증, 리뷰 가능 |

**B 를 선택했다**(사용자 결정 2026-11-21). 근거 셋: ① 지금 병목이 사람 몫인데 A 는 거기에 한 단계를 더 얹고 그것을 빠뜨리면 라이브에서 조용히 실패한다 ② 이 레포는 콘텐츠에 대해 로드맵 §5-② 에서 **같은 판정**(번들로 가고 정정은 업데이트로)을 이미 내렸다 ③ 테스트 기간엔 빌드 갱신이 예정된 활동이라 B 의 대가가 작다.

**A 를 다시 꺼낼 조건:** 「지금 당장」이 필요한 공지(진행 중인 장애 안내)가 실제로 생기고, 그때 규칙 배포를 사람이 할 수 있을 때.

### 5-2. 피드백에 로그인이 필요한가

| | **로그인 필수 (선택)** | 비로그인 허용 |
|---|---|---|
| 경로 | `users/{uid}/feedback/{id}` | 전역 `feedback/{autoId}`, 생성만 허용 |
| 규칙 변경 | **없음** (기존 규칙이 본인 쓰기를 이미 허용) | 필요 |
| 스팸 방어 | 계정이 신원이다 | **없음** (Firestore 에 쓰기 속도 제한이 없다) |
| 본인 글 다시 보기 | 된다 (기존 규칙이 읽기도 허용) | 안 된다 |
| 계정 삭제로 지워지는가 | 지워진다 | 익명 데이터라 불가 |
| 대가 | 테스터가 Google 로그인을 해야 한다 (허들·거부 가능) | — |

**로그인 필수를 선택했다**(사용자 결정 2026-11-21). 로그인은 이미 구현된 항목(「기기 간 동기」)이라 새 사람 몫이 없고, 규칙 변경 0 과 계정 삭제 포함이 함께 따라온다.

비로그인 사용자에게는 폼 자리에 **왜 로그인이 필요한지와 로그인 버튼**을 보인다 — 빈 화면이나 비활성 버튼을 두지 않는다.

### 5-3. Data safety 제출 전에 내보내도 되는가 — 빌드 플래그를 쓰지 않는다

리뷰가 「Console 갱신 전 빌드가 테스터에게 나가는 창」을 지적하며 `audio_lecture` 식 dart-define 게이트를 제안했다. **쓰지 않는다.** 근거:

1. **내부 테스트 트랙은 Data safety 면제다** — 공식 도움말이 "apps that are active on internal testing tracks are exempt from inclusion in the data safety section" 로 적는다. 로드맵 B1 이 그 트랙이다.
2. **비공개(closed) 테스트부터는 양식이 필요하고, 미완이면 Play 가 새 릴리스를 심사에 보내지 못하게 막는다** — 즉 14일 요건이 걸린 B2 에서는 **제출이 구조적으로 선행**된다. 플래그로 막을 창이 그만큼 좁다.
3. **웹은 Play 정책 대상이 아니다.** 웹 쪽 공시는 처리방침이고 그것을 **같은 PR 에서** 고친다(§7-4).
4. 레포의 Data safety 초안을 같은 PR 에서 갱신하므로 **제출 시점에 정확한 답이 준비돼 있다.** 사람이 할 일은 그 답을 Console 에 옮기는 것뿐이고, 그 작업은 B2 전에 이미 로드맵 A0 의 「Console 앱 콘텐츠 제출」로 잡혀 있다.

플래그를 넣으면 `bool.fromEnvironment` 상수 + `pages.yml` + `build_android_release.ps1` + `release_flag_sync_test` + CI 의 플래그 켠 단계가 따라와, **막는 위험보다 유지 비용이 크다.** 대신 §7-4 의 문서 갱신을 **이 PR 의 완료 기준에 넣어** 코드와 답안이 함께 나가게 한다.

> ⚠️ 이 판정은 공식 도움말 문면에 근거한다. **Console 화면이 최종 근거**라는 로드맵 §2 의 규율은 그대로다 — B2 개설 시 「앱 콘텐츠」가 완료 상태인지 사람이 확인한다.

## 6. 제약 (전부 2026-11-21 실측 · 리뷰가 9개 전부 재확인)

1. **`CloudStore` 는 `users/{uid}/{collection}/{docId}` 로 경로가 하드코딩돼 있다**(`firestore_cloud_store.dart:14`). 피드백은 이 추상화에 그대로 맞고, 공지(전역)는 맞지 않는다 — B 안이 그 문제를 없앤다.
2. **배포된 규칙은 `users/{uid}/{document=**}` 하나**이고 콘솔 배포는 사용자 몫이다.
3. **`account_deletion_test` 가 `sync_service.dart` 소스에서 `(uid, '<name>'` 패턴으로 컬렉션을 뽑아 `kSyncedCollections` 와 집합 일치를 단정한다.** 그 스캔은 **그 파일만** 읽으므로, `feedback` 을 목록에 그냥 더하면 **가드가 깨진다**.
4. **`legal_pages_test` 가 `privacy.html` 의 `data-record="<name>"` 집합이 `kSyncedCollections` 와 같은지 단정한다.**
5. **Data safety 초안이 「메시지: 없음」과 「기타 사용자 생성 콘텐츠: 자유 텍스트 입력은 없다」를 적는다**(`docs/play/2026-11-20-data-safety-and-listing-draft.md`). 피드백은 그 두 줄을 함께 거짓으로 만든다.
6. **시각 직렬화 관례는 `createdAtMs`(UTC epoch ms, `int`)다**(`attempt_record.dart:86`). 이 레포는 Firestore `Timestamp` 를 쓰지 않는다.
7. **`package_info_plus` 가 없고** 두 릴리스 명령 모두 `--build-name/--build-number` 를 넘기지 않는다(`pubspec.yaml:19` = `1.0.0+1`).
8. 문항·해설 렌더 경로는 평문 `Text` 다. **보기는 전 경로에서 셔플된다**(`applyOptionOrders`).
9. **`ExplainBox` 는 `quiz_page.dart` 두 곳에서만 쓰이고**(연습 퀴즈) 시험·자격증 모의고사·오답노트의 해설은 `quiz_widgets.dart` 의 **`ResultCard` 공용 위젯**이 그린다. 둘 다 문항 정체를 모른다(파라미터 추가가 필요하다).
10. **Firestore 오프라인 지속성이 Android 에서 기본 ON** 이고 `set()` 의 Future 는 서버 ack 까지 완료되지 않는다. 레포에 사용자 대면 awaited Firestore 쓰기 선례가 없다.
11. 메뉴는 `PopupMenuButton` 이고 `HomeHeader` 는 **홈 전용**이다(문서·시험 화면은 `AppHeader.document`).

## 7. 결정된 설계

### 7-1. 공지 (번들)

- **자산:** `flutter_app/assets/notices.json` + `pubspec.yaml` 파일 단위 선언.
- **스키마:** `[{ "id": "n-20261201-01", "date": "2026-12-01", "title": "...", "body": "..." }]` — 최신이 앞. `body` 는 평문이고 `\n` 으로 단락을 가른다.
- **모델·로더:** `lib/models/notice.dart` · `lib/data/notices.dart`(`rootBundle.loadString` — 문항 뱅크 로더와 같은 방식).
- **콘텐츠 규율 — append-only(리뷰 5 반영, 내 결정):** 공지는 **더하기만** 한다. **id 를 지우거나 재사용하지 않고** 이미 내보낸 공지의 `id`·`date` 를 바꾸지 않는다(오타 정정 같은 본문 수정은 허용). 그래야 읽음 기준을 id 하나로 저장할 수 있다. 가드가 **「기존 id 가 사라지지 않았다」**를 커밋된 목록과 대조하는 대신, 더 싼 쪽을 쓴다 — **id 집합이 유일하고 `date` 내림차순이며 형식이 맞는지**를 단정하고, append-only 는 문서 규율로 두고 §7-1 의 폴백이 그 위반을 **안전하게** 흡수한다(아래).
- **읽음 상태:** 로컬 KV 키 `notices.readUpTo` 에 **가장 최근 읽은 공지의 id**. 목록 화면을 열면 최신 id 로 갱신한다. **동기하지 않는다**(기기별 상태이고, 동기하면 컬렉션이 늘어 §6-3·§6-4 가드 셋을 모두 건드린다).
- **폴백 두 가지(리뷰 5 반영, 내 결정):**
  - `readUpTo` 가 **번들에 없는 id** 를 가리키면(규율 위반이나 손상) **「전부 읽음」으로 간주**한다. 「전부 안 읽음」으로 떨어뜨리면 전 기기에 배너가 되살아나는데, 그것이 더 나쁜 실패다.
  - `readUpTo` 가 **비어 있으면**(신규 설치) 역시 **「전부 읽음」**이다. 14일 테스트에서 새 테스터가 보는 첫 화면이 공지 배너가 되지 않게 한다 — 공지는 메뉴에서 언제든 읽을 수 있고, 배너는 **「내가 본 뒤에 새로 온 것」**만을 뜻하게 된다.
- **화면:** 라우트 `/notices` → `NoticesPage` (카드 목록, 최신 먼저, 안 읽은 것에 표식).
- **진입점 둘:** 메뉴 항목 「공지」(안 읽은 수를 함께) + **홈 배너**(안 읽은 공지가 있을 때만). 배너 우선순위는 **진행 중인 시험 > 오늘 할 일(due) > 공지** — 시계가 도는 것이 가장 급하다는 기존 판단을 유지한다.
- **가드:** id 유일·형식 · `date` 형식과 내림차순 · 본문 평문(마크다운 링크·단일 이탤릭 0건, 레포 전역 규율과 같은 탐지기) · pubspec 선언 · **빈 배열에서도 화면이 정상**(초기 상태가 그것이다) · 폴백 두 경우.

### 7-2. 피드백 (Firestore, 기존 경로)

- **경로:** `users/{uid}/feedback/{id}` — **기존 규칙 그대로.** `CloudStore.setDoc(uid, 'feedback', id, data)` 를 그대로 쓴다.
- **문서:**
  ```
  { "kind": "question|content|bug|idea|other",
    "body": "<1~2000자 평문>",
    "createdAtMs": 1764547200000,
    "app": { "version": "1.0.0+1", "platform": "android|web" },
    "context": { "certCode": "SAA-C03", "taskId": "saa-t1-1",
                 "questionId": "saa-t1-1-q3",
                 "shownOptions": ["...", "...", "...", "..."], "pickedIndex": 1 } }
  ```
  `context` 는 그 화면에서 열었을 때만 붙는다. `id` 는 클라이언트 생성(`createdAtMs` + 난수 접미사 — auto-id 가 없는 경로이므로).
- **보기 셔플 대응(리뷰 6 반영 + 2026-11-21 실측으로 단순화):** 원래 제시 순서 인덱스 배열(`optionOrder`)을 담으려 했으나, 실측하면 **`ResultCard` 가 받는 `Question` 은 이미 `applyOptionOrders` 가 적용된 것**이라 `q.options` 자체가 **사용자가 본 순서**다. 그래서 인덱스가 아니라 **보여 준 보기 원문(`shownOptions`)과 사용자가 고른 자리(`pickedIndex`)**를 담는다 — 운영자가 문항 JSON 과 맞출 필요 없이 바로 읽히고, 보기 네 개 원문은 수백 바이트라 크기도 문제가 없다. 전달은 `go_router` 의 `extra`(쿼리 문자열에 배열을 넣지 않는다). **폼 문구로도** 「어느 보기인지 내용을 그대로 적어 주시면 더 빠릅니다」를 유도한다.
- **서비스:** `lib/data/cloud/feedback_service.dart` — `CloudStore` 와 `AuthService` 만 받는다(테스트는 기존 `FakeCloudStore`·`FakeAuthService` 재사용). 주입은 `main.initCloudSync()` 안에서 기존 `syncController` 와 같은 `ValueNotifier<FeedbackService?>` 패턴으로 한다(동기 코드를 건드리지 않는다).
- **앱 버전:** `lib/app_version.dart` 에 `const kAppVersion = '1.0.0+1';` 를 두고 **가드가 `pubspec.yaml` 의 `version:` 과 일치를 단정**한다. 의존성을 더하지 않는 쪽이다(`package_info_plus` 는 웹 번들 오염 측정이 필요하고, 이 레포는 그 비용을 A4·D1 에서 두 번 치렀다). 버전을 올릴 때 두 곳을 고치고, 빠뜨리면 가드가 잡는다.
- **플랫폼:** `kIsWeb ? 'web' : defaultTargetPlatform.name`.
- **전송 완료 판정(리뷰 3 반영, 내 결정):** `setDoc` 을 **3초 타임아웃으로** 기다린다.
  - ack 가 오면 「보냈습니다」.
  - **타임아웃이면 성공으로 보고 「보냈습니다 — 네트워크가 연결되면 올라갑니다」**라고 적는다. Firestore 오프라인 큐는 앱을 닫아도 유지되고 재연결 시 올라가므로 사용자 관점에서 **참인 서술**이고, 끝나지 않는 스피너(§4-5)를 만들지 않는다.
  - 예외가 오면 실패 문구 + 재시도. `warningText`/`surface2` 는 `theme_contrast_test` 가 이미 AA 로 단정하는 쌍이다.
  - 가드는 **지연을 주입하는 Fake 스토어**로 세 분기를 짚는다.
- **화면:** 라우트 `/feedback` → `FeedbackPage` — 유형 선택 + 본문 + 전송, 그 아래 **내가 보낸 의견 목록**(`loadCollection`). 메뉴 항목 「의견 보내기」.
- **신고 진입점(사용자 결정 2026-11-21 — 결과 복기 + 연습 퀴즈. 2026-11-21 실측으로 범위가 좁아졌다):**
  - 공용 **`ResultCard`** 한 곳에 「신고」를 달면 **시험·자격증 모의고사·연습 퀴즈 결과 세 화면이 모두 덮인다** — `ResultsView` → `ResultCard` 경로의 호출부가 `exam_view.dart:425` 와 `quiz_page.dart:197` 둘뿐이고 `cert_exam_page` 는 `ExamView` 를 재사용한다(실측).
  - `ResultCard` 는 `Question` 을 그대로 받아 **`q.id` 와 보여 준 보기를 이미 안다** — 새 식별자 파라미터가 필요 없고, `onOpenStudy`(「null 이면 링크 숨김」)와 **같은 모양의 `onReport` 콜백 하나**만 더한다. 주지 않으면 버튼이 그려지지 않아 기존 호출부·스냅샷 영향이 없다.
  - ⚠️ **`ExplainBox` 에는 달지 않는다.** 그것은 진행 중 퀴즈의 즉시 피드백이고(문항당 두 개가 붙는다) 연습 퀴즈의 **결과** 화면은 이미 `ResultsView` 를 쓰므로 사용자가 고른 범위가 그대로 충족된다. 덤으로 「진행 중 이동 시 5문항 재샘플링」(리뷰 발견) 문제도 생기지 않는다 — 신고는 결과 화면에서만 열린다.
  - ⚠️ **오답노트(`review_page`)는 `ResultsView` 를 쓰지 않는다**(자체 UI — 리뷰 보고의 「review_page 도 공용으로 쓴다」는 부정확했다). 이번 범위 밖으로 두고 §9 에 적는다.
  - **학습문서 본문 화면도 이번 범위 밖**이다(후속 PR). 그래서 유형 「학습문서 오류」는 이번에 **컨텍스트 없이** 접수되고, 폼이 「어느 문서인지 적어 주세요」를 안내한다.
- **비로그인:** 폼 대신 **전용 안내 위젯** + 로그인 버튼. `SyncEntry` 를 그대로 재사용하지 않는다 — 그것은 「기기 간 동기」·로그아웃·계정 삭제를 함께 들고 있어 피드백 화면에 섞여 들어온다.

### 7-3. 삭제 범위와 동기 범위를 가른다 (§6-3 해소)

```
kSyncedCollections      = [attempts, checks, meta, plans, progress, viewed]   // 동기가 화해하는 것
kUserOwnedCollections   = [...kSyncedCollections, 'feedback']                 // 계정 삭제가 지우는 것
```

- `SyncController.deleteAccount` 가 **`kUserOwnedCollections`** 를 돈다.
- `account_deletion_test`: 소스 대조 단정은 **`kSyncedCollections` 로 그대로 유지**(그 가드의 목적은 동기 드리프트 탐지다) + 새 단정 둘 — 「`feedback` 이 동기 집합엔 없고 소유 집합엔 있다」, 「삭제가 소유 집합 전부를 건드린다」.
- `legal_pages_test`: `data-record` 집합을 **`kUserOwnedCollections`** 와 맞댄다.

### 7-4. 처리방침·Data safety·규칙 테스트 (이 PR 의 완료 기준에 든다)

- **`privacy.html`:** `data-record` 목록은 지금 「**동기하는** 학습 기록」 제목 아래 있다 — 피드백은 동기하지 않으므로 **별 소절로 분리**해 그 제목이 거짓이 되지 않게 한다(추출 정규식은 그대로 통과한다). 항목 문구: 「보낸 의견 — 의견의 유형·본문과 보낸 시각, 앱 버전·플랫폼, 문항 오류면 그 문항의 식별자와 보기 제시 순서. **운영자가 읽습니다.**」
- **지워지지 않는 사본을 공시한다(리뷰 4 반영, 내 결정):** 이 기능의 목적 자체가 신고를 레포 검수 흐름으로 들이는 것이므로, **운영자가 읽고 검수 노트로 전사한 사본과 그로 인한 콘텐츠 정정은 계정 삭제로 사라지지 않는다.** 「전사하지 않는다」는 운영 규율은 §1 의 목적을 깎으므로 택하지 않는다. 대신 **`delete-account.html` 의 「남는 것」 절과 처리방침 보존·삭제 절에 그 예외를 적는다**(`legal_pages_test` 가 그 절에 「남」을 요구하므로 가드도 그대로 맞는다). 이 레포의 「정직성 메모」 관례와 같은 처리다.
- **Data safety 초안:** 두 행을 함께 고친다 — 「메시지 › 기타 인앱 메시지」를 **예(수집)**, 「앱 활동 › 기타 사용자 생성 콘텐츠」의 근거 「자유 텍스트 입력은 없다」를 **의견 본문이 자유 텍스트임**으로. 목적은 「앱 기능·고객 지원」, 「계정 삭제로 지워진다」는 위 예외를 함께 적는다. **분류의 최종 근거는 Console 양식 화면**이라는 로드맵 §2 규율을 초안에 명시한다(§8-⑤ 가 미확인으로 둔 자리).
- **`rules.test.mjs`:** 피드백 **회귀 가드** 셋 — 본인 쓰기 성공 / 타인 경로 쓰기 거부 / 비로그인 쓰기 거부. 규칙을 바꾸지 않으므로 이것은 「지금 동작이 의도한 것임」을 못박는 테스트다.
- **로드맵 D2 완료 기준 정정(리뷰 발견):** 로드맵 `:160` 이 「규칙 테스트에 **공지(운영자만 쓰기)**·피드백(본인만 쓰기, **운영자만 읽기**) 케이스 추가」를 요구하는데, B 안에서는 **공지 규칙 케이스가 존재할 수 없고**(번들이다) `users/{uid}/feedback` 은 **본인도 읽는다**(§7-2 의 「내가 보낸 의견」이 그 권한에 기댄다). 그 행을 이 설계에 맞춰 같은 PR 에서 고친다.

## 9. 이번 범위에 넣지 않은 것 (기록)

- **학습문서 본문 화면의 신고 진입점** — 후속 PR(사용자 결정). 그 화면은 헤더·자가 점검·오디오 플레이어가 엮여 가장 붐빈다.
- **오답노트(`review_page`)의 신고 진입점** — 그 화면은 `ResultsView` 를 쓰지 않고 자체 UI 라 별 작업이다(2026-11-21 실측). 문항을 보여 주는 화면이므로 후속 후보로 남긴다.
- 피드백 유형별 라우팅(문항 오류를 검수 노트로 자동 전사) — 콘솔에서 읽고 사람이 판단하는 것으로 시작한다.
- 공지 「다시 보지 않기」·만료일.
- 피드백 첨부 파일·스크린샷 (Storage 를 끌고 온다).
- 피드백 UI 의 dart-define 게이트 — §5-3 의 근거로 쓰지 않는다.
