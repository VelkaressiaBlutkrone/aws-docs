# 시험 세션 문항 스냅샷 — 설계

_2026-10-24 · 상태: 설계(미구현) · 빌더 검수 1회 반영_

진행 중인 시험이 콘텐츠 릴리스를 가로질러도 **시작 시점 문항 그대로** 끝까지 유지되게 한다.

> **읽는 순서 안내.** §2가 의도, §3이 기각한 길, §4가 결정된 설계다. §4의 각 항목에는 **누가 정했는지**를 표시했다 — `[사용자]`는 사용자가 직접 답한 것, `[작성자]`는 이 문서가 정한 것(뒤집어도 좋다), §7은 빌더에게 넘긴 것이다.

---

## 1. 배경 — 무엇을 발견했나

`saa-t4-2`의 `[의심]` 항목을 정리하다가 통합 모의고사 복원에서 **문항 텍스트 개정이 걸러지지 않는 것**을 찾았다. 처음에는 `CertExamPage`가 `bankFingerprint`를 검사하지 않아서라고 봤는데, **그 전제가 틀렸다.** 현행 지문은 콘텐츠를 해싱하지 않는다:

```dart
/// 문제은행 지문(문항 수 + ID 목록) — 콘텐츠 개정 감지용.
String bankFingerprint(QuestionBank bank) =>
    '${bank.questions.length}:${bank.questions.map((q) => q.id).join(',')}';
```
— `lib/models/exam_session.dart`

문항 수와 ID 목록만 이어붙인 문자열이다. 따라서:

| 화면 | 감지하는 것 | 감지 못 하는 것 |
|---|---|---|
| `ExamPage` (Task 시험, 지문 검사) | 문항 추가·삭제·순서 변경 | **텍스트 개정** |
| `CertExamPage` (통합·약점, ID 존재 + 순서 길이) | 문항 삭제, 보기 개수 변경 | **텍스트 개정** |

즉 **두 시험 화면 공통 공백**이고, 원인은 "한쪽이 지문을 안 본다"가 아니라 **지문이 콘텐츠를 담지 않는다**는 것이다.

**왜 해로운가.** 복원은 세션의 `questionIds`로 **현재 에셋에서 문항을 다시 읽는다**. 보기 텍스트가 바뀌었는데 ID와 보기 **개수**가 그대로면 `restoreOrdered`(ID 존재)도 `ordersCoverQuestions`(길이)도 통과한다. 그러면 저장된 `optionOrders`가 **새 보기 텍스트**에 얹히고, 사용자가 고른 `picked`(표시 인덱스)가 다른 의미를 가리킬 수 있다 — 스펙 `2026-06-08-option-shuffle-question-sampling-design.md` §3.3이 시드 방식을 기각하며 막으려던 **무성 데이터 손상**과 같은 계열이다.

가상의 이야기가 아니다. 2026-10-24 PR #195·#196이 라이브 문항의 `stem`·`options` 텍스트를 고쳤다.

---

## 2. 의도 (why)

**시험을 시작한 사람은 그 시험을 끝낼 때까지 자기가 시작한 시험을 본다.** 문제도, 보기도, 채점도, 결과 화면의 해설도 시작 시점 그대로다. 중간에 콘텐츠 릴리스가 나가도 아무 일이 일어나지 않는다.

`[사용자]` 2026-10-24 결정:
- "시험을 풀던 사람이 중간에 콘텐츠 릴리스를 맞았을 때" → **"그 시험 진행 동안 유지"**
- "결과·오답 해설도 그때 보던 그 해설이어야 하나" → **"그때 보던 그 해설"**

---

## 3. 감지 안을 기각한다

개정을 **더 정확히 감지하는** 방향(콘텐츠 해시를 지문에 넣기, 문항별 해시 저장 등)은 **기각**한다.

이유는 단순하다. 감지해서 할 수 있는 일이 **세션 폐기**뿐인데, 그게 §2의 요구와 정반대다. 감지를 아무리 정밀하게 만들어도 결론이 "풀던 시험을 버린다"로 수렴하면 문제를 푼 게 아니다. 애초에 "어떤 해시를 쓸까"가 잘못된 질문이었다.

---

## 4. 결정된 설계

### 4.1 세션이 문항을 들고 간다

복원이 **현재 에셋을 전혀 읽지 않도록** 세션에 출제 문항 전체를 스냅샷으로 저장한다.

- 저장 내용: 출제된 `Question` 전체 필드 — `id` · `examGuideTaskId` · `skill` · `section` · `difficulty` · `stem` · `options` · `correct` · `explanation` · `wrongExplanations` · `sources` · `verified`
- **보기는 이미 표시 순서로 저장한다.** `Question.withOptionOrder(order)`가 `options`를 재배열하고 `correct`를 `order.indexOf(correct)`로 다시 매핑하므로, 그 결과를 그대로 저장한다
- 복원: 스냅샷을 역직렬화해 `ExamView`에 주입. 에셋 로드·ID 대조·순서 재적용 **전부 없음**

`skill`을 함께 저장하는 것은 의도다 — `AttemptRecord.wrongSkills`에 직렬화되는 값이므로, 사용자가 **실제로 본** 라벨이 기록에 남는 쪽이 옳다.

### 4.2 ⚠️ 스냅샷은 `verified` 게이트보다 우선한다 `[사용자]`

**결정:** 릴리스가 문항을 철회(`verified: true → false`)해도 **진행 중 시험은 그 문항으로 끝까지 출제·채점한다.**

이건 이 레포에서 가장 단단한 불변식과 **의도적으로** 어긋나므로 계약으로 박아야 한다:

- `QuestionBank.fromJson`이 `.where((q) => q.verified)`로 비검증 문항을 런타임에 걸러낸다(`lib/models/question.dart:113`). flip은 사람 검수 전용이다
- **따라서 스냅샷 역직렬화는 `QuestionBank.fromJson`을 쓰면 안 된다** — 쓰면 철회된 문항이 조용히 사라져 세션이 반쪽이 된다. 전용 역직렬화 경로를 둔다
- "스냅샷은 verified 게이트보다 우선한다"를 **테스트로 고정**한다(철회 상태의 에셋으로도 스냅샷 문항이 그대로 출제·채점되는지)

받아들이는 대가: 틀려서 내린 문항으로 채점된 결과가 `AttemptRecord`에 남을 수 있다. 사용자가 그 대가를 알고 선택했다.

### 4.3 응시 자격 게이트는 새 시험에만 적용한다 `[작성자, §4.2에서 파생]`

현행 `CertExamPage._load()`는 복원 판정 **전에** 게이트를 보고 세션을 지운다 — capacity 미달이면 `clearCertExamSessions`로 통합·약점 둘 다, 약점 응시 횟수 미달이면 `clear(_examId)`.

capacity는 `entry.questionCount` 합으로 계산되고 `questionCount`는 `verified:true` 수와 동적 불변식으로 묶여 있다. **즉 문항을 내리는 릴리스가 capacity를 ready→not-ready로 뒤집고, 그 순간 진행 중이던 세션이 복원 판정에 닿기도 전에 사라진다.** §4.2를 정해 놓고 이 경로를 두면 §2가 조용히 깨지고 반목표("오히려 세션을 잃는 것")에 바로 걸린다.

**재배치:** 세션을 먼저 읽고, 게이트는 **새 시험 시작 경로에만** 적용한다. 게이트 화면에서도 진행 중 시험이 있으면 "이어서 풀기"를 띄운다.

### 4.4 저장을 쪼갠다 — 스냅샷 1회 + 진행 소량 `[사용자]`

**결정 근거:** "세션을 지키려다 시험이 버벅이거나 저장이 실패하는 것"이 "구조를 더 복잡하게 만드는 것"보다 신경 쓰인다.

현행은 답을 고를 때마다 `_persist()`가 세션 전체를 다시 쓴다(`_pick`·`_toggleFlag`·`_go`). 스냅샷을 같은 레코드에 넣으면 65문항 시험에서 **112 KB 직렬화·쓰기가 100번 넘게** 반복된다 — 시험 내내 바뀌지 않는 데이터를 매 탭마다 다시 쓰는 낭비이고, localStorage 쓰기는 동기라 메인 스레드를 막는다.

| 키 | 내용 | 쓰기 빈도 |
|---|---|---|
| 스냅샷 | 출제 문항 전체(표시 순서 적용 완료) · `startedAtIso` · `durationSec` · **세대 nonce** | 시작 시 **1회** |
| 진행 | `index` · `picked` · `flagged` · **세대 nonce** | 매 탭(1 KB 미만) |

#### 4.4.1 세대 nonce가 필요한 이유 `[작성자]`

키를 쪼개면 단일 레코드가 갖던 원자성이 사라진다. `examId`는 시험마다 바뀌지 않는 **고정 문자열**(`exam:<taskId>` / `exam:<CODE>-mock|weak`)이라, 같은 키 위에 **다른 세대**가 겹칠 수 있다:

- **같은 탭:** "새로 시작"이 스냅샷을 새로 쓰고 진행을 지우는 두 번의 쓰기 중 두 번째가 쿼터로 실패하면 **새 스냅샷 + 옛 진행**이 남는다. 그 상태로 복원하면 옛 시험의 표시 인덱스가 새 문항에 얹힌다 — §1이 막으려는 손상 그 자체다
- **두 탭:** localStorage는 origin 공유다. A탭이 "새로 시작"하고 B탭이 옛 시험을 메모리에 든 채 진행만 기록하면 B의 진행이 A의 스냅샷에 얹힌다. **이 벡터는 쓰기 순서로 막을 수 없다**

그래서 스냅샷이 세대 nonce를 갖고 진행 키가 그것을 들고 다닌다. **불일치하면 진행을 버리고 스냅샷만으로 index 0·무선택에서 시작한다.**

#### 4.4.2 `submitted`는 저장하지 않는다 `[작성자]`

진행 키 목록에 `submitted`가 없는 것은 의도다. 실측하면 `ExamView._submit()`은 `_persist()`를 호출하지 않는다(`_persist()` 호출처는 `_pick`·`_toggleFlag`·`_go` 세 곳뿐) — **앱은 `submitted:true`를 한 번도 저장한 적이 없다.** 두 페이지의 `!existing.submitted` 가드와 `test/cert_exam_restore_test.dart`의 "제출된 세션" 분기는 **앱이 만들 수 없는 상태를 방어하는 코드**다. 지우지는 않되(방어로서 무해), 이 문서가 그 사실을 기록해 다음 사람이 실재하는 상태로 오해하지 않게 한다.

### 4.5 쓰기 시점 — 화면마다 다르다 `[사용자]`

| 화면 | 스냅샷 쓰기 | 근거 |
|---|---|---|
| `CertExamPage` (통합·약점) | **시작 버튼** 누를 때 1회(차출·셔플 확정 직후) | 시작 화면이 있다 |
| `ExamPage` (Task 시험, 5문항) | **첫 상호작용** 때 1회 | 현행 동작 유지 |

**결정:** Task 시험은 "첫 상호작용부터". 진입만 하고 아무것도 풀지 않고 나가면 세션이 생기지 않고, 재입장하면 5문항을 새로 뽑는다 — 지금과 같다. Task 시험은 반복 응시하는 연습용이라 새로 뽑히는 쪽이 자연스럽다. 따라서 **`ExamPage`에 "새로 시작" UI를 만들지 않는다.**

### 4.6 수명과 정리

- **제출 시 스냅샷·진행 둘 다 삭제** `[사용자]` — 현행 유지. 결과 화면에서 새로고침하면 결과가 사라지고 새 시험이 시작된다. "그때 보던 해설"은 제출 직후 결과 화면을 보는 동안 보장된다. 응시 기록은 그대로 남아 오답노트·약점 리포트에서 보인다
- **버려진 스냅샷은 시간 만료분만 정리** `[사용자]` — `startedAtIso + durationSec`이 이미 지나 복원해도 즉시 자동 제출될 세션만 지운다. **살아 있는 시험은 절대 건드리지 않는다.** 개수 상한·TTL 같은 기준은 반목표("오히려 세션을 잃는 것")를 위반할 수 있어 쓰지 않는다

### 4.7 따라서 사라지는 것

| 대상 | 왜 불필요해지나 |
|---|---|
| `bankFingerprint` (복원 경로) | 개정 감지 자체를 안 한다 |
| `restoreOrdered` (복원 경로) | ID로 현재 뱅크를 조회할 일이 없다 |
| `ordersCoverQuestions` | 저장 시점에 순서가 이미 적용돼 있다 |
| `ExamSession.optionOrders` | 같음 |

**잔존 호출처 실측(2026-10-24):** 이 셋은 두 페이지의 복원 분기와 테스트 4개 파일 밖에서는 쓰이지 않는다. 예외로 `exam_view.dart`가 세션을 만들 때 `bankFingerprint`를 **쓰는**(소비가 아니라 생산) 자리가 하나 있다. `practice:`/`review:` 접두 `examId`는 `AttemptRecord` 전용이고 세션 저장이 없으며, 클라우드 동기(`lib/data/cloud/*`)도 시험 세션을 다루지 않는다.

### 4.8 마이그레이션 — 기존 진행 세션은 폐기 `[작성자]`

구포맷 세션(스냅샷 없음)은 복원하지 않고 새 시험으로 시작한다. 스펙 §3.3이 `optionOrders` 도입 때 쓴 선례를 따른다 — *"구버전 세션은 복원 거부 → 새 시험 시작 (1회성 마이그레이션 비용)"*. 영향 범위는 릴리스 시점에 시험을 진행 중이던 사용자뿐이다.

## 5. 목표 · 비목표 · 반목표

**목표**
- 진행 중 시험이 콘텐츠 릴리스를 가로질러도 문항·보기·채점·해설이 시작 시점 그대로
- 복원 경로가 에셋에 의존하지 않음
- 시험 중 쓰기 비용이 현행과 같은 수준(스냅샷을 매 탭 다시 쓰지 않음)

**비목표**
- **오답노트·약점 리포트의 본문 고정.** 응시 기록은 문항 ID만 들고 현재 뱅크에서 본문을 읽는다. 지난주 오답을 오늘 복습하면 개정된 본문이 보이는데, "그 시험 진행 동안"이 아니라 범위 밖이다
- **제출 후 결과 화면의 새로고침 복원**(§4.6)
- 개정 감지 기능 자체(§3에서 기각)
- 에셋 버전 관리·구버전 에셋 보존

**반목표 (기술적으로 동작해도 실패로 볼 것)**
- 시험 중 입력이 버벅이거나 저장이 실패해 **오히려 세션을 잃는 것** — 사용자가 가장 신경 쓴 지점
- 스냅샷 쓰기 실패가 **시험 시작 자체를 막는 것**
- 정리(GC) 규칙이 **살아 있는 시험을 지우는 것**
- 기존 응시 기록(`AttemptRecord`)의 의미가 바뀌는 것

- **쿼터 산수:** `content_index`에 `ContentEntry`가 **81개**다. Task 시험만 전부 열어 두면 ≈730 KB, 자격증별 통합·약점(각 112 KB)까지 더하면 1 MB를 넘는다. 같은 origin의 localStorage(보통 5 MB)를 응시 이력·열람·플랜 저장소와 나눠 쓴다 — §4.6의 정리 규칙이 이걸 겨냥한다
- **기존 복원 테스트:** `test/cert_exam_restore_test.dart`(4분기) · `test/exam_session_test.dart` · `test/mock_exam_test.dart` · `test/exam_view_test.dart`. 이 설계는 복원 계약을 바꾸므로 **이 테스트들이 바뀐다** — 무엇이 어떻게 바뀌는지 PR에서 명시할 것
- ⚠️ 에셋을 읽는 페이지를 한 테스트 파일에서 두 번 이상 렌더하면 `rootBundle` 캐시 때문에 다음 테스트가 **예외 없이 멈춘다** → `setUp(rootBundle.clear)`

## 8. 검증 계획

- **릴리스를 가로지르는 복원**: 스냅샷과 다른 본문의 에셋이 있어도 시작 시점 문항·보기 순서·채점·해설이 유지되는지
- **철회 우선 계약(§4.2)**: 에셋에서 `verified:false`로 내려간 문항도 스냅샷이면 그대로 출제·채점되는지 — 역직렬화가 `QuestionBank.fromJson`의 필터를 타지 않는다는 것을 고정
- **게이트 순서(§4.3)**: capacity가 not-ready로 뒤집혀도 진행 중 세션이 살아남고 "이어서 풀기"가 보이는지

- **쓰기 비용(§4.4)**: 스냅샷이 시험 중 다시 쓰이지 않는지(쓰기 횟수 계측 백엔드)
- **정리 규칙(§4.6)**: 시간 만료 세션만 지워지고 살아 있는 세션은 남는지
