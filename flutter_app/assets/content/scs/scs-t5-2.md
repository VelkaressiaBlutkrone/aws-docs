# 저장 데이터 (암호화 선택·무결성·수명 주기와 보존·복제와 백업)

> **커버하는 공식 Task** — SCS-C03 · 도메인 5 「데이터 보호」(18%) · **작업 5.2 저장 데이터에 대한 제어 설계 및 구현** (`scs-t5-2`)
> 이 문서는 위 한 작업에 1:1로 매핑되고 공식 기술 4개(5.2.1~5.2.4)를 모두 덮습니다. 키 자료 자체의 계보(KMS 키 저장소 넷·가져온 키·회전)는 작업 5.3(`scs-t5-3`)이 다룹니다.

> ⚠️⚠️ **이 작업에는 「최근에 바뀐 기본값」이 두 개 있습니다.** 2023-01-05부터 **모든 새 객체 업로드가 SSE-S3로 자동 암호화**되고, **2026년 4월부터 새 범용 버킷은 SSE-C가 기본으로 비활성화**됩니다(§1-2). 둘 다 "예전에는 이렇게 했다"가 지금은 거짓이 되는 자리입니다.

> ⚠️⚠️ 그리고 공식 가이드가 데이터 무결성 수단으로 드는 **「S3 Glacier 저장소 잠금」은 신규 고객에게 열려 있지 않은 서비스의 기능**입니다(§2-3). 개념은 알아 두고 **새 설계의 축으로 삼지 않습니다.**

## ✅ 학습 목표 체크리스트

- [ ] S3 서버 측 암호화 선택지와 **상호 배타성**을 안다
- [ ] **최근 바뀐 기본값 둘**(SSE-S3 자동·SSE-C 비활성화)을 말한다
- [ ] Object Lock의 **모드 둘·보존 유형 둘·법적 보존**을 구분한다
- [ ] EBS 스냅샷 잠금이 **IAM 권한을 넘어서는** 이유를 안다
- [ ] Glacier **저장소 잠금의 상태와 두 단계 절차**를 안다
- [ ] CloudTrail **로그 파일 무결성 검증**의 기제를 설명한다
- [ ] S3·EFS·FSx for Lustre의 **수명 주기·백업 조건**을 가른다
- [ ] 랜섬웨어 보호에서 **논리적 에어 갭 저장소**의 역할을 안다

## 🎯 왜 중요한가

저장 데이터 문항은 **"암호화는 됐는데 통제가 없다"**거나 **"보존 규칙을 걸었는데 지워졌다"**로 나옵니다. 둘 다 **어느 통제가 누구를 막는지**를 모르면 풀 수 없습니다.

가장 날카로운 자리는 **"IAM 권한으로도 못 지우는 것"**입니다 — Object Lock **준수 모드**, EBS 스냅샷 잠금, Glacier **저장소 잠금**이 모두 그 범주이고 **각각 되돌릴 수 있는 정도가 다릅니다**(§2). 반대로 **버킷 정책으로는 S3 수명 주기 삭제를 막을 수 없다**는 비대칭도 있습니다(§3-1). 그 둘이 이 문서의 뼈대입니다.

## ⚡ 시험 직전 요약

- **모든 S3 버킷은 기본 암호화가 구성돼 있고 SSE-S3가 기본값**입니다(2023-01-05부터 모든 새 객체 업로드가 자동 암호화, 추가 비용·성능 영향 없음)
- ⚠️⚠️ **2026년 4월부터 새 범용 버킷은 SSE-C가 비활성화**됩니다 — 쓰려면 버킷 생성 후 **`PutBucketEncryption`으로 의도적으로 활성화**해야 합니다
- ⚠️ **`PUT` 요청으로 지정할 수 있는 것은 SSE-KMS·DSSE-KMS·SSE-C**이고 **기본 암호화 구성으로 설정할 수 있는 것은 SSE-KMS·DSSE-KMS**뿐입니다. **한 객체에 두 유형을 동시에 적용할 수 없습니다**
- ⚠️⚠️ **기본 암호화 구성을 바꿔도 기존 객체의 암호화 유형은 바뀌지 않습니다** — **S3 Batch Operations + S3 Inventory**로 Copy 해 재작성합니다
- **Object Lock은 버전 관리가 켜진 버킷에서만** 동작하고, ⚠️ **준수 모드에서는 루트 사용자를 포함한 어떤 사용자도** 덮어쓰거나 삭제할 수 없습니다. **거버넌스 모드**는 특정 IAM 권한을 가진 사용자가 풀 수 있습니다
- ⚠️ **보존 기간에는 고정과 가변 두 유형**이 있습니다 — 가변은 **이벤트 보존 + 기간**을 두고 **보존을 해제할 때** S3가 보존 만료일을 정합니다
- ⚠️⚠️ **잠긴 EBS 스냅샷은 IAM 권한과 무관하게 어떤 사용자도 삭제할 수 없고** 잠금·해제에 **추가 비용이 없습니다**
- ⚠️⚠️ **Glacier 저장소 잠금은 신규 고객에게 열려 있지 않은 독립 Glacier 서비스의 기능**입니다. 잠금은 **두 단계**이고 **24시간 안에 완료하지 않으면 정책이 삭제**됩니다
- ⚠️⚠️ **버킷 정책으로 S3 수명 주기의 삭제·전환을 막을 수 없습니다** — 모든 보안 주체의 모든 작업을 거부해도 수명 주기는 정상 동작합니다
- **랜섬웨어 보호의 축은 AWS Backup 논리적 에어 갭 저장소**입니다 — 불변이고 **Vault Lock 준수 모드가 기본 장착**이며 백업이 **AWS Backup 서비스 소유 계정**에 저장됩니다

## 🔤 먼저 알아야 할 용어

| 용어 | 뜻 |
|---|---|
| **WORM** | write-once-read-many. 한 번 쓰면 바꿀 수 없는 저장 모델입니다 |
| **거버넌스 모드 / 준수 모드** | 전자는 특정 IAM 권한으로 보존을 풀 수 있고, 후자는 **루트 사용자를 포함해 누구도** 풀 수 없습니다 |
| **법적 보존(legal hold)** | 만료일이 **없는** 보존. 명시적으로 제거할 때까지 유지되고 보존 기간과 독립입니다 |
| **다이제스트 파일** | CloudTrail이 전달한 로그 파일들의 해시와 **이전 다이제스트의 서명**을 담는 파일 |
| **서명 프로필 / 코드 서명 구성** | 전자는 AWS Signer의 **발행자 신원**, 후자는 Lambda에서 허용 서명 프로필과 검증 정책을 정하는 리소스 |
| **논리적 에어 갭 저장소** | 불변이고 **서비스 소유 계정**에 백업을 두는 AWS Backup의 2차 저장소 유형 |
| **다자 승인(MPA)** | 저장소 소유 계정에 접근할 수 없을 때 승인 팀의 동의로 복구를 여는 절차 |
| **기본 정책 / 사용자 지정 정책** | Data Lifecycle Manager의 두 갈래. 전자는 리전 전체를, 후자는 **태그로 지정한** 리소스를 대상으로 합니다 |

## 📖 핵심 개념

### 1) 저장 데이터 암호화를 설계한다 (기술 5.2.1) {#encrypt-at-rest}

#### 1-1. S3 서버 측 암호화 — 선택지와 상호 배타성

**서버 측 암호화는 데이터를 받는 서비스가 목적지에서 암호화하는 것**입니다. S3는 객체 수준에서 **AWS 데이터 센터의 디스크에 쓸 때 암호화**하고 접근할 때 복호화합니다.

| 유형 | 키를 누가 관리하나 | 특징 |
|---|---|---|
| **SSE-S3** | S3 | **모든 버킷의 기본값.** 객체마다 **고유 키**로 암호화하고, 추가 안전장치로 **그 키 자체를 루트 키로 암호화해 정기적으로 교체**합니다. **AES-256** |
| **SSE-KMS** | 나 또는 AWS(KMS) | 키를 따로 보고 제어 정책을 편집하며 **CloudTrail로 키 사용을 추적**할 수 있습니다. 고객 관리형 키 또는 AWS 관리형 키 |
| **DSSE-KMS** | 나 또는 AWS(KMS) | SSE-KMS와 비슷하지만 **객체 수준 암호화를 두 겹**으로 적용합니다 |
| **SSE-C** | **내가 제공** | S3가 암·복호를 하지만 **키는 내가 관리해 요청마다 보냅니다** |

⚠️⚠️ **한 객체에 여러 유형의 서버 측 암호화를 동시에 적용할 수 없습니다** — 공식이 "You can't apply different types of server-side encryption to the same object simultaneously"라고 적고, 선택지를 **상호 배타적**이라고 부릅니다.

⚠️ **「개수」를 외우지 않습니다.** 공식 페이지 본문은 "four mutually exclusive options"라고 적는데 **같은 페이지의 소제목은 다섯 개**입니다(위 넷 + **SSE-FSX**). 수가 아니라 **각 선택지가 무엇을 바꾸는가**를 고정합니다.

⚠️ **지정할 수 있는 자리가 다릅니다** — `PUT` 요청으로 지정할 수 있는 것은 **SSE-KMS·DSSE-KMS·SSE-C**이고, **대상 버킷의 기본 암호화 구성으로 설정할 수 있는 것은 SSE-KMS·DSSE-KMS**입니다. "버킷 기본값을 SSE-C로 둔다"는 성립하지 않습니다.

⚠️ 그리고 **암호화 여부가 접근 방식을 바꾸지 않습니다** — 요청을 인증하고 권한이 있으면 암호화된 객체와 아닌 객체의 접근 방법이 같고, **미리 서명된 URL도 똑같이 동작**하며 list API는 암호화 여부와 무관하게 모든 객체를 돌려줍니다.

#### 1-2. ⚠️⚠️ 최근에 바뀐 기본값 둘

| 변경 | 내용 |
|---|---|
| **2023-01-05 —** SSE-S3 자동 적용 | **모든 새 객체 업로드가 자동으로 암호화**됩니다(추가 비용 없음·성능 영향 없음). 상태는 **CloudTrail 로그 · S3 Inventory · S3 Storage Lens · 콘솔 · API 응답 헤더**에서 확인합니다 |
| **2026년 4월 —** SSE-C 기본 비활성화 | **모든 새 범용 버킷에서 SSE-C가 모든 새 쓰기 요청에 대해 비활성화**됩니다. **SSE-C로 암호화된 객체가 없는 기존 버킷**도 같은 조치를 받았습니다. ⚠️ SSE-C가 필요한 애플리케이션은 **버킷을 만든 뒤 `PutBucketEncryption` API로 의도적으로 활성화**해야 합니다 |

⚠️ 이 둘은 **기본값이 최근에 바뀐 자리**입니다. "S3는 기본적으로 암호화되지 않으므로 기본 암호화를 켜라"와 "SSE-C는 아무 버킷에서나 쓸 수 있다"가 둘 다 지금은 거짓입니다.

#### 1-3. 기존 객체는 바뀌지 않는다

⚠️⚠️ **버킷의 기본 암호화 구성을 SSE-KMS로 바꿔도 그 버킷에 이미 있는 객체의 암호화 유형은 바뀌지 않습니다.** 소급 적용하려면 **S3 Batch Operations**를 씁니다 — 객체 목록(S3 Inventory)을 주고 **Copy objects** 작업으로 같은 버킷에 다시 써서 SSE-KMS 객체로 만듭니다. 한 작업이 **수십억 객체**를 처리할 수 있습니다.

> 「설정을 바꿨는데 왜 기존 데이터가 그대로인가」는 이 도메인에서 **세 번** 나오는 모양입니다 — 여기(S3 기본 암호화), 작업 5.3의 **CloudWatch Logs 데이터 보호 정책**(이미 수집된 로그), 그리고 KMS **키 회전**(데이터를 재암호화하지 않습니다, `scs-t5-3` §2-2).

#### 1-4. KMS와 CloudHSM 중에서 고른다

공식 기술 5.2.1이 **"AWS CloudHSM 또는 AWS KMS 등의 적절한 암호화 키 서비스 선택"**을 명시합니다. 그 판단의 공식 근거는 **키 저장소 넷의 절충안**이고 작업 5.3에서 다룹니다(`scs-t5-3` §1). 여기서 기억할 한 줄만 미리 둡니다 — **공식은 "모든 옵션이 똑같이 안전하고 차이는 운영 절충"**이라고 적고 **대부분의 고객에게 표준 키 저장소**를 권합니다.

### 2) 데이터 무결성을 보호한다 (기술 5.2.2) {#integrity}

#### 2-1. S3 Object Lock

Object Lock은 **WORM 모델**로 객체를 저장해, 고정·가변 기간 또는 무기한으로 삭제·덮어쓰기를 막습니다. ⚠️ **S3 버전 관리가 켜진 버킷에서만 동작**하고, 잠금 정보는 **그 객체 버전의 메타데이터**에 저장되며 **요청에 지정된 버전만** 보호합니다.

**관리 방법이 둘입니다.**

| 방법 | 성질 |
|---|---|
| **보존 기간** | 객체 버전이 잠겨 있는 기간. ⚠️ **유형이 둘**입니다 — **고정**은 내가 보존 만료일(retain-until-date)을 지정하고, **가변**은 **이벤트 보존과 그 기간**을 지정해 **보존을 해제할 때 S3가 만료일을 정합니다**(이벤트 보존 중에는 S3가 만료일을 현재 값보다 이르게 바꾸지 않습니다) |
| **법적 보존** | 보존 기간과 **같은 보호**이지만 **만료일이 없습니다.** 명시적으로 제거할 때까지 유지되고 보존 기간과 **독립**입니다 |

한 객체 버전은 **보존 기간·법적 보존·둘 다**를 가질 수 있습니다.

**모드 둘이 핵심입니다.**

- **거버넌스 모드** — 대부분의 사용자에게서 삭제를 막지만, **특정 IAM 권한을 가진 사용자**가 보존 설정을 바꾸거나 삭제할 수 있습니다
- ⚠️⚠️ **준수 모드** — 보호된 객체 버전을 **AWS 계정의 루트 사용자를 포함한 어떤 사용자도** 덮어쓰거나 삭제할 수 없습니다

⚠️ **버킷 정책으로 허용 범위를 좁힐 수 있습니다** — **`s3:object-lock-remaining-retention-days` 조건 키**로 허용되는 **최소·최대 보존 기간**을 정합니다. 그리고 버킷에 **기본 보존 기간**을 설정할 수도 있습니다.

⚠️ 규제 적합성의 근거는 **Cohasset Associates 평가**입니다 — **SEC 17a-4 · CFTC · FINRA** 규제 대상 환경용으로 평가됐습니다.

#### 2-2. EBS 스냅샷 잠금

⚠️⚠️ **잠긴 스냅샷은 그 사용자의 IAM 권한과 무관하게 어떤 사용자도 삭제할 수 없습니다.** 실수·악의적 삭제를 막거나 **특정 기간 WORM 형식으로 보관**하는 데 씁니다. 잠긴 스냅샷도 **평소처럼 사용**할 수 있습니다.

- 모드는 **준수 모드와 거버넌스 모드** 둘이고, **특정 기간** 또는 **특정 날짜까지** 잠글 수 있습니다
- ⚠️ **잠금과 해제에 추가 비용이 없습니다** — 잠긴 스냅샷에도 표준 EBS 스냅샷 스토리지 비용만 냅니다
- Object Lock과 같이 **Cohasset Associates**가 SEC 17a-4·CFTC·FINRA 환경용으로 평가했습니다

> ⚠️ 이 잠금은 **보존 자동화와 충돌합니다** — Data Lifecycle Manager는 보존 정책과 무관하게 **잠긴 스냅샷을 삭제할 수 없습니다**(§4-1).

#### 2-3. ⚠️⚠️ Glacier 저장소 잠금 — 닫힌 서비스의 기능이다

공식 기술 5.2.2가 **"S3 Glacier 저장소 잠금"**을 데이터 무결성 수단으로 듭니다. 개념은 이렇습니다.

- **저장소 잠금 정책**으로 개별 금고(vault)에 **WORM 같은 준수 통제**를 배포하고 **그 정책을 이후 편집에서 잠급니다**. ⚠️ **잠긴 뒤에는 정책을 바꾸거나 삭제할 수 없습니다**
- **금고 액세스 정책과 다릅니다** — 둘 다 접근을 통제하지만 **저장소 잠금만 잠글 수 있어** 준수 통제를 강하게 강제합니다. 금고 액세스 정책은 **준수와 무관하고 임시이며 자주 바뀌는** 접근 통제에 씁니다. **함께 쓸 수 있습니다**(저장소 잠금으로 삭제 거부, 액세스 정책으로 지정된 제3자에게 읽기 허용)
- ⚠️⚠️ **잠금은 두 단계**입니다 — ① 정책을 연결해 잠금을 **개시**하면 **진행 중(in-progress)** 상태가 되고 **잠금 ID**가 돌아옵니다. 이 상태에서 **24시간** 안에 정책을 검증해야 합니다 ② 그 잠금 ID로 **완료**합니다. ⚠️ **24시간 안에 완료하지 않으면 저장소 잠금 정책이 삭제됩니다.** 정책이 의도대로 동작하지 않으면 **중단**할 수 있습니다
- 공식 권고 순서: **금고를 만들고 → 저장소 잠금을 완료하고 → 그 다음에 아카이브를 업로드**합니다(그래야 정책이 그 아카이브에 적용됩니다)

⚠️⚠️ **그런데 금고와 저장소 잠금은 「원래의 독립 Glacier 서비스」의 것이고, 그 서비스는 신규 고객을 받지 않습니다.** 공식 Glacier 개발자 안내서의 모든 페이지가 머리에 **"This page is only for existing customers of the Amazon Glacier service using Vaults and the original REST API from 2012."**를 달고, **기존 데이터는 무기한 안전하게 유지되며 마이그레이션이 필요하지 않다**고 적습니다. 새 아카이브 요구에는 공식이 **S3 Glacier 스토리지 클래스**(Instant Retrieval · Flexible Retrieval · Deep Archive)를 권합니다.

⚠️ **스토리지 클래스는 정상입니다** — 닫힌 것은 **금고 기반의 독립 서비스**이고, S3 버킷 안의 Glacier 스토리지 클래스는 영향이 없습니다. 둘을 섞으면 거짓이 됩니다. **새 설계에서 WORM이 필요하면 S3 Object Lock 준수 모드**가 그 자리입니다.

#### 2-4. CloudTrail 로그 파일 무결성 검증

로그 파일이 **CloudTrail이 전달한 뒤 수정·삭제·변경되지 않았는지** 판정하는 기능입니다.

- **업계 표준 알고리즘으로 만들어졌습니다** — **해싱은 SHA-256**, **디지털 서명은 SHA-256 with RSA**입니다. 공식이 "computationally infeasible to modify, delete or forge CloudTrail log files without detection"이라고 적습니다
- **다이제스트 파일**이 **매시간** 전달되고, 그 안에 **그 시간에 전달된 로그 파일들의 정보와 해시 값**이 들어갑니다. ⚠️ 그리고 **이전 다이제스트 파일의 디지털 서명**과 **현재 다이제스트의 서명**(S3 메타데이터 절)이 들어가 **사슬**을 이룹니다
- ⚠️ 다이제스트 파일은 **로그 파일과 같은 S3 버킷**에 전달되지만 **다른 폴더**에 들어갑니다 — 그래서 **세분화된 접근 통제 정책**을 걸 수 있습니다
- 검증은 **AWS CLI**로 하거나 내 도구를 만들어 할 수 있고, 전 리전·여러 계정의 다이제스트를 **한 버킷으로 모을 수 있습니다**

#### 2-5. 디지털 코드 서명 — AWS Signer

**AWS Signer**는 완전관리형 코드 서명 서비스로, 코드가 **변경되지 않았고 신뢰된 발행자로부터 왔음**을 디지털 서명으로 검증합니다.

| 대상 | 방식 |
|---|---|
| **Lambda** | **서명 프로필**(발행자 신원)을 만들고, Lambda에 **코드 서명 구성(CSC)**을 만들어 허용 서명 프로필과 **검증 정책**을 지정합니다. ⚠️ 정책은 **경고(배포 허용)** 또는 **적용(배포 차단)** 둘입니다 |
| **IoT** | ACM으로 **제3자 코드 서명 인증서를 가져와** 업데이트에 서명합니다 |
| **컨테이너 이미지** | Notary Project 의 **Notation CLI**와 함께 쓰고, **서명이 이미지와 함께 레지스트리에 저장**됩니다 |

- ⚠️ Lambda 경로의 전제가 둘입니다 — **버전 관리가 켜진 S3 버킷**이 필요하고, 서명 프로필에 **플랫폼**(예: `AWSLambda-SHA384-ECDSA`)과 **서명 유효 기간**을 지정합니다
- 흐름은 **서명 프로필 생성 → CSC 생성·함수에 연결 → 아티팩트 서명(서명 작업) → `CreateFunction`·`UpdateFunctionCode`로 배포**이고, ⚠️ **검증은 배포 수락 전에** 일어납니다. CSC가 `Enforce`면 서명 검증 실패 시 **배포가 실패**합니다

### 3) 수명 주기와 보존을 자동화한다 (기술 5.2.3) {#lifecycle}

#### 3-1. S3 수명 주기 — 버킷 정책으로 막을 수 없다

**S3 수명 주기 구성**은 객체 그룹에 적용할 규칙 집합이고 **액션이 두 종류**입니다.

- **전환 액션** — 다른 스토리지 클래스로 옮깁니다(예: 생성 30일 후 S3 Standard-IA, 1년 후 S3 Glacier Flexible Retrieval). ⚠️ **전환 요청에는 비용이 있습니다**
- **만료 액션** — 객체를 만료시켜 **S3가 대신 삭제**합니다. ⚠️ 비용은 **최소 스토리지 기간이 있는 클래스에서 만료할 때만** 발생합니다

⚠️⚠️ **버킷 정책으로 수명 주기의 삭제·전환을 막을 수 없습니다** — 공식이 Important 로 적습니다: **"even if your bucket policy denies all actions for all principals, your S3 Lifecycle configuration still functions as normal."** "모든 보안 주체를 거부하는 버킷 정책을 걸어 뒀으니 데이터가 안전하다"는 거짓이고, **보존이 요건이면 Object Lock**이 그 자리입니다.

- ⚠️ **구성은 기존 객체와 이후 추가되는 객체 모두에 적용됩니다** — 30일 만료 규칙을 오늘 추가하면 **이미 30일이 넘은 객체가 제거 대기열에** 들어갑니다
- ⚠️ **과금은 객체가 수명 주기 액션 대상이 되는 즉시** 바뀝니다(실제 만료가 지연돼도 그 이후 스토리지 비용을 내지 않습니다). **예외는 S3 Intelligent-Tiering 전환**으로, 그쪽은 **실제로 전환된 뒤에야** 과금이 바뀝니다
- ⚠️ **수명 주기 전환에 데이터 검색 요금은 없지만**, `PUT`·`COPY`·수명 주기로 **어느 클래스에 데이터를 넣을 때는 요청당 수집 요금**이 있습니다

#### 3-2. Amazon EFS 수명 주기 — 정책 셋

EFS 수명 주기 구성은 **정책 셋**으로 이뤄지고 **파일 시스템 전체**에 적용됩니다. 전환 시점은 **Standard 스토리지 클래스에서 마지막으로 접근된 시점**을 기준으로 하며, ⚠️ 그 시점은 **공개된 POSIX 속성이 아니라 내부 타이머**가 추적합니다(Standard의 파일에 접근하면 타이머가 재설정됩니다).

| 정책 | 기본값 |
|---|---|
| **IA로 전환** | Standard에서 **30일** 접근되지 않은 파일을 Infrequent Access 로 옮깁니다 |
| **Archive로 전환** | Standard에서 **90일** 접근되지 않은 파일을 Archive 로 옮깁니다 |
| **Standard로 전환** | ⚠️ **기본은 되돌리지 않습니다** — IA·Archive 에서 접근해도 그 클래스에 머무릅니다. 지연이 가장 중요한 용례(작은 파일을 대량으로 다루는 애플리케이션 등)에서는 **「첫 접근 시」**를 고릅니다 |

- ⚠️⚠️ **Archive 로 바로 갈 수 없습니다** — IA 로 전환되기 전에는 Archive 로 전환할 수 없어서 **`TransitionToArchive`는 설정하지 않거나 `TransitionToIA`보다 늦어야** 합니다
- ⚠️ **Archive 스토리지 클래스는 Elastic 처리량 모드와 General Purpose 성능 모드 파일 시스템에서만** 쓸 수 있습니다
- 파일 시스템당 **수명 주기 구성은 하나**이고, 빈 정책 배열로 호출하면 **기존 구성이 삭제**됩니다

#### 3-3. FSx for Lustre 백업 — 조건 둘

⚠️⚠️ **자동 일일 백업은 조건이 둘입니다** — **Persistent 스토리지**이고 **독립 파일 시스템**(S3 버킷에 연결되지 않은 것)이어야 합니다. **S3에 연결된 파일 시스템은 자동 백업을 받지 않고**, 그 경우의 공식 대안은 **데이터 리포지토리 연결**로 S3와 동기 상태를 유지하는 것입니다.

- 백업은 **증분**입니다 — 마지막 백업 이후의 변경만 저장합니다
- 백업은 생성 시 정한 **일일 백업 창** 중에 일어나고, 그 시작 시점에 **스토리지 I/O가 잠시 중단**될 수 있습니다(보통 몇 초 미만)
- ⚠️⚠️ **보존 기간은 0~90일이고 기본값이 0일**입니다 — **0은 자동 일일 백업을 끈다는 뜻**이고, 공식이 중요 기능이 있는 파일 시스템에는 자동 일일 백업을 **강하게 권합니다**
- ⚠️ **자동 일일 백업은 파일 시스템을 삭제하면 함께 삭제**됩니다
- 창과 보존 기간은 **`UpdateFileSystem` API** 또는 `update-file-system` CLI 로 바꿉니다

### 4) 안전한 복제와 백업 (기술 5.2.4) {#backup}

#### 4-1. Amazon Data Lifecycle Manager

DLM은 **백업 생성과 보존 요건을 정책으로** 정의합니다. 정책은 대개 **정책 유형**(스냅샷 또는 EBS 기반 AMI) · **대상 리소스**(인스턴스 또는 EBS 볼륨) · **생성 빈도** · **보존 임계값** · **추가 작업**(교차 리전 복사·아카이빙·리소스 태그 지정)을 지정합니다.

| 갈래 | 성질 |
|---|---|
| **기본 정책** | **리전의 모든 볼륨·인스턴스 중 최근 백업이 없는 것**을 백업합니다. 제외 파라미터로 뺄 수 있고, ⚠️ **계정·리전별로 리소스 유형당 하나만** 둘 수 있습니다 |
| **사용자 지정 정책** | **태그로 지정한** 리소스를 대상으로 하고 **빠른 스냅샷 복원 · 스냅샷 아카이빙 · 교차 계정 복사 · 사전·사후 스크립트** 같은 고급 기능을 지원합니다. ⚠️ **한 정책에 스케줄 최대 4개**이고 스케줄마다 빈도·보존·고급 기능을 따로 둡니다 |

사용자 지정 정책의 종류는 **EBS 스냅샷 정책 · EBS 기반 AMI 정책 · 교차 계정 복사 이벤트 정책**입니다.

⚠️ **보존은 개수 기반 또는 기간 기반**입니다. 그리고 ⚠️⚠️ **잠긴 스냅샷은 보존 정책과 무관하게 DLM이 삭제할 수 없습니다**(§2-2) — "DLM이 스냅샷을 지우지 않는다"의 원인 중 하나입니다.

#### 4-2. AWS Backup 논리적 에어 갭 저장소 — 랜섬웨어 보호의 축

공식 기술 5.2.4가 **"랜섬웨어 보호"**를 명시하고, 그 자리의 서비스 기능이 **논리적 에어 갭 저장소**입니다. 표준 백업 저장소를 넘어서는 보안을 주는 **2차 저장소 유형**입니다.

- **각 저장소가 암호화됩니다** — **AWS 소유 키(기본)** 또는 선택적으로 **고객 관리형 KMS 키**로. 어느 쪽인지는 **API와 콘솔에서 보여** 준수 보고에 쓸 수 있습니다
- ⚠️⚠️ **각 저장소에 AWS Backup Vault Lock의 준수 모드가 장착**돼 있습니다 — 불변 백업입니다
- ⚠️⚠️ **백업이 AWS Backup 서비스 소유 계정에 저장됩니다.** 그 결과 **CloudTrail 로그의 속성 변경 항목에서 백업이 조직 밖으로 공유된 것처럼 보입니다** — 알고 있어야 오탐으로 조사하지 않습니다
- **공유 경로가 둘이고 용도가 다릅니다**

| 수단 | 언제 |
|---|---|
| **AWS RAM 공유** | **미리 계획된** 공유. 포렌식 계정·복구 계정에 저장소를 공유해 **복사 단계 없이 직접 복원**합니다(다른 조직의 계정도 가능). 복원 테스트·사전 준비에 씁니다 |
| **다자 승인(MPA)** | **저장소 소유 계정에 접근할 수 없을 때**. 깨끗한 계정에서 복구 요청을 올리면 승인 팀이 승인 포털에서 검토·승인하고, MPA가 저장소를 요청 계정에 공유합니다 |

- ⚠️ **소유 계정이 (악의적으로든 아니든) 닫혀도** MPA 로 저장소의 백업에 접근(복원·복사)할 수 있습니다 — 단 **폐쇄 후 기간(post-closure period)이 끝나면** 더는 접근할 수 없습니다
- 공식 권고는 **같은 또는 별도 계정의 논리적 에어 갭 저장소에 교차 리전 복사**를 두는 것이고, 비용을 줄이려 **사본 하나만** 두려면 **MPA 온보딩 후 「Primary backups to 논리적 에어 갭 저장소」**를 씁니다

#### 4-3. AWS DataSync — 그리고 닫힌 기능 하나

DataSync 는 **AWS 스토리지 서비스로·에서·사이에** 파일·객체 데이터를 옮기는 전송 서비스입니다.

- 온프레미스 쪽은 **NFS · SMB · HDFS · 객체 스토리지**, AWS 쪽은 **S3 · EFS · FSx for Windows File Server · FSx for Lustre · FSx for OpenZFS · FSx for NetApp ONTAP**, 그리고 **다른 클라우드의 객체 스토리지**도 대상입니다
- ⚠️ **보안 관점의 요점 둘** — **암호화와 데이터 무결성 검증이 내장**돼 종단 간 보안을 제공하고, **VPC 엔드포인트를 지원**해 **퍼블릭 인터넷을 거치지 않고** 전송할 수 있습니다. AWS 스토리지 접근은 **IAM 역할** 같은 내장 보안 수단으로 합니다
- 용도는 **마이그레이션 · 콜드 데이터 아카이브**(S3 Glacier Flexible Retrieval·Deep Archive 로 직접) **· 복제 · 클라우드 내 처리용 전송**입니다

⚠️⚠️ **`AWS DataSync Discovery` 기능은 지원 종료됐습니다**(공식 `AWS Lifecycle Changes` 기준 2025-05-20). 온프레미스 스토리지의 성능·용량을 분석해 마이그레이션 대상과 AWS 스토리지 서비스를 추천하던 기능이고, **DataSync 자체는 정상**입니다. **기능 단위로 갈라** 기억합니다 — "온프레미스 스토리지를 분석해 추천을 받는다"는 선택지는 지금 성립하지 않습니다.

## ✍️ 시험 포인트

- **"S3 기본 암호화를 켜라"는 이미 기본이다** — 2023-01-05부터 모든 새 객체가 SSE-S3로 자동 암호화됩니다
- **"새 버킷에서 SSE-C가 거부된다"는 2026년 4월 기본 변경이다** — `PutBucketEncryption`으로 켭니다
- **"버킷 기본값을 SSE-C로"는 불가능하다** — 기본 구성은 SSE-KMS·DSSE-KMS뿐입니다
- **"기본 암호화를 KMS로 바꿨는데 기존 객체가 그대로"는 정상이다** — Batch Operations + Inventory 로 Copy 합니다
- **"두 겹 암호화가 규제 요건"은 DSSE-KMS다**
- **"루트도 못 지우게 하라"는 Object Lock 준수 모드다** — 거버넌스 모드는 IAM 권한으로 풀립니다
- **"만료일 없이 무기한 보존"은 법적 보존이다**
- **"보존 만료일을 사건 종료 시점부터 센다"는 가변 보존(이벤트 보존)이다**
- **"Object Lock을 켰는데 안 된다"는 버전 관리가 꺼진 것이다**
- **"허용 보존 기간의 상·하한을 강제하라"는 `s3:object-lock-remaining-retention-days`다**
- **"IAM 권한과 무관하게 스냅샷 삭제 금지"는 EBS 스냅샷 잠금이고 추가 비용이 없다**
- **"DLM이 스냅샷을 안 지운다"의 후보에 스냅샷 잠금이 있다**
- **"Glacier 저장소 잠금으로 새 WORM 아카이브를 설계"는 지금 성립하지 않는다** — 신규 고객에게 닫힌 서비스이고, 새 설계는 S3 Object Lock입니다
- **"저장소 잠금을 개시만 하고 뒀다"는 24시간 뒤 정책이 삭제된다**
- **"로그가 변조됐는지 증명하라"는 CloudTrail 로그 파일 무결성 검증이다**(SHA-256 + SHA-256 with RSA, 다이제스트 사슬)
- **"다이제스트 파일에 별도 접근 통제"는 같은 버킷의 다른 폴더이기 때문이다**
- **"서명되지 않은 Lambda 배포를 차단하라"는 코드 서명 구성의 적용(Enforce) 모드다**
- **"컨테이너 이미지 서명"은 Signer + Notation CLI다**
- **"버킷 정책으로 모든 삭제를 막았으니 안전하다"는 틀렸다** — 수명 주기는 그대로 동작합니다
- **"EFS에서 바로 Archive로"는 안 된다** — IA 를 먼저 거칩니다
- **"S3에 연결된 Lustre 파일 시스템의 자동 백업"은 없다** — 데이터 리포지토리 연결을 씁니다
- **"Lustre 백업이 안 잡힌다"는 보존 기간 기본값이 0일이기 때문이다**
- **"랜섬웨어로 백업 계정까지 잃었다"는 논리적 에어 갭 저장소 + 다자 승인이다**
- **"온프레미스 스토리지를 분석해 추천받자"는 지금 성립하지 않는다** — DataSync Discovery 는 지원 종료입니다

## ⚠️ 흔한 함정 {#pitfalls}

- ❌ "한 객체에 SSE-KMS와 SSE-C를 함께 적용한다" → **동시에 적용할 수 없습니다**
- ❌ "서버 측 암호화 선택지는 정확히 네 가지다" → 본문은 넷이라 적지만 **같은 페이지의 소제목은 다섯**입니다. 수를 외우지 않습니다
- ❌ "암호화된 객체는 미리 서명된 URL로 못 받는다" → **똑같이 동작**합니다
- ❌ "Object Lock은 버전 관리 없이도 된다" → **버전 관리가 켜진 버킷에서만**입니다
- ❌ "준수 모드도 루트 사용자는 풀 수 있다" → **루트도 못 합니다**
- ❌ "법적 보존에 만료일을 지정한다" → **만료일이 없습니다**
- ❌ "Object Lock을 걸면 버킷의 모든 객체가 보호된다" → 보존·법적 보존은 **요청에 지정된 버전**만 보호합니다
- ❌ "스냅샷 잠금은 유료 기능이다" → **잠금·해제에 추가 비용이 없습니다**
- ❌ "잠긴 스냅샷은 복원에도 쓸 수 없다" → **평소처럼 사용**할 수 있습니다
- ❌ "Glacier 금고와 S3 Glacier 스토리지 클래스는 같은 것이다" → **다릅니다.** 금고 기반 독립 서비스가 신규 고객에게 닫혔고 스토리지 클래스는 정상입니다
- ❌ "저장소 잠금 정책을 나중에 수정한다" → **완료 후에는 변경·삭제 불가**입니다
- ❌ "아카이브를 올린 뒤 저장소 잠금을 건다" → 공식 권고는 **잠금을 완료한 뒤 업로드**입니다
- ❌ "다이제스트 파일은 로그와 다른 버킷에 간다" → **같은 버킷의 다른 폴더**입니다
- ❌ "코드 서명 구성을 붙이면 무조건 차단된다" → **경고 모드**도 있습니다
- ❌ "Signer 는 Lambda 전용이다" → **IoT·컨테이너 이미지**도 지원합니다
- ❌ "수명 주기 만료를 버킷 정책으로 막는다" → **막을 수 없습니다**
- ❌ "수명 주기 규칙은 새 객체에만 적용된다" → **기존 객체에도** 적용됩니다
- ❌ "만료가 늦어지면 그 기간도 과금된다" → **대상이 되는 즉시** 과금이 바뀝니다(Intelligent-Tiering 전환은 예외)
- ❌ "EFS에서 접근하면 자동으로 Standard 로 돌아온다" → **기본은 돌아오지 않습니다**
- ❌ "Archive 는 모든 EFS 파일 시스템에서 쓸 수 있다" → **Elastic 처리량 + General Purpose 성능 모드**만입니다
- ❌ "Lustre 자동 백업은 기본으로 켜져 있다" → **보존 기간 기본값이 0일(끔)**입니다
- ❌ "DLM 기본 정책을 리소스 유형마다 여러 개 둔다" → **하나만** 둘 수 있습니다
- ❌ "사용자 지정 정책에 스케줄을 많이 넣는다" → **최대 4개**입니다
- ❌ "논리적 에어 갭 저장소가 조직 밖으로 공유된 것은 사고다" → **서비스 소유 계정에 저장되기 때문**이고 정상입니다

## 🧪 자가 점검

**Q1.** 준수팀이 "금융 기록을 7년간 WORM 으로 보관하고, 운영자 실수나 자격 증명 유출로도 지워지지 않게 하라"고 요구합니다. 새로 설계하는 중이고 아카이브 비용을 낮추고 싶습니다. (→ 2-1·2-3 무결성)

<details><summary>정답 보기</summary>

**S3 Object Lock 준수 모드 + 수명 주기 전환으로 설계합니다. Glacier 저장소 잠금은 새 설계의 축이 아닙니다.**

- **준수 모드**는 보호된 객체 버전을 **AWS 계정의 루트 사용자를 포함한 어떤 사용자도** 덮어쓰거나 삭제할 수 없게 합니다. 거버넌스 모드는 **특정 IAM 권한**으로 풀리므로 "자격 증명 유출로도 지워지지 않게"라는 요구를 만족하지 못합니다
- ⚠️ **버전 관리가 켜진 버킷에서만** 동작하고, 허용 보존 기간의 상·하한은 버킷 정책의 **`s3:object-lock-remaining-retention-days`** 조건 키로 강제합니다. 버킷 **기본 보존 기간**도 둘 수 있습니다
- 비용은 **수명 주기 전환 액션**으로 낮춥니다(예: 일정 기간 후 S3 Glacier Flexible Retrieval). ⚠️ 단 **버킷 정책으로는 수명 주기 삭제를 막을 수 없으므로** 보존 자체는 Object Lock 이 담당해야 합니다
- ⚠️⚠️ **`S3 Glacier 저장소 잠금`은 금고 기반의 독립 Glacier 서비스 기능이고 그 서비스는 신규 고객을 받지 않습니다.** 개념(두 단계 잠금·24시간 검증 창)은 시험 범위이지만 **새 설계의 축으로 삼지 않습니다**

⚠️ 규제 근거가 필요하면 **Cohasset Associates 평가**(SEC 17a-4·CFTC·FINRA)를 인용합니다 — Object Lock 과 EBS 스냅샷 잠금 모두 그 평가를 받았습니다.
</details>

**Q2.** 보안팀이 버킷 정책에 "모든 보안 주체의 모든 작업 거부"를 넣고 "이제 이 버킷의 데이터는 삭제될 수 없다"고 보고했습니다. 같은 버킷에는 30일 만료 수명 주기 규칙이 있습니다. (→ 3-1 수명 주기)

<details><summary>정답 보기</summary>

**거짓입니다. 버킷 정책으로 수명 주기의 삭제·전환을 막을 수 없습니다.**

- 공식이 Important 로 적습니다 — **"You can't use a bucket policy to prevent deletions or transitions by an S3 Lifecycle rule. For example, even if your bucket policy denies all actions for all principals, your S3 Lifecycle configuration still functions as normal."**
- 게다가 ⚠️ **수명 주기 구성은 기존 객체에도 적용**되므로, 30일 만료 규칙을 추가한 시점에 **이미 30일이 넘은 객체가 제거 대기열에** 들어갑니다
- 보존이 요건이면 수단은 **Object Lock**입니다(준수 모드면 루트도 못 지웁니다). 수명 주기는 **비용 최적화 도구**이고 **보존 통제가 아닙니다**

⚠️ 덤으로 과금 사실 하나 — **객체가 수명 주기 액션 대상이 되는 즉시 과금이 바뀝니다**(실제 만료가 지연돼도 그 이후 스토리지 비용을 내지 않습니다). 예외는 **S3 Intelligent-Tiering 전환**으로, 그쪽은 실제 전환 후에 바뀝니다.
</details>

**Q3.** 규제 대응으로 버킷 기본 암호화를 SSE-KMS 로 바꿨습니다. 며칠 뒤 감사에서 "기존 객체 상당수가 여전히 SSE-S3"라는 지적이 나왔습니다. 설정이 잘못된 것입니까? (→ 1-1·1-3 암호화)

<details><summary>정답 보기</summary>

**설정은 정상입니다. 기본 암호화 구성을 바꿔도 기존 객체의 암호화 유형은 바뀌지 않습니다.**

- 공식이 명시합니다 — 기본 암호화 구성을 SSE-KMS 로 바꿔도 **버킷에 이미 있는 객체의 암호화 유형은 변경되지 않습니다**
- 소급 적용은 **S3 Batch Operations**로 합니다 — **S3 Inventory** 로 객체 목록을 만들고 **Copy objects** 작업으로 같은 버킷에 다시 써서 SSE-KMS 객체로 만듭니다. 한 작업이 **수십억 객체**를 처리할 수 있습니다
- ⚠️ 설계 단계에서 알아 둘 제약 — **한 객체에 여러 유형의 서버 측 암호화를 동시에 적용할 수 없고**, **기본 암호화 구성으로 설정할 수 있는 것은 SSE-KMS·DSSE-KMS**뿐입니다(SSE-C 는 `PUT` 요청에서만 지정합니다)

⚠️ 같은 「설정을 바꿔도 기존 데이터는 그대로」 모양이 이 도메인에 **셋** 있습니다 — 여기, **CloudWatch Logs 데이터 보호 정책**(이미 수집된 로그), **KMS 키 회전**(데이터를 재암호화하지 않습니다). 둘은 `scs-t5-3`에서 다룹니다.
</details>

**Q4.** 랜섬웨어 대응 설계를 요청받았습니다. 요구는 "백업이 불변이어야 하고, **백업을 가진 계정 자체가 침해돼도** 복구할 수 있어야 한다"입니다. (→ 4-2 논리적 에어 갭 저장소)

<details><summary>정답 보기</summary>

**AWS Backup 논리적 에어 갭 저장소를 쓰고, 복구 경로로 다자 승인(MPA)을 온보딩합니다.**

- 논리적 에어 갭 저장소는 **표준 백업 저장소를 넘어서는 보안**을 주는 2차 저장소 유형이고, ⚠️ **각 저장소에 AWS Backup Vault Lock 의 준수 모드가 장착**돼 불변입니다. 암호화는 **AWS 소유 키(기본)** 또는 **고객 관리형 KMS 키**로 하고 **어느 쪽인지 API·콘솔에서 보입니다**
- ⚠️⚠️ **백업이 AWS Backup 서비스 소유 계정에 저장**되므로 저장소 소유 계정이 침해돼도 백업 자체가 그 계정 안에 있지 않습니다
- 공유 경로가 **둘이고 용도가 다릅니다** — **AWS RAM**은 **미리 계획된** 공유(포렌식·복구 계정에 사전 공유해 복사 단계 없이 직접 복원, 복원 테스트에도 씁니다), **MPA**는 **저장소 소유 계정에 접근할 수 없을 때** 깨끗한 계정에서 복구 요청을 올리고 승인 팀이 승인하면 MPA 가 저장소를 공유합니다. 공식은 **둘 다 구성**하라고 적습니다
- ⚠️ **소유 계정이 닫혀도** MPA 로 접근할 수 있지만 **폐쇄 후 기간이 끝나면** 더는 접근할 수 없습니다

⚠️ 운영 주의 — 이 저장소의 백업은 **CloudTrail 로그의 속성 변경 항목에서 조직 밖으로 공유된 것처럼 보입니다.** 설계상 그렇다는 것을 모르면 오탐으로 조사하게 됩니다.
</details>

**Q5.** FSx for Lustre 파일 시스템 둘을 운영합니다. A는 S3 버킷에 연결된 Persistent 파일 시스템, B는 독립 Persistent 파일 시스템입니다. 둘 다 자동 일일 백업이 보이지 않습니다. (→ 3-3 Lustre 백업)

<details><summary>정답 보기</summary>

**A는 구조적으로 자동 백업 대상이 아니고, B는 보존 기간이 기본값 0일이기 때문입니다.**

- 공식이 조건을 적습니다 — 자동 일일 백업은 **Persistent 스토리지**이고 **독립 파일 시스템**(S3 버킷에 연결되지 않은 것)에서만 예약할 수 있습니다. ⚠️ **S3 에 연결된 파일 시스템은 자동 백업을 받지 않습니다** → A 의 대안은 **데이터 리포지토리 연결**로 S3 와 동기 상태를 유지하는 것입니다
- B 는 ⚠️ **보존 기간이 0~90일이고 기본값이 0일**이며 **0은 자동 일일 백업을 끈다는 뜻**입니다. `UpdateFileSystem` API 또는 `update-file-system` CLI 로 백업 창과 보존 기간을 설정합니다
- 알아 둘 성질 — 백업은 **증분**이고, 백업 창 시작 시 **스토리지 I/O 가 잠시(보통 몇 초 미만) 중단**될 수 있으며, ⚠️ **자동 일일 백업은 파일 시스템을 삭제하면 함께 삭제**됩니다

⚠️ 공식이 중요 기능이 있는 파일 시스템에는 자동 일일 백업을 **강하게 권합니다** — 0일 기본값을 그대로 두는 것이 사실상의 기본 위험입니다.
</details>

**Q6.** 감사에서 "CloudTrail 로그가 전달 후 변조되지 않았음을 증명하고, 그 증명 자료에는 더 엄격한 접근 통제를 걸라"는 요구가 나왔습니다. 그리고 "마이그레이션 전에 온프레미스 스토리지를 분석해 추천을 받자"는 제안도 함께 올라왔습니다. (→ 2-4·4-3)

<details><summary>정답 보기</summary>

**로그 파일 무결성 검증을 켜고 다이제스트 폴더에 별도 정책을 걸고, 두 번째 제안은 성립하지 않습니다.**

- **로그 파일 무결성 검증**은 **SHA-256 해싱**과 **SHA-256 with RSA 디지털 서명**으로 만들어져 공식이 "변조·삭제·위조를 탐지 없이 하는 것이 계산적으로 불가능하다"고 적습니다
- **다이제스트 파일이 매시간** 전달되고 그 안에 전달된 로그 파일의 정보와 해시, 그리고 ⚠️ **이전 다이제스트 파일의 디지털 서명**(과 현재 다이제스트의 서명)이 들어가 **사슬**을 이룹니다 — 중간을 지우면 사슬이 끊깁니다
- ⚠️ 다이제스트는 **로그와 같은 버킷의 다른 폴더**에 가므로 **그 접두사에 더 세분화된 접근 통제 정책**을 걸 수 있습니다. 검증은 **AWS CLI** 로 하거나 직접 도구를 만들 수 있고, 전 리전·여러 계정의 다이제스트를 한 버킷으로 모을 수 있습니다
- ⚠️⚠️ **두 번째 제안은 지금 성립하지 않습니다** — 그 기능인 **`AWS DataSync Discovery` 는 지원 종료**됐습니다(2025-05-20). **DataSync 자체는 정상**이므로 전송은 그대로 쓰고, 분석·추천은 다른 방법을 찾아야 합니다

⚠️ DataSync 의 보안 관점 요점 둘은 함께 기억합니다 — **암호화와 데이터 무결성 검증이 내장**이고, **VPC 엔드포인트를 지원**해 퍼블릭 인터넷을 거치지 않고 전송할 수 있습니다.
</details>
