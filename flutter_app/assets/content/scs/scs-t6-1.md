# 계정의 중앙 배포와 관리 (조직·Control Tower·조직 정책·위임 관리자·루트 자격 증명)

> **커버하는 공식 Task** — SCS-C03 · 도메인 6 「보안 기반 및 거버넌스」(14%) · **작업 6.1 AWS 계정을 중앙에서 배포하고 관리하기 위한 전략 개발** (`scs-t6-1`)
> 이 문서는 위 한 작업에 1:1로 매핑되고 공식 기술 5개(6.1.1~6.1.5)를 모두 덮습니다.

> ⚠️ 이 작업의 문항은 **"그 통제가 실제로 어디까지 닿는가"**로 환원됩니다. 조직 정책은 세 가지가 서로 다른 범위를 갖고(§3-2), Control Tower의 제어는 **동작마다 구현 수단과 적용 범위가 다르며**(§2-2), 사전 제어는 **CloudFormation을 거치지 않는 요청을 막지 못합니다**(§2-4).

> 그리고 이 작업에서 가장 자주 틀리는 자리는 **관리 계정의 특수성**입니다 — **SCP와 RCP는 관리 계정의 주체를 제한하지 않지만 선언적 정책은 관리 계정에도 적용됩니다**(§3-2). 그 비대칭이 "왜 보안 서비스를 위임 관리자 계정으로 옮기는가"(§4)의 이유이기도 합니다.

## ✅ 학습 목표 체크리스트

- [ ] 조직 정책의 **범주 둘**(권한 부여 / 선언적)을 가른다
- [ ] 정책 유형별 **관리 계정 영향·서비스 연결 역할·유효 정책 보기**의 비대칭을 안다
- [ ] Control Tower 제어의 **동작 3종과 구현 수단**을 짝지운다
- [ ] **사전 제어가 막지 못하는 경로**를 설명한다
- [ ] **OU를 옮길 때 이전 제어가 남는** 함정을 안다
- [ ] 드리프트 감지의 **알림 경로와 중복 제거**를 안다
- [ ] **위임된 관리자**를 쓰는 이유와 전제를 말한다
- [ ] 루트 액세스 중앙 집중화의 **기능 둘**과 특권 세션의 한계를 안다

## 🎯 왜 중요한가

멀티 계정 거버넌스 문항은 "무엇을 쓰면 되는가"를 묻지 않습니다. 보기 네 개가 모두 실제로 존재하는 서비스이고, **그중 셋은 요건의 일부만 덮습니다.** 가르는 축은 늘 **범위**입니다 — 관리 계정에도 적용되는가, 서비스 연결 역할까지 통제하는가, CloudFormation 밖의 요청도 막는가, 리전 전부에서 동작하는가.

특히 "비준수 리소스가 아예 생기지 않게 하라"는 요건에서 **사전 제어를 고르면 함정**일 수 있습니다. 사전 제어는 `preCreate`·`preUpdate` 후크로 구현돼 **콘솔·API·SDK·다른 IaC 도구로 직접 만드는 요청에는 영향을 주지 않을 수 있습니다**(§2-4). 같은 요건에서 **예방 제어(SCP·RCP·선언적 정책)**는 API 수준이나 제어 플레인에서 막으므로 경로를 가리지 않습니다. 이 차이를 모르면 "사전"이라는 말에 끌려 틀립니다.

## ⚡ 시험 직전 요약

- ⚠️⚠️ **SCP·RCP는 관리 계정에 적용되지 않고 선언적 정책은 적용됩니다.** 그리고 **선언적 정책만 서비스 연결 역할을 통제**하고 **유효 정책 보기를 지원**합니다
- 조직 정책은 **권한 부여 정책(SCP·RCP)**과 **선언적 정책**의 두 범주입니다. **태그 정책·백업 정책·AI 서비스 옵트아웃 정책은 선언적 범주**이고 **권한을 부여·거부하지 않습니다**
- ⚠️ **선언적 정책은 서비스의 제어 플레인에서 시행되고 API 작업을 쓰지 않습니다.** 분리하면 속성이 **이전 상태로 롤백**됩니다
- 첨부 한도: **SCP 10개·10,240자 / RCP 5개·5,120자 / 선언적 10개·10,000자 / AI 서비스 옵트아웃 5개·2,500자**
- ⚠️⚠️ **제어 동작 3종의 구현이 다릅니다** — 예방=**SCP·RCP·선언적 정책**, 탐지=**Config 규칙**, 사전=**CloudFormation 후크**. 예방은 **모든 리전**, 탐지는 **Control Tower 지원 리전만**
- ⚠️⚠️ **사전 제어는 `preCreate`·`preUpdate` 후크라 콘솔·API·SDK·다른 IaC 경로를 막지 못할 수 있습니다.** 보안 문자열·보안 암호도 해결 전이라 평가하지 못합니다
- ⚠️ **랜딩 존 버전 4.0부터 필수 제어가 기본 적용되지 않습니다**
- ⚠️⚠️ **OU를 옮기면 이전 OU의 제어가 제거되지 않습니다** — 후크 기반 제어만 교체되고 **SCP·Config 규칙 제어는 항상 수동 제거**입니다
- ⚠️ **SCP는 관리 계정의 사용자·역할을 제한하지 않습니다** — 그래서 보안 서비스를 **위임된 관리자** 계정으로 옮깁니다. 전제는 **신뢰 액세스 활성화**입니다
- ⚠️⚠️ **루트 세션은 최대 15분**이고 `TaskPolicyArn`이 **필수**이며 **다섯 관리형 정책 중 하나**여야 합니다. 중앙 집중화는 **기능이 둘**이고 자격 증명 관리만 켜면 **멤버가 복구할 수 없습니다**

## 🔤 먼저 알아야 할 용어

| 용어 | 뜻 |
|---|---|
| **권한 부여 정책** | 주체(SCP) 또는 리소스(RCP)의 **최대 사용 가능 권한**을 API 수준에서 제한하는 정책 범주 |
| **선언적 정책** | 서비스의 **원하는 기준 구성**을 제어 플레인에서 시행하는 정책 범주. 서비스가 새 기능·API를 더해도 유지됩니다 |
| **유효 정책** | 조직 루트·OU에서 상속된 것과 계정에 직접 첨부된 것을 합친 **최종 규칙 집합** |
| **랜딩 존** | 보안·준수 모범 사례에 기반한 **잘 설계된 멀티 계정 환경** 전체를 담는 컨테이너 |
| **Account Factory** | 사전 승인된 구성으로 계정 프로비저닝을 표준화하는 **구성 가능한 계정 템플릿**. Service Catalog의 프로비저닝된 제품 위에 올라갑니다 |
| **제어(가드레일)** | 환경 전체에 지속적인 거버넌스를 주는 **평문으로 표현된 상위 규칙**. OU 단위로 적용됩니다 |
| **드리프트** | 모범 사례에서 **벗어난 상태**. 랜딩 존·OU·계정·리소스의 준수 상태가 바뀐 것입니다 |
| **위임된 관리자** | 특정 서비스에서 **조직 전 계정을 관리할 수 있도록 등록된 멤버 계정** |
| **특권 세션** | 멤버 계정의 루트 작업을 **작업 범위로 한정해** 수행하는 단기 세션(`sts:AssumeRoot`) |

## 📖 핵심 개념

### 1) 조직을 배포하고 구성한다 (기술 6.1.1) {#organizations}

#### 1-1. 무엇을 중앙에서 얻는가

AWS Organizations는 계정을 하나의 조직으로 묶어 **계정 생성·그룹화·정책 적용·서비스 활성화**를 중앙에서 합니다. 보안 관점에서 중요한 것은 네 가지입니다.

| 기능 | 보안상 의미 |
|---|---|
| **계정 관리** | 계정은 **권한·보안·비용·워크로드의 자연스러운 경계**입니다. 멀티 계정이 권장 모범 사례입니다 |
| **조직 정의** | OU로 묶고 **태그 정책**으로 분류·추적하며 속성 기반 액세스 제어의 바탕을 만듭니다 |
| **중앙 감사** | **CloudTrail을 계정 전체에 활성화**하면 그 로그는 **멤버 계정이 끄거나 수정할 수 없습니다** |
| **리소스 공유** | RAM으로 VPC 서브넷 같은 리소스를 한 번 만들어 공유합니다(작업 6.2) |

> 🧠 **원리:** 조직의 핵심 가치는 "한 번 정의해 전체에 적용"입니다. 그래서 시험은 **"그 한 번의 정의가 어디까지 닿는가"**를 묻습니다. 아래 §3-2의 비대칭 표가 이 작업의 중심입니다.

#### 1-2. 관리 계정은 특수하다

⚠️⚠️ **SCP는 관리 계정의 사용자·역할을 제한하지 않습니다.** 공식이 위임 관리자 문서에서 그 이유로 이렇게 적습니다 — "security features like Organizations service control policies (SCPs) do not restrict users or roles in the management account."

그래서 공식 권고는 **관리 계정을 그 계정만 할 수 있는 작업에만 쓰고 리소스는 다른 멤버 계정에 두는 것**입니다. 이것이 §4의 위임된 관리자가 존재하는 이유입니다.

### 2) Control Tower를 구현·관리하고 제어를 배포한다 (기술 6.1.2) {#control-tower}

#### 2-1. Control Tower는 오케스트레이션 계층이다

Control Tower는 새 서비스를 발명하지 않습니다. **AWS Organizations · AWS Service Catalog · AWS IAM Identity Center**를 포함한 여러 서비스의 기능을 **오케스트레이션**해 한 시간 안에 랜딩 존을 만듭니다.

- **랜딩 존** — OU·계정·사용자·리소스를 담는 조직 전체 컨테이너
- **제어** — 예방·탐지·사전 세 가지 동작, 필수·적극 권장·선택 세 가지 가이던스
- **Account Factory** — **Service Catalog의 프로비저닝된 제품 위에 만들어진** 추상화. 계정을 만들고 등록하며 제어·정책 적용을 자동화합니다
- **대시보드** — 프로비저닝된 계정, 적용된 제어, 비준수 리소스를 계정·OU별로 봅니다

> 🧠 **원리:** Account Factory가 Service Catalog 위에 있다는 사실이 작업 6.1과 6.2를 잇습니다. "계정 프로비저닝을 표준화하라"는 요건은 결국 **승인된 템플릿을 카탈로그로 배포**하는 것과 같은 기제입니다.

⚠️ 관리 계정 예외가 있습니다 — **관리 계정의 루트 사용자와 관리자는 제어가 거부할 작업을 수행할 수 있습니다.** 이것은 **의도된 것**이고 관리 계정이 사용 불가 상태에 빠지는 것을 막습니다. 다만 그 작업도 **로그 아카이브 계정의 로그에 계속 기록**됩니다.

#### 2-2. 제어의 동작 3종 — 구현 수단과 적용 범위가 다르다

| 동작 | 무엇을 하는가 | 구현 수단 | 상태값 | 리전 범위 |
|---|---|---|---|---|
| **예방(preventive)** | 정책 위반으로 이어지는 **작업을 금지** | **SCP · RCP · 선언적 정책** | `enforced` / `not enabled` | **모든 AWS 리전** |
| **탐지(detective)** | 계정 안 리소스의 **비준수를 감지**하고 대시보드로 알림 | **AWS Config 규칙** | `clear` / `in violation` / `not enabled` | **Control Tower 지원 리전만** |
| **사전(proactive)** | 프로비저닝 **전에** 리소스를 스캔하고 비준수면 프로비저닝하지 않음 | **CloudFormation 후크** | `PASS` / `FAIL` / `SKIP` | 후크 지원 리전만(§2-4) |

⚠️⚠️ **예방 제어의 구현 수단이 SCP 하나가 아닙니다.** 공식이 적는 수단은 **SCP·RCP·선언적 정책 셋**입니다. 그래서 Control Tower는 세 종류를 **매일 스캔**합니다(§2-5).

⚠️ 탐지 제어 중 **Security Hub CSPM과 통합된 것들**은 `Service-Managed Standard: AWS Control Tower` 표준이 소유하고 다른 Security Hub 제어와 똑같이 **Config 규칙으로 구현**됩니다. 제어 카탈로그에 있는 **AWS Config 통합 제어**는 Config가 소유합니다.

⚠️ 필수 제어 일부는 **여러 작업을 수행하는 단일 SCP**로 구현됩니다 — 그래서 제어 참조에서 **같은 SCP가 여러 필수 제어 아래 반복해 보입니다**.

#### 2-3. 가이던스 3종과 랜딩 존 4.0의 변화

| 가이던스 | 성격 |
|---|---|
| **필수(mandatory)** | 환경에서 활성화한 것에 따라 랜딩 존에 적용됩니다. Control Tower가 배포한 리소스를 보호합니다 |
| **적극 권장(strongly recommended)** | 잘 설계된 멀티 계정 환경의 공통 모범 사례. **OU 수준**에 적용됩니다 |
| **선택(elective)** | 엔터프라이즈에서 흔히 제한하는 작업을 추적·차단합니다. **OU 수준**에 적용됩니다 |

⚠️⚠️ **랜딩 존 버전 4.0부터 필수 제어가 기본으로 적용되지 않습니다.** 공식이 그 한 줄을 제어 동작 페이지 끝에 적습니다. "필수니까 당연히 켜져 있다"는 전제가 **버전에 달린** 셈이므로 적용 상태를 직접 확인해야 합니다.

#### 2-4. 사전 제어의 한계 셋 — 가장 자주 틀리는 자리

사전 제어는 **선택 제어**이고 **CloudFormation 후크와 Control Tower가 관리하는 후크**로 구현됩니다. 범주는 **제어 목표 · 프레임워크 · 서비스 · 그룹** 네 가지로 나뉩니다.

⚠️⚠️ **한계 ① 경로** — 사전 제어는 `preCreate`와 `preUpdate` **후크 핸들러**로 구현됩니다. 공식이 그 결과를 이렇게 적습니다:

> 이 제어들은 **AWS 콘솔·AWS API·AWS SDK·다른 IaC 도구를 통해 서비스에 직접 하는 요청에는 영향을 주지 않을 수 있습니다.**

즉 **"사전 제어를 켜면 비준수 리소스가 아예 생기지 않는다"는 거짓입니다.** 경로를 가리지 않고 막아야 하면 **예방 제어**(SCP·RCP·선언적 정책)가 답입니다.

⚠️ **한계 ② 보안 암호** — 사전 제어는 후크의 `targetNames` 속성으로 넘어온 문자열을 평가합니다. **보안 문자열과 보안 암호는 후크로 가기 전에 해결되지 않아** 사전 제어가 그 값을 평가할 수 없습니다.

⚠️ **한계 ③ 리전** — **CloudFormation 후크가 Control Tower 가용 리전 전부에서 지원되지는 않습니다.** 사전 제어를 배포해도 관리하는 모든 리전에서 동작하지 않을 수 있습니다.

> 🧠 **원리:** "사전"은 **시점**(배포 전)을 말하고 **경로의 완전성**을 말하지 않습니다. 완전성은 평가 지점이 어디냐에 달립니다 — 후크는 CloudFormation 안에, SCP·RCP는 API 앞에, 선언적 정책은 서비스 제어 플레인 안에 있습니다.

⚠️ 테스트 규율도 공식이 적습니다 — 예제 템플릿은 **한 제어만 테스트하도록** 만들어졌으므로 다른 제어는 `PASS`가 아닐 수 있고, 이는 **예상된 동작**입니다. 사전 제어는 **개별로 테스트한 뒤** 활성화합니다.

#### 2-5. 드리프트 — 감지 경로와 OU 이동 함정

Control Tower는 드리프트를 **자동으로 감지**합니다. 감지에는 `AWSControlTowerAdmin` 역할이 관리 계정에 지속 접근해 **Organizations에 읽기 전용 API 호출**을 할 수 있어야 하고, 그 호출은 **CloudTrail 이벤트로 보입니다.**

| 성질 | 내용 |
|---|---|
| **알림 경로** | 멤버 계정 드리프트는 **감사(audit) 계정에 집계된 SNS 알림**으로 드러납니다. 각 멤버 계정은 로컬 SNS 토픽과 Lambda 함수로 알립니다 |
| ⚠️ **자동 등록** | **설정에서 계정 자동 등록을 켜면 이 SNS 알림을 쓸 수 없습니다** |
| **구독 권장** | 멤버 계정 관리자는 `aws-controltower-AggregateSecurityNotifications` 같은 토픽을 구독하는 것이 모범 사례입니다 |
| **중복 제거** | 같은 유형의 드리프트가 같은 리소스에 반복되면 **첫 번째만** 알립니다. 해소된 뒤 재발하면 다시 알립니다 |
| **일일 스캔** | 관리형 **SCP·RCP·선언적 정책**을 매일 스캔합니다 |
| ⚠️ **TPS** | 스캔은 **관리 계정으로** Organizations를 호출하므로 **내 TPS 한도에 계산됩니다.** 내 스크립트가 같은 API를 같은 순간에 호출하면 스로틀될 수 있습니다 |

⚠️⚠️ **계정을 OU 사이에서 옮길 때의 함정이 이 작업에서 가장 날카롭습니다.** 공식이 이렇게 적습니다 — **이전 OU의 제어는 제거되지 않습니다.** 대상 OU에서 새 후크 기반 제어를 활성화하면 **옛 후크 기반 제어만** 제거되고 새 제어가 그것을 대체합니다. 그러나 **SCP와 AWS Config 규칙으로 구현된 제어는 계정이 OU를 바꿀 때 항상 수동으로 제거**해야 합니다.

### 3) 조직 정책으로 권한을 관리한다 (기술 6.1.3) {#org-policies}

#### 3-1. 범주는 둘이다

공식 가이드의 `기술 6.1.3`은 "SCP, RCP, AI 서비스 옵트아웃 정책, 선언적 정책"을 **한 줄에 나란히** 적습니다. 그런데 공식 문서는 정책을 **두 범주**로 나눕니다.

| 범주 | 무엇을 하는가 | 유형 |
|---|---|---|
| **권한 부여 정책** | 조직 전체에서 **보안을 중앙 관리**합니다 | **SCP**(주체의 최대 권한) · **RCP**(리소스의 최대 권한) |
| **선언적 정책** | 서비스와 그 기능을 **중앙에서 구성·관리**합니다 | EC2 · 백업 · **태그** · 채팅 애플리케이션 · **AI 서비스 옵트아웃** · Security Hub · Amazon Inspector · Amazon Bedrock · 업그레이드 롤아웃 · Amazon S3 · GuardDuty 등 |

⚠️ **그러므로 「SCP로 AI 서비스의 데이터 사용을 옵트아웃한다」는 거짓입니다.** 그것은 **전용 정책 유형**이고 권한을 부여·거부하지 않습니다.

⚠️ **선언적 정책 유형의 개수는 묻지 않습니다** — 공식 안에서 목록이 어긋납니다. 선언적 정책 전용 페이지의 주제 목록은 **AWS Shield Network Security Director 정책**을 포함하는데 정책 관리 페이지의 불릿 목록에는 없고, 같은 페이지의 요약 표에는 **Shield와 GuardDuty 행이 없습니다**. 유형은 계속 늘어나는 값입니다.

#### 3-2. 비대칭 표 — 이 작업의 중심

공식이 선언적 정책 페이지에 **권한 부여 정책과의 차이를 표로** 싣습니다.

| 축 | SCP | RCP | 선언적 정책 |
|---|---|---|---|
| **무엇을 통제하나** | 주체(IAM 사용자·역할)의 최대 권한 | 리소스의 최대 권한 | 서비스의 **기준 구성** |
| **어떻게** | **API 수준**에서 | **API 수준**에서 | **API 작업을 쓰지 않고** 원하는 구성을 시행 |
| ⚠️⚠️ **서비스 연결 역할 통제** | **아니오** | **아니오** | **예** |
| ⚠️⚠️ **관리 계정 영향** | **아니오** | **아니오** | **예** |
| ⚠️ **OU·계정의 유효 정책 보기** | 아니오 | 아니오 | **예** |
| **첨부 한도 / 최대 크기** | **10개 / 10,240자** | **5개 / 5,120자** | **10개 / 10,000자** |

⚠️ AI 서비스 옵트아웃 정책은 선언적 범주이지만 한도가 다릅니다 — **5개 / 2,500자**입니다. 채팅 애플리케이션 정책도 **5개**입니다.

> 🧠 **원리:** 세 줄의 비대칭이 모두 같은 뿌리에서 나옵니다. SCP·RCP는 **요청을 평가하는 정책**이라 관리 계정과 서비스 연결 역할처럼 "요청 평가에서 빼야 하는" 주체를 건드리지 못합니다. 선언적 정책은 **구성을 선언하는 정책**이라 요청 경로 밖에서 작동하므로 그 둘에도 미칩니다.

#### 3-3. 선언적 정책의 성질 셋

- **제어 플레인에서 시행됩니다.** 그래서 서비스가 **새 기능이나 API를 도입해도 기준 구성이 유지**됩니다("set once and forget"). 새 계정이 조직에 들어와도, 새 주체·리소스가 만들어져도 유지됩니다
- **상속과 유효 정책** — 조직 루트·OU·계정에 적용할 수 있고, 조직에 들어오는 계정은 자동으로 상속합니다. 상속분과 직접 첨부분을 합친 것이 **유효 정책**입니다
- ⚠️ **분리하면 롤백됩니다** — 선언적 정책을 떼면 **속성 상태가 정책을 붙이기 전 상태로 되돌아갑니다.** "정책을 떼도 구성은 남는다"가 아닙니다

⚠️ 투명성 장치도 있습니다 — **계정 상태 보고서**로 범위 내 계정의 지원 속성 현재 상태를 검토하고, **사용자 지정 오류 메시지**를 만들어 작업이 실패한 이유를 사용자에게 안내할 수 있습니다.

### 4) 보안 서비스를 한곳에서 관리한다 (기술 6.1.4) {#delegated-admin}

#### 4-1. 위임된 관리자 — 왜, 그리고 전제

Organizations와 통합되는 많은 AWS 서비스가 **멤버 계정 하나 이상을 그 서비스의 관리자로 등록**하게 합니다. 그 계정이 **위임된 관리자**이고, 조직의 모든 계정을 그 서비스에서 관리합니다.

**왜 쓰는가** — §1-2의 비대칭 때문입니다. SCP가 관리 계정의 주체를 제한하지 않으므로, 관리 계정에 리소스와 일상 운영을 두면 **조직의 가장 강한 통제가 적용되지 않는 곳에 가장 많은 작업이 쌓입니다.** 청구서에서 비용을 가려내기 어려운 것도 같은 이유입니다.

**등록 전 확인할 것 둘** —

1. **그 서비스가 위임된 관리자를 지원하는지** 확인합니다(Organizations와 함께 쓸 수 있는 서비스 표의 `Supports Delegated Administrator` 열)
2. **그 서비스의 신뢰 액세스를 활성화**합니다

⚠️ 위임된 관리자가 받는 것은 **그 서비스의 일부 관리 권한 + Organizations 읽기 전용 작업 권한**입니다. 조직 전체의 관리 권한이 아닙니다.

> 🧠 **원리:** 위임은 "관리 계정을 쓰지 않아도 되게" 만드는 장치입니다. 그래서 문항이 "관리 계정 사용을 최소화하면서 조직 전 계정의 X를 중앙 관리하라"고 하면 답은 거의 항상 **그 서비스의 위임된 관리자 등록**입니다.

#### 4-2. 이 자격증 범위에서 자주 나오는 위임 대상

| 서비스 | 중앙 관리하는 것 |
|---|---|
| **Security Hub CSPM** | 조직 전 계정의 결과 집계와 표준·제어 활성화(작업 6.3) |
| **AWS Config** | 다중 계정·다중 리전 애그리게이터(작업 6.3) |
| **CloudFormation StackSets** | 서비스 관리형 권한의 관리자 계정 역할(작업 6.2) |
| **IAM** | **루트 액세스 관리와 특권 작업**(§5) |
| **Firewall Manager** | 조직 전 보호 정책(작업 6.2) |

⚠️ Firewall Manager는 이름이 다릅니다 — **Firewall Manager 기본 관리자 계정**을 만드는 것이 전제 조건의 한 단계입니다(작업 6.2에서 다룹니다).

### 5) 루트 사용자 자격 증명을 관리한다 (기술 6.1.5) {#root-credentials}

#### 5-1. 중앙 집중화는 기능이 둘이다

루트 액세스 중앙 집중화를 켤 때 **활성화할 기능을 고릅니다.**

| 기능 | 무엇을 허용하나 |
|---|---|
| **루트 자격 증명 관리** | 관리 계정과 **IAM의 위임된 관리자**가 멤버 계정의 **루트 자격 증명을 삭제**할 수 있게 합니다 |
| **멤버 계정의 특권 루트 작업** | 관리 계정과 IAM 위임 관리자가 **루트 자격 증명이 필요한 일부 작업을 수행**할 수 있게 합니다 |

⚠️⚠️ **둘의 관계가 비대칭입니다.** 공식이 이렇게 적습니다 — **자격 증명이 삭제된 뒤 멤버 계정이 루트 자격 증명을 복구할 수 있게 하려면 「멤버 계정의 특권 루트 작업」을 활성화해야 합니다.** 자격 증명 관리만 켜고 삭제하면 **복구 경로가 없습니다.**

⚠️ 전제 셋 — 계정이 **Organizations로 관리**돼야 하고, **IAM의 신뢰 액세스**가 활성화돼야 하며(콘솔에 "루트 액세스 관리가 비활성화됨"이 보이면 그것입니다), 활성화 권한으로 `iam:EnableOrganizationsRootCredentialsManagement` · `iam:EnableOrganizationsRootSessions` · `organizations:EnableAwsServiceAccess` 등이 필요합니다. 위임 관리자 등록은 서비스 주체 **`iam.amazonaws.com`**으로 합니다.

#### 5-2. 무엇이 제거되고 무엇이 남는가

중앙 집중화 후 멤버 계정에서 제거할 수 있는 것은 **네 가지**입니다.

- 루트 사용자 **암호**
- 루트 사용자 **액세스 키**
- 루트 사용자 **서명 인증서**
- **MFA 비활성화**

⚠️ **Organizations에서 새로 만드는 계정은 기본적으로 루트 자격 증명이 없습니다.** 그리고 **계정 복구가 활성화되지 않으면 멤버 계정은 루트로 로그인하거나 루트 암호 복구를 할 수 없습니다.**

⚠️ 감사 쪽도 공식이 적습니다 — 멤버 계정의 루트 자격 증명 상태를 감사하려면 **`IAMAuditRootUserCredentials` 관리형 정책**으로 권한을 좁히거나 `iam:GetAccountSummary`가 있는 정책을 씁니다. 볼 수 있는 것은 **암호 존재 여부 · 액세스 키 존재 여부와 마지막 사용 시점 · 서명 인증서 보유 여부 · 연결된 MFA 디바이스**입니다.

#### 5-3. 특권 세션 — 한계가 시험 포인트다

루트 자격 증명을 복구하지 않고 멤버 계정의 루트 작업을 하려면 **특권 세션**을 만듭니다. 공식 API 참조가 한계를 명확히 적습니다.

| 매개변수 | 값 |
|---|---|
| ⚠️⚠️ **`DurationSeconds`** | **0~900초(15분)**. 기본값 **900**. 더 큰 값을 지정하면 **작업이 실패**합니다 |
| ⚠️ **`TaskPolicyArn`** | **필수**. 세션을 수행 가능한 특권 작업으로 한정하는 ID 기반 정책 |
| **`TargetPrincipal`** | **필수**. 멤버 계정의 주체 ARN 또는 계정 ID |
| **`MinimumSessionTokenSize`** | 세션 토큰의 최소 바이트 수. **4,096바이트를 넘을 수 없습니다** |

⚠️⚠️ **`TaskPolicyArn`은 다음 다섯 관리형 정책 중 하나여야 합니다.**

| 정책 | 세션이 할 수 있는 일 |
|---|---|
| `IAMAuditRootUserCredentials` | 루트 자격 증명 검토 |
| `IAMCreateRootUserPassword` | 멤버 루트 로그인 프로필 생성 |
| `IAMDeleteRootUserCredentials` | 멤버 루트 자격 증명 삭제 |
| `S3UnlockBucketPolicy` | S3 버킷 정책 삭제 |
| `SQSUnlockQueuePolicy` | SQS 대기열 정책 삭제 |

> 🧠 **원리:** 루트의 위험은 "무엇이든 할 수 있다"입니다. 특권 세션은 그 위험을 **두 방향으로 동시에 줄입니다** — **시간**(최대 15분)과 **작업 범위**(필수 작업 정책). 그래서 "S3 버킷 정책을 풀기 위한 세션으로 다른 루트 작업을 할 수 없다"가 성립합니다.

**대표 시나리오 둘**이 공식 모범 사례에 적혀 있습니다.

1. **모든 주체의 S3 버킷 접근을 거부하도록 잘못 설정된 버킷 정책을 제거**합니다
2. **모든 주체의 SQS 대기열 접근을 거부하는 리소스 기반 정책을 삭제**합니다

그리고 **멤버 계정이 루트 자격 증명을 복구하도록 허용**하는 특권 작업(`Allow password recovery`)이 있습니다. 그 뒤 **멤버 계정의 루트 이메일 수신함에 접근할 수 있는 사람**이 암호를 재설정해 로그인합니다. 공식 권고는 **그 작업이 끝나면 루트 자격 증명을 다시 삭제**하는 것입니다.

#### 5-4. 비상용 우회 절차

루트 자격 증명을 없애고 자동화된 경로로만 접근하는 환경에서는 **그 경로가 고장났을 때의 절차**가 필요합니다. Well-Architected 보안 원칙 `SEC03-BP03`이 이것을 요구합니다 — **자동화된 프로세스나 파이프라인 문제가 생긴 드문 경우에 워크로드에 비상 접근을 허용하는 프로세스**입니다.

| 축 | 공식이 적는 것 |
|---|---|
| **왜** | 최소 권한에 의존하면서도 **필요할 때 올바른 수준의 접근을 얻게** 하기 위해 |
| **형태** | 관리자가 요청을 **검증·승인**하는 프로세스. 예: 비상용 **교차 계정 역할**, 또는 비상 요청을 검증·승인하는 정해진 절차 |
| **안티패턴 ①** | 기존 ID 구성에 장애가 났을 때 **복구할 비상 프로세스가 없는 것** |
| **안티패턴 ②** | 문제 해결이나 복구를 위해 **장기 상승 권한을 부여하는 것** |
| **위험 수준** | 이 모범 사례를 세우지 않으면 **중간(Medium)** |

> 🧠 **원리:** 비상용 우회는 "루트를 남겨 두는 것"이 아닙니다. 공식이 드는 형태는 **미리 구성한 비상용 역할 + 승인 절차 + 단기 권한**입니다. 중앙 집중화 환경에서는 §5-3의 특권 세션이 그 역할의 일부를 대신합니다 — 15분·작업 범위·`sts:AssumeRoot` 권한 보유자만.

## ✍️ 시험 포인트

- **"비준수 리소스가 아예 만들어지지 않게"** → 경로를 가리지 않아야 하면 **예방 제어**(SCP·RCP·선언적 정책). **사전 제어는 CloudFormation 경로만** 봅니다(§2-4)
- **"서비스가 새 기능을 추가해도 구성이 유지되게"** → **선언적 정책**. "set once and forget"이 그 정책의 공식 이점 서술입니다
- **"서비스 연결 역할이 하는 일까지 통제"** 또는 **"관리 계정에도 적용"** → **선언적 정책만** 가능합니다(§3-2)
- **"조직 전 계정의 AI 서비스 데이터 사용을 중단"** → **AI 서비스 옵트아웃 정책**. SCP가 아닙니다
- **"계정을 OU로 옮겼는데 옛 제어가 남아 있다"** → **정상 동작**입니다. SCP·Config 규칙 제어는 **수동 제거**(§2-5)
- **"관리 계정 사용을 최소화하면서 조직 전체를 중앙 관리"** → **위임된 관리자 등록**(+ 신뢰 액세스 활성화)
- **"루트 자격 증명 없이 잘못된 버킷 정책을 풀어야 한다"** → **특권 세션** + `S3UnlockBucketPolicy`. **최대 15분**입니다
- **"멤버 계정이 나중에 루트를 복구할 수 있어야 한다"** → **「멤버 계정의 특권 루트 작업」도** 활성화해야 합니다(§5-1)
- **"드리프트 알림이 안 온다"** → **계정 자동 등록**을 켰는지 봅니다. 그러면 SNS 알림을 쓸 수 없습니다
- **"필수 제어가 켜져 있을 것이다"** → **랜딩 존 4.0부터는 기본 적용이 아닙니다**

## ⚠️ 흔한 함정 {#pitfalls}

- ❌ **"예방 제어는 SCP로 구현된다"** → 공식은 **SCP·RCP·선언적 정책 셋**을 적습니다. 그래서 일일 스캔 대상도 셋입니다
- ❌ **"사전 제어를 켜면 콘솔에서 만든 리소스도 막힌다"** → `preCreate`·`preUpdate` 후크라 **CloudFormation 밖의 요청에는 영향을 주지 않을 수 있습니다**
- ❌ **"사전 제어가 템플릿의 보안 암호 값도 검사한다"** → 보안 문자열·보안 암호는 **후크로 가기 전에 해결되지 않습니다**
- ❌ **"SCP를 조직 루트에 붙이면 관리 계정도 묶인다"** → **SCP·RCP는 관리 계정에 적용되지 않습니다.** 선언적 정책은 적용됩니다
- ❌ **"태그 정책으로 태그 없는 리소스 생성을 막는다"** → 태그 정책은 **권한을 부여·거부하지 않는** 선언적 범주입니다. 자세한 평가 규칙은 작업 6.2에서 다룹니다
- ❌ **"선언적 정책을 떼면 설정이 그대로 남는다"** → **이전 상태로 롤백**됩니다
- ❌ **"드리프트 알림은 멤버 계정마다 따로 본다"** → 멤버 드리프트는 **감사 계정에 집계**됩니다
- ❌ **"같은 드리프트가 계속 알림을 보낸다"** → **중복이 제거**돼 첫 번째만 옵니다. 해소 후 재발하면 다시 옵니다
- ❌ **"위임된 관리자는 조직 전체 관리자다"** → **그 서비스의 일부 관리 권한 + Organizations 읽기 전용**입니다
- ❌ **"특권 세션을 1시간 쓴다"** → **최대 900초**이고 더 큰 값을 주면 **작업이 실패**합니다
- ❌ **"루트 자격 증명을 지우면 MFA는 남는다"** → **MFA 비활성화도 제거 대상 넷 중 하나**입니다

## 🧪 자가 점검

**Q1.** 보안팀이 "조직의 모든 계정에서 EC2 퍼블릭 AMI 사용을 금지"하는 통제를 만들었습니다. 그런데 **관리 계정의 관리자**가 퍼블릭 AMI로 인스턴스를 띄우는 데 성공했고, 서비스 연결 역할이 수행하는 작업도 막히지 않았습니다. 어떤 정책 유형을 썼고 무엇으로 바꿔야 합니까? (→ 3-2 비대칭 표)

<details><summary>정답 보기</summary>

**SCP(또는 RCP)를 썼고 선언적 정책으로 바꿔야 합니다.**

- 공식이 선언적 정책 페이지에 표로 적습니다 — **관리 계정 영향**은 SCP **아니오** / RCP **아니오** / 선언적 정책 **예**이고, **서비스 연결 역할 통제**도 SCP **아니오** / RCP **아니오** / 선언적 정책 **예**입니다
- 두 증상이 **같은 뿌리**입니다. SCP·RCP는 **API 수준에서 요청을 평가**하는 권한 부여 정책이라 "요청 평가에서 빠지는" 주체에 닿지 못합니다
- 선언적 정책은 **서비스의 제어 플레인에서 API 작업을 쓰지 않고** 기준 구성을 시행합니다. 공식이 드는 예시 정책이 바로 **`Allowed Images Settings`**(허용된 이미지 설정)입니다
- 덧붙여 선언적 정책은 **OU·계정의 유효 정책 보기를 지원**하는 유일한 범주라 "지금 이 계정에 실제로 적용되는 규칙"을 확인할 수 있습니다

⚠️ 한도도 다릅니다 — SCP 10개·10,240자, RCP **5개·5,120자**, 선언적 10개·10,000자입니다.
</details>

**Q2.** "비준수 S3 버킷이 **아예 만들어지지 않게** 하라"는 요건에 플랫폼팀이 Control Tower **사전 제어**를 활성화했습니다. 그런데 한 팀이 콘솔에서 만든 퍼블릭 버킷이 그대로 생성됐습니다. 원인과, 요건을 실제로 만족시키는 방법은? (→ 2-4 한계 셋)

<details><summary>정답 보기</summary>

**사전 제어는 `preCreate`·`preUpdate` 후크 핸들러라 CloudFormation을 거치지 않는 요청을 막지 못합니다.**

- 공식이 사전 제어 페이지에 그대로 적습니다 — 이 제어들은 **"AWS 콘솔·AWS API·AWS SDK·다른 IaC 도구를 통해 서비스에 직접 하는 요청에는 영향을 주지 않을 수 있다"**
- 사전 제어가 보는 것은 **CloudFormation 스택 작업으로 리소스가 만들어지거나 업데이트될 때**입니다
- 경로를 가리지 않아야 하면 **예방 제어**를 씁니다 — 구현 수단이 **SCP·RCP·선언적 정책**이고, 앞 둘은 **API 앞**에서, 선언적 정책은 **서비스 제어 플레인 안**에서 작동하므로 콘솔이든 SDK든 같습니다
- ⚠️ 두 번째 한계도 함께 기억합니다 — **보안 문자열과 보안 암호는 후크로 가기 전에 해결되지 않아** 사전 제어가 평가할 수 없습니다
- ⚠️ 세 번째는 리전입니다 — **CloudFormation 후크가 Control Tower 가용 리전 전부에서 지원되지 않습니다**

⚠️ 그렇다고 사전 제어가 쓸모없는 것은 아닙니다. IaC 파이프라인이 유일한 배포 경로로 **강제된** 환경에서는 개발자에게 즉시 피드백을 주는 가장 싼 수단입니다. 틀린 것은 "사전 제어만으로 경로 전체가 닫힌다"는 전제입니다.
</details>

**Q3.** 운영팀이 계정 하나를 `Sandbox` OU에서 `Production` OU로 옮겼습니다. 그런데 샌드박스용으로만 켰던 느슨한 제어가 여전히 그 계정에 적용되는 것처럼 보입니다. 정상입니까? (→ 2-5 OU 이동)

<details><summary>정답 보기</summary>

**정상 동작입니다. OU를 옮겨도 이전 OU의 제어는 제거되지 않습니다.**

- 공식 드리프트 문서가 계정 드리프트 유형으로 **"OU 사이에서 이동된 계정"**을 적으면서 Note로 명시합니다 — **이전 OU의 제어는 제거되지 않습니다**
- 자동으로 교체되는 것은 **후크 기반 제어 하나뿐**입니다. 대상 OU에서 새 후크 기반 제어를 활성화하면 **옛 후크 기반 제어가 제거되고 새 제어가 대체**합니다
- ⚠️ **SCP와 AWS Config 규칙으로 구현된 제어는 계정이 OU를 바꿀 때 항상 수동으로 제거**해야 합니다
- 즉 OU 이동은 **거버넌스 이관의 절반**이고, 나머지 절반(옛 예방·탐지 제어 정리)은 운영 절차로 해야 합니다

⚠️ 이 상태가 **상속 드리프트**로 드러납니다. 드리프트 알림이 오지 않는다면 **설정에서 계정 자동 등록을 켰는지** 확인합니다 — 그 경우 SNS 드리프트 알림을 쓸 수 없습니다.
</details>

**Q4.** 보안팀이 조직의 모든 계정에서 Security Hub CSPM과 AWS Config를 중앙 관리하려고 합니다. 가장 간단한 길은 관리 계정에서 전부 운영하는 것처럼 보입니다. 공식 권고는 무엇이고 왜입니까? (→ 1-2·4-1 위임된 관리자)

<details><summary>정답 보기</summary>

**보안 계정을 각 서비스의 위임된 관리자로 등록하고, 관리 계정은 그 계정만 할 수 있는 작업에만 씁니다.**

- 이유가 공식 문서에 한 문장으로 있습니다 — **"Organizations의 SCP 같은 보안 기능은 관리 계정의 사용자나 역할을 제한하지 않습니다."** 즉 관리 계정에 운영을 쌓으면 **조직의 가장 강한 통제가 적용되지 않는 곳**에 작업이 모입니다
- 부수 효과로 **청구서에서 비용을 가려내기 쉬워집니다**
- 등록 전 두 가지를 확인합니다 — ① 그 서비스가 **위임된 관리자를 지원하는지**(Organizations와 함께 쓸 수 있는 서비스 표의 해당 열) ② 그 서비스의 **신뢰 액세스를 활성화**했는지
- ⚠️ 위임된 관리자가 받는 것은 **그 서비스의 일부 관리 권한과 Organizations 읽기 전용 작업 권한**입니다 — 조직 전체의 관리 권한이 아닙니다

⚠️ 이 자격증 범위에서 자주 나오는 위임 대상은 **Security Hub CSPM · AWS Config 애그리게이터 · StackSets(서비스 관리형) · IAM(루트 액세스 관리) · Firewall Manager**입니다.
</details>

**Q5.** 멤버 계정의 개발자가 S3 버킷 정책에 모든 주체를 거부하는 문장을 넣어 **자기 자신도 접근할 수 없게** 만들었습니다. 그 계정의 루트 자격 증명은 조직 정책에 따라 이미 삭제된 상태입니다. 어떻게 복구하고, 그 세션의 한계는 무엇입니까? (→ 5-1·5-3 특권 세션)

<details><summary>정답 보기</summary>

**관리 계정 또는 IAM 위임 관리자에서 `sts:AssumeRoot`로 특권 세션을 만들어 `S3UnlockBucketPolicy` 작업 정책으로 버킷 정책을 삭제합니다.**

- 전제는 **「멤버 계정의 특권 루트 작업」 기능이 활성화**돼 있는 것입니다. 「루트 자격 증명 관리」만 켜 두면 삭제는 되지만 이런 작업을 할 수 없습니다
- 공식 API 참조가 한계를 적습니다 — **`DurationSeconds`는 0~900초(15분)이고 기본값이 900이며, 더 큰 값을 지정하면 작업이 실패**합니다
- **`TaskPolicyArn`은 필수**이고 **다섯 관리형 정책 중 하나**여야 합니다 — `IAMAuditRootUserCredentials` · `IAMCreateRootUserPassword` · `IAMDeleteRootUserCredentials` · `S3UnlockBucketPolicy` · `SQSUnlockQueuePolicy`
- 그래서 **버킷 정책을 풀려고 만든 세션으로 다른 루트 작업을 할 수 없습니다**. 공식 모범 사례가 드는 시나리오가 바로 이 S3 사례와 **SQS 대기열의 리소스 기반 정책 삭제**입니다

⚠️ 루트 자격 증명 자체를 되살려야 하는 작업이라면 **`Allow password recovery`** 특권 작업을 수행하고, **멤버 계정의 루트 이메일 수신함에 접근할 수 있는 사람**이 암호를 재설정합니다. 공식 권고는 **작업이 끝나면 루트 자격 증명을 다시 삭제**하는 것입니다.
</details>

**Q6.** 감사인이 "루트 자격 증명을 모두 없앴다면 ID 파이프라인이 고장났을 때 어떻게 들어갑니까?"라고 묻습니다. 무엇을 보여 줘야 합니까? (→ 5-4 비상용 우회)

**미리 구성한 비상 접근 프로세스입니다.** Well-Architected 보안 원칙 **`SEC03-BP03`**이 이것을 요구합니다.

- 공식 서술 — **"자동화된 프로세스나 파이프라인 문제가 생긴 드문 경우에 워크로드에 비상 접근을 허용하는 프로세스"**입니다. 최소 권한에 의존하면서도 **필요할 때 올바른 수준의 접근을 얻게** 하는 것이 목적입니다
- 공식이 드는 형태는 **관리자가 요청을 검증·승인하는 절차**이고, 예로 **비상용 교차 계정 역할**을 듭니다
- 안티패턴 둘을 함께 보여 줍니다 — ① 기존 ID 구성 장애에서 **복구할 비상 프로세스가 없는 것** ② 문제 해결·복구를 위해 **장기 상승 권한을 부여하는 것**
- 이 모범 사례를 세우지 않았을 때의 **위험 수준은 중간(Medium)**입니다

⚠️ 중앙 집중화 환경에서는 §5-3의 특권 세션이 이 역할의 상당 부분을 대신합니다 — **15분 · 작업 범위 한정 · `sts:AssumeRoot` 권한 보유자만**. 즉 "루트를 남겨 두는 것"이 아니라 **짧고 좁은 경로를 미리 만들어 두는 것**이 답입니다.
