# 엔터프라이즈 통합 아키텍처 (연결 솔루션·기존 앱 개선·보안 액세스·환경 간 배포·CI/CD와 GenAI 게이트웨이)

> **커버하는 공식 Task** — AIP-C01 · 도메인 2 「구현 및 통합」(26%) · **작업 2.3 엔터프라이즈 통합 아키텍처 설계 및 구현** (`aip-t2-3`)
> 이 문서는 위 한 작업에 1:1로 매핑되고 공식 기술 5개(2.3.1~2.3.5)를 모두 덮습니다. ⚠️ 이 작업의 소재는 **GenAI 전용 서비스가 아니라 엔터프라이즈 통합의 일반 수단**입니다 — 공식 가이드가 「시험에 출제될 수 있는 기술 및 개념」에 **엔터프라이즈 통합·이벤트 기반 아키텍처·API 설계·CI/CD·하이브리드 클라우드**를 나란히 적기 때문입니다. 다만 **FM과 엮이는 축으로만** 봅니다.

---

## ✅ 학습 목표 체크리스트

- [ ] 느슨한 결합의 **전달 보장 계약**(재시도·DLQ)을 안다
- [ ] 이벤트 버스의 **규칙·대상 제약**과 Pipes와의 경계를 안다
- [ ] 기존 앱에 GenAI를 더하는 **세 진입점**을 가를 수 있다
- [ ] 페더레이션 유형 **셋**을 계정 구조로 고를 수 있다
- [ ] FM 접근의 **최소 권한**을 콘솔·API로 갈라 설계할 수 있다
- [ ] Outposts와 Wavelength가 **각각 무엇을 확장하는지** 안다
- [ ] 파이프라인 **스테이지 잠금과 대체**를 설명할 수 있다
- [ ] GenAI 게이트웨이가 모으는 **세 가지**를 안다

## 🎯 왜 중요한가

GenAI 기능이 기존 시스템에 들어갈 때 실패하는 지점은 **모델이 아니라 경계**입니다. 레거시 시스템은 동기 API만 알고, 보안 팀은 **누가 어떤 모델을 부를 수 있는지**를 묻고, 규제는 **데이터가 어느 관할 구역에 있는지**를 묻습니다.

그래서 이 작업의 다섯 기술은 **FM을 조직 안에 들여놓는 조건**을 하나씩 집습니다 — 어떻게 **잇고**(2.3.1·2.3.2), 어떻게 **막고**(2.3.3), 어디에 **두고**(2.3.4), 어떻게 **반복 배포하는가**(2.3.5)입니다.

---

## ⚡ 시험 직전 요약

- ⚠️⚠️ EventBridge 기본 재시도는 **24시간 · 최대 185회 · 지수 백오프 + 지터**이고, **모두 소진되면 이벤트가 드롭되고 더 처리되지 않습니다** — 유실을 막는 수단은 **DLQ**입니다.
- 이벤트는 **여러 규칙에 일치할 수 있고 각 규칙은 최대 다섯 개 대상**을 지정합니다. ⚠️ **규칙은 특정 버스에 연결**되어 그 버스가 받은 이벤트에만 적용됩니다.
- ⚠️ **EventBridge Pipes는 점대점 통합용**입니다 — **단일 소스 → 단일 대상**이고 **고급 변환과 강화**를 지원합니다.
- ⚠️⚠️ 공식이 **새 애플리케이션에는 `Custom Event Bus`로 시작하라**고 적습니다 — 기본 버스와 **`Custom Event Bus - Classic`**은 **규칙과 대상**으로 라우팅하고, `Custom Event Bus`는 **소비자가 만드는 구독자**에게 보내며 **리플레이용으로 이벤트를 보존**합니다.
- 페더레이션 유형 셋 — **Identity Center**(Organizations의 **여러 계정** · 워크포스) · **IAM**(**단일 독립 계정** · 단기·소규모 + **머신 사용자**) · **Cognito ID 풀**(앱 사용자). ⚠️ **OIDC는 AWS에서 돌지 않는 애플리케이션**(예: GitHub Actions)을 잇습니다.
- ⚠️ Bedrock 콘솔에는 **최소 권한 집합**이 필요하고 그보다 제한적이면 **콘솔이 의도대로 동작하지 않습니다.** ⭐ **CLI·API만 부르는 주체에게는 콘솔 권한이 필요 없습니다.**
- **Outposts는 고객 사업장으로** AWS를 확장하고, **Wavelength는 통신사(CSP) 네트워크 엣지로** 확장합니다 — 전자는 **온프레미스 데이터**, 후자는 **모바일 사용자 지연**입니다.
- ⚠️ **Outpost를 같은 VPC 안의 다른 Outpost나 Local Zone에 연결할 수 없습니다.**
- ⚠️⚠️ **파이프라인은 여러 실행을 동시에 처리하지만 스테이지는 한 번에 하나**만 처리합니다(처리 중 **잠깁니다**). 대기 중인 **인바운드 실행**은 **실패·대체·수동 중지**될 수 있고 상태에 **`Superseded`**가 있습니다.
- GenAI 게이트웨이가 모으는 셋 — **추상화**(도구를 MCP 호환으로 변환) · **제어**(도구 접근 **전에** 정책 평가) · **관찰성**(도구별 호출 수·성공률·오류율·지연 백분위수).

| 용어 | 뜻 |
|---|---|
| **이벤트 패턴** | 규칙이 이벤트를 고르기 위해 비교하는 JSON 조건 |
| **DLQ**(배달 못한 편지 큐) | 전달에 실패한 이벤트를 받아 두는 큐 |
| **ID 페더레이션** | AWS 밖의 ID 공급자로 인증하고 AWS 권한을 받는 방식 |

| **로컬 게이트웨이(LGW)** | Outposts 랙과 온프레미스 네트워크를 잇는 논리적 가상 라우터 |

| **GenAI 게이트웨이** | 모델·도구 접근을 한 지점으로 모아 제어·관찰하는 계층 |

## 📖 핵심 개념

### 1) 엔터프라이즈 연결 솔루션 (기술 2.3.1) {#connectivity}

> 🧠 원리: 레거시와 FM을 잇는 방법은 **동기 호출**과 **이벤트** 둘입니다. 동기는 단순하지만 **느린 쪽이 빠른 쪽을 묶고**, 이벤트는 느슨하지만 **전달 보장과 순서를 내가 설계**해야 합니다. 그 설계의 실체가 **재시도와 DLQ**입니다.

**API 기반 통합** — 레거시 시스템이 이해하는 것이 보통 REST이므로 **API 계층을 앞에 둡니다.** API Gateway는 **REST·HTTP·WebSocket API**를 만들고, 수십만 건의 동시 호출을 받아 **트래픽 관리·인가와 액세스 제어·모니터링·API 버전 관리**를 맡는 **「프런트 도어」**로 동작합니다.

**이벤트 기반 아키텍처** — 느슨한 결합의 핵심 계약은 **전달 보장**입니다.

- 전달이 **재시도 가능한 오류**로 실패하면 EventBridge가 재시도합니다. 기간과 횟수는 **대상의 재시도 정책**에서 정하고 **기본값은 24시간 · 최대 185회 · 지수 백오프와 지터**(무작위 지연)입니다.
- ⚠️⚠️ **모든 재시도가 소진되면 이벤트가 드롭되고 EventBridge는 더 처리하지 않습니다.** 그래서 **DLQ를 구성해 실패 이벤트를 전부 받아 두는 것**이 유실을 막는 공식 수단입니다.
- 공식이 드는 실패 원인 예: **대상 리소스를 쓸 수 없을 때** · **네트워크 상황**.

**이벤트 버스의 구조**:

- Classic 이벤트 버스는 이벤트를 받아 **0개 이상의 대상**에 전달하는 **라우터**입니다. **다수 소스 → 다수 대상** 라우팅에 맞고, 전달 전 **선택적 변환**을 할 수 있습니다.
- 규칙이 도착하는 이벤트를 **이벤트 패턴**으로 평가합니다. ⚠️ **규칙은 특정 이벤트 버스에 연결**되어 **그 버스가 받은 이벤트에만** 적용됩니다.
- ⚠️⚠️ **이벤트가 여러 규칙에 일치할 수 있고 각 규칙은 최대 다섯 개 대상**을 지정합니다. 아무 규칙에도 맞지 않으면 **EventBridge는 아무 일도 하지 않습니다** — 조용한 실패가 되므로 패턴을 먼저 검증합니다.
- ⚠️ **EventBridge Pipes는 다릅니다** — **점대점 통합용**이고 각 파이프가 **단일 소스**에서 받아 **단일 대상**으로 처리·전달하며 전달 전 **고급 변환과 강화(enrichment)**를 지원합니다. 「다수 → 다수」는 버스, 「하나 → 하나 + 강화」는 Pipes입니다.
- ⚠️⚠️ 공식이 **새 애플리케이션에는 `Custom Event Bus`로 시작하라**고 적습니다. 기본 버스와 **`Custom Event Bus - Classic`**은 **버스 소유자가 쓰는 규칙과 대상**으로 라우팅하는 반면, `Custom Event Bus`는 **소비자가 직접 만드는 구독자**에게 라우팅하고 **리플레이용으로 이벤트를 보존**합니다. 기존 규칙을 구독자로 옮기는 **마이그레이션 안내**가 따로 있습니다.

**데이터 동기화 패턴** — 이벤트로 잇는 순간 **두 시스템의 상태가 갈립니다.** 그래서 어느 쪽이 정본인지, 재시도로 **같은 이벤트가 두 번 올 때**(중복) 무엇을 하는지를 설계에 적어야 합니다. ⚠️ 재시도가 기본 **185회**라는 사실이 그대로 **멱등성 요구**가 됩니다.

### 2) 기존 애플리케이션에 GenAI를 더한다 (기술 2.3.2) {#augment}

> 🧠 원리: 기존 앱을 **고치지 않고** 기능을 더하는 방법이 셋입니다 — **앞에 붙이기**(API), **옆에서 듣기**(이벤트), **안에서 부르기**(함수). 고르는 기준은 **그 앱을 바꿀 수 있는가**입니다.

- **API Gateway로 마이크로서비스 통합** — 앱을 바꾸지 않고 **새 엔드포인트를 추가**해 GenAI 기능을 노출합니다. 그 자리에서 함께 쓰는 것들: **IAM 정책 · Lambda 권한 부여자(authorizer) · Cognito 사용자 풀**로 인증하고, **CloudWatch 액세스·실행 로깅과 경보**를 걸고, **AWS WAF**로 일반적인 웹 공격을 막고, **AWS X-Ray**로 지연을 추적합니다. 변경을 안전하게 내보내려면 **카나리 릴리스 배포**를 씁니다.
- **Lambda 웹훅 핸들러** — 외부 SaaS(CRM·티켓·채팅)가 **웹훅으로 밀어 주는** 이벤트를 받아 모델을 부릅니다. 앱을 바꿀 수 없고 상대가 HTTP를 밀어 줄 수 있을 때의 표준 경로입니다.
- **EventBridge로 이벤트 기반 통합** — 앱이 이미 내는 이벤트를 **규칙으로 골라** GenAI 처리로 보냅니다. ⭐ 원본 앱은 **무엇이 구독하는지 모릅니다** — 그것이 느슨한 결합의 값입니다.
- ⚠️ 셋을 섞을 때 흔한 실수는 **동기 경로에 긴 작업을 두는 것**입니다. 모델 응답이 길어질 수 있으면 **API는 수락만 하고** 처리는 이벤트·큐로 넘깁니다(작업 2.4·2.5의 계약과 함께 읽습니다).

### 3) 보안 액세스 프레임워크 (기술 2.3.3) {#secure-access}

> 🧠 원리: 「누가 FM을 쓸 수 있나」는 **두 층**입니다 — **사람을 인증하는 층**(페더레이션)과 **그 사람·워크로드가 무엇을 부를 수 있는지 정하는 층**(IAM 정책). 둘을 섞으면 어느 쪽에서 막혔는지 알 수 없습니다.

**① ID 페더레이션** — ⭐ 공식 모범 사례는 **사람 사용자가 IAM 사용자를 만들지 말고 ID 공급자로 페더레이션하는 것**입니다. 조직에 이미 디렉터리가 있을 때, 또는 모바일·웹 앱이 AWS 리소스에 접근해야 할 때 특히 그렇습니다. ⭐ **장기 자격 증명(액세스 키)을 애플리케이션에 배포·임베드하지 않아도 되는 것**이 보안 이득입니다.

| 유형 | 계정 구조 | 누구의 액세스를 관리하나 | 지원 ID 소스 |
|---|---|---|---|
| **IAM Identity Center 페더레이션** | **Organizations가 관리하는 여러 계정** | **워크포스의 사람 사용자** | SAML 2.0 · Managed Active Directory · Identity Center 디렉터리 |
| **IAM 페더레이션** | **단일 독립 계정** | **단기·소규모 배포의 사람 사용자**와 **머신 사용자** | SAML 2.0 · OIDC |
| **Cognito ID 풀 페더레이션** | 모든 계정 유형 | **리소스 접근에 IAM 인가가 필요한 앱의 사용자** | SAML 2.0 · OIDC · 일부 OAuth 2.0 소셜 IdP |

- ⚠️ **OIDC의 용례가 비자명합니다** — 공식이 **「AWS에서 돌지 않는 애플리케이션(예: GitHub Actions)을 AWS 리소스에 연결한다」**로 적습니다. CI/CD 파이프라인의 자격 증명 문제(기술 2.3.5)가 여기서 풀립니다.
- Identity Center 사용자는 **단기 자격 증명**을 받습니다. ⭐ 그리고 **account access manager**(IAM 기능)로 **기존 IAM 역할을 조직의 계정들에 걸쳐 Identity Center 사용자·그룹에 할당**할 수 있고, **권한 세트와 함께 또는 단독으로** 씁니다.

**② 모델·데이터 접근의 최소 권한** — Bedrock은 **기본적으로 사용자·역할에 권한이 없습니다.** 공식 정책 모범 사례 다섯:

- **AWS 관리형 정책으로 시작해 최소 권한으로 이동**합니다(`AmazonBedrockFullAccess`·`AmazonBedrockReadOnly`가 있고, 용례에 맞는 **고객 관리형 정책**으로 좁힙니다).
- **최소 권한을 적용**합니다 — 특정 리소스에 특정 조건에서 취할 수 있는 **액션을 정의**하는 것입니다.
- **조건으로 더 제한**합니다(예: 모든 요청을 SSL로, 또는 **특정 AWS 서비스를 통할 때만** 허용).
- **IAM Access Analyzer로 정책을 검증**합니다 — **100개 이상의 정책 검사**와 실행 가능한 권고를 줍니다.
- **MFA를 요구**합니다(API 작업에 MFA 조건을 더합니다).
- ⚠️ **콘솔에는 최소 권한 집합이 필요합니다** — 그보다 제한적인 정책을 만들면 **콘솔이 의도대로 동작하지 않습니다.** ⭐ 반대로 **CLI·API만 호출하는 주체에게는 콘솔 최소 권한이 필요 없고**, 수행하려는 **API 작업에 맞는 액션만** 허용합니다. 서비스 계정을 설계할 때 이 구분이 그대로 정책 크기를 줄입니다.
- 공식 예제 묶음이 **역할 기반 접근의 모양**을 보여 줍니다 — **파운데이션 모델 추론 거부** · **프로비저닝된 모델 호출 허용** · **Playground 채팅 최소 정책**. 역할을 「개발자 / 운영자 / 평가자」로 가를 때 이 셋이 출발점입니다.

### 4) 환경 간 AI 솔루션 (기술 2.3.4) {#cross-env}

> 🧠 원리: 데이터를 리전으로 **옮길 수 없을 때** 쓰는 수단과, 사용자에게 **더 가까이 가야 할 때** 쓰는 수단은 다릅니다. 이름이 비슷해 섞이지만 **확장하는 대상이 다릅니다** — 하나는 **내 건물**, 하나는 **통신사 네트워크**입니다.

**AWS Outposts — 고객 사업장으로의 확장**:

- 완전관리형으로 **AWS 인프라·서비스·API·도구를 고객 사업장으로 확장**합니다. **리전과 같은 프로그래밍 인터페이스**로 온프레미스에서 빌드·실행하면서 **로컬 컴퓨팅·스토리지로 더 낮은 지연과 로컬 데이터 처리**를 얻습니다 — **온프레미스 데이터 통합**이 이 기술의 용례입니다.
- Outpost는 고객 사이트에 배치된 **AWS 컴퓨팅·스토리지 용량 풀**이고 **AWS가 리전의 일부로 운영·모니터링·관리**합니다. Outpost에 **서브넷을 만들어** EC2·EBS·ECS 클러스터·RDS 인스턴스를 그 서브넷으로 만들고, ⭐ **Outpost 서브넷의 인스턴스는 같은 VPC 안에서 사설 IP로 리전의 인스턴스와 통신**합니다.
- ⚠️⚠️ **Outpost를 같은 VPC 안의 다른 Outpost나 Local Zone에 연결할 수 없습니다.**
- **서비스 링크**가 Outpost와 연결된 리전 사이의 통신 경로이고, **각 Outpost는 가용 영역과 그 리전의 확장**입니다.
- ⚠️ 폼 팩터에 따라 **온프레미스 연결 수단이 다릅니다** — **Outposts 랙**(42U)은 **로컬 게이트웨이(LGW)**, **Outposts 서버**(1U·2U, 공간·용량이 제한된 사이트)는 **로컬 네트워크 인터페이스**입니다.
- ⚠️ **컴퓨팅 랙이 4개 이상이면 ACE 랙을 반드시 설치**해야 합니다(다중 랙 배포의 네트워크 집계 지점). 4개 미만이어도 장차 확장할 계획이면 **조기 설치를 권장**합니다.

**AWS Wavelength — 통신사 네트워크 엣지로의 확장**:

- **모바일 기기와 최종 사용자에게 낮은 지연**을 주거나 기존 엣지 애플리케이션의 **복원력을 높이기** 위한 엣지 컴퓨팅입니다. 표준 AWS 컴퓨팅·스토리지를 **통신 서비스 공급자(CSP) 네트워크의 엣지**에 배치하고, **VPC를 하나 이상의 Wavelength Zone으로 확장**합니다.
- **Wavelength Zone**은 통신사 위치의 존이고 **리전과 연결되며 리전의 논리적 확장**이고 **리전의 컨트롤 플레인이 관리**합니다. ⭐ 그래서 **인터페이스를 쓸 때는 부모 리전을 씁니다.**
- ⚠️ **캐리어 게이트웨이는 두 목적**입니다 — 특정 위치의 **통신사 네트워크에서 들어오는 인바운드 허용**과 **통신사 네트워크·인터넷으로의 아웃바운드 허용**.
- **네트워크 경계 그룹**은 AWS가 IP 주소를 광고하는 **AZ·Local Zone·Wavelength Zone의 고유 집합**입니다.
- 쓸 수 있는 것: EC2·EBS·VPC 서브넷·캐리어 게이트웨이와 **EC2 Auto Scaling · EKS · ECS · Systems Manager · CloudWatch · CloudTrail · CloudFormation**. ⚠️ **Application Load Balancer는 일부 Wavelength Zone에서만** 됩니다.
- ⚠️ 그래서 「엣지에서 FM을 직접 돌린다」는 설계는 성립하지 않습니다 — Wavelength에서 돌리는 것은 **EC2·컨테이너 워크로드**이고, 모델 추론은 **부모 리전의 서비스**로 갑니다. 엣지가 줄이는 것은 **사용자와 애플리케이션 사이의 지연**입니다.

**보안 라우팅** — 두 경우 모두 **VPC가 경계**입니다. Outposts는 **사설 IP로 같은 VPC 안에서** 리전과 통신하고, Wavelength는 **VPC를 존으로 확장**합니다. 관할 구역 요구는 **데이터가 어디에 머무는지**로 맞추고, 접근 통제는 기술 2.3.3의 IAM 층으로 맞춥니다.

### 5) CI/CD와 GenAI 게이트웨이 (기술 2.3.5) {#cicd-gateway}

> 🧠 원리: 이 기술은 둘을 한 문장에 넣었습니다 — **어떻게 반복 배포하는가**(CI/CD)와 **소비를 어디로 모으는가**(게이트웨이). 둘의 공통점은 **표준화**입니다. 파이프라인이 배포를 표준화하고 게이트웨이가 접근을 표준화합니다.

**① CI/CD** — CodePipeline의 개념이 그대로 설계 어휘입니다.

- **파이프라인**은 소프트웨어 변경이 릴리스 프로세스를 통과하는 방식을 설명하는 **워크플로 구성물**이고 **스테이지**의 연속입니다.
- **스테이지**는 **환경을 격리하고 그 환경의 동시 변경 수를 제한**하는 논리 단위입니다. ⭐ GenAI 구성 요소의 테스트 스테이지를 따로 두는 이유가 이 정의에 있습니다.
- **액션 유형은 여섯**입니다 — **`source` · `build` · `test` · `deploy` · `approval` · `invoke`**. 직렬·병렬로 돌 수 있고 순서는 `runOrder`가 정합니다. ⭐ **`approval`이 액션 유형으로 있다**는 것이 「사람 승인을 파이프라인에 넣는다」의 근거입니다.
- ⚠️⚠️ **파이프라인은 여러 실행을 동시에 처리할 수 있지만 스테이지는 한 번에 하나만** 처리합니다 — 처리 중 스테이지는 **잠깁니다.** 들어가려고 기다리는 것이 **인바운드 실행**이고 **실패·대체·수동 중지될 수 있습니다.**
- 파이프라인 상태는 `InProgress`·`Stopping`·`Stopped`·`Succeeded`·**`Superseded`**·`Failed`입니다. ⚠️ **실패하면 스테이지가 잠금 해제**되어 **더 최신 실행이 따라잡아 들어올 수 있습니다** — 롤백 설계에서 이 동작을 모르면 「왜 옛 변경이 사라졌나」가 됩니다.
- **전환(transition)**을 비활성화해 실행이 스테이지에 들어가지 못하게 할 수 있습니다. ⚠️⚠️ 비활성화된 전환에 **여러 실행이 도착하면 활성화 시 가장 최신 실행만 계속**합니다(새 실행이 대기 실행을 **대체**합니다).
- 중지 방법은 둘 — **Stop and wait** · **Stop and abandon**이고 **중지된 실행은 재시도할 수 있습니다.**
- ⚠️ 「보안 스캔과 롤백 지원이 포함된 자동화된 테스트 프레임워크」는 **파이프라인의 스테이지 구성**으로 만듭니다 — 스캔을 `test` 액션으로, 승인을 `approval` 액션으로, 롤백은 실패 시 스테이지 잠금 해제 동작과 배포 액션의 되돌림으로 설계합니다.

**② GenAI 게이트웨이** — 공식 기술이 적는 「중앙 집중식 추상화 계층, 관찰성 및 제어 메커니즘」이 **에이전트 트래픽의 단일 보안 진입점**으로 구현됩니다.

| 모으는 것 | 무엇을 주는가 |
|---|---|
| **추상화** | API·Lambda 함수·기존 서비스를 **MCP 호환 도구로 변환**하고, 여러 API·함수·도구·에이전트·모델 공급자를 **한 엔드포인트 뒤로** 모은다(**인그레스·이그레스 인증을 모두** 제공한다) |
| **제어** | 정책 엔진을 게이트웨이에 연결하면 **모든 에이전트 트래픽을 가로채 도구 접근 전에** 각 요청을 평가한다 — ⭐ 보안 제어가 **에이전트 코드 밖으로** 나가므로 에이전트 조작으로 우회하기 어려워진다 |
| **관찰성** | **도구별 호출 수 · 성공률 · 유형별 오류율 · 지연 백분위수**를 추적하고 **복합 알람**으로 여러 지표를 묶는다 |
| **소비 통제** | 추론 타깃을 **분당 토큰(TPM)**으로, 엔드포인트의 **동시 연결 수**를 제한한다 |

- ⭐ **복합 알람이 왜 필요한지**가 이 기술의 좋은 시험 포인트입니다 — **지연이 오르면서 타임아웃 비율도 오르는 도구**는 단일 임계로는 어느 쪽도 울리지 않아도 **차단에 가까워진** 도구이고, 복합 보기가 단일 임계보다 **먼저** 열화를 잡습니다.
- ⚠️ 게이트웨이의 자세한 계약(의미 검색·동기화·라우팅 규칙·속도 제한 수치)은 **작업 2.1**이 소유합니다. 이 작업에서 묻는 것은 **왜 한 지점으로 모으는가**입니다.

## ✍️ 시험 포인트

- 「이벤트가 사라졌다」면 **재시도 소진 후 드롭**이고 대비 수단은 **DLQ**입니다.
- 「같은 처리가 두 번 일어났다」면 **재시도(기본 185회)**를 전제로 **멱등성**을 설계해야 합니다.
- 「규칙을 만들었는데 아무 일도 안 일어난다」면 **버스가 다르거나 이벤트 패턴이 안 맞는** 것입니다.
- 「한 소스에서 한 대상으로 보내며 강화까지」면 **Pipes**, 「다수 → 다수」면 **이벤트 버스**입니다.
- 「새로 이벤트 기반을 설계한다」면 공식 권고는 **`Custom Event Bus`로 시작**입니다.
- 「조직 전체 계정에 걸쳐 직원 액세스」면 **Identity Center**, 「단일 계정 + 머신 사용자」면 **IAM 페더레이션**, 「앱 사용자」면 **Cognito ID 풀**입니다.
- 「GitHub Actions가 AWS를 부른다」면 **OIDC**입니다.
- 「서비스 계정용 정책을 최소화」면 **콘솔 권한을 빼고 API 액션만** 둡니다.
- 「온프레미스 데이터를 리전으로 못 옮긴다」면 **Outposts**, 「모바일 사용자 지연」이면 **Wavelength**입니다.
- 「Outpost 두 대를 같은 VPC에서 잇는다」는 **안 됩니다.**
- 「컴퓨팅 랙이 네 개」면 **ACE 랙이 필수**입니다.
- 「배포가 왜 건너뛰어졌나」면 **스테이지 잠금과 대체(`Superseded`)**를 봅니다.
- 「파이프라인에 사람 승인을 넣는다」면 **`approval` 액션 유형**입니다.
- 「모델 접근을 한 지점으로 모으고 제어·관찰」이면 **GenAI 게이트웨이**이고, 제어는 **도구 접근 전** 평가입니다.

## ⚠️ 흔한 함정 {#pitfalls}

- ⚠️⚠️ **재시도가 영원히 계속된다고 생각하기.** **24시간·185회**로 끝나고 **드롭**됩니다.
- ⚠️ **DLQ 없이 중요한 이벤트를 흘리기.** 유실을 막는 공식 수단입니다.
- ⚠️ **규칙 하나에 대상을 여섯 개 이상 두려 하기.** **최대 다섯 개**입니다.
- ⚠️ **패턴이 안 맞는데 오류를 기대하기.** **아무 일도 일어나지 않습니다.**
- ⚠️ **Pipes를 다수 → 다수 라우터로 쓰려 하기.** **점대점**입니다.
- ⚠️⚠️ **새 설계에 Classic 버스 모델을 기본으로 고르기.** 공식은 **`Custom Event Bus`로 시작**하라고 적습니다.
- ⚠️ **사람 사용자용 IAM 사용자를 만들기.** 모범 사례는 **페더레이션**입니다.
- ⚠️⚠️ **Identity Center를 단일 계정 용도로 전제하기.** 그 유형은 **Organizations의 여러 계정**용입니다.
- ⚠️ **머신 사용자를 Identity Center로 다루려 하기.** 그 칸은 **IAM 페더레이션**입니다.
- ⚠️⚠️ **서비스 계정에 콘솔 최소 권한까지 붙이기.** CLI·API만 부르면 **필요 없습니다.**
- ⚠️ **관리형 정책에서 멈추기.** 공식은 **고객 관리형 정책으로 좁히라**고 적습니다.
- ⚠️⚠️ **Outposts와 Wavelength를 같은 축으로 보기.** **고객 사업장 ↔ 통신사 네트워크 엣지**입니다.
- ⚠️ **Wavelength에서 모델 추론을 직접 돌리려 하기.** 거기서 돌리는 것은 **EC2·컨테이너**이고 추론은 **부모 리전**입니다.
- ⚠️ **Outposts 서버에 로컬 게이트웨이를 기대하기.** 서버는 **로컬 네트워크 인터페이스**입니다.
- ⚠️⚠️ **스테이지가 동시에 여러 실행을 처리한다고 생각하기.** **하나씩**이고 **잠깁니다**.
- ⚠️ **비활성 전환에 쌓인 실행이 모두 순서대로 간다고 생각하기.** **최신 하나만** 계속합니다.
- ⚠️ **게이트웨이의 제어가 도구 호출 뒤에 돈다고 생각하기.** **접근 전에** 평가합니다.

## 🧪 자가 점검

**Q1.** 주문 이벤트로 GenAI 요약을 만드는 파이프라인에서 요약이 간헐적으로 누락됩니다. 어디를 보고 무엇을 추가합니까?

<details><summary>정답 보기</summary>

**재시도 소진 후 드롭**을 봅니다. EventBridge 기본값은 **24시간 · 최대 185회 · 지수 백오프 + 지터**이고 ⚠️⚠️ **모두 소진되면 이벤트가 드롭되고 더 처리되지 않습니다.** 추가할 것은 **DLQ**로, 실패 이벤트를 전부 받아 둡니다. 그리고 재시도가 기본 185회라는 사실 자체가 **멱등성 요구**가 됩니다 — 같은 이벤트가 두 번 처리돼도 안전해야 합니다.
</details>

**Q2.** 「CRM 한 곳의 변경을 받아 강화한 뒤 하나의 분석 대상으로 보낸다」와 「주문 이벤트를 다섯 팀이 각자 구독한다」는 각각 무엇으로 구현합니까?

<details><summary>정답 보기</summary>

앞은 **EventBridge Pipes**입니다 — **점대점 통합용**이고 **단일 소스 → 단일 대상**이며 전달 전 **고급 변환과 강화**를 지원합니다. 뒤는 **이벤트 버스**입니다 — **다수 소스 → 다수 대상** 라우팅에 맞고 **이벤트가 여러 규칙에 일치**할 수 있으며 **각 규칙은 최대 다섯 개 대상**을 지정합니다. ⚠️ 새로 설계한다면 공식 권고는 **`Custom Event Bus`로 시작**하는 것입니다(리플레이용 보존 + 소비자가 만드는 구독자).
</details>

**Q3.** 조직에 Active Directory가 있고 여러 AWS 계정의 직원 액세스를 관리해야 합니다. 어떤 페더레이션 유형이고, 같은 조직에서 GitHub Actions가 AWS를 부르는 경우는 무엇입니까?

<details><summary>정답 보기</summary>

전자는 **IAM Identity Center 페더레이션**입니다 — **Organizations가 관리하는 여러 계정**의 **워크포스 사람 사용자**이고 ID 소스에 **Managed Active Directory**가 듭니다(사용자는 **단기 자격 증명**을 받습니다). 후자는 **IAM 페더레이션의 OIDC**입니다 — 공식이 **「AWS에서 돌지 않는 애플리케이션(예: GitHub Actions)을 AWS 리소스에 연결한다」**로 적습니다. ⭐ 둘 다 **장기 액세스 키를 배포·임베드하지 않는** 것이 이득입니다.
</details>

**Q4.** 배치 추론만 수행하는 서비스 계정의 정책을 최소화하려 합니다. 무엇을 빼고 무엇으로 검증합니까?

<details><summary>정답 보기</summary>

**콘솔 최소 권한을 뺍니다** — 공식이 **「CLI·API만 호출하는 사용자에게는 콘솔 최소 권한이 필요 없고 수행하려는 API 작업에 맞는 액션만 허용한다」**고 적습니다. ⚠️ 반대로 콘솔을 써야 하는 주체에게 그보다 제한적인 정책을 주면 **콘솔이 의도대로 동작하지 않습니다.** 검증은 **IAM Access Analyzer**로 하고(**100개 이상의 정책 검사**와 실행 가능한 권고), 시작은 **AWS 관리형 정책**이지만 **고객 관리형 정책으로 좁히는** 것이 모범 사례입니다.
</details>

**Q5.** 규제로 환자 데이터를 건물 밖으로 낼 수 없는 병원과, 경기장 관중의 모바일 앱 지연을 줄이려는 사업. 각각 무엇을 쓰고 무엇을 확장합니까?

<details><summary>정답 보기</summary>

병원은 **AWS Outposts** — **고객 사업장으로** AWS 인프라·서비스·API·도구를 확장하고 **로컬 컴퓨팅·스토리지로 로컬 데이터 처리**를 합니다(Outpost 서브넷의 인스턴스는 **같은 VPC 안에서 사설 IP로** 리전과 통신합니다). 경기장은 **AWS Wavelength** — **통신사(CSP) 네트워크의 엣지**에 배치하고 **VPC를 Wavelength Zone으로 확장**합니다. ⚠️ Wavelength에서 돌리는 것은 **EC2·컨테이너 워크로드**이고 **모델 추론은 부모 리전**입니다 — 엣지가 줄이는 것은 **사용자와 애플리케이션 사이의 지연**입니다.
</details>

**Q6.** Outposts 랙 네 개로 확장하려 합니다. 반드시 필요한 것과, 서버 폼 팩터와 다른 점은 무엇입니까?

<details><summary>정답 보기</summary>

⚠️ **컴퓨팅 랙이 4개 이상이면 ACE 랙을 반드시 설치**해야 합니다(다중 랙 배포의 **네트워크 집계 지점**으로 물리 포트·논리 인터페이스 요구를 줄입니다). 4개 미만이어도 장차 확장 계획이 있으면 **조기 설치를 권장**합니다. 폼 팩터 차이는 **온프레미스 연결 수단**입니다 — **랙은 로컬 게이트웨이(LGW)**, **서버는 로컬 네트워크 인터페이스**입니다. ⚠️ 그리고 **같은 VPC 안의 다른 Outpost나 Local Zone에는 연결할 수 없습니다.**
</details>

**Q7.** 두 변경을 연달아 푸시했는데 앞의 것이 배포되지 않고 사라졌습니다. CodePipeline의 어떤 동작입니까?

<details><summary>정답 보기</summary>

**스테이지 잠금과 대체**입니다. ⚠️⚠️ **파이프라인은 여러 실행을 동시에 처리하지만 스테이지는 한 번에 하나만** 처리하며 처리 중에는 **잠깁니다.** 기다리는 **인바운드 실행**은 **대체(`Superseded`)**될 수 있고, 특히 **전환이 비활성화된 상태에 여러 실행이 도착하면 활성화 시 가장 최신 실행만 계속**합니다. 실패 시에는 스테이지가 **잠금 해제**되어 더 최신 실행이 따라잡아 들어올 수 있습니다.
</details>

**Q8.** 여러 팀이 각자 코드로 FM과 사내 도구를 부르고 있어 접근 통제와 지표가 흩어졌습니다. 「중앙 집중식 추상화 계층」이 모으는 것 셋은 무엇입니까?

<details><summary>정답 보기</summary>

**추상화 · 제어 · 관찰성**입니다. 추상화는 API·Lambda·기존 서비스를 **MCP 호환 도구로 변환**해 **한 엔드포인트 뒤로** 모으고(인그레스·이그레스 인증 모두 제공), 제어는 정책 엔진을 붙여 **도구 접근 전에** 모든 요청을 평가하며(⭐ 보안 제어가 **에이전트 코드 밖으로** 나갑니다), 관찰성은 **도구별 호출 수·성공률·유형별 오류율·지연 백분위수**를 추적하고 **복합 알람**으로 묶습니다. 소비 통제로 **분당 토큰(TPM)**과 **동시 연결 수**도 제한합니다.
</details>
