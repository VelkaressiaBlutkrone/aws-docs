# 프롬프트 엔지니어링 전략과 거버넌스 (지침 프레임워크·대화 컨텍스트·버전과 감사·품질 보증·반복 개선·프롬프트 체인)

> **커버하는 공식 Task** — AIP-C01 · 도메인 1 「파운데이션 모델 통합, 데이터 관리 및 규정 준수」(31%) · **작업 1.6 FM 상호 작용을 위한 프롬프트 엔지니어링 전략 및 거버넌스 구현** (`aip-t1-6`)
> 이 문서는 위 한 작업에 1:1로 매핑되고 공식 기술 6개(1.6.1~1.6.6)를 모두 덮습니다. 이 작업의 절반은 **프롬프트를 잘 쓰는 법**이 아니라 **프롬프트를 자산으로 관리하는 법**입니다 — 버전·승인·감사·회귀 테스트가 전부 여기 있습니다.

---

## ✅ 학습 목표 체크리스트

- [ ] Prompt management의 **변수·변형·버전**을 구분할 수 있다
- [ ] 프롬프트를 애플리케이션에 **통합하는 두 경로**를 안다
- [ ] Guardrails가 제공하는 **보호 장치의 종류**를 안다(개수는 외우지 않는다)
- [ ] 의도 인식에 **Comprehend 사용자 지정 분류**를 쓸 수 있다
- [ ] 프롬프트 거버넌스를 **CloudTrail ↔ 호출 로깅**으로 가를 수 있다
- [ ] 버전 비교로 **회귀 테스트**를 어떻게 하는지 안다
- [ ] 프롬프트 최적화의 **적용 한계**를 안다
- [ ] Flows의 노드로 **조건부 분기와 재사용**을 설명할 수 있다

---

## 🎯 왜 중요한가

프롬프트는 코드처럼 **배포되고 깨지고 되돌려집니다.** 그런데 많은 조직이 프롬프트를 소스 코드 문자열이나 위키에 둡니다. 그러면 **누가 언제 무엇을 바꿨는지**, **어느 버전이 운영에 있는지**, **바꾼 뒤 품질이 떨어졌는지**를 알 수 없습니다.

공식 기술 본문이 「파라미터화된 템플릿 및 승인 워크플로」·「사용 추적」·「액세스 기록」·「프롬프트 회귀 테스트」를 나란히 적는 것은 그래서입니다. 시험은 **「좋은 프롬프트의 문장」을 묻지 않고 「프롬프트를 운영 자산으로 다루는 수단」**을 묻습니다.

---

## ⚡ 시험 직전 요약

- **Prompt management**는 프롬프트를 만들고 저장해 **여러 워크플로에 재사용**한다. **변수**로 유연성을 주고 **변형(variants)**을 비교해 고르고 **버전**을 저장한다.
- ⚠️ **버전은 1부터 증분**으로 만들어진다(`CreatePromptVersion`).
- 애플리케이션 통합 경로는 **둘** — ① 모델 추론 시 **프롬프트를 지정** ② **플로에 프롬프트 노드를 추가**.
- 버전 비교는 콘솔이 **두 버전의 JSON을 나란히** 보여 주고 `+`(초록)·`-`(빨강)로 표시하며 ⭐ **테스트 변수를 채워 두 버전의 응답까지 비교**한다 — 이것이 회귀 테스트의 기본 수단이다.
- ⚠️⚠️ **단순 프롬프트 최적화는 「한 모델 · 짧은 프롬프트 하나」의 휴리스틱 재작성**이고 **평가 데이터를 쓰지 않으며 여러 모델을 지원하지 않는다**(약 **1k 토큰 이하**에서 가장 잘 동작 · **영어 권장**). 평가 주도 최적화는 **Advanced Prompt Optimization**이 따로 있다.
- **Guardrails**는 콘텐츠 필터 · 거부 주제 · 단어 필터 등을 제공한다. ⚠️ **단어 필터는 대소문자를 구분하지 않는 전체 단어·구 일치**다.
- 의도 인식은 **Comprehend 사용자 지정 분류**로 한다 — **분류기 훈련 → 분류**의 2단계이고 **동기(실시간)·비동기** 둘 다 된다.
- ⚠️⚠️ **분석할 문서 유형으로 훈련한 모델이 가장 정확하다**(평문용 모델 ↔ 네이티브 문서용 모델).
- 거버넌스 둘을 가른다 — **CloudTrail**은 **누가 어떤 API를 불렀는지**, **모델 호출 로깅**은 **요청·응답 본문**이다. ⚠️ 후자는 **기본이 꺼져 있다**.
- Flows의 **조건 노드**는 ⚠️⚠️ **조건을 순서대로 평가하고 둘 이상 만족하면 앞 조건이 우선**한다.

## 🔤 먼저 알아야 할 용어

| 용어 | 뜻 |
|---|---|
| **변수(variable)** | 프롬프트 안에서 호출 시점에 값이 채워지는 자리 |
| **변형(variant)** | 같은 프롬프트의 다른 구성(모델·파라미터·문구) — 비교해서 고른다 |
| **버전(version)** | 만족스러운 구성의 **스냅샷**. 1부터 증분 |
| **플로(flow)** | 노드를 연결해 만드는 GenAI 워크플로. 프롬프트를 노드로 넣는다 |
| **생각의 사슬** | 모델에게 추론 단계를 드러내게 하는 지시 패턴 |
| **사용자 지정 분류** | 내가 정의한 클래스로 문서를 분류하도록 훈련한 Comprehend 모델 |

## 📖 핵심 개념

### 1) 모델 지침 프레임워크 (기술 1.6.1) {#instructions}

> 🧠 원리: 「모델이 이렇게 행동하게 하라」는 요구는 **세 층**에서 구현됩니다 — **프롬프트**(역할·형식), **가드레일**(해도 되는 것의 경계), **템플릿**(일관성). 한 층으로 다 하려 하면 깨집니다.

**Prompt management**가 맡는 층: 역할 정의와 응답 형식을 **프롬프트 자산**으로 고정합니다.

- 프롬프트를 만들 때 **모델을 고르고 추론 파라미터를 수정**합니다.
- **변수**를 넣어 같은 프롬프트를 **다른 사용 사례에 맞게** 조정합니다.
- 테스트할 때 **변형을 비교**해 내 사용 사례에 가장 맞는 것을 고릅니다.
- ⭐ 공식 워크플로는 네 단계입니다 — ① 재사용할 프롬프트 생성(변수 포함) ② **모델·추론 프로필·에이전트** 중에서 추론 대상 선택과 추론 구성 ③ 테스트 값으로 실행하고 **변형 비교** ④ 애플리케이션 통합.

**Guardrails**가 맡는 층: 입력 프롬프트와 모델 응답에서 **원하지 않는 콘텐츠를 탐지·필터**하고 민감 정보를 보호합니다.

- **콘텐츠 필터** — 유해 텍스트·이미지를 사전 정의된 범주로 탐지하고 **범주마다 필터 강도를 구성**합니다. ⚠️ **Standard 계층**은 탐지를 **코드 요소 안**(주석·변수·함수 이름·문자열 리터럴)까지 확장합니다.
- **거부 주제** — 애플리케이션 맥락에서 원하지 않는 주제를 정의해 차단합니다.
- **단어 필터** — 차단할 단어·구를 직접 정의합니다. ⚠️ **대소문자를 구분하지 않는 전체 단어·전체 구 일치**입니다(부분 문자열이 아닙니다).
- ⛔ **유해 범주의 개수는 묻지 않습니다** — 공식 문서 안에서 열거가 갈리는 자리입니다. 이름과 **구성 가능하다는 성질**을 봅니다.
- ⚠️ 가드레일의 세부(계층·PII·문맥 근거 확인 등)는 **도메인 3**이 다룹니다. 여기서는 **「책임 있는 AI 지침을 적용하는 수단」**으로 압니다.

### 2) 대화 컨텍스트를 유지한다 (기술 1.6.2) {#conversation}

> 🧠 원리: 대화형 시스템에서 어려운 것은 생성이 아니라 **상태**입니다. 공식 기술이 드는 셋이 그 상태를 나눠 맡습니다.

| 수단 | 맡는 일 |
|---|---|
| **Step Functions** | 설명·확인을 주고받는 **워크플로의 단계와 분기** |
| **Amazon Comprehend** | **의도 인식** — 들어온 발화가 어느 범주인지 |
| **DynamoDB** | **대화 기록 저장** — 세션을 넘어 남는 상태 |

**의도 인식은 Comprehend 사용자 지정 분류**로 합니다(공식):

- **2단계**입니다 — ① 관심 있는 **클래스를 인식하도록 분류기를 훈련**하고 ② 그 모델로 문서를 분류합니다.
- **단일 문서를 동기(실시간)로** 분류하거나 **문서 집합을 비동기 작업**으로 분류합니다. 계정에 **분류기를 여럿** 둘 수 있습니다.
- 입력 유형이 다양합니다 — **평문 · PDF · Word · 이미지**.
- ⚠️⚠️ **분석할 문서 유형으로 훈련한 모델이 가장 정확합니다.** 평문을 분석하려면 평문으로 훈련한 모델, 반정형 문서(PDF·Word·이미지·Textract 출력·스캔 파일)를 분석하려면 **네이티브 문서로 훈련한 모델**을 씁니다.
- ⭐ 공식이 드는 용례가 이 자격증과 이어집니다 — **지원 요청 콘텐츠를 분류해 적절한 팀으로 라우팅**하고, **Transcribe와 결합**해 전화 지원 요청을 텍스트로 바꾼 뒤 분류합니다(작업 1.3의 Transcribe와 짝입니다).
- ⚠️ **Comprehend의 프롬프트 안전 분류는 유지 관리 상태**입니다(작업 1.3 참조) — 의도 인식에는 **사용자 지정 분류**를 씁니다.

### 3) 프롬프트 관리와 거버넌스 (기술 1.6.3) {#governance}

> 🧠 원리: 거버넌스는 **「무엇을 남기는가」**입니다. 공식 기술이 드는 네 수단이 서로 **다른 것을 남깁니다** — 섞으면 감사 요구를 못 맞춥니다.

| 수단 | 남기는 것 |
|---|---|
| **Prompt management** | **파라미터화된 템플릿**과 **버전** — 무엇이 승인된 구성인가 |
| **Amazon S3** | **템플릿 리포지토리** — 조직의 프롬프트 자산 보관 |
| **AWS CloudTrail** | **사용 추적** — 누가 어떤 **API**를 불렀는가 |
| **Amazon CloudWatch Logs** | **액세스 기록** — 호출의 **요청·응답 본문**(모델 호출 로깅) |

공식 사실로 가릅니다:

- **CloudTrail**은 Bedrock API 호출을 이벤트로 기록합니다. `InvokeModel` · `InvokeModelWithResponseStream` · `Converse` · `ConverseStream` · `ListAsyncInvokes`는 **관리 이벤트**로 남고, 그 밖의 Runtime API는 **데이터 이벤트**입니다. ⚠️ **데이터 이벤트는 대용량이라 기본으로 기록되지 않습니다.**
- **모델 호출 로깅**은 **전체 요청·응답 데이터와 메타데이터**를 S3 또는 CloudWatch Logs로 보냅니다. ⚠️⚠️ **기본이 비활성**이고, 켜면 **로깅 구성을 삭제할 때까지** 저장됩니다. 대상은 **같은 계정·같은 리전**만 지원합니다.
- ⚠️ 「누가 프롬프트를 바꿨는가」는 **CloudTrail**, 「그 프롬프트가 무엇을 받고 무엇을 냈는가」는 **모델 호출 로깅**입니다.

⭐ **버전이 승인 워크플로의 축입니다** — 버전은 **1부터 증분**으로 만들어지고, 애플리케이션은 **버전을 지정해** 배포합니다. 그래서 「승인된 버전만 운영에 둔다」와 「문제가 생기면 이전 버전을 가리킨다」가 성립합니다.

### 4) 품질 보증 (기술 1.6.4) {#qa}

> 🧠 원리: 프롬프트 변경은 **배포**입니다. 배포에는 **테스트와 회귀 감지**가 붙어야 합니다.

공식 기술이 드는 셋과 그 자리:

| 수단 | 하는 일 |
|---|---|
| **Lambda 함수** | **예상 출력 확인** — 결정적 검사(스키마·형식·금지 문구) |
| **Step Functions** | **엣지 케이스 테스트** — 입력 묶음을 순서·분기로 돌린다 |
| **CloudWatch** | **프롬프트 회귀 테스트** — 지표로 추세를 본다 |

⭐ **Prompt management의 버전 비교**가 손에 잡히는 회귀 수단입니다 — 콘솔이 **두 버전의 JSON을 나란히** 보여 주고 한쪽에만 있는 필드를 **`+`(초록)·`-`(빨강)**로 표시하며, **테스트 변수를 채워 `Run prompt`로 두 버전의 모델 응답을 비교**합니다.

⚠️ **의미 평가가 필요한 자리는 이 작업이 아닙니다** — 출력 품질을 점수로 재는 것은 **도메인 5**(평가 시스템)이고, 여기서는 **결정적 검사와 변경 감지**까지입니다.

### 5) 반복적으로 개선한다 (기술 1.6.5) {#iterate}

> 🧠 원리: 「프롬프트를 더 잘 쓴다」를 **반복 가능한 절차**로 바꾸는 것이 이 기술입니다. 공식 기술이 드는 넷이 그 절차입니다 — **구조화된 입력 구성 요소 · 출력 형식 사양 · 생각의 사슬 명령 패턴 · 피드백 루프**.

AWS가 제공하는 자동 수단은 **프롬프트 최적화**이고, **한계가 분명합니다**:

- **단순 프롬프트 최적화**는 **한 모델에 대한 짧은 프롬프트 하나의 빠른 휴리스틱 재작성**입니다.
- ⚠️ **약 1k 토큰 이하**의 프롬프트에서 가장 잘 동작합니다.
- ⚠️⚠️ **평가 데이터를 쓰지 않고 여러 모델을 지원하지 않습니다.** 평가가 재작성을 여러 모델에 걸쳐 끌고 가는 **평가 주도 최적화**는 **Advanced Prompt Optimization**이라는 **다른 기능**입니다.
- 동작은 둘 — 프롬프트 **구성 요소를 분석**하고, 성공하면 **재작성**합니다. 결과 텍스트를 **복사해 씁니다**.
- ⚠️ 공식 Note: **영어로 최적화할 것을 권합니다.**
- ⚠️ 지원 모델과 리전이 표로 정해져 있습니다 — ⛔ **모델 목록은 개정되므로 외우지 않습니다.**

### 6) 복잡한 프롬프트 시스템 (기술 1.6.6) {#flows}

> 🧠 원리: 프롬프트 하나로 안 되는 작업은 **여러 프롬프트를 순서와 조건으로 잇습니다.** 그 연결을 서비스로 하는 것이 플로입니다.

⚠️ **표기를 먼저 맞춥니다** — 공식 시험 가이드는 **`Amazon Bedrock Prompt Flows`**로 적는데 **현행 공식 문서의 이름은 `Amazon Bedrock Flows`**이고, Bedrock 사용자 안내서 목차에 구 표기가 **없습니다**. ⛔ 이 사이트는 **개명을 사실로 단정하지 않고** 현행 표기를 씁니다.

**Flows 동작 방식**: 노드를 연결해 워크플로를 만들고, **표현식으로 입력을 어떻게 해석할지** 정의합니다. 노드 구성은 **이름 · 유형 · 입력(이름·표현식·유형) · 출력 · 구성**이고 ⭐ **런타임에 표현식을 적용한 뒤 데이터 유형이 맞는지 Bedrock이 검증**합니다.

노드는 두 갈래입니다:

| 갈래 | 노드 |
|---|---|
| **플로 논리 제어** | **플로 입력**(⚠️ **정확히 하나이고 반드시 여기서 시작**) · **플로 출력**(⭐ **분기가 있으면 여러 개 가능**) · **조건** · **반복자(Iterator)** · **수집기(Collector)** · **DoWhile 루프** |
| **데이터 처리** | **프롬프트** · **에이전트** · **지식 베이스** · **S3 저장** · **S3 검색** · **Lambda 함수** · **인라인 코드** · **Lex** |

**조건 노드**(기술 본문의 「조건부 분기」):

- 입력마다 이름·유형·표현식을 주고 **업스트림 노드의 출력에 연결**합니다.
- 조건은 관계·논리 연산자로 정의합니다 — `==` · `!=`(문자열·숫자·불리언) · `>` · `>=` · `<` · `<=`(⚠️ **숫자만**).
- ⚠️⚠️ **조건은 순서대로 평가되고, 둘 이상이 만족되면 앞 조건이 우선합니다.** 이것을 모르면 「왜 두 번째 분기가 안 타지?」를 영원히 디버깅합니다.

**재사용 가능한 프롬프트 구성 요소**: Prompt management의 프롬프트를 **프롬프트 노드로 넣습니다**(§1의 통합 경로 ②). 그래서 한 프롬프트를 고치면 **그것을 쓰는 플로들이 함께** 바뀝니다 — 그것이 「재사용」의 실체이고, 동시에 **버전을 고정해야 하는 이유**입니다.

**통합 전처리·후처리**는 **Lambda 함수 노드**와 **인라인 코드 노드**가 맡습니다. 플로는 **불변 워크플로로 배포**해 테스트에서 운영으로 옮깁니다.

## ✍️ 시험 포인트

- 「프롬프트를 여러 워크플로에 재사용」이면 **Prompt management**이고, 통합은 **추론 시 지정** 또는 **프롬프트 노드**입니다.
- 「프롬프트를 고쳤는데 품질이 떨어졌다」면 **버전 비교**(JSON + 응답 비교)가 첫 수단입니다.
- 「짧은 프롬프트 하나를 빨리 다듬자」면 **단순 최적화**, 「평가로 여러 모델에 걸쳐」면 **Advanced**입니다.
- 「누가 프롬프트를 바꿨나」는 **CloudTrail**, 「무엇을 주고받았나」는 **모델 호출 로깅**(기본 꺼짐)입니다.
- 「발화를 범주로 가른다」면 **Comprehend 사용자 지정 분류**이고, **문서 유형에 맞춰 훈련**해야 합니다.
- 「조건 두 개가 다 맞는데 하나만 탄다」면 **앞 조건 우선**이 정답입니다.
- 「플로 출력이 여러 개여도 되나」는 **분기가 있으면 된다**입니다. **플로 입력은 하나뿐**입니다.

## ⚠️ 흔한 함정 {#pitfalls}

- ⚠️⚠️ **단순 프롬프트 최적화가 평가 기반이라고 생각하기.** 평가 데이터를 쓰지 않고 **한 모델**만 봅니다.
- ⚠️ **긴 프롬프트를 단순 최적화에 넣기.** **약 1k 토큰 이하**에서 가장 잘 동작합니다.
- ⚠️ **단어 필터를 부분 문자열 차단으로 생각하기.** **전체 단어·전체 구 일치**(대소문자 무시)입니다.
- ⚠️ **Guardrails의 유해 범주 개수를 외우기.** 공식 안에서 열거가 갈립니다.
- ⚠️⚠️ **모델 호출 로깅이 기본으로 켜져 있다고 생각하기.** 꺼져 있습니다.
- ⚠️ **CloudTrail로 프롬프트 본문을 찾기.** 본문은 **모델 호출 로깅**입니다.
- ⚠️⚠️ **평문으로 훈련한 분류기로 스캔 PDF를 분류하기.** **문서 유형에 맞춘 모델**이 가장 정확합니다.
- ⚠️ **프롬프트 안전 분류를 새 설계에 쓰기.** **유지 관리 상태**입니다.
- ⚠️⚠️ **조건 노드의 평가 순서를 모르고 설계하기.** **앞 조건이 우선**합니다.
- ⚠️ **플로 입력 노드를 여러 개 두려 하기.** **정확히 하나**입니다.

## 🧪 자가 점검

**Q1.** 프롬프트를 운영에 통합하는 공식 경로 두 가지는 무엇입니까?

<details><summary>정답 보기</summary>

**① 모델 추론을 실행할 때 프롬프트를 지정**하고, **② 플로에 프롬프트 노드를 추가해 그 프롬프트를 지정**합니다. 공식 Prompt management 워크플로의 4단계 중 마지막이고, Prompt management 문서는 **「프롬프트를 Amazon Bedrock Flows의 도움으로 애플리케이션에 통합한다」**고 적습니다.
</details>

**Q2.** 프롬프트를 고친 뒤 응답 품질이 떨어졌습니다. 콘솔에서 가장 먼저 쓸 수단은 무엇이고 무엇을 보여 줍니까?

<details><summary>정답 보기</summary>

**Prompt management의 버전 비교**입니다. 두 버전의 **JSON을 나란히** 보여 주고 한쪽에만 있는 필드를 **`+`(초록)·`-`(빨강)**로 표시합니다. ⭐ 그리고 **테스트 변수를 채워 `Run prompt`로 두 버전의 모델 응답까지 비교**할 수 있습니다. 버전은 **1부터 증분**으로 만들어집니다.
</details>

**Q3.** 「프롬프트 최적화로 평가 데이터를 넣어 세 모델에 맞게 다듬자」는 계획의 문제는 무엇입니까?

<details><summary>정답 보기</summary>

**단순 프롬프트 최적화는 평가 데이터를 쓰지 않고 여러 모델을 지원하지 않습니다** — 한 모델에 대한 **짧은 프롬프트 하나의 휴리스틱 재작성**이고 **약 1k 토큰 이하**에서 가장 잘 동작합니다. 평가가 재작성을 여러 모델에 걸쳐 끌고 가는 것은 **Advanced Prompt Optimization**이라는 **다른 기능**입니다. ⚠️ 공식은 **영어로 최적화**할 것을 권합니다.
</details>

**Q4.** 감사 팀이 「지난달 프롬프트 템플릿을 누가 수정했고, 그 프롬프트가 받은 입력과 낸 출력을 보여 달라」고 합니다. 각각 무엇을 씁니까?

<details><summary>정답 보기</summary>

**「누가 수정했나」는 CloudTrail**(API 호출 이벤트), **「무엇을 받고 냈나」는 모델 호출 로깅**(전체 요청·응답·메타데이터 → S3 또는 CloudWatch Logs)입니다. ⚠️⚠️ **모델 호출 로깅은 기본이 꺼져 있으므로**, 켜 두지 않았다면 **지난달 본문은 없습니다.** 그리고 대상은 **같은 계정·같은 리전**만 지원합니다.
</details>

**Q5.** 고객 지원 전화를 텍스트로 바꾼 뒤 의도별로 라우팅하려 합니다. 어떤 Comprehend 기능이고 훈련 데이터에서 주의할 점은 무엇입니까?

<details><summary>정답 보기</summary>

**사용자 지정 분류**입니다 — 분류기를 **훈련**한 뒤 문서를 분류하는 2단계이고, 공식이 **Transcribe와 결합해 전화 지원 요청을 분류하는 용례**를 직접 듭니다. ⚠️⚠️ 주의점은 **분석할 문서 유형으로 훈련한 모델이 가장 정확하다**는 것입니다(평문이면 평문으로, 반정형 문서면 네이티브 문서로). ⚠️ **프롬프트 안전 분류는 유지 관리 상태**라 의도 인식에 새로 고르지 않습니다.
</details>

**Q6.** 플로에서 조건 A와 조건 B가 모두 참인데 항상 A 분기만 실행됩니다. 왜입니까?

<details><summary>정답 보기</summary>

⚠️⚠️ **조건은 순서대로 평가되고 둘 이상이 만족되면 앞 조건이 우선**합니다(공식 Note). 설계 의도가 「둘 다 처리」라면 조건을 **상호 배타적으로** 다시 쓰거나 분기 구조를 바꿔야 합니다. 참고로 `>`·`>=`·`<`·`<=`는 **숫자 전용**이고 `==`·`!=`는 문자열·숫자·불리언에 쓸 수 있습니다.
</details>

**Q7.** 플로에 출력 노드를 두 개 두었습니다. 유효합니까? 입력 노드는 어떻습니까?

<details><summary>정답 보기</summary>

**출력 노드는 분기가 여러 개면 여러 개 둘 수 있습니다**(유효합니다). ⚠️ 반면 **플로 입력 노드는 정확히 하나**이고 **플로는 반드시 그 노드에서 시작**합니다. 입력 노드는 `InvokeFlow` 요청의 `content`를 받아 **데이터 유형을 검증**한 뒤 다음 노드로 보냅니다.
</details>
