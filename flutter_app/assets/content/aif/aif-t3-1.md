# FM 애플리케이션의 설계 고려 사항 (모델 선택 기준·추론 파라미터·RAG·벡터 저장소·사용자 지정 비용 절충·AI 에이전트)

> **커버하는 공식 Task** — AIF-C01 · 도메인 3 「파운데이션 모델의 적용」(28%) · **작업 3.1 파운데이션 모델(FM)을 사용하는 애플리케이션의 설계 고려 사항 설명** (`aif-t3-1`)
> 이 문서는 위 한 작업에 1:1로 매핑되고 공식 목표 6개(3.1.1~3.1.6)를 모두 덮습니다. 도메인 3은 **전체의 28%로 가장 큰 도메인**이고, 그 첫 작업인 3.1은 **"무엇을 고를 것인가"**를 묻습니다.

> ⚠️ **가이드 v1.1에서 바뀐 것** — 목표 **3.1.5**의 사용자 지정 접근 방식 목록에 **모델 증류**가 추가됐습니다. 그리고 목표 **3.1.6**은 v1.0의 "다단계 작업에서 에이전트의 역할 설명(예: Amazon Bedrock Agent, 에이전틱 AI, 모델 컨텍스트 프로토콜)"에서 **서비스 예시가 모두 삭제**되고 **"AI 에이전트의 역할을 정의하고 AI 에이전트의 비즈니스 애플리케이션을 설명"**으로 바뀌었습니다. 이 변화의 방향이 중요합니다 — 서비스 이름은 도메인 2·5로 옮겨 갔고, 도메인 3은 **역할과 비즈니스 적용**만 묻습니다.

## 🎯 왜 중요한가

도메인 3은 **28%로 다섯 도메인 중 가장 큽니다.** 그런데 3.1은 **FM을 만드는 법이 아니라 고르는 법**을 묻습니다. 공식 의사 결정 가이드가 이 작업의 성격을 한 줄로 요약합니다 — 생성형 AI 서비스를 정한 다음 **"사용 사례에 가장 좋은 결과를 주는 파운데이션 모델을 고른다"**는 것이고, 그 뒤에 **"적절한 FM을 고를 때 고려할 결정적 요소들"**이 나열됩니다.

이 작업의 문항은 거의 전부 **절충(trade-off)** 문항입니다. "가장 좋은 모델"을 고르게 하지 않고, 지문에 **지연 요구 · 예산 · 데이터 보유 상황 · 지식의 신선도** 같은 제약을 심어 두고 그 제약에 맞는 것을 고르게 합니다. 그래서 각 선택지가 **무엇을 포기하는지**를 아는 쪽이 이름을 외우는 쪽보다 빠릅니다.

> `aif-t2-2` 3절이 목표 2.2.3의 **다섯 축**(모델 유형 · 성능 요구 · 기능 · 제약 · 규정 준수)을 다뤘습니다. 3.1.1은 같은 결정을 **더 구체적인 기술 축**으로 쪼갭니다. 모달리티·모델 크기·지연·컨텍스트 윈도·요금·응답 품질은 거기서 이미 본 것이니, 여기서는 **다국어 · 모델 복잡도 · 입출력 길이 · 사용자 지정 가능성 · 프롬프트 캐싱**에 분량을 씁니다.

## ⚡ 시험 직전 요약

> 시험 직전에 이 열 줄만 다시 봅니다. 근거와 맥락은 아래 본문에 있습니다.

- **모델 선택은 "가장 큰 모델"이 아닙니다** — 공식은 파라미터가 많으면 성능이 좋아지는 경향이지만 **훈련이 비싸고 운영에 더 많은 연산 자원이 필요**하고 **추론이 느려질 수 있다**고 적습니다
- **모델별 사양표가 선택 기준의 실물입니다** — AWS가 모델마다 문서로 적는 것이 **입력·출력 모달리티 · 컨텍스트 윈도 · 최대 출력 토큰 · 지원 언어 · 미세 조정 가능 여부 · 프로비저닝된 처리량 지원 여부**입니다
- **온도는 분포의 모양을 바꿉니다** — 낮으면 분포가 **뾰족해져 결정론적**, 높으면 **평평해져 무작위적**입니다. 공식 API 문서는 낮은 예로 0.2~0.3, 높은 예로 0.8~0.9를 듭니다
- **Top K는 개수, Top P는 비율**입니다 — K=50은 가장 가능성 높은 **50개 토큰**, P=0.8은 누적 확률 분포의 **상위 80%**
- ⚠️ **입출력 길이는 무작위성 파라미터가 아닙니다** — 공식은 파라미터를 **「무작위성과 다양성」**과 **「길이」** 두 범주로 나눕니다. `max_tokens`는 **출력** 토큰 상한이고, 중단 시퀀스는 그 문자열이 생성되면 **거기서 멈춥니다**
- **RAG의 정의 한 줄** — **"응답을 생성하기 전에 훈련 데이터 소스 밖의 권위 있는 지식 기반을 참조하게 LLM 출력을 최적화하는 과정"**이고, 결정적으로 **"모델을 재훈련할 필요 없이"** 도메인에 맞춥니다
- **벡터 저장소는 검색 성격으로 갈립니다** — 하이브리드(키워드+의미) → OpenSearch · **그래프 기반(GraphRAG)** → Neptune Analytics · **SQL과 벡터를 함께** → Aurora PostgreSQL(pgvector). `Amazon RDS for PostgreSQL`도 **같은 pgvector 확장**을 씁니다
- **공식 사다리는 싼 것부터입니다** — **프롬프트 엔지니어링 → RAG → 지속적인 사전 훈련·미세 조정 → 사용자 지정 FM 구축**. 공식은 **"가장 자원이 덜 드는 선택지부터 시작하라"**고 적고, 마지막을 **"자원과 비용이 통상 가장 높은 선택지"**로 부릅니다
- ⚠️ **미세 조정은 레이블 데이터가 있을 때만 후보입니다** — 공식 조건에 **"작업에 관련된 레이블 데이터를 보유"**가 들어갑니다. 레이블이 없다면 **지속적인 사전 훈련**(비레이블 데이터)이나 RAG 쪽입니다
- ⚠️ **증류는 공짜 절감이 아닙니다** — 데이터 합성 기법이 돌면 **교사 모델 추론 호출이 온디맨드 요율로 추가 과금**되고, 미세 조정 데이터셋이 **최대 15,000개 프롬프트-응답 쌍**까지 커질 수 있습니다

## 🔤 먼저 알아야 할 용어

| 용어 | 뜻 |
|---|---|
| **모달리티(modality)** | 모델이 처리하는 **데이터 종류** — 텍스트 · 이미지(비전) · 임베딩 |
| **파라미터 수** | 모델 내부의 설정 변수 개수. 공식은 **모델 복잡도의 핵심 지표**로 적고 **큰 모델은 흔히 500억 개 이상**이라고 설명합니다 |
| **컨텍스트 윈도** | 응답을 생성할 때 모델이 **한 번에 고려할 수 있는 텍스트 양**(토큰) |
| **최대 출력 토큰** | 한 응답에서 생성할 수 있는 토큰 상한. `max_tokens`는 **내가 요청에 넣어 이 상한을 정하는 파라미터**입니다 |
| **추론 파라미터** | 추론 실행 시 응답에 영향을 주는 설정. 공식 분류는 **「무작위성과 다양성」**과 **「길이」** 두 범주입니다 |
| **임베딩(embedding)** | 텍스트·이미지·오디오를 **의미를 담은 숫자 배열**로 바꾼 표현. 비슷한 항목이 서로 가깝게 놓입니다 |
| **임베딩 모델** | 그 임베딩을 만드는 **파운데이션 모델의 한 종류** |
| **벡터 데이터베이스** | 임베딩을 저장하고 **유사도 검색**을 수행하는 저장소 |
| **RAG** | 검색 증강 생성. 외부 지식에서 관련 내용을 **검색해 프롬프트에 붙여** 응답을 개선하는 기법 |
| **컨텍스트 내 학습(in-context learning)** | 모델 가중치를 **건드리지 않고** 프롬프트 안의 지시·예시만으로 행동을 바꾸는 것 |
| **모델 증류(distillation)** | **교사(크고 유능한 모델)**의 지식을 **학생(작고 빠르고 저렴한 모델)**으로 옮기는 과정 |
| **프로비저닝된 처리량(PT)** | 고정 비용으로 모델의 처리량을 선점하는 것. 과금 축은 **모델 단위(MU) × 시간**입니다 |
| **AI 에이전트** | 공식 정의는 **"환경을 인지하고, 추론하고, 정의된 목표를 달성하기 위해 행동할 수 있는 자율적 개체"** |

## 📖 핵심 개념

### 1) 사전 훈련된 모델을 고르는 아홉 축 (목표 3.1.1) {#model-criteria}

공식 목표가 괄호에 드는 아홉 가지는 **비용 · 모달리티 · 지연 시간 · 다국어 · 모델 크기 · 모델 복잡도 · 사용자 지정 · 입력/출력 길이 · 프롬프트 캐싱**입니다. 외우는 대신 **가르는 질문**으로 바꿔 둡니다.

| 축 | 공식이 적는 것 | 가르는 질문 |
|---|---|---|
| **모달리티** | 모델이 처리하는 데이터 종류(텍스트·이미지·임베딩). **작업 중인 데이터와 맞아야** 합니다 | 내 입력과 출력이 **무엇인가** |
| **모델 크기** | 파라미터 수. **큰 모델은 흔히 500억 개 이상** | 얼마나 복잡한 패턴을 잡아야 하는가 |
| **모델 복잡도** | 파라미터 수가 **복잡도의 핵심 지표**. 복잡하면 성능은 좋아지는 경향이지만 **훈련이 비싸고 운영 연산 자원이 더 든다** | 복잡도의 대가를 치를 수 있는가 |
| **지연 시간** | 입력을 처리해 출력을 반환하는 시간. 대화형·**즉시 번역** 같은 실시간 용례에서 결정적 | 사용자가 **기다리고 있는가** |
| **비용** | FM 비용은 **모델 복잡도와 제공자의 가격 구조**가 정합니다. 작고 자원을 덜 쓰는 모델이 예산 친화적 선택지 | 예산이 이 복잡도를 버티는가 |
| **다국어** | AWS는 모델마다 **지원 언어**를 문서로 적습니다. 예로 Amazon Nova 이해 모델 사양표는 **지원 언어 200개 이상**이고 각주가 **최적화된 15개 언어**(영어·독일어·스페인어·프랑스어·이탈리아어·일본어·**한국어**·아라비아어·중국어 간체·러시아어·힌디어·포르투갈어·네덜란드어·터키어·히브리어)를 따로 적습니다 | **"지원한다"와 "최적화됐다"**가 같은가 |
| **입력/출력 길이** | 같은 사양표가 **컨텍스트 윈도**(입력 쪽)와 **최대 출력 토큰**(출력 쪽)을 **따로** 적습니다 | 긴 문서를 넣는 문제인가, 긴 답을 받는 문제인가 |
| **사용자 지정** | 사양표에 **미세 조정 가능 여부**가 모델마다 다르게 적혀 있습니다 | 이 모델을 **내 데이터로 고칠 수 있는가** |
| **프롬프트 캐싱** | **추론 응답 지연과 입력 토큰 비용을 줄이는 선택적 기능.** 모델 카드가 암시적·명시적 지원 여부를 적습니다 | **길고 반복되는 공통 맥락**이 있는가 |

**입력 길이와 출력 길이를 혼동하지 않는 것**이 이 목표에서 가장 실용적인 수확입니다. Amazon Nova 이해 모델 사양표를 보면 컨텍스트 윈도는 모델별로 **1M · 300k · 300k · 128k**로 크게 갈리는데, **최대 출력 토큰은 네 모델 모두 10K**입니다. 즉 **"컨텍스트 윈도가 크다"가 "긴 답을 준다"는 뜻이 아닙니다.**

**캐싱을 선택 기준으로 보는 관점.** `aif-t2-1` 6절이 캐싱의 작동(암시적·명시적, 접두부·TTL·과금)을 다뤘습니다. 여기서는 **모델을 고를 때 캐싱이 왜 축이 되는가**만 봅니다. 공식 문서는 명시적 캐싱의 **체크포인트당 최소 토큰이 모델별로 512~4,096 토큰 범위**라고 적고, 모델별 표로 그 최솟값·최대 체크포인트 수·지원 TTL·체크포인트를 받는 필드를 각각 다르게 싣습니다. 그래서 **"공통 접두부가 1,000 토큰쯤 되는 워크로드"**라면 최소 토큰이 4,096인 모델에서는 캐싱이 **아예 걸리지 않습니다**(추론은 성공하지만 접두부가 캐시되지 않습니다).

> ⚠️ **"지원 언어 200개 이상"을 "200개 언어에서 품질이 같다"로 읽으면 틀립니다.** 공식 각주가 **최적화된 언어를 15개로 따로 못박습니다.** 다국어 요구가 있는 문항은 **대상 언어가 그 좁은 목록에 드는지**를 묻는 쪽이 자연스럽습니다.

### 2) 추론 파라미터가 응답에 미치는 영향 (목표 3.1.2) {#inference-parameters}

공식 문서의 첫 문장이 이 목표의 전부입니다 — **"추론 파라미터는 모델이 생성 과정에서 고려하는 가능한 출력의 풀을 바꿀 수도 있고, 최종 응답을 제한할 수도 있습니다."** 이 **두 가지**가 그대로 공식 분류입니다.

**풀을 바꾸는 쪽 — 무작위성과 다양성.** 모델은 다음 토큰에 대한 **확률 분포**를 만들고 거기서 표본을 뽑습니다. 세 파라미터가 그 분포를 다르게 건드립니다.

| 파라미터 | 낮은 값의 효과 | 높은 값의 효과 |
|---|---|---|
| **온도(temperature)** | **높은 확률** 토큰의 가능성을 올리고 낮은 확률 토큰을 내립니다. 기술적으로는 분포 함수를 **뾰족하게** 만들어 **더 결정론적인 응답** | 분포를 **평평하게** 만들어 **더 무작위적인 응답** |
| **Top K** | 후보 토큰을 **적게** 봅니다. 고정 크기 풀에서 가능성이 낮은 것을 잘라냅니다 | 후보 토큰을 **많이** 봐서 낮은 확률 출력을 허용합니다 |
| **Top P** | 누적 확률 분포의 **작은 비율**만 봅니다. 그 비율이 덮는 후보 **개수는 토큰마다 달라집니다** | 분포의 **큰 비율**을 봐서 낮은 확률 출력을 허용합니다 |

공식 예시를 그대로 쓰면 셋의 차이가 선명합니다. 프롬프트 `I hear the hoof beats of "`에 대해 모델이 **horses 0.7 · zebras 0.2 · unicorns 0.1**을 후보로 뒀다고 합니다.

- **온도를 높이면** 분포가 평평해져 **unicorns를 고를 확률이 올라가고 horses를 고를 확률이 내려갑니다.**
- **Top K를 2로** 두면 가장 가능성 높은 **두 개**, 즉 horses와 zebras만 봅니다.
- **Top P를 0.7로** 두면 상위 70%에 드는 **horses 하나만** 보고, **0.9로** 두면 horses와 zebras를 봅니다.

공식 API 레퍼런스는 온도의 유효 범위를 **0 ~ 1**로 적고 **낮은 예로 0.2 또는 0.3(결정론적·예측 가능), 높은 예로 0.8 또는 0.9(창의적·예측 불가)**를 듭니다.

**최종 응답을 제한하는 쪽 — 길이.** 공식이 드는 세 가지입니다.

- **응답 길이(response length)** — 생성 응답에서 반환할 토큰의 **최소 또는 최대 개수를 지정하는 정확한 값**입니다. Amazon Bedrock의 토큰 용어 문서는 `max_tokens`를 **"모델이 생성할 수 있는 출력 토큰의 최대량을 설정하기 위해 요청에 제공하는 파라미터"**로 정의합니다.
- **페널티(penalties)** — 응답에서 특정 출력을 **얼마나 불리하게 할지**를 지정합니다. 공식 예는 **응답의 길이 · 반복되는 토큰 · 토큰의 빈도 · 토큰의 종류**입니다.
- **중단 시퀀스(stop sequences)** — 모델이 **더 이상 토큰을 생성하지 않게 하는 문자 시퀀스**입니다. 지정한 중단 시퀀스를 모델이 생성하면 **그 시퀀스 뒤에서 생성을 멈춥니다.**

> ⚠️ **파라미터 기본값과 범위는 모델마다 다릅니다.** 공식 문서가 **"추론 파라미터 기본값과 범위는 모델에 달려 있다"**고 명시하고 모델별 레퍼런스로 보냅니다. 그래서 "온도 기본값은 N이다" 같은 수치는 외울 대상이 아니고, **방향**(낮으면 결정론적)만 확정적입니다.

### 3) RAG의 정의와 비즈니스 적용 사례 (목표 3.1.3) {#rag}

**정의.** 공식 한 줄은 **"RAG는 응답을 생성하기 전에 훈련 데이터 소스 밖의 권위 있는 지식 기반을 참조하도록 대규모 언어 모델의 출력을 최적화하는 과정"**입니다. 그리고 결정적인 단서가 붙습니다 — RAG는 LLM의 능력을 특정 도메인이나 조직 내부 지식 기반으로 확장하며 **"모델을 재훈련할 필요 없이"** 그렇게 합니다.

**왜 필요한가.** 공식이 LLM의 **알려진 과제 네 가지**를 적습니다. ① 답을 모를 때 **거짓 정보를 제시** ② 사용자가 구체적·최신 응답을 기대할 때 **낡거나 일반적인 정보를 제시** ③ **권위 없는 출처**에서 응답 생성 ④ 서로 다른 훈련 출처가 같은 용어를 다른 뜻으로 써서 생기는 **용어 혼동으로 부정확한 응답**. 비유도 공식 문장입니다 — LLM은 **"시사를 따라가기를 거부하면서도 모든 질문에 절대적인 확신을 갖고 답하는, 지나치게 열정적인 신입 직원"** 같습니다.

**동작 네 단계.** 공식이 절 제목으로 나눠 적습니다.

| 단계 | 공식이 적는 내용 |
|---|---|
| **외부 데이터 생성** | API·데이터베이스·문서 저장소 등에서 온 **외부 데이터**를 **임베딩 언어 모델**이 수치 표현으로 바꿔 **벡터 데이터베이스**에 저장합니다. 이것이 생성형 AI 모델이 이해할 수 있는 **지식 라이브러리**가 됩니다 |
| **관련 정보 검색** | 사용자 질의를 **벡터 표현으로 바꿔** 벡터 데이터베이스와 매칭합니다. 공식 예 — 직원이 "내 연차가 얼마나 남았나요?"라고 검색하면 **연차 정책 문서와 그 직원의 과거 연차 기록**이 함께 검색됩니다 |
| **LLM 프롬프트 증강** | 검색된 관련 데이터를 **맥락으로 붙여 사용자 입력을 증강**합니다. 이 단계는 **프롬프트 엔지니어링 기법**을 씁니다 |
| **외부 데이터 갱신** | 외부 데이터가 **낡지 않게** 문서와 임베딩 표현을 **비동기로** 갱신합니다. 실시간 자동화나 **주기적 배치** 둘 다 가능합니다 |

**비즈니스 가치 네 가지**도 공식이 절 제목으로 적습니다 — **비용 효율적 구현**(FM 재훈련의 연산·금전 비용이 높은 데 비해 RAG가 새 데이터를 넣는 더 저렴한 방법) · **최신 정보**(최신 연구·통계·뉴스, 심지어 라이브 소셜 미디어 피드까지 연결) · **향상된 사용자 신뢰**(**출처 귀속**과 함께 정보를 제시해 사용자가 원문을 직접 확인할 수 있습니다) · **개발자 통제력 확대**(정보 출처를 바꿀 수 있고, **민감 정보 검색을 권한 수준별로 제한**할 수 있고, LLM이 잘못된 출처를 참조하면 그 지점을 **고칠 수 있습니다**).

**AWS에서의 구현 — Amazon Bedrock Knowledge Bases.** ⚠️ **이 문구의 귀속을 2026-11-06에 정정했습니다** — **"수집부터 검색과 프롬프트 증강까지 RAG 워크플로 전체를 구현하는 완전 관리형 기능"**은 **현행 지식 기반 페이지에 더 이상 없습니다**(두 방법으로 확인, 대조군 `Managed Knowledge Base` 5건). 현행 페이지가 적는 것은 **RAG 정의 한 문장**과 **두 유형**(관리형 / 고객 관리형)이고, 맨 앞 Important가 **"검색 정확도 최적화와 관리형 경험을 원하면 관리형 지식 기반을 권장한다"**고 적습니다. 즉 **"완전 관리형"으로 외우는 대신 「관리형이냐 고객 관리형이냐」로** 쥡니다 — 고객 관리형은 벡터 저장소를 포함한 RAG 파이프라인과 설정을 직접 운영하고, 서드파티 커넥터나 문서 수준 권한 같은 요구가 있을 때 고릅니다. **세션 컨텍스트 관리가 내장**돼 다중 턴 대화를 지원하고, 생성 응답에 **인용(citation)을 넣어** 원본 출처를 참조하고 정확성을 확인할 수 있습니다.

지식 기반은 **두 유형**입니다.

| 유형 | 공식이 적는 차이 |
|---|---|
| **Managed Knowledge Base** | Amazon Bedrock이 **데이터 수집·인덱싱·저장·검색 인프라를 관리**합니다. 벡터 저장소를 **내가 고르지 않습니다.** 공식이 **"최적화된 검색 정확도와 관리형 경험을 위해 권장"**합니다 |
| **Customer-managed Knowledge Base** | **내가 벡터 저장소를 포함한 RAG 파이프라인을 직접 구성·관리**합니다. 수집·파싱·인덱싱·저장 설정을 완전히 통제하는 대신 관련 인프라를 직접 운영합니다. ⚠️ 서드파티 커넥터 · 문서 수준 권한 · AgentCore Gateway 네이티브 통합 같은 기능은 **Managed 쪽에만** 있습니다 |

> ⚠️ **RAG는 의미 검색(semantic search)과 같은 것이 아닙니다.** 공식은 의미 검색을 **"방대한 외부 지식 출처를 LLM 애플리케이션에 더하려는 조직에서 RAG 결과를 향상시키는" 기술**로 적습니다. RAG가 전체 흐름이고, 의미 검색은 그 **검색 단계의 품질을 올리는 선택지**입니다. 공식은 RAG의 **키워드 검색 방식이 지식 집약적 작업에서 제한된 결과를 낸다**고 적습니다.

### 4) 임베딩을 저장하는 AWS 서비스 (목표 3.1.4) {#vector-stores}

공식 목표가 예로 드는 넷은 **Amazon OpenSearch Service · Amazon Aurora · Amazon Neptune · Amazon RDS for PostgreSQL**입니다. AWS 의사 결정 가이드가 **관점부터** 교정해 줍니다 — **"AWS에서 벡터 검색은 별도로 도입해야 하는 데이터베이스가 아니라, 이미 운영 중인 많은 데이터베이스와 서비스에 더할 수 있는 기능"**입니다. 그래서 첫 질문은 **"어떤 벡터 DB가 가장 좋은가"**가 아니라 **"내 데이터가 이미 어디에 있는가"**입니다.

| 서비스 | 공식이 적는 역할 | 가르는 질문 |
|---|---|---|
| **Amazon OpenSearch Service** | **검색 엔진**이고 관리형 클러스터와 서버리스 컬렉션 양쪽에서 **벡터 엔진**으로 벡터 검색을 지원합니다. **하이브리드 검색**(어휘 검색과 의미 검색 결합)이 강점이고, 벡터 인덱스를 **수평 확장**해야 할 때 이상적입니다 | **키워드와 의미를 함께** 검색해야 하는가 |
| **Amazon Aurora PostgreSQL** | **pgvector** 오픈 소스 확장을 갖춘 완전 관리형 관계형 데이터베이스입니다. **SQL과 벡터 질의를 함께** 쓰고 Aurora Serverless v2 배포에서도 벡터 검색을 지원합니다 | 관계형 데이터 옆에 **SQL로** 벡터를 두고 싶은가 |
| **Amazon RDS for PostgreSQL** | 공식이 Aurora PostgreSQL과 **같은 문단에서 함께** 적습니다 — 둘 다 **pgvector 확장을 갖춘 완전 관리형 관계형 데이터베이스**이고, **이미 PostgreSQL에 투자한 경우 이상적인 선택지**입니다 | 이미 **PostgreSQL 전문성**이 있는가 |
| **Amazon Neptune Analytics** | **그래프 알고리즘과 벡터 검색을 결합**한 분석 그래프 데이터베이스 엔진입니다. 공식이 쓰는 이름이 **GraphRAG** — 엔터티 간 **관계를 사용하는 검색**이고, 대규모 데이터셋에 대한 **더 높은 수준의 이해**가 필요한 질의에 이상적입니다 | 답이 **항목 사이의 관계**에 있는가 |

**Bedrock 지식 기반이 쓰는 벡터 저장소.** 공식 지식 기반 문서는 Customer-managed 구성의 벡터 저장소 예로 **Amazon OpenSearch Serverless · Amazon Aurora · Amazon Neptune**을 적습니다. 그리고 의사 결정 가이드의 기능 표가 서비스별로 **최대 차원 수 · 벡터 볼륨 · 하이브리드 검색 지원 · 읽기 지연 · 쓰기 지연**을 비교합니다 — 예컨대 OpenSearch는 **최대 16,000 차원**이고 **하이브리드 검색 가능**, Aurora PostgreSQL은 **인덱싱 2,000 차원**에 하이브리드는 **부분적(SQL)**이며 **커밋된 행이 즉시 질의 가능**합니다.

> 공식 문서는 **Amazon S3 Vectors**도 Bedrock 지식 기반이 쓸 수 있는 유효한 벡터 저장소로 싣습니다 — **낮은 비용의 벡터 저장**과 **질의당 과금**, **1초 미만 질의**, **인덱스당 20억 벡터**가 특징이고 **대규모 임베딩 컬렉션을 중간 정도의 질의 빈도로** 쓸 때를 위한 것입니다. 다만 **공식 시험 가이드의 예시 목록에는 없으므로**, 개념으로 알아 두되 시험에서 고르는 이름은 위 표의 넷으로 두는 편이 안전합니다.

> ⚠️ **"벡터 전용 데이터베이스를 새로 도입해야 한다"는 보기는 공식 서술과 어긋납니다.** 공식이 명시적으로 세 절충을 적습니다 — **기존 저장소 대 새 저장소 · 완전 관리형 대 자체 관리 · 비용·지연·규모**. 그리고 기존 저장소에 벡터 검색을 더하면 **팀이 이미 가진 엔진·기술·도구를 재사용**할 수 있다고 적습니다.

### 5) FM 사용자 지정의 비용 절충점 (목표 3.1.5) {#customization-cost}

**이 절이 이 문서의 심장입니다.** 공식 Well-Architected Generative AI Lens의 모범 사례 **GENOPS05-BP01**이 사다리를 그대로 적습니다 — **"가장 자원이 덜 드는 선택지(프롬프트 엔지니어링)부터 시작하고, 필요하면 점진적으로 더 고급 방법으로 올라가라."** 그리고 이 모범 사례가 확립되지 않았을 때의 **위험 수준은 High**입니다.

| 접근 방식 | 모델 가중치를 바꾸는가 | 공식이 적는 비용·노력 | 공식이 적는 "언제 쓰는가" |
|---|---|---|---|
| **컨텍스트 내 학습 / 프롬프트 엔지니어링** | **아니오** | **가장 자원이 덜 드는 선택지**이고 출발점 | **"잘 만든 프롬프트는 모델을 수정하지 않고도 원하는 결과를 얻는 경우가 많다"** |
| **RAG** | **아니오** | 프롬프트 다음 단계. **코어 모델 자체를 재훈련하지 않고** 도메인에 맞춥니다 | 외부 지식 출처를 검색 메커니즘으로 쓰게 해 응답을 특정 도메인·맥락에 맞출 때 |
| **지속적인 사전 훈련** | **예** | 미세 조정과 같은 층. 데이터가 **비레이블**이어도 됩니다 | 원래 훈련 세트에 없던 **새롭게 등장하는 데이터**로 사전 훈련 단계를 연장해 도메인 특화 지식을 축적할 때 |
| **미세 조정** | **예** | 같은 층이지만 ⚠️ **레이블 데이터가 전제**입니다 | **특정 작업의 성능 개선이 필요하고** · **작업에 관련된 레이블 데이터를 보유했고** · 모델이 **도메인 특화 언어**(예: 의학·법률 용어)를 이해해야 할 때 |
| **모델 증류** | **예**(학생 모델을 미세 조정) | 교사 추론 비용이 **추가로** 붙습니다(아래) | **작고 빠르고 비용 효율적인 모델**로 큰 모델에 가까운 품질을 특정 사용 사례에서 얻고 싶을 때 |
| **사용자 지정 FM 구축 / 사전 훈련** | **예**(처음부터) | 공식 표현으로 **"자원과 비용이 통상 가장 높은 선택지"** | **사용 가능한 사전 훈련 모델 중 어느 것도 요구를 못 맞추고** · **방대한 독점 데이터**가 있고 · **모델 아키텍처와 훈련 과정을 완전히 통제**해야 할 때 |

**Amazon Bedrock이 적는 사용자 지정 방법.** 공식 문서가 세 가지를 절 제목으로 싣습니다 — **지도 미세 조정**(레이블 데이터를 제공해 입력 유형과 출력 유형의 대응을 학습) · **강화 미세 조정**(레이블 입출력 쌍 대신 **보상 함수**를 정의하고 모델이 피드백 점수로 반복 학습) · **증류**. 그리고 과금 축이 명시됩니다 — **"모델 훈련은 모델이 처리한 토큰 수(훈련 데이터 코퍼스의 토큰 수 × 에포크 수)를 기준으로 과금되고, 모델 저장은 모델별 월 단위로 과금됩니다."**

**모델 증류의 세부**가 v1.1 신규 항목입니다.

- **방향** — **"더 크고 지능적인 모델(교사)의 지식을 더 작고 빠르고 비용 효율적인 모델(학생)에게 옮기는 과정"**입니다. 메커니즘은 교사에서 **합성 데이터(다양하고 고품질인 응답)를 생성**해 그것으로 **학생을 미세 조정**하는 것입니다.
- **데이터 경로 둘** — 내가 `.jsonl` 프롬프트를 제공하거나, **호출 로그(invocation logs)**에 쌓인 **기존 교사 응답**을 재사용합니다. 후자에서 프롬프트-응답 쌍을 쓰면 Bedrock이 **교사 응답을 다시 생성하지 않습니다**(단, 작업에 지정한 교사 모델이 로그의 모델과 **일치해야** 로그가 쓰입니다).
- ⚠️ **숨은 비용** — 공식 주의 문구입니다. Bedrock이 독점 데이터 합성 기법으로 **더 높은 품질의 교사 응답을 생성하면 교사 모델 추론 호출에 추가 요금이 발생하고, 그 요금은 교사 모델의 온디맨드 추론 요율로 과금됩니다.** 그리고 데이터 합성 기법이 **미세 조정 데이터셋 크기를 최대 15,000개 프롬프트-응답 쌍까지 늘릴 수 있습니다.**

**사용자 지정에는 꼬리 비용이 하나 더 붙습니다 — 서빙.** 사용자 지정 모델은 기반 모델처럼 그냥 호출할 수 없고 **추론을 따로 설정**해야 합니다. 공식 「사용자 지정 모델의 추론 설정」 페이지가 선택지를 **둘**로 적습니다.

| 선택지 | 공식이 적는 내용 |
|---|---|
| **프로비저닝된 처리량(PT) 구매** | **보장된 처리량을 갖는 전용 컴퓨팅 용량**으로 일관된 성능과 더 낮은 지연을 얻습니다. ⚠️ 과금은 **시간당**이고 축은 **모델 단위(MU) × 시간**입니다. 약정은 **무약정 · 1개월 · 6개월**이고 **길수록 시간당 가격이 할인**되지만 약정 기간이 끝나기 전에는 **삭제할 수 없습니다** |
| **사용자 지정 모델 배포(온디맨드 추론)** | **사용자 지정 모델 배포**를 만들고 그 배포의 ARN으로 호출합니다. **쓴 만큼만 내고 프로비저닝된 컴퓨팅 자원을 설정할 필요가 없습니다.** ⚠️ 다만 조건이 좁습니다 — 공식이 리전을 **US East(버지니아 북부)와 US West(오레곤) 둘**로 적고, **2025-07-16 이후에 사용자 지정한 모델**이어야 하며 **지원 기반 모델 목록**도 따로 있습니다 |

> ⚠️ **PT 페이지는 아직 "모델을 사용자 지정했다면, 그것을 쓰려면 프로비저닝된 처리량을 구매해야 한다"고 적습니다.** 더 구체적인 「사용자 지정 모델의 추론 설정」 페이지가 위의 **두 선택지**를 싣고 있으니, 시험에서 통하는 안전한 서술은 **"사용자 지정 모델은 전용 용량을 사거나 배포를 따로 만들어야 호출할 수 있다"**입니다. 공통점이 핵심입니다 — **사용자 지정의 비용은 훈련비로 끝나지 않습니다.**

### 6) AI 에이전트의 역할과 비즈니스 애플리케이션 (목표 3.1.6) {#ai-agents}

v1.1이 이 목표에서 **서비스 예시를 전부 지웠습니다.** 그러니 여기서 묻는 것은 **역할**과 **어디에 쓰는가** 둘입니다.

**역할의 공식 정의.** Well-Architected Generative AI Lens가 적습니다 — **"AI 에이전트는 환경을 인지하고, 추론하고, 정의된 목표를 달성하기 위해 행동할 수 있는 자율적 개체"**입니다. 그리고 구성이 한 문장에 담깁니다 — **"생성형 AI에서 에이전트 시스템의 핵심은 보통 대규모 언어 모델(LLM)이고, 거기에 검색(정보 접근) · 도구(환경과의 상호 작용) · 메모리 같은 기능이 덧붙습니다."**

**가장 중요한 설계 원칙은 "자율성은 많을수록 좋은 것이 아니다"입니다.** 공식 문장 둘을 붙여 읽습니다 — **"에이전틱 시스템은 좁은 범위의 행동을 하는 수준부터 스스로를 자율적으로 오케스트레이션하는 수준까지 다양한 정도의 에이전시를 가질 수 있습니다."** 그리고 **"에이전틱 시스템을 설계할 때는 작업 복잡도가 요구할 때만 시스템의 에이전시를 높이는 것이 중요합니다."**

공식이 적는 **에이전틱 패턴 세 가지**가 그 스펙트럼을 보여 줍니다.

| 패턴 | 공식 서술 | 에이전시 정도 |
|---|---|---|
| **LLM 증강 워크플로** | 코드 경로가 **대부분 결정론적**이고 특정 단계만 LLM이 판단합니다. 공식 예 — 들어온 문서를 단순·복잡으로 분류하고 **도구 호출로 올바른 경로에 라우팅**하는 문서 처리 시스템 | **낮습니다.** 그래도 도구 호출로 판단하므로 전체적으로는 에이전틱 시스템입니다 |
| **자율 에이전트** | LLM에 **검색·도구·메모리**를 붙여 **루프에서 오케스트레이션**합니다. 이것이 **ReAct(reason and act) 루프**이고, 도구 목록과 사용 지침을 받아 **LLM이 중단 이유를 받을 때까지** 돕니다. 추론의 지침은 전통적으로 **시스템 프롬프트**에 목표·역할 등으로 적습니다 | 높습니다 |
| **하이브리드** | 실제로는 둘을 섞습니다. 공식 예인 **plan and solve 루프**는 LLM이 **계획과 작업 분해**를 만들고, 그 작업 목록을 큐에 넣어 **여러 ReAct 에이전트**가 해결하고, 끝나면 **또 한 번의 LLM 호출**이 사용자에게 돌려줄지 작업을 더 추가할지 결정합니다 | **높습니다** |

**비즈니스 애플리케이션.** 공식 「에이전틱 AI란 무엇인가」 페이지가 **사용 사례 네 가지**를 절 제목으로 적습니다. 목표 3.1.6이 묻는 바로 그 목록입니다.

| 사용 사례 | 공식이 적는 내용 |
|---|---|
| **연구·개발 지원** | 가설 검증 · 연구 정보 수집 · 데이터 수집 · **여러 데이터 출처에 걸친 통찰 종합** 같은 수동 과정에서 사람의 개입을 줄입니다. **다중 에이전트 오케스트레이션**으로 감독자가 여러 전문 모델을 써서 복잡한 R&D 파이프라인을 구성합니다 |
| **코드 전환** | 현대화·마이그레이션의 복잡도를 전문 에이전트로 걷어 냅니다. 공식 예 — Windows 기반 **.NET 애플리케이션을 Linux로 현대화**, 그리고 **모놀리식 z/OS COBOL 애플리케이션을 개별 구성요소로 분해**해 **수개월이 걸리던 과정을 수 분으로** 줄입니다 |
| **사고 대응 자동화** | 취약점이든 수동 오류든 사고가 생기면 대응 경로 전체를 자동화합니다 — **문제 롤백 · 사고 보고서 작성 · 알아야 할 팀원에게 통지**. 더 구체적이고 깊은 **사후 분석**까지 제공합니다 |
| **고객 서비스 자동화** | 문의를 처리하며 **회사 문서를 빠르게 검색**해 적절한 답을 찾고, 그것으로 부족하면 **사용자와 소통해 정보를 더 모아** 해결로 안내합니다. 여러 차례 시도해도 해결하지 못하면 **사람 지원 담당자에게 연락해 담당을 배정**합니다 |

공식이 적는 **비즈니스 이점 네 가지**도 같은 자리에서 나옵니다 — **효율 증가**(지루한 과정을 자동화해 직원 시간을 문제 해결·전략 수립 같은 일로 돌립니다) · **사용자 신뢰 증가**(기존 고객 데이터로 맞춤 메시지를 만들고 **선호하는 어조로** 응대) · **지속적 개선**(상호 작용하고 피드백에서 배워 의사 결정을 최적화하는 **재귀 루프**) · **인간 증강**(사람 담당자와 협업하는 도구로 생산성을 높입니다).

> ⚠️ **에이전트를 만드는 AWS 정본은 `Amazon Bedrock AgentCore`입니다.** 공식 문서가 **"2023년 11월 출시된 Amazon Bedrock Agents는 이제 Amazon Bedrock Agents Classic이며 2026년 7월 30일부터 신규 고객에게 열리지 않습니다"**라고 적고, 그 서비스는 **유지 보수 모드**입니다. 범위는 그 서비스 하나입니다 — **"Amazon Bedrock은 계속 완전히 지원되며, 기존 Amazon Bedrock 모델·Knowledge Bases·Guardrails는 영향을 받지 않습니다."** 다만 **목표 3.1.6은 서비스 이름을 묻지 않습니다.** 서비스 매칭은 도메인 2의 작업 2.1·2.3과 도메인 5의 작업 5.1에서 다룹니다.

## ✍️ 시험 포인트

- **모델 선택 문항은 지문의 제약을 먼저 찾습니다** — **지연**이 걸리면 작고 빠른 모델, **긴 문서**가 걸리면 컨텍스트 윈도, **긴 답**이 걸리면 최대 출력 토큰, **특정 언어**가 걸리면 지원 언어와 최적화 언어, **예산**이 걸리면 모델 복잡도입니다.
- **온도 문항은 방향만 묻습니다** — 낮으면 **결정론적**, 높으면 **무작위적**. 수치 기본값은 모델마다 달라 출제될 수 없습니다.
- **Top K와 Top P의 차이는 "개수 대 비율"** 하나입니다. P는 같은 값이어도 **토큰마다 후보 개수가 달라집니다.**
- **길이 파라미터는 무작위성과 다른 범주**입니다. "출력이 중간에 끊긴다"는 증상은 온도가 아니라 **최대 출력 토큰**이나 **중단 시퀀스**를 봅니다.
- **RAG 문항의 핵심 단서는 「최신」과 「출처」**입니다 — 지식이 **자주 바뀌거나** 답에 **인용·출처 귀속**이 필요하면 RAG입니다.
- **벡터 저장소 문항은 검색 성격으로 갈립니다** — 키워드와 의미를 **함께** → OpenSearch · **관계·그래프** → Neptune Analytics · **SQL과 함께** → Aurora PostgreSQL 또는 RDS for PostgreSQL(pgvector).
- **사용자 지정 문항은 순서와 전제를 봅니다** — 아직 프롬프트를 손보지 않았다면 **프롬프트 엔지니어링**이 정답이고, **레이블 데이터가 없다면 미세 조정은 오답**입니다.
- **"작은 모델로 큰 모델급 품질"**이라는 표현이 나오면 **모델 증류**입니다. 그리고 그 보기에는 **교사 추론 추가 과금**이라는 꼬리가 붙습니다.
- **에이전트 문항은 자율성의 정도를 묻습니다** — 사람이 매 단계를 지시하면 에이전트가 아니고, 반대로 **결정론적 경로에 LLM 판단 한 지점만** 있어도 에이전틱 시스템입니다.

## ⚠️ 흔한 함정 {#pitfalls}

- ❌ **"컨텍스트 윈도가 크면 긴 답을 받을 수 있다"** → **입력 쪽과 출력 쪽은 다른 사양**입니다. Amazon Nova 이해 모델은 컨텍스트 윈도가 **1M~128k로 갈리는데 최대 출력 토큰은 모두 10K**입니다.
- ❌ **"온도를 올리면 응답이 길어진다"** → 온도는 **확률 분포의 모양**만 바꿉니다. 길이는 **「길이」 범주의 파라미터**(응답 길이·페널티·중단 시퀀스)가 정합니다.
- ❌ **"Top P를 0.8로 두면 후보가 항상 같은 개수다"** → P는 **누적 확률의 비율**이라 **그 비율이 덮는 후보 개수가 토큰마다 달라집니다.** 고정 개수는 Top K입니다.
- ❌ **"RAG를 쓰려면 모델을 재훈련해야 한다"** → 공식 정의의 핵심이 **"모델을 재훈련할 필요 없이"**입니다. 가중치는 그대로이고 **프롬프트에 검색 결과를 붙입니다.**
- ❌ **"RAG와 미세 조정은 같은 문제를 푼다"** → 지식을 **넣는 곳이 다릅니다.** RAG는 **외부 지식 기반**에 두고 질의마다 검색해 붙이므로 **데이터를 갱신하면 즉시 반영**됩니다. 미세 조정은 **모델 파라미터**에 넣으므로 지식이 바뀌면 **다시 훈련**해야 하고, 애초에 **레이블 데이터가 전제**입니다.
- ❌ **"벡터를 저장하려면 전용 벡터 데이터베이스를 새로 도입해야 한다"** → 공식은 **"벡터 검색은 이미 운영 중인 많은 데이터베이스와 서비스에 더할 수 있는 기능"**이라고 적습니다.
- ❌ **"Managed Knowledge Base에서도 벡터 저장소를 고른다"** → Managed 쪽은 **Amazon Bedrock이 벡터 저장소까지 관리**해서 **내가 고르지 않습니다.** 고르는 쪽은 Customer-managed입니다.
- ❌ **"증류는 비용을 줄이는 방법이니 추가 비용이 없다"** → 데이터 합성 기법이 돌면 **교사 모델 추론이 온디맨드 요율로 추가 과금**됩니다. 줄어드는 것은 **완성된 학생 모델의 운영 비용**입니다.
- ❌ **"미세 조정한 모델도 기반 모델처럼 바로 호출하면 된다"** → **추론을 따로 설정**해야 합니다 — **PT 구매**나 **사용자 지정 모델 배포(온디맨드)**이고, 후자는 **리전·사용자 지정 시점·지원 기반 모델**에 제약이 있습니다.
- ❌ **"에이전트는 자율성이 높을수록 좋다"** → 공식 설계 원칙이 정확히 반대입니다 — **"작업 복잡도가 요구할 때만 시스템의 에이전시를 높인다."**
- ❌ **"목표 3.1.6에서 Amazon Bedrock Agents를 고르면 된다"** → v1.1은 그 목표에서 **서비스 예시를 삭제**했고, 그 서비스는 **Agents Classic으로 개명돼 2026년 7월 30일부터 신규 고객에게 열리지 않습니다.** 에이전트 구축의 정본은 **AgentCore**입니다.

## 🧪 자가 점검

**Q1.** 모델 A는 컨텍스트 윈도 300k · 최대 출력 토큰 10k이고, 모델 B는 컨텍스트 윈도 128k · 최대 출력 토큰 10k입니다. "200페이지 계약서 전문을 넣고 한 단락 요약을 받는다"와 "짧은 지시로 30페이지 보고서를 생성한다" 중 모델 선택이 갈리는 쪽은 어디이고 왜인가요? (→ 1) 사전 훈련된 모델을 고르는 아홉 축)

<details><summary>정답 보기</summary>

**첫 번째(긴 문서를 넣는 쪽)에서 갈립니다.** 공식 모델 사양표가 **컨텍스트 윈도**(입력 쪽에서 한 번에 고려할 수 있는 양)와 **최대 출력 토큰**(한 응답에서 생성할 수 있는 상한)을 **따로** 적고, 두 모델은 **최대 출력 토큰이 같습니다.** 그래서 긴 입력을 넣는 작업에서는 300k 쪽이 필요하고, **긴 출력을 받는 작업에서는 두 모델이 동일하게 10k에 묶입니다.**

이것이 "컨텍스트 윈도가 크면 긴 답을 준다"는 오해를 깨는 자리입니다. Amazon Nova 이해 모델 네 종은 컨텍스트 윈도가 **1M · 300k · 300k · 128k**로 크게 갈리지만 **최대 출력 토큰은 모두 10K**입니다.
</details>

**Q2.** 다음 중 **무작위성과 다양성** 범주가 아닌 파라미터를 골라, 공식 분류를 근거로 설명하세요 — 온도 · Top K · Top P · 중단 시퀀스. (→ 2) 추론 파라미터가 응답에 미치는 영향)

<details><summary>정답 보기</summary>

**중단 시퀀스(stop sequences)**입니다. 공식 문서는 추론 파라미터를 **「무작위성과 다양성」**과 **「길이」** 두 범주로 나누고, **온도·Top K·Top P를 앞쪽**에, **응답 길이·페널티·중단 시퀀스를 뒤쪽**에 둡니다.

가르는 기준도 공식 첫 문장에 있습니다 — 추론 파라미터는 **"모델이 생성 과정에서 고려하는 가능한 출력의 풀을 바꿀 수도 있고, 최종 응답을 제한할 수도 있다"**는 것입니다. 온도·Top K·Top P는 **풀(확률 분포)을 바꾸고**, 중단 시퀀스는 **"모델이 더 이상 토큰을 생성하지 않게 하는 문자 시퀀스"**로 **최종 응답을 제한**합니다.
</details>

**Q3.** 사내 정책 문서가 매주 바뀌고, 답변에는 **어느 문서의 어느 부분을 근거로 했는지**가 함께 나와야 합니다. RAG와 미세 조정 중 무엇을 고르고, 공식 서술의 어느 근거로 가르나요? (→ 3) RAG의 정의와 비즈니스 적용 사례)

<details><summary>정답 보기</summary>

**RAG입니다.** 공식이 적는 RAG의 장점 둘이 지문의 두 요구와 정확히 대응합니다.

- **최신 정보** — RAG는 최신 연구·통계·뉴스를 생성 모델에 제공하게 하고, **자주 갱신되는 정보 출처**에 LLM을 직접 연결할 수 있습니다. 외부 데이터는 **비동기로 갱신**하면 되고 **모델을 재훈련할 필요가 없습니다.**
- **향상된 사용자 신뢰** — **"RAG는 LLM이 출처 귀속(source attribution)과 함께 정확한 정보를 제시하게 한다"**이고 출력에 **인용이나 참조**를 넣을 수 있습니다. Amazon Bedrock Knowledge Bases도 **생성 응답에 인용을 포함해 원본 출처를 참조하고 정확성을 확인할 수 있다**고 적습니다.

미세 조정은 지식을 **모델 파라미터 안에** 넣으므로 문서가 바뀌면 다시 훈련해야 하고, 어느 문서를 근거로 했는지 인용을 돌려주지 못합니다. 게다가 공식 미세 조정 조건에는 **레이블 데이터 보유**가 들어갑니다.
</details>

**Q4.** 제품 카탈로그가 이미 Aurora PostgreSQL에 있고, 팀에는 PostgreSQL 전문성이 있습니다. 한편 다른 팀은 **엔터티 사이의 관계를 따라가는 검색**이 필요합니다. 두 팀에 각각 어떤 선택을 권하고, 공식이 쓰는 이름은 무엇인가요? (→ 4) 임베딩을 저장하는 AWS 서비스)

<details><summary>정답 보기</summary>

- **첫 팀 → Amazon Aurora PostgreSQL(pgvector).** 공식은 Aurora PostgreSQL과 **Amazon RDS for PostgreSQL**을 **pgvector 오픈 소스 벡터 검색 확장을 갖춘 완전 관리형 관계형 데이터베이스**로 함께 적고, **"이미 관계형 데이터베이스, 특히 PostgreSQL에 투자했다면 이상적인 선택지"**라고 명시합니다. 의사 결정 가이드도 **「SQL과 벡터」** 요구를 Aurora PostgreSQL에 매핑합니다.
- **둘째 팀 → Amazon Neptune Analytics.** 공식은 이것을 **그래프 알고리즘과 벡터 검색을 결합한 분석 그래프 데이터베이스 엔진**으로 적고, 그 용례에 **GraphRAG**라는 이름을 붙입니다 — **"엔터티 관계를 사용하는 검색"**입니다.

그리고 관점 하나가 더 중요합니다. 공식이 **"AWS에서 벡터 검색은 별도로 도입해야 하는 데이터베이스가 아니라 이미 운영 중인 많은 데이터베이스와 서비스에 더할 수 있는 기능"**이라고 적으므로, **데이터가 이미 있는 곳에 벡터를 더하는 쪽**이 기본 답입니다.
</details>

**Q5.** 팀이 **레이블 데이터가 전혀 없는 상태**에서 "우리 도메인 용어를 모델이 이해하게 하자"며 곧바로 미세 조정 예산을 요청했습니다. 공식 모범 사례를 근거로 이 요청을 검토하세요. (→ 5) FM 사용자 지정의 비용 절충점)

<details><summary>정답 보기</summary>

**순서와 전제가 둘 다 어긋납니다.**

- **전제** — 공식 GENOPS05-BP01이 **지속적인 사전 훈련 또는 미세 조정을 고르는 조건**으로 **① 특정 작업·사용 사례의 성능 개선이 필요하다 ② 작업에 관련된 레이블 데이터를 보유했다 ③ 모델이 도메인 특화 언어를 이해해야 한다 ④ 애플리케이션의 정확도를 높이고 싶다**를 듭니다. 레이블 데이터가 없으면 **지도 미세 조정의 전제가 빠집니다**(Amazon Bedrock의 지도 미세 조정 설명도 **"레이블 데이터를 제공"**으로 시작합니다). 비레이블 데이터로 도메인 지식을 쌓는 쪽은 **지속적인 사전 훈련**입니다.
- **순서** — 공식은 **"가장 자원이 덜 드는 선택지(프롬프트 엔지니어링)부터 시작하고 필요하면 점진적으로 올라가라"**고 적고, **"잘 만든 프롬프트는 모델을 수정하지 않고도 원하는 결과를 얻는 경우가 많다"**고 덧붙입니다. 그다음이 **RAG**로, **코어 모델 자체를 재훈련하지 않고** 외부 지식 출처로 도메인에 맞추는 단계입니다.

덧붙여 비용 축도 봐야 합니다. 사용자 지정 모델은 **훈련 과금**(훈련 코퍼스 토큰 수 × 에포크 수)과 **월 저장 과금**이 붙고, 거기에 **추론 설정**(PT 구매 또는 사용자 지정 모델 배포)이 또 필요합니다.
</details>

**Q6.** "작고 빠른 모델로 큰 모델에 가까운 품질을 내고 싶다"는 요구에 맞는 사용자 지정 방법은 무엇이고, 비용 계산에서 빠뜨리기 쉬운 항목은 무엇인가요? (→ 5) FM 사용자 지정의 비용 절충점)

<details><summary>정답 보기</summary>

**모델 증류(model distillation)**입니다. 공식 정의가 그대로 요구에 대응합니다 — **"더 크고 지능적인 모델(교사)의 지식을 더 작고 빠르고 비용 효율적인 모델(학생)에게 옮기는 과정"**이고, 그 과정에서 **학생 모델의 성능이 특정 사용 사례에 대해 개선**됩니다. 메커니즘은 교사에서 **합성 데이터를 생성**해 **학생을 미세 조정**하는 것입니다.

**빠뜨리기 쉬운 항목은 교사 모델 추론 비용**입니다. 공식 주의 문구가 명시합니다 — Bedrock이 독점 데이터 합성 기법으로 더 높은 품질의 교사 응답을 생성하면 **교사 모델 추론 호출에 추가 요금이 발생하고 그것이 교사 모델의 온디맨드 추론 요율로 과금**되며, 데이터 합성 기법이 **미세 조정 데이터셋을 최대 15,000개 프롬프트-응답 쌍까지 늘릴 수 있습니다.**

결과물은 사용자 지정 모델이므로 **추론 설정 비용**도 따라옵니다 — **PT 구매**(MU × 시간) 또는 **사용자 지정 모델 배포**(온디맨드, 리전·시점·지원 모델 제약).
</details>

**Q7.** 들어온 문서를 "단순"과 "복잡"으로 분류하고 도구 호출로 알맞은 처리 경로에 보내는 시스템이 있습니다. 나머지 코드 경로는 전부 결정론적입니다. 이것은 에이전틱 시스템인가요? 공식 서술을 근거로 답하세요. (→ 6) AI 에이전트의 역할과 비즈니스 애플리케이션)

<details><summary>정답 보기</summary>

**예, 에이전틱 시스템입니다 — 다만 에이전시 정도가 낮은 쪽입니다.** 공식 Well-Architected Generative AI Lens가 이것을 **「LLM 증강 워크플로」**로 이름 붙여 적고, 예시가 지문과 같습니다 — 들어온 문서를 단순·복잡으로 분류하고 **도구 호출로 올바른 경로에 라우팅**하는 문서 처리 시스템. 그리고 판정을 명시합니다 — **"에이전시 정도는 낮지만, 도구 호출을 통해 판단을 내리고 있으므로 전체로서는 여전히 에이전틱 시스템"**입니다.

중요한 것은 그다음 원칙입니다. 공식은 에이전시가 **좁은 범위의 행동부터 스스로를 자율적으로 오케스트레이션하는 수준까지 스펙트럼**이라고 적고, **"작업 복잡도가 요구할 때만 시스템의 에이전시를 높여야 한다"**고 못박습니다. 즉 **이 시스템을 자율 에이전트로 바꾸는 것이 자동으로 개선은 아닙니다.**
</details>
