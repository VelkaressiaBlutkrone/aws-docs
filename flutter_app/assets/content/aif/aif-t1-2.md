# AI의 실제 사용 사례 (가치·부적합·기법 선택·응용·관리형 서비스·FM 대 기존 ML)

> **커버하는 공식 Task** — AIF-C01 · 도메인 1 「AI 및 ML의 기초」(20%) · **작업 1.2 AI의 실제 사용 사례 파악** (`aif-t1-2`)
> 이 문서는 위 한 작업에 1:1로 매핑되고 공식 목표 6개(1.2.1~1.2.6)를 모두 덮습니다. 작업 1.1이 **낱말**이었다면 1.2는 **판단**입니다. 문항이 상황을 주고 "이 경우에 적합한 것은?"을 묻기 때문에, 외워야 하는 것은 서비스 목록이 아니라 **갈림길을 가르는 질문 한 줄**입니다.

> ⚠️ **가이드 v1.1에서 바뀐 것** — 공식 개정 표 기준으로 이 작업에서 달라진 것은 둘입니다. 목표 **1.2.4**의 응용 예시에 **지식 기반과 에이전틱 AI**가 추가됐고, 목표 **1.2.6**(기존 ML 모델인가 FM인가)은 **새로 생긴 목표**입니다. 2026-04-30 이전 교재는 이 둘을 빠뜨립니다.

## 🎯 왜 중요한가

도메인 1은 전체의 **20%**입니다. 그중 1.2는 이 시험이 응시자에게 실제로 기대하는 것 — **"이 문제에 AI를 쓸 것인가, 쓴다면 어느 도구를 쓸 것인가"** — 를 그대로 묻습니다.

여기서 가장 자주 틀리는 방향은 **"AI를 쓰는 쪽이 늘 정답"**이라는 반사입니다. 공식 문서는 반대로 적습니다. AWS Well-Architected 기계 학습 렌즈는 ML이 올바른 해법인지 **먼저 평가하라**는 것을 베스트 프랙티스로 두고, "ML 솔루션으로 곧바로 뛰어들어 더 단순한 대안을 평가하지 않는 것"을 **안티패턴**으로 명시합니다. 그래서 1.2.2 유형의 문항은 **"ML을 쓰지 않는다"가 정답인 경우**가 실제로 있습니다.

나머지 절반은 **분류 연습**입니다. 상황을 읽고 회귀·분류·클러스터링 중 하나로, 또 관리형 서비스 중 하나로 떨어뜨리는 일입니다. 이건 서비스를 많이 아는 것보다 **입력과 출력의 모양**을 기억하는 쪽이 빠릅니다.

## ⚡ 시험 직전 요약

> 시험 직전에 이 열 줄만 다시 봅니다. 근거와 맥락은 아래 본문에 있습니다.

- **ML을 쓰는 공식 조건은 둘**입니다 — **규칙을 코딩할 수 없을 때**(요인이 너무 많고 규칙이 겹침)와 **확장할 수 없을 때**(사람이 감당할 양이 아님)
- ⚠️ **거꾸로가 1.2.2의 정답입니다** — 공식은 **"단순한 규칙·계산·사전 정의된 단계로 목표값을 정할 수 있으면 ML이 필요 없다"**고 적습니다
- **비용-이점 분석의 비용 항목**: 데이터 준비·저장·훈련 컴퓨팅·**레이블링**·모델 호스팅·추론·**지속적인 유지보수와 재훈련**. 그리고 가장 제약된 자원은 사람(데이터 사이언티스트)일 수 있습니다
- **기법 가르기**: 목표값이 **수학적으로 연속**이면 **회귀**, **범주(이산)**면 **분류**, **레이블이 없고 묶는 것이 목적**이면 **클러스터링**
- **분류는 둘로 더 갈립니다** — 상호 배타적인 두 클래스면 **이진 분류**, 셋 이상이면 **다중 클래스 분류**
- **입력 → 출력으로 외우는 서비스 6종**: Transcribe(오디오→텍스트) · Polly(텍스트→음성) · Translate(텍스트→다른 언어 텍스트) · Comprehend(문서→인사이트) · Lex(음성·텍스트→의도와 대화) · SageMaker AI(직접 구축·훈련·배포)
- ⚠️ **Comprehend의 기본 기능은 UTF-8 텍스트만 받습니다.** 이미지·PDF·Word를 받는 것은 **사용자 지정 분류와 사용자 지정 엔터티 인식**뿐입니다
- **지식 기반은 RAG입니다** — 수집(청크 분할 → 임베딩 → 벡터 DB 저장)과 검색(질의 임베딩 → 지식 기반 조회 → **프롬프트 보강**) 두 단계이고, 생성된 응답에 **인용**이 붙어 원본 데이터 소스를 확인할 수 있습니다
- **FM을 고르는 이유는 속도와 비용**입니다 — 공식은 **"사전 훈련된 FM을 쓰는 것이 고유 ML 모델을 처음부터 훈련하는 것보다 빠르고 저렴하다"**고 적습니다
- ⚠️ **기존 ML 모델을 고르는 이유는 설명 가능성**입니다 — 공식은 복잡한 모델이 정확도는 높지만 해석이 어렵고, **결정 트리·선형 회귀 같은 단순한 모델은 설명이 직관적인 대신 성능을 일부 희생**한다고 적습니다

## 🔤 먼저 알아야 할 용어

| 용어 | 뜻 |
|---|---|
| **회귀(regression)** | 상관된 하나 이상의 변수로 **종속 목표 변수의 값**을 추정하는 것. 목표값이 연속입니다 |
| **이진 분류** | 속성을 보고 **사전에 정의된 상호 배타적인 두 클래스** 중 하나에 배정하는 지도 학습 |
| **다중 클래스 분류** | 같은 방식으로 **여러 클래스** 중 하나에 배정하는 지도 학습 |
| **클러스터링** | 특정 입력들을 **함께 묶어 전체로 범주화**하는 비지도 학습 기법 |
| **차원 축소** | 데이터셋의 **특성 수를 줄이는** 비지도 기법. 다른 ML 기능의 전처리로 자주 씁니다 |
| **관리형 AI 서비스** | 모델을 직접 만들지 않고 **API 호출로 기능을 쓰는** 서비스. 사전 훈련된 모델을 서비스가 관리합니다 |
| **RAG(검색 증강 생성)** | 데이터 소스의 정보로 **생성된 응답의 관련성과 정확성을 높이는** 기법 |
| **지식 기반(knowledge base)** | 그 RAG를 구현하는 구성 요소. 질의가 들어오면 데이터를 검색해 응답을 보강합니다 |
| **설명 가능성(explainability)** | 모델이 **어떻게 그 결정에 도달했는지** 이해·해석할 수 있는 성질 |
| **운영 제약(operational constraints)** | 모델을 실제로 돌리는 데 드는 인프라·통합·유지보수 요구 |

## 📖 핵심 개념

### 1) AI/ML이 가치를 내는 자리 (목표 1.2.1) {#value}

공식 가이드가 드는 예는 **인간의 의사 결정 지원 · 솔루션 확장성 · 자동화** 셋입니다. 각각의 근거와 **가르는 질문**은 이렇습니다.

| 가치 축 | 공식이 적는 내용 | 가르는 질문 |
|---|---|---|
| **의사 결정 지원** | ML 시스템은 **대용량 데이터를 빠르고 정확하게** 처리하고, 동적·복잡한 데이터에서 **예상치 못한 패턴을 실시간으로** 찾아내 런타임에 데이터 기반 결정을 돕습니다. FM 문서도 **"인간의 의사 결정을 지원하는 능력"**을 들고 임상 진단·의사 결정 지원 시스템·분석을 예로 적습니다 | 사람이 **판단은 하되 근거가 데이터에 묻혀 있는가** |
| **솔루션 확장성** | 공식 조건이 명확합니다 — **"확장할 수 없다"**: 이메일 수백 통은 사람이 스팸인지 판단할 수 있지만 **수백만 통이면 불가능**해지고, ML은 이런 대규모 문제에 효과적입니다 | 사람이 **양을 감당할 수 있는가** |
| **자동화** | ML 알고리즘은 **사람 개입 없이** 데이터를 필터링·정렬·분류하고, 보고서 요약·문서 스캔·오디오 전사·콘텐츠 태깅처럼 **지루하고 시간이 드는 일**을 대신합니다 | 같은 판단을 **반복해서** 내려야 하는가 |

그리고 ML을 쓰는 또 하나의 공식 조건이 **"규칙을 코딩할 수 없다"**입니다. 공식 서술을 그대로 옮기면 이렇습니다 — 이메일이 스팸인지 같은 작업은 **단순한(결정론적) 규칙 기반 해법으로 충분히 풀리지 않습니다.** 답에 영향을 주는 **요인이 너무 많고**, 그 규칙들이 **서로 겹치거나 아주 미세하게 조정**되어야 해서 사람이 정확하게 코딩하기 어려워집니다.

> 즉 1.2.1을 외우는 방법은 **"규칙으로 쓸 수 없다 + 사람 손으로 감당할 수 없다"** 두 조건입니다. 이 둘 중 하나도 성립하지 않으면 다음 절로 갑니다.

### 2) AI/ML 솔루션이 적절하지 않은 경우 (목표 1.2.2) {#not-fit}

이 목표는 시험에서 **"ML을 쓰지 말라"가 정답**이 되는 자리입니다. 공식 근거가 두 갈래로 있습니다.

**갈래 1 — 규칙으로 정해지는 일.** 공식은 못박아 적습니다: **"단순한 규칙, 계산, 또는 사전에 정해진 단계로 목표값을 결정할 수 있고 그것을 데이터 기반 학습 없이 프로그래밍할 수 있다면 ML이 필요하지 않습니다."** 같은 문서가 **"ML은 모든 유형의 문제에 대한 해법이 아니다"**라고 먼저 적습니다.

**갈래 2 — 예측이 아니라 특정 결과가 필요한 일.** ML은 본질적으로 **확률적**이어서 출력이 "이렇게 될 확률이 X%"입니다(작업 1.1에서 다룹니다). 입력이 같으면 **반드시** 같은 값이 나와야 하는 계산에는 규칙 기반 로직이 맞습니다.

**비용-이점 분석**은 공식이 가장 구체적으로 적어 둔 부분입니다. 기계 학습 렌즈는 ML이 **"데이터 준비, 특수 하드웨어, 지속적인 유지보수에 상당한 투자를 요구하며 그것이 비즈니스 가치로 정당화되어야 한다"**고 적고, 비용 항목을 이렇게 나열합니다.

- 데이터 준비·엔지니어링 비용
- 데이터 저장 비용
- 다양한 하드웨어 옵션에서의 **모델 훈련** 비용
- 지도 학습이 필요하다면 **데이터 레이블링** 비용
- 모델 드리프트나 편향 때문에 생기는 **재훈련** 비용
- **모델 호스팅과 추론** 비용
- 지속적인 **유지보수·모니터링** 비용

⚠️ 같은 문서가 **"데이터 사이언티스트 같은 전문 인력이 가장 제약된 자원일 수 있고, 그들의 시간 배분이 중대한 고려 사항"**이라고 적습니다. 비용은 돈만이 아닙니다.

**공식이 드는 갈림길 예시**가 이 절의 핵심입니다.

| 상황 | 공식 판정 | 이유 |
|---|---|---|
| 금융 거래의 **사기 탐지** | ML이 **유리하다** | 사기 행위가 **끊임없이 진화**해서 규칙이 따라가지 못합니다 |
| 단순한 **재고 관리** | **규칙 기반**이 낫다 | 규칙으로 충분히 표현됩니다 |

공식이 적는 안티패턴 네 가지도 그대로 문항이 됩니다 — ① 더 단순한 대안을 평가하지 않고 ML로 직행 ② 데이터 준비·유지보수를 포함한 **총비용 과소평가** ③ 기존 방식이나 규칙 기반과의 **베이스라인 비교를 세우지 않음** ④ 데이터 사이언티스트 가용성·출시 시간 같은 **특수 자원 제약 간과**.

### 3) 사용 사례에 맞는 기법 선택 (목표 1.2.3) {#techniques}

공식이 예로 드는 셋은 **회귀 · 분류 · 클러스터링**입니다. 정의는 공식 문서의 서술을 씁니다.

| 기법 | 공식 정의 | 학습 유형 | 공식이 드는 예 | 가르는 질문 |
|---|---|---|---|---|
| **회귀** | 상관된 하나 이상의 변수·속성으로 **종속 목표 변수의 값을 추정** | 지도 | 욕실·침실 수, 집과 정원 면적으로 **집값 예측** | 맞혀야 하는 값이 **연속**인가 |
| **이진 분류** | 속성을 보고 **사전 정의된 상호 배타적인 두 클래스** 중 하나에 배정 | 지도 | 진단 검사 결과로 **질병 여부** 판정 | 답이 **둘 중 하나**인가 |
| **다중 클래스 분류** | 속성을 보고 **여러 클래스** 중 하나에 배정 | 지도 | 문서와 가장 관련 있는 **주제**(종교·정치·금융 등) 예측 | 답이 **정해진 여러 범주 중 하나**인가 |
| **클러스터링** | 특정 데이터 입력들을 **함께 묶어 전체로 범주화** | 비지도 | **네트워크 트래픽 유형을 식별**해 잠재적 보안 사건을 예측 | 레이블이 **없고** 묶는 것이 목적인가 |

공식이 이 셋을 가르는 축은 **목표값의 수학적 성질**입니다. 데이터에 목표값(출력)이 있으면 지도 학습 문제이고, 그 목표값이 **범주형(수학적으로 이산)**이면 **분류**, **수학적으로 연속**이면 **회귀**입니다. 목표값 자체가 없으면 지도 학습이 아닙니다.

비지도 쪽에는 클러스터링 말고도 공식이 함께 싣는 기법이 있습니다. 1.2.3에 직접 나오지는 않지만 보기로 섞이기 쉬워 한 줄씩 둡니다.

| 비지도 기법 | 하는 일 | 공식이 드는 예 |
|---|---|---|
| **연관 규칙 학습** | 데이터셋 입력 사이의 **규칙 기반 관계**를 찾아냅니다 | 장바구니 분석으로 **커피와 우유가 함께 팔린다**는 규칙 발견 |
| **확률 밀도** | 출력 값이 입력에 대해 **정상 범위 안에 있을 가능성**을 예측합니다 | 서버실 온도계가 분포상 갑자기 낮은 값을 재면 **장비 고장** 신호 |
| **차원 축소** | 데이터셋의 **특성 수를 줄입니다.** 전처리로 복잡도와 오버헤드를 낮춥니다 | 이미지 인식에서 **배경 특성을 흐리거나 잘라내기** |

> ⚠️ **예측(forecasting)은 별도 기법이 아니라 회귀 문제로 떨어지는 경우가 많습니다.** 맞혀야 하는 것이 수량·금액·온도처럼 연속값이면 공식 정의상 회귀입니다. 「예측」이라는 낱말만 보고 새 범주를 만들지 않습니다.

### 4) 실제 AI 애플리케이션의 예시 (목표 1.2.4) {#applications}

공식 목표가 예로 드는 여덟 가지입니다. **무엇을 입력으로 받아 무엇을 내놓는 일인지**로 정리하면 보기 비교가 쉬워집니다.

| 응용 | 하는 일 | 대표 AWS 서비스 |
|---|---|---|
| **컴퓨터 비전** | 이미지·비디오를 분석해 객체·장면·텍스트·얼굴을 검출·분류 | `Amazon Rekognition` — 이미지·비디오 분석 서비스이고 **ML 전문성이 필요 없습니다** |
| **NLP** | 문서에서 엔터티·핵심 구문·감정 같은 인사이트 추출 | `Amazon Comprehend` |
| **음성 인식** | 오디오를 텍스트로 변환 | `Amazon Transcribe` — **자동 음성 인식(ASR)** 서비스 |
| **추천 시스템** | 사용자 데이터로 **항목 추천**을 생성하거나 사용자 세그먼트를 만듦 | `Amazon Personalize` |
| **사기 행위 탐지** | 거래가 사기인지 판정 — **분류 문제**로 떨어집니다 | 공식은 사기 행위가 **끊임없이 진화**하기 때문에 ML이 유리한 전형적 사례로 듭니다 |
| **예측** | 수요·가격·이탈 시점 같은 **연속값**을 추정 — **회귀 문제**로 떨어집니다 | 목표값이 연속이면 회귀입니다(앞 절) |
| **지식 기반** | 사내 데이터를 검색해 FM의 응답을 보강(RAG) | `Amazon Bedrock Knowledge Bases` |
| **에이전틱 AI** | 목표를 받아 **도구와 데이터에 걸쳐 스스로 행동** | `Amazon Bedrock AgentCore` |

**지식 기반을 조금 더 봅니다.** 공식은 FM에게 **일반 지식은 있지만** 우리 회사 데이터는 없다는 점에서 출발합니다. RAG는 **데이터 소스의 정보로 생성된 응답의 관련성과 정확성을 높이는 기법**이고, 지식 기반은 질의가 들어오면 데이터를 검색해 관련 정보를 찾아 응답 생성에 씁니다. 동작은 **두 단계**입니다.

1. **수집(ingestion)** — 데이터 위치를 지정하면 지식 기반이 내부적으로 문서를 가져와 **텍스트 블록으로 청크 분할**하고, 텍스트를 **임베딩으로 변환**해 선택한 **벡터 데이터베이스에 저장**합니다. 임베딩은 Amazon Bedrock이 관리·갱신해 벡터 DB를 데이터와 동기 상태로 유지합니다.
2. **검색과 프롬프트 보강** — 질의를 **임베딩으로 변환**해 지식 기반을 조회하고, **검색 결과를 컨텍스트 정보로 프롬프트에 보강**한 뒤 모델이 생성한 응답을 돌려줍니다.

⚠️ 시험에 쓰이는 성질은 **인용(citation)**입니다. 공식은 지식 기반으로 **생성된 응답에 인용을 포함해 원본 데이터 소스를 참조하고 정확성을 확인할 수 있다**고 적습니다. "출처를 댈 수 있어야 한다"는 요구가 지문에 있으면 이쪽입니다.

> ⚠️ **지식 기반은 이제 두 종류입니다**(2026-11-06 실측 — 공식 페이지가 재구성됐습니다). **관리형 지식 기반(Managed Knowledge Base)**과 **고객 관리형 지식 기반(Customer-managed Knowledge Base)**으로 갈리고, 공식은 페이지 맨 앞 Important 블록에서 **"검색 정확도 최적화와 관리형 경험을 원하면 관리형 지식 기반을 권장한다"**고 적습니다. 위 두 단계 흐름은 **두 유형과 무관하게 참**이지만, "어느 쪽을 고르나"를 묻는 지문이면 **직접 운영할 것이 있느냐**가 갈림길입니다(고객 관리형은 벡터 저장소를 포함한 RAG 파이프라인과 설정을 직접 운영합니다). 자세한 갈림길은 `aif-t3-1`에 있습니다.

**에이전틱 AI 쪽**의 정본은 `Amazon Bedrock AgentCore`입니다. 공식은 이를 **"어떤 프레임워크와 파운데이션 모델로든 매우 효과적인 에이전트를 안전하게 대규모로 구축·배포·운영하는 에이전틱 플랫폼"**으로 정의하고, **인프라 관리 없이** 에이전트가 적절한 권한과 거버넌스 아래 **도구와 데이터에 걸쳐 행동**하게 하고 프로덕션에서 **성능과 품질을 모니터링**할 수 있다고 적습니다. 세부는 도메인 2에서 다룹니다.

### 5) AWS 관리형 AI/ML 서비스의 기능 (목표 1.2.5) {#managed-services}

공식 목표가 이름을 적는 여섯 개입니다. **입력 → 출력**으로 외웁니다.

| 서비스 | 입력 → 출력 | 공식이 적는 정체 | 기억할 성질 |
|---|---|---|---|
| **Amazon SageMaker AI** | 데이터 → **직접 만든 모델** | **완전 관리형 ML 서비스.** ML 모델을 **구축·훈련·배포**해 프로덕션 준비된 호스팅 환경에 올립니다 | 관리형 API 서비스가 아니라 **모델을 만드는 쪽**입니다. 자체 알고리즘·프레임워크 지원 |
| **Amazon Transcribe** | 오디오 → **텍스트** | **자동 음성 인식 서비스.** ML 모델로 오디오를 텍스트로 변환합니다 | **실시간(스트리밍)**과 **Amazon S3의 미디어 파일(배치)** 두 방식. 화자 분리·다중 채널 분석·콘텐츠 필터링 |
| **Amazon Translate** | 텍스트 → **다른 언어 텍스트** | **텍스트 번역 서비스.** 고품질 번역을 온디맨드로 제공합니다 | 비정형 텍스트 문서 번역, 다국어 애플리케이션 구축 |
| **Amazon Comprehend** | 문서 → **인사이트** | **NLP로 문서 내용에 대한 인사이트를 추출**합니다 | 엔터티 · 핵심 구문 · **PII** · 언어 · 감정 · **대상 지정 감정** · 구문. **사전 훈련 모델이라 훈련 데이터를 줄 필요가 없습니다** |
| **Amazon Lex** | 음성·텍스트 → **의도와 대화 응답** | 음성과 텍스트로 **대화형 인터페이스를 구축**하는 서비스 | **NLU + ASR**을 합쳐 SLU를 만듭니다. 딥 러닝 전문성 없이 봇을 만들고, 대화 흐름을 콘솔에서 지정 |
| **Amazon Polly** | 텍스트 → **음성** | 텍스트를 **실제 같은 음성으로 변환**하는 클라우드 서비스 | TTS 음성 옵션이 **생성형·롱폼·신경망·표준** 네 갈래. **합성한 음성을 캐시해 재생하는 데 추가 비용이 없습니다** |

**이 여섯이 서로 맞물리는 방식**이 공식 문서에 있습니다. Amazon Translate 페이지는 다른 서비스와의 통합을 이렇게 적습니다 — Amazon Comprehend로 비정형 텍스트에서 **엔터티·감정·핵심 구문을 추출**하고, Amazon Transcribe로 **여러 언어의 자막과 실시간 캡션**을 만들고, Amazon Polly로 **번역된 내용을 말하게** 합니다. 그래서 "영어 회의 녹음을 한국어 음성 안내로"는 **Transcribe → Translate → Polly** 세 단계입니다.

⚠️ **`Amazon SageMaker`와 `Amazon SageMaker AI`는 다른 것을 가리킵니다.** 공식 서술이 명확합니다 — **2024년 12월 3일에 Amazon SageMaker가 Amazon SageMaker AI로 이름이 바뀌었고**, 같은 날 **차세대 Amazon SageMaker**가 데이터·분석·AI를 묶은 **통합 플랫폼**으로 출시됐습니다. 그 플랫폼 안에서 모델을 구축·훈련·배포하는 구성 요소가 **Amazon SageMaker AI**입니다. 그리고 두 가지를 더 기억합니다.

- **개명은 기존 기능 이름에 적용되지 않습니다.** 공식이 **"이 이름 변경은 기존 Amazon SageMaker 기능 어디에도 적용되지 않는다"**고 적습니다. 그래서 `SageMaker JumpStart`는 그대로이고 `SageMaker AI JumpStart`는 틀린 표기입니다.
- **API 네임스페이스도 그대로입니다.** 하위 호환을 위해 `sagemaker` API 네임스페이스, AWS CLI 명령, `AmazonSageMaker` 접두어 관리형 정책, 서비스 엔드포인트, `AWS::SageMaker` CloudFormation 리소스가 바뀌지 않았습니다.

공식 목표의 괄호는 **"예"**이므로 여섯 개로 끝이 아닙니다. 범위 내 목록에 있는 다음 서비스도 같은 축으로 정리해 둡니다.

| 서비스 | 입력 → 출력 | 기억할 성질 |
|---|---|---|
| **Amazon Rekognition** | 이미지·비디오 → **검출·분석 결과** | 객체·장면·텍스트·부적합 콘텐츠·얼굴. **Face Liveness**는 얼굴 기반 신원 확인에서 **사기를 억제**하는 기능으로, 인쇄 사진·딥페이크 같은 스푸핑 공격 탐지를 돕습니다 |
| **Amazon Personalize** | 상호작용 데이터 → **항목 추천 / 사용자 세그먼트** | **대부분의 사용 사례에서 항목 상호작용 데이터**를 주로 씁니다(사용자가 항목을 클릭한 기록 등). 실시간 개인화 API와 대량 배치 작업을 모두 제공 |
| **Amazon Nova** | 텍스트·이미지·비디오 → **텍스트** 또는 **이미지·비디오** | 이해 모델(Micro·Lite·Pro)은 텍스트·이미지·비디오를 받아 텍스트를 내고, 생성 모델(Canvas·Reel)은 텍스트·이미지를 받아 이미지·비디오를 냅니다 |

⚠️ **입력 형식 함정이 Comprehend에 있습니다.** 공식은 **"Amazon Comprehend의 모든 기능이 입력으로 UTF-8 텍스트 문서를 받는다"**고 적고, **이미지 파일·PDF 파일·Word 파일을 추가로 받는 것은 사용자 지정 분류와 사용자 지정 엔터티 인식뿐**이라고 적습니다. 스캔된 PDF 더미에 바로 감정 분석을 돌릴 수 없습니다.

### 6) 기존 ML 모델인가 FM인가 (목표 1.2.6) {#ml-vs-fm}

공식 목표가 드는 판단 축은 **규제 문제 · 설명 가능성 요구 사항 · 운영 제약 조건** 셋입니다.

**FM 쪽의 공식 논거는 속도와 비용**입니다. 공식은 FM을 처음부터 개발하는 데는 수백만 달러가 들지만, **"데이터 과학자가 사전 훈련된 FM을 써서 새 ML 애플리케이션을 개발하는 것이 고유 ML 모델을 처음부터 훈련하는 것보다 빠르고 저렴하다"**고 적습니다. 그리고 FM이 **사전 훈련됐더라도 추론 시점에 입력·프롬프트에서 계속 배울 수 있다**는 점, 명시적으로 훈련받지 않은 주제의 프롬프트에도 일관되게 응답할 수 있다는 점을 듭니다.

**그 FM의 공식 약점**이 그대로 운영 제약입니다.

| 공식이 적는 FM의 과제 | 판단에 쓰이는 방식 |
|---|---|
| **인프라 요구** | 처음부터 구축하면 비용이 크고 자원이 막대하며 **훈련에 수개월**이 걸립니다 |
| **프런트엔드 개발** | 실용화하려면 프롬프트 엔지니어링·파인 튜닝·파이프라인 엔지니어링 도구를 포함해 **소프트웨어 스택에 통합**해야 합니다 |
| **이해 부족** | 문법적·사실적으로 맞는 답을 주면서도 **프롬프트의 맥락을 이해하기 어려워**하고 사회적·심리적으로 인식하지 못합니다 |
| **신뢰할 수 없는 답변** | 특정 주제의 답변이 신뢰할 수 없거나 부적절·유해·부정확할 수 있습니다 |
| **편향** | 훈련 데이터셋에서 혐오 표현이나 부적절한 어조를 **습득할 가능성**이 있습니다 |

**기존 ML 모델 쪽의 공식 논거는 설명 가능성**입니다. 공식 서술이 이 절의 핵심 문장입니다 — **"모델 복잡도와 설명 가능성 사이의 트레이드오프가 핵심 고려 사항"**이고, **심층 신경망 같은 복잡한 모델은 더 높은 정확도를 낼 수 있지만 해석하기 어려운 경우가 많고, 결정 트리나 선형 회귀 같은 더 단순한 모델은 더 직관적인 설명을 주는 대신 성능을 일부 희생할 수 있습니다.**

**규제 축**도 같은 문서가 적습니다. 설명 가능성은 **규제 산업**과 **결정이 개인에게 영향을 주는 애플리케이션**에서 특히 중요하고, 안티패턴에는 **"비즈니스나 규제가 설명 가능성을 요구하는데도 해석 가능성보다 모델 성능 지표를 우선시하는 것"**과 **"더 단순하고 해석 가능한 대안이 비즈니스 요구를 충족하는데도 복잡한 모델을 쓰는 것"**이 들어 있습니다.

공식이 드는 **대비 예시 한 쌍**이 문항으로 거의 그대로 나옵니다.

| 상황 | 공식 판정 |
|---|---|
| **신용 승인 시스템** | 신청이 **거절된 이유에 대한 명확한 설명**이 필요할 수 있습니다 → 설명 가능성 우선 |
| **제조 품질 관리 시스템** | 설명 가능성보다 **정확도를 우선**할 수 있습니다 |

정리하면 가르는 질문은 셋입니다.

| 축 | 가르는 질문 | 기울어지는 쪽 |
|---|---|---|
| **규제** | 결정의 근거를 **규제 기관·감사에 제출**해야 하는가 | 설명 가능한 기존 ML 모델 |
| **설명 가능성** | 개별 예측에 대해 **왜 그런가**를 사람에게 답해야 하는가 | 결정 트리·선형 회귀 같은 단순 모델 |
| **운영 제약** | 전용 모델을 **훈련·유지할 데이터와 인력·시간**이 있는가 | 없으면 사전 훈련된 FM 또는 관리형 AI 서비스 |

## ✍️ 시험 포인트

- **1.2.2 문항은 "AI를 쓰지 않는다"가 정답일 수 있습니다.** 지문에 **"규칙으로 완전히 정해진다"**거나 **"입력이 같으면 반드시 같은 값"**이 있으면 그쪽입니다.
- **비용-이점 문항**은 훈련 비용만 세게 하지 않습니다 — **레이블링 · 호스팅 · 재훈련 · 유지보수**와 **전문 인력의 시간**까지 공식 목록에 있습니다.
- **기법 선택 문항**은 **목표값의 형태** 한 줄로 갈립니다. 금액·수량이면 회귀, 범주면 분류, 레이블이 없으면 클러스터링입니다.
- **「예측」이라는 낱말에 속지 않습니다** — 맞혀야 하는 값이 연속이면 공식 정의로는 회귀 문제입니다.
- **서비스 선택 문항**은 **입력 데이터의 형태**부터 봅니다. 오디오면 Transcribe, 텍스트의 의미면 Comprehend, 언어 변환이면 Translate, 소리를 내야 하면 Polly, 대화를 주고받아야 하면 Lex, 이미지·비디오면 Rekognition입니다.
- **"모델을 직접 만들어야 하는가"**가 SageMaker AI와 관리형 AI 서비스를 가릅니다. 사전 훈련된 기능으로 충분하면 관리형 서비스가 운영 부담이 작습니다.
- **"출처를 확인할 수 있어야 한다"**는 요구는 지식 기반(RAG)의 **인용** 성질을 가리킵니다.
- **1.2.6 문항**은 셋 중 하나를 지문에 심어 둡니다 — **규제 제출 · 개별 예측 설명 · 모델을 만들 자원**. 설명 요구가 보이면 단순·해석 가능한 모델, 자원 제약이 보이면 사전 훈련 FM입니다.

## ⚠️ 흔한 함정 {#pitfalls}

- ❌ **"AI/ML을 쓰는 쪽이 항상 더 나은 설계다"** → 공식은 **"ML은 모든 유형의 문제에 대한 해법이 아니다"**라고 적고, 더 단순한 대안을 평가하지 않는 것을 **안티패턴**으로 둡니다.
- ❌ **"ML 비용은 곧 훈련 비용이다"** → 공식 비용 목록에는 데이터 준비·저장·**레이블링**·호스팅·추론·**재훈련**·모니터링이 함께 있습니다.
- ❌ **"클러스터링으로 고객의 구매 금액을 예측한다"** → 클러스터링은 **묶는** 비지도 기법입니다. 연속값 추정은 **회귀**입니다.
- ❌ **"분류는 한 종류다"** → 공식은 **이진 분류와 다중 클래스 분류를 구분하는 것이 표준 관행**이라고 적습니다.
- ❌ **"Amazon Comprehend에 스캔 PDF를 넣어 감정 분석을 한다"** → 기본 기능은 **UTF-8 텍스트만** 받습니다. PDF·이미지·Word는 **사용자 지정 분류·사용자 지정 엔터티 인식**에서만 입력이 됩니다.
- ❌ **"Amazon Transcribe는 배치 전용이다"** → **실시간 스트리밍**과 **S3 미디어 파일 배치** 둘 다 됩니다.
- ❌ **"Amazon Lex는 음성을 텍스트로 바꾸는 서비스다"** → 그건 Transcribe입니다. Lex는 **의도를 이해해 대화를 진행**하는 대화형 인터페이스 서비스입니다(내부에 ASR과 NLU를 함께 씁니다).
- ❌ **"`Amazon SageMaker AI JumpStart`가 맞는 표기다"** → 개명은 **기존 기능 이름에 적용되지 않습니다.** `SageMaker JumpStart`가 맞습니다.
- ❌ **"FM이 더 크고 새로우니 어떤 사용 사례에도 더 낫다"** → 공식은 FM의 과제로 **인프라 요구·통합 부담·맥락 이해 부족·신뢰할 수 없는 답변·편향**을 적고, 설명 가능성이 요구되는 자리에서는 **더 단순한 모델**을 권합니다.
- ❌ **"설명 가능성은 항상 최우선이다"** → 공식 예시가 그렇지 않다고 적습니다. **제조 품질 관리**는 정확도를 우선할 수 있고, **신용 승인**은 설명이 필요합니다. 요구는 사용 사례가 정합니다.

## 🧪 자가 점검

**Q1.** 배송비가 「무게 × 구간 단가 + 지역 고정 할증」으로 완전히 정해집니다. 담당자가 "요즘 다들 AI를 쓰니 배송비도 ML로 예측하자"고 제안합니다. 공식 근거로 답하세요. (→ 2) AI/ML 솔루션이 적절하지 않은 경우)

<details><summary>정답 보기</summary>

**ML을 쓸 이유가 없습니다.** 공식은 **"단순한 규칙, 계산, 또는 사전에 정해진 단계로 목표값을 결정할 수 있고 그것을 데이터 기반 학습 없이 프로그래밍할 수 있다면 ML이 필요하지 않습니다"**라고 적고, 같은 문서가 먼저 **"ML은 모든 유형의 문제에 대한 해법이 아니다"**라고 못박습니다.

여기에 더해 이 요구는 **결정론적**입니다. 같은 무게·같은 지역이면 **반드시** 같은 금액이 나와야 하므로, 확률적 출력을 내는 ML은 요구 자체와 맞지 않습니다. 공식 목표 1.2.2가 드는 예 — **"예측 대신 특정 결과가 필요한 상황"** — 이 바로 이것입니다.
</details>

**Q2.** 같은 고객 데이터로 세 가지를 하려고 합니다. ① 다음 달 결제 금액(원)을 맞힌다 ② 이탈할지 여부를 맞힌다 ③ 레이블이 전혀 없는 상태에서 비슷한 고객끼리 묶는다. 각각 어떤 기법이고 무엇으로 갈랐나요? (→ 3) 사용 사례에 맞는 기법 선택)

<details><summary>정답 보기</summary>

① **회귀** ② **이진 분류** ③ **클러스터링**입니다.

가른 축은 **목표값의 성질**입니다. 공식은 데이터에 목표값(출력)이 있으면 지도 학습 문제이고, 그 목표값이 **범주형(수학적으로 이산)**이면 **분류**, **수학적으로 연속**이면 **회귀**라고 적습니다. 회귀는 **"상관된 하나 이상의 변수로 종속 목표 변수의 값을 추정"**하는 것입니다.

②는 답이 **상호 배타적인 두 클래스**라서 이진 분류입니다(공식은 이진과 다중 클래스를 구분하는 것이 표준 관행이라고 적습니다). ③은 목표값이 아예 없고 **입력들을 묶어 전체로 범주화**하는 일이므로 비지도 기법인 클러스터링입니다.
</details>

**Q3.** 영어로 진행된 회의 녹음을 받아 **한국어 자막**과 **한국어 음성 안내**를 만들어야 합니다. 어떤 관리형 서비스를 어떤 순서로 쓰나요? (→ 5) AWS 관리형 AI/ML 서비스의 기능)

<details><summary>정답 보기</summary>

**Amazon Transcribe → Amazon Translate → Amazon Polly** 순서입니다.

입력과 출력으로 그대로 이어집니다 — Transcribe는 **오디오를 텍스트로** 변환하는 자동 음성 인식 서비스이고, Translate는 **텍스트를 다른 언어 텍스트로** 번역하며, Polly는 **텍스트를 음성으로** 변환합니다.

공식 Amazon Translate 문서가 이 조합을 직접 적습니다 — Amazon Transcribe로 **여러 언어의 자막과 실시간 캡션**을 만들 수 있고, Amazon Polly로 **번역된 내용을 말하게** 할 수 있다고 적습니다.
</details>

**Q4.** 스캔된 계약서 PDF 2만 건이 있습니다. "Amazon Comprehend에 그대로 넣어 감정 분석을 돌리면 된다"는 계획을 검토하세요. (→ 5) AWS 관리형 AI/ML 서비스의 기능)

<details><summary>정답 보기</summary>

**그대로는 안 됩니다.** 공식은 **"Amazon Comprehend의 모든 기능이 입력으로 UTF-8 텍스트 문서를 받는다"**고 적고, **이미지 파일·PDF 파일·Word 파일을 추가로 받는 것은 사용자 지정 분류와 사용자 지정 엔터티 인식뿐**이라고 적습니다. 감정 탐지는 사전 훈련 모델이 제공하는 인사이트이고 그쪽 입력은 텍스트입니다.

참고로 Comprehend가 사전 훈련 모델로 내놓는 인사이트는 **엔터티 · 핵심 구문 · PII · 언어 · 감정 · 대상 지정 감정 · 구문**이고, 이 모델은 대량의 텍스트로 계속 훈련되므로 **훈련 데이터를 따로 줄 필요가 없습니다.**
</details>

**Q5.** 대출 거절 건에 대해 금융 감독 기관이 **개별 거절 사유**를 요구합니다. 팀은 정확도가 가장 높았던 심층 신경망 모델을 쓰고 싶어 합니다. 공식 서술을 근거로 판단하세요. (→ 6) 기존 ML 모델인가 FM인가)

<details><summary>정답 보기</summary>

**설명 가능성이 요구를 지배하므로 해석 가능한 모델 쪽으로 기울여야 합니다.**

공식은 **"모델 복잡도와 설명 가능성 사이의 트레이드오프가 핵심 고려 사항"**이라고 적고, **심층 신경망 같은 복잡한 모델은 더 높은 정확도를 낼 수 있지만 해석하기 어려운 경우가 많고, 결정 트리나 선형 회귀 같은 더 단순한 모델은 더 직관적인 설명을 주는 대신 성능을 일부 희생할 수 있다**고 적습니다.

같은 문서가 안티패턴으로 **"비즈니스나 규제가 설명 가능성을 요구하는데도 해석 가능성보다 모델 성능 지표를 우선시하는 것"**을 들고, 대비 예시로 **신용 승인 시스템은 신청이 거절된 이유에 대한 명확한 설명이 필요할 수 있지만 제조 품질 관리 시스템은 설명 가능성보다 정확도를 우선할 수 있다**고 적습니다. 지금은 앞쪽입니다.
</details>

**Q6.** 사내 정책 문서 수천 건을 근거로 직원 질문에 답하는 도우미를 만들려고 합니다. 답변에는 **어느 문서에서 나온 말인지**가 함께 보여야 합니다. 어떤 접근이고 내부적으로 무슨 일이 일어나나요? (→ 4) 실제 AI 애플리케이션의 예시)

<details><summary>정답 보기</summary>

**지식 기반을 둔 RAG**이고, AWS에서는 `Amazon Bedrock Knowledge Bases`가 그 구성 요소입니다. 공식은 FM에게 **일반 지식은 있다**는 데서 출발해, RAG를 **데이터 소스의 정보로 생성된 응답의 관련성과 정확성을 높이는 기법**으로 정의합니다.

동작은 **두 단계**입니다.

1. **수집(ingestion)** — 데이터 위치를 지정하면 지식 기반이 내부적으로 문서를 가져와 **텍스트 블록으로 청크 분할**하고, 텍스트를 **임베딩으로 변환**해 선택한 **벡터 데이터베이스에 저장**합니다. 임베딩은 Amazon Bedrock이 관리·갱신해 벡터 DB를 데이터와 동기 상태로 유지합니다.
2. **검색과 프롬프트 보강** — 질의를 **임베딩으로 변환**해 지식 기반을 조회하고, **검색 결과를 컨텍스트 정보로 프롬프트에 보강**한 뒤 모델이 생성한 응답을 돌려줍니다.

문제가 요구한 "어느 문서에서 나왔는지"가 결정적입니다 — 공식은 지식 기반으로 **생성된 응답에 인용을 포함해 원본 데이터 소스를 참조하고 정확성을 확인할 수 있다**고 적습니다.
</details>
