# ML 개발 수명 주기 (파이프라인 단계·모델 소스·프로덕션 사용·서비스 매핑·MLOps·지표)

> **커버하는 공식 Task** — AIF-C01 · 도메인 1 「AI 및 ML의 기초」(20%) · **작업 1.3 ML 개발 수명 주기 설명** (`aif-t1-3`)
> 이 문서는 위 한 작업에 1:1로 매핑되고 공식 목표 6개(1.3.1~1.3.6)를 모두 덮습니다. 작업 1.1이 **낱말**이었다면 1.3은 **순서와 선택**입니다. 단계 이름을 외우는 공부가 아니라 **각 단계가 무엇을 받아 무엇을 내놓는지**를 손에 쥐는 것이 목표입니다.

> ⚠️ **가이드 v1.1에서 바뀐 것** — 목표 1.3.1이 단계 열거에서 **"구성 요소 설명 및 구분"**으로 축약됐습니다(외우는 문제 → **가르는** 문제). 목표 1.3.4의 서비스 예시는 SageMaker 하위 기능 열거에서 **Amazon Bedrock · Amazon Quick · Kiro · SageMaker AI**로 교체됐습니다. 목표 1.3.6에서는 **AUC가 빠지고 정밀도·재현율이 들어왔습니다** — 지표 공부는 정확도·정밀도·재현율·F1 네 개에 집중합니다.

## ✅ 학습 목표 체크리스트

- [ ] AI/ML 파이프라인 단계를 **입력과 산출물**로 구분하고, 단계가 **순차적이지 않다**는 것을 안다
- [ ] 모델 소스 세 갈래(사전 훈련 오픈 소스 · 관리형 FM API · 사용자 지정 훈련)를 고르는 기준을 말할 수 있다
- [ ] **관리형 API**와 **자체 호스팅 엔드포인트**를 인프라·과금·제어·전문성 네 축으로 가른다
- [ ] 파이프라인 각 단계에 붙는 AWS 서비스를 **그 단계의 일**로 설명한다
- [ ] MLOps의 **네 가지 원칙**과 성숙도 레벨 0·1·2, 그리고 **기술 부채**가 왜 생기는지 안다
- [ ] 정확도 · 정밀도 · 재현율 · F1이 **각각 무엇을 재는지** 말하고 혼동 짝을 가른다
- [ ] 기술 지표와 비즈니스 지표(사용자당 비용 · 개발 비용 · 고객 피드백 · ROI)를 **연결**한다

## 🎯 왜 중요한가

작업 1.3의 문항은 "이 단계에서 할 일은?" 또는 "이 상황에 어떤 배포 방식인가?"로 나옵니다. 둘 다 **단계의 경계**를 알면 풀리고, 모르면 그럴듯한 보기 네 개 중에서 헤맵니다.

그리고 이 작업은 다른 네 도메인의 **뼈대**입니다. 도메인 3의 파운데이션 모델 적용은 "모델 소스 선택 → 커스터마이징 → 평가 → 배포"라는 이 파이프라인을 FM에 맞게 특수화한 것이고, 도메인 4·5의 거버넌스·모니터링은 여기서 배우는 **MLOps 원칙**이 그대로 쓰입니다. 1.3을 건너뛰면 뒤의 세 도메인이 따로 떨어진 암기 과목이 됩니다.

공식 문서가 되짚는 사실 하나를 먼저 짚습니다. AWS Prescriptive Guidance는 ML을 프로덕션에 올리는 일이 **"표준 소프트웨어 개발 프로젝트에서는 생기지 않는 많은 문제를 가져온다"**고 적고, ML 실무자가 소프트웨어 공학 배경이 아닌 경우가 많아 테스트 가능한 코드·모듈화·버전 관리 같은 관행에 익숙하지 않다고 지적합니다. 그 결과가 **기술 부채**입니다. MLOps는 이 부채를 막으려고 생긴 규율입니다.

## ⚡ 시험 직전 요약

> 시험 직전에 이 열 줄만 다시 봅니다. 근거와 맥락은 아래 본문에 있습니다.

- **공식 수명 주기는 6단계**입니다 — 비즈니스 목표 식별 → ML 문제 정의 → 데이터 처리 → 모델 개발 → 모델 배포 → 모델 모니터링
- ⚠️ **단계는 순차적이지 않습니다** — 공식은 **"반드시 순차적이지 않으며 피드백 루프를 가질 수 있다"**고 적습니다. "앞 단계로 되돌아갈 수 없다"는 보기는 틀립니다
- **ML 문제 정의 단계의 핵심 산출물**은 "무엇을 관측하고 무엇을 예측할지"(레이블 · 대상 변수)와 **최적화할 성능·오차 지표**입니다
- **모델 소스 세 갈래**: 사전 훈련 오픈 소스(`SageMaker JumpStart`) · 관리형 FM API(`Amazon Bedrock`) · 사용자 지정 훈련(`SageMaker AI` 훈련 작업·HyperPod)
- ⚠️ **오픈 소스 모델의 라이선스 검토는 사용자 책임**입니다 — 공식이 **"적용되는 라이선스 조건을 검토하고 준수할 책임은 귀하에게 있다"**고 명시합니다
- **관리형 API(Bedrock)는 서버리스**라 인프라 관리가 없고 **토큰당 과금**입니다. **자체 호스팅(SageMaker AI 엔드포인트)**은 **비용·처리량·지연의 트레이드오프를 직접 관리**할 때 고릅니다
- **MLOps 네 원칙**: 버전 관리 · 자동화 · Continuous X · 모델 거버넌스. **Continuous X는 CI · CD · 지속적 훈련 · 지속적 모니터링** 네 가지입니다
- **드리프트는 두 종류**: **데이터 드리프트**(입력 데이터 분포 변화) ↔ **개념 드리프트**(입력과 출력의 관계 변화). 재훈련은 **필요할 때만** 합니다
- **지표 네 개**: 정확도(전체 중 맞힌 비율) · 정밀도 `TP/(TP+FP)` · 재현율 `TP/(TP+FN)` · F1(정밀도와 재현율의 **조화 평균**)
- ⚠️ **불균형 데이터에서 정확도만 보면 속습니다** — 공식 예가 **"이메일의 1%만 스팸인" 데이터셋**이고, 이때는 `BalancedAccuracy` 쪽이 더 나은 측정입니다. **재현율만 보는 것도 불충분**합니다(전부 양성으로 답하면 재현율이 완벽해집니다)

## 🔤 먼저 알아야 할 용어

| 용어 | 뜻 |
|---|---|
| **AI/ML 파이프라인** | 비즈니스 목표에서 프로덕션 모니터링까지 이어지는 단계들의 묶음. 공식은 이것을 **수명 주기**라고 부르고 **반복적·순환적**이라고 적습니다 |
| **특성 엔지니어링(feature engineering)** | 데이터에서 변수를 **생성·변환·추출·선택**하는 과정. 데이터 처리 단계에 속합니다 |
| **검증 세트(validation set)** | 훈련에 쓰지 않고 떼어 둔 데이터. 모델이 **훈련 데이터를 넘어 일반화하는지** 확인하는 데 씁니다 |
| **추론 엔드포인트** | 애플리케이션이 요청 페이로드를 보내 예측을 받는 프로덕션 접점 |
| **모델 레지스트리** | 모델 버전과 메타데이터(용도 그룹, 성능 지표 기준선)를 중앙에서 추적하는 저장소 |
| **특성 저장소(feature store)** | 특성을 이름 붙여 저장·재사용하는 저장소. **훈련과 실시간 추론에서 같은 특성**을 쓰게 합니다 |
| **데이터 드리프트** | 입력 데이터의 **분포**가 훈련 때와 달라지는 것 |
| **개념 드리프트** | 입력과 출력(대상 변수) **사이의 관계**가 달라지는 것 |
| **지속적 훈련(CT)** | 재배포를 위해 모델을 **자동으로 재훈련**하는 활동. MLOps의 Continuous X 중 하나입니다 |
| **TP · FP · FN** | 참 양성 · 거짓 양성(실제로는 음성인데 양성이라 예측) · 거짓 음성(실제로는 양성인데 음성이라 예측) |
| **기술 부채** | 테스트·모듈화·버전 관리 없이 쌓인 결과물이 시간이 갈수록 **복잡해지고 유지하기 어려워지는** 상태 |

## 📖 핵심 개념

### 1) AI/ML 파이프라인의 구성 요소 (목표 1.3.1) {#pipeline}

AWS Well-Architected 머신러닝 렌즈가 **6단계**로 정리합니다. v1.1이 "설명 및 **구분**"으로 바꿨으니, 외우는 대상은 이름이 아니라 **경계**입니다.

| 단계 | 무엇을 받는가 | 무엇을 내놓는가 | 가르는 질문 |
|---|---|---|---|
| **비즈니스 목표 식별** | 풀려는 문제와 그 사업적 가치 | **측정 가능한 비즈니스 목표와 성공 기준** | 성공을 숫자로 말할 수 있는가 |
| **ML 문제 정의** | 비즈니스 문제 | **무엇을 관측하고 무엇을 예측할지**(레이블·대상 변수) + 최적화할 성능·오차 지표 | 예측 대상이 정해졌는가 |
| **데이터 처리** | 원천 데이터 | 사용 가능한 형식의 데이터 + **특성** | 데이터가 모델에 들어갈 모양인가 |
| **모델 개발** | 처리된 데이터 | 훈련·튜닝·평가를 통과한 **모델 아티팩트** | 검증 세트에서 성능이 기준을 넘었는가 |
| **모델 배포** | 검증된 모델 | **예측을 내놓는 프로덕션 엔드포인트** | 애플리케이션이 호출할 수 있는가 |
| **모델 모니터링** | 프로덕션 입력·예측 | 드리프트·품질 저하 **경보**와 재훈련 신호 | 성능이 유지되고 있는가 |

데이터 처리는 **데이터 수집 · 데이터 준비(전처리·특성 엔지니어링)** 하위 단계로 다시 갈라집니다. 모델 개발은 **구축 · 훈련 · 튜닝 · 평가**이고, 공식 문서는 모델 작업 쪽을 **데이터 전처리 → 모델 훈련 → 모델 평가 → 최적화** 네 묶음으로도 설명합니다. 평가 단계의 목적은 한 문장으로 요약됩니다 — **"모델이 훈련 데이터셋을 넘어 일반화할 수 있는지 확인하는 것"**이고, 그래서 **검증 세트**라는 별도 데이터셋을 씁니다.

> ⚠️ **가장 자주 나오는 함정은 "순서"입니다.** 공식은 **"수명 주기의 단계들은 반드시 순차적이지 않으며 피드백 루프를 가질 수 있다"**고 명시합니다. 모니터링에서 발견한 드리프트가 데이터 처리나 모델 개발로 되돌아가는 것이 정상 동작입니다.

### 2) ML 모델의 소스 (목표 1.3.2) {#model-sources}

공식 목표가 드는 예가 **"사전 훈련된 오픈 소스 모델"**과 **"사용자 지정 모델 훈련"** 둘인데, 실무에서는 그 사이에 **관리형 FM API**가 있습니다. 세 갈래로 보면 선택이 쉬워집니다.
> ⚠️ **영문 가이드는 이 목표를 「FM 모델의 소스」로 적습니다.** 한국어판은 **「ML 모델의 소스 설명」**인데 영문판은 **"Describe sources of FM models"**입니다(둘 다 2026-11-03 실측). 그래서 이 절은 **전통 ML 모델만의 이야기가 아닙니다** — 아래 세 갈래가 FM에도 그대로 적용되고, 실제로 가운데 칸이 관리형 FM API입니다. 절 제목은 한국어 목표를 따르지만 **범위는 영문 쪽으로 읽는 것이 안전합니다.**

| 소스 | 대표 경로 | 공식이 적는 성격 | 고르는 상황 |
|---|---|---|---|
| **사전 훈련 오픈 소스** | `SageMaker JumpStart` | **"다양한 문제 유형에 대한 사전 훈련된 오픈 소스 모델을 제공"**하고, 배포 전에 **점진적으로 훈련·튜닝**할 수 있습니다 | 비슷한 문제가 이미 풀려 있고, 가중치를 손에 쥐고 싶을 때 |
| **관리형 FM API** | `Amazon Bedrock` | **"Amazon과 주요 AI 기업의 파운데이션 모델을 API로 제공하는 완전관리형 서비스"** | 모델을 직접 만들 생각이 없고 빠르게 실험·배포하고 싶을 때 |
| **사용자 지정 훈련** | `Amazon SageMaker AI`(훈련 작업 · HyperPod) | **"어떤 사용 사례든 ML 모델을 구축·훈련·배포"**하고, 컨테이너·오케스트레이션 계층까지 제어 | 데이터와 위험 요인이 고유해 처음부터 만들어야 할 때 |

공식 결정 가이드는 이 셋을 **배타적 선택이 아니라 단계적 여정**으로 설명합니다 — **프롬프트 엔지니어링과 RAG로 시작(Bedrock) → 프롬프팅으로 안 되는 행동 변화가 필요하면 서버리스 커스터마이징(SFT·DPO) → 보상 신호 최적화가 필요하면 강화 학습(RLVR·RLAIF) → 인프라 전면 제어가 필요하면 훈련 작업이나 HyperPod**. 그리고 SageMaker AI에서 훈련한 사용자 지정 모델은 **SageMaker AI 엔드포인트로 배포**하거나 **Bedrock에 가져와(custom model import) 서버리스 추론**으로 쓸 수 있습니다.

> ⚠️ **오픈 소스 모델을 쓸 때의 책임 소재가 문항이 됩니다.** JumpStart 문서는 **"서드파티 콘텐츠를 다운로드하거나 사용하기 전에: 적용되는 라이선스 조건을 검토하고, 그것이 귀하의 사용 사례에 수용 가능한지 확인할 책임은 귀하에게 있습니다"**라고 적습니다. "AWS가 라이선스를 대신 검토해 준다"는 보기는 틀립니다.

### 3) 프로덕션 환경에서 모델을 사용하는 방법 (목표 1.3.3) {#production-use}

목표가 드는 예가 **관리형 API 서비스**와 **자체 호스팅 API** 둘입니다. 공식 결정 가이드의 비교 표가 가르는 축을 그대로 줍니다.

| 축 | **관리형 API** (`Amazon Bedrock`) | **자체 호스팅** (`Amazon SageMaker AI` 엔드포인트) |
|---|---|---|
| 인프라 | **서버리스** — 공식은 **"인프라를 관리하지 않아도 된다"**고 적습니다 | 전용 엔드포인트. 훈련 작업·HyperPod는 **노드 수준까지 제어** |
| 과금 | **처리한 입력·출력 토큰 기준 종량제**이고 **Priority · Flex · Reserved 서비스 계층**을 고를 수 있습니다 | **자리에 따라 둘로 갈립니다** — **서버리스 모델 커스터마이징은 토큰당**(공식은 "Bedrock과 같은 요금 단순성"이라고 적습니다), **관리형 훈련 작업 · 추론 · HyperPod는 컴퓨팅·스토리지 사용량 기준**(인스턴스 유형·크기에 따라 다름) |
| 통합 | **사전 훈련 모델을 API 호출로** 애플리케이션에 통합 | **사용자 지정 모델**을 통합, 선택지가 더 많습니다 |
| 필요한 전문성 | 사전 훈련 모델을 쓰는 데 **기본적인 ML 전문성** | 고급 훈련 작업에는 **더 깊은 ML 전문성**이 도움 |
| 대상 사용자 | 기술 의사결정자 · AI 애플리케이션·에이전트를 만드는 개발자 | ML 실무자 · ML 엔지니어 · 데이터 과학자 · AI 플랫폼 팀 |
| 고르는 이유 | 커스텀 모델 개발에 크게 투자하지 않고 만들 때 | **비용·지연·처리량 트레이드오프를 직접 관리**해야 할 때 |

**가르는 질문 한 줄** — **"인프라를 만질 이유가 있는가?"** 없으면 관리형 API, 있으면 자체 호스팅입니다. 공식 문서가 적는 제어의 구체적 내용이 바로 **비용·처리량·지연의 트레이드오프**라, 이 세 낱말이 지문에 보이면 SageMaker AI 쪽입니다. 반대로 **"ML 전문성이 제한적이다"**, **"빠르게 실험하고 싶다"**가 보이면 Bedrock 쪽입니다.

> 추론 자체의 네 가지 유형(실시간 · 서버리스 · 비동기 · 배치 변환)은 작업 1.1에서 다뤘습니다. 여기서는 **누가 호스팅하는가**만 가르면 됩니다.

### 5) MLOps의 기본 개념 (목표 1.3.5) {#mlops}

공식 정의부터 봅니다 — MLOps는 **"ML 워크플로와 배포를 자동화하고 단순화하는 관행의 모음"**이고, **"ML 애플리케이션 개발(Dev)과 ML 시스템 배포·운영(Ops)을 통합하는 문화이자 관행"**입니다.

**네 가지 원칙**이 목표에 나온 낱말들과 하나씩 맞물립니다.

| 원칙 | 내용 | 목표의 어느 낱말인가 |
|---|---|---|
| **버전 관리** | ML 훈련 코드·모델 명세를 버전화해 **재현 가능하고 감사 가능하게** 만듭니다. 공식은 **재현성**을 "같은 입력이면 각 단계가 같은 결과를 내는 것"으로 적습니다 | **반복 가능한 프로세스** |
| **자동화** | 데이터 수집·전처리·훈련·검증·배포 단계를 자동화해 **반복성·일관성·확장성**을 확보합니다. IaC로 환경을 재현합니다 | **확장 가능한 시스템** |
| **Continuous X** | **지속적 통합**(코드 검증·테스트를 데이터와 모델까지 확장) · **지속적 배포**(새 모델이나 예측 서비스를 자동 배포) · **지속적 훈련**(재배포용 자동 재훈련) · **지속적 모니터링**(비즈니스 관련 지표로 데이터·모델 모니터링) | **모델 모니터링 · 모델 재훈련** |
| **모델 거버넌스** | 데이터 과학자·엔지니어·비즈니스 이해관계자의 협업, 문서화, **예측에 대한 피드백 수집 체계**, 민감 데이터 보호, 그리고 **라이브 전에 모델을 검토·검증·승인하는 구조화된 절차** | **프로덕션 준비 상태 달성** |

**실험**은 이 그림의 출발점입니다. 공식은 탐색적 데이터 분석이 **"최선의 모델 버전이 배포 준비가 될 때까지 여러 모델을 실험하게 만든다"**고 적고, 그래서 **실험 추적과 ML 훈련 파이프라인 관리가 필수**라고 못박습니다. 자동화의 목적도 같습니다 — 공식은 자동화된 테스트가 **"문제를 일찍 발견하게 해 빠른 수정과 학습을 돕는다"**고 적습니다.

**성숙도 레벨 세 단계**는 "무엇을 배포하는가"로 갈립니다.

| 레벨 | 특징 | 배포 대상 |
|---|---|---|
| **레벨 0** | 모든 단계가 수동이고 단계 간 전환도 수동. 데이터 과학자가 훈련된 모델을 **아티팩트로 넘기고** 엔지니어가 배포. 릴리스가 드물고 **능동적 성능 모니터링이 없습니다** | **훈련된 모델** |
| **레벨 1** | ML 파이프라인을 자동화해 **지속적으로 훈련**. 개발·사전 프로덕션·프로덕션에서 **같은 파이프라인 구현**. 중앙 **특성 저장소**로 특성 정의를 표준화 | **훈련 파이프라인** |
| **레벨 2** | 레벨 1 전부 + **파이프라인 오케스트레이터**와 **모델 레지스트리**. 파이프라인 구축 → 배포 → 서빙이 여러 파이프라인에서 반복됩니다 | **여러 파이프라인** |

**기술 부채 관리**가 v1.1 목표에 명시된 이유도 공식 문서에 있습니다. AWS Prescriptive Guidance는 ML 솔루션이 **"애초에 제대로 만들기가 더 까다롭고"**, **"데이터 분포가 예상된·예상 못 한 여러 이유로 시간이 지나며 크게 벗어나는 변동성 큰 환경에 존재한다"**고 적습니다. 그리고 많은 ML 실무자가 소프트웨어 공학 배경이 아니라 테스트 가능한 코드·모듈화·버전 관리에 익숙하지 않다고 지적하며, **"이런 과제들이 기술 부채를 만들고, ML 팀에서는 복리 효과를 타고 솔루션이 시간이 갈수록 더 복잡하고 유지하기 어려워진다"**고 적습니다.

**모델 모니터링과 재훈련**은 한 쌍입니다. 프로덕션의 모델은 **데이터 패턴·사용자 행동·비즈니스 환경의 변화로 자연히 성능이 저하**되고, 이것을 **모델 드리프트**라 부르며 재훈련이 필요해집니다. 드리프트는 두 종류로 갈립니다.

- **데이터 드리프트** — **입력 데이터의 분포** 변화
- **개념 드리프트** — **입력 변수와 출력 변수 사이의 관계** 변화

> ⚠️ **"드리프트를 보면 바로 재훈련"이 공식 권고가 아닙니다.** 재훈련은 **상당한 컴퓨팅 자원을 소비**하므로, 공식은 **자동 모니터링과 명확한 성능 임계값**을 세워 **필요할 때만** 재훈련하라고 적습니다. 그리고 모니터링 전략에는 **기술 지표(정확도·정밀도·재현율)와 비즈니스 KPI를 함께** 넣으라고 적습니다 — 이 문장이 목표 1.3.6으로 이어집니다.

### 6) 모델 성능 지표와 비즈니스 지표 (목표 1.3.6) {#metrics}

v1.1이 AUC를 빼고 **정밀도·재현율**을 넣었습니다. 네 개만 정확히 잡습니다.

| 지표 | 공식 정의 | 무엇을 재는가 | 범위 |
|---|---|---|---|
| **정확도(Accuracy)** | **"올바르게 분류된 항목 수와 (올바르게·잘못) 분류된 전체 항목 수의 비율"** | 전체 중 맞힌 비율. 이진·다중 클래스 모두 | 0~1 (1이 완벽) |
| **정밀도(Precision)** | `Precision = TP/(TP+FP)` — **"식별한 양성 전체 중에서 참 양성을 얼마나 잘 예측하는가"** | 양성이라 말했을 때 **그 말이 맞는 비율** | 0~1 |
| **재현율(Recall)** | `Recall = TP/(TP+FN)` — **"데이터셋의 모든 참 양성을 얼마나 올바르게 예측하는가"** | 실제 양성 중 **놓치지 않은 비율** | 0~1 |
| **F1** | **정밀도와 재현율의 조화 평균** | 둘의 **균형** | 0~1 (1이 최선, 0이 최악) |

**혼동 짝 ①: 정밀도 ↔ 재현율.** 공식 문서가 각각에 **비용의 방향**을 붙여 설명합니다.

- **정밀도는 거짓 양성의 비용이 클 때 중요합니다.** 공식 예가 선명합니다 — **"항공기 안전 시스템이 비행에 안전하다고 거짓으로 판정하면 거짓 양성의 비용이 매우 크다"**.
- **재현율은 참 양성을 모두 찾아야 할 때 중요합니다.** 공식 예는 **암 검사**입니다. 놓친 환자(거짓 음성)가 치명적이기 때문입니다.
- ⚠️ **그런데 공식은 바로 이어 경고합니다** — **"재현율만 측정하는 것은 종종 불충분하다. 모든 출력을 참 양성으로 예측하면 완벽한 재현율 점수가 나오기 때문이다."** 그래서 둘을 묶는 **F1**이 필요합니다.

**혼동 짝 ②: 정확도 ↔ 불균형 데이터.** 이것이 이 목표에서 가장 자주 나오는 함정입니다.

공식은 실제 응용에서 **"데이터가 불균형할 수 있고, 일부 클래스가 다른 클래스보다 현저히 빈번하다"**고 적습니다. 그 결과는 **"모델이 다수 클래스에서는 잘 동작하지만 소수 클래스를 정확히 예측하지 못하는"** 상태입니다. 이때 정확도는 높게 나오면서도 정작 찾아야 할 것을 못 찾습니다. 공식이 드는 완화 기법이 **데이터 리샘플링 · 다른 평가 지표 사용 · 이상 탐지 알고리즘 적용**이고, 지표 쪽의 공식 답이 `BalancedAccuracy`입니다 — 공식 설명이 **"양성 또는 음성의 수가 서로 크게 다른 불균형 데이터셋, 예를 들어 이메일의 1%만 스팸인 경우에 더 나은 정확도 측정을 준다"**입니다.

> 참고로 SageMaker AI Autopilot의 **기본 목표 지표**가 이 사정을 반영합니다 — **이진 분류의 기본값은 `F1`**이고 **다중 클래스 분류의 기본값은 `Accuracy`**입니다. 이진 분류에서 기본값이 정확도가 아니라는 점이 기억을 돕습니다.

**비즈니스 지표**는 기술 지표와 **연결**될 때만 뜻을 가집니다. 공식 Well-Architected 모범 사례가 직접 적는 안티패턴이 그것입니다.

| 비즈니스 지표 | 공식이 적는 내용 |
|---|---|
| **ROI(투자 수익률)** | 모델이 배포되면 **전달되는 가치를 추적하는 리포팅 체계**를 세웁니다. 효과적인 리포팅은 **모델이 전달한 가치를 지속적인 런타임 비용과 비교**해 조치를 취하게 합니다 |
| **사용자당 비용 · 개발 비용** | ROI가 음수라면 **지연을 줄이려 서버리스 추론을 쓰거나**, **정확도와 복잡도의 타협점을 바꿔 런타임 비용을 줄이거나**, 간단한 모델을 앞에 둬 전체 모델로 가는 사례를 **분류·필터링**하는 식으로 개선할 수 있습니다 |
| **고객 피드백** | 모니터링 시스템은 **사용자 피드백을 수집해** 모델을 유지·개선하고 시간이 지나도 적합하게 유지합니다. 거버넌스 쪽에서도 **예측에 대한 피드백을 수집해 재훈련하는 체계**를 세우라고 적습니다 |

공식이 명시하는 **안티패턴 네 가지**가 그대로 문항 재료입니다.

- 성공 지표나 비즈니스 KPI를 정의하지 않고 모델을 배포한다
- ⚠️ **정확도 같은 기술 지표만 보고 비즈니스 결과와 연결하지 않는다**
- ⚠️ **ROI를 초기 배포 직후 한 번만 측정하고 지속적으로 측정하지 않는다**
- ROI 계산에서 **ML 모델 운영의 전체 비용**을 빠뜨린다

## ✍️ 시험 포인트

- **단계 식별 문항**은 **산출물**로 갈립니다 — "무엇을 예측할지 정한다"는 **ML 문제 정의**, "변수를 만들고 변환한다"는 **데이터 처리**, "예측을 내놓는 엔드포인트가 생긴다"는 **모델 배포**입니다.
- **순서 문항**은 **피드백 루프**로 걸러집니다 — "단계는 순차적이며 되돌아갈 수 없다"는 보기는 공식 서술과 반대입니다.
- **모델 소스 문항**은 **가중치를 손에 쥐는가**로 갈립니다 — 쥐지 않으면 관리형 API, 쥐되 만들지는 않으면 사전 훈련 오픈 소스, 처음부터 만들면 사용자 지정 훈련입니다.
- **배포 방식 문항**은 **비용·지연·처리량**이라는 세 낱말이 나오는지 봅니다 — 나오면 자체 호스팅 엔드포인트, 안 나오고 "빠르게·전문성 적게"가 나오면 관리형 API입니다.
- **서비스 매핑 문항**은 **자리를 잘못 놓은 보기**를 찾는 문제입니다 — `Kiro`는 개발 도구, `Amazon Quick`은 분석·BI, `Amazon Bedrock`은 모델 API, `SageMaker AI`는 구축·훈련·배포입니다.
- **MLOps 문항**은 네 원칙 중 **어느 원칙의 문제인가**로 묻습니다 — 재현이 안 되면 **버전 관리**, 사람이 매번 손으로 하면 **자동화**, 승인 절차가 없으면 **거버넌스**입니다.
- **지표 문항**은 **비용의 방향**을 봅니다 — 거짓 양성이 비싸면 **정밀도**, 거짓 음성이 비싸면 **재현율**, 둘 다 중요하면 **F1**, 클래스가 심하게 치우쳐 있으면 **정확도를 믿지 않습니다**.

## ⚠️ 흔한 함정 {#pitfalls}

- ❌ **"ML 수명 주기는 한 번 지나가면 끝나는 순차 공정이다"** → 공식은 단계가 **반드시 순차적이지 않고 피드백 루프를 가질 수 있다**고 적습니다.
- ❌ **"특성 엔지니어링은 모델 개발 단계의 일이다"** → **데이터 처리** 단계입니다. 모델 개발은 구축·훈련·튜닝·평가입니다.
- ❌ **"모델 평가는 훈련 데이터로 한다"** → 목적이 **훈련 데이터셋을 넘어 일반화하는지 확인**하는 것이므로 **검증 세트**라는 별도 데이터셋을 씁니다.
- ❌ **"오픈 소스 사전 훈련 모델은 AWS가 라이선스를 검토해 준다"** → 공식은 **라이선스 조건 검토·준수 책임이 사용자에게 있다**고 명시합니다.
- ❌ **"SageMaker AI는 무조건 컴퓨팅 사용량 기준으로만 과금된다"** → **자리에 따라 갈립니다.** 공식은 **서버리스 모델 커스터마이징에 토큰당 요금**을 적용한다고 적고(Bedrock과 같은 요금 단순성), **관리형 훈련 작업 · 추론 · HyperPod**에만 **컴퓨팅·스토리지 사용량 기준**을 적용합니다. Bedrock 쪽은 토큰 기준 종량제입니다.
- ❌ **"Bedrock과 SageMaker AI 중 하나만 골라야 한다"** → 공식은 **배타적이지 않다**고 적고, 점진적 커스터마이징 파이프라인에서 **함께 쓰는** 경로를 제시합니다.
- ❌ **"Amazon QuickSight가 Amazon Quick으로 대체되어 기존 API가 끊긴다"** → QuickSight는 Quick 안의 기능 **Amazon Quick Sight**로 이어지고, **기존 API·SDK·통합은 변경 없이 동작**합니다.
- ❌ **"MLOps는 DevOps의 다른 이름이다"** → MLOps에서는 **원천 데이터가 소스 코드와 나란히 1급 입력**이라, 데이터·모델·파라미터·훈련 구성까지 버전화하고 데이터 변경이 파이프라인을 촉발합니다.
- ❌ **"드리프트가 감지되면 즉시 재훈련하는 것이 모범 사례다"** → 재훈련은 자원을 크게 소비하므로 **임계값을 세워 필요할 때만** 합니다.
- ❌ **"정확도가 99%면 좋은 모델이다"** → **불균형 데이터**에서는 다수 클래스만 맞히고도 그 숫자가 나옵니다. 공식 예가 **이메일의 1%만 스팸인** 데이터셋이고, 이때는 `BalancedAccuracy`나 F1 쪽을 봅니다.
- ❌ **"재현율이 1.0이면 완벽한 모델이다"** → 공식이 직접 경고합니다 — **모든 출력을 참 양성으로 예측하면 완벽한 재현율이 나옵니다.**
- ❌ **"정확도가 올랐으니 프로젝트가 성공했다"** → 공식 안티패턴입니다. **기술 지표만 보고 비즈니스 결과와 연결하지 않는 것**, 그리고 **ROI를 배포 직후 한 번만 재는 것** 둘 다 이름이 붙어 있습니다.

## 🧪 자가 점검

**Q1.** 파이프라인에서 "무엇을 관측하고 무엇을 예측할지"를 결정하는 단계의 이름은 무엇이고, 그 단계에서 **함께** 정해야 하는 것은 무엇인가요? (→ 1) AI/ML 파이프라인의 구성 요소)

<details><summary>정답 보기</summary>

**ML 문제 정의(ML problem framing)** 단계입니다. 공식은 이 단계를 **"비즈니스 문제를 머신러닝 문제로 구성하는 것 — 무엇이 관측되고 무엇이 예측되어야 하는가(레이블 또는 대상 변수로 알려진 것)"**로 정의합니다.

그리고 함께 정하는 것이 **최적화할 성능·오차 지표**입니다. 공식은 **"무엇을 예측할지와 성능·오차 지표를 어떻게 최적화해야 하는지를 결정하는 것이 이 단계의 핵심"**이라고 적습니다. 즉 예측 대상과 지표는 **같은 단계의 산출물**입니다.
</details>

**Q2.** 1,000건 중 10건만 사기인 거래 데이터로 모델을 만들었습니다. 모델이 모든 거래를 "정상"으로 예측했습니다. 정확도는 얼마이고, 이 상황을 공식 문서는 어떻게 설명하나요? (→ 6) 모델 성능 지표와 비즈니스 지표)

<details><summary>정답 보기</summary>

**정확도는 99%입니다**(990/1,000). 정확도의 공식 정의가 **"올바르게 분류된 항목 수와 전체 항목 수의 비율"**이기 때문에, 다수 클래스만 맞혀도 높게 나옵니다.

공식 문서는 이것을 **불균형 데이터** 문제로 설명합니다 — **"일부 클래스가 다른 클래스보다 현저히 빈번"**하면 훈련 과정이 치우쳐 **"모델이 다수 클래스에서는 잘 동작하지만 소수 클래스를 정확히 예측하지 못한다"**는 것입니다. 완화 기법으로 **데이터 리샘플링 · 다른 평가 지표 사용 · 이상 탐지 알고리즘 적용**을 듭니다.

지표 쪽 공식 답은 `BalancedAccuracy`입니다 — **"양성 또는 음성의 수가 서로 크게 다른 불균형 데이터셋, 예를 들어 이메일의 1%만 스팸인 경우에 더 나은 정확도 측정을 준다"**고 적습니다.
</details>

**Q3.** "우리 모델은 재현율이 1.0입니다"라는 보고를 받았습니다. 공식 서술을 근거로 이 보고를 검토하세요. 그리고 거짓 양성의 비용이 큰 경우에는 어떤 지표를 봐야 하나요? (→ 6) 모델 성능 지표와 비즈니스 지표)

<details><summary>정답 보기</summary>

**그 숫자만으로는 좋은 모델이라고 말할 수 없습니다.** 공식 문서가 직접 경고합니다 — **"재현율만 측정하는 것은 종종 불충분하다. 모든 출력을 참 양성으로 예측하면 완벽한 재현율 점수가 나오기 때문이다."** 즉 전부 양성이라고 답하는 모델도 재현율 1.0을 받습니다. 그래서 **정밀도**를 함께 보거나, 둘의 **조화 평균인 F1**을 봅니다.

**거짓 양성의 비용이 큰 경우에는 정밀도(Precision)**입니다. 공식 정의가 `Precision = TP/(TP+FP)`이고, **"거짓 양성의 비용이 클 때 중요한 지표"**라고 적으며 **"항공기 안전 시스템이 비행에 안전하다고 거짓으로 판정하는"** 예를 듭니다.
</details>

**Q4.** 팀에 ML 전문성이 거의 없고, 사전 훈련 모델을 호출해 빠르게 챗봇을 만들려 합니다. 또 다른 팀은 자체 데이터로 훈련한 모델을 띄우면서 비용·처리량·지연을 직접 조절해야 합니다. 각각 어떤 방식이고 과금은 어떻게 다릅니까? (→ 3) 프로덕션 환경에서 모델을 사용하는 방법)

<details><summary>정답 보기</summary>

첫 팀은 **관리형 API(`Amazon Bedrock`)**입니다. 공식 비교 표가 Bedrock의 필요 전문성을 **"사전 훈련 모델을 쓰는 데 필요한 기본적인 ML 전문성"**으로 적고, 통합을 **"API 호출로 사전 훈련 모델을 애플리케이션에 통합"**으로 적습니다. 그리고 **"Bedrock은 서버리스이므로 인프라를 관리하지 않아도 된다"**고 명시합니다. 과금은 **처리한 입력·출력 토큰 기준 종량제**입니다.

둘째 팀은 **자체 호스팅(`Amazon SageMaker AI` 전용 엔드포인트)**입니다. 공식은 **"비용·지연·처리량 트레이드오프를 직접 관리해야 할 때 SageMaker AI를 고려하라"**고 적습니다. 전용 엔드포인트로 추론을 돌리므로 과금은 **컴퓨팅·스토리지 사용량 기준**입니다 — 다만 **SageMaker AI 전체가 그런 것은 아닙니다.** 공식은 **서버리스 모델 커스터마이징에는 토큰당 요금**을 적용한다고 적습니다.

⚠️ 덧붙여, 공식은 이 선택이 **배타적이지 않다**고 적습니다. Bedrock에서 프로토타입을 만들고, 인프라 제어가 필요해지면 SageMaker AI 엔드포인트나 HyperPod로 옮기는 경로가 공식 권고입니다.
</details>

**Q5.** `SageMaker JumpStart`에서 공개 모델을 가져와 제품에 쓰려고 합니다. 공식 문서가 **사용자의 책임**으로 적는 것은 무엇인가요? (→ 2) ML 모델의 소스)

<details><summary>정답 보기</summary>

**라이선스 조건의 검토와 준수입니다.** JumpStart 문서는 **"서드파티 콘텐츠를 다운로드하거나 사용하기 전에: 적용되는 라이선스 조건을 검토하고 그것이 귀하의 사용 사례에 수용 가능한지 확인할 책임은 귀하에게 있습니다"**라고 적습니다.

참고로 JumpStart의 성격은 **"다양한 문제 유형에 대한 사전 훈련된 오픈 소스 모델을 제공"**하는 것이고, 받은 모델을 **배포 전에 점진적으로 훈련·튜닝**할 수 있습니다.
</details>

**Q6.** MLOps의 "Continuous X"에 해당하는 네 가지 활동을 쓰고, 그중 어느 것이 목표 1.3.5의 「모델 재훈련」에 대응하는지 답하세요. (→ 5) MLOps의 기본 개념)

<details><summary>정답 보기</summary>

공식이 적는 네 활동은 **지속적 통합 · 지속적 배포 · 지속적 훈련 · 지속적 모니터링**이고, 시스템의 어느 곳이든 변경이 생기면 **지속적으로 일어나는** 활동들입니다.

- **지속적 통합** — 코드의 검증·테스트를 **파이프라인의 데이터와 모델까지** 확장합니다
- **지속적 배포** — 새로 훈련된 모델이나 모델 예측 서비스를 **자동으로 배포**합니다
- **지속적 훈련** — 재배포를 위해 ML 모델을 **자동으로 재훈련**합니다 → **「모델 재훈련」에 대응하는 항목입니다**
- **지속적 모니터링** — **비즈니스 관련 지표**로 데이터와 모델을 모니터링합니다

⚠️ 지속적 훈련은 "드리프트가 보이면 무조건 돌린다"는 뜻이 아닙니다. 공식은 재훈련이 **상당한 컴퓨팅 자원을 소비**하므로 **명확한 성능 임계값**을 세워 **필요할 때만** 재훈련하라고 적습니다.
</details>

**Q7.** 프로덕션 모델에 대해 "정확도 0.94를 달성했으므로 이 프로젝트는 성공입니다. ROI는 배포 직후 한 번 계산해 뒀습니다"라는 보고를 받았습니다. 공식 모범 사례를 근거로 검토하세요. (→ 6) 모델 성능 지표와 비즈니스 지표)

<details><summary>정답 보기</summary>

**두 문장 모두 공식이 이름 붙인 안티패턴입니다.**

- **"정확도 같은 기술 지표만 보고 비즈니스 결과와 연결하지 않는다"** — 공식 Well-Architected 모범 사례가 그대로 적는 안티패턴입니다. 모니터링 전략에는 **기술 지표(정확도·정밀도·재현율)와 비즈니스 관련 KPI를 함께** 넣어야 합니다.
- **"ROI를 초기 배포 직후 한 번만 측정하고 지속적으로 측정하지 않는다"** — 역시 명시된 안티패턴입니다. 공식은 모델이 배포되면 **전달되는 가치를 추적하는 리포팅 체계**를 세우고, **전달한 가치를 지속적인 런타임 비용과 비교**해 조치를 취하라고 적습니다.

ROI가 음수일 때 공식이 드는 개선 방향도 함께 기억합니다 — **서버리스 추론으로 지연을 줄이기**, **정확도와 복잡도의 타협점을 바꿔 런타임 비용을 줄이기**, **간단한 모델을 앞에 둬 전체 모델로 보낼 사례를 분류·필터링하기**. 그리고 ROI 계산에서 **운영 전체 비용**을 빠뜨리는 것도 안티패턴입니다.
</details>
