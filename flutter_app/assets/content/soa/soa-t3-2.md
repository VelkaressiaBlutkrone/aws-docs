이 문서를 끝내면 다음을 스스로 설명하고, 콘솔/CLI에서 직접 구성할 수 있어야 합니다.

- [ ] **AMI 구성 요소** — 루트 볼륨·블록 디바이스 매핑·시작 권한·연결된 스냅샷을 설명할 수 있다

- [ ] **배포 전략** — 롤링·블루/그린의 차이와 트레이드오프를 개념적으로 설명할 수 있다

## 🎯 왜 중요한가

- 도메인 3은 "리소스를 어떻게 표준화해서 배포하고, 그 이후 어떻게 최신으로 유지하는가"를 묻습니다. **AMI는 표준화의 출발점**입니다. 운영자는 검증된 AMI를 한 번 구워(bake) 전 플릿에 동일하게 펼치고, 정기적으로 패치해 다시 굽는 사이클을 돌립니다.
- 시험은 함정으로 **AMI의 리전·계정 경계**를 자주 냅니다. AMI는 리전 단위 리소스라 다른 리전에서 쓰려면 **복사**해야 하고, 다른 계정에서 쓰려면 **공유**해야 합니다. 또 AMI를 만들면 함께 생성되는 **EBS 스냅샷**의 존재와 비용도 출제 포인트입니다.
- 패치는 SOA 운영의 핵심입니다. 본 문서는 **전략 개념**(베이스라인·패치 그룹·유지 관리 기간이 어떻게 맞물리는지)을 잡고, 실제 SSM Patch Manager 운영 절차는 `soa-t3-3`에서 깊게 다룹니다.

## 📖 핵심 개념

### 1) AMI 구성 — 무엇이 들어 있나

> 공식 정의: **"Amazon Machine Image(AMI)는 인스턴스를 시작하는 데 필요한 정보(운영체제·애플리케이션·구성)를 담은 템플릿이다."**

| 구성 요소 | 의미 |
|---|---|
| **루트 볼륨 템플릿** | OS·애플리케이션이 담긴 루트 디바이스(보통 EBS 백업 → 스냅샷 기반) |
| **블록 디바이스 매핑** | 인스턴스 시작 시 연결할 EBS 볼륨·인스턴스 스토어 정의 |
| **시작 권한(Launch Permission)** | 누가 이 AMI로 인스턴스를 시작할 수 있는지(소유자·특정 계정·공개) |

**핵심 사실:**

- 대부분의 AMI는 **EBS 백업**이며, AMI를 생성하면 루트(및 추가) 볼륨의 **EBS 스냅샷이 함께 만들어집니다**. AMI를 등록 해제(deregister)해도 **연결된 스냅샷은 자동 삭제되지 않으므로** 비용 정리 시 따로 지워야 합니다.
- **블록 디바이스 매핑**으로 추가 데이터 볼륨, 볼륨 크기·유형, 종료 시 삭제(DeleteOnTermination) 여부를 정의합니다.
- AMI는 **리전 단위 리소스**입니다(특정 리전에 등록됨).

> 🧠 원리: AMI를 등록 해제해도 왜 스냅샷은 함께 지워지지 않을까요?
> AMI는 스냅샷을 참조하는 메타데이터 레이어이고, 스냅샷 자체는 독립된 EBS 리소스입니다.
> 같은 스냅샷이 여러 AMI에서 공유 참조될 수 있어, 한 AMI 해제 시 스냅샷을 자동으로 지우면 다른 AMI가 깨질 수 있습니다.
> 따라서 스냅샷 생명주기는 AMI 생명주기와 분리돼 있으며, 비용 정리는 운영자가 두 단계를 명시적으로 수행해야 합니다.

### 2) AMI 공유와 리전 간 복사

| 작업 | 의미 | 경계 |
|---|---|---|
| **리전 간 복사(Copy)** | AMI를 다른 **리전**으로 복제(새 AMI ID·스냅샷 생성) | 리전 경계를 넘기 위함 |
| **계정 간 공유(Share)** | 시작 권한을 특정 **계정**(또는 공개)에 부여 | 같은 리전 내 다른 계정이 사용 |

**핵심 사실:**

- AMI ID는 **리전마다 다릅니다.** 멀티 리전 배포라면 각 리전에 AMI를 **복사**해야 하고, 복사본은 **새 AMI ID와 새 스냅샷**을 갖습니다.
- 계정 간 사용은 **시작 권한 공유**로 처리합니다. 다른 리전 + 다른 계정이면 "복사 + 공유"를 조합합니다.
- **암호화된 AMI**를 공유하려면 사용한 **KMS 키도 함께 공유**해야 다른 계정이 복호화·시작할 수 있습니다.

> 🧠 원리: 리전 간 AMI 복사가 단순 링크 공유가 아니라 새 AMI ID와 새 스냅샷을 만드는 이유는 무엇일까요?
> AMI는 특정 리전의 EBS 스냅샷 ID를 직접 참조하는 구조인데, 스냅샷은 리전 내부에서만 접근 가능한 리전 격리 리소스입니다.
> 복사 시 스냅샷 데이터를 대상 리전으로 전송하고 새 스냅샷을 생성해야만 해당 리전에서 인스턴스를 시작할 수 있으므로, 새 AMI ID와 새 스냅샷 생성은 리전 격리 모델의 직접 결과입니다.
> 운영자 관점에서는 멀티 리전 배포마다 각 리전의 AMI ID를 별도로 관리해야 한다는 실무 함의가 있습니다.

### 3) 골든 AMI 패턴

> **골든 AMI(Golden AMI)**: 보안 강화·에이전트·공통 패키지·기본 구성을 미리 적용한 **표준 베이스 이미지**입니다. 모든 인스턴스를 이 이미지에서 시작해 일관성과 부팅 속도(런타임에 설치할 게 적음)를 확보합니다.

**운영 절차 — 굽기 → 배포 → 갱신 사이클:**

```
① 베이스 OS에서 인스턴스 시작
② 패치 적용 + 에이전트(SSM/CloudWatch) + 공통 패키지 설치 + 하드닝
③ 검증 후 AMI 생성(bake) → 버전 태그 부여
④ 시작 템플릿/ASG가 새 AMI를 참조하도록 갱신 → 롤링 교체로 배포
⑤ 주기적으로(예: 월간) 보안 패치 반영해 ②~④ 반복
```

> 골든 AMI는 **"미리 구워 넣기(bake-in)"**, 런타임 구성 도구(user data·SSM·Ansible 등)는 **"부팅 시 입히기(bake-on-launch)"**입니다. 둘을 섞어 변하지 않는 베이스는 이미지로, 자주 바뀌는 설정은 런타임으로 분리하는 것이 모범 사례입니다.

> 🧠 원리: 왜 골든 AMI 패턴은 모든 설정을 이미지에 구워 넣지 않고 런타임과 분리할까요?
> 이미지를 다시 구우려면 빌드·테스트·배포 사이클 전체를 재실행해야 해서 변경 비용이 큽니다.
> 자주 바뀌는 설정(환경별 엔드포인트·런타임 구성 등)까지 이미지에 포함하면 작은 변경에도 AMI를 다시 굽고 플릿 전체를 교체해야 해, 운영 민첩성이 크게 떨어집니다.
> bake-in과 런타임을 분리하면 베이스 이미지 수명을 늘리면서도 환경별 설정을 빠르게 반영할 수 있어, 이미지 재빌드 빈도와 런타임 구성 복잡도 사이의 트레이드오프를 조율합니다.

### 4) EC2 Image Builder — 이미지 파이프라인 자동화

> 공식 정의: **"EC2 Image Builder는 안전하고 최신 상태인 OS 이미지의 생성·관리·배포를 자동화하는 완전관리형 서비스다."**

- 골든 AMI를 **손으로 굽는 작업을 파이프라인으로 자동화**합니다: **이미지 레시피(베이스 이미지 + 구성 요소[패키지·하드닝·테스트])** → 빌드 → 자동 테스트 → 배포(원하는 리전/계정에 배포·공유).
- **스케줄**이나 베이스 이미지 업데이트에 따라 자동으로 새 버전을 굽게 할 수 있어, 정기 패치 사이클을 자동화합니다.
- 출력은 AMI(또는 컨테이너 이미지)이며, 배포 단계에서 **여러 리전·계정으로 자동 배포·공유**할 수 있습니다.

> 시험에서 "표준 이미지를 정기적으로·자동으로 패치·재배포하고 싶다"는 단서가 나오면 **EC2 Image Builder**가 정답 후보입니다.

> 🧠 원리: 골든 AMI를 수작업으로 굽는 것과 Image Builder 파이프라인으로 자동화하는 것의 운영 차이는 무엇일까요?
> 수작업 방식에서는 빌드 절차가 사람의 기억·문서에 의존해, 담당자 교체나 오류 발생 시 절차가 흐트러지고 이미지 간 일관성이 깨지기 쉽습니다.
> Image Builder는 이미지 레시피와 구성 요소를 코드로 정의하므로 빌드 절차가 버전 관리되고, 동일한 입력이 항상 동일한 출력 이미지를 만드는 재현성을 확보합니다.
> 재현성이 확보되면 정기 패치 사이클을 스케줄로 실행할 수 있어, 운영자가 수동으로 개입하지 않아도 이미지가 최신 상태로 유지됩니다.

### 5) 패치 전략 개요 (상세는 soa-t3-3)

> 실행 도구는 **Systems Manager Patch Manager**입니다. 여기서는 세 구성요소가 어떻게 맞물리는지 **개념**만 잡습니다.

| 구성요소 | 역할 |
|---|---|
| **패치 베이스라인(Patch Baseline)** | 어떤 패치를 승인/거부할지 규칙 정의(심각도·분류·자동 승인 지연 등) |
| **패치 그룹(Patch Group)** | `Patch Group` 태그로 인스턴스를 묶어, 그룹별로 다른 베이스라인을 적용 |
| **유지 관리 기간(Maintenance Window)** | 패치를 적용할 **정해진 시간 창**(서비스 영향 최소화) |

```
패치 그룹(태그)  →  연결된 패치 베이스라인(승인 규칙)
                  →  유지 관리 기간에 스캔/설치 실행
```

> 핵심 아이디어: **언제(유지 관리 기간) · 무엇을(베이스라인) · 어디에(패치 그룹)** 패치를 적용할지를 분리해, 환경(dev/prod)마다 다른 정책을 안전하게 운영합니다. 인스턴스를 패치 그룹에 넣으려면 **`Patch Group`(키 철자 주의) 태그**를 붙이고, 같은 값을 베이스라인에 등록합니다.

> 🧠 원리: 패치 정책을 베이스라인·패치 그룹·유지 관리 기간으로 분리하는 이유는 무엇일까요?
> 하나의 규칙으로 통합하면 dev 서버에 엄격한 prod 패치 규칙이 적용되거나 반대로 prod에 느슨한 규칙이 들어오는 혼용 오류가 생기고, 변경 시 모든 환경이 함께 영향받습니다.
> 세 구성요소를 독립적으로 유지하면 "무엇을·어디에·언제"를 각각 조합할 수 있어, dev는 자동 승인·배치 작업 시간에 실행하고 prod는 엄격한 심각도 필터와 유지 관리 기간을 사용하는 식으로 환경별 정책을 안전하게 격리합니다.
> 태그 기반 그룹화는 인스턴스를 별도 구조로 관리하지 않고 기존 EC2 태깅 체계 위에 올라가므로, 새 인스턴스가 올바른 태그를 갖고 시작되는 순간 자동으로 올바른 패치 정책에 포함됩니다.

### 6) 배포 전략 개념 — 롤링 vs 블루/그린

| 전략 | 방식 | 트레이드오프 |
|---|---|---|
| **롤링(Rolling)** | 기존 플릿을 **일부씩 교체**(예: 한 번에 25%) | 추가 인프라 거의 불필요, 그러나 배포 중 **혼합 버전** 공존·롤백 느림 |
| **블루/그린(Blue/Green)** | 새 환경(그린)을 **별도로 띄우고** 트래픽을 한 번에 전환 | 빠른 롤백(되돌려 라우팅)·혼합 버전 없음, 그러나 **두 배 인프라**·비용 |

**핵심 사실:**

- **롤링**은 ASG의 인스턴스 새로 고침(instance refresh)이나 CloudFormation 업데이트 정책으로 구현합니다. 비용은 낮지만 배포 중 두 버전이 동시에 트래픽을 받습니다.
- **블루/그린**은 새 버전을 완전히 검증한 뒤 **DNS/로드밸런서 대상 그룹 전환**으로 한 번에 컷오버합니다. 문제가 생기면 **이전 환경으로 즉시 되돌릴 수 있어 롤백이 빠릅니다**(카나리는 그린에 소량 트래픽만 먼저 흘려 검증하는 변형).

> 🧠 원리: 블루/그린이 롤링보다 롤백이 빠른 이유는 무엇일까요?
> 롤링은 배포 중 기존 인스턴스를 점진적으로 교체하므로, 배포 후반부에 문제가 발견되면 이미 교체된 인스턴스들을 다시 구버전으로 교체하는 추가 롤링이 필요합니다.
> 블루/그린은 블루 환경이 전환 이후에도 그대로 유지되어 있으므로, 문제 발견 시 로드밸런서 대상을 다시 블루로 전환하는 단일 작업으로 즉시 되돌릴 수 있습니다.
> 롤백 속도의 차이는 "구버전 환경이 배포 후에도 살아 있는가"에 달려 있으며, 이것이 블루/그린의 두 배 인프라 비용을 정당화하는 주요 운영 근거입니다.

## ✍️ 시험 포인트

- **AMI = 인스턴스 시작 템플릿**(OS+앱+구성). **리전 단위 리소스**. 다른 리전 → **복사(Copy)**, 다른 계정 → **공유(Share, 시작 권한)**.
- AMI 생성 시 **EBS 스냅샷이 함께 생성**되고, AMI **deregister 후에도 스냅샷은 남음**(별도 삭제 필요).
- **암호화 AMI 공유**에는 **KMS 키 공유**도 필요.
- **블록 디바이스 매핑**으로 추가 볼륨·크기·종료 시 삭제 여부 정의.
- **골든 AMI** = 하드닝·에이전트·패치를 미리 구운 표준 이미지 → 일관성·빠른 부팅.
- **EC2 Image Builder** = 이미지 빌드·테스트·배포 **파이프라인 자동화**(정기 패치 재배포에 적합).
- **패치 전략 = 베이스라인(무엇) + 패치 그룹(어디, `Patch Group` 태그) + 유지 관리 기간(언제)**.
- **롤링 vs 블루/그린**: 롤링=점진 교체·저비용·혼합 버전, 블루/그린=병렬 환경·빠른 롤백·두 배 비용.

## ⚠️ 흔한 함정

1. **"AMI는 모든 리전에서 쓸 수 있다."** → AMI는 **리전 단위**입니다. 다른 리전에서 쓰려면 **복사**(새 AMI ID·스냅샷 생성)가 필요합니다.
   *(원리: §2 — 스냅샷은 리전 격리 리소스라 복사 시 대상 리전에 새 스냅샷을 만들어야 인스턴스 시작이 가능하다.)*

2. **"AMI를 등록 해제하면 스냅샷도 자동으로 지워진다."** → 아닙니다. **연결된 EBS 스냅샷은 남아** 비용이 계속 발생합니다. 정리하려면 스냅샷을 별도로 삭제해야 합니다.
   *(원리: §1 — AMI와 스냅샷은 독립 생명주기를 가지며 공유 참조 구조 때문에 연동 삭제가 불가하다.)*

3. **"AMI를 다른 계정과 공유하면 끝이다(암호화 무관)."** → **암호화된 AMI**라면 사용한 **KMS 키도 공유**해야 대상 계정이 복호화·시작할 수 있습니다.
   *(원리: §2 — 암호화 AMI는 KMS 키 정책으로 복호화 권한이 제어되므로, 키 공유 없이는 복호화가 불가하다.)*

4. **"모든 구성을 AMI에 구워 넣어야 한다."** → 자주 바뀌는 설정까지 구우면 이미지를 너무 자주 다시 만들어야 합니다. **변하지 않는 베이스는 이미지로, 자주 바뀌는 설정은 런타임(user data·SSM)으로** 분리하는 것이 모범 사례입니다.
   *(원리: §3 — 이미지 재빌드 비용은 크므로, 변경 빈도가 높은 설정은 런타임으로 분리해 AMI 수명을 늘려야 한다.)*

5. **"패치 그룹은 콘솔에서 그룹을 만들어 인스턴스를 끌어다 넣는다."** → 패치 그룹은 **`Patch Group` 태그**로 정의하고 같은 값을 베이스라인에 등록하는 방식입니다(태그 키 철자 주의).
   *(원리: §5 — 태그 기반 그룹화는 올바른 태그를 가진 인스턴스를 자동으로 해당 패치 정책에 포함시킨다.)*

6. **"블루/그린이 항상 롤링보다 낫다."** → 블루/그린은 **두 배 인프라**가 필요해 비용이 큽니다. 빠른 롤백·무중단이 중요하면 블루/그린, 비용 절감·점진 배포면 롤링이 적합합니다.
   *(원리: §6 — 블루/그린의 즉시 롤백은 구버전 환경이 배포 후에도 살아 있기 때문이며, 이것이 두 배 비용의 운영 근거다.)*

## 🧪 자가 점검

> 아래는 학습용 자가 점검입니다. (정식 검증 문항은 별도 문항 파일 참조)

**Q1.** ap-northeast-2에서 만든 골든 AMI를 us-east-1의 다른 AWS 계정에서도 인스턴스 시작에 쓰려 합니다. 어떤 작업들이 필요한가요?

<details><summary>정답 보기</summary>

AMI는 리전 단위라 먼저 **us-east-1으로 복사(Copy)**해야 합니다(새 AMI ID·스냅샷 생성). 그다음 복사본의 **시작 권한을 대상 계정에 공유(Share)**합니다. AMI가 암호화돼 있다면 사용한 **KMS 키도 해당 계정과 공유**해야 복호화·시작이 가능합니다. 즉 "복사 + 공유(+ KMS 키 공유)" 조합입니다.
</details>

**Q2.** 매월 보안 패치를 반영한 표준 이미지를 자동으로 빌드·테스트하고 여러 리전에 배포하려 합니다. 어떤 서비스가 적합한가요?

<details><summary>정답 보기</summary>

**EC2 Image Builder**가 적합합니다. 이미지 레시피(베이스 이미지 + 패치·하드닝·에이전트 구성 요소)와 파이프라인을 정의하면, 스케줄에 따라 자동으로 이미지를 빌드·테스트하고 지정한 리전·계정으로 배포·공유합니다. 골든 AMI를 수작업으로 굽는 사이클을 자동화하는 것이 핵심 가치입니다.
</details>

**Q3.** 비용을 정리하려고 오래된 AMI를 여러 개 등록 해제했는데도 스토리지 비용이 줄지 않았습니다. 왜일까요?

<details><summary>정답 보기</summary>

AMI를 **등록 해제(deregister)해도 연결된 EBS 스냅샷은 자동 삭제되지 않기** 때문입니다. AMI 생성 시 함께 만들어진 스냅샷이 그대로 남아 스토리지 비용이 계속 발생합니다. 비용을 줄이려면 더 이상 필요 없는 **스냅샷을 별도로 삭제**해야 합니다.
</details>

**Q4.** 운영 환경에서 빠른 롤백이 가능한 무중단 배포를 원하고, 일시적으로 두 배의 인프라 비용은 감수할 수 있습니다. 어떤 배포 전략이 적합한가요?

<details><summary>정답 보기</summary>

**블루/그린(Blue/Green) 배포**가 적합합니다. 새 버전(그린)을 별도 환경에 완전히 띄워 검증한 뒤, 로드밸런서/DNS로 트래픽을 한 번에 전환합니다. 문제가 생기면 **이전 환경(블루)으로 즉시 되돌려** 빠르게 롤백할 수 있습니다. 대신 전환 기간 동안 두 환경이 공존해 비용이 늘어납니다. 비용을 아끼고 점진 교체를 원하면 롤링이 대안입니다.
</details>
