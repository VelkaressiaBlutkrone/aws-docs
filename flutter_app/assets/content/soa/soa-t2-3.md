# 백업·복원 전략 — AWS Backup·스냅샷·수명주기

> **커버하는 공식 Task** — SOA-C03 · 도메인 2 「신뢰성 및 비즈니스 연속성」(22%) · **Task 2.3 백업 및 복원 전략 구현** (`soa-t2-3`)
> 이 문서는 백업 메커니즘(AWS Backup·EBS 스냅샷·RDS 백업·S3 버전 관리)에 집중합니다. RTO/RPO 기반 DR 전략 선택은 `soa-t2-4`에서 다룹니다.

---

## ✅ 학습 목표 체크리스트

이 문서를 끝내면 다음을 스스로 설명하고, 콘솔/CLI에서 직접 구성할 수 있어야 합니다.

- [ ] **AWS Backup** — 백업 계획·규칙·백업 볼트·교차 리전/계정 복사·Vault Lock을 구성할 수 있다
- [ ] **EBS 스냅샷** — 증분 저장·S3 보관·각 스냅샷이 완전한 복원 지점이라는 성질을 안다
- [ ] **DLM** — Data Lifecycle Manager로 스냅샷·AMI 생성·보존·삭제를 자동화할 수 있다
- [ ] **RDS 백업** — 자동 백업 보존·PITR·수동 스냅샷의 차이를 구분할 수 있다
- [ ] **S3 보호** — 버전 관리·수명 주기·복제를 조합한 데이터 보호 패턴을 안다
- [ ] **불변 백업** — Vault Lock(규정 준수 모드)·MFA Delete로 랜섬웨어·삭제 위협을 막는 법을 안다
- [ ] **운영 절차** — 백업 계획 구성 → 정기 실행 → 복원 테스트의 절차를 수행할 수 있다

## 🎯 왜 중요한가

- 도메인 2(22%) Task 2.3은 "백업이 존재하는가"를 넘어 **백업이 정책대로 자동 실행되고, 보존되며, 실제로 복원되는가**를 운영자 관점에서 묻습니다.
- SOA는 "백업했다"가 아니라 **"복원 테스트를 했는가", "보존 기간이 규정을 충족하는가", "삭제·변조로부터 보호되는가"**를 함정으로 출제합니다.
- CLF/SAA에서 스냅샷·백업을 개념으로 봤다면, SOA는 **AWS Backup 정책 기반 중앙 관리**, **DLM 자동화**, **Vault Lock 불변성** 같은 운영 절차를 직접 구성하도록 요구합니다.

## 🔤 먼저 알아야 할 용어

이 문서를 읽는 데 필요한 기초 용어입니다. 이미 알면 건너뛰세요.

| 용어 | 영문 | 한 줄 풀이 |
|---|---|---|
| **증분 백업** | Incremental Backup | 이전 백업 이후 변경된 데이터만 저장하는 방식 — 전체 복사 대비 저장 공간과 시간이 절약됨 |
| **WORM** | Write Once Read Many | 한 번 쓰면 수정·삭제가 불가능한 저장 속성 — 금고에 잠근 종이처럼 원본이 보존됨 |
| **특정 시점 복원** | PITR (Point-In-Time Recovery) | 데이터베이스 변경 로그를 이용해 보존 기간 내 임의 시점으로 되돌리는 복원 방법 |
| **AMI** | Amazon Machine Image | EC2 인스턴스를 기동하는 데 필요한 OS·설정·볼륨 스냅샷을 묶은 이미지 템플릿 |
| **콜드 스토리지** | Cold Storage | 접근 빈도가 낮고 비용이 저렴한 저장 계층 — Glacier 등이 해당하며 검색 시간이 걸림 |
| **교차 리전 복제** | CRR (Cross-Region Replication) | S3 버킷 객체를 다른 AWS 리전 버킷으로 자동 복제하는 기능 |
| **MFA Delete** | Multi-Factor Authentication Delete | S3 버전 영구 삭제·버전 관리 중단 시 MFA 인증 코드를 추가로 요구하는 보호 장치 |

## 📖 핵심 개념

### 1) AWS Backup — 정책 기반 중앙 백업

> 공식 정의: **"AWS Backup은 여러 AWS 서비스에 걸친 데이터 보호를 중앙에서 구성·관리·자동화하는 완전관리형 서비스다."**

| 구성 요소 | 역할 |
|---|---|
| **백업 계획(Backup Plan)** | 언제·얼마나 자주·어디에 백업할지 정의하는 정책 컨테이너 |
| **백업 규칙(Backup Rule)** | 일정(cron/rate)·보존 기간·콜드 스토리지 전환·대상 볼트·교차 리전/계정 복사 설정 |
| **백업 볼트(Backup Vault)** | 백업(복구 지점)을 저장하는 논리적 컨테이너. KMS 암호화·액세스 정책 적용 |
| **리소스 할당** | 태그 또는 리소스 ID로 백업 대상(EBS·RDS·DynamoDB·EFS·S3 등)을 계획에 연결 |

- **교차 리전 복사**: 규칙에서 백업을 다른 리전 볼트로 복사 → 리전 장애 대비.
- **교차 계정 복사**: 별도 계정 볼트로 복사 → 계정 침해·실수 삭제로부터 격리.

> 🧠 원리: 왜 AWS Backup은 리소스를 직접 나열하지 않고 태그로 할당할까요?
> 태그 기반 할당은 새 리소스가 생성될 때 해당 태그만 붙으면 백업 대상에 자동으로 포함되므로, 관리자가 계획을 수정하지 않아도 인프라 변화가 백업 정책에 반영됩니다.
> 리소스 ID를 직접 나열하는 방식은 리소스가 교체·증설될 때마다 목록을 수동으로 갱신해야 해 운영 실수로 이어질 수 있습니다.
> 태그 정책과 백업 계획을 조합하면 "이 태그가 있는 모든 리소스는 이 정책으로 백업된다"는 선언적 운영이 가능합니다.

### 2) Backup Vault Lock — 불변 백업

> Vault Lock은 백업을 **WORM(Write Once Read Many)**으로 보호해 보존 기간 내 삭제·변경을 막습니다.

| 모드 | 특성 |
|---|---|
| **거버넌스(Governance) 모드** | 특정 IAM 권한을 가진 사용자만 잠금 해제·삭제 가능. 운영 실수 방지용 |
| **규정 준수(Compliance) 모드** | **루트 사용자도 되돌릴 수 없음.** 콜드오프(grace) 기간 경과 후에는 잠금 해제 불가 → 랜섬웨어·내부자 삭제로부터 강력 보호 |

> **운영 포인트**: 규정 준수 모드는 한 번 확정되면 누구도 보존 정책을 약화하거나 백업을 조기 삭제할 수 없습니다. 규제 준수(금융·의료)나 랜섬웨어 대비에 사용합니다.

> 🧠 원리: 왜 Vault Lock에는 거버넌스와 규정 준수 두 모드가 분리되어 있을까요?
> 거버넌스 모드는 실수나 의도치 않은 삭제를 방지하면서도 권한을 가진 관리자가 잠금을 해제할 수 있는 유연성을 남겨두어, 정책 변경이나 테스트 환경에서 운영 부담을 줄일 수 있습니다.
> 규정 준수 모드는 콜드오프 기간이 지나면 루트 계정을 포함해 어떤 사용자도 잠금을 해제할 수 없어, 법적·규제적 감사에서 "누군가 조작할 수 없었음"을 증명할 수 있습니다.
> 두 모드의 분리는 "운영 편의"와 "규제 불가역성" 사이의 트레이드오프를 조직이 상황에 맞게 선택하도록 합니다.

### 3) EBS 스냅샷 — 증분이지만 각 스냅샷은 완전한 복원 지점

> 공식: **"EBS 스냅샷은 증분식으로 저장되며 Amazon S3에 보관된다(사용자가 직접 볼 수 없는 AWS 관리 S3)."**

- **증분(Incremental)**: 첫 스냅샷은 전체, 이후엔 **직전 스냅샷 이후 변경된 블록만** 저장 → 비용·시간 절약.
- **각 스냅샷은 완전한 복원 지점**: 증분 저장이지만, 어떤 스냅샷에서 복원하든 그 시점의 **전체 볼륨**이 복원됩니다. 중간 스냅샷을 지워도 의존하는 데이터는 자동 보존됩니다.
- **AMI**: AMI는 인스턴스의 루트(및 추가) EBS 볼륨 스냅샷을 포함합니다. AMI를 만들면 그 시점 볼륨 스냅샷이 함께 생성됩니다.
- **교차 리전/계정 복사**: 스냅샷을 다른 리전·계정으로 복사 가능(DR·공유).

> 🧠 원리: 왜 증분으로 저장하면서도 각 스냅샷은 독립적으로 복원할 수 있을까요?
> EBS 스냅샷은 실제 데이터 블록을 참조 구조로 관리하므로, 어떤 스냅샷이든 그 시점의 전체 볼륨 상태를 구성하는 모든 블록을 추적할 수 있습니다.
> 중간 스냅샷을 삭제할 때 AWS는 다른 스냅샷이 참조하는 블록을 파악해 삭제하지 않고 보존하므로, 남아 있는 스냅샷의 복원 능력이 유지됩니다.
> 이 구조 덕분에 "증분으로 저장하면 이전 스냅샷에 의존한다"는 직관과 달리, 어느 스냅샷이든 그 시점 전체 볼륨의 독립적인 복원 지점으로 동작합니다.

### 4) DLM — Data Lifecycle Manager (스냅샷·AMI 자동화)

> DLM은 **EBS 스냅샷과 AMI의 생성·보존·삭제를 정책으로 자동화**합니다.

| 항목 | 내용 |
|---|---|
| **대상 선택** | 태그로 EBS 볼륨·인스턴스를 지정 |
| **일정** | 생성 주기(예: 매일/매시간)와 시작 시간 |
| **보존** | 개수 기반 또는 기간 기반(예: 최근 7개 / 30일) 유지 후 자동 삭제 |
| **교차 리전/계정** | 정책에서 다른 리전·계정으로 복사 |

> AWS Backup과 DLM은 모두 스냅샷을 자동화하지만, **여러 서비스를 정책 하나로 중앙 관리**하려면 AWS Backup, **EBS·AMI에 한정한 가볍고 무료인 자동화**는 DLM을 씁니다.

> 🧠 원리: 왜 DLM은 EBS·AMI에만 작동하고 RDS·DynamoDB는 다루지 않을까요?
> DLM은 EBS 볼륨과 EC2 인스턴스의 스냅샷 API를 직접 호출하는 방식으로 동작하므로, 같은 API 체계를 공유하는 EBS·AMI 범위 안에서 일관된 정책을 적용할 수 있습니다.
> RDS·DynamoDB는 스토리지 계층이 추상화된 관리형 서비스로 EBS 스냅샷 API를 공유하지 않으며, 각 서비스는 자체 백업 메커니즘을 갖고 있습니다.
> 이 범위 제약이 DLM을 가볍고 무료로 유지하는 이유이기도 하며, 다중 서비스가 필요하면 그 통합을 AWS Backup이 맡습니다.

### 5) RDS 백업 — 자동 백업·PITR·수동 스냅샷

| 유형 | 특성 |
|---|---|
| **자동 백업(Automated Backups)** | 매일 백업 + 트랜잭션 로그. **보존 기간 1~35일**. 보존 기간 내 **특정 시점 복원(PITR)** 가능 |
| **특정 시점 복원(PITR)** | 보존 기간 내 임의 시점(초 단위 근접)으로 **새 인스턴스** 복원 |
| **수동 스냅샷(Manual Snapshot)** | 사용자가 명시적으로 생성. **직접 삭제하기 전까지 무기한 보존**(35일 제한 없음) |

- **핵심 차이**: 자동 백업은 보존 기간(최대 35일) 후 사라지고 PITR을 지원합니다. 장기 보관이 필요하면 **수동 스냅샷**을 만듭니다(또는 AWS Backup으로 관리).
- 복원은 항상 **새 DB 인스턴스**로 이루어집니다(기존 인스턴스를 덮어쓰지 않음).
- RDS 스냅샷도 **교차 리전 복사** 가능 → DR.

> 🧠 원리: 왜 RDS 자동 백업에는 최대 35일 한도가 있고 수동 스냅샷은 무기한일까요?
> 자동 백업은 PITR을 지원하기 위해 매일 전체 백업과 연속 트랜잭션 로그를 유지하므로, 보존 기간이 길어질수록 저장·관리 비용이 누적됩니다.
> AWS는 자동 백업의 보존 기간 상한을 최대 35일로 제한하며, 그 이상의 장기 보관은 사용자가 명시적으로 수동 스냅샷을 생성하거나 AWS Backup으로 관리해야 합니다.
> 운영 복구(PITR)는 자동 백업으로, 감사·규제 요건의 장기 보관은 무기한 유지되는 수동 스냅샷으로 분리하는 것이 트레이드오프를 명확히 하는 접근입니다.

### 6) S3 데이터 보호 — 버전 관리 + 수명 주기 + 복제

| 기능 | 역할 |
|---|---|
| **버전 관리(Versioning)** | 객체의 모든 버전 보존. 덮어쓰기·삭제 시 이전 버전 복구 가능. 삭제는 **삭제 마커**로 처리(원복 가능) |
| **MFA Delete** | 버전 영구 삭제·버전 관리 중단에 MFA 요구 → 실수·악의 삭제 방지 |
| **수명 주기(Lifecycle)** | 시간 경과에 따라 스토리지 클래스 전환(예: Standard→IA→Glacier)·만료 삭제 자동화 |
| **복제(Replication, CRR/SRR)** | 다른 리전(CRR)·동일 리전(SRR) 버킷으로 객체 자동 복제. **버전 관리 활성화가 전제** |

> S3는 백업 대상이자 백업 저장소입니다. 버전 관리로 변조·삭제를 되돌리고, 수명 주기로 오래된 버전을 저비용 계층으로 보내며, 복제로 리전 장애에 대비합니다(복제 상세는 `soa-t2-4`).

> 🧠 원리: 왜 S3 복제(CRR/SRR)는 버전 관리가 활성화되어 있어야만 동작할까요?
> 복제는 버킷에 새로 추가·변경되는 객체를 대상 버킷에 동기화하는데, 객체가 덮어쓰이거나 삭제될 때 이전 상태를 추적하려면 버전 식별자가 필요합니다.
> 버전 관리가 없으면 동일 키에 새 객체가 쓰일 때 이전 객체가 사라지므로, 복제 엔진이 "어느 버전을 복제했고 어느 변경이 새 것인지" 구분하는 기준이 없어집니다.
> 이 의존성으로 인해 버전 관리를 먼저 켜지 않으면 복제 설정 자체가 거부되며, 소스·대상 버킷 모두에 버전 관리가 필요한 이유가 됩니다.

### 7) 운영 절차 — 백업 계획 → 정기 실행 → 복원 테스트

1. **AWS Backup**에서 백업 계획 생성: 규칙(일정·보존·콜드 스토리지·교차 리전 복사) 정의.
2. **리소스 할당**: 태그(예: `Backup=daily`)로 EBS·RDS·DynamoDB·EFS 등을 계획에 연결.
3. (선택) **Vault Lock** 적용으로 백업 불변화(규제·랜섬웨어 대비).
4. **정기 실행 모니터링**: AWS Backup 작업 상태·실패 알림(EventBridge/SNS)을 확인.
5. **복원 테스트(★ 핵심)**: 주기적으로 복구 지점에서 **실제 복원**을 수행해 데이터 무결성과 RTO를 검증. "백업은 됐는데 복원이 안 되는" 상황을 사전에 발견.

> 🧠 원리: 왜 백업 성공 기록만으로는 복원 가능성을 보장할 수 없을까요?
> 백업 작업의 성공 여부는 데이터가 백업 저장소에 기록되었음을 의미하지만, 그 데이터가 실제로 완전하고 일관된 상태인지, 복원 절차가 목표 RTO 안에 완료될 수 있는지는 별도로 검증해야 합니다.
> 스토리지 손상, 백업 에이전트 오류, 의존 리소스 설정 변화 등이 복원 과정에서만 드러나는 문제를 만들 수 있으며, 이는 실제 장애 상황에서 처음 확인하면 늦습니다.
> 정기 복원 테스트는 이러한 잠재적 문제를 사전에 발견하고, 실제 장애 시 절차와 담당자가 익숙해져 있도록 하는 운영 검증의 핵심 수단입니다.

## ✍️ 시험 포인트

- **AWS Backup = 다중 서비스 중앙 백업**(EBS·RDS·DynamoDB·EFS·S3 등). 계획→규칙→볼트→리소스 할당(태그) 구조.
- **Vault Lock 규정 준수 모드 = 루트도 못 지움**(WORM). 거버넌스 모드는 권한자만 해제 가능. 랜섬웨어·규제 대비.
- **EBS 스냅샷 = 증분 저장이지만 각 스냅샷은 완전한 복원 지점**. S3에 저장. 중간 스냅샷 삭제해도 복원 가능.
- **DLM = EBS 스냅샷·AMI 자동화**(무료, 태그 기반). 다중 서비스 통합 관리는 AWS Backup.
- **RDS 자동 백업 = 1~35일 보존 + PITR**. **수동 스냅샷 = 무기한 보존**(장기 보관). 복원은 항상 새 인스턴스.
- **S3 복제(CRR/SRR)는 버전 관리 활성화가 전제**. 버전 관리 + MFA Delete로 삭제 방지.
- **백업했다 ≠ 복원된다** → 정기 복원 테스트가 운영의 핵심.

## ⚠️ 흔한 함정

1. **"EBS 스냅샷은 증분이라 중간 걸 지우면 복원이 깨진다."** → 아닙니다. 각 스냅샷은 **완전한 복원 지점**입니다. AWS가 의존 블록을 자동 보존하므로 어떤 스냅샷에서든 그 시점 전체 볼륨이 복원됩니다.
   *(원리: §3 — 스냅샷은 참조 구조로 블록을 관리해 삭제해도 다른 스냅샷이 필요한 블록은 자동 보존된다.)*

2. **"RDS 자동 백업은 영구 보관된다."** → 자동 백업은 **최대 35일** 보존 후 만료됩니다. 장기 보관이 필요하면 **수동 스냅샷**을 만들거나 AWS Backup으로 관리해야 합니다.
   *(원리: §5 — 자동 백업은 최대 35일까지 보존되며, 장기 보관이 필요하면 수동 스냅샷이나 AWS Backup을 명시적으로 사용해야 한다.)*

3. **"S3 복제만 켜면 된다."** → CRR/SRR은 **소스·대상 버킷 모두 버전 관리가 활성화**되어 있어야 동작합니다. 버전 관리 없이 복제는 구성할 수 없습니다.
   *(원리: §6 — 버전 식별자가 없으면 복제 엔진이 어느 변경이 새 것인지 추적하는 기준이 없어 설정 자체가 거부된다.)*

4. **"Vault Lock 거버넌스 모드면 루트가 못 지운다."** → 거버넌스 모드는 **권한을 가진 사용자**가 해제·삭제할 수 있습니다. 루트도 되돌릴 수 없는 진짜 불변성은 **규정 준수(Compliance) 모드**입니다.
   *(원리: §2 — 거버넌스는 권한자가 잠금 해제 가능한 유연성을, 규정 준수는 루트도 되돌릴 수 없는 불가역성을 각각 제공하는 트레이드오프다.)*

5. **"백업 계획만 만들면 모든 리소스가 백업된다."** → 백업 계획에 **리소스를 할당(태그/ID)**해야 백업됩니다. 태그가 없거나 할당이 빠지면 백업 대상에서 누락됩니다.
   *(원리: §1 — 태그 기반 할당은 선언적이므로 태그 없는 리소스는 계획 범위에 포함되지 않는다.)*

6. **"DLM으로 RDS·DynamoDB도 자동화한다."** → DLM은 **EBS 스냅샷·AMI**만 자동화합니다. RDS·DynamoDB·EFS 등 다중 서비스 통합 자동화는 **AWS Backup**입니다.
   *(원리: §4 — DLM은 EBS 스냅샷 API를 공유하는 EBS·AMI만 지원하며, 스토리지가 추상화된 관리형 서비스는 각자 자체 백업 메커니즘을 사용한다.)*

7. **"백업이 성공했으니 복원도 된다."** → 검증 없는 백업은 위험합니다. 정기 **복원 테스트**로 무결성과 RTO를 확인해야 합니다.
   *(원리: §7 — 백업 성공 기록은 데이터 완전성과 RTO 달성을 보장하지 않으며, 복원 과정에서만 드러나는 문제가 있다.)*

## 🧪 자가 점검

> 아래는 학습용 자가 점검입니다. (정식 검증 문항은 별도 문항 파일 참조)

**Q1.** EBS 볼륨을 매일 스냅샷하는데 비용이 걱정됩니다. 또 며칠 전 스냅샷을 지우면 그 이후 스냅샷 복원이 깨질까 우려됩니다. 사실은 어떤가요?

<details><summary>정답 보기</summary>

EBS 스냅샷은 **증분 저장**이라 첫 스냅샷 이후에는 변경된 블록만 저장하므로 비용이 절약됩니다. 그리고 각 스냅샷은 **독립적인 완전한 복원 지점**입니다. 중간 스냅샷을 삭제해도 다른 스냅샷이 참조하는 데이터 블록은 AWS가 자동으로 보존하므로, 남아 있는 어떤 스냅샷에서든 해당 시점의 전체 볼륨을 정상 복원할 수 있습니다. 생성·보존·삭제를 자동화하려면 DLM을 사용합니다.
</details>

**Q2.** 규제 요건상 백업을 7년간 보관해야 하며, 내부자나 랜섬웨어가 백업을 조기 삭제하지 못하도록 해야 합니다. 어떻게 구성하나요?

<details><summary>정답 보기</summary>

**AWS Backup의 백업 볼트에 Vault Lock을 규정 준수(Compliance) 모드로 적용**합니다. 규정 준수 모드는 콜드오프 기간 경과 후에는 **루트 사용자도** 보존 정책을 약화하거나 백업을 삭제할 수 없는 WORM 불변성을 제공합니다. 백업 계획의 보존 기간을 규제에 맞게(예: 7년) 설정하고, 필요 시 교차 계정/리전 복사로 격리합니다.
</details>

**Q3.** RDS 데이터베이스를 실수로 잘못된 쿼리로 손상시켰습니다. 30분 전 상태로 되돌리고 싶습니다. 자동 백업 보존 기간 내라면 어떻게 하나요?

<details><summary>정답 보기</summary>

**특정 시점 복원(PITR)**을 사용합니다. RDS 자동 백업은 매일 백업 + 트랜잭션 로그를 보존 기간(1~35일) 동안 유지하므로, 보존 기간 내 임의 시점(예: 30분 전)으로 복원할 수 있습니다. 복원은 **새 DB 인스턴스**로 생성되므로, 검증 후 애플리케이션 엔드포인트를 새 인스턴스로 전환합니다.
</details>

**Q4.** EBS·RDS·DynamoDB·EFS를 하나의 정책으로 일정·보존·교차 리전 복사까지 중앙 관리하고 싶습니다. 어떤 서비스를 쓰나요?

<details><summary>정답 보기</summary>

**AWS Backup**입니다. 백업 계획에 규칙(일정·보존·콜드 스토리지·교차 리전/계정 복사)을 정의하고, 태그 또는 리소스 ID로 EBS·RDS·DynamoDB·EFS·S3 등 다중 서비스를 한 계획에 할당해 중앙에서 관리합니다. DLM은 EBS 스냅샷·AMI 자동화에 한정되므로 이 다중 서비스 요구에는 적합하지 않습니다.
</details>

**Q5 (원리).** 왜 S3 버킷에 버전 관리 없이 복제를 설정하려 하면 실패하나요?

<details><summary>정답 보기</summary>

S3 복제는 소스 버킷에서 발생하는 객체 변경을 대상 버킷에 동기화하는데, 동일 키에 새 객체가 쓰이거나 삭제가 발생할 때 "어느 버전까지 복제했고 무엇이 새 변경인지"를 추적하는 기준으로 버전 식별자를 사용합니다. 버전 관리가 비활성화된 버킷에는 버전 식별자가 없어 복제 엔진이 변경을 추적할 수 없으므로, AWS는 복제 설정 자체를 거부합니다.
</details>
