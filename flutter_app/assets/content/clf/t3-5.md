## 📖 핵심 개념

### 1) Amazon VPC — 나만의 격리된 가상 네트워크

**Amazon VPC(Virtual Private Cloud)**는 **내가 정의한, 논리적으로 격리된 가상 네트워크**에 AWS 리소스를 시작하게 해 줍니다. 자체 데이터센터의 전통적 네트워크와 닮았지만 AWS의 확장 인프라 위에서 동작합니다.

**핵심 구성요소:**

| 구성요소 | 역할 |
|---|---|
| **서브넷(Subnet)** | VPC 안의 **IP 주소 범위**. **하나의 AZ**에 속함. 리소스를 여기에 배치 |
| **라우트 테이블(Route Table)** | 서브넷·게이트웨이의 **트래픽이 어디로 갈지** 결정 |
| **인터넷 게이트웨이(Internet Gateway)** | VPC를 **인터넷에 연결** |
| **VPC 엔드포인트(Endpoint)** | 인터넷 게이트웨이 없이 **AWS 서비스에 프라이빗하게** 연결 |
| **NAT 게이트웨이** | *프라이빗* 서브넷의 리소스가 인터넷으로 *나가는* 것만 허용(인바운드는 차단) |

> **퍼블릭 서브넷 vs 프라이빗 서브넷:** 인터넷 게이트웨이로 가는 경로가 있으면 **퍼블릭**(예: 웹 서버), 없으면 **프라이빗**(예: DB). VPC 자체는 무료이고 일부 구성요소(NAT 게이트웨이 등)만 과금됩니다.

> 🧠 원리: 왜 VPC는 서브넷을 AZ 단위로 나누고, 라우트 테이블로 경로를 별도로 제어할까요?
> 서브넷이 AZ 하나에 속하도록 제한하면 리소스를 여러 AZ에 분산 배치해 장애 격리가 가능해집니다 — AZ 하나에 장애가 생겨도 다른 AZ의 서브넷과 리소스는 영향을 받지 않습니다.
> 라우트 테이블을 서브넷 수준에서 별도로 두면 같은 VPC 안에서도 퍼블릭(인터넷 게이트웨이 경로 포함)과 프라이빗(인터넷 경로 없음) 서브넷을 다르게 제어할 수 있어, 웹 서버와 DB를 같은 네트워크 경계 안에 두면서 외부 접근 범위를 다르게 설정하는 것이 가능합니다.
> 두 원칙을 묶으면 물리적 장애 격리(AZ)와 논리적 접근 격리(서브넷 라우트 테이블)가 서로 다른 계층에서 독립적으로 작동해, 하나가 변경돼도 다른 하나에 영향을 주지 않는 설계가 됩니다.

### 2) VPC 보안 2층 — 보안 그룹 vs 네트워크 ACL (2.4 복습)

VPC 안 트래픽은 두 층에서 걸러집니다(자세한 비교는 [보안 구성요소 2.4](#)).

- **보안 그룹** = **인스턴스 수준**, **Stateful**(응답 자동 허용), **허용(Allow) 규칙만**.
- **네트워크 ACL** = **서브넷 수준**, **Stateless**(응답도 규칙 필요), **허용·거부(Deny) 모두**.

> 🧠 원리: 왜 VPC는 보안 그룹(인스턴스)과 네트워크 ACL(서브넷)을 두 층으로 분리해 운영할까요?
> 보안 그룹은 특정 인스턴스가 받을 수 있는 트래픽만 정밀하게 제어하고, 같은 요청에 대한 응답 트래픽을 자동으로 허용하는 Stateful 방식으로 설정 부담을 줄입니다.
> 네트워크 ACL은 서브넷 전체에 일괄 적용되는 방어선으로, 허용·거부 규칙을 모두 명시적으로 정의해 서브넷 경계에서 넓은 범위의 트래픽을 차단하는 데 사용합니다.
> 두 층을 함께 쓰면 서브넷 경계에서 큰 범위를 차단하고 개별 인스턴스에서 세밀한 허용 규칙을 적용하는 심층 방어(defense in depth)가 가능해집니다.

### 3) Amazon Route 53 — DNS 웹 서비스

**Amazon Route 53**은 **고가용성·확장성 있는 DNS(Domain Name System) 웹 서비스**입니다. 세 가지 기능을 (조합해) 수행합니다:

1. **도메인 등록(Domain registration)** — `example.com` 같은 도메인 이름을 등록.
2. **DNS 라우팅(DNS routing)** — 사용자가 도메인 이름을 입력하면 **그 이름을 리소스의 IP로 변환**해 브라우저를 웹사이트·앱에 연결.
3. **상태 확인(Health checking)** — 리소스(웹 서버 등)가 정상인지 자동 점검하고, **비정상 리소스에서 트래픽을 우회**.

> 한 줄: **Route 53 = AWS의 DNS.** "도메인 이름을 IP로 연결 / 도메인 등록 / 트래픽 라우팅"이면 Route 53. (다양한 라우팅 정책: 지연시간·지리·가중치·장애 조치 등.)

> 🧠 원리: 왜 Route 53은 단순 이름 변환에 그치지 않고 상태 확인(헬스 체크)을 DNS와 함께 제공할까요?
> DNS가 도메인 이름을 IP로 변환하기만 한다면, 해당 IP의 서버가 응답 불능 상태일 때도 사용자 요청을 그쪽으로 보내 실패가 발생합니다.
> Route 53은 리소스 상태를 주기적으로 확인해 비정상 엔드포인트를 DNS 응답에서 제외하거나 다른 리소스로 자동 라우팅하므로, 애플리케이션 계층의 장애 조치가 DNS 수준에서 가능해집니다.
> 이 방식으로 별도의 로드 밸런서 없이도 여러 리전·엔드포인트 사이에서 가용성 기반 라우팅이 가능해집니다.

### 4) 온프레미스 연결 — Direct Connect vs Site-to-Site VPN (★ 시험 핵심)

온프레미스(자체 데이터센터)를 AWS에 잇는 두 방법:

| 구분 | **AWS Direct Connect** | **AWS Site-to-Site VPN** |
|---|---|---|
| 무엇 | **전용 물리 회선**(표준 이더넷 광케이블)으로 내 네트워크를 AWS에 직접 연결 | 온프레미스와 VPC를 **IPsec VPN 터널**로 연결 |
| 경로 | **공용 인터넷을 우회**(ISP를 거치지 않음) | **공용 인터넷 위**로(암호화된 터널) |
| 성능 | **일관되고 안정적**(전용) | 인터넷 상태에 의존 |
| 구축·시작 | 물리 회선 구축 필요(수주~수개월) | **기존 인터넷 회선으로 빠르게 시작**(소프트웨어 설정) |
| 보안 | 프라이빗 회선 | **IPsec 암호화** |

> 시험 신호:
> - **"일관된 고성능 / 전용 / 공용 인터넷을 거치지 않는다 / 대용량 안정적 전송"** → **Direct Connect**.
> - **"기존 인터넷 회선으로 빠르게 시작 / 암호화된 연결 / 인터넷을 통해 안전하게"** → **Site-to-Site VPN**.
> - 구성: VPN은 AWS 측 **가상 프라이빗 게이트웨이(또는 Transit Gateway)** + 고객 측 **고객 게이트웨이**.

> 🧠 원리: 왜 Direct Connect는 인터넷을 통한 암호화 대신 전용 물리 회선을 별도로 구축하는 방식을 택할까요?
> 공용 인터넷은 경로가 고정되지 않고 여러 사업자를 거치기 때문에, 대역폭이 다른 트래픽과 공유되고 지연시간이 시간대·경로에 따라 달라집니다.
> 전용 물리 회선은 해당 트래픽만 사용하는 독점 경로이므로 대역폭과 지연시간이 예측 가능하게 유지되고, 공용 인터넷을 우회하기 때문에 네트워크 경로 수준의 프라이버시도 확보됩니다.
> 이 일관성이 필요한 대용량 데이터 전송이나 규정상 공용 인터넷을 거칠 수 없는 워크로드에 Direct Connect가 Site-to-Site VPN보다 적합한 이유입니다.

### 5) 엣지 서비스 — CloudFront · Global Accelerator (3.2 복습)

전 세계 사용자에게 빠르게 전달하는 엣지 서비스(자세한 내용은 [글로벌 인프라 3.2](#)):

- **Amazon CloudFront** = **CDN**(콘텐츠를 엣지에 *캐시*).
- **AWS Global Accelerator** = **고정 IP + AWS 글로벌 네트워크 라우팅**(캐싱 아님).

> 🧠 원리: 왜 CloudFront와 Global Accelerator는 같은 엣지 거점을 활용하면서도 서로 다른 방식으로 성능을 높일까요?
> CloudFront는 콘텐츠(이미지·HTML·영상 등)를 엣지 로케이션에 캐시해 두고 사용자 가까이서 응답하므로, 반복 요청 시 오리진 서버까지 왕복하지 않아 지연시간이 줄어듭니다.
> Global Accelerator는 콘텐츠를 캐시하지 않고 사용자 트래픽을 공용 인터넷 대신 AWS 글로벌 백본 네트워크를 통해 최적 경로로 오리진까지 전달하므로, 캐시하기 어려운 동적 요청이나 실시간 트래픽의 지연시간과 안정성을 높이는 데 적합합니다.
> 두 서비스는 "캐싱으로 오리진 왕복 제거"와 "네트워크 경로 최적화"라는 서로 다른 메커니즘으로 성능을 높여, 워크로드 특성에 따라 골라 쓰거나 함께 쓸 수 있습니다.

## ✍️ 시험 포인트

- **VPC** = 논리적으로 격리된 *나만의* 가상 네트워크. **서브넷**은 하나의 AZ 안 IP 범위.
- **인터넷 게이트웨이** = VPC를 인터넷에 연결. **라우트 테이블** = 트래픽 경로 결정.
- **Route 53 = DNS**(도메인 등록·이름→IP 라우팅·헬스 체크).
- **Direct Connect = 전용 프라이빗 회선(인터넷 우회, 일관된 성능).** **Site-to-Site VPN = 인터넷 위 IPsec 암호화 터널(기존 인터넷 회선으로 빠르게 시작).**
- **보안 그룹(인스턴스·stateful·허용) vs 네트워크 ACL(서브넷·stateless·허용+거부)** ([2.4](#)).
- **CloudFront = CDN 캐싱, Global Accelerator = 고정 IP 라우팅** ([3.2](#)).

## ⚠️ 흔한 함정

1. **"Route 53은 로드 밸런서다."** → ❌. Route 53은 **DNS**(도메인 이름을 IP로 해석·라우팅). 인스턴스 간 트래픽 분산은 **ELB**([3.3](#)).
   *(원리: §3 — Route 53은 도메인 이름을 IP로 변환하고 상태 기반으로 엔드포인트를 라우팅하는 DNS 서비스로, 인스턴스 풀에 트래픽을 분산하는 로드 밸런서와 동작 계층이 다르다.)*
2. **"Direct Connect는 인터넷을 통한 암호화 연결이다."** → ❌. Direct Connect는 **전용 물리 회선으로 공용 인터넷을 우회**합니다. *인터넷 위 IPsec*은 **Site-to-Site VPN**.
   *(원리: §4 — Direct Connect는 전용 물리 회선으로 공용 인터넷을 우회해 일관된 성능을 확보하는 구조이며, IPsec 암호화 터널로 인터넷 위에서 연결하는 방식은 Site-to-Site VPN이다.)*
3. **"서브넷은 여러 AZ에 걸친다."** → ❌. **서브넷은 하나의 AZ**에 속합니다(고가용성은 여러 AZ에 서브넷을 두어 구성).
   *(원리: §1 — 서브넷을 AZ 단위로 제한해 두면 AZ 단위 장애 격리가 가능해지며, 고가용성은 여러 AZ에 별도 서브넷을 두는 방식으로 구성한다.)*
4. **"VPC를 쓰면 추가 요금이 많이 든다."** → ⚠️ VPC 자체는 무료. NAT 게이트웨이 등 *일부 구성요소*만 과금.
   *(원리: §1 본문 — VPC 자체는 논리적 격리를 제공하는 구조로 과금되지 않으며, NAT 게이트웨이처럼 처리하는 트래픽이 발생하는 구성요소만 별도로 과금된다.)*
5. **"인터넷에 노출하면 안 되는 DB도 퍼블릭 서브넷에 둔다."** → ❌. 외부 노출이 불필요한 리소스는 **프라이빗 서브넷**에.
   *(원리: §1 — 퍼블릭 서브넷은 인터넷 게이트웨이 경로가 있어 외부에서 접근 가능한 구조이고, DB처럼 직접 노출이 불필요한 리소스는 그 경로가 없는 프라이빗 서브넷에 두어 접근 범위를 좁힌다.)*
6. **"빠르게 온프레미스를 연결하려면 Direct Connect."** → ⚠️ 시작 용이성은 반대. **VPN은 기존 인터넷 회선으로 빠르게 시작하기 쉽고**, Direct Connect는 **전용 연결로 일관된 성능**을 제공하지만 물리 회선 구축이 필요합니다.
   *(원리: §4 — Direct Connect는 물리 회선 구축이 필요해 시작까지 시간이 걸리지만 일관된 성능을 얻을 수 있고, Site-to-Site VPN은 소프트웨어 설정만으로 기존 인터넷 회선을 통해 빠르게 시작할 수 있어 시작 용이성과 일관된 성능이 각각의 차별점이다.)*

## 🧪 자가 점검

> 아래는 학습용 자가 점검입니다. (정식 검증 문항은 `t3-5.questions.json` 참조)

**Q1.** AWS 리소스를 논리적으로 격리된 *나만의* 가상 네트워크 안에서 실행하고, 서브넷·라우트 테이블·인터넷 게이트웨이를 직접 제어하려면 무엇을 쓰나요?

<details><summary>정답 보기</summary>

**Amazon VPC**(Virtual Private Cloud). 내가 정의한, 논리적으로 격리된 가상 네트워크에 리소스를 시작하고 IP 범위·서브넷·라우팅·게이트웨이를 제어합니다.
</details>

**Q2.** 도메인 이름(example.com)을 등록하고, 사용자가 그 이름을 입력했을 때 해당 리소스의 IP로 연결되도록 라우팅하려면 어떤 서비스인가요?

<details><summary>정답 보기</summary>

**Amazon Route 53**(DNS 웹 서비스). 도메인 등록, 도메인 이름→IP 라우팅, 리소스 상태 확인의 세 기능을 제공합니다.
</details>

**Q3.** 온프레미스 데이터센터를 AWS에 **공용 인터넷을 거치지 않는 전용 회선**으로 연결해 일관되고 안정적인 네트워크 성능을 얻으려면? 그리고 **빠르고 저렴하게 인터넷을 통해 암호화 연결**하려면?

<details><summary>정답 보기</summary>

전자는 **AWS Direct Connect**(전용 물리 회선, 인터넷 우회), 후자는 **AWS Site-to-Site VPN**(공용 인터넷 위 IPsec 암호화 터널).
</details>

**Q4.** 한 서브넷은 몇 개의 가용 영역(AZ)에 속하나요? 그리고 VPC를 인터넷에 연결하는 구성요소는?

<details><summary>정답 보기</summary>

서브넷은 **하나의 AZ**에 속합니다(여러 AZ에 서브넷을 두어 고가용성 구성). VPC를 인터넷에 연결하는 것은 **인터넷 게이트웨이**입니다.
</details>

---

**Q5 (원리).** 왜 온프레미스와 AWS를 연결할 때 Site-to-Site VPN만으로 충분하지 않고 Direct Connect가 별도로 필요할까요?

<details><summary>정답 보기</summary>

Site-to-Site VPN은 공용 인터넷 위에 IPsec 암호화 터널을 만들기 때문에, 인터넷 경로의 혼잡도와 구간별 지연에 따라 대역폭과 지연시간이 달라집니다. 대용량 데이터를 지속적으로 전송하거나 성능 변동이 허용되지 않는 워크로드는 이 가변성이 문제가 됩니다. Direct Connect는 전용 물리 회선으로 공용 인터넷을 완전히 우회하므로 대역폭과 지연시간이 예측 가능하게 유지되고, 규정상 공용 인터넷 경유가 금지된 워크로드도 수용할 수 있어 VPN과 해결하는 요구 자체가 다릅니다.
</details>
