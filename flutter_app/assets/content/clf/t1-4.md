| 용어 | 영문 | 한 줄 풀이 |
|---|---|---|
| **자본 지출** | CapEx (Capital Expenditure) | 자산을 *미리 구매*하는 지출 — 서버·데이터센터 선투자가 대표적 |
| **운영 지출** | OpEx (Operational Expenditure) | 서비스를 *사용한 만큼* 매기는 지출 — 클라우드 월 청구가 대표적 |
| **총소유비용** | TCO (Total Cost of Ownership) | 직접 비용뿐 아니라 *운영·인력·유지보수 등 간접 비용*을 모두 합한 실제 비용 |
| **과대 프로비저닝** | over-provisioning | 실제 수요보다 *크게 자원을 잡아두어* 낭비가 발생하는 상태 |
| **규모의 경제** | economies of scale | 사용량이 많아질수록 *단위당 비용이 낮아지는* 현상 |
| **IaC** | Infrastructure as Code | 인프라를 *코드(템플릿) 형태*로 정의해 자동으로 프로비저닝하는 방식 |
| **메트릭** | metric | 시스템 상태를 나타내는 *측정값* — CPU 사용률·네트워크 트래픽 등 |

## 📖 핵심 개념

### 1) 클라우드 경제학의 출발 — 고정비 vs 변동비

- **고정비(자본 지출, CapEx):** 데이터센터·물리 서버를 *미리 크게* 사 두는 비용. 사용 여부와 무관하게 발생.
- **변동비(운영 지출, OpEx):** 클라우드에서 **쓴 만큼만** 내는 비용.

> 공식: 클라우드는 **"고정비를 변동비로 바꾸고, 소비한 만큼만 IT 비용을 낸다."** 온프레미스에는 *숨은 비용*(전력·냉각·공간·하드웨어 교체·운영 인력, 과대 프로비저닝으로 노는 용량)이 많습니다. 클라우드는 이를 줄입니다(규모의 경제로 변동비도 더 저렴).

> 🧠 원리: 왜 클라우드는 고정비를 변동비로 바꿀 수 있을까요?
> 온프레미스에서 서버를 사려면 피크 수요를 예측해 미리 충분한 용량을 구입해야 합니다.
> 그런데 실제 트래픽은 시간·계절·이벤트에 따라 크게 달라지기 때문에 대부분의 시간엔 구입한 용량의 일부만 쓰이고 나머지는 놀게 됩니다.
> 클라우드는 대규모 공유 인프라 위에서 수요에 맞게 할당·반납하는 구조이므로, 고객은 실제 사용한 시간·용량에 대해서만 비용을 냅니다.
> 고정 자산 매입이 아니라 서비스 소비로 전환되기 때문에 선투자 없이도 필요한 만큼 사용할 수 있습니다.

### 2) 적정 크기 조정(rightsizing) — Compute Optimizer

**rightsizing**은 워크로드에 **딱 맞는 크기의 리소스**를 골라 *과대/과소 프로비저닝*을 없애 비용을 낮추는 것입니다.

**AWS Compute Optimizer**는 리소스의 **구성·사용률 메트릭을 분석**해 **rightsizing 권장**과 **유휴 리소스 식별**을 제공합니다.

- 리소스가 *최적인지* 보고하고, **비용을 줄이고 성능을 높이는** 최적화 권장을 생성.
- 과대 프로비저닝(낭비)·과소 프로비저닝(성능 부족)을 짚어 *옮기거나 크기 조정*하도록 도움.

> 시험 신호: **"리소스 사용률을 분석해 적정 크기를 권장(rightsizing)"** → Compute Optimizer.

> 🧠 원리: Compute Optimizer가 왜 단순히 현재 크기를 줄이는 게 아니라 메트릭 분석을 기반으로 권장을 생성할까요?
> 과대 프로비저닝과 과소 프로비저닝은 모두 비용 문제를 일으키지만, 리소스를 무조건 줄이면 피크 시점에 성능이 떨어집니다.
> Compute Optimizer는 실제 사용 패턴(CPU·메모리·네트워크 메트릭의 최댓값·평균값)을 관찰해, 현재 크기가 실제 수요 대비 어느 방향으로 얼마나 어긋났는지를 파악합니다.
> 관찰된 패턴 안에서 비용과 성능이 모두 수용 가능한 크기를 찾아 권장하기 때문에, 단순 축소가 아니라 워크로드 특성에 맞는 조정이 가능합니다.

### 3) 라이선스 — BYOL vs 라이선스 포함

| 방식 | 의미 |
|---|---|
| **BYOL(Bring Your Own License)** | **이미 보유한 소프트웨어 라이선스를 가져와** 클라우드에서 사용(예: EC2 **Dedicated Hosts**로 기존 서버 바운드 라이선스 활용) |
| **라이선스 포함(License Included)** | 서비스 요금에 **라이선스 비용이 포함**(별도 라이선스 구매 불필요) |

> 기존 라이선스가 아깝다면 **BYOL**로 재활용해 비용을 아낄 수 있습니다.

> 🧠 원리: 왜 BYOL 옵션이 필요할까요?
> 소프트웨어 라이선스는 대개 물리 서버의 코어 수나 소켓 수에 묶인 형태로 판매됩니다.
> 클라우드로 이전할 때 해당 라이선스를 그냥 두면 이미 지불한 비용이 낭비되고, 클라우드 요금에 포함된 라이선스를 새로 구입하면 이중 비용이 발생합니다.
> Dedicated Hosts처럼 물리 호스트 단위로 할당된 환경을 제공하면, 기존 서버 바운드 라이선스 조건을 그대로 충족할 수 있어 기존 계약을 재활용할 수 있습니다.

### 4) 자동화의 비용 이점 — CloudFormation

**AWS CloudFormation**(IaC)으로 인프라를 **템플릿(코드)으로 반복·일관되게** 프로비저닝하면([3.1](#)):

- *사람이 수동으로 클릭*할 때 생기는 **실수·불일치·시간 비용**을 줄입니다.
- 여러 리전·계정에 **동일 환경을 빠르게 복제**해 운영 효율을 높입니다.

> 자동화 = *인적 비용·오류 감소* + *일관성*. CLF는 "자동화의 이점"을 비용 최적화 맥락에서 묻습니다.

> 🧠 원리: 왜 인프라를 코드(IaC)로 정의하면 수동 클릭보다 비용이 낮아질까요?
> 수동으로 콘솔을 클릭해 인프라를 구성하면, 담당자가 달라지거나 반복할 때마다 설정이 조금씩 달라질 수 있습니다.
> 이렇게 생긴 환경 불일치는 버그의 원인이 되고, 원인을 추적하는 데 엔지니어 시간이 소비됩니다.
> CloudFormation 템플릿은 동일한 코드를 실행하면 항상 동일한 환경이 만들어지도록 보장하므로, 불일치에서 비롯되는 오류 추적·수정 비용이 줄어듭니다.
> 또한 새 환경 구축 시 같은 템플릿을 재실행하면 되므로 반복 작업에 드는 인적 시간도 줄어듭니다.

### 5) 관리형 서비스로 총비용(TCO) 절감

**관리형 서비스**(예: **Amazon RDS, DynamoDB, ECS, EKS**)는 패치·백업·확장·고가용성 같은 **운영 작업을 AWS가 대신**합니다([3.3](#)·[3.4](#)).

- 고객은 *운영 인력·시간*을 줄이고 **애플리케이션에 집중** → **총소유비용(TCO) 절감**.
- 예: EC2에 DB를 직접 설치(OS·DB 패치·백업 직접) vs **RDS**(AWS가 관리).

> 시험 신호: **"운영 부담을 줄여 비용을 낮춘다"** → 관리형 서비스(RDS·DynamoDB 등).

> 🧠 원리: 관리형 서비스가 왜 단가가 높더라도 TCO를 낮출 수 있을까요?
> EC2에 데이터베이스를 직접 설치하면, OS 패치·DB 버전 업그레이드·백업 스케줄·장애 복구·다중 가용 영역 구성 등을 모두 엔지니어가 직접 수행해야 합니다.
> 이 작업들은 눈에 잘 띄지 않지만 계획·실행·검증에 상당한 인력 시간을 씁니다.
> RDS 같은 관리형 서비스는 이 작업들을 AWS가 맡으므로, 해당 운영 인력 비용이 청구서에 나타나지 않는 방식으로 절감됩니다.
> 서비스 단가는 높아도 절감된 인력 비용을 합산하면 실제 TCO는 낮아지는 경우가 많습니다.

### 탄력성으로 비용 최적화 — Auto Scaling (보강)

수요에 맞춰 용량을 자동으로 늘리고 줄이면(예: **Amazon EC2 Auto Scaling**), 피크 기준 고정 용량이 부르는 **과대 프로비저닝 비용**을 없앱니다. 한가할 땐 줄이고 바쁠 땐 늘려 *사용한 만큼만* 지불하므로, **탄력성이 곧 비용 효율**입니다. (정적으로 딱 맞는 크기를 고르는 것은 *rightsizing*, 수요에 따라 동적으로 조절하는 것은 *Auto Scaling*.)

> 시험 신호: "변동 수요에 맞춰 비용 최적화" → **Auto Scaling**(탄력성).
> 출처: [What is Amazon EC2 Auto Scaling?](https://docs.aws.amazon.com/autoscaling/ec2/userguide/what-is-amazon-ec2-auto-scaling.html)

> 🧠 원리: rightsizing과 Auto Scaling은 어떻게 다른 문제를 해결할까요?
> rightsizing은 *수요가 비교적 일정할 때* 해당 수요에 맞는 인스턴스 크기를 고르는 정적 최적화입니다.
> Auto Scaling은 *수요가 시간에 따라 크게 달라질 때* 인스턴스 수를 동적으로 늘리고 줄여 과대/과소 프로비저닝을 동시에 방지합니다.
> 두 접근은 상호 배타적이지 않습니다 — 인스턴스 유형은 rightsizing으로 최적화하고, 그 인스턴스를 Auto Scaling 그룹에 올려 수요 변동에 대응하면 비용 효율이 높아집니다.

## ✍️ 시험 포인트

- **고정비(CapEx) → 변동비(OpEx).** 온프레의 숨은 비용(전력·냉각·공간·인력·노는 용량) 제거.
- **rightsizing = 적정 크기**(과대/과소 프로비저닝 제거). 도구 = **Compute Optimizer**.
- **BYOL** = 기존 라이선스 재활용. **라이선스 포함** = 요금에 라이선스 포함.
- **자동화(CloudFormation)** = 수동 작업의 비용·오류↓, 일관성↑.
- **관리형 서비스(RDS·DynamoDB·ECS·EKS)** = AWS가 운영 → 운영비·TCO↓.

## ⚠️ 흔한 함정

1. **"클라우드 비용 = 서버 임대료만 보면 된다."** → ❌. 온프레의 *숨은 비용*(전력·냉각·공간·인력·과대 프로비저닝)까지 포함해 **TCO**로 비교해야 합니다.
   *(원리: §1 — 고정비 모델에는 실제 사용 여부와 무관하게 발생하는 간접 비용이 포함되어 있어, 서버 구매가만으로 비교하면 온프레의 실제 비용을 과소평가한다.)*
2. **"리소스는 넉넉히 크게 잡는 게 안전하다."** → ⚠️ 과대 프로비저닝은 *낭비*입니다. **rightsizing**(Compute Optimizer)으로 적정 크기로.
   *(원리: §2 — 메트릭 기반 분석 없이 크게 잡으면 실제 수요보다 과대 프로비저닝된 용량이 계속 비용을 발생시킨다.)*
3. **"기존 소프트웨어 라이선스는 클라우드에서 못 쓴다."** → ❌. **BYOL**로 기존 라이선스를 가져와 쓸 수 있습니다(예: EC2 Dedicated Hosts).
   *(원리: §3 — Dedicated Hosts 같은 물리 호스트 단위 할당 방식이 기존 서버 바운드 라이선스 조건을 충족해 재활용을 가능하게 한다.)*
4. **"관리형 서비스는 항상 더 비싸다."** → ⚠️ 단가만 보면 그럴 수 있으나, *운영 인력·시간*을 줄여 **총비용(TCO)**은 낮아지는 경우가 많습니다.
   *(원리: §5 — 패치·백업·복구 등 운영 작업에 드는 인력 비용이 TCO에서 절감되므로, 서비스 단가만이 아닌 전체 비용으로 비교해야 한다.)*
5. **"자동화는 비용과 무관하다."** → ❌. 자동화(IaC)는 *수동 작업 비용·오류*를 줄이는 비용 이점이 있습니다.
   *(원리: §4 — 코드 기반 반복 배포는 환경 불일치를 방지해 오류 추적·수정에 드는 인적 비용을 줄인다.)*

## 🧪 자가 점검

> 아래는 학습용 자가 점검입니다. (정식 검증 문항은 `t1-4.questions.json` 참조)

**Q1.** 온프레미스 대비 클라우드의 비용 구조를 한 문장으로?

<details><summary>정답 보기</summary>

**고정비(데이터센터·서버 선투자)를 변동비(쓴 만큼)로 전환**하고, 온프레의 숨은 비용(전력·냉각·공간·인력·과대 프로비저닝)을 줄이며, 규모의 경제로 단가도 낮춥니다.
</details>

**Q2.** 리소스의 사용률을 분석해 과대/과소 프로비저닝을 짚고 적정 크기(rightsizing)를 권장하는 AWS 서비스는?

<details><summary>정답 보기</summary>

**AWS Compute Optimizer**. 구성·사용률 메트릭을 분석해 rightsizing 권장과 유휴 리소스 식별을 제공하고, 비용을 줄이고 성능을 높이도록 돕습니다.
</details>

**Q3.** 이미 보유한 소프트웨어 라이선스를 클라우드로 가져와 재활용하는 방식은 무엇이라고 하나요?

<details><summary>정답 보기</summary>

**BYOL(Bring Your Own License)**. 예를 들어 EC2 Dedicated Hosts에서 기존 서버 바운드 라이선스를 사용할 수 있습니다. (반대는 '라이선스 포함' — 요금에 라이선스가 포함.)
</details>

**Q4.** 데이터베이스를 EC2에 직접 설치하는 대신 Amazon RDS 같은 관리형 서비스를 쓰면 비용 면에서 어떤 이점이 있나요?

<details><summary>정답 보기</summary>

패치·백업·확장·고가용성 같은 운영을 AWS가 대신하므로 **운영 인력·시간이 줄어 총소유비용(TCO)이 낮아집니다.** 고객은 애플리케이션에 집중할 수 있습니다.
</details>

---

**Q5 (원리).** 왜 관리형 서비스는 단가가 직접 운영보다 높더라도 총소유비용(TCO)은 낮아질 수 있나요?

<details><summary>정답 보기</summary>

**운영 인력 비용이 TCO에서 사라지기 때문입니다.** 패치·백업·장애 복구 등을 AWS가 맡으면, 이를 직접 수행하는 엔지니어 시간이 절감되고 그 비용이 서비스 단가 차이를 상쇄합니다.
</details>
