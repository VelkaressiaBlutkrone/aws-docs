## 📖 핵심 개념

### 1) AWS를 다루는 네 가지 방법 — 콘솔 · CLI · SDK · IaC

| 방법 | 무엇 | 언제 적합 |
|---|---|---|
| **관리 콘솔(Console)** | 웹 브라우저 **GUI** | 탐색·학습·일회성 수동 작업 |
| **AWS CLI** | **명령줄**에서 명령·스크립트로 제어 | 자동화·반복 작업, 터미널 |
| **AWS SDK** | **언어별 API 라이브러리**(Java·Python 등) | *애플리케이션 코드* 안에서 AWS 호출 |
| **IaC(CloudFormation)** | **템플릿(코드)**으로 인프라 정의 | 반복·일관·버전 관리되는 인프라 |

> CLI·SDK·(직접) API는 모두 **프로그래밍 방식 접근**입니다. 콘솔은 같은 일을 *손으로* 합니다. 공식 표현: AWS CLI는 *"명령줄 셸에서 AWS 서비스와 상호작용"*하며 *"AWS Management Console과 동등한 기능"*을 제공합니다.

> 🧠 원리: 콘솔·CLI·SDK·직접 API 호출은 어떻게 모두 "동등한 기능"을 제공할 수 있을까요?
> 이 네 방법은 내부적으로 모두 동일한 AWS 서비스 API를 호출하는 서로 다른 껍데기(인터페이스)이기 때문입니다.
> 콘솔에서 버튼을 클릭하면 브라우저가 그에 대응하는 API를 호출하고, CLI 명령도, SDK 메서드도 결국 같은 AWS API 서버에 요청을 보냅니다.
> 어떤 방법을 쓰든 AWS 서비스는 동일한 요청을 처리하며, 방법의 차이는 누가(사람/코드/앱) 어떤 상황에서 편리한가의 차이입니다.

### 2) IaC와 AWS CloudFormation — 인프라를 코드로

**IaC(Infrastructure as Code)**는 인프라를 *손으로 클릭*하는 대신 **코드(템플릿)로 정의**해 자동·반복·일관되게 프로비저닝하는 방식입니다.

**AWS CloudFormation**이 AWS의 대표 IaC 서비스입니다.

- **템플릿**(텍스트, JSON/YAML)에 원하는 모든 리소스(EC2·RDS 등)를 기술하면, CloudFormation이 **프로비저닝·구성을 대신**하고 *의존성*까지 처리합니다.
- 리소스 묶음을 **스택(stack)**이라는 단일 단위로 관리(스택 삭제 시 일괄 삭제).
- **빠르게 복제**: 템플릿을 재사용해 *여러 리전·계정*에 **동일하게 반복** 생성.
- 템플릿이 텍스트라 **버전 관리**가 가능 — *누가·언제·무엇을* 바꿨는지 추적하고 이전 버전으로 **롤백**.

> 시험 신호: **"인프라를 코드로 / 반복·일관되게 프로비저닝 / 여러 리전에 동일하게 / 버전 관리"** → **CloudFormation(IaC)**.

> 🧠 원리: 왜 CloudFormation 템플릿은 여러 번 실행하거나 여러 리전에 적용해도 같은 결과를 낼까요?
> 템플릿이 **선언형(declarative)**이기 때문입니다. 절차("먼저 EC2를 만들고, 그 다음 RDS를 연결하라")가 아니라 최종 상태("EC2와 RDS가 이렇게 연결된 상태")를 선언합니다.
> CloudFormation은 현재 상태와 선언된 목표 상태의 차이를 계산해, 필요한 변경만 수행합니다.
> 같은 조건이라면 같은 선언은 어디서 실행해도 동일한 최종 상태로 수렴합니다.

### 3) 일회성 vs 반복 프로세스

- **일회성·탐색**: 콘솔에서 손으로 해도 충분합니다.
- **반복·재현 가능해야 함**: **자동화(CLI 스크립트)** 또는 **IaC(CloudFormation)**로. *사람이 매번 클릭*하면 실수·불일치가 생깁니다.

> "매번 똑같은 환경을 여러 번 만들어야 한다" → 손이 아니라 **코드/자동화**.

> 🧠 원리: 수작업 반복이 왜 결국 환경 불일치를 낳을까요?
> 사람이 매번 콘솔에서 클릭해 환경을 만들면, 클릭 순서·실수·누락이 기록되지 않습니다.
> 설정 방법을 기억하는 사람이 바뀌거나, 시간이 지나 세부 절차를 잊으면 두 번째 환경은 첫 번째와 미묘하게 달라집니다.
> 이처럼 환경마다 조금씩 달라지는 현상을 구성 표류(configuration drift)라고 합니다.
> 코드(IaC 템플릿 또는 CLI 스크립트)는 명세 자체가 기록이므로, 리뷰·비교·재현이 가능하고 표류를 방지합니다.
> 그래서 반복 작업에서 코드/자동화가 기본값이 됩니다.

### 4) 배포 모델 — 클라우드 · 하이브리드 · 온프레미스

| 모델 | 무엇 |
|---|---|
| **클라우드(Cloud)** | 애플리케이션을 *전부 클라우드*에서 배포·운영(클라우드 네이티브) |
| **하이브리드(Hybrid)** | *클라우드 + 온프레미스를 함께* — 둘을 네트워크로 연결(예: VPN·Direct Connect) |
| **온프레미스(On-premises)** | 자체 데이터센터에서 운영(가상화·컨테이너 등 *프라이빗* 클라우드 형태 포함) |

> 하이브리드의 핵심은 **연결** — 온프레미스와 AWS를 안전·안정적으로 잇는 것(아래 5).

> 🧠 원리: 왜 하이브리드 배포 모델이 필요한 걸까요?
> 이상적으로는 모든 워크로드를 클라우드로 이전하면 간단하지만, 현실에는 세 가지 제약이 있습니다.
> 첫째, 레거시 시스템은 클라우드 환경에 맞게 재설계하기 어렵거나 비용이 큽니다.
> 둘째, 규제 요건이 특정 데이터를 특정 물리 위치에 보관하도록 요구할 수 있습니다.
> 셋째, 지연 시간이 매우 엄격한 일부 처리는 온프레미스에서 수행해야 할 수 있습니다.
> 이 제약들 때문에 "온프레미스에 남길 것"과 "클라우드에 둘 것"을 나눠야 하고, 그러면 둘을 어떻게 안전하게 연결하느냐가 핵심 문제가 됩니다.

### 5) 연결 옵션 — 공용 인터넷 · VPN · Direct Connect (3.5 연계)

| 옵션 | 특징 |
|---|---|
| **공용 인터넷(Public Internet)** | 가장 간단. 서비스 수준 암호화(HTTPS/TLS) 의존 |
| **AWS Site-to-Site VPN** | 온프레미스↔VPC를 **공용 인터넷 위 IPsec 암호화 터널**로. **빠르고 저렴** |
| **AWS Direct Connect** | **전용 물리 회선**으로 공용 인터넷을 **우회**. **일관되고 안정적**(구축 느림·비용↑) |

> 자세한 구분은 [네트워크 서비스 3.5](#). 시험 신호: *빠르고 저렴한 암호화 연결* = VPN, *전용·일관된 고성능* = Direct Connect.

> 🧠 원리: VPN과 Direct Connect는 왜 성능과 비용 특성이 반대인가요?
> 두 옵션의 차이는 패킷이 지나가는 경로의 성격에서 비롯됩니다.
> VPN은 공용 인터넷 위에 IPsec 암호화 터널을 얹습니다. 경로 자체는 공용이므로 혼잡에 따라 지연이 변동될 수 있고, 기존 인터넷 회선을 그대로 활용하므로 상대적으로 빠르고 간단하게 시작할 수 있습니다.
> Direct Connect는 온프레미스부터 AWS 네트워크까지 물리적으로 전용 회선을 설치합니다. 경로가 공용 인터넷과 분리되어 있어 혼잡의 영향을 받지 않으므로 대역폭과 지연이 일관됩니다.
> 그 대신 물리 회선 구축에는 시간과 비용이 필요합니다.
> "빠르게 시작 = VPN, 일관·안정 = Direct Connect"는 이 경로 구조의 직접적인 귀결입니다.

## ✍️ 시험 포인트

- **콘솔 = GUI(손)** · **CLI = 명령줄(스크립트)** · **SDK = 앱 코드(언어별 API)** · **IaC = 템플릿(인프라를 코드로)**.
- **CloudFormation = IaC.** "인프라를 코드로 / 반복·일관 / 여러 리전 동일 / 버전 관리·롤백" → CloudFormation.
- **반복·재현**은 손(콘솔)이 아니라 **자동화(CLI)·IaC**로.
- **배포 모델**: 전부 클라우드 = 클라우드, *온프레+클라우드 혼합* = **하이브리드**, 자체 DC = 온프레미스.
- **연결**: 인터넷(간단) · **VPN(인터넷 위 IPsec, 빠르고 저렴)** · **Direct Connect(전용 회선, 일관)**.

## ⚠️ 흔한 함정

1. **"반복되는 인프라 배포를 매번 콘솔에서 손으로 한다."** → ⚠️ 비효율·실수. **CloudFormation(IaC)**나 CLI 스크립트로 자동화·일관화.
   *(원리: §3 — 수작업 반복은 기록이 남지 않아 구성 표류가 생기고, 코드/자동화가 이를 방지한다.)*

2. **"CloudFormation은 애플리케이션 코드를 실행하는 서비스다."** → ❌. CloudFormation은 *인프라(리소스)*를 템플릿으로 프로비저닝하는 **IaC**입니다(코드 실행은 Lambda·EC2 등).
   *(원리: §2 — 템플릿은 최종 상태를 선언하는 문서이며, 애플리케이션 코드를 실행하는 런타임이 아니다.)*

3. **"CLI와 SDK는 같은 것이다."** → ⚠️ 구분. **CLI = 명령줄 도구**, **SDK = 애플리케이션 코드에서 쓰는 언어별 라이브러리**.
   *(원리: §1 — 둘 다 동일한 AWS API를 호출하는 껍데기지만, CLI는 사람이 터미널에서 쓰고 SDK는 앱 코드 안에서 호출하는 목적이 다른 인터페이스다.)*

4. **"하이브리드는 곧 멀티 클라우드다."** → ❌. 하이브리드는 *온프레미스 + 클라우드* 조합입니다(여러 클라우드 사용과는 다른 개념).
   *(원리: §4 — 하이브리드는 레거시·규제·지연 제약으로 온프레미스를 완전히 이전하지 못해 클라우드와 함께 쓰는 모델이다.)*

5. **"Direct Connect는 인터넷을 통한 암호화 연결이다."** → ❌. Direct Connect는 *전용 회선으로 인터넷을 우회*. *인터넷 위 IPsec*은 **Site-to-Site VPN** ([3.5](#)).
   *(원리: §5 — Direct Connect는 경로 자체가 물리적 전용 회선이라 공용 인터넷을 통하지 않으며, 인터넷 위 IPsec 터널인 VPN과 구조가 다르다.)*

## 🧪 자가 점검

> 아래는 학습용 자가 점검입니다. (정식 검증 문항은 `t3-1.questions.json` 참조)

**Q1.** 동일한 AWS 인프라(EC2·RDS 등)를 여러 리전에 일관되고 반복 가능하게 프로비저닝하고, 변경을 코드처럼 버전 관리하려 합니다. 어떤 접근/서비스인가요?

<details><summary>정답 보기</summary>

**IaC(Infrastructure as Code) — AWS CloudFormation**. 템플릿에 리소스를 한 번 정의해 여러 리전·계정에 동일하게 반복 생성하고, 템플릿이 텍스트라 버전 관리·롤백이 가능합니다.
</details>

**Q2.** 웹 콘솔(GUI) 없이, 터미널에서 명령과 스크립트로 AWS 서비스를 제어해 작업을 자동화하려면 무엇을 쓰나요?

<details><summary>정답 보기</summary>

**AWS CLI**(Command Line Interface). 명령줄 셸에서 AWS Management Console과 동등한 기능을 명령으로 실행하고, 셸 스크립트로 자동화할 수 있습니다.
</details>

**Q3.** 일부 워크로드는 자체 데이터센터(온프레미스)에 두고 일부는 AWS 클라우드에 두어, 둘을 네트워크로 연결해 함께 운영하는 배포 모델은?

<details><summary>정답 보기</summary>

**하이브리드(Hybrid)** 배포 모델. 온프레미스와 클라우드를 함께 쓰며, 보통 **Site-to-Site VPN**이나 **Direct Connect**로 연결합니다.
</details>

**Q4.** 콘솔·CLI·SDK·CloudFormation 중, *애플리케이션 코드 안에서* 언어별 라이브러리로 AWS를 호출하는 것은? 그리고 *인프라를 템플릿(코드)으로* 정의하는 것은?

<details><summary>정답 보기</summary>

애플리케이션 코드에서 호출하는 것은 **AWS SDK**(언어별 API 라이브러리), 인프라를 템플릿으로 정의하는 것은 **AWS CloudFormation**(IaC)입니다.
</details>

---

**Q5 (원리).** 왜 CloudFormation 템플릿은 여러 번 실행하거나 여러 리전에 적용해도 같은 결과를 내나요?

<details><summary>정답 보기</summary>

템플릿이 **선언형**이기 때문입니다. 절차가 아니라 *최종 상태*를 선언하므로 CloudFormation이 현재 상태와의 차이만 계산해 맞춰 줍니다. 같은 조건이라면 같은 선언은 어디서 실행해도 같은 상태로 수렴합니다.
</details>
