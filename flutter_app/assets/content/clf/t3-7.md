# AI/ML·분석 서비스

> **커버하는 공식 Task** — CLF-C02 · 도메인 3 「클라우드 기술 및 서비스」(34%) · **Task 3.7 AI/ML·분석 서비스 식별** (`clf-t3-7`)
> 이 문서는 위 한 Task에 1:1로 매핑됩니다. 시험은 *세부 구현*이 아니라 **"이 시나리오에 맞는 AI/ML 또는 분석 서비스가 무엇인가"**를 묻습니다.

## 🎯 왜 중요한가

- 도메인 3(34%)에서 이 Task는 **서비스 이름 매칭**이 거의 전부입니다. 각 서비스가 *한 문장으로 무엇을 하는지*만 분명하면 풀립니다.
- 두 묶음으로 외우면 쉽습니다: **AI/ML(SageMaker·Lex·Kendra)**와 **분석(Athena·Kinesis·Glue·QuickSight)**. 각 묶음 안에서 *역할이 겹치지 않으니* 키워드로 1:1 매칭됩니다.
- 시험은 깊은 ML 지식을 요구하지 않습니다 — *"챗봇이면 Lex"* 수준의 식별이면 충분합니다.

## 🔤 먼저 알아야 할 용어

이 문서를 읽는 데 필요한 기초 용어입니다. 이미 알면 건너뛰세요.

| 용어 | 영문 | 한 줄 풀이 |
|---|---|---|
| **머신러닝** | Machine Learning (ML) | 데이터에서 패턴을 *스스로 학습해 예측·분류하는 알고리즘과 그 학습 과정* — SageMaker는 이 모델의 구축·훈련·배포를 관리합니다 |
| **자동 음성 인식** | ASR (Automatic Speech Recognition) | 사람의 *음성 신호를 텍스트로 변환*하는 기술 — Lex·Transcribe가 이 방식으로 음성 입력을 처리합니다 |
| **자연어 이해** | NLU (Natural Language Understanding) | 텍스트 안의 *의도(intent)와 개체(entity)를 파악*하는 기술 — Lex가 사용자 말의 의미를 파악하는 데 사용합니다 |
| **스트리밍** | Streaming | 데이터를 *배치로 모아 처리하지 않고 발생하는 즉시 연속적으로 전달·처리*하는 방식 — Kinesis가 이 방식으로 실시간 데이터를 수집합니다 |
| **클릭스트림** | Clickstream | 사용자가 웹·앱에서 *클릭·탐색한 이력이 시간 순서대로 연속 발생*하는 이벤트 데이터 — Kinesis의 대표 수집 대상입니다 |
| **데이터 카탈로그** | Data Catalog | 데이터의 *위치·스키마·형식 등 메타데이터를 중앙에 등록·검색*할 수 있게 하는 목록 — Glue가 ETL 파이프라인과 함께 관리합니다 |
| **서버리스** | Serverless | 서버 프로비저닝·관리 없이 *코드나 쿼리를 실행할 때만 리소스가 할당*되고 사용한 만큼만 과금되는 실행 모델 — Athena·Glue가 이 방식으로 동작합니다 |

## 📖 핵심 개념

### 1) AI/ML 서비스 3종 — SageMaker · Lex · Kendra

| 서비스 | 한 줄 역할 | 떠올릴 키워드 |
|---|---|---|
| **Amazon SageMaker (AI)** | **ML 모델을 구축·훈련·배포**하는 완전관리형 ML 서비스(데이터 과학자·개발자용) | "*커스텀* 머신러닝 모델", "모델 훈련·배포" |
| **Amazon Lex** | **음성·텍스트 대화형 인터페이스(챗봇)** 구축 — 자동 음성 인식(ASR) + 자연어 이해(NLU) | "*챗봇*", "음성봇", "대화형 인터페이스" |
| **Amazon Kendra** | **지능형 엔터프라이즈 검색** — ML·자연어로 문서/콘텐츠에서 의미 기반 검색 | "*문서/콘텐츠 검색*", "엔터프라이즈 검색" |

> 한 문장 구분: **SageMaker는 *모델을 만든다*, Lex는 *대화한다(챗봇)*, Kendra는 *찾는다(검색)*.**
> ℹ️ 정직성 메모: Amazon SageMaker는 2024-12 **Amazon SageMaker AI**로 이름이 바뀌었습니다(ML 구축·훈련·배포 기능). 기존 'SageMaker'는 데이터·분석·AI 통합 플랫폼 명칭으로 확장됐습니다. CLF에선 "ML 모델 구축·훈련·배포 = SageMaker(AI)"로 기억하면 됩니다.

> 🧠 원리: 왜 AWS는 챗봇(Lex), 문서 검색(Kendra), 커스텀 모델 구축(SageMaker)을 하나의 AI 서비스로 통합하지 않고 별도 서비스로 분리했을까요?
> 세 서비스는 AI를 활용하는 목적과 입력·출력 형태가 다릅니다. Lex는 발화 의도(intent)를 파악해 대화 흐름을 제어하는 데 최적화되어 있고, Kendra는 대용량 문서에서 관련 구절을 의미 기반으로 검색·순위화하는 데 특화돼 있습니다.
> SageMaker는 어떤 종류의 데이터든 고객이 직접 정의한 모델을 훈련·평가·배포하는 일반 ML 플랫폼으로, Lex나 Kendra처럼 특정 사용 사례에 고정된 것이 아닙니다.
> 각 서비스를 별도로 두면 특정 사용 사례에 맞게 내부 최적화를 독립적으로 발전시킬 수 있고, 챗봇만 필요한 경우에 ML 플랫폼 전체를 사용할 필요 없이 해당 기능만 선택해 쓰는 것이 가능합니다.

### 2) 분석 서비스 4종 — Athena · Kinesis · Glue · QuickSight

| 서비스 | 한 줄 역할 | 떠올릴 키워드 |
|---|---|---|
| **Amazon Athena** | **Amazon S3의 데이터를 표준 SQL로 직접 쿼리**(서버리스, 쿼리당 과금) | "*S3를 SQL로*", "서버리스 쿼리", "임시(ad-hoc) 분석" |
| **Amazon Kinesis** | **실시간 스트리밍 데이터**를 대규모로 수집·처리 | "*실시간*", "스트리밍", "로그·클릭스트림 실시간" |
| **AWS Glue** | **서버리스 데이터 통합 — ETL(추출·변환·적재)** 파이프라인, 데이터 카탈로그 | "*ETL*", "데이터 준비·통합", "데이터 카탈로그" |
| **Amazon QuickSight** | **클라우드 BI — 대화형 대시보드·시각화** | "*대시보드*", "시각화", "비즈니스 인텔리전스(BI)" |

> 한 문장 구분:
> - **Athena = S3를 *SQL로 묻는다*(쿼리).**
> - **Kinesis = *실시간으로 흘려보낸다*(스트리밍).**
> - **Glue = *모아서 정제·변환한다*(ETL).**
> - **QuickSight = *보기 좋게 그린다*(대시보드·BI).**

> ℹ️ 정직성 메모: Amazon QuickSight는 **Amazon Quick**으로 진화하면서 BI 기능이 **Amazon Quick Sight**로 이어집니다(기존 QuickSight API·SDK는 그대로 동작). CLF에선 "대시보드·시각화·BI = QuickSight"로 기억하면 됩니다.

> 🧠 원리: 왜 분석 파이프라인은 Kinesis→Glue→Athena/QuickSight처럼 별도 서비스들을 연결하는 구조가 되었을까요?
> 데이터 분석의 각 단계는 서로 다른 처리 특성을 요구합니다. 실시간 수집(Kinesis)은 수백만 건의 이벤트를 낮은 지연시간으로 받아내야 하고, 변환(Glue)은 다양한 소스의 스키마를 통일하는 배치 처리가 적합합니다.
> 쿼리(Athena)는 저장된 데이터에 임시(ad-hoc)로 SQL을 실행하는 구조가 필요하고, 시각화(QuickSight)는 그 결과를 대화형으로 탐색하는 UI 레이어입니다.
> 단계마다 요구사항이 달라 하나의 서비스로 통합하면 각 단계의 성능을 최적화하기 어렵고, 필요한 단계만 선택해 조합할 수 있는 구조가 비용과 복잡도를 관리하는 데 유리합니다.

### 3) 한눈에 — 시나리오 → 서비스

| 시나리오 | 서비스 |
|---|---|
| 고객 문의에 답하는 음성/문자 **챗봇** | **Lex** |
| 회사 문서를 자연어로 **검색** | **Kendra** |
| 데이터로 **커스텀 ML 모델**을 훈련·배포 | **SageMaker (AI)** |
| **S3에 쌓인 로그**를 SQL로 즉석 분석 | **Athena** |
| 클릭스트림·로그를 **실시간**으로 수집·처리 | **Kinesis** |
| 여러 소스 데이터를 **정제·변환(ETL)** | **Glue** |
| 분석 결과를 **대시보드로 시각화** | **QuickSight** |

> 🧠 원리: 왜 이 시나리오 테이블은 각 서비스가 겹치지 않고 1:1로 매칭될 수 있을까요?
> 각 서비스는 데이터 처리 흐름에서 서로 다른 단계나 사용 형태에 대응합니다. AI 묶음에서 Lex는 사용자 발화에서 의도를 파악하고, Kendra는 문서 집합에서 관련 구절을 찾고, SageMaker는 데이터로 커스텀 모델을 만드는 것으로 입력 대상과 출력 형태가 다릅니다.
> 분석 묶음에서 Kinesis는 이벤트가 발생하는 즉시 수집하고, Glue는 여러 소스의 데이터를 정제·변환하고, Athena는 정제된 데이터를 SQL로 조회하고, QuickSight는 그 결과를 시각화하는 순서로 역할이 이어집니다.
> 각 서비스가 다루는 입력 데이터 형태와 출력 목적이 달라 같은 시나리오에서 두 서비스가 동시에 정답이 되는 경우가 생기지 않으며, 이 점이 시험에서 키워드로 1:1 매칭을 가능하게 합니다.

### 언어 AI — Amazon Translate · Amazon Transcribe (보강)

- **Amazon Translate**: 텍스트를 여러 언어로 **자동 번역**하는 신경망 기계 번역 서비스.
- **Amazon Transcribe**: **음성을 텍스트로** 변환하는 자동 음성 인식(ASR). 통화·녹음을 텍스트화해 검색·분석에 활용 — 텍스트를 음성으로 만드는 **Amazon Polly**의 반대 방향입니다.

> 시험 신호: "여러 언어로 번역" → **Translate**, "음성 → 텍스트" → **Transcribe**, "텍스트 → 음성" → **Polly**.
> 출처: [Amazon Translate](https://docs.aws.amazon.com/translate/latest/dg/what-is.html), [Amazon Transcribe](https://docs.aws.amazon.com/transcribe/latest/dg/what-is.html)

> 🧠 원리: 왜 Transcribe와 Polly는 같은 음성-텍스트 변환 영역에서 별도 서비스로 분리되어 있을까요?
> 음성을 텍스트로 바꾸는 것(ASR)과 텍스트를 음성으로 합성하는 것(TTS, Text-to-Speech)은 모델 구조와 최적화 방향이 반대입니다. ASR은 음향 신호에서 언어 패턴을 추론해야 하고, TTS는 텍스트를 자연스러운 발음·억양의 오디오로 생성해야 합니다.
> 두 방향을 단일 서비스로 묶으면 각 방향의 모델을 독립적으로 개선하기 어렵고, 음성 인식만 필요한 사용자가 합성 기능까지 포함된 서비스를 쓸 이유가 없습니다.
> 용도별로 분리해 두면 필요한 방향만 선택해 쓸 수 있고, 각 서비스의 언어 지원·정확도·지연시간을 독립적으로 발전시키는 것이 가능합니다.

## ✍️ 시험 포인트

- **챗봇/대화형 = Lex.** **문서·엔터프라이즈 검색 = Kendra.** **커스텀 ML 모델 구축·훈련·배포 = SageMaker(AI).**
- **S3를 SQL로 쿼리 = Athena**(서버리스). **실시간 스트리밍 = Kinesis.**
- **ETL/데이터 통합·준비 = Glue**(서버리스). **대시보드·시각화·BI = QuickSight.**
- 분석 흐름이 함께 나오면: **Kinesis(실시간 수집) → Glue(ETL) → Athena/QuickSight(쿼리·시각화)** 식으로 역할이 이어집니다.
- 깊은 ML 지식 불필요 — *한 줄 역할*로 매칭.

## ⚠️ 흔한 함정

1. **"챗봇을 만들려면 SageMaker를 쓴다."** → ❌. 대화형 챗봇은 **Lex**. SageMaker는 *커스텀 ML 모델* 구축·훈련·배포.
   *(원리: §1 — SageMaker는 데이터로 커스텀 모델을 구축·훈련·배포하는 범용 ML 플랫폼이고, Lex는 ASR+NLU를 결합한 대화형 인터페이스에 특화된 서비스로 목적이 다르다.)*
2. **"문서 검색도 Lex로 한다."** → ❌. 자연어 **검색**은 **Kendra**. Lex는 *대화(챗봇)*.
   *(원리: §1 — Lex는 발화 의도와 개체를 파악해 대화 흐름을 제어하는 서비스이고, Kendra는 문서·콘텐츠에서 의미 기반으로 관련 구절을 검색·순위화하는 서비스로 처리 대상과 출력 방식이 다르다.)*
3. **"S3 데이터를 분석하려면 먼저 DB로 옮겨야 한다."** → ⚠️ 불필요. **Athena**로 S3를 *그 자리에서* 표준 SQL로 쿼리(서버리스).
   *(원리: §2 — Athena는 서버리스로 S3에 저장된 데이터를 별도 이전 없이 표준 SQL로 직접 쿼리하며, 쿼리한 데이터 양만큼만 과금되는 구조라 임시 분석에 DB 구축 비용 없이 쓸 수 있다.)*
4. **"Glue로 대시보드를 만든다."** → ❌. 시각화·대시보드는 **QuickSight**. Glue는 *ETL(데이터 준비)*.
   *(원리: §2 — Glue는 여러 소스의 데이터를 추출·변환·적재해 분석 가능한 형태로 준비하는 서비스이고, QuickSight는 그 결과를 대화형 대시보드로 시각화하는 BI 서비스로 파이프라인에서 역할이 다르다.)*
5. **"실시간 스트리밍을 Athena로 처리한다."** → ❌. 실시간 스트리밍 수집·처리는 **Kinesis**. Athena는 *저장된 데이터의 SQL 쿼리*.
   *(원리: §2 — Kinesis는 이벤트가 발생하는 즉시 수집·처리하는 스트리밍 구조이고, Athena는 S3에 이미 저장된 데이터를 대상으로 SQL을 실행하는 배치 쿼리 구조라 처리 시점이 다르다.)*
6. **"QuickSight로 데이터를 변환·정제한다."** → ❌. 변환·정제(ETL)는 **Glue**. QuickSight는 *시각화(BI)*.
   *(원리: §2 — Glue는 스키마 불일치·오염 데이터를 변환·정제해 분석에 쓸 수 있는 형태를 만드는 ETL 서비스이고, QuickSight는 이미 정제된 데이터를 시각적으로 탐색하는 레이어라 역할이 다르다.)*

**Q1.** 고객 문의에 음성·문자로 응답하는 챗봇을 만들려면? 그리고 회사 내부 문서를 자연어로 검색하게 하려면?

<details><summary>정답 보기</summary>

챗봇은 **Amazon Lex**(음성·텍스트 대화형, ASR+NLU). 자연어 문서 검색은 **Amazon Kendra**(지능형 엔터프라이즈 검색).
</details>

**Q2.** 데이터로 직접 머신러닝 모델을 구축·훈련하고 운영 환경에 배포하려면 어떤 서비스인가요?

<details><summary>정답 보기</summary>

**Amazon SageMaker (AI)**. 데이터 과학자·개발자가 ML 모델을 구축·훈련·배포하는 완전관리형 ML 서비스입니다.
</details>

**Q3.** Amazon S3에 저장된 로그 데이터를, 별도 인프라 없이 표준 SQL로 즉석에서 분석하려면? 그리고 클릭스트림을 실시간으로 수집·처리하려면?

<details><summary>정답 보기</summary>

S3를 SQL로 쿼리하는 것은 **Amazon Athena**(서버리스). 실시간 스트리밍 수집·처리는 **Amazon Kinesis**입니다.
</details>

**Q4.** 여러 소스의 데이터를 추출·변환·적재(ETL)해 분석용으로 준비하려면? 그리고 그 결과를 대화형 대시보드로 시각화하려면?

<details><summary>정답 보기</summary>

ETL·데이터 통합은 **AWS Glue**(서버리스). 대시보드 시각화·BI는 **Amazon QuickSight**입니다.
</details>

**Q5 (원리).** 왜 Athena는 S3의 데이터를 분석할 때 별도 데이터베이스나 데이터 웨어하우스에 먼저 복사하지 않고 S3에서 직접 쿼리하는 방식을 선택했을까요?

<details><summary>정답 보기</summary>

데이터를 DB나 웨어하우스에 적재하려면 로드 작업과 별도 인프라 비용이 필요하고, 임시(ad-hoc) 분석처럼 쿼리 빈도가 낮은 경우에는 그 비용이 분석 가치를 초과할 수 있습니다. Athena는 S3에 저장된 데이터에 직접 SQL을 실행하고 실제로 스캔한 데이터 양만 과금하는 서버리스 구조이므로, 인프라를 프로비저닝하거나 데이터를 이전하지 않고도 필요할 때만 분석하는 것이 가능합니다. 이 방식은 데이터 레이크처럼 대용량 데이터를 S3에 두고 필요할 때만 선택적으로 쿼리하는 분석 패턴에 적합합니다.
</details>
