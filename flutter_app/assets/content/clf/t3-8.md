## 🔤 먼저 알아야 할 용어

이 문서를 읽는 데 필요한 기초 용어입니다. 이미 알면 건너뛰세요.

| 용어 | 영문 | 한 줄 풀이 |
|---|---|---|
| **pub/sub** | Publish/Subscribe | 발행자가 *주제(topic)*에 메시지를 보내면 그 주제를 구독한 모든 수신자에게 전달되는 메시징 패턴 — SNS가 이 방식으로 한 메시지를 여러 구독자에게 동시에 푸시합니다 |
| **팬아웃** | Fan-out | 하나의 메시지를 *여러 수신 대상에 복제해 동시에 전달*하는 전달 방식 — SNS 주제에서 여러 SQS 큐·Lambda 등으로 메시지를 뿌릴 때 이 패턴이 사용됩니다 |
| **폴링** | Polling | 소비자가 *주기적으로 요청을 보내 새 메시지가 있는지 확인하고 가져오는* 방식 — SQS 소비자는 서버가 푸시하는 대신 큐에 직접 폴링해 메시지를 처리합니다 |
| **디커플링** | Decoupling | 시스템 컴포넌트 간 *직접 의존 없이 독립적으로 동작하도록 분리*하는 아키텍처 원칙 — SQS 큐를 사이에 두면 생산자·소비자가 서로의 처리 속도와 무관하게 작동합니다 |
| **이벤트 버스** | Event Bus | *여러 소스에서 발생하는 이벤트를 받아 규칙에 따라 적절한 타겟으로 라우팅*하는 중앙 메시지 전달 채널 — EventBridge가 AWS 서비스·앱·서드파티 이벤트를 이 방식으로 연결합니다 |
| **MQTT** | Message Queuing Telemetry Transport | *제한된 대역폭·배터리 환경에서 기기와 클라우드 간 경량 메시지를 주고받도록 설계된* IoT 표준 프로토콜 — AWS IoT Core가 이 프로토콜로 기기와 통신합니다 |
| **DaaS** | Desktop as a Service | 데스크톱 환경을 *클라우드에서 가상으로 제공해 사용자가 기기·장소에 무관하게 접근*할 수 있도록 하는 서비스 모델 — WorkSpaces가 이 방식으로 Windows·Linux 데스크톱을 제공합니다 |

## 📖 핵심 개념

### 1) 앱 통합 메시징 — SNS · SQS · EventBridge (★ 시험 핵심)

느슨하게 결합된(decoupled) 시스템을 잇는 세 가지 메시징/이벤트 서비스입니다.

| 서비스 | 한 줄 역할 | 전달 방식 | 떠올릴 키워드 |
|---|---|---|---|
| **Amazon SNS** | **pub/sub 알림** — 발행자가 *주제(topic)*에 보내면 여러 구독자에게 **푸시** | 하나 발행 → **여러 구독자에 복제 푸시(팬아웃)** | "*알림*", "SMS/이메일 발송", "여러 대상에 동시 전달" |
| **Amazon SQS** | **메시지 큐** — 컴포넌트를 디커플링하고 메시지를 큐에 보관 | 큐에 저장 → 소비자가 **폴링(pull)해 처리** | "*큐*", "컴포넌트 *디커플링*", "비동기 작업 버퍼" |
| **Amazon EventBridge** | **서버리스 이벤트 버스** — 이벤트를 *규칙*으로 소스→타겟 라우팅 | 이벤트 소스 → 규칙 → 타겟 | "*이벤트 버스*", "이벤트 기반", "여러 소스의 이벤트 라우팅" |

> **SNS vs SQS** (단골 비교):
> - **SNS = 발행/구독(pub/sub), 푸시.** 한 메시지를 *여러 구독자*에게 동시에 보냄(알림·팬아웃).
> - **SQS = 큐, 풀.** 메시지를 큐에 쌓아 두고 *소비자가 가져가* 처리(보통 한 소비자가 한 메시지 처리). 컴포넌트 디커플링·부하 평준화.
> - 자주 **함께** 씀: SNS 주제 → 여러 SQS 큐로 팬아웃(SNS가 뿌리고 각 SQS가 안전하게 버퍼링).

> **EventBridge**는 *이벤트 기반* 아키텍처용 — AWS 서비스·자체 앱·서드파티의 이벤트를 받아 규칙으로 여러 타겟에 라우팅합니다("이벤트 버스").

> 🧠 원리: 왜 AWS는 알림(SNS)과 큐(SQS)를 하나의 메시징 서비스로 통합하지 않고 별도 서비스로 유지할까요?
> SNS의 pub/sub 모델은 발행 즉시 모든 구독자에게 메시지를 복제해 푸시하므로, 메시지를 저장하거나 재시도하는 메커니즘 없이 전달하는 데 최적화돼 있습니다.
> SQS의 큐 모델은 메시지를 내구성 있게 보관하고 소비자가 자신의 속도로 폴링해 처리하도록 설계돼, 생산자와 소비자의 처리 속도 차이를 흡수하는 버퍼 역할이 핵심입니다.
> 두 모델을 단일 서비스로 통합하면 어느 쪽 패턴도 최적화하기 어렵고, SNS 주제에서 여러 SQS 큐로 팬아웃하는 조합처럼 두 서비스를 연계해 각자의 강점을 활용하는 아키텍처를 구성하는 것이 가능합니다.

### 2) 최종 사용자 컴퓨팅 — Amazon WorkSpaces

**Amazon WorkSpaces**는 사용자에게 **가상의 클라우드 기반 데스크톱(DaaS, Desktop as a Service)**을 프로비저닝합니다.

- Windows·Linux 데스크톱을 클라우드에서 제공 — **하드웨어 조달·복잡한 SW 설치 불필요.**
- 사용자는 **여러 기기·웹 브라우저에서 어디서나** 자기 데스크톱에 접근. 사용자 추가·제거가 빠름.

> 시험 신호: **"관리형 가상 데스크톱 / 클라우드 데스크톱 / 어디서나 접근하는 사내 PC 환경"** → WorkSpaces.

> 🧠 원리: 왜 WorkSpaces는 물리적 PC를 각 사용자에게 배포하는 대신 클라우드 가상 데스크톱을 제공하는 모델을 선택했을까요?
> 물리적 PC는 구매·배송·OS 설치·보안 패치·기기 분실 관리까지 IT 팀이 각 단말을 개별적으로 다뤄야 하고, 사용자 수가 늘거나 줄 때 하드웨어 조달과 반납 시간이 따라옵니다.
> 클라우드 가상 데스크톱은 데이터와 환경이 클라우드에 있으므로 기기를 분실해도 데이터 유출 위험이 낮고, 사용자 추가·제거를 관리 콘솔에서 처리할 수 있어 물리 기기 없이 인원 변화에 빠르게 대응하는 것이 가능합니다.
> 사용자는 어떤 기기에서든 같은 데스크톱 환경에 접근할 수 있으므로, 원격 근무나 다기기 환경에서도 일관된 작업 환경을 유지하는 것이 가능합니다.

### 3) IoT — AWS IoT Core

**AWS IoT Core**는 **IoT 기기를 AWS 클라우드 서비스 및 다른 기기에 연결**하는 관리형 서비스입니다.

- 기기가 안전하게 클라우드와 **메시지를 주고받음**(MQTT·HTTPS 등 프로토콜, 메시지 브로커 pub/sub).
- 센서·스마트 기기 등 대규모 IoT 기기를 연결·관리.

> 시험 신호: **"IoT 기기를 클라우드에 연결 / 기기 메시징"** → IoT Core.

> 🧠 원리: 왜 IoT 기기를 클라우드에 연결할 때 일반 HTTP API 대신 MQTT 같은 경량 프로토콜을 쓰는 전용 서비스가 필요할까요?
> IoT 기기는 메모리·전력·네트워크 대역폭이 제한된 환경에서 동작하는 경우가 많아, HTTP의 헤더·연결 오버헤드가 기기 자원 대비 크게 작용할 수 있습니다.
> MQTT는 작은 페이로드와 지속적 연결을 유지하면서 수백만 기기가 동시에 낮은 지연시간으로 메시지를 주고받는 데 적합하도록 설계돼, 배터리 소모와 대역폭을 줄이는 것이 가능합니다.
> IoT Core는 이 프로토콜을 지원하는 관리형 메시지 브로커를 제공해, 대규모 기기 연결·인증·라우팅을 직접 구현하지 않고도 클라우드 서비스와 연계하는 것이 가능합니다.

### 4) 그 외 범위 내 서비스 — 위치만 알아 두기

CLF는 아래 묶음도 *대략 어디에 속하는지*를 묻습니다(깊은 지식 불필요).

| 묶음 | 대표 서비스(예) |
|---|---|
| **비즈니스 앱** | Amazon Connect(콜센터), Amazon SES(이메일 발송) |
| **개발자 도구** | CloudShell(브라우저 셸), Cloud9(IDE), CodeCommit/Build/Deploy/Pipeline, X-Ray(분산 추적) |
| **프런트엔드·모바일** | AWS Amplify, AWS AppSync |
| **고객 지원** | AWS Support, AWS IQ, AWS Managed Services(AMS) |

> 이 표는 *식별용 참고*입니다 — 시험은 "이 서비스가 어느 범주인가" 정도를 묻습니다.

> 🧠 원리: 왜 CLF는 이 묶음의 서비스들에 대해 깊은 지식 대신 범주 식별 수준만 요구할까요?
> CLF는 클라우드 실무자 수준의 폭넓은 식별 능력을 평가하는 시험으로, 특정 서비스의 내부 동작보다 어떤 시나리오에 어떤 범주의 서비스를 선택하는지를 판단하는 능력을 측정합니다.
> Connect·Amplify·X-Ray 같은 서비스들은 특정 역할(콜센터·모바일 백엔드·추적)에 특화돼 있어, 시험에서는 시나리오 키워드를 보고 해당 범주임을 인식하면 충분합니다.
> 깊은 구현 지식은 전문 자격증(Developer·SysOps 등) 수준의 시험에서 다루므로, CLF에서는 서비스 이름과 범주 간 매칭 능력이 평가 범위가 됩니다.

### SQS 큐 유형 — 표준 vs FIFO (보강)

- **표준 큐(Standard)**: 거의 무제한 처리량, **최선 순서(best-effort ordering)**, **최소 한 번(at-least-once) 전달** — 메시지가 가끔 중복되거나 순서가 뒤바뀔 수 있습니다.
- **FIFO 큐**: **순서 보장(First-In-First-Out)** + **정확히 한 번(exactly-once) 처리**. 주문 처리처럼 순서와 중복 제거가 중요한 워크로드에 적합합니다.

> 시험 신호: "순서·정확히 한 번" → **FIFO**, "최대 처리량·순서 무관" → **표준**.
> 출처: [Amazon SQS](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/welcome.html)

> 🧠 원리: 왜 SQS는 모든 큐를 FIFO로 만들지 않고 순서를 보장하지 않는 표준 큐도 제공할까요?
> FIFO 순서와 정확히 한 번 처리를 보장하려면 메시지 순서를 추적하고 중복을 검사하는 추가 조율이 필요해, 표준 큐보다 처리량에 제약이 생깁니다.
> 많은 워크로드에서 메시지 처리 순서는 중요하지 않고 최대한 빠른 처리량이 필요한 경우가 있어, 이런 상황에서 FIFO의 조율 비용을 부담하면 성능이 낭비됩니다.
> 두 유형을 제공함으로써 순서와 중복 제거가 필요한 워크로드는 FIFO를, 처리량이 우선인 워크로드는 표준 큐를 선택해 각자의 요구에 맞게 최적화하는 것이 가능합니다.

## ✍️ 시험 포인트

- **SNS = 알림(pub/sub, 여러 구독자에 푸시, SMS·이메일).** **SQS = 메시지 큐(디커플링, 소비자가 폴링).** **EventBridge = 서버리스 이벤트 버스(이벤트 라우팅).**
- **SNS vs SQS**: 한 메시지를 *여러 곳에 동시에* = SNS. *큐에 쌓아 두고 처리* = SQS.
- **WorkSpaces = 관리형 가상 데스크톱(DaaS).**
- **IoT Core = IoT 기기를 클라우드에 연결·메시징.**
- 비즈니스 앱 Connect(콜센터)·SES(이메일), 개발 도구 X-Ray(추적)·CloudShell 등은 *범주만* 매칭.

## ⚠️ 흔한 함정

1. **"SNS와 SQS는 같은 것이다."** → ❌. **SNS = pub/sub 푸시(여러 구독자 동시)**, **SQS = 큐(소비자가 폴링)**. 모델이 다릅니다.
   *(원리: §1 — SNS는 발행 즉시 모든 구독자에게 메시지를 복제해 푸시하는 팬아웃 모델이고, SQS는 메시지를 큐에 내구성 있게 보관하고 소비자가 폴링해 처리하는 큐 모델로, 전달 방향과 저장 방식이 근본적으로 다르다.)*
2. **"이메일·SMS 알림을 SQS로 보낸다."** → ❌. 다중 대상 *알림*은 **SNS**(SMS·이메일 등 엔드포인트). SQS는 *큐*.
   *(원리: §1 — SNS는 이메일·SMS·HTTP 등 다양한 엔드포인트를 구독자로 등록해 알림을 푸시할 수 있는 pub/sub 서비스이고, SQS는 엔드포인트에 알림을 보내는 것이 아니라 소비자 애플리케이션이 폴링해 처리하는 큐 서비스다.)*
3. **"컴포넌트를 느슨하게 결합(디커플링)하려면 SNS만 쓴다."** → ⚠️ 보통 **SQS**(큐로 버퍼링)나 SNS+SQS 조합. SQS가 디커플링의 대표.
   *(원리: §1 — SQS 큐는 생산자와 소비자 사이에 메시지를 내구성 있게 보관해 각자의 처리 속도 차이를 흡수하는 버퍼 역할을 하므로, 컴포넌트 디커플링의 핵심 수단이 된다.)*
4. **"WorkSpaces는 서버용 가상 머신(EC2)이다."** → ❌. WorkSpaces는 *최종 사용자용 가상 **데스크톱***(DaaS). 서버 컴퓨팅은 EC2.
   *(원리: §2 — WorkSpaces는 최종 사용자에게 Windows·Linux 데스크톱 환경을 클라우드에서 제공하는 DaaS 서비스이고, EC2는 애플리케이션 실행·서버 역할을 위한 가상 머신으로 대상 사용자와 제공하는 환경이 다르다.)*
5. **"IoT 기기 연결도 그냥 EC2로 한다."** → ⚠️ IoT 기기의 안전한 연결·메시징 관리는 **IoT Core**가 전용으로 제공.
   *(원리: §3 — IoT Core는 MQTT 등 경량 프로토콜 지원, 기기 인증, 대규모 동시 연결 관리를 관리형으로 제공하는 전용 서비스이고, EC2로 직접 구현하면 이 모든 기능을 자체 구축해야 한다.)*
6. **"X-Ray는 보안 서비스다."** → ❌. **X-Ray는 분산 애플리케이션 추적(디버깅)** 개발자 도구입니다.
   *(원리: §4 — X-Ray는 마이크로서비스 간 요청 흐름을 추적해 병목·오류를 시각화하는 분산 추적 도구로 개발자 도구 범주에 속하며, 보안 서비스는 IAM·GuardDuty·Shield 등 별도 범주가 담당한다.)*

## 🧪 자가 점검

> 아래는 학습용 자가 점검입니다. (정식 검증 문항은 `t3-8.questions.json` 참조)

**Q1.** 하나의 이벤트(예: 주문 생성)를 여러 구독자(이메일·여러 SQS 큐·Lambda)에게 동시에 푸시 알림으로 보내려면 어떤 서비스인가요?

<details><summary>정답 보기</summary>

**Amazon SNS**(pub/sub 메시징). 주제(topic)에 발행하면 여러 구독자 엔드포인트(SQS·Lambda·이메일·SMS 등)로 메시지를 복제해 푸시합니다(팬아웃).
</details>

**Q2.** 마이크로서비스 컴포넌트들을 느슨하게 결합(디커플링)하기 위해, 메시지를 큐에 보관하고 소비자가 가져가 처리하게 하려면?

<details><summary>정답 보기</summary>

**Amazon SQS**(메시지 큐). 메시지를 큐에 안전하게 저장하고 소비자가 폴링해 처리하므로, 생산자·소비자를 분리(디커플링)하고 부하를 평준화합니다.
</details>

**Q3.** 사용자에게 클라우드 기반 가상 데스크톱(Windows/Linux)을 제공해 어디서나 접근하게 하려면? 그리고 IoT 기기를 안전하게 클라우드에 연결하려면?

<details><summary>정답 보기</summary>

가상 데스크톱은 **Amazon WorkSpaces**(DaaS), IoT 기기 연결은 **AWS IoT Core**입니다.
</details>

**Q4.** SNS와 SQS의 핵심 차이를 한 문장으로?

<details><summary>정답 보기</summary>

**SNS**는 발행/구독(pub/sub)으로 한 메시지를 *여러 구독자에게 동시에 푸시*하고, **SQS**는 메시지를 *큐에 쌓아 두고 소비자가 폴링해 처리*합니다(컴포넌트 디커플링).
</details>

---

**Q5 (원리).** 왜 SNS와 SQS는 자주 함께(SNS 주제 → 여러 SQS 큐) 쓰이는 구조가 되었을까요?

<details><summary>정답 보기</summary>

SNS 주제에 여러 SQS 큐를 구독자로 등록하면, 하나의 이벤트(예: 주문 생성)를 여러 다운스트림 컴포넌트(결제·재고·알림)에 동시에 전달하면서도 각 컴포넌트가 자신의 SQS 큐에서 독립적인 속도로 메시지를 소비할 수 있습니다. SNS 단독으로는 소비자가 일시 다운됐을 때 메시지를 재전달할 보관 장소가 없고, SQS 단독으로는 하나의 이벤트를 여러 큐에 동시에 복제하는 브로드캐스트가 없으므로, 두 서비스를 조합해야 넓은 팬아웃과 각 소비자별 독립적인 내구성 처리를 동시에 달성하는 것이 가능합니다.
</details>
