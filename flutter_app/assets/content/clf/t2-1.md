## 🔤 먼저 알아야 할 용어

이 문서를 읽는 데 필요한 기초 용어입니다. 이미 알면 건너뛰세요.

| 용어 | 영문 | 한 줄 풀이 |
|---|---|---|
| **IaaS** | Infrastructure as a Service | 서버·스토리지·네트워크 등 *인프라를 서비스 형태로* 제공 — 고객이 OS부터 직접 관리(EC2가 대표적) |
| **하이퍼바이저** | hypervisor | 물리 서버 위에서 *여러 가상 머신을 실행·격리*하는 소프트웨어 계층 |
| **게스트 OS** | guest OS | 가상 머신 위에 설치된 *고객 소유의 운영체제* — 호스트 OS(AWS가 관리)와 구분 |
| **서버리스** | serverless | 서버 프로비저닝·관리 없이 코드를 실행하는 모델 — 함수 실행형 **Lambda**가 대표적이며, **Fargate·S3·DynamoDB·SQS** 등 비(非)함수형 서비스도 서버리스로 분류됩니다 |
| **추상화** | abstraction | 하위 구현 세부 사항을 숨기고 *더 높은 수준의 인터페이스만 노출*하는 것 — 추상화가 높을수록 고객이 관리할 영역이 줄어듦 |
| **IAM** | Identity and Access Management | AWS 리소스에 대한 *접근 권한을 사용자·역할·정책 단위로 제어*하는 서비스 |
| **보안 그룹** | security group | EC2·RDS 등 AWS 리소스에 대한 *인바운드/아웃바운드 네트워크 트래픽을 제어*하는 가상 방화벽 |

## 📖 핵심 개념

### 1) 한 줄 정의 — 경계선은 "of vs in" {#of-vs-in}

AWS는 **클라우드 *자체*의 보안(Security *of* the Cloud)**, 고객은 **클라우드 *내부*의 보안(Security *in* the Cloud)**을 책임집니다.

- **of the cloud (AWS):** 클라우드를 *돌리는* 것 — 하드웨어, 시설, 네트워크, 호스트 OS, 가상화 계층.
- **in the cloud (고객):** 클라우드 *안에 올리는* 것 — 내 데이터, 내 앱, 내 OS 설정, 내 접근 권한.

> 기억 장치: **"AWS는 상자(box)를, 고객은 상자 안 내용물(contents)을 지킨다."**

> 🧠 원리: 왜 "of"와 "in"이라는 전치사 하나로 책임을 나눌 수 있을까요?
> AWS는 클라우드를 *실행시키는* 물리 하드웨어·하이퍼바이저·네트워킹 인프라를 직접 소유하고, 고객은 그 위에 *올린* 데이터·앱·접근 설정을 소유합니다.
> 소유 경계가 물리-논리로 명확히 갈리기 때문에, 인프라 계층에서 발생하는 결함(하드웨어 고장·하이퍼바이저 취약점)은 AWS가, 그 위 논리 계층의 설정 오류(공개 S3 버킷·과도한 IAM 권한)는 고객이 책임지는 구조가 성립합니다.
> "of the cloud"는 인프라 그 자체를, "in the cloud"는 인프라 안에 담긴 내용물을 가리키므로, 두 전치사가 물리-논리 경계를 자연스럽게 표현합니다.

### 2) 책임 분담표 {#responsibility-table}

| 구분 | AWS 책임 — "of the cloud" | 고객 책임 — "in the cloud" |
|---|---|---|
| 물리 | 데이터센터 물리 보안, 전력·냉각 등 환경 제어 | (없음 — 완전히 AWS가 처리) |
| 인프라 | 하드웨어, 글로벌 인프라(리전·AZ·엣지), 네트워킹 | — |
| 가상화 | 호스트 OS, 하이퍼바이저(가상화 계층) | — |
| 게스트 OS | (IaaS에서는 고객) | 게스트 OS 업데이트·**보안 패치**(EC2 등 IaaS) |
| 애플리케이션 | 관리형 서비스를 구동하는 소프트웨어 | 내가 올린 애플리케이션·유틸리티 |
| 네트워크 설정 | 인프라 장비 구성 | **보안 그룹(방화벽) 규칙**, 네트워크 트래픽 보호 |
| 자격증명 | — | **IAM** 사용자·그룹·정책, 최소 권한 설정 |
| 데이터 | 디스크 폐기 등 매체 보안 | **내 데이터 자체**, 분류, **암호화 옵션 선택**(전송 중/저장 시) |
| 교육 | AWS 직원 보안 교육 | 자사 직원 보안 교육 |

> **불변 규칙:** 어떤 서비스를 쓰든 **고객 데이터, 자산 분류, IAM 접근 권한 관리는 항상 고객 책임**입니다. 이건 서비스가 아무리 추상화돼도 AWS로 넘어가지 않습니다.

> 🧠 원리: 왜 데이터·IAM·자산 분류만은 어떤 서비스에서도 고객 책임으로 남을까요?
> 추상화 수준이 높아지면 OS·패치·런타임 같은 인프라 운영 작업은 AWS로 이전되지만, 데이터의 내용·가치·보호 필요성은 AWS가 알 수 없습니다.
> 고객만이 자신의 데이터가 얼마나 민감한지, 누구에게 접근을 허용해야 하는지를 판단할 수 있기 때문에, 분류와 접근 제어(IAM)는 서비스 추상화 수준과 무관하게 항상 고객에게 귀속됩니다.
> AWS가 이 결정까지 대신하면 데이터 주권이 AWS에 넘어가는 구조가 되므로, 이 항목은 서비스 계층이 아닌 *데이터 소유권* 원칙에서 비롯됩니다.

### 3) 공유 책임 (Shared Controls) — 같은 주제를 양쪽이 나눠 가진다 {#shared-controls}

일부 통제는 *층이 나뉘어* 양쪽 모두에 존재합니다. AWS는 인프라 층을, 고객은 자기 층을 책임집니다.

| 공유 통제 | AWS 쪽 | 고객 쪽 |
|---|---|---|
| **패치 관리** | 인프라의 결함 패치 | 게스트 OS·애플리케이션 패치 |
| **구성 관리** | 인프라 장비 구성 | 내 게스트 OS·DB·애플리케이션 구성 |
| **인식 및 교육** | AWS 직원 교육 | 자사 직원 교육 |

> 추가 개념 — **상속 통제(Inherited Controls):** 고객이 AWS로부터 *완전히 상속*받는 통제(물리·환경 통제). 온프레미스라면 직접 했어야 할 일을 AWS가 대신 떠안아 줍니다.

> 🧠 원리: 왜 패치·구성·교육은 "공유" 통제가 되고, 물리 보안은 공유가 아닐까요?
> 패치·구성·교육은 인프라 계층과 고객 계층 *각각에* 동일한 주제가 존재합니다 — AWS는 물리 서버 펌웨어를 패치하고, 고객은 게스트 OS를 패치합니다.
> 같은 이름의 통제가 두 계층에 독립적으로 존재하기 때문에 "공유"라는 표현이 붙습니다.
> 반면 물리 보안은 데이터센터 건물과 하드웨어에만 존재하는 통제여서 고객이 개입할 계층 자체가 없습니다 — 그래서 공유 없이 AWS 단독 책임입니다.

### 4) 핵심 중의 핵심 — 서비스에 따른 책임 이동 {#service-responsibility}

> 공식 문서 원문: **"Security in the cloud — Your responsibility is determined by the AWS service that you use."**
> (클라우드 내부의 보안 — *당신의 책임 범위는 당신이 사용하는 AWS 서비스에 따라 결정된다.*)

추상화 수준이 높아질수록 **고객 책임은 줄고 AWS 책임이 늘어납니다.** 같은 "공동 책임"이라도 서비스마다 경계선이 다릅니다.

```
고객 책임 많음  ←─────────────────────────────────→  고객 책임 적음
   EC2 (IaaS)          RDS (관리형 DB)         Lambda (서버리스)
   게스트 OS 패치 O      게스트 OS 패치 X(AWS)     OS·서버 X(AWS)
   앱·런타임 관리 O      DB 엔진 패치 X(AWS)       런타임 X(AWS)
   보안그룹 O           보안그룹·DB계정 O         실행역할(IAM)·코드 O
```

| 서비스 | AWS가 책임지는 것 | 고객이 책임지는 것 |
|---|---|---|
| **EC2** (IaaS) | 하드웨어, 호스트 OS, 가상화 | **게스트 OS 패치**, 애플리케이션, 보안 그룹, 방화벽 — *대부분 고객* |
| **RDS** (관리형 DB) | **게스트 OS·DB 엔진 패치**, 하부 인프라, 자동 백업·복제 | DB 설정·계정·권한, 보안 그룹(네트워크 접근), IAM, 암호화 옵션 선택, SSL/TLS 적용 |
| **Lambda** (서버리스) | OS·서버·런타임·확장·패치 (전부) | **함수 코드와 그 의존성**, 실행 역할(IAM 권한), 데이터 |

> 한눈에: **EC2는 OS 패치가 고객, RDS는 OS·엔진 패치가 AWS, Lambda는 서버 자체가 안 보임(전부 AWS).** 단, 세 경우 모두 **데이터·IAM은 고객**.

> 🧠 원리: 왜 서비스 추상화 수준이 높아질수록 고객의 책임 범위가 줄어들까요?
> 추상화가 높다는 것은 AWS가 더 많은 하위 계층(OS·런타임·인프라)을 직접 운영하겠다는 계약 선택입니다.
> EC2(IaaS)에서는 AWS가 하이퍼바이저까지만 관리하므로 게스트 OS부터는 고객이 패치·구성해야 하지만, RDS는 AWS가 게스트 OS와 DB 엔진까지 관리 범위를 확장했기 때문에 그만큼 고객 책임이 위로 올라갑니다.
> Lambda는 OS와 런타임을 AWS가 완전히 숨기므로 고객이 관리할 수 있는 가장 낮은 계층이 함수 코드와 그 의존성까지로 좁아집니다.
> 서비스가 관리 범위를 늘릴수록 고객이 접근할 수 있는 계층이 줄어드는 것이 이동의 메커니즘입니다.

### 한 문장 요약 — "of" vs "in" the cloud (보강)

AWS는 **"클라우드의 보안(security *of* the cloud)"** — 클라우드를 실행하는 인프라(하드웨어·소프트웨어·네트워킹·시설)를 책임지고, 고객은 **"클라우드 *안*의 보안(security *in* the cloud)"** — 그 위에 올린 데이터·구성·접근 관리를 책임집니다. 이 한 문장이 공동 책임 모델의 핵심 표현입니다.

> 출처: [AWS 공동 책임 모델](https://aws.amazon.com/compliance/shared-responsibility-model/)

> 🧠 원리: 왜 이 한 문장이 "원칙"으로 작동할까요?
> 시험에 나오는 어떤 서비스든, 그 계층을 소유·운영하는 주체가 누구인지만 따지면 책임자를 유추할 수 있기 때문입니다.
> 암기한 표가 기억나지 않아도 "이 계층은 누가 만들고 굴리는가"라는 질문 하나로 답이 복원됩니다.
> 그래서 표를 외우는 것보다 이 소유 기준 하나를 이해하는 쪽이 오래갑니다.

## ✍️ 시험 포인트

- "**물리적 보안 / 데이터센터 / 하드웨어 / 가상화 계층 / 호스트 OS**" → 보기에 나오면 **AWS 책임**. (예외 거의 없음)
- "**보안 그룹 구성 / IAM 사용자·권한 / 게스트 OS 패치(EC2) / 데이터 암호화 *설정* / 데이터 분류**" → **고객 책임**.
- "어떤 서비스를 쓰든 항상 고객" → **데이터 + IAM(접근 관리) + 자산 분류**. (단골 정답)
- **서비스를 바꿔 묻는 문제**: 게스트 OS 패치 주체를 묻고 보기에 EC2/RDS/Lambda를 섞어 둔다 → EC2만 고객, 나머지는 AWS.
- "암호화"는 함정 주의: **암호화 기능 제공·키 인프라 = AWS / 암호화를 *켤지, 어떻게 쓸지* 선택 = 고객.**
- 공유 통제 3종(**패치·구성·인식교육**)은 "둘 다 책임"이 정답인 경우가 많다.

## ⚠️ 흔한 함정 {#pitfalls}

1. **"클라우드라서 AWS가 보안을 다 해준다."** → ❌. AWS는 *of the cloud*만. 데이터·접근권한·앱 보안은 고객.
   *(원리: §1 — "of"와 "in"의 경계에서 인프라 계층은 AWS가, 그 위 논리 계층의 설정과 데이터는 고객이 소유한다.)*
2. **"S3에 올린 데이터는 AWS가 암호화·보호한다."** → ⚠️ 2023년 1월 이후 **신규 객체에는 SSE-S3 기본 암호화가 자동 적용**됩니다. 단, **접근 정책·데이터 분류·KMS 키 선택 등 추가 보호는 여전히 고객 책임**입니다. (S3 버킷을 공개로 잘못 열어 생긴 유출은 100% 고객 책임)
   *(원리: §2 — 기본 암호화는 AWS가 제공하지만, 데이터의 민감도와 접근 허용 범위 설정·키 관리 선택은 고객만 판단할 수 있어 분류·접근 제어·KMS 활용 여부는 항상 고객 책임이다.)*
3. **"RDS도 관리형이니 보안 그룹·DB 계정까지 AWS가 한다."** → ❌. AWS는 OS·엔진 패치까지. **네트워크 접근(보안 그룹)·DB 사용자·IAM·암호화 옵션은 고객.**
   *(원리: §4 — 서비스 추상화가 높아져도 고객이 생성한 논리 접근 설정(보안 그룹·계정·IAM)은 고객 소유 계층으로 남는다.)*
4. **"Lambda는 서버가 없으니 보안 책임도 없다."** → ❌. **함수 코드, 의존성, 실행 역할(IAM 권한), 데이터**는 고객.
   *(원리: §4 — Lambda는 고객이 관리할 계층을 함수 코드와 IAM 역할까지로 좁힌 것이지 없앤 것이 아니다.)*
5. **"게스트 OS 패치는 항상 고객."** → ❌. **EC2(IaaS)만** 고객. RDS·Lambda의 OS 패치는 AWS.
   *(원리: §4 — 서비스 추상화 수준에 따라 게스트 OS가 고객 접근 계층에 들어오는지 여부가 달라진다.)*
6. **"공동 책임 = 50:50으로 나눈다."** → ❌. 비율이 아니라 *영역*으로 나뉘며, 그 영역은 **서비스에 따라 이동**한다.
   *(원리: §4 — 공동 책임은 비율로 고정되지 않으며, 서비스에 따라 어느 계층까지 고객 영역인지가 달라진다.)*

## 🧪 자가 점검

> 아래는 학습용 자가 점검입니다. (정식 검증 문항 5개는 `t2-1.questions.json` 참조)

**Q1.** EC2 인스턴스의 게스트 OS에 보안 패치를 적용할 책임은 누구에게 있나요?

<details><summary>정답 보기</summary>

**고객.** EC2는 IaaS이므로 게스트 OS의 업데이트·보안 패치, 그 위의 애플리케이션, 보안 그룹 구성까지 고객 책임입니다. (호스트 OS·하이퍼바이저는 AWS)
</details>

**Q2.** 같은 데이터베이스라도 EC2에 직접 설치한 DB와 Amazon RDS는 책임이 어떻게 다른가요?

<details><summary>정답 보기</summary>

EC2 위 DB는 **게스트 OS와 DB 엔진 패치까지 고객**이 합니다. RDS는 **그 OS·엔진 패치를 AWS가** 대신합니다(관리형). 단 RDS에서도 DB 계정·권한, 보안 그룹, IAM, 암호화 옵션은 고객 책임입니다.
</details>

**Q3.** 서비스 종류와 무관하게 *언제나* 고객 책임으로 남는 것 세 가지는?

<details><summary>정답 보기</summary>

**① 고객 데이터 자체, ② 자산 분류, ③ IAM을 통한 접근 권한 관리.** 추상화가 아무리 높아도(예: Lambda) 이 셋은 AWS로 넘어가지 않습니다.
</details>

**Q4.** "패치 관리"가 공유 통제(Shared Control)인 이유는?

<details><summary>정답 보기</summary>

층이 나뉘기 때문입니다. **AWS는 인프라의 결함을 패치**하고, **고객은 자신의 게스트 OS와 애플리케이션을 패치**합니다 — 같은 주제를 양쪽이 각자 층에서 책임집니다.
</details>

---

**Q5 (원리).** 왜 서비스 추상화 수준이 높아질수록(EC2→RDS→Lambda 순) 고객의 책임 범위가 줄어드나요?

<details><summary>정답 보기</summary>

**AWS가 관리하는 계층이 위로 확장될수록, 고객이 접근할 수 있는 계층이 그만큼 위로 밀려나기 때문입니다.** 접근할 수 없는 계층은 책임질 수도 없으므로, 추상화가 높을수록 고객 책임은 코드·데이터·권한 쪽으로 좁아집니다.
</details>
