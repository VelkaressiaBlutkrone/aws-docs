# 데이터베이스 서비스 (관계형·NoSQL·인메모리)

## 🎯 왜 중요한가

- 도메인 3(34%)에서 데이터베이스는 **"어떤 DB를 고를까?"**를 묻습니다. 핵심은 **관계형(RDS/Aurora) vs NoSQL(DynamoDB)** 구분과, **EC2에 직접 vs 관리형**의 트레이드오프입니다.
- [공동 책임 모델](#)의 연장선입니다: **관리형 서비스(RDS)일수록 AWS가 더 많이(패치·백업·HA) 책임**집니다. "운영 부담을 줄이고 싶다"는 곧 관리형입니다.
- "초고속 조회로 DB 부하를 줄인다"(ElastiCache), "DB를 AWS로 옮긴다"(DMS) 같은 시나리오도 단골입니다.

## 🔤 먼저 알아야 할 용어

이 문서를 읽는 데 필요한 기초 용어입니다. 이미 알면 건너뛰세요.

| 용어 | 영문 | 한 줄 풀이 |
|---|---|---|
| **트랜잭션** | Transaction | 여러 DB 작업을 *한 묶음으로 처리*해, 전부 성공하거나 전부 취소되도록 보장하는 처리 단위 — 계좌 이체처럼 중간 실패가 허용되지 않는 작업에 필요합니다 |
| **페일오버** | Failover | 주(Primary) 인스턴스에 장애가 발생했을 때 *대기(Standby) 인스턴스로 자동 전환*하는 메커니즘 — 다운타임을 최소화하는 고가용성의 핵심입니다 |
| **복제본** | Read Replica | 원본 DB의 데이터를 *읽기 전용으로 복사*해 둔 인스턴스 — 읽기 요청을 분산해 원본 DB 부하를 줄입니다 |
| **스키마** | Schema | 테이블 구조·컬럼·데이터 타입 등 *데이터가 어떤 형태로 저장되는지를 정의한 설계도* — 엔진마다 스키마 문법이 달라 이기종 마이그레이션 시 변환이 필요합니다 |
| **조인(JOIN)** | JOIN | 관계형 DB에서 *두 개 이상의 테이블을 공통 컬럼으로 결합*해 한 번에 조회하는 연산 — NoSQL은 이를 지원하지 않아 비정규화 설계가 필요합니다 |
| **파티션** | Partition (Shard) | 대규모 데이터를 *여러 서버에 나눠 저장*하는 단위 — DynamoDB는 키를 기반으로 파티션에 분산해 단일 파티션 안에서 읽기를 완결합니다 |
| **이기종 마이그레이션** | Heterogeneous Migration | *다른 엔진(예: Oracle → Aurora)으로 DB를 이전*하는 작업 — 스키마 문법·데이터 타입이 달라 스키마 변환 도구(SCT)가 추가로 필요합니다 |

## 📖 핵심 개념

### 1) EC2에 직접 설치 vs 관리형 DB(RDS) — 누가 관리하나 (★)

같은 데이터베이스라도 *어디에 두느냐*에 따라 관리 부담이 다릅니다.

| 작업 | EC2에 직접 설치 | **Amazon RDS(관리형)** |
|---|---|---|
| OS 설치·패치 | 고객 | **AWS** |
| DB 소프트웨어 설치·패치 | 고객 | **AWS** |
| 백업 | 고객 | **AWS** |
| 고가용성(HA) | 고객 | **AWS** |
| 확장(Scaling) | 고객 | **AWS** |
| 쿼리 튜닝·애플리케이션 최적화 | 고객 | 고객 |

> 즉 **RDS는 "지루한 관리 작업"을 AWS가 대신** 해 주고, 고객은 *쿼리 튜닝·앱*에 집중합니다. "운영 부담 최소화 / 패치·백업 자동" → 관리형(RDS).

> 🧠 원리: 왜 AWS는 EC2에 DB를 직접 설치하는 방식을 없애지 않고, 관리형 RDS를 별도로 제공할까요?
> EC2에 직접 설치하면 OS·DB 엔진·백업·HA 설정 등 모든 운영 작업을 고객이 제어할 수 있어, 특수한 설정이나 검증되지 않은 DB 엔진이 필요한 경우에 적합합니다.
> 하지만 대다수 워크로드는 DB 운영 자체가 목적이 아니라 쿼리와 애플리케이션 로직에 집중해야 하는데, OS·패치·백업·페일오버를 직접 관리하면 그 시간이 "차별화되지 않는 무거운 작업(undifferentiated heavy lifting)"에 소비됩니다.
> 관리형 RDS를 별도로 두면, 제어가 필요한 팀은 EC2를 쓰고 운영 부담을 줄이고 싶은 팀은 RDS를 선택해 같은 인프라 위에서 각자 필요한 트레이드오프를 고를 수 있습니다.

### 2) 관계형 데이터베이스 — Amazon RDS와 Amazon Aurora

**Amazon RDS(Relational Database Service)**는 클라우드에서 **관계형 DB를 쉽게 설정·운영·확장**하게 해 주는 관리형 서비스입니다.

- 익숙한 엔진을 그대로: **MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, IBM Db2** (그리고 **Aurora**).
- AWS가 **백업·소프트웨어 패치·자동 장애 감지·복구**를 관리.
- **고가용성**: **Multi-AZ 배포**(다른 AZ에 동기식 대기 인스턴스를 두고 문제 시 자동 페일오버). **읽기 전용 복제본(read replica)**으로 읽기 확장.

**Amazon Aurora**는 **MySQL·PostgreSQL과 호환되는 완전관리형 관계형 DB 엔진**입니다.

- **Amazon RDS의 일부**로, RDS의 관리·운영 기능(프로비저닝·패치·백업·복구)을 그대로 사용.
- **고성능**: 일부 워크로드에서 **표준 MySQL의 최대 5배, PostgreSQL의 최대 3배 처리량**. 스토리지가 자동 확장되고 AZ 간 복제로 고가용성.
- 기존 MySQL·PostgreSQL 앱을 거의 수정 없이 사용.

> 관계형(RDS/Aurora) 신호: **정형 데이터, SQL, 트랜잭션, 테이블·조인.** "MySQL/PostgreSQL 호환 고성능"이면 **Aurora**.

> 🧠 원리: 왜 Aurora는 새로운 DB 엔진을 만들면서도 MySQL·PostgreSQL과 호환되는 방식을 택했을까요?
> 기존 MySQL·PostgreSQL 사용자가 Aurora로 이전할 때 애플리케이션 코드·드라이버·쿼리를 거의 바꾸지 않아도 되도록, 호환성을 유지하면 마이그레이션 비용과 위험이 낮아집니다.
> 동시에 Aurora는 스토리지 계층을 별도로 재설계해 I/O 병목을 줄이고 AZ 간 복제를 스토리지 수준에서 처리함으로써, 호환성을 포기하지 않고도 처리량을 높이는 것이 가능해집니다.
> 결과적으로 "MySQL·PostgreSQL 생태계의 친숙함"과 "AWS 최적화 스토리지의 성능"을 동시에 제공하는 포지셔닝이 되어, 기존 관계형 앱을 클라우드로 옮기는 경로가 만들어집니다.

### 3) NoSQL — Amazon DynamoDB

**Amazon DynamoDB**는 **서버리스·완전관리형 분산 NoSQL** 데이터베이스로, **어떤 규모에서도 한 자릿수 밀리초** 성능을 제공합니다.

- **서버리스**: 서버를 프로비저닝·패치·관리하지 않음. 트래픽에 따라 자동 확장(0까지 — 트래픽 없으면 비용 없음).
- **키-값 + 문서** 데이터 모델. (관계형의 *JOIN*은 지원하지 않음 → 비정규화 설계)
- 기본적으로 **3개 AZ에 자동 복제**(높은 내구성·가용성). **글로벌 테이블**로 멀티 리전.
- 용도: 대규모 트래픽·일관된 고속 성능이 필요한 곳(장바구니, 게임 상태, 세션, 리더보드 등).

> NoSQL(DynamoDB) 신호: **유연한 스키마, 키-값/문서, 초대규모 확장, 일관된 밀리초 지연, 서버리스.** "관계·조인이 핵심"이면 오히려 RDS.

> 🧠 원리: 왜 DynamoDB는 JOIN을 지원하지 않는 키-값/문서 모델을 선택했을까요?
> 관계형 DB에서 JOIN은 여러 테이블을 연결하기 위해 데이터를 조합하는 연산인데, 데이터가 여러 서버에 분산된 환경에서 JOIN을 수행하면 서버 간 네트워크 조율이 필요해 지연시간이 급증합니다.
> DynamoDB는 키 기반으로 데이터를 파티션(샤드)에 분산해, 한 항목 조회가 단일 파티션 안에서 완결되도록 설계해 어떤 규모에서도 한 자릿수 밀리초가 가능합니다.
> JOIN 대신 비정규화(관련 데이터를 한 항목에 미리 중복 저장)를 설계 원칙으로 삼으면, 읽기 성능을 분산 규모와 함께 유지할 수 있습니다.

### 4) 인메모리 — Amazon ElastiCache

**Amazon ElastiCache**는 **분산 인메모리 데이터 스토어/캐시**를 쉽게 설정·관리·확장하게 해 주는 관리형 서비스입니다.

- 엔진: **Valkey, Memcached, Redis OSS**. 서버리스 또는 노드 기반 클러스터.
- **자주 조회하는 데이터를 메모리에 캐시**해 애플리케이션 성능을 높이고 **백엔드 DB 부하를 줄입니다.**

> 시험 신호: **"DB 앞에 캐시를 둬 반복 조회를 초고속으로 / DB 부하 경감"** → ElastiCache.

> 🧠 원리: 왜 DB를 더 빠르게 만드는 대신 앞에 캐시 계층을 별도로 두는 방식을 선택할까요?
> DB는 내구성·일관성을 위해 디스크에 데이터를 기록하는 구조로 최적화돼 있어, 디스크 I/O 자체가 메모리보다 느린 한계가 있습니다.
> 반복 조회되는 데이터를 메모리에 캐시해 두면, 같은 요청이 올 때 DB까지 가지 않고 메모리에서 바로 응답해 지연시간이 크게 줄고 DB로 가는 요청 수도 줄어 DB가 쓰기·복잡한 쿼리에 집중할 수 있습니다.
> DB와 캐시를 분리하면 각각을 독립적으로 확장·교체할 수 있어, 캐시 히트율이 높은 워크로드에서는 DB 비용을 늘리지 않고 읽기 처리량을 높이는 것이 가능합니다.

### 5) 데이터베이스 마이그레이션 — AWS DMS (+ SCT)

**AWS DMS(Database Migration Service)**는 **데이터베이스를 AWS로(또는 클라우드/온프레 간) 마이그레이션**하는 서비스입니다.

- 일회성 이전 또는 **진행 중 변경을 복제**해 소스·타겟을 동기화(마이그레이션 중에도 운영 지속 → 다운타임 최소화).
- **동종(homogeneous, 같은 엔진)** 및 **이기종(heterogeneous, 다른 엔진)** 마이그레이션 모두 지원.
- **스키마 변환**: 엔진이 다를 때 **AWS Schema Conversion Tool(SCT)** 또는 DMS Schema Conversion으로 소스 스키마를 타겟 엔진에 맞게 변환.

> 시험 신호: **"온프레미스 DB를 AWS로 옮긴다"** → DMS. **"엔진을 바꿔 옮긴다(예: Oracle→Aurora)"** → DMS + **SCT**.

> 🧠 원리: 왜 DMS는 소스 DB를 중단하지 않고 마이그레이션하는 방식을 제공할까요?
> 대규모 프로덕션 DB를 옮기려면 데이터 복사에 상당한 시간이 걸리는데, 그 동안 소스 DB를 중단하면 비즈니스가 멈추는 다운타임이 발생합니다.
> DMS는 초기 전체 데이터 로드 후 CDC(변경 데이터 캡처)로 소스에서 발생하는 변경을 타겟에 계속 반영해, 마이그레이션 기간 동안 소스와 타겟을 동기화된 상태로 유지합니다.
> 동기화가 충분히 따라잡혔을 때 짧은 컷오버(전환) 창만 필요해, 다운타임을 최소화하면서 대용량 DB를 이전하는 것이 가능합니다.

### 6) 한눈에 — 어떤 데이터베이스?

| 필요 | 서비스 |
|---|---|
| 정형 데이터·SQL·트랜잭션(관계형) | **Amazon RDS** (또는 고성능 MySQL/PostgreSQL → **Aurora**) |
| 유연한 스키마·초대규모·일관된 밀리초·서버리스(NoSQL) | **Amazon DynamoDB** |
| 초고속 인메모리 캐시로 DB 부하 경감 | **Amazon ElastiCache** |
| DB를 AWS로 마이그레이션 | **AWS DMS** (+ 엔진 변경 시 **SCT**) |

> 🧠 원리: 왜 데이터베이스 선택 기준에서 데이터 모델(관계형 vs 키-값/문서)이 서비스·가격보다 먼저 결정되어야 할까요?
> 데이터 모델은 애플리케이션이 데이터를 읽고 쓰는 패턴을 결정하며, 선택 후 변경하려면 스키마·코드·마이그레이션 비용이 모두 따라옵니다.
> 관계형 모델(SQL·조인·트랜잭션)이 필요한 워크로드를 NoSQL로 구현하거나 반대로 하면, 아무리 비용이나 성능 지표가 좋아도 애플리케이션 요구를 충족하지 못하는 구조적 한계가 생깁니다.
> 데이터 모델을 먼저 결정하면 적합한 서비스 범위가 좁혀지고, 이후 성능·비용·관리 부담 기준으로 세부 선택이 가능해집니다.

---

## ✍️ 시험 포인트

- **EC2 직접 설치 = 고객이 OS·DB 패치·백업·HA 관리. RDS = AWS가 관리**(쿼리 튜닝만 고객). "운영 부담↓·패치/백업 자동" → RDS.
- **관계형 = RDS / Aurora. NoSQL = DynamoDB.** "MySQL·PostgreSQL 호환 고성능" → **Aurora**(RDS의 일부).
- **DynamoDB** = 서버리스 NoSQL, 키-값/문서, **한 자릿수 밀리초**, 무제한 확장. JOIN 없음.
- **ElastiCache** = 인메모리 캐시(Redis/Memcached/Valkey), DB 부하 경감.
- **DMS** = DB 마이그레이션(최소 다운타임). **이기종 엔진 변환 = SCT**.
- 관계형이면 RDS/Aurora, 키-값·대규모면 DynamoDB — *데이터 모델*로 가른다.

---

## ⚠️ 흔한 함정

1. **"DynamoDB는 관계형 데이터베이스다."** → ❌. DynamoDB는 **NoSQL**(키-값/문서). 관계형(SQL·조인)은 RDS·Aurora.
   *(원리: §3 — DynamoDB는 JOIN 없이 키 기반 파티션에 데이터를 분산해 어떤 규모에서도 일관된 지연시간을 유지하는 NoSQL 모델로, 관계형과 구조적으로 다른 설계다.)*
2. **"Aurora는 RDS와 완전히 별개 서비스다."** → ❌. **Aurora는 Amazon RDS의 일부**이며 MySQL·PostgreSQL 호환.
   *(원리: §2 — Aurora는 MySQL·PostgreSQL 호환성을 유지하면서 스토리지 계층을 재설계해 성능을 높인 RDS 엔진으로, RDS의 관리·운영 기능을 그대로 사용한다.)*
3. **"운영 부담을 줄이려는데 EC2에 직접 DB를 설치한다."** → ⚠️ 반대. 패치·백업·HA를 AWS가 맡는 **RDS**가 운영 부담이 적습니다.
   *(원리: §1 — EC2 직접 설치는 OS·패치·백업·HA 같은 "차별화되지 않는 무거운 작업"을 고객이 담당하는 구조이며, 관리형 RDS는 이를 AWS가 처리해 운영 부담이 줄어든다.)*
4. **"ElastiCache는 영구 데이터베이스로 쓴다."** → ⚠️ 주의. ElastiCache는 *인메모리 캐시*로 성능 가속·DB 부하 경감이 목적입니다(주 데이터 저장소는 RDS/DynamoDB 등).
   *(원리: §4 — ElastiCache는 반복 조회 데이터를 메모리에 두어 DB I/O를 줄이는 캐시 계층으로, 내구성 있는 주 저장소가 아니라 읽기 성능 가속이 목적이다.)*
5. **"엔진을 Oracle에서 Aurora로 바꿔 옮기는데 스키마는 그냥 복사하면 된다."** → ❌. 이기종 마이그레이션은 **SCT**(또는 DMS Schema Conversion)로 스키마를 타겟 엔진에 맞게 변환해야 합니다.
   *(원리: §5 — 엔진마다 스키마 문법·데이터 타입이 달라, 이기종 이전 시 소스 스키마를 타겟 엔진에 맞게 변환하는 도구(SCT)가 필요하다.)*
6. **"DynamoDB는 서버를 직접 프로비저닝해야 한다."** → ❌. DynamoDB는 **서버리스** — 서버 관리 없이 자동 확장.
   *(원리: §3 — DynamoDB는 서버 프로비저닝·패치·관리를 AWS가 처리하고 트래픽에 따라 자동 확장되는 서버리스 모델로, 고객은 데이터와 쿼리에만 집중한다.)*

## 🧪 자가 점검

> 아래는 학습용 자가 점검입니다. (정식 검증 문항은 `t3-4.questions.json` 참조)

**Q1.** 관계형 데이터베이스를 운영하되 OS·DB 패치, 백업, 고가용성 구성 같은 관리 작업을 AWS에 맡기고 싶습니다. EC2에 직접 설치하는 것과 비교해 무엇을 선택해야 하나요?

<details><summary>정답 보기</summary>

**Amazon RDS**(관리형 관계형 DB). EC2에 직접 설치하면 OS·DB 패치·백업·HA·확장을 모두 고객이 하지만, RDS는 이를 AWS가 관리하고 고객은 쿼리 튜닝·앱에 집중합니다.
</details>

**Q2.** 유연한 스키마의 키-값 데이터를, 초대규모에서도 일관된 한 자릿수 밀리초로 처리하는 서버리스 데이터베이스가 필요합니다. 무엇인가요?

<details><summary>정답 보기</summary>

**Amazon DynamoDB**(서버리스 NoSQL). 키-값·문서 모델, 어떤 규모에서도 한 자릿수 밀리초 성능, 서버 관리 없는 자동 확장이 특징입니다.
</details>

**Q3.** 자주 조회되는 데이터를 메모리에 캐시해 응답을 초고속으로 만들고 백엔드 데이터베이스 부하를 줄이려면?

<details><summary>정답 보기</summary>

**Amazon ElastiCache**(인메모리 캐시, Redis/Memcached/Valkey). 반복 조회를 메모리에서 처리해 성능을 높이고 DB 부하를 줄입니다.
</details>

**Q4.** 온프레미스 Oracle 데이터베이스를 Amazon Aurora로 옮기려 합니다. 엔진이 다른데 어떤 서비스/도구를 쓰나요?

<details><summary>정답 보기</summary>

**AWS DMS**로 데이터를 마이그레이션하고, 엔진이 다른 이기종 마이그레이션이므로 **AWS Schema Conversion Tool(SCT)**(또는 DMS Schema Conversion)로 스키마를 Aurora에 맞게 변환합니다.
</details>

---

**Q5 (원리).** 왜 DynamoDB는 JOIN을 지원하지 않는 비정규화 설계를 선택할까요?

<details><summary>정답 보기</summary>

관계형 모델은 데이터를 여러 테이블로 나눠 정규화하고 JOIN으로 조합하는 방식을 선택한 반면, DynamoDB는 처음부터 "JOIN 없이 단일 키 조회로 끝낸다"는 설계 목표를 세웠습니다. 그 목표를 위해 관련 데이터를 한 항목에 미리 중복 저장(비정규화)해 두고, 어떤 규모에서도 단일 파티션 안에서 읽기를 완결해 지연시간을 예측 가능하게 유지합니다. 이 트레이드오프(중복 저장 감수 → 분산 규모에서 일관된 밀리초)는 관계형 DB가 해결하기 어려운 초대규모 고속 조회 워크로드를 위해 의도적으로 선택된 설계입니다.
</details>
