## 📖 핵심 개념

### 1) 3층 구조 — 리전 ⊃ 가용 영역(AZ) ⊃ (엣지는 별도 망)

| 구성요소 | 한 줄 정의 | 핵심 |
|---|---|---|
| **리전(Region)** | 서로 **격리된 별개의 지리적 영역** (예: 서울 `ap-northeast-2`) | 리전끼리 격리 → 최대 내결함성. **리소스는 리전 간 자동 복제 안 됨** |
| **가용 영역(AZ)** | 한 리전 *안의* **다수의 격리된 위치**(하나 이상의 데이터센터) (예: `ap-northeast-2a`) | 물리적으로 분리·격리. 여러 AZ에 분산하면 **단일 위치 장애를 견딤** |
| **엣지 로케이션(Edge Location)** | 사용자 *가까이* 콘텐츠를 캐시/전달하는 거점(POP) | CloudFront 등 엣지 서비스가 사용. 리전·AZ와 **별개의 글로벌 망** |

> 공식 표현: *"Regions are separate geographic areas"*, *"Availability Zones are multiple, isolated locations within each Region."* 그리고 *"Regions are isolated from each other, and we don't automatically replicate resources across Regions."*

### 2) 고가용성의 핵심 — 여러 AZ에 분산

AWS의 데이터센터는 견고하지만, **드물게** 한 위치에 장애가 날 수 있습니다. 모든 인스턴스를 *한 위치*에 뒀다가 그곳에 장애가 나면 전부 멈춥니다.

> 공식: *"By launching EC2 instances in multiple Availability Zones, you can protect your applications from the failure of a single location in the Region."* — 한 AZ가 실패해도 *다른 AZ의 인스턴스가 요청을 처리*하도록 설계.

- **AZ는 단일 장애점(SPOF)을 공유하지 않도록 격리**돼 있습니다 → 한 AZ의 정전·화재가 다른 AZ로 번지지 않음.
- 리전 내 AZ들은 **저지연 네트워크로 연결**돼, 멀티 AZ로 분산해도 빠르게 통신합니다.
- 그래서 **고가용성 = 멀티 AZ**가 CLF의 기본 공식입니다.

### 3) 여러 "리전"을 쓰는 시점 — AZ로는 안 되는 이유들

AZ 분산은 *한 리전 안의* 고가용성입니다. 다음과 같은 요구는 **여러 리전**이 필요합니다.

| 요구 | 왜 멀티 리전인가 |
|---|---|
| **재해 복구(DR)·비즈니스 연속성** | 리전 전체가 영향받는 광역 재해에도 다른 리전에서 서비스 지속 |
| **지연시간(latency) 단축** | 전 세계 사용자에게 *각자 가까운 리전*에서 서비스 → 응답 빠름 |
| **데이터 주권(data residency)** | "데이터를 특정 국가/지역 안에 보관" 같은 **법적·규제 요건** 충족 |

> 리전 선택의 흔한 기준: ① **데이터 주권/규정**, ② 사용자와의 **지연시간**(가까운 리전), ③ **서비스 가용성**(리전마다 제공 서비스 차이), ④ **비용**(리전별 요금 차이).

### 4) 엣지 — 사용자 가까이서 빠르게: CloudFront vs Global Accelerator (★ 시험 단골)

둘 다 "AWS 글로벌 엣지 망으로 빠르게"지만 **하는 일이 다릅니다.**

**Amazon CloudFront** — **콘텐츠 전송 네트워크(CDN)**
- 정적·동적 웹 콘텐츠(.html·.css·.js·이미지 등)를 **전 세계 엣지 로케이션에 캐시**해 사용자에게 **가장 낮은 지연**으로 전달.
- 요청은 *가장 가까운 엣지*로 라우팅되고, 엣지에 사본이 있으면 즉시 전달(없으면 origin(S3·HTTP 서버)에서 가져와 캐시).
- 키워드: **"캐싱", "콘텐츠 전송", "정적/동적 웹 콘텐츠"**.

**AWS Global Accelerator** — **글로벌 네트워크 라우팅 + 고정 IP**
- **정적 IP 주소(애니캐스트)**를 고정 진입점으로 제공하고, **AWS 글로벌 네트워크**로 트래픽을 **가장 가까운/건강한 리전 엔드포인트**(ALB·NLB·EC2·EIP)로 라우팅.
- 콘텐츠를 *캐시하지 않습니다.* health·위치 기반으로 *경로*를 최적화해 가용성·성능을 높임. (TCP/UDP 기반 앱에 적합)
- 키워드: **"고정 IP", "비-HTTP/TCP·UDP", "최적 엔드포인트로 라우팅", "캐싱 아님"**.

> 한 문장 구분: **CloudFront = 콘텐츠를 엣지에 *캐시*(CDN). Global Accelerator = 고정 IP로 *경로*를 최적화(라우팅).** 웹 페이지·이미지 가속이면 CloudFront, 게임·IoT·VoIP 같은 *비웹 TCP/UDP* 앱에 고정 IP·저지연 라우팅이면 Global Accelerator.

### 5) 근접·확장 인프라 — Local Zones · Wavelength · Outposts

표준 리전·AZ로 부족한 "더 가까이/온프레미스" 요구에 답하는 확장입니다.

| 인프라 | 무엇 | 언제 |
|---|---|---|
| **AWS Local Zones** | 컴퓨팅·스토리지·DB 등을 **대도시·인구 밀집지 가까이** 둔 리전의 확장 | 특정 도시 사용자에게 **저지연**(실시간 게임·라이브 스트리밍·AR/VR), 데이터 레지던시 |
| **AWS Wavelength** | **통신사 5G 네트워크 엣지**에 AWS 컴퓨팅·스토리지 배포 | **5G 모바일 기기**에 **초저지연(ultra-low latency)** |
| **AWS Outposts** | AWS 인프라·서비스를 **고객 온프레미스(자체 데이터센터)**로 확장 | 데이터를 *건물 안*에 둬야 하거나 온프레 시스템과 *초근접* 처리 필요 |

> 한눈에: **Local Zones = 도시 근접 저지연 · Wavelength = 5G 엣지 초저지연 · Outposts = 내 데이터센터 안에 AWS.**

## ✍️ 시험 포인트

- **"고가용성 / 단일 데이터센터 장애 대비"** → **여러 AZ에 분산**. (단일 리전·단일 AZ는 오답)
- **"리전 vs AZ"**: 리전 = 격리된 지리적 영역, AZ = 리전 *안의* 격리된 위치. 리소스는 **리전 간 자동 복제 안 됨**.
- **"데이터를 특정 국가에 보관(규제)"** → **리전 선택**(데이터 주권). "광역 재해 대비" → **멀티 리전**(DR).
- **CloudFront** = CDN, *콘텐츠 캐싱*(웹/이미지). **Global Accelerator** = *고정 IP + 글로벌 네트워크 라우팅*(TCP/UDP, 캐싱 아님).
- **엣지 로케이션** = 사용자 가까이 캐시/전달하는 거점(리전·AZ와 별개 망).
- **Local Zones** = 특정 대도시 근접 저지연 · **Wavelength** = 5G 초저지연 · **Outposts** = 온프레미스에 AWS.

## ⚠️ 흔한 함정

1. **"고가용성을 위해 한 AZ에 인스턴스를 여러 개 띄운다."** → ❌. 같은 AZ 안 다중화는 *그 AZ 장애*에 무력. **여러 AZ에 분산**해야 단일 위치 장애를 견딤.
2. **"리전을 바꾸면 리소스가 자동으로 따라온다."** → ❌. 리전은 격리돼 있고 **리소스는 리전 간 자동 복제되지 않습니다.** 복제는 직접 구성.
3. **"CloudFront와 Global Accelerator는 같은 것이다."** → ❌. CloudFront는 *콘텐츠 캐싱(CDN)*, Global Accelerator는 *고정 IP로 경로 최적화(라우팅, 캐싱 안 함)*.
4. **"엣지 로케이션에서 EC2 인스턴스를 실행한다."** → ❌. 엣지 로케이션은 주로 *콘텐츠 캐시/전달*용. 사용자 근처에서 *컴퓨팅*을 돌리려면 **Local Zones/Wavelength/Outposts**.
5. **"AZ 하나가 곧 데이터센터 하나다."** → ⚠️ 부정확. AZ는 **하나 이상의 데이터센터**로 구성된 격리된 위치입니다.
6. **"멀티 AZ면 재해 복구(DR)까지 끝난다."** → ⚠️ 부분적. 멀티 AZ는 *리전 내* 고가용성. *리전 전체* 광역 재해 대비는 **멀티 리전**.

## 🧪 자가 점검

> 아래는 학습용 자가 점검입니다. (정식 검증 문항은 `t3-2.questions.json` 참조)

**Q1.** 단일 데이터센터(위치) 장애에도 애플리케이션이 계속 동작하게 하려면, 같은 리전 안에서 무엇을 해야 하나요?

<details><summary>정답 보기</summary>

**여러 가용 영역(AZ)에 인스턴스를 분산**합니다. AZ는 서로 격리돼 있어 한 AZ가 실패해도 다른 AZ의 인스턴스가 요청을 처리할 수 있습니다(고가용성의 기본 공식).
</details>

**Q2.** "데이터를 특정 국가 영토 안에만 보관해야 한다"는 규제 요건은 무엇을 선택해 충족하나요? 그리고 리소스는 리전 간에 자동 복제되나요?

<details><summary>정답 보기</summary>

해당 국가의 **리전을 선택**해 그 안에 리소스를 둡니다(데이터 주권). 리전은 서로 격리돼 있고 **리소스는 리전 간에 자동 복제되지 않습니다** — 복제가 필요하면 직접 구성합니다.
</details>

**Q3.** 전 세계 사용자에게 이미지·웹 콘텐츠를 낮은 지연으로 전달하려면? 그리고 고정 IP로 TCP/UDP 트래픽을 가장 가까운 리전 엔드포인트로 라우팅하려면?

<details><summary>정답 보기</summary>

전자는 **Amazon CloudFront**(CDN — 엣지 로케이션에 콘텐츠 캐시). 후자는 **AWS Global Accelerator**(고정 애니캐스트 IP + AWS 글로벌 네트워크 라우팅, 캐싱 아님).
</details>

**Q4.** 특정 대도시 사용자에게 매우 낮은 지연(저지연)이 필요하면 무엇을 쓰고, 통신사 5G 망 엣지에서 초저지연이 필요하면 무엇을 쓰나요?

<details><summary>정답 보기</summary>

전자는 **AWS Local Zones**(인구 밀집지 근접 배치), 후자는 **AWS Wavelength**(5G 네트워크 엣지). 온프레미스 데이터센터 안에 AWS가 필요하면 **AWS Outposts**입니다.
</details>
