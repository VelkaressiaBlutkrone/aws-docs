# 스토리지 서비스 (객체·블록·파일)

- 도메인 3(34%)에서 스토리지는 **"어디에 저장하지?"**를 묻는 핵심 영역입니다. 시험은 *상황*을 주고 **S3(객체) · EBS(블록) · EFS(파일)** 중 고르게 합니다 — 이 셋의 구분이 절반입니다.
- 두 번째 축은 **S3 안에서의 비용 최적화**입니다: 자주 안 쓰는 데이터를 더 싼 클래스(IA·Glacier)로, *접근 패턴을 모르면* Intelligent-Tiering으로 — 이걸 **수명 주기**로 자동화합니다.
- "온프레미스와 연결"(Storage Gateway), "여러 서비스를 한곳에서 백업"(AWS Backup) 같은 키워드도 단골입니다.

## 📖 핵심 개념

### 1) 세 가지 스토리지 유형 — 객체 vs 블록 vs 파일 (★ 시험 핵심)

| 유형 | 서비스 | 비유 | 접근 방식 | 대표 용도 |
|---|---|---|---|---|
| **객체(Object)** | **Amazon S3** | 무한 확장 사물함(키 → 객체) | HTTP/REST API | 정적 파일·백업·아카이브·데이터 레이크·웹 콘텐츠 |
| **블록(Block)** | **Amazon EBS** | 가상 하드디스크 | EC2 인스턴스에 *연결(마운트)* | OS 부팅 볼륨, 데이터베이스, 앱의 디스크 |
| **파일(File)** | **Amazon EFS / FSx** | 네트워크 공유 폴더 | 여러 인스턴스가 *동시* 마운트(NFS 등) | 여러 서버가 공유하는 파일 시스템 |

> 한 문장 구분: **S3 = 인터넷으로 접근하는 객체 저장소. EBS = 한 EC2에 붙는 디스크. EFS = 여러 EC2가 같이 쓰는 공유 폴더.**

### 2) Amazon S3 — 객체 스토리지의 표준

**Amazon S3(Simple Storage Service)**는 **업계 최고 수준의 확장성·가용성·보안·성능**을 제공하는 **객체 스토리지** 서비스입니다.

- 데이터를 **버킷(bucket)** 안에 **객체(object)**로 저장합니다. 객체는 *파일 + 메타데이터*, 버킷은 *객체의 컨테이너*.
- **99.999999999%(eleven 9's) 내구성**으로 설계 — 사실상 데이터를 잃지 않도록.
- 용도: **데이터 레이크, 웹사이트, 백업·복원, 아카이브, 빅데이터 분석** 등.
- **기본은 private** — 명시적으로 권한을 줘야 접근 가능([공동 책임 모델](#): 공개 설정 실수는 고객 책임).
- **사용한 만큼만 과금**(미리 용량 구매 불필요).

#### S3 스토리지 클래스 — 접근 빈도 ↔ 비용 트레이드오프

같은 S3라도 *얼마나 자주 쓰는지*에 따라 클래스를 골라 비용을 최적화합니다. **모든 클래스가 동일한 11 nines 내구성**으로 설계됩니다(가용성·비용·검색 방식이 다름).

| 클래스 | 언제 |
|---|---|
| **S3 Standard** | 자주 접근하는 데이터(기본값) |
| **S3 Intelligent-Tiering** | **접근 패턴을 모르거나 변동**할 때 — 자동으로 계층 이동(검색 수수료 없음) |
| **S3 Standard-IA / One Zone-IA** | 가끔 접근(밀리초 접근, 검색 수수료). One Zone-IA는 *단일 AZ*라 더 싸지만 AZ 손실에 취약 |
| **S3 Glacier Instant Retrieval** | 분기 1회 수준, 즉시(밀리초) 검색 필요한 아카이브 |
| **S3 Glacier Flexible Retrieval** | 연 1회 수준, 분~시간 검색 허용 아카이브 |
| **S3 Glacier Deep Archive** | 연 1회 미만, **최저 비용**, 시간 단위 검색 — 장기 보관 |

> 시험 신호: **"접근 패턴을 모른다/변한다"** → **Intelligent-Tiering**. **"거의 안 보고 가장 싸게 장기 보관"** → **Glacier Deep Archive**.

#### S3 수명 주기(Lifecycle)
**수명 주기 구성**으로 객체를 시간에 따라 **자동으로 더 싼 클래스로 전환**하거나 **만료(삭제)**시켜 비용을 최적화합니다. (예: 업로드 시 Standard → 30일 후 Standard-IA → 1년 후 Glacier)

### 3) Amazon EBS — EC2에 붙는 블록 디스크

**Amazon EBS(Elastic Block Store)**는 **EC2 인스턴스와 함께 쓰는 블록 스토리지 볼륨**을 제공합니다.

- **EBS 볼륨을 인스턴스에 연결**하면 로컬 하드드라이브처럼 파일 저장·앱 설치에 씁니다.
- 볼륨 데이터는 **한 가용 영역(AZ) 안에서 여러 서버에 자동 복제**돼 단일 컴포넌트 장애로부터 보호됩니다. (볼륨은 한 AZ에 존재)
- **EBS 스냅샷** = 볼륨의 *시점 백업*으로, 볼륨과 **독립적으로** 보존됩니다. 스냅샷으로 다른 AZ·리전·계정으로 복원·이동 가능.
- 유형: SSD(트랜잭션)·HDD(처리량) 기반으로 성능·비용 최적화.

> **EBS vs 인스턴스 스토어(Instance Store)** (단골 함정): **EBS = 영속적**(인스턴스를 중지·종료해도 데이터 유지). **인스턴스 스토어 = 임시**(인스턴스를 중지·최대절전·종료하면 데이터 삭제). 영속 데이터는 EBS.

### 4) Amazon EFS / FSx — 여러 서버가 공유하는 파일 시스템

**Amazon EFS(Elastic File System)**는 **서버리스·완전 탄력적 공유 파일 스토리지**입니다.

- 용량·성능을 **프로비저닝·관리하지 않고** 파일을 공유. 파일이 늘고 줄 때 **자동으로 확장·축소**(페타바이트 규모).
- **여러 컴퓨트(EC2·ECS·EKS·Lambda·Fargate)에서 동시에 마운트**해 같은 파일을 공유합니다(**NFS** 프로토콜).
- **Regional**(여러 AZ에 중복 저장, 권장) 또는 **One Zone**(단일 AZ) 유형.
- ⚠️ **Linux 기반** 워크로드용 — **Windows EC2는 미지원**.

> **Windows 파일 공유나 고성능 컴퓨팅(HPC)이 필요하면 Amazon FSx**(FSx for Windows File Server, FSx for Lustre 등)를 씁니다.

### 5) 하이브리드와 백업 — Storage Gateway · AWS Backup

**AWS Storage Gateway** — **하이브리드 클라우드 스토리지**.
- **온프레미스 환경/애플리케이션을 AWS 클라우드 스토리지에 연결**합니다. **로컬 캐싱**으로 저지연 접근을 유지하면서 데이터는 AWS에 저장.
- 유형: **S3 File Gateway, FSx File Gateway, Tape Gateway(가상 테이프 아카이브), Volume Gateway(블록)**.
- 키워드: **"온프레미스 ↔ AWS 스토리지 연결", "하이브리드"**.

**AWS Backup** — **중앙화·자동화 백업**.
- **여러 AWS 서비스(EBS·RDS·DynamoDB·EFS·S3 등)의 백업을 한곳에서** 정책(**백업 플랜**)으로 자동화·관리합니다.
- 서비스별로 따로 만들던 스크립트·수동 작업을 없애고, 백업 활동을 *중앙에서 감사*합니다. 크로스 리전·크로스 계정 백업, Vault Lock(WORM)도 지원.
- 키워드: **"여러 서비스 백업을 한곳에서 중앙 관리·자동화"**.

## ✍️ 시험 포인트

- **객체 = S3 / 블록 = EBS / 파일(공유) = EFS.** "여러 EC2가 *동시에* 같은 파일을" → **EFS**. "한 EC2의 디스크" → **EBS**. "인터넷으로 접근하는 파일·백업·정적 호스팅" → **S3**.
- **S3 11 nines 내구성**, 기본 private, 사용한 만큼 과금.
- **접근 패턴 모름/변동 → S3 Intelligent-Tiering.** **거의 안 보는 최저가 장기 보관 → S3 Glacier Deep Archive.**
- **S3 Lifecycle** = 시간에 따라 더 싼 클래스로 자동 전환/만료(비용 최적화).
- **EBS = 영속(단일 AZ, 스냅샷으로 백업), 인스턴스 스토어 = 임시.**
- **EFS = Linux 공유 파일**, Windows 공유는 **FSx for Windows File Server**.
- **Storage Gateway = 하이브리드(온프레-클라우드)**, **AWS Backup = 여러 서비스 중앙 백업**.

---

## ⚠️ 흔한 함정

1. **"여러 EC2가 같은 데이터를 동시에 쓰려면 EBS를 공유한다."** → ❌. 일반 EBS 볼륨은 보통 *한 인스턴스*에 붙습니다. *여러 서버 동시 공유*는 **EFS**(파일).
2. **"인스턴스 스토어에 중요한 데이터를 저장한다."** → ❌. 인스턴스 스토어는 *임시* — 인스턴스를 중지·종료하면 사라집니다. 영속 데이터는 **EBS**나 **S3**.
3. **"자주 안 쓰는 데이터도 S3 Standard에 둔다."** → ⚠️ 비효율. **IA·Glacier**로 옮기거나 **Lifecycle**로 자동 전환해 비용을 낮춥니다.
4. **"S3 Glacier는 S3와 별개 서비스라 따로 옮겨야 한다."** → ❌. Glacier는 **S3의 스토리지 클래스**입니다(객체는 S3에 그대로 있음).
5. **"EFS로 Windows 서버 파일 공유를 한다."** → ❌. EFS는 *Linux*용. Windows 파일 공유는 **FSx for Windows File Server**.
6. **"백업하려면 서비스마다 따로 스크립트를 짠다."** → ⚠️ 비효율. **AWS Backup**으로 여러 서비스 백업을 *중앙에서* 정책으로 자동화합니다.

**Q1.** 여러 EC2 인스턴스가 *동시에* 같은 파일 시스템을 마운트해 공유해야 합니다. 객체(S3)·블록(EBS)·파일(EFS) 중 무엇인가요?

<details><summary>정답 보기</summary>

**Amazon EFS**(파일 스토리지). 여러 컴퓨트가 동시에 마운트해 같은 파일을 공유합니다(NFS). EBS는 보통 한 인스턴스에, S3는 객체를 HTTP로 접근합니다.
</details>

**Q2.** 거의 접근하지 않는 데이터를 가장 낮은 비용으로 장기 보관하려 합니다. 그리고 접근 패턴을 전혀 예측할 수 없는 데이터는?

<details><summary>정답 보기</summary>

거의 안 보는 최저가 장기 보관은 **S3 Glacier Deep Archive**. 접근 패턴을 모르거나 변동하면 **S3 Intelligent-Tiering**(자동으로 계층을 옮겨 비용 최적화)입니다.
</details>

**Q3.** EBS 볼륨과 인스턴스 스토어(instance store)의 가장 큰 차이는?

<details><summary>정답 보기</summary>

**EBS는 영속적**입니다 — 인스턴스를 중지·종료해도 데이터가 유지되고 스냅샷으로 백업할 수 있습니다. **인스턴스 스토어는 임시**라 인스턴스를 중지·종료하면 데이터가 사라집니다.
</details>

**Q4.** 온프레미스 애플리케이션을 AWS 클라우드 스토리지에 연결하면서 로컬 캐싱으로 저지연 접근을 유지하려면? 그리고 EBS·RDS·DynamoDB 백업을 한곳에서 자동화하려면?

<details><summary>정답 보기</summary>

하이브리드 연결은 **AWS Storage Gateway**. 여러 서비스의 백업을 중앙에서 정책으로 자동화·관리하는 것은 **AWS Backup**입니다.
</details>
