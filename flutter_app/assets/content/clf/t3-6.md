## 🔤 먼저 알아야 할 용어

이 문서를 읽는 데 필요한 기초 용어입니다. 이미 알면 건너뛰세요.

| 용어 | 영문 | 한 줄 풀이 |
|---|---|---|
| **마운트** | Mount | 스토리지 볼륨이나 파일 시스템을 *운영체제에 연결해 디렉터리처럼 접근할 수 있게 하는 과정* — EBS는 EC2에 마운트해 로컬 디스크처럼, EFS는 여러 인스턴스에 동시에 마운트합니다 |
| **내구성** | Durability | 저장한 데이터가 *시간이 지나도 손실되지 않을 확률* — S3의 11 nines 내구성은 1,000만 개 객체 중 1개 미만의 손실 가능성을 뜻합니다 |
| **프로비저닝** | Provisioning | 서비스를 사용하기 전에 *용량·성능을 미리 할당하고 설정하는 작업* — EFS는 이 과정 없이 자동으로 확장·축소됩니다 |
| **아카이브** | Archive | 자주 접근하지 않지만 *장기간 보존해야 하는 데이터를 저렴한 스토리지에 옮겨 보관*하는 것 — S3 Glacier 클래스가 이 용도를 위해 설계됐습니다 |
| **NFS** | Network File System | 네트워크를 통해 *원격 파일 시스템을 로컬 폴더처럼 마운트*할 수 있게 하는 표준 프로토콜 — EFS가 이 방식으로 여러 컴퓨트에 공유됩니다 |
| **WORM** | Write Once Read Many | 한 번 쓴 데이터를 *수정하거나 삭제하지 못하도록 잠그는 정책* — AWS Backup의 Vault Lock이 이 방식으로 백업 데이터의 변조를 방지합니다 |

## 📖 핵심 개념

### 1) 세 가지 스토리지 유형 — 객체 vs 블록 vs 파일 (★ 시험 핵심)

| 유형 | 서비스 | 비유 | 접근 방식 | 대표 용도 |
|---|---|---|---|---|
| **객체(Object)** | **Amazon S3** | 무한 확장 사물함(키 → 객체) | HTTP/REST API | 정적 파일·백업·아카이브·데이터 레이크·웹 콘텐츠 |
| **블록(Block)** | **Amazon EBS** | 가상 하드디스크 | EC2 인스턴스에 *연결(마운트)* | OS 부팅 볼륨, 데이터베이스, 앱의 디스크 |
| **파일(File)** | **Amazon EFS / FSx** | 네트워크 공유 폴더 | 여러 인스턴스가 *동시* 마운트(NFS 등) | 여러 서버가 공유하는 파일 시스템 |

> 한 문장 구분: **S3 = 인터넷으로 접근하는 객체 저장소. EBS = 한 EC2에 붙는 디스크. EFS = 여러 EC2가 같이 쓰는 공유 폴더.**

> 🧠 원리: 왜 AWS는 하나의 스토리지 서비스로 모든 용도를 통합하지 않고, 객체·블록·파일 세 유형을 별도 서비스로 제공할까요?
> 각 유형은 데이터에 접근하는 방식과 그에 따른 성능 최적화 방향이 근본적으로 다릅니다. 블록 스토리지는 OS가 섹터 단위로 직접 읽고 쓰므로 낮은 지연시간을 위해 전용 프로토콜과 캐시 전략이 필요하고, 파일 시스템은 동시 접근 일관성을 위해 디렉터리 잠금(locking) 관리가 필요합니다.
> 객체 스토리지는 잠금 없이 키 하나에 데이터를 통째로 저장·조회하므로 수평 확장과 인터넷 접근에 최적화할 수 있지만, 그 대신 부분 수정이나 파일 잠금을 지원할 수 없습니다.
> 각 방식을 단일 서비스로 통합하면 어느 쪽 워크로드에도 최적이 아닌 중간값이 되므로, 용도별로 분리해 각각을 최적화한 서비스를 두는 것이 가능합니다.

### 2) Amazon S3 — 객체 스토리지의 표준

**Amazon S3(Simple Storage Service)**는 **업계 최고 수준의 확장성·가용성·보안·성능**을 제공하는 **객체 스토리지** 서비스입니다.

- 데이터를 **버킷(bucket)** 안에 **객체(object)**로 저장합니다. 객체는 *파일 + 메타데이터*, 버킷은 *객체의 컨테이너*.
- **99.999999999%(eleven 9's) 내구성**으로 설계 — 사실상 데이터를 잃지 않도록.
- 용도: **데이터 레이크, 웹사이트, 백업·복원, 아카이브, 빅데이터 분석** 등.
- **기본은 private** — 명시적으로 권한을 줘야 접근 가능([공동 책임 모델](#): 공개 설정 실수는 고객 책임).
- **사용한 만큼만 과금**(미리 용량 구매 불필요).

#### S3 스토리지 클래스 — 접근 빈도 ↔ 비용 트레이드오프

같은 S3라도 *얼마나 자주 쓰는지*에 따라 클래스를 골라 비용을 최적화합니다. **모든 클래스가 동일한 11 nines 내구성**으로 설계됩니다(가용성·비용·검색 방식이 다름).

| 클래스 | 언제 |
|---|---|
| **S3 Standard** | 자주 접근하는 데이터(기본값) |
| **S3 Intelligent-Tiering** | **접근 패턴을 모르거나 변동**할 때 — 자동으로 계층 이동(검색 수수료 없음) |
| **S3 Standard-IA / One Zone-IA** | 가끔 접근(밀리초 접근, 검색 수수료). One Zone-IA는 *단일 AZ*라 더 싸지만 AZ 손실에 취약 |
| **S3 Glacier Instant Retrieval** | 분기 1회 수준, 즉시(밀리초) 검색 필요한 아카이브 |
| **S3 Glacier Flexible Retrieval** | 연 1회 수준, 분~시간 검색 허용 아카이브 |
| **S3 Glacier Deep Archive** | 연 1회 미만, **최저 비용**, 시간 단위 검색 — 장기 보관 |

> 시험 신호: **"접근 패턴을 모른다/변한다"** → **Intelligent-Tiering**. **"거의 안 보고 가장 싸게 장기 보관"** → **Glacier Deep Archive**.

> 🧠 원리: 왜 S3 Intelligent-Tiering은 접근 패턴을 모를 때 유리하고, 패턴이 명확할 때는 오히려 비효율적일 수 있을까요?
> Intelligent-Tiering은 객체의 접근 이력을 모니터링해 자동으로 계층을 이동시키는데, 이 모니터링에 객체당 소량의 관리 비용이 발생합니다.
> 접근 패턴이 예측 가능하다면 수명 주기 정책으로 직접 클래스를 지정하는 것이 모니터링 비용 없이 동일한 비용 최적화를 달성할 수 있습니다.
> 패턴이 불규칙하거나 예측할 수 없는 데이터에서는 자동 계층 이동이 과도한 검색 수수료를 줄여 주기 때문에, Intelligent-Tiering이 수동 클래스 선택보다 유리합니다.

> 🧠 원리: 왜 S3는 하나의 고정된 스토리지 계층 대신 접근 빈도에 따라 선택하는 여러 클래스를 두었을까요?
> 데이터는 생성 직후에는 자주 조회되다가 시간이 지나면 거의 접근하지 않는 패턴을 보이는 경우가 많은데, 모든 데이터를 동일한 빠른 스토리지에 두면 드물게 읽히는 오래된 데이터도 높은 비용을 지불하게 됩니다.
> S3는 동일한 11 nines 내구성을 유지하면서 가용성·검색 지연·비용만 다른 클래스를 두어, 접근 빈도가 낮을수록 더 낮은 비용의 클래스를 선택할 수 있게 합니다.
> 이 구조 덕분에 수명 주기 정책으로 객체를 자동으로 더 싼 클래스로 이동시켜, 접근 패턴에 맞춰 비용을 최적화하는 것이 가능합니다.

#### S3 수명 주기(Lifecycle)
**수명 주기 구성**으로 객체를 시간에 따라 **자동으로 더 싼 클래스로 전환**하거나 **만료(삭제)**시켜 비용을 최적화합니다. (예: 업로드 시 Standard → 30일 후 Standard-IA → 1년 후 Glacier)

> 🧠 원리: 왜 S3 수명 주기는 객체를 바로 삭제하지 않고 단계적으로 더 싼 클래스로 옮긴 뒤 만료시키는 방식을 선택할까요?
> 규정·감사 등의 이유로 데이터를 즉시 삭제할 수 없고 일정 기간 보존해야 하는 경우가 많아, 바로 삭제하는 단일 정책만으로는 이 요구를 충족하기 어렵습니다.
> 클래스를 단계적으로 내리면 보존 의무 기간 동안에도 가장 낮은 비용으로 데이터를 유지할 수 있고, 보존 기간이 끝난 시점에 만료(삭제) 규칙을 적용해 스토리지 비용을 정리하는 것이 가능합니다.
> 전환과 만료 규칙을 조합하면 "얼마나 자주 접근하는가"와 "얼마나 보존해야 하는가"라는 두 기준을 동시에 자동화된 정책으로 다루는 것이 가능합니다.

### 3) Amazon EBS — EC2에 붙는 블록 디스크

**Amazon EBS(Elastic Block Store)**는 **EC2 인스턴스와 함께 쓰는 블록 스토리지 볼륨**을 제공합니다.

- **EBS 볼륨을 인스턴스에 연결**하면 로컬 하드드라이브처럼 파일 저장·앱 설치에 씁니다.
- 볼륨 데이터는 **한 가용 영역(AZ) 안에서 여러 서버에 자동 복제**돼 단일 컴포넌트 장애로부터 보호됩니다. (볼륨은 한 AZ에 존재)
- **EBS 스냅샷** = 볼륨의 *시점 백업*으로, 볼륨과 **독립적으로** 보존됩니다. 스냅샷으로 다른 AZ·리전·계정으로 복원·이동 가능.
- 유형: SSD(트랜잭션)·HDD(처리량) 기반으로 성능·비용 최적화.

> **EBS vs 인스턴스 스토어(Instance Store)** (단골 함정): **EBS = 영속적**(인스턴스를 중지·종료해도 데이터 유지). **인스턴스 스토어 = 임시**(인스턴스를 중지·최대절전·종료하면 데이터 삭제). 영속 데이터는 EBS.

> 🧠 원리: 왜 EBS 볼륨은 스냅샷을 볼륨과 별도로 S3에 저장하는 방식으로 백업을 설계할까요?
> EBS 볼륨은 특정 AZ 안에 존재해 그 AZ 내 장애로부터는 자동 복제로 보호되지만, AZ 전체가 영향을 받는 상황이나 다른 리전·계정으로 데이터를 이전해야 할 때는 볼륨 자체만으로는 범위를 벗어나지 못합니다.
> 스냅샷을 볼륨과 독립적으로 S3에 저장하면 볼륨의 가용 영역 경계에 묶이지 않아, 스냅샷을 다른 AZ·리전·계정에서 복원해 볼륨을 생성하는 것이 가능합니다.
> 이렇게 스냅샷이 볼륨 생명 주기와 분리되어야, 인스턴스를 종료한 뒤에도 데이터를 보존하거나 재해 복구 목적으로 다른 위치에 복원하는 경로가 만들어집니다.

### 4) Amazon EFS / FSx — 여러 서버가 공유하는 파일 시스템

**Amazon EFS(Elastic File System)**는 **서버리스·완전 탄력적 공유 파일 스토리지**입니다.

- 용량·성능을 **프로비저닝·관리하지 않고** 파일을 공유. 파일이 늘고 줄 때 **자동으로 확장·축소**(페타바이트 규모).
- **여러 컴퓨트(EC2·ECS·EKS·Lambda·Fargate)에서 동시에 마운트**해 같은 파일을 공유합니다(**NFS** 프로토콜).
- **Regional**(여러 AZ에 중복 저장, 권장) 또는 **One Zone**(단일 AZ) 유형.
- ⚠️ **Linux 기반** 워크로드용 — **Windows EC2는 미지원**.

> **Windows 파일 공유나 고성능 컴퓨팅(HPC)이 필요하면 Amazon FSx**(FSx for Windows File Server, FSx for Lustre 등)를 씁니다.

> 🧠 원리: 왜 EFS는 미리 용량을 프로비저닝하지 않고 자동으로 확장·축소되는 서버리스 방식을 선택했을까요?
> 여러 서버가 동시에 마운트하는 공유 파일 시스템은 접속하는 컴퓨트 수와 워크로드에 따라 사용량이 예측하기 어렵게 변동되는 경우가 많습니다.
> 미리 용량을 예약하면 피크 수요를 기준으로 프로비저닝해야 하므로 평소에는 비용이 낭비되고, 예측이 빗나가면 용량 부족이 발생합니다.
> 파일이 추가·삭제될 때 스토리지가 자동으로 확장·축소되면 실제 사용량에 대해서만 비용이 발생하고, 용량 계획 없이 페타바이트 규모까지 늘어나는 것이 가능합니다.

### 5) 하이브리드와 백업 — Storage Gateway · AWS Backup

**AWS Storage Gateway** — **하이브리드 클라우드 스토리지**.
- **온프레미스 환경/애플리케이션을 AWS 클라우드 스토리지에 연결**합니다. **로컬 캐싱**으로 저지연 접근을 유지하면서 데이터는 AWS에 저장.
- 유형: **S3 File Gateway, FSx File Gateway, Tape Gateway(가상 테이프 아카이브), Volume Gateway(블록)**.
- 키워드: **"온프레미스 ↔ AWS 스토리지 연결", "하이브리드"**.

**AWS Backup** — **중앙화·자동화 백업**.
- **여러 AWS 서비스(EBS·RDS·DynamoDB·EFS·S3 등)의 백업을 한곳에서** 정책(**백업 플랜**)으로 자동화·관리합니다.
- 서비스별로 따로 만들던 스크립트·수동 작업을 없애고, 백업 활동을 *중앙에서 감사*합니다. 크로스 리전·크로스 계정 백업, Vault Lock(WORM)도 지원.
- 키워드: **"여러 서비스 백업을 한곳에서 중앙 관리·자동화"**.

> 🧠 원리: 왜 Storage Gateway는 온프레미스 데이터를 AWS로 직접 이전하는 대신 로컬 캐싱을 유지하면서 클라우드에 저장하는 방식을 선택할까요?
> 온프레미스 애플리케이션은 로컬 파일 시스템이나 NAS에 접근하는 방식으로 개발돼 있어, 모든 데이터를 먼저 AWS로 이전한 뒤에야 클라우드 스토리지를 쓸 수 있다면 전환 비용과 운영 중단이 큽니다.
> 로컬 캐시는 자주 접근하는 데이터를 온프레미스 쪽에 두어 기존 애플리케이션이 지연시간을 느끼지 않도록 하고, 실제 영구 저장은 AWS 클라우드 스토리지(S3·FSx 등)에서 이루어집니다.
> 이 방식으로 기존 온프레미스 워크로드를 수정하지 않고도 점진적으로 클라우드 스토리지를 활용하는 하이브리드 운영이 가능합니다.

## ✍️ 시험 포인트

- **객체 = S3 / 블록 = EBS / 파일(공유) = EFS.** "여러 EC2가 *동시에* 같은 파일을" → **EFS**. "한 EC2의 디스크" → **EBS**. "인터넷으로 접근하는 파일·백업·정적 호스팅" → **S3**.
- **S3 11 nines 내구성**, 기본 private, 사용한 만큼 과금.
- **접근 패턴 모름/변동 → S3 Intelligent-Tiering.** **거의 안 보는 최저가 장기 보관 → S3 Glacier Deep Archive.**
- **S3 Lifecycle** = 시간에 따라 더 싼 클래스로 자동 전환/만료(비용 최적화).
- **EBS = 영속(단일 AZ, 스냅샷으로 백업), 인스턴스 스토어 = 임시.**
- **EFS = Linux 공유 파일**, Windows 공유는 **FSx for Windows File Server**.
- **Storage Gateway = 하이브리드(온프레-클라우드)**, **AWS Backup = 여러 서비스 중앙 백업**.

## ⚠️ 흔한 함정

1. **"여러 EC2가 같은 데이터를 동시에 쓰려면 EBS를 공유한다."** → ❌. 일반 EBS 볼륨은 보통 *한 인스턴스*에 붙습니다. *여러 서버 동시 공유*는 **EFS**(파일).
   *(원리: §4 — EFS는 NFS 프로토콜로 여러 컴퓨트에서 동시에 마운트해 같은 파일을 공유하도록 설계된 파일 스토리지이며, 블록 볼륨인 EBS와 접근 모델이 다르다.)*
2. **"인스턴스 스토어에 중요한 데이터를 저장한다."** → ❌. 인스턴스 스토어는 *임시* — 인스턴스를 중지·종료하면 사라집니다. 영속 데이터는 **EBS**나 **S3**.
   *(원리: §3 — EBS는 인스턴스 생명 주기와 독립적으로 데이터를 유지하는 영속 블록 스토리지인 반면, 인스턴스 스토어는 호스트에 물리적으로 붙어 인스턴스가 멈추면 데이터가 사라지는 임시 저장소다.)*
3. **"자주 안 쓰는 데이터도 S3 Standard에 둔다."** → ⚠️ 비효율. **IA·Glacier**로 옮기거나 **Lifecycle**로 자동 전환해 비용을 낮춥니다.
   *(원리: §2 — S3는 동일한 내구성을 유지하면서 접근 빈도에 따라 가용성·비용이 다른 클래스를 두어, 드물게 접근하는 데이터는 더 낮은 비용의 IA·Glacier 클래스로 이동시켜 비용을 최적화하도록 설계됐다.)*
4. **"S3 Glacier는 S3와 별개 서비스라 따로 옮겨야 한다."** → ❌. Glacier는 **S3의 스토리지 클래스**입니다(객체는 S3에 그대로 있음).
   *(원리: §2 — Glacier는 S3 스토리지 클래스 중 하나로, 객체는 동일한 S3 버킷에 존재하며 클래스 전환은 수명 주기 정책으로 자동 처리할 수 있다.)*
5. **"EFS로 Windows 서버 파일 공유를 한다."** → ❌. EFS는 *Linux*용. Windows 파일 공유는 **FSx for Windows File Server**.
   *(원리: §4 — EFS는 Linux 기반 NFS 프로토콜을 사용하므로 Windows EC2는 지원되지 않으며, Windows 파일 공유가 필요하면 SMB 프로토콜을 지원하는 FSx for Windows File Server를 써야 한다.)*
6. **"백업하려면 서비스마다 따로 스크립트를 짠다."** → ⚠️ 비효율. **AWS Backup**으로 여러 서비스 백업을 *중앙에서* 정책으로 자동화합니다.
   *(원리: §5 — AWS Backup은 EBS·RDS·DynamoDB·EFS·S3 등 여러 서비스의 백업을 하나의 백업 플랜으로 통합 관리해, 서비스별 수동 스크립트 없이 중앙에서 정책·감사를 적용할 수 있다.)*

## 🧪 자가 점검

> 아래는 학습용 자가 점검입니다. (정식 검증 문항은 `t3-6.questions.json` 참조)

**Q1.** 여러 EC2 인스턴스가 *동시에* 같은 파일 시스템을 마운트해 공유해야 합니다. 객체(S3)·블록(EBS)·파일(EFS) 중 무엇인가요?

<details><summary>정답 보기</summary>

**Amazon EFS**(파일 스토리지). 여러 컴퓨트가 동시에 마운트해 같은 파일을 공유합니다(NFS). EBS는 보통 한 인스턴스에, S3는 객체를 HTTP로 접근합니다.
</details>

**Q2.** 거의 접근하지 않는 데이터를 가장 낮은 비용으로 장기 보관하려 합니다. 그리고 접근 패턴을 전혀 예측할 수 없는 데이터는?

<details><summary>정답 보기</summary>

거의 안 보는 최저가 장기 보관은 **S3 Glacier Deep Archive**. 접근 패턴을 모르거나 변동하면 **S3 Intelligent-Tiering**(자동으로 계층을 옮겨 비용 최적화)입니다.
</details>

**Q3.** EBS 볼륨과 인스턴스 스토어(instance store)의 가장 큰 차이는?

<details><summary>정답 보기</summary>

**EBS는 영속적**입니다 — 인스턴스를 중지·종료해도 데이터가 유지되고 스냅샷으로 백업할 수 있습니다. **인스턴스 스토어는 임시**라 인스턴스를 중지·종료하면 데이터가 사라집니다.
</details>

**Q4.** 온프레미스 애플리케이션을 AWS 클라우드 스토리지에 연결하면서 로컬 캐싱으로 저지연 접근을 유지하려면? 그리고 EBS·RDS·DynamoDB 백업을 한곳에서 자동화하려면?

<details><summary>정답 보기</summary>

하이브리드 연결은 **AWS Storage Gateway**. 여러 서비스의 백업을 중앙에서 정책으로 자동화·관리하는 것은 **AWS Backup**입니다.
</details>

---

**Q5 (원리).** 왜 S3는 파일 시스템처럼 디렉터리 구조를 두는 대신 버킷 안에 키-객체 쌍으로 저장하는 객체 모델을 선택했을까요?

<details><summary>정답 보기</summary>

파일 시스템은 디렉터리 구조와 파일 잠금(locking)을 관리하는 메타데이터 계층이 필요한데, 수십억 개의 객체를 다루는 환경에서는 이 중앙 메타데이터 관리가 확장성의 병목이 됩니다. 객체 모델에서는 키 하나에 데이터 전체를 HTTP API로 저장·조회하고 잠금이 없기 때문에, 요청을 독립적으로 분산 처리할 수 있어 단일 네임스페이스에 수십억 개의 객체를 수평 확장하는 것이 가능합니다. 또한 HTTP 기반 접근은 인터넷을 통해 어디서나 별도 마운트 없이 접근할 수 있어, 정적 파일·백업·데이터 레이크처럼 대규모·글로벌 접근이 필요한 워크로드에 적합한 구조가 됩니다.
</details>
