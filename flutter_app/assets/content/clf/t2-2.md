## 📖 핵심 개념

### 1) 거버넌스 vs 컴플라이언스 — 두 단어를 먼저 가른다

- **거버넌스(Governance):** 내 조직이 클라우드 리소스를 *어떻게 통제·감시·관리*하는가. 규칙을 세우고(정책), 무슨 일이 일어나는지 *가시성*을 확보하는 활동. → CloudTrail·Config·CloudWatch 같은 도구가 여기 쓰입니다.
- **컴플라이언스(Compliance):** 외부의 *규정·표준*(법률, 산업 표준 — 예: PCI DSS, HIPAA, ISO, SOC, GDPR)을 충족함을 *증명*하는 것.

> [공동 책임 모델](#)의 연장: **AWS는 "클라우드 *자체*"의 컴플라이언스**를 제3자 감사로 입증하고(그 증거가 AWS Artifact), **고객은 "클라우드 *안*에서 자신이 쓰는 방식"의 컴플라이언스**를 직접 입증합니다.

> 🧠 원리: 왜 거버넌스와 컴플라이언스는 별개 개념이고, 서로 다른 도구를 필요로 할까요?
> 거버넌스는 *내부 가시성* 확보가 목적입니다 — 지금 리소스가 어떻게 구성돼 있고 누가 무엇을 했는지 알아야 규칙을 집행할 수 있기 때문에, CloudTrail·Config·CloudWatch 같은 관찰 도구가 쓰입니다.
> 컴플라이언스는 *외부 규제 기관 또는 감사자에게 증명*하는 활동이어서, 내부 로그만으로는 부족하고 제3자가 서명한 보고서(Artifact가 제공)나 규정 프레임워크에 매핑된 증거(Audit Manager)가 필요합니다.
> 두 활동은 목적(내부 통제 vs 외부 증명)과 수신자(운영팀 vs 감사자)가 달라서 도구도 분리됩니다.

### 2) 컴플라이언스 증거는 어디서 받나 — AWS Artifact

**AWS Artifact**는 **AWS의 보안·컴플라이언스 문서를 온디맨드로 *다운로드*** 하는 셀프서비스 포털입니다.

- 받을 수 있는 것: **ISO·PCI·SOC 보고서**, 그리고 AWS 보안 통제의 구현·운영 효과를 검증한 **인증서(certifications)**.
- **무료**입니다("free of charge").
- AWS와의 **계약(agreement)**(여러 계정 포함)을 검토·수락·추적하는 것도 Artifact에서 합니다.
- 이 문서들을 *감사자나 규제기관에 제출하는 audit artifact*로 쓸 수 있습니다.

> ⚠️ 주의: Artifact는 **"AWS 인프라가 규정을 지킨다"는 증거를 받는 곳**입니다. *내가 만든* 컴플라이언스 문서는 내가(고객이) 마련해야 합니다(공동 책임).

> **Artifact vs Audit Manager** (단골 비교): **Artifact** = *AWS 인프라*의 컴플라이언스 보고서를 받는 곳(다운로드). **Audit Manager** = *내 AWS 사용*이 규정을 지키는지 **증거를 자동 수집·관리**(감사 준비). 공식 문서 표현: Artifact는 "AWS Cloud infrastructure meets the compliance requirements"를 증명, Audit Manager는 "your usage of AWS services is in compliance"를 입증.

> 🧠 원리: 왜 AWS Artifact는 "다운로드"만 제공하고 고객의 컴플라이언스를 직접 입증하지 않을까요?
> Artifact가 담고 있는 보고서는 AWS 인프라에 대한 제3자 감사 결과입니다 — AWS가 물리 데이터센터·가상화 계층을 어떻게 운영하는지 독립 감사기관이 검증한 문서입니다.
> 그런데 고객이 그 인프라 위에서 *어떻게 서비스를 구성하고 데이터를 다루는지*는 AWS가 알 수 없으므로, 그 영역의 컴플라이언스 증명은 고객 본인이 마련해야 합니다.
> 공동 책임 모델에서 "클라우드 안"의 설정과 데이터가 고객 책임인 것과 같은 이유입니다.

### 3) 탐지 3종 — GuardDuty · Inspector · Macie (★ 시험 핵심 구분)

세 서비스 모두 "보안 문제를 찾아 finding(보고)을 만든다"는 점은 같습니다. 차이는 **무엇을 입력으로 보는가**입니다.

| 서비스 | 한 줄 정체 | 무엇을 분석하나 | 떠올릴 키워드 |
|---|---|---|---|
| **Amazon GuardDuty** | **위협 탐지(threat detection)** | **CloudTrail 관리 이벤트 · VPC 흐름 로그 · DNS 로그**를 ML·위협 인텔리전스로 분석 | "악성·비정상 *활동*", "침해된 자격증명", "크립토마이닝", "위협 탐지" |
| **Amazon Inspector** | **취약점 관리(vulnerability management)** | **EC2 인스턴스 · ECR 컨테이너 이미지 · Lambda 함수**를 스캔(소프트웨어 취약점·CVE, 의도치 않은 네트워크 노출) | "*취약점*", "CVE", "패치 안 된 소프트웨어", "자동 스캔" |
| **Amazon Macie** | **데이터 보안(data security)** | **Amazon S3**의 객체를 ML·패턴 매칭으로 분석해 **민감 데이터(PII 등)**를 발견·분류 | "S3", "민감 데이터", "*PII*", "개인정보 노출" |

> 한 문장 기억법: **GuardDuty는 *나쁜 행동*을, Inspector는 *약한 곳(취약점)*을, Macie는 *민감한 데이터*를 찾는다.**
> - 로그를 보고 "수상한 활동"이면 → **GuardDuty**
> - 워크로드를 스캔해 "이 소프트웨어에 알려진 취약점이 있다"면 → **Inspector**
> - "S3에 신용카드 번호·주민번호가 들어 있나?"면 → **Macie**

> 🧠 원리: 왜 탐지 3종은 하나로 합쳐지지 않고 입력 신호별로 별도 서비스로 나뉘었을까요?
> GuardDuty는 CloudTrail·VPC 흐름 로그·DNS 로그라는 *행동 기록*을 ML과 위협 인텔리전스로 분석하고, Inspector는 EC2·ECR·Lambda의 *소프트웨어 패키지 목록과 네트워크 구성*을 취약점 데이터베이스와 대조하며, Macie는 S3 객체 *내용물*을 패턴 매칭으로 분류합니다.
> 세 서비스는 분석하는 데이터의 형식·출처·판단 기준이 달라, 같은 엔진으로 처리할 수 없는 서로 다른 탐지 문제를 각각 풀고 있습니다.
> 세 신호를 하나의 엔진에 합치면 서로 다른 형식의 데이터를 단일 파이프라인으로 처리해야 해, 각 영역의 탐지 기준을 독립적으로 조정하기 어려워집니다.

### 4) 종합과 보호 — Security Hub(CSPM)와 Shield

**AWS Security Hub**(현재 공식 명칭 **AWS Security Hub CSPM**, Cloud Security Posture Management)는 **여러 곳의 보안 findings를 한곳에 모으는 "집계자"**입니다.

- **GuardDuty·Inspector·Macie** 같은 AWS 서비스 *및* 파트너 제품의 findings를 **표준 형식(ASFF)으로 통합** → *single pane of glass*(단일 화면).
- 동시에 **AWS 모범 사례·산업 표준(FSBP·CIS·PCI DSS·NIST)** 대비 **자동 보안 점검**을 돌려 보안 점수를 매깁니다.

> 시험 신호: **"여러 보안 서비스의 결과를 *한곳에 모아* 본다 / 표준 대비 점검한다"** → Security Hub. (탐지 자체를 *하는* 건 GuardDuty/Inspector/Macie, 그 결과를 *모으는* 건 Security Hub.)

**AWS Shield**는 **DDoS(분산 서비스 거부) 공격으로부터 보호**합니다.

| 구분 | AWS Shield **Standard** | AWS Shield **Advanced** |
|---|---|---|
| 비용 | **무료**(모든 고객에 자동 적용) | **유료**(구독) |
| 보호 | 흔한 볼류메트릭 DDoS(UDP 반사, TCP SYN 플러드 등) 자동 방어 | 추가 탐지·완화, **DDoS 비용 보호**, **24x7 DDoS 대응팀(SRT)** |

> **Shield vs WAF**: **Shield = DDoS(네트워크/전송 계층의 *대량 트래픽* 공격)**. **WAF = 웹 애플리케이션 방화벽**으로 SQL 인젝션·XSS 같은 *애플리케이션 계층(L7)* 요청을 규칙으로 필터. (WAF는 다음 Task [2.4](#)에서 더 자세히.)

> 🧠 원리: 왜 Security Hub는 탐지를 직접 하지 않고 집계 전용으로 설계됐을까요?
> GuardDuty·Inspector·Macie는 각자의 입력 신호·분석 엔진을 가진 전문 탐지 서비스이고, 그 결과를 표준 형식(ASFF)으로 출력합니다.
> Security Hub는 이 표준 출력을 소비해 여러 서비스와 파트너 제품의 findings를 한 화면에 모으고, CIS·FSBP 같은 보안 기준 대비 자동 점검까지 수행하는 역할에 집중합니다.
> 탐지와 집계를 한 서비스에 합치면 새로운 탐지 소스를 추가할 때마다 전체를 변경해야 하므로, 역할을 분리해 확장성을 높인 구조입니다.

### 5) 암호화 — 전송 중 vs 저장 시, 그리고 KMS

클라우드 보안의 큰 이점 하나는 **광범위한 암호화를 쉽게 켤 수 있다는 것**입니다. 암호화는 *데이터가 어디 있느냐*에 따라 둘로 나뉩니다.

| 구분 | 무엇을 보호 | 어떻게 |
|---|---|---|
| **전송 중(in transit)** | *네트워크를 이동하는* 데이터(클라이언트↔서비스, 서비스↔서비스) | **TLS/SSL**(HTTPS) |
| **저장 시(at rest)** | *디스크·스토리지에 저장된* 데이터(S3, EBS, RDS 등) | 스토리지 암호화 + **암호화 키 관리** |

**AWS KMS(Key Management Service)**는 데이터를 암호화하는 데 쓰는 **암호화 키를 생성·제어**하는 관리형 서비스입니다.

- KMS 키는 **FIPS 140-3 보안 레벨 3 검증 HSM**으로 보호되며 **암호화되지 않은 채로 KMS를 떠나지 않습니다.**
- **키 정책(key policy)**으로 누가 키를 쓸 수 있는지 통제합니다.
- S3·EBS·RDS 등 많은 AWS 서비스와 통합되어 *저장 시 암호화*의 키 역할을 합니다.

> 기억: **"무엇을 켤지(암호화 여부)·키를 어떻게 쓸지는 고객, 암호화 *기능과 키 인프라*는 AWS가 제공"**([공동 책임 모델](#)과 동일한 경계).

> 🧠 원리: 왜 KMS 키는 암호화되지 않은 채로 KMS를 떠나지 않을까요?
> 암호화 키가 네트워크나 메모리를 통해 외부에 노출되면, 키를 탈취한 공격자가 그 키로 보호된 모든 데이터를 복호화할 수 있게 됩니다.
> KMS는 FIPS 140-3 레벨 3 검증 HSM 안에서만 키 연산(암호화·복호화·서명)을 수행하고, 평문 키를 HSM 경계 밖으로 내보내지 않음으로써 키 자체의 기밀성을 유지할 수 있습니다.
> 고객이 키를 직접 다룰 필요 없이 "이 데이터를 이 키로 암호화해 달라"는 요청만 보내는 구조여서, 키 노출 위험을 줄일 수 있습니다.

### 6) 거버넌스·감사·모니터링 3종 — CloudTrail · Config · CloudWatch (★ 시험 핵심 구분)

이 셋이 가장 많이 헷갈립니다. **각자 답하는 질문**으로 외우세요.

| 서비스 | 답하는 질문 | 무엇을 기록/측정 | 떠올릴 키워드 |
|---|---|---|---|
| **AWS CloudTrail** | **"*누가* 무엇을 했나?"** | **API 호출·계정 활동**을 이벤트로 기록(사용자·역할·서비스가 콘솔/CLI/SDK로 한 행동) — 누가·언제·어디서·무슨 액션 | "API 호출", "*감사*", "*누가* ~했는가", "활동 기록" |
| **AWS Config** | **"리소스가 *어떻게 구성*돼 있나?"** | 리소스의 **구성 상태와 변경 이력**, 원하는 구성 준수 여부(Config 규칙)를 평가 | "*구성* 변경", "구성 이력", "원하는 설정 준수 평가" |
| **Amazon CloudWatch** | **"*잘 돌아가*나?"** | **메트릭·로그·알람·대시보드** — 성능·운영 상태·리소스 사용률을 실시간 모니터링 | "*모니터링*", "메트릭", "*알람*", "성능·CPU·지연" |

> 한 문장 기억법:
> - **CloudTrail = *누가* 했나(감사 추적)** — "Actions taken by a user, role, or an AWS service are recorded as events."
> - **Config = *어떻게 구성*됐나(구성의 사진첩)** — 시간에 따른 구성 변화를 보고 규정 준수를 평가.
> - **CloudWatch = *잘 작동*하나(성능 모니터)** — 메트릭과 알람.

**AWS Audit Manager**는 위 데이터(CloudTrail·Config·Security Hub 등)를 끌어다 **감사 증거 수집을 자동화**하고, **컴플라이언스 프레임워크(CIS·PCI DSS·GDPR·HIPAA·SOC 2 등)**에 매핑해 **감사 보고서**를 만들어 줍니다.

> ℹ️ 정직성 메모: AWS Audit Manager는 **2024년 이후 *신규 고객 등록을 중단***했습니다(기존 고객은 계속 사용). 다만 **CLF 공식 시험 가이드는 Audit Manager를 거버넌스 서비스로 명시**하고 있어, 시험엔 여전히 "감사 증거 수집 자동화 = Audit Manager"로 등장할 수 있습니다. 개념(증거 수집 자동화 + 프레임워크 매핑)만 기억해 두세요.

> 🧠 원리: 왜 CloudTrail·Config·CloudWatch는 "같은 것을 다르게 보는" 게 아니라, 입력 신호 자체가 달라서 세 서비스로 나뉠까요?
> CloudTrail의 입력은 *API 호출 이벤트*입니다 — 누가 어떤 액션을 취했는지 기록하는 행동 감사 데이터입니다.
> Config의 입력은 *리소스 구성 스냅숏*입니다 — 리소스가 특정 시점에 어떤 속성값을 가지고 있었는지, 그것이 원하는 상태와 일치하는지를 평가하는 상태 데이터입니다.
> CloudWatch의 입력은 *메트릭과 로그*입니다 — CPU·메모리·지연 시간 같은 연속적 성능 수치와 운영 로그로, 시스템이 지금 잘 작동하는지를 판단합니다.
> 입력이 다르면 저장 형식·보존 기간·쿼리 방식도 달라지므로, 질문별로 전용 서비스가 분리된 구조가 각 영역의 기능을 독립적으로 발전시키기 쉽습니다.

## ✍️ 시험 포인트

- **탐지 3종 매칭**: "악성/비정상 *활동*" → GuardDuty · "*취약점*/CVE 스캔(EC2·ECR·Lambda)" → Inspector · "S3의 *민감 데이터*/PII" → Macie.
- **감사 3종 매칭**: "*누가* API를 호출" → CloudTrail · "리소스 *구성* 변경·이력·준수 평가" → Config · "*성능*·메트릭·알람" → CloudWatch.
- **집계** = Security Hub. "여러 보안 서비스의 findings를 한곳에 모아 표준 대비 점검" → Security Hub(CSPM).
- **DDoS** = Shield. 모두에게 **자동·무료**면 Standard, 추가 보호·비용 보호·24x7 대응팀이면 **Advanced**.
- **컴플라이언스 보고서(SOC·PCI·ISO) 다운로드** = **AWS Artifact**(무료). *내 사용*의 감사 증거 자동 수집 = **Audit Manager**.
- **암호화**: 네트워크 이동 중 = *전송 중*(TLS) · 저장 매체 = *저장 시*(at rest) · 암호화 *키 관리* = **KMS**.
- **보안 로그 위치**: API 활동 = CloudTrail, 애플리케이션/시스템 로그 = CloudWatch Logs, 네트워크 흐름 = VPC 흐름 로그.

## ⚠️ 흔한 함정

1. **"GuardDuty가 취약점을 스캔한다."** → ❌. GuardDuty는 *로그를 분석해 위협(나쁜 활동)*을 탐지. 워크로드의 *취약점(CVE)* 스캔은 **Inspector**.
   *(원리: §3 — GuardDuty와 Inspector는 입력 신호(행동 로그 vs 소프트웨어 패키지)와 탐지 기준(위협 패턴 vs CVE 데이터베이스)이 달라 별도 서비스로 분리돼 있다.)*
2. **"S3 민감 데이터 탐지도 GuardDuty."** → ❌. S3의 *민감 데이터/PII* 발견·분류는 **Macie**. (GuardDuty는 위협 활동, Inspector는 취약점.)
   *(원리: §3 — Macie는 S3 객체 내용물을 패턴 매칭으로 분류하는 다른 입력·분석 엔진을 가진 서비스다.)*
3. **"Security Hub(CSPM)가 위협을 직접 탐지한다."** → ❌. Security Hub는 **위협 탐지 서비스가 아니라**, GuardDuty·Inspector·Macie 등의 findings를 **집계**하고 **보안 표준·컨트롤 점검**(자체 findings 생성)을 수행합니다. 위협 활동 탐지 자체는 GuardDuty·Inspector·Macie가 합니다.
   *(원리: §4 — Security Hub는 개별 탐지 서비스의 ASFF 출력을 소비해 집계·표준 대비 자동 점검(자체 findings 생성)까지 수행하는 역할에 집중하며, 탐지와 집계·점검의 책임 축을 분리해 확장성을 높인 구조다.)*
4. **"CloudTrail로 CPU·성능을 모니터링한다."** → ❌. 성능·메트릭·알람은 **CloudWatch**. CloudTrail은 *누가 무슨 API를 호출*했는지(활동 감사).
   *(원리: §6 — CloudTrail의 입력은 API 호출 이벤트(행동)이고, CloudWatch의 입력은 메트릭·로그(성능)여서 다루는 신호 자체가 다르다.)*
5. **"Config는 누가 변경했는지(사람)를 알려준다."** → ⚠️ 혼동 주의. Config는 *무엇이 어떻게 구성됐고 어떻게 바뀌었는지*(구성 상태·이력). *누가 그 API를 호출*했는지는 **CloudTrail**. (둘은 짝으로 자주 함께 쓰임.)
   *(원리: §6 — Config의 입력은 리소스 구성 스냅숏(상태)이고, CloudTrail의 입력은 API 호출 이벤트(행동)여서 "무엇이 바뀌었나"와 "누가 바꿨나"는 다른 신호에서 답한다.)*
6. **"Shield가 SQL 인젝션·XSS를 막는다."** → ❌. 그건 애플리케이션 계층 공격이라 **WAF**. Shield는 *DDoS*(대량 트래픽).
   *(원리: §4 — Shield는 네트워크·전송 계층의 대량 트래픽 공격을 방어하고, L7 요청 내용 필터링은 WAF가 담당하는 별도 책임 축이다.)*
7. **"AWS Artifact에서 내 회사 컴플라이언스 문서를 만들어 준다."** → ❌. Artifact는 *AWS의* 보고서를 *다운로드*하는 곳. 내 컴플라이언스 증명은 내가 마련(Audit Manager가 증거 수집을 도울 수 있음).
   *(원리: §2 — 공동 책임 모델과 같은 이유로, 고객이 클라우드 안에서 어떻게 서비스를 구성했는지는 AWS가 알 수 없어 고객 영역의 컴플라이언스 증명은 고객 몫이다.)*

## 🧪 자가 점검

> 아래는 학습용 자가 점검입니다. (정식 검증 문항은 `t2-2.questions.json` 참조)

**Q1.** "EC2 인스턴스와 컨테이너 이미지에 알려진 *취약점(CVE)*이 있는지 자동으로 스캔"하려면 어떤 서비스인가요? 그리고 "CloudTrail·VPC·DNS 로그를 분석해 *악성 활동*을 탐지"하는 서비스는?

<details><summary>정답 보기</summary>

전자는 **Amazon Inspector**(취약점 관리: EC2·ECR·Lambda 스캔), 후자는 **Amazon GuardDuty**(위협 탐지: 로그 분석). 둘 다 finding을 만들지만 *취약점 vs 활동*으로 갈립니다.
</details>

**Q2.** "누가 언제 어떤 API를 호출했는지" 알고 싶을 때와, "어떤 리소스가 시간에 따라 어떻게 구성·변경됐는지" 알고 싶을 때, 각각 어떤 서비스인가요?

<details><summary>정답 보기</summary>

전자는 **AWS CloudTrail**(API·계정 활동 감사 — *누가 했나*), 후자는 **AWS Config**(리소스 구성 상태·변경 이력 — *어떻게 구성됐나*). 성능·메트릭이면 CloudWatch입니다.
</details>

**Q3.** GuardDuty, Inspector, Macie를 모두 켰습니다. 이 모든 findings를 *한곳에서* 보고 CIS·PCI 같은 표준 대비 점검까지 하려면?

<details><summary>정답 보기</summary>

**AWS Security Hub(CSPM)**. 여러 서비스·파트너 제품의 findings를 표준 형식으로 *집계*하고, 모범 사례·표준 대비 자동 점검과 보안 점수를 제공합니다(single pane of glass). 탐지 자체는 개별 서비스가 합니다.
</details>

**Q4.** 모든 AWS 고객이 *자동·무료로* 받는 DDoS 보호는 무엇이고, 24x7 대응팀과 DDoS 비용 보호가 필요하면 무엇으로 올려야 하나요?

<details><summary>정답 보기</summary>

기본은 **AWS Shield Standard**(자동·무료, 흔한 볼류메트릭 DDoS 방어). 추가 탐지·완화, DDoS 비용 보호, 24x7 DDoS 대응팀(SRT)이 필요하면 **AWS Shield Advanced**(유료).
</details>

---

**Q5 (원리).** 왜 CloudTrail·Config·CloudWatch는 각자 다른 질문에 답하고, 하나로 합칠 수 없나요?

<details><summary>정답 보기</summary>

**세 서비스는 행동(API 호출)·상태(리소스 구성)·성능(메트릭)이라는 서로 다른 입력 신호를 각각 소비하기 때문입니다.** 입력 형식과 분석 목적이 달라 하나의 엔진으로 처리할 수 없고, 하나로 합치면 각 질문에 대한 정밀도를 유지하기 어렵습니다.
</details>
