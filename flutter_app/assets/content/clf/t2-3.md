| 용어 | 영문 | 한 줄 풀이 |
|---|---|---|
| **주체** | principal | IAM에서 *요청을 보낼 수 있는 존재* — 사용자·역할·애플리케이션 등 |
| **장기 자격증명** | long-term credentials | 만료되지 않고 *계속 유효한* 자격증명 — IAM 사용자의 암호·액세스 키 |
| **임시 자격증명** | temporary credentials | *짧은 유효 기간* 후 자동 만료되는 자격증명 — 역할(Role)이 assume될 때 STS가 발급 |
| **페더레이션** | federation | 외부 자격증명 공급자(예: 회사 Active Directory)가 발급한 신원을 *그대로 AWS에서 신뢰*하는 방식 |
| **IdP** | Identity Provider | 사용자 신원을 *발행·관리*하는 외부 시스템 — 회사 디렉터리·Google Workspace 등 |
| **TOTP** | Time-based One-Time Password | 현재 시각을 입력으로 삼아 *30~60초마다 새로운 6자리 코드를 생성*하는 일회용 암호 방식 |
| **FIDO** | Fast IDentity Online | 공개키 암호를 이용해 *서버에 비밀번호를 보내지 않는* 인증 표준 — 피싱에 구조적으로 강함 |

## 📖 핵심 개념

### 1) IAM이란 — 인증과 인가를 책임지는 전역 서비스

**AWS Identity and Access Management(IAM)**는 *누가 인증(sign in)되고 무엇을 할 권한(authorize)이 있는지*를 제어해 AWS 리소스 접근을 안전하게 관리하는 웹 서비스입니다.

- **인증(Authentication):** "너 누구야?" — 로그인 자격증명이 신뢰된 **주체(principal)**와 일치하는지 확인.
- **인가(Authorization):** "그래서 이걸 해도 돼?" — 그 주체가 해당 리소스에 대한 권한을 *정책(policy)*으로 부여받았는지 확인.

> **시험 포인트:** IAM은 **특정 리전에 종속되지 않는 전역(global) 서비스**이며, **추가 비용이 없습니다.** IAM·IAM Identity Center·STS 자체는 무료이고, 그 자격증명으로 *다른* 서비스를 쓸 때만 과금됩니다.

> 🧠 원리: 왜 IAM은 인증과 인가를 하나의 서비스에서 처리할까요?
> 인증(주체 확인)과 인가(허용 행동 판단)는 *순서상 묶인* 과정입니다 — 먼저 누구인지 알아야, 그 신원에 붙은 정책을 조회해 무엇을 허용할지 결정할 수 있습니다.
> 두 단계를 같은 서비스가 처리해야 인증 결과(주체 정보)를 인가 판단에 즉시 전달할 수 있고, 정책 적용을 API 요청마다 일관되게 강제할 수 있습니다.
> 두 단계를 별도 서비스로 나누면 주체 정보를 전달하는 중간 경로가 생겨 추가적인 신뢰 경계가 필요해집니다.

### 2) 자격증명(Identities) — 누가 접근하는가 {#identities}

| 자격증명 | 한 줄 정의 | 핵심 |
|---|---|---|
| **루트 사용자** | 계정 생성 시 만들어지는, **모든 서비스·리소스에 완전 접근**하는 단 하나의 신원 | 일상 사용 금지·강력 보호 대상 |
| **IAM 사용자** | 한 사람 또는 한 애플리케이션을 위한, 특정 권한을 가진 계정 내 신원 | 장기 자격증명(암호·액세스 키) |
| **IAM 그룹** | **IAM 사용자들의 모음.** 그룹에 정책을 붙이면 소속 사용자 전원이 그 권한을 받음 | 권한을 *사람 단위*가 아니라 *역할 단위*로 관리 |
| **IAM 역할(Role)** | 특정 사람에 묶이지 않은, 권한을 가진 신원. **맡아서(assume)** 쓰며 **임시 자격증명** 발급 | 장기 암호·액세스 키 없음 → 더 안전 |
| **페더레이션 사용자** | 외부 자격증명 공급자(IdP)의 기존 신원이 IAM **역할을 맡아** 접근 | 회사 디렉터리·SSO 연동 |

> **정책(Policy)**은 "이 신원이 *어떤 리소스에, 어떤 조건에서, 무슨 행동을* 할 수 있는가"를 정의하는 권한 문서(JSON)입니다. 자격증명에 정책을 붙여 권한이 정해집니다.

> 🧠 원리: 왜 IAM 역할은 장기 자격증명 없이 임시 자격증명을 발급하는 방식을 택했을까요?
> 장기 자격증명(암호·액세스 키)은 유출되더라도 명시적으로 삭제하지 않는 한 계속 유효합니다 — 공격자가 탈취하면 아무 제한 없이 장기간 남용할 수 있습니다.
> 역할의 임시 자격증명은 짧은 유효 기간이 지나면 자동으로 만료되므로, 같은 방식으로 탈취돼도 피해 창이 시간적으로 제한됩니다.
> 이 설계 덕분에 EC2·Lambda 같은 서비스가 역할을 맡아 동작할 때 코드에 키를 하드코딩하지 않아도 됩니다.

### 3) 루트 사용자 — 가장 강력하니 가장 조심해서 {#root-user}

계정을 만들 때 받는 이메일·암호가 곧 **루트 사용자** 자격증명이고, 이 신원은 **계정의 모든 것에 접근**합니다. 그래서 AWS는 *일상 작업에 루트를 쓰지 말라*고 강하게 권고합니다.

**루트 사용자 보호 방법(모범 사례):**
1. **루트에 MFA를 등록·활성화**한다 (가장 강력한 신원이므로 1순위).
2. **일상 작업은 별도의 관리(administrator) 신원**으로 — AWS는 **IAM Identity Center에 관리 사용자**를 만들어 daily 작업을 하라고 권장.
3. **루트 사용자의 액세스 키를 만들지 않는다** (프로그래밍 접근에 루트를 쓰지 말 것).
4. 루트 자격증명을 안전하게 **잠가 보관**하고 꼭 필요한 루트 전용 작업에만 쓴다.

**루트로만 할 수 있는 작업(루트 전용 작업, 일부):**
- **AWS 계정 해지(close account)** — 단독 계정의 경우.
- **계정 설정 변경** — 루트 사용자 이메일·암호·루트 액세스 키 변경(단독 계정).
- **AWS Support 플랜 변경·취소**, **Billing 콘솔에 대한 IAM 접근 활성화**.
- **IAM 사용자 권한 복구** — 유일한 IAM 관리자가 실수로 자기 권한을 박탈했을 때 루트로 복구.
- **Reserved Instance Marketplace 판매자 등록**, **S3 버킷의 MFA Delete 구성** 등.

> 한눈에: **계정 자체에 대한 것·"잠겨버린 상황을 푸는 것"은 루트, 그 외 일상 리소스 작업은 IAM**으로.

> 🧠 원리: 왜 루트 사용자는 일상 작업에 쓰지 않는 것이 모범 사례로 굳어졌을까요?
> 루트는 어떤 정책으로도 권한을 제한할 수 없는 *완전 접근* 신원이어서, 일상에서 사용할수록 자격증명이 노출될 기회가 늘어나고 사고 시 피해 범위가 계정 전체로 확대됩니다.
> IAM 사용자나 역할에는 최소 권한 정책을 적용해 피해 반경을 좁힐 수 있지만, 루트는 그런 제한 자체가 불가능합니다.
> 따라서 루트는 잠가 두고 루트 전용 작업에만 사용하는 것이, 자격증명 노출 위험과 최악의 피해 반경을 동시에 줄이는 방법입니다.

### 4) 최소 권한 원칙 + 그룹·정책으로 권한 관리 {#least-privilege}

> 공식 모범 사례 원문: **"grant only the permissions required to perform a task"** — 작업에 *필요한 권한만* 부여하라(=**least-privilege permissions**, 최소 권한).

- 처음엔 넓게 시작하더라도, 사용 패턴이 잡히면 **권한을 줄여 최소 권한으로 수렴**시킨다.
- **AWS 관리형 정책(AWS managed policies)**으로 빠르게 시작하되, 그것은 모든 고객용이라 *과한* 경우가 많으니 **고객 관리형 정책**으로 좁힌다.
- **권한은 사람마다 따로 붙이지 말고 그룹으로**: 같은 역할의 사용자들을 **IAM 그룹**에 넣고 그룹에 정책을 연결하면, 입·퇴사·역할 변경 시 그룹 멤버십만 바꾸면 된다.

> 🧠 원리: 왜 그룹에 정책을 붙이는 방식이 사용자마다 개별로 붙이는 것보다 안전할까요?
> 사용자마다 정책을 직접 붙이면 같은 역할을 가진 사람 수만큼 각기 다른 권한 집합이 생길 수 있어, 변경이나 감사 시 일관성을 확인하기 어렵습니다.
> 그룹 하나에 정책을 연결하면 소속 사용자 전원에게 동일한 권한이 적용되고, 역할이 바뀌면 그룹 멤버십 변경 하나로 권한을 일괄 갱신할 수 있습니다.
> 변경 지점이 단일화되므로 과도하게 넓은 권한이 특정 개인에게만 남는 상황을 줄이는 데 도움이 됩니다.

### 5) 로그인 보안 강화 — MFA와 암호 정책 {#mfa-password}

**MFA(다중 인증, Multi-Factor Authentication):** 사용자 이름·암호(*아는 것*)에 더해, **기기가 생성하는 추가 인증(*가진 것*)**을 요구해 보안을 한 단계 높입니다. 자격증명이 유출돼도 두 번째 요소 없이는 로그인할 수 없습니다.

| MFA 유형 | 설명 |
|---|---|
| **패스키 / 보안 키 (FIDO)** | 공개키 암호 기반, **피싱에 강함(phishing-resistant)** → AWS가 가능한 곳에선 *가장 권장* |
| **가상 인증 앱 (Virtual MFA)** | 휴대폰 앱이 TOTP(시간 기반 일회용 코드) 생성 |
| **하드웨어 TOTP 토큰** | 6자리 코드를 만드는 물리 기기 |

> 참고: AWS는 **SMS 문자 기반 MFA 지원을 종료**했습니다. 루트·IAM 사용자는 각각 최대 **8개**의 MFA 기기를 등록할 수 있습니다.

**암호 정책(Password Policy):** 계정에 **사용자 지정 암호 정책**을 걸어 IAM 사용자 암호의 **최소 길이, 문자 종류(대문자·소문자·숫자·특수문자), 만료(rotation) 기간, 재사용 금지**를 강제할 수 있습니다.

> ⚠️ 암호 정책은 **IAM 사용자에게만** 적용되며 **루트 사용자 암호나 액세스 키에는 적용되지 않습니다.**

> 🧠 원리: 왜 패스키/보안 키(FIDO)는 같은 MFA 중에서도 피싱에 구조적으로 강할까요?
> TOTP 같은 방식은 사용자가 코드를 입력하는 과정에서 가짜 사이트가 그 코드를 가로채 실시간으로 진짜 사이트에 재사용할 수 있습니다.
> FIDO는 공개키 암호를 사용하고, 인증 응답에 *요청을 보낸 서버의 출처(origin)*를 포함시켜 서명합니다 — 가짜 사이트와 진짜 사이트의 도메인이 달라 서명이 진짜 서버에서 검증되지 않습니다.
> 비밀값(개인키)이 기기 밖으로 나가지 않고 출처 검증이 프로토콜에 내장돼 있어, 가짜 사이트에 응답해도 재사용이 불가능한 구조입니다.

### 6) 중앙 집중식 접근 — IAM Identity Center (이전 AWS SSO) {#identity-center}

**AWS IAM Identity Center**는 **인력(workforce) 사용자**가 **여러 AWS 계정과 애플리케이션**에 접근하는 것을 *한곳에서* 관리하게 해 줍니다.

- **단일 로그인(SSO):** 한 번 로그인하면 할당된 모든 계정·앱에 접근(AWS 액세스 포털).
- **하나의 페더레이션 지점:** **기존 외부 자격증명 공급자(IdP)**를 연결하거나, Identity Center 안에서 사용자를 직접 만들어 관리.
- **2022년 7월 26일, AWS Single Sign-On(AWS SSO)에서 IAM Identity Center로 이름이 바뀌었습니다.**

> 모범 사례 방향: **사람(human user)은 IAM 사용자(장기 자격증명)보다 IAM Identity Center나 페더레이션을 통한 *임시 자격증명*** 사용을 권장.

> 🧠 원리: 왜 IAM Identity Center는 각 계정마다 따로 IAM 사용자를 만드는 대신 중앙에서 단일 접근 지점을 제공할까요?
> 계정마다 IAM 사용자를 따로 만들면, 퇴사나 역할 변경 시 모든 계정의 사용자를 각각 찾아 수정해야 해 누락이 생길 수 있습니다.
> IAM Identity Center는 사용자 목록과 권한 할당을 한 곳에서 관리하므로, 한 번의 변경이 연결된 모든 계정에 즉시 반영됩니다.
> 또한 임시 자격증명으로 접근해 장기 키의 누적 위험을 줄이면서, 기존 IdP(회사 디렉터리)의 신원을 그대로 신뢰해 별도 계정을 만드는 부담도 없앱니다.

### 7) 자격증명 저장 — Secrets Manager {#secrets-manager}

**AWS Secrets Manager**는 **데이터베이스 자격증명, API 키, OAuth 토큰** 같은 비밀(secret)을 **안전하게 저장·조회·자동 교체(rotation)**합니다.

- **하드코딩 제거:** 코드에 비밀번호를 박아 넣는 대신, 런타임에 Secrets Manager를 *호출해* 동적으로 가져옵니다 → 소스·로그 유출로부터 보호.
- **자동 교체:** 일정에 따라 비밀을 주기적으로 자동 교체해 장기 비밀의 위험을 줄입니다.
- 비교: **순수 AWS 자격증명은 IAM**, **암호화 키는 KMS**가 적합. 설정값·비밀을 더 저렴하게 보관하려면 **Systems Manager Parameter Store**도 있음(자동 교체는 Secrets Manager의 강점).

> 🧠 원리: 왜 Secrets Manager의 자동 교체가 단순히 비밀을 저장하는 것보다 보안 측면에서 중요할까요?
> 비밀을 안전한 곳에 저장하더라도 오래 바뀌지 않는 비밀은 유출 사실을 모른 채 장기간 공격자가 사용할 수 있는 창을 열어 둡니다.
> 자동 교체는 일정 주기마다 새 비밀을 발급하고 구 비밀을 무효화하므로, 탈취된 비밀의 유효 기간이 교체 주기 이내로 제한됩니다.
> 교체가 자동화되면 사람이 수동으로 바꾸는 과정에서 발생하는 누락이나 지연 위험도 줄일 수 있습니다.

### IAM은 글로벌 서비스 (보강) {#iam-global}

IAM 사용자·그룹·역할·정책은 특정 리전에 묶이지 않고 **계정 전체(모든 리전)에 동일하게 적용**됩니다. 리전별로 따로 만들 필요가 없습니다. 또한 권한은 **IAM 정책**(JSON 문서)으로 정의하며, 어떤 작업(Action)을 어떤 리소스(Resource)에 허용(Allow)/거부(Deny)할지 기술해 사용자·그룹·역할에 연결합니다.

> 시험 신호: "IAM 엔터티가 리전에 묶이나?" → 아니다(글로벌). "권한을 정의하는 것" → IAM **정책**.
> 출처: [What is IAM?](https://docs.aws.amazon.com/IAM/latest/UserGuide/introduction.html), [IAM 정책](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies.html), [Global services](https://docs.aws.amazon.com/whitepapers/latest/aws-fault-isolation-boundaries/global-services.html)

> 🧠 원리: 왜 IAM 정책은 사용자·그룹·역할에 *붙이는* 방식으로 설계됐을까요?
> AWS 리소스 종류는 수십 가지이고 그 조합으로 만들어지는 권한 경우의 수는 매우 많습니다 — 리소스마다 접근자를 지정하면 관계 수가 리소스 수에 비례해 빠르게 늘어납니다.
> 정책을 신원(주체)에 붙이는 방식은 "이 사람이 할 수 있는 것"을 한 문서에 모아 두어, 권한 변경이 필요할 때 정책 하나만 수정하면 됩니다.
> 정책을 JSON 문서로 표현하면 버전 관리·감사·재사용이 쉬워지고, Allow/Deny 명시 규칙으로 기본 거부(deny-by-default) 원칙을 일관되게 구현할 수 있습니다.

### 애플리케이션·디렉터리 아이덴티티 — Cognito와 Directory Service {#app-directory-identity}

IAM은 **AWS 리소스에 접근하는 주체**를 다루고, IAM Identity Center는 **조직 인력(workforce)의 여러 계정·앱 접근**을 중앙 관리합니다. 반대로 **Amazon Cognito**는 웹·모바일 앱의 최종 사용자(customer/app user) 로그인에, **AWS Directory Service**는 Microsoft Active Directory 또는 LDAP 기반 디렉터리를 AWS에서 쓰는 데 초점이 있습니다.

| 서비스 | 한 줄 역할 | 언제 고르는가 |
|---|---|---|
| **Amazon Cognito User Pool** | 앱 사용자를 저장·가입·로그인시키는 사용자 디렉터리이자 OIDC/OAuth 기반 인증 서버 | 웹·모바일 앱의 회원가입·로그인·JWT 토큰 발급 |
| **Amazon Cognito Identity Pool** | 인증된 사용자 또는 게스트 사용자에게 **임시 AWS 자격증명**을 발급 | 앱 사용자가 S3·DynamoDB 같은 AWS 리소스에 제한적으로 접근해야 할 때 |
| **AWS Managed Microsoft AD** | AWS가 관리하는 실제 Microsoft Active Directory | AD 기능이 필요한 Windows 워크로드·AWS 관리형 앱 |
| **AD Connector** | 온프레미스 AD로 인증 요청을 전달하는 프록시 | 기존 회사 AD를 그대로 써서 WorkSpaces 등 AWS 앱에 로그인할 때 |
| **Simple AD** | Samba 기반의 기본 AD 호환 디렉터리 | 저비용·소규모의 기본 디렉터리가 필요할 때 |

| 헷갈리는 선택지 | 경계 |
|---|---|
| **IAM 사용자/역할** | AWS API 권한을 가진 계정 내 주체. 앱 최종 사용자 회원가입용이 아님 |
| **IAM Identity Center** | 직원·관리자 같은 인력 사용자의 다중 계정 접근 중앙 관리 |
| **Cognito** | 고객·앱 사용자 로그인과 앱에서 쓸 토큰·임시 자격증명 |
| **Directory Service** | Active Directory·LDAP 호환 디렉터리와 Windows/WorkSpaces 계열 연동 |

> 🧠 원리: 왜 Cognito는 User Pool과 Identity Pool을 분리할까요?
> 앱 사용자를 "로그인시켜 누구인지 확인"하는 것과, 그 사용자가 "AWS 리소스에 어떤 권한으로 접근할지 결정"하는 것은 서로 다른 문제입니다.
> User Pool은 가입·로그인·토큰 발급처럼 애플리케이션 인증을 담당하고, Identity Pool은 신뢰된 토큰을 받아 AWS STS 임시 자격증명으로 교환합니다.
> 두 단계를 나누면 앱은 사용자 인증만 필요한 경우 User Pool만 쓸 수 있고, S3 업로드 같은 AWS 리소스 접근이 필요할 때만 Identity Pool과 IAM 역할을 연결할 수 있습니다.
> Directory Service는 또 다른 축으로, 앱 회원 로그인보다 기존 Microsoft AD/LDAP 디렉터리를 AWS 워크로드와 연결하는 데 초점이 있습니다.

## ✍️ 시험 포인트

- **"계정 해지 / 계정 이메일·암호 변경 / Support 플랜 변경 / RI Marketplace 판매자 등록 / IAM 권한 복구"** → **루트 전용 작업**. 보기에 나오면 "루트 사용자".
- **"EC2 시작 / IAM 사용자·정책 생성 / S3 버킷 만들기"** 같은 일상 작업 → **IAM(관리자)으로 충분** (루트 불필요).
- **루트 보호** 정답 패턴: ①루트 MFA 켜기 ②일상은 IAM/Identity Center ③**루트 액세스 키 만들지 않기**.
- **최소 권한**: "필요한 권한만" = 정답. "일단 관리자 권한 주고 나중에 회수"는 항상 오답.
- **그룹**: 여러 사용자에게 같은 권한 → **그룹에 정책 붙이고 사용자 추가** (개별 부여·루트 공유는 오답).
- **MFA** = 암호 + 기기 인증. 보안 강화 요구 → MFA. **가장 피싱에 강한 유형 = 패스키/보안 키(FIDO).**
- **IAM Identity Center**(=옛 AWS SSO): **여러 계정·앱 + SSO + 페더레이션**. "다중 계정 인력 접근 중앙 관리" 키워드.
- **Secrets Manager**: DB 자격증명·API 키 **저장 + 자동 교체**, 하드코딩 제거.
- **IAM은 전역 서비스이며 무료** (다른 서비스 사용분만 과금).
- **Cognito User Pool = 앱 사용자 로그인**, **Cognito Identity Pool = 앱 사용자에게 임시 AWS 자격증명**, **Directory Service = Microsoft AD/LDAP 디렉터리 연동**.

## ⚠️ 흔한 함정 {#pitfalls}

1. **"루트 사용자로 매일 작업하면 편하다."** → ❌. 루트는 *완전 접근*이라 사고 시 피해가 최대. 일상은 IAM/Identity Center, 루트는 잠가 두고 루트 전용 작업에만.
   *(원리: §3 — 루트는 어떤 정책으로도 권한을 제한할 수 없어 일상 사용이 늘수록 자격증명 노출 기회와 피해 반경이 동시에 커진다.)*
2. **"프로그래밍 접근이 필요하니 루트 액세스 키를 만들자."** → ❌. **루트 액세스 키는 만들지 않는 것**이 모범 사례. 역할(임시 자격증명) 또는 IAM 사용자 키를 쓴다.
   *(원리: §2 — 역할의 임시 자격증명은 유효 기간이 지나면 자동 만료되어 탈취되더라도 피해 창이 시간적으로 제한된다.)*
3. **"보안을 위해 모든 사용자에게 관리자 권한을 주고 문제 생기면 뺀다."** → ❌. 최소 권한의 반대. *필요한 권한만* 부여.
   *(원리: §4 — 그룹과 정책으로 변경 지점을 단일화하면 과도한 권한이 특정 개인에게 남는 상황을 줄일 수 있다.)*
4. **"암호 정책을 강하게 걸면 루트 암호도 그 규칙을 따른다."** → ❌. 암호 정책은 **IAM 사용자 전용**, 루트 암호·액세스 키엔 적용 안 됨.
   *(원리: §5 본문 — 암호 정책은 IAM 사용자 자격증명에만 작동하며, 루트는 별도 보호 수단(MFA·잠금)이 필요하다.)*
5. **"MFA는 또 다른 비밀번호다."** → ❌. MFA는 *아는 것(암호)* + *가진 것(기기 코드)*의 **다른 요소** 결합. 같은 종류를 두 번 묻는 게 아님.
   *(원리: §5 — FIDO 같은 MFA는 비밀값이 기기 밖으로 나가지 않아 암호 단독 방식과는 구조적으로 다른 인증 채널을 추가한다.)*
6. **"IAM Identity Center는 애플리케이션 최종 사용자(소비자) 로그인용이다."** → ❌. Identity Center는 **인력(workforce) 사용자**의 다중 계정·앱 접근용. (소비자용 ID는 다른 서비스 영역)
   *(원리: §6 — Identity Center는 계정 수에 관계없이 인력 사용자 접근을 중앙에서 관리해 변경 누락을 줄이는 구조다.)*
7. **"DB 비밀번호는 코드에 적어 두고 잘 숨기면 된다."** → ❌. **Secrets Manager**에 저장하고 런타임에 호출 + 자동 교체.
   *(원리: §7 — 자동 교체는 탈취된 비밀의 유효 기간을 교체 주기 이내로 제한하고, 코드에 비밀을 두는 수동 관리의 누락 위험을 없앤다.)*

8. **"앱 최종 사용자 로그인은 IAM 사용자로 만든다."** → ❌. 웹·모바일 앱 사용자 로그인은 **Amazon Cognito User Pool**이 적합합니다. IAM 사용자는 AWS 계정 안에서 AWS API를 호출하는 주체입니다.
   *(원리: §9 — IAM은 AWS 리소스 접근 권한을 가진 주체를 관리하고, Cognito User Pool은 앱 사용자의 가입·로그인·토큰 발급을 담당해 신뢰 경계가 다르다.)*

9. **"Cognito User Pool만 있으면 앱 사용자가 S3에 접근할 AWS 자격증명을 자동으로 받는다."** → ⚠️ 구분. User Pool은 인증 토큰을 발급하고, AWS 임시 자격증명 발급은 **Identity Pool**과 IAM 역할 연결이 담당합니다.
   *(원리: §9 — 인증과 AWS 권한 부여를 분리해, AWS 리소스 접근이 필요한 경우에만 토큰을 STS 임시 자격증명으로 교환한다.)*

10. **"Directory Service는 소비자 앱 로그인용 서비스다."** → ❌. Directory Service는 Microsoft AD·LDAP 기반 디렉터리를 AWS 서비스와 연결하거나 AWS에서 관리형 AD를 쓰기 위한 서비스입니다.
   *(원리: §9 — Directory Service는 기존 기업 디렉터리와 Windows/WorkSpaces 계열 워크로드 연동을 다루며, 앱 회원 가입·로그인 기능은 Cognito가 담당한다.)*

예: **AWS 계정 해지(단독 계정)**, **계정 루트 이메일·암호 변경**, **AWS Support 플랜 변경/취소**, **Reserved Instance Marketplace 판매자 등록**, **(유일한 관리자가 자기 권한을 날렸을 때) IAM 권한 복구**. 공통점은 *계정 자체*에 대한 작업이거나 *잠긴 상황을 푸는* 작업입니다.
</details>

**Q2.** 같은 권한이 필요한 개발자 5명에게 권한을 부여·관리하는 가장 권장되는 방법은?

<details><summary>정답 보기</summary>

**IAM 그룹**을 만들어 필요한 정책을 그룹에 연결하고 5명을 그룹에 추가합니다. 권한 변경이 필요하면 그룹 정책만 고치면 되고, 사람마다 따로 붙이지 않아 관리가 단순합니다.
</details>

**Q3.** MFA가 단순히 "비밀번호 하나 더"가 아닌 이유는?

<details><summary>정답 보기</summary>

MFA는 *아는 것*(암호)에 더해 *가진 것*(기기가 생성하는 일회용 코드/보안 키)이라는 **다른 종류의 요소**를 함께 요구합니다. 암호가 유출돼도 두 번째 요소가 없으면 로그인할 수 없습니다. 가장 강력한 유형은 피싱에 강한 **패스키/보안 키(FIDO)**입니다.
</details>

**Q4.** 애플리케이션이 쓰는 데이터베이스 자격증명을 코드에 하드코딩하지 않으려면 어떤 서비스를 쓰고, 추가로 무엇이 가능합니까?

<details><summary>정답 보기</summary>

**AWS Secrets Manager**에 저장하고 런타임에 호출해 동적으로 가져옵니다. 더해서 **자동 교체(rotation)**를 설정해 비밀을 주기적으로 바꿔 장기 노출 위험을 줄일 수 있습니다.
</details>

---

**Q5 (원리).** 왜 IAM 역할을 쓰면 IAM 사용자의 장기 액세스 키보다 보안 측면에서 유리할까요?

<details><summary>정답 보기</summary>

**역할이 발급하는 임시 자격증명은 유효 기간이 지나면 자동으로 만료되기 때문입니다.** 장기 액세스 키는 명시적으로 삭제하지 않는 한 탈취 후에도 계속 유효하지만, 역할의 임시 자격증명이 탈취되면 피해 창이 만료 시간 이내로 제한됩니다. 또한 EC2·Lambda 같은 서비스가 역할을 맡으면 코드에 키를 하드코딩하지 않아도 됩니다.
</details>
