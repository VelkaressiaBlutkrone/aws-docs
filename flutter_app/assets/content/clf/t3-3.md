## 📖 핵심 개념

### 1) Amazon EC2 — 클라우드의 가상 서버 (IaaS) {#ec2}

**Amazon EC2(Elastic Compute Cloud)**는 AWS 클라우드에서 **온디맨드로 크기 조절 가능한 컴퓨팅 용량**을 제공합니다. EC2 인스턴스는 곧 **클라우드의 가상 서버**입니다.

- 필요한 만큼 가상 서버를 **늘리고(scale up) 줄일(scale down)** 수 있습니다.
- **인스턴스 유형(instance type)**이 그 인스턴스의 하드웨어(CPU·메모리·네트워크·스토리지 균형)를 결정합니다 — 워크로드에 맞춰 고릅니다.
- **AMI**(Amazon Machine Image)는 OS·소프트웨어를 담은 인스턴스 템플릿입니다.
- EC2는 OS·확장·보안 그룹 등 **많은 부분을 고객이 제어**합니다([공동 책임 모델](#)의 IaaS — 게스트 OS 패치는 고객).

> **인스턴스 유형은 "용도별"로 나뉩니다**(시험 단골): **범용**, **컴퓨팅 최적화**(CPU 집약), **메모리 최적화**(대용량 메모리·인메모리 DB), **스토리지 최적화**(높은 디스크 처리량), **가속 컴퓨팅**(GPU). 각 유형은 *컴퓨팅·메모리·네트워크·스토리지의 다른 균형*을 제공합니다.

> 참고: 간단한 웹사이트·앱을 *저렴하고 예측 가능한 월정액*으로 빠르게 띄우려면 **Amazon Lightsail**도 있습니다(EC2보다 단순).

> 🧠 원리: 왜 EC2는 인스턴스 유형을 용도별로 나눠 고객이 선택하게 할까요?
> 워크로드마다 필요한 하드웨어 자원의 균형이 다릅니다 — 머신러닝 학습은 GPU가 필수지만, 단순 웹 서버는 범용 CPU로 충분합니다.
> 하나의 고정 사양으로 모든 워크로드를 처리하면 자원이 낭비되거나 부족해지는 두 경우가 생기므로, 인스턴스 유형을 컴퓨팅·메모리·스토리지·GPU 최적화로 분리해 고객이 필요한 균형을 선택하게 합니다.
> 이 구조 덕분에 고객은 실제 필요한 자원에만 비용을 지불하고, AWS는 동일한 물리 인프라를 더 다양한 용도로 효율적으로 활용할 수 있습니다.

### 2) 컨테이너 — Amazon ECS vs Amazon EKS {#containers}

컨테이너는 앱과 의존성을 함께 패키징해 *어디서나 동일하게* 실행합니다. AWS의 두 오케스트레이션 서비스:

| 서비스 | 한 줄 | 키워드 |
|---|---|---|
| **Amazon ECS** (Elastic Container Service) | AWS의 **완전관리형 컨테이너 오케스트레이션** 서비스. 컨테이너화된 앱을 배포·관리·확장(Docker 통합) | "컨테이너", "Docker", "AWS 네이티브 오케스트레이션" |
| **Amazon EKS** (Elastic Kubernetes Service) | **완전관리형 Kubernetes** 서비스. Kubernetes 컨트롤 플레인을 직접 설치·운영할 필요 없이 AWS가 관리 | **"Kubernetes"**, "k8s 표준" |

> 시험 신호: 보기에 **"Kubernetes"**가 있으면 → **EKS**. 그냥 컨테이너 오케스트레이션이면 → **ECS**. 두 서비스 모두 **EC2** 위에서 돌리거나 **Fargate**(서버리스)로 돌릴 수 있습니다.

> 🧠 원리: 왜 AWS는 ECS와 EKS를 하나로 합치지 않고 별도 서비스로 제공할까요?
> ECS는 AWS가 자체 설계한 오케스트레이션 방식으로, AWS 네이티브 서비스와 통합이 간단하고 Kubernetes 학습 없이 빠르게 컨테이너를 운영할 수 있습니다.
> EKS는 업계 표준 Kubernetes 컨트롤 플레인을 AWS가 관리해 주는 서비스로, 이미 Kubernetes를 쓰거나 멀티클라우드·온프레미스 Kubernetes 환경과 연속성이 필요한 팀에 학습·이식 비용 없이 이전할 수 있게 합니다.
> 두 오케스트레이션 방식이 담당하는 사용자 기반과 이식성 요구가 달라 별도 서비스로 나뉘어 있으며, 기저 컴퓨팅(EC2 또는 Fargate)은 두 서비스가 공유합니다.

### 컨테이너 이미지와 배치 작업 — Amazon ECR · AWS Batch {#registry-batch}

컴퓨팅 서비스는 "코드를 실행하는 곳"만 있는 것이 아닙니다. 컨테이너를 실행하려면 **이미지를 보관하는 레지스트리**가 필요하고, 오래 걸리거나 대량으로 반복되는 작업은 **배치 워크로드**로 스케줄링할 수 있습니다.

| 서비스 | 한 줄 역할 | 헷갈리지 말 것 |
|---|---|---|
| **Amazon ECR** | Docker/OCI 컨테이너 이미지를 저장·공유·관리하는 AWS 관리형 컨테이너 이미지 레지스트리 | 컨테이너를 실행하지 않습니다. ECS/EKS/Lambda 컨테이너 이미지가 가져갈 저장소입니다. |
| **AWS Batch** | 대규모 배치·ML·시뮬레이션·분석 작업을 큐에 넣고, 필요한 컴퓨팅을 자동 프로비저닝해 실행 | 항상 켜진 웹 서버가 아니라, 제출된 작업(job)을 계획·스케줄·실행합니다. |

| 시나리오 | 정답 신호 |
|---|---|
| "컨테이너 이미지를 프라이빗하게 저장하고 취약점 스캔·수명 주기 정책을 적용한다" | **Amazon ECR** |
| "수천 개의 렌더링·분석·시뮬레이션 작업을 큐에 제출하고 컴퓨팅 용량을 자동으로 맞춘다" | **AWS Batch** |

> 🧠 원리: 왜 ECR과 Batch는 ECS/EKS/Lambda 같은 실행 서비스와 분리되어 있을까요?
> 컨테이너 이미지는 실행되기 전의 불변 패키지이고, 이를 안전하게 저장·권한 제어·복제·스캔하는 문제는 컨테이너를 실제로 스케줄링해 실행하는 문제와 다릅니다.
> ECR은 이미지 저장소 역할에 집중하고, ECS/EKS/Lambda/Fargate 같은 실행 환경은 필요한 시점에 이미지를 가져와 실행합니다.
> Batch는 웹 요청을 즉시 처리하는 서비스가 아니라 큐에 쌓인 작업을 적절한 컴퓨팅 자원에 배치해 처리량과 비용을 맞추는 오케스트레이션 서비스입니다.
> 그래서 "이미지를 보관할 곳"이면 ECR, "작업을 대량 실행할 스케줄러"이면 Batch, "서비스를 계속 실행할 런타임"이면 ECS/EKS/Lambda/Fargate로 나뉩니다.

### 3) 서버리스 — AWS Lambda(함수)와 AWS Fargate(컨테이너) {#serverless}

"서버리스"는 *서버가 없다*가 아니라 **서버를 내가 프로비저닝·관리하지 않는다**는 뜻입니다.

**AWS Lambda** — **서버 관리 없이 코드를 실행**하는 컴퓨팅 서비스.
- **이벤트에 응답해 코드 실행**(파일 업로드·API 요청·DB 변경 등). 서버·OS 유지보수, 용량 프로비저닝, **자동 확장**, 로깅을 전부 AWS가 처리 — *나는 코드만 책임*.
- **사용한 컴퓨팅 시간만큼만 과금**(pay-per-use, 코드가 안 돌 땐 비용 없음). 함수는 한 번에 최대 15분 실행.
- 키워드: **"서버 관리 없이", "이벤트 기반", "코드만", "짧게 실행"**.

**AWS Fargate** — **서버리스 컨테이너 컴퓨팅 엔진**.
- **ECS·EKS와 함께** 사용해, **EC2 인스턴스 클러스터를 관리하지 않고** 컨테이너를 실행. 서버 유형 선택·확장 시점·클러스터 패킹 고민이 사라짐.
- 키워드: **"서버리스 컨테이너", "클러스터 관리 없이 컨테이너"**.

> 한눈에: **Lambda = 서버리스 *함수*(이벤트·코드). Fargate = 서버리스 *컨테이너*(ECS/EKS의 서버 관리 제거).**

> 🧠 원리: 왜 Lambda와 Fargate는 같은 "서버리스"라는 이름을 쓰면서도 다른 실행 단위를 택했을까요?
> Lambda는 *함수* 단위로 이벤트에 반응해 짧게 실행하는 패턴에 최적화돼 있어, 실행이 없을 때 비용이 발생하지 않고 이벤트 수에 따라 자동 확장이 가능합니다.
> Fargate는 *컨테이너* 단위 — 이미 컨테이너로 패키징된 앱을 EC2 클러스터 관리 없이 실행하고 싶은 요구를 충족하기 위해, ECS·EKS와 함께 동작하며 서버 프로비저닝 부담만 제거합니다.
> 실행 모델이 다른(이벤트 코드 vs 컨테이너 앱) 두 요구를 단일 서비스로 합치면 각각에 맞는 과금·확장 방식을 제공하기 어려워, 함수 단위와 컨테이너 단위로 분리한 구조가 됩니다.

### 4) 탄력성 — Amazon EC2 Auto Scaling {#autoscaling}

**Amazon EC2 Auto Scaling**은 애플리케이션 부하를 처리할 **올바른 수의 EC2 인스턴스**를 유지합니다.

- **Auto Scaling 그룹**에 최소(min)·최대(max)·원하는 용량(desired)을 정하면, 정의한 **조건(스케일링 정책)에 따라 인스턴스를 자동으로 추가/제거**합니다.
- 수요가 늘면 용량을 더하고 줄면 빼서 — **가용성을 유지하고 비용을 절감**합니다. 이것이 클라우드의 **탄력성(elasticity)**입니다.
- 건강 검사로 손상된 인스턴스를 자동 교체하고, **여러 AZ에 균등 분산**해 고가용성도 높입니다.

> 시험 신호: **"수요 변화에 맞춰 자동으로 늘리고 줄인다 / 탄력성"** → EC2 Auto Scaling.

> 🧠 원리: 왜 EC2 Auto Scaling은 인스턴스를 미리 충분히 준비해 두지 않고, 조건에 따라 늘리고 줄이는 방식을 택할까요?
> 트래픽은 시간대·이벤트에 따라 변하는데, 최대 수요에 맞춰 항상 인스턴스를 유지하면 수요가 낮은 시간대에 비용이 낭비됩니다.
> Auto Scaling은 정의된 조건(CPU 사용률 등 스케일링 정책)을 실시간으로 감시해 필요한 만큼만 인스턴스를 추가·제거하므로, 가용성을 유지하면서 유휴 자원에 대한 비용을 줄일 수 있습니다.
> 이 동적 조정 방식이 클라우드의 탄력성(elasticity)을 실현하는 메커니즘으로, 온프레미스에서 피크 대비 과잉 프로비저닝하던 방식과 근본적으로 다릅니다.

### 5) 트래픽 분산 — Elastic Load Balancing(ELB) {#elb}

**Elastic Load Balancing(ELB)**은 **들어오는 트래픽을 여러 대상(EC2·컨테이너·IP)에 자동으로 분산**합니다(하나 이상의 AZ에 걸쳐).

- 등록된 대상의 **상태를 검사해 건강한 대상에만** 트래픽을 보냅니다 → **가용성·내결함성 증가**.
- 트래픽 변화에 따라 **자동으로 확장**됩니다.
- **Auto Scaling + ELB**는 단짝: Auto Scaling이 인스턴스를 늘리면 ELB가 자동으로 등록해 트래픽을 고르게 보냅니다.

| 로드 밸런서 유형 | 처리 계층 | 용도 |
|---|---|---|
| **Application Load Balancer(ALB)** | L7 | HTTP/HTTPS 웹 트래픽 |
| **Network Load Balancer(NLB)** | L4 | TCP/UDP, 초고성능·저지연 |
| **Gateway Load Balancer(GWLB)** | L3/4 | 서드파티 가상 어플라이언스(방화벽 등) |

> 🧠 원리: 왜 ELB는 트래픽을 단순히 순서대로 나누지 않고, 대상의 상태를 검사해 건강한 대상에만 보낼까요?
> 인스턴스가 늘어나도 그 중 일부가 응답 불능 상태라면 그쪽으로 들어온 요청은 실패합니다 — 단순 순환 분산은 장애 인스턴스를 제외하는 기능이 없습니다.
> ELB는 상태 검사(health check)로 각 대상의 정상 여부를 주기적으로 확인해, 비정상 대상을 자동으로 분산 풀에서 제외하고 정상 대상에만 트래픽을 보냄으로써 인스턴스 장애가 사용자 요청 실패로 이어지지 않게 합니다.
> 이 상태 기반 분산 방식이 Auto Scaling과 결합되면 — Auto Scaling이 장애 인스턴스를 교체하고, ELB가 그 동안 남은 정상 인스턴스로만 트래픽을 유지해 — 고가용성을 만들어 냅니다.

### 6) 한눈에 — 관리 부담 스펙트럼 {#spectrum}

```
많이 관리(제어 큼)  ←──────────────────────────────→  적게 관리(AWS가 더)
   EC2            ECS/EKS (on EC2)        Fargate            Lambda
 가상 서버         컨테이너 클러스터      서버리스 컨테이너    서버리스 함수
 OS·확장 직접      EC2 관리 필요          서버 관리 없음       코드만(이벤트)
```

> 고르는 법: **OS·환경을 완전히 제어해야** → EC2. **컨테이너**를 쓰는데 서버 관리는 싫다 → **Fargate**. **이벤트에 짧게 반응하는 코드** → **Lambda**. **Kubernetes** 표준이 필요 → **EKS**.

> 🧠 원리: 왜 AWS는 컴퓨팅 선택지를 하나의 서비스로 통합하지 않고 EC2·컨테이너·서버리스로 나눴을까요?
> 각 선택지는 관리 부담과 제어 수준 사이의 트레이드오프가 다르고, 그 트레이드오프가 필요한 워크로드가 다릅니다 — OS·환경을 세밀하게 제어해야 하는 레거시 앱은 EC2가, 이식성 있는 컨테이너 앱은 ECS·EKS·Fargate가, 이벤트에 짧게 반응하는 기능은 Lambda가 적합합니다.
> 단일 서비스로 모든 트레이드오프를 커버하면 제어가 필요한 고객에게는 너무 단순해지고, 단순함이 필요한 고객에게는 너무 복잡해져 모든 사용자에게 최선이 되지 않습니다.
> 선택지를 스펙트럼으로 나눠 두면 팀이 필요에 맞는 수준을 골라 쓸 수 있고, 같은 앱 안에서도 컴포넌트마다 다른 모델을 혼합할 수 있습니다.

## ✍️ 시험 포인트

- **EC2** = 클라우드의 *가상 서버*. **인스턴스 유형** = 용도별(컴퓨팅/메모리/스토리지 최적화) 하드웨어 균형.
- **"서버를 관리하고 싶지 않다 + 이벤트로 코드 실행"** → **Lambda**(서버리스 함수, 사용한 시간만 과금).
- **"컨테이너인데 서버/클러스터 관리는 싫다"** → **Fargate**(서버리스 컨테이너). **"Kubernetes"** → **EKS**.
- **ECR = 컨테이너 이미지 저장소**, **AWS Batch = 큐 기반 배치 작업 실행·스케줄링**.
- **"수요에 맞춰 인스턴스 자동 증감 / 탄력성"** → **EC2 Auto Scaling**.
- **"트래픽을 여러 인스턴스에 분산 / 가용성"** → **ELB**. 웹(HTTP)=ALB, TCP/UDP=NLB.
- **Auto Scaling(탄력성) + ELB(분산) + 멀티 AZ(고가용성)**는 함께 다니는 3종 세트.

## ⚠️ 흔한 함정 {#pitfalls}

1. **"서버리스는 서버가 아예 없다는 뜻이다."** → ❌. 서버는 있지만 **내가 프로비저닝·관리하지 않습니다**(AWS가 처리). 그래서 *서버리스*.
   *(원리: §3 — Lambda와 Fargate는 서버 프로비저닝을 AWS가 처리하는 실행 모델로, 서버 자원이 존재하지 않는 것이 아니라 고객이 관리하지 않는 구조다.)*
2. **"Lambda로 24시간 계속 도는 서버를 운영한다."** → ⚠️ 부적합. Lambda 함수는 *이벤트에 반응해 짧게* 실행(한 번에 최대 15분). 상시 가동 서버라면 EC2/컨테이너가 보통 적합.
   *(원리: §3 — Lambda는 이벤트 발생 시마다 실행·종료하는 함수 단위 모델로, 상시 가동 서버의 연속 실행 패턴과 다른 실행 단위다.)*
3. **"컨테이너를 쓰면 무조건 EC2를 직접 관리해야 한다."** → ❌. **Fargate**를 쓰면 EC2 클러스터 관리 없이 컨테이너를 실행합니다.
   *(원리: §3 — Fargate는 ECS·EKS의 서버리스 컴퓨팅 엔진으로, 컨테이너 실행에 필요한 클러스터 관리 부담을 AWS가 처리해 제거하는 구조다.)*
4. **"ECS와 EKS는 같다."** → ❌. **EKS는 Kubernetes** 관리형 서비스. 보기에 "Kubernetes"면 EKS.
   *(원리: §2 — ECS는 AWS 네이티브 오케스트레이션, EKS는 업계 표준 Kubernetes 컨트롤 플레인을 관리해 주는 서비스로, 대상 사용자와 이식성 요구가 달라 별도 서비스로 분리돼 있다.)*
5. **"Auto Scaling이 트래픽을 분산한다."** → ❌. *인스턴스 수를 조절*하는 건 Auto Scaling, *트래픽을 분산*하는 건 **ELB**. (둘은 함께 쓰임)
   *(원리: §5 — ELB는 상태 검사로 정상 인스턴스에만 트래픽을 분산하는 역할에 집중하며, 인스턴스 수 조정은 Auto Scaling의 스케일링 정책이 담당하는 별도 메커니즘이다.)*
6. **"로드 밸런서는 인스턴스를 늘려 준다."** → ❌. ELB는 *분산*만, *증감*은 Auto Scaling.
   *(원리: §5 — ELB는 기존 인스턴스 풀에 들어온 트래픽을 건강한 대상에 분산하는 역할에 집중하며, 인스턴스 수 조정은 Auto Scaling의 스케일링 정책이 담당하는 별도 기능이다.)*

7. **"ECR은 컨테이너를 실행하는 서비스다."** → ❌. ECR은 **이미지 레지스트리**입니다. 컨테이너 실행은 ECS/EKS/Fargate/Lambda 같은 실행 서비스가 맡습니다.
   *(원리: §3 — 이미지를 저장·관리하는 문제와 컨테이너를 스케줄링해 실행하는 문제는 서로 다른 책임이다.)*

8. **"Batch는 사용자가 접속하는 웹 애플리케이션 서버다."** → ❌. AWS Batch는 큐에 제출한 배치 작업을 계획·스케줄·실행하는 서비스입니다. 상시 요청 처리 웹 서버는 EC2·컨테이너·Lambda 쪽을 봅니다.
   *(원리: §3 — Batch는 작업 단위의 처리량과 컴퓨팅 용량을 맞추는 오케스트레이션이고, 지속적으로 사용자 요청을 받는 런타임과 실행 패턴이 다르다.)*

## 🧪 자가 점검

> 아래는 학습용 자가 점검입니다. (정식 검증 문항은 `t3-3.questions.json` 참조)

**Q1.** "서버를 프로비저닝하거나 관리하지 않고, 이미지 업로드 같은 이벤트에 반응해 짧게 코드를 실행하고, 실행한 시간만큼만 비용을 내고 싶다." 어떤 서비스인가요?

<details><summary>정답 보기</summary>

**AWS Lambda**(서버리스 함수). 서버·OS·확장을 AWS가 관리하고, 이벤트에 반응해 코드를 실행하며, 사용한 컴퓨팅 시간만큼만 과금합니다.
</details>

**Q2.** 컨테이너로 앱을 운영하려는데 EC2 인스턴스 클러스터를 직접 관리하고 싶지 않습니다. 그리고 표준 Kubernetes가 필요하면?

<details><summary>정답 보기</summary>

서버 관리 없이 컨테이너를 실행하려면 **AWS Fargate**(서버리스 컨테이너 엔진, ECS·EKS와 함께). 표준 **Kubernetes**가 필요하면 **Amazon EKS**(관리형 Kubernetes)를 씁니다.
</details>

**Q3.** 웹 애플리케이션의 수요가 시간대별로 크게 변합니다. 인스턴스 수를 자동으로 늘리고 줄이려면? 그리고 그 인스턴스들에 트래픽을 고르게 나눠 주려면?

<details><summary>정답 보기</summary>

인스턴스 수 자동 증감(탄력성)은 **EC2 Auto Scaling**, 트래픽을 여러 인스턴스에 분산하는 것은 **Elastic Load Balancing(ELB)**. 둘은 함께 쓰여 탄력성과 고가용성을 만듭니다.
</details>

**Q4.** EC2와 Lambda의 가장 큰 차이를 "관리 부담" 관점에서 한 문장으로?

<details><summary>정답 보기</summary>

**EC2**는 가상 서버로 OS·확장 등 *많은 부분을 고객이 관리*합니다. **Lambda**는 서버를 *전혀 관리하지 않고* 코드만 올리면 AWS가 실행·확장·유지보수를 처리합니다(서버리스).
</details>

---

**Q5 (원리).** 왜 Auto Scaling과 ELB는 하나의 서비스로 합쳐지지 않고, 각각 별개로 동작할까요?

<details><summary>정답 보기</summary>

두 서비스는 서로 다른 문제를 해결하기 때문입니다. Auto Scaling은 스케일링 정책에 따라 인스턴스 수를 늘리고 줄여 적절한 용량을 유지하는 역할을 합니다. ELB는 현재 존재하는 인스턴스 풀에서 건강한 대상만 골라 트래픽을 분산하는 역할을 합니다. 두 역할을 분리해 두면 각각을 독립적으로 구성·확장할 수 있고, 함께 쓸 때 Auto Scaling이 인스턴스를 추가하면 ELB가 자동으로 새 인스턴스를 풀에 포함해 탄력성과 고가용성이 동시에 만들어집니다.
</details>
