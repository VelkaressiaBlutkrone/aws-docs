## 🎯 왜 중요한가

- 도메인 3(34%)에서 컴퓨팅은 **"어떤 서비스로 실행할까?"**를 가장 직접적으로 묻는 곳입니다. 시험은 *상황*을 주고 EC2 · 컨테이너(ECS/EKS) · 서버리스(Lambda/Fargate) 중 고르게 합니다.
- 핵심은 **관리 부담의 스펙트럼**입니다: **EC2(내가 많이 관리) → 컨테이너 → Fargate/Lambda(AWS가 더 많이 관리)**. "서버를 관리하고 싶지 않다"가 나오면 서버리스 쪽입니다.
- **Auto Scaling(탄력성)**과 **ELB(분산)**는 거의 항상 함께 등장합니다 — *탄력성·고가용성* 키워드의 단골 정답입니다.

## 📖 핵심 개념

### 1) Amazon EC2 — 클라우드의 가상 서버 (IaaS)

**Amazon EC2(Elastic Compute Cloud)**는 AWS 클라우드에서 **온디맨드로 크기 조절 가능한 컴퓨팅 용량**을 제공합니다. EC2 인스턴스는 곧 **클라우드의 가상 서버**입니다.

- 필요한 만큼 가상 서버를 **늘리고(scale up) 줄일(scale down)** 수 있습니다.
- **인스턴스 유형(instance type)**이 그 인스턴스의 하드웨어(CPU·메모리·네트워크·스토리지 균형)를 결정합니다 — 워크로드에 맞춰 고릅니다.
- **AMI**(Amazon Machine Image)는 OS·소프트웨어를 담은 인스턴스 템플릿입니다.
- EC2는 OS·확장·보안 그룹 등 **많은 부분을 고객이 제어**합니다([공동 책임 모델](#)의 IaaS — 게스트 OS 패치는 고객).

> **인스턴스 유형은 "용도별"로 나뉩니다**(시험 단골): **범용**, **컴퓨팅 최적화**(CPU 집약), **메모리 최적화**(대용량 메모리·인메모리 DB), **스토리지 최적화**(높은 디스크 처리량), **가속 컴퓨팅**(GPU). 각 유형은 *컴퓨팅·메모리·네트워크·스토리지의 다른 균형*을 제공합니다.

> 참고: 간단한 웹사이트·앱을 *저렴하고 예측 가능한 월정액*으로 빠르게 띄우려면 **Amazon Lightsail**도 있습니다(EC2보다 단순).

### 2) 컨테이너 — Amazon ECS vs Amazon EKS

컨테이너는 앱과 의존성을 함께 패키징해 *어디서나 동일하게* 실행합니다. AWS의 두 오케스트레이션 서비스:

| 서비스 | 한 줄 | 키워드 |
|---|---|---|
| **Amazon ECS** (Elastic Container Service) | AWS의 **완전관리형 컨테이너 오케스트레이션** 서비스. 컨테이너화된 앱을 배포·관리·확장(Docker 통합) | "컨테이너", "Docker", "AWS 네이티브 오케스트레이션" |
| **Amazon EKS** (Elastic Kubernetes Service) | **완전관리형 Kubernetes** 서비스. Kubernetes 컨트롤 플레인을 직접 설치·운영할 필요 없이 AWS가 관리 | **"Kubernetes"**, "k8s 표준" |

> 시험 신호: 보기에 **"Kubernetes"**가 있으면 → **EKS**. 그냥 컨테이너 오케스트레이션이면 → **ECS**. 두 서비스 모두 **EC2** 위에서 돌리거나 **Fargate**(서버리스)로 돌릴 수 있습니다.

### 3) 서버리스 — AWS Lambda(함수)와 AWS Fargate(컨테이너)

"서버리스"는 *서버가 없다*가 아니라 **서버를 내가 프로비저닝·관리하지 않는다**는 뜻입니다.

**AWS Lambda** — **서버 관리 없이 코드를 실행**하는 컴퓨팅 서비스.
- **이벤트에 응답해 코드 실행**(파일 업로드·API 요청·DB 변경 등). 서버·OS 유지보수, 용량 프로비저닝, **자동 확장**, 로깅을 전부 AWS가 처리 — *나는 코드만 책임*.
- **사용한 컴퓨팅 시간만큼만 과금**(pay-per-use, 코드가 안 돌 땐 비용 없음). 함수는 한 번에 최대 15분 실행.
- 키워드: **"서버 관리 없이", "이벤트 기반", "코드만", "짧게 실행"**.

**AWS Fargate** — **서버리스 컨테이너 컴퓨팅 엔진**.
- **ECS·EKS와 함께** 사용해, **EC2 인스턴스 클러스터를 관리하지 않고** 컨테이너를 실행. 서버 유형 선택·확장 시점·클러스터 패킹 고민이 사라짐.
- 키워드: **"서버리스 컨테이너", "클러스터 관리 없이 컨테이너"**.

> 한눈에: **Lambda = 서버리스 *함수*(이벤트·코드). Fargate = 서버리스 *컨테이너*(ECS/EKS의 서버 관리 제거).**

### 4) 탄력성 — Amazon EC2 Auto Scaling

**Amazon EC2 Auto Scaling**은 애플리케이션 부하를 처리할 **올바른 수의 EC2 인스턴스**를 유지합니다.

- **Auto Scaling 그룹**에 최소(min)·최대(max)·원하는 용량(desired)을 정하면, 정의한 **조건(스케일링 정책)에 따라 인스턴스를 자동으로 추가/제거**합니다.
- 수요가 늘면 용량을 더하고 줄면 빼서 — **가용성을 유지하고 비용을 절감**합니다. 이것이 클라우드의 **탄력성(elasticity)**입니다.
- 건강 검사로 손상된 인스턴스를 자동 교체하고, **여러 AZ에 균등 분산**해 고가용성도 높입니다.

> 시험 신호: **"수요 변화에 맞춰 자동으로 늘리고 줄인다 / 탄력성"** → EC2 Auto Scaling.

### 5) 트래픽 분산 — Elastic Load Balancing(ELB)

**Elastic Load Balancing(ELB)**은 **들어오는 트래픽을 여러 대상(EC2·컨테이너·IP)에 자동으로 분산**합니다(하나 이상의 AZ에 걸쳐).

- 등록된 대상의 **상태를 검사해 건강한 대상에만** 트래픽을 보냅니다 → **가용성·내결함성 증가**.
- 트래픽 변화에 따라 **자동으로 확장**됩니다.
- **Auto Scaling + ELB**는 단짝: Auto Scaling이 인스턴스를 늘리면 ELB가 자동으로 등록해 트래픽을 고르게 보냅니다.

| 로드 밸런서 유형 | 처리 계층 | 용도 |
|---|---|---|
| **Application Load Balancer(ALB)** | L7 | HTTP/HTTPS 웹 트래픽 |
| **Network Load Balancer(NLB)** | L4 | TCP/UDP, 초고성능·저지연 |
| **Gateway Load Balancer(GWLB)** | L3/4 | 서드파티 가상 어플라이언스(방화벽 등) |

### 6) 한눈에 — 관리 부담 스펙트럼

```
많이 관리(제어 큼)  ←──────────────────────────────→  적게 관리(AWS가 더)
   EC2            ECS/EKS (on EC2)        Fargate            Lambda
 가상 서버         컨테이너 클러스터      서버리스 컨테이너    서버리스 함수
 OS·확장 직접      EC2 관리 필요          서버 관리 없음       코드만(이벤트)
```

> 고르는 법: **OS·환경을 완전히 제어해야** → EC2. **컨테이너**를 쓰는데 서버 관리는 싫다 → **Fargate**. **이벤트에 짧게 반응하는 코드** → **Lambda**. **Kubernetes** 표준이 필요 → **EKS**.

## ✍️ 시험 포인트

- **EC2** = 클라우드의 *가상 서버*. **인스턴스 유형** = 용도별(컴퓨팅/메모리/스토리지 최적화) 하드웨어 균형.
- **"서버를 관리하고 싶지 않다 + 이벤트로 코드 실행"** → **Lambda**(서버리스 함수, 사용한 시간만 과금).
- **"컨테이너인데 서버/클러스터 관리는 싫다"** → **Fargate**(서버리스 컨테이너). **"Kubernetes"** → **EKS**.
- **"수요에 맞춰 인스턴스 자동 증감 / 탄력성"** → **EC2 Auto Scaling**.
- **"트래픽을 여러 인스턴스에 분산 / 가용성"** → **ELB**. 웹(HTTP)=ALB, TCP/UDP=NLB.
- **Auto Scaling(탄력성) + ELB(분산) + 멀티 AZ(고가용성)**는 함께 다니는 3종 세트.

---

## ⚠️ 흔한 함정

1. **"서버리스는 서버가 아예 없다는 뜻이다."** → ❌. 서버는 있지만 **내가 프로비저닝·관리하지 않습니다**(AWS가 처리). 그래서 *서버리스*.
2. **"Lambda로 24시간 계속 도는 서버를 운영한다."** → ⚠️ 부적합. Lambda 함수는 *이벤트에 반응해 짧게* 실행(한 번에 최대 15분). 상시 가동 서버라면 EC2/컨테이너가 보통 적합.
3. **"컨테이너를 쓰면 무조건 EC2를 직접 관리해야 한다."** → ❌. **Fargate**를 쓰면 EC2 클러스터 관리 없이 컨테이너를 실행합니다.
4. **"ECS와 EKS는 같다."** → ❌. **EKS는 Kubernetes** 관리형 서비스. 보기에 "Kubernetes"면 EKS.
5. **"Auto Scaling이 트래픽을 분산한다."** → ❌. *인스턴스 수를 조절*하는 건 Auto Scaling, *트래픽을 분산*하는 건 **ELB**. (둘은 함께 쓰임)
6. **"로드 밸런서는 인스턴스를 늘려 준다."** → ❌. ELB는 *분산*만, *증감*은 Auto Scaling.

**Q1.** "서버를 프로비저닝하거나 관리하지 않고, 이미지 업로드 같은 이벤트에 반응해 짧게 코드를 실행하고, 실행한 시간만큼만 비용을 내고 싶다." 어떤 서비스인가요?

<details><summary>정답 보기</summary>

**AWS Lambda**(서버리스 함수). 서버·OS·확장을 AWS가 관리하고, 이벤트에 반응해 코드를 실행하며, 사용한 컴퓨팅 시간만큼만 과금합니다.
</details>

**Q2.** 컨테이너로 앱을 운영하려는데 EC2 인스턴스 클러스터를 직접 관리하고 싶지 않습니다. 그리고 표준 Kubernetes가 필요하면?

<details><summary>정답 보기</summary>

서버 관리 없이 컨테이너를 실행하려면 **AWS Fargate**(서버리스 컨테이너 엔진, ECS·EKS와 함께). 표준 **Kubernetes**가 필요하면 **Amazon EKS**(관리형 Kubernetes)를 씁니다.
</details>

**Q3.** 웹 애플리케이션의 수요가 시간대별로 크게 변합니다. 인스턴스 수를 자동으로 늘리고 줄이려면? 그리고 그 인스턴스들에 트래픽을 고르게 나눠 주려면?

<details><summary>정답 보기</summary>

인스턴스 수 자동 증감(탄력성)은 **EC2 Auto Scaling**, 트래픽을 여러 인스턴스에 분산하는 것은 **Elastic Load Balancing(ELB)**. 둘은 함께 쓰여 탄력성과 고가용성을 만듭니다.
</details>

**Q4.** EC2와 Lambda의 가장 큰 차이를 "관리 부담" 관점에서 한 문장으로?

<details><summary>정답 보기</summary>

**EC2**는 가상 서버로 OS·확장 등 *많은 부분을 고객이 관리*합니다. **Lambda**는 서버를 *전혀 관리하지 않고* 코드만 올리면 AWS가 실행·확장·유지보수를 처리합니다(서버리스).
</details>
